# Interview Guide: Design a URL Shortener (TinyURL)

## 🗣️ The Interview Scenario

> "Design a URL shortening service like TinyURL or the link shortener LinkedIn uses on posts. I'll give you the traffic numbers as we go — start with requirement gathering, and don't just tell me you'll use a hash function; tell me *why* or why not, and how you'd guarantee no two users ever collide on the same short code across a fleet of servers."

This question sounds simple on the surface, but the interviewer is really testing whether you can derive a length/encoding scheme from real numbers, and whether you understand distributed unique-ID generation — the actual hard part of this problem.

## 🏗️ Architect's Explanation (For a New Developer)

At its heart, a URL shortener is just a lookup table: `short_code -> long_url`. A `POST` request comes in with a long URL, the service computes a short code, stores the pair, and returns the short URL. A `GET` request with the short code looks up the row and redirects to the long URL. That part is easy.

The genuinely hard engineering problem hiding underneath is: **how do you generate a short code that is (a) short enough, (b) never collides with another code, and (c) can be generated by many servers at once without them stepping on each other?** That last part is the real system-design meat of this question — it's fundamentally a **distributed unique ID generation** problem wearing a URL-shortener costume.

Think of it like a parking garage with multiple entrance booths. If every booth just prints ticket numbers 1, 2, 3... independently, two cars from two different booths will get ticket #47 at the same time — a collision. You either need one central ticket dispenser (which becomes a bottleneck and a single point of failure), or you hand each booth its **own pre-assigned range of ticket numbers** so they never overlap and never need to talk to each other for every single ticket.

## 📊 Visualize It

**End-to-end request flow:**

```
User --POST long_url--> Load Balancer --> TinyURL App Servers (per data center)
                                              |         |
                                        talks to     Cache + Relational DB
                                        Zookeeper     (id | short_url | long_url)
                                        for a unique
                                        range/ID
                                              |
User <--GET short_url-- Load Balancer <------+  (DB lookup: short_url -> long_url)
```

**Zookeeper range partitioning (the core trick):**

```
Total space: 62^7 ≈ 3.5 trillion possible 7-char codes

Range 1: 0        - 1,000,000     -> assigned to Worker Thread 1
Range 2: 1,000,000 - 2,000,000     -> assigned to Worker Thread 2
Range n: 11,000,000 - 12,000,000   -> assigned to Worker Thread n

Each worker only hands out IDs from ITS OWN range -> zero collisions,
zero need to coordinate on every single request.
When a worker exhausts its range, Zookeeper hands it a fresh unused range.
```

## 🔧 Deep Dive: How It Actually Works

### 1. Requirement gathering — deriving the length mathematically
- First clarifying question: **"How short should the URL be?"** Interviewer answer: "as short as possible" — which forces you to actually compute a number instead of guessing.
- Traffic assumption: **10 million URLs/day**. Requirement: the service must support this for **100 years** without running out of codes.
  - `10,000,000 × 365 × 100 = 365,000,000,000` → **365 billion** URLs must be supportable.
- Allowed character set: `0–9`, `a–z`, `A–Z` → `10 + 26 + 26 = 62` characters.
- Combinatorics per code length:
  - `62^6 ≈ 56 billion` — **not enough** (need 365 billion).
  - `62^7 ≈ 3.5 trillion` — comfortably enough.
- **Conclusion: 7-character short codes.** This is the single most important derived number in the whole design — always show the arithmetic in an interview rather than quoting "7" from memory.

### 2. Why hash functions (MD5/SHA-1) are rejected
- MD5 is a 128-bit hash → 16 bytes → since each hex digit represents a nibble (4 bits) and a byte is 8 bits, 16 bytes → **32 hex characters**.
- SHA-1 is 160-bit → 20 bytes → **40 hex characters**.
- Both are far longer than the 7 characters required. Truncating to the first 7 characters to force the length down **reintroduces collisions**: two different long URLs can easily share the same first 7 hex characters while differing later, producing duplicate short codes for different destinations. This is why hash-and-truncate is explicitly rejected as an approach.

### 3. Base62 encoding — how it actually works
- Any decimal number can be converted into another base. Base62 uses all 62 allowed characters as "digits": `0–9` = 0–9, then `a`=10, `b`=11, `c`=12 ... continuing through the alphabet up to 61.
- Worked example from the walkthrough: converting the decimal number **1000** to base62:
  - `1000 ÷ 62 = 16` remainder `8`.
  - `16` in base62 is the digit `g` (since `a`=10, `b`=11, `c`=12, `d`=13, `e`=14, `f`=15, `g`=16).
  - Reading from the last quotient to the remainder gives `g8` as the base62 representation of 1000.
- This means: **generate a unique numeric ID first, then base62-encode it** to get the short code.

### 4. Padding and the length guarantee
- A small numeric ID (like the example `16` → `g`) encodes to fewer than 7 base62 characters. Since the requirement is a consistent 7-character code, short results are **padded** to reach exactly 7 characters (conceptually similar to padding seen in Base64 encoding).
- Can base62 encoding of a valid ID ever exceed 7 characters? No — because the ID generator is constrained to only ever hand out numbers within the `0` to `62^7` (≈3.5 trillion) range, the base62 representation is mathematically guaranteed to fit within 7 characters (the maximum being the base62 equivalent of `zzzzzzz`).

### 5. The real hard problem: distributed unique ID generation
The walkthrough explicitly frames this as a standalone, important interview question: **"How do you generate a unique ID in a distributed environment?"** Three approaches are compared:

- **Single auto-increment DB column:** Works for a toy example, but at 10 million requests/day you cannot serve everything from one DB server — you need multiple, distributed DB servers. That immediately creates a **synchronization problem** (two servers must never generate the same ID) and a **single point of failure** (if the one ID-generating DB goes down, the whole system stops).
- **Ticket Server:** A centralized auto-increment service that all distributed app servers call into for a new ID. It solves synchronization by centralizing it — but reintroduces the exact same single-point-of-failure problem: if the ticket server goes down, every app instance relying on it is impacted.
- **Snowflake (Twitter's approach):** Timestamp-based ID composed of reserved bit segments — a timestamp portion (example given: 41 bits), a machine ID portion (uniquely identifies the generating machine), and a sequence number portion (a counter that increments within the same timestamp, wrapping back to 0 once its bit-length limit is reached). Because it doesn't depend on a central server, it avoids the single-point-of-failure problem, and uniqueness comes from the combination of timestamp + machine ID + sequence.
- **Zookeeper (the preferred approach for this problem):** Zookeeper is defined as a distributed coordination service — it lets distributed applications coordinate reliably. Instead of generating IDs itself, it **partitions the total ID space (≈3.5 trillion, i.e., `62^7`) into ranges** (e.g., 0–1,000,000, 1,000,000–2,000,000, etc.) and **assigns each range to a specific worker thread/app server**. Each worker only draws IDs from its own assigned range — no cross-server coordination is needed per request, and there's no collision risk. When a worker exhausts its range, Zookeeper simply hands it the next unused range. Because the total space (3.5 trillion) is so much larger than the actual requirement (365 billion), it's an acceptable trade-off if a chunk of a range goes unused (e.g., low traffic on a given worker) — there's ample headroom.

### 6. High-level architecture
- **Client → Load Balancer → TinyURL app servers**, organized per data center (multiple data centers supported).
- Each data center has its own **cache + database** layer.
- Because the schema is a single simple table (`id | short_url | long_url`) with **no complex joins**, a **relational DB** is explicitly chosen here — this is a deliberate, simple table design, not a big-data/NoSQL problem.
- The application layer talks to **Zookeeper** to obtain a unique ID (from its assigned range), base62-encodes it (padding if needed), and persists the `short_url -> long_url` mapping.
- No CDN is required for this design — the problem is intentionally scoped to be simple past the ID-generation piece; the interviewer's real interest is almost always concentrated on *how the short code gets generated uniquely*, not the rest of the plumbing.

## 🔥 Real Production Incident & Fix

**What broke:** An early version of the shortener used a single centralized "Ticket Server" (a plain auto-increment counter service) to hand out numeric IDs to all app servers before base62-encoding them. During a marketing campaign traffic spike, the ticket server's CPU and connection pool saturated, causing p99 latency on `POST /shorten` to jump from ~40ms to over 4 seconds, and eventually the ticket server itself became unresponsive — taking URL creation down for the entire fleet even though every app server and DB shard was otherwise healthy.

**How it was detected/diagnosed:** APM traces showed every app server's request latency bottlenecked on a single downstream call — the ticket server RPC — while DB and cache latencies stayed flat. A quick look at the ticket server's own connection count graph showed it pinned at its max pool size, with request queueing climbing linearly. Because it was one logical service (even if replicated for read availability, writes were still serialized through one counter), it was a textbook single point of failure/bottleneck.

**Root cause:** Every single ID request — across every app server, in every data center — had to synchronously round-trip to one centralized auto-increment service. There was no way to distribute that write load, because correctness (no duplicate IDs) depended entirely on serializing through that one component.

**The fix:** The ticket server was replaced with **Zookeeper-based range partitioning**: each app server (worker) is handed a dedicated block of, e.g., 1 million IDs at startup and only calls back to Zookeeper once that block is exhausted — turning a "call a central service on every request" problem into "call a central service roughly once per million requests." Post-fix, `POST /shorten` p99 latency dropped to single-digit milliseconds even under 5x the original campaign traffic, because ID generation became a local, in-memory operation for the vast majority of requests.

```
BEFORE (Ticket Server, every request):        AFTER (Zookeeper ranges, rare calls):

App1 --\                                       App1 (owns range 1M-2M) -> local counter
App2 ---> Ticket Server (bottleneck) -> DB     App2 (owns range 2M-3M) -> local counter
App3 --/                                       App3 -> ... only calls Zookeeper
   (every single request hits one component)      when its range is exhausted
```

## ❓ Likely Interview Follow-Up Questions & Answers

**Q1: Why not just use MD5 or SHA-1 and take the first 7 characters?**
Both generate much longer digests (32 hex characters for MD5, 40 for SHA-1) than the 7 characters required, so you'd have to truncate. Truncation throws away entropy and lets two different long URLs collide on the same first 7 characters, producing duplicate short codes for different destinations — which silently corrupts the mapping. That's why base62-encoding a guaranteed-unique numeric ID is preferred over hash truncation.

**Q2: Walk me through exactly why you chose 7 characters and not 6 or 8.**
With 62 allowed characters, 6-character codes give `62^6 ≈ 56 billion` combinations, which is short of the 365 billion required for 10M URLs/day over 100 years. 7-character codes give `62^7 ≈ 3.5 trillion`, comfortably above requirement. You always pick the smallest length that clears the required capacity, since shorter is the explicit design goal.

**Q3: If the same long URL is submitted twice, should it get the same short code or a different one?**
This wasn't explicitly decided in the walkthrough's base design (it generates a new unique ID per POST regardless of URL content), but a natural follow-up improvement is to first check if the long URL already has a mapping (e.g., via a reverse index or a hash of the long URL) and return the existing short code, avoiding duplicate rows for identical inputs — this is a common enhancement to raise if asked.

**Q4: Why is Zookeeper preferred over the Snowflake approach here?**
Both solve distributed unique ID generation without a central bottleneck. Snowflake bases uniqueness on timestamp + machine ID + sequence bits and requires no coordination service at request time, but needs careful clock-sync and machine-ID management. Zookeeper's range-partitioning approach was preferred in this design because it directly maps onto the base62 numeric-ID space (0 to 62^7) and keeps the "worker owns a contiguous block, refills when exhausted" model simple to reason about and monitor.

**Q5: What happens if Zookeeper itself becomes unavailable?**
Because each worker is handed a large block of IDs upfront (e.g., a million at a time) rather than calling Zookeeper per-request, a short Zookeeper outage doesn't stop ID generation — workers keep consuming their already-assigned range. The failure mode only bites if a worker exhausts its range and Zookeeper is unavailable to hand out the next one, which is why block sizes and Zookeeper's own availability need to be tuned together.

**Q6: How would you extend this design to support custom aliases (vanity URLs) or expiration?**
Custom aliases require checking the requested alias for availability against the DB before insert (a uniqueness constraint on `short_url`), bypassing the ID-generation path entirely for that request. Expiration would add a `expires_at` column and either a background sweep job or a check at redirect-time (`GET`) that returns a "link expired" response instead of redirecting once the timestamp has passed.

## 🔑 Key Takeaway

Say this out loud in the interview: **"The interesting part of designing a URL shortener isn't the encoding — it's generating a globally unique ID across a distributed fleet without a single point of failure. Base62-encoding a range-partitioned ID (e.g., via Zookeeper) solves both the collision problem and the bottleneck problem at once."**
