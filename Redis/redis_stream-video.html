Redis Streams

Build a replayable, consumer-group-based workflow without blocking the request path. We will use voucher verification as the production scenario.

XADDConsumer groupsPELXAUTOCLAIMIdempotency
Scenario

20,000 voucher requests per minute, slow partner verification

“I do not let the API wait for partner verification. The API validates the request, records an idempotent acceptance, and appends a work event. A consumer group performs the slow work. The key invariant is: one voucher request produces at most one business outcome, even if delivery happens more than once.”

Failure conditions

  • Client retries after network timeout.
  • Worker crashes after partner success, before acknowledgement.
  • One consumer is slow while others are idle.
  • Retained stream data consumes memory.

Design goals

  • Fast acceptance and observable status.
  • At-least-once work recovery.
  • Idempotent partner and database effects.
  • Bounded backlog and retention.
Architecture

Big picture: API, stream, consumer group, durable business state

+----------------+ +--------------------+ +----------------------+ | Client / POS | ---> | Voucher API | ---> | Redis Stream | | retry-safe key | | validate + accept | XADD | voucher-events | +----------------+ +---------+----------+ +----------+-----------+ | | v v +------------------+ +----------------------+ | Postgres | | Group: verifiers | | request / result | | worker-a, worker-b | +------------------+ +----------+-----------+ | v Partner verification API
Why this architecture: Redis coordinates short-lived asynchronous delivery; Postgres owns business truth and idempotency. The consumer group scales workers without sending the same new entry to every worker in that group.
Stream model

Stream IDs, entries, and ordering

voucher-events 1710000000000-0 voucherId=V-101 tenantId=acme amount=200 requestId=req-42 1710000000450-0 voucherId=V-102 tenantId=acme amount=300 requestId=req-43 1710000000450-1 voucherId=V-103 tenantId=globex amount=150 requestId=req-44 milliseconds - sequence 1710000000450-1
Why IDs matter: the ID gives the ordering of entries in this stream and lets consumers request ranges. It is not a global business idempotency key. Use `requestId` or a unique database constraint for an external side effect.
Core commands

Append, read, and keep retention explicit

XADD voucher-events * voucherId V-101 amount 200 requestId req-42 XREAD BLOCK 5000 COUNT 10 STREAMS voucher-events $ XGROUP CREATE voucher-events voucher-verifiers $ MKSTREAM XTRIM voucher-events MAXLEN ~ 100000

How I explain these live

  • XADD: append a field/value event and let Redis generate the ID.
  • XREAD: independent simple reader; `$` means entries after the read starts.
  • XGROUP: establish a competing-consumer group.
  • XTRIM: control memory separately from acknowledgement.
Why retention is explicit: `XACK` only removes a PEL record. It does not remove the stream entry. Memory sizing must include entries, consumer groups, pending work, and the recovery window.
Consumer group

Pending Entries List: delivery is not completion

Producer --- XADD ---> voucher-events --- XREADGROUP ---> worker-a | delivery creates PEL entry | | | v | process side effect | | +----- XACK after success ----------+ worker-a crashes ---> XPENDING ---> XAUTOCLAIM idle entry ---> worker-b
Why the PEL exists: it lets Redis distinguish “never delivered” from “delivered but not acknowledged.” `XAUTOCLAIM` recovers abandoned work. Choose idle time above normal processing duration or healthy slow workers can be processed twice.
ER relationship diagram

Business record, event record, and consumer attempt

+---------------------+ 1 * +--------------------------+ | voucher_request |------------>| voucher_processing_event | | request_id (PK) | | event_id (PK) | | idempotency_key | | redis_stream_id | | voucher_id, status | | request_id (FK) | +----------+----------+ +-------------+------------+ | 1 | 1 * * +----------+----------+ +-------------+------------+ | verification_result | | consumer_attempt | | request_id (FK) | | stream_id, consumer | | partner_reference | | delivery_count, outcome | +---------------------+ +--------------------------+
Why an ER model when Redis is not relational: Redis handles delivery; the database provides audit, reconciliation, and business idempotency after a stream entry is trimmed or a partner dispute occurs.
Sequence diagram

Commit the business result before acknowledgement

Client Voucher API Postgres Redis Stream Worker Partner | POST /verify | | | | | |-------------->| dedupe | | | | | | INSERT accepted |--------------->| | | | | XADD event |------------------------------->| | |<--------------| 202 + requestId | | | | | | | | XREADGROUP | | | | | |--------------->| verify | | | | UPDATE result | |----------->| | | |<--------------------------------| XACK |
Why this sequence: if the worker crashes before `XACK`, it is safe to retry because the business write and partner call use `requestId` idempotently. If you acknowledge first, a crash can lose the work forever.
API design

Accept work quickly and expose status

POST /api/v1/voucher-verifications Idempotency-Key: checkout-987-voucher-1 X-Correlation-Id: trace-abc { "voucherId": "V-101", "amount": 200 } 202 Accepted { "requestId": "req-42", "status": "PENDING" } GET /api/v1/voucher-verifications/req-42

Purpose of each decision

  • 202: verification is long-running; HTTP does not pretend it is complete.
  • Idempotency key: protects client retries at the intake boundary.
  • Correlation ID: ties API logs to stream ID and worker attempts.
  • Status endpoint: provides recovery when client connection fails.
Java implementation

Spring Boot consumer: durable effect, then acknowledge

public void process(MapRecord<String, Object, Object> message) { VoucherEvent event = mapper.toEvent(message); verificationService.verifyIdempotently(event.requestId()); redisTemplate.opsForStream() .acknowledge("voucher-verifiers", message); } // Recover idle messages in a scheduled, bounded task. redisTemplate.opsForStream().autoClaim( "voucher-verifiers", "worker-b", Duration.ofMinutes(1), "0-0");
Why this implementation shape: acknowledgement is last. The service must persist a unique `requestId` outcome so a claimed message cannot charge, credit, or verify twice. Use bounded batches and timeouts; a growing stream is not a reason for unbounded threads.

Senior traps

15-YOE trap questions with model answers

“Does `XACK` delete the message?”
No. It removes the message from this group’s Pending Entries List. Stream retention is an independent decision using `XTRIM`, `MAXLEN`, or `MINID`.
“Does a consumer group give exactly-once processing?”
No. A worker can finish a side effect and fail before acknowledgement. Make the database write and partner call idempotent using `requestId`.
“Why not set `XAUTOCLAIM` idle time to five seconds?”
Because a healthy partner call may run longer than five seconds. The entry would be claimed while the original worker is still active. Set the threshold from observed tail latency plus safety margin.
Live interview script

How a strong architect closes the Redis Streams discussion

“I choose Redis Streams for a low-latency, replayable workflow when the required retention and throughput fit Redis. The API accepts requests idempotently and returns `202`. It persists the business request, then an outbox relay appends the event. Consumer-group workers process it and acknowledge only after the business result is durable. I monitor consumer lag, PEL size, idle pending entries, delivery count, memory, and trim age. `XAUTOCLAIM` recovers abandoned work, but idempotency protects the external effect. If I need long replay, very high throughput, or a broad event platform, I choose Kafka.”
