# Redis Streams: Production Guide and 15-YOE Interview Script

## Scenario

**Interviewer:** "A voucher-verification API receives 20,000 requests per minute during a sale. Verification can call a slow partner system. How would you avoid blocking the API, losing requests, or processing a voucher twice?"

**Strong answer:** "I would accept the request quickly, write a durable processing record, and append an event to a Redis Stream. A consumer group distributes verification work across workers. Each worker acknowledges a message only after the partner call and database update succeed. If a worker dies, another worker claims its idle pending message."

```text
Client -> Voucher API -> Redis Stream -> Consumer Group -> Verification Workers
                 |                            |                    |
                 v                            v                    v
            Postgres request              Pending Entries       Partner API
            + idempotency key                 List              + result update
```

**Why Redis Streams?** The API is fast because it does not wait for the slow work. Unlike Redis Pub/Sub, a stream keeps entries for replay and exposes pending work. Unlike a plain list, it provides consumer groups, message IDs, acknowledgements, and idle-message recovery.

## What a Redis Stream Is

A Redis Stream is an append-only log stored at a Redis key. Each entry has:

- A stream ID, normally generated by Redis as `milliseconds-sequence`, for example `1710000000000-0`.
- Field/value pairs, for example `voucherId=V-101`, `amount=200`, `tenantId=acme`.
- Retention controlled by explicit trimming or approximate max length.

The ID orders entries within one stream. It is not a global transaction ID and must not be used as the only idempotency key for an external side effect.

```text
voucher-events
  1710000000000-0  voucherId=V-101 amount=200 tenantId=acme
  1710000000450-0  voucherId=V-102 amount=300 tenantId=acme
  1710000000450-1  voucherId=V-103 amount=150 tenantId=globex
```

### Why this design

The API owns request validation and idempotency. Redis Streams owns short-to-medium-lived delivery and worker coordination. Postgres remains the durable system of record for voucher status and the idempotency result. The worker owns the side effect and calls `XACK` only after the durable status update succeeds.

## Core Commands

### Append an event: `XADD`

```bash
XADD voucher-events * voucherId V-101 tenantId acme amount 200 requestId req-42
```

Use `*` so Redis creates the ID. The response is the entry ID.

### Read history or new entries: `XREAD`

```bash
XREAD COUNT 10 STREAMS voucher-events 0-0
XREAD BLOCK 5000 COUNT 10 STREAMS voucher-events $
```

`0-0` reads from the beginning. `$` waits for entries added after the command begins. `XREAD` is useful for simple independent readers, not competing workers.

### Create a consumer group: `XGROUP CREATE`

```bash
XGROUP CREATE voucher-events voucher-verifiers $ MKSTREAM
```

`$` starts the group at new entries. Use `0-0` only when the group must process retained history.

### Consume as a group: `XREADGROUP`

```bash
XREADGROUP GROUP voucher-verifiers worker-a \
  BLOCK 5000 COUNT 10 STREAMS voucher-events >
```

`>` means entries never delivered to another consumer in this group. The delivery creates or updates a Pending Entries List (PEL) record.

### Acknowledge only after success: `XACK`

```bash
XACK voucher-events voucher-verifiers 1710000000000-0
```

**Production correction:** `XACK` removes the entry from the consumer group's PEL. It does **not** delete the entry from the stream. Retention is managed independently with `XTRIM`, `MAXLEN`, or `MINID`.

### Inspect and recover pending work

```bash
XPENDING voucher-events voucher-verifiers
XAUTOCLAIM voucher-events voucher-verifiers worker-b 60000 0-0 COUNT 20
```

`XAUTOCLAIM` transfers messages idle for at least 60 seconds to `worker-b`. Choose idle time above the longest expected processing time, otherwise a slow healthy worker and the claimant can both process the same message.

### Retention

```bash
XADD voucher-events MAXLEN ~ 100000 * voucherId V-104 amount 250
XTRIM voucher-events MINID ~ 1710000000000-0
```

Approximate trimming (`~`) is faster but does not guarantee the exact count. Never trim an entry before all consumer groups that need it have processed it.

## ER Relationship Diagram

Redis Streams is not relational, but a production design still has an ownership model:

```text
+---------------------+  1       *  +--------------------------+
| voucher_request     |------------>| voucher_processing_event |
| request_id (PK)     |             | event_id (PK)            |
| idempotency_key     |             | redis_stream_id          |
| voucher_id          |             | request_id (FK)          |
| status              |             | event_type, created_at   |
+----------+----------+             +-------------+------------+
           | 1                                      |
           |                                        | 1
           *                                        *
+----------+----------+             +-------------+------------+
| verification_result |             | consumer_attempt          |
| request_id (FK)     |             | stream_id, consumer       |
| partner_reference   |             | delivery_count, outcome   |
+---------------------+             +--------------------------+
```

### Why persist this separately from Redis

The stream is delivery infrastructure. Postgres records the business truth: whether voucher `V-101` was accepted, rejected, or requires review. This model also lets an operator prove what happened after stream retention has removed the entry.

## Sequence Diagram

```text
Client       Voucher API        Postgres        Redis Stream        Worker       Partner
  | POST /verify  |                 |                |                |            |
  |-------------->| idempotency     |                |                |            |
  |               | INSERT accepted |--------------->|                |            |
  |               | XADD event      |------------------------------->|            |
  |<--------------| 202 + requestId |                |                |            |
  |               |                 |                | XREADGROUP     |            |
  |               |                 |                |--------------->| verify     |
  |               |                 |                |                |----------->|
  |               |                 | UPDATE result  |                |<-----------|
  |               |                 |<--------------------------------| XACK       |
```

### Why this order matters

If the API writes to Postgres but crashes before `XADD`, the request is accepted but never processed. In a high-value system, use a transactional outbox in Postgres and a relay that performs `XADD`. If a worker crashes after the partner succeeds but before `XACK`, the event can be delivered again. The partner call and database write must use `requestId` as an idempotency key.

## Spring Boot Implementation Shape

```java
public record VoucherEvent(String requestId, String voucherId, BigDecimal amount) {}

@Transactional
public AcceptedResponse accept(VerifyVoucherCommand command, String idempotencyKey) {
    VoucherRequest request = requests.insertIfAbsent(command, idempotencyKey);
    outbox.save(VoucherAcceptedEvent.from(request));
    return new AcceptedResponse(request.id(), request.status());
}

public void process(MapRecord<String, Object, Object> message) {
    VoucherEvent event = mapper.toEvent(message);
    verificationService.verifyIdempotently(event);
    redisTemplate.opsForStream().acknowledge("voucher-verifiers", message);
}
```

The consumer should use a bounded executor, batch reads, explicit timeouts, and a retry policy. Do not create unbounded worker threads just because the stream is growing.

## Technology Choices

### Redis Streams vs Redis Pub/Sub

| Question | Redis Streams | Redis Pub/Sub |
|---|---|---|
| History | Retained until trimmed | Fire and forget |
| Consumer recovery | PEL, `XACK`, `XAUTOCLAIM` | Subscriber misses messages while offline |
| Choose when | Work queue, replay, audit window | Live UI updates where loss is acceptable |
| Example 1 | Voucher verification | Typing indicator |
| Example 2 | Image-processing jobs | Dashboard refresh hint |

### Redis Streams vs Kafka

| Question | Redis Streams | Kafka |
|---|---|---|
| Best fit | Low-latency workflow near existing Redis | High-throughput durable event platform |
| Operations | Simpler for an existing Redis estate | Partitions, brokers, retention, ecosystem |
| Choose when | Short retention, moderate fan-out, operational simplicity | Long replay, many consumers, large throughput |
| Example 1 | Cart-expiry worker queue | Order-event analytics history |
| Example 2 | Session cleanup jobs | Fraud model training pipeline |

## Trade-offs

- **Consumer group:** distributes work, but each group has its own PEL and retention needs.
- **At-least-once delivery:** recovers worker failures, but requires idempotent side effects.
- **Long retention:** helps debugging and replay, but consumes Redis memory.
- **Blocking reads:** reduce polling, but consumers still need a graceful shutdown and timeout.
- **`XAUTOCLAIM`:** recovers abandoned work, but a too-small idle threshold creates duplicate processing.

## Senior Trap Questions

### "Does `XACK` delete the message?"

No. It removes the entry from that consumer group's PEL. Use `XDEL` or trimming to remove stream entries, with careful consideration for other consumer groups.

### "Can Redis Streams guarantee exactly-once processing?"

No. Delivery is at-least-once. A worker can complete an external side effect and fail before `XACK`. Use a business idempotency key, a unique database constraint, and idempotent partner APIs.

### "Why not use `XREADGROUP ... >` to recover pending messages?"

`>` reads never-delivered entries only. Pending entries require `XPENDING`, `XCLAIM`, or preferably `XAUTOCLAIM`.

### "What happens if you trim a pending entry?"

The PEL can reference an entry whose payload no longer exists. Redis can report a deleted ID; your recovery code must handle it. Size retention from the maximum processing time, retry window, and consumer-group lag.

## Interview Close

## Scenario-Based Practice Questions

1. **A payment-retry queue needs replay for audit, but Redis Pub/Sub subscribers report missing messages after redeploys. What do you change?**
   Move the workflow to a Redis Stream with a consumer group. Pub/Sub only delivers to currently connected subscribers; a Stream retains entries so a redeployed consumer can resume from its last unacknowledged ID via `XREADGROUP ... >` and recover idle work with `XAUTOCLAIM`.

2. **Two workers in the same consumer group both call the partner API for the same voucher. What is missing from the design?**
   Idempotency. Delivery is at-least-once, so a retry or an aggressive `XAUTOCLAIM` idle threshold can hand the same entry to a second worker. The partner call and the database write must be idempotent using a stable key such as `requestId`, not the stream ID.

3. **A teammate proposes calling `XDEL` right after `XACK` to "keep the stream clean." What risk does this introduce?**
   `XACK` only clears the entry from one consumer group's PEL; other consumer groups may still need that entry. Deleting it immediately can break replay or audit for those groups. Retention should follow an `XTRIM`/`MAXLEN`/`MINID` policy sized for every consumer group's lag, not for a single group's acknowledgement.

4. **`XAUTOCLAIM` idle time is set to 5 seconds to "recover failures fast," but healthy workers now double-process messages. Why, and how do you fix it?**
   The partner call sometimes takes longer than 5 seconds, so a still-healthy worker is treated as dead and its message is claimed by another worker. Set the idle threshold above the observed p99 processing time plus a safety margin.

5. **Product asks whether Redis Streams can guarantee a voucher is verified exactly once. How do you respond?**
   No mechanism in Redis Streams gives exactly-once delivery; it is at-least-once. Exactly-once *effects* are achieved at the application layer with an idempotency key and a unique database constraint, not by the stream itself.

6. **The team must choose between Redis Streams and Kafka for an event feed that must be replayed for 90 days by a dozen independent analytics consumers. Which do you pick, and why?**
   Kafka. Long retention, many independent consumer groups, and high throughput fit Kafka's partitioned log and operational model better than Redis, where that much retained data becomes memory-expensive.

7. **A consumer crashes mid-batch after writing to Postgres but before calling `XACK`. What happens to that entry, and is that acceptable?**
   The entry stays in the PEL as pending and is redelivered once judged idle (via `XCLAIM`/`XAUTOCLAIM` or a fresh `XREADGROUP`). This is acceptable only if the Postgres write is idempotent, so redelivery does not double-apply the effect.

8. **How would you size the memory and retention window for one Redis Stream feeding three consumer groups with different processing speeds?**
   Retention must cover the slowest consumer group's maximum expected lag plus its recovery window, not the fastest one. Track PEL size and consumer lag per group, and base `MAXLEN`/`MINID` trimming on the slowest group.

9. **Why would an architect prefer `XREADGROUP ... BLOCK` over polling with `XRANGE` in a loop?**
   Blocking reads avoid needless round trips when new entries are infrequent while still returning immediately once data arrives. A polling loop wastes calls when the stream is idle and adds a fixed poll-interval delay.

10. **A stream entry's payload is missing when a claimed message is processed. What could have happened, and how should the consumer behave?**
    A trim (`XTRIM`/`MAXLEN`/`MINID`) or an `XDEL` removed the entry from the stream while it was still referenced in a group's PEL. The consumer should handle the missing-entry case defensively (log, alert, acknowledge without reprocessing) instead of crashing.

11. **Why is the stream entry ID (`milliseconds-sequence`) unsafe to use as the sole idempotency key for an external side effect?**
    The ID only orders entries within that stream; it says nothing about business identity and can be regenerated in replay or migration scenarios. A separate business key such as `requestId`, tied to a unique database constraint, is required.

"I use Redis Streams when I need a low-latency append-only event log with recoverable consumer groups and my operational retention window fits Redis. The API accepts idempotently, the worker commits the business result before `XACK`, abandoned work is recovered with `XAUTOCLAIM`, and retention is configured from actual backlog and recovery requirements. For long replay, very high throughput, or broad independent consumption, I would choose Kafka instead."
