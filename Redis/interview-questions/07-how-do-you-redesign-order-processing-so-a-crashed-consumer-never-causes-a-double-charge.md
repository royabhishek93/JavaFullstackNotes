# How do you redesign order processing so a crashed consumer never causes a double charge?

**Type:** Advanced Scenario-Based
**Topic:** Redis Streams — Reliable Delivery & Idempotency
**Level:** Staff/Principal Interview (15+ YOE)

## Direct Answer
Redesign the pipeline around three layers, each owning one job: the API layer owns request validation and an idempotency key; the Stream owns delivery and retry; the payment write owns durability with a unique constraint on that idempotency key. `XACK` must be the *last* step in the worker, only sent after the charge is confirmed and persisted.

## Easy Explanation
Imagine a cashier who takes your order slip, hands it to the kitchen, and only throws the slip away once the kitchen confirms your food is cooked and paid for. If the cashier gets distracted mid-way and someone else picks up the slip, the kitchen should recognize "I already made this exact order" and not cook it twice. That recognition — not the slip-passing — is what stops the double charge.

## Diagram
```
                    +-------------------+
Client -----POST--->|  Order API        |
                    |  1. validate      |
                    |  2. INSERT order  |----(idempotency_key UNIQUE)----> Postgres
                    |     status=PENDING|
                    +--------+----------+
                             | XADD order-events
                             v
                    +-------------------+
                    | Redis Stream       |
                    +--------+----------+
                             | XREADGROUP >
                             v
                    +-------------------+
                    | Worker             |
                    | a) call payment    |
                    |    gateway with    |
                    |    idempotencyKey  |
                    | b) UPDATE order    |
                    |    SET status=PAID |
                    |    WHERE key=? AND |
                    |    status=PENDING  |
                    | c) XACK  <--- LAST |
                    +-------------------+

If the worker crashes between (a) and (c):
  -> message stays pending -> gets redelivered
  -> step (b)'s WHERE clause makes the UPDATE a no-op the 2nd time
  -> payment gateway also treats the same idempotencyKey as "already charged"
  -> result: charge happens exactly once, work can be retried safely
```

## Production Example
A ride-hailing app charges a rider after a trip ends:

```java
@Transactional
public void chargeRider(MapRecord<String, Object, Object> message) {
    PaymentEvent event = mapper.toEvent(message);

    int updated = orderRepo.markPaidIfPending(event.orderId(), event.idempotencyKey());
    if (updated == 1) {
        paymentGateway.charge(event.idempotencyKey(), event.amount()); // gateway also dedupes on this key
    }
    // if updated == 0, another worker already handled it — safe to skip

    redisTemplate.opsForStream().acknowledge("payment-workers", message);
}
```

Most payment gateways (Stripe, Razorpay, etc.) accept an idempotency key for exactly this reason — they expect retries from distributed systems and handle it on their side too.

## Why Interviewers Ask This
This question checks whether a candidate can design an end-to-end safety net across three systems (API, Redis, database/gateway) instead of trying to solve everything inside Redis. It's a strong signal of production experience with financial or billing systems.
# How do you redesign order processing so a crashed consumer never causes a double charge?

**Type:** Advanced Scenario-Based
**Topic:** Redis Streams — Reliable Delivery & Idempotency
**Level:** Senior/Staff Interview (10–15+ YOE)

## Direct Answer
Move the "did we already charge this order" decision out of Redis entirely and into a database with a **unique constraint**. Redis Streams only need to guarantee the *work item* is not lost; the database needs to guarantee the *side effect* only happens once. Combine: (1) an idempotency key generated by the client, (2) a unique DB constraint on that key, (3) `XACK` only after the DB commit succeeds.

## Easy Explanation
Imagine a call center where every customer complaint gets a ticket number before anyone picks up the phone. If the same complaint is called in twice by mistake, the agent checks "have we already resolved ticket #4521?" before doing anything. Redis is the phone queue — it makes sure no ticket is lost. The unique ticket number and the "already resolved?" check is what makes calling twice harmless. Without the ticket number, two agents calling the same customer back would waste effort or (worse) issue two refunds.

## Diagram
```
                    +-------------------------------------------------+
                    |               Order Service (API)                |
                    | 1. client sends Idempotency-Key: order-8842      |
                    | 2. INSERT order (status=PENDING) if not exists   |
                    | 3. XADD order-events  requestId=order-8842       |
                    +----------------------+---------------------------+
                                           |
                                           v
                    +-------------------------------------------------+
                    |             Redis Stream: order-events            |
                    |  consumer group: charge-workers                   |
                    +----------------------+---------------------------+
                                           |
                         XREADGROUP >     v
                    +-------------------------------------------------+
                    |  Worker crashes here <-- BEFORE XACK              |
                    |  charge attempt started, response unknown         |
                    +----------------------+---------------------------+
                                           |
                             XAUTOCLAIM (after idle window)
                                           v
                    +-------------------------------------------------+
                    | New worker re-reads same event                    |
                    | SELECT ... WHERE requestId = 'order-8842'         |
                    |   -> already CHARGED?  -> skip charge, just XACK  |
                    |   -> still PENDING?    -> charge once, then XACK  |
                    +-------------------------------------------------+
```

## Production Example
```sql
CREATE UNIQUE INDEX ux_orders_idempotency ON orders(idempotency_key);
```
```java
@Transactional
public void chargeOrder(OrderEvent event) {
    Order order = orderRepo.findByIdempotencyKey(event.requestId());
    if (order.getStatus() == CHARGED) {
        return; // already done — safe no-op, even on redelivery
    }
    paymentGateway.charge(order);          // idempotent gateway call too, if possible
    order.setStatus(CHARGED);
    orderRepo.save(order);
}
```
Payment gateways like Stripe support this natively via an `Idempotency-Key` header, so even the *external* call is protected, not just your own database.

## Why Interviewers Ask This
This question checks whether a candidate can design an end-to-end safety net rather than relying on any single component. A 15-YOE engineer is expected to name the unique constraint, the idempotency key propagation, and the ordering of "do work, then acknowledge" — not just "use Redis Streams."
