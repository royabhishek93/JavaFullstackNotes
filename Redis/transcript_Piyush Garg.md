## Scenario-Based Questions

1. **A profile page joins five tables with several foreign-key lookups on every single page load, and users complain the page feels slow after every refresh.** What is the underlying problem, and how does caching the assembled result in Redis fix it?**
   Every refresh recomputes the same expensive multi-table query from scratch, so response time and database load both grow with every hit. Caching the final computed response in Redis after the first fetch lets subsequent requests return instantly from memory instead of re-running the joins.

2. **You cache an API response in Redis but never set an expiry.** What problem does this create months later, and how do you fix it?**
   Without an expiry, the cached data becomes stale forever and users may see outdated information indefinitely (or memory keeps growing with data nobody prunes). Set an expiry on the cache key (e.g., `EXPIRE key 30` or `SET key value EX 30`) so the value refreshes periodically or is cleared automatically.

3. **A new engineer stores a user record with a key literally named `1000` and its value `Piyush`.** Why is this a bad key name, and what convention should replace it?**
   A bare numeric key gives no indication of what it represents or which entity it belongs to. The convention is `entity:id` such as `user:1000`, which groups related keys, stays self-descriptive, and lets tools display them under a common "user" folder-like grouping.

4. **You want a value to be written only if it does not already exist, so a first-time initialization does not accidentally overwrite existing data.** Which option on the `SET` command enforces this?**
   The `NX` option (`SET key value NX`). It only stores the value if the key is not already present; if the key exists, the command returns nil/no-op instead of overwriting it.

5. **A Node.js/Express endpoint proxies a slow third-party API and takes 1–4 seconds per request.** What is the cache-aside pattern that fixes this, step by step?**
   On each request: check Redis for a cached value first; if present, return it immediately; if absent, fetch from the slow API, store the result in Redis with an expiry, and then return it to the caller. Subsequent requests within the expiry window are served from Redis in milliseconds instead of seconds.

6. **A chat feature needs WebSocket connections spread across multiple horizontally scaled Node.js instances, and a message from a user on instance A must reach a subscriber connected to instance B.** How does Redis Pub/Sub solve this cross-instance delivery problem?**
   Each Node.js instance subscribes to a shared Redis channel; when instance A receives a message, it publishes it to that channel, and Redis fans it out to every subscribed instance (including B), which then forwards it to its own locally connected WebSocket clients.

7. **A food-delivery style feature needs "show me everything within 5 km of the user's current coordinates," and doing the distance math in application code is slow and error-prone.** Which Redis capability should you reach for instead?**
   Geospatial commands (e.g., adding coordinates and searching by radius from a point). Redis computes the distance/radius filtering internally, returning matching entries and their distances directly.

8. **You need to represent a session token that must vanish automatically 30 seconds after creation, without a background cleanup job.** How do you implement this, and what Redis feature makes the cleanup job unnecessary?**
   Set the token as a string with an expiry (`SET key value EX 30` or `EXPIRE key 30` after setting it). Redis's built-in key expiration automatically removes the key when the TTL elapses, so no separate cleanup job is needed.

9. **A running counter (like a page-visit count) can be read and incremented by many requests at nearly the same moment.** Which Redis command keeps the increment safe without the application doing its own read-modify-write, and why does that matter?**
   `INCR` (or `INCRBY`). It performs the increment atomically inside Redis, so concurrent requests never read the same stale value and overwrite each other's increment, which a manual get-then-set in application code could allow.

10. **You need to fetch several unrelated cached values (a user record and a couple of messages) in one round trip instead of issuing separate `GET` calls.** Which command reduces this to a single call?**
    `MGET`, which accepts multiple keys and returns all their values in one response, avoiding the overhead of multiple sequential round trips.

11. **For local development you want to both run a Redis server and visually inspect the keys/values without memorizing every CLI command.** What is the simplest way to get both a Redis server and a GUI in one container?**
    Run the Redis Stack Docker image (exposing the standard Redis port and the GUI's web port). It bundles a Redis server together with a browser-based client, so you get both without a separate visualization tool.
