## NEW LEARNER FOUNDATION — Read This First If You Are New

```
KEY TERMS EXPLAINED SIMPLY
============================

CACHE
  A fast storage layer that saves the result of slow operations so you
  don't have to repeat them. Think of it like sticky notes on your desk:
  instead of walking to the filing room every time, you wrote the answer
  on a sticky note. Cache = sticky notes, Database = filing room.

  Without cache: every request hits the database → 50-200ms per query
  With cache:    first request hits DB and stores result → subsequent
                 requests read from cache → under 5ms

REDIS
  An in-memory key-value store. Data lives in RAM, not disk → extremely fast.
  Supports strings, lists, sets, sorted sets, hashes, and more.
  Key: "product:123"   Value: the entire product JSON object

ELASTICACHE
  AWS-managed Redis (or Memcached). AWS handles OS patching, backups,
  failover. You just point your app at the ElastiCache endpoint.

TTL (Time To Live)
  How long a cached item stays valid. After TTL expires, the next
  request gets a cache miss → fetches fresh data from DB → re-caches.
  Example: TTL=15min means cached product data auto-expires after 15 minutes.

CACHE MISS / CACHE HIT
  Cache HIT:  key found in cache → return immediately (fast)
  Cache MISS: key not in cache → go to DB → store result → return (slower)

SESSION
  When you log into a website, the server stores your login state as a
  "session" — who you are, what's in your cart, etc. In a single-server
  app, sessions live in memory. In a multi-server app (ECS/EKS), sessions
  must be shared — otherwise logging in on Server A means Server B doesn't
  know you're logged in. Redis solves this (shared session store).

EVICTION
  When Redis runs out of memory, it must delete old keys to make room.
  The eviction POLICY decides which keys to delete:
  allkeys-lru = delete the least recently used key (oldest, least accessed)
  noeviction  = refuse new writes, throw error (dangerous for caches!)

CLUSTER MODE
  Running Redis across multiple servers (shards) for horizontal scaling.
  Each shard owns a portion of the data (hash slots 0-16383 split evenly).
  Allows more data and higher throughput than a single Redis node.
  Trade-off: multi-key operations can fail if keys are on different shards.
```

### PART 1 — When They Ask: "How do you handle sessions in ECS with multiple tasks?"

> **You say:**
>
> "Without shared sessions, a user logs in on Task 1 and their session is stored
> in Task 1's JVM memory. The next request from the same user hits Task 2 — Task 2
> has no session — user is logged out. This is the classic sticky session problem.
>
> You could use ALB sticky sessions (target group stickiness) — but then if Task 1
> dies, all its users are logged out simultaneously. And it prevents even load distribution.
>
> The correct solution is externalized sessions with Spring Session + Redis. Session
> data lives in ElastiCache. Any task can serve any user's request because they all
> read from the same Redis."

```
SESSION PROBLEM WITHOUT REDIS
================================

  ALB
   │
   ├─ Request 1 (User A) ──► Task 1  [session: {userId: 123, cart: [...]}] in MEMORY
   │
   └─ Request 2 (User A) ──► Task 2  [no session for User A] → 401 Unauthorized!

SESSION SOLUTION WITH SPRING SESSION + REDIS
============================================

  ALB
   │
   ├─ Request 1 (User A) ──► Task 1 ──► Redis: SET session:abc123 {userId:123,cart:[...]} TTL=30m
   │
   └─ Request 2 (User A) ──► Task 2 ──► Redis: GET session:abc123 → {userId:123,cart:[...]} ✅
                                         Task 2 serves request correctly!
```

```xml
<!-- pom.xml -->
<dependency>
    <groupId>org.springframework.session</groupId>
    <artifactId>spring-session-data-redis</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
```

```yaml
# application.yml
spring:
  session:
    store-type: redis
    redis:
      namespace: swiggy:session      # key prefix in Redis
      flush-mode: on-save            # write to Redis only when session changed
    timeout: 30m                     # session TTL
  data:
    redis:
      host: ${REDIS_HOST}            # ElastiCache primary endpoint
      port: 6379
      timeout: 2s                    # connection timeout
      lettuce:
        pool:
          max-active: 10
          max-idle: 5
          min-idle: 1
```

```java
@SpringBootApplication
@EnableRedisHttpSession(maxInactiveIntervalInSeconds = 1800)
public class SwiggyApplication { }
```

### PART 2 — When They Ask: "Walk me through product catalog caching with Redis."

> **You say:**
>
> "For the product catalog, I use a cache-aside pattern with Spring Cache backed
> by Redis. The key design decisions are: TTL (how long before data is considered
> stale), cache key design (must uniquely identify the query), and what to do
> when Redis is unavailable.
>
> For product details: 15-minute TTL — products change infrequently.
> For category listings: 5-minute TTL — flash sales can change these.
> For search results: 2-minute TTL — highly dynamic.
>
> When a product is updated via admin panel, I explicitly evict the cache entry
> so the next read gets fresh data."

```java
@Configuration
@EnableCaching
public class RedisConfig {

    @Bean
    public RedisCacheManager cacheManager(RedisConnectionFactory factory) {
        // Default config
        RedisCacheConfiguration defaultConfig = RedisCacheConfiguration
            .defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(15))
            .serializeValuesWith(
                RedisSerializationContext.SerializationPair.fromSerializer(
                    new GenericJackson2JsonRedisSerializer()  // JSON, not Java serialization
                )
            )
            .disableCachingNullValues();    // don't cache nulls (avoids stale "not found")

        // Per-cache TTL overrides
        Map<String, RedisCacheConfiguration> configs = new HashMap<>();
        configs.put("products",   defaultConfig.entryTtl(Duration.ofMinutes(15)));
        configs.put("categories", defaultConfig.entryTtl(Duration.ofMinutes(5)));
        configs.put("search",     defaultConfig.entryTtl(Duration.ofMinutes(2)));

        return RedisCacheManager.builder(factory)
            .cacheDefaults(defaultConfig)
            .withInitialCacheConfigurations(configs)
            .build();
    }
}

@Service
public class ProductCatalogService {

    @Cacheable(value = "products", key = "#productId",
               unless = "#result == null")
    public Product getProduct(Long productId) {
        return productRepo.findById(productId).orElse(null);
    }

    @Cacheable(value = "categories", key = "#category + ':' + #page")
    public Page<Product> getByCategory(String category, int page) {
        return productRepo.findByCategory(category, PageRequest.of(page, 20));
    }

    @CacheEvict(value = "products", key = "#product.id")
    public Product updateProduct(Product product) {
        return productRepo.save(product);
    }

    @CacheEvict(value = {"products", "categories"}, allEntries = true)
    public void invalidateCatalog() {
        log.info("Full catalog cache evicted (flash sale or bulk import)");
    }
}
```

### PART 3 — Trap Questions the Interviewer Will Ask

---

#### Trap 1: "Cluster Mode vs Non-Cluster Mode — what breaks with Cluster Mode?"

> **You say:**
>
> "This is a real trap. In Redis Cluster mode, keys are distributed across
> 16,384 hash slots spread over your shards. Each key maps to a specific slot
> using CRC16(key) mod 16384.
>
> The problem is multi-key operations. If you do MGET on two keys that are on
> different shards, Redis throws a CROSSSLOT error. Similarly, transactions
> with MULTI/EXEC, Lua scripts, and pipeline operations all break if the keys
> span shards.
>
> I've seen this happen with Spring Cache's `@Caching` annotation that tries
> to evict multiple caches in one operation — in cluster mode it throws
> CROSSSLOT at runtime."

```
REDIS CLUSTER — CROSSSLOT TRAP
================================

  Hash slots: 0 ─────────── 16383

  Shard-1: slots 0-5460      Shard-2: slots 5461-10922   Shard-3: slots 10923-16383
  ─────────────────────      ─────────────────────────   ──────────────────────────
  key "product:123"          key "product:456"           key "session:abc"
    CRC16 → slot 2000           CRC16 → slot 7000          CRC16 → slot 14000

  MGET "product:123" "product:456"  ← CROSSSLOT ERROR!
  (keys are on different shards — Redis can't execute this atomically)

  FIX — Hash Tags: force keys to the same slot
  ──────────────────────────────────────────────
  "product:{catalog}:123"    both use {catalog} as hash tag
  "product:{catalog}:456"    → CRC16("{catalog}") → same slot → same shard

  Spring Cache with Cluster: use simple string keys (one key per operation)
  Avoid multi-key operations entirely in cluster mode for safety.
```

```yaml
# application.yml — Cluster Mode config
spring:
  data:
    redis:
      cluster:
        nodes:
          - swiggy-redis.cluster.0001.xxx.cache.amazonaws.com:6379
          - swiggy-redis.cluster.0002.xxx.cache.amazonaws.com:6379
          - swiggy-redis.cluster.0003.xxx.cache.amazonaws.com:6379
        max-redirects: 3    # follow MOVED redirections in cluster
      lettuce:
        cluster:
          refresh:
            adaptive: true            # auto-refresh cluster topology
            period: 60s               # refresh every 60s
```

#### Trap 2: "What happens when Redis runs out of memory?"

> **You say:**
>
> "ElastiCache Redis has a maximum memory limit. When it's full, behaviour
> depends on the `maxmemory-policy` setting. If you leave it at the default
> `noeviction`, Redis starts returning OOM errors to your application.
> Spring Cache then throws an exception, which propagates up — your app
> throws 500 errors because the cache is full.
>
> I always set `maxmemory-policy: allkeys-lru` for cache-only Redis clusters.
> This evicts the least-recently-used key when memory is full — cache misses
> go to DB, but the app stays healthy.
>
> For session Redis, I use `volatile-lru` so only keys with TTL are evicted —
> sessions that are still TTL-valid can be evicted if needed, but they were
> expiring anyway."

```
REDIS EVICTION POLICIES — Which to Choose
==========================================

  Policy              What Gets Evicted        When to Use
  ─────────────────────────────────────────────────────────────────
  noeviction          Nothing — OOM error       Never for caches!
                                                (default — dangerous)
  allkeys-lru         Any key (LRU order)       Cache-only Redis ✅
  allkeys-lfu         Any key (LFU order)       Cache with hot spots ✅
  volatile-lru        Only keys with TTL (LRU)  Mixed cache + persistent ✅
  volatile-ttl        Keys with shortest TTL    When TTL accuracy matters
  allkeys-random      Any random key            Almost never

  SWIGGY SETUP:
  Session cluster:    volatile-lru   (sessions have TTL, non-session keys preserved)
  Product cache:      allkeys-lru    (pure cache — evict anything if full)
```

```
# ElastiCache Parameter Group setting
maxmemory-policy = allkeys-lru
```

#### Trap 3: "What happens if ElastiCache is down? Does your app crash?"

> **You say:**
>
> "This is the resilience question. If Redis is down and your Spring Cache
> throws an uncaught exception, your entire request fails — you've introduced
> a hard dependency on Redis for every cache read.
>
> The fix has two parts: configure a `CacheErrorHandler` that catches Redis
> exceptions and falls through to the database, and add a circuit breaker
> on the Redis connection so you don't hammer a dead Redis.
>
> The goal is cache-as-an-optimisation, not cache-as-a-requirement. The app
> should work (slower) without cache."

```java
@Configuration
public class ResilientCacheConfig {

    @Bean
    public CacheErrorHandler cacheErrorHandler() {
        return new CacheErrorHandler() {
            @Override
            public void handleCacheGetError(RuntimeException ex, Cache cache, Object key) {
                log.warn("Cache GET failed for key={} in cache={}: {}",
                         key, cache.getName(), ex.getMessage());
                // Don't re-throw — cache miss → method will execute and fetch from DB
            }

            @Override
            public void handleCachePutError(RuntimeException ex, Cache cache,
                                            Object key, Object value) {
                log.warn("Cache PUT failed: {}", ex.getMessage());
                // Don't re-throw — data was fetched correctly, just not cached
            }

            @Override
            public void handleCacheEvictError(RuntimeException ex, Cache cache, Object key) {
                log.warn("Cache EVICT failed: {}", ex.getMessage());
            }

            @Override
            public void handleCacheClearError(RuntimeException ex, Cache cache) {
                log.warn("Cache CLEAR failed: {}", ex.getMessage());
            }
        };
    }
}
```

#### Trap 4: "Lettuce vs Jedis — which do you use and why?"

> **You say:**
>
> "Lettuce is the Spring Boot default since 2.0. It's built on Netty — non-blocking,
> asynchronous. One connection can handle many concurrent requests through pipelining.
> It's the right choice for most Spring Boot apps.
>
> Jedis is synchronous and thread-per-connection. You need a large connection pool
> because each thread needs its own connection. Under high concurrency, Jedis
> can exhaust its connection pool and queue requests.
>
> The Lettuce trap: by default (non-cluster mode), Lettuce uses a single shared
> connection. Under very high concurrency with blocking operations (BLPOP, etc.),
> that single connection becomes a bottleneck. Fix: enable connection pooling
> in Lettuce explicitly."

```yaml
# Lettuce with connection pooling (for high-concurrency apps)
spring:
  data:
    redis:
      lettuce:
        pool:
          enabled: true
          max-active: 16        # max connections in pool
          max-idle: 8
          min-idle: 2
          max-wait: 2s          # wait max 2s for a connection — fail fast
```

### PART 4 — Advanced: Two-Layer Caching (Caffeine L1 + Redis L2)

> **You say:**
>
> "For Swiggy's restaurant listing — 10 million requests per hour on the home
> page — even 5ms Redis latency per request adds up. We use a two-layer cache:
> Caffeine in-process as L1 (sub-millisecond), Redis as L2 (5ms).
>
> Caffeine holds the top 10,000 most-accessed restaurants per pod, TTL 30 seconds.
> Redis holds the full catalog, TTL 5 minutes.
>
> On a cache miss in Caffeine, we check Redis. On a miss in Redis, we hit the DB.
> This gives us the speed of local cache with the consistency of shared Redis."

```
TWO-LAYER CACHE ARCHITECTURE
==============================

  Request for Restaurant #42
        │
        ▼
  Caffeine (L1 — in-process, sub-ms)
  HIT: return instantly ✅
  MISS:
        │
        ▼
  Redis ElastiCache (L2 — shared, 5ms)
  HIT: populate Caffeine L1, return ✅
  MISS:
        │
        ▼
  PostgreSQL RDS (source of truth, 50ms)
  → populate Redis L2 (TTL=5min)
  → populate Caffeine L1 (TTL=30s)
  → return ✅

  LATENCY PROFILE:
  L1 hit: < 1ms
  L2 hit: 3-8ms
  DB hit: 40-80ms

  CACHE INVALIDATION:
  Product updated → evict from Redis L2
                  → publish invalidation event via Redis Pub/Sub
                  → ALL pods evict from their Caffeine L1
```

## Interview Cheat Sheet (Say This Confidently)

> "For ElastiCache in production: session clustering with Spring Session + Redis eliminates sticky session problems and pod-death logout issues — any pod can serve any user. Product caching with Spring Cache + Redis: always use JSON serialization (not Java serialization) so schema changes don't crash deserialization on deploy. Cluster mode breaks multi-key operations (CROSSSLOT) — use hash tags to colocate related keys. Always configure a CacheErrorHandler so Redis failure degrades gracefully to DB, not application 500 errors. Set maxmemory-policy=allkeys-lru for pure caches, volatile-lru for mixed usage. Lettuce is non-blocking and shares connections efficiently, but enable pooling for apps using blocking commands. For the hottest data, layer Caffeine in-process over Redis to get sub-millisecond reads."
