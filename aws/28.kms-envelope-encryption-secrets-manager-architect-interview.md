## NEW LEARNER FOUNDATION — Read This First If You Are New

```
KEY TERMS EXPLAINED SIMPLY
============================

KMS (Key Management Service)
  AWS service that creates and manages encryption keys. You never see or
  download the actual master key material — it lives inside HSMs (Hardware
  Security Modules) inside AWS datacenters. You call KMS via API to
  encrypt/decrypt data. KMS is the "key factory" — it makes and stores keys.

CMK (Customer Managed Key)
  A KMS key you create and control. You set the key policy (who can use it),
  you control rotation (annual auto-rotation), you can schedule deletion
  (7-30 day waiting period). Costs $1/month + $0.03 per 10,000 API calls.

DEK (Data Encryption Key)
  A temporary symmetric key generated by KMS specifically to encrypt your
  data. Unlike the CMK (which never leaves KMS), the DEK is handed to your
  application — but only briefly, used in memory, then discarded.

ENVELOPE ENCRYPTION
  A two-key system: your master key (CMK) encrypts a smaller key (DEK),
  and the DEK encrypts your actual data. This is how you encrypt large
  files using KMS (which itself only accepts ≤ 4KB inputs directly).
  Think of it like: the DEK is cash in an envelope, the CMK is the safe
  that holds that sealed envelope. The cash (data) and the envelope (DEK)
  travel together. To open: get the envelope decrypted by the safe (KMS),
  then use the cash (DEK) to open the data.

AWS Managed Key
  KMS keys AWS creates and manages on your behalf, per service per account.
  Examples: aws/rds, aws/s3, aws/secrets-manager. Free. Rotated automatically
  every year. You cannot change their key policy or use them for cross-account
  access. Sufficient for most standard encryption needs.

AWS Owned Key
  Keys that AWS owns internally — not visible to you at all. Used for
  S3 SSE-S3 (no KMS involvement), DynamoDB default encryption, etc.
  Zero cost, zero visibility, zero control. Fine when you don't need
  audit trails on key usage.

Secrets Manager
  AWS service for securely storing and auto-rotating secrets: database
  passwords, API keys, OAuth tokens, TLS certificates. You store a secret
  once; Secrets Manager rotates it on a schedule (using a Lambda function)
  and keeps old versions valid during a rotation window so no downtime.
  $0.40/secret/month.

Parameter Store (SSM)
  AWS Systems Manager service for storing configuration strings.
  Standard tier is FREE (up to 10,000 parameters). No built-in rotation.
  Best for non-sensitive config: feature flags, endpoint URLs, cron
  schedules, environment names. SecureString parameters are KMS-encrypted.

ROTATION
  Automatically changing a secret (e.g., DB password) on a schedule.
  Secrets Manager rotation: Lambda generates new password → updates RDS →
  stores new value in Secrets Manager → old + new both valid briefly →
  old version deprecated. Zero downtime because old credential still works
  during the rotation window.

IRSA (IAM Roles for Service Accounts)
  EKS mechanism to give individual pods their own IAM role without
  hardcoding AWS credentials. Pod annotations link to a service account,
  which maps to an IAM role via OIDC federation. Pod can then call
  GetSecretValue on Secrets Manager — no credentials in the container.
```

### SECTION 1 — Why KMS Has a 4KB Limit — Envelope Encryption

---

#### When They Ask: "Why can't you just encrypt a large file directly with KMS?"

> **You say:**
>
> "KMS is designed around a hard limit: it can directly encrypt or decrypt
> only up to 4KB of data in a single API call. The reason is architectural —
> KMS keys never leave the HSM, so every encrypt/decrypt round-trips through
> AWS's key infrastructure. A 500MB file would be impractical.
>
> The solution is envelope encryption. Instead of sending your data to KMS,
> you ask KMS for a temporary data key (DEK). KMS returns two things: the
> plaintext DEK and an encrypted copy of that same DEK. You use the plaintext
> DEK in your application's memory to encrypt your actual data — locally,
> no network round-trip. Then you immediately discard the plaintext DEK.
> You store the encrypted data and the encrypted DEK together.
>
> To decrypt: you send just the encrypted DEK (which is tiny — under 4KB)
> to KMS. KMS decrypts it and returns the plaintext DEK. You use it to
> decrypt your data. Then discard again.
>
> The security guarantee: the plaintext DEK never persists to disk or logs.
> AWS never touches your actual data. The CMK in KMS protects the DEK, which
> protects the data. Two-layer protection."

```
ENVELOPE ENCRYPTION — STEP BY STEP
=====================================

  ENCRYPT PATH:
  ─────────────
  Your App
      │
      ├─[1]─► KMS.GenerateDataKey(KeyId="cmk-arn", KeySpec="AES_256")
      │            │
      │            └─► KMS returns:
      │                  plaintext_DEK  (32 bytes, AES-256 key)
      │                  encrypted_DEK  (the DEK encrypted under your CMK)
      │
      ├─[2]─► Encrypt actual data using plaintext_DEK  (local, in memory)
      │        e.g., AES-256-GCM encrypt(your_500MB_backup, plaintext_DEK)
      │
      ├─[3]─► Discard plaintext_DEK from memory immediately
      │
      └─[4]─► Store to S3 / DynamoDB:
                  encrypted_data     (your 500MB backup, now ciphertext)
                  encrypted_DEK      (small blob, < 4KB)
                  (stored together as a bundle — neither is useful alone)

  DECRYPT PATH:
  ─────────────
  Your App
      │
      ├─[1]─► Read from S3: encrypted_data + encrypted_DEK
      │
      ├─[2]─► KMS.Decrypt(CiphertextBlob=encrypted_DEK)
      │            └─► KMS returns: plaintext_DEK
      │                (KMS verifies caller has kms:Decrypt permission first)
      │
      ├─[3]─► Decrypt data using plaintext_DEK (local, in memory)
      │
      └─[4]─► Discard plaintext_DEK from memory immediately

  SECURITY GUARANTEE:
  ─────────────────────
  plaintext_DEK:  lives in memory only — never written to disk, never logged
  encrypted_DEK:  useless without KMS access (controlled by key policy)
  AWS:            only ever sees encrypted_DEK — never your raw data
  Attacker:       stealing encrypted_data alone is useless (has no DEK)
                  stealing encrypted_DEK alone is useless (has no KMS access)
                  must compromise BOTH + KMS access to win
```

```java
// Java: AWS Encryption SDK handles envelope encryption automatically
// Add to pom.xml:
// <dependency>
//   <groupId>com.amazonaws</groupId>
//   <artifactId>aws-encryption-sdk-java</artifactId>
//   <version>2.4.0</version>
// </dependency>

import software.amazon.awssdk.services.kms.KmsClient;
import software.amazon.awssdk.services.kms.model.*;

@Service
public class EnvelopeEncryptionService {

    private final KmsClient kmsClient;
    private final String cmkArn = "arn:aws:kms:us-east-1:123456789:key/abc-def";

    // ENCRYPT: GenerateDataKey → encrypt locally → store bundle
    public EncryptedBundle encrypt(byte[] plaintext) {
        // Step 1: Ask KMS for a data key
        GenerateDataKeyResponse dataKeyResponse = kmsClient.generateDataKey(
            GenerateDataKeyRequest.builder()
                .keyId(cmkArn)
                .keySpec(DataKeySpec.AES_256)
                .build()
        );

        byte[] plaintextDEK  = dataKeyResponse.plaintext().asByteArray();
        byte[] encryptedDEK  = dataKeyResponse.ciphertextBlob().asByteArray();

        // Step 2: Encrypt data locally in memory with plaintextDEK (AES-256-GCM)
        byte[] encryptedData = aesEncrypt(plaintext, plaintextDEK);

        // Step 3: Discard plaintextDEK — overwrite memory
        java.util.Arrays.fill(plaintextDEK, (byte) 0);

        // Step 4: Return bundle (encryptedData + encryptedDEK stored together)
        return new EncryptedBundle(encryptedData, encryptedDEK);
    }

    // DECRYPT: KMS.Decrypt(encryptedDEK) → decrypt data locally
    public byte[] decrypt(EncryptedBundle bundle) {
        // Step 1: Ask KMS to decrypt the encrypted DEK
        DecryptResponse decryptResponse = kmsClient.decrypt(
            DecryptRequest.builder()
                .ciphertextBlob(SdkBytes.fromByteArray(bundle.encryptedDEK()))
                .keyId(cmkArn)
                .build()
        );

        byte[] plaintextDEK = decryptResponse.plaintext().asByteArray();

        // Step 2: Decrypt data locally in memory
        byte[] plaintext = aesDecrypt(bundle.encryptedData(), plaintextDEK);

        // Step 3: Discard plaintextDEK
        java.util.Arrays.fill(plaintextDEK, (byte) 0);

        return plaintext;
    }
}
```

> **Interviewer follow-up: "What does the AWS Encryption SDK add over calling KMS directly?"**
>
> "The Encryption SDK handles the envelope encryption plumbing automatically —
> GenerateDataKey, local AES-GCM encryption, key commitment, and serializing

> time/count window) to reduce KMS API calls and costs. For greenfield code I
> use the SDK. For existing systems I sometimes call KMS directly when I need
> full control over the bundle format."

### SECTION 2 — KMS Key Types — CMK vs AWS Managed vs AWS Owned

---

#### When They Ask: "What are the different KMS key types and when do you use each?"

> **You say:**
>
> "There are three tiers. AWS Owned keys are invisible to you — AWS uses them
> internally. S3 SSE-S3 uses an owned key. No cost, no visibility, no control.
> Fine when you have no audit or compliance requirement.
>
> AWS Managed keys are per-service per-account — aws/rds, aws/s3, aws/secrets-manager.
> They're free, auto-rotate annually, and AWS manages the key policy. You cannot
> change the policy or share them cross-account. Good for most standard use cases.
>
> Customer Managed Keys are keys you create. One dollar per month per key, plus
> three cents per ten thousand API calls. You write the key policy, you enable
> rotation, you control who can use it and who can administer it. You can share
> across accounts. You can schedule deletion with a 7-to-30-day waiting period.
>
> I use CMK when I need HIPAA or PCI compliance that requires proving you control
> the key — the auditor asks who owns the key, and with AWS Managed you can only
> say 'AWS'. With CMK you can say 'my team owns this key, here is the policy,
> here are the CloudTrail logs of every usage.'
>
> The critical trap: KMS has a resource-based key policy AND IAM policies.
> Unlike most AWS services where IAM alone grants access, KMS requires the
> key policy to explicitly allow the IAM principal. If the key policy doesn't
> list your role, the role cannot use that key — even if the IAM policy allows
> kms:Decrypt. Both must be correct."

```
KMS KEY TYPE COMPARISON
=========================

  Type              Visibility  Cost          Rotation    Policy Control  Use Case
  ────────────────────────────────────────────────────────────────────────────────────
  AWS Owned Key     None        Free          AWS-managed  None           S3 SSE-S3, DynamoDB
                                                                          default. "I don't
                                                                          care about keys."

  AWS Managed Key   CloudTrail  Free          Annual auto  Cannot change  Standard encryption
  (aws/rds, etc.)   logs only                 (by AWS)                   without compliance
                                                                          requirement.

  Customer Managed  Full        $1/month      You enable   Full control   HIPAA, PCI, BYOK,
  Key (CMK)        visibility  + $0.03/10K   annual auto  you write      cross-account,
                               API calls      rotate       key policy     audit ownership.

  DECISION TREE:
  ──────────────
  Cross-account access needed?          → CMK (only option)
  HIPAA/PCI "who owns the key" audit?  → CMK (you can prove ownership)
  BYOK (Bring Your Own Key)?           → CMK with custom key material
  Simple internal app, no compliance?  → AWS Managed Key (free, zero ops)
  Don't need key visibility at all?    → AWS Owned Key (S3 SSE-S3 default)
```

> **Interviewer follow-up: "I give my ECS task role kms:Decrypt in IAM. Why can't it decrypt?"**
>
> "Classic KMS trap. KMS is the only AWS service where IAM permissions alone
> are not sufficient. The key policy is a resource-based policy on the key itself,
> and it must explicitly grant access to the principal. If your key policy only has
> the root account principal, then only the root account can use the key regardless
> of what IAM says. Fix: add the ECS task role ARN to the key policy's Allow
> statement for kms:Decrypt. Both the key policy and the IAM policy must allow
> the action."

### SECTION 3 — Secrets Manager — Auto-Rotation Without Downtime

---

#### When They Ask: "How do you rotate database credentials without taking the service down?"

> **You say:**
>
> "Secrets Manager handles rotation automatically using a Lambda function it
> manages. The rotation process is designed for zero downtime because of the
> version staging labels: AWSCURRENT, AWSPENDING, and AWSPREVIOUS.
>
> Here's the rotation sequence: the Lambda creates a new password on RDS
> (the old one still works), stores the new password in Secrets Manager as
> AWSPENDING. The Lambda then tests the new credential to verify it works.
> On success, it promotes AWSPENDING to AWSCURRENT and demotes the old one
> to AWSPREVIOUS. The old credential stays valid for one rotation window.
>
> Applications that call GetSecretValue always get AWSCURRENT. During the
> brief rotation window, if a cached old credential fails (connection refused),
> the app should retry GetSecretValue to get the new one. This is the retry
> pattern that enables zero downtime."

```
SECRETS MANAGER ROTATION — ZERO DOWNTIME
==========================================

  BEFORE ROTATION:
  ─────────────────
  Secret: prod/swiggy/db-password
    AWSCURRENT:   password = "OldPass123"    ← app uses this
    AWSPREVIOUS:  password = "VeryOldPass"   ← deprecated

  DURING ROTATION (Lambda executing):
  ─────────────────────────────────────
  Step 1: createSecret
    → Lambda generates new password "NewPass456"
    → Secrets Manager stores as AWSPENDING
    (AWSCURRENT "OldPass123" still valid — app keeps working)

  Step 2: setSecret
    → Lambda calls RDS.modifyDBInstance to add "NewPass456"
    → RDS now accepts BOTH "OldPass123" AND "NewPass456"

  Step 3: testSecret
    → Lambda opens connection to RDS using "NewPass456"
    → Verifies login succeeds
    → If test fails: rotation aborted, AWSCURRENT unchanged

  Step 4: finishSecret
    → AWSPENDING  → promoted to AWSCURRENT  ("NewPass456")
    → AWSCURRENT  → demoted  to AWSPREVIOUS ("OldPass123")
    → AWSPREVIOUS (old) → deleted

  AFTER ROTATION:
  ────────────────
  Secret: prod/swiggy/db-password
    AWSCURRENT:   password = "NewPass456"    ← app uses this
    AWSPREVIOUS:  password = "OldPass123"    ← still valid briefly

  APP RETRY PATTERN (handle rotation gracefully):
  ─────────────────────────────────────────────────
  DB connection fails
      │
      └─► Catch SQLRecoverableException
              │
              └─► GetSecretValue() again (no-cache call)
                      │
                      └─► Reconnect with new password ✅
```

### SECTION 4 — Secrets Manager vs Parameter Store — Cost Decision

---

#### When They Ask: "When would you use Parameter Store instead of Secrets Manager?"

> **You say:**
>
> "Cost drives this decision. Secrets Manager is forty cents per secret per month
> plus five cents per ten thousand API calls. Sounds cheap until you have
> 100 microservices each with 5 secrets — that's 24 dollars a month just in
> secret storage, not counting the API calls.
>
> Parameter Store Standard tier is free up to ten thousand parameters. No built-in
> rotation. 4KB value limit per parameter. Throughput limit of 40 transactions
> per second by default — Parameter Store Advanced unlocks 1000 TPS but costs money.
>
> My rule: if the value needs rotation or if it would cause a security incident
> if leaked — DB password, API key, OAuth client secret — it goes in Secrets Manager.
> If it's non-sensitive config — feature flag status, service endpoint URLs,
> cron schedule expressions, environment names — it goes in Parameter Store for free.
> Even sensitive values that never rotate, like a third-party webhook signature
> that never changes, go in Secrets Manager for the audit trail and versioning."

```
SECRETS MANAGER vs SSM PARAMETER STORE
=========================================

                         Secrets Manager              Parameter Store
  ─────────────────────────────────────────────────────────────────────────
  Price                  $0.40/secret/month           FREE (Standard tier)
                         + $0.05/10K API calls        up to 10,000 params

  Auto-rotation          YES — built-in Lambda        NO (must build yourself)

  Versioning             AWSCURRENT / AWSPENDING /    Yes, but manual
                         AWSPREVIOUS staging labels

  Value size             65KB                         4KB (Standard)
                                                      8KB (Advanced, paid)

  Throughput             Generous                     40 TPS (Standard)
                                                      1000 TPS (Advanced, paid)

  Cross-account          Yes                          Limited

  Use for                DB passwords, API keys,      Feature flags,
                         OAuth tokens, TLS certs,     endpoint URLs,
                         anything that rotates        cron schedules,
                                                      environment names,
                                                      non-sensitive config

  COST EXAMPLE (100 microservices, 5 secrets each):
  ─────────────────────────────────────────────────
  Secrets Manager:  100 × 5 × $0.40 = $200/month   (just storage)
  Parameter Store:  500 params        = $0/month    (Standard, free tier)

  DECISION:
  ─────────
  Needs rotation?          → Secrets Manager (no contest)
  Sensitive + audit trail? → Secrets Manager (even without rotation)
  Non-sensitive config?    → Parameter Store (free)
  Feature flags?           → Parameter Store (free, high read volume ok)
```

### SECTION 5 — KMS in Practice — RDS, S3, EBS

---

#### When They Ask: "How do you encrypt data at rest across RDS, S3, and EBS?"

> **You say:**
>
> "At rest encryption has a major gotcha for RDS: you must enable encryption
> at creation time. You cannot enable encryption on a running RDS instance.
> If you forget, the recovery path is: take a snapshot, copy the snapshot
> with encryption enabled, restore from the encrypted snapshot. That means
> downtime or a blue-green cutover.
>
> When you encrypt RDS at creation, it encrypts everything automatically:
> the primary data, automated backups, read replicas, and snapshots. They
> all inherit the same CMK.
>
> For S3, SSE-KMS encrypts each object with a unique DEK under your CMK.
> You set the default encryption on the bucket so every PUT uses your CMK
> automatically without the application needing to specify it per request.
>
> For EBS, there's an account-level setting in EC2: enable encryption by
> default. Once set, every new EBS volume in the account is automatically
> encrypted. Existing volumes need to be snapshot-and-restore to get
> encryption.
>
> And for in-transit: TLS everywhere. ACM certificate on the ALB, RDS
> requires SSL connection string, ElastiCache Redis TLS endpoint, S3
> HTTPS only bucket policy. The compliance checklist is: encryption at rest
> via KMS, encryption in transit via TLS, key access audit via CloudTrail,
> and rotation via Secrets Manager. That four-part answer covers HIPAA and
> PCI baseline."

```
ENCRYPTION AT REST — SERVICE BY SERVICE
=========================================

  RDS Aurora
  ───────────
  Enable: checked at creation only (cannot enable later!)
  CMK:    aws/rds (managed) or your CMK (compliance)
  Scope:  encrypts data files, automated backups, read replicas, snapshots

  S3
  ───
  Enable: bucket default encryption → Server-Side Encryption → SSE-KMS
  CMK:    aws/s3 (managed) or your CMK

    "Resource": "arn:aws:s3:::my-bucket/*",

      "StringNotEquals": {

  ──────────────────

  App → Secrets Mgr: Always HTTPS (AWS SDK enforces this by default)

  ─────────────────────────────────────────────
  ✅ Encryption at rest   → KMS (CMK for compliance, Managed for standard)
  ✅ Encryption in transit → TLS everywhere (ACM + RDS SSL + Redis TLS)
  ✅ Key access audit      → CloudTrail logs every kms:Decrypt + kms:GenerateDataKey
  ✅ Secret rotation       → Secrets Manager auto-rotation (DB passwords every 30d)
```

## COMMON TRAPS — What Interviewers Test

```
TRAP 1: Enabling KMS on RDS after creation
──────────────────────────────────────────
Problem:  You cannot enable encryption on a running RDS instance.
          The "Enable encryption" checkbox is greyed out after creation.
Recovery: 1. Create snapshot of unencrypted instance
          2. Copy snapshot with "Enable encryption" + specify CMK
          3. Restore new RDS from encrypted snapshot
          4. Blue-green traffic cutover
Cost:     Downtime (or blue-green) + snapshot storage
Prevention: Always check encryption checkbox at RDS creation.
            Use Terraform with storage_encrypted = true enforced in policy.

TRAP 2: Key Policy — IAM alone is NOT enough for KMS
─────────────────────────────────────────────────────
Problem:  ECS task has IAM policy allowing kms:Decrypt.
          Task still gets AccessDeniedException on KMS.
Reason:   KMS requires BOTH key policy + IAM to allow the principal.
          Key policy does not list the task role → denied at key level.
Fix:      Add task role ARN to the CMK key policy's Allow statement.
Rule:     KMS is unique — always check both the key policy AND the IAM policy.

TRAP 3: Secrets Manager cost adds up with many microservices
────────────────────────────────────────────────────────────
Problem:  100 microservices × 5 secrets each = 500 secrets
          500 × $0.40/month = $200/month just in storage
          + API call costs on top
Mitigation:
  - Store related secrets as one JSON secret ("prod/service/all-secrets")
    → 1 secret instead of 5 → $0.40 vs $2.00/month per service
  - Use Parameter Store for non-sensitive config (free)
  - Cache GetSecretValue in memory (next trap covers this)

TRAP 4: Calling GetSecretValue on every request
────────────────────────────────────────────────
Problem:  App calls secretsClient.getSecretValue() inside every HTTP handler.
          At 1000 RPS: 1000 SM API calls/second → massive cost + throttling.
          $0.05 per 10K calls → $0.005/request → $432/day at 1000 RPS.
Fix:      Cache the secret in memory at startup. Refresh only on:
            - App restart (startup fetch)
            - Connection failure (retry → GetSecretValue to detect rotation)
            - Scheduled refresh every 10-60 minutes (optional)
Rule:     Secrets Manager is a storage/rotation system, not a real-time lookup.
          Treat it like a config source, not a database.

TRAP 5: Parameter Store throughput limit
─────────────────────────────────────────
Problem:  Standard Parameter Store: 40 TPS default per account per region.
          100 services each poll GetParameter on every request → throttling.
Fix:
  - Cache parameter values in memory (TTL 5 minutes for flags)
  - Use Parameter Store Advanced tier ($0.05/10K higher throughput) if needed
  - Or move high-read config to environment variables (set at deployment)
Rule:     Parameter Store is for config at startup or low-frequency polling,
          not for per-request lookups.

TRAP 6: CMK deletion has a 7-30 day waiting period
────────────────────────────────────────────────────
Problem:  You call kms:ScheduleKeyDeletion.
          Data encrypted with that key becomes permanently unrecoverable
          after the waiting period. There is no "undo" after deletion completes.
Behavior: Key enters PendingDeletion state (7-30 days, you choose).
          During waiting: key cannot be used to encrypt/decrypt.
          You can cancel deletion during waiting period.
          After waiting period: key and all encrypted data → permanently lost.
Rule:     Before deleting: verify nothing is encrypted with this key
          (CloudTrail: search for kms:GenerateDataKey / kms:Decrypt on this key).
          Set minimum 30-day waiting period in production.
          Add CloudWatch alarm: alert if key enters PendingDeletion state.

TRAP 7: Cross-account KMS requires both key policy AND IAM
───────────────────────────────────────────────────────────
Problem:  Account A has CMK. Account B needs to encrypt/decrypt with it.
          Account B adds kms:Decrypt to its IAM role → still denied.
Fix:      TWO changes required:
          1. Account A's CMK key policy: add Account B role as principal
          2. Account B's IAM role: add kms:Decrypt permission + resource = CMK ARN
          Both must be in place simultaneously.
Rule:     Cross-account KMS = key policy change in source account + IAM in target account.

TRAP 8: Rotation Lambda must be in same VPC as private RDS
────────────────────────────────────────────────────────────
Problem:  Secrets Manager rotation is configured.
          Rotation Lambda is created by Secrets Manager automatically.
          Lambda cannot reach private RDS → rotation fails silently.
          AWSCURRENT never updates → stale password after 30 days → app breaks.
Reason:   Private RDS has no public endpoint. Lambda without VPC config
          runs in AWS-managed VPC and cannot reach your private subnets.
Fix:      Configure the rotation Lambda to run in your VPC:
          - Lambda VPC config: your private subnets + security group
          - Security group: allow outbound 5432 (Postgres) or 3306 (MySQL)
          - RDS security group: allow inbound from Lambda security group
Rule:     Always test rotation manually (RotateSecret API) after setup.
          Check Lambda CloudWatch logs for rotation errors.
```
