## NEW LEARNER FOUNDATION — Read This First If You Are New

```
KEY TERMS EXPLAINED SIMPLY
============================

S3 STORAGE CLASS
  S3 is not one flat tier. AWS offers 7 different storage classes with
  different prices and retrieval speeds. "Standard" is the default —
  fast and expensive. "Glacier Deep Archive" is the cheapest but takes
  12 hours to retrieve. You choose based on how often you need the data.

LIFECYCLE RULE
  An automated S3 rule: "after 30 days, move to Infrequent Access.
  After 90 days, move to Glacier. After 7 years, delete."
  You define the rule once — AWS moves the objects automatically.
  This is how you cut storage costs without manual work.

PARQUET
  A file format for storing data in columns instead of rows. Think of
  a spreadsheet: row storage stores all 100 columns of Row 1, then Row 2.
  Parquet stores all values of Column 1 first, then Column 2.
  When you only need 3 out of 100 columns (SELECT price, qty, date),
  Parquet reads only those 3 columns from disk. 97 columns are never read.

COLUMNAR STORAGE
  Storing data column-by-column instead of row-by-row. CSV/JSON = row
  storage (read everything). Parquet/ORC = columnar storage (read only
  what you need). Analytics queries (SELECT avg(price)...) read 1 column
  out of 100 — columnar is 100x cheaper.

ATHENA
  AWS-managed SQL engine (based on Presto) that runs queries directly over
  files in S3. No servers to manage, no clusters to start. You write SQL,
  Athena reads the S3 files and returns results. You pay $5 per TB scanned
  (or less with Parquet). Perfect for ad-hoc analytics over archived data.

PARTITION PRUNING
  When your S3 files are organized in folders by date/region/service:
  s3://bucket/orders/year=2026/month=08/day=31/
  Athena understands the folder structure. A query with WHERE year=2026
  AND month=08 will skip all other year/month folders entirely — it reads
  only the relevant partition. This is partition pruning: "don't even look
  at data you don't need."

DATA LAKE
  A centralized S3 storage repository that holds raw, cleaned, and
  aggregated data in its native format (no forced schema). Unlike a
  data warehouse (Redshift), a data lake accepts any format: JSON logs,
  CSV exports, Parquet analytics tables, images, binary files.
  You define the schema at query time (schema-on-read).

S3 INTELLIGENT-TIERING
  An S3 storage class that automatically moves objects between tiers
  based on actual access patterns. AWS monitors each object and moves
  rarely-accessed objects to cheaper tiers — and moves them back if
  they are accessed again. You pay a small monitoring fee per 1,000 objects.
  Best for data with unpredictable access patterns.

GLACIER
  AWS's archival storage tier. Three variants:
  - Glacier Instant Retrieval: milliseconds to retrieve (like Standard)
  - Glacier Flexible Retrieval: minutes to hours (cost optimized)
  - Glacier Deep Archive: up to 12 hours (cheapest possible storage)
  You cannot read Glacier data without explicitly initiating a restore first
  (except Instant Retrieval). Glacier is for data you keep for compliance
  but rarely need.
```

### SECTION 1 — When They Ask: "Walk me through S3 storage classes and when you use each one."

> **You say:**
>
> "There are 7 storage classes and the choice is about frequency of access versus
> cost. Let me walk through them from hottest to coldest.
>
> Standard is $0.023 per GB per month — 11 nines durability, millisecond access,
> no retrieval fee. Use it for active data: the last 30 days of orders, live user
> sessions, images being actively served. Hot data that gets read all the time.
>
> Standard-IA — Infrequent Access — is $0.0125 per GB per month, but there's a
> $0.01 per GB retrieval fee and a 30-day minimum storage charge. Use this for
> data accessed less than once a month: monthly billing exports, 60-day-old logs.
> The trap: if you put data in IA and then read it heavily, the retrieval fees
> add up fast and exceed the storage savings.
>
> One Zone-IA is $0.01 per GB — same retrieval fee as Standard-IA, but stored in
> only one Availability Zone. If that AZ goes down, data is gone. Use it only for
> reconstructable data: thumbnail images (you can regenerate from originals),
> processed log summaries (you have the raw logs in Bronze).
>
> Glacier Instant Retrieval is $0.004 per GB per month — same milliseconds access
> as Standard, but 90-day minimum storage charge. Use for quarterly reports,
> compliance snapshots that need to be readable immediately but are rarely touched.
>
> Glacier Flexible Retrieval is $0.0036 per GB — retrieval takes minutes to hours.
> Use for annual archives, data you might need once a year but not urgently.
>
> Glacier Deep Archive is $0.00099 per GB per month — the cheapest AWS storage that
> exists. Retrieval is up to 12 hours and costs extra. Use for compliance archives
> that regulations require you to keep for 7 years but you will almost never read.
>
> S3 Intelligent-Tiering monitors each object's access pattern and auto-moves it
> between Standard and cheaper tiers. Small monitoring fee of $0.0025 per 1,000
> objects. Use this when access patterns are unpredictable — say, content on an OTT
> platform where some old episodes suddenly go viral and need Standard speed."

```java
// Java — Apply lifecycle rule via AWS SDK v2
import software.amazon.awssdk.services.s3.S3Client;
import software.amazon.awssdk.services.s3.model.*;

public class S3LifecycleConfig {

    private final S3Client s3Client;

    public void applyOrderLogsLifecycle(String bucketName) {
        LifecycleRule rule = LifecycleRule.builder()
            .id("order-logs-tiering")
            .status(ExpirationStatus.ENABLED)
            .filter(LifecycleRuleFilter.builder()
                .prefix("silver/orders/")
                .build())
            .transitions(
                Transition.builder()
                    .days(30)
                    .storageClass(TransitionStorageClass.STANDARD_IA)
                    .build(),
                Transition.builder()
                    .days(90)
                    .storageClass(TransitionStorageClass.GLACIER_IR)
                    .build(),
                Transition.builder()
                    .days(365)
                    .storageClass(TransitionStorageClass.DEEP_ARCHIVE)
                    .build()
            )
            .expiration(LifecycleExpiration.builder()
                .days(2556)   // 7 years
                .build())
            .build();

        s3Client.putBucketLifecycleConfiguration(
            PutBucketLifecycleConfigurationRequest.builder()
                .bucket(bucketName)
                .lifecycleConfiguration(
                    BucketLifecycleConfiguration.builder()
                        .rules(rule)
                        .build()
                )
                .build()
        );
    }
}

### SECTION 2 — When They Ask: "Why is Parquet so much cheaper for Athena queries?"

> **You say:**
>
> "Athena charges $5 per terabyte scanned. So the goal is to minimize how much
> data Athena reads. Parquet achieves this in two ways: columnar skipping and
> compression.
>
> Consider a billion-row orders table with 50 columns. If I query
> SELECT AVG(price) FROM orders — I only need one column out of fifty.
> With CSV or JSON, every row's 50 columns are stored together. Athena must
> read ALL 50 columns for all 1 billion rows just to extract the price column.
> That's 500GB scanned at $2.50 per query.
>
> With Parquet, the price column is stored contiguously. Athena reads ONLY the
> price column file — the other 49 columns are never touched. That's 10GB scanned
> at $0.05 per query. Same result, 50x cheaper.
>
> Then Parquet adds compression on top. The price column might look like
> [99, 100, 100, 99, 100, 100, 100...]. Parquet uses run-length encoding and
> dictionary encoding — repetitive values compress dramatically. That 10GB
> column might compress to under 1GB. Now you're looking at $0.005 per query
> versus $2.50 — a 500x cost difference.
>
> The second lever is partitioning. If you store S3 files in folders named
> year=2026/month=08/day=31, Athena understands the folder as a partition key.
> A query with WHERE year=2026 AND month=08 AND day=31 skips every other folder
> completely — it reads only that day's data. For a 3-year dataset, a single-day
> query reads 1/1095th of the total data."

```
ROW STORAGE (CSV) vs COLUMNAR STORAGE (PARQUET)
=================================================

  CSV — Row Storage:
  ──────────────────
  Row 1: [order_id=1, user_id=u1, product=phone,  price=999, qty=1, status=paid, ...]
  Row 2: [order_id=2, user_id=u2, product=laptop, price=1299,qty=1, status=paid, ...]
  Row 3: [order_id=3, user_id=u3, product=phone,  price=999, qty=2, status=refund,...]
  ... 1 billion rows ...

  Query: SELECT AVG(price) FROM orders
  Athena must read ALL 50 columns of ALL 1B rows to find the price column
  → 500 GB scanned → $2.50 per query

  PARQUET — Columnar Storage:
  ────────────────────────────
  order_id column: [1, 2, 3, 4, 5, 6 ...]       (stored together)
  user_id column:  [u1, u2, u3, u4 ...]          (stored together)
  price column:    [999, 1299, 999, 799, 999 ...] (stored together) ← Athena reads ONLY this
  status column:   [paid, paid, refund, paid ...] (stored together)
  ...49 other columns stored separately, NEVER READ for AVG(price)...

  Query: SELECT AVG(price) FROM orders
  Athena reads ONLY the price column file
  → 10 GB scanned → $0.05 per query (50x cheaper)

  + COMPRESSION on price column: [999, 1299, 999, 799, 999, 999, 999]
    Run-length: "999 × 3, then 1299 × 1, then 799 × 1, then 999 × 3"
    → 10 GB compresses to ~1 GB → $0.005 per query (500x cheaper than CSV!)

PARTITION PRUNING:
──────────────────
  S3 layout: s3://lake/silver/orders/year=2026/month=08/day=31/part-0001.parquet
                                     year=2026/month=08/day=30/
                                     year=2026/month=07/
                                     year=2025/
                                     year=2024/

  Query: SELECT * FROM orders WHERE year='2026' AND month='08' AND day='31'
  Athena touches ONLY: year=2026/month=08/day=31/ folder
  Everything else (2025, 2024, other months) — NEVER OPENED
  → For 3-year dataset: query 1 day = 1/1095 of total data
```

### SECTION 3 — When They Ask: "How does Athena work and how do you avoid expensive queries?"

> **You say:**
>
> "Athena is AWS-managed Presto — a distributed SQL engine that reads directly
> from S3. No servers to provision, no clusters to start. You point it at an S3
> path, define a schema in the Glue Data Catalog, and run SQL.
>
> The cost control story is all about limiting what Athena scans. Three levers:
> First, Parquet instead of CSV — already covered.
> Second, partitioning — WHERE clauses on partition keys skip entire folder trees.
> Third, Athena Workgroups — you can enforce per-query data scan limits. If a
> junior analyst writes SELECT * without a date filter, the workgroup rejects the
> query at 100GB scan limit instead of running a $50 query.
>
> The operational pattern I use: Athena is asynchronous. You call
> StartQueryExecution and get back a QueryExecutionId immediately. Your API
> doesn't wait — it returns the queryId to the client. The client polls
> GetQueryExecution until status is SUCCEEDED, then calls GetQueryResults.
> This solves the 29-second API Gateway timeout problem for long-running analytics.
>
> For schema management: Glue crawlers scan your S3 data and auto-generate the
> table schema in the Glue Data Catalog. Athena then queries that table. When
> you add new partitions — new day folders — run MSCK REPAIR TABLE or use
> Glue's automatic partition discovery, or call
> ADD PARTITION explicitly."

```

  GET 200 { status: "RUNNING" }               ◄─ { status: "RUNNING" }

  GET /analytics/query/abc ─────────────────►  GetQueryExecution("abc")

  WHY: API Gateway has a hard 29-second timeout. Athena queries over large
  data can take minutes. Async pattern: POST starts query, GET polls status.
  The actual Athena execution happens independently — no timeout risk.

```java
// Athena async query execution — Java AWS SDK v2
import software.amazon.awssdk.services.athena.AthenaClient;
import software.amazon.awssdk.services.athena.model.*;

@Service
public class AthenaQueryService {

    private final AthenaClient athenaClient;

    // Step 1: Start query — returns immediately with queryExecutionId
    public String startQuery(String sql) {
        StartQueryExecutionRequest request = StartQueryExecutionRequest.builder()
            .queryString(sql)
            .queryExecutionContext(QueryExecutionContext.builder()
                .database("silver_db")
                .build())
            .resultConfiguration(ResultConfiguration.builder()
                .outputLocation("s3://data-lake-prod/athena-results/")
                .build())
            .workGroup("analytics-team")   // workgroup enforces scan limits
            .build();

        return athenaClient.startQueryExecution(request).queryExecutionId();
    }

    // Step 2: Poll status — call every 2 seconds from client
    public String getStatus(String queryExecutionId) {
        GetQueryExecutionResponse response = athenaClient.getQueryExecution(
            GetQueryExecutionRequest.builder()
                .queryExecutionId(queryExecutionId)
                .build()
        );
        QueryExecutionStatus status = response.queryExecution().status();
        return status.stateAsString(); // QUEUED, RUNNING, SUCCEEDED, FAILED, CANCELLED
    }

    // Step 3: Fetch results — call only when status == SUCCEEDED
    public List<Map<String, String>> getResults(String queryExecutionId) {
        GetQueryResultsResponse response = athenaClient.getQueryResults(
            GetQueryResultsRequest.builder()
                .queryExecutionId(queryExecutionId)
                .maxResults(1000)
                .build()
        );

        List<ColumnInfo> columns = response.resultSet().resultSetMetadata().columnInfo();
        List<Map<String, String>> rows = new ArrayList<>();

        // First row is header — skip it
        boolean isHeader = true;
        for (Row row : response.resultSet().rows()) {
            if (isHeader) { isHeader = false; continue; }
            Map<String, String> rowMap = new LinkedHashMap<>();
            List<Datum> data = row.data();
            for (int i = 0; i < columns.size(); i++) {
                rowMap.put(columns.get(i).name(), data.get(i).varCharValue());
            }
            rows.add(rowMap);
        }
        return rows;
    }
}

### SECTION 4 — When They Ask: "How do you trigger processing when a file lands in S3?"

> **You say:**
>
> "S3 has a native event notification system. When an object is PUT into a bucket,
> S3 can trigger a Lambda, push to SQS, publish to SNS, or send an event to
> EventBridge. This is the foundation of event-driven file processing.
>
> The simple pattern: customer uploads a CSV → S3 PUT event → Lambda reads
> the CSV → parses rows → writes to DynamoDB. No polling, no cron job.
> The Lambda executes within seconds of the file arriving.
>
> The more powerful pattern is EventBridge routing. Instead of one Lambda for
> all S3 events, EventBridge lets you route by key prefix. Files under orders/
> go to the order Lambda. Files under logs/ go to the log processing Lambda.
> Clean separation without a monolithic routing function.
>
> The resilience pattern: for bursty workloads — 10,000 files arrive in 10 seconds —
> direct S3 to Lambda can overwhelm Lambda concurrency limits. Instead: S3 → SQS
> → Lambda with concurrency control. SQS buffers the events. Lambda polls SQS
> at a controlled rate. If Lambda fails, the message goes to a DLQ for retry."

```
S3 EVENT NOTIFICATION PATTERNS
================================

  SIMPLE: Direct S3 → Lambda
  ────────────────────────────
  [S3 Object PUT]
        │ s3:ObjectCreated:*
        ▼
  [Lambda: ThumbnailGenerator]
  • triggered within seconds
  • event contains: bucket, key, size, ETag
  • Lambda downloads file, generates thumbnail, uploads to output bucket

  ROUTED: S3 → EventBridge → Multiple Lambdas
  ─────────────────────────────────────────────
  [S3 Object PUT]
        │ (EventBridge integration enabled on bucket)
        ▼
  [EventBridge Rule: prefix=orders/]  ──────────► [Lambda: InventoryUpdater]

### SECTION 5 — When They Ask: "What is S3 Select and when do you use it instead of Athena?"

> **You say:**
>
> "S3 Select is a targeted filter within a single S3 object. Think of it as SQL
> pushed down into the S3 storage layer. Instead of downloading a 1GB log file
> to your Lambda or EC2 instance and then filtering it in your code, you send
> S3 a SQL expression and S3 returns only the matching rows — before the data
> ever leaves the storage service.
>
> The distinction from Athena is scope. Athena is for analytics across hundreds
> or thousands of S3 files — a full table scan with GROUP BY and aggregations.
> S3 Select is for filtering within ONE file. You'd use S3 Select if you have a
> 500MB CSV log file in S3 and you want only the rows where status='ERROR'. S3
> filters and returns maybe 20MB. Your Lambda receives 20MB instead of 500MB —
> 97% less data transfer, 97% less Lambda processing time, lower cost.
>
> The use case I hit on the OTT platform: we store daily per-user watch history
> as a large JSON file in S3. A Lambda that generates recommendation email needs
> only one user's history. S3 Select: WHERE userId = '12345' — S3 returns
> that user's 10 records. No need to download the entire 500MB day file."

```
S3 SELECT vs ATHENA — When to Use Which
=========================================

  S3 SELECT                              ATHENA
  ──────────────────────────────────────────────────────────────────────
  ONE file                               MANY files (a full table)
  Filter / extract rows                  Aggregate, join, group by
  Called from Lambda / application       Called for analytics / reporting
  Returns data to your code              Returns result set to query client
  No catalog / schema needed             Requires Glue catalog + DDL
  Billed: per GB scanned in file         Billed: $5 per TB scanned
  Latency: milliseconds                  Latency: seconds to minutes

  EXAMPLE: 1GB error log file in S3
  ──────────────────────────────────
  Without S3 Select:
    Lambda downloads 1GB → filters in memory → finds 5MB of errors
    Data transfer: 1GB, Lambda memory needed: 1GB+, time: 30s

  With S3 Select:
    Lambda sends SQL to S3: SELECT * FROM S3Object WHERE status='ERROR'
    S3 filters internally → returns 5MB to Lambda
    Data transfer: 5MB, Lambda memory needed: 20MB, time: 2s
    Cost: 80% reduction in data scanned

  USE S3 SELECT WHEN:
    ✓ You know the exact file (one object, not a table)
    ✓ You want a subset of rows from that file
    ✓ The filter is simple (WHERE clause, no aggregation)
    ✓ Called from application code at runtime (not analyst ad-hoc)

  USE ATHENA WHEN:
    ✓ Querying a table (hundreds/thousands of Parquet files)
    ✓ You need GROUP BY, COUNT, AVG, JOIN
    ✓ Ad-hoc analytics, BI dashboards, scheduled reports
    ✓ You don't know which files contain the matching data
```

```java
// S3 Select — filter rows within a single S3 object
import software.amazon.awssdk.services.s3.S3Client;
import software.amazon.awssdk.services.s3.model.*;

@Service
public class S3SelectService {

    private final S3Client s3Client;

    public List<String> selectErrorRows(String bucket, String key) throws Exception {
        SelectObjectContentRequest request = SelectObjectContentRequest.builder()
            .bucket(bucket)
            .key(key)
            .expression("SELECT * FROM S3Object s WHERE s.status = 'ERROR'")
            .expressionType(ExpressionType.SQL)
            .inputSerialization(InputSerialization.builder()
                .json(JSONInput.builder()
                    .type(JSONType.LINES)   // newline-delimited JSON (NDJSON)
                    .build())
                .build())
            .outputSerialization(OutputSerialization.builder()
                .json(JSONOutput.builder()
                    .recordDelimiter("\n")
                    .build())
                .build())
            .build();

        List<String> results = new ArrayList<>();

        s3Client.selectObjectContent(request, SelectObjectContentResponseHandler.builder()
            .subscriber(SelectObjectContentResponseHandler.Visitor.builder()
                .onRecords(event -> {
                    String data = event.payload().asUtf8String();
                    results.addAll(Arrays.asList(data.split("\n")));
                })
                .build())
            .build());

        return results;
    }
}

### SECTION 6 — When They Ask: "Explain the data lake architecture you'd use for a large-scale system."

> **You say:**
>
> "I use a three-layer architecture: Bronze, Silver, and Gold. Each layer has
> a distinct purpose and different Athena query patterns.
>
> Bronze is raw, immutable data. Every event arrives exactly as produced —
> no transformation, no filtering. If a CSV has bad columns, they land in
> Bronze as-is. Bronze is the source of truth for replay. If we discover
> a bug in our Silver transformation three months later, we replay Bronze
> through the fixed pipeline. Bronze data is never deleted.
>
> Silver is cleaned, standardized Parquet, partitioned by date and dimension.
> All schemas are normalized. Bad rows are quarantined to a dead-letter S3 path.
> Silver is what Athena queries for most analytics. The transformation from
> Bronze to Silver runs via either Kinesis Firehose inline conversion or an
> AWS Glue ETL job on a schedule.
>
> Gold is pre-aggregated business metrics. A scheduled Glue job reads Silver
> and writes Gold: daily_revenue_by_region, user_cohort_weekly_retention,
> top_content_by_views. Gold files are small and fast — used by BI tools like
> QuickSight that non-technical stakeholders use for dashboards.
>
> The catalog layer is Glue Data Catalog — a Hive-compatible metastore. One
> central place that describes all table schemas, partition definitions, and
> S3 locations. Athena, EMR, and Redshift Spectrum all read from it. A Glue
> crawler runs nightly to discover new partitions added by Firehose."

```
DATA LAKE — BRONZE / SILVER / GOLD LAYERS
==========================================

  BRONZE (raw, immutable)
  ────────────────────────
  s3://lake/raw/service=order-service/year=2026/month=08/day=31/
  - JSON as received from Kinesis Firehose
  - No transformation, schema may vary, bad data included
  - Lifecycle: Standard → IA (30d) → Glacier (365d) → Keep 7 years
  - Never delete until legal retention expires
  - Query frequency: rarely (only for replay / debugging)

       │
       │ Kinesis Firehose (inline Parquet conversion)
       │     OR
       │ AWS Glue ETL Job (scheduled, batch)
       ▼

  ────────────────────────────────────────

  - Bad rows → s3://lake/quarantine/orders/... (separate bucket)
  - Lifecycle: Standard 90 days → Glacier Instant → Deep Archive 5 years
  - Query frequency: daily (analytics, monitoring, investigations)

## COMMON TRAPS — What the Interviewer Wants to Catch You On

```
TRAP 1: No Partition Pruning → Athena Scans Everything → Expensive Bill
─────────────────────────────────────────────────────────────────────────
  Mistake: SELECT * FROM orders WHERE status='ERROR'
  Problem: status is not a partition key — Athena scans ALL partitions
           For 3 years of data: scans every file for all 1095 days
  Fix:     Always include partition keys in WHERE:
           WHERE year='2026' AND month='08' AND status='ERROR'
           Athena skips 1094 day-partitions, reads only today's data
  Rule:    If your query doesn't filter on partition columns, it is
           a full table scan. Always include year/month/day in WHERE.

TRAP 2: Storing CSV in S3, Querying with Athena — Expensive
─────────────────────────────────────────────────────────────
  Mistake: Firehose delivers raw JSON/CSV to S3, Athena queries it
  Problem: Athena scans all bytes of every row even for a 2-column SELECT
           1TB of CSV at $5/TB = $5 per query
  Fix:     Convert to Parquet BEFORE query time
           Firehose: enable "Record format conversion" → Parquet
           Glue ETL: Bronze JSON → Silver Parquet as scheduled job
           Then: 1TB CSV → ~100GB Parquet → $0.50 per query (10x saving)

TRAP 3: Glacier Retrieval Fees and Delays Catch You Off-Guard
─────────────────────────────────────────────────────────────
  Mistake: Assume Glacier data is instantly readable like Standard
  Problem: Deep Archive = up to 12 hours to restore PLUS a retrieval fee
           Flexible Retrieval = minutes to 12 hours
           If a compliance request comes in and data is Deep Archive,
           you cannot deliver it for 12 hours — a legal problem.
  Fix:     Glacier Instant Retrieval for data that must be readable same-day
           Deep Archive only for data you will NEVER need urgently
           Test your restore process annually — don't discover 12h delay
           during an actual compliance audit.

TRAP 4: Standard-IA 30-Day Minimum Storage Charge
───────────────────────────────────────────────────
  Mistake: Move objects to Standard-IA at Day 1 to save costs
  Problem: AWS charges you for 30 days minimum even if you delete at Day 5
           Lifecycle rule: transition after 30 days NOT at creation
           Short-lived objects (< 30 days) in IA cost MORE than Standard
  Fix:     Lifecycle rule transition: minimum Days: 30 for Standard-IA
           One Zone-IA also has 30-day minimum
           Glacier IR has 90-day minimum

TRAP 5: Forgetting MSCK REPAIR TABLE After New Partitions
──────────────────────────────────────────────────────────
  Mistake: Firehose writes new day folder: year=2026/month=08/day=31/
           Team runs Athena query for that day — returns 0 rows
  Problem: Athena's partition metadata in Glue catalog is stale
           It doesn't know the new folder exists until told
  Fix (option A): MSCK REPAIR TABLE silver_db.orders;
                  (scans S3, adds all missing partitions — slow on large tables)
  Fix (option B): ALTER TABLE silver_db.orders ADD PARTITION
                  (year='2026', month='08', day='31')
                  LOCATION 's3://lake/silver/orders/year=2026/month=08/day=31/'
                  (fast, specific)
  Fix (option C): Glue crawler nightly on the bucket (automatic)
  Fix (option D): Firehose partition discovery via EventBridge automation

TRAP 6: The Small File Problem — Thousands of Tiny Files
──────────────────────────────────────────────────────────
  Mistake: Firehose writes 1KB Parquet files every 60 seconds (low buffer)
           After 1 year: millions of tiny files in S3
  Problem: Athena opens each file individually to read its metadata/header.
           1 million 1KB files = 1 million S3 GET requests = 1 million
           metadata reads before any data is read → query takes 5 minutes
           for what should be a 10-second query.
  Fix:     Increase Firehose buffer: 128MB or 5 minutes before flushing
           Run a daily Glue compaction job: read many small files → write
           one large Parquet file per partition → small files become history
  Target:  Files should be 128MB - 1GB each (Athena sweet spot)
           Fewer, larger files = faster Athena queries

TRAP 7: S3 Select vs Athena Confusion
───────────────────────────────────────
  Mistake: Using Athena to filter a single known S3 file (overkill)
           Using S3 Select to query across 1000 Parquet files (impossible)
  Rule:    S3 Select = one file, filter rows, return to your code at runtime
           Athena = many files, SQL analytics, for analysts and BI tools
  Example: Lambda needs to read one user's data from today's log file
           → S3 Select (fast, cheap, single file)
           Analyst wants to see all errors across all services last month
           → Athena (many files, SQL aggregation)

TRAP 8: Glue Crawler Cost at High Frequency
─────────────────────────────────────────────
  Mistake: Schedule Glue crawler to run every 5 minutes (to detect new partitions)
  Problem: Glue crawler charges per DPU-hour. Running every 5 min on a large
           bucket = crawler running almost continuously = significant cost
  Fix:     Run Glue crawler once per day (nightly) — new partitions discovered
           within 24 hours.
           For real-time partition discovery: use ALTER TABLE ADD PARTITION
           called by the Lambda or job that creates the partition — instant
           and free (it's just an API call to Glue catalog).
```

## Interview Cheat Sheet (Say This Confidently)

> "For S3 data lake architecture in production: I use three layers — Bronze for raw immutable ingestion via Kinesis Firehose, Silver for Parquet-converted partitioned data queryable by Athena, and Gold for pre-aggregated metrics consumed by QuickSight. Lifecycle rules automate cost: Standard for 30 days, Standard-IA at 30 days, Glacier Instant at 90 days, Deep Archive at 365 days for compliance retention. The biggest Athena cost trap is forgetting partition pruning — always include year/month/day in WHERE clauses or a single query scans years of data at $5/TB. Parquet versus CSV is a 10x to 100x cost difference because Athena reads only the columns you SELECT, not the entire row. Athena is async — StartQueryExecution returns immediately, you poll GetQueryExecution for status, which solves the 29-second API Gateway timeout for analytics endpoints. S3 Select is different from Athena: it filters within a single file and returns data to your application code — use it when you know exactly which file you need and want only a subset of rows. Small file problem is real: Firehose on low buffer settings creates millions of tiny files that slow Athena dramatically — buffer to 128MB and run daily compaction jobs. After adding new S3 partitions, always run MSCK REPAIR TABLE or use ALTER TABLE ADD PARTITION — otherwise Athena returns zero rows from new data."
