### PART 2 — When They Ask: "So how does the SDK actually get the credentials then?"

> **You say:**
>
> "AWS runs a special HTTP server inside every EC2 instance at a fixed IP address —
> 169.254.169.254. This is called the Instance Metadata Service, or IMDS.
>
> It's only reachable from inside the instance — not from the internet, not from
> outside. When the AWS SDK initializes, it calls this endpoint and gets back
> temporary credentials that expire every 6 hours and rotate automatically.
>
> Here's the exact chain the SDK runs..."

```
SDK CREDENTIAL PROVIDER CHAIN — What happens when S3Client.builder().build() runs
===================================================================================

  S3Client.builder().build()
          |
          v
  +-----------------------------------------------+
  |  DefaultCredentialsProvider runs this chain:  |
  |                                               |
  |  1. Java system properties                    |
  |     -Daws.accessKeyId=?   --> NOT SET         |
  |                                               |
  |  2. Environment variables                     |
  |     AWS_ACCESS_KEY_ID=?   --> NOT SET in prod |
  |                                               |
  |  3. ~/.aws/credentials file                   |
  |     exists?               --> NO (on EC2)     |
  |                                               |
  |  4. EC2 Instance Metadata (IMDS)              |
  |     http://169.254.169.254 --> ✅ FOUND!      |
  +-----------------------------------------------+
          |
          | HTTP GET
          v
  +-----------------------------------------------+
  |  IMDS Response (auto-generated by AWS):       |
  |  {                                            |
  |    "AccessKeyId":     "ASIA3FLIPKART...",     |
  |    "SecretAccessKey": "wJalrXUtnFE...",       |
  |    "Token":           "AQoDYXdz...",          |
  |    "Expiration":      "2026-08-19T10:00:00Z"  |

  |                                               |
  |  ⚠ These rotate EVERY 6 HOURS automatically  |
  |  ⚠ Even if stolen, they expire soon          |
  +-----------------------------------------------+
          |
          v
  SDK uses these temp creds for all S3 API calls
```

**AwsConfig.java**

```java
@Configuration
public class AwsConfig {

    @Value("${aws.region}")
    private String region;

    @Bean
    public S3Client s3Client() {
        return S3Client.builder()
            .region(Region.of(region))
            // No credentials here.
            // On EC2: SDK calls http://169.254.169.254 automatically
            // On local dev: SDK reads ~/.aws/credentials
            .build();
    }

    @Bean
    public S3Presigner s3Presigner() {
        return S3Presigner.builder()
            .region(Region.of(region))
            .build();
    }
}
```

**ProductImageService.java**

```java
@Service
public class ProductImageService {

    private final S3Client s3Client;
    private final S3Presigner s3Presigner;

    @Value("${s3.bucket.name}")        // flipkart-product-images
    private String bucketName;

    public ProductImageService(S3Client s3Client, S3Presigner s3Presigner) {
        this.s3Client = s3Client;
        this.s3Presigner = s3Presigner;
    }

    // SCENARIO 1: Generate presigned URL so browser uploads directly to S3
    // Used for: seller product image uploads
    public String generateUploadUrl(String productId, String fileName) {
        String s3Key = "products/" + productId + "/" + fileName;

        return s3Presigner.presignPutObject(r -> r
                .signatureDuration(Duration.ofMinutes(10))  // URL valid for 10 mins
                .putObjectRequest(q -> q
                    .bucket(bucketName)
                    .key(s3Key)
                    .contentType("image/jpeg")))
            .url()
            .toString();
        // Returns: https://flipkart-product-images.s3.amazonaws.com/products/123/img.jpg?X-Amz-Signature=...
    }

    // SCENARIO 2: Generate presigned GET URL so user can view product image
    // Used for: product detail page image loading
    public String generateDownloadUrl(String s3Key) {
        return s3Presigner.presignGetObject(r -> r
                .signatureDuration(Duration.ofHours(1))
                .getObjectRequest(q -> q.bucket(bucketName).key(s3Key)))
            .url()
            .toString();
    }

    // SCENARIO 3: Large file upload via server (e.g. bulk catalog import CSV)
    // S3TransferManager handles multipart automatically for files > 8MB
    public void uploadCatalogFile(String sellerId, Path csvFilePath) {
        String s3Key = "catalog-imports/" + sellerId + "/" + csvFilePath.getFileName();

        try (S3TransferManager transferManager = S3TransferManager.builder()
                .s3Client(S3AsyncClient.builder()
                    .region(Region.of("ap-south-1"))
                    .build())
                .build()) {

            FileUpload upload = transferManager.uploadFile(r -> r
                .putObjectRequest(p -> p.bucket(bucketName).key(s3Key))
                .source(csvFilePath));

            upload.completionFuture().join();  // blocks until upload completes
        }
    }
}
```

**ProductController.java**

```java
@RestController
@RequestMapping("/api/products")
public class ProductController {

    private final ProductImageService imageService;

    // Seller requests an upload URL (doesn't send the file here)
    @PostMapping("/{productId}/image-upload-url")
    public ResponseEntity<Map<String, String>> getUploadUrl(
            @PathVariable String productId,
            @RequestParam String fileName) {

        String uploadUrl = imageService.generateUploadUrl(productId, fileName);

        return ResponseEntity.ok(Map.of(
            "uploadUrl", uploadUrl,
            "expiresInMinutes", "10"
        ));
    }
}
```

### PART 4 — When They Ask: "Why presigned URL instead of uploading through your server?"

> **You say:**
>
> "Great question — this is a classic interview point. Let me draw this out."

```
WITHOUT PRESIGNED URL (Bad in Prod)
=====================================

  Seller Browser
       |
       |  POST /upload  (image bytes — maybe 5MB)
       v
  +------------------+
  | Spring Boot App  |  <-- handles ALL the bytes
  | EC2 (4GB RAM)    |  <-- 10,000 sellers uploading = OOM
  +------------------+
       |
       |  SDK PutObject (bytes again)
       v
  +-----------+
  |    S3     |
  +-----------+

  PROBLEMS:
  - App server memory fills up fast
  - Double bandwidth: browser→server + server→S3
  - Upload speed limited by EC2's bandwidth
  - EC2 costs scale with traffic


WITH PRESIGNED URL (Correct in Prod)
======================================

  Seller Browser
       |
       |  POST /api/products/123/image-upload-url
       |  (just filename, no bytes)
       v
  +------------------+
  | Spring Boot App  |  <-- generates signed URL in <5ms
  | (barely any CPU) |  <-- returns URL, done
  +------------------+
       |
       |  Returns: { "uploadUrl": "https://s3.aws.../...?X-Amz-Signature=abc" }
       v
  Seller Browser
       |
       |  PUT https://s3.aws.../...?X-Amz-Signature=abc
       |  (direct to S3, server not involved)
       v
  +-----------+
  |    S3     |  <-- handles all the bandwidth
  +-----------+

  BENEFITS:
  - App server handles zero bytes
  - S3 absorbs all bandwidth (scales infinitely)
  - Faster uploads (direct path to S3)
  - EC2 costs stay flat regardless of upload volume
```

> **You say:**
>
> "So in Flipkart's case, during a Big Billion Days sale, hundreds of thousands of
> sellers are updating their product images. Without presigned URLs, every image byte
> would flow through their app servers. That's impossible to scale. With presigned URLs,
> the app server just generates a signed URL — that takes microseconds — and S3 handles
> everything else."

```
MULTIPART UPLOAD FLOW — Flipkart Bulk Catalog Import
======================================================

  Seller uploads: catalog_500MB.csv

  S3TransferManager automatically does this:
  |
  +-- Step 1: Initiate Multipart Upload
  |   POST /catalog.csv?uploads
  |   S3 returns: UploadId = "VXBsb2FkIElE..."
  |
  +-- Step 2: Upload Parts in Parallel (default 8MB per part)
  |
  |   Part 1 (bytes   0 -   8MB)  ----\
  |   Part 2 (bytes   8 -  16MB)  -----\
  |   Part 3 (bytes  16 -  24MB)  ------+---> S3 (parallel threads)

      { parts: [{partNumber:1, eTag:"..."}, ...] }

  YOUR CODE: Just this (TransferManager handles everything above)
  ---------------------------------------------------------------
  transferManager.uploadFile(r -> r
      .putObjectRequest(p -> p.bucket(bucket).key("catalog.csv"))

    .completionFuture().join();
```

> "The nice thing about TransferManager is I don't write any of that multipart logic.

### EC2 vs EKS — Side by Side

```
EC2 (IAM Instance Profile)          EKS (IRSA — IAM Roles for Service Accounts)
============================         =============================================

  AWS attaches IAM role                AWS attaches IAM role
  to the EC2 machine                   to a Kubernetes ServiceAccount
         |                                      |
  SDK calls IMDS:                      AWS injects a token FILE into the pod:
  http://169.254.169.254               /var/run/secrets/eks.amazonaws.com/
         |                               serviceaccount/token

         |                             SDK reads env vars:

  S3 call authenticated                AWS_ROLE_ARN=arn:aws:iam::123:role/...
                                                |
                                       SDK calls STS:
                                       AssumeRoleWithWebIdentity(token, roleArn)
                                                |
                                       Gets temp credentials
                                                |
                                                v
                                       S3 call authenticated

```

### How IRSA Is Set Up (DevOps does this, not your Java code)

```
STEP 1 — Create IAM Role with Web Identity Trust
=================================================

  IAM Role: flipkart-seller-service-eks-role

  Trust Policy:
  {
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::123456789:oidc-provider/oidc.eks.ap-south-1.amazonaws.com/..."
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "oidc.eks.../...:sub": "system:serviceaccount:flipkart:seller-service-sa"
      }
    }
  }

  Permission Policy (same as EC2):
  s3:PutObject, s3:GetObject on flipkart-product-images/*


STEP 2 — Annotate Kubernetes ServiceAccount
============================================

  # kubernetes/serviceaccount.yaml
  apiVersion: v1
  kind: ServiceAccount
  metadata:
    name: seller-service-sa
    namespace: flipkart
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::123456789:role/flipkart-seller-service-eks-role
                                  ^--- This is the only config needed


STEP 3 — Pod uses that ServiceAccount
======================================

  # kubernetes/deployment.yaml
  spec:
    serviceAccountName: seller-service-sa   <-- attach here
    containers:
      - name: seller-service
        image: flipkart/seller-service:latest
        # No env vars for credentials. No secrets mounted.
        # AWS automatically injects the token file into the pod.
```

## ARCH-1: VPC Endpoint for S3

### When They Ask: "How does your EC2/EKS talk to S3 — does traffic go over the internet?"

> **You say:**
>
> "No, and this is an important architecture decision. By default, S3 calls from EC2
> go over the public internet — which means latency, NAT gateway costs, and potential
> exposure. In production at Flipkart scale, you set up a VPC Gateway Endpoint for S3.
> This creates a private route inside the AWS network — traffic never leaves AWS at all.
>
> It has three benefits: no NAT gateway cost (which can be massive at high throughput),
> lower latency since traffic stays on AWS backbone, and you can write a bucket policy
> that ONLY allows access from the VPC — so even if credentials leak, S3 is unreachable
> from outside."

```
WITHOUT VPC ENDPOINT (Default — Bad for Prod)
===============================================

  EC2 / EKS Pod
       |
       | S3 SDK call
       v
  +--------------+
  | NAT Gateway  |  <-- costs money per GB ($0.045/GB)
  +--------------+
       |
       | Public Internet
       v
  +-----------+
  |    S3     |
  +-----------+

  Problems:
  - NAT Gateway cost: at 1TB/day = ~$45/day = ~$1,350/month
  - Traffic goes over public internet (exposure risk)
  - Higher latency


WITH VPC GATEWAY ENDPOINT (Correct Prod Setup)
================================================

  EC2 / EKS Pod
       |
       | S3 SDK call (same code, nothing changes)
       v
  +----------------------+
  | VPC Route Table      |
  | Destination: S3      |
  | Target: vpce-xxx     |  <-- Gateway Endpoint
  +----------------------+
       |
       | AWS Private Network (never leaves AWS)
       v
  +-----------+
  |    S3     |
  +-----------+

  Benefits:
  - Zero NAT Gateway cost for S3 traffic
  - Traffic stays on AWS backbone (faster)
  - Bucket policy can enforce VPC-only access

  Setup (Terraform, done once by DevOps):
  ----------------------------------------
  resource "aws_vpc_endpoint" "s3" {
    vpc_id       = aws_vpc.main.id
    service_name = "com.amazonaws.ap-south-1.s3"
    route_table_ids = [aws_route_table.private.id]
  }

  Bucket Policy (enforces VPC-only):
  ------------------------------------
  {
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:*",
    "Condition": {
      "StringNotEquals": {
        "aws:sourceVpce": "vpce-xxxxxxxx"
      }
    }
  }

  Spring Boot code: ZERO changes needed.
  SDK automatically uses the VPC route.
```

**One-liner:**
> "VPC Gateway Endpoint routes all S3 traffic over the AWS private network — no NAT
> cost, lower latency, and the bucket policy can enforce that S3 is only reachable
> from inside the VPC."

### When They Ask: "How does Flipkart serve product images to 300 million users?"

>
> "S3 alone can't handle that read volume efficiently — every request would hit S3
> directly, and users in Chennai would fetch from Mumbai S3, users in Delhi too.
> The answer is CloudFront in front of S3.
>
> CloudFront is AWS's CDN — it has edge locations across India and globally. Product
> images are cached at the edge closest to the user. After the first request, S3 is
> never hit again until the cache expires. At Flipkart scale, maybe 95% of image
> reads are served from CloudFront cache — S3 only handles the 5% cache misses."

```
WITHOUT CLOUDFRONT
====================

  User in Chennai          User in Delhi           User in Bangalore
       |                        |                        |
       |                        |                        |
       +------------------------+------------------------+
                                |
                                | ALL requests hit S3 directly
                                v
                     +--------------------+
                     | S3 Mumbai          |
                     | (origin)           |
                     +--------------------+

  Problems:
  - S3 handles EVERY read request
  - Latency same for all users (no geo-distribution)
  - S3 request costs add up (per-request pricing)


WITH CLOUDFRONT (Prod Setup)
==============================

  User in Chennai          User in Delhi           User in Bangalore
       |                        |                        |
       v                        v                        v
  +----------+           +----------+           +----------+
  | CF Edge  |           | CF Edge  |           | CF Edge  |
  | Chennai  |           | Delhi    |           | Bangalore|
  +----------+           +----------+           +----------+
  Cache hit? YES          Cache hit? YES          Cache hit? NO
  Return cached           Return cached                |
  image instantly         image instantly              | Cache miss
  (no S3 hit)             (no S3 hit)                  v
                                              +--------------------+
                                              | S3 Mumbai (origin) |
                                              | Fetch + cache it   |
                                              +--------------------+

  Result:
  - ~95% requests served from edge cache (milliseconds)
  - S3 only handles ~5% (cache misses)
  - Users get images from nearest edge location
  - S3 request costs drop by 95%

  URL structure:
  Without CDN:  https://flipkart-images.s3.ap-south-1.amazonaws.com/products/123/img.jpg
  With CDN:     https://images.flipkart.com/products/123/img.jpg
                (CNAME pointing to CloudFront distribution)
```

**Spring Boot code — return CDN URL instead of S3 URL:**

```java

    @Value("${cdn.base.url}")           // https://images.flipkart.com
    private String cdnBaseUrl;

    // For uploads — still use presigned S3 URL (upload goes directly to S3 origin)
    public String generateUploadUrl(String productId, String fileName) {
        // ... same presigned PUT code as before
    }
}
```

```
# application.properties
cdn.base.url=https://images.flipkart.com
s3.bucket.name=flipkart-product-images
```

**One-liner:**
> "CloudFront sits in front of S3 as a CDN. 95% of image reads are served from the
> nearest edge location — S3 only handles cache misses. My code just returns the CDN
> URL for reads and the presigned S3 URL for uploads."

## ARCH-4: Encryption at Rest — SSE-S3 vs SSE-KMS

### When They Ask: "How do you protect data at rest in S3?"

> **You say:**
>
> "S3 supports multiple encryption options. For most production use cases we use
> SSE-KMS — Server Side Encryption with KMS managed keys. Let me explain the
> difference and why KMS matters at Flipkart scale."

```
ENCRYPTION OPTIONS COMPARISON
================================

  SSE-S3 (Simple, less control)
  --------------------------------
  - AWS manages the key entirely
  - No audit trail of who decrypted what
  - No key rotation control
  - Good for: non-sensitive data, logs, analytics

  SSE-KMS (Production standard)
  --------------------------------
  - You create the key in AWS KMS
  - Every S3 read/write logs to CloudTrail (who accessed what, when)
  - Key rotation configurable (annually automatic)
  - You can REVOKE the key → instant data lockout
  - Good for: user PII, payment data, product catalog


ENCRYPTION FLOW WITH SSE-KMS
==============================

  Spring Boot uploads file:
  |
  | PutObject request + file bytes
  v
  +------------------------+
  | S3                     |
  | 1. Calls KMS: generate |
  |    data encryption key |
  +------------------------+
            |
            | GenerateDataKey API call
            v
  +------------------------+
  | AWS KMS                |
  | Returns:               |
  | - plaintext key        |
  | - encrypted key        |
  +------------------------+
            |
  S3 uses plaintext key to encrypt your file
  S3 stores encrypted key alongside the object
  S3 discards plaintext key immediately

  On download:
  S3 → KMS: decrypt this key → KMS returns plaintext → S3 decrypts file → you get bytes
  CloudTrail logs: "seller-service-role decrypted object products/123/img.jpg at 14:32"
```

**Spring Boot code — specify KMS key on upload:**

```java
public void uploadEncrypted(String bucket, String key, byte[] data, String kmsKeyId) {
    s3Client.putObject(
        PutObjectRequest.builder()
            .bucket(bucket)
            .key(key)
            .serverSideEncryption(ServerSideEncryption.AWS_KMS)
            .ssekmsKeyId(kmsKeyId)   // arn:aws:kms:ap-south-1:123:key/abc-def
            .build(),
        RequestBody.fromBytes(data)
    );
}
```

```
# application.properties
s3.kms.key.id=arn:aws:kms:ap-south-1:123456789:key/abc-def-ghi
```

**One-liner:**
> "SSE-KMS encrypts every object using a KMS-managed key. Every decrypt is logged in
> CloudTrail — full audit trail of who accessed what. You can also revoke the key and
> instantly lock out all access to the data."

## ARCH-5: Bucket Policy vs IAM Policy — Two Layers of Access Control

### When They Ask: "What's the difference between bucket policy and IAM policy?"

> **You say:**
>
> "This comes up a lot. There are two layers of access control in S3, and both must
> allow the action for it to succeed. Think of it as two doors — IAM policy is the
> first door, bucket policy is the second. You need both open."

```
TWO-LAYER ACCESS CONTROL
==========================

  Spring Boot App (identity: flipkart-seller-service-role)
       |
       | s3:PutObject request
       v
  +-------------------------------+
  | DOOR 1: IAM Policy Check      |
  | "Does this IAM role have      |
  |  s3:PutObject permission?"    |
  |                               |
  | IAM Policy on role says:      |
  | Allow s3:PutObject on         |
  | flipkart-product-images/*     |
  |                               |
  | Result: ✅ ALLOWED            |
  +-------------------------------+
       |
       v
  +-------------------------------+
  | DOOR 2: Bucket Policy Check   |
  | "Does the bucket allow this   |
  |  principal to PutObject?"     |
  |                               |
  | Bucket Policy says:           |
  | Allow s3:PutObject only from  |
  | flipkart-seller-service-role  |
  | AND only from VPC endpoint    |
  |                               |
  | Result: ✅ ALLOWED            |
  +-------------------------------+
       |
       v
  Upload succeeds


  DENY OVERRIDES EVERYTHING:
  If EITHER policy has an explicit Deny → access blocked
  regardless of what the other policy says.


WHEN TO USE WHICH
==================

  IAM Policy          → control what your APP can do
                        (attached to role/user)
                        "seller-service-role can PutObject"

  Bucket Policy       → control who can access YOUR BUCKET
                        (attached to bucket)
                        "only VPC traffic allowed"
                        "only specific roles allowed"
                        "block all public access"
                        "enforce encryption on upload"

  Both together       → defence in depth
  Flipkart example    → IAM allows seller-service to upload
                        Bucket policy denies all non-VPC traffic
                        Result: even with valid creds,
                        upload from internet is blocked
```

**One-liner:**
> "IAM policy controls what the identity can do, bucket policy controls who can access
> the bucket. Both must allow the action. Bucket policy is your last line of defence —
> you can enforce VPC-only access or encryption regardless of what IAM says."

## ARCH-6: Error Handling + Retry in Spring Boot

### When They Ask: "How do you handle S3 failures in production?"

> **You say:**
>
> "S3 is highly reliable but not infallible. Network blips, throttling, temporary
> outages — these happen. The SDK has built-in retry with exponential backoff, but
> you need to know what's retryable and what's not, and handle it correctly in your
> service."

```
S3 EXCEPTION HIERARCHY
========================

  SdkException (base)
  |
  +-- SdkClientException     → problem on YOUR side
  |   Examples:              → NOT retryable
  |   - No network           → check your code/infra
  |   - File not found
  |   - Invalid bucket name
  |
  +-- S3Exception            → problem reported by S3
      |
      +-- 4xx errors         → NOT retryable (your fault)
      |   - 403 Forbidden    → IAM/bucket policy wrong
      |   - 404 Not Found    → object doesn't exist
      |   - 400 Bad Request  → invalid params
      |
      +-- 5xx errors         → RETRYABLE (S3's fault)
          - 500 InternalError
          - 503 SlowDown (throttling)


SDK DEFAULT RETRY BEHAVIOR
============================

  Attempt 1: fails with 503 SlowDown
  Wait: 100ms
  Attempt 2: fails with 503 SlowDown
  Wait: 200ms
  Attempt 3: fails with 503 SlowDown
  Wait: 400ms
  Attempt 4: succeeds ✅

  Default: 3 retries, exponential backoff
  Configurable per client
```

**Spring Boot code — production error handling:**

```java
@Service
public class ProductImageService {

    private static final Logger log = LoggerFactory.getLogger(ProductImageService.class);

    public void uploadFile(String bucket, String key, byte[] data) {
        try {
            s3Client.putObject(
                PutObjectRequest.builder().bucket(bucket).key(key).build(),
                RequestBody.fromBytes(data)
            );
        } catch (S3Exception e) {
            if (e.statusCode() == 403) {
                // IAM role or bucket policy issue — alert the team, don't retry
                log.error("S3 access denied for key={} httpStatus=403. Check IAM role.", key);
                throw new StorageAccessDeniedException("S3 permission error", e);
            }
            // 5xx: SDK already retried 3 times. If still failing, propagate.
            log.error("S3 upload failed after retries key={} status={}", key, e.statusCode());
            throw new StorageException("S3 upload failed", e);

        } catch (SdkClientException e) {
            // Network/config issue on our side
            log.error("S3 client error (network/config) key={}", key, e);
            throw new StorageException("S3 client error", e);
        }
    }

    // Custom retry config on the client (if you need more retries than default)
    @Bean
    public S3Client s3Client() {
        return S3Client.builder()
            .region(Region.of("ap-south-1"))
            .overrideConfiguration(c -> c
                .retryPolicy(r -> r.numRetries(5)))  // 5 retries instead of default 3
            .build();
    }
}
```

**One-liner:**
> "The SDK retries 5xx errors automatically with exponential backoff. In application code
> I catch S3Exception vs SdkClientException separately — 403 means IAM config problem
> so I alert the team, 5xx means transient S3 issue and I surface it after SDK retries
> exhaust."

## TRAP-1 — "You set a presigned URL expiry of 7 days. Will it work?"

> **Interviewer asks:**
> "I see you're generating presigned URLs. If I set the expiry to 7 days, is that fine?"

> **You say:**
>
> "Actually — this is a trap that burns a lot of teams in production. The answer
> depends on what's signing the URL. If you're signing with an IAM user access key,
> yes, you can go up to 7 days. But in production we never use IAM user keys — we use
> IAM roles on EC2 or IRSA on EKS. And roles issue temporary credentials that max out
> at 12 hours.
>
> So even if my code says Duration.ofDays(7), the URL will silently break after 12
> hours — because the underlying credential that signed it has expired. S3 sees an
> expired signature and returns 403. No warning, no exception at generation time.
>
> In production, I keep upload URLs at 15 minutes and download URLs at 1 hour. If a
> user needs longer access — say a download link we email them — I build a redirect
> endpoint that generates a fresh presigned URL on every click."

## TRAP-2 — "Your EC2 has the correct IAM role but you're still getting 403. Why?"

> **Interviewer asks:**
> "The IAM role is attached, the policy looks right, but S3 is returning 403.
> How do you debug this?"

> **You say:**
>
> "This happens in production more than you'd think, and it's almost never just the
> IAM policy. There are five places that can cause a 403, and I'd check them in order.
>
> First — bucket policy. IAM allows the role, but the bucket policy has an explicit
> Deny. Explicit Deny always wins. Most common case: we added a VPC-only restriction
> to the bucket policy, and someone is testing from their laptop outside the VPC.
>
> Second — Block Public Access. If the bucket policy tries to grant public access but
> Block Public Access is on at the bucket level, S3 overrides everything with 403.
>
> Third — SCP, Service Control Policy. If the AWS account is in an Organization and
> the platform team added an org-level Deny, it overrides IAM and bucket policy both.
> This one is invisible to the app team — you need the cloud platform team to check it.
>
> Fourth — KMS key policy. If the bucket uses SSE-KMS, the IAM role needs separate
> permission on the KMS key itself — kms:GenerateDataKey for writes, kms:Decrypt for
> reads. The IAM role can be perfect but if the KMS key policy does not allow it, you
> get 403. This is the most commonly missed one in prod.
>
> Fifth — ARN mismatch. ListBucket needs the bucket ARN without the slash-star.
> PutObject needs it with slash-star. Getting these mixed up gives 403 for specific
> operations only."

```
403 DIAGNOSIS TREE — CHECK IN THIS ORDER
==========================================

  EC2 (role attached) → S3 SDK call → 403 Forbidden

  +----------------------------------------------------------+
  | CHECK 1: Bucket Policy — explicit Deny?                  |
  |  aws s3api get-bucket-policy --bucket flipkart-images    |
  |  Look for: "Effect": "Deny"                              |
  |  Common: Deny if not from VPC — local test hits this     |
  +----------------------------------------------------------+
       | No Deny found
       v
  +----------------------------------------------------------+
  | CHECK 2: Block Public Access                             |
  |  aws s3api get-public-access-block --bucket ...          |
  |  BlockPublicPolicy=true + policy grants public = 403     |
  |  Fix: never grant public — use presigned URLs            |
  +----------------------------------------------------------+
       | Not the issue
       v
  +----------------------------------------------------------+
  | CHECK 3: SCP — Service Control Policy (org level)        |
  |  Ask cloud platform team to check org policies           |
  |  Denies here OVERRIDE all IAM and bucket policy          |
  |  Not fixable by app team                                 |
  +----------------------------------------------------------+
       | No SCP blocking
       v
  +----------------------------------------------------------+
  | CHECK 4: KMS Key Policy  <-- MOST COMMONLY MISSED        |
  |  Bucket uses SSE-KMS?                                    |
  |  IAM role needs BOTH on the KMS key ARN:                 |
  |  - kms:GenerateDataKey (for PutObject)                   |
  |  - kms:Decrypt         (for GetObject)                   |
  |  Perfect IAM S3 policy + missing KMS = 403               |
  +----------------------------------------------------------+
       | KMS policy is fine
       v
  +----------------------------------------------------------+
  | CHECK 5: ARN Mismatch in IAM Policy                      |
  |  WRONG:                                                  |
  |  s3:ListBucket on arn:aws:s3:::bucket/*   (/* is wrong)  |
  |  s3:PutObject  on arn:aws:s3:::bucket     (/* missing)   |
  |                                                          |
  |  CORRECT:                                                |
  |  s3:ListBucket on arn:aws:s3:::bucket     (no /*)        |
  |  s3:PutObject  on arn:aws:s3:::bucket/*   (with /*)      |
  +----------------------------------------------------------+
```

**One-liner:**
> "Five causes in order: bucket policy Deny, Block Public Access, org-level SCP,
> missing KMS key permission, ARN mismatch. The KMS one is most missed in prod."

## TRAP-4 — "Two sellers upload to the same S3 key at the same time. What happens?"

> **Interviewer asks:**
> "What if two sellers both upload products/123/cover.jpg simultaneously?"

> **You say:**
>
> "Last write wins — and both sellers get a 200 OK. Neither gets an error. One image
> is silently dropped. That is the dangerous part — there is no signal that data was lost.
>
> But honestly, if this is happening in prod it is a key design problem, not an S3
> problem. We should never have two sellers writing to the same S3 key. The fix is to
> make the key unique by construction — include the seller ID and a UUID in every key.
> Something like: products/{productId}/{sellerId}/{uuid}.jpg
>
> Now it is physically impossible for two uploads to collide because every key is unique.
>
> Versioning is the safety net on top of that — if somehow two writes do land on the
> same key, versioning preserves both. You can roll back to any previous version. But
> I design the key structure so it never happens in the first place."

```
CONCURRENT WRITE — KEY DESIGN IS THE REAL FIX
===============================================

  BAD KEY DESIGN — collision possible:
  --------------------------------------
  Seller A: PUT products/123/cover.jpg  (14:00:01.100)
  Seller B: PUT products/123/cover.jpg  (14:00:01.150)

  S3: last write wins
  Seller A's image: gone. Both callers: HTTP 200. No error.


  GOOD KEY DESIGN — collision impossible:
  ----------------------------------------
  Seller A: PUT products/123/sellerA001/a3f8-uuid.jpg
  Seller B: PUT products/123/sellerB002/c9d1-uuid.jpg

  Different keys. Both stored. No collision. No data loss.


  Spring Boot key generation:
  ----------------------------
  public String generateS3Key(String productId, String sellerId, String fileName) {
      String ext = fileName.substring(fileName.lastIndexOf('.'));
      return "products/" + productId + "/" + sellerId
             + "/" + UUID.randomUUID() + ext;
  }
  // products/123/sellerA001/3f8a9c2d-4b5e-uuid.jpg
  // Globally unique every time.


  VERSIONING — safety net if keys do collide:
  ---------------------------------------------
  Version 1 (Seller A):  versionId = "aaa111"
  Version 2 (Seller B):  versionId = "bbb222"

  GET products/123/cover.jpg              -> returns bbb222 (latest)
  GET products/123/cover.jpg?versionId=aaa111 -> returns aaa111
  Neither version lost. Rollback possible.
```

**One-liner:**
> "Last write wins, both get 200, data silently lost — fix by design: UUID in the key
> makes collision impossible. Versioning is the safety net behind that."

## TRAP-5 — "What happens if someone accidentally deletes the KMS key?"

> **Interviewer asks:**
> "Your S3 bucket is SSE-KMS encrypted. A developer accidentally schedules the KMS
> key for deletion. What happens to your data?"

> **You say:**
>
> "KMS has a grace period — minimum 7 days, maximum 30. During that window the key is
> disabled. Every S3 read and write fails with 403. This is actually your early warning
> signal — if S3 suddenly returns 403 on everything, one of the first things I check
> is KMS key status.
>
> During that grace period you can cancel the deletion. One AWS CLI call, key comes
> back, 403s stop, all data is accessible again. No harm done.
>
> But if no one catches it before the waiting period expires — the key is permanently
> deleted. The data is still physically in S3, but the encryption key is gone. It cannot
> be recovered by you, by AWS support, by anyone. Permanent data loss.
>
> In production we have three safeguards. No developer has kms:ScheduleKeyDeletion
> permission — only a break-glass role. A CloudTrail alert fires the moment any KMS
> key state changes — that goes straight to PagerDuty. And we replicate critical buckets
> to a separate region encrypted with a different KMS key, so if one key is gone the
> replica is still accessible."

```
KMS KEY DELETION TIMELINE
===========================

  Day 0:   Developer schedules deletion (7-day wait chosen)
  |
  | Immediately: Key state -> PENDING_DELETION
  |              All S3 reads/writes -> 403 AccessDeniedException
  |              CloudTrail fires event -> PagerDuty alert  <- CATCH IT HERE
  |
  Day 1-6: Grace period
  |  aws kms cancel-key-deletion --key-id arn:aws:kms:...
  |  Key re-enabled -> 403s stop -> all data accessible
  |
  Day 7:   Waiting period expires
           Key PERMANENTLY DELETED
           Data in S3: still physically present
           Data readable: NO
           Recovery by anyone: IMPOSSIBLE


  THREE PROD SAFEGUARDS:
  =======================

  1. IAM: only break-glass role has kms:ScheduleKeyDeletion
     Normal developer role: kms:Encrypt, kms:Decrypt only

  2. CloudTrail alert:
     Event pattern: { "source": ["aws.kms"],
                      "detail-type": ["AWS API Call via CloudTrail"],
                      "detail": { "eventName": ["ScheduleKeyDeletion"] } }
     Target: SNS -> PagerDuty P1

  3. Cross-region replication to different key:
     Primary:  ap-south-1  encrypted with key-A
     Replica:  ap-southeast-1 encrypted with key-B
     Both keys must be deleted simultaneously to lose data
```

**One-liner:**
> "7-day grace period — key disabled, 403s are your warning, cancel to recover.
> After expiry: permanent data loss, no recovery. Safeguards: no dev has delete
> permission, CloudTrail alert on key state change, cross-region replica on a different key."

## TRAP-7 — "We put Lambda inside a VPC. Now it can't reach S3. Why?"

> private network. No internet needed.

> hour. It works, but you are paying unnecessarily when the Gateway Endpoint is free
> and actually faster since traffic stays on the AWS backbone."

## TRAP-8 — "Why not just use s3:* on * to keep things simple?"

> **Interviewer asks:**
> "To avoid all these IAM permission issues, why not just give the role s3:* on *?
> The app only uses what it needs anyway."

> **You say:**
>
> "I would push back on that hard. It sounds pragmatic but it is a critical security
> mistake in production.
>
> s3:* on * means the application identity can DeleteBucket, can PutBucketPolicy to
> make the bucket public, can PutBucketLogging to disable the audit trail, and can
> GetObject on every bucket in the entire account — not just ours.
>
> Now consider a realistic threat. Our service has a dependency vulnerability — Log4Shell,
> or a vulnerable library. An attacker gets remote code execution inside the pod. With
> s3:* on *, they can delete all S3 data across the account, disable logging so there
> is no audit trail of what they did, and exfiltrate every S3 bucket in the account
> including other teams' data.
>
> With least privilege — PutObject and GetObject scoped to our specific bucket and
> key prefix — the blast radius of that same attack is limited to our service's data
> only. Everything else in the account is protected.
>
> The correct policy is three statements: PutObject on our product images prefix,
> GetObject on the same prefix, and DeleteObject scoped to the seller's own prefix
> so a seller cannot delete another seller's files."

```
s3:* ON * — BLAST RADIUS OF A COMPROMISE
==========================================

  Scenario: RCE vulnerability in a dependency (Log4Shell etc.)
  Attacker executes code inside the Spring Boot pod.

  WITH s3:* on *:
  ----------------
  Attacker can call:

  s3:DeleteBucket          -> delete flipkart-product-images-prod
  s3:PutBucketPolicy       -> make all buckets public (data breach)
  s3:PutBucketLogging      -> disable audit logs (cover tracks)
  s3:DeleteObject on *     -> delete files in ALL buckets in account
  s3:GetObject on *        -> read ALL data in ALL buckets in account
                             payments team, user data team, everything
  s3:PutBucketVersioning   -> disable versioning (no rollback possible)

  Result: total data loss + breach + no audit trail


  WITH LEAST PRIVILEGE:
  ----------------------
  {
    "Statement": [
      {
        "Effect": "Allow",
        "Action": ["s3:PutObject", "s3:GetObject"],
        "Resource": "arn:aws:s3:::flipkart-product-images-prod/products/*"
      },
      {
        "Effect": "Allow",
        "Action": ["s3:DeleteObject"],
        "Resource": "arn:aws:s3:::flipkart-product-images-prod/products/${aws:PrincipalTag/sellerId}/*"
      },
      {
        "Effect": "Allow",
        "Action": ["s3:ListBucket"],
        "Resource": "arn:aws:s3:::flipkart-product-images-prod",
        "Condition": { "StringLike": { "s3:prefix": "products/*" } }
      }
    ]
  }

  Same RCE attack with least privilege:
  Attacker limited to: our product images only
  Cannot touch: other teams' buckets, policies, logging, billing
  Blast radius: contained
```

**One-liner:**
> "s3:* on * means one RCE vulnerability = full account data breach and deletion.
> Least privilege scopes to our bucket and prefix only — blast radius is contained
> to our service's data."

## TRAP-9 — "How do you give your service access to an S3 bucket in another AWS account?"

> **Interviewer asks:**
> "Flipkart's seller service is in Account A. The shared media bucket is managed by
> a central media team in Account B. How do you make this work?"

> **You say:**
>
> "Cross-account S3 access requires two grants, not one. Both must be in place or
> the request fails. Think of it as two doors — the IAM policy in Account A lets the
> role say 'I am allowed to make this S3 call,' and the bucket policy in Account B
> lets that specific role ARN through to the bucket.
>
> First, the IAM role in Account A needs an explicit Allow on s3:PutObject and
> s3:GetObject pointing at the bucket ARN in Account B.
>
> Second, the bucket policy in Account B must list the role ARN from Account A and
> allow those actions. Without that bucket policy, Account B's S3 rejects the request
> regardless of what Account A's IAM says.
>
> The Spring Boot code does not change at all — just the bucket name in properties.
>
> But there is a gotcha that bites most teams: object ownership. When Account A uploads
> to Account B's bucket, the object is owned by Account A by default. Account B's own
> applications cannot read that object — they do not own it. The fix is Bucket Owner
> Enforced on Account B's bucket. This makes all uploaded objects owned by the bucket
> account regardless of who uploaded them."

```
CROSS-ACCOUNT S3 — TWO GRANTS REQUIRED
=========================================

  Account A (123456789)        Account B (987654321)
  Seller Service               Media Team
  IAM Role: seller-role        S3: flipkart-shared-media

  GRANT 1 — Account A IAM Role policy:
  +------------------------------------+
  | Allow s3:PutObject, s3:GetObject   |
  | Resource:                          |
  |  arn:aws:s3:::flipkart-shared-     |
  |  media/*                           |
  +------------------------------------+
  Role says: "I am allowed to call this bucket"

  GRANT 2 — Account B Bucket Policy:
  +------------------------------------+
  | Allow s3:PutObject, s3:GetObject   |
  | Principal:                         |
  |  arn:aws:iam::123456789:role/       |
  |  seller-role                       |
  | Resource:                          |
  |  arn:aws:s3:::flipkart-shared-     |
  |  media/*                           |
  +------------------------------------+
  Bucket says: "I accept that specific role"

  BOTH must allow -> access granted
  EITHER missing  -> 403 AccessDenied

  +------------------+  two-grant  +------------------+
  | Account A        | ----------> | Account B        |
  | seller-role      |             | S3 Bucket        |
  | IAM allows it    |             | Policy allows it |
  +------------------+             +------------------+


  GOTCHA — Object Ownership:
  ===========================
  Account A uploads -> object owned by Account A
  Account B tries to read -> 403 (does not own it)

  FIX: set on Account B's bucket once:
  aws s3api put-bucket-ownership-controls \
    --bucket flipkart-shared-media \
    --ownership-controls Rules=[{ObjectOwnership=BucketOwnerEnforced}]

  After: ALL objects owned by Account B regardless of uploader
  Spring Boot code: zero changes
```

**One-liner:**
> "Cross-account needs two grants — IAM in Account A allows the call, bucket policy
> in Account B allows that role ARN. Missing either = 403. Set Bucket Owner Enforced
> or Account B cannot read objects Account A uploaded."

## TRAP-10 — "S3 Transfer Acceleration vs CloudFront — can CloudFront handle uploads too?"

> **Interviewer asks:**
> "We have international sellers uploading images from the US and Europe to our Mumbai
> S3 bucket. We also need fast image loading for buyers globally. Can we just put
> CloudFront in front and solve both?"

> **You say:**
>
> "They look similar — both use AWS edge locations — but they solve opposite directions
> of the same problem, and CloudFront is not the right tool for large file uploads.
>
> CloudFront is built for reads. It caches objects at edges globally so buyers in
> London, New York, and Delhi all get images from the nearest edge. That is what we
> already use for product image delivery.
>
> Transfer Acceleration is for writes — it speeds up uploads from clients who are
> geographically far from your S3 region. A seller in New York uploading to Mumbai S3
> has to send data over the public internet for thousands of miles. With Transfer
> Acceleration, they upload to the nearest AWS edge in New York, and AWS routes that
> data from the edge to Mumbai over the AWS backbone — which is optimized, lower
> jitter, and significantly faster than the public internet for long hauls.
>
> The catch is cost — Transfer Acceleration adds $0.04 to $0.08 per GB. For Indian
> sellers uploading to Mumbai S3, they are in the same region, latency is already fast,
> no need for it. We only enable it for international seller flows."

```
TRANSFER ACCELERATION vs CLOUDFRONT — OPPOSITE DIRECTIONS
===========================================================

  CLOUDFRONT — reads (buyer views product image):
  -------------------------------------------------
  Buyer in London
       |
       | GET images.flipkart.com/products/123/img.jpg
       v
  +--------------------+
  | CloudFront Edge    |  London edge — 5ms away
  | Cache hit: YES     |  return immediately, no S3 hit
  +--------------------+
       | (cache miss only — ~5% of requests)
       v
  +--------------------+
  | S3 Mumbai (origin) |  ~200ms away
  +--------------------+


  TRANSFER ACCELERATION — writes (seller uploads image):
  -------------------------------------------------------
  Seller in New York

  WITHOUT Acceleration:
  New York -> public internet (10,000km) -> S3 Mumbai
  ~300ms RTT, variable, packet loss risk

  WITH Acceleration:
  New York -> nearest CF edge (5ms) -> AWS backbone -> S3 Mumbai
  Backbone: optimized, low jitter, significantly faster

  Upload URL changes to accelerate endpoint:
  flipkart-images.s3-accelerate.amazonaws.com
  Cost: extra $0.04-$0.08 per GB

  FLIPKART DECISION:
  -------------------
  Indian sellers (90%):    direct S3 PUT in same region, fast enough
  International sellers:   Transfer Acceleration enabled
  All buyers globally:     CloudFront CDN for reads
```

**One-liner:**
> "CloudFront = fast reads globally (CDN caches at edge). Transfer Acceleration =
> fast uploads from distant clients (upload to nearest edge, AWS backbone to S3).
> Opposite directions. CloudFront does not replace Acceleration for large uploads."
