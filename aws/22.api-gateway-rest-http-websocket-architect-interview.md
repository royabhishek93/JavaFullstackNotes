## NEW LEARNER FOUNDATION — Read This First If You Are New

```
KEY TERMS EXPLAINED SIMPLY
============================

API GATEWAY
  A fully managed AWS service that sits in front of your backend (Lambda,
  ECS, or any HTTP endpoint). It receives HTTP or WebSocket requests from
  clients, optionally authenticates/throttles/transforms them, and forwards
  them to your backend. Think of it as the "front door" for your API.

LAMBDA PROXY INTEGRATION
  The most common way to connect API Gateway to Lambda. API Gateway bundles
  the ENTIRE incoming HTTP request (headers, body, path params, query
  params, context) into a single JSON event object and sends it to Lambda.
  Lambda must respond with a specific JSON structure: statusCode, headers,
  and body. API Gateway then converts that back into an HTTP response.

REST API (Original API Gateway)
  The original, feature-rich API Gateway type. Supports request/response
  transformation using Velocity templates (VTL), direct SQS/Step Functions
  integration, per-stage caching, usage plans, and API keys. Costs $3.50
  per million requests.

HTTP API (API Gateway v2)
  A newer, simpler, cheaper version of API Gateway. 71% cheaper at $1.00
  per million requests and about 3x lower latency. Best for most Lambda
  microservices. Does NOT support response caching or direct SQS integration.

WEBSOCKET API
  Instead of the client making a new request each time (HTTP), a WebSocket
  keeps one persistent TCP connection open between client and server.
  Either side can send messages at any time — perfect for chat, live score
  updates, or real-time dashboards.

INTEGRATION TIMEOUT
  API Gateway has a hard maximum wait time of 29 seconds for your backend
  to respond. If Lambda takes longer, API Gateway returns 504 to the client
  (even if Lambda keeps running). This is NOT configurable — you must design
  around it for long-running operations.

USAGE PLAN
  A configuration that attaches to an API key to define throttle limits
  (requests per second, burst) and quota (requests per day or month). Used
  to enforce per-client rate limiting — e.g., free tier vs. paid tier.
```

## SECTION 1 — REST API vs HTTP API vs WebSocket API: The Decision

### Interviewer asks: "There are multiple API Gateway types. Walk me through how you decide which one to use."

> **You say:**
>
> "There are three types and each one solves a different problem.
>
> REST API is the original, full-featured type. It costs $3.50 per million requests and has
> everything — per-stage caching, usage plans with API keys, custom Lambda authorizers with
> caching, request and response transformation using Velocity templates, and direct integrations
> to SQS, Step Functions, DynamoDB, and other AWS services without a Lambda in between.
> The latency overhead is around 200ms per request.
>
> HTTP API is the v2 type — 71% cheaper at $1.00 per million, lower latency around 60ms,
> and has JWT authorizers built in (Cognito or any OIDC provider, no custom Lambda code needed).
> CORS is a single toggle. But it only supports Lambda proxy and HTTP backends — no direct
> SQS integration, no response caching, no usage plans.
>
> WebSocket API is for persistent bidirectional connections. When a user opens a chat window,
> the browser connects once and the connection stays open. The server can push messages to
> the client any time. This is the only managed AWS option for WebSocket at scale without
> running your own EC2 servers.
>
> My decision rule: HTTP API for most Lambda microservices — the cost and latency win is real.
> REST API when I need SQS direct integration, request transformation, or API key monetization
> with usage plans. WebSocket API for real-time features: chat, live sports scores, driver
> location tracking, live dashboards."

```
DECISION MATRIX
================

  Requirement                         → Use
  ─────────────────────────────────────────────────────────
  Standard Lambda microservice        → HTTP API (cheaper)
  JWT auth (Cognito / Auth0 / Okta)   → HTTP API (built-in)
  API key monetization / tiers        → REST API (usage plans)
  Request/response transformation     → REST API (VTL templates)
  Direct SQS or Step Functions        → REST API (service proxy)
  Per-stage response caching          → REST API
  Real-time chat / notifications      → WebSocket API
  Live score / driver location        → WebSocket API
  Server-sent events, dashboards      → WebSocket API

  PRICING SUMMARY:
  ┌─────────────────────┬──────────────┬─────────────────────────┐
  │ Type                │ Price/M req  │ Extra                   │
  ├─────────────────────┼──────────────┼─────────────────────────┤
  │ REST API            │ $3.50        │ Cache: $0.02/hr/0.5GB   │
  │ HTTP API            │ $1.00        │ —                        │
  │ WebSocket API       │ $1.00/M msg  │ $0.25/M connection-min  │
  └─────────────────────┴──────────────┴─────────────────────────┘
```

### Interviewer asks: "Tell me more about WebSocket API — how does routing work?"

> **You say:**
>
> "When a client connects, API Gateway assigns a unique connectionId — a string like
> 'Abc123XYZ'. That connectionId represents the open connection. It persists until the
> client disconnects or the connection times out (10 minutes of idle by default, 2 hours max).
>
> WebSocket API uses route selection. You define routes based on a field in the incoming
> message — typically an action field. So if the client sends
> `{ action: 'sendMessage', text: 'hello' }`, the $default route or a custom sendMessage
> route fires the corresponding Lambda.
>
> There are three built-in routes: $connect (fires when a client connects — validate auth here),
> $disconnect (fires when a client leaves — clean up stored connectionIds), and $default
> (catches any message that doesn't match a custom route).
>
> To push a message TO a client from your Lambda, you call the API Gateway Management API
> with the connectionId and the payload. This is the server-to-client push."

```
WEBSOCKET API — CONNECTION LIFECYCLE
======================================

  Browser / App
      |
      |  wss://xyz.execute-api.us-east-1.amazonaws.com/prod
      |  (one-time handshake, then persistent)
      ▼
  API Gateway WebSocket API
      |
      ├─ $connect     → Lambda: validate token, store connectionId in DynamoDB
      |                  DynamoDB: { connectionId: "Abc123", userId: "U-456" }
      |
      ├─ $disconnect  → Lambda: delete connectionId from DynamoDB
      |
      ├─ sendMessage  → Lambda: reads message, finds target user's connectionId
      |                  in DynamoDB, calls Management API to push to recipient
      |
      └─ $default     → Lambda: fallback handler

  SERVER-PUSH (Lambda → Client):
      Worker Lambda
          │
          │  POST https://{api-id}.execute-api.{region}.amazonaws.com/{stage}
          │       /@connections/{connectionId}
          │  Body: { "text": "Your order is confirmed!" }
          ▼
      API Gateway delivers to browser over existing WebSocket connection

  BILLING NOTE:
  Connection-minutes = $0.25 per million connection-minutes
  1000 users × 30 min session = 30,000 connection-minutes = $0.0075
  (not expensive, but surprises teams who don't model it)
```

## SECTION 2 — Lambda Proxy Integration vs Non-Proxy

### Interviewer asks: "How does Lambda Proxy integration work, and when would you NOT use it?"

> **You say:**
>
> "Lambda Proxy is the default for almost everyone and for good reason. API Gateway
> packages the entire HTTP request into a single JSON event and passes it to Lambda.
> Everything is there — the HTTP method, path, query string parameters, headers, stage
> variables, the request context including the caller's IP and the authorizer result,
> and the body as a string. Lambda does its logic and returns a specific JSON shape:
> statusCode as a number, headers as a map, and body as a string. API Gateway converts
> that to an HTTP response.
>
> The gotcha that trips up Java developers: even if the client sends Content-Type application/json,
> the body arrives in Lambda as a raw string. In Node.js you have to call JSON.parse(event.body).
> In Spring Boot Lambda handlers, @RequestBody works automatically only if you configure the
> Jackson handler properly — and you need to check the isBase64Encoded flag for binary payloads.
>
> Non-Proxy integration is the alternative. You write Apache Velocity (VTL) mapping templates
> to transform the request before it reaches Lambda, and transform Lambda's response before
> returning to the client. The Lambda function never sees HTTP — it sees a clean, shaped payload.
> The use case is when you have a Lambda that is not HTTP-aware (maybe it is shared with SQS
> invocations too), or when you want API Gateway to do validation and shaping without Lambda
> touching it. In practice, most greenfield teams use proxy. Non-proxy appears in legacy
> integrations or when you are doing a direct AWS service integration like SQS-proxy."

```
LAMBDA PROXY vs NON-PROXY
==========================

  PROXY INTEGRATION (most common):
  ─────────────────────────────────
  HTTP Request
    POST /orders
    Content-Type: application/json
    Body: {"item": "biryani", "qty": 2}
          │
          ▼ API Gateway wraps everything
  Lambda event = {
    "httpMethod": "POST",
    "path": "/orders",
    "headers": { "Content-Type": "application/json", ... },
    "queryStringParameters": null,
    "pathParameters": null,
    "body": "{\"item\":\"biryani\",\"qty\":2}",   ← STRING, not object!
    "isBase64Encoded": false,
    "requestContext": { "authorizer": { "claims": {...} } }
  }
          │
          ▼ Lambda must return THIS shape
  {
    "statusCode": 201,
    "headers": { "Content-Type": "application/json" },
    "body": "{\"orderId\":\"ORD-123\",\"status\":\"PLACED\"}"
                                                ↑ STRING again
  }

  NON-PROXY INTEGRATION:
  ──────────────────────
  HTTP Request → [VTL Mapping Template] → clean payload → Lambda
  Lambda response → [VTL Response Template] → HTTP Response
  
  Lambda never sees headers/path — just the shaped data you defined.
  Example VTL: #set($body = $util.parseJson($input.body))
               { "item": "$body.item", "qty": $body.qty }
```

### Interviewer asks: "Show me the Spring Boot Lambda handler returning a proper proxy response."

> **You say:**
>
> "Spring Boot has the aws-serverless-java-container library that handles the translation.
> You add it as a dependency and your StreamLambdaHandler translates the API GW event
> into a Spring HttpServletRequest automatically — so your @RestController code is identical
> to regular Spring Boot. Alternatively for Spring Cloud Function on Lambda, the function
> just returns a response and the framework wraps it. But let me show you the raw handler
> approach first so you understand what is happening underneath."

```java
// RAW Lambda Handler (no Spring) — shows the proxy contract clearly
public class OrderHandler implements RequestHandler<APIGatewayProxyRequestEvent, APIGatewayProxyResponseEvent> {

    private final ObjectMapper mapper = new ObjectMapper();

    @Override
    public APIGatewayProxyResponseEvent handleRequest(
            APIGatewayProxyRequestEvent event, Context context) {

        // body is a STRING — must parse
        String rawBody = event.getBody();
        OrderRequest request;
        try {
            request = mapper.readValue(rawBody, OrderRequest.class);
        } catch (Exception e) {
            return response(400, Map.of("error", "Invalid JSON body"));
        }

        // read path param: /orders/{orderId}
        String orderId = event.getPathParameters().get("orderId");

        // read query param: ?status=PLACED
        String status = event.getQueryStringParameters() != null
            ? event.getQueryStringParameters().get("status")
            : null;

        // read Cognito user from authorizer context
        Map<String, Object> claims = (Map<String, Object>)
            event.getRequestContext().getAuthorizer().get("claims");
        String userId = (String) claims.get("sub");

        OrderResponse orderResponse = orderService.placeOrder(request, userId);
        return response(201, orderResponse);
    }

    private APIGatewayProxyResponseEvent response(int statusCode, Object body) {
        try {
            return new APIGatewayProxyResponseEvent()
                .withStatusCode(statusCode)
                .withHeaders(Map.of("Content-Type", "application/json"))
                .withBody(mapper.writeValueAsString(body));  // must be STRING
        } catch (Exception e) {
            return new APIGatewayProxyResponseEvent()
                .withStatusCode(500)
                .withBody("{\"error\":\"serialization failed\"}");
        }
    }
}

// Spring Boot with aws-serverless-java-container (your @RestController works unchanged)
// StreamLambdaHandler.java
public class StreamLambdaHandler implements RequestStreamHandler {
    private static SpringBootLambdaContainerHandler<AwsProxyRequest, AwsProxyResponse> handler;

    static {
        try {
            handler = SpringBootLambdaContainerHandler.getAwsProxyHandler(Application.class);
        } catch (ContainerInitializationException e) {
            throw new RuntimeException(e);
        }
    }

    @Override
    public void handleRequest(InputStream inputStream, OutputStream outputStream,
                              Context context) throws IOException {
        handler.proxyStream(inputStream, outputStream, context);
    }
}
```

## SECTION 3 — The 29-Second Hard Timeout: Forces Async Pattern

### Interviewer asks: "What happens when a client triggers an operation that takes more than 29 seconds?"

> **You say:**
>
> "This is one of the most important architecture constraints in serverless. API Gateway
> has a hard maximum integration timeout of 29 seconds. Lambda can run for up to 15 minutes.
> Those two facts create a dangerous mismatch.
>
> If you wire API Gateway directly to a Lambda that runs for 2 minutes — maybe it is
> generating a large PDF report or transcoding a video — API Gateway cuts the connection
> at 29 seconds and returns 504 Gateway Timeout to the client. But Lambda keeps running
> in the background, burning money, with no one to receive the result.
>
> The fix is an async job pattern. The initial Lambda does one thing only: put the job
> request onto SQS and immediately return a jobId to the client in under 1 second.
> A separate worker Lambda polls SQS and does the actual long work. When it finishes,
> it writes the result to DynamoDB with the jobId as the key. The client polls a status
> endpoint — GET /jobs/{jobId}/status — and a lightweight Lambda reads DynamoDB and
> returns PENDING, PROCESSING, COMPLETE, or FAILED with the result.
>
> For a better user experience, instead of polling, the client connects via WebSocket API.
> When the worker Lambda finishes, it pushes a completion notification to the WebSocket
> connection directly. No polling needed."

```
29-SECOND TIMEOUT — ASYNC JOB PATTERN
========================================

  BAD (will 504 for long operations):
  ────────────────────────────────────
  Client → API GW → Lambda (2-min job) → 504 after 29s ❌
                         └── Lambda still running, result lost

  GOOD — Async Job Pattern:
  ─────────────────────────
  STEP 1: Accept request (< 1 second)
  ┌──────────┐     ┌──────────┐     ┌────────────────────────┐
  │  Client  │────►│ API GW   │────►│ Lambda: job-acceptor   │
  │          │     │ POST     │     │  1. validate input     │
  │          │◄────│ /export  │◄────│  2. put message to SQS │
  │ 202 +    │     └──────────┘     │  3. return { jobId }   │
  │ jobId    │                      └──────────┬─────────────┘
  └──────────┘                                 │
                                               ▼
  STEP 2: Process (can take up to 15 min)   [SQS Queue]
                                               │
                                               ▼
                                    ┌──────────────────────┐
                                    │ Worker Lambda         │
                                    │  - polls SQS          │
                                    │  - does the long work │
                                    │  - writes to DynamoDB │
                                    │    { jobId, status,   │
                                    │      result, updatedAt}│
                                    └──────────────────────┘

  STEP 3a: Client polls (simple approach)
  ┌──────────┐     ┌──────────┐     ┌─────────────────────┐
  │  Client  │────►│ API GW   │────►│ Lambda: status-check │
  │          │◄────│ GET      │◄────│  reads DynamoDB      │
  │ PENDING  │     │ /jobs/   │     │  returns status +    │
  │ COMPLETE │     │ {jobId}  │     │  result when done    │
  └──────────┘     └──────────┘     └─────────────────────┘

  STEP 3b: WebSocket push (better UX)
  Worker Lambda ──► API GW Management API ──► WebSocket ──► Client
  (no polling, instant notification when job completes)

  REAL EXAMPLES WHERE THIS APPLIES:
  • Payment System:  fraud analysis (ML model, 45 sec) → must be async
  • Food Delivery:   bulk menu import (1000 items, 2 min) → async
  • Video platform:  transcoding (10 min) → definitely async
  • E-commerce:      monthly invoice PDF generation → async
```

### Interviewer asks: "Show me the SQS enqueue Lambda code for this pattern."

```java
// job-acceptor Lambda — responds in < 1 second
@Component
public class JobAcceptorHandler implements RequestHandler<APIGatewayProxyRequestEvent, APIGatewayProxyResponseEvent> {

    @Autowired private SqsClient sqsClient;
    @Autowired private ObjectMapper mapper;

    private final String queueUrl = System.getenv("JOB_QUEUE_URL");

    @Override
    public APIGatewayProxyResponseEvent handleRequest(
            APIGatewayProxyRequestEvent event, Context context) {

        String jobId = UUID.randomUUID().toString();

        JobRequest jobRequest = parseBody(event.getBody(), JobRequest.class);
        jobRequest.setJobId(jobId);
        jobRequest.setRequestedAt(Instant.now().toString());

        // enqueue — this takes ~5ms
        sqsClient.sendMessage(SendMessageRequest.builder()
            .queueUrl(queueUrl)
            .messageBody(serialize(jobRequest))
            .messageGroupId(jobId)            // for FIFO queues
            .messageDeduplicationId(jobId)
            .build());

        // respond IMMEDIATELY — well within 29s
        return response(202, Map.of(
            "jobId", jobId,
            "status", "ACCEPTED",
            "statusUrl", "/jobs/" + jobId + "/status"
        ));
    }
}

// Worker Lambda — SQS trigger, can run up to 15 minutes
@Component
public class JobWorkerHandler implements RequestHandler<SQSEvent, Void> {

    @Autowired private DynamoDbClient dynamoDb;
    private final String jobTable = System.getenv("JOB_STATUS_TABLE");

    @Override
    public Void handleRequest(SQSEvent event, Context context) {
        for (SQSEvent.SQSMessage message : event.getRecords()) {
            JobRequest job = deserialize(message.getBody(), JobRequest.class);

            updateStatus(job.getJobId(), "PROCESSING", null);
            try {
                Object result = doLongWork(job);          // takes minutes
                updateStatus(job.getJobId(), "COMPLETE", serialize(result));
            } catch (Exception e) {
                updateStatus(job.getJobId(), "FAILED", e.getMessage());
                throw e;   // re-throw so SQS retries / DLQ gets it
            }
        }
        return null;
    }

    private void updateStatus(String jobId, String status, String result) {
        Map<String, AttributeValue> item = new HashMap<>();
        item.put("jobId", AttributeValue.fromS(jobId));
        item.put("status", AttributeValue.fromS(status));
        item.put("updatedAt", AttributeValue.fromS(Instant.now().toString()));
        if (result != null) item.put("result", AttributeValue.fromS(result));

        dynamoDb.putItem(PutItemRequest.builder()
            .tableName(jobTable).item(item).build());
    }
}
```

## SECTION 4 — Usage Plans + API Keys: Per-Client Throttling

### Interviewer asks: "How would you implement different rate limits for free vs. paid customers calling your API?"

> **You say:**
>
> "This is exactly what Usage Plans and API Keys are for in API Gateway REST API.
> Important caveat first: an API Key is NOT authentication. It is metering and throttling.
> If you need to know who is calling, use Cognito or a Lambda authorizer. Usage Plans are
> about enforcing limits after authentication.
>
> Here is the setup: you create API Keys — generated opaque strings. Clients include their
> key in the x-api-key header on every request. Then you create Usage Plans. Each usage plan
> defines a throttle rate in requests per second, a burst size, and a quota in requests
> per day or per month. You attach one or more API Keys to a Usage Plan. Now that key gets
> exactly those limits.
>
> For a food delivery platform API marketplace: free tier gets 100 requests per day, pro tier
> gets 10,000 per day, enterprise gets 100,000 per day and a higher burst. Partners on the
> free tier can prototype without paying. Partners who upgrade get more capacity. This is also
> how AWS Marketplace works — third-party APIs listed there use this mechanism.
>
> In production, we always combine Usage Plans with real authentication. Cognito authorizer
> validates the JWT first, then API Gateway checks the x-api-key for throttle limits. One
> handles identity, the other handles rate limiting."

```
USAGE PLAN ARCHITECTURE
========================

  API Keys:               Usage Plans:
  ─────────               ────────────
  key-abc123  ──────────► FREE TIER
                          rate: 10 req/sec
                          burst: 20
                          quota: 100 req/day

  key-def456  ──────────► PRO TIER
  key-ghi789             rate: 100 req/sec
                          burst: 200
                          quota: 10,000 req/day

  key-xyz999  ──────────► ENTERPRISE TIER
                          rate: 1000 req/sec
                          burst: 2000
                          quota: 100,000 req/day

  REQUEST FLOW:
  Client
    │  x-api-key: key-def456
    │  Authorization: Bearer <jwt>
    ▼
  API Gateway
    1. Cognito Authorizer validates JWT      → identity confirmed
    2. API Key lookup → finds PRO TIER plan  → apply throttle limits
    3. Rate check: under 100 req/sec?        → pass
    4. Quota check: under 10,000 today?      → pass
    5. Forward to Lambda
    
  WHEN LIMIT EXCEEDED:
  429 Too Many Requests
  {"message": "Limit Exceeded"}

  REMEMBER: API Key ≠ Authentication
  ────────────────────────────────────
  API Key: who gets how many requests (metering)
  Cognito/Lambda Authorizer: who is allowed at all (authn/authz)
```

## SECTION 5 — ALB vs API Gateway vs Custom Ingress

### Interviewer asks: "When would you use an ALB instead of API Gateway, and when would you use neither?"

> **You say:**
>
> "These three options exist on a spectrum from 'managed and feature-rich but adds latency'
> to 'maximum control at the cost of operational work.'
>
> ALB is a Layer 7 HTTP load balancer. It can route by path and hostname to ECS tasks,
> EKS pods, EC2 instances, or Lambda. Latency overhead is about 1 millisecond — essentially
> invisible. It costs about $0.008 per LCU-hour. But it has no built-in auth, no throttling,
> no request transformation, no caching. You need your application to do all of that.
>
> API Gateway REST or HTTP is fully managed. Built-in Cognito and Lambda authorizers,
> built-in throttling, optional caching, CloudWatch metrics and logging with no setup. The
> cost is 50 to 200ms of latency overhead per request and more per-request cost. For a
> Lambda microservice, this is the natural fit — Lambda and API Gateway were designed together.
>
> Custom Ingress — nginx-ingress or AWS Load Balancer Controller on EKS — is maximum
> flexibility. Your platform team controls it. You can do advanced routing, mutual TLS,
> circuit breaking. Good for EKS-native workloads where you already have the platform team.
>
> My rule: Lambda gets API Gateway — they are designed together, and the latency overhead
> does not matter because Lambda itself has more startup variance. ECS or EKS microservices
> get ALB — lower cost, lower latency, no per-request API Gateway pricing. Real-time features
> on any backend get WebSocket API — there is no managed alternative that does not require
> running a stateful server."

## SECTION 6 — Stage Variables, Custom Domains, CORS

### Interviewer asks: "How do you manage dev vs. staging vs. production in API Gateway?"

> **You say:**
>
> "API Gateway has the concept of stages. Each stage gets its own URL:
> `https://abc123.execute-api.us-east-1.amazonaws.com/dev` and `.../prod`.
> Each stage can point to a different Lambda alias — so the dev stage invokes the dev alias
> and prod invokes the prod alias. You can deploy a new version to dev, test it, then deploy
> to prod — same API definition, different Lambda version.
>
> Stage variables are like environment variables for a stage. You define
> `lambdaAlias = dev` on the dev stage and `lambdaAlias = prod` on prod. The integration
> URI uses `${stageVariables.lambdaAlias}` to resolve at runtime. This is how one API
> definition drives multiple environments without duplication.
>
> For custom domains, you create an ACM certificate and a custom domain name resource in
> API Gateway. Then you map api.swiggy.com to your API. The big trap: if you are using
> edge-optimized deployment (CloudFront-backed), the ACM certificate MUST be created in
> us-east-1 regardless of where your API is. That catches teams who create the cert in
> ap-south-1 and wonder why it does not show up in the custom domain dropdown.
>
> CORS: HTTP API has a single toggle in the console and a simple CORS configuration block.
> REST API requires you to enable CORS per resource — it creates an OPTIONS method
> with the right headers. The mistake is forgetting to add CORS headers to error responses.
> API Gateway only adds CORS headers to successful responses unless you configure it
> on the gateway response types (DEFAULT_4XX and DEFAULT_5XX) as well."

```
STAGES AND CUSTOM DOMAINS
===========================

  STAGE VARIABLES PATTERN:
  ─────────────────────────
  Stage: dev
    stageVariables:
      lambdaAlias: dev
      logLevel: DEBUG
      dbEndpoint: dev.rds.internal

  Stage: prod
    stageVariables:
      lambdaAlias: prod
      logLevel: WARN
      dbEndpoint: prod.rds.internal

  Integration URI: arn:aws:lambda:...:function:order-handler:${stageVariables.lambdaAlias}
                                                              ─────────────────────────────
                                                              resolves to :dev or :prod

  CUSTOM DOMAIN SETUP:
  ─────────────────────
  api.swiggy.com (Route53)
          │
          ▼
  API Gateway Custom Domain Name
          │
          ├── Edge-optimized → ACM cert MUST be in us-east-1 (CloudFront requires it)
          │
          └── Regional → ACM cert can be same region as API
          │
          ▼
  API Mapping: api.swiggy.com → my-api / prod stage
               api.swiggy.com/v2 → my-api-v2 / prod stage

  CORS CONFIGURATION (HTTP API — simple):
  ─────────────────────────────────────────
  # CDK
  HttpApi.Builder.create(this, "Api")
      .corsPreflight(CorsPreflightOptions.builder()
          .allowOrigins(List.of("https://swiggy.com"))
          .allowMethods(List.of(CorsHttpMethod.GET, CorsHttpMethod.POST))
          .allowHeaders(List.of("Content-Type", "Authorization"))
          .build())
      .build();

  CORS TRAP — REST API (must also add to gateway responses):
  ────────────────────────────────────────────────────────────
  Resources: add OPTIONS method + enable CORS ✓
  Gateway Response DEFAULT_4XX: add Access-Control-Allow-Origin header ← OFTEN MISSED
  Gateway Response DEFAULT_5XX: same ← OFTEN MISSED
  Without this: 401 / 500 errors arrive without CORS headers → browser blocks them
```

## SECTION 7 — Spring Boot Integration Examples

### Calling API Gateway from Spring Boot (RestTemplate / WebClient)

```java
// application.yml
api-gateway:
  base-url: https://api.swiggy.com
  order-service: /orders
  catalog-service: /catalog

// WebClient (reactive) calling API Gateway endpoint
@Service
public class OrderGatewayClient {

    private final WebClient webClient;

    public OrderGatewayClient(WebClientBuilder builder,
                               @Value("${api-gateway.base-url}") String baseUrl) {
        this.webClient = builder
            .baseUrl(baseUrl)
            .defaultHeader("x-api-key", System.getenv("PARTNER_API_KEY"))
            .build();
    }

    public Mono<OrderResponse> placeOrder(OrderRequest request, String jwtToken) {
        return webClient.post()
            .uri("/orders")
            .header("Authorization", "Bearer " + jwtToken)
            .bodyValue(request)
            .retrieve()
            .onStatus(HttpStatus::is4xxClientError, response ->
                response.bodyToMono(String.class)
                    .flatMap(body -> Mono.error(new OrderException("Client error: " + body))))
            .onStatus(HttpStatus::is5xxServerError, response ->
                Mono.error(new OrderException("Server error — retry later")))
            .bodyToMono(OrderResponse.class)
            .timeout(Duration.ofSeconds(25));  // stay under 29s API GW limit
    }
}

// RestTemplate (synchronous) — legacy services
@Service
public class CatalogClient {

    private final RestTemplate restTemplate;
    private final String catalogUrl;

    public CatalogClient(RestTemplateBuilder builder,
                          @Value("${api-gateway.base-url}") String baseUrl) {
        this.restTemplate = builder
            .setConnectTimeout(Duration.ofSeconds(3))
            .setReadTimeout(Duration.ofSeconds(25))  // stay under 29s
            .build();
        this.catalogUrl = baseUrl + "/catalog";
    }

    public CatalogItem[] getMenuItems(String restaurantId) {
        HttpHeaders headers = new HttpHeaders();
        headers.set("x-api-key", System.getenv("PARTNER_API_KEY"));
        headers.setContentType(MediaType.APPLICATION_JSON);

        ResponseEntity<CatalogItem[]> response = restTemplate.exchange(
            catalogUrl + "/restaurants/" + restaurantId + "/menu",
            HttpMethod.GET,
            new HttpEntity<>(headers),
            CatalogItem[].class);

        return response.getBody();
    }
}

// WebSocket client (Spring WebSocket for connecting to API GW WebSocket API)
@Component
public class DriverLocationWebSocketClient {

    private WebSocketSession session;

    public void connect(String wsUrl, String driverId) throws Exception {
        WebSocketClient client = new StandardWebSocketClient();
        session = client.doHandshake(
            new AbstractWebSocketHandler() {
                @Override
                protected void handleTextMessage(WebSocketSession s, TextMessage msg) {
                    LocationUpdate update = parse(msg.getPayload());
                    locationEventPublisher.publish(update);
                }
            },
            wsUrl + "?driverId=" + driverId
        ).get(5, TimeUnit.SECONDS);
    }

    public void sendLocation(double lat, double lng) throws Exception {
        String payload = String.format(
            "{\"action\":\"updateLocation\",\"lat\":%f,\"lng\":%f}", lat, lng);
        session.sendMessage(new TextMessage(payload));
    }
}
```

## COMMON TRAPS AND GOTCHAS

```
TRAP 1 — THE 29-SECOND WALL
  API Gateway integration timeout is 29 seconds HARD. Cannot be increased.
  Any Lambda that runs longer than 29 seconds: client gets 504, Lambda keeps running.
  Fix: async pattern (SQS → worker Lambda → DynamoDB polling or WebSocket push).

TRAP 2 — ACM CERT MUST BE IN US-EAST-1 FOR EDGE-OPTIMIZED
  If you create an ACM cert in ap-south-1 and try to use edge-optimized custom domain
  in API Gateway, the cert will NOT appear in the dropdown. It simply won't show.
  Fix: for edge-optimized, ALWAYS create the cert in us-east-1.
  For regional deployment, cert can be in the same region as the API.

TRAP 3 — API KEY ≠ AUTHENTICATION
  An API Key in API Gateway is NOT security. It is metering and throttling.
  Anyone who finds the x-api-key header value can call your API.
  Fix: always combine with a real authorizer (Cognito JWT or Lambda authorizer) for auth.
  Usage Plans handle rate limits. Cognito/Lambda authorizer handles identity.

TRAP 4 — BODY IS A STRING IN PROXY MODE
  In Lambda Proxy integration, event.body is ALWAYS a string even if Content-Type is JSON.
  In Node.js: JSON.parse(event.body) — forget this and you get [object Object].
  In Java: mapper.readValue(event.getBody(), MyClass.class) — same principle.
  Also: if isBase64Encoded is true, decode first before parsing.

TRAP 5 — WEBSOCKET CONNECTION-MINUTES BILLING SURPRISE
  WebSocket API charges $0.25 per million connection-minutes in addition to per-message cost.
  1000 concurrent users × 60 minute sessions × 30 days = 1.8 billion connection-minutes
  = $450/month just for keeping connections alive, even with zero messages sent.
  Fix: implement idle timeout and reconnect logic. Disconnect idle clients after N minutes.

TRAP 6 — CORS ERRORS ON 4XX AND 5XX RESPONSES
  API Gateway only injects CORS headers on success responses by default (REST API).
  A 401 from your authorizer or a 500 Lambda error arrives without CORS headers.
  The browser blocks it before your frontend code even sees the status code.
  Fix: configure Gateway Responses for DEFAULT_4XX and DEFAULT_5XX with CORS headers.
  HTTP API adds CORS headers to all responses including errors — this only bites REST API.

TRAP 7 — HTTP API DOES NOT SUPPORT DIRECT SQS INTEGRATION
  HTTP API only supports Lambda proxy and HTTP backends. If you need to put a message
  directly on SQS from API Gateway without a Lambda, you need REST API's AWS service
  integration. Teams switch from REST to HTTP API for cost savings and break this.
  Fix: audit your integrations before migrating REST → HTTP API.

TRAP 8 — BINARY MEDIA TYPES AND BASE64 ENCODING
  API Gateway does not transparently pass binary data (images, PDFs, audio) by default.
  If a Lambda returns binary data without declaring binaryMediaTypes in the API config
  and without base64-encoding the body with isBase64Encoded: true, the binary data
  gets corrupted — it passes through as text and UTF-8 encoding mangles the bytes.
  Fix: declare binaryMediaTypes (e.g., image/*, application/pdf) on the REST API.
  Set isBase64Encoded: true and base64-encode the body in Lambda response.
```
