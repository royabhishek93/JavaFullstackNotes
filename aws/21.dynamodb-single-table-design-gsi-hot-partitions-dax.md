## NEW LEARNER FOUNDATION — Read This First If You Are New

```
KEY TERMS EXPLAINED SIMPLY
============================

DYNAMODB
  AWS's fully managed NoSQL key-value and document database. No servers to
  manage. Scales to any size automatically. Charges per read/write operation,
  not per row stored. Single-digit millisecond latency at any scale.
  Think: a giant distributed hash map with optional sort keys.

PARTITION KEY (PK)
  The primary lookup key. DynamoDB hashes this value to decide which physical
  server (partition) stores the item. Example: PK = "USER#123".
  All items with the same PK live on the same partition.
  You can ONLY query: "give me items where PK = X" — no full-table scans
  (extremely expensive), no ad-hoc WHERE clauses like SQL.

SORT KEY (SK)
  An optional second key within a partition. Items with the same PK are sorted
  by SK. Allows range queries: "give me USER#123's orders from 2026-01-01 to
  2026-08-31". Without SK, a partition can have only one item per PK.
  PK + SK together form a composite primary key — PK identifies the partition,
  SK identifies the item within that partition.

SINGLE-TABLE DESIGN
  Putting MULTIPLE entity types (Users, Orders, Sessions, Reviews) into ONE
  DynamoDB table, distinguished by different SK prefixes. Why? DynamoDB can't
  join tables — if you need User + Orders in one query, they must be in the
  same table (same PK) so one query returns both. Sounds weird coming from SQL,
  but it's the standard DynamoDB pattern at scale.

GSI (Global Secondary Index)
  A way to query on a non-PK attribute. Example: your table's PK is USER#123,
  but you need to query by email. Create a GSI with PK=email. DynamoDB
  maintains a copy of the data sorted by the GSI key — queries against it are
  eventual consistency by default. Each table can have up to 20 GSIs.

LSI (Local Secondary Index)
  Like a GSI but shares the same partition key as the table. Allows different
  sort keys for the same PK. Must be created at table creation time. Limit:
  10 GB per partition with LSI. Less common than GSI.

DAX (DynamoDB Accelerator)
  A write-through in-memory cache that sits transparently between your app and
  DynamoDB. You point your SDK at the DAX endpoint instead of the DynamoDB
  endpoint. Cache hit: returns in microseconds. Cache miss: DAX fetches from
  DynamoDB, caches it, and returns to you. Zero code change in your app.

CAPACITY UNIT
  DynamoDB's billing unit.
  RCU (Read Capacity Unit)  = one strongly-consistent 4 KB read per second
                             (or two eventually-consistent reads)
  WCU (Write Capacity Unit) = one 1 KB write per second
  Over-provisioned → wasted money. Under-provisioned → throttling.

HOT PARTITION
  A physical partition that receives disproportionately more requests than
  others. Every DynamoDB partition can handle max 3000 RCU and 1000 WCU.
  Even if your table has 10,000 RCU total, if ALL reads hit the same
  partition, you are throttled at 3000 RCU. This is the hot partition trap.
```

## INTERVIEW SCRIPT

### OPENING — When They Ask: "When would you choose DynamoDB over RDS?"

> **You say:**
>
> "The decision comes down to access patterns and scale. RDS is the right choice
> when you need complex joins, ad-hoc queries, strong ACID guarantees across multiple
> tables, or when your data model is likely to evolve with new columns — relational
> databases handle schema changes gracefully.
>
> DynamoDB wins when you have very high write throughput — millions of writes per
> second — when your access patterns are known upfront and simple, when you're past
> 100 million rows and sharding RDS becomes painful, or when you need truly serverless
> scaling with zero DBA overhead.
>
> The trap I see junior engineers fall into is choosing DynamoDB for everything.
> It's actually harder to use correctly than RDS. If you don't know your access
> patterns before designing the table, you'll end up doing expensive full-table
> scans, which defeats the entire purpose."

```
  Complex joins between 3+ tables?       YES → RDS             NO → DynamoDB
  Ad-hoc queries (analytics, reports)?   YES → RDS             NO → DynamoDB

  Schema changes expected?               YES → RDS             NO → DynamoDB
  > 100M rows and growing fast?          expensive → DynamoDB   ← DynamoDB
  Write throughput > 10K/sec?            painful → DynamoDB     ← DynamoDB
  Known, fixed access patterns?          either                ← DynamoDB
  Serverless / no DBA team?              careful               ← DynamoDB

  CONCRETE NUMBERS:
  ─────────────────────────────────────────────────────────────────────────
  RDS Aurora: max ~64TB storage, ~200K reads/s with read replicas
  DynamoDB:   unlimited storage, millions of ops/sec, auto-sharded

  PRODUCTION EXAMPLES:
  ─────────────────────────────────────────────────────────────────────────
  Flipkart orders (financial records, joins to payments)     → Aurora RDS
  Flipkart product catalog (50M items, get-by-ID only)       → DynamoDB
  WhatsApp messages (append-only, PK=chatId, SK=timestamp)   → DynamoDB
  Job scheduler state (PK=jobId, get by status)              → DynamoDB
  User authentication (complex user profile, roles, RBAC)    → RDS
  Session storage (simple key-value, TTL)                    → DynamoDB or Redis
```

> **You say:**
>
> "The anti-pattern I want to call out specifically: I've seen teams use DynamoDB
> for a feature that starts simple — 'just get user by ID' — but then product adds
> requirements: 'filter by city', 'sort by registration date', 'get all users who
> purchased in the last 7 days'. Each new access pattern requires a new GSI.
> After 5 GSIs, you're paying for 5 copies of your data and your table is a mess.
>
> If the product roadmap is unclear, start with RDS. Migrate to DynamoDB when the
> access patterns are proven and stable."

## SECTION 2 — Single-Table Design

---

### When They Ask: "Explain DynamoDB single-table design. Why would you put Users and Orders in the same table?"

> **You say:**
>
> "In a relational database, you put related data in separate tables and JOIN them
> at query time. DynamoDB has no JOIN operation. So if you need a user plus all
> their orders in a single response — which is the most common e-commerce query —
> and they're in separate tables, you need two separate DynamoDB queries, then
> merge them in your application code.
>
> Single-table design solves this by putting related entities under the same
> partition key. If PK=USER#123 has items with SK=PROFILE, SK=ORDER#001,
> SK=ORDER#002, then one Query with PK=USER#123 returns everything in a single
> round trip.
>
> The mental model shift: you design the table around your access patterns,
> not around your entities. Start with the list of every query your app will
> make, then design PK/SK to make those queries efficient."

```
SINGLE-TABLE DESIGN — E-Commerce Example
==========================================

  TABLE: ecommerce (PK + SK composite key)
  ──────────────────────────────────────────────────────────────────────────
  PK              SK                  Attributes
  ──────────────────────────────────────────────────────────────────────────
  USER#123        PROFILE             name="Abhishek", email="a@b.com", city="Pune"
  USER#123        ORDER#2026-08-31-001 total=2500, status="PLACED", items=[...]
  USER#123        ORDER#2026-08-30-002 total=1200, status="DELIVERED", items=[...]
  USER#123        SESSION#tok-abc      expires=2026-09-01, device="mobile"
  USER#123        REVIEW#PROD#456      rating=5, text="Great product", date="2026-08-31"

  PRODUCT#456     DETAIL              name="Laptop", price=55000, category="electronics"
  PRODUCT#456     INVENTORY#PUNE      qty=45, warehouse="PUNE-01"
  PRODUCT#456     INVENTORY#MUMBAI    qty=12, warehouse="MUM-01"

  ORDER#2026-08-31-001  STATUS    userId="USER#123", total=2500, status="PLACED"

  ──────────────────────────────────────────────────────────────────────────

  ACCESS PATTERNS SATISFIED:
  ──────────────────────────────────────────────────────────────────────────
  1. Get user profile          → Query PK=USER#123, SK=PROFILE
  2. Get all orders for user   → Query PK=USER#123, SK begins_with "ORDER#"
  3. Get user + all orders     → Query PK=USER#123 (returns all SK rows) — 1 round trip!
  4. Get recent orders only    → Query PK=USER#123, SK between ORDER#2026-08 and ORDER#2026-09
  5. Get product + inventory   → Query PK=PRODUCT#456 (returns DETAIL + all INVENTORY rows)

  ENTITY TYPE DISCRIMINATOR:
  ──────────────────────────────────────────────────────────────────────────
  Add attribute "entityType" = "USER_PROFILE" | "ORDER" | "SESSION" | "PRODUCT"
  Lets Lambda/service know which entity type to deserialize into
```

```java
// DynamoDB SDK v2 — Query all items for a user (profile + orders)
import software.amazon.awssdk.services.dynamodb.DynamoDbClient;
import software.amazon.awssdk.services.dynamodb.model.*;

@Service
public class UserOrderRepository {

    private final DynamoDbClient dynamoDb;
    private static final String TABLE = "ecommerce";

    // Get user profile + all orders in ONE query
    public List<Map<String, AttributeValue>> getUserWithOrders(String userId) {
        QueryRequest request = QueryRequest.builder()
            .tableName(TABLE)
            .keyConditionExpression("PK = :pk AND SK BETWEEN :start AND :end")
            .expressionAttributeValues(Map.of(
                ":pk",    AttributeValue.fromS("USER#" + userId),
                ":start", AttributeValue.fromS("ORDER#"),   // SK >= "ORDER#"
                ":end",   AttributeValue.fromS("PROFILE")   // SK <= "PROFILE" (alphabetically after ORDER)
            ))
            .build();
        // Note: use "begins_with" for prefix scans — cleaner than BETWEEN
        return dynamoDb.query(request).items();
    }

    // Get only orders for a user (SK prefix scan)
    public List<Map<String, AttributeValue>> getOrders(String userId) {
        QueryRequest request = QueryRequest.builder()
            .tableName(TABLE)
            .keyConditionExpression("PK = :pk AND begins_with(SK, :skPrefix)")
            .expressionAttributeValues(Map.of(
                ":pk",       AttributeValue.fromS("USER#" + userId),
                ":skPrefix", AttributeValue.fromS("ORDER#")
            ))
            .scanIndexForward(false)    // newest first (descending SK order)
            .limit(20)                  // pagination — don't return everything
            .build();

        QueryResponse response = dynamoDb.query(request);
        return response.items();
    }

    // Put a new order
    public void putOrder(String userId, String orderId, Map<String, AttributeValue> orderData) {
        Map<String, AttributeValue> item = new HashMap<>(orderData);
        item.put("PK", AttributeValue.fromS("USER#" + userId));
        item.put("SK", AttributeValue.fromS("ORDER#" + orderId));
        item.put("entityType", AttributeValue.fromS("ORDER"));
        // Also write the ORDER#xxx → STATUS lookup item for GSI access
        item.put("GSI1PK", AttributeValue.fromS("STATUS#" + orderData.get("status").s()));
        item.put("GSI1SK", AttributeValue.fromS("ORDER#" + orderId));

        PutItemRequest request = PutItemRequest.builder()
            .tableName(TABLE)
            .item(item)
            .conditionExpression("attribute_not_exists(PK)")  // prevent overwrite
            .build();
        dynamoDb.putItem(request);
    }
}
```

### When They Ask: "How do you design for multiple access patterns with GSI overloading?"

> **You say:**
>
> "GSI overloading means reusing the same GSI index for multiple entity types, each
> with a different meaning for the GSI PK and SK. I name the GSI attributes GSI1PK
> and GSI1SK generically so they can hold different values per entity type.
>
> For our e-commerce example: orders need to be queried by status (ops team wants
> all PENDING orders), and products need to be queried by category. Both can use
> the same GSI — the GSI PK just holds different prefixes."

```
GSI OVERLOADING — One GSI, Multiple Access Patterns
=====================================================

  MAIN TABLE
  ─────────────────────────────────────────────────────────────────────
  PK              SK                  GSI1PK              GSI1SK
  ─────────────────────────────────────────────────────────────────────
  USER#123        ORDER#001           STATUS#PENDING      2026-08-31T10:00:00
  USER#456        ORDER#002           STATUS#PENDING      2026-08-31T10:05:00
  USER#789        ORDER#003           STATUS#DELIVERED    2026-08-30T09:00:00
  PRODUCT#001     DETAIL              CATEGORY#electronics  PRODUCT#001
  PRODUCT#002     DETAIL              CATEGORY#electronics  PRODUCT#002
  PRODUCT#003     DETAIL              CATEGORY#fashion      PRODUCT#003

  GSI1 (GSI1PK + GSI1SK as key)
  ─────────────────────────────────────────────────────────────────────
  Query GSI1 where GSI1PK = "STATUS#PENDING"
  → returns ORDER#001 and ORDER#002 (all pending orders) ✅

  Query GSI1 where GSI1PK = "CATEGORY#electronics"
  → returns PRODUCT#001 and PRODUCT#002 ✅

  ONE GSI serves TWO completely different access patterns!
  Pay for one GSI instead of two.
```

## SECTION 3 — GSI Hot Partition Trap

---

### When They Ask: "What is a hot partition in DynamoDB and how do you fix it?"

> **You say:**
>
> "A hot partition happens when a disproportionate share of your reads or writes
> hit the same physical partition. Every DynamoDB partition has a hard limit:
> 3,000 RCU and 1,000 WCU. If you have 30,000 provisioned RCU but one partition
> is receiving all the traffic, you're throttled at 3,000 — you've wasted 90%
> of your capacity.
>
> The most common cause I've seen: a GSI on a low-cardinality attribute. Classic
> example — a GSI where the key is order status. There are only four statuses:
> PENDING, PROCESSING, SHIPPED, DELIVERED. All new orders are PENDING, so
> every new order write goes to the PENDING partition of that GSI. Instant hot partition.
>
> Let me walk through three fixes."

```
HOT PARTITION — How It Happens
================================

  Order GSI on "status" attribute
  ─────────────────────────────────────────────────────────────────────
  GSI PK = status

  Partition: "PENDING"
  ████████████████████████████████████████████████████████ ← 98% of traffic
  (All new orders start as PENDING — writes hammer this partition)

  Partition: "PROCESSING"
  ████ ← 2% of traffic

  Partition: "SHIPPED"
  ██ ← < 1%

  Partition: "DELIVERED"
  █ ← < 1%

  RESULT: ProvisionedThroughputExceededException on writes
          CloudWatch: ConsumedWriteCapacityUnits spikes, throttled requests spike

  SYMPTOMS TO MENTION IN INTERVIEW:
  ─────────────────────────────────────────────────────────────────────
  • ProvisionedThroughputExceededException in application logs
  • DynamoDB CloudWatch metric: ThrottledRequests > 0
  • ConsumedWriteCapacityUnits on one GSI partition = 100% of limit
  • Application: retries with exponential backoff → high latency
```

```
FIX 1 — GSI Sparse Index (Only Index Actionable States)
=========================================================

  Problem: You don't actually need a GSI for DELIVERED orders
           (ops only queries PENDING and PROCESSING)

  Solution: Only write GSI1PK when status is PENDING or PROCESSING.
            DynamoDB only includes items in a GSI if the GSI key attribute EXISTS.

  ITEM when order placed:
    PK=USER#123, SK=ORDER#001, status="PENDING",
    GSI1PK="STATUS#PENDING"   ← present → appears in GSI

  ITEM when order delivered:
    PK=USER#123, SK=ORDER#001, status="DELIVERED"
    GSI1PK is REMOVED (delete the attribute via UpdateItem)
    → item is REMOVED from GSI automatically ✅

  GSI now only contains items you actually need to query.
  DELIVERED orders (90% of all orders) are NOT in the GSI → much smaller index
  → far less write traffic to GSI partitions.
```

```
FIX 2 — Write Sharding (Add Random Suffix to Distribute Load)
==============================================================

  Instead of GSI1PK = "STATUS#PENDING"
  Use:          GSI1PK = "STATUS#PENDING#" + random(1..10)

  So the GSI key becomes one of:
    STATUS#PENDING#1
    STATUS#PENDING#2
    ...
    STATUS#PENDING#10

  Now writes are spread across 10 partitions instead of 1.

  TRADE-OFF: To query ALL pending orders, you must now run 10 parallel queries
             (one per shard suffix) and merge results in your application.

  ┌──── Query PENDING orders ────────────────────────────────────────┐
  │                                                                   │
  │  CompletableFuture<List> shard1 = query("STATUS#PENDING#1")      │
  │  CompletableFuture<List> shard2 = query("STATUS#PENDING#2")      │
  │  ...                                                              │
  │  CompletableFuture<List> shard10 = query("STATUS#PENDING#10")    │
  │                                                                   │
  │  allOf(shard1..shard10).join() → merge → sort → paginate         │
  └───────────────────────────────────────────────────────────────────┘

  Acceptable when: you need even write distribution more than simple queries.
  Not acceptable when: query simplicity is critical (e.g., the ops team runs
  ad-hoc queries directly against DynamoDB console).
```

```
FIX 3 — Time-Based Key (Best for Ordered Data)
================================================

  Instead of: GSI1PK = "STATUS#PENDING"
  Use:        GSI1PK = "STATUS#PENDING#2026-08-31"  (date partition)

  This naturally distributes writes across days.
  Query "all pending orders today": one query against STATUS#PENDING#2026-08-31
  Query "all pending orders this week": 7 queries (one per day), parallel, merge.

  BEST FOR: orders, events, logs, notifications — anything time-ordered.

  Combined key pattern (used in production):
    GSI1PK = "STATUS#PENDING#2026-08-31"
    GSI1SK = ISO timestamp (for sorting within the day)

  HOT (bad)                 vs    DISTRIBUTED (good)
  ─────────────────────────────────────────────────────
  STATUS#PENDING            vs    STATUS#PENDING#2026-08-31
  ████████████ all traffic       ██ (today's traffic, spreads over days)
                                 STATUS#PENDING#2026-08-30
                                 ██ (yesterday's — barely touched)
                                 STATUS#PENDING#2026-08-29
                                 █
```

```java
// DynamoDB SDK v2 — Write sharding example for order status GSI
@Service
public class OrderStatusRepository {

    private final DynamoDbClient dynamoDb;
    private static final int SHARD_COUNT = 10;
    private static final Random RANDOM = new Random();

    // Write: assign random shard suffix
    public void writeOrder(String userId, String orderId) {
        int shard = RANDOM.nextInt(SHARD_COUNT) + 1;  // 1 to 10
        String gsi1pk = "STATUS#PENDING#" + shard;

        Map<String, AttributeValue> item = Map.of(
            "PK",       AttributeValue.fromS("USER#" + userId),
            "SK",       AttributeValue.fromS("ORDER#" + orderId),
            "status",   AttributeValue.fromS("PENDING"),
            "GSI1PK",   AttributeValue.fromS(gsi1pk),
            "GSI1SK",   AttributeValue.fromS(Instant.now().toString())
        );
        dynamoDb.putItem(PutItemRequest.builder().tableName("ecommerce").item(item).build());
    }

    // Read: scatter-gather across all shards
    public List<Map<String, AttributeValue>> getAllPendingOrders() {
        List<CompletableFuture<QueryResponse>> futures = IntStream.rangeClosed(1, SHARD_COUNT)
            .mapToObj(shard -> CompletableFuture.supplyAsync(() -> {
                QueryRequest req = QueryRequest.builder()
                    .tableName("ecommerce")
                    .indexName("GSI1")
                    .keyConditionExpression("GSI1PK = :pk")
                    .expressionAttributeValues(Map.of(
                        ":pk", AttributeValue.fromS("STATUS#PENDING#" + shard)
                    ))
                    .build();
                return dynamoDb.query(req);
            }))
            .collect(Collectors.toList());

        return futures.stream()
            .map(CompletableFuture::join)
            .flatMap(response -> response.items().stream())
            .collect(Collectors.toList());
    }
}
```

## SECTION 4 — DAX vs ElastiCache — Which Cache to Use With DynamoDB

---

### When They Ask: "What is DAX and when would you use it instead of ElastiCache?"

> **You say:**
>
> "DAX — DynamoDB Accelerator — is a write-through, in-memory cache that is
> purpose-built for DynamoDB. It's transparent: you point your DynamoDB SDK
> at the DAX cluster endpoint instead of the DynamoDB endpoint. Your code
> changes zero lines — DAX intercepts the call, checks its cache, returns the
> item if it's there, or fetches from DynamoDB and caches the result.
>
> DAX gives you microsecond read latency for item lookups by PK. Standard
> DynamoDB is single-digit milliseconds — DAX brings that to under 100 microseconds.
>
> ElastiCache Redis is a general-purpose cache you manage yourself. You can use
> it for anything — RDS queries, DynamoDB items, API responses, session state.
> But you write your own cache-aside logic: check Redis, on miss fetch from
> source, write to Redis, handle TTL, handle invalidation.
>
> When I use DAX: simple GetItem by primary key that's called thousands of
> times per second with the same key — think product detail page.
> When I use ElastiCache: I need to cache the result of a complex query, cache
> data from multiple sources, or need fine-grained invalidation logic."

```
DAX ARCHITECTURE — Transparent Write-Through Cache
====================================================

  YOUR APPLICATION
        │
        │ SDK call to DAX endpoint (not DynamoDB endpoint)
        ▼
  ┌──────────────────────────────────────────────┐
  │  DAX Cluster (Multi-AZ, 3 nodes minimum)     │
  │  ┌──────────────┐  ┌──────────────────────┐  │
  │  │ Item Cache   │  │ Query Cache          │  │
  │  │ GetItem by   │  │ Query/Scan result    │  │
  │  │ PK → item    │  │ sets (separate TTL)  │  │
  │  │ TTL: 5 min   │  │ TTL: 1 min (default) │  │
  │  └──────────────┘  └──────────────────────┘  │
  └─────────────────────┬────────────────────────┘
          CACHE HIT:    │     CACHE MISS:
          return <1ms   │     forward to DynamoDB
                        ▼
                 DynamoDB (5-10ms)
                 result cached in DAX → returned to app


  WHAT DAX DOES NOT CACHE:
  ─────────────────────────────────────────────────
  • Strongly consistent reads (ConsistentRead=true) — bypasses DAX entirely
  • Transactional reads (TransactGetItems) — bypasses DAX
  • Writes — DAX forwards to DynamoDB, then updates its cache (write-through)
  • If item not in table → cache MISS result NOT cached (no negative caching)
```

```
ELASTICACHE (Redis) WITH DYNAMODB — Cache-Aside Pattern
=========================================================

  YOUR APPLICATION
        │
        │ 1. Check Redis
        ▼
  ┌──────────────┐
  │  ElastiCache  │
  │  Redis        │ ─── HIT: return cached item (< 5ms)
  └──────┬────────┘
         │ MISS
         │ 2. Fetch from DynamoDB
         ▼
  ┌──────────────┐
  │  DynamoDB    │ ─── returns item (5-10ms)
  └──────┬────────┘
         │ 3. Write to Redis with TTL
         ▼
  ┌──────────────┐
  │  ElastiCache  │ ─── cached, next request hits Redis
  └──────────────┘
         │ 4. Return to app
         ▼
  APPLICATION

  YOU WRITE ALL THIS LOGIC YOURSELF.
  YOU MANAGE: TTL, invalidation on update, cache stampede prevention.
```

```
DAX vs ElastiCache — DECISION TABLE
======================================

  Criterion                     DAX                      ElastiCache Redis
  ─────────────────────────────────────────────────────────────────────────────
  Setup                         Change endpoint URL       Write cache-aside logic
  Works with                    DynamoDB ONLY             Any data source
  Latency                       < 100 microseconds        < 5 milliseconds
  Consistent reads              Bypasses cache            Your choice
  Custom invalidation           Not possible              Full control
  Query result caching          Yes (separate TTL)        Yes (manual)
  Cross-service cache           No                        Yes (RDS + DDB + APIs)
  Session storage               No                        Yes
  Cost                          EC2-based nodes (~$200/mo) EC2-based nodes (~$50+)
  Code change needed            Zero (endpoint swap)      Yes (cache logic)
  ─────────────────────────────────────────────────────────────────────────────

  USE DAX WHEN:
  → Your bottleneck is DynamoDB GetItem/Query latency
  → You need sub-millisecond reads with zero code change
  → Access pattern is simple: get by PK, or predictable query
  → You do NOT need strongly consistent reads

  USE ELASTICACHE WHEN:
  → You need to cache results from multiple services (RDS + DDB + external APIs)
  → You need fine-grained cache invalidation (update product → evict cache)
  → You're caching session state, rate-limit counters, leaderboards
  → You want control over what gets cached and for how long
  → Your queries are complex and you cache the result set, not individual items

  BOTH TOGETHER (advanced):
  → DAX for hot GetItem calls (product detail, user profile)
  → ElastiCache for session state, cross-service caching, custom logic
```

## SECTION 5 — DynamoDB Streams and Exactly-Once Processing

---

### When They Ask: "How do you use DynamoDB Streams for real-time sync to Elasticsearch?"

> **You say:**
>
> "DynamoDB Streams is an ordered log of every change — INSERT, MODIFY, REMOVE —
> on every item in a table. The log is retained for 24 hours. Each item's changes
> appear in the correct order within that item's shard.
>
> The classic use case is CDC — change data capture. When a product is updated in
> DynamoDB, the Streams record triggers a Lambda, which updates the Elasticsearch
> index. Your search index stays in sync without your application having to call
> Elasticsearch directly. The product service writes to DynamoDB and is done —
> the async pipeline handles search separately.
>
> But there's a trap: Lambda event source mapping gives you at-least-once delivery.
> A Lambda invocation can fail and be retried — your downstream system may process
> the same change twice. For Elasticsearch this is usually fine — idempotent PUT.
> For a billing system or audit trail, you need deduplication."

```
DYNAMODB STREAMS → LAMBDA → ELASTICSEARCH (CDC Pipeline)
=========================================================

  DynamoDB Table (ecommerce)
    │  Product updated: PK=PRODUCT#456, name changed
    │
    ▼
  DynamoDB Streams
  ┌──────────────────────────────────────────────────────────┐
  │ Shard-0: [{eventName: MODIFY, newImage: {...},           │
  │            oldImage: {...}}]                             │
  │ Shard-1: [INSERT record for new product]                 │
  │ Shard-2: [REMOVE record for deleted product]             │
  │ Retention: 24 hours                                      │
  │ Ordered: per item (not across items)                     │
  └──────────────────┬───────────────────────────────────────┘
                     │ Event Source Mapping (batch size: 10)
                     ▼
  AWS Lambda (product-search-sync)
  ┌──────────────────────────────────────────────────────────┐
  │  for each record:                                        │
  │    if INSERT or MODIFY → upsert to Elasticsearch         │
  │    if REMOVE → delete from Elasticsearch                 │
  └──────────────────┬───────────────────────────────────────┘
                     │
                     ▼
  Amazon Elasticsearch Service (OpenSearch)
  → Product search index stays current
  → < 1 second lag from DynamoDB write to search indexed
```

```
THE EXACTLY-ONCE TRAP
======================

  Lambda at-least-once delivery:
  ─────────────────────────────────────────────────────────
  1. Lambda processes batch of 10 Streams records
  2. Item #7 processing fails (Elasticsearch timeout)
  3. Lambda returns error
  4. AWS retries the ENTIRE batch from the beginning
  5. Items 1-6 are processed AGAIN

  For Elasticsearch: safe — upsert is idempotent (PUT replaces)
  For Audit Ledger:  DANGEROUS — audit entry written twice

  FIX OPTION 1 — Conditional Write Idempotency Check
  ─────────────────────────────────────────────────────────
  Before processing, write to a "processed events" DynamoDB table:
    PK = streamEventId (unique per Streams record)
    conditionExpression = "attribute_not_exists(PK)"
  If the condition fails → event already processed → skip it.

  FIX OPTION 2 — SQS FIFO with MessageDeduplicationId
  ─────────────────────────────────────────────────────────
  DynamoDB Stream → Lambda (just enqueues to SQS FIFO)
                 → SQS FIFO deduplication window = 5 minutes
                 → Consumer Lambda processes from SQS FIFO
  SQS FIFO deduplication: if same MessageDeduplicationId arrives
  within 5 minutes, the second copy is discarded automatically.
```

```java
// Lambda handler for DynamoDB Streams → Elasticsearch sync
public class ProductSearchSyncHandler
        implements RequestHandler<DynamodbEvent, Void> {

    private final ElasticsearchClient esClient;
    private final DynamoDbClient dedupeDb;

    @Override
    public Void handleRequest(DynamodbEvent event, Context context) {
        for (DynamodbEvent.DynamodbStreamRecord record : event.getRecords()) {
            String eventId = record.getEventID();

            // Idempotency check — skip if already processed
            if (alreadyProcessed(eventId)) {
                log.info("Skipping duplicate eventId={}", eventId);
                continue;
            }

            try {
                String eventName = record.getEventName(); // INSERT / MODIFY / REMOVE
                switch (eventName) {
                    case "INSERT":
                    case "MODIFY":
                        Map<String, AttributeValue> newImage =
                            record.getDynamodb().getNewImage();
                        indexProduct(newImage);
                        break;
                    case "REMOVE":
                        String productId = record.getDynamodb()
                            .getKeys().get("PK").getS()
                            .replace("PRODUCT#", "");
                        deleteFromIndex(productId);
                        break;
                }
                markProcessed(eventId);  // write to dedup table with TTL=7 days
            } catch (Exception e) {
                log.error("Failed to process eventId={}", eventId, e);
                throw e;  // re-throw → Lambda retries the batch
            }
        }
        return null;
    }

    private boolean alreadyProcessed(String eventId) {
        try {
            GetItemResponse response = dedupeDb.getItem(GetItemRequest.builder()
                .tableName("processed-events")
                .key(Map.of("eventId", AttributeValue.fromS(eventId)))
                .build());
            return response.hasItem();
        } catch (Exception e) {
            return false;  // on error, assume not processed — safe to retry
        }
    }

    private void markProcessed(String eventId) {
        dedupeDb.putItem(PutItemRequest.builder()
            .tableName("processed-events")
            .item(Map.of(
                "eventId", AttributeValue.fromS(eventId),
                "ttl",     AttributeValue.fromN(
                    String.valueOf(Instant.now().plusSeconds(604800).getEpochSecond()) // 7 days TTL
                )
            ))
            .conditionExpression("attribute_not_exists(eventId)")  // race-condition safe
            .build());
    }
}
```

## SECTION 6 — DynamoDB Capacity Modes

---

### When They Ask: "On-demand vs provisioned — which do you choose and why?"

> **You say:**
>
> "On-demand mode is pay-per-request — no capacity planning, instant scale,
> but 5x to 7x more expensive per request than provisioned. It's perfect for
> unpredictable workloads, new features in development, or tables that are
> accessed infrequently.
>
> Provisioned mode requires you to declare RCU and WCU upfront. If your
> application sends more requests than provisioned, DynamoDB throttles you.
> But it's significantly cheaper at steady, predictable loads. You add
> Auto Scaling on top — set target utilization to 70% and DynamoDB adjusts
> capacity up and down automatically.
>
> The critical trap most people miss: even with unlimited provisioned capacity,
> a single partition can never handle more than 3,000 RCU or 1,000 WCU. This
> is the hot partition limit — it's a hard physical limit per partition shard,
> not a configuration setting."

```
CAPACITY MODES — On-Demand vs Provisioned
==========================================

  ON-DEMAND MODE
  ──────────────────────────────────────────────────────────────────
  • Pay per request: $1.25 per million reads, $1.25 per million writes
  • No capacity planning needed
  • Scales instantly to any traffic spike
  • More expensive at high, steady throughput
  • Best for: unpredictable workloads, dev/test tables, new features
  • Limitation: can have 2x previous peak as instant cap — if you've
    never had more than 100 req/s, sudden 10,000 req/s may throttle briefly

  PROVISIONED MODE + AUTO SCALING
  ──────────────────────────────────────────────────────────────────
  • Pay for capacity reserved (whether used or not)
  • Much cheaper at predictable loads (~5x cost difference)
  • Auto scaling: min=100 RCU, max=10000 RCU, target=70% utilization
  • Scale-out: fast (within 1-2 minutes when utilization > 70%)
  • Scale-in: slow (cooldown period = 300 seconds by default — prevent thrash)
  • Best for: production tables with predictable, steady traffic

  HARD LIMITS TO MEMORIZE:
  ──────────────────────────────────────────────────────────────────
  Per partition: max 3,000 RCU  (strongly consistent)
                 max 6,000 RCU  (eventually consistent — counted at 0.5 RCU each)
                 max 1,000 WCU
  Per table (soft limits, can request increase):
                 40,000 RCU and 40,000 WCU (us-east-1)
  Item size: max 400 KB per item

  ADAPTIVE CAPACITY
  ──────────────────────────────────────────────────────────────────
  DynamoDB's automatic mitigation for hot partitions:
  • Detects which partitions are hot → reallocates unused capacity from
    cool partitions to the hot one
  • Can sustain brief hot partition spikes, NOT chronic hotspots
  • Does NOT eliminate the 3,000 RCU per-partition hard limit — it just
    borrowing unused capacity, which means cool partitions get less
  • Do NOT rely on adaptive capacity as a substitute for proper key design
```

```
PROVISIONED + AUTO SCALING — CloudFormation / CDK config
=========================================================

  AUTO SCALING SETUP (conceptual):

  Table:  ecommerce
  RCU:    provisioned = 1000
  WCU:    provisioned = 500

  Auto Scaling Policy:
    minCapacity: 100 RCU
    maxCapacity: 10000 RCU

  SCENARIO:
  ─────────────────────────────────────────────────────────────────
  t=0min:   traffic = 600 RCU/s → 60% of 1000 → below 70% → no action
  t=5min:   flash sale starts → 800 RCU/s → 80% of 1000 → SCALE UP triggered

  t=30min:  flash sale ends → 200 RCU/s → 16% of 1200 → SCALE DOWN triggered (after cooldown)
  t=35min:  DynamoDB scales to 300 RCU (200/0.7 ≈ 286 → rounds up)
```

## COMMON TRAPS AND GOTCHAS

1. **Designing the table before knowing access patterns.** DynamoDB is access-pattern-first. Sit down with the product team, list every query the application will ever need, then design PK/SK. If you design the table first, you'll be doing expensive Scan operations later.

2. **GSI on low-cardinality attributes.** Never make a GSI on `status`, `boolean`, `country`, or any field with fewer than 100 distinct values. All writes to the same value hit the same GSI partition. Use sparse indexes or sharding instead.

3. **Relying on Scan for any production query.** `Scan` reads every item in the table and filters client-side. On a 100M row table, a Scan charges you for every single item read. One Scan query can cost hundreds of dollars. If you're writing a Scan, you've missed an access pattern — add a GSI instead.

4. **Forgetting the 400 KB item size limit.** If you're storing a chat conversation or order history directly in an item, you'll hit this. Pattern: store messages as separate items with PK=CHAT#id, SK=MSG#timestamp — never embed unbounded lists in a single item.

5. **Strongly consistent reads bypass DAX.** If you set `ConsistentRead=true` on your GetItem call, DAX is completely bypassed — you pay full DynamoDB read cost and get DynamoDB latency. DAX only accelerates eventually consistent reads (the default).

6. **Lambda retries with Streams = at-least-once, not exactly-once.** Any state change in downstream systems (Elasticsearch, billing, audit) must be idempotent or use a deduplication mechanism. Never assume a Lambda triggered by Streams fires exactly once.

7. **On-demand mode cost shock at scale.** On-demand is 5-7x more expensive than provisioned at steady load. A table doing 100,000 writes/second in on-demand mode will run up a $10,000+/month bill. Profile your access patterns and switch to provisioned + auto scaling once traffic is predictable.

8. **Missing TTL on transient data.** DynamoDB charges for storage. Sessions, temporary tokens, deduplication records — always set a `ttl` attribute (Unix epoch seconds) and enable TTL on the table. DynamoDB deletes expired items automatically at no charge. Forgetting this causes storage to balloon with stale data.
