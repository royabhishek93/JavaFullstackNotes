### PART 1 — When They Ask: "How does ECS Auto Scaling work? Show me the config."

> **You say:**
>
> "ECS Service Auto Scaling uses AWS Application Auto Scaling under the hood.
> We configure target tracking policies — similar to a thermostat. Set a target
> CPU of 60%, and Auto Scaling automatically adds or removes tasks to keep
> average CPU near that target.
>
> For the Order Service we use two policies: CPU-based for request-driven load,
> and ALB request count per target for more precise scaling when CPU doesn't
> correlate well with load."

```
ECS AUTO SCALING — Two Policy Types
======================================

  Target Tracking: CPU @ 60%
  ───────────────────────────
  Current: 4 tasks, avg CPU = 80%
  Target:  60% CPU
  Action:  need ~5.3 tasks to bring CPU to 60%
           → scale to 6 tasks (round up)

  Current: 6 tasks, avg CPU = 30%
  Target:  60% CPU
  Action:  could reduce to 3 tasks
           → but scale-in cooldown (10 min) prevents premature removal
           → waits 10 min, still 30% → scale to 3 tasks

  Target Tracking: ALB Requests/Target @ 1000
  ────────────────────────────────────────────
  Current: 4 tasks, 6000 req/min
  Target:  1000 req/min per task
  Action:  need 6 tasks → scale to 6

  USE BOTH POLICIES (AWS picks the one that requires MORE tasks):
  CPU says 6, Requests say 8 → ECS scales to 8 (more conservative)
```

**Terraform config for ECS Auto Scaling:**

```hcl
# Register the ECS service as a scalable target
resource "aws_appautoscaling_target" "order_service" {
  max_capacity       = 20      # never exceed this (cost protection)
  min_capacity       = 2       # never go below (always available)
  resource_id        = "service/swiggy-prod/order-service"
  scalable_dimension = "ecs:service:DesiredCount"
  service_namespace  = "ecs"
}

# Policy 1: CPU-based scaling
resource "aws_appautoscaling_policy" "cpu_scaling" {
  name               = "order-service-cpu-scaling"
  policy_type        = "TargetTrackingScaling"
  resource_id        = aws_appautoscaling_target.order_service.resource_id
  scalable_dimension = aws_appautoscaling_target.order_service.scalable_dimension
  service_namespace  = aws_appautoscaling_target.order_service.service_namespace

  target_tracking_scaling_policy_configuration {
    target_value       = 60.0   # keep CPU at 60%
    scale_out_cooldown = 120    # 2 min before adding more tasks after scale-out
    scale_in_cooldown  = 600    # 10 min before removing tasks after scale-in

    predefined_metric_specification {
      predefined_metric_type = "ECSServiceAverageCPUUtilization"
    }
  }
}

# Policy 2: ALB request count per target
resource "aws_appautoscaling_policy" "request_scaling" {
  name               = "order-service-request-scaling"
  policy_type        = "TargetTrackingScaling"
  resource_id        = aws_appautoscaling_target.order_service.resource_id
  scalable_dimension = aws_appautoscaling_target.order_service.scalable_dimension
  service_namespace  = aws_appautoscaling_target.order_service.service_namespace

  target_tracking_scaling_policy_configuration {
    target_value       = 1000   # 1000 requests/min per task
    scale_out_cooldown = 120
    scale_in_cooldown  = 600

    predefined_metric_specification {
      predefined_metric_type = "ALBRequestCountPerTarget"
      resource_label         = "${aws_lb.main.arn_suffix}/${aws_lb_target_group.order.arn_suffix}"
    }
  }
}
```

### PART 2 — When They Ask: "What is the warmup period? Why does it matter?"

> **You say:**
>
> "This is a question most engineers don't think about until a traffic spike
> causes an incident. ECS Auto Scaling fires and new tasks start, but there's
> a gap between 'task started' and 'task serving traffic'.
>
> For a Spring Boot service, that gap can be 60-90 seconds: container pulls,
> JVM startup, Spring context initialization, database connection pool warmup,
> health check passes, ALB registers target, traffic shifts.
>
> If you're scaling in response to current overload — CPU already at 90% —
> the new tasks take 90 seconds to help. During those 90 seconds the existing
> tasks are overloaded. Requests timeout or are slow."

```
SCALING WARMUP TIMELINE — 4 Minutes from Trigger to Full Capacity
===================================================================

  t=0:    CPU crosses 60% threshold
          Auto Scaling decides to add 2 tasks

  t=0:    ECS allocates Fargate resources (Nitro micro-VM)

  t=30s:  Container image pulled from ECR
          (if not cached on the Fargate host — first pull is slow)

  t=50s:  Container starts
          JVM begins loading Spring Boot application

  t=80s:  Spring context loaded
          HikariCP creates initial DB connections (min-idle: 2)
          Application listening on port 8080

  t=90s:  ECS sends /actuator/health → 200 OK
          ALB begins health check interval (every 30s)

  t=120s: After 2 consecutive health checks pass
          ALB registers target as healthy
          Traffic begins routing to new tasks

  t=240s: New tasks fully warmed (connection pool full, JIT compiled)
          At peak efficiency

  TOTAL: ~4 minutes from Auto Scaling trigger to full capacity

  ╔═══════════════════════════════════════════════════════════════╗
  ║  IMPLICATION: Scale out BEFORE you're overwhelmed.           ║
  ║  60% CPU target (not 80%) buys you 4 minutes of headroom     ║
  ║  before tasks are at capacity.                               ║
  ╚═══════════════════════════════════════════════════════════════╝
```

**Spring Boot health check tuning for fast startup:**

```yaml
# application.yml — optimize startup time
spring:
  jpa:
    open-in-view: false         # don't hold DB connection through entire request
  datasource:
    hikari:
      initialization-fail-timeout: 30000  # fail fast if DB unreachable at startup

management:
  health:
    db:
      enabled: true             # ALB only gets healthy if DB is reachable
    redis:
      enabled: true
  endpoint:
    health:
      show-details: never       # don't leak internal state in health response
```

```yaml
# ALB target group health check settings:
HealthCheckProtocol: HTTP
HealthCheckPath: /actuator/health
HealthCheckIntervalSeconds: 30     # check every 30s
HealthyThresholdCount: 2           # 2 passes = healthy (60s to become healthy)
UnhealthyThresholdCount: 3         # 3 failures = unhealthy (90s to remove)
HealthCheckTimeoutSeconds: 5       # each check must respond in 5s
```

### PART 3 — When They Ask: "How do you scale async workers (SQS consumers)?"

> **You say:**
>
> "For the notification workers consuming from SQS, CPU isn't a good scaling signal.
> A consumer waiting for messages uses almost zero CPU. The right signal is
> SQS queue depth — how many messages are waiting to be processed.
>
> We use a custom CloudWatch metric and a step scaling policy.
> If more than 1000 messages are in the queue, add tasks. If it drops below 100,
> remove tasks."

```
SQS DEPTH-BASED SCALING — Notification Workers
================================================

  ApproximateNumberOfMessagesVisible (SQS metric)
         |
         v
  CloudWatch Alarm → ECS Step Scaling

  SCALE-OUT STEPS:
  0-100   messages: 1 task   (baseline)
  100-500 messages: 2 tasks
  500-1000 messages: 4 tasks
  1000+   messages: 8 tasks

  SCALE-IN:
  Scale-in cooldown: 5 min (don't remove tasks while still draining)
  Scale-in when: queue depth < 100 for 5 consecutive minutes
```

```hcl
# Custom CloudWatch metric alarm for SQS depth
resource "aws_cloudwatch_metric_alarm" "sqs_depth_high" {
  alarm_name          = "notification-queue-depth-high"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods  = 1
  metric_name         = "ApproximateNumberOfMessagesVisible"
  namespace           = "AWS/SQS"
  period              = 60
  statistic           = "Average"
  threshold           = 1000

  dimensions = {
    QueueName = "order-notification-queue"
  }

  alarm_actions = [aws_appautoscaling_policy.sqs_step_scaling.arn]
}

resource "aws_appautoscaling_policy" "sqs_step_scaling" {
  name               = "notification-worker-sqs-scaling"
  policy_type        = "StepScaling"
  resource_id        = aws_appautoscaling_target.notification_worker.resource_id
  scalable_dimension = aws_appautoscaling_target.notification_worker.scalable_dimension
  service_namespace  = aws_appautoscaling_target.notification_worker.service_namespace

  step_scaling_policy_configuration {
    adjustment_type          = "ChangeInCapacity"
    cooldown                 = 120
    metric_aggregation_type  = "Average"

    step_adjustment {
      metric_interval_lower_bound = 0
      metric_interval_upper_bound = 500
      scaling_adjustment          = 2     # add 2 tasks for 0-500 over threshold
    }
    step_adjustment {
      metric_interval_lower_bound = 500
      scaling_adjustment          = 4     # add 4 tasks for 500+ over threshold
    }
  }
}
```

### PART 4 — When They Ask: "How do you load test? Show me."

> **You say:**
>
> "We use k6 — it's a JavaScript-based load testing tool, open source, runs
> anywhere. The test simulates realistic Swiggy user behavior: browse restaurants,
> add to cart, place order.
>
> I run load tests in two scenarios before every major release: steady state
> at 10x normal load, and a spike test that jumps to 50x in 60 seconds.
> I watch ECS task count, CPU, error rate, and p99 latency in CloudWatch while the
> test runs."

**k6 load test script:**

```javascript
// swiggy-load-test.js
import http from 'k6/http';
import { check, sleep } from 'k6';
import { Rate, Trend } from 'k6/metrics';

// Custom metrics
const errorRate    = new Rate('errors');
const orderLatency = new Trend('order_latency_ms');

export const options = {
    stages: [
        { duration: '2m',  target: 50  },  // ramp up to 50 users
        { duration: '5m',  target: 50  },  // hold at 50 users (baseline)
        { duration: '1m',  target: 500 },  // SPIKE: 10x jump in 60 seconds
        { duration: '3m',  target: 500 },  // hold at spike (watch ECS scale out)
        { duration: '2m',  target: 50  },  // ramp down (watch scale in)
        { duration: '1m',  target: 0   },  // cool down
    ],
    thresholds: {
        'http_req_duration': ['p99<500'],  // 99th percentile < 500ms
        'errors':            ['rate<0.01'], // error rate < 1%
        'order_latency_ms':  ['p95<300'],  // order placement p95 < 300ms
    },
};

const BASE_URL = __ENV.BASE_URL || 'https://staging.swiggy.com';

export function setup() {
    // Login once, get token for all virtual users
    const loginRes = http.post(`${BASE_URL}/api/auth/login`, JSON.stringify({
        email:    'loadtest@swiggy.com',
        password: __ENV.LOAD_TEST_PASSWORD,
    }), { headers: { 'Content-Type': 'application/json' } });

    check(loginRes, { 'login succeeded': (r) => r.status === 200 });
    return { token: loginRes.json('accessToken') };
}

export default function (data) {
    const headers = {
        'Authorization': `Bearer ${data.token}`,
        'Content-Type':  'application/json',
    };

    // Step 1: Browse restaurants
    const restaurantsRes = http.get(
        `${BASE_URL}/api/restaurants?lat=12.97&lng=77.59`,
        { headers }
    );
    check(restaurantsRes, { 'got restaurants': (r) => r.status === 200 });
    errorRate.add(restaurantsRes.status !== 200);

    sleep(1);  // user browsing time

    // Step 2: View menu
    const restaurants = restaurantsRes.json('restaurants');
    if (!restaurants || restaurants.length === 0) return;
    const restaurantId = restaurants[0].id;

    const menuRes = http.get(
        `${BASE_URL}/api/restaurants/${restaurantId}/menu`,
        { headers }
    );
    check(menuRes, { 'got menu': (r) => r.status === 200 });

    sleep(2);  // user choosing food

    // Step 3: Place order (the critical path)
    const startTime = Date.now();
    const orderRes = http.post(
        `${BASE_URL}/api/orders`,
        JSON.stringify({
            restaurantId: restaurantId,
            items: [{ itemId: 'item-1', quantity: 2 }],
            deliveryAddress: { lat: 12.97, lng: 77.59 }
        }),
        { headers }
    );
    orderLatency.add(Date.now() - startTime);

    check(orderRes, {
        'order placed':  (r) => r.status === 201,
        'has order id':  (r) => r.json('orderId') !== undefined,
    });
    errorRate.add(orderRes.status !== 201);

    sleep(3);  // think time between iterations
}
```

### PART 6 — When They Ask: "How do you prevent tasks from being killed mid-request?"

> **You say:**
>
> "Scale-in is where most engineers cause their own incidents.
> When ECS terminates a task during scale-in, it sends SIGTERM to the container.
> If the container doesn't handle it, the JVM dies immediately — any in-flight
> requests get a 502 from the ALB.
>
> Three things protect in-flight requests: scale-in protection on active tasks,
> connection draining on the ALB target group, and graceful shutdown in Spring Boot."

```
GRACEFUL SCALE-IN — 3 Layers of Protection
============================================

  Layer 1: ECS Scale-In Protection
  ──────────────────────────────────
  Mark tasks as "scale-in protected" while processing requests
  ECS will not terminate protected tasks during scale-in
  App logic removes protection when idle

  Layer 2: ALB Connection Draining (Deregistration Delay)
  ─────────────────────────────────────────────────────────
  When ECS marks a task for termination:
  ├── ALB stops sending NEW requests to the task
  ├── In-flight requests continue to be processed
  └── After 30s (deregistration delay): ALB force-closes connections
      ECS then sends SIGTERM to the container

  Layer 3: Spring Boot Graceful Shutdown
  ────────────────────────────────────────
  SIGTERM received by Spring Boot
  ├── Tomcat stops accepting new connections
  ├── Waits for in-flight requests to complete
  ├── After all requests done (or 30s timeout): JVM shuts down
  └── Zero dropped requests
```

```yaml
# application.yml — Spring Boot graceful shutdown
server:
  shutdown: graceful        # wait for in-flight requests before shutdown

spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s  # max wait before force shutdown
```

```yaml
# ECS Task Definition — stop timeout
{
  "stopTimeout": 60,   # give container 60s to shut down gracefully
                       # must be > ALB deregistration delay (30s)
                       # + Spring Boot shutdown timeout (30s)
}
```

## ONE-LINER ANSWERS

**"What metric do you use to trigger scaling for API services?"**
> "CPU target tracking at 60% plus ALB request count per target at 1000 req/min per task.
> AWS Auto Scaling picks whichever policy requires more tasks — conservative by design."

**"Why not just over-provision and avoid scaling altogether?"**
> "At Swiggy scale, over-provisioning for peak means paying for 20 tasks at 4am when
> 2 would do. That's 10x the cost. Auto Scaling pays for actual capacity used.
> The 4-minute warmup is the tradeoff — acceptable if you scale at 60% not 80%."

**"What happens if traffic spikes faster than your scale-out can keep up?"**
> "Two mitigations: CloudFront caches GET responses (restaurant listings, menus) so those
> requests don't hit ECS at all. And ALB queues connections briefly — it doesn't drop
> them immediately. But if the spike is too fast, you pre-scale: schedule more tasks
> before known peak hours like Diwali using scheduled scaling actions."

## FAILURE SCENARIOS

| Scenario | What Happens |
|---|---|
| Auto Scaling fires but tasks fail health check | Unhealthy tasks don't join ALB target group — scale-out effectively does nothing. Old tasks still running. Alert fires on failed task count. |
| Scale-in kills task mid-request | ALB deregistration delay (30s) + Spring Boot graceful shutdown prevents this — in-flight requests complete |
| CPU stays at 100% despite scaling | Hit max_capacity limit, or bottleneck isn't CPU (DB connection exhaustion, Redis single-thread). Add RDS Proxy, check connection pool config. |
| Scale-out cooldown too short | Tasks scale out, but next scale-out fires before new tasks are healthy → more tasks added → task count overshoots. Increase cooldown. |
| k6 load test runs against prod by mistake | Use environment variables: `BASE_URL` required, no default to prod. CI always sets staging URL. |
| Warmup takes longer than expected (cold ECR pull) | ECR image not cached on Fargate host (happens after long idle period). Pre-pull by running a warmup task before peak, or use larger ECR cache TTL. |
