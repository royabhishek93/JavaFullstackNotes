## NEW LEARNER FOUNDATION — Read This First If You Are New

```
KEY TERMS EXPLAINED SIMPLY
============================

DNS (Domain Name System)
  Translates human-readable names to IP addresses.
  "api.uber.com" → "54.23.101.5"
  Like a phone book: you look up a name, get a number.

TTL (Time To Live)
  How long a DNS answer can be cached by the client or intermediate
  resolver before it must ask Route53 again.
  TTL=300 → client reuses the IP for up to 5 minutes.
  Low TTL = fresher data, more DNS queries, faster failover.
  High TTL = stale data possible, fewer queries, slower failover.

ROUTING POLICY
  The rule Route53 uses to decide WHICH record(s) to return when a
  client queries your domain. There are 7 policies (see Section 1).

HEALTH CHECK
  Route53 probes your endpoint (HTTP/HTTPS/TCP) from ~15 global
  locations. If it fails, Route53 stops returning that record.
  This is how automatic failover works.

CNAME (Canonical Name)
  A DNS record that maps one name to another name.
  "www.example.com" → "example.com"
  Cannot be used at the zone apex (the root domain "example.com" itself).

ALIAS RECORD
  A Route53 extension that maps a name directly to an AWS resource
  (ALB, CloudFront distribution, S3 website endpoint).
  Works at the zone apex. FREE — no charge for alias queries.
  Auto-tracks IP changes of the AWS resource.

HOSTED ZONE
  A container in Route53 that holds all the DNS records for a domain.
  "Public hosted zone" → internet-accessible.
  "Private hosted zone" → only resolvable inside your VPC.

GLOBAL ACCELERATOR
  An AWS network service that gives you two static anycast IP addresses.
  Traffic enters AWS at the nearest edge PoP and travels on AWS's private
  backbone to your endpoint — not on the public internet.
  Faster for dynamic API calls; sub-30s failover (no DNS TTL dependency).

ANYCAST
  A routing technique where multiple servers share the same IP address.
  The network automatically sends traffic to the nearest one.
  Global Accelerator uses anycast — same two IPs, worldwide, always
  routed to nearest AWS edge.

GEOLOCATION vs GEOPROXIMITY
  Geolocation: route based on WHERE the client IS (country/continent).
  Geoproximity: route based on distance to region, with an adjustable
  bias to expand or shrink a region's coverage area.
```

## SECTION 1 — The 7 Route53 Routing Policies

---

### PART 1 — When They Ask: "Explain all Route53 routing policies."

> **You say:**
>
> "I'll go through all 7 and give you a real production use case for each."

```
THE 7 ROUTE53 ROUTING POLICIES — VISUAL OVERVIEW
==================================================

1. SIMPLE
   ───────
   Client ──► Route53 ──► returns single record ──► Endpoint A
   (No health checks, no logic)

2. WEIGHTED
   ─────────
   Client ──► Route53 ──► 80% → Endpoint A (stable)
                      └──► 20% → Endpoint B (canary)

3. LATENCY-BASED
   ──────────────
   User in Tokyo  ──► Route53 measures latency → returns ap-northeast-1
   User in London ──► Route53 measures latency → returns eu-west-1

4. FAILOVER (Active-Passive)
   ─────────────────────────
   Healthy:  Client ──► Route53 [health check ✅] ──► PRIMARY (us-east-1)
   Failure:  Client ──► Route53 [health check ✗]  ──► SECONDARY (us-west-2)

5. GEOLOCATION
   ────────────
   User in Germany  ──► Route53 (country=DE) ──► EU endpoint
   User in Japan    ──► Route53 (country=JP) ──► APAC endpoint
   User anywhere else ► Route53 (default)    ──► US endpoint

6. GEOPROXIMITY (Traffic Flow only)
   ──────────────────────────────────
   Normal:      ◄──────────────────────────────────────────►
                us-east-1 [bias=0]       eu-west-1 [bias=0]
                (midpoint split at Atlantic)

   With bias:   ◄─────────────────────────────────►──────────►
                us-east-1 [bias=+50]     eu-west-1 [bias=0]
                (us-east-1 covers more of Europe now — gradual migration)

7. MULTI-VALUE ANSWER
   ───────────────────
   Client ──► Route53 ──► returns up to 8 healthy IPs
                          Client picks one (like a mini load balancer)
```

#### Policy 1 — Simple

> **You say:**
>
> "Simple routing returns one record for one endpoint. No health checks.
> No logic. If the endpoint is down, Route53 still returns it — your
> users hit a dead server. Use this only for dev environments or
> single-server setups where you don't need resilience.
>
> You can return multiple IPs in a Simple record — Route53 returns all
> of them and the client picks randomly. But there are still no health
> checks, so unhealthy IPs can be returned."

```
SIMPLE ROUTING
==============
  api.dev.myapp.com → A record → 54.23.101.5

  Query: "api.dev.myapp.com?"
  Response: "54.23.101.5" (always, healthy or not)

  Use case: single dev/test server where downtime is acceptable.
  Never use in production if you care about availability.
```

---

#### Policy 2 — Weighted

> **You say:**
>
> "Weighted routing assigns a numeric weight to each record. Route53
> distributes traffic proportionally. 80 + 20 = 100 total weight,
> so 80% goes to one endpoint and 20% to another.
>
> This is my go-to for canary deployments. I deploy a new version to
> a new ECS task definition, set its weight to 5, watch error rates
> in CloudWatch for 30 minutes, then gradually shift weight.
>
> The key trap: weight=0 means the record receives NO traffic but still
> exists in Route53. This is how you 'pause' an endpoint without deleting
> it. But weight=0 is NOT failover — if your primary endpoint fails and
> you only have Simple or Weighted records, Route53 keeps returning the
> failing IP. Use Failover policy for actual DR."

```
WEIGHTED ROUTING — CANARY DEPLOYMENT
======================================

  Step 1: Initial state (100% stable)
  ────────────────────────────────────
  api.uber.com  Weight=100  → ECS task-def v42 (stable)
  api.uber.com  Weight=0    → ECS task-def v43 (new, receiving nothing)

  Step 2: Start canary (5% to new version)
  ─────────────────────────────────────────
  api.uber.com  Weight=95   → ECS task-def v42
  api.uber.com  Weight=5    → ECS task-def v43

  Step 3: Promote (50/50 test)
  ─────────────────────────────
  api.uber.com  Weight=50   → ECS task-def v42
  api.uber.com  Weight=50   → ECS task-def v43

  Step 4: Full rollout
  ─────────────────────
  api.uber.com  Weight=0    → ECS task-def v42 (kept for quick rollback)
  api.uber.com  Weight=100  → ECS task-def v43

  Health check on each weighted record → if one fails, Route53
  skips it and sends 100% to the healthy record automatically.
```

---

#### Policy 3 — Latency-Based

> **You say:**
>
> "Latency-based routing sends a user to the AWS region that has the
> lowest measured network latency for that user's IP range.
>
> Important: this is NOT purely geographic. A user in South America
> might get routed to us-east-1 if that has better measured latency
> than sa-east-1 on that particular day. Route53 maintains a latency
> table that AWS updates based on actual measurements.
>
> UBER uses this globally. A driver in Seoul gets routed to
> ap-northeast-1. A driver in Berlin gets eu-west-1. The dispatcher
> and GPS updates are latency-sensitive — even 50ms difference matters
> when coordinating ride matching."

```
LATENCY-BASED ROUTING — UBER GLOBAL
======================================

  Driver app in Seoul (South Korea)
        │
        ▼ DNS query: "api.uber.com?"
  Route53 checks latency table:
    ap-northeast-1 (Tokyo):    8ms   ← lowest ✅
    us-east-1 (Virginia):     180ms
    eu-west-1 (Ireland):      250ms
        │
        ▼ Returns: ap-northeast-1 ALB IP
        │
        ▼ Driver's GPS update: 8ms round trip to Tokyo

  Driver app in London
        │
        ▼ DNS query: "api.uber.com?"
  Route53 checks latency table:
    eu-west-1 (Ireland):       12ms   ← lowest ✅
    us-east-1 (Virginia):     120ms
    ap-northeast-1 (Tokyo):   210ms
        │
        ▼ Returns: eu-west-1 ALB IP

  COMBINE WITH HEALTH CHECKS:
  If ap-northeast-1 health check fails → Route53 routes Seoul user
  to the next-lowest-latency region (e.g., ap-southeast-1 at 25ms)
```

#### Policy 4 — Failover (Active-Passive)

> **You say:**
>
> "Failover routing is the DR pattern. You have one PRIMARY record
> (type=PRIMARY) with a health check attached, and one SECONDARY
> record (type=SECONDARY) as the fallback.
>
> While the health check passes, all traffic goes to PRIMARY.
> When health check fails 3 consecutive times, Route53 stops returning
> the PRIMARY record and starts returning SECONDARY.
>
> The failover timing depends on two variables: the DNS TTL and the
> health check interval. I'll cover the formula in Section 2."

```
FAILOVER ROUTING — PAYMENT SYSTEM DR
=======================================

  NORMAL OPERATION:
  ─────────────────
  pay.company.com → Route53
                     │
                     ├── PRIMARY: us-east-1 ALB [health check ✅]
                     │   Type=PRIMARY, TTL=60
                     │
                     └── SECONDARY: us-west-2 ALB (warm standby)
                         Type=SECONDARY, TTL=60
                         (not returned while PRIMARY is healthy)

  DNS response → us-east-1 ALB IP → user processes payment

  FAILURE SCENARIO:
  ─────────────────
  t=0:   us-east-1 goes down (AZ failure, app crash)
  t=10s: Route53 checker 1 probes → FAIL
  t=40s: Route53 checker 2 probes → FAIL
  t=70s: Route53 checker 3 probes → FAIL (3 consecutive failures)
  t=70s: Route53 marks PRIMARY unhealthy
  t=70s: Route53 stops returning us-east-1 IP
  t=130s: All cached DNS entries expire (TTL=60s)
  t=130s: All users now get us-west-2 IP
  Total failover window: ~90-150 seconds

  RECOVERY:
  ─────────
  us-east-1 restored → health check passes 3× → Route53 returns
  PRIMARY again → TTL expires → users route back to us-east-1
```

#### Policy 5 — Geolocation

> **You say:**
>
> "Geolocation routes based on the geographic location of the client's
> DNS resolver IP. You configure records for specific countries,
> continents, or US states.
>
> The critical trap: you MUST configure a default record. If a user
> queries from a location with no matching record and there's no default,
> Route53 returns NXDOMAIN — the domain does not exist. That means an
> unhandled region causes DNS failures for those users.
>
> GDPR is the primary driver for geolocation. EU user data must stay in
> EU data centers. We route *.eu.company.com to eu-west-1 via geolocation,
> and the eu-west-1 stack writes to Aurora in Frankfurt, not us-east-1."

```
GEOLOCATION ROUTING — OTT PLATFORM CONTENT LICENSING
=======================================================

  stream.platform.com records:
  ──────────────────────────────────────────────────────────
  Location: India          → ap-south-1 ALB (Bollywood content)
  Location: United States  → us-east-1 ALB (US licensed content)
  Location: Germany        → eu-central-1 ALB (EU GDPR compliant)
  Location: Default        → us-east-1 ALB (fallback for all others)
                                              ↑
                                    ALWAYS CONFIGURE THIS

  User in India queries stream.platform.com
  Route53: country = IN → return ap-south-1 IP
  User gets: Indian content library + Hindi subtitles
  Data stored: ap-south-1 (complies with India data localization)

  User in Antarctica queries stream.platform.com
  Route53: country = AQ → no specific record → DEFAULT record
  Route53: return us-east-1 IP ✅

  WITHOUT DEFAULT RECORD:
  User in Antarctica → NXDOMAIN → app cannot load → user churns
```

#### Policy 6 — Geoproximity (Traffic Flow Only)

> **You say:**
>
> "Geoproximity is like geolocation but with a bias knob. You can
> expand or shrink how much geographic area a region covers.
> A bias of +50 expands the region's coverage area; -50 shrinks it.
>
> This requires Route53 Traffic Flow — the visual policy editor.
> You can't configure it with simple record sets.
>
> The real use case is gradual regional migration. I'm moving traffic
> from us-east-1 to a new eu-west-2 region. I start with bias=0 (normal
> midpoint split). I gradually increase eu-west-2's bias — it pulls
> more users from us-east-1 without a hard cutover."

```
GEOPROXIMITY — GRADUAL MIGRATION FROM US-EAST-1 TO EU-WEST-2
==============================================================

  Phase 1: Initial (bias=0 for both)
  ───────────────────────────────────
  Geographic midpoint between us-east-1 and eu-west-2 splits traffic.
  Eastern US + Atlantic → us-east-1
  Western Europe        → eu-west-2

  Phase 2: Expand eu-west-2 coverage (eu-west-2 bias=+25)
  ──────────────────────────────────────────────────────────
  eu-west-2's coverage area GROWS eastward into the Atlantic.
  More Eastern US users now routed to eu-west-2.
  Monitor error rates and latency before continuing.

  Phase 3: Further expand (eu-west-2 bias=+75)
  ─────────────────────────────────────────────
  Most of the US + Europe now hits eu-west-2.
  us-east-1 only serves its immediate vicinity.

  Phase 4: Complete migration (us-east-1 bias=-100 or delete record)
  ───────────────────────────────────────────────────────────────────
  100% traffic now on eu-west-2.

  KEY: Geoproximity is about physical distance to the region endpoint.
  Geolocation is about country/continent boundaries.
  They serve different purposes — don't confuse them.
```

#### Policy 7 — Multi-Value Answer

> **You say:**
>
> "Multi-value answer returns up to 8 healthy records when a client
> queries. The client picks one — effectively distributing load without
> an ALB. This is not a substitute for a real load balancer, but it's
> useful for internal services, simple web servers, or non-HTTP workloads.
>
> Unlike Simple routing, Multi-value DOES support health checks. Each
> record has its own health check. If 3 of your 8 records are unhealthy,
> Route53 only returns the 5 healthy ones."

```
MULTI-VALUE ANSWER
===================

  internal-api.company.com — 6 records, each with health check:

  IP: 10.0.1.10  [health ✅]
  IP: 10.0.1.11  [health ✅]
  IP: 10.0.1.12  [health ✗]  ← Route53 excludes this
  IP: 10.0.1.13  [health ✅]
  IP: 10.0.1.14  [health ✅]
  IP: 10.0.1.15  [health ✗]  ← Route53 excludes this

  Route53 response: 10.0.1.10, 10.0.1.11, 10.0.1.13, 10.0.1.14
  (only 4 healthy IPs returned, client picks one)

  vs. Simple multi-value: all 6 IPs returned including unhealthy ones

  Use case: microservice-to-microservice calls, non-ALB workloads,
  UDP services where ALB is not an option.
  NOT a replacement for ALB — no connection draining, no SSL offload.
```

### DECISION TABLE — Which Routing Policy to Use

```
USE CASE → POLICY DECISION TABLE
==================================

  Scenario                               → Policy to Use
  ─────────────────────────────────────────────────────────────────────
  Single dev server, no HA needed        → Simple
  Canary deploy / A/B test (HTTP)        → Weighted
  Global app, route to lowest latency    → Latency-based
  DR failover, active-passive            → Failover
  Data residency (GDPR), language routing → Geolocation
  Gradual regional migration             → Geoproximity (Traffic Flow)
  Multiple healthy IPs, no ALB           → Multi-Value Answer

  Combination examples:
  ─────────────────────
  Global DR with latency optimization:
    → Latency-based PLUS health checks on each region
    (Route53 picks lowest latency, falls back to next-lowest if unhealthy)

  GDPR + DR:
    → Geolocation to route EU users to eu-west-1
    → Failover within eu-west-1 records for AZ-level DR

  Stock broker (fairness + compliance):
    → Geolocation to comply with financial regulations per country
    → Failover within each region for exchange connectivity DR
```

## SECTION 2 — Health Checks: How Failover Actually Works

---

### PART 2 — When They Ask: "How do Route53 health checks work under the hood?"

> **You say:**
>
> "Route53 has about 15 health checker locations worldwide — places like
> Virginia, Ireland, Singapore, Tokyo. Each checker independently probes
> your endpoint. If 18% or more of checkers report the endpoint as
> healthy, Route53 considers it healthy. That's a majority-vote model —
> one checker having a network hiccup doesn't fail your endpoint.
>
> There are three check types: HTTP/HTTPS endpoint checks, TCP port
> checks, and CloudWatch alarm checks. The CloudWatch alarm check is
> the key for private resources inside a VPC."

```
ROUTE53 HEALTH CHECK ARCHITECTURE
===================================

  Route53 Global Health Checkers (~15 locations):
  ─────────────────────────────────────────────────
  [Virginia]  [Oregon]  [Ireland]  [Frankfurt]
  [Tokyo]     [Sydney]  [Singapore] [São Paulo]
  [Mumbai]    [Seoul]   [Hong Kong] ...

  Each checker independently polls your endpoint every 30s (or 10s).

  Threshold rule:
  ────────────────
  Unhealthy after: 3 consecutive failures from a single checker
  Healthy status:  ≥ 18% of checkers report healthy

  (This means transient network issues in one region don't flip your
  health check — you need persistent failures from multiple checkers)

  CHECK TYPES:
  ─────────────
  1. HTTP/HTTPS:
     Route53 opens TCP connection, sends HTTP GET to path you specify.
     Expects 2xx or 3xx within 4s (30s interval) or 2s (10s interval).
     Can check response body for a string (first 5,120 bytes).

  2. TCP:
     Route53 opens TCP connection to port. If connection established
     within timeout → healthy. No application-level check.

  3. CloudWatch Alarm:
     Route53 watches a CloudWatch alarm state (OK/ALARM/INSUFFICIENT).
     Use this when your endpoint is in a private VPC — Route53 checkers
     can't reach VPC-private ALBs. CloudWatch agent runs inside VPC,
     publishes metrics, alarm reflects actual health.

  CALCULATED HEALTH CHECK:
  ─────────────────────────
  Combine multiple health checks with AND/OR logic:
  Example: "healthy only if BOTH the API check AND the DB check pass"
  → Create a Calculated check: child1 AND child2
  Use for: complex health conditions, multi-dependency services.
```

### FAILOVER TIMING FORMULA

> **You say:**
>
> "This is a question architects get wrong. People assume health checks
> give instant failover. They don't. The actual time from failure to
> recovery is: TTL plus the health check cycle time.
>
> TTL is how long the old IP is cached. If TTL=300, users keep hitting
> the dead endpoint for up to 5 minutes AFTER Route53 has already
> declared it unhealthy. That's why I always set TTL=60 for
> failover records."

```
FAILOVER TIMING FORMULA
========================

  Max failover time = TTL + (failure_threshold × check_interval)

  STANDARD HEALTH CHECK (30s interval, threshold=3):
  ─────────────────────────────────────────────────────
  TTL=60, interval=30s, threshold=3:
  → 60 + (3 × 30) = 60 + 90 = 150 seconds max failover
  ≈ 2.5 minutes

  FAST HEALTH CHECK (10s interval, threshold=3):
  ─────────────────────────────────────────────────
  TTL=60, interval=10s, threshold=3:
  → 60 + (3 × 10) = 60 + 30 = 90 seconds max failover
  ≈ 1.5 minutes
  Cost: 3× more expensive than standard checks

  COMPARISON TABLE:
  ──────────────────
  Scenario          TTL   Interval  Threshold  Max Failover
  ────────────────────────────────────────────────────────
  Default (bad!)    300   30s       3          390s (6.5 min)
  Production        60    30s       3          150s (2.5 min)
  Low-latency DR    60    10s       3          90s  (1.5 min)
  Payment/trading   30    10s       3          60s  (1 min)

  PRE-MAINTENANCE TRICK:
  ───────────────────────
  Before planned maintenance, reduce TTL from 300 → 60 at least
  5 minutes before starting work. This lets cached DNS entries expire
  so the actual failover window is short when you flip the health check.
  After maintenance, restore TTL=300 to reduce DNS query cost.
```

### PRIVATE RESOURCE HEALTH CHECK PATTERN

> **You say:**
>
> "A common junior mistake: 'I'll add a health check to my internal ALB.'
> Route53 health checkers are on the public internet. They cannot reach
> a VPC-private ALB that has no public IP or internet-facing listener.
>
> The fix is the CloudWatch alarm health check pattern. Your application
> writes metrics to CloudWatch — error rate, response time, custom
> health signals. You create a CloudWatch alarm on those metrics. Route53
> watches the alarm state. If the alarm fires, Route53 marks the record
> unhealthy and fails over."

```
PRIVATE RESOURCE HEALTH CHECK — THE CORRECT PATTERN
=====================================================

  WRONG (doesn't work):
  ──────────────────────
  Route53 health checker → [public internet] → VPC private ALB
                                               (no route! private subnet)
  Result: health check always shows "connection refused" or timeout
          → Route53 might mark everything unhealthy incorrectly

  CORRECT PATTERN:
  ─────────────────
  Inside VPC:
  ECS Task / EC2 → writes custom metrics to CloudWatch
                   (e.g., health_status=1 if OK, health_status=0 if sick)

  CloudWatch Alarm:
  Alarm name: "payment-service-health"
  Condition: health_status < 1 for 3 datapoints → ALARM state

  Route53 Health Check (type=CloudWatch Alarm):
  Watches: "payment-service-health" alarm
  Healthy: alarm state = OK
  Unhealthy: alarm state = ALARM

  Route53 health checker → CloudWatch API (public) → alarm state
                                                     (no VPC access needed)

  This pattern also works for:
  ─────────────────────────────
  • RDS Aurora reader endpoint health (DB connection pool metrics)
  • SQS queue depth (failover when queue is overwhelmed)
  • Any custom application health that doesn't expose HTTP externally
```

## SECTION 3 — Route53 vs Global Accelerator: The Key Decision

---

### PART 3 — When They Ask: "When do you use Route53 vs Global Accelerator?"

> **You say:**
>
> "This is a critical distinction. Route53 and Global Accelerator solve
> overlapping problems but with fundamentally different mechanisms. The
> wrong choice costs you either money or availability.
>
> Route53 is DNS-based. The client resolves a name to an IP, then makes
> a connection over the public internet to that IP. DNS TTL means the
> IP can be stale for the TTL window after failover.
>
> Global Accelerator uses anycast IPs. The client connects to the same
> two IP addresses globally. Traffic enters AWS at the nearest edge PoP
> and travels on AWS's private backbone. Failover happens at the
> connection level — no DNS TTL dependency. Sub-30 second failover."

```
ROUTE53 PATH vs GLOBAL ACCELERATOR PATH
=========================================

  ROUTE53 (DNS-based):
  ─────────────────────
  User in Tokyo
      │
      │ 1. DNS query: "api.stock-broker.com?"
      ▼
  Route53 → returns ap-northeast-1 ALB IP: 52.197.xxx.xxx
      │
      │ 2. HTTPS connection over PUBLIC INTERNET to 52.197.xxx.xxx
      │    (multiple hops across ISP networks, variable latency)
      ▼
  ap-northeast-1 ALB → ECS → Response

  Failover: ALB fails → health check fails 3× → Route53 updates DNS
  → but existing clients keep hitting old IP until TTL expires (60-300s)

  GLOBAL ACCELERATOR PATH:
  ─────────────────────────
  User in Tokyo
      │
      │ 1. HTTPS to anycast IP: 75.2.xx.xx (same IP from anywhere)
      ▼
  Nearest AWS Edge PoP (Osaka, Japan) — enters AWS backbone immediately
      │
      │ 2. AWS private backbone (low-latency, high-reliability fiber)
      │    Not the public internet — AWS owns these fiber links
      ▼
  ap-northeast-1 ALB → ECS → Response

  Failover: ALB unhealthy → GA detects at connection level
  → within 30s, routes to next healthy endpoint (us-west-2)
  → NO DNS TTL dependency → instant rerouting for new connections

  VISUAL COMPARISON:
  ───────────────────
  Route53:           User → [PUBLIC INTERNET 🌐] → Region
  Global Accelerator: User → [PoP] → [AWS BACKBONE ⚡] → Region
```

================================================

  ─────────────────────────────────────────────────────────────────────

## SECTION 4 — Alias Records vs CNAME

---

### PART 4 — When They Ask: "When do you use an Alias record vs a CNAME?"

> **You say:**
>
> "This comes up in every DNS architecture review. CNAME is a standard
> DNS record that maps one name to another name. It has two limitations:
> it cannot be used at the zone apex — the root domain itself — and
> Route53 charges for CNAME query resolution.
>
> Alias is a Route53-only extension. It maps a name directly to an
> AWS resource. It works at the zone apex. It's FREE. And it automatically
> tracks IP changes in the underlying resource — when your ALB adds or
> removes IPs during scaling, the Alias record follows.
>
> The rule is simple: whenever you're pointing to an AWS resource,
> always use Alias. CNAME is for pointing to external non-AWS hostnames."

```
ALIAS vs CNAME — COMPARISON
=============================

  CNAME:
  ───────
  www.example.com   CNAME   example.com        ✅ (subdomain to root)
  app.example.com   CNAME   myapp.us-east-1.elb.amazonaws.com  ✅
  example.com       CNAME   ???                ✗  CANNOT — zone apex!

  Why can't CNAME be at the zone apex?
  DNS spec (RFC 1912): at the apex, you must have SOA and NS records.
  A CNAME at the apex would conflict — the DNS spec forbids it.

  ALIAS:
  ───────
  example.com       ALIAS   myapp.us-east-1.elb.amazonaws.com  ✅
  api.example.com   ALIAS   my-dist.cloudfront.net             ✅
  www.example.com   ALIAS   my-bucket.s3-website-us-east-1...  ✅

  ALIAS TARGETS (what you can Alias to):
  ────────────────────────────────────────
  • Application Load Balancer (ALB)
  • Network Load Balancer (NLB)
  • Classic Load Balancer (CLB)
  • CloudFront distribution
  • Elastic Beanstalk environment
  • S3 static website endpoint
  • API Gateway custom domain
  • VPC Interface Endpoint
  • Another Route53 record in the SAME hosted zone

  COST COMPARISON:
  ─────────────────
  CNAME query:  $0.40 per million queries
  Alias query:  FREE (Route53 resolves alias internally, not charged)

  PRACTICAL RULE:
  ────────────────
  Pointing to AWS resource?    → Always use ALIAS
  Pointing to external domain? → Use CNAME (only option)
  Zone apex (root domain)?     → Must use ALIAS (CNAME not allowed)
```

## SECTION 5 — Multi-Region Failover Pattern (Active-Passive)

---

### PART 5 — When They Ask: "Walk me through a full multi-region DR setup."

> **You say:**
>
> "This is the architecture pattern that combines everything we've
> discussed. For a payment system, I'd set up active-passive failover
> with Route53 Failover policy, health checks, and Aurora Global Database.
>
> The key insight: Route53 failover only switches DNS. The database
> failover — promoting the Aurora reader to writer in us-west-2 —
> is a separate automated step. They need to be coordinated."

```
MULTI-REGION ACTIVE-PASSIVE FAILOVER — COMPLETE PATTERN
=========================================================

  NORMAL OPERATION:
  ──────────────────

  api.payments.com → Route53
    ├── PRIMARY (Failover type=PRIMARY):
    │   Record: us-east-1 ALB DNS
    │   Health Check: HTTPS to /health endpoint, interval=10s
    │   TTL: 60
    │
    └── SECONDARY (Failover type=SECONDARY):
        Record: us-west-2 ALB DNS
        Health Check: (optional on secondary)
        TTL: 60

  ALL traffic → us-east-1 ALB → ECS → Aurora Writer (us-east-1)

  Aurora Global Database replication:
  us-east-1 Writer ──[async, <1s RPO]──► us-west-2 Reader Replica

  FAILURE SCENARIO (us-east-1 AZ failure):
  ──────────────────────────────────────────

  t=0:    us-east-1 app servers become unhealthy
  t=10s:  Route53 checker 1 fails
  t=20s:  Route53 checker 2 fails
  t=30s:  Route53 checker 3 fails → health check = UNHEALTHY
  t=30s:  Route53 stops returning PRIMARY record
  t=60s:  CloudWatch alarm triggers Lambda (or EventBridge rule)
  t=65s:  Lambda calls Aurora Global DB API: promote us-west-2 to Writer
          (Aurora promotion: ~1 minute for global failover)
  t=90s:  DNS TTL expires, new queries get us-west-2 ALB IP
  t=125s: Aurora us-west-2 is now Writer
  t=125s: All new connections hit us-west-2 ALB → us-west-2 Aurora Writer
  Total: ~2 minutes RTO

  RECOVERY FLOW:
  ───────────────

  1. Restore us-east-1 application
  2. Re-sync Aurora: us-west-2 (now writer) replicates to us-east-1
  3. Update Route53 health check to pass us-east-1 again
  4. Route53 returns PRIMARY; DNS TTL expires
  5. Traffic shifts back to us-east-1 (re-promote Aurora if needed)

  COMBINATION ARCHITECTURE (Production-Grade):
  ─────────────────────────────────────────────

  api.payments.com
        │
        ▼
  Route53 (Failover policy)
        ├── PRIMARY: Latency-based record in us-east-1
        └── SECONDARY: Latency-based record in us-west-2

  This means: normally, latency routing picks the best region.
  During failure, failover kicks in and skips the unhealthy region.
  This is called "combining routing policies with health checks."
```

```yaml
# Infrastructure-as-Code example: Route53 Failover records (AWS CDK concept)
# Primary record
route53_record_primary:
  name: api.payments.com
  type: A
  set_identifier: primary
  failover: PRIMARY
  alias:
    dns_name: us-east-1-alb.us-east-1.elb.amazonaws.com
    evaluate_target_health: true   # use ALB's own health as the health check
  ttl: 60

# Secondary record
route53_record_secondary:
  name: api.payments.com
  type: A
  set_identifier: secondary
  failover: SECONDARY
  alias:
    dns_name: us-west-2-alb.us-west-2.elb.amazonaws.com
    evaluate_target_health: true
  ttl: 60

# Health check (for primary)
health_check:
  type: HTTPS
  resource_path: /actuator/health
  fqdn: us-east-1-alb.us-east-1.elb.amazonaws.com
  port: 443
  request_interval: 10          # fast check (3× cost)
  failure_threshold: 3
  regions:                       # check from specific regions
    - us-east-1
    - eu-west-1
    - ap-northeast-1
```

## COMMON TRAPS — What Trips Up Junior Engineers

```
THE 7 COMMON ROUTE53 TRAPS
============================

TRAP 1: CNAME at the zone apex
────────────────────────────────
  Wrong:  example.com  CNAME  my-alb.us-east-1.elb.amazonaws.com
          (DNS spec forbids CNAME at zone apex — "CNAME and other data" error)
  Fix:    example.com  ALIAS  my-alb.us-east-1.elb.amazonaws.com
          Always use ALIAS for AWS resources, especially at the root domain.

TRAP 2: TTL not reduced before planned maintenance
───────────────────────────────────────────────────
  Wrong:  TTL=300. Start maintenance window. Failover takes 390 seconds.
          Users hit dead server for 6.5 minutes.
  Fix:    30 minutes before maintenance: reduce TTL from 300 → 60.
          Wait 5 minutes (old TTL expires). Proceed with maintenance.
          Failover window shrinks to 90-150 seconds.
          After maintenance: restore TTL=300 to reduce DNS query cost.

TRAP 3: Health check cannot reach VPC-private ALB
───────────────────────────────────────────────────
  Wrong:  Create HTTP health check pointing to internal ALB with no
          public IP. Route53 checkers are on the public internet —
          they can't reach it. Health check always reports Unhealthy.
  Fix:    Use CloudWatch Alarm health check type. Publish application
          health metrics to CloudWatch from inside VPC. Create alarm.
          Route53 watches alarm state via CloudWatch API (public).

TRAP 4: Geolocation policy without a default record
──────────────────────────────────────────────────────
  Wrong:  Configure records for US, EU, APAC — nothing else.
          User in Africa queries domain → no matching record → NXDOMAIN.
          App breaks for users in uncovered geographies.
  Fix:    Always add a Default record as the catch-all.
          Default serves users from any location not explicitly mapped.

TRAP 5: Using Weight=0 as a failover mechanism
────────────────────────────────────────────────
  Wrong:  Think that setting primary weight=0 will stop traffic if it's
          unhealthy. Weight=0 just removes that record from traffic
          distribution — but if the other record is also down, you get
          NXDOMAIN. And Weight doesn't "check" anything automatically.
  Fix:    Use Failover routing policy for DR. Weighted is for intentional
          traffic splitting. Attach health checks to weighted records so
          Route53 skips unhealthy ones in the distribution.

TRAP 6: Global Accelerator is not a CDN
─────────────────────────────────────────
  Wrong:  "I'll use Global Accelerator to speed up my image delivery."
          GA routes traffic to your origin — it does NOT cache.
          Sending large static files through GA costs $0.008/GB on top
          of normal data transfer. Very expensive for high-bandwidth assets.
  Fix:    CloudFront for static/cacheable content (images, JS, CSS, video).
          Global Accelerator for dynamic API calls, WebSockets, non-HTTP.
          They complement each other — use both for their strengths.

TRAP 7: Health check cost not accounted for
────────────────────────────────────────────
  Scenario: 100 services, each with 1 Route53 health check.
  Cost: $0.50/month × 100 = $50/month (basic)
       Fast checks (10s): $1.00/month × 100 = $100/month
  At scale (500 microservices): $250-$500/month just for health checks.
  Fix:    Use Calculated health checks to combine child checks.
          Use ALB's built-in health check (evaluate_target_health=true)
          instead of a separate Route53 check where possible.
          Reserve Route53 health checks for cross-region failover records.
```

## Interview Cheat Sheet (Say This Confidently)

> "For Route53 in production: there are 7 routing policies — Simple for single servers, Weighted for canary deployments, Latency-based for global apps, Failover for active-passive DR, Geolocation for data residency and content licensing, Geoproximity for gradual regional migration, and Multi-value for non-ALB multi-endpoint distribution. Always attach health checks to Failover, Weighted, Latency, and Geolocation records for automatic recovery. The failover timing formula is TTL plus threshold times interval — reduce TTL to 60 seconds before planned maintenance. For private VPC resources, use CloudWatch alarm health checks since Route53 checkers are on the public internet. Always use Alias records instead of CNAME when pointing to AWS resources — Alias is free, works at the zone apex, and auto-tracks IP changes. Choose Global Accelerator over Route53 when you need sub-30-second failover without DNS TTL dependency, fixed anycast IPs for client firewall whitelisting, or AWS backbone routing for dynamic APIs — but remember GA is not a CDN, CloudFront is."
