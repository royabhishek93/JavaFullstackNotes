### OPENING — When They Ask: "How do you host your React frontend on AWS?"

> **You say:**
>
> "The Swiggy customer-facing React app is hosted on S3 + CloudFront. No EC2,
> no Nginx, no servers to manage. The build artifacts — HTML, JS, CSS, images —
> go into an S3 bucket. CloudFront sits in front and caches those files at
> 450+ edge locations worldwide.
>
> A customer in Mumbai gets the JS bundle served from a Mumbai edge node,
> not from us-east-1. That's the core reason for CloudFront — latency, not just cost.
>
> Let me walk through the full architecture and then the deployment pipeline."

SWIGGY REACT APP HOSTING — Full Architecture

### PART 1 — When They Ask: "How is the S3 bucket configured?"

> **You say:**
>
> "The S3 bucket is NOT configured for public website hosting. That's the old way.
> Instead, CloudFront accesses S3 using an Origin Access Control — OAC.
> The bucket policy allows only CloudFront to read from it. Direct S3 URL access
> is blocked. This is a security improvement over the old OAI approach."

```
S3 BUCKET SETUP (modern approach — no public access)
======================================================

  Bucket: swiggy-web-prod
  ├── Block all public access: ENABLED
  ├── Static website hosting: DISABLED (we use CloudFront, not S3 hosting)
  ├── Versioning: ENABLED
  │   └── keeps previous builds for rollback
  └── Bucket policy:
      {
        "Statement": [{
          "Effect": "Allow",
          "Principal": {
            "Service": "cloudfront.amazonaws.com"
          },
          "Action": "s3:GetObject",
          "Resource": "arn:aws:s3:::swiggy-web-prod/*",
          "Condition": {
            "StringEquals": {
              "AWS:SourceArn": "arn:aws:cloudfront::123:distribution/ABCDEF"
            }
          }
        }]
      }

  WHY NOT S3 WEBSITE HOSTING?
  ┌──────────────────────────────────────────────────────────┐
  │  S3 website hosting:                                     │
  │  ├── HTTP only (no HTTPS on s3-website.amazonaws.com)   │
  │  ├── Direct URL accessible (bypasses CloudFront)        │
  │  └── OAI (old) vs OAC (new) — OAC is more secure       │
  │                                                          │
  │  CloudFront + OAC:                                       │
  │  ├── HTTPS everywhere (ACM cert)                        │
  │  ├── S3 URL blocked — only via CloudFront               │
  │  └── DDoS protection via AWS Shield Standard            │
  └──────────────────────────────────────────────────────────┘
```

### PART 2 — When They Ask: "How is CloudFront configured?"

> **You say:**
>
> "CloudFront has two cache behaviors. The default behavior serves the React
> static files from S3. The `/api/*` behavior forwards requests to the ALB
> where Spring Boot runs. This means the React app calls `/api/orders` —
> no CORS issue because it's the same CloudFront domain, same origin."

```
CLOUDFRONT DISTRIBUTION — Two Behaviors
==========================================

  swiggy.com (CloudFront)
  │
  ├── Default behavior (/*):
  │   ├── Origin: S3 bucket (via OAC)
  │   ├── Viewer protocol: HTTPS only (redirect HTTP → HTTPS)
  │   ├── Compress objects: YES (gzip/brotli)
  │   ├── Cache policy:
  │   │   └── index.html:     TTL=0 (no cache — always fresh)
  │   │       *.js, *.css:    TTL=1year (content-hash in filename)
  │   └── Error pages:
  │       └── 403/404 → /index.html (React Router handles routing)
  │
  └── /api/* behavior:
      ├── Origin: ALB (https://alb.swiggy.internal)
      ├── Cache policy: NONE (all requests forwarded)
      ├── Origin request policy: forward all headers + cookies
      ├── Allowed methods: GET, POST, PUT, DELETE, OPTIONS
      └── TTL: 0 (never cache API responses)

  WHY SAME CLOUDFRONT FOR /api/*?
  ┌──────────────────────────────────────────────────────────┐
  │  React on swiggy.com calling api.swiggy.com → CORS      │
  │  React on swiggy.com calling swiggy.com/api → no CORS   │
  │                                                          │
  │  Same domain = no CORS headers needed                    │
  │  Simpler config, no OPTIONS preflight overhead           │
  └──────────────────────────────────────────────────────────┘
```

### PART 3 — When They Ask: "How does HTTPS work? Custom domain?"

> **You say:**
>
> "Route 53 + ACM. We create a certificate in ACM for swiggy.com and *.swiggy.com,
> validate it via DNS validation — ACM creates a CNAME record, Route 53 confirms it.
> Then attach the certificate to CloudFront.
>
> One gotcha: ACM certificates for CloudFront must be created in us-east-1 regardless
> of where your resources are. CloudFront is global and only reads ACM from us-east-1.
> I've seen engineers waste 2 hours because they created the cert in ap-south-1."

```
HTTPS SETUP — Route 53 + ACM + CloudFront
==========================================

  Step 1: Request ACM certificate
  ├── Region: us-east-1 (MUST be this region for CloudFront)
  ├── Domain: swiggy.com
  ├── Wildcard: *.swiggy.com
  └── Validation: DNS (not email — DNS validation is automatic with Route 53)

  Step 2: Route 53 DNS validation
  ├── ACM creates a CNAME: _abc123.swiggy.com → _def456.acm-validations.aws
  ├── Route 53 auto-creates this record (AWS console one-click)
  └── ACM marks certificate as ISSUED (within 5 minutes)

  Step 3: Attach certificate to CloudFront
  ├── SSL certificate: Custom SSL certificate → select swiggy.com cert
  └── Security policy: TLSv1.2_2021 (no old TLS)

  Step 4: Route 53 DNS record
  ├── Type: A (alias)
  ├── Name: swiggy.com
  └── Alias target: CloudFront distribution domain (d123.cloudfront.net)

  RESULT: swiggy.com → Route 53 → CloudFront (TLS termination) → S3 or ALB
```

### PART 4 — When They Ask: "How do you manage different environments (dev/staging/prod)?"

> **You say:**
>
> "Environment variables in React work differently than backend services.
> The React build is a static bundle — there's no runtime environment.
> All config must be baked into the bundle at build time.
>
> We use `.env` files per environment and a GitHub Actions workflow that
> sets the right environment variables during `npm run build`.
> The result is three separate bundles deployed to three S3 buckets."

```
REACT ENVIRONMENT CONFIGURATION
==================================

  .env.development:
  REACT_APP_API_BASE_URL=http://localhost:8080
  REACT_APP_COGNITO_USER_POOL_ID=us-east-1_DEV123
  REACT_APP_COGNITO_CLIENT_ID=dev-client-id

  .env.staging:
  REACT_APP_API_BASE_URL=https://staging.swiggy.com
  REACT_APP_COGNITO_USER_POOL_ID=us-east-1_STG456
  REACT_APP_COGNITO_CLIENT_ID=staging-client-id

  .env.production:
  REACT_APP_API_BASE_URL=https://swiggy.com
  REACT_APP_COGNITO_USER_POOL_ID=us-east-1_PROD789
  REACT_APP_COGNITO_CLIENT_ID=prod-client-id

  IMPORTANT: REACT_APP_ prefix required for Create React App
  These values are BAKED INTO the JS bundle at build time
  → Never put secrets here (they're visible in the browser!)
  → Only non-sensitive config: URLs, pool IDs, feature flags
```

**GitHub Actions build + deploy:**

```yaml
jobs:
  deploy-react:
    runs-on: ubuntu-latest
    environment: production

    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci            # ci is faster and reproducible vs npm install

      - name: Build React app
        run: npm run build
        env:
          REACT_APP_API_BASE_URL:         https://swiggy.com
          REACT_APP_COGNITO_USER_POOL_ID: ${{ secrets.COGNITO_USER_POOL_ID }}
          REACT_APP_COGNITO_CLIENT_ID:    ${{ secrets.COGNITO_CLIENT_ID }}
          # REACT_APP_ values baked into bundle — not runtime

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123:role/github-react-deploy-role
          aws-region: us-east-1

      - name: Sync to S3
        run: |
          # Upload static assets with 1-year cache (content-hash in filename)
          aws s3 sync build/static s3://swiggy-web-prod/static \
            --cache-control "max-age=31536000,immutable" \
            --delete

          # Upload index.html with no-cache (always check for new version)
          aws s3 cp build/index.html s3://swiggy-web-prod/index.html \
            --cache-control "no-cache,no-store,must-revalidate"

          # Upload other root files (manifest.json, robots.txt)
          aws s3 sync build s3://swiggy-web-prod \
            --exclude "static/*" \
            --exclude "index.html" \
            --cache-control "max-age=86400"

      - name: Invalidate CloudFront cache
        run: |
          aws cloudfront create-invalidation \
            --distribution-id ${{ secrets.CLOUDFRONT_DIST_ID }} \
            --paths "/index.html" "/manifest.json"
          # Only invalidate index.html — static/* has content-hash names
          # (different SHA = different filename = no invalidation needed)
```

### PART 5 — When They Ask: "How does React handle routing with S3?"

> **You say:**
>
> "This is a classic gotcha. React Router handles routing client-side — the URL
> `/orders/123` is not an actual file on S3. If a user bookmarks that URL and
> navigates directly, S3 returns a 403 because the file doesn't exist.
>
> The fix: configure CloudFront to return `index.html` for all 403 and 404 errors.
> React Router then reads the URL and renders the correct component. The server
> never needs to know about the route."

```
REACT ROUTER + CLOUDFRONT FIX
================================

  WITHOUT fix (broken):
  User navigates to: swiggy.com/orders/123
  CloudFront → S3: GET /orders/123
  S3: 403 NoSuchKey (file doesn't exist)
  User sees: 403 error page

  WITH fix:
  CloudFront Custom Error Pages:
  ├── HTTP error code: 403
  │   └── Response page path: /index.html
  │       Response code: 200
  ├── HTTP error code: 404
  │   └── Response page path: /index.html
  │       Response code: 200

  User navigates to: swiggy.com/orders/123
  CloudFront → S3: GET /orders/123
  S3: 403 NoSuchKey
  CloudFront: maps 403 → serves /index.html with 200
  Browser: loads React app
  React Router: reads URL /orders/123 → renders OrderDetail component
  User sees: Order detail page ✓
```

### PART 6 — When They Ask: "What about CORS when React calls the API?"

> **You say:**
>
> "Because we route `/api/*` through the same CloudFront distribution as the React app,
> both are served from `swiggy.com`. Same origin — no CORS.
>
> But during local development, the React dev server runs on `localhost:3000` and
> the Spring Boot API on `localhost:8080`. That's cross-origin, so we configure
> CORS in Spring Boot to allow `localhost:3000`."

```java
// Spring Boot CORS config (from SecurityConfig, already shown in file 8)
config.setAllowedOrigins(List.of(
    "https://swiggy.com",        // prod CloudFront
    "https://staging.swiggy.com", // staging CloudFront
    "http://localhost:3000"      // local React dev server
));
```

> **You say:**
>
> "One more thing — if you ever need to call the API directly (bypassing CloudFront)
> during development or testing, you'd need CORS. But in production we never expose
> the ALB DNS name publicly — it's internal VPC. Everything goes through CloudFront."

## ONE-LINER ANSWERS

**"Why CloudFront and not just S3 website hosting?"**
> "S3 website hosting doesn't support HTTPS with custom domains, exposes direct S3 URLs,
> and serves from one region. CloudFront gives us HTTPS, edge caching in 450 locations,
> and blocks direct S3 access."

**"How do you deploy a new React version without users seeing a broken state?"**
> "Static files with content-hash names are uploaded first. Then index.html is uploaded.
> There's a window where old index.html references new JS — but since CloudFront caches
> old JS with max-age, the old version keeps working until index.html propagates."

**"What if CloudFront is caching a stale version?"**
> "CloudFront invalidation on `/index.html`. Takes under a minute to propagate globally.
> JS/CSS don't need invalidation — new content hashes in filenames are new URLs."

## FAILURE SCENARIOS

| Scenario | What Happens |
|---|---|
| Bad React build deployed | S3 rollback to previous version (versioning enabled) + CloudFront invalidate index.html |
| CloudFront serving stale index.html | `aws cloudfront create-invalidation --paths "/index.html"` — propagates in ~1 min |
| ACM cert expires | ACM auto-renews if DNS validation CNAME is still in Route 53 |
| S3 bucket accidentally made public | OAC policy blocks all direct access — no data exposure even if policy misconfigured |
| React Router 404 on refresh | CloudFront custom error response: 404 → index.html (200) |
| API CORS error in prod | Shouldn't happen — /api/* is same CloudFront domain. Means app is calling API directly, not via CloudFront |
