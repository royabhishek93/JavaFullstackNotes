Architecture

Big picture AWS architecture

+-------------------+ +-------------------------------+ | Users / Clients | -----> | Edge: Route53 / CloudFront / | | HTTPS + identity | | WAF / ALB or API Gateway | +-------------------+ +---------------+---------------+ | v +--------------------------------+ | Private application workload | | ECS / EKS / Lambda / EC2 | +-------+----------------+-------+ | | v v +-----------------+ +-----------------+ | Data: RDS / S3 | | Async / Cache | | DynamoDB | | SQS / Redis | +-----------------+ +-----------------+ Topic focus: ALB -> EKS -> HPA/KEDA -> IRSA -> AWS services
Why this topology: traffic enters through a controlled edge, workloads stay private, and stateful dependencies are isolated. Each layer has an independent scaling and failure boundary.
Network and IAM

Network and identity boundary

Internet --> [WAF / ALB] --> Public subnet | v Private subnet: application role | +--------------+--------------+ v v VPC endpoint / NAT Data subnet AWS APIs privately DB / cache security group IAM role -> STS temporary credential -> least-privilege action
Why this boundary: no application server accepts direct internet traffic, no static cloud key is embedded in code, and a security group references the caller role or security group rather than a broad CIDR wherever possible.
API Design

API contract: POST /events

POST /events Authorization: Bearer JWT or workload identity Idempotency-Key: client-generated-key X-Correlation-Id: trace-id 202 Accepted for asynchronous work { "requestId": "req_123", "status": "ACCEPTED" }

Why this contract

  • Idempotency: network retries never create duplicate AWS work.
  • Correlation: joins API logs, traces, queue messages, and alarms.
  • 202: avoids holding HTTP during durable async processing.
  • Status resource: lets clients recover after timeout.

Technology Choices

Category 1: EKS + KEDA versus ECS Fargate

A: EKS + KEDA

  • Why pick A: best default for this note’s operational constraint.
  • When A fits: the managed control plane and clear failure model offset its cost.
  • Examples: production order path; independently scaled worker workload.

B: ECS Fargate

  • Why pick B: a different control, portability, or lifecycle requirement dominates.
  • When B fits: the team can own its additional operational complexity.
  • Examples: specialized batch processing; existing platform-standard workload.
Difference: do not ask which product is “better.” Ask who owns nodes, deployment, scaling, failure recovery, and cost at the expected traffic shape.
Technology Choices

Category 2: RDS/Aurora versus DynamoDB

A: RDS / Aurora

  • Difference: relational model, joins, constraints, and transactions.
  • Choose A: orders, payments, bookings, and audits need relational invariants.
  • Examples: seat allocation; tenant billing ledger.

B: DynamoDB

  • Difference: access-pattern-first, serverless scale, no relational joins.
  • Choose B: predictable key access with very high throughput.
  • Examples: idempotency records; request status or session state.
Decision rule: choose Aurora when relationships and transactions are central; choose DynamoDB when access patterns are known and scale must be operationally simple.

Senior Traps

15 YOE trap questions with model answers

Trap: “My ECS/EKS task has an IAM role, so it is fully secure.”
Answer: “No. I still constrain the trust policy, the permission policy, network egress, secrets access, and application authorization. IAM is one layer, not a substitute for tenant or business authorization.”
Trap: “SQS guarantees exactly-once processing.”
Answer: “Standard SQS is at-least-once. FIFO removes some duplicates within constraints but downstream side effects still need idempotent business keys.”
Trap: “Multi-AZ means disaster recovery is solved.”
Answer: “Multi-AZ addresses an AZ failure. Regional DR still requires a defined RTO/RPO, replication, failover decision, runbook, and drills.”

Recovery decision

“I use timeouts, bounded retries with jitter, and a DLQ for poison work. I do not retry a non-idempotent external action blindly. For data loss, I map backup and replication to the agreed RPO.”

Evidence to retain

Correlation ID, deployment/image digest, IAM principal, event ID, request state, and an alarm timeline make the incident reconstructable.

Live Interview Script

How I would answer EKS Production Scaling &amp; Traps — Interview Conversational Script live

“I would start from the risk: a queue backlog grows while pods look healthy but cannot make progress. I put the public edge behind WAF and an ALB or API Gateway, run compute in private subnets, and give the workload a least-privilege IAM role with temporary credentials. The API carries idempotency and correlation IDs, then persists accepted work before asynchronous execution. I monitor the failure mode, CPU throttling, IP exhaustion, or unsafe node draining, using CloudWatch metrics, logs, traces, and DLQ alarms. I choose EKS + KEDA when its operational model fits; I use ECS Fargate only when the extra control is a real requirement. Finally, I prove it through IAM, load, resilience, and recovery drills.”
Follow-up: “Where would you simplify?”
Answer: “For a lower-risk internal workflow, I might remove multi-region DR or asynchronous fanout, but I would document the lower guarantee and keep private networking, IAM roles, observability, and tested rollback.”
