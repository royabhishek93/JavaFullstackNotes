# Production Security Architecture: What a 15-YOE Architect Must Know

## Scenario

**Interviewer:** "You are designing a multi-tenant React and Spring Boot platform on EKS. It uses external IDPs, Aurora PostgreSQL, S3, SQS, and 30 microservices. What do you own as the architect?"

**You say:** "I own the security properties of the whole request, not a list of tools. I define identity boundaries, authorization rules, tenant isolation, service trust, recovery objectives, and evidence needed after failure. Then I prove those controls through tests and incident drills."

The non-negotiable invariant is:

> A valid identity can access only the data, action, AWS resource, and tenant explicitly authorized for it, while the platform remains recoverable during failures.

## 1. Big Picture Architecture

```text
React SPA -> IDP -> JWT -> WAF / ALB -> EKS ingress -> Spring Boot services
    |                                  |                    |
    |                                  |                    +-> IRSA -> S3 / SQS / Secrets Manager
    |                                  |                    |
    +-> CloudFront / S3                +-> RDS Proxy -> Aurora PostgreSQL
                                                           |
                                              RLS + audit + backup / PITR

Observability: correlation ID -> logs, traces, metrics, security audit events
```

### Why this design

**You say:** "Every arrow is a trust boundary. The browser is public, the IDP authenticates, the ingress limits exposure, services authorize, PostgreSQL protects data, and IRSA limits AWS calls. Security failures happen when we assume one boundary protects the next one."

### Cross questions

- Which component is internet-facing? Only the controlled edge.
- Does a valid JWT grant AWS permissions? No. Only workload IAM/IRSA does.
- Does an IAM role grant access to a customer order? No. Application authorization does.

## 2. Identity Broker Strategy

```text
Tenant login policy
-------------------
acme.app.com   -> allow issuer: https://acme.okta.com/oauth2/default
globex.app.com -> allow issuer: https://login.microsoftonline.com/TENANT/v2.0
public.app.com -> allow issuer: https://accounts.google.com

JWT (iss + sub) -> external_identity -> internal user_id -> tenant_membership
```

### Why we choose it

**You say:** "I allow-list issuers per tenant. I never accept an arbitrary issuer just because its JWT is correctly signed. The business uses a provider-neutral `user_id`; `issuer + sub` maps a login identity to that user."

### Trade-off

| Choice | Why pick it | Cost / mitigation |
|---|---|---|
| Managed broker: Okta, Entra, Auth0 | MFA, SSO, availability, patches are operated for us | Vendor dependency; preserve internal `user_id` and exportable identity mapping |
| Self-hosted Keycloak | Data control, on-prem, deep custom federation | Operate HA DB, upgrades, backups, key rotation, CVE response |

### Senior trap

**Question:** "Can we link an Okta and Google account when email matches?"

**Strong answer:** "No. Email can change, be recycled, or be unverified. I require verified account linking by authenticating the existing account, or a controlled enterprise migration using a trusted immutable identifier."

## 3. Authorization Model: Scope Is Not Enough

```text
JWT scope                 Application role               Object rule
---------                 ----------------               -----------
orders.read      +        CUSTOMER              +        order.tenant_id == caller.tenant
                                                 +        order.created_by == caller.user_id
                                                           where ownership is required

Result: allow or deny
```

### Why we choose it

**You say:** "Scopes answer whether a token may call a class of API. Roles answer what the user can do in our product. Object-level authorization answers whether they can do it to this specific order. A valid token with `orders.read` must not read every tenant's order."

### API design

```text
GET /api/orders/{orderId}
Authorization: Bearer access-token
X-Correlation-Id: trace-123

401 = token absent or invalid
403 = valid identity lacks permission
404 = resource intentionally not disclosed, if policy requires it
```

Keep authorization decisions in a service/policy layer, not only controller annotations. Controller annotations are useful coarse protection; domain/service checks own resource-level policy.

### Cross questions

- When do you return `403` versus `404`? Decide whether revealing resource existence is permitted.
- Where do permissions live? In the IDP for coarse claims and in app policy/data for domain decisions.
- How do you audit a deny? Log subject, tenant, action, resource type, result, and correlation ID, never the token.

## 4. Token Lifecycle and JWKS

```text
IDP private key -> signs JWT (kid=key-2)
                              |
                              v
Spring Boot -> OIDC discovery -> JWKS public keys -> cached key matching kid
                              |
                              v
validate: signature + iss + aud + exp + nbf + token type + scopes
```

### Why we choose it

**You say:** "With RS256, only the IDP holds the private signing key. Each service gets public keys from JWKS and validates tokens locally. Public keys can verify a token but cannot mint one. This lets the IDP rotate keys without a microservice redeploy."

### HS256 versus RS256

| Choice | Difference | When to choose | Two examples |
|---|---|---|---|
| RS256 + JWKS | Private signer, public verifiers; recommended for distributed systems | External IDP, many services, partner tokens | Okta user token; Entra workforce SSO |
| HS256 | One shared secret signs and verifies | Small single trusted backend only | Internal prototype; short-lived local development token |

**HS256 is not recommended** for microservices: any verifier holding the shared secret can mint valid tokens, and rotating the secret requires coordinated rollout.

### Senior trap

**Question:** "A JWT signature is valid. Can we accept it?"

**Strong answer:** "No. I also validate allowed issuer, service-specific audience, expiry, not-before, token type, scopes, and applicable authorization policy. A token signed by a valid issuer but meant for another audience is denied."

## 5. Tenant Isolation: Code Plus Database

```text
JWT issuer + subject
        |
        v
membership authorization -> active tenant -> transaction-local DB context
                                                    |
                                                    v
PostgreSQL RLS: tenant_id = current_setting('app.tenant_id', true)
                                                    |
                                                    v
only current tenant rows returned or written
```

### Why we choose it

**You say:** "Application checks are necessary but can be missed in a new query, export, cache key, or background worker. RLS is defense in depth. It turns a missing tenant predicate into an empty or denied result instead of a cross-tenant data leak."

### Production rules

- Use `USING` and `WITH CHECK`: reads and writes need protection.
- Set tenant context transaction-locally on the same pooled DB connection.
- Use a non-owner database role and test connection reuse between tenants.
- Include tenant ID in Redis keys, S3 prefixes/policies, search indexes, and async event payloads.

### Senior trap

**Question:** "We use `WHERE tenant_id = ?` in every repository. Why add RLS?"

**Strong answer:** "Repository filters are a convention. RLS protects against a missed filter, native SQL, a new data export, and human operational queries. It is not a replacement for authorization; it is the final database barrier."

## 6. Service Identity and AWS Workload Identity

```text
User request: React -> user JWT -> Order API

Internal call: Order API -> client-credentials token
                            aud=payment-api, scope=payments.charge -> Payment API

AWS call: Order pod -> ServiceAccount -> IRSA -> STS temporary credentials -> SQS/S3/Secrets
```

### Why we choose it

**You say:** "A user token represents a human. A client-credentials token represents a service. IRSA represents a Kubernetes workload to AWS. Each has a different audience and blast radius. I do not reuse one identity for all three jobs."

### Cross questions

- Why not forward the browser token to Payment? Only do that when Payment must authorize directly on behalf of that user and its audience/scopes permit it.
- Why not use the node role? It gives every pod on a node the same AWS blast radius.
- How do we limit IRSA? Trust policy binds namespace plus service account; permission policy allows exact action, resource, and condition.

## 7. Secrets, Network, and Supply Chain

```text
Internet -> WAF -> ALB -> private EKS pods -> RDS Proxy -> private Aurora
                              |                 |
                              |                 +-> TLS + DB security group
                              v
                  IRSA -> Secrets Manager -> short-lived mounted secret

CI -> tests -> SBOM -> image scan/sign -> ECR digest -> admission policy -> EKS
```

### Why we choose it

**You say:** "Private subnet is not a complete control. I also use security groups, actual enforced NetworkPolicies, controlled egress, TLS, secret rotation, non-root containers, immutable image digests, and admission policy. Defense in depth means one failed control does not expose everything."

### Technology choices

| Category | A | B | When A is better | Examples |
|---|---|---|---|---|
| Secrets | AWS Secrets Manager | Kubernetes Secret only | Rotation, KMS audit, cross-service retrieval | DB credential rotation; partner API key rotation |
| Network policy | EKS VPC CNI policy enforcement | Cilium | Native EKS integration and simpler AWS estate | Deny app-to-db traffic; restrict DNS egress |
| Supply chain | ECR + Inspector + signed digest | Self-managed registry/scanner | AWS-native pipeline and fewer operators | Reject critical CVE image; pin payment image digest |

## 8. EKS and Database Resilience

```text
AZ-a: node -> order-api pod       Aurora writer / RDS Proxy
AZ-b: node -> order-api pod       Aurora replica / RDS Proxy
AZ-c: node -> autoscaling spare   Aurora storage replicated

HPA scales pods -> cluster autoscaler/Karpenter adds nodes -> RDS Proxy absorbs connection churn
```

### Why we choose it

**You say:** "Two replicas are a minimum, not an availability design. I spread replicas across zones, use readiness/startup probes, a PDB, `maxUnavailable: 0` where justified, node capacity planning, and load-tested autoscaling. Aurora handles managed database failover; application pods stay stateless."

### Trade-offs

- More replicas improve availability but multiply database connections. Budget total Hikari pools across maximum HPA scale.
- RDS Proxy reduces connection churn but does not give unlimited database capacity.
- Multi-AZ handles an AZ failure; regional DR requires a separate RTO/RPO, replication, runbook, and drill.

### Senior trap

**Question:** "We have two pods and Aurora Multi-AZ. Are we done?"

**Strong answer:** "No. Both pods might land on one node/AZ, probes might be wrong, the database may fail over slower than client timeouts, and a deployment can still take capacity out. I test pod kill, node drain, AZ loss, failover, and connection storm scenarios against SLOs."

## 9. Observability and Incident Readiness

```text
Request correlation ID
       |
       +-> API access log: issuer, user_id, tenant, route, status
       +-> trace: React -> ingress -> Order -> Payment -> database
       +-> metric: auth failures, 403 rate, RLS denies, latency, pool usage
       +-> audit: authorization decision, admin action, deployment image digest

Alert -> runbook -> isolate -> rotate/revoke -> recover -> postmortem
```

### Why we choose it

**You say:** "An incident without evidence becomes guesswork. I need to reconstruct who acted, in which tenant, through which service version, using which authorization decision. I never log passwords, raw JWTs, refresh tokens, or sensitive personal data."

### Required runbooks

- IDP outage or JWKS refresh failure
- Compromised/revoked token or leaked secret
- Cross-tenant access attempt or confirmed data exposure
- Aurora failover, failed restore, or connection saturation
- Bad deployment, privileged pod, or compromised workload

### Cross questions

- What alarm detects a tenant escape? RLS-denial anomalies, authorization-deny spike, and audit correlation, plus synthetic cross-tenant tests.
- What is your RTO/RPO? A business agreement measured by drills, not an aspiration.

## 10. Production Validation Matrix

| Area | Scenario | Expected result |
|---|---|---|
| Token | Wrong `iss`, `aud`, expired, ID token, missing scope | `401`/`403`; no DB access |
| Tenant | Acme token requests Globex order, including cache/export/async path | Denied; RLS and audit record it |
| IDP | Unknown `kid`, allowed key rotation, temporary JWKS outage | Cached known key works; controlled alert/degradation |
| EKS | Pod kill, node drain, AZ impairment, rolling release | Service meets documented availability SLO |
| Database | RDS Proxy connection surge and Aurora failover | Bounded retries; no data corruption; pool recovers |
| Supply chain | Critical CVE or privileged container submitted | CI/admission rejects deployment |

### Why this validation matters

**You say:** "A diagram says what we intend. A production drill proves what happens when the system is stressed, misconfigured, or partially unavailable. Each row must have an owner, a repeatable test, an observed result, and an agreed recovery time."

## 11. Advanced Areas Often Missed in Architect Rounds

```text
Employee joins / leaves -> HR system -> SCIM -> IDP -> groups / access -> audit
                                        |
                                        v
                             application membership and session revocation

Browser -> CSP / trusted scripts / token policy -> API abuse controls -> WAF / rate limits

Data lifecycle -> classification -> encryption / KMS -> retention -> deletion / legal hold
```

### Why these areas matter

**You say:** "Authentication is not finished at login. In production, a user leaves, a browser is compromised, an API is abused, a signing key rotates, and data reaches its retention date. I need controls for the entire identity and data lifecycle, not only token validation."

### Identity lifecycle, federation, and break-glass access

- Use **SCIM** or a controlled provisioning process to create, update, and deprovision workforce users from the enterprise directory. Deprovisioning must remove IDP groups, application memberships, active sessions, API keys, and privileged access.
- For enterprise SSO, support SAML or OIDC federation per tenant, but preserve the `issuer + sub -> internal user_id` mapping.
- Create tightly controlled **break-glass** administration: separate accounts, hardware MFA, short-lived elevation, mandatory audit, alerting on every use, and regular access review. It must not be an undocumented shared admin password.
- Decide whether authorization is evaluated live, cached briefly, or embedded in tokens. Short cache TTL and explicit revocation are needed when disabling an administrator must take effect quickly.

### Browser, API abuse, and perimeter protection

- Use CSP with nonces/hashes, strict `connect-src`, dependency review, and output sanitization to reduce XSS. PKCE protects an authorization code; it does not protect a stolen browser token from XSS.
- Add WAF managed rules, bot controls where appropriate, API rate limits by tenant/user/IP, request-size limits, pagination limits, and idempotency keys for write operations.
- Validate webhook signatures and replay timestamps. Use an egress proxy or allow-list for outbound webhooks to avoid SSRF and data exfiltration.

### Key, privacy, and data governance

- Define KMS key ownership, rotation, grants, separation between production and non-production keys, and what happens if a key is disabled. Encrypting data is not enough if every workload can decrypt it.
- Classify PII, payment data, and secrets. Define data minimization, retention, deletion, backup retention, legal hold, data-residency rules, and access-review evidence.
- Keep production data out of lower environments unless it is appropriately masked and approved. Test data masking as seriously as encryption.

### IDP and authorization dependency failure

```text
Okta / Entra unavailable
        |
        +-> Existing valid JWT with cached JWKS key: normal API validation can continue
        +-> New login / refresh token: unavailable or degraded according to product policy
        +-> Unknown kid / JWKS cache miss: fail closed, alert, never accept an unverified token

Membership / policy service unavailable
        |
        +-> high-risk write or admin action: fail closed
        +-> low-risk read: only serve explicitly safe cached authorization, if policy allows
```

### Why fail closed here

**You say:** "A cached public key can verify an already issued token, so normal validation can continue during a temporary IDP outage. But an unknown signing key cannot be trusted. For authorization data, I degrade only where an explicitly safe cached decision exists; money movement, tenant administration, and privilege changes fail closed."

### Senior traps

**Question:** "Our JWT lasts one hour. An admin is removed now. Are they blocked now?"

**Strong answer:** "Not automatically. The token may remain valid until expiry. I choose short access-token lifetime, revoke refresh/session at the IDP, and use live or short-lived cached authorization checks for high-risk actions. For emergency revocation, I can deny a token `jti` or user session with a bounded TTL, accepting the operational cost."

**Question:** "Can we keep serving traffic when JWKS is unavailable?"

**Strong answer:** "Only existing tokens whose `kid` maps to a previously cached trusted public key can be validated. For an unknown key or expired cache policy, I fail closed. Availability never justifies accepting a token whose signature cannot be verified."

**Question:** "Does encryption at rest solve privacy?"

**Strong answer:** "No. It protects storage media. Privacy also needs data minimization, authorization, audit, retention/deletion, key grants, data residency, and safe non-production handling."

## Senior Interview Close

**You say:**

"My design starts with the invariant, not the product names: a caller accesses only authorized tenant data and actions. I use an allow-listed IDP and `issuer + sub` to resolve a provider-neutral internal user. JWT signature validation is local through cached JWKS public keys, but authorization also requires scopes, application role, ownership, and tenant policy. EKS workload identity through IRSA is separate from the user identity. Aurora and RLS protect durable data, while network, secrets, immutable supply chain, observability, and tested runbooks limit blast radius and prove recovery. The important measure is not whether every tool is present; it is whether a specific failure is detected, contained, and recoverable."
