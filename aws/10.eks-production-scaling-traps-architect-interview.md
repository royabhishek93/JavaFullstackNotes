## NEW LEARNER FOUNDATION — Read This First If You Are New

```
KEY TERMS EXPLAINED SIMPLY
============================

CONTAINER
  A lightweight, isolated package containing your app + all its
  dependencies. Think of it like a shipping container — consistent,
  portable, runs the same everywhere (dev laptop, test server, cloud).

POD
  The smallest deployable unit in Kubernetes. A pod is one or more
  containers that run together on the same machine and share resources.
  In practice: 1 pod = 1 container = 1 instance of your service.

NODE
  A physical or virtual machine (EC2 instance on AWS) that runs pods.
  A node can run many pods. A cluster has many nodes.

DEPLOYMENT
  A Kubernetes object that says "I want 3 replicas of my Order Service
  running at all times." If a pod dies, Deployment creates a new one.

HPA (Horizontal Pod Autoscaler)
  Automatically increases or decreases the number of pods based on metrics
  like CPU usage. If CPU > 70%, add more pods. If CPU < 30%, remove pods.
  Think: thermostat for your application.

KEDA (Kubernetes Event-Driven Autoscaler)
  Like HPA but can scale on ANY external metric: SQS queue depth,
  Kafka consumer lag, Redis list length, etc.
  KEY feature: can scale to ZERO pods (no traffic = no pods = no cost).

CPU REQUEST vs CPU LIMIT
  Request: "This pod needs at least 500m (0.5 core) to function."
           Used by scheduler to decide which node to place the pod on.
  Limit:   "This pod must never use more than X CPU."
           If pod tries to exceed the limit, Linux kernel THROTTLES it
           (slows it down) — even if the node has spare capacity!

CPU Millicores: 1000m = 1 full CPU core. 500m = half a core.

IRSA (IAM Roles for Service Accounts)
  A way to give each Kubernetes pod its own AWS permissions, without
  hardcoding AWS credentials. Uses OIDC (a token-based identity system)
  to let pods assume IAM roles automatically.

PDB (PodDisruptionBudget)
  A rule that says "always keep at least N pods running."
  Prevents Kubernetes from accidentally removing all pods at once
  during maintenance, node drains, or rolling deployments.

VPC CNI
  The networking plugin that gives each Kubernetes pod its own real
  VPC IP address (instead of an overlay network). This means pods are
  fully routable within your VPC — but uses VPC IP addresses, which
  are a finite resource.
```

### OPENING — When They Ask: "How do you handle auto-scaling on EKS in production?"

> **You say:**
>
> "On Swiggy's EKS cluster, we have three levels of scaling that work together:
>
> Pod-level scaling with HPA — adds more pods when CPU or memory is high.
> Node-level scaling with Cluster Autoscaler — adds more EC2 nodes when pods
> can't be scheduled because nodes are full.
> Event-driven scaling with KEDA — scales based on business metrics like SQS
> queue depth, which CPU doesn't capture at all.
>
> The critical insight is that CPU-based HPA alone is often the wrong signal.
> A consumer service processing SQS messages can have low CPU but 50,000 messages
> queued — you need KEDA to scale on queue depth.
>
> Let me walk through each layer and the production traps I've hit."

```
SWIGGY EKS — THREE-LAYER SCALING
===================================

  SQS Queue (order events)
       │ 50,000 messages queued
       │ KEDA watches this
       ▼
  Order Consumer Pods (scale 1 → 20 based on queue depth)
       │
       │ CPU > 70%?
       │ HPA watches this
       ▼
  API Pods (scale 3 → 30 based on CPU/RPS)
       │
       │ API pods scheduled but no nodes available?
       ▼
  EKS Nodes (scale 3 → 10 via Cluster Autoscaler)

  SCALING RESPONSE TIME:
  HPA:              ~1-2 min (polls every 15s, scale-up delay)
  KEDA:             ~30s (watches metrics source directly)
  Cluster Autoscaler: 2-5 min (must provision new EC2 instance)
```

### PART 1 — When They Ask: "HPA vs KEDA — when do you use each?"

> **You say:**
>
> "HPA works for CPU and memory — if your service is compute-bound, HPA is right.
> A typical API service that does data processing: as requests go up, CPU goes up,
> HPA adds pods. That works well.
>
> KEDA is for external metric scaling. The classic example: a notification consumer
> reads from SQS and sends emails. The consumer is mostly idle — it reads a message,
> calls an email API, waits. CPU stays at 5% even with 100,000 messages queued.
> HPA sees low CPU and doesn't scale. KEDA can watch the SQS ApproximateNumberOfMessages
> and scale to zero when empty, scale to 20 when queue is deep."

```
HPA — CPU-BASED SCALING (API Services)
=======================================

# hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-api
  minReplicas: 3
  maxReplicas: 30
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70   # scale when avg CPU > 70%
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60    # wait 60s before scaling up again
      policies:
      - type: Pods
        value: 4
        periodSeconds: 60              # add max 4 pods per minute
    scaleDown:
      stabilizationWindowSeconds: 300  # wait 5 min before scaling down (avoid flapping)
      policies:
      - type: Percent
        value: 10
        periodSeconds: 60              # remove max 10% of pods per minute
```

```yaml
# KEDA — SQS Queue Depth Scaling (Consumer Services)
# keda-scaledobject.yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: notification-consumer-scaler
spec:
  scaleTargetRef:
    name: notification-consumer
  minReplicaCount: 0      # scale to ZERO when queue empty (cost saving!)
  maxReplicaCount: 20
  pollingInterval: 15     # check SQS every 15 seconds
  cooldownPeriod: 60      # wait 60s before scaling to zero
  triggers:
  - type: aws-sqs-queue
    authenticationRef:
      name: keda-sqs-auth   # IRSA role with SQS read permissions
    metadata:
      queueURL: https://sqs.us-east-1.amazonaws.com/123/swiggy-notifications
      awsRegion: us-east-1
      targetMessagesPerPod: "500"   # 1 pod per 500 messages
      # 5000 messages → 10 pods; 0 messages → 0 pods
```

### PART 2 — Trap: CPU Requests vs Limits (The Hidden Throttling Bug)

> **You say:**
>
> "This is the number one performance trap I've seen on EKS. Kubernetes CPU limits
> cause throttling — not just killing — when a pod tries to use more CPU than its limit.
>
> Here's the scenario: we set cpu request=500m, cpu limit=500m for an Order Service pod.
> Under normal load, the pod uses 300m — fine. During a traffic spike, it tries to use
> 700m. The node has spare CPU. But the limit is 500m — Kubernetes throttles the pod to
> 500m. Response time doubles. We see latency spikes in production. The node is sitting
> 40% idle. This is completely wasteful.
>
> My production rule: always set memory limit = memory request (OOM is a clear failure).
> For CPU, set request accurately (for scheduler), set limit much higher or omit it
> (let the pod burst when the node has spare capacity)."

```
CPU THROTTLING — The Hidden Performance Trap
=============================================

  Node: 4 CPU cores available
  ┌──────────────────────────────────────────────────────┐
  │ Pod A: cpu request=500m, limit=500m                  │
  │   Normal load: using 300m — fine                     │
  │   Traffic spike: wants 700m                          │
  │     Node has 2 free cores (2000m available!)         │
  │     BUT: limit is 500m → Kubernetes THROTTLES to 500m│
  │     Result: 40% slower responses, node sitting idle  │
  └──────────────────────────────────────────────────────┘

  CORRECT PRODUCTION CONFIG:
  ───────────────────────────

resources:
  requests:
    cpu: "500m"     # what scheduler uses for pod placement
    memory: "512Mi" # accurate — used for scheduling
  limits:
    cpu: "2000m"    # high ceiling or omit — let pod BURST on free node capacity
    memory: "512Mi" # = request — OOM kill is correct behaviour for memory overuse

  WHY memory limit = memory request:
    Memory can't be "given back" like CPU (no throttling, only OOM kill)
    If pod leaks memory past limit → OOM kill → restart → detects the bug
    If no limit → pod eats all node memory → node fails → OTHER pods evicted

  WHY high CPU limit (or none):
    CPU is compressible — throttled pod just gets slower, doesn't die
    Let pods burst during traffic spikes — that's why you have spare capacity
```

### PART 3 — Trap: IRSA vs Node IAM Role (Blast Radius)

> **You say:**
>
> "IRSA — IAM Roles for Service Accounts — is the correct way to give pods
> AWS permissions in EKS. The trap is using node IAM roles instead.
>
> With node IAM roles, every pod on that node shares the same AWS permissions.
> If your payment service pod is on the same node as an internal tool pod,
> the internal tool has payment service's S3 and DynamoDB permissions. That's
> a security blast radius problem.
>
> With IRSA, each Kubernetes service account gets its own IAM role via OIDC
> federation. Payment service pod → payment-service-sa → iam-role-payment.
> Internal tool pod → internal-tool-sa → iam-role-internal-tool.
> Completely isolated."

```
IRSA — HOW IT WORKS
====================

  EKS OIDC Provider
       │
       │ issues JWT token to pod's service account
       ▼
  Pod (running with serviceAccount: payment-service-sa)
       │ has JWT token mounted at /var/run/secrets/kubernetes.io/serviceaccount
       │
       │ calls STS AssumeRoleWithWebIdentity
       ▼
  AWS STS → validates JWT against EKS OIDC → issues temporary credentials
       │
       ▼
  IAM Role: arn:aws:iam::123:role/payment-service-role
  Policy: { S3: GetObject on payment-receipts/*, DynamoDB: GetItem on payments }
  → Payment service pod gets ONLY these permissions

SETUP:
```

```yaml
# 1. Service Account with IAM role annotation
apiVersion: v1
kind: ServiceAccount
metadata:
  name: payment-service-sa
  namespace: swiggy
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789:role/payment-service-role
```

```bash
# 2. IAM Role with OIDC trust (created via eksctl or Terraform)
eksctl create iamserviceaccount \
  --name payment-service-sa \
  --namespace swiggy \
  --cluster swiggy-prod \
  --attach-policy-arn arn:aws:iam::123:policy/PaymentServicePolicy \
  --approve

# 3. Pod spec uses the service account
# deployment.yaml
spec:
  serviceAccountName: payment-service-sa  # pod gets this role's credentials
  containers:
  - name: payment-service
    image: swiggy/payment-service:v1.2.3
    # AWS SDK automatically picks up IRSA credentials from environment
```

### PART 4 — Trap: Pod Disruption Budget (PDB) — Silent Outage During Deployment

> **You say:**
>
> "Without a PodDisruptionBudget, during a rolling deployment or node drain,
> Kubernetes can evict all replicas of a service simultaneously. If you have
> 3 pods and Kubernetes evicts 2 during a node drain, you're on 1 pod
> handling 100% of traffic while the new pods spin up. That's a partial outage.
>
> PDB prevents this. You define the minimum pods that must always be available.
> Kubernetes respects this during voluntary disruptions — node drains, deployments,
> autoscaler scale-down."

```
WITHOUT PDB — Rolling Deployment Outage
=========================================

  T+0s:  3 pods running (Pod A, Pod B, Pod C)
  T+5s:  Node drain starts (Node 1 has Pod A and Pod B)
  T+5s:  Kubernetes evicts Pod A  → 2 pods left
  T+5s:  Kubernetes evicts Pod B  → 1 pod left (Pod C handles all traffic)
  T+30s: New pods scheduled on other nodes
  T+60s: New pods ready
  Result: 55 seconds with 1 pod → service degraded/failed under load

WITH PDB — Controlled Disruption
==================================

  PDB: minAvailable = 2 (always keep at least 2 pods)

  T+0s:  3 pods (Pod A, Pod B, Pod C) — PDB allows disruption of 1
  T+5s:  Kubernetes evicts Pod A   → 2 pods left ← PDB threshold reached
  T+5s:  Kubernetes tries to evict Pod B → BLOCKED by PDB
  T+30s: New Pod A replacement becomes Ready → now 3 ready → PDB allows disruption
  T+30s: Kubernetes evicts Pod B → 2 pods + replacement still running
  Result: Always at least 2 pods — safe
```

```yaml
# pdb.yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: order-api-pdb
spec:
  minAvailable: 2          # always keep at least 2 pods
  # OR: maxUnavailable: 1  # never more than 1 pod unavailable at once
  selector:
    matchLabels:
      app: order-api

# COMBINED WITH: deployment rolling update strategy
# deployment.yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0    # never take a pod down before replacement is ready
      maxSurge: 1          # can have 1 extra pod during rollout
```

### PART 5 — Trap: Node IP Exhaustion with AWS VPC CNI

> **You say:**
>
> "AWS VPC CNI gives each pod its own real VPC IP address. This is elegant for
> security and routing, but the consequence is IP exhaustion.
>
> If your EKS nodes are in a /24 subnet — 256 addresses minus reserved — you
> have about 250 pod IPs. With 3 nodes each running 30 pods, you've used 90 IPs.
> Sounds fine. But each EC2 instance also pre-warms ENIs. A t3.large pre-allocates
> 12 IPs on startup even if only 5 pods are scheduled.
>
> Add autoscaling, larger node groups, and you can exhaust a /24 subnet with
> 50 pods actually running. The symptom: pods stuck in Pending with
> 'failed to allocate IP address'. Very confusing."

```
VPC CNI — IP EXHAUSTION PROBLEM
=================================

  /24 Subnet: 256 - 5 (AWS reserved) = 251 usable IPs

  Node 1 (m5.large): 3 ENIs × 10 IPs = 30 IPs pre-allocated
  Node 2 (m5.large): 30 IPs pre-allocated
  Node 3 (m5.large): 30 IPs pre-allocated
  Total pre-allocated: 90 IPs (even if only 20 pods running!)

  Autoscaler adds Node 4: 30 more IPs → 120 used
  Autoscaler adds Node 5-8: 240 IPs used
  → 11 IPs left → next pod: "Failed to allocate IP address"

  FIXES:
  ───────
  1. Use /23 or /22 subnets (larger — plan this BEFORE cluster creation!)

  2. Enable prefix delegation (AWS VPC CNI v1.9+):
     Each ENI slot holds /28 prefix (16 IPs) instead of 1 IP
     m5.large: 3 ENIs × 10 slots × 16 IPs = 480 IPs per node!

  3. Custom networking: pods get IPs from secondary CIDR (100.64.0.0/16)
     not from primary subnet — infinite IP space effectively
```

```bash
# Enable prefix delegation (add-on config)
kubectl set env daemonset aws-node \
  -n kube-system \
  ENABLE_PREFIX_DELEGATION=true \
  WARM_PREFIX_TARGET=1
```

### PART 6 — Advanced: Spot Instances + Interruption Handling

> **You say:**
>
> "For Swiggy's non-critical workloads — ML batch jobs, test environments,
> worker services — we use EC2 Spot instances for 70% cost savings. But Spot
> instances can be interrupted with 2 minutes notice.
>
> The architecture: use a mixed node group with On-Demand as base capacity for
> critical services, and Spot for scalable workers. When Spot is interrupted,
> Cluster Autoscaler falls back to On-Demand automatically.
>
> The application must handle interruption gracefully — Kubernetes sends SIGTERM
> 2 minutes before the instance is reclaimed. Spring Boot's graceful shutdown
> will drain in-flight requests. SQS consumers should checkpoint their offset
> before SIGTERM completes."

```
SPOT INSTANCE INTERRUPTION HANDLING
=====================================

  T-120s: AWS sends Spot interruption notice → EC2 metadata endpoint
  T-120s: Node interruption handler (aws-node-termination-handler) detects it
  T-120s: Node marked Unschedulable (no new pods scheduled on it)
  T-120s: Pods evicted gracefully (SIGTERM sent)
  T-90s:  Spring Boot graceful shutdown: drains active HTTP requests (30s window)
  T-60s:  SQS consumers: finish current message processing, stop polling
  T-30s:  Application exits cleanly
  T-0s:   EC2 instance reclaimed by AWS

  Spring Boot graceful shutdown config:
```

```yaml
server:
  shutdown: graceful              # drain requests before shutdown

spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s  # max 30s to drain

# Kubernetes deployment: give pods time to drain
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 60   # 60s before SIGKILL
      containers:
      - name: order-service
        lifecycle:
          preStop:
            exec:
              command: ["/bin/sh", "-c", "sleep 5"]  # wait for ALB to drain
              # ALB deregistration delay is 30s — pod needs to wait
              # before it stops accepting connections
```

## Interview Cheat Sheet (Say This Confidently)

> "On EKS in production: three layers of scaling — KEDA for event-driven services (SQS depth), HPA for CPU-bound APIs, Cluster Autoscaler for node provisioning. CPU limits are the hidden performance trap — setting limit=request throttles pods even when nodes have spare capacity. Always set memory limit=request (OOM kill is correct), but set CPU limit high or omit it for bursty services. IRSA gives each service account its own IAM role — never use node IAM roles (too broad, whole node shares permissions). PodDisruptionBudgets prevent rolling deployments from evicting all pods simultaneously. VPC CNI IP exhaustion is a capacity-planning trap — use /22+ subnets or enable prefix delegation before you build the cluster, not after."
