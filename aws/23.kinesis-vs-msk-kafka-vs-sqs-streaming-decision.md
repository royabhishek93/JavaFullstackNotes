## NEW LEARNER FOUNDATION — Read This First If You Are New

```
KEY TERMS EXPLAINED SIMPLY
============================

KINESIS DATA STREAMS (KDS)
  AWS-managed real-time streaming service. You write records into a stream.
  The stream is split into shards. Each shard handles 1MB/s write, 2MB/s read.
  Consumers pull from shards and process records in order (per shard).
  Records persist for 24 hours by default (up to 365 days).

SHARD
  The unit of capacity in Kinesis. Think of it like a lane on a highway.
  1 shard = 1MB/s in, 2MB/s out. You add shards to increase throughput.
  A shard key (like user_id) determines which shard a record goes to.
  Records with the same shard key always go to the same shard → ordering guaranteed.

KINESIS FIREHOSE (now called Kinesis Data Firehose / Amazon Data Firehose)
  A managed delivery service. You PUT records in, Firehose buffers them and
  automatically delivers batches to S3, Redshift, or OpenSearch.
  You do NOT write consumer code. It's fire-and-forget delivery.
  Buffer: delivers every 60 seconds OR when buffer hits 128MB (whichever first).

MSK (Managed Streaming for Apache Kafka)
  AWS-managed Apache Kafka. AWS handles broker provisioning, OS patching,
  replication, and failover. You bring your Kafka producers/consumers as-is.
  MSK Serverless: no broker sizing — auto-scales, pay per GB written/read.

KAFKA CONSUMER GROUP
  A group of consumers that together read a Kafka topic. Each partition is
  assigned to exactly one consumer in the group. Different groups each get
  ALL messages independently (like Kinesis EFO but built into Kafka).
  Example: group "analytics" and group "billing" both get every order event.

SQS (Simple Queue Service)
  A message queue. Producers send messages. Consumers pull messages and process
  them. After processing, consumer deletes the message. If not deleted within
  the visibility timeout, the message becomes visible again (retry mechanism).
  Standard: at-least-once delivery, no ordering guarantee.
  FIFO: exactly-once, strict ordering per MessageGroupId.

SNS (Simple Notification Service)
  A pub/sub push service. Publisher sends one message to a topic. SNS instantly
  pushes it to all subscribers (SQS queues, Lambda, HTTP endpoints, email).
  No retention — if a subscriber is down, message is lost (use SQS buffer).

ENHANCED FAN-OUT (EFO)
  A Kinesis feature where each registered consumer gets a DEDICATED 2MB/s per
  shard, instead of sharing the shard's 2MB/s with all other consumers.
  Without EFO: 5 consumers share 2MB/s → each gets ~400KB/s (they starve).
  With EFO: 5 consumers each get their own 2MB/s → 10MB/s total throughput.
  Cost: $0.015 per shard-hour per registered consumer.

PARTITION KEY (Kafka) / SHARD KEY (Kinesis)
  A field in the event used to route to the correct partition/shard.
  All events with the same key go to the same partition/shard → ordering.
  Choose high-cardinality keys (user_id, order_id) not low-cardinality
  (order_status = "PLACED" would send ALL placed orders to one shard = HOT SHARD).

VISIBILITY TIMEOUT (SQS)
  When a consumer reads a message from SQS, the message is hidden from other
  consumers for the visibility timeout period (default 30s). If the consumer
  finishes and deletes the message → done. If consumer crashes and doesn't
  delete → message reappears after timeout → another consumer retries.

DEAD LETTER QUEUE (DLQ)
  After a message fails N times (maxReceiveCount), SQS sends it to a DLQ.
  You inspect the DLQ to find messages that keep failing, debug the issue.
  Every SQS queue should have a DLQ configured.
```

## SECTION 2 — Kinesis Data Streams Deep Dive

### When They Ask: "Explain Kinesis shards, hot shards, and Enhanced Fan-Out."

> **You say:**
>
> "A Kinesis stream is divided into shards. Each shard is a fixed capacity lane:
> 1MB/s write, 2MB/s read. All consumers share that 2MB/s read per shard.
>
> The shard key you choose when putting a record determines which shard it goes to.
> If you use a low-cardinality key like order_status, every 'PLACED' order goes to
> the same shard — you get a hot shard, that shard is throttled, and you lose ordering
> guarantees for other records while the hot shard is saturated.
>
> Use high-cardinality keys: user_id, order_id, session_id. Then load distributes
> evenly across shards.
>
> Enhanced Fan-Out solves the multi-consumer read problem. Without it, if you have
> Lambda + analytics app + audit service all reading the same stream, they share the
> shard's 2MB/s. With EFO, each registered consumer gets a dedicated 2MB/s pipe per
> shard. It uses HTTP/2 push instead of polling — lower latency too."

```
SHARD MODEL — WITHOUT Enhanced Fan-Out (SHARED throughput)
===========================================================

  Kinesis Stream
  ┌──────────────────────────────────────────────────┐
  │  Shard-1: 1MB/s write capacity                   │
  │  ┌─────────────────────────────────────────────┐  │
  │  │  READ capacity: 2MB/s SHARED by ALL          │  │
  │  │                                              │  │
  │  │  Consumer A (Lambda)     ──► ~400KB/s        │  │
  │  │  Consumer B (Analytics)  ──► ~400KB/s        │  │
  │  │  Consumer C (Audit)      ──► ~400KB/s        │  │
  │  │  Consumer D (Billing)    ──► ~400KB/s        │  │
  │  │  Consumer E (Alerts)     ──► ~400KB/s        │  │
  │  │                                              │  │
  │  │  TOTAL: 5 × 400KB/s = 2MB/s (at limit!)     │  │
  │  │  → consumers starve each other               │  │
  │  └─────────────────────────────────────────────┘  │
  └──────────────────────────────────────────────────┘

  SHARD MODEL — WITH Enhanced Fan-Out (DEDICATED throughput)
  ===========================================================

  Kinesis Stream
  ┌──────────────────────────────────────────────────┐
  │  Shard-1: 1MB/s write capacity                   │
  │  ┌─────────────────────────────────────────────┐  │
  │  │  READ capacity: DEDICATED 2MB/s per consumer │  │
  │  │                                              │  │
  │  │  Consumer A (Lambda)     ──► 2MB/s dedicated │  │
  │  │  Consumer B (Analytics)  ──► 2MB/s dedicated │  │
  │  │  Consumer C (Audit)      ──► 2MB/s dedicated │  │
  │  │  Consumer D (Billing)    ──► 2MB/s dedicated │  │
  │  │  Consumer E (Alerts)     ──► 2MB/s dedicated │  │
  │  │                                              │  │
  │  │  TOTAL: 5 × 2MB/s = 10MB/s                  │  │
  │  │  → each consumer gets full throughput        │  │
  │  └─────────────────────────────────────────────┘  │
  └──────────────────────────────────────────────────┘

  Extra cost: $0.015/shard-hour per registered consumer
  Extra benefit: HTTP/2 push = ~65ms latency vs ~200ms polling

HOT SHARD PROBLEM
==================

  BAD shard key — order_status (only 4 values: PLACED, PAID, SHIPPED, DELIVERED)
  ┌───────────────────────────────────────────────────────┐
  │  Shard-1 ← key="PLACED"   ALL new orders here → 🔥   │
  │  Shard-2 ← key="PAID"     throttled, backed up        │
  │  Shard-3 ← key="SHIPPED"  mostly idle                 │
  │  Shard-4 ← key="DELIVERED" mostly idle                │
  └───────────────────────────────────────────────────────┘

  GOOD shard key — order_id (UUID, millions of values)
  ┌───────────────────────────────────────────────────────┐
  │  Shard-1 ← hash(order_id) range 0-25%   ~even load   │
  │  Shard-2 ← hash(order_id) range 25-50%  ~even load   │
  │  Shard-3 ← hash(order_id) range 50-75%  ~even load   │
  │  Shard-4 ← hash(order_id) range 75-100% ~even load   │
  └───────────────────────────────────────────────────────┘
```

```java
// Spring Boot — Kinesis Producer using AWS SDK v2
@Service
public class OrderEventProducer {

    private final KinesisAsyncClient kinesisClient;

    public OrderEventProducer() {
        this.kinesisClient = KinesisAsyncClient.builder()
            .region(Region.AP_SOUTH_1)
            .credentialsProvider(DefaultCredentialsProvider.create())
            .build();
    }

    public CompletableFuture<PutRecordResponse> publishOrderEvent(OrderEvent event) {
        String payload = new ObjectMapper().writeValueAsString(event);

        PutRecordRequest request = PutRecordRequest.builder()
            .streamName("order-events-stream")
            .partitionKey(event.getOrderId())    // HIGH cardinality — distributes evenly
            .data(SdkBytes.fromUtf8String(payload))
            .build();

        return kinesisClient.putRecord(request);
    }
}
```

## SECTION 3 — Kinesis Firehose: Zero-Code Delivery to S3 / Redshift / OpenSearch

### When They Ask: "How would you build a clickstream analytics pipeline for 10M users?"

> **You say:**
>
> "Firehose is not a streaming consumer — it is a managed delivery service.
> You put records in, Firehose buffers them (60 seconds or 128MB, whichever
> comes first), then delivers compressed batches to S3, Redshift, or OpenSearch.
> You write zero consumer code for this delivery path.
>
> For 10M users clicking through an OTT platform, I'd do:
> Mobile/React → Kinesis Data Streams (partition key = user_id) → Firehose
> attached as a consumer → S3 in Parquet format → Athena for ad-hoc SQL queries.
>
> Firehose also supports inline Lambda transformation — so I can enrich records
> (add geo from IP, convert JSON to Parquet) before they land in S3.
>
> The 60-second buffer is the main trade-off. Firehose is for analytics pipelines
> where you can tolerate near-real-time (1-minute delay). Not for real-time fraud
> detection — use KDS directly there."


## SECTION 4 — MSK (Managed Kafka): When to Use Real Kafka on AWS

### When They Ask: "When would you use MSK over Kinesis?"

> **You say:**
>
> "MSK is AWS-managed Apache Kafka. AWS handles broker provisioning, OS patching,
> cross-AZ replication, and ZooKeeper or KRaft. You bring your existing Kafka
> producers and consumers untouched.
>
> I choose MSK over Kinesis in four scenarios:
>
> One — you already have a Kafka codebase. Migrating to Kinesis means rewriting
> all producers and consumers. MSK lets you lift-and-shift.
>
> Two — you need Kafka ecosystem tools: Kafka Streams for stateful stream
> processing, ksqlDB for SQL over streams, Kafka Connect for database CDC,
> Glue Schema Registry for Avro/Protobuf schema enforcement.
>
> Three — you need more than 1MB/s per partition. Kinesis shards are hard-capped
> at 1MB/s write. Kafka partitions can handle much higher throughput.
>
> Four — multi-consumer fan-out without per-consumer cost. In Kinesis, every
> additional consumer sharing a shard either degrades throughput or requires EFO
> at extra cost. In Kafka, adding a new consumer group costs nothing extra — each
> group independently reads all messages."

```
MSK vs KINESIS — DECISION TREE
================================

  New project on AWS, no Kafka history?
  ├── YES → Use Kinesis Data Streams (simpler ops, AWS-native integrations)
  └── NO → Do you have Kafka producers/consumers to migrate?
            ├── YES → Use MSK (zero rewrite, lift-and-shift)
            └── NO → Do you need any of these?
                      ├── Kafka Streams / ksqlDB stateful processing
                      ├── Kafka Connect (CDC from RDS)
                      ├── Schema Registry (Avro / Protobuf)
                      ├── Log compaction (keep only latest per key)
                      ├── Exactly-once transactions (producer + consumer)
                      ├── > 1MB/s per partition throughput
                      └── Many consumer groups without paying per-consumer EFO
                          │
                          ├── Any YES → Use MSK
                          └── All NO  → Use Kinesis (simpler, cheaper at low scale)

=====================================================

  Driver App (location update every 3s)
        │
        │  Kafka Producer (partition key = driver_id)
        ▼
  ┌──────────────────────────────────────────────────┐
  │  MSK Cluster (3 brokers, 3 AZs)                  │
  │  Topic: "driver-location-updates"                │
  │  Partitions: 50 (each driver always same shard)  │
  │  Replication factor: 3                           │
  │  Retention: 1 hour (location data stales fast)   │
  └──────────┬───────────────────────────────────────┘
             │
    ┌────────┼────────────┐
    ▼        ▼            ▼
  Consumer  Consumer    Consumer

  "tracking" "eta-calc" "heatmap"
```

## SECTION 5 — SQS Standard vs FIFO: Task Queue Patterns

### When They Ask: "When do you use SQS FIFO vs Standard? What is visibility timeout?"

> **You say:**
>
> "SQS Standard is for async task queues where the work is idempotent — meaning
> processing the same message twice is safe. At-least-once delivery means you might
> get a duplicate. Your worker must handle that: check if the order email was already
> sent before sending again.
>
> SQS FIFO is for cases where ordering matters AND duplicates are unacceptable.
> Financial transactions are the classic example: if I process payment twice or out
> of order, money is gone or the account goes negative. FIFO guarantees exactly-once
> processing and strict order per MessageGroupId.
>
> Visibility timeout is the core reliability mechanism. When a worker reads a message,
> SQS hides it for the timeout period. If the worker finishes and calls DeleteMessage,
> it's gone. If the worker crashes and never calls DeleteMessage, SQS makes the message
> visible again after the timeout — another worker retries. The trap is: set your
> visibility timeout to be longer than your maximum processing time. If payment
> processing takes 45 seconds but visibility timeout is 30 seconds, the message
> reappears while still being processed → duplicate payment attempt."

```
SQS STANDARD — E-Commerce Async Task Queue
===========================================

  Order Service
        │  (order placed)
        │
        ▼
  ┌───────────────────────────────────────────────┐
  │  SQS Standard Queue: "order-post-processing"  │
  │  Visibility Timeout: 5 minutes                │
  │  Message Retention: 14 days                   │
  │  DLQ after: 3 failed attempts                 │
  └───────┬───────────────────────────────────────┘
          │ (workers COMPETE — each msg processed once)
    ┌─────┼──────┐
    ▼     ▼      ▼
  Email  Resize  Push
  Worker Image   Notif
         Worker  Worker
  (workers are independent, all process different messages)

SQS FIFO — Financial Payment Queue
=====================================

  Order Service
        │  MessageGroupId = order_id
        │  MessageDeduplicationId = idempotency_key
        ▼
  ┌───────────────────────────────────────────────────┐
  │  SQS FIFO Queue: "payment-processing.fifo"        │
  │  Throughput: 300 TPS base, 3000 TPS with batching │
  │  MessageGroupId: order_id                         │
  │  → Messages for same order processed in order     │
  │  → Messages for different orders processed in     │
  │    parallel (different groups run concurrently)   │
  └───────────────────────────────────────────────────┘
          │
          ▼
    Payment Worker
    (reads 1 message per MessageGroupId at a time)

  ORDER-001: CHARGE → CONFIRM → RECEIPT  (in order, no duplicates)
  ORDER-002: CHARGE → CONFIRM → RECEIPT  (parallel to ORDER-001)
  ORDER-003: CHARGE → CONFIRM → RECEIPT  (parallel to both)

VISIBILITY TIMEOUT TRAP:
  Processing time: 45s
  Visibility timeout: 30s  ← WRONG — message reappears while still processing!
  Fix: visibility timeout = 2 × max_processing_time = 90s minimum
```

```java
// Spring Boot — SQS Consumer with Spring Cloud AWS
@Component
public class OrderPostProcessingWorker {

    // Spring Cloud AWS auto-deletes message on successful return
    // On exception, message becomes visible again after visibility timeout
    @SqsListener(value = "order-post-processing",
                 deletionPolicy = SqsMessageDeletionPolicy.ON_SUCCESS)
    public void processOrder(OrderEvent event, @Headers Map<String, Object> headers) {
        // Idempotency check — SQS Standard can deliver duplicates
        if (processedOrderRepository.alreadyProcessed(event.getOrderId())) {
            log.info("Skipping duplicate: {}", event.getOrderId());
            return;
        }
        emailService.sendConfirmation(event);
        processedOrderRepository.markProcessed(event.getOrderId());
    }
}

// Manual SQS receive using AWS SDK v2
@Service
public class SqsPollingService {

    private final SqsClient sqsClient;

    public List<Message> pollMessages(String queueUrl) {
        ReceiveMessageRequest request = ReceiveMessageRequest.builder()
            .queueUrl(queueUrl)
            .maxNumberOfMessages(10)
            .waitTimeSeconds(20)       // Long polling — waits up to 20s for messages
            .visibilityTimeout(300)    // 5 minutes visibility timeout
            .build();

        return sqsClient.receiveMessage(request).messages();
    }

    public void deleteMessage(String queueUrl, Message message) {
        DeleteMessageRequest deleteRequest = DeleteMessageRequest.builder()
            .queueUrl(queueUrl)
            .receiptHandle(message.receiptHandle())
            .build();
        sqsClient.deleteMessage(deleteRequest);
    }
}
```

## SECTION 6 — SNS Fan-Out Pattern

### When They Ask: "How do you notify multiple services when an order is placed?"

> **You say:**
>
> "When an order is placed, multiple downstream systems need to react: inventory
> must be reserved, the notification service must send a confirmation, the analytics
> pipeline must record the event, and the fraud detection system must score the order.
>
> The naive approach is the Order Service calling each of those services directly.
> That creates tight coupling — if the notification service is down, the order
> placement fails.
>
> The right pattern is SNS fan-out. Order Service publishes one message to an SNS
> topic. SNS instantly pushes it to multiple SQS queues — one per downstream service.
> Each service has its own queue, its own consumer, its own retry logic. If the
> notification service is down, its SQS queue accumulates messages and drains when
> it recovers. Zero coupling.
>
> SNS alone is not enough — it's push-based with no retention. If a subscriber is
> down when SNS pushes, the message is lost. The SQS buffer between SNS and each
> consumer is what gives you durability."

```
SNS FAN-OUT → MULTIPLE SQS QUEUES
====================================

  Order Service
        │  (order placed event)
        ▼
  ┌─────────────────────────────────────────┐
  │  SNS Topic: "order-events"              │
  │  (push to all subscribers instantly)    │
  └───┬───────────┬────────────┬────────────┘
      │           │            │
      ▼           ▼            ▼
  ┌───────┐  ┌─────────┐  ┌──────────┐
  │  SQS  │  │   SQS   │  │   SQS    │
  │Inventory│ │Notifica-│  │Analytics │
  │ Queue │  │tion Q   │  │  Queue   │
  └───┬───┘  └────┬────┘  └────┬─────┘
      │           │             │
      ▼           ▼             ▼
  Inventory  Notification   Analytics
   Worker      Worker        Worker

  If Notification Worker is down:
  → SNS still delivers to all other SQS queues (inventory and analytics unaffected)
  → Notification SQS queue accumulates messages (14 days retention)
  → When Notification Worker recovers, it drains the queue
  → Zero message loss, zero coupling

SNS MESSAGE FILTERING
======================

  SNS Subscription Filter Policy (on the Analytics Queue subscription):
  {
    "event_type": ["ORDER_PLACED", "ORDER_CANCELLED"]
    // Analytics only receives placed/cancelled, not SHIPPED or DELIVERED
  }

  Inventory Queue subscription filter:
  {
    "event_type": ["ORDER_PLACED", "ORDER_CANCELLED"]
    // Only needs to reserve/release inventory on placed or cancelled
  }

  This prevents unnecessary message delivery and reduces worker processing.

SNS vs EventBridge
===================

  SNS: Fan-out to known, fixed subscribers. Simple attribute-based filtering.
  EventBridge: Content-based routing to many targets. Filter by ANY JSON field.
               Native integration with 200+ AWS services (SageMaker, Step Functions).
               Use EventBridge when you need: complex routing rules, schema registry,
               event archiving/replay, cross-account event buses.

  Rule of thumb:
  SNS → multiple SQS queues (simple fan-out within your account)
  EventBridge → complex routing, AWS service integrations, cross-account
```

## COMMON TRAPS AND GOTCHAS

```
TRAP 1: Kinesis 1MB/s shard write limit is PER SHARD, not per stream
  ───────────────────────────────────────────────────────────────────
  Symptom: ProvisionedThroughputExceededException even after adding shards.
  Cause: Hot shard — all records going to 1 shard (low cardinality partition key).
  Fix: Use order_id or user_id as shard key, not order_status or event_type.
  Also: A single record > 1MB is rejected outright. Kinesis max record size = 1MB.

TRAP 2: SQS Visibility Timeout shorter than processing time = duplicate processing
  ────────────────────────────────────────────────────────────────────────────────
  Symptom: Workers process the same message twice. Payment charged twice.
  Cause: Processing takes 90s, visibility timeout is 30s → SQS makes message
         visible again at 30s → second worker picks it up → two workers process it.
  Fix: Visibility timeout = at minimum 2× max expected processing time.
       For variable processing time, use ChangeMessageVisibility to extend it.

TRAP 3: SQS FIFO 3000 TPS ceiling — not for high-throughput streaming
  ────────────────────────────────────────────────────────────────────
  SQS FIFO with batching handles 3000 TPS. That's 3000 messages per second.
  For high-volume event streams (1M clicks/min = 16,666/s), FIFO is the wrong tool.
  Use Kinesis or MSK for high-throughput. Use FIFO only for low-volume ordered tasks.

TRAP 4: Kinesis Firehose 60-second minimum buffer delay
  ──────────────────────────────────────────────────────
  Firehose buffers for 60 seconds OR 128MB. You cannot get sub-minute delivery.
  If your use case needs real-time alerting (fraud detection, live dashboards),
  Firehose is wrong — use KDS directly with Lambda or KCL consumer.
  Firehose is for analytics pipelines where 1-minute latency is acceptable.

TRAP 5: MSK broker sizing — underprovision = replication lag
  ─────────────────────────────────────────────────────────
  MSK provisioned requires you to choose broker type and count upfront.
  Underprovisioned brokers cause replication lag → consumers see stale data.
  Solution: Use MSK Serverless (auto-scales) for variable workloads.
  Or: Monitor kafka.server:ReplicaMaxLag and set alarms.

TRAP 6: SNS fan-out without SQS buffer = message loss on subscriber downtime
  ──────────────────────────────────────────────────────────────────────────
  SNS push is fire-and-forget. If the target Lambda or HTTP endpoint is down,
  SNS retries briefly then drops the message.
  ALWAYS put SQS queues between SNS and your consumers.
  SNS → SQS → Worker (not SNS → Lambda directly for critical business events).

TRAP 7: Kinesis consumer reads are SHARED by default (no Enhanced Fan-Out)
  ─────────────────────────────────────────────────────────────────────────
  If you have 3 Lambdas all triggered by the same KDS stream, they SHARE the
  2MB/s read capacity per shard. Under high load, they starve each other.
  You only notice this at scale — in dev/staging with low volume it looks fine.
  Fix: Register Enhanced Fan-Out consumers for production multi-consumer setups.

TRAP 8: SQS Long Polling vs Short Polling — cost and empty receive charges
  ─────────────────────────────────────────────────────────────────────────
  Default SQS receive is short polling — returns immediately even if empty.
  An empty receive still counts as an API call → you pay for it.
  At scale: 10 workers × 1 poll/s × 86400s = 864,000 API calls/day, many empty.
  Fix: Always use waitTimeSeconds=20 (Long Polling) — reduces empty receives,
       reduces cost, reduces CPU on polling workers.
```
