### OPENING — When They Ask: "How do you handle async messaging between microservices?"

> **You say:**
>
> "Let me use the most concrete example — when a customer places an order on Swiggy.
>
> The Order Service accepts the request, persists the order, and immediately returns
> a response to the customer. But now three things need to happen: send a confirmation
> email, send an SMS, and push the data to the analytics pipeline.
>
> If Order Service directly called Email Service, SMS Service, and Analytics Service
> synchronously — that's three blocking HTTP calls, three failure points, and the
> customer waits for all three to complete before getting a confirmation.
>
> Instead: Order Service publishes one event to SNS. SNS fans it out to three SQS
> queues. Each consumer service processes at its own pace. The customer gets their
> confirmation in 200ms regardless of whether the email service is slow."

```
SNS FAN-OUT PATTERN — Swiggy Order Placed
==========================================

  Order Service
      |
      | Publish: OrderPlacedEvent
      | {orderId: "ORD-123", userId: "U-456",
      |  total: 450.00, items: [...]}
      v
  SNS Topic: swiggy-order-placed
      |
      ├──────────────────────────────────────────┐
      |                                          |
      v                                          v
  SQS: order-email-queue            SQS: order-sms-queue
      |                                          |
      v                                          v
  Email Service                         SMS Service
  (send order confirmation)            (send SMS notification)
      |                                          |
      |            ┌─────────────────────────────┘
      |            |
      |            v
      |     SQS: order-analytics-queue
      |            |
      |            v
      |     Analytics Service
      |     (push to data warehouse)
      |
  DLQ: order-email-dlq          DLQ: order-sms-dlq
  (after 3 retries, message      DLQ: order-analytics-dlq
   lands here for investigation)

  RESULT:
  ✓ Order Service: 200ms response (no downstream blocking)
  ✓ Email Service: processes in ~2sec (user doesn't wait)
  ✓ SMS Service:   processes in ~1sec
  ✓ Analytics:     processes in batch (minutes ok)
  ✓ If Email fails: retried from SQS, not the customer's problem
```

### PART 1 — When They Ask: "How is SNS and SQS configured?"

> **You say:**
>
> "SNS topic with three SQS subscriptions. Each SQS queue has its own consumer
> and its own DLQ. The DLQ gets a CloudWatch alarm — when any message lands in the
> DLQ, oncall gets paged within 5 minutes.
>
> I always set up the DLQ alarm before the happy-path alarm. A message in the DLQ
> means a real failure that needs investigation — it should never sit silently."

```
AWS INFRASTRUCTURE SETUP
==========================

  SNS Topic:
  Name: swiggy-order-placed
  Type: Standard (not FIFO — ordering not required for notifications)

  SQS Queues (one per consumer):
  ┌─────────────────────────────────────────────────────────────┐
  │  Queue: order-email-queue                                   │
  │  Visibility timeout: 30s (must be > email send time)        │
  │  Message retention: 4 days (default)                        │
  │  DLQ: order-email-dlq                                       │
  │  Max receive count: 3 (retry 3 times before DLQ)            │
  └─────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────┐
  │  Queue: order-sms-queue                                     │
  │  Visibility timeout: 30s                                    │
  │  DLQ: order-sms-dlq, Max receive count: 3                   │
  └─────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────┐
  │  Queue: order-analytics-queue                               │
  │  Visibility timeout: 5min (analytics processing is slower)  │
  │  DLQ: order-analytics-dlq, Max receive count: 5             │
  └─────────────────────────────────────────────────────────────┘

  SNS Subscriptions:
  swiggy-order-placed → order-email-queue     (raw message delivery: enabled)
  swiggy-order-placed → order-sms-queue       (raw message delivery: enabled)
  swiggy-order-placed → order-analytics-queue (raw message delivery: enabled)

  CloudWatch Alarms (critical — set these up FIRST):
  Metric: ApproximateNumberOfMessagesVisible
  Queue:  *-dlq
  Threshold: >= 1
  Action: SNS → PagerDuty / email oncall
```

  order-sms-queue-url:   ${SQS_SMS_QUEUE_URL}

**OrderService.java (producer — publishes to SNS):**

```java
@Service
public class OrderService {

    private final SnsTemplate snsTemplate;

    @Value("${sns.order-placed-topic-arn}")
    private String orderPlacedTopicArn;

    public OrderResponse placeOrder(PlaceOrderRequest request, String userId) {
        // 1. Persist order to RDS
        Order order = orderRepository.save(Order.from(request, userId));

        // 2. Publish event to SNS (async — does not wait for consumers)
        OrderPlacedEvent event = OrderPlacedEvent.builder()
            .orderId(order.getId())
            .userId(userId)
            .total(order.getTotal())
            .items(order.getItems())
            .restaurantId(order.getRestaurantId())
            .placedAt(Instant.now())
            .build();

        snsTemplate.sendNotification(orderPlacedTopicArn, event, "OrderPlaced");
        // Fire and forget — SNS publish is ~5ms, consumer processing happens async

        // 3. Return response immediately — don't wait for email/SMS
        return OrderResponse.from(order);
    }
}
```

**EmailNotificationService.java (consumer — listens to SQS):**

```java
@Service
public class EmailNotificationService {

    @SqsListener("${sqs.order-email-queue-url}")
    public void handleOrderPlaced(OrderPlacedEvent event) {
        // Spring Cloud AWS:
        // 1. Long-polls SQS (up to 20s wait, free when no messages)
        // 2. On message received: sets visibility timeout (30s)
        //    → message invisible to other consumers during processing
        // 3. Calls this method
        // 4. If method returns normally: deletes message from SQS
        // 5. If method throws: does NOT delete → SQS retries after timeout

        log.info("Sending confirmation email for order: {}", event.getOrderId());

        try {
            emailProvider.send(EmailRequest.builder()
                .to(userService.getEmail(event.getUserId()))
                .subject("Order Confirmed: " + event.getOrderId())
                .template("order-confirmation")
                .data(Map.of(
                    "orderId", event.getOrderId(),
                    "total",   event.getTotal(),
                    "items",   event.getItems()
                ))
                .build());
        } catch (EmailProviderException e) {
            // Throwing here means SQS will retry after visibility timeout
            // After 3 retries: message moves to DLQ
            log.error("Email send failed for order: {}. Will retry.", event.getOrderId(), e);
            throw e;     // rethrow so SQS knows processing failed
        }
    }
}
```

### PART 3 — When They Ask: "What is a DLQ and why does every queue need one?"

> **You say:**
>
> "DLQ is Dead Letter Queue. When SQS retries a message and it keeps failing —
> after 3 attempts in our config — SQS moves it to the DLQ instead of dropping it.
>
> Without a DLQ, a permanently failing message would be retried forever, blocking
> the queue and creating an infinite retry loop. Or worse — SQS would delete it
> after the retention period and you'd never know it failed.
>
> With a DLQ, the message is preserved for investigation. The CloudWatch alarm on
> DLQ depth fires within 5 minutes, an engineer investigates, fixes the root cause,
> and replays the message from the DLQ."

```
DLQ FLOW — What Happens When Email Send Fails
===============================================

  SNS publishes message to order-email-queue
          |
          v
  EmailService.handleOrderPlaced() throws EmailProviderException
          |
          | SQS: visibility timeout expires (30s)
          | Message becomes visible again
          v
  EmailService.handleOrderPlaced() called again (retry #1)
          |
          | Still fails
          v
  EmailService.handleOrderPlaced() called again (retry #2)
          |
          | Still fails
          v
  EmailService.handleOrderPlaced() called again (retry #3)
          |
          | Max receive count reached = 3
          v
  SQS moves message to: order-email-dlq
          |
          | CloudWatch alarm fires (DLQ depth >= 1)
          v
  PagerDuty alert → engineer investigates
  ├── Check email provider status (is SES/SendGrid down?)
  ├── Fix the root cause
  └── Replay from DLQ:
      aws sqs send-message --queue-url order-email-queue \
        --message-body "$(aws sqs receive-message --queue-url order-email-dlq \
        --query 'Messages[0].Body' --output text)"

  MESSAGE IS NOT LOST — preserved in DLQ until replayed or expired
```

### PART 4 — When They Ask: "How do you handle duplicate messages?"

> **You say:**
>
> "SQS Standard guarantees at-least-once delivery — meaning the same message
> can occasionally be delivered twice. This is rare but possible, especially
> during retries or network issues.
>
> For email: sending a duplicate order confirmation is annoying but acceptable.
> For payment: sending a duplicate payment event is catastrophic.
>
> The fix: idempotency. Each message has a unique ID. Before processing,
> check Redis or a DB whether that ID was already processed."

```
IDEMPOTENCY PATTERN FOR SQS CONSUMERS
========================================

  SQS message has built-in MessageId (UUID)
  Also: we put orderId in the message payload

  NAIVE (duplicates cause double emails):
  ────────────────────────────────────────
  receive message (orderId: ORD-123)
  send email → done
  receive same message again (SQS duplicate)
  send email again → PROBLEM (customer gets 2 emails)

  WITH IDEMPOTENCY KEY (safe):
  ────────────────────────────
  receive message (orderId: ORD-123)
  check Redis: SETNX "email-sent:ORD-123" "1" TTL=24h
  → Redis returns 1 (key was new) → process: send email, mark done
  Redis: "email-sent:ORD-123" = "1" (for 24 hours)

  receive same message again (SQS duplicate)
  check Redis: SETNX "email-sent:ORD-123" "1" TTL=24h
  → Redis returns 0 (key already exists) → SKIP, already processed
  delete from SQS queue → done

  NO DUPLICATE EMAIL
```

```java
@Service
public class EmailNotificationService {

    private final RedisTemplate<String, String> redis;

    @SqsListener("${sqs.order-email-queue-url}")
    public void handleOrderPlaced(OrderPlacedEvent event) {
        String idempotencyKey = "email-sent:" + event.getOrderId();

        // SETNX: set if not exists, returns true if key was NEW
        Boolean isNew = redis.opsForValue()
            .setIfAbsent(idempotencyKey, "1", Duration.ofHours(24));

        if (Boolean.FALSE.equals(isNew)) {
            log.info("Email already sent for order {}. Skipping.", event.getOrderId());
            return;  // SQS will delete message — no reprocessing
        }

        // First time processing this orderId
        try {
            emailProvider.send(buildEmail(event));
        } catch (Exception e) {
            // Remove idempotency key so next retry can try again
            redis.delete(idempotencyKey);
            throw e;
        }
    }
}
```

### PART 5 — When They Ask: "Standard SQS vs FIFO SQS — which do you use?"

> **You say:**
>
> "Standard SQS for notifications — email, SMS, analytics. Order doesn't matter
> and throughput is more important. Standard SQS can do 3000 messages/second
> per queue, FIFO is limited to 300/second.
>
> FIFO SQS for order state transitions — if an order goes from PLACED → CONFIRMED →
> PREPARING → DELIVERED, those events must be processed in order. Standard SQS
> might deliver DELIVERED before PLACED — the restaurant UI shows a delivered order
> that was never confirmed. FIFO prevents that."

```
STANDARD vs FIFO SQS — When to Use Each
==========================================

  STANDARD SQS:
  ├── Throughput: unlimited (3000 msg/s with batching)
  ├── Delivery: at-least-once (rare duplicates possible)
  ├── Ordering: best-effort (not guaranteed)
  ├── Use for: email, SMS, analytics, logging, anything idempotent
  └── Our queues: order-email-queue, order-sms-queue, order-analytics-queue

  FIFO SQS:
  ├── Throughput: 300 msg/s (3000 with high throughput mode)
  ├── Delivery: exactly-once (deduplication built-in)
  ├── Ordering: guaranteed within message group
  ├── Use for: order state machine, payment events, inventory updates
  └── Our queues: order-state-queue.fifo, payment-events-queue.fifo

  FIFO EXAMPLE — Order State Machine:
  ┌──────────────────────────────────────────────────────────┐
  │  MessageGroupId: ORD-123  (all events for same order)    │
  │                                                          │
  │  Message 1: PLACED     ─────────────────────────────┐   │
  │  Message 2: CONFIRMED  ─ processed in this order ──┤   │
  │  Message 3: PREPARING  ─────────────────────────────┤   │
  │  Message 4: DELIVERED  ─────────────────────────────┘   │
  │                                                          │
  │  MessageGroupId: ORD-456 (different order, parallel)     │
  │  Can be processed concurrently with ORD-123              │
  └──────────────────────────────────────────────────────────┘
```

### PART 6 — When They Ask: "How do you handle slow consumers or backpressure?"

> **You say:**
>
> "SQS handles backpressure naturally — messages queue up and consumers process
> at their own rate. The analytics queue might have 10,000 messages waiting;
> that's fine, they'll process over the next few minutes.
>
> The risk is when the queue grows unbounded. We set a CloudWatch alarm on
> queue depth — if analytics-queue has more than 1,000 messages, that means
> processing is slower than publishing. We auto-scale the Analytics Service
> based on SQS depth."

```
SQS CONSUMER SCALING STRATEGY
================================

  CloudWatch Metric: ApproximateNumberOfMessagesVisible
  Queue: order-analytics-queue

  ECS Service Auto Scaling Policy:
  ├── Scale-out: queue depth > 1000 → add 2 tasks
  ├── Scale-in:  queue depth < 100  → remove 1 task
  └── Min tasks: 1, Max tasks: 10

  AppAutoScaling:
  TargetTrackingScalingPolicy:
    TargetValue: 100  (messages per task)
    CustomizedMetricSpecification:
      MetricName: ApproximateNumberOfMessagesVisible
      Namespace: AWS/SQS
      QueueName: order-analytics-queue
    ScaleOutCooldown: 60s
    ScaleInCooldown: 300s

  RESULT:
  Peak load:  10,000 msgs → 10 analytics tasks, clears in ~2 min
  Normal load: 100 msgs   → 1 analytics task, sufficient
  Zero load:               → 1 task (minimum, ready for next burst)
```

### CLOSING — Strong Finish

> **You say:**
>
> "The SNS + SQS fan-out pattern gives Order Service complete decoupling from
> downstream consumers. If SMS Service is down for maintenance, messages queue
> in SQS for up to 4 days — when it comes back online, it processes the backlog
> automatically. No event is lost, no alert fires during planned maintenance.
>
> Three design decisions I always enforce: DLQ on every queue before going live,
> CloudWatch alarm on DLQ depth, and idempotency keys on consumers that have
> real-world side effects like payments or emails. These three things catch 90%
> of async messaging failures before they become incidents."

## QUICK REFERENCE

| Topic | What to say |
|---|---|
| SNS purpose | Fan-out: one publish → multiple SQS queues simultaneously |
| SQS purpose | Buffer + retry: consumers process at own pace, retry on failure |
| DLQ trigger | After N failed retries (max receive count), message moves to DLQ |
| Visibility timeout | How long a message is hidden while being processed — set > processing time |
| Standard SQS | High throughput, best-effort ordering, at-least-once delivery |
| FIFO SQS | 300/s, exactly-once, ordered within MessageGroupId |
| Idempotency | Redis SETNX on unique ID before processing — skip if already done |
| Consumer scaling | ECS Auto Scaling based on SQS ApproximateNumberOfMessagesVisible |
| Message retention | 4 days (default) — consumer has 4 days to process before message expires |

## ONE-LINER ANSWERS

**"How does SNS differ from SQS?"**
> "SNS is pub/sub — publish once, deliver to multiple subscribers simultaneously.
> SQS is a queue — messages wait until a consumer polls and processes them.
> In fan-out, SNS delivers to multiple SQS queues — combining both."

**"What happens if a consumer is down when SNS publishes?"**
> "Messages queue in SQS. SQS retains them for up to 4 days.
> When the consumer recovers, it processes the backlog automatically.
> SNS direct invocation (no SQS) would lose the event if the consumer is down —
> that's why you always put SQS between SNS and your service."

**"How do you handle a message that keeps failing?"**
> "After N retries (configurable), SQS moves it to the DLQ. CloudWatch alarm fires.
> Engineer investigates: fix the bug, redeploy, then replay messages from DLQ
> using the AWS console or CLI. Message is never lost."

**"Why not just use Kafka for all async messaging?"**
> "Kafka is better for high-throughput streaming and event sourcing. SQS+SNS
> is better for simple notification fan-out — fully managed, no brokers to operate,
> native AWS IAM auth, and DLQ is built-in. For Swiggy's order notifications,
> SQS fan-out is simpler and cheaper than running MSK for this use case."

## FAILURE SCENARIOS

| Scenario | What Happens |
|---|---|
| Email provider down for 1 hour | Messages retry up to 3 times, then go to DLQ. DLQ alarm fires. After email provider recovers, replay from DLQ — all emails sent eventually |
| SQS consumer crashes mid-processing | Visibility timeout expires → message becomes visible again → retried by next consumer instance |
| SNS publish fails (rare) | Order Service should use Outbox pattern for reliability — see file 7 |
| DLQ grows with 1000 messages | Indicates systemic failure — email provider down for hours. Fix provider, replay in batches |
| Consumer processes too slowly | Queue depth rises → ECS Auto Scaling adds tasks → backlog clears |
| Duplicate SQS message delivered | Idempotency key in Redis prevents duplicate email/payment — skip already-processed messages |
| SQS message retention expires (4 days) | Message deleted permanently — for critical events (payments), use longer retention (14 days max) or Kafka for replay capability |
