## Part 1: The Problem We're Solving

**Me:** "So here's the situation. You're building a SaaS platform - let's say it's an order fulfillment system, payment processing platform, or document verification service. You have hundreds or thousands of customer companies using your product."

"Each customer has their own systems, and they need to integrate with yours. They send you requests - 'process this order', 'verify this document', 'charge this payment' - and they need to know when it's done."

### The Core Challenge

```text
Simple view:
Customer → Your API → Process → Response

Reality:
Customer A → \
Customer B →  → Your API → Long-running work → How do they get results?
Customer C → /
  (100s of customers, some are spiky, some fail, networks drop)
```

**Me:** "The tricky parts are:"

1. **The work takes time** - Maybe 30 seconds, maybe 5 minutes. Can't block HTTP that long.
2. **Networks fail** - Customer sends request, network dies, they retry. Now you might process twice.
3. **Multi-tenant fairness** - Customer A shouldn't kill the system for everyone else.
4. **Reliable delivery** - Once you accept a request, you can't lose it.
5. **Getting results back** - How does the customer know when you're done?

```text
The Pattern We Use:

Step 1: Quick Acceptance
Customer → API → "202 Accepted, here's your ID" (returns in 200ms)
                      |
                      v
                [Work queued safely]

Step 2: Background Processing
Queue → Worker → Do actual work → Mark complete

Step 3: Notify Customer
Your System → Webhook → Customer's callback URL
            OR
Customer → Poll API → Get status
```

**Me:** "Let me explain the flow in plain English."

### Request Flow (Happy Path)

```text
Timeline of a single request:

t=0ms:   Customer POSTs to /v1/requests
         Headers: { Idempotency-Key: "abc-123", X-Tenant-Id: "customer-a" }

t=50ms:  API Gateway validates tenant auth, rate limit OK
         
t=100ms: Spring Boot receives request
         → Check idempotency table (is abc-123 already processed?)
         → Validate JSON schema
         → Check tenant has permission

t=150ms: Write to database (single @Transactional block):
         → INSERT requests row    (status='ACCEPTED', payload, hash)
         → INSERT idempotency_key  (key, request_id, hash, 24h TTL)
         → INSERT outbox_event    (type='REQUEST_CREATED')
         → INSERT audit_log row   (action='REQUEST_ACCEPTED')
         All 4 inserts commit together — or all rollback

t=180ms: Publish to Kafka/SQS:
         Topic: "requests.created"
         Message: { request_id: 'req-789', tenant_id: 'customer-a' }

t=200ms: Return to customer:
         HTTP 202 Accepted
         { 
           "request_id": "req-789",
           "status": "ACCEPTED",
           "message": "Processing started",
           "poll_url": "/v1/requests/req-789"
         }

------- Customer is now unblocked, their API call returned -------

t=2s:    Worker picks up message from queue
         → Load request from database
         → Execute business logic (call payment API, verify document, etc.)
         → This might take 30 seconds

t=30s:   Work completes successfully
         → UPDATE requests: status='COMPLETED', completed_at=now()
         → INSERT outbox_events row (triggers webhook dispatch)
         
t=31s:   Outbox publisher sees new event
         → Dispatch webhook to customer
         POST https://customer-a.com/webhooks/provider-events
         Body: { request_id: 'req-789', status: 'COMPLETED', result: {...} }

t=32s:   Customer webhook returns 200 OK
         → Mark webhook attempt as DELIVERED

Done! Customer has their result.
```

**Me:** "Now, that's the happy path. But what makes this production-ready is handling all the failure cases."

**Me:** "The IntegrationService is where all the business logic lives. I think of it as a strict 7-step pipeline. The ordering matters — if I swap steps 1 and 3, I burn a rate-limit token on a request we're about to detect as a duplicate. Every ordering decision is intentional."

```text
┌──────────────────────────────────────────────────────────────────────┐
│  IntegrationService.acceptRequest() — THE 7-STEP PIPELINE           │
│  (annotated @Transactional — all DB writes commit as one unit)      │
├──────────────────────────────────────────────────────────────────────┤
│                                                                       │
│  STEP 1: CHECK IDEMPOTENCY  ← exit early before spending anything   │
│  ──────────────────────────                                          │
│  Look up (tenant_id, idempotency_key) in idempotency_keys table     │
│                                                                       │
│  Found + same payload hash → return cached response immediately     │
│  Found + different hash    → throw 409 Conflict                     │
│  Not found                 → continue to step 2                     │
│                                                                       │
│  STEP 2: TENANT AUTHORIZATION                                        │
│  ────────────────────────────                                        │
│  Is tenant ACTIVE? Does their plan allow this resource type?        │
│  Throws 403 Forbidden if not.                                       │
│                                                                       │
│  STEP 3: RATE LIMIT CHECK                                            │
│  ──────────────────────────                                          │
│  Token bucket per tenant in Redis.                                  │
│  Throws 429 Too Many Requests if exhausted.                         │
│                                                                       │
│  STEP 4: PAYLOAD SCHEMA VALIDATION                                   │
│  ─────────────────────────────────                                   │
│  Does payload match the agreed API contract for this schema version?│
│  Throws 400 with field-level error detail if not.                  │
│                                                                       │
│  STEP 5: FOUR DATABASE INSERTS IN ONE TRANSACTION                   │
│  ─────────────────────────────────────────────────                   │
│  ① INSERT INTO requests    (status='ACCEPTED', payload, hash)       │
│  ② INSERT INTO idempotency_keys  (key, request_id, hash, expires)   │
│  ③ INSERT INTO audit_log   (action='REQUEST_ACCEPTED')              │
│  ④ INSERT INTO outbox_events     (type='REQUEST_CREATED')  ← KEY    │
│                                                                       │
│  All 4 commit atomically. If Kafka is down right now, ④ ensures    │
│  the event will publish when it recovers. Nothing is lost.         │
│                                                                       │
│  STEP 6: (covered by ③ above — audit inside same transaction)       │
│                                                                       │
│  STEP 7: RETURN 202 ACCEPTED                                         │
│  ────────────────────────────                                        │
│  { request_id, status: 'ACCEPTED', poll_url }                       │
│  Customer is unblocked. Background processing starts via outbox.    │
│                                                                       │
└──────────────────────────────────────────────────────────────────────┘
```

**Me:** "The worker is a completely separate process — different pod, different JVM, consuming from Kafka. My most important rule about workers: never trust the Kafka message payload for business data. The message is a signal, not the source of truth. Here's the full contract:"

```text
┌──────────────────────────────────────────────────────────────────────┐
│  WORKER (RequestWorker) — FOUR NON-NEGOTIABLE RULES                  │
├──────────────────────────────────────────────────────────────────────┤
│                                                                       │
│  RULE 1: Kafka message = signal only, not data                      │
│  ─────────────────────────────────────────────                       │
│  Message contains only: { request_id, tenant_id }                   │
│  Worker loads the full request from PostgreSQL.                     │
│  Why? Kafka is not the source of truth. DB is. If the payload in    │
│  Kafka is from a stale retry, you'd process the wrong version.      │
│                                                                       │
│  RULE 2: Claim with optimistic lock before starting                 │
│  ─────────────────────────────────────────────────                   │
│  UPDATE requests SET status='PROCESSING' WHERE status='QUEUED'      │
│  If rowcount=0 → already claimed by another worker → skip           │
│  This is your second duplicate-execution guard.                     │
│                                                                       │
│  RULE 3: Retryable vs Non-Retryable failures are different          │
│  ────────────────────────────────────────────────────               │
│                                                                       │
│  Retryable (throw → Kafka redelivers with backoff):                 │
│    Network timeouts, 503 Service Unavailable, DB connection lost    │
│                                                                       │
│  Non-Retryable (mark FAILED, ACK message, do NOT redeliver):        │
│    400 Bad Request, 403 Forbidden, 404 Not Found from downstream    │
│    Retrying a bad request will keep failing — move on.              │
│                                                                       │
│  RULE 4: Kafka ACK ordering is critical                             │
│  ──────────────────────────────────────                              │
│                                                                       │
│  CORRECT:    update DB → commit → ACK Kafka message                 │
│  DANGEROUS:  ACK Kafka → update DB  (pod dies = message lost)       │
│                                                                       │
│  At-least-once delivery is safe because WorkflowOrchestrator        │
│  blocks the illegal PROCESSING → PROCESSING transition.             │
│                                                                       │
└──────────────────────────────────────────────────────────────────────┘
```

**Me:** "The IdempotencyService looks simple but it handles a subtle race condition that most implementations get wrong. Two threads can both check 'has this key been seen?' simultaneously, both get 'no', and both try to INSERT. Here's why that's fine and how the database absorbs the race:"

```text
┌──────────────────────────────────────────────────────────────────────┐
│  IDEMPOTENCY SERVICE — THE RACE CONDITION AND WHY IT'S SAFE         │
├──────────────────────────────────────────────────────────────────────┤
│                                                                       │
│  findByKey(tenantId, idempotencyKey):                               │
│  ─────────────────────────────────────                               │
│  SELECT from idempotency_keys WHERE (tenant_id, key)                │
│                                                                       │
│  Returns null   → first time this key has been seen                 │
│  Returns record → replay scenario:                                  │
│    Same payload hash   → return cached response (safe replay)       │
│    Different hash      → throw 409 Conflict (key misuse)            │
│                                                                       │
│  store(tenantId, key, requestId, payloadHash):                      │
│  ──────────────────────────────────────────────                      │
│  INSERT INTO idempotency_keys (expires_at = now() + 24h)            │
│                                                                       │
│  THE RACE — and why the DB constraint wins:                         │
│  ──────────────────────────────────────────                          │
│                                                                       │
│  Thread 1:  SELECT → not found → INSERT ← succeeds                 │
│  Thread 2:  SELECT → not found → INSERT ← DuplicateKeyException    │
│                                   PRIMARY KEY constraint fires !!   │
│                                                                       │
│  Thread 2 catches DuplicateKeyException and re-fetches the record. │
│  Both threads now have the same request_id.                         │
│  No distributed locks needed. The DB is the arbiter.               │
│                                                                       │
│  EXPIRY:                                                             │
│  24-hour TTL on keys. Nightly cleanup job deletes expired rows.     │
│  After 24h, the same idempotency key generates a new request_id.   │
│                                                                       │
└──────────────────────────────────────────────────────────────────────┘
```

**Me:** "The WorkflowOrchestrator is a simple class but it does something important: it makes every status transition go through a single auditable gate. Without it, I've seen status updates scattered across the codebase with no consistency."

```text
┌──────────────────────────────────────────────────────────────────────┐
│  WORKFLOWORCHESTRATOR — ALLOWED TRANSITIONS AND WHY                 │
├──────────────────────────────────────────────────────────────────────┤
│                                                                       │
│  ACCEPTED    →  PROCESSING  (worker picks it up)                    │
│  ACCEPTED    →  CANCELLED   (user cancels before processing)        │
│  PROCESSING  →  COMPLETED   (success path)                          │
│  PROCESSING  →  FAILED      (permanent failure)                     │
│  PROCESSING  →  UNKNOWN_PENDING_RECON  (timeout, unclear outcome)   │
│  COMPLETED   →  (nothing — terminal)                                │
│  FAILED      →  (nothing — terminal)                                │
│                                                                       │
│  transition(request, newStatus):                                     │
│  ─────────────────────────────────                                     │
│  1. Check ALLOWED_TRANSITIONS[currentStatus].contains(newStatus)    │
│  2. If not allowed → throw IllegalStateTransitionException          │
│     (stack trace shows exactly what called it — instant debug)     │
│  3. If allowed   → UPDATE status, write to audit_log               │
│                                                                       │
│  WITHOUT THIS CLASS (what I've seen in codebases):                  │
│                                                                       │
│  workerService:    request.setStatus(COMPLETED)  ← skips audit     │
│  reconciler:       request.setStatus(COMPLETED)  ← double-counts   │
│  webhookService:   request.setStatus(FAILED)     ← wrong caller    │
│                                                                       │
│  With the orchestrator, every transition is logged in one place.    │
│  Illegal transitions throw immediately with a clear stack trace.    │
└──────────────────────────────────────────────────────────────────────┘
```

**Me:** "The WebhookDispatcher has one job: get the result to the customer reliably. I design this defensively because I've been on-call when webhooks fail silently. Every attempt is recorded, every retry is tracked, and there is always a fallback."

```text
┌──────────────────────────────────────────────────────────────────────┐
│  WEBHOOKDISPATCHER — DELIVERY ALGORITHM                              │
├──────────────────────────────────────────────────────────────────────┤
│                                                                       │
│  1. LOAD TENANT WEBHOOK CONFIG (from Redis cache → DB fallback)     │
│     webhook_url and webhook_secret for this tenant_id               │
│     Cached in Redis (TTL 5 min) — avoids DB hit per dispatch        │
│                                                                       │
│  2. BUILD SIGNED PAYLOAD                                             │
│     Body: { request_id, status, result, event_id, timestamp }      │
│     X-Signature: HMAC-SHA256(body, webhook_secret)                  │
│     Why signature? Customer verifies it's really us, not a         │
│     replay attack from a third party. OWASP A07 compliance.        │
│                                                                       │
│  3. HTTP POST WITH HARD TIMEOUT (10 seconds, never more)            │
│     2xx response  → DELIVERED, done                                 │
│     4xx response  → PERMANENT FAIL, don't retry (their bug)         │
│     5xx / timeout → TRANSIENT FAIL, retry with backoff              │
│                                                                       │
│  4. RETRY SCHEDULE                                                   │
│     Attempt 1: immediate                                            │
│     Attempt 2: +1 second                                            │
│     Attempt 3: +5 seconds                                           │
│     Attempt 4: +30 seconds                                          │
│     Attempt 5: +5 minutes                                           │
│     After 5 failures → DEAD LETTER QUEUE + PagerDuty alert          │
│                                                                       │
│  5. CUSTOMER ALWAYS HAS FALLBACK                                    │
│     GET /v1/requests/{id} returns current status at any time.      │
│     Customers who can't receive webhooks can poll instead.          │
│                                                                       │
│  6. EVERY ATTEMPT RECORDED                                          │
│     INSERT INTO webhook_attempts (attempt_no, status,               │
│                                    http_status_code, error_message)  │
│     When customer says 'I never got it' — show them the log.       │
│                                                                       │
└──────────────────────────────────────────────────────────────────────┘
```

## Part 4: Database Schema and Indexing Strategy

**Me:** "Let me show you the database design. This is critical for both performance and correctness."

### Database Schema

**Me:** "Let me draw the table structures instead. I find this more useful in an interview than DDL — you can see at a glance what each column is for and why it exists."

```text
┌────────────────────────────────────────────────────────────────────────────┐
│  TABLE: requests                (main lifecycle, ~10M rows/month)    │
├────────────────────────────────────────────────────────────────────────────┤
│  tenant_id       PK component — every row is scoped to a tenant      │
│  request_id      PK component — UUID per request                     │
│  idempotency_key UNIQUE per tenant — DB constraint prevents dupes    │
│  correlation_id  NULLABLE — customer’s own reference ID              │
│  status          CHECK: ACCEPTED/PROCESSING/COMPLETED/FAILED          │
│  payload         JSONB — the actual request data                      │
│  payload_hash    SHA-256 of payload — used for idempotency replay     │
│  result          JSONB NULLABLE — populated when COMPLETED            │
│  error_code      NULLABLE — populated when FAILED                     │
│  created_at      DEFAULT now()                                        │
│  updated_at      Updated on every status transition                   │
│  completed_at    NULLABLE — when work actually finished               │
│                                                                        │
│  INDEXES:                                                              │
│  ON (tenant_id, status, created_at DESC)                              │
│    → "Show me all failed requests for tenant X in the last hour"      │
│                                                                        │
│  ON (status, updated_at) WHERE status IN ('ACCEPTED','PROCESSING')    │
│    → Partial index: only the ~1% of rows that are still active        │
│    → Reconciliation worker uses this to find stuck requests           │
└────────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────────┐
│  TABLE: idempotency_keys        (fast duplicate lookup, separate)     │
├────────────────────────────────────────────────────────────────────────────┤
│  (tenant_id, idempotency_key)  PK + UNIQUE — DB enforces no dupes    │
│  request_id                    FK → requests (which request was made)│
│  payload_hash                  For replay verification               │
│  expires_at                    now() + 24h — nightly cleanup target  │
│                                                                        │
│  INDEX ON (expires_at): DELETE WHERE expires_at < NOW() each night   │
└────────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────────┐
│  TABLE: outbox_events           (reliable event publishing)           │
├────────────────────────────────────────────────────────────────────────────┤
│  event_id, tenant_id, request_id, event_type, payload                │
│  published_at  NULLABLE — NULL means not yet sent to Kafka           │
│                                                                        │
│  INDEX ON (created_at) WHERE published_at IS NULL                    │
│    → Partial index: usually <100 rows in normal operation            │
│    → Outbox publisher queries this every 5 seconds                   │
└────────────────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────────────────┐
│  TABLE: webhook_events + webhook_attempts  (delivery evidence trail)  │
├────────────────────────────────────────────────────────────────────────────┤
│  webhook_events:                                                       │
│    event_id, tenant_id, request_id, payload, signature               │
│    delivered_at  NULLABLE — NULL means not yet delivered             │
│                                                                        │
│  webhook_attempts (child of webhook_events):                          │
│    attempt_no       INT — which retry this was (1, 2, 3, 4, 5)       │
│    status           DELIVERED / FAILED / TIMEOUT                      │
│    http_status_code INT — actual HTTP code received                   │
│    error_message    TEXT — what went wrong                            │
│                                                                        │
│  This is your evidence when a customer says 'I never got it.'        │
```

**Me:** "The reconciliation worker runs as a Kubernetes CronJob every 5 minutes. It's the safety net for requests that landed in UNKNOWN_PENDING_RECON. Let me walk through exactly what it does:"

```text

│  RECONCILIATION WORKER — EVERY 5 MINUTES                             │
├──────────────────────────────────────────────────────────────────────┤
│                                                                       │

│                                                                       │
│  3. REPAIR STATE                                                     │
│                                                                       │

│     External says FAILED:                                            │

│                                                                       │
```

### Failure Scenario 2: Duplicate Events

```text
Problem:
Worker processes message → Completes successfully → Crashes before ACKing
Kafka redelivers message → Worker processes again → DUPLICATE!

Solution - Deduplication Service:

┌──────────────────────────────────────────────────────┐
│  Message arrives from Kafka                           │
│  Message ID: "msg-12345"                              │
└─────────────────────┬────────────────────────────────┘
                      │
                      v
         ┌────────────────────────────┐
         │  Check: Have we seen       │
         │  "msg-12345" before?       │
         └────────┬───────────┬───────┘
                  │           │
            YES   │           │   NO
                  v           v
          ┌─────────┐    ┌─────────────────┐
          │ Ignore  │    │ Mark as seen    │
          │ + ACK   │    │ Process request │
          └─────────┘    │ ACK message     │
                         └─────────────────┘
```

**Me:** "Deduplication at the Kafka consumer level is the second guard after idempotency keys. The scenario it covers: worker processes a message, updates the DB successfully, then the pod dies before committing the Kafka offset. Kafka redelivers. Without dedup we process it twice. Here's how Redis SETNX prevents that atomically:"

```text
┌──────────────────────────────────────────────────────────────────────┐
│  DEDUPSERVICE — ATOMIC REDIS SETNX PATTERN                          │
├──────────────────────────────────────────────────────────────────────┤
│                                                                       │
│  isDuplicate(messageId):                                             │
│  ──────────────────────────                                          │
│  Redis SETNX "dedup:msg:{messageId}" = "1" (TTL 24h)               │
│                                                                       │
│  SETNX succeeded (key was absent) → FIRST TIME → process it         │
│  SETNX failed (key existed)       → DUPLICATE  → log + discard      │
│                                                                       │
│  WHY SETNX?                                                          │
│  It's atomic — two concurrent threads racing on the same message ID  │
│  can only have one succeed. No distributed locks needed.            │
│                                                                       │
│  WHY 24H TTL?                                                        │
│  Kafka redelivery windows are typically seconds. 24h gives ample     │
│  protection without Redis memory growing indefinitely.              │
│                                                                       │
│  Kafka consumer flow:                                               │
│    Message arrives with kafka_message_id header                     │
│    dedupService.isDuplicate(messageId)?                             │
│      YES → log "duplicate detected", return (ACK message)           │
│      NO  → proceed to process the request                           │
│                                                                       │
│  COMBINED WITH WORKFLOWORCHESTRATOR:                                 │
│  Even if dedup misses a duplicate (Redis restart), the orchestrator │
│  blocks ACCEPTED → PROCESSING twice. Defence in depth.              │
└──────────────────────────────────────────────────────────────────────┘
```

### Failure Scenario 5: Database Write Succeeds, Event Publish Fails

```text
Problem:
BEGIN TRANSACTION
  INSERT INTO requests ...
COMMIT → Success ✓
  
Publish to Kafka → Network error ✗

Result: Request exists in DB but worker never processes it!

Solution - Transactional Outbox Pattern:

┌──────────────────────────────────────────────────────┐
│  Atomic Write (Same Transaction)                      │
│                                                       │
│  BEGIN TRANSACTION                                    │
│    INSERT INTO requests (...)                        │
│    INSERT INTO outbox_events (...)  ← Key!           │
│  COMMIT                                               │
│                                                       │
│  Either both succeed or both fail                    │
└─────────────────────┬────────────────────────────────┘
                      │
                      v
┌──────────────────────────────────────────────────────┐
│  Separate Outbox Publisher (runs every 5 seconds)    │
│                                                       │
│  SELECT * FROM outbox_events                         │
│  WHERE published_at IS NULL                          │
│  LIMIT 100                                           │
│                                                       │
│  For each event:                                     │
│    Publish to Kafka                                  │
│    UPDATE outbox_events                              │
│    SET published_at = NOW()                          │
│                                                       │
│  → Eventually consistent, but guaranteed delivery    │
└──────────────────────────────────────────────────────┘
```

**Me:** "The outbox pattern solves a classic distributed systems problem: how do you atomically write to a database AND publish to Kafka when they're different systems that can't share a transaction? Let me draw the exact failure scenario it prevents, and then how the outbox fixes it:"

```text
┌──────────────────────────────────────────────────────────────────────┐
│  TRANSACTIONAL OUTBOX PATTERN — FULL EXPLANATION                     │
├──────────────────────────────────────────────────────────────────────┤
│                                                                       │
│  THE PROBLEM (what happens WITHOUT outbox):                         │
│  ───────────────────────────────────────────────               │
│  BEGIN TRANSACTION                                                   │
│    INSERT INTO requests (status='ACCEPTED')  ← succeeds             │
│  COMMIT                                                              │
│  kafkaTemplate.send(...)  ← network error!                          │
│                                                                       │
│  Result: Request exists in DB, Kafka message never sent.            │
│  Worker never picks it up. Request stays ACCEPTED forever.          │
│                                                                       │
│  THE FIX — Outbox Pattern:                                          │
│  ───────────────────────────────────────                               │
│  BEGIN TRANSACTION                                                   │
│    INSERT INTO requests      (status='ACCEPTED')  ← succeeds        │
│    INSERT INTO outbox_events (type='REQUEST_CREATED')  ← KEY        │
│  COMMIT   ← BOTH or NEITHER, atomically                             │
│                                                                       │
│  Now the outbox_event is durable in the DB. Can't be lost.          │
│                                                                       │
│  OUTBOX PUBLISHER (separate @Scheduled job, every 5 seconds):       │
│  ──────────────────────────────────────────────────────      │
│                                                                       │
│  SELECT * FROM outbox_events WHERE published_at IS NULL LIMIT 100   │
│                                                                       │
│  For each event:                                                     │
│    ① kafkaTemplate.send("requests.created", event.payload)           │
│    ② UPDATE outbox_events SET published_at=now() WHERE id=?         │
│                                                                       │
│  If ① fails (Kafka down):                                           │
│    Log warning, skip, retry on next 5-second tick.                  │
│    Events accumulate in outbox_events. When Kafka recovers,         │
│    all pending events publish automatically.                        │
│                                                                       │
│  If ① succeeds but ② fails (DB blip):                               │
│    Next tick re-fetches the same event (published_at still NULL).   │
│    Kafka gets a duplicate. Worker's DedupService catches it. Safe.  │
│                                                                       │
└──────────────────────────────────────────────────────────────────────┘
```

### 11.1 Data Isolation Strategy — The Most Commonly Asked Question

**Interviewer:** "You mentioned multi-tenant. How do you actually isolate one tenant's data from another?"

**Me:** "This is the foundational architectural decision for any multi-tenant system, and there's no single right answer — it's a trade-off between isolation, cost, and operational complexity. Let me walk through all four options and tell you which I'd choose and why."

```
┌──────────────────────────────────────────────────────────────────────────┐
│  DATA ISOLATION STRATEGIES — TRADE-OFF MATRIX                            │
├───────────────────┬───────────────┬──────────────┬────────────┬──────────┤
│ Strategy          │ Isolation     │ Cost         │ Ops burden │ Best for │
├───────────────────┼───────────────┼──────────────┼────────────┼──────────┤
│ A: Shared schema  │ Lowest        │ Lowest       │ Low        │ High     │
│    tenant_id col  │ SQL bug leaks │ 1 DB cluster │            │ tenant   │
│                   │ everything    │              │            │ count    │
├───────────────────┼───────────────┼──────────────┼────────────┼──────────┤
│ B: Schema-per-    │ Medium        │ Medium       │ Medium     │ 10s-100s │
│    tenant         │ Connection    │ 1 DB, N      │ migrations │ of       │
│    search_path    │ misconfigured │ schemas      │ × N        │ tenants  │
│                   │ leaks data    │              │ schemas    │          │
├───────────────────┼───────────────┼──────────────┼────────────┼──────────┤
│ C: DB-per-tenant  │ Highest       │ Highest      │ High       │ <10      │
│                   │ Full kernel   │ N DBs        │ migrations │ enterprise│
│                   │ isolation     │              │ × N DBs    │ tenants  │
├───────────────────┼───────────────┼──────────────┼────────────┼──────────┤
│ D: Hybrid (tiers) │ Configurable  │ Balanced     │ Medium     │ SaaS     │
│    free=shared    │ Free tenants  │ 1 shared +   │            │ with     │
│    paid=dedicated │ share risk    │ N enterprise │            │ tiers    │
└───────────────────┴───────────────┴──────────────┴────────────┴──────────┘
```

**Me:** "For the system I described, I'd use **Option A (shared schema) with Option D for enterprise tiers**. Here's my reasoning:

We might have thousands of tenants. A DB per tenant at that scale means thousands of connection pools, thousands of migration runs, thousands of backup schedules. That's not operationally viable.

Shared schema with `tenant_id` on every table is simple and scales. But it has one critical weakness — a SQL bug that omits the `WHERE tenant_id=?` filter leaks everyone's data. So I harden it with two layers:"

```
│    USING (tenant_id = current_setting('app.tenant_id'));              │
│                                                                       │
│  SET app.tenant_id = 'customer-a';                                   │
│  SELECT * FROM requests;  -- only sees customer-a rows               │
│                           -- even if WHERE clause is missing !!      │
│                                                                       │
│  Layer 2: Application-Level Guard in Spring Boot                     │
│  ──────────────────────────────────────────────                      │
│                                                                       │
│  @Aspect                                                              │
│  public class TenantIsolationAspect {                                │

│    public void assertTenantContext() {                               │
│      if (TenantContext.get() == null)                                │
│        throw new MissingTenantContextException();                    │

│  }                                                                    │
│                                                                       │
│  Layer 3: Integration Tests That Prove Isolation                     │
│  ────────────────────────────────────────────────                    │
│                                                                       │
│  @Test                                                                │
```

### 11.2 Zero-Downtime Schema Migrations at Scale

**Interviewer:** "How do you deploy database changes without downtime when you have 10 million rows shared across thousands of tenants?"

**Me:** "This is where most teams get burned. Let me show you the wrong way first, and then the right way.

The wrong way is what developers do instinctively:"

```
┌──────────────────────────────────────────────────────────────────────┐
│  NAIVE MIGRATION (causes downtime at scale)                          │
│                                                                       │
│  ALTER TABLE requests ADD COLUMN priority INT NOT NULL DEFAULT 5;    │
│                                                                       │
│  On 10M rows → PostgreSQL rewrites the entire table                  │
│  Duration: minutes                                                    │
│  Impact: Table locked for reads AND writes during rewrite            │
│  Result: All API calls fail with lock timeout                        │
└──────────────────────────────────────────────────────────────────────┘
```

**Me:** "The correct approach is the **expand-contract pattern**. You never change the schema in one step — you expand first (add new column, backwards compatible), deploy the new code that uses both old and new, then contract (remove old column once all code is off it)."

```
┌──────────────────────────────────────────────────────────────────────┐
│  EXPAND-CONTRACT PATTERN — Zero Downtime                             │
├──────────────────────────────────────────────────────────────────────┤
│                                                                       │
│  PHASE 1: EXPAND (backwards compatible)                              │
│  ─────────────────────────────────────                               │
│                                                                       │
│  ALTER TABLE requests                                                │
│    ADD COLUMN priority_v2 INT;  -- nullable, no default              │
│                                                                       │
│  → Safe: no table rewrite, no lock                                   │
│  → Old code still works (ignores the new column)                     │
│                                                                       │
│  PHASE 2: DEPLOY CODE that writes to BOTH columns                   │
│  ──────────────────────────────────────────────                      │
│                                                                       │
│  INSERT INTO requests (priority, priority_v2, ...)                  │
│  VALUES (5, 5, ...)  -- write to both during migration window        │
│                                                                       │
│  PHASE 3: BACKFILL old rows                                          │
│  ─────────────────────────                                           │
│                                                                       │
│  UPDATE requests                                                     │
│  SET priority_v2 = priority                                          │
│  WHERE priority_v2 IS NULL                                           │
│  LIMIT 10000;  -- run in batches, never lock full table              │
│                                                                       │
│  (run as background job, 10K rows at a time, sleep between batches) │
│                                                                       │
│  PHASE 4: DEPLOY CODE that reads from priority_v2 only             │
│                                                                       │
│  PHASE 5: CONTRACT (remove old column)                               │
│  ─────────────────────────────────────                               │
│                                                                       │
│  ALTER TABLE requests DROP COLUMN priority;                          │
│  ALTER TABLE requests RENAME COLUMN priority_v2 TO priority;        │
│                                                                       │
│  → Total migration: 0 seconds of downtime                           │
│  → Each phase independently deployable and rollback-safe            │
│                                                                       │
└──────────────────────────────────────────────────────────────────────┘
```

**Me:** "In Spring Boot, I use **Flyway** with a strict naming convention: `V{version}__description.sql`. For high-risk migrations, I also use `pg_repack` which rewrites the table in the background without holding locks. The key principle is: if your migration can't run in under 1 second, it needs to be broken into phases."

### 11.3 Saga Pattern — Distributed Transactions Across Services

**Interviewer:** "What if processing a request involves multiple steps across different services — and one of them fails halfway through?"

**Me:** "This is the distributed transactions problem, and it comes up constantly in microservices. Let me give you a concrete example from our system:

Processing an order means:
1. Charge the customer's card (Payment Service)
2. Reserve the items (Inventory Service)
3. Notify the warehouse (Shipping Service)

If step 2 fails after step 1 already charged the card — we have a mess. The customer was charged for something they can't receive.

We can't use a database transaction across services — they're in different databases. The solution is the **Saga pattern**."

```
┌──────────────────────────────────────────────────────────────────────┐
│  SAGA PATTERN — Choreography vs Orchestration                        │
├──────────────────────────────────────────────────────────────────────┤
│                                                                       │
│  OPTION A: CHOREOGRAPHY (Event-Driven)                               │
│  ─────────────────────────────────────                               │
│                                                                       │
│  ┌─────────┐ charged  ┌───────────┐ reserved  ┌──────────┐          │
│  │ Payment │─────────►│ Inventory │──────────►│ Shipping │          │
│  │ Service │          │  Service  │           │  Service │          │
│  └─────────┘          └─────┬─────┘           └──────────┘          │
│                             │                                         │
│                     reserve FAILED                                    │
│                             │                                         │
│                             ▼                                         │
│                  ┌──────────────────────┐                            │
│                  │ Publish              │                            │
│                  │ "inventory.failed"   │                            │
│                  │ event                │                            │
│                  └──────────┬───────────┘                            │
│                             │                                         │
│                             ▼                                         │
│                  ┌──────────────────────┐                            │
│                  │ Payment Service      │                            │
│                  │ listens, issues      │                            │
│                  │ REFUND (compensate)  │                            │
│                  └──────────────────────┘                            │
│                                                                       │
│  Pro: No central coordinator, fully decoupled                        │
│  Con: Hard to follow, hard to debug, "saga" logic scattered          │
│                                                                       │
│  OPTION B: ORCHESTRATION (Recommended for complex flows)             │
│  ────────────────────────────────────────────────────                │
│                                                                       │
│  ┌───────────────────────────────────────────────────────────────┐  │
│  │  Order Saga Orchestrator  (in our IntegrationService)         │  │
│  │                                                               │  │
│  │  Step 1: chargeCard()     → SUCCESS → continue               │  │
│  │  Step 2: reserveInventory() → FAIL                           │  │
│  │                                                               │  │
│  │  Compensation sequence (in reverse):                         │  │
│  │  Step 1 rollback: refundCard()  → SUCCESS                    │  │
│  │                                                               │  │
│  │  Saga ends: FAILED (with clean state)                        │  │
│  └───────────────────────────────────────────────────────────────┘  │
│                                                                       │
│  Pro: Single place to read the entire workflow                       │
│  Con: Orchestrator becomes a bottleneck if not designed carefully    │
│                                                                       │
└──────────────────────────────────────────────────────────────────────┘
```

**Me:** "In practice I use a SagaBuilder that encodes this exactly. Each step is registered with a forward function AND a compensating function. The builder executes steps in order and runs compensations in reverse on failure. The critical discipline is that every compensating action must be idempotent — calling refundCard() twice must produce the same result as calling it once, because compensations can fail and be retried."

```text
┌──────────────────────────────────────────────────────────────────────┐
│  SAGA ORCHESTRATOR — HOW TO BUILD ONE                                │
├──────────────────────────────────────────────────────────────────────┤
│                                                                       │
│  SagaBuilder.create()                                               │
│    .step("charge-card",                                             │
│          forward:     paymentService.charge(order),                 │
│          compensate:  paymentService.refund(ctx.chargeId))          │
│    .step("reserve-inventory",                                       │
│          forward:     inventoryService.reserve(order),              │
│          compensate:  inventoryService.release(ctx.reservationId))  │
│    .step("notify-shipping",                                         │
│          forward:     shippingService.schedule(order),              │
│          compensate:  shippingService.cancel(ctx.shipmentId))       │
│    .build()                                                         │
│    .execute()                                                       │
│                                                                       │
│  ON FAILURE AT STEP 2 (reserve-inventory):                          │
│    Step 1 compensate runs: paymentService.refund(ctx.chargeId)      │
│    Saga ends: FAILED with clean state, no dangling charges          │
│                                                                       │
│  WHAT IF COMPENSATION ITSELF FAILS?                                 │
│  ──────────────────────────────────────────────                    │
│  Mark saga as COMPENSATION_FAILED in the database.                  │
│  Alert ops team immediately — do NOT swallow silently.              │
│  Manual remediation required (human calls bank, etc.)              │
│                                                                       │
│  SAGA STATE PERSISTED TO DATABASE:                                  │
│    saga_id, request_id, current_step, status                        │
│    context (JSONB) — stores results of each completed step          │
│    failure_step, started_at, completed_at                           │
│                                                                       │
│  If pod dies mid-saga: on restart, load saga state from DB,        │
│  determine phase (forward or compensation), resume from there.      │
└──────────────────────────────────────────────────────────────────────┘
```

**Me:** "The key insight is: in distributed systems, you don't get ACID transactions across service boundaries. You get eventual consistency through compensation. Every step that can succeed must have a compensating action that can undo it. Design your steps to be idempotent — calling refundCard() twice should be safe."

### 11.6 API Versioning Strategy

**Interviewer:** "Tenant A is still on v1 of your API. Tenant B just upgraded to v2 which has breaking changes. How do you manage this?"

**Me:** "API versioning is one of those topics where there's a right answer and five wrong answers. Let me walk you through how I think about it.

First: what constitutes a breaking change? Adding a field is not breaking. Removing a field is. Changing a field's type is. Changing behavior of an existing endpoint is. I document this distinction clearly in our API contract spec."

```

├──────────────────────────────────────────────────────────────────────┤
```

**Me:** "The critical discipline is: the shared service layer contains the business logic, and versioned controllers handle the translation between old and new API contracts. When v1 is finally sunset, I delete the v1 controller, nothing else changes."

### 11.7 Bulkhead Pattern — Thread Pool Isolation Per Tenant

**Interviewer:** "If Tenant A has a slow downstream dependency that's causing their requests to take 30 seconds, how do you prevent that from starving threads for Tenant B?"

**Me:** "This is exactly why you should never use a single shared thread pool in a multi-tenant system. The Bulkhead pattern — borrowed from naval engineering — means you partition resources so a flood in one compartment doesn't sink the ship."

```
┌──────────────────────────────────────────────────────────────────────┐
│  BULKHEAD PATTERN — Thread Pool Per Tenant Tier                      │
│                                                                       │
│  WITHOUT BULKHEAD (dangerous):                                       │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │  Shared Thread Pool: 50 threads                             │    │
│  │                                                              │    │
│  │  Tenant A: 48 threads stuck waiting on slow API ──────────► │    │
│  │  Tenant B: needs a thread ────────────────────► STARVED     │    │
│  └─────────────────────────────────────────────────────────────┘    │
│                                                                       │
│  WITH BULKHEAD (safe):                                               │
│  ┌──────────────────────────────────────────────────────────────┐   │
│  │  Tenant A thread pool: 20 threads (max)                      │   │
│  │  Tenant A: 20 threads stuck → Tenant A's requests queue up   │   │
│  │            Tenant A gets 429 on 21st request                 │   │
│  └──────────────────────────────────────────────────────────────┘   │
│  ┌──────────────────────────────────────────────────────────────┐   │
│  │  Tenant B thread pool: 20 threads (max)                      │   │
│  │  Tenant B: completely unaffected by Tenant A's issues        │   │
│  └──────────────────────────────────────────────────────────────┘   │
│  ┌──────────────────────────────────────────────────────────────┐   │
│  │  Default thread pool: 10 threads (shared, low priority)      │   │
│  └──────────────────────────────────────────────────────────────┘   │
│                                                                       │
│  RESILIENCE4J IMPLEMENTATION:                                        │
│                                                                       │
│  // In application.yml:                                              │
│  resilience4j.bulkhead:                                              │
│    instances:                                                        │
│      tenant-a:                                                       │
│        maxConcurrentCalls: 20                                        │
│        maxWaitDuration: 100ms                                        │
│      tenant-b:                                                       │
│        maxConcurrentCalls: 20                                        │
│        maxWaitDuration: 100ms                                        │
│                                                                       │
│  // In code:                                                         │
│  @Bulkhead(name = "{tenantId}", fallbackMethod = "rateLimitFallback")│
│  public Result processForTenant(String tenantId, Request req) {     │
│      return workerService.execute(req);                              │
│  }                                                                    │
│                                                                       │
└──────────────────────────────────────────────────────────────────────┘
```

"Combined with the circuit breaker pattern — where after 5 consecutive failures for a tenant's downstream, we open the circuit and fail-fast for 30 seconds — this gives complete blast radius containment. Tenant A's infrastructure issues stay tenant A's problem."

### 11.9 Row-Level Security (PostgreSQL RLS) — DB-Enforced Tenant Isolation

**Me:** "One of the most dangerous failure modes in a multi-tenant system is a missing `WHERE tenant_id = ?` clause. A developer writes a query, ships it, and suddenly Tenant A can see Tenant B's data. The application layer filters data by tenant — but the DB has no idea. One bug and you have a data breach.

PostgreSQL Row-Level Security moves the isolation enforcement into the database itself. Even if the application forgets the tenant filter, the DB silently applies it. This is defence in depth for multi-tenancy."

---

#### The Problem: Application-Level Filtering is Fragile

```
Application-level filtering:

  SELECT * FROM orders WHERE tenant_id = 'tenant-abc';
                             ↑
                   Developer MUST remember this.
                   One missing WHERE clause = data leak.
                   No DB-level safety net.
```

```java
// Easy to forget in a complex JOIN:
@Query("SELECT o FROM Order o JOIN o.items i WHERE i.productId = :productId")
List<Order> findByProduct(@Param("productId") Long productId);
// ❌ Missing tenant_id filter — returns all tenants' orders
```

---

#### PostgreSQL RLS: The DB Enforces Isolation

```sql
-- Step 1: Enable RLS on the table
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders FORCE ROW LEVEL SECURITY;  -- applies to table owner too

-- Step 2: Create policy — DB applies this WHERE clause to EVERY query
CREATE POLICY tenant_isolation_policy ON orders
    USING (tenant_id = current_setting('app.current_tenant_id')::UUID);

-- Now even this dangerous query is safe:
SELECT * FROM orders;
-- DB automatically rewrites to:
-- SELECT * FROM orders WHERE tenant_id = current_setting('app.current_tenant_id')::UUID
-- Tenant A CANNOT see Tenant B's rows — ever.
```

---

#### Spring Boot Integration: Setting the Tenant Context in the DB Session

```java
// Approach 1: Hibernate interceptor — sets tenant per transaction
@Component
public class TenantAwareHibernateInterceptor extends EmptyInterceptor {

    @Override
    public void beforeTransactionCompletion(Transaction tx) {
        // no-op
    }
}

// Approach 2 (Recommended): JPA EntityManager with session variable
@Repository
public class TenantAwareOrderRepository {

    @PersistenceContext
    private EntityManager entityManager;

    private void setTenantContext(String tenantId) {
        // Sets PostgreSQL session variable before every query
        entityManager.createNativeQuery(
            "SELECT set_config('app.current_tenant_id', :tenantId, true)"
        ).setParameter("tenantId", tenantId)
         .getSingleResult();
    }

    public List<Order> findAllOrders() {
        String tenantId = TenantContext.getCurrentTenant(); // from ThreadLocal
        setTenantContext(tenantId);
        // RLS policy now active — DB filters automatically
        return entityManager.createQuery("SELECT o FROM Order o", Order.class)
                            .getResultList();
    }
}
```

#### Approach 3: Spring AOP — Automatically Set Tenant on Every Repository Call

```java
// Cleaner: AOP aspect sets tenant context before every DB call
@Aspect
@Component
public class RlsTenantAspect {

    @Before("execution(* com.example.repository..*(..))")
```

#### Multiple Policies: Read vs Write Isolation

```sql
-- Separate policies for SELECT and INSERT/UPDATE/DELETE
-- Prevents accidental cross-tenant writes too

-- Read policy
CREATE POLICY orders_read_policy ON orders
    FOR SELECT
    USING (tenant_id = current_setting('app.current_tenant_id')::UUID);

-- Write policy — tenant can only insert rows for themselves
CREATE POLICY orders_write_policy ON orders
    FOR INSERT
    WITH CHECK (tenant_id = current_setting('app.current_tenant_id')::UUID);

-- Update/Delete policy
CREATE POLICY orders_modify_policy ON orders
    FOR ALL
    USING (tenant_id = current_setting('app.current_tenant_id')::UUID)
    WITH CHECK (tenant_id = current_setting('app.current_tenant_id')::UUID);

-- Platform admin bypass (superuser role bypasses RLS)
-- Create a separate DB role for platform admin queries:
CREATE ROLE platform_admin BYPASSRLS;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO platform_admin;
```

#### RLS vs Application-Level Filtering — When to Use Which

```
┌──────────────────────┬────────────────────────┬────────────────────────┐
│                      │ Application Filtering  │ PostgreSQL RLS         │
├──────────────────────┼────────────────────────┼────────────────────────┤
│ Safety               │ Only as good as code   │ DB enforces always     │
│ Bug risk             │ One missing WHERE =     │ DB silently filters    │
│                      │ data breach             │ even on buggy queries  │
│ Performance          │ No overhead             │ Tiny overhead          │
│                      │                         │ (index on tenant_id)   │
│ Complex queries      │ Developer handles       │ Automatic              │
│ Platform admin view  │ Easy (no filter)        │ BYPASSRLS role         │
│ Cross-tenant reports │ Easy                    │ Needs BYPASSRLS role   │
│ ORM compatibility    │ Fully compatible        │ Needs session var setup│
│ Audit / compliance   │ Trust the developer     │ DB-enforced — auditable│
└──────────────────────┴────────────────────────┴────────────────────────┘

Recommendation:
  Use BOTH — defence in depth.
  Application filter: primary, explicit, readable in code.
  RLS policy: safety net, catches any missed filter.
```

#### Interview Talking Points

**Q: Why not just use application-level filtering?**
Application filters are only as reliable as the developer writing the query. One missed `WHERE tenant_id = ?` in a JOIN, a native SQL query, or a reporting query causes a data breach. RLS is a database-enforced safety net — it cannot be bypassed by application bugs.

**Q: How do you handle platform admin queries that need all tenants?**
Create a separate DB role `platform_admin BYPASSRLS`. Application service uses `app_user` (RLS active). Admin tools/reporting use `platform_admin` (bypasses RLS). Never give the application user BYPASSRLS.

**Q: Does RLS work with JPA/Hibernate?**
Yes — you set the PostgreSQL session variable `app.current_tenant_id` before each transaction via interceptor, AOP aspect, or HikariCP connection hook. Hibernate queries are filtered transparently.

**Q: Performance impact of RLS?**
Negligible with proper indexing. Always index `tenant_id` on every RLS-protected table. PostgreSQL uses the index for the RLS filter just like any other WHERE clause.

**Q: How does this compare to schema-per-tenant isolation?**
RLS is simpler operationally (one schema, one connection pool) but requires trusting the DB policy. Schema-per-tenant gives stronger isolation but has connection pool limits and migration complexity. For most SaaS: RLS + shared schema. For enterprise/regulated: schema or DB per tenant.
