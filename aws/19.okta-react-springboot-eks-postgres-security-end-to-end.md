# Okta + React + Spring Boot Microservices + EKS + PostgreSQL: End-to-End Security

## The first architect correction

**Interviewer:** "We store username and hashed password in PostgreSQL. React gets an OAuth2 JWT from Okta. Each Spring Boot service has two EKS pods. Is that secure?"

**Strong answer:** "Those are two different identity authorities. If Okta authenticates users, Okta owns the password and password reset lifecycle. Our PostgreSQL database stores an application user profile keyed by Okta's immutable `sub` claim, never a duplicate login password. PostgreSQL runs as Amazon RDS or Aurora in private DB subnets across Availability Zones; it is not a pair of Kubernetes database pods. EKS runs stateless Spring Boot replicas in private application subnets. Every service validates the Okta access token locally against Okta's JWKS and applies authorization to the requested resource."

## Scenario

You operate a multi-tenant order platform:

- React SPA is served through CloudFront.
- Okta is the third-party OpenID Connect provider.
- Order, Catalog, and Payment Spring Boot services run on EKS, minimum two replicas each.
- Aurora PostgreSQL stores application and tenant data.
- A customer from tenant `acme` must never access `globex` data, even if a developer accidentally omits a tenant condition.

The key invariant is:

> A caller can act only as the validated Okta subject, inside its authorized tenant, with the least privilege necessary for both business data and AWS infrastructure.

### Why this design

React never sees a client secret. The browser obtains tokens directly from Okta through Authorization Code with PKCE. The ALB only exposes the ingress path; EKS pods and Aurora have no public IPs. Each service validates a token locally, so normal requests do not need a network call to Okta. IRSA is separate from user identity: it gives a pod permission to call AWS APIs, not permission to act as the user.

## The Three Identity Boundaries

```text
User identity       Okta access token        Who is the human or client?
Application identity app_user + membership   What tenant and business actions are allowed?
Workload identity   IRSA IAM role            Which AWS API may this pod call?
```

Never merge these boundaries. An Okta scope does not grant `s3:GetObject`; an IAM role does not prove that a human may refund an order; a PostgreSQL user is not an end-user identity. This separation makes incident impact and access reviews understandable.

## Identity Ownership: Okta Passwords vs Local Passwords

### Preferred: Okta is the identity authority

```text
Okta user
  sub = 00uabc123             immutable external identity
  email = user@acme.com       mutable profile attribute
  groups / custom claims      authorization input

PostgreSQL app_user
  id = UUID                   internal application identity
  okta_subject = 00uabc123    UNIQUE, immutable link to Okta
  tenant_id = acme            application membership
  status = ACTIVE
  password_hash = NOT STORED
```

Okta stores credentials, supports MFA, account recovery, breach protections, session management, and password policy. The application receives an already-authenticated identity.

### Simple explanation: what does "Okta owns credentials" mean?

It means: **do not store the user's password in PostgreSQL when Okta is your login system.**

Imagine Rahul uses the application:

```text
Rahul enters email + password in React
  |
  v
Okta verifies the password and returns an access token
  |
  | token contains: sub = 00uabc123
  v
React sends the token to Spring Boot
  |
  v
Spring Boot validates the token, then finds Rahul's app profile in PostgreSQL
WHERE okta_subject = '00uabc123'
```

Okta returns a signed access token similar to this:

```json
{
  "sub": "00uabc123",
  "email": "rahul@company.com",
  "scope": "orders.read orders.write"
}
```

Your PostgreSQL row contains application data, not Rahul's login password:

```text
app_user
--------
id             = 551e...
okta_subject   = 00uabc123
tenant_id      = acme
display_name   = Rahul
role           = CUSTOMER
status         = ACTIVE
password_hash  = NOT STORED
```

Use `sub`, not email, as the link. Email can change; `sub` is Okta's stable unique identity for that user. Therefore, the same Rahul is still recognized when he changes `rahul@gmail.com` to `rahul@company.com`.

```text
Okta responsibilities:        password, MFA, reset password, account lockout, JWT
PostgreSQL responsibilities:  tenant membership, application role, orders, preferences, audit
```

Keeping passwords in both places creates two login systems and doubles password-reset, MFA, lockout, breach-response, and audit work.

### Where to store `provider_subject`, and why

Keep the provider subject in **both places for different reasons**:

- **Okta keeps it** because it owns the external identity. Okta emits it in the JWT as the `sub` claim.
- **Your PostgreSQL database keeps a mapping** because your application needs to find its own user and business records from that JWT.

Do not use the Okta subject as the primary key of `orders`, `payments`, or other business tables. Create your own stable application user ID and map every external identity to it:

```text
Okta JWT
--------
iss = https://company.okta.com/oauth2/default
sub = 00uabc123
         |
         | Spring Boot looks up issuer + sub
         v
external_identity                         app_user
-----------------                         -----------------
identity_id = I-501                       user_id = U-1001
user_id = U-1001  --------------------->  tenant_id = acme
provider = OKTA                            display_name = Rahul
issuer = https://company.okta.com/...      status = ACTIVE
provider_subject = 00uabc123
```

```sql
CREATE TABLE app_user (
    user_id UUID PRIMARY KEY,
    tenant_id VARCHAR(50) NOT NULL REFERENCES tenant(tenant_id),
    display_name VARCHAR(200) NOT NULL,
    status VARCHAR(30) NOT NULL
);

CREATE TABLE external_identity (
    identity_id UUID PRIMARY KEY,
    user_id UUID NOT NULL REFERENCES app_user(user_id),
    provider VARCHAR(30) NOT NULL,
    issuer TEXT NOT NULL,
    provider_subject VARCHAR(255) NOT NULL,
    linked_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (issuer, provider_subject)
);
```

The safe external lookup key is **`issuer + sub`**. A subject is guaranteed unique only within the identity provider and authorization server that issued it. Do not use email as this key because users can change email addresses.

### What happens if we change from Okta to another IDP?

This mapping is exactly what makes migration manageable. Orders and payments continue to point to your internal `user_id`, not an Okta-specific ID:

```text
Before migration
  order.created_by_user_id = U-1001
  U-1001 -> OKTA -> issuer + sub = 00uabc123

After migration to Keycloak or Cognito
  order.created_by_user_id = U-1001       unchanged
  U-1001 -> KEYCLOAK -> issuer + sub = 4fa9c8...
```

During migration, create and verify a new `external_identity` row for the same `user_id`. A controlled account-linking journey can ask the user to authenticate with both providers once, or a verified admin migration can map identities through a trusted immutable identifier. Do not automatically link accounts by matching email alone; recycled, changed, or unverified emails can create account takeover risk.

**Simple rule:** Okta's `sub` identifies the user to your application today. Your `user_id` identifies the user to your business forever.

### Only if the product owns login: local password storage

If a product has a business requirement for local credentials, store an **Argon2id** password hash, per-user salt, and a server-side pepper held in a KMS-backed secret. Never store plaintext passwords, reversible encryption, or unsalted fast hashes such as MD5/SHA-256.

```sql
CREATE TABLE app_user (
    id UUID PRIMARY KEY,
    username CITEXT UNIQUE NOT NULL,
    password_hash TEXT NOT NULL,        -- Argon2id encoded hash only
    password_changed_at TIMESTAMPTZ NOT NULL,
    failed_login_count INT NOT NULL DEFAULT 0,
    locked_until TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Do not combine local passwords and Okta for the same user unless you have an explicit account-linking and migration design. It doubles reset, lockout, MFA, audit, and breach-response responsibilities.

### Why this model

Email is not a primary key because it can change or be re-used. `tenant_id` is taken from a trusted membership lookup or a carefully controlled Okta claim, never from a React request header. Database-level Row-Level Security is the final tenant isolation layer.

## End-to-End Login and API Sequence

```text
React             Okta                 ALB / Ingress          Order API             Aurora
  | login click     |                       |                    |                    |
  |-- auth code + PKCE -->                  |                    |                    |
  |<-- code --------|                       |                    |                    |
  |-- code_verifier -> token endpoint       |                    |                    |
  |<-- access token / refresh token --------|                    |                    |
  | GET /orders, Bearer access_token ------>|                    |                    |
  |                                          |---- route ------->|                    |
  |                                          |                   | JWKS signature,    |
  |                                          |                   | issuer, audience,  |
  |                                          |                   | expiry, scopes     |
  |                                          |                   |--- SET tenant ---->|
  |                                          |                   |--- query ---------->|
  |<-----------------------------------------|<-- 200/403 -------|                    |
```

### Why Authorization Code with PKCE

The browser is a public client and cannot protect a secret. PKCE binds the authorization code to the browser-generated verifier. Do not use the implicit flow. Prefer a backend-for-frontend with secure HttpOnly cookies when your XSS threat model or token-handling policy requires the backend to hold tokens instead of browser JavaScript.

## Setup From Beginning to Production

### 1. Create AWS network and accounts

Use separate AWS accounts for development, staging, and production. In production, create a VPC across three AZs:

```text
Public subnets:       ALB, NAT gateways
Private app subnets:  EKS nodes and pods
Private DB subnets:   Aurora/RDS only

Internet -> IGW -> ALB only
EKS -> NAT / VPC endpoints for controlled egress
EKS -> RDS Proxy -> Aurora on TCP 5432
```

Security groups should reference other security groups:

- ALB accepts `443` from the internet through WAF.
- EKS workload security group accepts the application port only from the ALB security group.
- RDS Proxy accepts `5432` only from the EKS workload security group.
- Aurora accepts `5432` only from the RDS Proxy security group.

Use VPC endpoints for STS, ECR, S3, CloudWatch Logs, and Secrets Manager where possible. This reduces NAT cost and internet egress paths.

### 2. Create Aurora PostgreSQL, not database pods

Use Aurora PostgreSQL Multi-AZ with a writer and a reader, automated backups, encryption with KMS, TLS required, Performance Insights, and CloudWatch alarms. Place it in an RDS DB subnet group spanning private DB subnets.

Set `publicly_accessible = false`, deletion protection, a backup retention period aligned to the RPO, and point-in-time recovery. Test a restore into an isolated account or VPC; a backup that has never been restored is only a hope. Use a distinct non-owner database role for each service or service-owned schema. Do not give every microservice a shared database superuser.

Use RDS Proxy for pod connection bursts. With two or more replicas per service, HPA scale-out can multiply Hikari pools quickly. A starting rule is to size each service pool deliberately and keep total possible connections below the database budget; do not let every pod default to 10-20 connections without calculation.

For example, 10 services x 2 minimum pods x 10 connections already creates 200 possible connections before autoscaling. RDS Proxy helps absorb churn but does not create unlimited database capacity.

### 3. Install and secure EKS

Create a private EKS API endpoint where operations allow it, managed node groups across at least two AZs, and an EKS add-on baseline: VPC CNI, CoreDNS, kube-proxy, AWS Load Balancer Controller, External Secrets Operator, metrics-server, Cluster Autoscaler or Karpenter, and CloudWatch/OTel collection.

Use a `Deployment` for every stateless Spring service, not a `StatefulSet`. Set `replicas: 2`, topology spread across nodes/AZs, readiness/liveness/startup probes, resource requests, a PodDisruptionBudget, and an HPA.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-api
spec:
  replicas: 2
  selector:
    matchLabels: { app: order-api }
  template:

        livenessProbe:  { httpGet: { path: /actuator/health/liveness, port: 8080 } }
        resources:
          requests: { cpu: 500m, memory: 768Mi }
          limits: { memory: 768Mi }
```

### 4. Configure Okta

Create an Okta OIDC application for the React SPA:

- Grant type: Authorization Code and Refresh Token.
- Require PKCE. Do not issue a client secret to React.
- Restrict exact sign-in and sign-out redirect URIs for each environment.
- Create a custom authorization server with an API audience such as `api://orders`.
- Define groups/scopes such as `orders.read`, `orders.write`, `payments.charge`.
- Add a narrow tenant claim only if its source and lifecycle are controlled. Do not trust a tenant ID supplied by the browser.
- Enable MFA and a risk-appropriate sign-on policy for administrators and privileged actions.

An API access token must be validated for `iss`, `aud`, signature, `exp`, `nbf`, and authorization scopes. An ID token is for the client application and must not be accepted as an API bearer token.

### 5. React implementation

Use an OIDC client that supports Authorization Code + PKCE. Keep access tokens in memory where possible. Do not put long-lived access tokens in `localStorage`; an XSS bug can extract them. Use a strict Content Security Policy, dependency scanning, and sanitize any HTML rendering.

```ts
const oidc = new OktaAuth({
  issuer: 'https://YOUR_OKTA_DOMAIN/oauth2/default',
  clientId: 'react-spa-client-id',
  redirectUri: `${window.location.origin}/login/callback`,
  scopes: ['openid', 'profile', 'email', 'orders.read'],
  pkce: true,
});

const token = await oidc.tokenManager.get('accessToken');
await fetch('/api/orders', {
  headers: { Authorization: `Bearer ${token?.accessToken}` },
});
```

Configure exact CORS origins at the ingress and Spring application; never use `*` with credentials. For a pure bearer-token SPA, CSRF protection is usually not needed because browsers do not automatically attach an `Authorization` header. If you use a BFF and HttpOnly session cookie, enable CSRF protection, set `Secure`, `HttpOnly`, and an appropriate `SameSite` policy, and protect every state-changing endpoint.

```java
@Bean
CorsConfigurationSource corsConfigurationSource() {
    var config = new CorsConfiguration();
    config.setAllowedOrigins(List.of("https://app.example.com"));
    config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
    config.setAllowedHeaders(List.of("Authorization", "Content-Type", "X-Correlation-Id"));
    config.setAllowCredentials(false); // bearer-token SPA, no cookies
    var source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/api/**", config);
    return source;
}
```

### 6. Configure each Spring Boot microservice as an OAuth2 Resource Server

Each service independently validates access tokens. Do not forward a user token to every internal service by default. For service-to-service work, use workload identity or OAuth2 client credentials with service-specific audience and scopes.

```yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://YOUR_OKTA_DOMAIN/oauth2/default
  datasource:
    url: jdbc:postgresql://RDS_PROXY_ENDPOINT:5432/orders
    hikari:
      maximum-pool-size: 8
      minimum-idle: 2
      data-source-properties:
        sslmode: verify-full
```

```java
@Bean
SecurityFilterChain security(HttpSecurity http) throws Exception {
    return http
        .csrf(csrf -> csrf.disable()) // only for stateless bearer-token API
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/actuator/health/**").permitAll()
            .requestMatchers(HttpMethod.GET, "/api/orders/**").hasAuthority("SCOPE_orders.read")
            .requestMatchers(HttpMethod.POST, "/api/orders/**").hasAuthority("SCOPE_orders.write")
            .anyRequest().authenticated())
        .oauth2ResourceServer(oauth -> oauth.jwt(jwt -> jwt
            .jwtAuthenticationConverter(jwtAuthenticationConverter())))
        .build();
}

private Converter&lt;Jwt, ? extends AbstractAuthenticationToken&gt; jwtAuthenticationConverter() {
    // Map only approved Okta scopes/groups. Validate tenant membership separately.
}
```

Add an audience validator. `issuer-uri` supplies signature and issuer validation, but the service should reject a token minted for a different API audience.

```java
@Bean
JwtDecoder jwtDecoder() {
  NimbusJwtDecoder decoder = NimbusJwtDecoder.withIssuerLocation(OKTA_ISSUER).build();
  OAuth2TokenValidator<Jwt> issuer = JwtValidators.createDefaultWithIssuer(OKTA_ISSUER);
  OAuth2TokenValidator<Jwt> audience = jwt -> jwt.getAudience().contains("api://orders")
    ? OAuth2TokenValidatorResult.success()
    : OAuth2TokenValidatorResult.failure(new OAuth2Error("invalid_token", "Wrong audience", null));
  decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(issuer, audience));
  return decoder;
}
```

The `aud` value is service-specific. Payment Service must not accept a token meant only for Order Service. Map scopes to authorities and perform object-level authorization in the service layer: a valid `orders.read` scope does not automatically allow reading every order.

### JWT parts, JWKS, and the HMAC misunderstanding

A compact JWT has three dot-separated parts:

```text
part 1                 part 2                    part 3
-------                -------                   -------
base64Url(header) . base64Url(payload) . base64Url(signature)

header:  algorithm and key ID (`kid`)
payload: sub, iss, aud, exp, scopes, and other claims
signature: proof that the issuer signed part 1 + "." + part 2
```

Your "recalculate part 1 and part 2, then compare to part 3" description applies to an **HS256** token:

```text
signature = HMAC-SHA256(shared_secret, part1 + "." + part2)

Issuer and every validating service need the same shared_secret.
```

**HS256 is not recommended for this Okta + multiple Spring Boot microservice architecture.** Every service that validates the token receives the shared secret. A compromised Order Service could then mint a valid token for Payment Service. Secret rotation also becomes a coordinated deployment problem across every service.

Okta normally issues tokens using an asymmetric algorithm such as **RS256**:

```text
Okta private key  -> signs part1 + "." + part2 -> signature (part 3)
Spring Boot       -> verifies signature using Okta public key
```

Spring Boot does not recreate an HMAC in this approach. It uses RSA signature verification with the public key. The public key can verify a token but cannot create a new valid token.

```text
JWT header: { "alg": "RS256", "kid": "key-2026-01" }
                                      |
                                      v
Spring Boot -> OIDC discovery document -> JWKS endpoint -> public keys
                                      |
                                      v
                         select public key matching `kid`
                                      |
                                      v
                  verify signature, issuer, audience, expiry, scopes
```

JWKS means **JSON Web Key Set**. It contains multiple public keys, not JWT part 1, part 2, and part 3. Multiple keys allow safe key rotation: an older token can validate with the old public key while new tokens use the new `kid`. Spring Boot caches JWKS keys and refreshes when it sees an unknown `kid`; it does not normally call Okta for every API request.

**When can HS256 be acceptable?** A small, single trusted backend can use it when the secret can be protected and all issuers/verifiers are equally trusted. Even then, asymmetric signing is generally the safer default when tokens cross service or organizational boundaries.

### 7. Tenant authorization and PostgreSQL RLS

Authentication answers "who is this?" Authorization answers "may this subject access this tenant and order?" Resolve membership from an application-controlled table or a well-governed Okta group claim. Set tenant context once per transaction and enforce it in the database:

```sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON orders
USING (tenant_id = current_setting('app.tenant_id', true))
WITH CHECK (tenant_id = current_setting('app.tenant_id', true));
```

```java
@Transactional
public List&lt;Order&gt; findOrders(TenantId tenantId) {
  jdbcTemplate.queryForObject(
    "select set_config('app.tenant_id', ?, true)", String.class, tenantId.value());
    return orderRepository.findAll();
}
```

The `true` argument makes the setting transaction-local, so it is cleared at transaction end before HikariCP returns the connection to its pool. Use a non-owner application database role; table owners can bypass RLS unless `FORCE ROW LEVEL SECURITY` and role design are applied correctly. Resolve `tenantId` only after subject-to-tenant membership authorization, and test both reads and writes for tenant escape.

### 8. Give pods AWS permissions using IRSA

Okta identifies a user. IRSA identifies a Kubernetes workload to AWS. They must not be confused.

```text
order-api pod
  -> Kubernetes ServiceAccount: order-api
  -> projected OIDC token
  -> STS AssumeRoleWithWebIdentity
  -> IAM role: order-api-role
  -> permitted: secretsmanager:GetSecretValue for orders/*, sqs:SendMessage for order-events
```

Bind the IAM role trust policy to one namespace and one service account. Do not let the node IAM role grant business-service permissions.

For internal service calls, use OAuth2 Client Credentials with a separate Okta service application, audience, and narrow scopes, or use a workload identity mechanism at the platform boundary. Do not pass the browser's broad user token through every hop merely because it is convenient. Pass a minimal immutable actor context such as subject and correlation ID for audit when needed.

### 9. Secrets, TLS, and supply chain

- Store DB credentials and third-party keys in Secrets Manager, encrypted with KMS.
- External Secrets Operator synchronizes only the required secret to a namespace; do not put secret values in Git, image layers, logs, or Helm values.
- TLS terminates at ALB and should also use TLS to the pod where policy requires. Enforce TLS from app to RDS Proxy/Aurora.
- Build immutable images, scan images, sign or attest them, pin image digests, and use admission policy to reject unapproved registries and privileged pods.
- Restrict Kubernetes RBAC, use NetworkPolicies, and separate namespaces by trust boundary.

Kubernetes NetworkPolicies only protect traffic when the EKS network-policy implementation is enabled. Confirm the EKS VPC CNI network policy agent or a compatible CNI is actually enforcing policy before treating YAML as a control. Start deny-by-default, then allow only required paths:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: order-api-ingress
spec:
  podSelector: { matchLabels: { app: order-api } }
  policyTypes: [Ingress, Egress]
  ingress:
  - from:
    - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: ingress } }
    ports: [{ protocol: TCP, port: 8080 }]
  egress:
  - to:
    - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } }
    ports: [{ protocol: UDP, port: 53 }]
```

Add explicit egress rules for RDS Proxy and approved AWS/private endpoints. Avoid an unrestricted `0.0.0.0/0` egress rule, because it undermines the private-subnet boundary.

## Production Readiness Runbook

Before the first production release, prove the following in staging:

1. A token with a wrong issuer, audience, expired time, missing scope, or ID-token `typ` is rejected.
2. An `acme` subject cannot read, insert, update, or delete `globex` rows, including through a pooled connection reused after an `acme` request.
3. Each service account can call only its approved AWS APIs; node credentials cannot access service secrets or queues.
4. A pod rollout, node drain, one-AZ node failure, RDS failover, Okta JWKS key rotation, and RDS Proxy connection surge remain within documented SLOs.
5. An image with a critical policy violation, a privileged container, or an unapproved registry is rejected before reaching EKS.
6. Audit logs link `sub`, tenant, request/correlation ID, route, authorization outcome, and deployment image digest without recording bearer tokens or passwords.

## Cross Questions

1. **Why not validate the JWT by calling Okta on every request?**
   JWT validation is local using cached JWKS public keys, which avoids latency and an availability dependency on Okta. Use introspection only when you require near-real-time revocation semantics and can accept the dependency.

2. **How do you revoke a JWT immediately?**
   Keep access tokens short-lived, revoke refresh tokens/session in Okta, and for high-risk endpoints use token introspection or a deny-list keyed by `jti` with a short TTL. “JWT is stateless” is a trade-off, not magic revocation.

3. **Why two EKS pods?**
   Two is minimum availability during one pod failure or a rolling deployment. It is not enough without anti-affinity/topology spread, PDB, healthy nodes in multiple AZs, and a correctly sized autoscaler.

4. **Can PostgreSQL have two active writer pods?**
   Not as ordinary PostgreSQL pods without a complex consensus/replication operator. Use Aurora/RDS Multi-AZ for managed writer failover. Read replicas serve reads, not a second independent writer.

5. **Does the frontend’s tenant header provide tenant isolation?**
   No. A browser can alter it. Resolve tenant from token/membership and enforce it in PostgreSQL RLS as defense in depth.

## Senior Trap Questions

### "We use Okta. Should we still store a BCrypt hash in our users table?"

Not for the same authentication path. Okta should own user credentials. Store the Okta `sub`, tenant membership, application status, and audit data. Storing a second password hash creates conflicting reset, lockout, MFA, and breach workflows. Use local Argon2id only for a deliberate local-identity product requirement.

### "The ALB validates OAuth. Do individual services still need token validation?"

Yes, unless there is a rigorously controlled trusted identity propagation design. Each service is a resource server and should validate token issuer, signature, audience, expiry, and scope. Edge validation is useful defense in depth, not the only authorization boundary.

### "We have two pods, so rolling deploy is safe."

Not necessarily. A single node or AZ can host both pods, readiness may be wrong, or both pods can be evicted during maintenance. Use `maxUnavailable: 0`, a PDB, topology spread, proper startup/readiness probes, and test the deployment under real load.

### "Can I pass the user’s bearer token to Payment Service?"

Only when Payment needs to make an authorization decision specifically on behalf of that user and the token has Payment audience/scopes. Otherwise use service identity, propagate a signed minimal actor context for audit, and avoid turning one broad user token into universal internal access.

"I separate three identities: the user identity from Okta, the application identity in PostgreSQL, and the workload identity from IRSA. React uses Authorization Code with PKCE. Every Spring Boot service runs at least two stateless, AZ-spread EKS replicas and validates Okta access tokens locally. Aurora PostgreSQL, behind RDS Proxy in private DB subnets, owns durable application data; it does not store Okta passwords. Tenant isolation is enforced in code and PostgreSQL RLS.
