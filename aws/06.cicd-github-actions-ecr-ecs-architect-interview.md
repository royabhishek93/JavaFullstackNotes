### OPENING — When They Ask: "Walk me through your CI/CD pipeline."

> **You say:**
>
> "For the Swiggy microservices on ECS Fargate, every service has the same pipeline.
> When a developer pushes to main, within about 8 minutes, the new container is
> running in production. No manual steps, no SSH, no kubectl apply.
>
> The pipeline is five stages: build and test, Docker image, push to ECR,
> update ECS task definition, trigger ECS rolling deployment.
>
> Let me draw the full flow and then walk through each stage."

```
SWIGGY CI/CD PIPELINE — Full Flow
====================================

  Developer
      |
      | git push → main branch
      v
  GitHub
      |
      | triggers GitHub Actions workflow
      v
  ┌─────────────────────────────────────────────────────────┐
  │  GitHub Actions Runner (ubuntu-latest)                  │
  │                                                         │
  │  Stage 1: BUILD + TEST (2-3 min)                        │
  │  ├── mvn test (unit tests + integration tests)          │
  │  ├── fail fast: if tests fail → pipeline stops          │
  │  └── no deployment if tests fail                        │
  │                                                         │
  │  Stage 2: DOCKER BUILD (1-2 min)                        │
  │  ├── docker build -t order-service:${SHA} .             │
  │  └── tag with git SHA (never "latest")                  │
  │                                                         │
  │  Stage 3: PUSH TO ECR (1 min)                           │
  │  ├── aws ecr get-login-password | docker login          │

  │        swiggy/order-service:${SHA}                      │
  │                                                         │

  │                                                         │

  │  ├── aws ecs update-service                             │
  │  │   --force-new-deployment                             │
  │  └── wait for service stability (health checks pass)    │
  └─────────────────────────────────────────────────────────┘
      |
      v
  ECS Fargate
  ├── spins up new task with new image
  ├── health check passes (ALB: /actuator/health)
  ├── traffic shifts to new task
  └── old task drained and stopped

  Total time: ~8 minutes from git push to production
```

### PART 1 — The GitHub Actions Workflow File

> **You say:**
>
> "Here's the actual workflow file. Every microservice has the same structure —
> only the service name and ECR repository URL differ. Everything else is identical.
> That's intentional — one pattern, zero surprises across 5 services."

**.github/workflows/deploy.yml:**

```yaml
name: Build and Deploy to ECS

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]   # runs tests on PR, no deployment

env:
  AWS_REGION:        us-east-1
  ECR_REGISTRY:      123456789.dkr.ecr.us-east-1.amazonaws.com
  ECR_REPOSITORY:    swiggy/order-service
  ECS_CLUSTER:       swiggy-prod
  ECS_SERVICE:       order-service
  CONTAINER_NAME:    order-service   # must match name in task definition

jobs:
  # ─────────────────────────────────────────────
  # JOB 1: Test (runs on every push + PR)
  # ─────────────────────────────────────────────
  test:
    runs-on: ubuntu-latest

    services:
      postgres:
        image: postgres:15
        env:
          POSTGRES_DB:       testdb
          POSTGRES_USER:     test
          POSTGRES_PASSWORD: test
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 10s

      redis:
        image: redis:7
        ports:
          - 6379:6379

    steps:
      - uses: actions/checkout@v4

      - name: Set up Java 21
        uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: 'temurin'
          cache: maven       # cache .m2 between runs → 60% faster

      - name: Run tests
        run: mvn test --no-transfer-progress
        env:
          SPRING_DATASOURCE_URL: jdbc:postgresql://localhost:5432/testdb
          SPRING_DATASOURCE_USERNAME: test
          SPRING_DATASOURCE_PASSWORD: test
          SPRING_REDIS_HOST: localhost

      - name: Upload test results
        if: always()                      # upload even if tests fail
        uses: actions/upload-artifact@v4
        with:
          name: test-results
          path: target/surefire-reports/

  # ─────────────────────────────────────────────
  # JOB 2: Build + Deploy (only on main push)
  # ─────────────────────────────────────────────
  deploy:
    needs: test                           # waits for test job to pass
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'

    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789:role/github-actions-deploy-role
          aws-region: ${{ env.AWS_REGION }}
          # No hardcoded keys! Uses OIDC identity federation

      - name: Login to Amazon ECR
        id: login-ecr
        uses: aws-actions/amazon-ecr-login@v2

      - name: Build, tag, and push Docker image
        id: build-image
        env:
          IMAGE_TAG: ${{ github.sha }}    # git SHA — immutable, traceable
        run: |
          docker build -t $ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG .
          docker push $ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG
          echo "image=$ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG" >> $GITHUB_OUTPUT

      - name: Download current ECS task definition
        run: |
          aws ecs describe-task-definition \
            --task-definition order-service \
            --query taskDefinition \
            > task-definition.json

      - name: Update task definition with new image
        id: task-def
        uses: aws-actions/amazon-ecs-render-task-definition@v1
        with:
          task-definition: task-definition.json
          container-name: ${{ env.CONTAINER_NAME }}
          image: ${{ steps.build-image.outputs.image }}

      - name: Deploy to ECS
        uses: aws-actions/amazon-ecs-deploy-task-definition@v1
        with:
          task-definition: ${{ steps.task-def.outputs.task-definition }}
          service: ${{ env.ECS_SERVICE }}
          cluster: ${{ env.ECS_CLUSTER }}
          wait-for-service-stability: true    # blocks until deployment complete
          # Fails the pipeline if deployment fails — no silent failures
```

### PART 2 — When They Ask: "Why git SHA instead of 'latest' tag?"

> **You say:**
>
> "This comes up every time. 'Latest' is a trap. If you tag every build as 'latest',
> you can't tell what version is actually running in production — the ECR image and
> the running task both say 'latest' but might be different builds.
>
> With a git SHA tag — say `a3f9c12` — I can look at any running ECS task,
> see the image tag, do `git log a3f9c12 -1`, and know exactly what code is running.
> That's invaluable at 2am during an incident.
>
> We keep the last 10 images in ECR via a lifecycle policy. Older ones are
> automatically deleted to control storage costs."

```
DOCKER IMAGE TAGGING STRATEGY
================================

  BAD (what juniors do):
  ├── order-service:latest  → every build overwrites this
  ├── Which build is in prod? Unknown.
  └── Rollback: you can't tag rollback to previous "latest"

  GOOD (what we do):
  ├── order-service:a3f9c12  → git SHA, immutable
  ├── order-service:b2e8d01  → previous release
  ├── order-service:c1d7f09  → two releases ago
  │
  └── kubectl describe pod → image: order-service:a3f9c12
      git log a3f9c12 -1 → "feat: add Redis idempotency"
      → know EXACTLY what's running in prod

  ECR LIFECYCLE POLICY (keep 10 images, delete older):
  {
    "rules": [{
      "rulePriority": 1,
      "description": "Keep last 10 images",
      "selection": {
        "tagStatus": "tagged",
        "tagPrefixList": [""],
        "countType": "imageCountMoreThan",
        "countNumber": 10
      },
      "action": { "type": "expire" }
    }]
  }
```

### PART 3 — When They Ask: "How do you handle credentials? You can't hardcode AWS keys."

> **You say:**
>
> "We use OIDC federation — GitHub Actions proves its identity to AWS using a
> JWT token issued by GitHub. AWS validates the token and grants a temporary
> IAM role. No static access keys anywhere.
>
> This is the right answer for 2024. Any pipeline using `AWS_ACCESS_KEY_ID` as
> a GitHub secret is a risk — keys can be leaked in logs, need rotation,
> and have no expiry."

```
GITHUB ACTIONS OIDC FEDERATION (no static keys)
==================================================

  GitHub Actions Runner
      |
      | 1. Request JWT from GitHub OIDC provider
      |    JWT claims:
      |    { repo: "swiggy/order-service",
      |      branch: "main",
      |      workflow: "deploy" }
      |
      v
  AWS IAM (STS AssumeRoleWithWebIdentity)
      |
      | 2. Trust policy on the IAM role:
      |    "Allow if token.repo == 'swiggy/order-service'"
      |    "Allow if token.branch == 'main'"
      |
      | 3. Return temporary credentials (1hr)
      |    AccessKeyId, SecretAccessKey, SessionToken
      |
      v
  GitHub Actions continues with temporary credentials
  ├── push to ECR
  ├── update ECS task definition
  └── update ECS service

  IAM ROLE POLICY (minimal permissions):
  {
    "Version": "2012-10-17",
    "Statement": [
      {
        "Effect": "Allow",
        "Action": [
          "ecr:GetAuthorizationToken",
          "ecr:BatchCheckLayerAvailability",
          "ecr:PutImage",
          "ecr:InitiateLayerUpload",
          "ecr:UploadLayerPart",
          "ecr:CompleteLayerUpload"
        ],
        "Resource": "arn:aws:ecr:us-east-1:123:repository/swiggy/*"
      },
      {
        "Effect": "Allow",
        "Action": [
          "ecs:DescribeTaskDefinition",
          "ecs:RegisterTaskDefinition",
          "ecs:UpdateService",
          "ecs:DescribeServices"
        ],
        "Resource": "*"
      },
      {
        "Effect": "Allow",
        "Action": "iam:PassRole",
        "Resource": "arn:aws:iam::123:role/ecs-task-execution-role"
      }
    ]
  }
```

### PART 4 — When They Ask: "Rolling vs Blue-Green — what do you use?"

> **You say:**
>
> "ECS has three deployment strategies. We use rolling for most services
> and blue-green for payment-critical paths.
>
> Rolling: ECS gradually replaces old tasks with new ones. At peak load
> we run 4 tasks, so with minimum healthy 50%, ECS can kill 2 old tasks and
> start 2 new ones at once. Takes about 3 minutes. Downside: for about 2 minutes
> you have a mix of old and new code running — both versions handling traffic.
>
> Blue-green with CodeDeploy: spin up entirely new tasks, shift 10% traffic,
> wait 5 minutes, shift 100%. If health checks fail at any point, instant rollback.
> The old tasks stay alive until you confirm success. Downside: double the cost
> during the transition window."

```
ROLLING DEPLOYMENT (what we use for most services):
=====================================================

  t=0: 4 tasks running (v1, v1, v1, v1)
       Load: 25% each

  t=1: ECS stops 2 tasks, starts 2 new ones
       Running: v1, v1, v2, v2 (starting...)
       Load: v1 gets 50% total, v2 gets 0% (not healthy yet)

  t=2: v2 tasks pass health check (/actuator/health → 200)
       Running: v1, v1, v2, v2
       Load: 25% each (mix of versions!)

  t=3: ECS stops remaining v1 tasks, starts 2 more v2
       Running: v2, v2, v2, v2
       Load: 25% each

  RISK: 2 minutes where v1 and v2 both serve traffic
  → must ensure backward compatibility (new code handles old API shape)

  ECS SERVICE DEPLOYMENT CONFIG:
  {
    "deploymentConfiguration": {
      "minimumHealthyPercent": 50,   // kill up to 50% of tasks at once
      "maximumPercent": 200          // allow double capacity during rollout
    }
  }

  BLUE-GREEN (for payment service):
  ===================================

  t=0: Blue (current): 4 tasks (v1)
       Green (new):     0 tasks

  t=1: Green starts: 4 tasks (v2) spin up
       ALB: 100% traffic → Blue, 0% → Green

  t=2: CodeDeploy shifts 10% → Green
       5-minute observation window
       CloudWatch alarms: 5xx rate, latency

  t=3: If alarms clear → 100% to Green
       Blue tasks stay alive for 30 min (instant rollback available)

  t=30min: Blue tasks terminated
```

### PART 5 — When They Ask: "How do you handle a bad deployment?"

> **You say:**
>
> "Two scenarios. During deployment: GitHub Actions waits for ECS service stability.
> If the new task fails its health check three times, ECS stops the deployment,
> keeps old tasks running, and GitHub Actions marks the step as failed.
>
> After deployment: If a post-deploy issue appears, we roll back by triggering
> the pipeline again with the previous git SHA. Takes the same 8 minutes as
> a normal deploy. We keep the previous 10 images in ECR specifically for this."

```
DEPLOYMENT FAILURE HANDLING
==============================

  FAILURE DURING DEPLOYMENT (health check fails):
  ─────────────────────────────────────────────────
  ECS starts new task
      |
      | /actuator/health → 500 (app crash on startup)
      |
      | ALB health check fails
      |   3 consecutive failures → target deregistered
      |
      | ECS stops new task
      | Old tasks still running
      |   (minimumHealthyPercent: 50 → at least 2 old tasks stayed up)
      |
      | GitHub Actions step timeout
      |   wait-for-service-stability: true → pipeline FAILS
      |   Slack/email notification: "deploy-failed for order-service"
      |
      v
  Production: still running old version, zero impact

  FAILURE AFTER DEPLOYMENT (discovered in prod):
  ────────────────────────────────────────────────
  Option 1: New deploy from previous commit
    git revert HEAD
    git push main
    → pipeline runs, deploys previous code (8 min)

  Option 2: Rollback to specific SHA
    git push origin a3f9c12:main --force-with-lease
    → pipeline deploys exact known-good image (from ECR cache, fast!)

  HOW TO FIND THE LAST GOOD SHA:
    git log --oneline -5
    a3f9c12 feat: add Redis idempotency   ← running 3 deployments ago
    b2e8d01 fix: null check in cart service
    c1d7f09 chore: update dependencies
```

### PART 6 — When They Ask: "How do you promote from dev to staging to prod?"

> **You say:**
>
> "We have three environments with separate ECS clusters, separate RDS instances,
> separate ECR repositories. The same Docker image is promoted — we don't rebuild
> for each environment.
>
> Dev: every push to a feature branch deploys. Quick, noisy, expected to break.
> Staging: every push to main deploys automatically, with integration tests.
> Production: triggered manually via a GitHub Actions workflow_dispatch event,
> or automatically after staging tests pass — depends on the team's risk tolerance."

```
ENVIRONMENT PROMOTION PIPELINE
=================================

  Feature Branch Push
          |
          v
  ┌────────────────────┐
  │  DEV Environment   │
  │  ECS: dev-cluster  │
  │  RDS: dev-postgres │
  │  Auto-deploy       │
  └────────────────────┘
          |
          | merge to main
          v
  ┌────────────────────┐
  │  STAGING           │
  │  ECS: stage-cluster│
  │  RDS: stage-postgres│
  │  Auto-deploy       │
  │  + E2E tests run   │
  └────────────────────┘
          |
          | E2E tests pass
          | manual approval (GitHub env protection rule)
          v
  ┌────────────────────┐
  │  PRODUCTION        │
  │  ECS: prod-cluster │
  │  RDS: prod-postgres│
  │  Manual trigger    │
  │  OR auto after E2E │
  └────────────────────┘

  KEY PRINCIPLE: Same Docker image travels through all envs
  Dev image:  order-service:a3f9c12
  Staging:    order-service:a3f9c12  (same SHA, different cluster)
  Prod:       order-service:a3f9c12  (same SHA, different cluster)

  This guarantees: if it works in staging, prod runs identical code.
```

## ONE-LINER ANSWERS

**"Why not use CodePipeline instead of GitHub Actions?"**
> "GitHub Actions keeps build logic in the repo — same repo, same PR, same review.
> CodePipeline is AWS-centric and harder to version-control. For teams already on GitHub,
> GitHub Actions is simpler and faster to iterate."

**"What if two engineers push at the same time?"**
> "GitHub Actions queues workflows per branch. The second push triggers a new run
> which may cancel the previous one mid-flight (with concurrency: cancel-in-progress).
> ECS never gets a half-applied state — either the deployment completes or it doesn't start."

**"How do you test the Docker image before pushing to ECR?"**
> "In the build stage we run `docker run --rm order-service:$SHA ./wait-for-it.sh && mvn verify -Pintegration`
> against the built image with a local Compose environment. If that fails, ECR never sees the image."

## FAILURE SCENARIOS

| Scenario | What Happens |
|---|---|
| Unit test fails | Pipeline stops at test stage, no image built, no deployment |
| Docker build fails | Pipeline stops, ECR unchanged, prod unaffected |
| ECR push fails (network) | GitHub Actions retries 3 times, then fails — prod unaffected |
| New task fails health check | ECS keeps old tasks, GitHub Actions step times out and fails |
| Deployment succeeds but app has bug | Roll back: re-run pipeline with previous git SHA |
| AWS credentials expired | OIDC tokens are 1hr — the role is re-assumed fresh each run |
| ECR image limit reached | Lifecycle policy deletes images >10 — old SHA no longer in ECR, need to rebuild for rollback |
