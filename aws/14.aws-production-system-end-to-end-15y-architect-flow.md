## Step 2: AWS Account and Org Model

Do not start by launching random compute instances.

Use a multi-account model via AWS Organizations:

~~~text
AWS Organization
       |
       +---- Dev Account
       +---- QA Account
       +---- Prod Account
       +---- Security Account
       +---- Logging Account
~~~

**What is AWS Organizations?**
AWS Organizations is a centralized account management service that lets you create and manage multiple AWS accounts under a single organization.

**Why we need it:**

- **Better security boundaries**: Blast radius containment - if dev account is compromised, prod remains isolated.
- **Cleaner compliance and auditing**: Each environment has its own audit trail and compliance controls.
- **More predictable billing and ownership**: Clear cost allocation per environment/team.
- **Centralized policy management**: Apply Service Control Policies (SCPs) across accounts from one place.

## Step 3: VPC First, Then Network Controls

Design the network foundation before compute and data services.

~~~text
VPC
10.0.0.0/16
 |
 +-----------------------------+
 |                             |
 v                             v
Public Subnets              Private Subnets
 |                             |
 ALB                           EKS
 NAT Gateway                   RDS
                               Redis
~~~

### Core Network Components Explained:

**1. VPC (Virtual Private Cloud)**
- **What:** Isolated virtual network in AWS cloud that you fully control.
- **Why:** Provides network isolation, custom IP addressing, and control over traffic routing. Foundation for all other resources.

**2. CIDR Block (e.g., 10.0.0.0/16)**
- **What:** IP address range for your VPC.
- **Why:** Determines how many IP addresses available (65,536 for /16). Must plan for growth and avoid conflicts with on-prem networks.

**3. Public Subnets**
- **What:** Subnets with direct internet access via Internet Gateway.
- **Why:** Host internet-facing resources like ALB and NAT Gateway. Users access your app through these.

**4. Private Subnets**
- **What:** Subnets with NO direct internet access.
- **Why:** Host backend services (EKS, RDS, Redis) for security. Compromised apps can't directly exfiltrate data to internet.

**5. Multi-AZ Design**
- **What:** Spreading subnets across multiple Availability Zones (datacenters).
- **Why:** High availability - if one AZ fails, others continue serving traffic. Required for production SLAs.

**6. Route Tables**
- **What:** Rules determining where network traffic is directed.
- **Why:** Control traffic flow - public subnets route to Internet Gateway, private subnets route to NAT Gateway.

**7. Internet Gateway**
- **What:** Horizontally scaled gateway allowing bidirectional internet communication.
- **Why:** Enables resources in public subnets to receive inbound requests from users and respond back.

**8. NAT Gateway**
- **What:** Network Address Translation service in public subnet.
- **Why:** Allows private subnet resources (EKS pods, RDS) to initiate outbound internet connections (OS updates, external APIs) while blocking inbound access.

**9. Security Groups**
- **What:** Stateful virtual firewalls at instance/resource level.
- **Why:** Control exactly which traffic can reach your resources (e.g., "RDS only accepts connections from EKS security group on port 5432").

**10. NACLs (Network Access Control Lists)**
- **What:** Stateless firewalls at subnet level.
- **Why:** Additional security layer for subnet-wide rules. Use when you need explicit DENY rules or subnet-level protection.

Why VPC first:

- Every downstream service must attach to this network model.
- Rework later is expensive and risky - changes require recreation of resources.

## Step 4: IAM and Least Privilege

Use roles, not embedded credentials.

~~~text
EKS Application
      |
      | IAM Role
      v
     S3
~~~

**What is IAM (Identity and Access Management)?**
AWS service for securely controlling access to AWS resources.

**Why we need IAM Roles (not hardcoded credentials):**

- **Security**: Roles provide temporary credentials that auto-rotate. No hardcoded keys in code/config.
- **Auditability**: CloudTrail logs which role accessed what resource.
- **Principle of Least Privilege**: Grant only the minimum permissions needed for each service.
- **No credential management**: No passwords/keys to rotate, store, or leak in Git.

Example access policy intent:

~~~text
Order Service
   |
   +---- Read/Write -> Order S3 bucket
   +---- Read       -> Secrets Manager
~~~

**Why this pattern:**
- Order Service can only access its own S3 bucket, not other services' buckets.
- If Order Service is compromised, blast radius is limited to what its IAM role permits.
- Secrets Manager integration means database passwords never appear in environment variables or config files.

Architect-level point:

- Start least privilege from day one.
- Scope permissions by service and environment.
- Use temporary credentials and role assumption patterns.

## Step 5: Provision Supporting Data and Platform Services

Provision by capability, not by convenience:

~~~text
                 AWS
                  |
      +-----------+-----------+
      |           |           |
     RDS        Redis        S3
      |           |           |
 PostgreSQL     Cache       Files
~~~

### Data Layer Components Explained:

**1. RDS (Relational Database Service) - PostgreSQL**
- **What:** Managed relational database service.
- **Why we need it:**
  - **Managed operations**: AWS handles backups, patching, failover automatically.
  - **Multi-AZ failover**: Automatic failover to standby in seconds if primary fails.
  - **Point-in-time recovery**: Restore database to any second within retention period.
  - **Scalability**: Read replicas for scaling read-heavy workloads.
  - **No infrastructure management**: No need to provision VMs, install DB software, configure replication.

**2. Redis (ElastiCache)**
- **What:** In-memory data store for caching and session management.
- **Why we need it:**
  - **Performance**: Sub-millisecond latency vs hundreds of milliseconds for database queries.
  - **Reduce database load**: Cache frequently accessed data (product catalog, user sessions).
  - **Session store**: Distributed sessions across multiple EKS pods.
  - **Rate limiting**: Track API call counts per user with fast TTL-based expiry.
  - **Real-time features**: Pub/sub for notifications, leaderboards, counters.

**3. S3 (Simple Storage Service)**
- **What:** Object storage service for files and unstructured data.
- **Why we need it:**
  - **Scalability**: Unlimited storage, no capacity planning needed.
  - **Durability**: 99.999999999% (11 nines) - virtually no data loss.
  - **Cost-effective**: Much cheaper than database BLOB storage.
  - **Use cases**: Store user uploads (images, PDFs), application logs, backup files, static assets.
  - **Lifecycle policies**: Auto-archive old data to Glacier for cost savings.

**4. Kafka / MSK (Managed Streaming for Kafka)**
- **What:** Distributed event streaming platform.
- **Why we need it:**
  - **Async processing**: Decouple services - Order Service publishes event, Notification Service processes independently.
  - **Event sourcing**: Maintain audit trail of all state changes.
  - **Scalability**: Handle millions of events per second.
  - **Reliability**: Events are persisted, guaranteed delivery even if consumer is down.
  - **Real-time pipelines**: Stream processing for analytics, fraud detection, inventory updates.

Architect-level decisions include:

- **Backup and retention strategy**: RDS automated backups (7-35 days), S3 versioning, Kafka retention periods.
- **Encryption at rest and in transit**: RDS encryption, S3 encryption, TLS for all connections.
- **Throughput and scaling limits**: IOPS for RDS, memory for Redis, partitions for Kafka.
- **HA and failover requirements**: Multi-AZ RDS, Redis cluster mode, MSK multi-AZ brokers.

## Step 6: Create EKS for Containerized Workloads

~~~text
AWS
 |
 v
EKS Cluster
 |
 +-------------------+
 |                   |
Node 1              Node 2
 |                   |
Pod                 Pod
Order Service       Order Service
~~~

**What is EKS (Elastic Kubernetes Service)?**
Managed Kubernetes service - AWS operates the Kubernetes control plane (API server, scheduler, etcd).

**Why we need EKS:**

- **Container orchestration**: Automatically manages deployment, scaling, and health of containerized applications.
- **Self-healing**: Replaces crashed pods automatically.
- **Service discovery**: Built-in DNS for pod-to-pod communication.
- **Load balancing**: Distributes traffic across healthy pods.
- **Rolling updates**: Deploy new versions with zero downtime.
- **Resource efficiency**: Bin-packing multiple services on same nodes.
- **Portability**: Kubernetes manifests work across any K8s cluster (not locked to AWS).

**EKS vs plain EC2:**
- EC2: You manually install apps, configure load balancing, handle failures, scale manually.
- EKS: Declare desired state, Kubernetes ensures it's maintained.

Configure:

**1. Node groups and sizing**
- **What:** EC2 instances that run your pods.
- **Why:** Right-size compute (t3.medium for low traffic, m5.2xlarge for high CPU workloads).

**2. Namespaces and policy boundaries**
- **What:** Logical isolation within cluster.
- **Why:** Separate dev/staging/prod workloads, apply resource quotas, enforce network policies.

**3. Ingress and load balancing integration**
- **What:** Routing rules connecting ALB to Kubernetes services.
- **Why:** Single ALB can route to multiple microservices based on URL path.

**4. Cluster autoscaling and pod autoscaling**
- **What:** Auto-add nodes when pods can't schedule; scale pod replicas based on CPU/memory.
- **Why:** Handle traffic spikes automatically without manual intervention.

**5. Runtime security controls**
- **What:** Pod Security Standards, network policies, OPA/Gatekeeper.
- **Why:** Prevent pods from running as root, restrict inter-pod communication, enforce security policies.

## Step 7: Use IaC as the Standard Path

In production, infrastructure should be reviewable and repeatable.

~~~text
Terraform
   |
   v
terraform plan
   |
   v
Review
   |
   v
terraform apply
   |
   v
AWS Infrastructure
~~~

**What is IaC (Infrastructure as Code) / Terraform?**
Declarative configuration files that define infrastructure. Terraform reads .tf files and creates/updates AWS resources to match.

**Why we need IaC (vs ClickOps in AWS Console):**

- **Repeatability**: Create identical dev/staging/prod environments from same code.
- **Version control**: Infrastructure changes go through Git - track who changed what and when.
- **Code review**: Peer review infrastructure changes before applying to prod.
- **Disaster recovery**: Rebuild entire environment from scratch if region fails.
- **Documentation**: Code IS the documentation - always accurate, never outdated.
- **Drift detection**: `terraform plan` shows if someone made manual changes in console.
- **Rollback**: Git revert infrastructure changes just like application code.
- **Automation**: CI/CD can provision infrastructure, not just deploy apps.

**What is Terraform Plan?**
Dry-run that shows exactly what will change (create/update/destroy) before executing.

**Why we need it:**
- Catch mistakes before they happen (accidentally deleting production database).
- Required approval step before destructive changes.

Typical repo layout:

~~~text
terraform/
 |
 +-- vpc/
 +-- iam/
 +-- eks/
 +-- rds/
 +-- redis/
 +-- s3/
 +-- alb/
~~~

Architect-level point:

- Promote infrastructure changes through the same quality gates as code.
- Enforce review, drift control, and rollback paths.

## Step 10: Push Image to ECR

~~~text
Developer / CI Pipeline
          |
          v
    Docker Image
          |
          v
         ECR
          |
          v
         EKS
~~~

**What is ECR (Elastic Container Registry)?**
Private Docker image registry managed by AWS.

**Why we need ECR (vs Docker Hub):**

- **Security**: Images stored in your AWS account, not public registry. Integrated with IAM.
- **Vulnerability scanning**: Automatic scanning for CVEs in images.
- **Performance**: Images pull faster within same AWS region - lower latency to EKS.
- **Lifecycle policies**: Auto-delete old/unused images to save storage costs.
- **Audit trail**: CloudTrail logs who pushed/pulled which image.
- **No rate limits**: Docker Hub has pull rate limits; ECR doesn't.
- **Compliance**: Keep container images within your compliance boundary.

Example tags:

~~~text
ECR
 |
 +-- order-service:1.0
 +-- order-service:1.1
 +-- order-service:1.2
~~~

Architect-level point:

- **Tag images with immutable identifiers (commit SHA)**: Ensures exact version deployed is traceable to source code commit.
- **Keep promotion flow auditable across environments**: Same image (verified in dev) promotes to prod - no rebuild, no drift.

## Step 12: Expose Through DNS and Load Balancer

~~~text
User
 |
 v
Route 53
 |
 v
ALB
 |
 v
Kubernetes Service
 |
 v
Spring Boot Pods
~~~

### Ingress Components Explained:

**1. Route 53**
- **What:** AWS DNS service that translates domain names (api.company.com) to IP addresses.
- **Why we need it:**
  - **Custom domains**: Users access api.company.com instead of ugly ALB DNS name.
  - **Health checks**: Auto-route traffic away from unhealthy regions/endpoints.
  - **Geo-routing**: Route EU users to EU region, US users to US region.
  - **Failover**: Automatically switch to DR region if primary fails.
  - **Weighted routing**: Gradually shift traffic during blue-green deployments (90% old, 10% new).

**2. ALB (Application Load Balancer)**
- **What:** Layer 7 (HTTP/HTTPS) load balancer that distributes traffic across multiple targets.
- **Why we need it:**
  - **High availability**: Distributes requests across multiple EKS pods in different AZs.
  - **SSL termination**: Handles HTTPS encryption/decryption so pods don't have to.
  - **Path-based routing**: /orders → Order Service, /payments → Payment Service (single ALB, multiple microservices).
  - **Health checks**: Only sends traffic to healthy pods.
  - **Sticky sessions**: Route same user to same pod (if needed for stateful apps).
  - **WAF integration**: Attach Web Application Firewall for protection against SQL injection, XSS.
  - **Auto-scaling**: Scales capacity automatically based on traffic.

**3. Kubernetes Service**
- **What:** K8s abstraction that provides stable IP/DNS for a set of pods.
- **Why we need it:**
  - **Stable endpoint**: Pods get replaced frequently (deployments, crashes) with new IPs. Service provides fixed IP.
  - **Load balancing**: Distributes traffic across healthy pod replicas.
  - **Service discovery**: Other services can call order-service.default.svc.cluster.local without knowing pod IPs.

Key point:

- **ALB handles request distribution and ingress integration**: Internet → ALB → K8s cluster.
- **Route 53 manages DNS and can be used for health-aware routing**: Monitors endpoint health and routes accordingly.

## Step 13: Configuration and Secrets

Do not hardcode secrets into images.

Wrong approach:

~~~text
DB_PASSWORD=abc123
~~~

Preferred:

~~~text
Secrets Manager
       |
       v
     EKS
       |
       v
Spring Boot
~~~

**What is Secrets Manager?**
AWS service for securely storing, retrieving, and rotating secrets (passwords, API keys, certificates).

**Why we need Secrets Manager (vs environment variables in Docker):**

- **Security**: Secrets encrypted at rest with KMS, not plain text in images/config.
- **No Git leaks**: Secrets never appear in source code, Dockerfile, or Git history.
- **Automatic rotation**: Rotate database passwords without redeploying applications.
- **Audit trail**: CloudTrail logs every secret access - know who accessed what, when.
- **Fine-grained access**: IAM controls which services can read which secrets.
- **Dynamic retrieval**: Application fetches secrets at startup, not baked into image.

**Why this matters:**
- Docker images are immutable artifacts that get pushed to registries, stored, scanned, copied across environments.
- If DB password is in the image, anyone with ECR access sees it.
- With Secrets Manager, image contains NO sensitive data - only reference to secret name.

**What are ConfigMaps / Parameter Store?**
- **ConfigMaps (Kubernetes)**: Store non-sensitive config (feature flags, API endpoints, timeouts).
- **Parameter Store (AWS)**: AWS service for storing config and encrypted secrets (lightweight alternative to Secrets Manager).

**Why separate config from secrets:**
- Config (log level, timeout values) can be version-controlled and visible to developers.
- Secrets (passwords, private keys) must never appear in Git, logs, or error messages.

Use ConfigMaps or Parameter Store for non-sensitive config.

## Step 14: CI/CD End-to-End Automation

~~~text
Developer
    |
    v
Git Push
    |
    v
CI/CD
    |
    +---- Unit Tests
    +---- SonarQube
    +---- Security Scan
    +---- Build JAR
    +---- Docker Build
    +---- Push Image -> ECR
    +---- Deploy -> EKS
    |
    v
Production
~~~

**What is CI/CD (Continuous Integration / Continuous Deployment)?**
Automated pipeline that builds, tests, and deploys code on every commit.

**Why we need CI/CD:**

- **Speed**: Deploy multiple times per day vs monthly manual releases.
- **Quality**: Every commit is tested automatically before merge.
- **Consistency**: Same deployment process every time, no human error.
- **Fast feedback**: Developers know within minutes if their code breaks tests.
- **Rollback**: Previous image version is one click away in ECR.
- **Reduced risk**: Small, frequent changes are easier to debug than large quarterly releases.

### Pipeline Stage Components Explained:

**1. Unit Tests**
- **What:** Automated tests that verify individual functions/classes work correctly.
- **Why:** Catch bugs before they reach production. Failed tests block merge.

**2. SonarQube**
- **What:** Static code analysis tool that scans for code quality issues.
- **Why:** Detects code smells, security vulnerabilities, technical debt, test coverage gaps.

**3. Security Scan**
- **What:** Tools like Snyk, Trivy that scan dependencies and Docker images for known CVEs.
- **Why:** Block deployment if vulnerable libraries detected (e.g., Log4Shell).

**4. Build JAR**
- **What:** Compile Java source code into executable .jar file.
- **Why:** Create deployable artifact from source code.

**5. Docker Build**
- **What:** Package JAR + JVM + OS into immutable container image.
- **Why:** "Works on my machine" → "works everywhere". Consistent runtime across environments.

**6. Push Image → ECR**
- **What:** Upload Docker image to private registry with unique tag (commit SHA).
- **Why:** Versioned artifact storage for deployment and rollback.

**7. Deploy → EKS**
- **What:** Update Kubernetes deployment to use new image version.
- **Why:** Zero-downtime rolling update - new pods start before old pods terminate.

Architect-level point:

- **Guard production with approval or policy gates**: Manual approval step before prod deploy for compliance.
- **Keep deploys repeatable and rollback-friendly**: Same pipeline script works in all environments; previous versions always available.

## Step 15: Observability and Operations

~~~text
Spring Boot
    |
    +---- Logs
    +---- Metrics
    +---- Traces
             |
             v
        Monitoring
~~~

### Observability Components Explained:

**1. Logs**
- **What:** Timestamped text records of application events (requests, errors, state changes).
- **Why we need logs:**
  - **Debugging**: See exact error message and stack trace when issue occurs.
  - **Audit trail**: Who did what, when (user login, order placement, payment failure).
  - **Compliance**: Retain logs for regulatory requirements.
  - **Troubleshooting**: Search for specific customer ID or transaction across all services.
  - **Tools:** CloudWatch Logs, ELK Stack (Elasticsearch, Logstash, Kibana), Splunk.

**2. Metrics**
- **What:** Numeric measurements collected over time (CPU %, request count, latency, error rate).
- **Why we need metrics:**
  - **Performance monitoring**: Is response time acceptable? (p95, p99 latency)
  - **Capacity planning**: CPU trending up → need to scale before hitting limit.
  - **SLA tracking**: 99.9% uptime requires measuring actual uptime.
  - **Alerting**: Trigger alerts when thresholds breached (error rate > 5%).
  - **Tools:** CloudWatch Metrics, Prometheus, Datadog, Grafana.

**3. Traces**
- **What:** End-to-end tracking of single request across multiple microservices.
- **Why we need traces:**
  - **Distributed debugging**: Request took 5 seconds - which service was slow?
  - **Bottleneck identification**: Gateway → Order → Payment → Inventory - which hop failed?
  - **Latency breakdown**: 80% of time spent in database query, not application code.
  - **Service dependencies**: Visualize which services call which.
  - **Tools:** AWS X-Ray, Jaeger, Zipkin, Datadog APM.

**4. CloudWatch Alarms**
- **What:** Rules that trigger notifications when metrics cross thresholds.
- **Why we need alarms:**
  - **Proactive response**: Know about issues before customers complain.
  - **On-call automation**: Page engineer when CPU > 80% for 5 minutes.
  - **Auto-scaling triggers**: Scale up when request count exceeds capacity.
  - **Incident response**: Integrate with PagerDuty, Slack, email.

Example alerting:

~~~text
CPU > 80%
     |
     v
CloudWatch Alarm
     |
     v
Alert
~~~

**Why this pattern:**
- Reactive monitoring (checking dashboards) doesn't scale - you can't watch 50 services 24/7.
- Alarms bring issues to you automatically.

**Why THREE pillars (logs, metrics, traces):**
- **Metrics** tell you WHAT is broken (high error rate).
- **Logs** tell you WHY it broke (NullPointerException in OrderService.java:142).
- **Traces** tell you WHERE in the request flow it broke (Payment Service → Database timeout).

Use CloudWatch baseline plus optional Prometheus/Grafana and tracing stack.

## Important Correction to Sound Truly Senior

Infrastructure creation and application deployment are not always strictly sequential.

In strong organizations:

- Platform/infrastructure teams and application teams work in parallel.
- CI/CD may provision infrastructure through IaC pipelines.
- Application pipelines can be decoupled and release independently.
