## NEW LEARNER FOUNDATION — Read This First If You Are New

```
KEY TERMS EXPLAINED SIMPLY
============================

DATABASE CONNECTION
  Every time your app talks to a database, it opens a "connection" —
  a dedicated channel (TCP socket) from your app to the DB server.
  Opening a connection takes 20-50ms and uses memory on both sides.
  Think of it like a phone call — you dial, wait for answer, then talk.

CONNECTION POOL (HikariCP)
  Instead of opening/closing a connection for every request, a pool
  keeps N connections open and reuses them. Request comes in → borrow
  a connection → use it → return it to pool.
  HikariCP is the fastest connection pool library for Java/Spring Boot.
  It is included by default in Spring Boot — no extra setup needed.

  Without pool: 1000 requests → 1000 connection open/close → slow + expensive
  With pool:    1000 requests → 10 connections reused → fast + efficient

RDS (Relational Database Service)
  AWS-managed MySQL / PostgreSQL / SQL Server. AWS handles backups,
  patching, and hardware. You just use it like a normal database.

AURORA
  AWS's own cloud-native database — compatible with MySQL and PostgreSQL
  but 5x faster. Storage is automatically replicated across 3 Availability
  Zones (data centres) in 6 copies. You pay only for what you use.

MULTI-AZ
  Running your database in multiple Availability Zones (physical data centres
  in the same region). If one data centre has a power cut, your DB
  automatically switches to another — zero manual work from you.

READ REPLICA
  A copy of your database that only handles READ queries (SELECT).
  Your app reads from replicas to reduce load on the main (primary) DB.
  Writes (INSERT/UPDATE/DELETE) always go to the primary only.

RDS PROXY
  A middleman that sits between your app and the database. 200 pods can
  connect to the proxy → proxy maintains only 20 real DB connections.
  Think of it as a shared taxi — 200 people use 20 taxis, not 200.

max_connections
  The maximum number of simultaneous connections Aurora can handle.
  For db.r5.large: ~1000. Exceed this → "too many connections" error.
  RDS Proxy prevents your app from ever hitting this limit.
```

### OPENING — When They Ask: "How do you manage database connections in production on AWS?"

> **You say:**
>
> "Database connection management is one of the most common root causes of production
> incidents I've seen. The two scenarios that have woken me up at 3 AM are: connection
> pool exhaustion when traffic spikes, and stale connections after an RDS failover.
>
> For Flipkart's order service on ECS Fargate, we solved both with a combination of:
> properly tuned HikariCP inside the application, and RDS Proxy in front of Aurora.
>
> Let me walk through the problem first, then the solution."

### PART 1 — When They Ask: "What is RDS Proxy and when do you need it?"

> **You say:**
>
> "RDS Proxy sits between your application and RDS/Aurora. It maintains a warm pool
> of database connections and multiplexes many application connections onto fewer
> database connections.
>
> You need it in three cases:
> First: Lambda functions. Each Lambda invocation opens a new DB connection —
> 1000 concurrent Lambdas = 1000 connection attempts. RDS Proxy absorbs this.
>
> Second: ECS/EKS with many tasks. If you run 50 Fargate tasks, each with a
> connection pool of 10, that's 500 connections. Add autoscaling and you can hit
> Aurora's max_connections limit during a traffic spike.
>
> Third: Blue-green deployments and failovers. RDS Proxy handles the switchover
> transparently — your app's connections stay alive through the proxy even while
> Aurora is failing over."

```
RDS PROXY — HOW MULTIPLEXING WORKS
=====================================

  Application Connections (many)      DB Connections (few)
  ─────────────────────────────────────────────────────────

  Task-1 conn-1  ──┐
  Task-1 conn-2  ──┤
  Task-2 conn-1  ──┤                  DB conn-1 ─── Aurora
  Task-2 conn-2  ──┼──► RDS Proxy ──► DB conn-2 ─── Aurora
  Task-3 conn-1  ──┤   (pools &       DB conn-3 ─── Aurora
  ...            ──┤  multiplexes)    ...
  Task-50 conn-10─┘

  500 app connections → 20 DB connections (25× reduction)

  HOW MULTIPLEXING WORKS:
  - When your transaction is idle (between SQL statements):
    Proxy can lend that DB connection to another app connection
  - When your transaction is active:
    DB connection is "pinned" to your app connection for duration
  - Pinning triggers: SET commands, stored procedures, some prepared statements
    (avoid these with RDS Proxy — they prevent multiplexing)
```

```yaml
# application.yml — RDS Proxy endpoint replaces direct RDS endpoint
spring:
  datasource:
    # Use the RDS Proxy endpoint, NOT the cluster endpoint
    url: jdbc:postgresql://flipkart-order-proxy.proxy-xxx.us-east-1.rds.amazonaws.com:5432/orders
    username: ${DB_USERNAME}        # from AWS Secrets Manager (RDS Proxy uses IAM auth)
    password: ${DB_PASSWORD}
    hikari:
      maximum-pool-size: 10         # per-task pool (proxy handles the rest)
      minimum-idle: 2
      connection-timeout: 3000      # 3s — fail fast, don't queue forever
      idle-timeout: 600000          # 10 min — less than RDS Proxy idle timeout (30 min)
      max-lifetime: 1800000         # 30 min — MUST be less than RDS Proxy connection lifetime
      validation-timeout: 1000
      connection-test-query: SELECT 1
```

### PART 2 — When They Ask: "How does Aurora Multi-AZ work? What happens on failover?"

> **You say:**
>
> "Aurora is fundamentally different from RDS Multi-AZ. Let me explain both.
>
> Standard RDS Multi-AZ: you have one primary and one standby. The standby is
> NOT serving traffic — it's a hot standby only. If primary fails, Aurora promotes
> the standby. DNS switches. Takes about 60 seconds.
>
> Aurora: the storage layer is always replicated across 3 AZs regardless. What you
> configure separately are read replicas — they serve live read traffic and act as
> failover candidates.
>
> With Aurora, failover is faster — typically 30 seconds — because a read replica
> is already serving queries and just needs to be promoted. No standby waiting idle."

```
AURORA MULTI-AZ ARCHITECTURE — Flipkart
=========================================

  AZ-1 (us-east-1a)    AZ-2 (us-east-1b)    AZ-3 (us-east-1c)
  ─────────────────    ─────────────────    ─────────────────
  Aurora Primary       Aurora Replica-1     Aurora Replica-2
  (writer) ←           (reader) ←           (reader) ←
                        ↑                    ↑
  Shared Aurora Storage Layer (6 copies across 3 AZs — always)
  ─────────────────────────────────────────────────────────────
  Data never lost even if 2 AZs fail simultaneously

  ENDPOINTS:
  Cluster endpoint (writer):  flipkart-orders.cluster-xxx.rds.amazonaws.com
    └── always points to the current PRIMARY
    └── use for all WRITE operations

  Reader endpoint:            flipkart-orders.cluster-ro-xxx.rds.amazonaws.com
    └── load-balanced across all read replicas
    └── use for read-only queries (reports, search, order history)

  FAILOVER SEQUENCE (Primary fails):
  T+0s:   Primary crashes
  T+30s:  Aurora promotes Replica-1 to Primary
  T+30s:  Cluster endpoint DNS updated → points to new Primary
  T+90s:  Your application reconnects (if HikariCP configured correctly)
```

```java
// Spring Boot DataSource config for Aurora (handles failover gracefully)
@Bean
public HikariDataSource dataSource() {
    HikariConfig config = new HikariConfig();

    // Use cluster endpoint (not instance endpoint!) — survives failover
    config.setJdbcUrl("jdbc:postgresql://flipkart-orders.cluster-xxx.rds.amazonaws.com:5432/orders"
                    + "?connectTimeout=3&socketTimeout=30");
    config.setUsername(secretsManager.getUsername());
    config.setPassword(secretsManager.getPassword());

    config.setMaximumPoolSize(10);
    config.setMinimumIdle(2);
    config.setConnectionTimeout(3_000);
    config.setIdleTimeout(600_000);
    config.setMaxLifetime(1_800_000);

    // CRITICAL for failover: HikariCP must detect dead connections and reconnect
    config.setKeepaliveTime(60_000);            // keepalive every 60s (detects stale connections)
    config.setConnectionTestQuery("SELECT 1");   // validate connection before use

    return new HikariDataSource(config);
}
```

### PART 3 — Trap Questions the Interviewer Will Ask

---

#### Trap 1: "What happens if you use the read replica endpoint right after a write?"

> **You say:**
>
> "This is the read replica replication lag trap. When you write to the primary,
> Aurora replication is typically under 100ms but it's not zero. If your code writes
> an order and immediately reads it back via the reader endpoint, you may get a
> cache miss or stale data — the replica hasn't received the change yet.
>
> I've seen this cause a production bug where a user placed an order, was redirected
> to the order confirmation page, and the order wasn't there — because the
> confirmation page read from the replica.
>
> The fix is: read your own writes from the primary (use the writer endpoint for
> the confirmation fetch). Use read replicas only for genuinely independent reads
> like browsing, search, or reports."

```
REPLICATION LAG TRAP
=====================

  User: "Place Order" → POST /orders
                          │
                          ▼
                     OrderService
                     orderRepo.save(order)   ← writes to PRIMARY
                          │
                          │ redirect
                          ▼
                     GET /orders/12345       ← reads from READER ENDPOINT
                          │
                          ▼
                     Reader Replica          ← replication lag: 50-200ms
                     Order #12345?           ← NOT YET REPLICATED
                          │
                          ▼
                     Optional<Order>.empty() ← 404 returned!
                     → "Order not found" — but it exists on primary!

  FIX: Read-your-own-writes from PRIMARY for consistency-sensitive reads.
       Reserve reader endpoint for: reports, search, analytics, history.
```

```java
// Two DataSources: one for writes, one for reads
@Configuration
public class DataSourceConfig {

    @Bean("writeDataSource")
    public DataSource writeDataSource() {
        // Cluster endpoint (writer) — for writes and consistency-sensitive reads
        return buildDataSource("flipkart-orders.cluster-xxx.rds.amazonaws.com");
    }

    @Bean("readDataSource")
    public DataSource readDataSource() {
        // Reader endpoint — for reports, history, search
        return buildDataSource("flipkart-orders.cluster-ro-xxx.rds.amazonaws.com");
    }
}

// Route based on @Transactional(readOnly = true)
public class RoutingDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        return TransactionSynchronizationManager.isCurrentTransactionReadOnly()
            ? "READ" : "WRITE";
    }
}
```

#### Trap 2: "Instance endpoint vs Cluster endpoint — what's the difference and why does it matter?"

> **You say:**
>
> "Instance endpoint points to a specific Aurora instance by hostname — like
> `mydb-instance-1.xxx.rds.amazonaws.com`. Cluster endpoint points to whichever
> instance is currently the primary — like `mydb.cluster-xxx.rds.amazonaws.com`.
>
> The trap: if you hardcode the instance endpoint and Aurora fails over, the new
> primary is a different instance with a different endpoint. Your application
> is still pointing at the old primary — which is now a read replica and will
> reject writes with `ERROR: cannot execute INSERT in a read-only transaction`.
>
> Always use the cluster endpoint in application.properties. Never hardcode
> instance endpoints for the writer."

---

#### Trap 3: "HikariCP maxLifetime vs RDS Proxy idle timeout — what's the relationship?"

> **You say:**
>
> "RDS Proxy closes idle connections after a configurable idle timeout — default
> 30 minutes. HikariCP's `maxLifetime` should be set LESS than that timeout.
>
> If HikariCP maxLifetime is 60 minutes but RDS Proxy closes idle connections at
> 30 minutes — HikariCP thinks the connection is alive, hands it to a thread,
> the thread sends a query, gets a broken pipe exception, transaction fails.
>
> Rule: maxLifetime < RDS Proxy idle timeout - 30 seconds buffer.
> I set maxLifetime=1,740,000ms (29 min) when proxy idle timeout is 30 min."

```
HIKARICP vs RDS PROXY TIMEOUT — What Kills Your Connection
===========================================================

  Timeline:
  T+0s:     HikariCP creates connection → goes to idle pool
  T+1800s:  RDS Proxy: "this connection idle for 30 min" → closes it
  T+1830s:  Thread requests connection from HikariCP
  T+1830s:  HikariCP: "I have a connection! maxLifetime=3600s, it's only 30 min old"
            HikariCP hands dead connection to thread
  T+1830s:  Thread issues SQL → "Connection reset by peer" → transaction fails

  FIX: maxLifetime = (proxy idle timeout - 30s) in milliseconds
       RDS Proxy idle timeout = 1800s (30 min default)
       maxLifetime = (1800 - 30) × 1000 = 1,770,000ms
```

### PART 4 — Advanced Scenario: Lambda + RDS Proxy

> **You say:**
>
> "Lambda is the most extreme case. Each Lambda invocation is potentially a new
> process — it has no persistent state. Without RDS Proxy, 1000 concurrent
> Lambda invocations create 1000 new database connections simultaneously.
> Aurora db.r5.large max_connections is around 1000. You'll hit the limit.
>
> Lambda cold start time also includes TCP handshake and TLS negotiation with the
> DB — typically 20-50ms extra. RDS Proxy absorbs this: Lambda connects to the
> proxy (which keeps warm connections), and the proxy reuses an existing DB connection."

```
LAMBDA → RDS PROXY → AURORA
==============================

  Without RDS Proxy:
  ─────────────────
  1000 Lambda invocations
       │
       │ each opens a new DB connection
       ▼
  1000 TCP connections to Aurora   → hits max_connections
  Each connection: 20-50ms overhead
  Cold start problem: every new Lambda container = new connection

  With RDS Proxy:
  ──────────────
  1000 Lambda invocations
       │
       │ each connects to RDS Proxy (fast, proxy is in same VPC)
       ▼
  RDS Proxy (warm pool of 20 DB connections)
       │
       │ multiplexes 1000 → 20
       ▼
  Aurora: only 20 connections, never hits max_connections

  Lambda VPC Config:
  Lambda must be in SAME VPC as RDS Proxy (or VPC peered)
  Lambda security group: allow outbound to RDS Proxy security group on port 5432
  RDS Proxy security group: allow inbound from Lambda security group on port 5432
```

```java
// Lambda handler with connection pool (Hikari in Lambda)
public class OrderLambdaHandler implements RequestHandler<APIGatewayProxyRequestEvent, String> {

    // Static — shared across warm Lambda invocations (NOT recreated per invocation)
    private static final HikariDataSource dataSource = buildDataSource();

    private static HikariDataSource buildDataSource() {
        HikariConfig config = new HikariConfig();
        config.setJdbcUrl(System.getenv("RDS_PROXY_URL"));  // from Lambda env var
        config.setMaximumPoolSize(2);    // Lambda: small pool — most requests are short
        config.setMinimumIdle(1);
        config.setConnectionTimeout(3_000);
        config.setMaxLifetime(870_000);  // 14.5 min — Lambda max execution + buffer
        return new HikariDataSource(config);
    }

    @Override
    public String handleRequest(APIGatewayProxyRequestEvent event, Context context) {
        try (Connection conn = dataSource.getConnection()) {
            // Use connection
        }
    }
}
```

## Interview Cheat Sheet (Say This Confidently)

> "For Aurora in production: always use the cluster endpoint (not instance endpoint) for writes — it automatically points to the primary after failover. Use the reader endpoint only for read replicas, and be aware of replication lag — avoid reading from the replica immediately after a write if you need consistency. RDS Proxy is essential for Lambda (solves the 1000-connections problem) and for ECS with many tasks. The critical HikariCP tuning: maxLifetime must be less than RDS Proxy's idle connection timeout to avoid getting handed a dead connection. And keepalive should be enabled so HikariCP detects stale connections before a thread tries to use them."
