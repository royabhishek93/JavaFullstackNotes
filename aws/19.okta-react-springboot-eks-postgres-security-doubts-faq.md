# Okta, Keycloak, JWT, PostgreSQL, and EKS: Doubts Clearing FAQ

This file collects the questions raised while designing a production React, Spring Boot, EKS, Aurora PostgreSQL, and identity-provider architecture.

## 1. If Okta owns credentials, what does PostgreSQL store?

Okta stores the user's login credentials: password hash, MFA settings, password-reset flow, lockout rules, and login session.

PostgreSQL stores the application's data about that user: internal user ID, tenant membership, application role, profile preferences, orders, payments, and audit history.

```text
Rahul enters email + password
        |
        v
Okta verifies password
        |
        v
JWT: sub = 00uabc123
        |
        v
Spring Boot finds the application user in PostgreSQL
WHERE issuer = 'https://company.okta.com/oauth2/default'
  AND provider_subject = '00uabc123'
```

```text
Okta:       password, MFA, login, reset password, JWT issuance
PostgreSQL: tenant, application role, profile, orders, audit records
```

Do not store the same user's password in both Okta and PostgreSQL. That creates two competing authentication systems.

## 2. Why use `sub` instead of email?

`sub` is the stable unique identifier issued by the identity provider. Email is a profile attribute that can change.

```text
Today:    rahul@gmail.com    -> sub = 00uabc123
Tomorrow: rahul@company.com -> sub = 00uabc123
```

The application still recognizes the same person. Do not use email as the identity key.

## 3. Where should `provider_subject` be stored?

Keep it in both places, for different purposes:

- The IDP stores it as the identity's own identifier and sends it as the JWT `sub` claim.
- PostgreSQL stores a mapping so the application can resolve the JWT identity to its internal user.

```text
JWT
---
iss = https://company.okta.com/oauth2/default
sub = 00uabc123

PostgreSQL
----------
external_identity
  user_id = U-1001
  issuer = https://company.okta.com/oauth2/default
  provider_subject = 00uabc123
```

The safe external identity key is `issuer + sub`, because a `sub` is unique only within its issuer.

## 4. Is `app_user` and `external_identity` one database?

Usually yes at first: they are two tables in the application identity/profile database.

```text
Application PostgreSQL database
-------------------------------
app_user
external_identity
tenant_membership
application_role
audit_event
```

Business services such as Order and Payment should refer to the internal `user_id`, not to an Okta or Google subject.

At larger scale, the profile/mapping database may belong to a dedicated Identity Profile service. The principle stays the same: business records use internal `user_id`.

## 5. Why have an internal `user_id` at all?

It prevents identity-provider changes from rewriting business data.

```text
order.created_by_user_id = U-1001

Before: U-1001 -> Okta    -> sub 00uabc123
After:  U-1001 -> Keycloak -> sub 4fa9c8
```

Orders, payments, tenant memberships, and audit records still reference `U-1001`. Only the external identity mapping changes.

## 6. What if we use multiple IDPs?

One internal user can have multiple external identity mappings.

```text
app_user
--------
user_id = U-1001
tenant_id = acme
name = Rahul

external_identity
-----------------
user_id = U-1001 | provider = OKTA   | issuer = acme.okta.com | subject = 00u-okta-123
user_id = U-1001 | provider = GOOGLE | issuer = accounts.google.com | subject = google-789
```

On each request, Spring Boot validates the token against an allowed issuer, then resolves:

```sql
SELECT user_id
FROM external_identity
WHERE issuer = :issuer
  AND provider_subject = :subject;
```

Never automatically link users only by matching email. Ask the user to authenticate with the existing account, or run a verified enterprise migration using a trusted immutable identifier.

## 7. Does every IDP have a separate user/password database?

Logically, yes: each identity provider has an identity directory that owns credentials and authentication policy.

```text
Okta                 -> Okta-operated credential directory
Microsoft Entra ID   -> Microsoft/customer Entra directory
Auth0                -> Auth0-operated credential directory
Self-hosted Keycloak -> database operated by your company
```

The exact physical database implementation of a hosted provider is not your concern. It may be a distributed internal platform, not one visible database. What matters is that product microservices do not own or duplicate those password hashes.

## 8. Can one IDP delegate login to another IDP?

Yes. This is federation or identity brokering.

```text
React -> Okta -> redirects to customer Microsoft Entra ID
                              |
                              v
                    Entra authenticates password + MFA
                              |
                              v
                    Okta issues token for your application
```

In this case, the password may live only in the customer's Entra directory. Okta acts as the broker for your application.

## 9. Okta versus Keycloak: why are they different?

The protocol is similar: both can implement OpenID Connect and OAuth2. The operating model is different.

```text
Okta
----
Your application -> HTTPS -> Okta managed cloud
                              Okta handles availability, upgrades,
                              credential directory, MFA, and patching.

Keycloak
--------
Your application -> HTTPS -> Keycloak in your EKS / VM / data center
                              Your company handles its database, availability,
                              upgrades, backups, patching, and incident response.
```

Choose Okta or another managed provider when identity is not your differentiator and you want a managed security platform. Choose Keycloak when you need self-hosting, strict data residency, deep customization, offline/on-prem support, or accept the operational responsibility.

## 10. What is discovery and a JWKS endpoint?

The IDP signs tokens with a private key. Your services must verify the signature with the matching public key. The IDP publishes public keys at its JSON Web Key Set (JWKS) endpoint.

```text
Okta private key -> signs JWT
Spring Boot      -> verifies JWT using Okta public key from JWKS
```

The OpenID Connect discovery document tells Spring Boot where the issuer's endpoints are:

```text
https://company.okta.com/oauth2/default/.well-known/openid-configuration
```

It contains a `jwks_uri`, such as:

```text
https://company.okta.com/oauth2/default/v1/keys
```

JWT header:

```json
{ "alg": "RS256", "kid": "key-2026-01" }
```

Validation flow:

```text
1. Spring Boot reads `iss` and `kid` from the token.
2. It obtains and caches the allowed issuer's public JWKS keys over HTTPS.
3. It selects the public key matching `kid`.
4. It verifies JWT signature, issuer, audience, expiry, and scopes.
```

JWKS avoids sharing private keys with microservices and allows the IDP to rotate signing keys without redeploying every service. Keys are cached; normal API requests do not call the IDP.

## 11. Which approach do most companies use?

Most companies use a centralized identity platform rather than storing password hashes in every product service:

- Managed IDP: Okta, Microsoft Entra ID, Auth0, Cognito, Ping.
- Central internal identity platform: common at very large companies.
- Self-hosted Keycloak: common where control, cost, or data residency warrants operating it.

The exact internal systems used by Amazon or Flipkart are not public. At their scale, the standard pattern is still centralized authentication and credential handling, separate from order, payment, catalog, and other product databases.

## 12. What does real production flow look like?

```text
1. User opens app.acme.com.
2. React redirects to the tenant's configured IDP using Authorization Code + PKCE.
3. The IDP authenticates password, passkey, SSO, and/or MFA.
4. IDP returns an access token with iss, sub, aud, expiry, and scopes.
5. React calls Order API with Bearer access token.
6. Order API validates the token locally using cached JWKS public keys.
7. Order API resolves issuer + sub to internal user_id and tenant membership.
8. Order API performs object-level authorization and PostgreSQL RLS.
9. Order API calls other services using service identity/client credentials where appropriate.
10. Logs record correlation ID, internal user ID, tenant, authorization outcome, and deployment version; never tokens or passwords.
```

## 13. Where does EKS fit, and why are there two pods?

EKS runs stateless Spring Boot application containers. It is not the identity provider and it should not run PostgreSQL for this architecture.

```text
Public:     WAF -> ALB / Ingress
Private:    EKS Order API, Payment API, Catalog API: minimum 2 replicas each
Database:   Aurora PostgreSQL + RDS Proxy in private DB subnets
External:   Okta / Entra / Auth0 over HTTPS
```

Two replicas provide minimum availability for a single pod failure or rolling update. Production requires more than the number two: topology spreading across nodes/AZs, readiness probes, a PodDisruptionBudget, HPA, and adequate node capacity.

## 14. User identity, application identity, and workload identity: what is the difference?

```text
User identity        issuer + sub in JWT      Who is the human/client?
Application identity internal user_id         Which tenant and application data belong to them?
Workload identity    IRSA IAM role            Which AWS APIs can this pod call?
```

An Okta JWT scope does not grant AWS S3 permissions. An IRSA IAM role does not prove that the human may refund an order. Keep these three authorization systems separate.

## 15. Senior interview answer

"I use a provider-neutral internal `user_id` and map every external login through a unique `issuer + sub` record. A hosted provider like Okta runs its credential platform outside my EKS cluster; self-hosted Keycloak is my operational responsibility. React uses PKCE, services validate signed tokens locally with cached JWKS public keys, and business records use internal IDs. This lets us support multiple IDPs or migrate one without rewriting orders and payments, while keeping credentials centralized and tenant authorization inside our application and database."
