## NEW LEARNER FOUNDATION — Read This First If You Are New

```
KEY TERMS EXPLAINED SIMPLY
============================

EVENT BUS
  A channel that receives events and routes them to targets.
  Think of it like a postal sorting facility: mail (events) arrives,
  sorting rules examine the address (event content), and mail is
  delivered to the right destination (target).
  AWS has a default event bus (AWS service events) and you create
  custom buses for your application events.

EVENT
  A JSON message describing something that happened.
  Example: "OrderPlaced", "PaymentFailed", "VideoUploaded".
  Every EventBridge event has a standard envelope:
    source      → who sent it ("com.swiggy.orders")
    detail-type → what happened ("OrderPlaced")
    detail      → the actual payload (order JSON)

RULE
  A filter + target definition attached to an event bus.
  "When an event matches THIS pattern, send it to THAT target."
  One bus can have up to 300 rules. One rule can have up to 5 targets.

EVENT PATTERN
  The JSON filter inside a rule. Supports exact match, prefix,
  numeric range, exists check, anything-but — all on nested fields.
  This is the killer feature: route DIFFERENT events to DIFFERENT
  targets based on content, not just topic name.

TARGET
  Where EventBridge delivers the matched event.
  20+ native targets: Lambda, SQS, SNS, Step Functions, Kinesis,
  API Gateway, ECS task, CodePipeline, and more.

EVENTBRIDGE SCHEDULER
  A fully managed job scheduler — like cron, but serverless.
  Cron schedules (recurring) and one-time schedules (fire once at
  an exact datetime, then auto-delete). Replaces cron containers,
  Quartz clusters, and hand-rolled timer services.

EVENTBRIDGE PIPES
  Point-to-point integrations between a source (DynamoDB Stream,
  Kinesis, SQS) and a target with optional filtering and enrichment.
  Zero Lambda glue code for simple routing between AWS services.

DEAD-LETTER QUEUE (DLQ)
  When EventBridge cannot deliver to a target (Lambda throttled,
  target unavailable), it retries for up to 24 hours with
  exponential backoff. After all retries fail, it writes the event
  to an SQS DLQ so you can inspect and replay it.
  Without a DLQ: failed events are silently dropped.
```

### OPENING — When They Ask: "Walk me through how you handle event-driven communication in your architecture."

> **You say:**
>
> "I use three messaging services that look similar but solve different problems.
> SNS for push fan-out to multiple subscribers — one message, many receivers,
> no filtering. SQS for work queues — tasks that need exactly-once processing,
> retry, and a DLQ.
>
> EventBridge is for content-based routing — when the destination depends on
> what is INSIDE the event. On a payment system, a failed payment for $50,000
> needs to go to fraud detection. A successful payment goes to notification and
> analytics. With SNS you'd send to all subscribers and filter in Lambda. With
> EventBridge, the bus itself routes — no Lambda tax on the filtering.
>
> Then EventBridge Scheduler for any time-triggered work. And EventBridge Pipes
> when I need to connect a DynamoDB stream to a target without writing boilerplate
> Lambda glue code.
>
> Let me draw the architecture and go deep on each."

### SECTION 1 — When They Ask: "EventBridge vs SNS vs SQS — when do you use each?"

> **You say:**
>
> "This is the decision I make upfront in any event-driven design.
>
> SNS: push-based fan-out. One message goes to all subscribers simultaneously.
> Supports email, SMS, HTTP, SQS, Lambda. But no content-based filtering at the
> SNS level — every subscriber gets every message and must filter themselves.
> No replay — once delivered, it's gone.
>
> SQS: pull-based queue. Consumers poll for messages. Competing consumers share
> work — N consumers pulling from one queue each process different messages.
> Built-in retry and DLQ. Perfect for task queues where you want one worker
> to process each job exactly once.
>
> EventBridge: content-based routing. The bus reads the event JSON and routes
> to different targets based on field values. A FAILED payment event goes to
> fraud Lambda. A SUCCEEDED payment event goes to notification Lambda. The
> decision is made at the infrastructure layer, not in application code.
> 100+ AWS services can publish natively. 20+ target types natively.
>
> Scheduled jobs: EventBridge Scheduler — not cron containers, not Quartz."

```
SNS vs SQS vs EVENTBRIDGE — DECISION TREE
==========================================

  New event-driven requirement
          │
          ▼
  Do multiple services need the same event?
  ├── YES → Do they all need EVERY event, no filtering?
  │         ├── YES → SNS (simple fan-out, cheapest)
  │         └── NO  → EventBridge (content-based routing)
  │
  └── NO  → Is it a work queue (one consumer processes each task)?
            ├── YES → SQS (competing consumers, retry, DLQ)
            └── NO  → Is it time-triggered?
                      ├── YES → EventBridge Scheduler
                      └── NO  → EventBridge (single target, content-filtered)

  COST (approximate):
  SNS:          $0.50/million notifications
  SQS:          $0.40/million requests
  EventBridge:  $1.00/million custom events (but no per-rule cost)
  Scheduler:    $1.00/million scheduled invocations (first 14M/month free)
```

### SECTION 2 — When They Ask: "How does content-based filtering work in EventBridge?"

> **You say:**
>
> "An EventBridge rule has an event pattern — a JSON document that acts as a
> filter. EventBridge compares the incoming event against the pattern. Only
> events that match ALL conditions in the pattern trigger the rule.
>
> The pattern supports: exact match (string equality), prefix match, numeric
> range comparisons, exists/not-exists checks, and anything-but (exclusion).
> Critically, it works on NESTED JSON fields — I can filter on
> `detail.payment.status` or `detail.metadata.region`. SNS message filtering
> only works on flat message attributes, not nested JSON.
>
> Let me show you the fraud alert rule: route only FAILED payments over $10,000."

```json
// Rule: Fraud Alert — route only FAILED payments over $10,000
// EventBridge Event Pattern (the filter on the rule)
{
  "source": ["com.swiggy.payment"],
  "detail-type": ["PaymentProcessed"],
  "detail": {
    "status": ["FAILED"],
    "amount": [{ "numeric": [">", 10000] }]
  }
}
```

```json
// Rule: Route by region — India payments to India fraud team
{
  "source": ["com.swiggy.payment"],
  "detail-type": ["PaymentProcessed"],
  "detail": {
    "status": ["FAILED"],
    "metadata": {
      "region": ["IN"]
    },
    "amount": [{ "numeric": [">=", 5000, "<", 100000] }]
  }
}
```

```json
// All pattern operators available:
{
  "detail": {
    "status": ["FAILED"],                          // exact match
    "orderId": [{ "prefix": "ORD-2026" }],         // prefix match
    "amount": [{ "numeric": [">", 10000] }],       // numeric range
    "promoCode": [{ "exists": false }],            // field must NOT exist
    "paymentMethod": [{ "anything-but": ["COD"] }] // exclude COD payments
  }
}
```

> **Key differentiator from SNS:**
>
> "SNS message filtering works on flat MessageAttributes you attach manually.
> EventBridge pattern matching works on the actual JSON payload, including
> nested objects, without any extra attributes. For a complex order event with
> nested payment, customer, and item arrays, EventBridge lets me filter deep
> into the structure."

```
DLQ ON RULE — What Happens When Target Fails
=============================================

  EventBridge ──► [fraud-alert Lambda]
                     │
                     └── Lambda throttled (concurrency limit hit)
                              │
                              ▼ EventBridge retries with exponential backoff
                              ▼ (retries for up to 24 hours)
                              │
                         All retries exhausted
                              │
                              ▼
                     [DLQ: SQS fraud-alert-dlq]
                              │
                              ▼
                     CloudWatch alarm fires
                     On-call engineer inspects event
                     Manual replay via EventBridge replay feature

  Rule config:
  DeadLetterConfig:
    Arn: arn:aws:sqs:ap-south-1:123456789:fraud-alert-dlq

  WITHOUT DLQ: throttled events are silently dropped — you never know
  WITH DLQ:    failed events land in SQS for inspection and replay
```

### SECTION 3 — When They Ask: "How do you handle scheduled jobs in production?"

> **You say:**
>
> "On the Job Scheduler system, every job has a scheduled execution time. The
> naive approach is a polling loop — a Lambda or container running every minute,
> querying the DB for jobs due in the next minute. At 10,000 jobs per day that's
> 10,000 unnecessary DB polls per minute.
>
> The correct approach is EventBridge Scheduler. When a job is created with a
> scheduled time, I call SchedulerClient.createSchedule with the exact ISO
> datetime. EventBridge fires exactly at that time, invokes the Lambda, and I
> delete the schedule after execution. Zero polling, exact timing, serverless.
>
> For recurring jobs — like a daily report at 2am UTC — I use a cron schedule.
> For one-time jobs — send a notification at 3pm on Dec 25 — I use an at()
> expression. The schedule auto-deletes after firing."

```
JOB SCHEDULER — EventBridge Scheduler Architecture
===================================================

  Job Created (API request)
       │  jobId: "job-789"
       │  scheduledAt: "2026-09-01T15:00:00Z"
       │
       ▼
  Job Service
       │
       ├──► RDS: INSERT job (status=SCHEDULED)
       │
       └──► SchedulerClient.createSchedule(
                name: "job-789",
                scheduleExpression: "at(2026-09-01T15:00:00)",
                target: jobExecutorLambdaARN,
                flexibleTimeWindow: FLEXIBLE (±5 min)
            )
                    │
                    │  ... time passes ...
                    │
                    ▼
           2026-09-01T15:00:00 UTC fires
                    │
                    ▼
           jobExecutor Lambda invoked
                    │
                    ├──► Execute job logic
                    ├──► RDS: UPDATE job (status=COMPLETED)
                    └──► SchedulerClient.deleteSchedule("job-789")

  RECURRING JOBS (daily report):
  scheduleExpression: "cron(0 2 * * ? *)"  ← 2am UTC every day
  (cron format: min hour day-of-month month day-of-week year)

  ONE-TIME JOBS:
  scheduleExpression: "at(2026-12-25T00:00:00)"
  ActionAfterCompletion: DELETE  ← schedule auto-deletes after firing
```

```java
// Java SDK v2 — Create one-time schedule for a job
import software.amazon.awssdk.services.scheduler.SchedulerClient;
import software.amazon.awssdk.services.scheduler.model.*;

@Service
public class JobSchedulerService {

    private final SchedulerClient schedulerClient;

    public JobSchedulerService(SchedulerClient schedulerClient) {
        this.schedulerClient = schedulerClient;
    }

    public void scheduleJob(String jobId, Instant scheduledAt, String lambdaArn, String roleArn) {
        // Format: at(2026-09-01T15:00:00)
        String expression = "at(" + scheduledAt.toString().replace("Z", "") + ")";

        Target target = Target.builder()
            .arn(lambdaArn)
            .roleArn(roleArn)
            .input("""
                {"jobId": "%s", "scheduledAt": "%s"}
                """.formatted(jobId, scheduledAt))
            .build();

        FlexibleTimeWindow flexWindow = FlexibleTimeWindow.builder()
            .mode(FlexibleTimeWindowMode.FLEXIBLE)
            .maximumWindowInMinutes(5)   // fire within ±5 min (reduces Lambda cold starts)
            .build();

        CreateScheduleRequest request = CreateScheduleRequest.builder()
            .name("job-" + jobId)
            .scheduleExpression(expression)
            .scheduleExpressionTimezone("UTC")   // ALWAYS specify timezone
            .target(target)
            .flexibleTimeWindow(flexWindow)
            .actionAfterCompletion(ActionAfterCompletion.DELETE)  // auto-cleanup
            .build();

        schedulerClient.createSchedule(request);
    }

    public void deleteSchedule(String jobId) {
        schedulerClient.deleteSchedule(
            DeleteScheduleRequest.builder()
                .name("job-" + jobId)
                .build()
        );
    }

    // Recurring job — daily analytics report at 2am UTC
    public void createDailyReport(String reportName, String lambdaArn, String roleArn) {
        Target target = Target.builder()
            .arn(lambdaArn)
            .roleArn(roleArn)
            .input("""{"report": "%s"}""".formatted(reportName))
            .build();

        CreateScheduleRequest request = CreateScheduleRequest.builder()
            .name("daily-report-" + reportName)
            .scheduleExpression("cron(0 2 * * ? *)")   // 2am UTC every day
            .scheduleExpressionTimezone("UTC")
            .target(target)
            .flexibleTimeWindow(FlexibleTimeWindow.builder()
                .mode(FlexibleTimeWindowMode.OFF)        // exact time for reports
                .build())
            .build();

        schedulerClient.createSchedule(request);
    }
}
```

```
CRON EXPRESSION REFERENCE (EventBridge format)
===============================================

  cron(Minutes Hours Day-of-month Month Day-of-week Year)

  cron(0 2 * * ? *)         Every day at 2:00 AM UTC
  cron(0 9 ? * MON-FRI *)   Weekdays at 9:00 AM UTC
  cron(0/15 * * * ? *)      Every 15 minutes
  cron(0 0 1 * ? *)         1st of every month at midnight
  cron(0 18 ? * FRI *)      Every Friday at 6:00 PM UTC
  cron(0 8 1 1 ? 2027)      Jan 1 2027 at 8:00 AM (one-time via cron)

  IMPORTANT: EventBridge cron uses ? for "no specific value"
  Day-of-month and Day-of-week cannot both be set — one must be ?
  Minimum resolution: 1 minute (not seconds)
```

### SECTION 4 — When They Ask: "What is EventBridge Pipes and when do you use it?"

> **You say:**
>
> "EventBridge Pipes solves a specific boilerplate problem. You have a DynamoDB
> stream — every write to a table produces a stream record. You want those
> records to flow into EventBridge so your routing rules can act on them. The
> old way: write a Lambda to consume the stream, do minimal transformation, and
> publish to EventBridge. That Lambda is pure infrastructure glue — no real
> business logic, just plumbing.
>
> EventBridge Pipes replaces that Lambda. You configure a Pipe with: source
> (DynamoDB stream), optional filter (only INSERT events, skip MODIFY/REMOVE),
> optional enrichment (call a Lambda or Step Function to transform), and target
> (EventBridge bus, SQS, SNS, Step Functions).
>
> For the OTT platform — when a new video record is inserted to DynamoDB, a Pipe
> filters to INSERT-only, transforms the stream record into a clean VideoUploaded
> event, and puts it on the EventBridge bus. Notification rules and transcoding
> rules then fire. Zero glue Lambda code."

```
WITHOUT PIPES — The Boilerplate Problem
========================================

  DynamoDB Table (videos)
       │ stream
       ▼
  [glue Lambda 1]           ← reads stream records
       │ transforms to event
       ▼
  [EventBridge bus]
       │
       ├──► notification Lambda
       └──► transcoder Step Function

  PROBLEM: glue Lambda 1 is pure plumbing — just transforms
  DynamoDB stream format into EventBridge event format.
  Must be deployed, monitored, scaled, billed separately.


WITH EVENTBRIDGE PIPES — Zero Glue Code
========================================

  DynamoDB Table (videos)
       │ stream
       ▼
  ┌──────────────────────────────────────────┐
  │  EventBridge PIPE: "video-upload-pipe"   │
  │                                          │
  │  Source:    DynamoDB Stream (videos)     │
  │  Filter:    eventName = "INSERT" only    │
  │             (skip MODIFY, REMOVE)        │
  │  Enrichment: (optional) Lambda to add   │
  │              CDN metadata               │
  │  Target:    EventBridge bus             │
  │             "swiggy-ott"               │
  └──────────────────────────────────────────┘
       │
       ▼
  [EventBridge bus]
       │
       ├──► notification Lambda  (Rule: VideoUploaded)
       └──► transcoder Step Fn   (Rule: VideoUploaded)

  COST: $0.40/million events through Pipe
  (cheaper than Lambda invocation overhead at scale)
```

```
EVENTBRIDGE PIPES — SOURCE FILTER EXAMPLE
==========================================

  DynamoDB Stream record (what Pipes receives):
  {
    "eventName": "INSERT",
    "dynamodb": {
      "NewImage": {
        "videoId": {"S": "vid-123"},
        "title":   {"S": "Inception"},
        "status":  {"S": "UPLOADED"}
      }
    }
  }

  Pipe Filter (only forward INSERT events):
  {
    "eventName": ["INSERT"]
  }

  → MODIFY and REMOVE events are dropped at the Pipe — never reach target
  → INSERT events flow through to enrichment (optional) then target

  ENRICHMENT LAMBDA (optional, sits between filter and target):
  - Receives filtered source record
  - Can call external APIs, add computed fields, transform structure
  - Returns enriched payload that gets delivered to target
  - If no enrichment needed: Pipe delivers directly to target
```

```
PIPES vs LAMBDA — When to Choose
==================================

  Use PIPES when:
    Source is DynamoDB Stream, Kinesis, SQS, or Managed Streaming for Kafka
    Routing logic is simple (filter by field value)
    Transformation is minimal or handled by enrichment Lambda
    You want to eliminate a standalone glue Lambda
    Cost at scale: $0.40/M vs Lambda invocation overhead

  Use LAMBDA when:
    Complex multi-step transformation logic
    Multiple source records need to be aggregated into one event
    Business logic beyond simple field mapping
    Source type not supported by Pipes
    Fan-out to multiple targets per source record
```

### SECTION 5 — When They Ask: "How does EventBridge Schema Registry help your team?"

> **You say:**
>
> "On a payment system with 12 microservices all publishing to EventBridge,
> the first question new developers ask is: what does a PaymentProcessed event
> look like? What fields are available? Schema Registry auto-discovers event
> schemas from traffic and stores them with version history.
>
> The killer feature is code binding generation. I can pull down the schema for
> PaymentProcessed and generate a typed Java POJO automatically. No more
> manually writing event classes, no more typos in field names, no more
> surprise null pointer exceptions because you expected `paymentAmount` but
> the schema changed to `amount`.
>
> Schema versioning tracks breaking changes — if someone removes a required
> field, the registry shows a new major version. Teams can pin to a version or
> migrate deliberately."

```

================================

#### Trap 1: "A rule matches an event and needs to fan-out to 10 targets. How?"

> **You say:**
>
> "This hits the 5-target limit. Each EventBridge rule supports a maximum of 5
> targets. If I need to fan-out to 10 services, I cannot add 10 targets to one
> rule.
>
> The pattern: Rule target 1 is an SQS queue. An SNS topic is behind that queue
> and fans out to the remaining subscribers. Or: rule target 1 is another
> EventBridge bus — the event lands on a second bus and 5 more rules each with
> 5 targets give me 25 targets total.
>
> In practice for an OTT platform: VideoUploaded rule → SQS → SNS → 10 notification
> channels. The EventBridge rule routes the event into the fan-out layer, not
> directly to each service."

```

       ├── Target 1: transcoder-sfn (Step Functions)
       ├── Target 2: analytics-kinesis (Kinesis Firehose)
       ├── Target 3: video-index-lambda
       ├── Target 4: SQS notification-fanout-queue   ←─────────────┐
       └── Target 5: audit-log-lambda                              │

  notification-fanout-queue                                        │
       │                                                           │
       ▼                                                           │

#### Trap 2: "Your event got lost — EventBridge delivered it but Lambda never processed it. How do you debug?"

> **You say:**
>
> "First check: did EventBridge deliver the event to the target? CloudWatch
> Metrics on the rule show SuccessfulInvocationCount and FailedInvocationCount.
> If SuccessfulInvocationCount is 0 — EventBridge never delivered it.
>
> Check the event pattern: enable EventBridge logging to CloudWatch. All events
> that hit the bus are logged, including whether they matched any rule. If the
> event arrived but matched no rule, the pattern filter is wrong.
>
> If EventBridge shows it delivered but Lambda didn't run: check Lambda's own
> CloudWatch logs. Lambda concurrency limit? Throttled?
>
> Always have a DLQ on the rule. If Lambda was throttled, EventBridge retries
> for up to 24 hours. After 24 hours, the event goes to DLQ. Without DLQ: gone."

```
EVENTBRIDGE DEBUGGING CHECKLIST
=================================

  Event published → bus
       │
       ├─ Did it arrive? → CloudWatch: EventBridge/PutEvents API calls
       │
       ├─ Did it match a rule? → Enable EventBridge CloudWatch logging
       │   (log level: ALL — shows matched AND unmatched events)
       │   EventBridge → Settings → Log all events to CloudWatch log group
       │
       ├─ Did delivery succeed? → CloudWatch metric: SuccessfulInvocationCount
       │   If 0: target ARN wrong? IAM role missing? Lambda throttled?
       │
       ├─ Did Lambda execute? → Lambda CloudWatch logs
       │   Check for: throttling, timeout, OOM, uncaught exception
       │
       └─ DLQ: check SQS DLQ for any failed events
                  (metadata on message: failure reason, attempt count)

  IAM CHECK — most common delivery failure:
  EventBridge needs an IAM role with permission to invoke the target.
  Each target needs its own IAM role (or the rule's role must cover all targets).
  Missing: events arrive at bus, pattern matches, but delivery fails silently.
```

#### Trap 3: "EventBridge Scheduler timezone — how do you handle users in IST scheduling jobs?"

> **You say:**
>
> "This is a real production trap I've seen. EventBridge Scheduler stores and fires
> in UTC by default. If a user in India (IST, UTC+5:30) schedules a job for 9:00 AM,
> you must convert to UTC — 3:30 AM UTC — BEFORE passing to SchedulerClient.
>
> The trap is when you pass the local time string without conversion. At 9:00 AM IST,
> `scheduleExpressionTimezone` defaults to UTC, and the job fires 5:30 hours early.
>
> Always set `scheduleExpressionTimezone` explicitly. If the user is in IST, set it
> to `Asia/Kolkata` and pass the user's local time. EventBridge handles the
> UTC conversion internally. Never assume UTC on both ends."

```java
// WRONG — passes local time, no timezone
CreateScheduleRequest bad = CreateScheduleRequest.builder()
    .scheduleExpression("at(2026-09-01T09:00:00)")   // user said 9am IST
    // no timezone → defaults to UTC → fires at 9am UTC = 2:30pm IST !!!
    .build();

// CORRECT — specify user's timezone
CreateScheduleRequest good = CreateScheduleRequest.builder()
    .scheduleExpression("at(2026-09-01T09:00:00)")   // 9am in user's timezone
    .scheduleExpressionTimezone("Asia/Kolkata")       // IST = UTC+5:30
    .build();
// EventBridge converts to UTC internally → fires at correct local time
```

## COMMON TRAPS — The 7 You Must Know

```
TRAP 1: 5-TARGET LIMIT PER RULE
  Each rule allows maximum 5 targets.
  FIX: Route to SQS → SNS fan-out, or route to a second EventBridge bus.

TRAP 2: 24-HOUR RETRY WINDOW
  EventBridge retries failed deliveries for up to 24 hours.
  After 24 hours: event is gone unless you have a DLQ configured on the rule.
  ALWAYS configure a DLQ (SQS) on every rule for production.

TRAP 3: 256KB EVENT SIZE LIMIT
  EventBridge events max out at 256KB per event.
  For large payloads (video metadata, order with 100 items): store payload in S3,
  publish the S3 key in the EventBridge event (claim-check pattern).
  FIX: { "s3Bucket": "events-store", "s3Key": "orders/ord-123.json" }

TRAP 4: SCHEDULER TIMEZONE PITFALL
  scheduleExpressionTimezone defaults to UTC if not set.
  Users in non-UTC timezones will get jobs firing at wrong times.
  FIX: Always set scheduleExpressionTimezone to user's IANA timezone.

TRAP 5: PIPES VS LAMBDA FOR COMPLEX TRANSFORMATION
  EventBridge Pipes is for simple filtering + enrichment.
  If transformation needs: aggregation, multiple API calls, conditional branching,
  fan-out per record → use Lambda, not Pipes enrichment.
  Pipes enrichment Lambda must return synchronously (max 5 min timeout).

TRAP 6: EVENTBRIDGE VS SNS FOR SIMPLE FAN-OUT
  EventBridge custom events cost $1.00/million.
  SNS costs $0.50/million notifications.
  For simple fan-out where all subscribers need all messages: SNS is cheaper
  and simpler. EventBridge overhead is only worth it when you need
  content-based routing, schema registry, or advanced patterns.

TRAP 7: IAM ROLE PER TARGET
  EventBridge needs an IAM execution role to invoke each target type.
  Lambda: Lambda resource-based policy (allow eventbridge.amazonaws.com)
  SQS: IAM role with sqs:SendMessage on the queue ARN
  Step Functions: IAM role with states:StartExecution
  Missing IAM → events arrive, match rule, but delivery silently fails.
  FIX: Check CloudWatch metric FailedInvocationCount on the rule.
```
