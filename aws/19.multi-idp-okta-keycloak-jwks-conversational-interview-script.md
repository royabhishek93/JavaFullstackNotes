# Multi-IDP Security Architecture: Conversational 15-YOE Interview Script

## Scenario

**Interviewer:** "We have React, Spring Boot microservices on EKS, Aurora PostgreSQL, and Okta. Tomorrow, one enterprise customer asks for Microsoft Entra ID, and another asks for Google login. How do you design this without rewriting the application?"

**You say:**

"I would first separate three concerns that teams often mix together: login identity, our application's business identity, and the AWS identity of a pod. Once those are separate, adding Okta, Entra, Google, or Keycloak becomes an identity-mapping change, not an order or payment migration. Let me walk through the request from browser to database."

## 1. Big Picture: Who Owns What?

```text
                         HUMAN LOGIN IDENTITY

  React SPA ---- OAuth2/OIDC + PKCE ----> Okta / Entra / Google / Keycloak
      |                                           |
      | Bearer access token                        | authenticates password,
      v                                           | passkey, SSO, MFA
+------------------------+                         |
| WAF -> ALB -> EKS      | <-----------------------+
| Spring Boot services   |
| validate token         |
+-----------+------------+
            |
            | issuer + sub -> internal user_id
            v
+------------------------+       +--------------------------+
| Identity/Profile DB    | ----> | Order / Payment databases|
| app_user               |       | business records use      |
| external_identity      |       | internal user_id          |
+------------------------+       +--------------------------+
            |
            v
  IRSA role -> AWS services: Secrets Manager, S3, SQS
```

### Why we choose this

**You say:** "The IDP proves who successfully logged in. Our application decides which tenant that person belongs to and what business objects they may access. IRSA gives a pod access to AWS; it does not authorize a human user. Keeping these boundaries separate prevents a login-provider change from changing business records."

### Cross questions

- Who owns password reset and MFA? The IDP.
- Who owns the user's orders and tenant membership? The application.
- Can an IAM role let a user refund an order? No. IAM authorizes a workload to AWS, not a user inside the application.

## 2. Okta Versus Keycloak

**Interviewer:** "Why are Okta and Keycloak different if both give JWT tokens?"

**You say:** "The protocol can be the same, but the operating responsibility is completely different. With Okta, I consume a managed identity platform. With Keycloak, I operate an identity platform."

```text
Managed Okta                               Self-hosted Keycloak
------------                               --------------------
Your EKS -> HTTPS -> Okta cloud            Your EKS -> Keycloak pods -> Keycloak DB
                      |                                  |
                      +-- Okta owns:                      +-- Your team owns:
                          upgrades                             upgrades
                          high availability                   HA and scaling
                          credential storage                  credential DB
                          MFA and recovery                    backup and restore
                          security patching                   CVE response
```

### Why we choose each

| Choice | Why pick it | Better fit | Two realistic examples |
|---|---|---|---|
| Okta or Entra | Outsource credential security and operations | Enterprise SSO, fast compliance | Employee SSO with Entra; B2B SaaS customers using Okta | 
| Keycloak | Full control over data and customization | On-prem, strict data residency, complex federation | Bank with isolated environment; telecom with private data center |

**Trade-off:** "A managed IDP has licensing and vendor dependency. Self-hosted Keycloak has infrastructure and security operations cost. I choose based on identity requirements, not because a JWT looks the same."

### Senior trap

**Interviewer:** "We run Keycloak with two pods. Is identity now highly available?"

**Strong answer:** "Not automatically. I also need a highly available database, shared or replicated cache/session design, anti-affinity across zones, backups tested through restore, key rotation, and a patching process. Two containers alone do not produce a resilient identity platform."

## 3. Where Do Passwords Actually Live?

**Interviewer:** "Do all IDPs maintain a separate database for username and password hash?"

**You say:** "Conceptually, each identity provider has a credential directory. The physical implementation may be distributed and hidden behind the provider's service. What matters to our product is that Order Service and Payment Service do not store or validate user passwords."

```text
Hosted provider                         Self-hosted provider
---------------                         --------------------
Okta: Okta-operated directory           Keycloak: company-operated DB
Entra: Microsoft/customer directory     Password hash managed by Keycloak
Auth0: Auth0-operated directory          MFA, backups, HA are our work

Application PostgreSQL
----------------------
NO user password hash for Okta users
YES: internal user_id, tenant, roles, business data, audit
```

### Why we choose this

**You say:** "A password system includes hashing, MFA, reset flows, lockouts, rate limits, breached-password detection, session revocation, and audit. Duplicating it in every product service creates avoidable attack surface."

### Cross questions

- What if a legacy product must keep local passwords? Use Argon2id, unique salts, a KMS-protected pepper, throttling, MFA, and a migration plan.
- Should we keep a BCrypt hash and Okta password for the same login? No, unless there is an explicit temporary migration design.

## 4. Provider Subject: The Bridge Between IDP and Business Data

**Interviewer:** "What is `provider_subject`, and why do we store it?"

**You say:** "The JWT's `sub` is the IDP's stable name for the authenticated identity. I store a mapping from `issuer + sub` to our own internal `user_id`. The internal ID is what every business table uses."

```text
JWT from Okta
-------------
iss = https://acme.okta.com/oauth2/default
sub = 00u-okta-123
              |
              | lookup by issuer + sub
              v
external_identity                  app_user                 order
-----------------                  --------                 -----
identity_id = I-501                user_id = U-1001         created_by = U-1001
user_id = U-1001  ----------------> tenant_id = acme
issuer = acme.okta.com
provider_subject = 00u-okta-123
```

### Why we choose this

**You say:** "Email can change. A provider subject is stable within an issuer. Our own `user_id` is stable forever inside the business. Therefore, we never make an Okta subject the foreign key for orders or payments."

```sql
CREATE UNIQUE INDEX external_identity_issuer_subject_uq
ON external_identity (issuer, provider_subject);
```

### Senior trap

**Interviewer:** "Can we auto-link Google and Okta accounts when their email matches?"

**Strong answer:** "No. Email may be changed, recycled, unverified, or controlled by a different identity authority. I require the user to authenticate with the existing identity, or use a verified enterprise migration with a trusted immutable mapping."

## 5. Multiple IDPs in One Real-Time Product

**Interviewer:** "How does it work when Acme uses Okta and Globex uses Entra?"

**You say:** "At login, React discovers the tenant's approved issuer from a trusted configuration, for example its custom domain. It redirects only to that allowed issuer. At the API, each token is accepted only if its issuer, JWKS key, audience, expiry, and scopes match an explicitly registered tenant configuration."

```text
acme.app.com   -> tenant config -> Okta issuer
globex.app.com -> tenant config -> Entra issuer
public app     -> login choice  -> Google issuer

After token validation:
issuer + sub -> external_identity -> user_id -> tenant membership -> authorization
```

### Why we choose this

Do not trust a `tenantId` header, URL parameter, or unvalidated `iss` supplied by the browser. The API uses an allow-list of issuer configurations. A token from a valid but unrelated IDP is still rejected.

### Cross questions

- How do we allow a user to belong to multiple tenants? Model `tenant_membership(user_id, tenant_id, role)` and require an explicit active tenant selection authorized by that membership.
- Should every microservice query the identity database on every request? Usually no. Validate the JWT locally, then use a short-lived cached membership/authorization lookup or a dedicated authorization service for complex policies.

## 6. JWKS and Discovery: How Spring Boot Trusts a Token

**Interviewer:** "What is JWKS, and why does Spring Boot call an endpoint over HTTPS?"

**You say:** "An IDP signs a JWT with its private key. It never gives that private key to our services. Instead it publishes public keys as a JWKS document. Spring Boot downloads and caches those public keys so it can verify the signature locally."

```text
Okta private signing key
          |
          | signs
          v
JWT header: { alg: RS256, kid: key-2026-01 }
          |
          v
Spring Boot ---------------- HTTPS ----------------> OIDC discovery document
     |                                              /.well-known/openid-configuration
     |                                                         |
     +--------------------- HTTPS ---------------------------+
                            JWKS endpoint: public keys
                            finds public key with matching kid
```

### Why we choose this

**You say:** "JWKS lets the provider rotate signing keys without deploying every microservice. The public keys are cached, so we do not make a remote Okta call for every API request. We still validate `iss`, `aud`, signature, `exp`, `nbf`, and scopes on every request."

### Implementation shape

```java
NimbusJwtDecoder decoder = NimbusJwtDecoder.withIssuerLocation(issuer).build();
OAuth2TokenValidator<Jwt> audience = jwt -> jwt.getAudience().contains("api://orders")
    ? OAuth2TokenValidatorResult.success()
    : OAuth2TokenValidatorResult.failure(new OAuth2Error("invalid_token"));
decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
    JwtValidators.createDefaultWithIssuer(issuer), audience));
```

### Senior traps

**"If signature validation passes, can we accept the token?"**

No. A valid signature only proves that a trusted issuer signed it. The service must also reject a wrong issuer, wrong audience, expired/not-yet-valid token, wrong token type, and insufficient scope.

**"What if Okta rotates keys while traffic is live?"**

The JWT `kid` changes. The decoder refreshes the JWKS cache when it cannot find a matching key. Monitor JWKS refresh failures and ensure egress/DNS to the permitted issuer is available.

## 7. End-to-End Production Request

```text
React              IDP               ALB/Ingress       Order API         Identity DB      Orders DB
  | login ---------->|                     |                |                  |                |
  |<-- JWT (iss,sub,aud,scope) ------------|                |                  |                |
  | GET /orders Bearer JWT ---------------->|--------------->|                  |                |
  |                                         |                | validate JWT    |                |
  |                                         |                | issuer+sub ---->|                |
  |                                         |                |<-- U-1001/acme -|                |
  |                                         |                | membership + RLS|--------------->|
  |<----------------------------------------|<---------------| 200 orders      |                |
```

### Why this sequence

**You say:** "The edge protects the public entry point, but the service still validates the access token because it is the resource server. It resolves external identity to internal identity, confirms tenant membership, then enforces object-level authorization and RLS. A valid login never automatically means access to every order."

## 8. EKS, Service-to-Service Calls, and AWS Permissions

```text
Browser JWT                          Workload AWS identity
-----------                          ---------------------
React -> Order API                   Order pod -> ServiceAccount -> IRSA -> STS -> SQS/S3/Secrets

Internal business call
----------------------
Order API -> client_credentials token with aud=payment-api, scope=payments.charge -> Payment API
```

### Why we choose this

**You say:** "The browser token represents a human. IRSA represents a pod. Client credentials represent Order Service when it calls Payment Service. I do not give the node role every AWS permission and I do not forward a broad browser token through every internal service."

### Trade-offs

| Decision | Benefit | Cost / mitigation |
|---|---|---|
| Two-plus EKS replicas | Pod and rollout resilience | Spread across nodes/AZs, use PDB and readiness probes |
| Per-service IRSA | Reduced AWS blast radius | More IAM policies; test them in CI |
| Client credentials | Narrow internal-service authority | Token lifecycle; cache safely and use short expiry |
| Managed Aurora | HA and backups handled by AWS | Cost and connection limits; use RDS Proxy and pool budgets |

## 9. Production Checklist

1. Allow-list issuers per tenant and configure exact redirect URIs.
2. Validate JWT signature, issuer, audience, expiry, not-before, token type, and scope.
3. Use `issuer + sub` as unique external identity; use internal `user_id` in business tables.
4. Require verified account linking for multiple IDPs; never rely on email equality.
5. Keep EKS workloads and Aurora private; expose only WAF/ALB ingress.
6. Use RDS Proxy and size total Hikari connections across all replicas.
7. Use PostgreSQL RLS with both `USING` and `WITH CHECK` plus a transaction-local tenant context.
8. Grant AWS permissions through namespace/service-account-bound IRSA roles.
9. Test wrong issuer/audience, cross-tenant reads and writes, pod/AZ failure, IDP key rotation, and database failover.
10. Log correlation ID, internal user ID, tenant, authorization outcome, and image digest. Never log passwords or bearer tokens.

## Interview Close

**You say:**

"My design is provider-neutral. Okta, Entra, Google, and Keycloak are external authentication authorities. I normalize them through an `issuer + sub` mapping to an internal `user_id`, so business data never depends on a provider-specific identifier. React uses PKCE, Spring Boot services validate tokens locally with cached JWKS keys, EKS workloads use IRSA for AWS access, and PostgreSQL enforces tenant boundaries. This gives us secure multi-IDP support today and a practical migration path tomorrow."
