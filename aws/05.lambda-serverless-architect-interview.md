## CONVERSATIONAL SCRIPT

### Phase 1 — How Lambda Works Internally

**You'd say in an interview:**
"Lambda runs your function inside a micro-VM (Firecracker). When an event arrives:

1. If a warm container exists for this function → reuse it (warm start, ~1-5ms overhead)
2. If no container exists → cold start:
   - AWS downloads your deployment package
   - Starts a Firecracker micro-VM
   - For Java: starts the JVM, loads classes
   - Runs your static initializers / Spring context init
   - Then calls your handler

The init phase runs OUTSIDE the billed duration — but the user still waits for it.

Once your handler returns, the container stays alive for ~15 minutes waiting for the next request. If another request comes in within that window → warm start. After 15 minutes idle → container is frozen/recycled.

This 'container reuse' is why you can store DB connections, cache, etc. in static fields — they survive across warm invocations for the same container."

### Phase 2 — Java Cold Start Solutions

#### Solution 1: AWS Lambda SnapStart (Java 11+)

```
Normal flow:
  Deploy → first invocation → JVM starts → Spring inits → handler runs
  Cold start: 5000ms

SnapStart flow:
  Deploy → AWS runs init phase ONCE → takes snapshot of JVM memory state
  Next cold start: restore from snapshot → skip JVM + Spring init
  Cold start: ~200ms ✅

How to enable:
  Function configuration → SnapStart → PublishedVersions
  Must use versioned aliases (not $LATEST)
  Not free: snapshot takes ~15s on deploy (one-time cost)

TRAP: SnapStart restores the SAME JVM state to multiple containers simultaneously.
  If your init code generates random values (UUID, crypto keys) → all instances
  share the same "random" seed! Fix: generate randoms in handler(), not init.
```

#### Solution 2: GraalVM Native Image

```
Compile Java → native binary (no JVM at runtime)
Cold start: ~50-100ms
Binary size: ~20-50MB
Tradeoff: reflection/proxies need config; Spring Native support; longer build time
Use case: latency-critical APIs, <100ms SLA

AWS Lambda: use provided.al2 runtime with native binary
```

#### Solution 3: Provisioned Concurrency

```java
// CloudFormation / SAM template
Properties:
  ProvisionedConcurrencyConfig:
    ProvisionedConcurrentExecutions: 10  // keep 10 containers warm

// Cost: you pay for 10 containers 24/7 regardless of traffic
// Use when: predictable peak load, cost acceptable, Java cold start unacceptable
// Don't use when: bursty/unpredictable traffic (expensive)
```

### Phase 4 — SQS + Lambda (Event-Driven — Most Common Pattern)

```
 ┌──────────────────────────────────────────────────────────────────────┐
 │  Producer → SQS Queue → Lambda (Event Source Mapping)              │
 │                                                                      │
 │  SQS Queue                Lambda                                    │
 │  ┌──────────────┐         ┌────────────────────────────┐           │
 │  │ msg1         │ poll    │ BatchSize: 10               │           │
 │  │ msg2   ──────┼────────►│ handler(List<SQSMessage>)   │           │
 │  │ msg3         │         │                            │           │
 │  │ msg4         │         │ success: delete from queue  │           │
 │  └──────────────┘         │ failure: message returns    │           │
 │                           │ → retry → DLQ after maxAttempts         │
 │                           └────────────────────────────┘           │
 │                                                                      │
 │  KEY SETTINGS:                                                       │
 │  BatchSize: 1-10000 messages per invocation                         │
 │  BatchWindow: wait up to Ns to fill batch (reduces invocations)     │
 │  MaximumConcurrency: cap parallel Lambda invocations per queue      │
 └──────────────────────────────────────────────────────────────────────┘
```

```java
// ─── SQS Lambda Handler ───────────────────────────────────────────
public class OrderEventHandler implements RequestHandler<SQSEvent, SQSBatchResponse> {

    private final OrderService orderService = new OrderService(); // init ONCE (warm reuse)

    @Override
    public SQSBatchResponse handleRequest(SQSEvent event, Context context) {
        List<SQSBatchResponse.BatchItemFailure> failures = new ArrayList<>();

        for (SQSEvent.SQSMessage message : event.getRecords()) {
            try {
                Order order = parseOrder(message.getBody());
                orderService.process(order);
                // Success: message auto-deleted from queue
            } catch (Exception ex) {
                context.getLogger().log("Failed messageId: " + message.getMessageId()
                    + " error: " + ex.getMessage());
                // Report partial failure — only this message stays in queue
                failures.add(SQSBatchResponse.BatchItemFailure.builder()
                    .withItemIdentifier(message.getMessageId())
                    .build());
            }
        }
        return SQSBatchResponse.builder().withBatchItemFailures(failures).build();
    }
}
// Without SQSBatchResponse: if ANY message fails → ENTIRE batch retried
// With SQSBatchResponse: only failed messages retry → avoids duplicate processing ✅
```

### Phase 5 — Concurrency Deep Dive

```
 CONCURRENCY TYPES:
 ┌──────────────────────────────────────────────────────────────────────┐
 │                                                                      │
 │  Unreserved Concurrency (default)                                   │
 │  → shares from account pool (1000 default)                          │
 │  → one noisy function can starve others                             │
 │                                                                      │
 │  Reserved Concurrency                                                │
 │  → guarantee: this function gets up to N concurrent executions      │
 │  → cap: also LIMITS this function to N (throttle beyond N)          │
 │  → use: protect downstream DB (max 50 Lambda → 50 DB connections)   │
 │                                                                      │
 │  Provisioned Concurrency                                             │
 │  → pre-warm N containers, always ready                              │
 │  → eliminates cold starts for those N instances                     │
 │  → cost: pay per GB-second even when idle                           │
 │                                                                      │
 │  Example — payment service:                                         │
 │  Reserved=100 (never starves), Provisioned=20 (first 20 always warm)│
 └──────────────────────────────────────────────────────────────────────┘

 THROTTLING BEHAVIOR:
 ┌──────────────────────────────────────────────────────────────────────┐
 │  Synchronous (API Gateway): throttled → 429 TooManyRequests         │
 │  Asynchronous (SQS/SNS):   throttled → retry with backoff → DLQ    │
 └──────────────────────────────────────────────────────────────────────┘
```

RESOURCE LIMITS:
┌──────────────────────────────────────────────────────────────────────┐

  More memory → more vCPU → faster execution
  Example: 128MB takes 3000ms = $0.006

  Java benefits most from higher memory (JVM JIT needs CPU)
  Recommended for Java: start at 512MB–1024MB, tune with load tests

## Senior Trap Questions

**Q1: "Lambda is stateless — but I see people storing things in static variables. Is that safe?"**
```
Partially safe, with caveats.

Static variables PERSIST across warm invocations of the SAME container.
Example:
  static AmazonDynamoDB client = AmazonDynamoDBClientBuilder.defaultClient();
  // This is fine — client reused across warm calls. ✅

TRAPS:
  1. Don't store user-specific data in statics (shared across requests in same container).
  2. Don't assume state exists — cold start = fresh container = empty statics.
  3. With SnapStart: statics are restored from snapshot.
     If you stored crypto random in static init → same value in all containers! ❌
     Fix: generate randomness in handler(), not static init.

Safe to store in statics:
  - DB/HTTP clients (expensive to create, thread-safe)
  - Config values loaded at startup
  - Pre-compiled regex/parsers

Never store in statics:
  - Per-request state
  - Mutable shared objects without thread safety
  - Crypto keys / nonces / UUIDs generated per-container
```

**Q2: "Your Lambda is connected to RDS. It starts getting OOM (OutOfMemory) errors. Why?"**
```
Classic scenario: Lambda scales to 500 concurrent → 500 containers
→ each container opens its own DB connection pool (HikariCP default: 10)
→ 500 × 10 = 5000 DB connections
→ RDS max_connections = 500 (db.t3.medium default)
→ RDS rejects connections → Lambda throws connection errors, not OOM

Actual OOM: if you set HikariCP pool to 20 on a 128MB Lambda:
  Connection pool overhead + JVM + Spring → exceeds 128MB

FIX:
  1. Use RDS Proxy: pools and multiplexes → Lambda sees "unlimited" connections,
     proxy holds actual pool to RDS. Recommended always for Lambda + RDS.
  2. Reduce pool size for Lambda: HikariCP minimumIdle=1, maximumPoolSize=2
     Lambda concurrency × 2 << RDS max_connections
  3. Increase Lambda memory (also increases available RAM).
  4. Set Reserved Concurrency on Lambda to cap connections:
     Reserved=50 × pool=2 = 100 connections ≤ RDS max ✅
```

**Q3: "You have a Lambda that processes SQS messages. Suddenly it's processing the same message 1000 times. Why?"**
```
Poison pill / infinite retry loop.

Scenario:
  Message arrives → Lambda processes → throws exception
  → SQS returns message to queue (visibility timeout expires)
  → Lambda picks it up again → throws again → repeat forever

Without maxReceiveCount configured:
  Message retries indefinitely.
  1 bad message keeps triggering Lambda 1000s of times.

FIX:
  1. Set SQS RedrivePolicy: maxReceiveCount=3
     After 3 failures → moves to DLQ (Dead Letter Queue)
  2. Use SQSBatchResponse partial failure reporting:
     Only the failed message retries, not the whole batch.
  3. Handle poison pills: if deserialization fails → send to DLQ manually
     (don't let bad JSON format spin forever)
  4. Alert on DLQ depth: CloudWatch alarm on DLQ ApproximateNumberOfMessagesVisible > 0

Code guard:
  try {
      processMessage(msg);
  } catch (UnrecoverableException e) {
      // Don't rethrow — let Lambda succeed so message is deleted
      // Log + manually send to DLQ / alert
      deadLetterService.send(msg, e);
  } catch (TransientException e) {
      throw e; // Let SQS retry
  }
```

**Q4: "How does Lambda handle a Java OutOfMemoryError vs a timeout? Different behavior?"**
```
OOM (OutOfMemoryError):
  Lambda container dies immediately.
  Invocation: marked as error, client gets error response.
  Container: recycled (next invocation gets a fresh cold start).
  DLQ: for async invocations, event goes to DLQ after retry.

Timeout:
  Lambda kills the container after configured timeout.
  Same as OOM: container recycled.
  For SQS: message visibility timeout must be > Lambda timeout.
  If Lambda times out on SQS message:
    visibility timeout expires → message back in queue → retry.
    Set SQS visibility timeout = 6× Lambda timeout (AWS recommendation).

Key difference for debugging:
  OOM: CloudWatch shows "Runtime.ExitError" or "SIGSEGV"
  Timeout: CloudWatch shows "Task timed out after X seconds"
  Both: check Lambda memory utilization (CloudWatch Insights):
    filter @type = "REPORT"
    | stats max(@maxMemoryUsed) by @logStream
```

## Interview Cheat Sheet

> "Lambda is event-driven serverless compute — code runs on demand, no server management. For Java the hardest problem is cold start: JVM + Spring Boot can take 5-10 seconds. Three production fixes: AWS SnapStart snapshots the JVM after init and restores it — cuts cold start from 5s to ~200ms with no code changes; GraalVM Native Image compiles to native binary for <100ms cold start; Provisioned Concurrency keeps N containers pre-warmed. Always use RDS Proxy when Lambda connects to RDS — Lambda scales to hundreds of containers each opening connection pools, RDS Proxy multiplexes them into a manageable pool. For SQS triggers, always implement SQSBatchResponse partial failure reporting — without it, one failed message in a batch of 10 causes all 10 to retry, creating duplicates. Set SQS RedrivePolicy maxReceiveCount=3 + DLQ to prevent poison pill infinite loops. Memory sizing: more memory = more vCPU; Java benefits hugely — 512MB at 500ms can be cheaper than 128MB at 3000ms."
