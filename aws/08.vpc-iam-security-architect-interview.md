## NEW LEARNER FOUNDATION — Read This First If You Are New

```
KEY TERMS EXPLAINED SIMPLY
============================

VPC (Virtual Private Cloud)
  Your own isolated private network inside AWS. Think of it as a
  fenced compound you own inside the AWS data centre. Nothing enters
  or leaves without your permission.
  You define the IP address range (CIDR), subnets, routing, and firewalls.

CIDR (Classless Inter-Domain Routing)
  A way of writing IP address ranges.
  10.0.0.0/16 means: all addresses from 10.0.0.0 to 10.0.255.255 (65,536 IPs)
  10.0.1.0/24 means: all addresses from 10.0.1.0 to 10.0.1.255 (256 IPs)
  /16 = large network, /24 = small subnet

SUBNET
  A slice of your VPC's IP range, tied to one Availability Zone.
  Public subnet:  has a route to the internet (via Internet Gateway)
  Private subnet: no direct internet access — traffic goes via NAT Gateway
  Isolated subnet: no internet access at all, not even outbound

INTERNET GATEWAY
  The "front door" of your VPC — allows traffic to flow between your VPC
  and the public internet. Only resources in public subnets use it.

NAT GATEWAY (Network Address Translation)
  Allows private subnet resources to initiate outbound internet connections
  (e.g., download npm packages, call external APIs) WITHOUT being reachable
  from the internet. Like a one-way valve — outbound only.

SECURITY GROUP
  A virtual firewall attached to each EC2/container. Rules are STATEFUL:
  if you allow inbound traffic on port 8080, the response traffic is
  automatically allowed outbound (you don't write a separate outbound rule).

NACL (Network Access Control List)
  A subnet-level firewall. Rules are STATELESS: you must explicitly
  allow BOTH inbound AND outbound traffic, including response traffic.
  Applied to entire subnets, not individual resources.

VPC ENDPOINT
  A private connection from your VPC to AWS services (S3, DynamoDB, etc.)
  that stays entirely within the AWS backbone — no internet, no NAT Gateway.
  Saves NAT Gateway costs and keeps data off the public internet.

IAM ROLE
  A set of AWS permissions. Instead of giving a service a username/password,
  you attach a role. The service automatically gets temporary credentials.
  "This ECS task is allowed to read from this S3 bucket" = IAM role.

ENI (Elastic Network Interface)
  A virtual network card attached to an EC2 instance. Each ENI has
  one or more private IP addresses from the subnet it's in.
```

### OPENING — When They Ask: "Walk me through your production VPC design."

> **You say:**
>
> "For Flipkart's production environment, the VPC is designed around the
> principle of defence in depth — multiple layers of isolation, so that a
> breach of one layer doesn't expose everything.
>
> We use a three-tier subnet model: public subnets for internet-facing
> components, private subnets for application workloads, and isolated
> subnets for databases that have no route to the internet whatsoever.
>
> The key insight is: your RDS database should never be in a public subnet,
> and your ECS tasks should never need a public IP. Everything that needs
> internet access uses either a NAT Gateway (outbound only) or a VPC Endpoint
> (stays on the AWS backbone entirely)."

### PART 1 — When They Ask: "Security Groups vs NACLs — what's the difference?"

> **You say:**
>
> "Security groups are the primary firewall mechanism — they're attached to
> ENIs (network interfaces) and are stateful. Stateful means: if you allow
> inbound on port 8080, the response traffic is automatically allowed outbound,
> even if you have no outbound rule for it. You don't have to think about
> return traffic.
>
> NACLs are subnet-level and stateless. If you allow inbound on port 8080,
> you must explicitly allow outbound ephemeral ports (1024-65535) for the
> response to go back. Many teams get caught by this — they configure NACLs
> for new services and traffic silently fails because they forgot the outbound
> ephemeral range.
>
> My rule: security groups for everything, NACLs only as an extra layer for
> specific threat isolation (like blocking a /16 CIDR you're being attacked from)."

```
SECURITY GROUP vs NACL — THE STATEFUL TRAP
============================================

  SECURITY GROUP (Stateful):
  ─────────────────────────
  Inbound rule:  TCP port 8080 from ALB SG  ← allow
  Outbound rule: (nothing) OR "all traffic"

  Traffic flow:
  ALB → ECS Task (port 8080)    ✅ matches inbound rule
  ECS Task → ALB (ephemeral port)  ✅ AUTOMATICALLY allowed (stateful)

  NACL (Stateless — the trap):
  ──────────────────────────────
  Subnet NACL inbound:  TCP port 8080 from 0.0.0.0/0  ← allow
  Subnet NACL outbound: (nothing configured)

  Traffic flow:
  Client → ECS Task (port 8080)  ✅ matches inbound rule
  ECS Task → Client (ephemeral port 50000)  ❌ NO outbound rule → DROPPED!
  Result: Connection established, data sent, response silently dropped
  → Looks like a hanging request / timeout

  FIX for NACL outbound:
  Allow outbound TCP ports 1024-65535 (ephemeral range)
  ALSO allow outbound TCP port 443 for HTTPS to external services

  PRACTICAL NACL RULES (for private subnet):
  ┌─────┬────────────┬──────────────┬────────────────────┬──────────┐
  │ Rule│ Type       │ Port Range   │ Source             │ Allow    │
  ├─────┼────────────┼──────────────┼────────────────────┼──────────┤
  │ 100 │ HTTP       │ 80           │ 10.0.0.0/16        │ ALLOW    │
  │ 110 │ HTTPS      │ 443          │ 10.0.0.0/16        │ ALLOW    │
  │ 120 │ PostgreSQL │ 5432         │ 10.0.10.0/23       │ ALLOW    │
  │ 130 │ Redis      │ 6379         │ 10.0.10.0/23       │ ALLOW    │
  │ 140 │ Ephemeral  │ 1024-65535   │ 0.0.0.0/0          │ ALLOW    │
  │ *   │ ALL        │ ALL          │ ALL                │ DENY     │
  └─────┴────────────┴──────────────┴────────────────────┴──────────┘
```

### PART 2 — When They Ask: "How do your services communicate securely within VPC?"

> **You say:**
>
> "All inter-service communication stays within the private subnet — it never
> touches the internet. Services communicate by security group — the ECS task
> security group allows inbound from the ALB security group on the application
> port, and from other service security groups for internal calls.
>
> The critical principle: never use CIDR ranges in security group rules
> if you can use security group IDs. CIDR rules don't update when pods
> get new IPs. Security group references are dynamic — 'allow traffic from
> anything in the order-service SG' automatically covers new pods."

```
SECURITY GROUP DESIGN — Reference SGs, Not CIDRs
===================================================

  ┌──────────────────────────────────────────────────────────┐
  │  sg-alb: Application Load Balancer                       │
  │  Inbound:  443 from 0.0.0.0/0 (internet)                 │
  │  Outbound: 8080 to sg-order-service                      │
  └──────────────────────────┬───────────────────────────────┘
                              │
  ┌───────────────────────────▼──────────────────────────────┐
  │  sg-order-service: Order Service ECS Tasks               │
  │  Inbound:  8080 from sg-alb           ← ALB only         │
  │  Inbound:  8080 from sg-internal-tools← internal tools   │
  │  Outbound: 5432 to sg-rds             ← RDS only         │
  │  Outbound: 6379 to sg-elasticache     ← Redis only       │
  │  Outbound: 443 to 0.0.0.0/0           ← outbound HTTPS   │
  └──────────────────────────────────────────────────────────┘

  WHY SG references > CIDR:
  - ECS task gets new IP on restart → CIDR rule may not match
  - Auto-scaling adds pods → CIDR needs updating
  - SG reference: "allow from sg-order-service" matches all current
    AND future tasks with that security group automatically
```

### PART 3 — When They Ask: "How do your ECS tasks access S3 without hardcoding credentials?"

> **You say:**
>
> "ECS tasks use IAM task roles — an IAM role attached to the ECS task definition.
> When the task starts, ECS injects temporary credentials via the container
> credentials endpoint. The AWS SDK inside the container automatically picks
> these up — no hardcoded keys, no environment variables with credentials.
>
> For EKS pods, the equivalent is IRSA — IAM Roles for Service Accounts —
> using OIDC federation.
>
> For really sensitive operations — fetching the DB password, JWT secret —
> we use AWS Secrets Manager. The IAM task role has permission to call
> secretsmanager:GetSecretValue for specific secret ARNs only."

```
ECS TASK ROLE — CREDENTIAL FLOW
=================================

  ECS Task Definition:
  taskRoleArn: arn:aws:iam::123:role/order-service-task-role

  IAM Role Policy (order-service-task-role):
  {
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::flipkart-receipts/*"    ← specific bucket only
  },
  {
    "Effect": "Allow",
    "Action": "secretsmanager:GetSecretValue",
    "Resource": "arn:aws:secretsmanager:us-east-1:123:secret:flipkart/prod/db-*"
  }

  CREDENTIAL INJECTION FLOW:
  ──────────────────────────
  ECS Agent on EC2/Fargate
       │ injects temporary credentials
       ▼
  Container environment: AWS_CONTAINER_CREDENTIALS_RELATIVE_URI
       │
       ▼
  AWS SDK calls: http://169.254.170.2/v2/credentials/<uuid>
       │ returns: AccessKeyId, SecretAccessKey, Token (valid 1 hour, auto-rotated)
       ▼
  S3Client.putObject() → works without any hardcoded keys ✅

  Spring Boot:
  No config needed — AWS SDK auto-detects credentials from ECS task role
  AmazonS3 client = AmazonS3ClientBuilder.defaultClient();  // just works
```

### Trap 1: NAT Gateway Cross-AZ Data Transfer Costs

> **You say:**
>
> "This is a cost trap that surprises many teams. NAT Gateway charges $0.045/GB
> for data processed PLUS $0.01/GB for cross-AZ data transfer.
>
> If you have one NAT Gateway in AZ-1 and ECS tasks in AZ-2 and AZ-3,
> all outbound internet traffic from those tasks crosses AZ boundaries to reach
> the NAT Gateway. At high bandwidth, this adds up to thousands of dollars monthly.
>
> The fix: one NAT Gateway per AZ. More expensive in hourly charges ($0.045/h × 3)
> but eliminates the cross-AZ transfer cost. For production, this almost always
> pays off."

```
NAT GATEWAY COST TRAP
=======================

  WRONG — Single NAT Gateway:
  ────────────────────────────
  AZ-1: NAT Gateway ← ECS tasks in AZ-1 → direct, no cross-AZ charge
  AZ-2: ECS tasks → must route to AZ-1 NAT Gateway → $0.01/GB cross-AZ
  AZ-3: ECS tasks → must route to AZ-1 NAT Gateway → $0.01/GB cross-AZ

  Example: 1 TB/day cross-AZ traffic × 30 days = 30 TB × $0.01 = $300/month extra

  CORRECT — NAT Gateway per AZ:
  ──────────────────────────────
  AZ-1: NAT Gateway ← AZ-1 ECS tasks route table → this NAT GW
  AZ-2: NAT Gateway ← AZ-2 ECS tasks route table → this NAT GW
  AZ-3: NAT Gateway ← AZ-3 ECS tasks route table → this NAT GW

  Each AZ's traffic exits through its own NAT GW → no cross-AZ transfer charges
  Extra cost: 2 more NAT GW × $0.045/h × 720h = ~$65/month → cheaper than $300/month
```

### Trap 2: VPC Endpoints — Pay Once, Save Every Request

> **You say:**
>
> "Without VPC endpoints, when your ECS task calls the S3 API, the traffic
> leaves your VPC, goes through the NAT Gateway, goes to the public internet,
> hits the S3 endpoint, and comes back. You pay NAT Gateway processing charges
> on every byte of S3 data.
>
> With a VPC endpoint for S3, traffic goes from your private subnet directly
> to S3 over the AWS private backbone — no NAT Gateway, no internet, zero
> data processing cost from NAT.
>
> I set up VPC endpoints as a standard practice for any service my apps
> call heavily: S3, DynamoDB, Secrets Manager, ECR, STS."

```
VPC ENDPOINT — TRAFFIC PATH COMPARISON
========================================

  WITHOUT VPC Endpoint:
  ECS Task (private subnet)
    → NAT Gateway (public subnet)  ← $0.045/GB NAT processing fee
    → Internet Gateway
    → Public internet
    → s3.amazonaws.com
    Total: slow, expensive, traffic leaves AWS network

  WITH VPC Endpoint (Gateway type for S3):
  ECS Task (private subnet)
    → VPC Endpoint (Gateway endpoint — FREE for S3/DynamoDB)
    → AWS private backbone
    → S3 bucket
    Total: fast, free, never leaves AWS network

  TYPES OF VPC ENDPOINTS:
  ┌────────────────┬──────────────────────────────────────────────┐
  │ Gateway EP     │ S3, DynamoDB only — FREE                     │
  │                │ Configured in route table                    │
  ├────────────────┼──────────────────────────────────────────────┤
  │ Interface EP   │ All other services (ECR, Secrets Mgr, STS,  │
  │                │ SSM, SNS, SQS, CloudWatch, etc.)             │
  │                │ $0.01/h + $0.01/GB — charged but still       │
  │                │ cheaper + private vs going through NAT       │
  └────────────────┴──────────────────────────────────────────────┘

  MUST-HAVE VPC ENDPOINTS for ECS/EKS:
  - com.amazonaws.region.s3            (Gateway — free)
  - com.amazonaws.region.dynamodb      (Gateway — free)
  - com.amazonaws.region.ecr.dkr       (Interface — pull container images privately)
  - com.amazonaws.region.ecr.api       (Interface)
  - com.amazonaws.region.secretsmanager(Interface)
  - com.amazonaws.region.sts           (Interface — for IRSA/task roles)
  - com.amazonaws.region.logs          (Interface — CloudWatch logs)
```

### Part 4 — When They Ask: "How do you prevent privilege escalation in IAM?"

> **You say:**
>
> "Privilege escalation in IAM means: a developer with limited permissions
> creates an IAM role or policy that grants themselves admin access.
> For example, if a dev has iam:CreateRole and iam:AttachRolePolicy, they
> can create a role with AdministratorAccess and assume it.
>
> The defence is IAM Permission Boundaries. A permission boundary is a
> policy that caps the maximum permissions any role or user can have,
> regardless of what policies are attached. Even if someone attaches
> AdministratorAccess, the permission boundary is the ceiling.
>
> In practice: developers in our account have a boundary that only allows
> them to create roles with the same boundary attached — so they can't create
> roles more powerful than themselves."

```
IAM PERMISSION BOUNDARY — Privilege Escalation Defence
========================================================

  Without Boundary:
  Developer has: iam:CreateRole, iam:AttachRolePolicy
  Developer creates: role-super-admin with AdministratorAccess
  Developer assumes: role-super-admin → full admin!
  → Security breach via legitimate API calls

  With Permission Boundary:
  Developer has same permissions + boundary: "max-dev-boundary"
  "max-dev-boundary" allows: specific services only, denies iam:* broadly

  Developer tries to create role-super-admin:
  → Boundary check: "does boundary allow AdministratorAccess?" → NO
  → CreateRole fails: "You can only create roles with this boundary attached"

  POLICY EVALUATION ORDER:
  ─────────────────────────
  1. SCP (Service Control Policy) — account/OU level ceiling
  2. Permission Boundary — role/user level ceiling
  3. Identity Policy — what the role actually has
  4. Resource Policy — what the resource allows
  Final effective permission = INTERSECTION of all layers

  Effective permission = IdentityPolicy ∩ PermissionBoundary ∩ SCP
  (most restrictive wins)
```

### Trap 3: Secrets in Environment Variables (ECS/EKS)

> **You say:**
>
> "Putting secrets directly in ECS task definition environment variables is a
> trap. The task definition is stored in plain text in ECS. Anyone with
> ecs:DescribeTaskDefinition can read all environment variables. Worse, if
> you print environment variables in logs for debugging — DB password goes
> to CloudWatch in plain text.
>
> The correct approach is reference secrets by ARN, not value. ECS and
> EKS both support injecting secrets from Secrets Manager at container
> start time — the value is fetched and injected as an environment variable,
> but it's never stored in the task definition or pod spec."

```
SECRETS — WRONG vs RIGHT
==========================

  WRONG ❌ — Value in task definition (visible to anyone with ECS read access):
  {
    "environment": [
      {"name": "DB_PASSWORD", "value": "S3cr3tPassw0rd!"}  ← plain text in ECS!
    ]
  }

  CORRECT ✅ — Reference from Secrets Manager:
  {
    "secrets": [
      {
        "name": "DB_PASSWORD",
        "valueFrom": "arn:aws:secretsmanager:us-east-1:123:secret:prod/db-password-xxxxx"
      },
      {
        "name": "JWT_SECRET",
        "valueFrom": "arn:aws:secretsmanager:us-east-1:123:secret:prod/jwt-secret-xxxxx"
      }
    ]
  }

  ECS task role needs:
  secretsmanager:GetSecretValue on the specific secret ARNs
  kms:Decrypt if secrets are encrypted with a customer-managed KMS key

  IN KUBERNETES (EKS):
  Use External Secrets Operator → syncs from Secrets Manager to K8s Secret
  Mount K8s Secret as env var or volume → pod never has plaintext secret in spec
```

## Interview Cheat Sheet (Say This Confidently)

> "Production VPC design: three tiers — public (ALB, NAT GW), private (ECS/EKS tasks), isolated (RDS, Redis — no internet route). Security groups are stateful (forget return traffic), NACLs are stateless (must allow ephemeral ports outbound). Always use security group references in rules, not CIDRs — they automatically cover new pods. One NAT Gateway per AZ prevents cross-AZ data transfer charges — a common cost surprise. VPC endpoints for S3 and DynamoDB are free and eliminate NAT processing charges on all S3/DynamoDB traffic. Secrets go in Secrets Manager and are referenced by ARN in task definitions — never as plain-text environment variable values. IAM permission boundaries prevent privilege escalation — developers can only create roles bounded by the same policy that limits them."
