## NEW LEARNER FOUNDATION — Read This First If You Are New

```
KEY TERMS EXPLAINED SIMPLY
============================

METRIC
  A numeric value measured over time. Examples: CPU at 72%, request count = 1200/min,
  order latency = 320ms. Metrics are stored as time-series data.
  Think: a graph on a dashboard — the Y axis is the metric value, X axis is time.

NAMESPACE
  A container that groups related metrics together.
  AWS services use namespaces like "AWS/EC2", "AWS/RDS", "AWS/ApplicationELB".
  You create your own: "Swiggy/OrderService", "Netflix/StreamingService".
  Without namespaces, 10,000 metrics from 50 services would be an unnavigable mess.

DIMENSION
  A key-value pair that further filters a metric.
  Example: metric "OrderLatency" with dimension ServiceName=order-service, Environment=prod
  vs. ServiceName=order-service, Environment=staging.
  Without dimensions, all environments' metrics would merge into one meaningless number.

ALARM
  A rule that watches a metric. Three states:
    OK               — metric is within the normal threshold
    ALARM            — metric crossed the threshold (e.g., P99 > 500ms for 3 datapoints)
    INSUFFICIENT_DATA — not enough data to evaluate (service just started, or gap in metrics)
  An alarm triggers actions: SNS notification → PagerDuty, Slack, or Lambda.

LOG GROUP
  A named container in CloudWatch Logs for one service's log streams.
  Naming convention: /ecs/order-service, /aws/lambda/payment-function.
  All logs from all instances of order-service flow into one log group.

LOG STREAM
  One log source within a log group. Each container instance writes to its own log stream.
  Log Group: /ecs/order-service
    Log Stream: order-service/order-service/a1b2c3d4 (container ID)
    Log Stream: order-service/order-service/e5f6g7h8

X-RAY TRACE
  One end-to-end request as it travels through ALL services.
  User clicks "Place Order" → trace follows that request through:
  order-service → payment-service → bank-API → notification-service.
  You can see the full timeline: where the 800ms went across all services.

X-RAY SEGMENT
  One service's contribution to a trace. When order-service handles a request,
  it creates one segment. That segment records start time, end time, HTTP status,
  errors, and metadata specific to that service.

X-RAY SUBSEGMENT
  A unit of work WITHIN a segment. Inside order-service's segment, you might have:
  - subsegment: "DynamoDB query" (12ms)
  - subsegment: "Redis cache check" (3ms)
  - subsegment: "HTTP call to payment-service" (320ms) ← where the latency is!

SAMPLING RULE
  X-Ray does NOT trace every single request (would be too expensive/noisy).
  Default: trace 5% of all requests.
  Smart sampling: trace 100% of requests that have errors.
  Custom: trace 100% of requests from specific IP or with specific header.

SERVICE MAP
  A visual graph that X-Ray auto-generates showing:
  - All services in your system as nodes
  - Arrows showing how they call each other
  - Each node coloured by health (green = OK, yellow = latency, red = errors)
  - Latency numbers on the edges between services
  This is how you find bottlenecks in 30 seconds during an incident.

CONTAINER INSIGHTS
  Enhanced CloudWatch for ECS/EKS that gives you pod-level metrics.
  Without it: you see EC2 node CPU (blended across all pods).
  With it:    you see pod-by-pod CPU, memory, and which pod was OOMKilled.
  Must be explicitly enabled — not on by default for EKS.
```

> **You say:**
>
> "I think about observability in three layers — metrics, logs, and traces —
> because each answers a different question during an incident.
>
> Metrics tell you WHAT happened: P99 spiked to 1200ms at 14:32.
> Logs tell you WHY it happened: NullPointerException in OrderService line 42
> after a Redis connection timeout.
> Traces tell you WHERE across services the time went: order-service itself was
> fine, but payment-service was calling bank-API which took 800ms.
>
> On a food delivery platform, I wire all three with CloudWatch Metrics for
> custom business signals — OrderPlacementLatency, PaymentFailureRate —
> CloudWatch Logs Insights for structured log queries, and X-Ray for
> cross-service trace correlation.
>
> Let me walk through each layer and the traps."

### SECTION 1 — When They Ask: "How do you emit custom metrics from a Java service?"

> **You say:**
>
> "CloudWatch distinguishes two types of metrics: system metrics that AWS collects
> automatically — CPU, memory, NetworkIn, ALB RequestCount — and custom metrics
> that your application code emits via the PutMetricData API.
>
> System metrics are free, but they're infrastructure signals. They don't tell
> you that your payment failure rate jumped 3% because of a gateway timeout.
> Custom metrics are your business signals — OrderPlacementLatency,
> PaymentFailureRate, CartAbandonmentCount.
>
> You group custom metrics under a namespace — I use Swiggy/OrderService —
> and attach dimensions so you can filter: ServiceName=order-service,
> Environment=prod, Region=ap-south-1.
>
> The resolution choice matters for cost: standard resolution (1-minute)
> is the default. High-resolution (1-second) costs exactly 2x and is only
> worth it for real-time dashboards like a payment processing SLA dashboard."

```
SYSTEM METRICS vs CUSTOM METRICS
==================================

  AUTO-COLLECTED BY AWS (free)          YOU EMIT FROM CODE (charged)
  ─────────────────────────────────     ──────────────────────────────────────
  AWS/EC2:                              Swiggy/OrderService:
    CPUUtilization                        OrderPlacementLatency (ms, P50/P99)
    NetworkIn, NetworkOut                 PaymentFailureRate (%)
    DiskReadOps                           CartAbandonmentCount (count/min)

  AWS/ApplicationELB:                   Swiggy/PaymentService:
    RequestCount                          PaymentGatewayLatency (ms)
    TargetResponseTime                    FailedTransactionCount
    HTTPCode_ELB_5XX_Count                SuccessfulPaymentAmount ($)

  AWS/RDS:                              Swiggy/NotificationService:
    FreeStorageSpace                      SMSDeliveryRate (%)
    DatabaseConnections                   PushNotificationFailures
    ReadLatency, WriteLatency

  NAMESPACE + DIMENSION STRUCTURE:
  ─────────────────────────────────
  Namespace:  "Swiggy/OrderService"
  MetricName: "OrderPlacementLatency"
  Dimensions: ServiceName=order-service
              Environment=prod
              Region=ap-south-1
  Unit:       Milliseconds
  Value:      342.5
```

```java
// build.gradle / pom.xml dependency
// software.amazon.awssdk:cloudwatch:2.x

@Service
@Slf4j
public class OrderMetricsService {

    private final CloudWatchAsyncClient cloudWatch;

    // Emit latency metric on every order placement
    public void recordOrderPlacementLatency(long latencyMs, String restaurantId) {
        MetricDatum datum = MetricDatum.builder()
            .metricName("OrderPlacementLatency")
            .unit(StandardUnit.MILLISECONDS)
            .value((double) latencyMs)
            // Dimensions let you slice the metric by restaurant, region, etc.
            .dimensions(
                Dimension.builder().name("ServiceName").value("order-service").build(),
                Dimension.builder().name("Environment").value(System.getenv("ENVIRONMENT")).build(),
                Dimension.builder().name("RestaurantRegion").value(restaurantId.substring(0, 3)).build()
            )
            // HIGH_RESOLUTION = 1-second granularity — costs 2x standard
            // STANDARD (default) = 1-minute granularity
            .storageResolution(60)   // 60 = standard, 1 = high-resolution
            .build();

        PutMetricDataRequest request = PutMetricDataRequest.builder()
            .namespace("Swiggy/OrderService")
            .metricData(datum)
            .build();

        // Async — fire and forget, don't block the order request
        cloudWatch.putMetricData(request).whenComplete((response, ex) -> {
            if (ex != null) {
                log.warn("Failed to emit CloudWatch metric: {}", ex.getMessage());
                // NEVER let metrics emission crash the business logic
            }
        });
    }

    // Emit payment failure rate as a count metric
    public void recordPaymentFailure(String failureReason) {
        MetricDatum datum = MetricDatum.builder()
            .metricName("PaymentFailureCount")
            .unit(StandardUnit.COUNT)
            .value(1.0)
            .dimensions(
                Dimension.builder().name("FailureReason").value(failureReason).build(),
                Dimension.builder().name("Environment").value(System.getenv("ENVIRONMENT")).build()
            )
            .storageResolution(60)
            .build();

        PutMetricDataRequest request = PutMetricDataRequest.builder()
            .namespace("Swiggy/PaymentService")
            .metricData(datum)
            .build();

        cloudWatch.putMetricData(request);
    }
}
```

```java
// Wire it into your order service
@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orderRepo;
    private final PaymentService paymentService;
    private final OrderMetricsService metrics;

    public Order placeOrder(OrderRequest request) {
        long start = System.currentTimeMillis();
        try {
            Order order = orderRepo.save(request.toOrder());
            paymentService.charge(order);
            long latencyMs = System.currentTimeMillis() - start;
            metrics.recordOrderPlacementLatency(latencyMs, request.getRestaurantId());
            return order;
        } catch (PaymentException ex) {
            metrics.recordPaymentFailure(ex.getReason());
            throw ex;
        }
    }
}
```

### SECTION 2 — When They Ask: "How do you build P99 latency alarms? Walk me through your on-call setup."

> **You say:**
>
> "The P99 pattern is the right way to alarm on latency. If you alarm on average
> latency, the majority of your slow requests are hidden — a 5-second request
> for 1% of users is swamped by 200ms requests for 99% of users, average stays
> fine. P99 surfaces that 5-second tail.
>
> The pattern: emit OrderPlacementLatency as a custom metric, then create a
> CloudWatch alarm with PERCENTILE statistic p(99) and threshold 500ms for
> 3 consecutive 1-minute datapoints. Alarm triggers an SNS topic. That topic
> fans out to PagerDuty for on-call paging, a Lambda for auto-remediation,
> and a Slack channel for team visibility.
>
> The trap: alarm on a single metric alone causes alert fatigue. In practice I
> use composite alarms — ALARM only if BOTH P99 > 500ms AND ErrorRate > 1%.
> A latency spike without errors is usually a single heavy query, not an outage.
> The composite alarm rings only when the service is genuinely degraded."

```
P99 ALARM FLOW
==============

  OrderPlacementLatency metric
  (emitted every request, 1-min rollup)
         │
         ▼
  CloudWatch Alarm
  ┌──────────────────────────────────────────────────────────┐
  │ Metric:    Swiggy/OrderService → OrderPlacementLatency   │
  │ Statistic: p99                                           │
  │ Threshold: > 500 ms                                      │
  │ Periods:   3 consecutive 1-minute windows               │
  │ State:     OK → ALARM                                    │
  └──────────────────────────────────────────────────────────┘
         │ ALARM
         ▼
  SNS Topic: swiggy-p99-alerts
  ┌──────────────────────────────────────┐
  │  Subscribers:                        │
  │  ├─ PagerDuty webhook  (on-call page)│
  │  ├─ Lambda function    (auto-scale)  │
  │  └─ Slack webhook      (team notify) │
  └──────────────────────────────────────┘

  COMPOSITE ALARM (noise reduction):
  ─────────────────────────────────────
  ALARM if:
    P99LatencyAlarm = ALARM
    AND
    ErrorRateAlarm  = ALARM
  → Fires only when service is genuinely degraded
  → Single-metric alarms are informational (dashboards only)
```

```
ALARM STATES — Handle All Three
================================

  OK                         — metric is within threshold
  ALARM                      — threshold breached → page on-call
  INSUFFICIENT_DATA          — metric data missing (service crashed?)

  TRAP: Most teams only handle OK→ALARM transitions.
  INSUFFICIENT_DATA is actually dangerous — your service stopped emitting
  metrics entirely (container OOMKilled, deployment in progress, or worse:
  the service died silently). Treat INSUFFICIENT_DATA like ALARM.

  FIX: Set TreatMissingData = breaching
       So alarm moves to ALARM state when data stops arriving.
```

```yaml
# CloudFormation / CDK equivalent — P99 Alarm definition
OrderP99LatencyAlarm:
  Type: AWS::CloudWatch::Alarm
  Properties:
    AlarmName: "swiggy-order-p99-latency-alarm"
    AlarmDescription: "Order placement P99 latency > 500ms for 3 min"
    Namespace: "Swiggy/OrderService"
    MetricName: "OrderPlacementLatency"
    Dimensions:
      - Name: ServiceName
        Value: order-service
      - Name: Environment
        Value: prod
    ExtendedStatistic: "p99"        # PERCENTILE statistic, not Average
    ComparisonOperator: GreaterThanThreshold
    Threshold: 500                  # 500ms
    Period: 60                      # 1-minute rollup
    EvaluationPeriods: 3            # 3 consecutive violations before ALARM
    TreatMissingData: breaching     # MISSING = bad, not OK
    AlarmActions:
      - !Ref SwiggyCriticalSnsTopic
    OKActions:
      - !Ref SwiggyCriticalSnsTopic  # notify on recovery too

# Composite Alarm (P99 AND error rate both bad)
OrderDegradedCompositeAlarm:
  Type: AWS::CloudWatch::CompositeAlarm
  Properties:
    AlarmName: "swiggy-order-service-degraded"
    AlarmRule: >
      ALARM("swiggy-order-p99-latency-alarm")
      AND
      ALARM("swiggy-order-error-rate-alarm")
    AlarmActions:
      - !Ref SwiggyPagerDutySnsTopic  # Only page on-call when BOTH are bad
```

```
SLO ALARM PATTERN — 99.9% Availability SLO
============================================

  SLO: 99.9% of order requests succeed (0.1% error budget)
  Monthly error budget: 43.2 minutes of full-down time
                        OR unlimited partial degradation under 0.1%

  Multi-window burn rate alarm (Google SRE model):
  ─────────────────────────────────────────────────
  Window 1:  1-hour  window, burn rate > 14.4x  → CRITICAL (page immediately)
             (consuming 1-hour of budget in 1-hour = 14.4x normal)
  Window 2:  6-hour  window, burn rate > 6x     → HIGH     (page within 30min)
  Window 3:  72-hour window, burn rate > 1x     → LOW      (ticket, not page)

  Implementation:
  ErrorBudgetBurnRate = (error_rate_in_window / monthly_error_budget_fraction)
  If you're at 14.4x for 1 hour = you'll exhaust monthly budget in 2 hours.
  Page NOW.
```

### SECTION 3 — When They Ask: "How do you use CloudWatch Logs Insights? Show me an incident query."

> **You say:**
>
> "CloudWatch Logs Insights is an in-place query engine over your log groups.
> You don't need to export to S3 or pay for Athena — you query directly in the
> console or via API.
>
> The key to making it useful is structured logging. If your services emit JSON
> logs, Insights can query any field directly. If you log plain text strings,
> you're stuck using `like` pattern matching which is fragile and slow.
>
> My standard setup: each service emits JSON logs with fields like orderId,
> userId, latencyMs, status, traceId. Then during an incident I can run:
> 'show me all failed orders in the last 5 minutes grouped by error type'.
>
> The operational trap: CloudWatch Logs default retention is NEVER EXPIRE.
> A high-traffic service logging 1GB/day at $0.50/GB = $180/month just for
> log storage, growing every month. Always set retention to 30-90 days."

```
LOG GROUP STRUCTURE
====================

  CloudWatch Logs
  ├── /ecs/swiggy-order-service          ← one log group per service
  │   ├── order-service/container/a1b2  ← one log stream per container
  │   └── order-service/container/c3d4
  ├── /ecs/swiggy-payment-service
  ├── /ecs/swiggy-notification-service
  ├── /aws/lambda/swiggy-payment-fn      ← Lambda auto-creates log group
  └── /aws/eks/swiggy-cluster/pods       ← Container Insights pods log

  RETENTION SETTINGS (set these or pay forever):
  /ecs/order-service         → 30 days  (active debugging window)
  /aws/lambda/*              → 14 days  (Lambda logs are often noisy)
  /aws/eks/*/pods            → 7 days   (very high volume)
  Security audit logs        → 365 days (compliance)
```

```sql
-- CloudWatch Logs Insights — incident queries

-- Query 1: Find all exceptions in last 15 minutes, grouped by exception type
fields @timestamp, @message, @logStream
| filter @message like /Exception/
| stats count() as errorCount by errorType
| sort errorCount desc
| limit 20

-- Query 2: Find slow orders (latency > 1000ms) in structured JSON logs
fields @timestamp, orderId, userId, latencyMs, status
| filter latencyMs > 1000
| sort latencyMs desc
| limit 50

-- Query 3: Error rate by 5-minute bucket (to find when degradation started)
fields @timestamp, status
| filter status = "FAILED" or status = "SUCCESS"
| stats
    count_distinct(case(status="FAILED", orderId)) as failures,
    count_distinct(orderId) as total
    by bin(5m)
| sort @timestamp asc

-- Query 4: Correlate by traceId across services (find all logs for one request)
fields @timestamp, @message, service, orderId
| filter traceId = "1-64a1b2c3-d4e5f6a7b8c9d0e1"
| sort @timestamp asc
```

```java
// Structured JSON logging — Spring Boot with Logback JSON encoder

// logback-spring.xml
// Add dependency: net.logstash.logback:logstash-logback-encoder

// Your service emits structured JSON
@Slf4j
@Service
public class OrderService {

    public Order placeOrder(OrderRequest request) {
        long start = System.currentTimeMillis();

        // Structured log — every field is queryable in Logs Insights
        MDC.put("orderId", request.getOrderId());
        MDC.put("userId", request.getUserId());
        MDC.put("restaurantId", request.getRestaurantId());
        MDC.put("traceId", AWSXRay.getCurrentTraceHeader());  // link to X-Ray

        try {
            Order order = orderRepo.save(request.toOrder());
            long latencyMs = System.currentTimeMillis() - start;

            log.info("Order placed successfully",
                StructuredArguments.kv("latencyMs", latencyMs),
                StructuredArguments.kv("status", "SUCCESS"),
                StructuredArguments.kv("orderAmount", order.getTotalAmount())
            );
            // Emits: {"level":"INFO","message":"Order placed","orderId":"xyz",
            //         "userId":"u1","latencyMs":342,"status":"SUCCESS",...}
            return order;

        } catch (Exception ex) {
            log.error("Order placement failed",
                StructuredArguments.kv("status", "FAILED"),
                StructuredArguments.kv("errorType", ex.getClass().getSimpleName()),
                StructuredArguments.kv("errorMessage", ex.getMessage())
            );
            throw ex;
        } finally {
            MDC.clear();
        }
    }
}
```

### SECTION 4 — When They Ask: "How does X-Ray distributed tracing work? Show me a real scenario."

> **You say:**
>
> "X-Ray solves the question that metrics and logs can't answer on their own:
> in a microservices call chain, where exactly did my 800ms latency go?
>
> Every request gets a Trace ID — a unique identifier propagated via the
> X-Amzn-Trace-Id header through every service call. Each service creates a
> Segment capturing its own execution time. Within a segment, fine-grained
> Subsegments capture individual DB queries, external HTTP calls, and cache hits.
>
> When an order request takes 800ms, X-Ray's waterfall view shows me: order-service
> itself was 20ms, the payment-service call was 760ms. Inside payment-service, the
> Redis check was 3ms but the bank-API call was 740ms. Bank-API is the culprit.
> Without X-Ray, I'd be guessing.
>
> Sampling is the critical cost control: trace 5% by default, 100% of errors.
> Without a sampling rule, tracing 100% of 10,000 req/sec gets very expensive very fast."

```
X-RAY TRACE ANATOMY
=====================

  User clicks "Place Order" → request travels through 4 services

  TRACE ID: 1-64a1b2c3-d4e5f6a7b8c9d0e1   (propagated via header)
  ─────────────────────────────────────────────────────────────────

  order-service          [0ms ─────── 25ms]       Segment
    ├─ DynamoDB query    [2ms ─── 14ms]            Subsegment
    ├─ Redis cache       [15ms ─ 18ms]             Subsegment
    └─ HTTP→payment-svc  [19ms ─────────────── 820ms] Subsegment
         │
         └── payment-service  [19ms ──────────── 818ms]  Segment
               ├─ Redis check  [20ms ─ 23ms]             Subsegment
               ├─ Fraud check  [24ms ──── 44ms]          Subsegment
               └─ HTTP→bank    [45ms ───────────── 815ms] Subsegment
                    │
                    └── bank-api  [45ms ──────────── 813ms] Segment (3rd party)
                          ← 768ms spent here! ←

  notification-service   [821ms ─── 840ms]        Segment

  TOTAL: 840ms
  BOTTLENECK: bank-api (768ms / 91% of total latency)
  ACTION: cache bank responses, add timeout + retry with exponential backoff
```

```
X-RAY SERVICE MAP
==================

  Auto-generated from trace data — visual during incidents

  ┌──────────────┐     ┌──────────────────┐     ┌──────────────┐
  │   ALB        │────►│  order-service   │────►│payment-service│
  │  p99: 840ms  │     │  p99: 25ms  ✅   │     │ p99: 800ms ⚠ │
  │  err: 0.1%   │     │  err: 0.1%       │     │ err: 0.5%    │
  └──────────────┘     └──────────────────┘     └──────┬───────┘
                               │                        │
                       ┌───────▼──────┐        ┌────────▼──────┐
                       │   DynamoDB   │        │   bank-api    │
                       │  p99: 12ms ✅│        │  p99: 780ms ❌│
                       └──────────────┘        │  err: 0.5%    │
                                               └───────────────┘

  Colours: ✅ green = healthy  ⚠ yellow = elevated latency  ❌ red = errors
  One glance shows: bank-api is the source of all latency pain.
```

```
ANNOTATIONS vs METADATA — Which Is Which
==========================================

  ANNOTATION (indexed — can search/filter traces by these)
  ─────────────────────────────────────────────────────────
  Use for: orderId, userId, restaurantId, environment
  Max 50 annotations per trace
  Stored as indexed key-value pairs in X-Ray
  Example: "Show me all traces where orderId = ORD-12345"

  METADATA (NOT indexed — attached to trace but not searchable)
  ──────────────────────────────────────────────────────────────
  Use for: full request payload, response body, debug details
  No limit (within trace size limit of 64KB)
  Use for diagnosing a specific known trace, not for filtering

  RULE: Put identifying/filtering values in ANNOTATIONS.
        Put large diagnostic payloads in METADATA.
```

// implementation 'com.amazonaws:aws-xray-recorder-sdk-spring:2.x'

        AWSXRay.getCurrentSegment().putAnnotation("userId", request.getUserId());

            System.getenv("ENVIRONMENT"));

### SECTION 5 — When They Ask: "How do you monitor EKS at the pod level? What's Container Insights?"

> **You say:**
>
> "Without Container Insights, CloudWatch only sees EC2 node-level metrics —
> the average CPU of the entire node. If node CPU is 60%, you can't tell if
> that's three healthy pods at 20% each, or one pod at 58% about to OOMKill
> while the others are idle.
>
> Container Insights adds the CloudWatch agent as a DaemonSet to every EKS node.
> It collects pod-level CPU, memory, filesystem, and network — one metric per
> pod, not per node. Now when OOMKilled appears in your events, you go straight
> to Container Insights, filter by the affected pod, and see exactly when its
> memory crossed the limit.
>
> The integration with HPA is what makes it powerful for scaling. You can expose
> Container Insights metrics to KEDA as an external metric source — so your job
> scheduler scales up when order-service pod memory approaches the limit,
> not after OOMKill has already happened."

```
CONTAINER INSIGHTS — NODE vs POD VISIBILITY
=============================================

  WITHOUT Container Insights:
  ─────────────────────────────
  EC2 Node: cpu=62%, memory=71%
  ← Which pod is causing this? No idea.
  ← Is anything about to OOMKill? No idea.

  WITH Container Insights:
  ─────────────────────────
  order-service-pod-1:  cpu=18%, memory=412MB / 512MB (80%) ← approaching limit!
  order-service-pod-2:  cpu=22%, memory=380MB / 512MB (74%)
  order-service-pod-3:  cpu=19%, memory=501MB / 512MB (98%) ← OOMKill imminent!
  payment-service-pod-1: cpu=8%, memory=220MB / 512MB (43%)

  ACTION: Scale out order-service before pod-3 gets OOMKilled.

  METRICS AVAILABLE:
  ──────────────────
  pod_cpu_utilization           (% of requested CPU)
  pod_memory_utilization        (% of memory limit)
  pod_network_rx_bytes          (incoming bytes/sec)
  pod_network_tx_bytes          (outgoing bytes/sec)
  node_filesystem_utilization   (disk usage on node)
  cluster_failed_node_count     (node failures)
```

## COMMON TRAPS — What Interviewers Test

```
TRAP 1: Forgetting Log Retention
─────────────────────────────────
Mistake: Never setting log retention (CloudWatch default = NEVER EXPIRE)
Impact:  High-traffic service logs 1GB/day at $0.50/GB storage
         = $180/month growing each month → $500+/month within 3 months
Fix:     Always set RetentionInDays: 30 (default), 90 (compliance), 7 (high-volume)
         In CDK: every LogGroup must have retentionDays property
         Audit existing groups: aws logs describe-log-groups | grep -v retentionInDays

TRAP 2: High-Resolution Metrics Cost 2x
─────────────────────────────────────────
Mistake: Setting storageResolution=1 (1-second) for all custom metrics
Impact:  Standard custom metrics: $0.30/metric/month
         High-resolution:         $0.60/metric/month
         100 custom metrics × 2x = $60/month extra for no benefit
Fix:     Use storageResolution=60 (standard, 1-min) for most metrics
         Only use storageResolution=1 for real-time payment SLA dashboards

TRAP 3: X-Ray Costs Explode Without Sampling Rules
────────────────────────────────────────────────────
Mistake: Tracing 100% of requests in production
Impact:  10,000 req/sec × 60s × $5 per million traces = $3,000/month
         vs 5% sampling = $150/month
Fix:     Default sampling rule: FixedRate=0.05 (5%), ReservoirSize=10
         Separate rule: FixedRate=1.0 for error requests (100% errors always)
         Never set FixedRate=1.0 globally

TRAP 4: Ignoring INSUFFICIENT_DATA Alarm State
─────────────────────────────────────────────────
Mistake: Only handling OK→ALARM transitions in runbooks
Reality:  INSUFFICIENT_DATA means the service stopped sending metrics
          = container OOMKilled, deployment failed, network partition
Fix:      TreatMissingData: breaching on all production alarms
          Set INSUFFICIENT_DATA actions same as ALARM actions

TRAP 5: Alert Fatigue Without Composite Alarms
────────────────────────────────────────────────
Mistake: Each metric has its own alarm that pages on-call
Impact:  P99 latency alarm + error rate alarm + throughput alarm all fire
         simultaneously for same incident = 3 pages at 2AM
         Engineers start ignoring alarms ("it's probably nothing again")
Fix:     Use CompositeAlarm: page only when P99 > 500ms AND ErrorRate > 1%
         Single metric alarms are informational (dashboard/Slack), not pagers

TRAP 6: Container Insights Not Enabled by Default on EKS
──────────────────────────────────────────────────────────
Mistake: Assuming Container Insights is on after cluster creation
Reality: EKS does NOT enable CloudWatch Container Insights by default
         You see node-level EC2 metrics but not pod-level metrics
Fix:     aws eks update-addon --addon-name amazon-cloudwatch-observability
         Verify: kubectl get pods -n amazon-cloudwatch (should show DaemonSet)

TRAP 7: Missing Dimensions on Custom Metrics
──────────────────────────────────────────────
Mistake: Emitting OrderPlacementLatency without ServiceName/Environment dimensions
Impact:  prod and staging metrics merge into the same time series
         Alarm on prod fires from a staging load test
         Can't filter dashboard by environment
Fix:     Always include at minimum: Environment, ServiceName
         Consider: Region, AZ, Version for advanced slicing

TRAP 8: CloudWatch vs Prometheus/Grafana — Using the Wrong Tool
─────────────────────────────────────────────────────────────────
Mistake: Using CloudWatch custom metrics for EKS-native cardinality-heavy metrics
Reality:  CloudWatch charges per metric + per API call
          High-cardinality metrics (per-pod, per-endpoint) create thousands of
          custom metrics → $300+/month just for metrics
Fix:      EKS-native workloads → Prometheus (free, runs in cluster) + Grafana
          Lambda, managed services (RDS, SQS, SNS) → CloudWatch (auto-integrated)
          Hybrid: Prometheus for pod/service metrics, CloudWatch for infra + alarms
```
