### PART 1 — When They Ask: "Why private subnets? Walk me through the VPC design."

> **You say:**
>
> "This is the most important security decision in the whole architecture.
>
> Think of it like Swiggy's office building. The reception desk is at the front —
> that's your ALB in the public subnet. It accepts visitors. But the actual servers
> running the business are deep inside the building, not accessible from the street.
> That's your ECS tasks in the private subnet.
>
> In AWS terms — the public subnet has an Internet Gateway route, meaning traffic
> from the internet can reach resources there. The private subnet has NO Internet
> Gateway route — nothing from the internet can directly reach those services."

```
VPC SUBNET DESIGN — 3 AZs for high availability
=================================================

  VPC: 10.0.0.0/16

  AZ-a (us-east-1a)         AZ-b (us-east-1b)         AZ-c (us-east-1c)
  +-----------------------+  +-----------------------+  +-----------------------+
  | PUBLIC: 10.0.1.0/24   |  | PUBLIC: 10.0.2.0/24   |  | PUBLIC: 10.0.3.0/24   |
  | ALB nodes             |  | ALB nodes             |  | ALB nodes             |
  | NAT Gateway           |  |                       |  |                       |
  +-----------------------+  +-----------------------+  +-----------------------+
  | PRIVATE: 10.0.11.0/24 |  | PRIVATE: 10.0.12.0/24 |  | PRIVATE: 10.0.13.0/24 |
  | ECS tasks             |  | ECS tasks             |  | ECS tasks             |
  +-----------------------+  +-----------------------+  +-----------------------+
  | DATA: 10.0.21.0/24    |  | DATA: 10.0.22.0/24    |  | DATA: 10.0.23.0/24    |
  | RDS, Redis, MSK       |  | RDS, Redis, MSK       |  | RDS, Redis, MSK       |
  +-----------------------+  +-----------------------+  +-----------------------+

  ROUTING:
  Public subnet  → Internet Gateway  (internet-facing)
  Private subnet → NAT Gateway       (outbound only: for ECR pulls, Secrets Manager)
  Data subnet    → No internet route  (completely internal)

  WHY NAT GATEWAY in private subnet?
  ECS tasks need to:
  - Pull Docker images from ECR (outbound HTTPS)
  - Call Secrets Manager API (outbound HTTPS)
  - Call STS for IAM credentials (outbound HTTPS)
  NAT allows outbound-only. No inbound from internet possible.
```

> **You continue:**
>
> "The NAT Gateway is expensive but critical — it's the one-way door that lets
> private services reach AWS APIs without being reachable from the internet.
> I always put NAT Gateway in just one AZ to save cost in non-prod environments,
> but in production I put one in each AZ — if the NAT AZ goes down, services in
> the other AZs shouldn't lose internet access."

```
  |  Step 3: Register new Task Definition    |
```

```
ECR REPOSITORY — one per service:

  123456789.dkr.ecr.us-east-1.amazonaws.com/
  ├── swiggy/order-service         (tags: abc1234, def5678, ...)
  ├── swiggy/payment-service       (tags: abc1234, def5678, ...)
```

**Dockerfile for Order Service:**

```dockerfile
# Multi-stage build — keeps final image small
FROM eclipse-temurin:21-jdk-alpine AS builder
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests

FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
# Non-root user — security best practice
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser
COPY --from=builder /app/target/order-service-*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

> **You say:**
>
> "Two things worth highlighting in the Dockerfile — multi-stage build keeps
> the final image under 200MB by not including the JDK or Maven in the runtime image.
> And running as non-root is a security baseline — if someone exploits the app,
> they don't get root in the container."

### PART 3 — When They Ask: "Show me the ECS Task Definition. How do services get their config?"

> **You say:**
>
> "The task definition is like the blueprint for your container. It says how much
> CPU and memory, which Docker image to run, what environment config to inject,
> and — critically — where secrets come from.
>
> This is where most teams make their first mistake."

```
SECRETS MANAGER vs ENV VARS — The Most Common Mistake
======================================================

  WRONG (what junior engineers do):
  +---------------------------------------+
  | ECS Task Definition                   |
  | environment:                          |
  |   - name: DB_PASSWORD                 |
  |     value: "mypassword123"            |  ← NEVER DO THIS
  +---------------------------------------+

  WHY IT'S WRONG:
  ECS has a metadata endpoint reachable from inside every container:
  curl http://169.254.170.2/v2/metadata
  → returns task definition JSON
  → includes ALL environment variables in PLAINTEXT
  → any process inside the container can read DB_PASSWORD


  RIGHT (what production systems do):
  +---------------------------------------+
  | ECS Task Definition                   |
  | secrets:                              |
  |   - name: DB_PASSWORD                 |
  |     valueFrom: arn:aws:secretsmanager:|
  |       us-east-1:123:secret:           |
  |       prod/order-db/password          |
  +---------------------------------------+
          |
          | ECS agent fetches at container startup
          v
  +------------------+
  | Secrets Manager  |
  | (encrypted at    |
  |  rest with KMS)  |
  +------------------+
          |
          | Injected as env var
          v
  Container starts with DB_PASSWORD available
  Value never stored in task definition
  Never visible in CloudTrail or ECS console logs
```

> **You say:**
>
> "Two roles in the task definition — and people always confuse them.
> executionRoleArn is used by the ECS agent to PULL the image from ECR and
> FETCH secrets from Secrets Manager. The app never touches it.
> taskRoleArn is the role YOUR APPLICATION uses — S3 access, SQS, whatever the service needs.
> Totally separate permissions, totally separate roles."

```
TWO ROLES — What Each Does
============================

  executionRole (used by ECS agent, not your code):
  ├── ecr:GetAuthorizationToken
  ├── ecr:BatchGetImage          (pull Docker image from ECR)
  ├── secretsmanager:GetSecretValue  (fetch secrets at startup)
  └── logs:CreateLogStream       (send logs to CloudWatch)

  taskRole (used by YOUR Spring Boot app):
  ├── s3:GetObject, s3:PutObject      (if service accesses S3)
  ├── sqs:SendMessage, ReceiveMessage  (if service uses SQS)
  ├── kafka:*                          (if service uses MSK)
  └── xray:PutTraceSegments           (distributed tracing)

  Your Spring Boot code: S3Client.builder().build()
  SDK calls http://169.254.170.2/v4/credentials → gets taskRole creds
  (Same IMDS concept as EC2, but the endpoint path differs for Fargate)
```

### PART 4 — When They Ask: "How does the ALB route to the right service?"

> **You say:**
>
> "Path-based routing. The ALB has listener rules that forward requests
> to different Target Groups based on the URL path.
> Each microservice registers its ECS tasks as targets in its own Target Group."

```
ALB PATH-BASED ROUTING
=======================

  Incoming requests:
  POST /api/orders/place     → Target Group: order-service-tg
  POST /api/payments/process → Target Group: payment-service-tg
  GET  /api/restaurants/near → Target Group: restaurant-service-tg

  ALB Listener Rules (priority order):
  +-------------------------------------------+
  |  Rule 1: path /api/orders/*    → order-tg  |
  |  Rule 2: path /api/payments/*  → payment-tg|
  |  Rule 3: path /api/restaurants/→ rest-tg   |
  |  Rule 4: path /api/delivery/*  → deliver-tg|
  |  Rule 99: DEFAULT              → 404        |
  +-------------------------------------------+

  Target Group: order-service-tg
  +-------------------------------------------+
  |  Target 1: 10.0.11.45:8080  (ECS task 1) |
  |  Target 2: 10.0.12.67:8080  (ECS task 2) |
  |  Health Check: GET /actuator/health → 200  |
  |  Interval: 30s                            |
  +-------------------------------------------+

  When ECS adds a new task (scale out):
  → Task registers its IP:port with the target group automatically
  → ALB starts routing to it after health checks pass
  → No manual registration needed
```

**Spring Boot Actuator health endpoint (required for ALB):**

```java
// application.yml
management:

```

### PART 5 — When They Ask: "How does Order Service talk to Payment Service?"

> **You say:**
>
> "Two patterns — synchronous for things that need an immediate response,
> asynchronous via Kafka for things that don't.
>
> For synchronous calls, I use Spring Cloud OpenFeign with an internal ALB
> or AWS Cloud Map for service discovery.
> For async, I publish an event to MSK and let the downstream service consume it.
>
> The key principle is: don't make a synchronous call when you don't need the response
> immediately. It creates tight coupling and cascading failures."

```
SERVICE COMMUNICATION — Two Patterns
======================================

  SYNCHRONOUS (REST via Internal ALB or Cloud Map):

  Order Service                           Restaurant Service
  (task: 10.0.11.45)                     (task: 10.0.12.70)
        |                                        ^
        |  GET http://restaurant-service/        |
        |      api/restaurants/{id}/menu         |
        |  (via Cloud Map DNS)                   |
        +----------------------------------------+
                                                 |
                     Cloud Map resolves:         |
                     restaurant-service.swiggy.local → 10.0.12.70:8080

  ASYNCHRONOUS (Kafka via MSK):

  Order Service                 MSK (Kafka)              Notification Service
        |                      +-----------+                     |
        | publish event        |           |  consume event      |
        +--------------------->| order-    |-------------------->|
          OrderPlacedEvent     | events    |  send email/SMS     |
                               +-----------+         |
                                    |                v
                               Inventory Service  Delivery Service
                               (reserve stock)    (assign rider)
```

**OpenFeign client for sync calls:**

```java
// Feign client in Order Service to call Restaurant Service
@FeignClient(
    name = "restaurant-service",
    url = "${services.restaurant.url}",   // points to Cloud Map DNS
    configuration = FeignConfig.class
)
public interface RestaurantServiceClient {

    @GetMapping("/api/restaurants/{id}/menu")
    RestaurantMenuResponse getMenu(@PathVariable String id);

    @GetMapping("/api/restaurants/{id}/availability")
    AvailabilityResponse checkAvailability(@PathVariable String id);
}

// application.yml (Order Service):
services:
  restaurant:
    url: http://restaurant-service.swiggy.local:8080
    # Cloud Map DNS resolves this to the actual ECS task IPs

// FeignConfig with timeout and circuit breaker:
@Configuration
public class FeignConfig {

    @Bean
    public Request.Options requestOptions() {
        return new Request.Options(
            2000, TimeUnit.MILLISECONDS,   // connect timeout
            5000, TimeUnit.MILLISECONDS,   // read timeout
            true
        );
    }
}
```

**Kafka event publishing from Order Service:**

```java
@Service
public class OrderEventPublisher {

    private final KafkaTemplate<String, OrderEvent> kafkaTemplate;

    public void publishOrderPlaced(Order order) {
        OrderPlacedEvent event = OrderPlacedEvent.builder()
            .orderId(order.getId())
            .customerId(order.getCustomerId())
            .restaurantId(order.getRestaurantId())
            .totalAmount(order.getTotalAmount())
            .items(order.getItems())
            .timestamp(Instant.now())
            .build();

        // key = orderId ensures all events for same order go to same partition
        kafkaTemplate.send("order-events", order.getId(), event);
    }
}

// application.yml (MSK connection with IAM auth):
spring:
  kafka:
    bootstrap-servers: ${MSK_BOOTSTRAP_BROKERS}
    producer:
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.springframework.kafka.support.serializer.JsonSerializer
      acks: all         // wait for all replicas to acknowledge
      retries: 3
    properties:
      security.protocol: SASL_SSL
      sasl.mechanism: AWS_MSK_IAM
      sasl.jaas.config: software.amazon.msk.auth.iam.IAMLoginModule required;
```

### PART 6 — When They Ask: "How does RDS work with Spring Boot? Walk me through the connection pool."

> **You say:**
>
> "Each ECS task gets its own database connection pool — managed by HikariCP,
> which is Spring Boot's default. The key is tuning the pool size correctly,
> because if you have too many tasks or too large a pool, you'll exhaust RDS connections
> before you hit CPU limits. I've seen this exact issue in production."

```
HIKARICP CONNECTION POOL — Per Task
=====================================

  RDS PostgreSQL db.r6g.large:
  Max connections = (RAM in GB × 25) ≈ 250 connections total

  ECS Service: Order Service
  ┌──────────────────────────────────────────────────────────────┐
  │  Task 1: max-pool-size=10 connections                        │
  │  Task 2: max-pool-size=10 connections                        │
  │  Task 3: max-pool-size=10 connections  (after scale-out)     │
  │  Total across 3 tasks: 30 connections                        │
  └──────────────────────────────────────────────────────────────┘

  Other services also connect to same RDS:
  ┌──────────────────────────────────────────────────────────────┐
  │  Payment Svc: 2 tasks × 10 = 20 connections                  │
  │  Restaurant Svc: 2 tasks × 10 = 20 connections               │
  │  Admin/Migration: ~5 connections                             │
  │  Total: 30 + 20 + 20 + 5 = 75 connections                   │
  └──────────────────────────────────────────────────────────────┘

  250 max − 75 used = 175 headroom ← enough room to scale further

  IF YOU DON'T CALCULATE THIS:
  Auto-scaling kicks in → 10 Order Service tasks spin up
  10 × 10 = 100 new connections + existing 45 = 145
  Plus Payment + Restaurant scaling too
  → HikariCP throws: "Connection is not available, request timed out after 30000ms"
  → App broken even though RDS CPU is fine

  SOLUTION for large scale: RDS Proxy
  ┌──────────────────────────────────────────────────────────────┐
  │  RDS Proxy sits between ECS tasks and RDS                    │
  │  Tasks connect to Proxy (max 1000 connections to Proxy)      │
  │  Proxy maintains a small pool to RDS (e.g., 50 connections)  │
  │  Connection multiplexing: 1000 app connections → 50 DB conns │
  └──────────────────────────────────────────────────────────────┘
```

**application.yml with production HikariCP settings:**

```yaml
spring:
  datasource:
    url: jdbc:postgresql://${DB_HOST}:5432/swiggy_orders
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}          # injected from Secrets Manager
    driver-class-name: org.postgresql.Driver
    hikari:
      maximum-pool-size: 10           # max connections per task
      minimum-idle: 2                 # keep 2 warm connections always
      connection-timeout: 30000       # wait 30s before failing (ms)
      idle-timeout: 600000            # close idle connections after 10min
      max-lifetime: 1800000           # recreate connections after 30min
                                      # (prevents stale connections past
                                      #  RDS's wait_timeout)
      pool-name: OrderServicePool
      leak-detection-threshold: 60000 # warn if connection held > 60s

  jpa:
    hibernate:
      ddl-auto: validate              # NEVER create/update in prod
    properties:
      hibernate:
        dialect: org.hibernate.dialect.PostgreSQLDialect
        default_schema: orders
```

### PART 7 — When They Ask: "How does Redis fit into this architecture?"

> **You say:**
>
> "ElastiCache Redis serves three purposes in the Swiggy architecture —
> caching, idempotency, and distributed locks. Let me walk through each."

```
REDIS USE CASES IN ORDER SERVICE
==================================

  USE CASE 1 — Restaurant Menu Cache:
  ┌──────────────────────────────────────────────────────────────┐
  │  Order Service needs restaurant menu to validate the order   │
  │                                                              │
  │  WITHOUT CACHE:                                              │
  │  Every order → REST call to Restaurant Service → slow        │
  │                                                              │
  │  WITH REDIS CACHE:                                           │
  │  Order arrives                                               │
  │  → Check Redis: key "menu:{restaurantId}"                    │
  │  → CACHE HIT: return in <1ms ✓                              │
  │  → CACHE MISS: call Restaurant Service → store in Redis      │
  │                TTL = 5 minutes (menu doesn't change often)   │
  └──────────────────────────────────────────────────────────────┘

  USE CASE 2 — Idempotency (Duplicate Order Prevention):
  ┌──────────────────────────────────────────────────────────────┐
  │  Customer's app retries POST /api/orders due to timeout      │
  │  Two identical requests reach Order Service                  │
  │                                                              │
  │  Request carries: X-Idempotency-Key: uuid-abc-123            │
  │                                                              │
  │  First request:                                              │
  │  SETNX idempotency:uuid-abc-123 "PROCESSING" EX 300         │
  │  → success → process order → update Redis to "COMPLETED"    │
  │                                                              │
  │  Second request (retry):                                     │
  │  SETNX idempotency:uuid-abc-123 → FAILS (key exists)        │
  │  → return cached response from first request                 │
  │  Customer gets same response, no duplicate order created     │
  └──────────────────────────────────────────────────────────────┘

  USE CASE 3 — Rate Limiting (ShedLock / custom):
  ┌──────────────────────────────────────────────────────────────┐
  │  Prevent one customer from placing 100 orders/minute         │
  │                                                              │
  │  Redis sliding window counter per customerId                 │
  │  INCR rate:order:{customerId}:{minute}                       │
  │  EXPIRE rate:order:{customerId}:{minute} 60                  │
  │  If counter > 10: return 429 Too Many Requests               │
  └──────────────────────────────────────────────────────────────┘
```

**Spring Boot Redis config:**

```java
@Configuration
public class RedisConfig {

    @Bean
    public RedisConnectionFactory redisConnectionFactory(
            @Value("${spring.redis.host}") String host,

            RedisConnectionFactory factory) {
        RedisTemplate<String, Object> template = new RedisTemplate<>();
        template.setConnectionFactory(factory);
        template.setKeySerializer(new StringRedisSerializer());
        template.setValueSerializer(new GenericJackson2JsonRedisSerializer());

// Idempotency check in Order Service:
@Service
public class OrderService {

    private final StringRedisTemplate redis;

    public OrderResponse placeOrder(PlaceOrderRequest request, String idempotencyKey) {
        String key = "idempotency:" + idempotencyKey;

        // Try to set key — returns false if already exists (NX = only if Not eXists)
        Boolean isNew = redis.opsForValue()
            .setIfAbsent(key, "PROCESSING", Duration.ofMinutes(5));

        if (Boolean.FALSE.equals(isNew)) {
            // Duplicate request — return cached response
            String cached = redis.opsForValue().get(key + ":response");
            return parseResponse(cached);
        }

        // First time — process the order
        Order order = createOrder(request);

        // Cache the response for future duplicate requests
        redis.opsForValue().set(
            key + ":response",
            toJson(order),
            Duration.ofMinutes(5)
        );
        redis.opsForValue().set(key, "COMPLETED", Duration.ofMinutes(5));

        return mapToResponse(order);
    }
}
```

### PART 8 — When They Ask: "How does Auto Scaling work? What metric do you scale on?"

> **You say:**
>
> "Two different scaling strategies depending on the service type.
> For request-handling services like Order Service, I scale on CPU.
> For async worker services like Notification Service, I scale on SQS queue depth.
>
> The reason is different — CPU is the right signal for synchronous services
> because high CPU means incoming requests are overwhelming the tasks.
> But for a queue consumer, CPU stays near zero when the queue is empty —
> you need to scale on queue depth, not CPU."

```
AUTO SCALING — Two Strategies
================================

  Strategy 1: CPU-based (Order, Payment, Restaurant Services)

  ECS Service Auto Scaling Policy:
  Type: TargetTrackingScaling
  Metric: ECSServiceAverageCPUUtilization
  Target: 60%

  Behavior:
  CPU < 40% for 10min → scale IN  (remove 1 task, wait 10min before next)
  CPU > 60% for 3min  → scale OUT (add 1 task)
  Min tasks: 2  Max tasks: 10

  Why 60% target (not 80%)?
  At 80%, by the time new tasks spin up (60-90 seconds), you've
  already been overloaded for 3+ minutes. 60% gives headroom
  for the spin-up window.

  ──────────────────────────────────────────────────────────────────────
  Strategy 2: SQS Queue Depth (Notification Service)

  SQS Queue: order-notification-queue
  Metric: ApproximateNumberOfMessagesVisible

  Calculation:
  Target messages per task: 10
  Current queue depth: 100 messages
  Required tasks: 100 / 10 = 10 tasks

  If queue depth suddenly hits 500 (lunch rush):
  Required: 500 / 10 = 50 tasks (capped at max 20)
  → Scale out to 20 tasks immediately

  Queue drains → scale back in when depth drops
  ──────────────────────────────────────────────────────────────────────
  Scale-out Timeline (what happens after you get a traffic spike):

  t=0s    CPU spikes above 60%
  t=3min  CloudWatch alarm: 3 consecutive breaches
  t=3m10s ECS registers new task
  t=3m40s New task passes health check (startPeriod=60s)
  t=4m    ALB routes traffic to new task
  t=4m30s CPU normalizes

  This 4-minute gap is why I keep minimum 2 tasks (not 1).
  During scale-out, the existing tasks absorb the load.
```

### PART 9 — When They Ask: "What happens if a service goes down? How do you handle failures?"

> **You say:**
>
> "Three levels of failure handling — at the infrastructure level, the application level,
> and the data level. Let me walk through each."

```
FAILURE HANDLING — Three Levels
==================================

  LEVEL 1 — Infrastructure (ECS handles this automatically):
  ┌──────────────────────────────────────────────────────────────┐
  │  Task unhealthy (ALB health check fails 3 times)             │
  │  → ECS stops task, starts replacement automatically          │
  │  → ALB drains connections before stopping (deregistration)   │
  │  → New task in different AZ if original AZ has issues        │
  └──────────────────────────────────────────────────────────────┘

  LEVEL 2 — Application (Resilience4j):
  ┌──────────────────────────────────────────────────────────────┐
  │  Order Service calls Restaurant Service synchronously        │
  │  Restaurant Service goes slow (GC pause, DB overload)        │
  │                                                              │
  │  WITHOUT Circuit Breaker:                                    │
  │  Each Order request waits 30s for Restaurant response        │
  │  Order thread pool fills up (all threads waiting)            │
  │  Order Service itself becomes unresponsive = cascade failure  │
  │                                                              │
  │  WITH Circuit Breaker (Resilience4j):                        │
  │  Failure rate > 50% in last 10 calls → circuit OPENS         │
  │  Subsequent calls: immediate fallback (no waiting)           │
  │  Fallback: return cached menu from Redis                     │
  │  Order Service stays healthy                                 │
  │  Circuit tries to close after 30s (half-open probing)        │
  └──────────────────────────────────────────────────────────────┘

  LEVEL 3 — Data (Outbox Pattern for Kafka reliability):
  ┌──────────────────────────────────────────────────────────────┐
  │  Order Service: save order AND publish Kafka event           │
  │  PROBLEM: what if DB save succeeds but Kafka publish fails?  │
  │  → Order saved, no notification sent = silent failure        │
  │                                                              │
  │  SOLUTION: Outbox Pattern                                    │
  │  BEGIN TRANSACTION                                           │
  │    INSERT into orders (order data)                           │
  │    INSERT into outbox_events (event_type, payload, status)   │
  │  COMMIT                                                      │
  │                                                              │
  │  Separate outbox processor (scheduled every 100ms):          │
  │  SELECT * from outbox_events where status = 'PENDING'        │
  │  → publish to Kafka                                          │
  │  → UPDATE status = 'PUBLISHED'                              │
  │                                                              │
  │  DB transaction guarantees order + event saved together.     │
  │  Outbox processor handles Kafka failures with retry.         │
  └──────────────────────────────────────────────────────────────┘
```

**Resilience4j Circuit Breaker:**

```java
// application.yml
resilience4j:
  circuitbreaker:
    instances:
      restaurant-service:
        sliding-window-size: 10
        failure-rate-threshold: 50       # open circuit at 50% failures
        wait-duration-in-open-state: 30s
        permitted-calls-in-half-open-state: 3
        slow-call-duration-threshold: 3s
        slow-call-rate-threshold: 50

// OrderService.java
@Service
public class OrderService {

    private final RestaurantServiceClient restaurantClient;
    private final RedisTemplate<String, Object> redis;

    @CircuitBreaker(name = "restaurant-service", fallbackMethod = "getMenuFromCache")
    public RestaurantMenuResponse getMenu(String restaurantId) {
        return restaurantClient.getMenu(restaurantId);
    }

    // Fallback: serve from Redis cache when restaurant service is down
    private RestaurantMenuResponse getMenuFromCache(String restaurantId,
                                                     Exception ex) {
        log.warn("Circuit open for restaurant-service, using cached menu: {}", ex.getMessage());
        RestaurantMenuResponse cached =
            (RestaurantMenuResponse) redis.opsForValue().get("menu:" + restaurantId);
        if (cached != null) return cached;
        throw new ServiceUnavailableException("Restaurant menu temporarily unavailable");
    }
}
```

> **You say:**
>
> "So to summarize the full Swiggy architecture end to end:
>
> One — VPC design: services in private subnets, ALB in public.
> Nothing is directly reachable from the internet except the load balancer.
>
> Two — ECS Fargate with Docker containers tagged by git SHA.
> The deployment pipeline builds, tests, pushes to ECR, and does a rolling
> deploy with zero downtime.
>
> Three — Task definitions use Secrets Manager references, never plaintext env vars.
> The task role is the identity for the Spring Boot app — same IMDS mechanism as EC2
> but the endpoint is 169.254.170.2 for Fargate.
>
> Four — Services communicate synchronously via Feign clients with circuit breakers,
> and asynchronously via MSK Kafka for fire-and-forget operations.
> The Outbox pattern guarantees Kafka events aren't silently lost.
>
> Five — Connection pool math matters. Each ECS task gets 10 DB connections.
> Ten tasks = 100 connections. If you don't plan this upfront, auto-scaling
> breaks your database instead of saving you.
>
> Six — Redis for caching, idempotency, and rate limiting. Three different use cases,
> all from one ElastiCache cluster.
>
> The reason this architecture works at Swiggy's scale is stateless tasks, horizontal scaling,
> async decoupling, and all state in managed services — RDS, Redis, MSK — not in the containers."

## ONE-LINER ANSWERS (If Interviewer Wants Short)

**"Why ECS Fargate over EC2?"**
> "No EC2 instances to patch, right-size, or manage. I define CPU and memory per task,
> AWS handles the underlying compute. I pay per second of task runtime."

**"Where do your DB credentials live?"**
> "Secrets Manager. Referenced by ARN in the task definition. ECS injects them
> at runtime — never stored in task definition plaintext, never in git."

**"How do services find each other?"**
> "Cloud Map for service discovery — each service registers with a DNS name like
> `restaurant-service.swiggy.local`. Feign clients resolve this to the actual task IPs."

**"How do you handle a service going down mid-request?"**
> "Resilience4j circuit breaker. After 50% failures over 10 calls, the circuit opens
> and we serve from Redis cache. The calling service stays healthy — no cascading failure."

**"How does scaling work?"**
> "CPU target tracking for synchronous services, SQS queue depth for async workers.
> Min 2 tasks always running for availability across two AZs."

**"Why Outbox pattern?"**
> "DB and Kafka are two different systems. A network blip between my service and Kafka
> after the DB commit means a silent data loss. Outbox wraps both in one DB transaction —
> the event is always published, even if it takes a retry."
