### PART 1 — When They Ask: "What is Cognito? How is it set up?"

> **You say:**
>
> "Cognito is AWS's managed identity service — think of it like building your
> own Auth0 or Okta but fully integrated with AWS.
>
> It has two main components. User Pool handles user identities — signup, login,
> password reset, MFA. Identity Pool handles AWS resource access — giving users
> temporary IAM credentials. For API authentication in Spring Boot, we only need
> the User Pool."

```
COGNITO USER POOL SETUP
=========================

  User Pool: swiggy-users
  ├── Attributes:  email (required), phone, name
  │               custom:role (admin / customer / restaurant_owner)
  │               custom:restaurantId (for restaurant owners)
  │
  ├── User Groups (maps to Spring authorities):
  │   ├── CUSTOMERS        → can place orders, view history
  │   ├── RESTAURANT_OWNERS → can update menu, view their orders
  │   ├── DELIVERY_AGENTS  → can accept/complete deliveries
  │   └── ADMINS           → full access
  │
  ├── App Clients:
  │   ├── swiggy-web-client
  │   │   ├── OAuth flows: authorization_code, refresh_token
  │   │   ├── Allowed callback: https://swiggy.com/callback
  │   │   └── Token validity: access=1hr, refresh=30days
  │   │
  │   └── swiggy-mobile-client
  │       ├── OAuth flows: authorization_code, refresh_token
  │       └── PKCE enabled (no client secret for mobile apps)
  │
  ├── Domain: swiggy.auth.us-east-1.amazoncognito.com
  │
  └── MFA: Optional TOTP (for restaurant owners and admins)

  WHAT COGNITO GIVES YOU FOR FREE:
  ✓ Signup + email verification
  ✓ Login with brute-force protection
  ✓ Password reset flow
  ✓ Token issuance (JWT, RS256 signed)
  ✓ JWKS endpoint for token validation
  ✓ Social login (Google, Facebook) with minimal config
  ✓ MFA (SMS, TOTP)
  ✓ Token rotation
```

> **You say:**
>
> "The critical thing is that Cognito signs tokens with RS256 — asymmetric crypto.
> Cognito holds the private key and signs the token. Every Spring Boot service
> validates the signature using the PUBLIC key from the JWKS endpoint.
> No service ever has the private key. That's the security model."

```
COGNITO JWKS ENDPOINT:
=======================

  URL (auto-generated by AWS):
  https://cognito-idp.us-east-1.amazonaws.com/{USER_POOL_ID}/.well-known/jwks.json

  Response:
  {
    "keys": [{
      "kid": "abc123",         ← key ID (rotates periodically)
      "kty": "RSA",
      "use": "sig",
      "n": "...",              ← RSA public key modulus
      "e": "AQAB"              ← RSA public key exponent
    }]
  }

  Spring Boot caches this on startup.
  If Cognito rotates the key → Spring Boot auto-fetches new keys.
  Your app never needs to be redeployed for key rotation.
```

### PART 2 — When They Ask: "What's inside the JWT token? What claims do you use?"

> **You say:**
>
> "A JWT has three parts — header, payload, signature.
> The payload is where all the claims live. Let me show you what Cognito puts in there
> and which ones Spring Security cares about."

```
JWT TOKEN ANATOMY — Cognito Access Token
==========================================

  Header (base64):
  {
    "alg": "RS256",
    "kid": "abc123"    ← used to look up public key in JWKS
  }

  Payload (base64):
  {
    "sub":         "a1b2c3d4-user-id-uuid",     ← USER'S COGNITO ID
    "iss":         "https://cognito-idp.us-east-1.amazonaws.com/us-east-1_ABC123",
    "client_id":   "swiggy-web-client",
    "event_id":    "xyz789",
    "token_use":   "access",                    ← MUST be "access" not "id"
    "scope":       "openid email",
    "auth_time":   1700000000,
    "exp":         1700003600,                  ← 1 HOUR from now
    "iat":         1700000000,
    "jti":         "unique-jwt-id",
    "username":    "user@gmail.com",
    "cognito:groups": ["CUSTOMERS"],            ← GROUP MEMBERSHIP
    "cognito:username": "a1b2c3d4-user-id-uuid"
  }

  Signature (RS256):
  RS256(base64(header) + "." + base64(payload), privateKey)

  WHAT SPRING SECURITY VALIDATES:
  ✓ Signature (against JWKS public key)
  ✓ exp (not expired)
  ✓ iss (matches your Cognito pool URL)
  ✓ token_use = "access" (not id or refresh token)

  WHAT YOUR CODE READS:
  ✓ sub          → user identity
  ✓ cognito:groups → maps to Spring GrantedAuthority roles
  ✓ username     → human-readable identifier for logs
```

> **You say:**
>
> "One trap — Cognito issues three tokens: access, id, and refresh.
> You should only validate access tokens in your API. The id token has user
> profile info (name, email) and is meant for the client app, not your API.
> I always add a check: `token_use must equal 'access'` — reject id tokens
> sent as Bearer tokens."

**SecurityConfig.java — the full filter chain:**

```java
@Configuration
@EnableWebSecurity
@EnableMethodSecurity          // enables @PreAuthorize on methods
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable())                // REST API — no CSRF needed
            .sessionManagement(session -> session
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS))  // no sessions
            .cors(cors -> cors.configurationSource(corsConfigurationSource()))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/actuator/health").permitAll()   // ALB health checks
                .requestMatchers("/actuator/info").permitAll()
                .requestMatchers(HttpMethod.GET, "/api/restaurants/**").permitAll()  // public menu
                .anyRequest().authenticated()            // everything else needs JWT
            )
            .oauth2ResourceServer(oauth2 -> oauth2
                .jwt(jwt -> jwt
                    .decoder(jwtDecoder())               // validates signature + claims
                    .jwtAuthenticationConverter(cognitoAuthConverter())  // maps groups to roles
                )
                .authenticationEntryPoint(customAuthEntryPoint())  // custom 401 response
            );

        return http.build();
    }

    @Bean
    public JwtDecoder jwtDecoder() {
        // Spring auto-fetches JWKS and caches it
        NimbusJwtDecoder decoder = NimbusJwtDecoder
            .withJwkSetUri("https://cognito-idp.us-east-1.amazonaws.com/" +
                           userPoolId + "/.well-known/jwks.json")
            .build();

        // Custom validators AFTER signature check:
        OAuth2TokenValidator<Jwt> withIssuer =
            JwtValidators.createDefaultWithIssuer(
                "https://cognito-idp.us-east-1.amazonaws.com/" + userPoolId
            );

        // Add custom validator: token_use must be "access" not "id"
        OAuth2TokenValidator<Jwt> withTokenUse = token -> {
            String tokenUse = token.getClaim("token_use");
            if ("access".equals(tokenUse)) return OAuth2TokenValidatorResult.success();
            return OAuth2TokenValidatorResult.failure(
                new OAuth2Error("invalid_token", "token_use must be 'access'", null)
            );
        };

        decoder.setJwtValidator(
            new DelegatingOAuth2TokenValidator<>(withIssuer, withTokenUse)
        );
        return decoder;
    }

    @Bean
    public JwtAuthenticationConverter cognitoAuthConverter() {
        // Maps Cognito groups → Spring GrantedAuthority
        JwtGrantedAuthoritiesConverter groupsConverter =
            new JwtGrantedAuthoritiesConverter();
        groupsConverter.setAuthoritiesClaimName("cognito:groups");
        groupsConverter.setAuthorityPrefix("ROLE_");
        // "CUSTOMERS" group → "ROLE_CUSTOMERS" authority

        JwtAuthenticationConverter converter = new JwtAuthenticationConverter();
        converter.setJwtGrantedAuthoritiesConverter(groupsConverter);
        return converter;
    }

    @Bean
    public CorsConfigurationSource corsConfigurationSource() {
        CorsConfiguration config = new CorsConfiguration();
        config.setAllowedOrigins(List.of(
            "https://swiggy.com",                    // prod CloudFront
            "http://localhost:3000"                  // local dev
        ));
        config.setAllowedMethods(List.of("GET","POST","PUT","DELETE","OPTIONS"));
        config.setAllowCredentials(true);
        config.setAllowedHeaders(List.of("*"));

        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/api/**", config);
        return source;
    }
}
```

**Using `@PreAuthorize` in controllers:**

```java
@RestController
@RequestMapping("/api/orders")
public class OrderController {

    // Only CUSTOMERS can place orders
    @PostMapping
    @PreAuthorize("hasRole('CUSTOMERS')")
    public ResponseEntity<OrderResponse> placeOrder(
            @RequestBody PlaceOrderRequest request,
            @AuthenticationPrincipal Jwt jwt) {   // inject the decoded JWT

        String customerId = jwt.getSubject();      // Cognito user ID (sub claim)
        String username   = jwt.getClaim("username");
        return ResponseEntity.ok(orderService.place(request, customerId));
    }

    // ADMINS can view any order, CUSTOMERS can only view their own
    @GetMapping("/{orderId}")
    @PreAuthorize("hasRole('ADMINS') or (hasRole('CUSTOMERS') and @orderSecurity.isOwner(#orderId, principal))")
    public ResponseEntity<OrderResponse> getOrder(@PathVariable String orderId) {
        return ResponseEntity.ok(orderService.getById(orderId));
    }

    // Restaurant owners see only orders for their restaurant
    @GetMapping("/restaurant/{restaurantId}")
    @PreAuthorize("hasRole('RESTAURANT_OWNERS') and @orderSecurity.ownsRestaurant(#restaurantId, principal)")
    public ResponseEntity<List<OrderResponse>> getRestaurantOrders(
            @PathVariable String restaurantId) {
        return ResponseEntity.ok(orderService.getByRestaurant(restaurantId));
    }
}

// Custom security expression bean:
@Component("orderSecurity")
public class OrderSecurityExpression {

    public boolean isOwner(String orderId, Jwt jwt) {
        String customerId = jwt.getSubject();
        return orderRepository.existsByIdAndCustomerId(orderId, customerId);
    }

    public boolean ownsRestaurant(String restaurantId, Jwt jwt) {
        String claimedRestaurantId = jwt.getClaim("custom:restaurantId");
        return restaurantId.equals(claimedRestaurantId);
    }
}
```

### PART 4 — When They Ask: "How does the user's identity flow across microservices?"

> **You say:**
>
> "This is where most engineers get it wrong. They validate the JWT in the first service
> and then lose the user identity when calling downstream services.
>
> The correct approach: propagate the original JWT as a Bearer token in every
> downstream call. Every service validates it independently against Cognito's JWKS.
> No re-issuance, no custom headers, no service-level user lookup."

```
TOKEN PROPAGATION ACROSS SERVICES
====================================

  Customer (JWT: sub=user-123, role=CUSTOMERS)
          |
          | Authorization: Bearer <customer_jwt>
          v
  Order Service ──validates JWT──> Cognito JWKS
          |
          | propagates SAME customer JWT downstream
          | Authorization: Bearer <customer_jwt>  ← SAME TOKEN
          v
  Payment Service ──validates JWT──> Cognito JWKS
          |
          | propagates SAME customer JWT downstream
          v
  Restaurant Service ──validates JWT──> Cognito JWKS

  WHY PROPAGATE THE ORIGINAL JWT (not a new one)?
  ┌──────────────────────────────────────────────────────────────┐
  │  ✓ Every service knows the REAL user identity (sub claim)    │
  │  ✓ Audit logs across services reference the same user ID     │
  │  ✓ Authorization rules work in every service independently   │
  │  ✓ No "inner service trusts all requests" security hole      │
  │  ✓ Distributed tracing links to user ID                      │
  └──────────────────────────────────────────────────────────────┘

  HOW IT WORKS IN PRACTICE:
  ┌──────────────────────────────────────────────────────────────┐
  │  1. Extract JWT from incoming request header                 │
  │  2. Pass it to Feign client via RequestInterceptor           │
  │  3. Feign automatically adds it to outgoing request header   │
  │  4. Next service validates it — same as direct call          │
  └──────────────────────────────────────────────────────────────┘
```

**Feign interceptor for JWT propagation:**

```java
// This bean runs for EVERY outgoing Feign call
@Component
public class JwtPropagationInterceptor implements RequestInterceptor {

    @Override
    public void apply(RequestTemplate template) {
        // Get the current request's Authorization header
        HttpServletRequest request =
            ((ServletRequestAttributes) RequestContextHolder
                .currentRequestAttributes()).getRequest();

        String authHeader = request.getHeader("Authorization");

        if (authHeader != null && authHeader.startsWith("Bearer ")) {
            // Forward the SAME JWT to the downstream service
            template.header("Authorization", authHeader);
        }
    }
}

// Register with Feign:
@Configuration
public class FeignConfig {
    @Bean
    public RequestInterceptor jwtPropagationInterceptor() {
        return new JwtPropagationInterceptor();
    }
}

// Feign client automatically gets the token on every call:
@FeignClient(name = "payment-service",
             url = "${services.payment.url}",
             configuration = FeignConfig.class)
public interface PaymentServiceClient {
    @PostMapping("/api/payments/capture")
    PaymentResponse capturePayment(@RequestBody CaptureRequest request);
    // Authorization: Bearer <customer_jwt> added automatically
}
```

### PART 5 — When They Ask: "What about service-to-service calls with no user?"

> **You say:**
>
> "Great question — this is the M2M pattern. When Order Service calls Payment Service
> as part of a background job — say a retry processor or a scheduled task —
> there's no user JWT in the thread context.
>
> For this we use the OAuth2 client_credentials grant.
> Each service has its own Cognito App Client with a client_id and client_secret.
> The service requests a token directly from Cognito, gets a service-level JWT,
> and uses that for the downstream call."

```
M2M (Machine-to-Machine) TOKEN FLOW
=====================================

  Order Service (background retry job)
          |
          | POST https://swiggy.auth.us-east-1.amazoncognito.com/oauth2/token
          | grant_type=client_credentials
          | client_id=order-service-m2m-client
          | client_secret=<secret from Secrets Manager>
          | scope=payment-service/capture
          |
          v
  Cognito returns:
  {
    "access_token": "<service_jwt>",
    "token_type": "Bearer",
    "expires_in": 3600
  }

  Service JWT payload (NO user claims):
  {
    "sub":       "order-service-m2m-client",
    "iss":       "https://cognito-idp.../swiggy-pool",
    "client_id": "order-service-m2m-client",
    "scope":     "payment-service/capture",
    "token_use": "access",
    "exp":       1700003600
  }
          |
          | Authorization: Bearer <service_jwt>
          v
  Payment Service
  ├── validates JWT signature (same JWKS)
  ├── checks scope = "payment-service/capture"
  └── no user identity — that's expected for M2M
```

**Spring Boot M2M client implementation:**

```java
// Service-level token manager (caches token, refreshes before expiry)
@Component
public class ServiceTokenProvider {

    private final RestTemplate restTemplate;
    private volatile String cachedToken;
    private volatile Instant tokenExpiry;

    @Value("${cognito.token-endpoint}")
    private String tokenEndpoint;

    @Value("${cognito.m2m.client-id}")
    private String clientId;

    @Value("${cognito.m2m.client-secret}")  // from Secrets Manager via ECS secret
    private String clientSecret;

    public String getToken() {
        // Return cached token if still valid (with 60s buffer)
        if (cachedToken != null && Instant.now().isBefore(tokenExpiry.minusSeconds(60))) {
            return cachedToken;
        }
        return fetchNewToken();
    }

    private synchronized String fetchNewToken() {
        // Double-check after acquiring lock
        if (cachedToken != null && Instant.now().isBefore(tokenExpiry.minusSeconds(60))) {
            return cachedToken;
        }

        MultiValueMap<String, String> body = new LinkedMultiValueMap<>();
        body.add("grant_type", "client_credentials");
        body.add("client_id", clientId);
        body.add("client_secret", clientSecret);
        body.add("scope", "payment-service/capture");

        TokenResponse response = restTemplate.postForObject(
            tokenEndpoint, body, TokenResponse.class
        );

        cachedToken = response.getAccessToken();
        tokenExpiry = Instant.now().plusSeconds(response.getExpiresIn());
        return cachedToken;
    }
}

// Feign interceptor for M2M calls (different from user JWT propagation):
@Component
public class ServiceTokenInterceptor implements RequestInterceptor {

    private final ServiceTokenProvider tokenProvider;

    @Override
    public void apply(RequestTemplate template) {
        // Use service token when no user context exists
        String userJwt = extractUserJwtFromContext();
        if (userJwt != null) {
            template.header("Authorization", "Bearer " + userJwt);
        } else {
            // Background job — use service M2M token
            template.header("Authorization", "Bearer " + tokenProvider.getToken());
        }
    }
}
```

**Payment Service validates scope for M2M calls:**

```java
@RestController
public class PaymentController {

    // Accessible by customers AND by order-service M2M token
    @PostMapping("/api/payments/capture")
    @PreAuthorize(
        "hasRole('CUSTOMERS') or " +
        "hasAuthority('SCOPE_payment-service/capture')"  // M2M scope claim
    )
    public PaymentResponse capture(@RequestBody CaptureRequest request,
                                   @AuthenticationPrincipal Jwt jwt) {

        boolean isServiceCall = jwt.getClaim("token_use").equals("access")
                             && jwt.getClaim("client_id") != null;

        if (isServiceCall) {
            // M2M call — no user context, trust the service
            return paymentService.captureForService(request);
        } else {
            // User call — validate ownership
            String userId = jwt.getSubject();
            return paymentService.captureForUser(request, userId);
        }
    }
}
```

### PART 6 — When They Ask: "How do you handle token expiry? What if the token expires mid-session?"

> **You say:**
>
> "This is the question everyone asks — and the answer has three layers.
> Frontend layer, Spring Boot layer, and what to do when refresh fails.
>
> The short answer is: Amplify handles refresh automatically on the React side.
> On the Spring Boot side, we just validate and return 401.
> The React app catches the 401, triggers a refresh, and retries the call."

```
TOKEN EXPIRY HANDLING — Full Flow
====================================

  NORMAL SESSION (token still valid):

  React App                   Spring Boot
      |                           |
      | Bearer <access_token>     |
      +-------------------------->|
      |                           | validates: OK
      |<--------------------------+
      |  200 OK                   |

  ──────────────────────────────────────────────

  EXPIRY SCENARIO (access token expired):

  React App      Amplify SDK        Cognito          Spring Boot
      |               |                |                  |
      | API call       |                |                  |
      +-------------->|                |                  |
      |               | check expiry:  |                  |
      |               | expired!       |                  |
      |               |                |                  |
      |               | POST /token    |                  |
      |               | grant=refresh  |                  |
      |               | refresh_token= |                  |
      |               | <30d token>    |                  |
      |               +--------------->|                  |
      |               |                | NEW access_token  |
      |               |<--------------+                  |
      |               |                                   |
      |               | retry original call               |
      |               | Bearer <new_access_token>         |
      |               +---------------------------------->|
      |               |                                   | validates: OK
      |               |<----------------------------------+
      | 200 OK         |                                   |
      |<--------------+                                   |

  THIS HAPPENS TRANSPARENTLY — user never sees a login page

  ──────────────────────────────────────────────

  REFRESH TOKEN EXPIRED (30 days of inactivity):

  React App      Amplify SDK        Cognito
      |               |                |
      |               | POST /token    |
      |               | grant=refresh  |
      |               +--------------->|
      |               |                | {"error": "NotAuthorizedException"}
      |               |<--------------+
      |               |
      |  redirect to /login
      |<--------------+
  User must log in again (30 days is intentional)
```

**React Amplify configuration (handles refresh transparently):**

```javascript
// amplify config in React app — one-time setup
import { Amplify } from 'aws-amplify';
import { fetchAuthSession } from 'aws-amplify/auth';

Amplify.configure({
    Auth: {
        Cognito: {
            userPoolId:            process.env.REACT_APP_COGNITO_USER_POOL_ID,
            userPoolClientId:      process.env.REACT_APP_COGNITO_CLIENT_ID,
            loginWith: { email: true }
        }
    }
});

// Axios interceptor — adds token to every request, refreshes if expired:
axios.interceptors.request.use(async (config) => {
    try {
        // fetchAuthSession() automatically refreshes if access token expired
        const session = await fetchAuthSession();
        config.headers.Authorization = `Bearer ${session.tokens.accessToken}`;
        return config;
    } catch (error) {
        // Refresh failed (30-day token expired) — redirect to login
        window.location.href = '/login';
        return Promise.reject(error);
    }
});

// 401 response interceptor (belt-and-suspenders):
axios.interceptors.response.use(
    response => response,
    async error => {
        if (error.response?.status === 401) {
            // Session expired on server side — redirect to login
            window.location.href = '/login';
        }
        return Promise.reject(error);
    }
);
```

> **You say:**
>
> "The key insight is that Amplify's `fetchAuthSession()` is smart — it checks the token
> expiry BEFORE making the call. If it's expired, it silently calls Cognito's token endpoint
> with the refresh token, gets a new access token, and hands it back.
> This all happens in the background — the user never sees anything.
>
> On the Spring Boot side, we don't need any refresh logic. We just validate the token
> and return 401 if it's expired. It's the client's job to refresh."

### PART 7 — When They Ask: "How does API Gateway fit in? Do you use Cognito Authorizer?"

> **You say:**
>
> "Two patterns. If you're using API Gateway in front of your services,
> you can push JWT validation to the API Gateway layer using a Cognito Authorizer —
> the gateway validates the token before the request even reaches Spring Boot.
>
> In the Swiggy architecture we're discussing — ALB in front of ECS Fargate —
> we validate in Spring Boot directly. No API Gateway.
>
> Let me show you both patterns so you can speak to either."

```
PATTERN 1 — ALB + ECS Fargate (what we've been building):
===========================================================

  Customer
      |  Bearer <jwt>
      v
  ALB  ──────────────────────────────► ECS Fargate
  (no JWT validation here)             Spring Security validates JWT
                                        vs Cognito JWKS

  Pros: simpler, no API Gateway cost
  Cons: all services must implement their own validation
  Best for: microservices where each service has different auth rules


PATTERN 2 — API Gateway + Cognito Authorizer:
==============================================

  Customer
      |  Bearer <jwt>
      v
  API Gateway
      |
      | Is this token valid?
      +──────────────────────────────► Cognito

      |  ✓ valid (200)
      |  ✗ invalid (401) → returns 401, Lambda/ECS never invoked

  Lambda / ECS Fargate

  Pros: one place validates all tokens, Spring Boot code simpler

  "For the Swiggy microservices on ECS Fargate, we validate in Spring Boot
   because each service has different authorization rules — Order Service
   checks ownership, Restaurant Service checks restaurant assignment.
   That logic can't live in API Gateway.

   If we were building a simpler read API on Lambda, I'd use the API Gateway
   Cognito Authorizer — it's free validation before Lambda is even invoked."
```

### PART 8 — When They Ask: "How do you handle token revocation? What if a user is compromised?"

> **You say:**
>
> "This is the honest limitation of JWTs — they're stateless.
> Once issued, the access token is valid until expiry, and Spring Boot's validation
> only checks the signature and expiry. It doesn't call Cognito to check if
> the token was revoked.
>
> Here's how I handle this in production."

```
TOKEN REVOCATION STRATEGIES
==============================

  SCENARIO: customer's account is compromised, admin revokes access

  PROBLEM: access token still valid for up to 1 hour
           Spring Boot validates signature + expiry → passes ✓

  STRATEGY 1 — Short access token TTL (what Swiggy uses):
  ┌──────────────────────────────────────────────────────────────┐
  │  Access token TTL: 1 hour (Cognito minimum is 5 minutes)     │
  │  Revoke in Cognito: AdminUserGlobalSignOut                   │
  │  Effect: refresh token immediately invalidated               │
  │          access token still valid for up to 1 hour          │
  │  Acceptable for most use cases — financial max exposure: 1hr │
  └──────────────────────────────────────────────────────────────┘

  STRATEGY 2 — Redis token blocklist (for zero-tolerance systems):
  ┌──────────────────────────────────────────────────────────────┐
  │  When user is revoked: store jti (JWT ID) in Redis           │
  │  Redis key: revoked:<jti>  TTL: 1 hour (same as access token) │
  │                                                              │
  │  Add to JWT validation in Spring Security:                   │
  │  After signature check: check Redis for jti                  │
  │  If found: return 401 (token revoked)                        │
  │                                                              │
  │  Cost: one Redis lookup per request                          │
  │  Benefit: instant revocation                                 │
  │  Used in: payment systems, healthcare, high-security apps    │
  └──────────────────────────────────────────────────────────────┘
```

**Redis token blocklist in Spring Security:**

```java
@Bean
public JwtDecoder jwtDecoder() {
    NimbusJwtDecoder decoder = NimbusJwtDecoder
        .withJwkSetUri(jwksUri)
        .build();

    // Add revocation check after standard validation:
    OAuth2TokenValidator<Jwt> revocationCheck = token -> {
        String jti = token.getId();   // jti claim — unique JWT ID
        if (jti != null && redis.hasKey("revoked:" + jti)) {
            return OAuth2TokenValidatorResult.failure(
                new OAuth2Error("token_revoked", "Token has been revoked", null)
            );
        }
        return OAuth2TokenValidatorResult.success();
    };

    decoder.setJwtValidator(
        new DelegatingOAuth2TokenValidator<>(
            JwtValidators.createDefaultWithIssuer(issuerUri),
            tokenUseValidator,
            revocationCheck           // <- add blocklist check
        )
    );
    return decoder;
}

// Admin endpoint to revoke a user's tokens:
@PostMapping("/admin/users/{userId}/revoke")
@PreAuthorize("hasRole('ADMINS')")
public void revokeUserTokens(@PathVariable String userId) {
    // 1. Revoke in Cognito (invalidates refresh token immediately)
    cognitoClient.adminUserGlobalSignOut(r -> r
        .userPoolId(userPoolId)
        .username(userId)
    );

    // 2. If using Redis blocklist: add current active JTIs to blocklist
    // (requires tracking active JTIs — adds complexity)

}
```

### CLOSING — Strong Finish

> **You say:**
>
> "So to summarize the Swiggy authentication system end to end:
>
> One — Cognito User Pool handles all authentication. Spring Boot services
> are pure resource servers — they only validate tokens, never issue them.
>
> Two — Every service uses the same Spring Security filter chain:
> validate JWT signature against Cognito's JWKS endpoint,
> check expiry and issuer, map Cognito groups to Spring roles.
> The code is identical across all five microservices.
>
> Three — Token propagation: the original user JWT flows through all services
> via a Feign RequestInterceptor. Each service validates independently.
> No service trusts another service blindly.
>
> Four — M2M for background jobs: client_credentials grant gives service-level tokens.
> Payment Service checks scope, not user role, for M2M calls.
>
> Five — Token refresh is the React/Amplify layer's job. Spring Boot returns 401.
> Amplify's fetchAuthSession() silently refreshes and retries — user never sees it.
>
> Six — Revocation: short TTL for most use cases, Redis blocklist for payment-sensitive
> operations where you need instant revocation.
>
> The beauty of this architecture is that Spring Boot services are completely stateless.
> No session store, no user lookup on every request — just cryptographic signature
> verification against a public key. That scales to any number of instances."

## ONE-LINER ANSWERS (If Interviewer Wants Short)

**"How does Spring Boot validate JWT without calling Cognito on every request?"**
> "It fetches Cognito's public key from the JWKS endpoint once at startup,
> caches it, and validates the token signature locally. No network call per request.
> Just RSA signature verification — microseconds."

**"What's the difference between access token and id token?"**
> "Access token is for APIs — contains scopes and groups. Id token is for the client app —
> contains user profile (name, email, picture). Your Spring Boot API should only
> accept access tokens, not id tokens as Bearer credentials."

**"How do you pass user identity between microservices?"**
> "Forward the original JWT in the Authorization header via a Feign RequestInterceptor.
> Every downstream service validates it independently against Cognito's JWKS.
> No re-issuance, no trust between services — just cryptographic validation."

**"What happens when an access token expires mid-session?"**
> "Spring Boot returns 401. Amplify's fetchAuthSession() intercepts the error,
> silently calls Cognito's token endpoint with the refresh token, gets a new access token,
> and retries the original request. The user sees nothing."

**"How does Order Service call Payment Service without a user?"**
> "M2M with client_credentials grant. Order Service authenticates as itself to Cognito
> and gets a service-level JWT. Payment Service validates the JWT and checks the scope
> claim — not a user role."
