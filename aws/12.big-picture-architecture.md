## The Key Relationships to Understand

```
  USER REQUEST FLOW (read path — e.g., "browse products"):
  User → CloudFront (cache hit? serve) → ALB → ECS Pod
       → ElastiCache Redis (cache hit? serve fast)
       → Aurora Read Replica (cache miss — slow path)
       → Cache result in Redis → return to user

  USER REQUEST FLOW (write path — e.g., "place order"):
  User → ALB → ECS Pod
       → Aurora PRIMARY (write)
       → Publish OrderPlaced event to SNS
       → SNS fans out to SQS queues (email, SMS, analytics)
       → SQS consumers (KEDA-scaled) process asynchronously

  AUTH FLOW:
  User → POST /login → Spring Security → BCrypt verify
       → Issue JWT (15min access + HttpOnly refresh cookie)
       → Subsequent requests: JWT filter validates token
       → SecurityContext set → @PreAuthorize checks role

  DEPLOYMENT FLOW:
  git push → GitHub Actions → mvn test → docker build
           → docker push ECR → update ECS task definition
           → ECS rolling deploy (PDB ensures no downtime)

  SECRET FLOW (zero hardcoded credentials):
  Pod starts → IRSA role → call Secrets Manager
  → Get DB password + JWT secret → HikariCP connects to RDS Proxy
  → RDS Proxy authenticates to Aurora
```

## Common Interview Flow (15-Year Architect Path)

```
Interviewer: "Design the Swiggy order system on AWS."

You draw the full diagram above and say:
  1. Edge layer: CloudFront + WAF protects + caches frontend
  2. ECS/EKS: pods scale with HPA (CPU) and KEDA (SQS depth)
  3. RDS Proxy: prevents connection exhaustion at scale
  4. ElastiCache: avoids hitting DB for every product/session read
  5. SQS/SNS: decouples order processing from notification delivery
  6. Secrets Manager + IRSA: zero hardcoded credentials anywhere
  7. VPC: three-tier subnet model, isolated DB layer, VPC endpoints

Then dive deep into whichever component they ask about.
Each file in this folder covers one deep-dive topic.
```
