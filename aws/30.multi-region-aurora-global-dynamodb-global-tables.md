## NEW LEARNER FOUNDATION — Read This First If You Are New

```
KEY TERMS EXPLAINED SIMPLY
============================

ACTIVE-PASSIVE
  One region handles ALL traffic (PRIMARY). Second region is a standby
  (SECONDARY) — it receives replicated data but does not serve user traffic.
  If primary fails, DNS is updated to point to secondary.
  Think of it like a car with a spare tyre: you drive on one tyre until it
  bursts, then switch to the spare.

  RPO (Recovery Point Objective):
    How much data you can afford to LOSE. If replication lag is 30 seconds,
    your RPO is 30 seconds — the last 30 seconds of writes are lost on failover.
    RPO = data lag between primary and secondary at the moment of failure.

  RTO (Recovery Time Objective):
    How long recovery TAKES. Time from failure detection to serving traffic
    again. Includes: detect failure + DNS TTL expiry + secondary promotion
    + health checks passing. Typical active-passive RTO: 60–300 seconds.

ACTIVE-ACTIVE
  BOTH regions handle live user traffic simultaneously. No "primary". Users
  in US hit us-east-1; users in Mumbai hit ap-south-1. Both regions can
  read AND write. Think of two equal branches of a bank, both serving
  customers at the same time.

  Challenge: what if two users update the SAME record at the same time in
  different regions? This is the "write conflict" problem. Solutions:
  - Last-Writer-Wins (LWW): higher timestamp wins, other write is silently lost
  - Application-level merge: app inspects both versions and merges them
  - CRDTs (Conflict-free Replicated Data Types): data types that can be
    merged mathematically (counters, sets) — used in Cassandra, Redis

AURORA GLOBAL DATABASE
  AWS-managed MySQL/PostgreSQL that replicates at the STORAGE layer (not SQL
  binlog) between regions. One primary region (read+write), up to 5 secondary
  regions (read-only replicas). Cross-region replication lag: < 1 second typical.
  Think of it as one database that physically exists in multiple regions
  simultaneously, with the primary accepting writes and secondaries handling reads.

DYNAMODB GLOBAL TABLES
  AWS-managed NoSQL that replicates across multiple regions. ALL regions accept
  reads AND writes. Conflict resolution: last-writer-wins by timestamp.
  No single "primary" — this is truly active-active at the data layer.

GLOBAL ACCELERATOR
  AWS service that provides two static anycast IP addresses. User traffic hits
  the nearest AWS edge PoP (Point of Presence), then travels over AWS's private
  global backbone instead of the public internet. Reduces latency 40–60% for
  dynamic API calls. Sub-30 second failover (connection-level, not DNS TTL).

DATA RESIDENCY
  Legal requirement that certain data (especially personal data) must be stored
  within a specific country or region. GDPR requires EU user personal data to
  stay in the EU (or countries with adequate protection). India's RBI mandate
  requires payment data to be stored in India only. Multi-region architecture
  must be designed to COMPLY with data residency — replication that copies data
  to non-compliant regions can cause regulatory violations.

LAST-WRITER-WINS (LWW)
  Conflict resolution strategy: when two conflicting writes exist for the same
  key, the one with the higher timestamp wins. The other write is silently
  discarded — no error, no notification. Suitable for eventually-consistent
  data where the latest value is always "correct" (user preferences, sessions).
  DANGEROUS for financial data, inventory, order state machines.
```

## SECTION 1 — Active-Active vs Active-Passive

### When They Ask: "What's the difference between active-active and active-passive, and when do you choose each?"

> **You say:**
>
> "These are two fundamentally different multi-region strategies with different
> cost, complexity, and failure characteristics.
>
> Active-passive: one region handles all traffic. The secondary is a warm standby —
> it receives replicated data but is not serving user requests. On failure, you
> update DNS to point to secondary. Failover time depends on DNS TTL (often 60–300s)
> plus health check propagation.
>
> RPO equals the replication lag at the moment of failure — if lag was 15 seconds,
> you lose 15 seconds of writes. RTO equals the time to detect failure, let DNS
> propagate, and have the secondary pass health checks.
>
> Active-active: both regions serve live traffic simultaneously. Lower latency
> for global users. Near-zero RTO for regional outages because traffic simply
> shifts to the healthy region — no DNS update needed if you're using Global
> Accelerator. But you must handle write conflicts, and you double your infrastructure cost.
>
> I choose active-passive for: internal tools, cost-sensitive workloads,
> workloads where 2-minute downtime is acceptable. I choose active-active for:
> global consumer products, financial platforms requiring zero downtime, any
> workload where users are distributed across continents."

```
ACTIVE-PASSIVE vs ACTIVE-ACTIVE
=================================

ACTIVE-PASSIVE:
────────────────
  Users ──► Route53 ──► us-east-1 (PRIMARY — serving all traffic)
                             │
                         replication
                         (async, lag)
                             │
                             ▼
                        eu-west-1 (SECONDARY — standby, NOT serving traffic)

  On failure of us-east-1:
  1. Route53 health check detects failure (~10-30s)
  2. DNS TTL expires — clients get new IP (~60-300s)
  3. Secondary promoted to primary (~60s for Aurora)
  Total RTO: 2-7 minutes typical
  RPO: replication lag at time of failure (seconds to minutes)

  Cost: secondary at reduced capacity. 30-50% extra cost.
  Use for: DR, dev/test, cost-sensitive B2B SaaS.

ACTIVE-ACTIVE:
────────────────
  US Users ──► Global Accelerator ──► us-east-1 (serving US traffic)
  EU Users ──► Global Accelerator ──► eu-west-1 (serving EU traffic)
                                           ▲
                                     BOTH regions = primary
                                     BOTH accept reads + writes

  On failure of us-east-1:
  1. Global Accelerator detects unhealthy endpoint (~10s)
  2. ALL traffic shifts to eu-west-1 (~20-30s)
  Total RTO: sub-30 seconds
  RPO: near-zero (DynamoDB GT replication in-flight writes may have lag)

  Cost: full capacity in both regions. 100% extra cost.
  Write conflicts: must design for LWW or application merge.
  Use for: global consumer apps, financial platforms, OTT, ride-hailing.
```

## SECTION 2 — Aurora Global Database

### When They Ask: "How does Aurora Global Database work, and how is it different from read replicas?"

> **You say:**
>
> "The key insight is WHERE replication happens. Standard MySQL read replicas
> use binlog replication — the primary executes SQL, writes to binlog, ships
> the binlog to replicas which re-execute. That's slow and CPU-intensive,
> especially cross-region.
>
> Aurora Global Database replicates at the STORAGE layer, below the SQL engine.
> Aurora uses a distributed storage system — 6 copies across 3 AZs in the primary
> region. The redo log pages are shipped directly from storage to the secondary
> region's storage. No SQL re-execution. This is why it achieves under 1 second
> cross-region lag versus minutes with binlog.
>
> The architecture: one primary region that accepts both reads and writes.
> Up to 5 secondary regions that are read-only. Dedicated infrastructure for
> cross-region replication — it doesn't compete with your normal read traffic.
>
> The use case I give in interviews: global SaaS platform where EU users need
> to read user profile data. Without Aurora Global, every EU read crosses the
> Atlantic — 80–150ms added latency. With Frankfurt secondary, EU reads are
> local — under 10ms."

```
AURORA GLOBAL DATABASE — STORAGE-LEVEL REPLICATION
======================================================

  us-east-1 (PRIMARY REGION)
  ────────────────────────────
  ┌─────────────────────────────────────────────────┐
  │  Aurora Writer Instance (reads + writes)        │
  │  Aurora Reader Instance(s) (reads only, local)  │
  │                                                 │
  │  Aurora Storage Layer                           │
  │  ┌──────┐  ┌──────┐  ┌──────┐  (6 copies,      │
  │  │ AZ-1a│  │ AZ-1b│  │ AZ-1c│   2 per AZ)      │
  │  └──────┘  └──────┘  └──────┘                  │
  └────────────────┬────────────────────────────────┘
                   │
          dedicated replication
          infrastructure (<1s lag)
          redo log pages only
          (NOT full SQL re-execution)
                   │
                   ▼
  eu-west-1 (SECONDARY REGION)
  ────────────────────────────
  ┌─────────────────────────────────────────────────┐
  │  Aurora Reader Instance(s) — READ ONLY          │
  │  EU users read here → no Atlantic crossing      │
  │                                                 │
  │  Aurora Storage Layer                           │
  │  ┌──────┐  ┌──────┐  ┌──────┐                  │
  │  │ AZ-1a│  │ AZ-1b│  │ AZ-1c│                  │
  │  └──────┘  └──────┘  └──────┘                  │
  └─────────────────────────────────────────────────┘

  KEY FACTS:
  - Lag: < 1 second typical (measure: aurora_global_db_replication_lag_msec)
  - Writes: ONLY to us-east-1 primary — NOT active-active writes
  - Reads from secondary: serve EU users locally
  - Failover (managed): promote secondary → ~1 minute
  - Failover (unmanaged): primary region completely gone → manual promotion
  - Max secondary regions: 5
  - Pricing: cross-region replication charges apply (~$0.20/GB)

  NOT active-active for writes. EU writes still go to us-east-1.
  Active-active writes require DynamoDB Global Tables (with LWW trade-off).
```

```java
// RoutingDataSource — route reads to secondary, writes to primary
@Configuration
public class DataSourceConfig {

    @Bean
    @Primary
    public DataSource routingDataSource(
            @Qualifier("writeDataSource") DataSource writeDs,
            @Qualifier("readDataSource") DataSource readDs) {

        AbstractRoutingDataSource routing = new AbstractRoutingDataSource() {
            @Override
            protected Object determineCurrentLookupKey() {
                // Route based on transaction type
                return TransactionSynchronizationManager.isCurrentTransactionReadOnly()
                    ? "read" : "write";
            }
        };

        Map<Object, Object> targets = new HashMap<>();
        targets.put("write", writeDs);
        targets.put("read", readDs);
        routing.setTargetDataSources(targets);
        routing.setDefaultTargetDataSource(writeDs);
        return routing;
    }
}

// Service layer — mark read transactions explicitly
@Service
public class UserProfileService {

    // @Transactional(readOnly = true) → routed to eu-west-1 secondary
    @Transactional(readOnly = true)
    public UserProfile getProfile(String userId) {
        return userRepo.findById(userId).orElseThrow();
    }

    // @Transactional (readOnly defaults to false) → routed to us-east-1 primary
    @Transactional
    public UserProfile updateProfile(UserProfile profile) {
        return userRepo.save(profile);
    }
}
```

### Trap: "If Aurora Global secondary is read-only, how do EU users update their own data?"

> **You say:**
>
> "This is the key architectural constraint people miss. Aurora Global is NOT
> active-active for writes. EU users can READ from Frankfurt at low latency,
> but their WRITES still cross the Atlantic to us-east-1.
>
> For a global SaaS, this is often acceptable because reads outnumber writes
> 10-to-1 or more. User profile reads: millions per minute. Profile updates:
> thousands per day. The write latency penalty (80ms extra) is invisible to
> users because profile updates are infrequent.
>
> For workloads that NEED active-active writes — like a chat app where users
> in Mumbai need to send messages that are immediately visible to users in New York
> — you use DynamoDB Global Tables, not Aurora Global. The trade-off is LWW
> conflict resolution.
>
> The architecture decision is: does your workload require active-active WRITES?
> If yes, DynamoDB Global Tables. If reads dominate and writes can tolerate
> cross-region trip, Aurora Global."

## SECTION 3 — DynamoDB Global Tables

### When They Ask: "How does DynamoDB Global Tables handle write conflicts?"

> **You say:**
>
> "This is the most dangerous trap in DynamoDB Global Tables and I've seen teams
> get burned by it in production.
>
> DynamoDB Global Tables uses last-writer-wins based on the write timestamp. All
> regions accept writes simultaneously, changes replicate asynchronously to all
> other regions in under a second typically. When two conflicting writes arrive
> at different regions for the same item, the one with the higher timestamp wins.
> The other write is silently lost. No error. No exception. No notification.
>
> Let me give you the concrete scenario: User A is in Mumbai. User B is in Virginia.
> They both open the same order item at the same time. User A updates it at T=1000ms.
> User B updates the same item at T=999ms. Both writes succeed — DynamoDB returns 200
> to both users. Both replicate globally. T=1000ms wins. User B's update at T=999ms
> is gone forever. User B has no idea their update was overwritten.
>
> For user watch history in an OTT platform, this is fine — last device sync wins.
> For financial balances, inventory counts, or order state machines, this is catastrophic."

```
DYNAMODB GLOBAL TABLES — LAST-WRITER-WINS CONFLICT SCENARIO
=============================================================

  T=995ms: User A opens Order #42 in Mumbai     → reads: {status: "PENDING"}
  T=996ms: User B opens Order #42 in Virginia   → reads: {status: "PENDING"}

           Mumbai (ap-south-1)        Virginia (us-east-1)
  ─────────────────────────────────────────────────────────
  T=999ms:                            User B writes:
                                      {status: "PROCESSING", ts: 999}
                                      DynamoDB returns 200 OK ✅

  T=1000ms: User A writes:
            {status: "SHIPPED", ts: 1000}
            DynamoDB returns 200 OK ✅

  T=1001ms: Replication begins in both directions

  T=1002ms: CONFLICT DETECTED (same item, two writes)
            WINNER: ts=1000 (User A's write)
            LOSER: ts=999 (User B's write) ← SILENTLY DISCARDED

  RESULT:
  - Both users got 200 OK — no error
  - Virginia now shows: {status: "SHIPPED"}  (User A's write)
  - User B's "PROCESSING" update is GONE FOREVER
  - No error log, no CloudWatch alert, no notification

  ⚠ THIS IS SILENT DATA LOSS ⚠

SAFE vs UNSAFE USE CASES:
──────────────────────────

  SAFE (LWW acceptable):                    UNSAFE (LWW causes bugs):
  ─────────────────────                     ────────────────────────
  User watch history                        Financial balances
  (last device sync wins = fine)            (concurrent debits → lost write)

  Shopping cart (browse)                    Inventory counts
  (last edit wins = fine)                   (oversell on concurrent purchase)

  Content metadata (title, thumbnail)       Order state machine
  (last admin edit wins = fine)             (PENDING→PROCESSING→SHIPPED race)

  User preferences / settings               Booking / seat reservation
  (last toggle wins = fine)                 (double booking on LWW loss)

  Session tokens                            Leaderboard scores
  (last login wins = fine)                  (score update silently lost)
```

```java
// WRONG: simple write — vulnerable to LWW silent loss for critical data
public void updateInventory(String productId, int newCount) {
    Map<String, AttributeValue> item = new HashMap<>();
    item.put("productId", AttributeValue.builder().s(productId).build());
    item.put("count", AttributeValue.builder().n(String.valueOf(newCount)).build());

    dynamoDbClient.putItem(PutItemRequest.builder()
        .tableName("Inventory")
        .item(item)
        .build());
    // ⚠ If two regions write simultaneously, one is silently lost
}

// CORRECT: conditional write with version attribute — detect conflicts
public void updateInventory(String productId, int expectedVersion, int newCount) {
    Map<String, AttributeValue> item = new HashMap<>();
    item.put("productId", AttributeValue.builder().s(productId).build());
    item.put("count", AttributeValue.builder().n(String.valueOf(newCount)).build());
    item.put("version", AttributeValue.builder().n(String.valueOf(expectedVersion + 1)).build());

    try {
        dynamoDbClient.putItem(PutItemRequest.builder()
            .tableName("Inventory")
            .item(item)
            .conditionExpression("version = :expectedVersion")
            .expressionAttributeValues(Map.of(
                ":expectedVersion", AttributeValue.builder()
                    .n(String.valueOf(expectedVersion)).build()
            ))
            .build());
    } catch (ConditionalCheckFailedException e) {
        // Another region already updated this item — retry or escalate
        throw new OptimisticLockException("Inventory conflict detected for " + productId, e);
    }
}

// For OTT watch history — LWW is FINE, simple write is correct
public void updateWatchHistory(String userId, String contentId, long positionMs) {
    Map<String, AttributeValue> item = new HashMap<>();
    item.put("userId", AttributeValue.builder().s(userId).build());
    item.put("contentId", AttributeValue.builder().s(contentId).build());
    item.put("positionMs", AttributeValue.builder().n(String.valueOf(positionMs)).build());
    item.put("updatedAt", AttributeValue.builder().n(String.valueOf(System.currentTimeMillis())).build());

    // LWW is acceptable here: if two devices update the watch position at the same
    // time, the more recent one wins — this is the correct behavior for resume playback
    dynamoDbClient.putItem(PutItemRequest.builder()
        .tableName("WatchHistory")
        .item(item)
        .build());
}
```

### Trap: "Is DynamoDB Global Tables eventually consistent or strongly consistent?"

> **You say:**
>
> "Within a region, DynamoDB supports both eventually consistent and strongly
> consistent reads. For Global Tables replication across regions — always
> eventually consistent. There is no cross-region strong consistency option.
>
> This means if a user in Mumbai writes to ap-south-1 and immediately reads
> from ap-south-1, they will see their write (local strong consistency is available).
> But if their next request routes to us-east-1 — perhaps they switched devices —
> they may see the state BEFORE their write for up to a few hundred milliseconds.
>
> For most use cases (watch history, preferences, sessions) this is fine.
> For financial data where a payment must be immediately reflected — use a
> single-region Aurora with Global Accelerator for routing, not DynamoDB Global Tables."

## SECTION 4 — Global Accelerator

### When They Ask: "What is AWS Global Accelerator and when do you use it vs CloudFront?"

> **You say:**
>
> "They both use AWS's global edge network but for completely different purposes
> and I get asked to differentiate them in every system design interview.
>
> CloudFront is a CDN — it caches content at edge locations. Perfect for
> images, videos, static assets, and cacheable API responses. A CloudFront
> edge in Singapore serves cached content without ever hitting your origin.
> Latency win comes from content being physically close to the user.
>
> Global Accelerator does NOT cache. It's a network-level accelerator for
> dynamic content — API calls, websocket connections, anything that can't be cached.
> When a Mumbai user calls your payment API, their TCP connection terminates at
> the nearest AWS edge PoP, then travels over AWS's private fiber backbone to your
> ALB in us-east-1. AWS backbone is faster and more reliable than the public internet.
>
> The second benefit is failover speed. CloudFront uses DNS TTL — switching origins
> takes minutes. Global Accelerator works at the connection level and can reroute
> traffic in under 30 seconds. I use this for active-active failover between regions."

```
  Use for:          Dynamic APIs               Static/cacheable content
```

## SECTION 5 — Data Residency

### When They Ask: "How do you handle GDPR and India data localization in a multi-region architecture?"

> **You say:**
>
> "Data residency requirements completely change how you think about replication.
> Performance-driven multi-region is about COPYING data everywhere for speed.
> Compliance-driven multi-region is about KEEPING data in specific places — which
> means you must sometimes NOT replicate.
>
> GDPR requires EU personal data to be stored in the EU or countries the EU
> considers to have adequate protection. If I use DynamoDB Global Tables and
> add a replica in us-east-1, EU user PII is now in the US — potential GDPR violation.
>
> India's RBI payment data localization mandate requires that payment instrument
> data, transaction data, and customer payment data are stored ONLY in India.
> A Mumbai Aurora primary that replicates to a Singapore secondary is compliant.
> A Mumbai Aurora primary that replicates to us-east-1 violates the RBI mandate.
>
> The solution is a data residency field on each user profile and routing logic
> in the application layer to direct database writes to the compliant region."

```
GDPR-COMPLIANT MULTI-REGION ARCHITECTURE
==========================================

  EU User Registration
        │
        ▼

        │
        ▼
  Sets: user.dataResidency = "EU"
        │

        ▼                                                     ▼
  Write user PII to                            DO NOT replicate PII to:
  Aurora primary eu-west-1 (Frankfurt)         - us-east-1 (US)
  (GDPR compliant)                             - ap-south-1 (India, not adequate)

  ⚠ DynamoDB Global Tables TRAP for GDPR:
  If you add eu-west-1 AND us-east-1 replicas to same Global Table,
  DynamoDB AUTOMATICALLY replicates EU user data to us-east-1.
  There is no per-item filtering in DynamoDB Global Tables replication.
  → Separate tables per region for PII, NOT Global Tables for EU PII

=====================================

        │

        │
```

```java
// Data residency routing — Spring Boot implementation
@Component
public class DataResidencyRouter {

    @Autowired
    private Map<String, JdbcTemplate> regionalJdbcTemplates;
    // Keys: "EU", "IN", "US" → each maps to Aurora primary in that region

    public JdbcTemplate getWriteClient(User user) {
        String residency = user.getDataResidency();
        JdbcTemplate client = regionalJdbcTemplates.get(residency);
        if (client == null) {
            return regionalJdbcTemplates.get("US"); // default
        }
        return client;
    }
}

@Service
public class UserDataService {

    @Autowired
    private DataResidencyRouter router;

    public void saveUserProfile(User user, UserProfile profile) {
        JdbcTemplate jdbcTemplate = router.getWriteClient(user);
        // Write goes to compliance-correct region
        jdbcTemplate.update(
            "INSERT INTO user_profiles (user_id, profile_data) VALUES (?, ?)",
            user.getUserId(),
            objectMapper.writeValueAsString(profile)
        );
    }
}
```

## COMMON TRAPS — What Interviewers Are Testing

```
8 COMMON MULTI-REGION TRAPS
=============================

TRAP 1 — MOST DANGEROUS: DynamoDB Global Tables LWW Silent Conflict
─────────────────────────────────────────────────────────────────────
  What happens: Two regions write same item simultaneously → one silently discarded
  When it bites: inventory oversell, financial balance errors, order state corruption
  Sign you failed: "We use DynamoDB Global Tables for all our data"
  Recovery: Conditional writes + version attribute for critical data,
            or don't use Global Tables for financial/inventory data

TRAP 2: Aurora Secondary Cannot Be Promoted in <1 min if PRIMARY REGION IS GONE
──────────────────────────────────────────────────────────────────────────────────
  Managed failover: ~1 minute (Aurora detects primary issue, promotes secondary)
  Unmanaged failover: when the ENTIRE primary region is down and Aurora control
  plane in that region is unreachable — you must manually promote the secondary
  using: aws rds failover-global-cluster --global-cluster-identifier my-global
  This takes longer (5-10 minutes) and requires runbook + operator action.
  Not tested? Your RTO claim of "1 minute" is theoretical, not proven.

TRAP 3: Not Testing Failover — Theoretical RPO/RTO vs Actual
──────────────────────────────────────────────────────────────
  "Our RTO is 1 minute" — when was this last tested?
  GameDays / chaos engineering: intentionally fail a region quarterly
  Measure: actual time from failure to serving traffic, actual data loss
  Teams that never test failover discover their runbooks are outdated when
  a real outage happens at 2am.

TRAP 4: Global Accelerator ≠ CDN — No Caching
──────────────────────────────────────────────
  Common confusion: "We use Global Accelerator to cache our API responses globally"
  Wrong: Global Accelerator does NOT cache. It routes. It accelerates.
  For caching: CloudFront. For dynamic API routing: Global Accelerator.
  Using Global Accelerator for static assets wastes money vs CloudFront.

TRAP 5: Multi-Region = 2x Cost (at minimum)
─────────────────────────────────────────────
  Every resource in primary region must exist in secondary region:
  EKS node groups, RDS instances, ElastiCache, NAT Gateways, Load Balancers
  Cross-region data transfer charges (Aurora replication, DynamoDB GT)
  Global Accelerator fixed cost: $0.025/hour (~$18/month) + data transfer
  Active-active = 100% extra. Active-passive = 30-50% extra.
  Always include cost in architecture discussion — shows business awareness.

TRAP 6: GDPR — DynamoDB Streams May Replicate EU PII to Non-EU Regions
────────────────────────────────────────────────────────────────────────
  DynamoDB Global Tables replicates ALL items to ALL replica regions.
  There is no per-item or per-attribute filtering in replication.
  If you add a us-east-1 replica to a table that stores EU PII:
  GDPR violation — EU personal data is now in the US.
  Fix: separate tables for EU PII (eu-west-1 only, no replicas outside EU)
       or use Aurora in eu-west-1 for PII, DynamoDB GT only for non-PII.

TRAP 7: DynamoDB Global Tables Pricing Surprise
─────────────────────────────────────────────────
  Replicated Write Request Unit = 2x the cost of a regular WRU
  A write to a Global Table with 3 replicas costs 3x rWRU per write
  High-write workloads can see 3-5x DynamoDB costs vs single-region
  Always calculate DynamoDB costs with replication multiplier before committing.

TRAP 8: Aurora Cross-Region Replication Transfer Charges
──────────────────────────────────────────────────────────
  Aurora Global Database cross-region replication is NOT free.
  Charge: ~$0.20/GB of replication data transferred
  High-write Aurora primary (e.g., payments, order events) generates
  significant replication data. A 500GB/day write workload = $100/day in
  replication costs alone. Include this in cost estimates.
```

## Interview Cheat Sheet (Say This Confidently)

> "For multi-region architecture: Aurora Global Database replicates at the storage layer — below SQL — achieving under 1 second cross-region lag, but writes still go to the primary region only, so it solves read latency for global users, not active-active writes. DynamoDB Global Tables is truly active-active — all regions accept writes — but the critical trap is last-writer-wins conflict resolution: when two regions write the same item simultaneously, one is silently discarded with no error. Use conditional writes with a version attribute for any data where silent loss is unacceptable — financial balances, inventory, order state machines. For watch history, sessions, and preferences, LWW is fine. Global Accelerator provides two static anycast IPs and routes traffic over AWS's private backbone — not a CDN, does not cache, but gives 40-60% latency improvement for dynamic APIs and sub-30-second failover without DNS TTL dependency. Use traffic dials for gradual blue-green deployments between regions. Data residency adds a compliance dimension: GDPR means EU PII must stay in EU regions — DynamoDB Global Tables replicates everywhere with no per-item filtering, so use separate regional tables or Aurora for EU PII. India's RBI mandate keeps payment data in Mumbai only. Active-active doubles your infrastructure cost — always quantify this in your design."
