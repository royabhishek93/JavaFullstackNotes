# #113 — Reflection-Heavy Code Path After Library Upgrade

> **Category:** CPU Profiling & Flame Graphs | **Type:** Scenario Q&A | **Priority:** 📘 Advanced

## 🗣️ The Interview Question
"After a library upgrade, CPU went up 30%. No other changes. How do you trace it?"

## 😊 Explain It Simply (for anyone)
Imagine an office where, instead of calling a coworker directly by name, someone has to walk over to the company directory, look up "who handles this task" from scratch, and then physically walk to find them — every single time, even for the same task repeated a thousand times a day. That lookup process is slow compared to just remembering "oh, that's Sarah's job" and going straight to her. In Java, "looking someone up in the directory instead of calling them directly" is called reflection — a way of finding and invoking a method by its name at runtime instead of calling it directly in code. It's flexible but much slower than a direct call. Libraries sometimes switch internally between a fast "direct call" style and a slower "reflection" style between versions, and if the results of that expensive lookup aren't cached, your program re-pays the lookup cost on every single use. A flame graph makes this obvious: you'll see `Method.invoke()` or `reflect.*` taking up a big, unexpected slice of the CPU pie that wasn't there before the upgrade.

## 📊 Visualize It
```
Before upgrade:  [req] -> [direct method call] -> [done]      (fast)

After upgrade:   [req] -> [class.getMethod("process")]  <- expensive lookup!
                            -> [method.invoke(...)]      <- every single call
                            -> [done]

Flame graph shows: java.lang.reflect.Method.invoke() now 30% wider than before
Fix: cache the Method object once (static field), don't re-look-up per call.
```

## 🏭 The Real Production Answer (15-YOE Level)
Library upgrades that change how classes are introspected, especially if they moved from code generation to reflection, can cause this.

async-profiler flame graph will show `java.lang.reflect.Method.invoke()` or `sun.reflect.*` high in the stack. In Java 8, the JVM uses generated bytecode for reflective calls after 15 invocations — but if method objects aren't cached, you re-pay the inflation cost on every call.

```java
// Problematic — re-looks up method every call
public Object invoke(Object target, Object[] args) throws Exception {
    Method m = target.getClass().getMethod("process", String.class);
    return m.invoke(target, args);
}

// Fixed — cache the Method object
private static final Method PROCESS_METHOD;
static {
    try {
        PROCESS_METHOD = MyService.class.getMethod("process", String.class);
        PROCESS_METHOD.setAccessible(true);
    } catch (NoSuchMethodException e) { throw new ExceptionInInitializerError(e); }
}
```

If it's a framework (Jackson, Spring), check if they upgraded from ASM-generated accessors to standard reflection.

## 🔑 Key Takeaway
A CPU regression right after a library upgrade with no other code changes is a strong signal to check the flame graph for `Method.invoke()` — the library likely switched from generated code to uncached reflection.
