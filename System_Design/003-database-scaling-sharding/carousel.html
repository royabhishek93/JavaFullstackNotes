1 celebrity account, 1 shard, all the load. Fix: dedicated VIP shard, aggressive Redis caching, fan-out-on-write for >1M followers.

Cross-Shard Queries

Trap 2

"Orders $1000-5000 in Mumbai last month" fans out to ALL shards — slow, expensive.

Fix: stream writes via Kafka into a separate OLAP store (Redshift/BigQuery) or Elasticsearch for analytics — never run ad-hoc analytical queries against the sharded transactional DB.

Replication Lag & Connection Exhaustion

Trap 3 & 4

Replication lag: order written to primary, "My Orders" reads a replica 200ms behind → order appears missing → user duplicates it. Fix: read-your-own-writes, route to primary for 1-2s post-write.

Connection exhaustion: 50 pods × 10 connections = 500, but Postgres max_connections=100. Fix: RDS Proxy / PgBouncer multiplexes thousands of app connections onto a small real pool.

Decision Tree & Interview Answer

Quick Reference

Read-heavy? → Read replicas first. Auto-scaling pods? → RDS Proxy/PgBouncer. Writes outgrowing 1 primary? → Shard (hash=even, range=time-series, directory=multi-tenant).

"At scale you hit the DB ceiling in order: read replicas first, then RDS Proxy to prevent connection exhaustion, then sharding when writes can't keep up. Hash sharding for even distribution, range for time-series, directory for large multi-tenant systems. Analytics queries go to a separate OLAP system, never the transactional sharded DB."
