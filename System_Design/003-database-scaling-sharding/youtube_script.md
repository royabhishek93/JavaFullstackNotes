# Database Scaling & Sharding — YouTube Script
Duration: ~10 min | Target: Engineers 3–10 YOE | Episode: 3 of 20

## HOOK (0:00–0:30)
"Your orders table just crossed five hundred million rows. Queries that used to take fifty milliseconds now take ten full seconds. Your first instinct is to shard the table — but pick the wrong sharding strategy, and you'll create a single 'hot shard' that gets slammed while ninety-nine other shards sit idle. Today I'm walking through exactly how real companies scale a database from zero to hundreds of millions of rows — and the two traps that break it at every single stage."

[Screen cue: A counter ticking up to "500,000,000 rows" then a query-latency graph spiking from 50ms to 10s.]

## THE PROBLEM (0:30–2:00)
"Think about it this way — imagine a phone book with a billion entries. One book is too heavy to search through. So you split it into twenty-six books, one per letter. 'Smith, John' goes straight to book S — fast lookup, because you only search one twenty-sixth of the entries. Database sharding is exactly that: you split one huge table across multiple database servers, and each server only holds a shard, a subset of the rows. Without sharding, all five hundred million orders sit on one server — slow, and a single point of failure. With four shards, each server only holds one hundred and twenty-five million rows, and queries speed back up. But before you even get to sharding, most systems scale through read replicas first — since eighty percent of database traffic in most apps is just reads, spreading that across replicas gives you five times the read capacity for free, while the primary is freed up purely for writes."

[Screen cue: Draw the four-tier scaling ladder — Single DB → Read Replicas → Sharding → Polyglot Persistence.]

## THE SOLUTION (2:00–5:00)
"Now watch what happens when you actually choose a sharding strategy. Range sharding splits by value range — order ID one to ten million on shard zero, ten million to twenty million on shard one. Great for simple range queries like 'orders between January first and January thirty-first' — that hits one shard. But it creates a hot shard automatically: all NEW orders always go to the latest shard, so your older shards sit idle while the newest one gets hammered. Hash sharding instead computes shard equals hash of user ID modulo four — this spreads load evenly, no hot shards, but now a range query like 'all orders from January' has to fan out to every single shard. And directory sharding uses a lookup table to decide placement — flexible enough to move an individual user to a dedicated shard, but that directory lookup adds an extra network hop and can itself become a bottleneck if you don't cache it. The production rule of thumb: high write throughput with even distribution needs hash sharding; time-series data that needs range queries uses range sharding plus archiving; large multi-tenant systems with wildly different traffic patterns use directory sharding."

[Screen cue: Draw three shard diagrams side by side — Range, Hash, Directory — with a green check or red X for 'even load' and 'range query support'.]

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"Here's the trap that catches almost everyone: the celebrity problem, also called a hot shard. Say you've got five hundred million users sharded by userId modulo one thousand — a thousand shards. Now imagine a celebrity with fifty million followers happens to land on shard three-forty-five. The moment they post, fifty million reads hit shard three-forty-five in the same minute, while the other nine hundred ninety-nine shards sit completely idle. That one shard times out under the load. The fix is threefold — detect high-traffic users and move them to a dedicated VIP shard using directory sharding, cache that celebrity's data aggressively in Redis so fifty million reads hit Redis instead of the database, and choose your fan-out strategy correctly: for celebrities with over a million followers, pre-compute and push the feed to every follower when they post — fan-out on write — but for a normal user with a hundred followers, fan-out on read, computing the feed at request time, is perfectly cheap. Second major trap: replication lag causing users to see stale data. Picture a Flipkart-style checkout — a user places an order, it's written to the primary, they're redirected to 'My Orders,' which reads from a replica that's two hundred milliseconds behind. Their brand-new order isn't there yet! They think it failed and place a duplicate order. Fix it with read-your-own-writes — after a write, route that specific user's reads to the primary for the next second or two, using a simple flag in Redis. And the third trap is connection pool exhaustion — ten pods times a ten-connection HikariCP pool equals one hundred connections, exactly at PostgreSQL's default max_connections limit. The moment your app auto-scales to fifty pods during a traffic spike, you're demanding five hundred connections, and the database starts rejecting everyone with 'too many clients already.' The fix is RDS Proxy or PgBouncer sitting between your app and the database — it multiplexes thousands of app-side connections down onto a small, safe pool of real database connections."

[Screen cue: Split diagram — 1,000 shards with shard #345 glowing red under load, then a connection-pool diagram showing 500 app connections funneling through a proxy into 100 real DB connections.]

## REAL WORLD (8:00–9:30)
"Flipkart's order system is the textbook replication-lag example — a customer places an order, checks 'My Orders' immediately, and if that read hits a lagging replica, they might not see their own order for a couple hundred milliseconds. Think about Instagram, hugely popular across India, and its hot-shard problem — the exact 'Virat Kohli posts, fifty million followers check his profile' scenario is precisely why platforms like this use dedicated VIP shards and push-based fan-out for celebrity accounts. And picture Swiggy or Zomato during a lunch-hour traffic spike — if their pods auto-scale from ten to fifty without a connection proxy in front of the database, they'd hit the exact connection-exhaustion wall that turns a traffic win into a total outage."
