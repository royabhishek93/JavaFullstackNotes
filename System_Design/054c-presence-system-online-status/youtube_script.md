# Presence System — Online/Last Seen — YouTube Script
Duration: ~10 min | Target: Engineers 3–10 YOE | Episode: 54c

## HOOK (0:00–0:30)
"You open WhatsApp, and it just knows Alice is online — you never clicked a 'go online' button, nobody asked you. Now scale that to two billion users, five hundred million of them online at the same time. That's sixteen million 'I'm still here' signals hitting your server every single second. Get this wrong, and either everyone looks perpetually offline, or your Redis cluster falls over under the write load. Today I'm breaking down exactly how WhatsApp-scale presence systems work — heartbeat plus Redis TTL — and the three traps engineers hit the moment they try to ship 'online' indicators in a group chat."

[Screen cue: A phone screen showing "Alice is online" with a green dot, then a counter racing up to "16,700,000 writes/sec".]

## THE PROBLEM (0:30–2:00)
"Think about it this way — presence is really just one question asked over and over: 'is this person still here right now?' The naive answer is to ping the database every time someone asks, but that's expensive and stale the instant you get the answer. The clever answer WhatsApp uses is a heartbeat: while the app is open, your phone quietly tells the server 'I'm still here' every thirty seconds, and the server writes that into Redis with an expiry — a TTL, time-to-live — of sixty seconds. As long as heartbeats keep arriving, that key keeps getting refreshed and stays alive. The moment your phone goes to the background or loses network, the heartbeats stop, and sixty seconds later, Redis quietly deletes that key on its own — no cron job, no cleanup script, nothing. The key existing means online. The key being gone means offline. That's the entire mechanism. But do the math at WhatsApp's scale — five hundred million concurrent users, each sending a heartbeat every thirty seconds — that's 16.7 million writes per second, and a single Redis node tops out around one million operations per second. One node is nowhere close to enough."

[Screen cue: Diagram — mobile app sending "heartbeat" every 30s to a WebSocket server, server writing SETEX to a single Redis node, node overloading.]

## THE SOLUTION (2:00–5:00)
"Here's how it actually works end to end. Every thirty seconds while the app is active, the client sends a heartbeat over its existing WebSocket connection. The server responds by running one Redis command: SETEX user:alice:online 60 '1' — set the key, with a value of one, and a sixty-second expiry. Notice the TTL is sixty seconds, but the heartbeat interval is thirty seconds — that's deliberate, it's exactly double. If one single heartbeat gets dropped due to a flaky network blip, the key is still alive when the next heartbeat arrives thirty seconds later, so nobody gets falsely marked offline over one bad packet. At the same time, the server writes a second key, user:alice:last_seen, with the current timestamp — this one has no TTL, it just sits there permanently, getting overwritten on every heartbeat. Now, reading presence status is beautifully cheap: when Bob opens a chat with Alice, the server runs EXISTS user:alice:online. If it returns one, Alice is online. If it returns zero — meaning the key expired — the server falls back to GET user:alice:last_seen and shows 'Last seen 14 minutes ago.' Both of those are O(1) operations, constant time, no matter whether you have a thousand users or five hundred million. For the scale problem — that 16.7 million writes per second — the fix is Redis Cluster: instead of one node, you shard by hashing the user ID into one of sixteen thousand three hundred eighty-four hash slots, and route each slot to one of, say, twenty physical shards. Twenty shards times roughly eight hundred fifty thousand ops per second each comfortably covers 17 million writes with headroom. And the memory footprint is tiny — each presence key is about fifty bytes, so five hundred million users is only twenty-five gigabytes total, split across your shards that's under two gigabytes each. That's the whole architecture: heartbeat, TTL, hash-sharded Redis Cluster."

[Screen cue: Draw the full pipeline — Mobile → WebSocket → SETEX with 60s TTL → Redis Cluster with 20 shards labeled by hash-slot ranges, then EXISTS query flowing back for reads.]

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"First trap: privacy. WhatsApp lets you set 'Who can see my Last Seen' to Everyone, My Contacts, or Nobody — and if you implement this by just checking the viewer's own settings, you've built a one-sided surveillance tool. The correct implementation checks BOTH users' settings before revealing either's last seen — this is WhatsApp's reciprocity rule. If Alice hides her last seen from Bob, Alice also cannot see Bob's last seen, full stop, no exceptions. Miss this check and you leak private data through an asymmetric loophole — someone hides their status but can still stalk everyone else's. Second trap, and this is the one that actually breaks systems in production: group chat presence fan-out. Say you naively try to show individual online indicators for every member of a 500-person group. Every time someone opens that group, you fire off 500 EXISTS commands to Redis — one per member. Now if a thousand people open that same group around the same time, that's five hundred thousand Redis queries just to render one screen. Push it to a group of a thousand members and a thousand people opening it, and you've generated one million Redis queries for a single group-chat screen load. That does not scale, and it's precisely the kind of thing that looks fine in a demo with five users and melts down in production with five hundred. WhatsApp's actual fix is to stop trying to show individual dots for large groups entirely — just show 'N members online,' an aggregate count, which is far cheaper to compute and honestly more useful anyway. For one-on-one chats, where there's only one EXISTS query per screen open, individual indicators are totally fine. Third trap: don't rely purely on TTL expiry for detecting disconnects, because that's a full sixty-second delay in the worst case — that's a 'soft' disconnect, discovered only when the key finally expires. A much faster path is listening for the WebSocket's own onDisconnect event, which fires the moment the TCP connection actually drops — that's a 'hard' disconnect, and it can update last_seen and clear the online key up to thirty seconds faster than waiting on the TTL alone. Production presence systems use both: TTL as the safety net, WebSocket disconnect events as the fast path."

[Screen cue: Split screen — left shows privacy leak diagram with a "one-sided check" red X, right shows the group-chat fan-out counter exploding from 500 to 500,000 to 1,000,000 queries.]

## REAL WORLD (8:00–9:30)
"You don't need to be WhatsApp to hit this exact problem. Think about Swiggy during lunch hour — every delivery partner's app is sending a location-and-availability heartbeat, and Swiggy's dispatch system needs to know instantly which of, say, three hundred thousand active partners are truly online and reachable versus whose app just crashed in the background — that's the identical heartbeat-plus-TTL pattern, just repurposed for delivery-partner availability instead of chat presence. Zomato has the restaurant-side version of this: a restaurant partner's tablet needs to show 'accepting orders' in near real time, and if that tablet loses connectivity mid-lunch-rush without a heartbeat-and-TTL safety net, Zomato keeps routing orders to a restaurant that's actually gone dark — a stale presence bug that directly costs orders and refunds. And PhonePe's merchant-side QR devices face the same core question at massive scale: is this merchant's device online and able to accept a payment right now, or has it silently dropped off Wi-Fi? Get the TTL window wrong — too short and flaky networks falsely mark merchants offline mid-transaction; too long and a genuinely offline merchant keeps looking reachable — and you either lose legitimate transactions or send payments toward a dead device."
