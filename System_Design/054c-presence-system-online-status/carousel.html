The Heartbeat Flow

Scenario 1 — How "Online" Actually Works

Every 30s
→
60s
SETEX ...online 60 "1"

Client sends a heartbeat every 30s over the open WebSocket. Server refreshes a Redis key with a 60-second TTL — double the heartbeat interval, so one dropped packet doesn't falsely mark you offline.

Silence Means Offline

Scenario 2 — TTL Expiry

No heartbeat
→
gone
Key expired

App backgrounds or loses network → no more heartbeats → 60s later Redis auto-deletes the key. No cron job. Key missing = offline. last_seen timestamp is written on every heartbeat and kept permanently (no TTL).

500M users × 1 heartbeat/30s = 16.7M writes/sec. One Redis node caps at ~1M ops/sec. Fix: Redis Cluster, hash user ID into 16,384 slots across 20 shards → ~850K ops/sec each. Memory: 500M × 50 bytes = 25GB total, under 2GB per shard.

Privacy Reciprocity Trap

Trap 1 — "Last Seen" Visibility

Settings: Everyone / My Contacts / Nobody.

✕ Checking only the viewer's own setting = one-sided surveillance.

✓ Correct fix: check BOTH users' settings before revealing either's last seen. If Alice hides hers from Bob, Alice also cannot see Bob's — no exceptions.

Group Chat Fan-Out Trap

Trap 2 — Naive Per-Member EXISTS

500 members
× 1000 opens
= 500,000 queries

✕ Individual online dots for every member doesn't scale. ✓ Real fix: show aggregate "N members online" count. 1-on-1 chats: single EXISTS per open is fine. Status pushed over the existing WebSocket instead of polled.

Detecting Disconnects

TTL expiry softUp to 60s delayNo heartbeat arrives in time

Production systems use both: TTL as the safety net, WebSocket disconnect events as the fast path — up to 30s faster.

Decision Tree & Interview Answer

Quick Reference

Need "online now"? → EXISTS user:{id}:online. Need last activity? → GET user:{id}:last_seen. Writes outgrowing 1 Redis node? → Redis Cluster, hash-sharded. Large group? → aggregate count, not per-member dots.
