300µs

That's the amount of clock drift between two app servers that scrambled a comment thread on a 6-node, 3-datacenter Cassandra cluster — "First!" rendered after its own reply.

The bug wasn't Cassandra. It was the wrong kind of UUID.

THE PROBLEM

6 nodes, 3 datacenters, masterless. Any node accepts any write, at any moment — no round trip to ask "what's next?" Forcing one coordinator would kill the entire point of going distributed.

Fallback: generate the ID on the client with a random UUID. Uniqueness: solved. Ordering: broken.

TRAP #1

Random UUID v4 as a clustering key = garbage order

8a41...3rd written→ sorts 1st (WRONG)
1b6f...1st written→ sorts 2nd
f2c9...2nd written→ sorts 3rd

128 bits of pure randomness. Zero relationship between value and creation time.

  • App needs ORDER BY created_at + an extra column
  • Ordering by a non-clustering column needs a secondary index or ALLOW FILTERING
  • Both are anti-patterns in a wide-partition workload at scale

THE FIX

TIMEUUID (v1): 128 bits, chronological by design

(60-bit timestamp)

(14-bit)

  • 60-bit timestamp = 100-nanosecond ticks since 1582-10-15 — sub-microsecond precision, effectively never wraps
  • Cassandra compares the reassembled timestamp first — not raw byte order
  • Two comments 1ms apart sort in that same order, natively, no extra logic

THE SOLUTION

Rows land on disk pre-sorted — for free

PRIMARY KEY (post_id, comment_id) · partition = post_id · clustering = TIMEUUID

1b6f...f001"First!"user-42
2a7c...f002"nice post"user-88
3f9d...f003"agreed"user-17
5e2a...f004"source?"user-42

Rows physically stored in ascending TIMEUUID order = ascending creation-time order. No ORDER BY, no sort/merge step.

~2–5ms p99

single partition read, local SSD, already time-ordered

Real arrival order at load balancer: X (A) → Y (B) → Z (C).
Stored order by TIMEUUID timestamp: Y → X → Z — because B's clock lags.

  • Comment thread: imperceptible, NTP keeps servers within 1–10ms anyway
  • Financial ledger: not acceptable — use a Snowflake ID or single-writer sequence
  • Mitigation: tight NTP/chronyd sync, or generate TIMEUUID server-side, never client-side

INTERNALS

Same-tick collisions & real throughput

Billions of CPU instructions/sec means two TIMEUUIDs can land in the same 100ns tick. RFC 4122's fix: the 14-bit clock_seq field.

16,384

possible clock_seq values (214) — bumped when the clock hasn't ticked forward, used as a tiebreaker

  • Uuids.timeBased() keeps an atomic counter so same-JVM calls microseconds apart still get strictly increasing values
  • 1M+ TIMEUUIDs/sec generated per JVM — generation is never the bottleneck
  • Real limit: Cassandra write throughput, ~10K–50K writes/sec per node (hardware + replication factor dependent)
