Professional Social Network at 950M Scale

Graph DB Feed Ranking 2nd Degree InMail Search Kafka
  • Two hardest problems: bidirectional connection graph + hybrid feed fan-out
  • PYMK (People You May Know): 2nd-degree traversal — O(N×M), always pre-computed

Connection Graph Design

Why NOT relational adjacency list (MySQL)?

  • 570B rows in a MySQL table → catastrophic index maintenance, table scans
  • WHERE user1_id=X OR user2_id=X never uses an index efficiently

Cassandra Two-Table Approach (bidirectional):

  connections_by_user          connections_by_friend
  PK: (user_id, conn_uid)      PK: (conn_uid, user_id)
  ─────────────────────────    ─────────────────────────
  Alice → Bob  ✓               Bob  ← Alice ✓
  Alice → Carol ✓              Carol ← Alice ✓

  "Get Alice's connections"    "Who added Alice?" (PYMK)
  → single partition scan      → single partition scan
  → O(1), no JOINs             → O(1), no JOINs

Two rows per connection: Alice accepts Bob → INSERT both rows via Kafka consumer. Remove connection → Kafka event → delete both rows asynchronously (brief inconsistency window is acceptable).

Graph DB (Neo4j) alternative: elegant Cypher for 3rd/4th degree. Adds infra complexity — Cassandra two-table preferred for 1st/2nd degree PYMK.

People You May Know (PYMK) Algorithm

  Input: User Alice (300 connections)  — pre-computed hourly

  Step 1 — Get 1st-degree connections
    Cassandra: SELECT FROM connections_by_user WHERE user_id=alice
    → [bob, carol, dave … 300 IDs]

  Step 2 — Get 2nd-degree (friends of friends)
    Batch-read each friend's connections (async parallel Cassandra IN)
    → ~90,000 candidate user_ids (300 × 300)

  Step 3 — Count mutual connections per candidate
    HashMap<userId, mutualCount>
    evan: 15 mutuals | frank: 3 | grace: 1

  Step 4 — Filter
    Remove: Alice herself, existing 1st-degree connections,
            blocked users, inactive accounts (is_active=false)

  Step 5 — Rank
    Sort by: mutual_count DESC
    Tiebreak: same_company + same_school + same_industry
    Take top 25 candidates

  Step 6 — Cache result
    Redis: SETEX pymk:{aliceId} 3600 [{userId, mutualCount} …]

  Recompute trigger: new connection added/removed + hourly sweep

Feed Generation — Hybrid Fan-out

  Normal user (Alice, 300 connections):
  ──────────────────────────────────────────────────────
  POST /posts → MySQL INSERT → Kafka: post-created
                                      │
                               Feed Fan-out Worker
                               For each of 300 connections:
                                 Redis ZADD feed:{conn_id} {ts} {postId}
                                 ZREMRANGEBYRANK (keep top 1000 only)

  Influencer (Bill Gates, 5M connections):
  ──────────────────────────────────────────────────────
  POST /posts → MySQL INSERT → Kafka: post-created
                                      │
                               Fan-out Worker
                               connection_count > 10K → SKIP write fan-out
                               Mark post: influencer_post = true

  Feed Read (Bob opens feed):
  ──────────────────────────────────────────────────────
  1. Redis ZREVRANGE feed:{bob} 0 99   (from normal connections)
  2. For each influencer Bob follows:
       Cassandra SELECT recent posts WHERE user_id=influencer LIMIT 5
  3. Merge + deduplicate + re-rank by engagement score
  4. Return top 20 posts

Feed Ranking Model

LinkedIn ≠ Instagram — professional quality over pure engagement maximization.

SignalWeight / Logic
RecencyExponential decay over 72 hours — recent posts ranked higher
Connection strengthFrequent viewers, message history, same company → 2× boost
Engagement velocityLikes + comments in first 2 hours signal quality content
Content typeOriginal thought leadership > reshares > pure job-post spam
Dwell timeTime spent reading (not scroll-past) — measured client-side
Comment-to-like ratioHigh ratio → substantive discussion → rank up
Spam demotion>3 hashtags, spam-flagged account → −50% score

Implementation: Trained ML ranking model. Features extracted at fan-out time, score stored as Redis sorted set score. Merged feed (normal + influencer pull) re-ranked at read time before serving top 20.

Cassandra messages schema:

  messages
  PRIMARY KEY: (conversation_id, sent_at DESC)
  Columns: message_id UUID, sender_id BIGINT,
           content TEXT, read_at TIMESTAMP NULL, is_inmail BOOLEAN

  conversation_id = hash(min(user1, user2), max(user1, user2))
  — deterministic, same value for both participants

  "Get last 50 messages between Alice and Bob"
    SELECT WHERE conversation_id=? LIMIT 50

Real-time delivery: WebSocket per user. Message → Cassandra write → push via WebSocket if recipient online, else FCM/APNs push notification.

Job Recommendation Engine

Two modes: Search (explicit) + Recommendations (implicit/personalized)

Job Search — Elasticsearch bool query:

  GET /jobs/search?keywords=java+developer&location=bangalore
  {
    must:   [ match title/description: "java developer" ]
    filter: [ geo_distance: 50km from bangalore,
              term: status = OPEN,
              range: salary_min >= requested ]
    should: [ match skills: user's skill list → boost score ]
  }

Job Recommendations — personalized pipeline:

  • Skills match: overlap between user skills and job required_skills
  • Career trajectory: users in same role/company/school who took this job
  • Location preference: from profile + past job history
  • Seniority fit: years of experience vs. job level requirement
  • Viewed profiles: recruiters who viewed you + their open job listings

Pre-computed daily batch job → cached in Redis: job_recs:{userId}

Endorsements & Skills Graph

Skills taxonomy (MySQL): normalized table (skill_id, name, category). Prevents free-text chaos — "Java" = "java" = "Java programming" all map to skill_id=42.

Cassandra endorsements schema:

  endorsements
  PRIMARY KEY: (endorsed_user_id, skill_id, endorser_id)
  Columns: endorsed_at TIMESTAMP

  "Count Java endorsements for Alice"
    SELECT COUNT(*) WHERE endorsed_user_id=alice AND skill_id=java_id

  "Did Bob endorse Alice for Java?"
    SELECT WHERE endorsed_user_id=alice AND skill_id=java AND endorser_id=bob

Endorsement authority weighting (for job matching):

  • Endorser works at top company in that skill domain → 2× weight
  • Endorser themselves highly endorsed for same skill → credibility boost
  • Self-endorsement: blocked at API level
  • Top-endorsed skills float to top of profile + boosted in job recommendation scoring

Endorsement event → Kafka → notify endorsed user + update skill sort order async.

Privacy & Data Residency

GDPR Right to Erasure — Staged deletion:

  • Stage 1 (immediate, sync): SET is_active=false, NULL out PII (name, email, photo). User invisible everywhere within seconds. Satisfies GDPR "make inaccessible" SLA.
  • Stage 2 (async, 30 days): Background job deletes both Cassandra connection rows, posts, endorsements, profile_views. Run at 10K deletes/sec — takes minutes for super-connectors.
  • Stage 3 (analytics): Replace user_id with hash in data warehouse and Kafka event history.

Profile Visibility Tiers:

SettingWho Sees Full Profile
PublicEveryone including Google search indexing
Connections only1st-degree connections; search shows name + headline only to others
PrivateOnly self; search shows "LinkedIn Member" — no name, no photo

Data residency: EU user data routes to EU data centers via API Gateway user.region header → regional cluster selection. Enforced at the gateway, not application layer.

Senior Q&A 1 — PYMK for a New User (0 Connections)?

"User signs up today with zero connections. PYMK needs connections to compute 2nd-degree suggestions. What do you show?"

Cold-start signals (no graph traversal needed):

  • Company email domain: Signup with a Google Workspace email → suggest verified employees of same company. Highest precision cold-start signal.
  • Profile seeding: User filled in current company + school → suggest people from same company + graduating class, ranked by connection_count.
  • Location + industry: Same city + same industry → suggest verified high-connection profiles.
  • Phone contact sync (opt-in): Match phone numbers in address book to LinkedIn users → direct 1:1 suggestions.
  • Invite chain: If user was invited by existing member → that member's connections are strong implicit suggestions.

Implementation: Onboarding flow collects company + school + phone. A one-time "cold start PYMK" job populates pymk:{userId} using profile signals instead of graph traversal. After first connection accepted → switch to standard 2nd-degree algorithm and recompute.

Senior Q&A 2 — CEO Posts, 50M Feeds Need Update?

"Satya Nadella (8M LinkedIn connections) posts a job announcement. Hybrid fan-out says >10K = pull mode. But 8M followers all load feed in the next 10 minutes. How do you handle the read surge?"

Pull fan-out is correct — writing to 8M Redis keys would take hours and spike the cluster. Handling the read surge:

  • Influencer post cache: Satya's latest posts cached at Feed Service layer: influencer_posts:{satyaId} TTL 60 sec. All 8M followers read from this single cache key — not 8M individual Cassandra lookups.
  • CDN edge caching: For public-visibility posts, cache the rendered post card at CDN edge with Cache-Control: max-age=60. Absorbs the spike entirely for uncustomized views.
  • Cassandra read replicas: Influencer's posts partition reads from nearest replica; consistency level ONE — eventual consistency is acceptable for a social feed.
  • Graceful degradation: On cache miss storm, serve stale result (last 5-min cache) rather than hammering Cassandra. User sees the post 5 min late — acceptable.
  • Circuit breaker: Feed Service monitors Cassandra error rate. If >5% errors → serve cached version only, skip influencer pull merging temporarily.

Senior Q&A 3 — 2nd Degree Graph Traversal at 900M Nodes?

"Your PYMK does 90K Cassandra reads per user. 50M active users need hourly recompute. Walk me through how this runs at scale."

Distributed PYMK worker fleet:

  • Stagger over the hour: 50M users / 3600 sec = 13,888 PYMK computes/sec needed.
  • Worker throughput: Each worker handles one user's PYMK. 90K Cassandra reads with async I/O → ~200ms per user. Need ~2,800 concurrent workers (13,888 × 0.2s).
  • Cassandra capacity: 100-node cluster × 100K reads/node/sec = 10B reads/sec. Needed: 13,888 × 90K = 1.25B reads/sec. Well within capacity.
  • Super-connector sampling: Users with >10K connections → sample 500 connections instead of full traversal. 32K → 500 sample → 150K candidates (quality nearly identical per user studies). Weighted toward recent connections.
  • Tiered recompute: Normal active users: hourly. Super-connectors (>10K): daily. Inactive (>30d no login): skip until next login event triggers a recompute.
  • Kafka-triggered: New connection accepted → immediate PYMK recompute event for both users — skip waiting for hourly batch cycle.

Closing Script

"Let me summarize the key design decisions and why each matters at 950M scale."

  • Cassandra two-table for connections: 570B rows need O(1) partition-key lookups, not MySQL table scans. Two tables answer both directions — "Alice's connections" and "who connected to Alice."
  • PYMK always pre-computed: 90K Cassandra reads per user is too expensive for real-time. Background hourly job; Redis cache. API response = 1 Redis GET = sub-millisecond.
  • Hybrid fan-out — the celebrity problem: Push for <10K connections (fast reads); pull for influencers (avoids 5M+ Redis writes per post). Feed read merges both buckets.
  • Professional feed ranking: Not pure engagement optimization — demotion rules for spam, original content boosted, connection-strength signal weighted higher than raw engagement.
  • GDPR at scale: Immediate soft-delete (set is_active=false) satisfies user-facing SLA within seconds; async cascading hard-delete runs over days without impacting production traffic.
  • Kafka decouples everything: POST /posts returns in <100ms. Fan-out, PYMK recompute, notifications, ES indexing — all async consumers off Kafka.
