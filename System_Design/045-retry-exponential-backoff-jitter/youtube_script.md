# Retry, Exponential Backoff & Jitter — YouTube Script
Duration: ~10 min | Target: Engineers 3–10 YOE | Episode: 45 of 20

## HOOK (0:00–0:30)
"A payment gateway times out for one thousand simultaneous transactions. Every single client does the obvious thing — it retries immediately. All one thousand requests slam back into the gateway at the exact same instant, in the exact same second, and the gateway — which was already struggling — goes completely down. This is called a thundering herd, and it's one of the most common ways engineers accidentally turn a temporary blip into a full outage. Today I'm showing you the three-part fix — exponential backoff, jitter, and idempotency — that every production retry system needs, and the SendGrid 429 rate-limit scenario that ties it all together."

[Screen cue: A counter showing "1000 requests" all hitting a single server icon at the same timestamp, server icon turning red and crashing.]

## THE PROBLEM (0:30–2:00)
"Think about it this way — imagine a restaurant tells one hundred waiting customers, 'come back in five minutes.' Every single one of them comes back in exactly five minutes. Now one hundred people arrive at the door at the exact same second, and the restaurant — which just barely started recovering — gets overwhelmed all over again. That's the thundering herd problem, and it's exactly what happens when a downstream service fails and every client retries with no delay at all. One thousand clients hit a failing service at t equals zero, all get an error, all retry at t equals one second, get the same error again, retry at t equals two seconds — the service can never recover because it's getting hammered in perfectly synchronized waves. The fix isn't just 'wait before retrying' — because even if every client waits, say, exactly one second, then exactly two seconds, then exactly four seconds, they're STILL all synchronized. All one thousand clients still arrive in a spike at t equals one, then t equals three, then t equals seven. Exponential backoff alone doesn't solve thundering herd — you need randomness too."

[Screen cue: Draw two timelines — top one shows synchronized spikes at t=1,2,3 with backoff but no jitter; bottom one shows the same requests spread smoothly across a range with jitter added.]

## THE SOLUTION (2:00–5:00)
"Now watch what happens when you add jitter — randomness — on top of exponential backoff. The formula for full jitter is: delay equals a random number between zero and the minimum of your cap and your base delay times two to the power of the attempt number. So on attempt one, instead of waiting exactly one second, each client picks a RANDOM wait between zero and two seconds. Attempt two: random between zero and four seconds. Attempt three: zero to eight seconds. Because every client picks a different random number, they naturally spread out across that window instead of all landing on the same second. There's also equal jitter, which always waits at least half the calculated backoff plus a random amount for the other half — giving you a more predictable minimum wait while still spreading load. And for very high-contention scenarios — think a huge fleet of servers all retrying against the same downstream — AWS recommends decorrelated jitter: delay equals a random number between your base delay and three times the PREVIOUS delay. This adapts based on what actually happened last time, which breaks up clustering even better than full jitter alone in extreme contention. The typical production configuration: base delay of one second, cap of thirty seconds, and a maximum of five attempts total."

[Screen cue: Draw the jitter formula table — Attempt 1 through 5, showing 'No Jitter' column with exact seconds versus 'Full Jitter' column with ranges like 0-2s, 0-4s, 0-8s.]

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"Here's the trap that catches almost every engineer at some point: retrying an error that retrying can never fix. If your request comes back with a 400 Bad Request, a 401 Unauthorized, a 403 Forbidden, a 404 Not Found, or a 422 Unprocessable Entity — retrying with the exact same request produces the exact same error every single time. Your auth token isn't going to magically become valid because you waited two seconds. You should ONLY retry on truly transient failures — a 429 Too Many Requests, a 503 Service Unavailable, a 502 Bad Gateway, or a plain network timeout. Second trap, and this one is expensive: retrying a POST request that isn't idempotent. Picture this — you send a payment request to a bank gateway. The bank actually processes the charge successfully, but the response times out before you see it. You don't know it succeeded, so you retry the exact same POST. The bank processes it AGAIN. Your customer is now charged twice for one purchase. The fix is an idempotency key — a unique ID, say a UUID, sent as a header like X-Idempotency-Key on every attempt, including retries. The very first time the bank sees that key, it processes the payment. Every subsequent request with the SAME key, it just returns the original result without charging again. This exact pattern applies to email sending too — SendGrid accepts an X-Message-ID header set to your notification's UUID, so if your retry succeeds after the original ALSO secretly succeeded, the customer only gets one email, not two. Third trap: ignoring the Retry-After header. When SendGrid or any well-behaved API returns a 429, it often tells you exactly how long to wait — 'Retry-After: 60' meaning wait sixty seconds. If you ignore that and use your own backoff calculation instead, you might retry too early and get rate-limited again, wasting one of your precious retry attempts. And the last trap: retrying forever with no maximum, and no dead-letter queue for messages that exhaust all their retries — if a downstream service is permanently down, unlimited retries just pile up load and, worse, silently lose data with nowhere for the failed message to go."

[Screen cue: Split diagram — left side shows a 400 error with a red 'X' and 'DO NOT RETRY' label; right side shows a 429/503 error with a green checkmark and 'RETRY WITH BACKOFF' label. Below it, a payment request flowing through an idempotency-key check before hitting the bank gateway.]

## REAL WORLD (8:00–9:30)
"SendGrid is the perfect real-world case study here — when it returns a 429 Too Many Requests during a burst of ten thousand notification sends, the correct handling is: first check for a Retry-After header and honor it exactly if present; if there's no header, fall back to exponential backoff with full jitter, base of one second, capped at thirty seconds, max five attempts; retry only on 429, 503, 502, and network errors — never on 400, 401, or 422; and attach the notification's UUID as an X-Message-ID so SendGrid deduplicates if a retry happens to land after the original already succeeded. Apple's Push Notification Service behaves the same way — a 429 from APNs needs the exact same full-jitter treatment to avoid hammering an already-rate-limited endpoint. And RFC 5321, the actual SMTP email standard, mandates a real-world backoff schedule of five minutes, ten minutes, twenty minutes, forty minutes, all the way up to twenty-four hours for retrying failed mail delivery — proof that this isn't just theory, it's baked into internet infrastructure that's decades old."

Combine all three with a circuit breaker to stop hammering a service that's clearly broken long-term, and a dead-letter queue so nothing silently vanishes when retries are exhausted.
