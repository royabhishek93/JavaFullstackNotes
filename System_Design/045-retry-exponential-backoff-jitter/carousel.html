Retry, Backoff & Jitter

Slide 1 / 9 — The Hook

1,000 retries

...all firing at the exact same second. A payment gateway that was just starting to recover gets hammered back down — a thundering herd caused by naive retry logic.

The Thundering Herd

The Problem

1,000 clients fail at t=0. All retry immediately at t=1s. Same error. Retry again at t=2s. Service never gets a chance to recover.

→

Synchronized waves = repeated overload, every second.

Backoff Alone Isn't Enough

Still Synchronized

Every client waits exactly 1s, then 2s, then 4s. They're STILL all synchronized — spikes just move to t=1, t=3, t=7.

t=1s, t=3s, t=7s — spikes, not spread.

Full Jitter Fixes It

The Solution

delay = random(0, min(cap, base × 2^attempt))

Each client picks a random wait → smooth, spread load.

Real World: SendGrid 429

Production Example

10,000 notifications in a burst → SendGrid returns 429 Too Many Requests.

  1. Check Retry-After header — honor it exactly if present
  2. No header? Full jitter: base=1s, cap=30s, max 5 attempts
  3. Retry only 429 / 503 / 502 / network errors
  4. Attach X-Message-ID (notification UUID) — dedupes on SendGrid's side

Same pattern: Apple APNs 429s, RFC 5321 SMTP backoff (5min→10min→20min→40min→24hr)

Decision Tree & Interview Line

Cheat Sheet

Transient error (429/503/502/timeout)? → Backoff + jitter + idempotency key. Permanent error (400/401/404/422)? → Do NOT retry.

"Exponential backoff gives a struggling service breathing room between retries; jitter ensures those retries don't all arrive at the same moment and recreate the original spike."

Combine with: Circuit breaker (stop hammering) + Dead-letter queue (nothing silently lost).
