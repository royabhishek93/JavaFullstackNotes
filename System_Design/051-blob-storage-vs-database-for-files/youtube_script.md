# Blob Storage vs Database for Files — YouTube Script
Duration: ~10 min | Target: Engineers 3–10 YOE | Episode: 51 of 122

## HOOK (0:00–0:30)
"Your users table has a column called profile_photo, type BLOB, storing a 2 megabyte JPEG directly inside MySQL. It feels elegant — one table, one query, ACID transactions, done. But that one column is quietly destroying your database. Buffer pool eviction that spikes every query's latency from 1 millisecond to 100 milliseconds. Backups that used to take 5 minutes now taking 6 hours. And at 10,000 concurrent image requests, your API servers burning 20 gigabytes of RAM just to push bytes they never should have touched. Today I'm breaking down exactly why storing files as BLOBs in your database is one of the most expensive mistakes in system design — and the one rule that fixes all of it."

## THE PROBLEM (0:30–2:00)
"Here's how it starts. You've got a users table — id, name, email — and someone says 'let's just add a profile_photo BLOB column, it's convenient, everything's in one place.' And technically, it works. You CREATE TABLE users with a BLOB column, you INSERT a 2 megabyte JPEG, and MySQL happily stores it. But think about what a normal row actually looks like — id, name, email, created_at — that's about 116 bytes. The moment you attach a 2 megabyte BLOB, that single row balloons to roughly 2 megabytes. And here's the part people miss: InnoDB, MySQL's storage engine, organizes data in fixed-size pages, and the maximum row size is around 65,535 bytes. A 2 megabyte row does not fit in a single page — it can't. So MySQL silently spills the BLOB into external off-page storage. And that means even a query as simple as 'SELECT name FROM users WHERE id equals 42' might trigger an extra disk read just to skip past that BLOB. The rule of thumb every production engineering team follows: store the actual file bytes in object storage like S3, and store only the file's metadata — its path, size, and content type — in the database. Let's break down exactly why that rule exists."

[Screen cue: Side-by-side comparison — "Normal row: 116 bytes" vs "Row with BLOB: 2MB" with an InnoDB page diagram showing overflow.]

## THE SOLUTION (2:00–5:00)
"The correct architecture splits responsibilities cleanly. MySQL stores metadata only — a users row with id 42, name Alice, and a column called profile_photo_key holding the string 'profiles/alice/photo-v3.jpg' — that's the S3 key, plus maybe the file size and an updated_at timestamp. That whole row is about 200 bytes. Meanwhile, the actual 2 megabyte image lives in S3 at that exact key, and gets served to users through a CDN URL like cdn.myapp.com/profiles/alice/photo-v3.jpg. Now walk through the upload flow: the client sends a PUT request with the image bytes to your API server. Your server validates it — is it actually a JPEG, is it under the size limit, does it look malicious — then uploads it straight to S3, gets back the S3 key, and runs a single UPDATE statement setting profile_photo_key on the user's row. That's it. No BLOB ever touches your database. And here's the consistency question everyone asks: what if the S3 upload succeeds but the database UPDATE fails? You get an orphaned S3 object — a file nobody references. No user ever sees a broken experience because of it. You just clean it up later with an S3 lifecycle policy that deletes unreferenced objects after 7 days, or by tracking the upload UUID in an outbox table and confirming cleanup asynchronously. Compare the row sizes: with BLOBs, 200 bytes ballooned to 2 megabytes. With the S3-key pattern, the row stays a clean 200 bytes — buffer pool stays clean, replication stays fast, and serving the image never touches your API server at all."

[Screen cue: Split diagram — left side "MySQL: 200-byte row with S3 key", right side "S3 + CDN: 2MB actual bytes served directly to browser".]

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"There are four separate ways storing BLOBs in your database quietly wrecks you, and most engineers only discover them one at a time, in production. First — buffer pool contamination. InnoDB's buffer pool is the RAM cache holding your hot, frequently-accessed pages, typically sized 1 to 8 gigabytes. Now run 'SELECT * FROM users LIMIT 1000' on a table with 2 megabyte BLOB columns — you just loaded 2 gigabytes of BLOB pages into that buffer pool, evicting the index pages and hot row data that used to live there. Every single query that used to be served from RAM now hits disk. Latency across your ENTIRE database — not just the BLOB query — spikes from 1 millisecond to 100 milliseconds. One bad query degrades everything for minutes. Second — the backup and replication nightmare. Say you've got 100,000 users, each with a 2 megabyte profile photo — that's 200 gigabytes of BLOB data sitting inside MySQL. A logical backup with mysqldump on a normal 2 gigabyte database takes about 5 minutes. With 200 gigabytes of BLOBs mixed in, that same backup takes 6 hours. And replication is worse — every INSERT or UPDATE carrying a 2 megabyte BLOB gets written to the binary log, so the binary log grows by 2 megabytes per user signup. Replicas have to download and apply that bloated log, and the moment you get a burst of signups, replication lag spikes. Third — you simply cannot serve files from a database over HTTP efficiently. To serve one profile photo from MySQL, the request has to go client, to your API server, to MySQL, load the full 2 megabyte BLOB, buffer it in memory, then stream it back over HTTP. Now scale that to 10,000 concurrent image requests — that's 10,000 database connections, exhausting your connection pool, and 20 gigabytes of RAM consumed by your API servers just pushing image bytes. Your real business traffic — orders, user lookups — gets starved of threads and connections it needs. Fourth, and this is the one people ask about most in interviews — when IS it okay to put a BLOB in the database? If a file is guaranteed to always be under 1 kilobyte — think small SVG icons or tiny base64 thumbnails — the row-size impact is negligible, and it's fine. For private, encrypted, access-controlled files like medical records or legal documents, S3 with presigned URLs still works for most cases, but some strict compliance environments require database-level encryption at rest with full audit trails, where something like PostgreSQL's bytea type can work — but even then, cap it under 1 megabyte per file. The actual rule: if ANY file could exceed 100 kilobytes, never store it in the database — use object storage. If every file is guaranteed under 1 kilobyte, the database is fine. Anything in that 1 kilobyte to 100 kilobyte gray zone — default to S3 unless you have a very specific reason not to."

## REAL WORLD (8:00–9:30)
"Think about Flipkart's product catalog — tens of millions of product images, each 200 kilobytes to a couple megabytes, served on every single product page view across the app. If those images lived as BLOBs in the primary transactional database instead of S3 plus a CDN, every product page load would compete with checkout and inventory queries for the exact same buffer pool and connection pool — a single Big Billion Days traffic spike would take down browsing and checkout together. Picture Swiggy or Zomato with restaurant and dish photos — every restaurant listing typically ships 5 to 10 images, and across hundreds of thousands of restaurants that's millions of files serving on every home screen scroll. Storing those as BLOBs means every scroll event forces the order and payment database to also stream image bytes through the API layer; storing them in S3 with a CDN in front means the browsing experience never touches the transactional database at all. And think about Paytm or PhonePe handling KYC document uploads — PAN cards, Aadhaar scans, bank statements — often 1 to 5 megabytes each, for hundreds of millions of users. These are exactly the 'private, access-controlled' files from our rule: they go into S3 with encryption at rest and short-lived presigned URLs for verification agents, never as raw BLOBs in the core user database, because a compliance audit or backup of that database would otherwise balloon from gigabytes to hundreds of terabytes."
