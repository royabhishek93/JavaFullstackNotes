Inverted Index & Elasticsearch

Slide 1 / 10 — The Hook

4min → 87ms

SQL LIKE '%running shoes%' across 50M rows: minutes, zero ranking. Elasticsearch: under 100ms, ranked by relevance.

Word → Documents, Not Document → Words

The Problem

Textbook index: look up "database" → pages 23, 45, 67. Done in 5 seconds, not an hour.

SQL LIKE '%...%' can't use a B-tree index — leading wildcard forces a full table scan every time.

Tokenize → Normalize → Stem

Building the Index

"The quick brown fox" → tokenize → ["The","quick","brown","fox"] → lowercase, remove stopwords → ["quick","brown","fox"] → stem → unchanged here, but "running"→"run"

Posting Lists

The Core Data Structure

TermPosting List
quick[doc_1, doc_3]
fox[doc_1, doc_2]

Query "quick fox" → intersect the 2 lists → doc_1. No scan, just a lookup.

BM25 Scoring

Relevance Ranking

Weighs term frequency (in THIS doc) against term rarity (across ALL docs).

"Gore-Tex running shoes" outranks "blue shoes" for a "Gore-Tex" search — rare terms carry more weight than common ones.

Shard Fan-Out

Scaling Search

Shard 0
Shard 1
...Shard N

Coordinator fans query to all shards in parallel, merges + re-ranks. ~10ms overhead added on top of the lookup.

text vs keyword

The #1 Mapping Mistake

text analyzed, for full-text search (name, description)

keyword exact, for filter/sort/facets ("Nike" stays "Nike")

✕ Map brand as text only → facets break. ✓ Fix: multi-field, index both ways.

must vs filter

Free Performance

must: scored, costs CPU every request (full-text relevance)

filter: NOT scored, cached, essentially free (in_stock=true, price<200)

Decision Tree & Interview Answer

Quick Reference

<1M docs, simple search? → Postgres tsvector. Need facets/fuzzy/>10M docs? → Elasticsearch.

"Elasticsearch pre-builds an inverted index at write time — a term-to-document map — so at query time it's not scanning documents, it's looking up a sorted list of matching IDs and scoring them by BM25 relevance in milliseconds regardless of dataset size."
