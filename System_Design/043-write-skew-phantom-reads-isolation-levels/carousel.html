Episode 43 · Write Skew & Phantom Reads

Two doctors both went home.
Zero doctors were left on call.

Alice reads: 2 on call
Thinks: "Bob's here, I can leave"
UPDATE alice → off ✔ COMMIT
Bob reads: 2 on call
Thinks: "Alice's here, I can leave"
UPDATE bob → off ✔ COMMIT
▼
RESULT: 0 doctors on call — invariant broken

Neither doctor had a dirty read. Neither had a lost update. Both decisions were individually valid. This is write skew.

System Design · Concurrency1/10
The Problem

Every read was valid. Every write was valid. The system still broke.

Isolation levels are usually taught as "does my read see dirty/uncommitted data." That only covers single-row bugs:

  • Dirty read — reading uncommitted data → fixed by READ COMMITTED
  • Lost update — two txns overwrite the same row → fixed by row locks
  • Phantom read — a new row appears mid-txn matching your query → fixed by SERIALIZABLE

Write skew lives above all three: two transactions read overlapping rows, each makes a locally-correct decision, and the combined writes violate an invariant that spanned multiple rows.

Nothing weaker than SERIALIZABLE isolation or explicit SELECT FOR UPDATE stops it.

Scenario 1 — Write Skew

The hospital on-call transaction log

BEGIN
SELECT count(*) WHERE shift='night' → 2
UPDATE oncall SET status='off' WHERE doctor='alice'
COMMIT
BEGIN
SELECT count(*) WHERE shift='night' → 2
UPDATE oncall SET status='off' WHERE doctor='bob'
COMMIT

Different rows written → no lock conflict → both commit. Reads were consistent; writes conflict on the invariant, not on a row.

Scenario 2 — Phantom Read

Seat booking: a row appears mid-transaction

T1: SELECT * FROM seats WHERE flight='AA100' AND status='available'
→ 3 rows
▼ concurrent INSERT + COMMIT by T2 ▼
T1 (same query, later): → 4 rows
A row that didn't exist at T1's start is now visible.

Existing rows didn't change — a new row snuck in and matched T1's predicate. That's the phantom.

The Fix — 4 Options

How to actually stop write skew

1SERIALIZABLE (SSI) — Postgres tracks read/write deps, aborts one txn at commit (~10-20% slower than RR). App must retry.

2SELECT FOR UPDATE — locks rows at read time; T2 blocks until T1 commits, no abort needed.

3Materialized conflict row — add a dummy row (e.g. shift_lock) every txn must UPDATE → forces serialization via a real row lock.

4Re-check before commit — lock rows, re-verify the invariant inside the txn, ROLLBACK if it would break.

Real World

Where this shows up at Indian tech scale

PhonePe / Paytm — Payments
Double-spend: 2 txns read balance=1000, both debit 900 → FOR UPDATE on account row serializes the debit.
Flipkart-style flash sale — Ticket/Item booking
Millions of concurrent buyers on 1 seat/item → FOR UPDATE contends too hard → R READ COMMITTED + idempotency key + Redis atomic counter
MakeMyTrip-style — Hotel booking
Room + date range invariant → FOR UPDATE on room+date rows OR SERIALIZABLE isolation.

Decision Tree + Interview Quote

Pick the right isolation strategy

Does the invariant involve COUNT/SUM across rows?
YES → SERIALIZABLE (locking all matching rows is fragile)
NO → exactly one row? → SELECT FOR UPDATE on that row
NO → 2-3 specific rows → FOR UPDATE on all of them OR SERIALIZABLE
"Write skew happens when two transactions each read rows the other will update — only SERIALIZABLE isolation or SELECT FOR UPDATE prevents the invariant violation."
