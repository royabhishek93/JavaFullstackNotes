HOOK

The Library With 1,000,000 Books

Two librarians. Same request: "books 500,001 through 500,010."

products / posts table — 1,000,000 rows, sorted by title
🄾 Offset Librarian
Starts at book 1. Counts to 500,000. Discards them all. Picks next 10.
Counted & discarded: 500,000 books just to hand you 10.
🄲 Cursor Librarian
Customer hands over a bookmark: "I left off here." Walk straight to it, grab next 10.
Zero wasted work — direct walk to the bookmark.
THE PROBLEM

Offset Pagination: The DB Scans What It Throws Away

LIMIT 10 OFFSET 500000 → MySQL still has to walk past the first 500,000 rows.

SELECT * FROM products ORDER BY created_at DESC LIMIT 10 OFFSET 500000;
OFFSET 20 (page 3)
20 discarded
10 returned
Rows scanned: 30  |  Returned: 10  |  Wasted: 20
OFFSET 500,000 (deep page)
500,000 scanned & discarded
10
Rows scanned: 500,010  |  Returned: 10  |  Wasted: 500,000
×100 users
→
50,000,000 rows scanned → 1,000 rows returned
100 concurrent users at page=50000 · 0.002% of the work was useful · DB CPU pinned at 100%, latency 5–30s
THE TRAP

The Shifting-Data Duplicate Bug

Between page 1 and page 2, 5 new posts get inserted at the top.

Page 1 request (OFFSET 0)
User sees posts A – J (blue = already seen)
▼  5 new posts inserted at the top  ▼
Page 2 request (OFFSET 10) — after inserts
Orange = NEW1–NEW5 (new)  |  Red (pulsing border) = A–E DUPLICATED from page 1
OFFSET shifts with every insert
The user's "page 2" now overlaps their "page 1" — same rows shown twice.
THE FIX — MECHANICS

Cursor Pagination: Tuple Comparison + B-Tree Seek

"Give me rows after this specific value" instead of "skip N rows."

SELECT id, title, created_at FROM products WHERE (created_at, id) < ('2024-01-15 10:30:00', 4521) ORDER BY created_at DESC, id DESC LIMIT 10; -- tuple comparison, not a row-count skip
root
…
2024-01-15
10:30:00 · id=4521
…
next 10
Step 1: B-tree lookup of the cursor value — O(log N)
Step 2: walk forward K=10 entries in the index — O(K)
Total cost: O(log N + K) ≈ 10 rows touched
Page 1 and page 50,000 cost exactly the same.
PROOF

No Duplicates, No Gaps

Cursor = J. Anything newer than J can never leak into "after J".

Page 1 (cursor = null)
Returns A…J. Last row's key saved as cursor = J (bookmark).
▼  5 new posts inserted (NEW1–NEW5, all newer than J)  ▼
Page 2 request: WHERE (created_at,id) < (J.created_at, J.id)
✕ excluded
NEW1–NEW5 are newer than J → filtered out by the WHERE clause. Only K, L, M, N… (after J) return.

API CONTRACT

What the Client Actually Sees

Offset Pagination API
GET /products?page=3&limit=10 { "data": [...], "total": 1000000, "page": 3, "totalPages": 100000 }
Cursor Pagination API
GET /products?limit=10 GET /products?cursor=eyJp...&limit=10 { "data": [...], "nextCursor": "eyJpZCI6NDUyMX0=", "hasMore": true }
hasMore = false → nextCursor omitted → end of results.
WHEN TO USE WHICH

Pick the Right Tool for the Access Pattern

Use Cursor Pagination
  • ✓Infinite scroll / feeds (social, notifications)
  • ✓Real-time data, frequent inserts
  • ✓Large datasets (millions of rows)
  • ✓Deep pagination (beyond page 100)
  • ✓Must avoid duplicates/gaps
Use Offset Pagination
  • ✕Admin dashboard "go to page 47"
  • ✕Static / rarely-changing data
  • ✕Small datasets (<10,000 rows)
  • ✕Need total count / total pages
  • ✕Random jump-to-page access
Hybrid Approach (most real products)

THE ONE-LINER

Say This in the Interview

"Offset pagination is O(N) — the DB must count N rows from the start every time; cursor pagination is O(1) — the cursor IS the index position, so page 1 and page 10,000 cost exactly the same."
Social Feed
Infinite scroll on (created_at, post_id) — O(1) per page.
E-Commerce Orders
Order history cursor on (order_date, order_id) — page 250 = page 1.
Leaderboard
Score cursor via ZREVRANGEBYSCORE — stays consistent as scores update.
OTT · 10M Videos
Cursor on (created_at, video_id) = 1 seek, 20 rows, zero wasted scans.
