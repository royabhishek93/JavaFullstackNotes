# Cache-Aside vs Write-Through vs Write-Behind — YouTube Script
Duration: ~10 min | Target: Engineers 3–10 YOE | Episode: 46 of the series

## HOOK (0:00–0:30)
"Picture a Black Friday sale. Your product page used to load in half a second. Right now it's taking five full seconds, because every single request is hitting Postgres directly. You reach for Redis — obviously — but here's the part almost nobody gets right on the first try: there are three completely different ways to keep a cache in sync with a database, and picking the wrong one either serves customers a stale price, or silently loses their shopping cart the moment the cache crashes. Today I'm breaking down cache-aside, write-through, and write-behind — with the exact production traps that catch engineers who think 'just add Redis' is the whole answer."

## THE PROBLEM (0:30–2:00)
"Think of it like a waiter with a notepad. The kitchen — your database — has the full menu: current prices, what's in stock, everything. You, the waiter, carry a small notepad — your cache — so you don't have to run to the kitchen every time a customer asks a question. The problem every engineer eventually hits is: how does the notepad stay in sync with the kitchen when the kitchen's menu changes? If you get this wrong, one of three things happens. Either your notepad shows the customer stale information — you tell them the salmon's available when it just sold out. Or every single kitchen update takes forever because you're updating two places every time. Or, worst case, you scribble something in your notepad, tell the customer 'done,' and then drop the notepad before the kitchen ever finds out — the update is just gone. Those three failure modes map exactly onto the three caching strategies: cache-aside, write-through, and write-behind. Each one trades off staleness, write latency, and durability risk differently, and the interview question that separates a junior from a senior engineer is knowing exactly which one to use for which kind of data."

[Screen cue: Three-way split screen — a stale menu, a slow double-write, and a notepad falling into a trash can labeled 'data lost'.]

## THE SOLUTION (2:00–5:00)
"Let's walk through all three, plus a fourth pattern worth knowing. Cache-aside, also called lazy loading, is the one you'll write most often. A request comes in, the app checks the cache first. On a miss, the app itself queries the database, writes the result into the cache, and returns it. Next request for the same key is a cache hit — fast, no database involved. The read path is simple: check cache, miss, query DB, populate cache, return. The write path is where it gets interesting — you write to the database first, and then you invalidate — delete — the cache key, rather than updating it. Why delete instead of update? Because deleting is idempotent. If two writers race to update the cache, you can end up with the cache holding an older value than the database — permanently wrong data. If you delete instead, the worst case is just one extra cache miss on the next read, which self-heals immediately. Write-through flips the write path: every write updates the cache and the database synchronously, before the write is confirmed. This means the cache is never stale — but every write is now two operations instead of one, so writes get slower. The read path becomes trivially fast because after the first write, the cache is guaranteed to have the value — no repeat cache misses except right at cold start, before any writes have happened yet. Write-behind, also called write-back, is the opposite extreme on the write side. You update the cache immediately, tell the client 'done' right away, and only batch-flush those changes to the database every one to five seconds through a write buffer or queue. This gives you the fastest possible write latency — perfect for high write-volume bursts like a shopping cart. But there's a real durability risk: if the cache crashes in that window before the batched write hits the database, that data is gone forever. And there's a fourth pattern worth knowing for interviews — read-through. It looks identical to cache-aside from the app's point of view, except the cache itself, not your application code, is responsible for going to fetch from the database on a miss. Redis doesn't do this natively — you'd need a caching layer like AWS ElastiCache with a custom provider, or a library like NCache, sitting in front of it."

[Screen cue: Draw the three write-path diagrams side by side — Cache-Aside (DB write then cache delete), Write-Through (cache + DB, both synchronous), Write-Behind (cache write, async queue, batched DB flush) — with a stopwatch icon on write-behind showing it's fastest.]

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"Here's where it actually breaks in production. Trap one: the double-write consistency problem in cache-aside. Say you write to the database first, then try to update — not invalidate, update — the cache, and that cache write fails because Redis timed out or hit an out-of-memory error. Now your database has the new value but your cache still has the old one — stale cache, and nobody notices until a customer complains. Flip the order — update the cache first, then the database — and if the database write fails this time, your cache has data that doesn't even exist in your source of truth yet. That's why the production rule is: write the database first, then invalidate — delete — the cache key, never update it directly. Trap two: cache stampede. Imagine ten thousand concurrent requests all miss the cache at the exact same moment — either it's cold start, or a popular key's TTL just expired. All ten thousand requests hit the database simultaneously for the same piece of data, and the database chokes or crashes under load it was never designed to take directly. Cache-aside is uniquely vulnerable to this because misses only get repaired by the next unlucky request. The fixes: a mutex lock where the first request to miss holds a lock and fetches from the database while everyone else waits for that same result instead of also querying the database; pre-warming the cache with your top keys before a big traffic event like a flash sale even starts; and adding random jitter — say zero to sixty seconds — on top of your base TTL, so thousands of keys don't all expire in the exact same second. Write-through, by the way, mostly sidesteps this problem, because the cache is populated on every write, not on read misses. Trap three: write-behind's durability gap. Redis is in-memory. If it crashes before that batched write hits the database, everything sitting in the write buffer is lost, permanently. The mitigation is Redis's append-only file, AOF — it logs every write operation to disk. Set 'appendfsync everysec' and you cap your worst-case data loss at one second, which is the sweet spot for most systems — 'appendfsync always' gives you zero data loss but roughly halves your write throughput, and 'appendfsync no' is fastest but leaves the OS in charge of when data actually hits disk, which is the riskiest option. Trap four: TTL is a tradeoff, not a free parameter. A short TTL, say thirty seconds, keeps data fresh but multiplies your database hits and your stampede risk. A long TTL, say one hour, protects your database but can leave customers staring at outdated prices or inventory for that entire hour. The production pattern that actually works: use a longer TTL as a safety net, but pair it with explicit cache invalidation on every write — so correctness comes from the invalidation, and the TTL is just there to catch anything you missed."

[Screen cue: Split diagram — a database on fire under 10,000 simultaneous requests labeled 'cache stampede', next to a Redis instance crashing mid-flush with a red 'DATA LOST' stamp over the write buffer.]

## REAL WORLD (8:00–9:30)
"Think about Flipkart or Myntra during a flash sale — product name, description, and images are the classic cache-aside case: read millions of times an hour, changed maybe twice a day, so a five-minute TTL keeps database load near zero. But price and available stock are exactly where you'd expect write-through — Flipkart cannot afford to show a customer nine hundred ninety-nine rupees when the real price just changed to fourteen ninety-nine, so every price update writes to Redis and Postgres synchronously before it's considered live. Now picture Zomato or Swiggy's cart service during lunch-hour rush — thousands of users adding and removing items, applying coupons, changing quantities every few seconds. That's a textbook write-behind workload: the cart update hits Redis instantly so the UI feels instant, and the actual database write is batched every couple of seconds, with Redis AOF turned on with 'appendfsync everysec' so a crash loses at most a second of cart activity, not the whole order. And for PhonePe or Paytm-style wallet balances, you'd never use plain cache-aside or write-behind — a stale or lost wallet balance is a direct financial-correctness bug, so those numbers are either read straight from the source of truth or kept behind a write-through cache with synchronous confirmation, because the cost of being wrong here is real money, not just a bad user experience."
