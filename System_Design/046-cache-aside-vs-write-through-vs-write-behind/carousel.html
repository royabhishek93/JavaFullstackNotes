Every write to the DB must somehow reach the cache. Get the ordering wrong and you either serve stale data, slow every write down, or silently lose data on a crash.

Write rule: DB.write(key, val) → cache.delete(key) — never cache.set(). Update-then-race = permanently wrong data; delete is idempotent and self-heals on next read.

✓ Zero stale reads after first write   ✕ Every write is 2 synchronous ops — slower

Use for data you can never show stale: prices, inventory counts, wallet balances. A ₹999 price shown when it's really ₹1499 is a business bug, not a UX nitpick.

Cold start or TTL expiry → every request hits the DB for the same key simultaneously. Fixes: mutex lock (1 fetches, rest wait), pre-warm before flash sales, TTL + random jitter (0-60s) so keys don't all expire together.

Production pattern: long TTL as a safety net + explicit cache.delete() on every write for correctness. Best of both.

Read-Through vs Cache-Aside

The Fourth Pattern

Cache-Aside: app code checks cache, and on miss the app queries the DB and populates the cache.

Read-Through: app always calls the cache; the cache itself fetches from the DB on a miss. App never talks to the DB directly.

Redis doesn't support this natively — needs a layer like AWS ElastiCache with a custom provider, AWS DAX, or NCache.

Decision Tree & Interview Answer

Quick Reference

Write-heavy bursts? → Write-Behind (+AOF). Stale data ever unacceptable (price, wallet)? → Write-Through. Otherwise, DB lookup on miss tolerable? → Cache-Aside.

"Cache-aside for read-heavy data where staleness is tolerable, write-through when you can never show stale data, and write-behind when your write volume outpaces what your DB can synchronously absorb."
