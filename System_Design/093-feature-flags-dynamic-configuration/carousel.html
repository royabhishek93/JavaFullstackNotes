Percentage Rollout

Consistent Hashing

bucket = hash(userId + flagKey + salt) % 100

User 12345 → bucket 17 → enabled (17 < 25%). Same user, same bucket, every server, every request — no per-user state stored anywhere.

✓ Raising 25%→50% keeps everyone already enabled, only adds new buckets — safe staged rollouts.

A/B Test Assignment & Phantom Exposures

Trap 2

Assignment consistency: same hash + salt = same user always gets the same variant for the whole experiment — or your results are contaminated.

Phantom exposures: logging on flag evaluation (e.g. a pre-fetch) instead of actual render inflates sample size with impressions nobody really saw.

✓ Fix: fire exposure events async, tied to real render, into a Kafka/analytics pipeline.

Real World

Where This Shows Up

Swiggy: a payment gateway kill switch during peak lunch-hour traffic turns a 2-min blip into avoiding a 30-min checkout outage.

Decision Tree & Interview Answer

Quick Reference

Need instant kill switch or staged rollout? → Flag platform. Setting never changes at runtime? → Just an env var. Infra-level routing? → Canary/blue-green, not an app flag. Slow-moving settings only, no urgency? → DB-polled config table.

"bucket = hash(userId + flagKey + salt) % 100 — deterministic, stateless, stable across servers, requests, and deploys. Evaluation stays local and in-memory; only rule updates get pushed over streaming. A kill switch is the same rollout mechanism flipped to zero, and it's only as good as its fallback to the last-known-good code path."
