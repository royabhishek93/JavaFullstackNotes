## THE PROBLEM (0:30–2:00)
"Here's the confusion everyone has: they compare Redis to a Java Spring Boot service backed by MySQL, and assume single-threaded must mean slower. But look at where the time actually goes in a typical MySQL-backed request. Client sends an HTTP request, a Java thread picks it up — that's one microsecond of real CPU work. Then the thread sends SQL over the network — one millisecond. Then MySQL reads the row from disk — five to ten milliseconds. Then the result comes back over the network — another millisecond. Total round trip: about ten milliseconds. But the actual CPU work in that whole request? Only zero point zero zero two milliseconds — point zero two percent of the time. The thread is sleeping ninety-nine point nine eight percent of the time, just waiting on disk and network. That's exactly why Java needs thread pools — while Thread A sleeps waiting on MySQL, Thread B handles a different request. You need five hundred threads to handle five hundred concurrent 'sleeping' requests. Now flip that model to Redis. There's no disk. Everything lives in RAM. A GET command is a hash table lookup — one hundred nanoseconds. There's nothing to sleep on. So the real question isn't 'how does one thread do multiple things at once' — it's 'how does one thread manage ten thousand concurrent connections without sleeping on any single one of them.'"

[Screen cue: Timeline diagram of the 10ms MySQL request — CPU work highlighted as a tiny sliver, sleep time as a huge grey block — then the same timeline for Redis showing 100 nanoseconds total.]

## THE SOLUTION (2:00–5:00)
"The answer is epoll — Linux kernel I/O multiplexing. Instead of blocking I/O, where a thread calls 'read from socket one,' finds no data, and gets parked to sleep by the OS until data arrives — which costs an expensive context switch of one to five microseconds every single time — Redis does something completely different. One thread registers ALL ten thousand sockets with epoll using epoll underscore ctl. Then it calls epoll underscore wait, and the OS blocks right there until ANY of those ten thousand sockets has data. When data shows up on socket forty-two, socket eight ninety-one, and socket thirty-three-oh-one, the OS wakes the thread ONCE and hands back the full list of ready sockets. The thread loops through every ready socket, reads the bytes that are already sitting in the kernel buffer, parses the command — say, 'GET user colon one two three' — executes it against the hash table in about a hundred nanoseconds, writes the reply back, and then calls epoll underscore wait again. No context switches between connections. No ten thousand threads eating ten gigabytes of RAM just for thread stacks. This is literally the Redis main loop — while server running: process time events for expiry and persistence, call ae underscore poll which wraps epoll, then loop through every ready file descriptor and either read-and-process or write-the-reply. One thread. Zero sleeping per connection. That's the entire secret."

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"Here's the trap that trips up almost every engineer in an interview: they assume adding more threads to Redis would make it faster. It's the opposite — it would make Redis SLOWER. Why? Redis has one global hash table. If two threads process commands simultaneously — say Thread 1 runs SET user colon one two three equals Bob, and Thread 2 runs SET user colon one two three equals Carol at the same time — you get a race condition, and you don't know which value wins. To prevent that, you need a mutex lock: Thread 1 locks, sets, unlocks; Thread 2 waits for the lock, then locks, sets, unlocks. Sounds fine until you look at the actual costs. A lock acquisition costs about fifty nanoseconds. The actual SET operation costs about one hundred nanoseconds. So single-threaded math is one hundred nanoseconds of work plus zero nanoseconds of locking equals one hundred nanoseconds per operation. Multi-threaded math is one hundred nanoseconds of work plus fifty nanoseconds of locking equals one hundred fifty nanoseconds per operation — fifty percent SLOWER. This is Amdahl's Law in action: the sequential fraction of Redis's actual work — hash table lookup, command parsing, data structure mutation — is one hundred percent sequential. Zero percent is parallelizable at the command-execution level. Adding eight cores to purely sequential code gives you zero speedup; it just adds lock overhead. Now, here's the specific race condition every engineer should be able to walk through: imagine page views equals ninety-nine. Thread A reads page views, gets ninety-nine. Thread B reads page views BEFORE Thread A writes back — also gets ninety-nine. Thread A writes one hundred. Thread B writes one hundred. You just LOST an increment — it should have been one hundred one. Single-threaded Redis can't have this bug: main thread reads ninety-nine, writes one hundred, THEN the next INCR command executes, reads one hundred, writes one hundred one. Correct, every time, with zero locks. That's exactly why INCR, SETNX, GETSET, LPUSH, and ZADD are all atomic by default in Redis — no MULTI slash EXEC needed for single-command atomicity. The architecture gives you that for free. And one more trap: engineers think Redis 6 made everything multi-threaded. It didn't. Redis 6 added OPTIONAL I/O threads — but only for reading and writing raw bytes from sockets, not for command execution. Picture io-threads set to four: I/O Thread 1 reads bytes from socket group A, I/O Thread 2 reads from group B, I/O Thread 3 from group C — but the main thread is still the only one that parses and executes commands, still single-threaded, still zero locks needed on the data structures. Before Redis 6, at one million ops per second, socket read and write was consuming about thirty percent of the single thread's time — that's the actual bottleneck Redis 6 solved, not command execution speed. And the last trap: don't confuse background threads with I/O threads. BGSAVE forks the process and writes an RDB snapshot from a copy-on-write child — main thread never blocks. Lazy free is the other one: deleting a key with ten million items would normally block the main thread for about five hundred milliseconds freeing memory — so Redis added the UNLINK command, which removes the key reference instantly in about one hundred nanoseconds, and hands the actual memory-freeing work to a background thread. None of these background threads ever touch the main hash table."

## REAL WORLD (8:00–9:30)
"Let's ground this in real numbers. Take a company doing a hundred million requests a day — that's about eleven hundred fifty-seven requests per second on average, and around eleven thousand five hundred seventy at ten-times peak traffic. A single Redis instance benchmarks at one hundred thousand to two hundred thousand GET ops per second, eighty thousand to one hundred fifty thousand SET ops per second, and up to a million ops per second with pipelining. That peak of eleven thousand five hundred seventy requests per second is only about ten percent of a single instance's capacity — meaning ONE Redis node handles that traffic with ninety percent headroom to spare. Swiggy operates at roughly this scale — around ten million orders a day system-wide — and a single well-provisioned Redis instance for session and cart caching comfortably absorbs that load without needing a cluster. Now scale it up: for something like PhonePe or Paytm running UPI transaction rate-limiting during a festival sale, you're leaning on Redis's atomic INCR plus EXPIRE for token-bucket counters — the single-threaded execution model is exactly why INCR never has a race condition on a shared counter, even when lakhs of transactions are hitting the same key per second. And picture Flipkart or Myntra during a Big Billion Days flash sale — session and cart data cached in Redis, traffic spiking one hundred times normal — a single instance handles that ten-percent-of-capacity spike easily, and if they truly needed to go past that, Redis Cluster with six primary nodes gets you six hundred thousand to one point two million ops per second combined, with zero cross-node locking because each node still executes its own commands single-threaded."
