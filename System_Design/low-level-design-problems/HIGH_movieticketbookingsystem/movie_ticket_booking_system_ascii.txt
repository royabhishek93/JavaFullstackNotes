Interview Notes
- Theater hierarchy is City -> Theater -> Screen -> Seat.
- Movie scheduling is Movie -> Show, and each Show runs on exactly one Screen.
- SeatAvailability is the critical concurrency table for per-show seat state.
- BookingSeat is required because one booking can contain multiple seats.
- Payment is 1:1 with Booking in the happy path, but booking remains the business root.

Relationship Summary
- City 1..N Theater
- Theater 1..N Screen
- Screen 1..N Seat
- Movie 1..N Show
- Screen 1..N Show
- Show 1..N SeatAvailability
- Seat 1..N SeatAvailability
- User 1..N Booking
- Show 1..N Booking
- Booking 1..N BookingSeat
- Seat 1..N BookingSeat
- Booking 1..1 Payment

DB Type Mapping
- PostgreSQL: City, Theater, Screen, Seat, Movie, Show, Booking, BookingSeat, Payment
- PostgreSQL + Redis: SeatAvailability
- Redis role: temporary seat reservation/lock acceleration and fast expiry handling
- Source of truth: PostgreSQL remains authoritative for final booking/payment state
