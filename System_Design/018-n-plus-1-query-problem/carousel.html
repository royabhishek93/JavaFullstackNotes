THE PROBLEM

One Line Hides 100 Extra Queries

JPA/Hibernate LAZY entity + an innocent-looking loop

Entity + the buggy loop
@Entity class Order { @OneToMany(fetch = FetchType.LAZY) List<OrderItem> items; // not loaded yet } List<Order> orders = repo.findAll(); // Query 1 for (Order o : orders) { print(o.getItems()); // Query 2..101 }
Generated SQL
-- Query 1 SELECT * FROM orders; -- 100 rows -- Query 2 (order_id=1) SELECT * FROM order_items WHERE order_id = 1; -- Query 3 (order_id=2) SELECT * FROM order_items WHERE order_id = 2; -- ... 97 more queries ... -- Query 101 (order_id=100) SELECT * FROM order_items WHERE order_id = 100;
101 queries total — 2ms each = 202ms
A single JOIN would return the same data in ~5ms

FIX 1 & 2

JOIN FETCH and @EntityGraph — Both Give 1 Query

Fix 1 — JOIN FETCH (JPQL)
@Query("SELECT o FROM Order o JOIN FETCH o.items") List<Order> findAllWithItems(); -- Generated SQL: -- SELECT o.*, oi.* -- FROM orders o INNER JOIN order_items oi -- ON oi.order_id = o.id
Fix 2 — @EntityGraph (Spring Data)
interface OrderRepository extends JpaRepository<Order, Long> { @EntityGraph(attributePaths = {"items"}) List<Order> findAll(); // Hibernate generates a LEFT JOIN }
→ 1 query
Always-needed relations, single round trip
→ 1 query
Cleaner syntax, same LEFT JOIN result
FIX 3

@BatchSize — Batch Loading (100 → 4 Queries)

Annotation
@OneToMany(mappedBy = "order", fetch = FetchType.LAZY) @BatchSize(size = 25) List<OrderItem> items;
Generated SQL — 4 batches
WHERE order_id IN (1...25) -- query 1 WHERE order_id IN (26...50) -- query 2 WHERE order_id IN (51...75) -- query 3 WHERE order_id IN (76...100) -- query 4

FIX 4

DTO Projection — Most Performant, Read-Only

Flat DTO + query
record OrderWithItemsDTO( Long orderId, String status, Long itemId, String productName, Integer quantity) {} @Query(""" SELECT new ...OrderWithItemsDTO( o.id, o.status, oi.id, oi.productName, oi.quantity) FROM Order o JOIN o.items oi """) List<OrderWithItemsDTO> findOrdersWithItems();
Group back in Java
Map<Long, List<OrderWithItemsDTO>> grouped = results.stream() .collect(groupingBy( OrderWithItemsDTO::orderId));
→ 1 query, no entity overhead
Best for read-only endpoints — no lazy proxies, no cartesian bloat if selected columns are flat
OTHER FRAMEWORKS

N+1 Isn't Just a Java Problem

Django ORM (Python)
# N+1: for o in Order.objects.all(): print(o.items.all()) # N queries # Fix: Order.objects.prefetch_related('items') # 2 queries total
ActiveRecord (Rails)
# N+1: Order.all.each { |o| puts o.items } # Fix: includes Order.includes(:items).all # 2 queries total
TypeORM (Node/TS)
// N+1: for (const o of orders) await o.items; // Fix: relations orderRepo.find({ relations: ['items'] });
Same fix, every ORM
Tell the query layer upfront what related data you need — eager-load with a JOIN instead of lazily fetching per row

Diagnostic rule of thumb
  • ✕Response time grows linearly with result size → N+1
  • !Grows logarithmically → probably an index issue
  • ✓Flat regardless of N → you're good
Interview debug playbook (/orders slow at 500ms)
Enable spring.jpa.show-sql=true + Hibernate SQL debug logging — 101 queries logged for 100 rows confirms N+1. Fix depends on access pattern: JOIN FETCH/@EntityGraph if items always needed, else keep LAZY + a separate projection endpoint. In prod, track queries-per-request via APM (Datadog/Micrometer) as a KPI, not just latency.
REAL WORLD · THE ONE-LINER

Where This Breaks Production

Social Media Feed
20 posts → 21 queries per feed load. At 1M concurrent users: 21M queries/sec. Fix: JOIN FETCH on post-author.
Food Delivery Listing
50 restaurants → 51 queries per page. Fix: @EntityGraph on restaurant-categories → 1 JOIN query.
E-Commerce Product Search
40 products → 81 queries (seller + rating per row). Fix: DTO projection with explicit JOIN, 1 round trip.
"N+1 happens when you let your ORM drive — the fix is to tell the DB what you need upfront with a JOIN, not ask it 'what's this entity's related data?' one row at a time."
