Partitions Are Mandatory

The Problem

CP MySQL (sync), ZooKeeper, HBase, etcd — refuse rather than risk wrong data

AP Cassandra, DynamoDB, CouchDB, Riak — stay available, tolerate staleness

Partition tolerance isn't optional — the real choice is C vs A when it happens.

One Product, Different CAP Choices

The Trap Nobody Expects

AP Product catalog — stale price for 30s is annoying, tolerable

CP Inventory decrement at checkout — overselling zero-stock items is a real disaster

CAP is a per-subsystem decision, not a whole-system decision.

Last-Write-Wins vs CRDT Counters

Conflict Resolution Trap

Default LWW (timestamp-based) can silently LOSE increments on a "like count" during concurrent writes.

Fix: Cassandra counter columns use CRDTs — merge by summing, never overwriting. No increment lost.

PACELC > CAP Day-to-Day

The More Useful Model

During a Partition: choose Availability or Consistency.

Else (normal ops, no partition): choose Latency or Consistency.

QUORUM reads in Cassandra = stronger consistency, but waits for 2/3 nodes → visible latency spike. This is the "Else" trade-off you make every day.
