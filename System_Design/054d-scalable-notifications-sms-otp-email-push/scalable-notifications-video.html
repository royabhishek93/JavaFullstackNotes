Why a Unified Notifications Platform?

"The hard part isn't sending one email. The hard part is sending 1 million notifications per minute on Black Friday, making sure every OTP lands in under 10 seconds, never duplicating a notification when Kafka replays a message, and still honoring a user's do-not-disturb preferences at 2am."

Real-World Scenarios

  • WhatsApp OTP — login code in <5s globally
  • Swiggy Push — "Your rider is 2 mins away"
  • Flipkart Email — 50M Black Friday promo blast
  • Bank SMS — transaction alert, zero tolerance for loss

Three Core Principles

  • 🚫 No notification loss — outbox pattern
  • 🔁 No duplicate delivery — idempotency
  • ⚡ Strict priority ordering — OTP never waits
All four channels share one platform. Single compliance layer, single rate limiter, single observability stack. No team reinvents retry logic.
Notification Service is internal infrastructure — like internal AWS SNS with company-specific business logic baked in. Order Svc, Auth Svc, and Marketing all send through the same platform.

Routing Logic

Priority set by caller. Notification Service validates against API key ACL — Marketing team API keys cannot send CRITICAL priority. Enforced at Layer 2 before outbox write.

OTP Special Rule

OTP expires in 30–300 seconds. Skip retry queue entirely — a 1-min backoff makes OTP useless. Immediate re-attempt or fast-fail.

OTP System Design — TOTP, HMAC-SHA1 & Rate Limits

OTP Generation — TOTP (RFC 6238)

// HMAC-SHA1 based 6-digit OTP secret = HMAC-SHA1(server_secret, user_id + purpose) counter = floor(current_unix_time / 30) // 30s window otp = truncate(HMAC-SHA1(secret, counter)) % 1_000_000 // Redis storage (auto-expiry) SET otp:{userId}:{purpose} {otp} EX 300 // 5 min TTL // Verification stored = Redis GET otp:{userId}:{purpose} valid = (input == otp_for_window_T) OR (input == otp_for_window_T-1) // clock skew ±30s if valid → Redis DEL key (single-use enforced)
Clock skew tolerance: accept current window T and previous window T-1. Covers 30 seconds of drift between client and server.

Anti-Flood & Security

Rate Limiting (Redis counters)

  • Max 5 OTPs / 10 min per user + purpose
  • Max 3 OTPs / min per IP address
  • Account lock for 15 min after 5 failed attempts
  • Exponential backoff after 3 wrong entries

DDoS Attack Mitigation

  • Rate limit at API Gateway — before any DB touch
  • CAPTCHA after 2 OTP requests from same IP/min
  • IP reputation check + datacenter/VPN block
  • Twilio Lookup API: reject landlines / VoIP
  • Silent fail: return 200 "OTP sent" even if blocked

Push Notification Path — FCM & APNs

FCM — Android & Web (Google)

  • HTTP v1 API with OAuth2 token (not legacy server key)
  • Priority: normal (silent) or high (wake screen)
  • Collapse key: dedup in-flight stacked notifications
  • 10,000 messages/sec per app — free tier
  • Topic fan-out: /topics/promo_users → broadcast to all subscribers

APNs — iOS & macOS (Apple)

  • HTTP/2 required; multiplex connections (max 1,000 concurrent streams)
  • Priority 10 = immediate alert, Priority 5 = low-power delivery
  • apns-collapse-id header for deduplication
  • JWT (.p8 key) auth — no cert renewal headache
  • <5,000/sec per connection (use connection pool)

Device Token Management

// Registration POST /api/v1/devices { userId, token, platform: "android"|"ios", appVersion } → UPSERT device_tokens SET active=true, updated_at=now() // Fan-out to multiple devices (same user, 3 phones) tokens = SELECT token FROM device_tokens WHERE userId=? AND active=true for each token → send push independently → collect failures asynchronously // Token cleanup (CRITICAL — do not skip) FCM 404 "InvalidRegistration" → active=false APNs 410 "Gone" → active=false NEVER retry with a dead token → silent failure forever
Stale tokens silently fail. Always remove on 410/404. Multi-device users need fan-out to ALL active tokens — one notification → N push requests.

SMS Gateway — Twilio, Fallback & Country Routing

Twilio (Primary)

  • Global: 180+ countries, carrier-grade delivery
  • 100 SMS/sec per number — use number pool for scale
  • $0.0075/SMS (US); varies by country
  • DLR webhooks: delivered / undelivered / failed
  • TCPA compliance + STOP keyword handling built-in
  • WhatsApp Business API via same SDK

Fallback — AWS SNS / MSG91

  • AWS SNS: US/EU fallback on Twilio outage (circuit breaker)
  • MSG91: India-primary — 5x cheaper, better IN carrier rates, TRAI DND built-in
  • Country routing: IN → MSG91, US/EU → Twilio, others → SNS
  • Circuit breaker trips at 50% failure rate → auto-switch in <10s

DLR Webhook & Retry Flow

// Twilio sends DLR to our endpoint POST /webhooks/twilio/dlr { MessageSid: "SM123abc", MessageStatus: "delivered" | "failed" | "undelivered", To: "+919999999999", ErrorCode: "30008" } // Rule: respond 200 OK within 15s — or Twilio retries! queue event immediately → batch-update delivery_status // Permanent failures (no retry): 30003 landline 30004 blocked 30006 unreachable 30007 carrier violation // Retriable failures: 30001 queue overflow 30002 timeout → push to notif.retry.standard with backoff
Never block the webhook handler. Queue the event, respond 200, process async. Twilio has a 15s webhook timeout — miss it and you get duplicate DLR callbacks.

Template Engine — Jinja2 / Handlebars, Locale & A/B

Immutable Versioning Design

// Template record — composite PK (id + version) { templateId: "order_confirm", version: 3, // never mutated channel: "email", locale: "en-IN", subject: "Order {{order_id}} confirmed ✓", body: "Hi {{name}}, your ₹{{amount}} order is confirmed.", variables: ["name", "order_id", "amount"], is_active: true } // PUT → creates NEW version, old version is_active=false // Never UPDATE body in place — 50K in-flight notifications // reference template_id + version; changing body mid-flight // makes them inconsistent // Redis cache key: template:{id}:{version} TTL 1h // Cache invalidation: new version = new key (self-solving)

Localization

Separate template per locale: en-IN, hi-IN, ta-IN. Locale resolved from user profile → fallback to en. Currency / date formatting applied per locale at render time.

A/B Testing

v3 (control) vs v4 (variant). Route 10% of recipients to v4 via feature flag in Notification Service. Track open rate per version in analytics. Promote winner to 100% after 48h.

Personalization

Variables injected at render time from caller payload. Rich HTML stored in S3, URL referenced in template body. Always require a text/plain fallback for accessibility + spam filters.

Deduplication — Idempotency Key & Redis TTL

Four Duplication Points

1
CDC publishes outbox record twice
Crashes after Kafka publish, before marking published=true. Kafka gets two copies. Fix: consumer idempotency check at Layer 4.
2
Kafka consumer crashes mid-send
Offset not committed → Kafka replays on restart. Fix: SELECT delivery_status WHERE notif_id + channel — if row exists, SKIP silently.
3
HTTP drop to provider
Provider sent email, our 202 response lost, we retry. Fix: pass X-Message-Id header — SendGrid deduplicates for 72h on their side.
4
Provider webhook fires twice
Webhooks are at-least-once. Fix: UPDATE delivery_status SET status=DELIVERED is idempotent — setting DELIVERED twice is safe.

Client Idempotency Key (24h Window)

POST /api/v1/notifications { "metadata": { "idempotency_key": "order-ORD456-email-v1" } } // Server-side check key = "idem:" + sha256(client_id + idempotency_key) cached = Redis GET key if cached: → return cached notificationId (200, no new row) else: → process notification normally → Redis SET key {notificationId} EX 86400 → return 200 OK { notificationId }
With all 4 safeguards active: a user receives two emails only if our DB idempotency AND SendGrid's own dedup both fail simultaneously. In practice: 0% duplicate rate.

User Preference Center — Opt-Out & DND Hours

Preference Schema

PUT /api/v1/preferences/{userId} { "channels": { "email": true, "sms": false, // SMS opt-out "push": true, "inapp": true }, "types": { "promotional": false, // marketing opt-out "transactional": true, "alerts": true }, "doNotDisturb": true, "dndWindow": { "start": "22:00", "end": "08:00", "timezone": "Asia/Kolkata" } } // Side effect: Redis DEL user_pref:{userId} // + publish to Kafka topic user.preference // → consumer does Redis SET with fresh value

Enforcement & Cache Consistency

Check at Layer 2 (Before Kafka)

Redis cache user_pref:{userId} — 24h TTL, 95% hit rate, sub-ms lookup. Check channels + types + DND before writing outbox. Skip channels the user opted out of.

Cache Invalidation Fix

User unsubscribes at 9am. Old Redis value lives 24h — they receive marketing email at 9:01am. Fix: DEL cache immediately on every preference write + Kafka event drives async SET refresh. Double-layer invalidation.

DND Enforcement

Marketing / transactional notifications received during DND window → queue for delivery at DND end time. OTP + security alerts bypass DND (user implicitly consented). Timezone-aware scheduling.

Delivery Tracking — Sent → Delivered → Opened

Status Lifecycle

PENDING → QUEUED → SENT → DELIVERED → OPENED ↓ ↓ CANCELLED RETRYING → DLQ ↓ FAILED (permanent) Transition rules: PENDING : In outbox, CDC not yet published to Kafka QUEUED : In Kafka, consumer has not picked up yet SENT : Provider accepted (202 / 200 response) DELIVERED : Provider DLR webhook confirmed delivery OPENED : Email pixel loaded / push notification tapped FAILED : Permanent (bounce, 410 Gone, STOP reply) RETRYING : Temp failure, in retry topic with backoff DLQ : 3 retries exhausted → PagerDuty ops alert CANCELLED : Cancelled before SENT (only valid in PENDING)
Tracked per channel per attempt. One notification_id can have email=DELIVERED, push=FAILED, SMS=SENT — independent delivery records.

Email Open Tracking

1×1 transparent pixel: /track/open/{notif_id}/{uid}.png. On pixel load → record open event. Note: Apple Mail Privacy Protection may inflate open rate — filter Apple proxy IPs.

Click Tracking

All links rewritten: /track/click/{notif_id}/{link_hash} → 302 redirect to original URL. Captures CTR per campaign, per template version.

Analytics Pipeline

Redis counters (per campaign, per hour) → Kafka events → Spark/Flink aggregation → InfluxDB → Grafana. Metrics: send rate, delivery rate, open %, CTR, bounce %, DLQ count.

Scaling Strategy — Kafka Partitioning & Bulk vs Real-Time

Kafka Partitioning

// Partition by user_id for consistent ordering producer.send({ topic: "notif.standard.email", key: user_id, // same user → same partition value: notification_json }) // Why user_id as partition key? // → Ordering preserved per user within a topic // → Predictable consumer routing // → Avoids thundering herd on one partition // Partition sizing (100M/day ≈ 1,200/sec avg) notif.critical.* 12 partitions (~100/sec/partition) notif.standard.* 30 partitions notif.promotional.* 20 partitions notif.bulk.* 10 partitions (throttled send rate) // Consumer lag SLA critical <100ms consumer lag standard <2s consumer lag bulk no hard SLA (best-effort)

Real-Time Lane

OTP, transactional, security alerts. Small payloads (<2KB). Low-latency critical path. Kafka consumer → provider in <5s. 80 workers across channels.

Bulk / Campaign Lane

50M user Black Friday blast. Pre-segment user list to S3 at T-24h. Campaign worker streams 10K-user batches → notif.bulk.email. Throttled: 1K/sec (IP warm-up). 50M ÷ 1K/sec = ~14 hours.

DB Scaling: notifications partitioned by created_at (monthly). delivery_status partitioned by channel. Archive to S3 Parquet after 90 days (Athena for analytics queries).

Senior Q&A 1 — OTP Flood Attack (DDoS via SMS)

"An attacker scripts your OTP endpoint with 10,000 different phone numbers per minute. You're spending $75/min on Twilio. How do you defend?"
1
API Gateway Rate Limit (first line)
Max 3 OTP requests/min per IP. Max 5 OTP requests/10min per user. Redis sliding window counter. Block before DB touch — zero cost per blocked request.
2
CAPTCHA Enforcement
After 2 OTP requests from same IP in 1 min → require reCAPTCHA v3 (invisible). No UX friction for legitimate users, stops bots.
3
IP Reputation Blocklist
Real-time IP reputation API (MaxMind, IPInfo). Block known VPN / proxy / datacenter IP ranges. Country-level rate cap for unexpected high-volume origins.
4
Phone Number Validation
Validate E.164 format before queuing. Twilio Lookup API: is this a real mobile number? Reject landlines and VoIP numbers — saves SMS cost (Lookup is cheaper than SMS).
5
Spending Alerts & Kill Switch
Twilio spend alert threshold: >$X/hour → pause SMS, trigger PagerDuty. Feature flag kill switch: disable OTP SMS globally within 30 seconds.
Silent fail: always return HTTP 200 "OTP sent" even when blocked. Never reveal that the number is rate-limited — prevents attacker from probing which numbers are blocked.

Senior Q&A 2 — Marketing Blast to 50M Users

"It's Black Friday. Marketing schedules a promo email to all 50M active users at 12:00am. Walk me through exactly how your system handles this without taking down production."

Pre-Launch (T-24h)

  • Segment query runs as Spark batch job → user_id list persisted to S3
  • Campaign record created: status=SCHEDULED, recipientCount=50M
  • IP warm-up check: are dedicated IPs at sending capacity?
  • Request SendGrid / SES hourly quota increase in advance
  • Scale Kafka bulk consumer instances: 5 → 20

At T+0 (12:00am)

  • Campaign worker streams S3 user list in 10K-user batches
  • Each batch → publish 10K messages to notif.bulk.email
  • Throttled send rate: 1,000 emails/sec (IP warm-up ceiling)
  • 50M ÷ 1,000/sec = ~14 hours total delivery window
  • Promotional opt-outs excluded at segment query time (not per-message)

Isolation from Real-Time Traffic

notif.bulk.* topic uses separate consumer group with 5–20 workers. Completely isolated from OTP and transactional Kafka topics. Black Friday campaign cannot impact OTP delivery by 1ms.

Guardrails

  • DND window: schedule delivery for post-DND if user is in quiet hours
  • Kill switch: pause campaign if bounce rate exceeds 2%
  • PagerDuty alert if DLQ rate exceeds 1%

Live Dashboard

Send rate, delivery rate, open rate, bounce %, DLQ count — all visible in real-time Grafana dashboard. Campaign manager can pause/resume without a deployment.

Senior Q&A 3 — Dedup Failure Race Condition

"Your idempotency check SELECTs from delivery_status. What if two Kafka consumers process the same notification simultaneously? Both see 0 rows, both call SendGrid. User gets two emails."

The Race Condition

Consumer A picks up message M t=0 Consumer B picks up message M t=0 (Kafka redelivery) A: SELECT delivery_status WHERE notif_id=X → 0 rows B: SELECT delivery_status WHERE notif_id=X → 0 rows A: POST /mail/send → SendGrid accepts ✓ B: POST /mail/send → SendGrid accepts ✓ ← DUPLICATE! A: INSERT delivery_status(X, EMAIL, SENT) B: INSERT delivery_status(X, EMAIL, SENT) → UNIQUE VIOLATION
SELECT-then-INSERT is not atomic. Two readers both pass the check before either writer commits. Classic TOCTOU race.

Fix: INSERT-First Idempotency

-- Unique constraint already in schema CREATE UNIQUE INDEX idx_dedup ON delivery_status(notification_id, channel); -- Consumer: INSERT first, don't SELECT first BEGIN; INSERT INTO delivery_status(notification_id, channel, status) VALUES ($1, $2, 'PROCESSING') ON CONFLICT (notification_id, channel) DO NOTHING; GET rowcount → 0 rows inserted → DUPLICATE DETECTED, skip + commit → 1 row inserted → we own this message, call SendGrid COMMIT;
INSERT is atomic at the DB level. Only one consumer wins the race — the other gets conflict, skips, no double-send. No SELECT needed.
Also pass X-Message-Id to SendGrid as final safety net — their 72h dedup catches any slip-through.

Three Guarantees Delivered

No Notification Loss

Transactional outbox pattern. CDC polls DB — not memory. Kafka 7-day retention. Any window can be replayed. Notification persists from the moment the DB transaction commits.

No Duplicate Delivery

Four-layer dedup: idempotency key → DB UNIQUE INDEX (INSERT-first) → X-Message-Id to provider → idempotent webhook handler. In practice: 0% duplicate rate.

Strict Priority Ordering

Dedicated Kafka topics + worker pools per priority tier. OTP <1s guaranteed regardless of bulk campaign load. Isolated retry topics per priority — P0 retry never starved by P2.
