Scenario 1

Strangler Fig — migrate one capability at a time

A routing facade (often your API Gateway) sits in front of the monolith. Only one route goes to the new service — everything else hits the monolith unchanged. Break something? Flip one route back.

Trap #1

Migrating checkout first is the classic mistake

Correct order: low-risk if it breaks, high-value to prove the pattern, loosely coupled in legacy code.

1. Search / catalog display — read-heavy, low-risk
2. Profile updates — write path, lower blast radius
3. Checkout / payment — LAST, once pattern is proven

Real Numbers

Sequential vs. parallel composition

4 services joined sequentially: 100–200ms added vs. a monolith JOIN's single-digit ms. Fan-out in parallel: cost drops to roughly the slowest single call.

Sequential — 4 hops chained
≈150ms total
Parallel fan-out — 4 hops at once
≈45ms total (slowest hop wins)
Latency: 5–50ms per hop, same-DC vs cross-region
Decision Framework

Pattern comparison

PatternSolvesCost/Tradeoff
Strangler FigIncremental monolith migration, no big-bang cutoverMonths–years; needs routing facade + careful order
BFFCompeting mobile/web/partner response shapesExtra layer per client type; some duplicated logic
Anti-Corruption LayerLegacy schema quirks vs. clean new domain modelTranslation code to maintain, but contained to one boundary
DB-per-servicePrevents re-coupling via shared tablesOld JOINs become API composition / read model
API CompositionCross-service joins at query timeAdded latency; mitigate with parallel fan-out
Precomputed Read ModelFrequent, perf-sensitive cross-service readsMore infra (event pipeline) but much faster reads

Interview Answer

Decision tree + the exact quote to use

10yo monolith → too risky to rewrite all at once?
  → Strangler fig: routing facade, migrate low-risk reads first, checkout last
  → New service needs legacy data? Anti-Corruption Layer
  → Multiple client types? BFF per client
  → Cross-service read after DB-per-service? API composition (parallel) or CQRS read model
"I would explicitly reject a big-bang rewrite... Instead, I'd use the strangler fig pattern: put a routing facade in front of the monolith, and migrate ONE capability at a time, starting with something read-heavy and low-risk, like product search, not the checkout flow."
