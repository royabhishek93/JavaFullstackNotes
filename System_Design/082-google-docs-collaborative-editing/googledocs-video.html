The Hardest Problem

"Two users type at the exact same position at the same time. Whose change wins?"

Document: "BC"   (Alice and Bob both have this on screen)

Alice types "A" at pos 0  →  her screen: "ABC"
Bob   types "D" at pos 2  →  his screen: "BCD"

Both ops race to the server simultaneously.
Who wins? ─── BOTH. That's the design challenge.

The answer is: neither edit is lost. The system must converge both users to "ABCD".

This is NOT a storage problem. NOT a scale problem. It's a conflict resolution problem.

The algorithm that solves it is called Operational Transformation (OT).

Google Docs has used OT since 2010. Figma and Notion use CRDT — we'll cover both.

Functional Requirements

  • Real-time co-editing — multiple users edit the same document simultaneously
  • Presence & cursors — see each collaborator's cursor in a distinct colour
  • Comments & suggestions — anchor to a text range, resolve/reopen
  • Version history — view and restore any past version of the document
  • Offline editing — edits queued locally, synced on reconnect
  • Sharing & permissions — Viewer / Commenter / Editor roles per user or link
  • Auto-save — no explicit save action; every keystroke is persisted
  • Rich text export — download as DOCX, PDF, HTML
  • @mention notifications — notify users tagged in comments

Start with plain text. Rich text (bold, tables) layers on top — same OT model, richer op types.

The Concurrent Edit Problem

Initial document: "BC"   (version = 5)

User A: INSERT "A" at pos 0, clientVersion=5
User B: INSERT "D" at pos 2, clientVersion=5

Both ops arrive at the server simultaneously.
Server processes A first → canonical = "ABC", version=6

Now B's op arrives: { INSERT "D" at pos 2, clientVersion=5 }
clientVersion 5 < server version 6 → CONCURRENT OP DETECTED

Without OT:  apply "D" at pos 2 → "ADBC"  ✗ (B's intent lost)
With OT:     transform B's pos 2 → pos 3  ✓
             apply "D" at pos 3 → "ABCD"  ✓

OT transforms the position of a later-arriving op to account for ops that were applied first.

The key insight: ops carry a clientVersion. The server transforms any op whose version is stale.

Operational Transformation — Deep Dive

OT TRANSFORM RULES  (transforming op1 against already-applied op2):

op2 = INSERT at position P:
  op1 = INSERT:  pos > P  → pos++      (shift right)
                 pos < P  → unchanged
                 pos = P  → tie-break by userId (lower ID wins)
  op1 = DELETE:  pos >= P → pos++
                 pos < P  → unchanged

op2 = DELETE at position P:
  op1 = INSERT:  pos > P  → pos--      (shift left)
                 pos <= P → unchanged
  op1 = DELETE:  pos > P  → pos--
                 pos = P  → NOOP       (char already gone)
                 pos < P  → unchanged

NOOP = the character op1 wanted to delete was already deleted by op2. Safe to discard.

The server applies Alice's op, then transforms Bob's op against it before applying. Both edits survive.

CRDT — The Alternative Approach

Core insight: OT fails without total ordering. CRDT eliminates the ordering requirement entirely.

Instead of integer positions, use FRACTIONAL IDs:

Initial:  B = 0.50,  C = 0.75

Alice inserts "A" before B → assigns position 0.25
Bob   inserts "D" after  C → assigns position 0.875

Merge: sort all chars by fractional position:
  A=0.25, B=0.50, C=0.75, D=0.875  →  "ABCD"  ✓

No transformation needed — positions never collide!

Tombstones: Deleted characters keep their ID but are marked deleted. Prevents resurrection of content.

Used by: Figma, Notion, Atom (Teletype). Position IDs = unique (siteId, clock) tuples.

CRDT is commutative: ops can arrive in any order and still converge. Ideal for offline editing.

WebSocket Session Management

CONNECT:   ws://editor/{docId}?userId={uid}&token={jwt}
ON CONNECT: server sends { content, version: 42, activeUsers: [...] }

STICKY ROUTING (critical for OT):
  WS Gateway uses consistent hash on docId.
  All 100 editors of doc-123 → same WS Server 3.
  OT requires total ordering; sticky routing enforces it.

HEARTBEAT:
  Client → server PING every 30s.
  Server closes connection if no PING in 60s.
  Client detects closure, reconnects in <1s.

RECONNECT WITH OP REPLAY:
  Client sends: { reconnect, docId, lastSeenVersion: 41 }
  Server replies: all ops since version 41
  Client transforms buffered unACKed ops against them
  Client resubmits buffered ops

Client maintains a local queue of unACKed ops. On disconnect, it never loses in-flight edits.

Operation Pipeline — End to End

CLIENT SIDE:
  User keystroke
    → Apply op locally (immediate feedback)
    → Debounce 50ms (batch rapid keystrokes)
    → Compress: "HELLO" typed in 200ms = 1 INSERT op
    → Add to unACKed queue
    → Send via WebSocket: { type, pos, content, clientVersion }

SERVER SIDE:
  Receive op
    → Validate: auth, doc permissions, op size < 10KB
    → Rate-limit: max 100 ops/sec per (userId, docId)
    → Read version V from Redis
    → If op.clientVersion < V: transform op against ops v+1..V
    → Apply to Redis canonical copy
    → Increment Redis version counter
    → Publish to Kafka (BEFORE ACKing client)
    → Broadcast transformed op to all other editors
    → Send OP_ACK { opId, serverVersion } to sender

Kafka publish before ACK guarantees durability. If server crashes after publish, op is safe in Kafka.

Presence & Cursor Awareness

Redis keys per active document:
  doc:{docId}:cursors     HASH    userId → { line, col, color }
  doc:{docId}:active_users SET    userIds  (TTL 30s, refreshed on activity)

CURSOR UPDATES:
  Client sends CURSOR_MOVE every 300ms (only if moved)
  Server: SET doc:{docId}:cursors[userId] = { line, col }
  Server: broadcast CURSOR_UPDATE to all room members

COLOR ASSIGNMENT:
  On join: server assigns deterministic color from palette
  Hash(userId) % palette_size → consistent color per user

SERVER → CLIENT: CURSOR_UPDATE message
  { userId, cursor: { line: 4, col: 12 }, color: "#FF5733", name: "Alice" }

CURSOR OT:
  When op is applied, server also transforms all cursor positions.
  INSERT at pos 3: cursors at pos >= 3 shift right by 1.
  Delete at pos 3: cursors at pos > 3 shift left by 1.

Cursor TTL of 30s auto-removes stale cursors if a user disconnects without sending a leave event.

Offline Editing

WHILE OFFLINE:
  Ops queued in IndexedDB (browser persistent storage)
  User continues editing with full local responsiveness
  Ops tagged with { clientVersion, localTimestamp }

ON RECONNECT:
  1. Client sends: { reconnect, docId, baseVersion: 42 }
  2. Server replies: all ops applied since version 42
  3. Client transforms local op queue against server ops
     (same OT rules — positions may shift)
  4. Client resubmits transformed ops one by one

EXAMPLE — offline 10 minutes, 200 local ops:
  Server applied 450 ops while client was offline
  Client must transform all 200 local ops against 450 server ops
  OT: O(local × server) = 200 × 450 = 90,000 transforms
  At <1µs each → <100ms total. Seamless sync.

For heavy offline use, CRDT is superior — no transform needed, just merge. OT offline sync is O(n×m).

Version History

DOCUMENT LIFECYCLE:

COLD (no active editors):
  Latest major version lives only in S3

User opens doc → WARM:
  Redis: canonical copy loaded from S3, version=10
  activeUsers set created

EDITING → minor auto-saves every 10–20s:
  Read Redis canonical → PUT to S3 as v10.1, v10.2 ...

Last editor leaves → RECONCILIATION JOB:
  1. Fetch base version v10 from S3
  2. Fetch ALL ops since v10 from Cassandra
  3. Replay ops → final document state
  4. PUT to S3 as v11 (MAJOR version)
  5. Delete minor versions v10.1 … v10.N from S3
  6. Delete session ops from Cassandra
  7. Delete Redis canonical key → COLD again

Minor versions are scaffolding — deleted after reconciliation. 50 minors × 50KB × 1M sessions/day = 2.5TB/day savings.

Commenting System

COMMENT ANCHOR:
  { docId, startPos, endPos, anchorVersion, text, authorId }
  anchorVersion = document version when comment was created

PROBLEM: document changes after comment is created.
SOLUTION: OT-transform the anchor on every op.
  INSERT before startPos → startPos++, endPos++
  DELETE overlaps anchor range → mark comment as "orphaned"

COMMENT STATES:
  OPEN     → active, shown in margin
  RESOLVED → hidden by default, accessible via history
  ORPHANED → anchor text was deleted; shown as "Context deleted"

@MENTION NOTIFICATIONS:
  Parse comment text for @{userId} patterns
  Send notification via pub/sub → push notification + email
  Notification: { docId, commentId, mentionedBy, snippet }

REPLY THREADING:
  comments table: (docId, commentId, parentId nullable)
  Replies inherit anchor from parent comment

Scaling Strategy

WS GATEWAY — 300 servers @ 100K connections each = 30M connections
  Consistent hash on docId → sticky server assignment
  Rebalance: when server joins/leaves, rehash affected docs
  New WS server loads canonical from Redis, resumes ops

REDIS CLUSTER — 100 shards
  Partition: hash(docId) % 100 → shard assignment
  5M active docs × 50KB = 250GB → 2.5GB per shard (manageable)
  TTL: canonical key expires 30min post last edit

CASSANDRA — partition key = docId
  25M ops/sec across 5M docIds = no hot partition
  Write amplification: each Kafka consumer writes one partition

HOT DOCUMENT (100 concurrent editors):
  100 users × 5 ops/sec = 500 ops/sec to one WS server
  OT engine: each op transforms against recent ops
  Mitigation: cap at 100 editors; allocate high-CPU pod
  Google Jupiter protocol: regional OT shards, 100ms sync

Export Pipeline

USER CLICKS "Download as PDF":

  1. API call: POST /api/v1/documents/{id}/export
     { format: "PDF" | "DOCX" | "HTML" | "TXT" }

  2. Export job enqueued to async queue (SQS/Kafka)
     Response 202 Accepted: { jobId: "exp_abc123" }

  3. Export Worker picks up job:
     a. Fetch latest canonical from Redis (or S3 if cold)
     b. Render to HTML (internal format)
     c. PDF  → headless Chrome (Puppeteer) renders HTML → PDF
        DOCX → pandoc converts HTML → DOCX
        TXT  → strip tags, extract plain text

  4. Upload result to S3: exports/{docId}/{jobId}.pdf

  5. Notify client via WebSocket or polling:
     GET /api/v1/documents/{id}/export/{jobId}
     → { status: "DONE", downloadUrl: "https://..." }

  Export links expire in 1 hour (S3 pre-signed URL).

Senior Q&A 1

"50 users simultaneously type in a 10,000-line document. How does your system handle this without lag?"

50 users × 5 ops/sec = 250 ops/sec hitting one WS server.

BOTTLENECK 1 — OT transform queue:
  Each new op must transform against recent concurrent ops.
  At 250 ops/sec with 50 concurrent users, transform depth is low
  because each user's ops are independent (different paragraphs).
  Batch transformation: group ops by paragraph, parallelize.

BOTTLENECK 2 — Redis write rate:
  250 ops/sec = trivial for Redis (handles 1M+ ops/sec).

BOTTLENECK 3 — Broadcast fan-out:
  Each op broadcast to 49 other users = 250 × 49 = 12,250 sends/sec.
  Per-user send queue; slow clients buffered, not blocked.

MITIGATION — Collaborative region sharding:
  Split 10,000 lines into regions (0–2500, 2501–5000...).
  Each region has its own op queue.
  Only editors in the same region need to transform against each other.
  Cross-region ops: transform only if they collide (rare).

Senior Q&A 2

"User A edits offline for 2 hours. They reconnect with 200 ops. Server applied 800 ops meanwhile. How do you reconcile?"

ON RECONNECT:
  Client sends: { reconnect, docId, baseVersion: 42 }
  Server fetches: all 800 ops since version 42 from Cassandra

TRANSFORM PHASE:
  For each of client's 200 local ops:
    Transform against all 800 server ops = 200 × 800 = 160,000 transforms
    At <1µs per transform → <160ms total
  Result: 200 transformed ops aligned to server version 842

CONFLICT HANDLING:
  INSERT-INSERT: positions shifted — handled by OT rules
  DELETE of already-deleted char: NOOP — character gone, skip
  Paradox: client deleted text that server also heavily edited?
    OT handles character by character. Each char has a definitive fate.

EDGE CASE — client offline for 2+ hours:
  Cassandra ops retention: only kept during active session.
  If reconciliation job ran (all users left), ops are deleted.
  Solution: keep ops for 24h; or use base snapshot + CRDT-style merge.
  Production recommendation: switch to CRDT for offline > session length.

Senior Q&A 3

"Implement undo/redo in a collaborative environment where other users have also edited since your last action."

NAIVE APPROACH — fails in collaboration:
  "Undo" = reverse my last op. But other users edited after me.
  Reversing my op at the old position corrupts others' text.

CORRECT APPROACH — Selective Undo with OT:
  Each user maintains a personal undo stack of their own ops.
  When user presses Ctrl+Z:
    1. Take their last op from personal undo stack
    2. Invert it: INSERT "A" at 5 → DELETE 1 char at 5
    3. Transform the inverted op against ALL ops applied after it
       (by anyone, including other users)
    4. Submit transformed inverse op as a new op

EXAMPLE:
  Alice: INSERT "X" at pos 5   → version 10
  Bob:   INSERT "Y" at pos 3   → version 11
  Alice undoes: inverse = DELETE at pos 5
    Transform DELETE(5) against INSERT(3): pos 5 → pos 6
    Submit: DELETE at pos 6  → removes Alice's "X" correctly

REDO:
  Redo = re-apply the undone op, transform against current state.
  Redo stack cleared if user makes a new edit (standard convention).
