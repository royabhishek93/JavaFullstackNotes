## THE PROBLEM (0:30–2:00)
"Think of your desk as your cache. You've got space for ten folders, but the filing cabinet behind you has a hundred. You keep the most useful ten on the desk. The moment the desk is full and you need an eleventh folder, one has to go — which one? LRU, Least Recently Used, says: remove whatever you haven't touched in the longest time — 'I haven't opened this since March, probably safe to file it away.' Recency as a stand-in for future usefulness. LFU, Least Frequently Used, says: remove whatever's been opened the fewest times total, period — 'I've opened this folder twice ever, versus that one five hundred times.' Frequency as the stand-in instead. TTL, Time To Live, says every folder literally has an expiry date stamped on it — expired folders go regardless of how often or how recently you touched them, because the data itself has a known freshness window, like a session token or an API response. And then there's Random — just grab any folder and toss it — which sounds dumb but is surprisingly close to LRU in performance if your access pattern is roughly uniform, with zero bookkeeping overhead. The real question was never 'which algorithm is best' — it's which one matches YOUR access pattern. And Redis doesn't force you to pick just one philosophy — it gives you eight concrete maxmemory-policy settings built from these four ideas, and choosing the wrong one can tank your hit rate or silently evict exactly the data you needed most."

[Screen cue: Desk-with-ten-folders animation, one new folder arriving, four candidate folders highlighted labeled LRU / LFU / TTL / Random.]

## THE SOLUTION (2:00–5:00)
"Let's get concrete. LRU under the hood is a doubly-linked list plus a hash map — head of the list is most-recently-used, tail is least-recently-used. Access a key, it jumps to the head. Cache full, you evict the tail. That's O(1) get, O(1) put, O(1) eviction. Redis doesn't actually maintain a perfect linked list, though — that costs memory at scale — so it approximates: it samples five random keys by default and evicts whichever of those five has gone the longest without being touched. Not exact LRU, but close enough, and way cheaper. LFU instead attaches a counter to every key — but not a plain counter, an eight-bit LOGARITHMIC counter that saturates at 255. A celebrity profile hit ten thousand times an hour saturates near 255. A one-time report accessed once sits at 1. On eviction, Redis kills the lowest counter first. And critically, that counter DECAYS — every lfu-decay-time minutes, by default just one minute, counters get halved, so something that was trending last week but hasn't been touched today gradually cools off instead of squatting in your cache forever. Now here's where Redis actually gives you eight distinct policies, not just 'LRU or LFU': noeviction is the default — and it REJECTS every write once memory is full, clients get OOM errors, use it only when the cache must never silently lose data. allkeys-lru evicts any key by recency — general purpose, works for most caching. volatile-lru does the same but ONLY considers keys that have a TTL set — keys with no TTL are permanent and never touched. allkeys-lfu evicts any key by frequency — best when a small hot set is getting almost all the traffic. volatile-lfu is the TTL-only version of that. allkeys-random and volatile-random just grab randomly, fastest option, great for uniform access. And volatile-ttl evicts whichever TTL-tagged key has the SMALLEST remaining time left — it's going to expire anyway, so kick it out now instead of waiting. Eight policies, four philosophies, and the production configuration is three lines: maxmemory 8gb, maxmemory-policy allkeys-lru, and if you're using LFU, tune lfu-log-factor and lfu-decay-time to control how fast the counter grows and how fast it cools down."

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"Here's the trap that catches almost every engineer who assumes LRU is always the safe default. Picture two keys. Key A is a celebrity profile — ten thousand accesses in the past hour, but the last one happened two minutes ago because nobody's requested it in the last two minutes. Key B is a one-time report, accessed exactly once, ever, but that single access happened one minute ago. Pure LRU logic says: A was idle for two minutes, B was idle for only one minute, so A is 'older' — evict A. That's dead wrong. You just evicted your most valuable, most-requested key, and kept a report nobody will ever look at again, purely because of an accident of timing. LFU gets this exactly right — A's frequency counter is near-saturated at 255, B's counter is sitting at 1, so B gets evicted instead, exactly as it should. The lesson: LRU is a great default for UNIFORM access patterns, but the moment your traffic is skewed — a power-law distribution where one percent of keys eat ninety-nine percent of the traffic — LRU will actively work against you. Second trap: people misread TTL equals zero as 'expire immediately.' It doesn't — TTL zero, or more precisely no TTL set at all, means the key lives forever until it's evicted by policy, not that it expires instantly. If you actually want a key to never be evicted — genuine source-of-truth data sitting inside a Redis instance that's also used as a cache — the fix isn't to just avoid setting a TTL and use allkeys-lru, because allkeys-lru will still evict ANY key including that one under memory pressure. You need volatile-lru specifically, and you deliberately do NOT set a TTL on that source-of-truth key — under volatile-lru, keys with no TTL are never eviction candidates at all. Third trap: not distinguishing 'evictions are happening' from 'evictions are fine.' Any nonzero evicted_keys counter — you check it with redis-cli INFO stats, grep evicted_keys — in a production cache, outside of a deliberate volatile-ttl-plus-noeviction combo for something like leaderboard safety, means your cache is either undersized for peak load or your TTLs are too aggressive — it is not a normal steady state, it's a signal to act. Pair that with redis-cli OBJECT FREQ on a key to see its live LFU counter, OBJECT IDLETIME to see its LRU idle seconds, and redis-cli --bigkeys to find your actual memory hogs before you start guessing. And while you're in there, check mem_fragmentation_ratio from INFO memory — anything above one-point-five means fragmentation is eating memory you think is free, and a restart or bumping maxmemory won't fix the root cause alone. And the fourth trap — teams tune maxmemory-samples once at five, the Redis default, and never revisit it. Five random samples for LRU or LFU approximation is fine for low-stakes caching, but if precision actually matters — you're deciding which of your highest-value keys survive — bumping maxmemory-samples to ten gets you meaningfully closer to true LRU or LFU ordering for a small, usually negligible CPU cost."

## REAL WORLD (8:00–9:30)
"Picture Swiggy during lunch-hour rush — restaurant and menu cache is exactly the celebrity-profile problem in a food-delivery costume. A handful of trending restaurants near office parks get slammed with thousands of menu-cache reads in twenty minutes, while thousands of other restaurant caches barely get touched. Run allkeys-lru there and the trending restaurant — accessed constantly but with a two-minute gap since the last read because of request bursts — can get evicted in favor of some restaurant that was touched once, ninety seconds ago. Switching that hot-path cache to allkeys-lfu keeps the actually-popular restaurants warm regardless of timing accidents. Now think about PhonePe or Paytm running rate-limiter counters in Redis for UPI transaction throttling — those counters are inherently short-lived, each one tagged with a TTL matching its rate-limit window, say sixty seconds. Under memory pressure, volatile-ttl is the correct policy there — it evicts whichever counter is closest to expiring anyway, since that data is about to become useless in a few seconds regardless. And picture a Flipkart-style flash sale — a handful of flash-sale SKUs get accessed hundreds of thousands of times in the first five minutes while the long tail of the catalog barely gets touched — that's a textbook allkeys-lfu candidate, because the alternative, allkeys-lru, risks evicting the flash-sale product's cache entry the instant there's even a short gap between bursts of traffic, right when you can least afford a cache miss hammering the database."
