# CRDTs: Conflict-Free Replicated Data Types — YouTube Script

## HOOK (0:00–0:30)
"Two people edit the same document while one of them is on a flight with no wifi. No server, no internet, no way to referee anything — and yet, the moment that flight lands and both devices reconnect, every edit merges perfectly, with zero conflicts and zero data loss. That's not magic — it's a data structure engineered so that merging two divergent copies is a mathematical guarantee, not a best effort. Today I'm breaking down CRDTs — Conflict-free Replicated Data Types — the technology behind Figma's multiplayer canvas and every serious offline-first app, plus the exact trap that quietly makes production CRDT documents balloon in memory until nobody wants to open them."

## THE PROBLEM (0:30–2:00)
"Picture two people each keeping their own grocery list on their own notepad, no phones, shopping in different aisles of the same store, planning to combine lists later. If both of them only ever ADD items — never cross anything out — combining the lists is trivial: just union them together. Order doesn't matter, duplicates don't matter, you can merge in any order any number of times and always land on the same result. Now suppose one person crosses an item off their OWN copy. If you naively just union the two lists, that crossed-off item can reappear from the other person's uncrossed copy — you just resurrected a deleted item. So instead of erasing the line, they leave a tombstone — 'milk, bought' — instead of deleting it outright. Now merging is safe again, because whichever copy has the tombstone, the tombstone wins. That tiny notepad trick is the entire idea behind a CRDT: design your data so that merging two replicas is commutative, associative, and idempotent — order doesn't matter, grouping doesn't matter, and merging the same update twice changes nothing. Get those three properties right, and you can replicate to as many nodes as you want, let them go offline for as long as you want, and they are mathematically guaranteed to converge — with zero central coordinator and zero locking."

[Screen cue: Animated grocery notepad — two lists merging with a naive union first (item reappears, red X), then the tombstone version merging cleanly (green check).]

## THE SOLUTION (2:00–5:00)
"Let's make this concrete with the simplest CRDT that exists: the G-Counter, a grow-only counter, like a distributed 'like' count spread across three datacenter replicas with zero coordination. The trick is each replica only ever writes to its OWN slot in a shared map — replica A tracks {A: count}, replica B tracks {B: count}, replica C tracks {C: count}. User likes a post on replica A — A increments its own slot to 1. Replica B gets three likes locally — B's slot goes to 3. Replica C gets one like — C's slot goes to 1. Nobody talked to anybody yet. Now the network partition heals, and the replicas gossip their state to each other. The merge function is beautifully simple: take the element-wise maximum of every key. Merge A's {A:1} with B's {B:3} and you get {A:1, B:3}. Merge that with C's {C:1} and you get {A:1, B:3, C:1}. The total like count is just the sum of every slot — five. And here's the key insight: because the merge function is max, it's commutative, associative, and idempotent automatically — you can merge in any order, merge the same state twice, and never get a wrong answer. Why not just use one shared integer with plus-one increments instead of per-replica slots? Because two replicas incrementing the SAME shared counter concurrently is exactly the lost-update race condition — you'd need locks or compare-and-swap across a network partition, which defeats the entire point of offline-tolerant replication. Splitting the counter per replica-origin sidesteps the race completely. Now scale that idea up to actual text. A document isn't a number, it's an ORDERED sequence of characters that can be inserted or deleted anywhere — you can't just union characters, you need stable ordering with no central 'position 5' concept, because position 5 means something different on every replica mid-edit. That's what RGA — Replicated Growable Array — solves: every character gets a globally unique ID made of a replica ID plus a logical clock, plus a reference to the character it was inserted after. Two offline replicas can both insert 'after the same character' concurrently, and when they reconnect and exchange those inserted nodes, a fixed, universally-agreed tie-break rule — higher logical clock wins, ties broken by replica ID — lets every single replica independently compute the exact same final order, with nobody needing to contact anybody at insert time."

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"Here's the trap that catches almost every team building their first CRDT text editor: tombstones. When you delete a character in RGA, you do NOT remove the node — you just flag it as deleted, because a concurrently-arriving remote insert might still reference 'insert after this node' and needs that node to still exist for ordering purposes. That sounds harmless until you do the math on a real editing session: a ten-thousand-character document that's been through fifty thousand total keystrokes — including all the deletes and retypes — can end up carrying forty thousand-plus tombstoned nodes, completely invisible to the user, but still sitting in memory and still getting transmitted and merged on every single sync. And the per-character overhead is brutal — replica ID, logical clock, parent reference, tombstone flag — that's thirty-three-plus bytes of bookkeeping PER CHARACTER, dwarfing the one or two bytes of actual text content. Production libraries like Automerge and Yjs solve this with garbage collection: once you can PROVE, using version vectors, that every single replica has already seen a tombstoned node, it's safe to physically compact it out of the structure — Yjs specifically merges contiguous surviving characters back into single string runs and prunes long-dead tombstone runs once causal stability is confirmed. Skip that GC pass, and memory grows unbounded over a long-lived document's history — this is genuinely the single biggest practical engineering challenge in production CRDT editors. Second trap: picking the wrong sync model for your bandwidth budget. CvRDT, state-based CRDTs, ship the FULL current state on every sync — dead simple to reason about, but for a five-thousand-character document with real edit history, that's fifty to a hundred fifty kilobytes uncompressed per sync, which is disastrous if you naively do that on every keystroke. CmRDT, operation-based CRDTs, ship individual operations instead — much lighter, forty to sixty bytes per character insert — but now your transport layer MUST guarantee reliable at-least-once delivery of every operation, because duplicates are harmless thanks to idempotency, but a DROPPED operation means a permanently missing edit with no way to detect it. Most production systems don't pick one — they're hybrid: operation-based for live real-time sync, with periodic state-based snapshots for fast new-client bootstrap and for that GC compaction pass. Third trap: reaching for a CRDT when you didn't need one. If your data model is highly relational, cross-referencing many entities with strict invariants — think a bank balance that must never be read in a transiently-inconsistent state — CRDTs are the wrong tool entirely, because they buy you eventual consistency, not strong consistency, and no amount of clever merge logic changes that fundamental guarantee."

## REAL WORLD (8:00–9:30)
"Figma's engineering blog has talked publicly about this — their multiplayer canvas uses a custom CRDT-like system, not textbook RGA, because vector shapes and their properties merge more like independent last-writer-wins fields per property than like one linear text sequence, which is a good reminder that 'CRDT' is a family of techniques, not one fixed algorithm you copy-paste. Now think about how this plays out at Indian scale. Picture a Swiggy delivery-partner app in a low-network pocket — a partner marks three orders 'picked up' and 'delivered' while stuck in a basement parking lot with zero bars, then walks out and reconnects. If the app used naive last-write-wins syncing, whichever update reaches the server last silently overwrites the others, and a genuinely delivered order can flip back to 'in transit.' A CRDT-style per-order status set, where 'delivered' and 'picked-up' events are additive facts rather than overwrites, converges correctly regardless of which update the server sees first — no lost deliveries, no confused restaurant dashboards. Now picture Zomato's restaurant-partner app for menu and price updates — a restaurant owner edits their menu offline on a spotty mobile connection while also updating item counts from a tablet in the kitchen at the same time. Treating each menu field as a CRDT register with a logical clock for tie-breaking means both edits survive the merge deterministically, instead of one device's update silently vanishing because it happened to sync a few seconds later. And picture PhonePe or Paytm's local transaction-history cache on the user's phone — entries getting added from multiple app sessions across devices need to merge into one clean, deduplicated history the moment connectivity returns, which is exactly the grow-only-set-plus-tombstone pattern from the G-Counter and RGA ideas, just applied to a list of transaction records instead of characters."
