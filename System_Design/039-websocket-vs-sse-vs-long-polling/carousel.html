Solution 1

Long Polling

GET /events?lastId=42hold... (20s)
event arrivesrespond id=43
GET /events?lastId=43hold again...

Latency: 1–5s  |  Overhead: ~500B headers/req

1 thread per waiting connection (blocking model) · works through every firewall

Solution 2

Server-Sent Events (SSE)

Client
text/event-stream (stays open)
Server

t=1s data:{"score":9821} → t=3s data:{"rank":1} → t=5s ...

Latency: <100ms  |  one-way, server → client only

Auto-reconnect built into browser's EventSource · multiplexes over HTTP/2

4 / 10
Solution 3

WebSocket

Client
HTTP 101 Upgrade → raw TCP frames
Server

Latency: <50ms  |  Overhead: ~2B/frame

Bidirectional — both sides send anytime · no built-in reconnect · some firewalls block the upgrade

5 / 10
Where Each Fits

Match the direction, match the protocol

● Chat (WhatsApp) — WebSocket: send + receive, same connection

● Uber driver tracking — WebSocket: GPS out every 3s + dispatch in

● Leaderboard — SSE: server pushes rank, no data sent back

● Google Docs editor — WebSocket: keystrokes + broadcasts, <100ms

● Stock Broker — WebSocket: orders out + bid/ask stream every 100ms

6 / 10
Deep Dive — Traps

Where engineers get it wrong

❶ Defaulting to WebSocket "because real-time" — SSE has no manual reconnect burden

❷ Ignoring corporate firewalls that block the WS upgrade handshake

❸ Forgetting sticky sessions — SSE/WS need LB affinity, long polling doesn't

❹ Long polling under 5s update frequency — burns threads + bandwidth

❺ Expecting SSE to receive client data — it's one-way, period

❻ Missing SSE's free HTTP/2 multiplexing advantage over WebSocket
