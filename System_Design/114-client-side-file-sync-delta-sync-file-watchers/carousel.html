SOLUTION · ROLLING HASH

Content-defined chunking fixes it

Boundary = local byte content, not position

…xyz
BOUNDARY
def…
Xxyz
BOUNDARY
def…

Rolling hash re-finds the SAME boundary pattern right after "xyz" — everything after re-aligns.

Rabin fingerprint rule: slide a 48-byte window, boundary when
hash(window) & bitmask == target

13-bit mask → 213 = ~8KB average chunk size. Min-size guard: 2KB (avoids pathological tiny chunks).

Same trick as rsync's rolling checksum, restic, BorgBackup.

Client-Side File Sync6 / 10
TRAPS · WATCHER RELIABILITY

Watchers fail silently. Plan for it.

Trap: watch-descriptor limit

/proc/sys/fs/inotify/max_user_watches default = 8,192 directories. Sync clients with 100K+ files must raise it via sysctl or watches silently fail to register.

Trap: event queue OVERFLOW

A git checkout touching 50,000 files in ~1 second overflows the kernel queue. Events are dropped — no error, no crash. Only fix: treat OVERFLOW as "trigger full rescan now."

Trap: watcher = only while process is alive

Full reconciliation scan required at every startup:

100K files, mostly unchanged: 15–45s
100K files, 5K changed: 3–8 min

CHEAT SHEET · INTERVIEW ANSWER

Watcher + rolling hash + version vectors

✓ Use full delta sync when files are large, bandwidth is constrained, and you control a persistent desktop client.

✗ Skip it when files are small, it's a stateless web upload form, or files change completely on every edit anyway.

"For detection, I use the OS's native file-watching API rather than polling... For efficient sync of large files, I use content-defined chunking with a rolling hash... fixed-offset chunking breaks catastrophically on insertions... The operational concern I'd flag is watcher reliability — I always run a full reconciliation scan once at client startup regardless of watcher health, and I monitor for the OVERFLOW event to trigger an immediate full-folder rescan."
