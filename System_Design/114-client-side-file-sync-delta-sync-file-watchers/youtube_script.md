## THE PROBLEM (0:30–2:00)
"So there are actually TWO separate problems bundled into 'file sync,' and if you don't separate them in your head, you'll design this wrong.

Problem one: how does the sync client even KNOW a file changed, the instant it happens? The naive answer is polling — walk the entire folder tree on a timer, check every file's modification time, compare it to what you saw last time. Sounds fine until you picture a laptop with 200,000 files in its sync folder. Now you're re-stat-ing 200,000 files over and over, and your change-detection latency is capped at your poll interval — if you poll every 30 seconds, you find out about a change up to 30 seconds late. That's slow, it's wasteful on CPU and disk I/O, and it does not scale.

Problem two, and this is the juicier one: even once you know a file changed, how do you avoid re-uploading the WHOLE thing? A 2GB video project file gets one small edit — do you really ship all 2 gigabytes back to the cloud? That's the delta sync problem, and it's surprisingly tricky to get right, because the obvious first attempt — splitting the file into fixed-size blocks — actually breaks catastrophically the moment someone inserts or deletes a single byte, which I'll show you in a second.

And there's a third problem lurking underneath both of these: what happens when the SAME file gets edited on two different devices while both are offline? No server-side referee was watching. Both edits are equally valid. Somebody has to decide what 'correct' even means here."

[Screen cue: Whiteboard-style diagram — three boxes labeled "1. Detect the change" / "2. Sync only what changed" / "3. Resolve conflicting edits," connected by arrows into a pipeline, with a red "?" over each box.]

## THE SOLUTION (2:00–5:00)
"Let's solve all three, in order.

**Detection — kill the polling loop.** Every major OS ships a kernel-level facility for this. Linux has `inotify`. macOS has `FSEvents`. Windows has `ReadDirectoryChangesW`. You register 'watch this folder' exactly once, and the kernel proactively PUSHES you a notification the instant a file is created, modified, or deleted. No loop, no spinning, no asking twice. That push typically arrives in under 10 milliseconds from the actual write() syscall. The sync client then debounces those events over roughly 200 to 500 milliseconds — because a single 'Save' in your word processor might fire three or four rapid write syscalls, and you want ONE sync pass out of that, not four.

**Delta sync — don't re-upload the whole file.** Once you know a file changed, split it into chunks and diff those chunks against what's already uploaded. But — and this is the part that trips people up — you cannot split at fixed byte offsets. Imagine four-byte fixed chunks: AAAA, BBBB, CCCC, DDDD. Now insert ONE byte at the very start. Every single chunk boundary shifts by one byte. Every chunk now looks completely different from before, even though nothing meaningful actually changed. Fixed-offset chunking gives you ZERO benefit for insertions or deletions — which, by the way, is basically every real-world text edit.

The fix is content-defined chunking using a rolling hash — Rabin fingerprinting is the classic algorithm. You slide a window, say 48 bytes, across the file, computing a rolling hash at every single byte offset. You declare a chunk boundary whenever that hash, masked against some bit pattern, hits a target value — for example, masking the low 13 bits gives you an average chunk size of 2 to the 13th power, which is 8,192 bytes, about 8KB. Because the boundary is determined by the actual BYTE CONTENT nearby, not an absolute position in the file, inserting a byte near the start doesn't break anything downstream — the rolling hash re-finds the exact same boundary pattern shortly after the insertion point, and everything after that re-aligns perfectly. Only the chunk or two actually touched by your edit look different. This is exactly how rsync's rolling checksum works, and it's the same core trick behind backup tools like restic and BorgBackup.

Then each chunk gets content-addressed — its own hash becomes its storage address — which gives you free deduplication across your ENTIRE file set, not just within one file. Two different documents sharing an identical paragraph? Same chunk, stored once.

**Conflict resolution — version vectors, never wall-clock time.** Say your laptop goes into airplane mode, you edit report.pdf, its version vector bumps to laptop:4, phone:2. Meanwhile your phone was ALSO offline on a different flight, and you edited the same file there — phone:3. Both devices come back online. The server compares vectors: if one vector is a strict superset of the other, that's a clean linear update, no conflict, just accept it. But if neither vector fully dominates the other — like laptop:4,phone:2 versus laptop:3,phone:3 — that's a genuine, unavoidable conflict. Two humans made two different valid edits with no way to order them causally. The fix is NOT comparing last-modified timestamps, because clocks lie — a device with a clock ten minutes fast wins every timestamp comparison regardless of which edit actually happened first in reality. Version vectors track causality — who saw what — not wall-clock time."

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"Now, here's the thing — this is where most 'I read about inotify once' answers fall apart in an interview, because watchers are NOT bulletproof, and if you don't know their failure modes, your design has a silent data-loss hole in it.

Trap number one: watch descriptor exhaustion. Linux's `inotify` has a system-wide limit on how many directories you can watch — the default is 8,192, controlled by `/proc/sys/fs/inotify/max_user_watches`. A sync client managing 100,000+ files across a deep folder tree will blow straight through that default unless you explicitly raise it via sysctl. Miss this, and your watcher just silently fails to register on directories past the limit — no crash, no obvious error, just... changes that never get detected.

Trap number two, and this is the nastier one: kernel event queue overflow. Picture a `git checkout` that touches 50,000 files in about a second. The kernel's watch event queue has a fixed depth, and when changes come in faster than your client drains them, the kernel fires a special OVERFLOW event and then just... drops everything after that. Your watcher doesn't error loudly. It doesn't crash. It just silently stops telling you about changes. If your code treats OVERFLOW like any other event — logs it and moves on — you now have files that are out of sync and nobody knows it. The only correct response to an OVERFLOW event is to immediately trigger a full reconciliation rescan of that folder tree.

Trap number three: treating the watcher as your ONLY source of truth. The watcher only fires while the client PROCESS is alive. Close your laptop lid, quit the app, and every single change made during that window is invisible to the watcher forever — there's no catch-up mechanism built into inotify itself. That's why every serious sync client runs a full manifest reconciliation scan once at startup, no matter how healthy the watcher looked last time. And that reconciliation scan has real, measurable costs — a full rescan of 100,000 mostly-unchanged files takes roughly 15 to 45 seconds, because even 'skipping' a file means at least a stat() syscall to check mtime and size. If 5,000 of those files genuinely changed while you were offline, budget 3 to 8 minutes for the re-chunking and re-hashing work on top.

Trap number four: fixed-offset chunking, which I mentioned already, but let me put a number on it — for the single most common edit pattern in the real world, typing more text into a document, fixed-offset chunking provides ZERO delta-sync benefit. You still re-upload the entire file past the insertion point, because every downstream chunk boundary shifted. If you ship this and call it 'delta sync,' you have built a bandwidth-saving feature that saves zero bandwidth for the majority of real edits.

Trap number five: last-write-wins for conflicts. It's tempting, it's one line of code — 'newer timestamp wins, overwrite the other' — and it is how you quietly destroy a user's work and torch their trust in your product forever. The correct move, once you detect a genuine divergent conflict via version vectors, is to keep BOTH files — sync the original under its normal name, and sync the conflicting edit under something like 'report (conflicted copy from Bob's laptop, 2024-06-01).txt' — fully synced to both devices, and let the human sort it out."

## REAL WORLD (8:00–9:30)
"Let's ground this in numbers you'd actually see in production.

Take a hypothetical, but entirely realistic, delivery-partner app — think Swiggy or Zomato style — where delivery partners upload proof-of-delivery photos and offline order logs at the end of a shift, often over patchy 3G in areas with weak towers. If that app naively re-uploaded the entire local SQLite log file every time a new delivery got appended, you'd be shipping megabytes for a few-hundred-byte addition, on a data plan where every megabyte costs the partner money. Apply content-defined chunking to that log file instead, and each sync only pushes the newly appended chunk — turning a multi-megabyte upload into a sub-100KB one, which on a 2G/3G uplink is the difference between a 2-second sync and a 30-second one that drains battery and burns data.

Now take a fintech merchant app — a PhonePe or Paytm style offline billing scenario — where a shopkeeper's device goes offline mid-day, racks up dozens of local transactions, and a SECOND device at the same shop also logs transactions offline. When both come back online, you cannot use 'last write wins' — that would silently drop real transactions with real money attached. This is exactly the version-vector conflict scenario from the diagram: the server has to detect that both device logs diverged concurrently, refuse to silently pick one, and reconcile or flag both transaction sets for review, because in payments, a 'lost edit' is a lost transaction, and that's an incident, not a UX inconvenience.

And for the watcher-scale numbers — remember the 8,192 default inotify watch limit? A Flipkart-style internal build/CI syncing tool watching a monorepo with 100,000+ files across tens of thousands of directories would hit that default limit almost immediately and need the sysctl bump to `max_user_watches` before it could even function — this is a real, well-documented operational gotcha for any engineering team running Linux-based file watchers at scale, not just consumer sync apps."
