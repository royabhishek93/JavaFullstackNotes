The Solution · Slide 3

Blue-Green: instant switch, instant rollback

Cutover = flip LB target. Rollback = flip it back. No redeploy.

Cost: 2x steady-state capacity during the transition window — best for infrequent, high-risk releases.

The Solution · Slide 6

Expand-Contract: zero-downtime schema change

1EXPAND — add username, keep user_name. App writes both, reads old.
2BACKFILL — copy old → new in a throttled batch job (avoid replication lag spikes).
3MIGRATE READS — app reads new column, still writes both. Verify.
4CONTRACT — write only new column, then DROP COLUMN user_name.

Every intermediate step is valid for both old and new code running concurrently during a rolling deploy — that's what makes it zero-downtime.

Never couple a schema change to a code rollout
Deep Dive · Slide 7

Chaos Engineering: break it on purpose

Hypothesis: payment-service fails over to a secondary AZ within 30s, no customer-visible errors.

AZ-1: pods killed
AZ-2: takes over

Blast radius capped <5% of production traffic, automated abort if customer-facing errors cross a threshold.

A chaos experiment that FAILS is more valuable — it found the gap before a real outage did.

Netflix Chaos Monkey — hospital-generator discipline
Deep Dive · Slide 8

Readiness vs. Liveness — don't mix these up

Readiness — "ready for traffic now?" Fail → pulled from LB pool. Gates canary/rolling promotion.
Liveness — "still alive?" Fail → pod killed & restarted. Self-healing, not routing.

Interview Answer · Slide 10

Decision tree & the exact quote to give

Schema change involved?
→ Use expand-contract, independent of code rollout.
High-risk, infrequent release?
→ Blue-green: instant switch, accept 2x cutover cost.
Frequent / revenue-critical release?
→ Canary: automated metric-gated promotion.
Need to validate resilience claims?
→ Chaos experiment, bounded blast radius.
