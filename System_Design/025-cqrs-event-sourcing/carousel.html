CQRS & Event Sourcing

The Hook — History Lost Forever

UPDATE

Traditional databases lose history on every UPDATE.

Order 42: When was it placed?
Answer: No idea — timestamp overwritten.

UPDATE orders SET status='SHIPPED'...
→ Placement timestamp: GONE

Financial systems can't afford this. That's why they never UPDATE.

The Problem: One Model Can't Do Both

CQRS Bank Counter Analogy

Counter A
Teller Window
Counter B
Customer Service

Counter A (Write): Validates transactions, applies business rules, ACID guarantees. Normalized data. Slow joins OK.

Counter B (Read): Answers balance queries instantly. Denormalized snapshot. Pre-aggregated. No joins.

They don't share the same queue. That's CQRS — separate write and read models optimized for different jobs.

Event Sourcing

Immutable Event Log vs Mutable State

Traditional (mutable state):

orders: {id: 42, status: "SHIPPED", total: 198}
✕ Can't answer: "When was order 42 placed?"

Event Sourcing (immutable log):

seq=1: OrderPlaced {orderId:42, total:198, ts:...}
seq=2: PaymentCharged {orderId:42, amount:198}
seq=3: OrderShipped {carrier:"UPS", tracking:...}
seq=4: OrderDelivered {deliveredAt:...}

✓ Current state = replay events 1..4. Complete audit trail. Time-travel queries. Never delete.

Snapshot Optimization

Solving the 2000 Events Problem

Problem: Order 42 has 2000 events (active since 2019). Replaying 2000 events on every read is slow.

Solution: Snapshot every 100 events

snapshot_store:
orderId: 42, seq: 1000, state: {status: SHIPPED, ...}
orderId: 42, seq: 1100, state: {status: DELIVERED, ...}

To get current state:

  1. Load latest snapshot (seq=1100) — 1 row read
  2. Replay events 1101..current — at most 100 events

Total: snapshot + 0-100 events, not 2000 events

Event Store Options

Kafka vs EventStoreDB vs PostgreSQL

Store Best For Limitation
Kafka Event streaming, retention forever, horizontal scale Can't query "get all events for orderId=42" efficiently
EventStoreDB Per-stream storage, optimistic concurrency, built-in projections Best for <1B events total
PostgreSQL Simple, battle-tested, UNIQUE(aggregate_id, version) for locking Single-node write bottleneck

Common pattern: Kafka for event streaming + PostgreSQL for per-aggregate event lookup.

Eventual Consistency

The 110ms Problem + 4 Solutions

TimeEvent
T+0msUser clicks "Place Order"

T+10msRead model NOT updated yet → order missing!

Solutions:

  • Optimistic UI: Show order from command response
  • Read-your-writes: Route user to write DB for 500ms
  • Event-driven UI: WebSocket push when read model updates
  • Accept it: 100ms lag is fine for most cases

Decision Framework

When to Use CQRS / Event Sourcing

Scenario Pattern Why
Simple CRUD app, <100K records Plain MVC + ORM CQRS overhead not worth it
Read-heavy, complex queries (dashboards) CQRS without Event Sourcing Separate read model, store current state
Audit trail required (finance, healthcare) Event Sourcing Immutable log is the requirement
Complex domain logic, multiple aggregates CQRS + Event Sourcing Bounded contexts, event-driven integration
Regulatory compliance (SEC, SEBI, GDPR) Event Sourcing mandatory Cannot delete history
Microservices integration Event Sourcing + Kafka Events are the integration contract

Real-World Examples

Where This Pattern Appears

System Why Event Sourcing / CQRS
Payment Ledger Every debit/credit stored as immutable event. Regulators audit complete history. Balance = sum of events.
E-Commerce CQRS: write (PostgreSQL, ACID) vs read (Elasticsearch). Black Friday queries don't compete with order writes.
Leaderboard Event log holds score history. "Show Alice's progression" = replay score events. Current standings in Redis ZSET.
Stock Broker SEC/SEBI require full audit. Every order, execution, cancellation = immutable event. Read models: open positions, P&L, tax lots.

Common pattern: Axon Framework (Java) with @Aggregate, @CommandHandler, @EventSourcingHandler annotations for write side. Event consumers update read models.

Decision Tree & Interview Answer

The Architect's One-Liner

Quick decision tree:

  • Need audit trail or time-travel? → Event Sourcing
  • Read/write ratio > 10:1? → CQRS
  • Regulatory compliance? → Event Sourcing mandatory
  • Complex domain + microservices? → Both (CQRS + Event Sourcing)
  • Simple CRUD? → Neither (plain MVC)
"Event Sourcing treats the database as an append-only ledger of what happened — never what 'currently is' — which gives you a complete audit trail, time-travel queries, and the ability to rebuild any read model from scratch; CQRS then separates who writes to that ledger from who reads from its projections, letting each side scale and evolve independently."

Complexity: High. Benefit: High. When justified: Payments, trading, healthcare, finance.
