## THE PROBLEM (0:30–2:00)
"Think about it this way — large systems don't read and write from the same database server. Writes go to a primary. Reads get spread across replicas — copies of the primary that stay in sync by replaying a change log. The catch is that this replication is asynchronous by default: the primary says 'write successful' the instant it commits locally, without waiting for any replica to catch up. Replicas usually catch up in milliseconds, but under load, that lag can stretch to hundreds of milliseconds or even seconds. Your profile page request landed on a replica that hadn't received your photo yet — it served you a 500-millisecond-old snapshot. This specific flavor of stale read has a name: read-your-own-writes, and whether you need to fix it depends entirely on the feature. Netflix's continue-watching row can be thirty seconds stale and nobody notices. A hotel booking that doesn't show up immediately after payment is a real, reportable bug."

[Screen cue: Draw the primary-to-replica replication diagram with three replicas each showing a different lag value — 10ms, 150ms, 800ms.]

## THE SOLUTION (2:00–5:00)
"Now watch the four fixes, from simplest to most precise. Solution one: read from primary after write. For a few seconds after any write, route that specific user's reads back to the primary instead of a replica, using a short-lived cookie or session flag. Dead simple, and fine for most systems, since writes are relatively rare per user. Solution two: monotonic reads, also called sticky routing. Instead of hitting a random replica each time, a user always reads from the SAME replica, based on a hash of their user ID. This guarantees you never see data go backward in time on refresh, though it doesn't eliminate the initial lag right after a write. Solution three, the most precise: LSN-based routing. Every write returns a log sequence number — a monotonically increasing position in the replication stream. You store that LSN with the user's session, and on the next read, you route to whichever replica has caught up PAST that LSN — checking `pg_last_wal_replay_lsn` in PostgreSQL, or `Seconds_Behind_Source` in MySQL. If no replica has caught up within, say, a hundred milliseconds, you just fall back to the primary. And solution four, semi-synchronous replication: the write itself doesn't return success until at least one replica has acknowledged receiving it — meaning that specific replica is guaranteed fresh the instant the write completes, at the cost of a few extra milliseconds of write latency."

[Screen cue: Draw all four solutions as a ladder of increasing precision, each with a one-line trade-off underneath.]

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"Here's the trap: engineers apply the SAME fix everywhere, when the correct answer is actually per-endpoint. A hotel booking that must appear immediately after payment needs LSN-based routing or semi-sync — the strictest guarantee. An order-history page after checkout is well served by a simple five-second read-from-primary window, because order writes per user are infrequent, so the primary barely notices the extra load. A watch-history or 'continue watching' list needs NO fix at all — thirty seconds of staleness there is genuinely invisible to the user, and adding LSN routing would be pure engineering waste. The second trap is not monitoring lag at all until it becomes an incident. In PostgreSQL, you'd track replication lag in seconds directly from `pg_stat_replication` — anything above five seconds for a same-datacenter replica is abnormal and worth investigating, above thirty seconds means the replica is probably stuck and should be pulled from the read pool entirely, because a badly lagging replica isn't just serving stale data, it's often behind on recent schema migrations too, which causes much scarier bugs. In MySQL, the equivalent metric is `Seconds_Behind_Source` from `SHOW REPLICA STATUS`, and a common Prometheus alert rule fires when that value exceeds ten seconds for more than two minutes straight."

## REAL WORLD (8:00–9:30)
"Think about a Swiggy or Zomato order — placed, then immediately shown on the order-tracking page; a five-second read-from-primary window after order creation is exactly the right amount of engineering effort here, since order writes per user are infrequent. Think about a hotel or flight booking platform like MakeMyTrip — this is the strictest case, where LSN-based routing is worth the extra complexity because a missing booking right after payment is a trust-destroying experience. And think about a video platform's watch history, similar to how Hotstar tracks what you were watching — this is the one place where you deliberately do NOT fix the lag, because thirty seconds of staleness on a 'continue watching' row costs you nothing and fixing it would waste engineering effort better spent elsewhere."
