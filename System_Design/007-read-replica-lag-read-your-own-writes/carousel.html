Primary says "success" the instant it commits locally — it does NOT wait for replicas.

Read From Primary After Write

Fix 1 — Simplest

For a few seconds after a write, route that user's reads back to the primary via a short-lived session flag.

✓ Dead simple   ✕ Adds load to primary if writes are frequent

Monotonic (Sticky) Reads

Fix 2

User always hits the SAME replica, hashed by user ID — never sees data go backward in time on refresh.

✕ Doesn't fix the FIRST read right after a write

LSN-Based Routing

Fix 3 — Most Precise

Write returns a Log Sequence Number. Read routes to whichever replica has caught up PAST that LSN — or falls back to primary if none have.

pg_last_wal_replay_lsn() (Postgres) / Seconds_Behind_Source (MySQL)

Semi-Synchronous Replication

Fix 4 — Write-Level Guarantee

Write doesn't return success until ≥1 replica acknowledges — that replica is guaranteed fresh.

✓ Strongest guarantee   ✕ Adds write latency (replica RTT)

Lag Monitoring Thresholds

Operational Alerting

✓ < 5s: normal

⚠️ > 5s: investigate — replica under load

✕ > 30s: pull replica from read pool — likely stuck, may also be behind on schema migrations

Decision Tree & Interview Answer

Quick Reference

Must be visible instantly? → LSN routing / semi-sync. Rare writes per user? → 5s primary window. Purely browsing history? → Leave it lagging.

"Read replicas give you horizontal read scaling but introduce lag — the first thing I do when adding replicas is decide per-endpoint whether staleness is acceptable, and implement LSN routing or a primary-read window for the endpoints where it isn't."
