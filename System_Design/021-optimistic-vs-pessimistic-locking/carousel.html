Locking is how you prevent two transactions from corrupting shared data — pessimistic (lock first, assume the worst) vs optimistic (check at write time, assume the best).

Lock Types (InnoDB / MySQL) · 3/9

Exclusive vs Shared vs Table-Level Locks

SELECT ... FOR UPDATE Exclusive (X)

Nobody else can read-for-update OR write this row. Full ownership until COMMIT.

LOCKED

SELECT ... FOR SHARE Shared (S)

Also: LOCK IN SHARE MODE. Others can also read-for-share, but nobody can write.

reader 1

LOCK TABLES seats WRITE Table-level

Locks the entire table. Never use in OLTP — kills concurrency for every row, not just the contended one.

Rule of thumb: default to row-level FOR UPDATE when you intend to write; use FOR SHARE only when you need to read-and-verify without blocking other readers.

Optimistic Locking · 5/9

Version Column — Check at Write Time, Not Read Time

CREATE TABLE seats (
    id INT PRIMARY KEY, status VARCHAR(20), user_id INT,
    version INT DEFAULT 0   -- the version counter
);
-- User A writes (checks version hasn't changed):
UPDATE seats SET status='booked', user_id='userA', version=version+1
WHERE id = 14 AND version = 5;  -- the optimistic check

Deadlock Prevention · 6/9

Three Rules That Eliminate Deadlocks

Rule 1 — Same lock order

WRONG A: lock 100→200. B: lock 200→100. → deadlock possible.

RIGHT Always ascending by id. A: 100→200. B: 100→200 (blocks on 100, then proceeds).

Rule 2 — Keep transactions short

WRONG BEGIN → FOR UPDATE → call external API (2s, lock held) → UPDATE → COMMIT.

RIGHT call external API first (no lock) → BEGIN → FOR UPDATE → UPDATE → COMMIT (lock held <10ms).

Rule 3 — Never upgrade locks

WRONG A reads (shared), then UPDATE (wants exclusive) while B also holds shared → both wait forever.

RIGHT If you'll write, use FOR UPDATE from the start. Don't read-then-upgrade.

Where This Shows Up · 9/9

Real-World Examples From Your System Designs

Payment System Pessimistic

SELECT FOR UPDATE on the account row. Without it, two concurrent debits both read balance=1000, both approve, account goes negative.

Ticket Booking Pessimistic

SELECT FOR UPDATE on the seat row so exactly one of two simultaneous clicks wins; the loser sees the committed "booked" state and fails gracefully.

Hotel Booking Optimistic

Lower contention than seats. @Version: read, attempt update, retry on version mismatch. Better throughput, retry cost is acceptable.

Stock Broker Pessimistic

Order matching locks both sides of a trade to calculate fill price atomically. Consistent lock order (lower order_id first) avoids deadlocks between matching threads.

"Use pessimistic locking when the cost of a conflict (double booking, negative balance) is higher than the cost of waiting; use optimistic locking when conflicts are rare and retrying is cheap."
