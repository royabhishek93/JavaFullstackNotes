InnoDB's primary key isn't just an index — it's the physical sort order of rows on disk (a clustered index).

THE FIX

Three Ways to Fix This

1. AUTO_INCREMENT BIGINT — clustered PK for internal use. public_id UUID column (unique index) for external/API exposure.

2. ULID — 01ARZ3NDEKTSV4RRFFQ69G5FAV. First part = timestamp (sorted), rest = randomness (unique). Inserts land near the end → minimal splits.

3. UUID v7 — first 48 bits = millisecond timestamp. Drop-in for UUID v4, no page-split problem. Native in PostgreSQL 17, MySQL 9.0+.

SOLUTIONS7 / 10
WHEN IT'S OK · REAL WORLD

Not Always Bad — Context Matters

  • ✓ PostgreSQL heap storage (not clustered by PK by default)
  • ✓ Low write volume < 1K inserts/sec
  • ✓ Used as a secondary key, not the clustered PK
  • ✓ Distributed ID generation (CockroachDB/Spanner handle it internally)

Real world: Swiggy/Zomato-style order tables use BIGINT PK + public_id UUID during lunch-rush write spikes. A Flipkart-style flash sale pushing 10K+ orders/sec stays at zero fragmentation on sequential BIGINT PKs — UUID PKs would scatter every insert across the whole tree. PhonePe/UPI-style ledgers use sequential/ULID trade IDs to keep the buffer pool hit rate high under microsecond-level trade inserts.
