Deep Dive

Bloom Filter: The First Line

  • False negatives: impossible — if X was added, always answers "probably yes"
  • False positives: ~1% — says "probably yes" for a key never added
  • 10M codes → ~12MB memory at 1% FPR
  • 99% of non-existent code requests blocked here: 0 cache, 0 DB
  • 1% (false positives) fall through to the negative cache layer

Rule of thumb: negative TTL = how long you're willing to serve a stale "not found" after the key is actually created.

NEVER set negative TTL = infinite — a registered user could get a permanent phantom 404.

Trap #1 — The Big One

Forgetting to Invalidate on Write

t=0: "user123" doesn't exist → cache NULL, TTL=60s

t=30: user registers as "user123" → DB write succeeds

t=31: lookup for "user123" → CACHE HIT (NULL) → still 404

User thinks signup failed → retries → "username taken" → support ticket filed

Correct write path: INSERT into DB → redis.delete(key) → redis.setex(key, ttl, data) → bloom_filter.add(key)

Deep Dive

What Negative Caching Does NOT Fix

  • Infinite unique keys: bot never repeats a key → cache fills with millions of one-time entries, each still costs 1 DB lookup. Fix: rate-limit by IP at ingress.
  • Cache stampede: 1,000s of requests for the same missing key arrive before the first negative entry is set → all hit DB at once. Fix: distributed lock or early refresh.
  • Rapid churn data: keys created/deleted many times/min → negative TTL must be <5s, protection is limited.

90 bytes per negative entry (1M entries = 90MB) vs. 2,000 CPU-seconds wasted on 1M uncached DB queries (2ms each). RAM wins.

Interview Cheat Sheet

Decision Tree

  • User-supplied ID can miss + misses repeat? → USE negative cache
  • Strict consistency (financial account lookup)? → SKIP
  • Changes every second (live inventory)? → SKIP — TTL too short to help
  • Static/rarely-created keyspace? → long TTL (1hr+)
"Cache the 'not found' answer with a short TTL — a negative cache entry costs 100 bytes but saves one full DB round-trip for every repeat miss."
