## THE PROBLEM (0:30–2:00)
"Think about it this way — scalability just means your system can handle more load without a redesign. Vertical scaling is buying a bigger server: simple, but there's always a ceiling, and it's a single point of failure. Horizontal scaling means adding MORE servers of the same size — no ceiling, but now you need something to distribute traffic across all of them. That's a load balancer. An L4 load balancer routes by IP and port — fast, but blind to what's actually in the request. An L7 load balancer reads the real HTTP request and can route by URL path — /api/orders here, /api/payment there — and it terminates SSL for you. The real unlock for horizontal scaling is making every single pod stateless: no pod remembers anything locally, so any pod can handle any request, and if one crashes, the load balancer just routes around it."

[Screen cue: Draw the request path — Route53 → CloudFront → ALB → auto-scaling pod fleet → Redis/Aurora — labeling each hop.]

## THE SOLUTION (2:00–5:00)
"Now watch what happens when you prepare for a flash sale properly. The day before, you pre-scale — manually bump pod count ahead of time, because auto-scaling reacts in two to three minutes, but flash-sale traffic spikes in SECONDS. You pre-warm your caches, loading hot product and inventory data into Redis at eleven forty-five PM before a midnight sale, because a cache miss during the sale means a database hit, and a database hit at that volume means an overwhelmed database. You route all read-heavy traffic — product pages, inventory checks — to read replicas, keeping only writes on the primary. You enable aggressive CDN caching for images and static assets with a long TTL, but a shorter TTL, say five minutes, for anything that changes like price. And you wrap slow dependencies like the payment gateway in circuit breakers so they fail fast instead of cascading into a full outage. During the sale itself, you don't write orders directly to the database — you accept the order instantly with a 200 response, drop it onto a queue like SQS, and let consumers process it at a controlled rate, so a burst of ten thousand simultaneous submissions doesn't become ten thousand simultaneous database writes. And you rate-limit per user with a token bucket in Redis — five requests per second per user — to stop bots and resellers from hammering the checkout."

[Screen cue: Draw the pre-sale checklist as five ticked boxes, then the queue-based order flow: Client → 200 Accepted → SQS → Consumer → DB.]

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"Here's the trap that quietly kills auto-scaling: sticky sessions. In the old model, a load balancer always routes user123 to server three, and that server keeps the session data in its own memory. Traffic spikes, auto-scaling adds server ten — but server three still holds every single sticky user, so server three sits at eighty percent CPU while the new servers idle at ten percent. And if server three crashes from an out-of-memory error, every user pinned to it loses their session entirely — mid-sale logouts, five hundred errors, at the worst possible moment. Auto-scaling literally cannot help you here, because all the load is pinned to one machine. The fix: make services stateless by storing sessions in Redis instead of server memory, so any pod can serve any request and the load balancer is finally free to distribute evenly. Second trap: your L7 load balancer terminates SSL and forwards the real client IP in an X-Forwarded-For header — but if your backend code reads request-dot-get-remote-addr instead of that header, every single request appears to come from the load balancer's own internal IP. Your rate limiter then sees ALL your users as one IP, and the moment any single user hits the limit, it blocks EVERYONE. And the third trap shows up during every rolling deployment: without connection draining, the load balancer marks an old pod as 'removing' and immediately stops sending it new requests — but that pod might still have fifty in-flight requests being processed, and those get killed mid-flight, producing 502 errors for real users. The fix is a thirty-second deregistration delay so in-flight requests finish cleanly, combined with a Kubernetes readiness probe so new pods don't receive traffic until they're actually warmed up, and a pre-stop hook that sleeps for ten seconds to give the load balancer time to notice a pod is terminating before it actually shuts down."

## REAL WORLD (8:00–9:30)
"Flipkart's Big Billion Days is the reference case for flash-sale readiness — pre-scaling, cache pre-warming, and queue-based order acceptance are exactly the pattern that lets a 10x traffic spike land without an outage. Picture a fashion platform like Myntra during their End of Reason Sale — if session data were still pinned to specific servers, a single overloaded pod could log out thousands of users mid-checkout during the highest-traffic hour of the year. And think about Swiggy or Zomato pushing a routine deployment during peak dinner-hour traffic — without connection draining and readiness probes, that completely normal deploy would generate a visible spike of 502 errors for real customers trying to place an order."
