✓ Aggressive CDN caching (long TTL for images, 5min for price)

Consistent Hashing — Cache Avalanche

Scenario 2

Plain hash(key) % N: adding a 5th Redis node remaps 100% of keys — cache hit rate crashes from 100% to 0%, all traffic slams the DB at once.

Fix: consistent hashing ring — adding/removing a node remaps only ~1/N of keys. Use Redis Cluster's built-in hash slots.

Sticky Sessions Break Auto-Scaling

Trap 1

Pod 4-10
10% CPU
Pod 3
80% CPU

All sticky users pinned to Pod 3 — new pods sit idle. If Pod 3 OOMs, every pinned user loses their session mid-sale.

Fix: sessions in Redis, not pod memory.

L7 SSL Termination Leaks the Real IP

Trap 2

request.getRemoteAddr() returns the LOAD BALANCER's IP, not the client's.

Rate limiter keyed on that IP blocks EVERY user the moment ANY user exceeds the limit.

Fix: read X-Forwarded-For / X-Real-IP, or set forward-headers-strategy: framework in Spring Boot.

Decision Tree & Interview Answer

Quick Reference

Any user-specific state? → Move it to Redis, keep pods stateless.

Expecting a traffic spike? → Pre-scale + pre-warm, don't rely on HPA alone.

Deploying under load? → Connection draining + readiness probe + preStop sleep.

"For any scale problem I start with making services stateless — sessions in Redis, not memory. ALB at L7 routes by path; consistent hashing in the cache layer prevents cache avalanche. For flash sales: pre-scale before traffic hits, pre-warm caches, and put order submission behind an async queue. The most common trap is sticky sessions — it kills auto-scaling because all load pins to one server."
