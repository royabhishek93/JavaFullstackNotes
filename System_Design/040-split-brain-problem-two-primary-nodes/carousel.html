60 seconds of split brain. Duplicate order ID. One customer's charge silently lost forever.

THE CORRUPTION

t=0 to t=60s: Both Primaries Accept Writes

  • OLD PRIMARY receives: ORDER #1001 (Alice, $200), ORDER #1002 (Charlie, $50), debit Alice −$200
  • NEW PRIMARY receives: ORDER #1001 (Bob, $150), ORDER #1003 (Diana, $300), debit Bob −$150
  • t=60s — network heals. Both nodes can talk again.

Conflict on reconciliation

  • ORDER #1001 exists on both — with two different users
  • Alice's balance debited on one node, Bob's on the other
  • One of these writes is silently lost
  • Inventory decremented twice, for two different customers

Result: money and data integrity destroyed — one customer charged with no order, one order ID collision in the database.

SOLUTION 1

Fencing / STONITH — "Shoot The Other Node In The Head"

OLD PRIMARY
FENCED / KILLED
◄ FENCE
NEW PRIMARY
(safe to write)
  • New primary sends a FENCE command: cut network, force-kill process, or revoke disk access
  • Rule: "Did the old primary actually stop? Confirmed? Then I accept writes."
  • Only ONE primary can exist — the old one is provably dead before the new one starts

  • A: "I only see myself — 1/3. No majority. Refusing writes."
  • B & C: "We see each other — 2/3. We have majority. Elect B."
  • Only one primary at a time — old one steps down voluntarily
  • How etcd, ZooKeeper, and Raft work: a leader must hold a majority lease to remain leader

WHERE ENGINEERS GET IT WRONG

Four Traps That Still Bite You

  • Data loss window: writes acked by old primary but not yet replicated are gone — even with perfect prevention
  • "Primary comes back" race: old primary returns after a transient blip; stale client connections still hit it unless drivers re-query Sentinel for current master
  • Clock skew (Cassandra): leaderless, last-write-wins by timestamp — skewed clocks pick the WRONG winner, silently
  • Timeout tuning ≠ prevention: a longer heartbeat timeout only makes split brain rarer, not impossible — only fencing/quorum removes it structurally
"For a leaderboard, losing a few writes is acceptable — rebuild from Kafka. For payments, Redis is never the source of truth — MySQL is — so Redis data loss is a cache miss, not a financial error."
Split-Brain Problem7 / 10
REAL WORLD

Split Brain at Indian Tech Scale

  • UPI / Payments platforms (PhonePe, Paytm): even 60s of split brain on the ledger DB risks double-debits at tens of millions of transactions/day — quorum + STONITH fencing is non-negotiable
  • Food delivery (Swiggy, Zomato): Redis holds live order status & delivery locations during peak dinner-time traffic — split brain here causes wrong ETAs, not lost money, because MySQL/Postgres remains the source of truth
  • E-commerce flash sales (Flipkart): Redis Cluster inventory counters via ZINCRBY — two nodes accepting increments during a blip diverges stock counts — fixed with min-replicas-to-write=1

CHEAT SHEET

Decision Tree + Interview One-Liner

  • Can the node reach a majority of the cluster? → No → step down, refuse writes
  • Is this node newly elected primary? → Yes → fence the old primary before accepting writes
  • Need zero data loss? → use synchronous replication (higher latency)
  • Can tolerate a small loss window? → async replication (lower latency)
"Split brain is when two nodes both think they're primary. The solution is to ensure only one can have a majority at a time — either through quorum requirements or fencing the old primary before promoting the new one."
