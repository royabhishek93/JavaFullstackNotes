The Solution — Three Pillars

Metrics · Logs · Traces

METRICS
Numeric time series. Cheap to store, cheap to alert on. Fast & coarse.
LOGS
Timestamped textual events. Rich, but expensive at scale.
TRACES
One request's full journey across every service, shared trace ID.
  • Metrics: "page someone if heart rate exceeds 140" — good for alerting, bad at explaining WHY.
  • Logs: rich context per event — but need to already know roughly where to look.
  • Traces: the only view that shows causal, cross-service timing in one place.
  • Retention trap: raw logs typically kept only 7–30 days hot, then archived — full-fidelity retention at metric-like durations is cost-prohibitive.

Trap — Sampling

Head-Based vs Tail-Based

Head-BasedTail-Based
Decision pointAt request STARTAFTER request completes
Typical ruleRandom 1%, or 100% w/ debug headerKeep all errors / slow traces, sample 1% of "fine" ones
RiskMay sample OUT the 1-in-10,000 request that erroredNone — errors always kept
CostCheap, simpleBuffering + collector-side complexity/cost layer
Best forLow-stakes, high-volume baseline visibilityDebugging real production incidents

Cardinality trap: a `userId` label on a metric can blow up storage/query cost by orders of magnitude. High-cardinality data belongs in logs/traces — never metric labels.

SLI · SLO · SLA · Error Budget

The Promise, and the Budget

SLA 99.9%
SLO 99.95%
SLI actual
  • SLI: the measured metric — e.g. 99.95% of requests, last 28 days, under 200ms.
  • SLO: internal target — deliberately tighter than the SLA on purpose.
  • SLA: external contractual promise — your alarm fires BEFORE you breach it.
  • Error budget = (1 − 0.9995) × 28 days × 24h × 60min ≈ 20.16 min/month.
  • Burn-rate alert: page if current pace would exhaust the month's budget in <6h (fast burn); slow creeping burn → ticket, not a page.

Decision Tree · Interview Answer

The Order of Operations

Confirm it's real → check p50/p95/p99 metrics
↓
Still unclear which of 15 services? → pull a trace, read the waterfall
↓
Trace narrows it to one span → pull that service's logs + trace ID
↓
Check against SLO → is error budget burning fast?
"Metrics are cheap and fast, so that's where I start, not logs. Logs alone across 15 services won't scale — that's exactly the case for distributed tracing, since every request already carries a trace ID through context propagation. Once tracing narrows it down, THEN I'd pull logs — because I already know precisely where to look. And I'd frame it against our SLO: if we're burning error budget fast enough to exhaust the month's allowance in a few hours, that's a page-now incident, not a ticket."
