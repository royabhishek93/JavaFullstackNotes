🔍 Search Engine System Design

Google-Scale Web Search

Crawler Inverted Index PageRank TF-IDF MapReduce Ranking

A search engine is two completely separate systems that share one artifact — the index.

  • Offline pipeline: Crawler → Parser → Indexer → builds the inverted index (runs continuously)
  • Online serving: Query in → lookup index → rank → return top-10 in <200ms

Most candidates conflate these. State this separation early — it impresses interviewers immediately.

"Design Google Search / Web Search Engine at 99,000 searches/second"

Opening Script — Scale & Context

"A search engine is two separate systems sharing one artifact — the index. The offline pipeline crawls the web and builds an inverted index. The online serving layer uses that index to answer queries in <200ms. The defining challenges are: building the inverted index at web scale, and query serving at 99,000 searches/second."

Web Scale Reality

  • 60 trillion pages indexed (Google)
  • 8.5 billion searches per day
  • 99,000 searches per second
  • ~1M pages/sec crawler throughput
  • 100–200 PB inverted index size
  • ~1.2 exabytes raw text content

Key Insight

  • Index is a derived artifact — source of truth is the crawled page store
  • Read:Write ≈ 10,000:1 — optimize for reads
  • Query cache absorbs 25–30% of all traffic
  • Breaking news indexed in minutes
  • Regular pages indexed in hours–days
  • Target p99 latency: <200ms end-to-end

Functional Requirements

In Scope

  • Crawl the web and store page content
  • Parse HTML — extract text, links, metadata
  • Build and maintain an inverted index
  • Accept user queries, return ranked results
  • Full-text multi-word queries
  • Phrase queries ("new york times")
  • Ranked results — relevance + authority
  • Spelling corrections and suggestions
  • Query expansion (synonyms)
  • Boolean queries (AND, OR, NOT)
  • Near-duplicate content detection
  • Fresh results — re-crawl changed pages

Out of Scope

  • Image / video search
  • Real-time social media indexing
  • Personalized search ranking

Scoping Questions to Ask

  • "Web-scale or domain-specific?"
  • "Phrase queries supported?"
  • "How fast — SLO for p99?"
  • "QPS target?"
  • "How many pages to index?"
Core: Crawl → Index → Rank → Serve

Non-Functional Requirements & Capacity

NFRs

  • Latency: p99 <200ms end-to-end query

  • Freshness: Top pages re-crawled within 24h

Key Tensions

Web Crawler Design

URL Frontier (Priority Queue)

Redis Sorted Set (ZPOPMIN = atomic)
score = PageRank_estimate × freshness_need

FRONT QUEUE (priority-based):
  HIGH:   news sites, .gov, .edu
  MEDIUM: known good domains
  LOW:    newly discovered URLs

BACK QUEUE (per-domain politeness):
  domain-A: [url1, url2, url3]
  domain-B: [url4, url5]
  → never 2 requests to same domain
    within crawl-delay window

URL Dedup — Bloom Filter

  • 100B URLs × 10 bits/URL = 125 GB (tiny)
  • False positives OK — skip a URL once
  • Never false negatives — never re-crawl

Crawl Flow

Frontier dequeue (highest priority,
                   politeness OK)
    → DNS Resolver (cached, TTL-aware)
    → robots.txt cache check
        allowed? → proceed
        blocked? → skip, mark URL
    → HTTP Fetcher
        200 OK    → store raw HTML
        301/302   → follow redirect (max 5)
        404/410   → mark URL dead
        429/503   → back-off, re-enqueue
    → SimHash check
        duplicate → discard
        changed   → parse queue
    → Extract links → URL Frontier

Spider Trap Prevention

  • URL depth limit (max depth 6)
  • Max URLs per domain per cycle
  • Detect repeating URL patterns
  • URL normalisation before dedup

Doc Processing

Raw text: "Java is a programming language"
    │
    ▼ Tokenize
  ["Java","is","a","programming","language"]
    │
    ▼ Lowercase
  ["java","is","a","programming","language"]
    │
    ▼ Remove Stop Words
  ["java","programming","language"]
    │
    ▼ Stem (Porter Stemmer)
  ["java","program","languag"]
    │
    ▼ Term Frequency Map
  {java:1, program:1, languag:1}
    │
    ▼ SimHash fingerprint (near-dup check)
  64-bit fingerprint → compare Hamming
  distance ≤ 3 → near-duplicate → skip
Anchor text of inbound links is a stronger relevance signal than the page's own text

Inverted Index — The Heart of Search

Structure: term → postings list

TERM        DOC_IDS + TF + POSITIONS
────────    ───────────────────────────────
"java"   →  [(doc1, tf=5, pos=[10,45,67]),
             (doc3, tf=2, pos=[5,89]), ...]
"tutorial"→ [(doc1, tf=3, pos=[11,46]),
             (doc7, tf=1, pos=[3]),    ...]
"python" →  [(doc2, tf=8, pos=[1,2,3]),
             (doc5, tf=4, pos=[22]),   ...]

Query "java tutorial":
  1. Lookup "java"     → {doc1, doc3, ...}
  2. Lookup "tutorial" → {doc1, doc7, ...}
  3. Intersect (AND)   → {doc1}
  4. Score doc1 by BM25
  5. Return top results

Posting List Fields

doc_id | tf | dl | pos[0] | pos[1] | ...
──────────────────────────────────────────
df  = document frequency (how many docs)
tf  = term frequency (occurrences in doc)
dl  = doc length (BM25 normalisation)
pos = positions (enables phrase matching)

Building the Index (MapReduce)

Phase 1: MAP (per document)
  doc_1: "java programming language"
  Emit: (java,doc1,tf=1), (program,doc1,tf=1)

Phase 2: SORT (by term globally)
  All (term, docId, tf) sorted by term

Phase 3: REDUCE (merge per term)
  java → [(doc1,1),(doc3,5),(doc7,2)]
  Sort by docId within list (fast merge)

Phase 4: WRITE to index shards
  Distribute: hash(term) % num_shards
    OR shard by doc_id range (preferred)

Delta + Base Index

  • Base index: full rebuild weekly
  • Delta index: last 24h, updated hourly
  • Queries hit BOTH; prefer delta version
  • Periodic merge: delta → base, reset delta
Stored as compressed binary (delta-encoded doc IDs). NOT a SQL table — custom Lucene segment files.

TF-IDF — Term Relevance Scoring

Formula

TF (Term Frequency)
  = count of term t in doc d
    ─────────────────────────
    total words in doc d

IDF (Inverse Document Frequency)
  = log( total docs / docs containing t )

TF-IDF(t, d) = TF(t, d) × IDF(t)

Intuition Examples

"the"     : TF=0.10, IDF=log(8B/8B)=0
            → score=0.00 (useless, everywhere)

"java"    : TF=0.05, IDF=log(8B/10M)≈3
            → score=0.15 (somewhat useful)

"graalvm" : TF=0.02, IDF=log(8B/100K)≈5
            → score=0.10 (very specific, rare)
High IDF = rare word = strong signal.
"the" in every doc = IDF≈0 = useless.

Why TF-IDF Has Limits

  • A 10,000-word doc mentioning "java" once scores same as a 100-word doc — unfair
  • Doubling TF doubles score — no diminishing returns
  • No length normalisation

Stop Words (removed before indexing)

  • "the", "a", "is", "of", "and", "in"
  • Appear in nearly every doc → IDF ≈ 0
  • Removing them saves index space and reduces noise

Stemming (applied before TF-IDF)

"running" → "run"
"searches"→ "search"
"developer"→ "develop"
Ensures "run" query matches "running" docs

PageRank Algorithm

Core Formula

PR(A) = (1 - d) + d × SUM(
          PR(B) / OutLinks(B)
        ) for all B that link to A

d = damping factor = 0.85
  (probability random surfer follows a
   link rather than jumping randomly)

Computed iteratively until convergence
  → typically 50–100 iterations
  → run as offline Spark batch job
     on the full web_graph table

Intuition

  • Wikipedia: millions of inbound links → very high PageRank
  • New blog, zero inbound links → PR ≈ 0
  • Linked by high-PR pages → boosted even with few total links
  • Quality of linker matters more than quantity of links

Dangling Nodes

  • Pages with no outbound links — "sink" all PageRank
  • Fix: distribute dangling node PR evenly across all pages
  • Or: add teleport probability to a random page

Anti-Spam (TrustRank)

Seed: known-good domains
  (Wikipedia, .gov, .edu, NYT)
TrustRank propagates OUTWARD from seeds.
Links FROM trusted pages = high value.
Links from new domains (registered <30d)
  = near-zero PageRank contribution.
Link farm detection: 1000s of pages
  with same content linking same target
  → ML spam classifier → penalise.
PageRank is computed OFFLINE (batch). It is 1 of 200+ ranking signals in modern Google — not dominant alone.

BM25 — Industry-Standard Text Ranking

Formula

BM25(t, d) = IDF(t) ×
  [ tf × (k1 + 1) ]
  ─────────────────────────────────────
  [ tf + k1 × (1 - b + b × dl/avgdl) ]

Parameters:
  k1    = 1.5  (TF saturation)
  b     = 0.75 (doc length normalisation)
  tf    = term frequency in doc
  dl    = document length
  avgdl = average document length

IDF(t) = log((N - df + 0.5) / (df + 0.5))
  N  = total documents
  df = documents containing term t

Why BM25 Beats TF-IDF

  • TF saturation (k1): seeing "java" 100× vs 10× is NOT 10× better — plateau effect
  • Length normalisation (b): long doc mentioning "java" once = less relevant than short doc
  • Avoids bias towards verbose documents

Where BM25 Is Used

  • Elasticsearch — default ranker
  • Apache Solr — default ranker
  • Lucene (underlying engine)
  • Google uses BM25 as baseline, then adds 200+ signals
BM25 scores are computed AT INDEX TIME and stored in the postings table — not recalculated per query.

Modern Ranking — 200+ Signals

Final Score Formula

score(doc, query) =
  α × BM25(doc, query)       text relevance
+ β × PageRank(doc)          link authority
+ γ × FreshnessScore(doc)    recency bonus
+ δ × AnchorTextScore(doc)   what others call it
+ ε × CTR_model(doc, query)  click-through rate

α, β, γ, δ, ε = learned weights (ML tuning)

FreshnessScore = 1 / (1 + days_since_crawl)
AnchorText = text of hyperlinks pointing here

E-E-A-T Signals (Google)

  • Experience — first-hand expertise signals
  • Expertise — author credentials, domain authority
  • Authoritativeness — inbound link quality
  • Trustworthiness — HTTPS, accuracy, factual

Other Key Ranking Factors

  • Query-document relevance — BM25 + BERT semantic similarity
  • Freshness — recently crawled pages get recency boost
  • Mobile-friendliness — responsive design signals
  • Page speed / Core Web Vitals
  • HTTPS security
  • Click-through rate (CTR) — past user behaviour
  • Dwell time — how long users stay on page
  • Bounce rate — users returning to search quickly

Query Intent (ML)

  • "jaguar" → animal, car, or NFL team?
  • BERT-based classifier predicts intent distribution
  • Return blended results for ambiguous queries
  • User clicks train future personalization

Query Processing Pipeline

User → "runing java tutorail"
         │
         ▼ Step 1: Cache Check
    Redis: query_cache:{hash} → HIT? → return instantly (30% of queries)
         │ MISS
         ▼ Step 2: Query Parsing
    Tokenize  : ["runing", "java", "tutorail"]
    Spell fix : ["running", "java", "tutorial"]
    Stem      : ["run", "java", "tutori"]
    Stop words: (none here — all meaningful)
    Expand    : "java" → may add "jvm" as synonym
         │
         ▼ Step 3: Shard Planning
    Document-based sharding → ALL shards must be queried
    (any shard can hold any term's documents)
         │
         ▼ Step 4: Parallel Shard Query (SCATTER — all at once)
    Each shard independently:
      • Lookup posting lists for "run", "java", "tutori"
      • Intersect → docs containing ALL terms
      • Score each doc: BM25 × PageRank
      • Return local top-K  (timeout: 50ms hard limit)
         │
         ▼ Step 5: GATHER + Global Rank (MERGE)
    Collect top-K from each shard
    Apply global signals: PageRank, freshness, CTR
    Re-rank → global top-10
         │
         ▼ Step 6: Cache + Snippet Generation
    Store in Redis (TTL: news=30s, static=1h)
    Extract best matching sentence per result
    Highlight matching terms in bold
         │
         ▼ Return results in <200ms

Spell Correction & Autocomplete

Spell Correction

Edit Distance (Levenshtein):
  "jaav" → "java" (1 substitution)
  "jaava" → "java" (1 deletion)

Approach:
  1. Generate candidates within edit distance 1–2
  2. Filter by query log frequency
     (how often was this term queried?)
  3. Rank by: frequency × phonetic similarity
  4. Use noisy channel model:
       P(intended | typed) ∝
         P(typed | intended) × P(intended)

N-gram model:
  "jaav dev" → check bigram frequency
  in query logs → "java dev" is 1000×
  more common → suggest correction

Autocomplete (Type-Ahead)

Trie Data Structure:
  j → ja → jav → java
                → java developer (freq: 1M)
                → java tutorial  (freq: 800K)
                → java spring    (freq: 600K)

Top-K completions stored at each trie node
(avoid full trie traversal per keypress)

Sources of suggestions:
  • Query log frequency (top searched)
  • Current trending queries
  • Personalized history (logged-in user)

Multilingual Support

  • Language detection at parse time (n-gram model)
  • Language-specific stemming rules
  • Separate stop word lists per language
  • Language tag on each posting → query routing filters by detected language

Index Sharding Strategies

Document-Based Sharding (PREFERRED)

Shard by: hash(URL) % N_shards
  OR: doc_id range per shard

Each shard holds ALL terms for its
  subset of documents.

Query "java": fan out to ALL N shards
  → each shard returns its local top-K
  → merger combines into global top-K

WHY this wins:
  No "hot posting list" problem
  "java" is distributed across all shards
  Each shard handles equal query load
  Balanced storage across shards

Replication

3 copies per shard (primary + 2 replicas)
100 PB ÷ 1 TB/server = 100,000 servers
× 3 replicas = 300,000 servers
(This is why Google has ~1M+ servers)

Term-Based Sharding (AVOID)

Shard by: hash(term) % N_shards
  Each shard owns all docs for its terms

WHY this fails at scale:
  "java" → 10M postings → ONE shard
  That shard is hot for every query
  containing "java" — bottleneck!
  Uneven shard load impossible to fix

Distributed Query Fan-Out

Query → Planner → fan-out to all N shards
Each shard: 10ms response target
Merger waits max 50ms (scatter-gather timeout)
  → if shard exceeds 50ms: partial results
  → "stragglers" dropped; SLO preserved

Latency budget breakdown:
  Query parse:    ~5ms
  Scatter-gather: ~40ms (all shards parallel)
  Merge + rank:   ~10ms
  Snippet gen:    ~5ms
  Network:        ~10ms
  Cache/return:   ~5ms  → Total: ~75ms p50

Index Freshness Strategy

Freshness Tiers

HIGH (re-crawl every 15 min–hours):
  • News sites, weather, stock tickers
  • Pages with <meta http-equiv="refresh">
  • Pages that changed on every prior crawl
  • RSS/Atom feed subscriptions
  • Sitemap ping via Search Console

MEDIUM (re-crawl daily):
  • Blog posts, product pages
  • Sitemap changefreq=daily pages
  • High-PageRank pages with recent changes

LOW (re-crawl weekly/monthly):
  • Wikipedia articles, static docs
  • Pages that never changed across 5 crawls
  • Low-traffic long-tail pages

Signal: if last_crawl_hash == current_hash
  → content unchanged → extend re-crawl interval

Delta + Base Index Architecture

BASE INDEX:
  Full inverted index — all crawled pages
  Rebuilt weekly (full rebuild via MapReduce)
  Stable, large, slow to update

DELTA INDEX:
  Pages crawled in last 24 hours
  Updated hourly
  Small and fast to query

QUERY SERVING:
  Query hits BOTH indexes in parallel
  Merge results → prefer DELTA if same docId
  (delta has fresher data)

MERGE JOB (periodic, low-traffic window):
  delta → base, reset delta
  Done during off-peak hours
Breaking news path: RSS/sitemap ping → expedited crawl queue → delta index → live in minutes

Crawl Priority Formula

priority = PageRank × freshness_need
freshness_need = 1 / days_since_changed

Scatter-Gather Query Serving

Why Scatter-Gather?

  • Index is 100+ PB — one machine cannot hold it
  • Sequential search: 1000 shards × 10ms = 10 seconds per query
  • Parallel scatter-gather: all shards simultaneously = 10ms regardless of count

Sequence

Query → fan-out to ALL N shards (SCATTER)
         │
         ├──▶ Shard 1: BM25 → local top-K
         ├──▶ Shard 2: BM25 → local top-K
         ├──▶ Shard 3: BM25 → local top-K
         └──▶ Shard N: BM25 → local top-K
                     │ (50ms timeout)
                     ▼ GATHER
         Result Merger:
           • Merge top-K from all shards
           • Apply PageRank + freshness boost
           • Global re-rank → top-10
           • Generate snippets

Latency Protection

  • Hedged requests: send to both primary and replica, use first response
  • Hard timeout 50ms: straggler shards dropped; partial results returned
  • Reduce top-K during load: return top-5 instead of top-20 per shard
  • Load shedding: drop lowest-priority queries if queue depth spikes

Java Implementation

// CompletableFuture scatter-gather
List<CompletableFuture<ShardResult>> futures =
  shards.stream()
    .map(shard -> shard.queryAsync(plan)
          .orTimeout(50, MILLISECONDS))
    .collect(toList());

CompletableFuture.allOf(futures.toArray(...))
  .thenApply(v -> merger.merge(futures));
Partial results > no results. Users rarely notice if 1/1000 shards is down.

Result Caching

Why Caching Is High-Leverage

  • Zipf's law: top 1% of queries = 20–30% of all traffic
  • "weather today", "youtube", "google" searched millions of times/hour
  • Cache hit avoids FULL index fan-out → massive latency + compute savings
  • 25–30% hit rate removes 30% of shard load entirely

Cache Key

Key  = hash(normalised_query_string)
         → lowercase, trimmed, sorted tokens
Value= serialised results list
TTL  = based on query category:
  news queries   → 30 seconds
  static queries → 1 hour
  popular queries→ 5 minutes

Cache Stack

L1: In-process memory cache
      (JVM heap, sub-ms, per instance)
L2: Redis cluster
      (shared, distributed, ~1ms)
L3: CDN (for static result pages, rare)

Cache Invalidation

  • TTL-based expiry (primary strategy)
  • No explicit invalidation on index update — acceptable staleness
  • Breaking news: short TTL (30s) for news-domain queries

Why NOT CDN for Query Results

  • Results are personalised (logged-in user)
  • Highly dynamic — TTL would be too short
  • Redis in-process cache is more flexible
Result caching is the single highest-leverage latency optimization in a search engine.

Failure Scenarios & Handling

Crawler Worker Crash

Risk: URLs in-flight are permanently lost
Fix:  URL leasing — worker gets 5-min lease
      → lease expires on crash
      → URL auto re-queued
      Idempotent crawl: re-fetching
      just overwrites stored HTML

Index Shard Down

Risk: queries to that shard → missing results
Fix:  3 replicas per shard (primary + 2)
      Query router auto-fails to replica
      Replica lag: slightly stale content
      (acceptable — eventual consistency)
      If ALL replicas down: partial results
      → never return 500 to users

Index Shard Overloaded

Risk: shard latency spikes → p99 > 200ms
Fix:  Result cache absorbs 30%+ of reads
      Per-shard timeout: 50ms hard limit
      Scatter-gather drops stragglers
      Load shedding on queue depth spike

Duplicate Content Flood

Risk: mirror sites fill index; crowd original
Fix:  SimHash dedup (near-dupes dropped)
      <link rel="canonical"> detection
      Domain trust score: low-trust = low prio

Query Latency Spike Runbook

1. Check cache hit rate — if dropped,
   replay recent popular queries to warm
2. Check shard latency metrics
   → which shard is slow?
3. One shard slow → route to replica
4. All shards slow → delta merge job
   competing for I/O → pause merge
5. Enable scatter-gather early timeout
   (reduce top-K per shard)
6. If still slow: serve from cache only

Spider Trap

Risk: infinite URL generation
Fix:  depth limit (6), per-domain URL cap,
      regex blacklist for session IDs,
      URL normalisation before dedup

Anti-Spam & Search Security

Content Spam Controls

  • Keyword stuffing: detect abnormally high TF for low-value terms
  • Hidden text: white text on white background → penalise page
  • Thin content: pages <100 meaningful words → low crawl priority
  • Cloaking: different HTML for crawler vs. human → permanent ban
  • Detect by comparing crawled HTML vs. rendered HTML (headless browser)

Link Spam Controls

  • Link farm detection: domain with 1000s of outbound links to same target
  • Nofollow: rel="nofollow" on sponsored links — no PageRank passed
  • TrustRank: trust propagates from seed domains (Wikipedia, .gov)
  • Domain age: links from domains <30 days old = near-zero PR

Query Abuse Controls

  • Rate limit per IP and per user (API Gateway)
  • Detect scraping patterns (sequential queries, no dwell time)
  • CAPTCHA challenge after threshold
  • Query length limit (max 64 tokens)
  • Block queries that probe API credentials

Crawler Ethics

MUST do:
  • Respect robots.txt (legal requirement)
  • Honour Crawl-delay directive
  • Identify as known crawler
    (not disguise as browser)
  • Limit requests per domain/sec
  • Back off on 429/503 responses
  • Distribute traffic across IP ranges
Violating robots.txt is a legal and ethical issue. Crawlers that ignore it are blocked or banned.

Senior Q&A — Levels 1 & 2

Q1: "User searches 'jaguar' — animal, car, or NFL team?"

"This is the query intent disambiguation problem. Short answer: return a blended result set, weighted by predicted intent."

  • Session context: previous query "buy" + "car" → car intent
  • Location signal: user near Jacksonville FL → NFL team more likely
  • Query co-occurrence: historically, "jaguar" with no context → 60% car, 30% animal, 10% NFL → weighted blend
  • ML intent classifier: BERT model trained on (query, click) pairs → predict intent distribution
  • Diverse top-10: return mix of all intents for ambiguous queries
  • User's click teaches the system their intent → personalise future results

Q2: "An index shard goes down. What happens?"

"Graceful degradation with replica failover. Every shard has 2–3 replicas."

  • Query router auto-routes to replica via heartbeat health check
  • If ALL replicas down: queries return partial results (missing that shard's docs)
  • Result page silently degrades — NEVER return 500 to users
  • PagerDuty alert fires immediately on full shard loss
  • SLA: 99.99% complete results requires 3 replicas — P(all down) = (0.001)³ ≈ negligible
Key principle: partial results > no results. 1/1000 shards down = users rarely notice.

Senior Q&A — Levels 3 & 4

Q3: "Webpage updates its content — how to re-index without re-crawling all?"

"Differential indexing. When a page is re-crawled (freshness scheduler triggers it), new content replaces old."

  • Lucene: docs are immutable once written to segment
  • Update = tombstone old docId (mark deleted) + insert new docId with new content
  • Merged segments eventually garbage-collect tombstoned docs
  • HTTP If-Modified-Since header: skip re-parsing if 304 Not Modified
  • Triggers: freshness priority scheduler, sitemap ping, RSS/Atom subscription, Search Console request

Q4: "Spammy site creates 10M fake links to boost PageRank — how to stop it?"

"Link quality vs. quantity. Several defences."

  • TrustRank: seed known-good domains (Wikipedia, .gov, .edu). TrustRank propagates outward — only trusted pages can pass PageRank effectively
  • Link farm detection: 10M pages with identical content linking same target → ML spam classifier flags cluster
  • Nofollow attribute: rel="nofollow" = no PageRank passed (for sponsored links)
  • Domain authority decay: domains registered <30 days = near-zero PR contribution until history is established
  • Google: dedicated spam team + ML classifiers + manual penalties via Search Console

2-Minute Whiteboard Summary

1. Crawl   : URL Frontier → Workers → Raw Store
2. Parse   : HTML Parser → text + links + meta
3. Dedup   : SimHash → drop near-duplicates
4. Index   : tokenize/stem → Inverted Index (sharded)
5. Rank    : BM25 at index time + PageRank (batch)
6. Query   : API → spell-correct → stem → expand
7. Fan-out : Planner → all shards parallel (50ms)
8. Merge   : top-K per shard → global rank
9. Cache   : Redis (TTL by query type)
10. Serve  : Snippets → highlight → return
11. Fresh  : Delta index (hourly) + Base (weekly)
12. Ops    : frontier depth + indexing lag +
             shard p99 + cache hit rate
"Crawl everything, index the important parts, rank by relevance and authority, serve under 200ms. The web is always changing — duplicate content is the norm — and every query must complete under 200ms regardless of how many shards we fan out to."
