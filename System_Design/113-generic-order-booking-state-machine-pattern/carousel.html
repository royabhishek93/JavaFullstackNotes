System Design — Booking State Machines

A cancelled order got shipped.

is_cancelled= true
is_shipped= true

Same row. Same moment. Nobody wrote a bug — the design was the bug: 5 independent boolean flags give you 2⁵ = 32 possible combinations, when maybe 8 are actually legal business states.

The Problem

Boolean flags have no single source of truth

Each flag is set by a different service, at a different time, with zero awareness of the others:

is_paidpayment svc
is_shippedwarehouse job
is_cancelledsupport tool
is_refundedfinance job
is_deliveredcarrier webhook

Nothing stops is_cancelled and is_shipped from both being true. There's no code path whose job is "check all five before allowing a change."

Same shape breaks: payments, food delivery, ticket booking, hotel booking, job schedulers, stock trading

DELIVERED & REFUNDED are terminal — no outgoing rows in the transition table

Persistence Pattern

Same transaction, always

orders
status, version
order_status_history
append-only, never edited

1. SELECT ... FOR UPDATE locks the row
2. UPDATE status=?, version=version+1 WHERE version=?
3. INSERT INTO order_status_history(...)
→ same TX. Either both rows change, or neither does.

This is the audit trail support & disputes teams query when a customer says "I was charged but it shows cancelled"

Edge Case #1

Duplicate webhook retry

Warehouse scanner never got its 200 OK → resends the same event.

Event 1
→
CONFIRMED→SHIPPEDlegal, applied, push sent
Event 2retry
→
SHIPPED→SHIPPED?not in table — rejected

Idempotency guard = transition table lookup + version column. No double transition, no duplicate customer notification.

Version conflict rate under concurrent writers: ~0.05–0.2% of transitions, retried with backoff

Out-of-order queue redelivery

Rare, but happens under partition rebalances. Customer cancels while a stale PaymentCaptured event is still in-flight.
