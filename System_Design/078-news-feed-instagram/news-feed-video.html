The Single Most Important Question:
"Cristiano Ronaldo posts. He has 200M followers.
Do you write to all 200M Redis caches?"

Answer: NO — that's the Celebrity Problem.
Hybrid fan-out solves it: push for regular users, pull for celebrities.
Core Challenge
Reads are 100× writes. Pre-compute feeds in Redis. Merge celebrity posts at read time.
Scale
500M DAU · 2B users · 100M posts/day · 115K feed reads/sec

📰 Feed Generation

Push vs Pull vs Hybrid Fan-out

ApproachHow It WorksWrite CostRead CostVerdict
Fan-out on Read
(Pull)		 On feed open: fetch posts from all 500 followees live from DB Cheap — just INSERT post once 500 DB queries per user open × 500M DAU = 250B reads/sec Simple writes. Catastrophically slow reads.
Fan-out on Write
(Push)		 On post: ZADD postId to every follower's Redis cache immediately via Kafka Expensive — N ZADD ops where N = follower count Ultra fast — ZRANGE O(log N) sub-ms Fast reads. Fatal celebrity problem at 200M followers.
Hybrid
(Instagram's approach ✓)		 Push for <10K followers. Skip fan-out for celebrities. Pull celeb posts at read time from hot Redis cache. Moderate — push for 99% of users Fast — ZRANGE + ~10 celeb GET ops at merge Best of both. Solves celebrity problem.
Why hybrid works: 99% of users have <10K followers (cheap push). Celebrities skip fan-out — their posts are cached in a hot Redis key. Users follow ≤10 celebrities on average → 10 Redis GETs at read time. Still under 200ms.
📰 Feed Generation

Fan-out on Write — Push Model Deep Dive

WRITE PATH (Post Creation):
  1. User posts → Post Service saves to Cassandra, publishes to Kafka topic: post-created

  2. Fan-out Worker consumes Kafka event:
     ┌─────────────────────────────────────────────────────────┐
     │  poster.followerCount < 10K?                            │
     │    YES → PUSH model:                                    │
     │      Fetch ALL follower IDs from followers_by_user table │
     │      For each followerId:                               │
     │        ZADD feed:{followerId} score=rankScore postId    │
     │      Score = recency estimate at write time             │
     │      (likes/comments not known yet — use timestamp)     │
     │                                                         │
     │    NO (celebrity) → SKIP fan-out:                       │
     │      LPUSH celeb_posts:{posterId} postId                │
     │      LTRIM celeb_posts:{posterId} 0 99  ← keep latest 100│
     └─────────────────────────────────────────────────────────┘

  3. Fan-out happens AFTER "post-ready" event (not "post-created")
     → ensures media is processed before post appears in feeds

INACTIVE USER OPTIMIZATION:
  Skip ZADD if feed:{followerId} does NOT exist in Redis
  (means user is inactive — no point writing to their cold feed)
  On their next login → cold rebuild from Cassandra (300-500ms once)
Throughput
1,160 posts/sec × avg 300 followers = 348,000 ZADD/sec. Redis cluster handles this easily across 50 shards.
Feed Size Cap
Max 500 postIds per feed ZSET. ZREMRANGEBYRANK evicts oldest when cap exceeded. Prevents unbounded growth.
📰 Feed Generation

The Celebrity Problem

Why pure push fan-out fails at scale:
Cristiano Ronaldo (200M followers) posts once.
Naive approach: 200M × ZADD = 200M Redis writes.
At 1ms/op with 1000 parallel workers → 200 seconds of lag.
His followers see the post 3+ minutes after he posted. Unacceptable.

Solution: Celebrity Pull Path

CELEBRITY THRESHOLD: followerCount >= 10,000

On post creation by celebrity:
  → NO fan-out. Just:
     INSERT post to Cassandra posts table
     LPUSH celeb_posts:{celebId} postId
     LTRIM celeb_posts:{celebId} 0 99    ← hot cache of recent 100 posts

At feed read time (hybrid merge):
  1. GET celeb_followees:{userId}         ← which celebrities does this user follow?
  2. For each celebrity (avg 5-10):
       GET celeb_posts:{celebId}          ← their recent postIds (hot Redis key)
  3. Merge with pre-pushed normal posts
  4. Rank → return top 20

Threshold Transition (Senior Q)

User grows from 9,999 to 15M followers:
  Background job runs daily on follower milestones:
    IF followerCount >= 10K → flag as celebrity in Redis SET: celebrity_users
  Transition is eventual — a few extra fan-out writes during transition are harmless.
  Past fan-out writes age out naturally (ZADD evicts old posts when cap = 500 reached).
  No retroactive cleanup needed. Eventual consistency — not a correctness issue.
📰 Feed Generation

Timeline Cache — Redis ZSET Design

KEY:   feed:{userId}
TYPE:  Sorted Set (ZSET)
VALUE: postId (Snowflake ID — encodes timestamp)
SCORE: ranking score (recency + engagement estimate)

WRITE (fan-out worker):
  ZADD feed:{userId} NX score postId
  ZREMRANGEBYRANK feed:{userId} 0 -501     ← trim to 500 entries (evict oldest)
  EXPIRE feed:{userId} 604800              ← 7-day TTL if user inactive

READ (feed service):
  ZREVRANGEBYSCORE feed:{userId} +inf -inf WITHSCORES LIMIT 0 200
  → returns top 200 candidate (postId, score) pairs for re-ranking

OTHER REDIS KEYS:
  celeb_posts:{userId}      LIST  LPUSH/LTRIM — recent 100 postIds (celebrities only)
  celeb_followees:{userId}  SET   SADD — which of my followees are celebrities
  likes:{postId}            INT   INCR/DECR — atomic like counter
  liked_by:{postId}         SET   SADD/SISMEMBER — idempotency check
  affinity:{uid}:{pid}      FLOAT ML affinity score, TTL=1hr

SNOWFLAKE ID — WHY IT'S THE SCORE:
  postId encodes creation timestamp (41-bit ms epoch + machine ID + sequence)
  Sort by postId = sort by creation time
  No separate created_at column needed in feed cache
  Range queries: postIds older than cursor → ZREVRANGEBYSCORE
Memory math: 500M active users × 500 postIds × 8 bytes = 2 TB. Redis cluster on 50 shards = 40 GB per shard. Comfortable. Inactive user TTL (7 days) keeps actual footprint much lower.
📰 Feed Generation

Feed Ranking — Two-Level Algorithm

Level 1: Candidate Generation (Redis)
  • ZREVRANGEBYSCORE feed:{userId} → top 200 postIds
  • Merge with celeb posts (~10 GET ops)
  • Total candidates: ~200-210 posts
  • Cost: sub-millisecond Redis ops
Level 2: Re-ranking (200 → 20)
  • Recency: hours since posted
  • Engagement: likes + comments + shares per unit time
  • Affinity: how often user interacts with this poster
  • Novelty: filter already-seen postIds
  • Return top 20

Ranking Score Formula

             (likes × 1) + (comments × 3) + (shares × 5)
  score  =  ────────────────────────────────────────────────
                       (hours_since_posted + 2) ^ 1.5

  → Gravity denominator ensures old posts sink over time
  → Comment weight (3×) > like weight (1×): deeper engagement valued more
  → Share weight (5×) highest: viral signal
  → Same gravity formula used by Hacker News — simple and explainable
  → Affinity score (ML): affinity:{viewerId}:{posterId} cached in Redis (TTL=1h)
Why two levels? Can't run ML on all 500 cached postIds in real-time. Level 1 is O(log N) Redis — cheap. Level 2 runs ML re-ranking on just 200 items — small input = sub-100ms. Same pattern used by YouTube, TikTok, Twitter.

  │    Resize: thumbnail (150×150), medium (600px wide)  │
  │    Convert: WebP (50% smaller, same perceptual quality)│

  │                                                      │
  │  Videos:                                             │
  │    Transcode: 1080p, 720p, 480p, 360p variants       │

  → ensures media is ready before post appears in feeds

  ~250 global edge PoPs. Pull-through cache.
  First request: CDN fetches from S3 (~100ms). Cached at edge.
  Subsequent requests: served from PoP (~5ms). 90%+ of reads here.
⚙️ Features & LLD

Cursor-Based Pagination

Offset Pagination — Why It Fails
GET /feed?page=1&pageSize=20
GET /feed?page=2&pageSize=20

Problem:
  Page 1 loads: posts [A, B, C, D ... T]
  New post X arrives (at top of feed)
  Page 2 loads: posts [B, C, D ... T, U]
                        ↑ post B shown again!

  Page drift: new arrivals shift everything down.
  Users see duplicates across pages.
  Also: OFFSET N in Cassandra = full scan to row N.
  Catastrophically slow at large offsets.
Cursor Pagination — The Right Way
GET /feed?cursor=<lastSeenPostId>&limit=20

"Give me 20 posts OLDER than this postId"

Redis: ZREVRANGEBYSCORE feed:{uid}
  (lastSeenPostId-1) -inf LIMIT 0 20

Why stable:
  New posts arrive at top. Cursor points to
  a specific postId in the middle of the feed.
  Loading "next 20 older than cursor" is
  unaffected by new posts at the top.
  No duplicates. Efficient: Cassandra WHERE
  post_id < cursor ORDER BY post_id DESC.

API Response

GET /api/v1/feed?cursor=7234891234560000&limit=20
Response: {
  "posts": [ { postId, author, caption, mediaUrls, likeCount, commentCount } ],
  "nextCursor": "7234891234520000"  ← postId of last item returned
}
// nextCursor null = no more posts (end of feed)
⚙️ Features & LLD

Stories — 24-Hour TTL Design

Stories are separate from the main feed — different TTL, different data model, different display order (chronological by followee, not ranked).

Data Model

Redis key:  stories:{userId}
Type:       ZSET  (score = expiry_timestamp)
Value:      storyId
TTL:        EXPIRE stories:{userId} 86400  ← 24 hours from first story
            ZADD  stories:{userId}  (now + 86400) storyId

Auto-expiry of individual stories:
  On read: ZREMRANGEBYSCORE stories:{userId} 0 (now)  ← evict expired
  → only shows stories where score (expiry) > current_time
  → no background job needed — lazy cleanup at read time

Story media: same pipeline as posts (S3 → CDN)
  But: CDN TTL set to 24 hours (matching story TTL)
  After 24hr: CDN evicts + S3 lifecycle rule deletes media

Stories feed (who has active stories?):
  GET celeb_followees + GET followees_by_user
  For each followee: ZCARD stories:{followeeId} > 0?
  → if yes: show story ring on their profile avatar

Viewed stories:
  story_views:{storyId}  SET of viewerIds  (TTL = 24hr)
  Prevents re-showing already-viewed stories
Why ZSET (not simple key)?
A user can post multiple stories. ZSET holds all storyIds for a user with individual expiry scores. Single key per user.
No fan-out for stories
Stories are pulled at open time. Simpler than feed. Users pull stories of everyone they follow — the set is small enough.
⚙️ Features & LLD

Like & Comment Counters — Redis INCR + Async DB Sync

LIKE FLOW (must be idempotent — prevent double-likes):

Redis data structures per post:
  likes:{postId}       INT  → atomic INCR counter
  liked_by:{postId}    SET  → set of userIds who liked

On "like" request from Alice:
  Lua script (atomic — runs as single Redis transaction):
    IF SISMEMBER liked_by:{postId} aliceId:
      return 0  (already liked → return 409 to client)
    ELSE:
      SADD liked_by:{postId} aliceId
      INCR likes:{postId}
      return 1  (success → return 200 to client)

On "unlike" request:
  Lua script:
    IF NOT SISMEMBER liked_by:{postId} aliceId:
      return 0  (not liked → return 409)
    ELSE:
      SREM liked_by:{postId} aliceId
      DECR likes:{postId}
      return 1
Async Write-back to Cassandra
Batch job every 5 minutes:
Reads likes:{postId} from Redis →
UPDATE posts SET like_count=N WHERE post_id=?

Why not per-like write: 100M likes/day = 1,157/sec write contention on single Cassandra row. Redis INCR handles 100K+/sec per key easily.
Comment Counts
Comments stored in Cassandra:
comments table (partition=post_id)

comment_count:{postId} INCR in Redis
Same write-back pattern.
Comment list: cursor pagination on comment_id TIMEUUID (time-ordered clustering key).

→ single-row lookups by postId are O(1)
→ range queries: WHERE post_id < cursor

followee_id  UUID  (PARTITION KEY)
follower_id  UUID  (CLUSTERING KEY)
created_at   TIMESTAMP

Query: SELECT follower_id
  FROM followers_by_user
  WHERE followee_id = ?
→ returns ALL followers of X
→ used by fan-out worker

followees_by_user (Cassandra)
follower_id  UUID  (PARTITION KEY)
followee_id  UUID  (CLUSTERING KEY)

Query: SELECT followee_id, is_celebrity
  FROM followees_by_user
  WHERE follower_id = ?
→ used by feed service at read time
Why TWO follow tables? Cassandra queries are partition-key bound. "Who follows X?" needs partition=followee. "Who does X follow?" needs partition=follower. You CANNOT efficiently answer both from one table. Two tables = two query patterns = perfect Cassandra fit.
comments (Cassandra)
post_id (PARTITION), comment_id TIMEUUID (CLUSTERING — time-ordered), user_id, text, is_deleted
users (MySQL)
user_id, username, email, password_hash, bio, profile_pic_url, follower_cnt, is_celebrity. MySQL for ACID — auth, account security, settings.

📈 Scaling

Redis ZSET vs Cassandra for Timeline

Redis Sorted Set (Production Choice)
Key: feed:{userId}
ZADD feed:{userId} score postId
ZREVRANGE feed:{userId} 0 199

Latency: O(log N) — sub-ms per read
Throughput: 100K+ ZRANGE ops/sec per shard
Memory: ~2 TB for 500M users (with TTL)
Cluster: shard by userId hash

Pros:
  Sub-millisecond reads
  Built-in sorted order (by score)
  ZREVRANGE = perfect for ranked feed
  INCR, SET, LIST all in same cluster

Cons:
  RAM-only → expensive at full scale
  No persistence without AOF/RDB overhead
  Max 500 entries per feed (by design)
Cassandra Timeline Table (Alternative)
Table: user_feed
  user_id    UUID  (PARTITION)
  post_id    Snowflake (CLUSTERING DESC)
  score      FLOAT

SELECT post_id FROM user_feed
  WHERE user_id = ?
  AND post_id < cursor
  LIMIT 20;

Latency: ~5-20ms per read (disk + network)
Throughput: 345K reads/sec needs 100s of nodes
Storage: disk → much cheaper than RAM
Persistence: built-in

Cons:
  10-100× slower than Redis for reads
  At 345K feed reads/sec: needs massive cluster
  Write amplification same as Redis fan-out
Verdict: Redis wins for the pre-computed feed cache because feed reads are latency-critical (target <200ms including ranking + DB fetch for post details). Cassandra works as a cold-rebuild fallback when Redis key expires. At 500M DAU scale, 5-20ms per Cassandra read × 345K reads/sec would require a massive cluster. Redis cluster is the correct production choice.
🎯 Interview Prep

Senior Q&A 1 — Celebrity Threshold Transition

Q: "You set the celebrity threshold at 10K followers. Cristiano Ronaldo gains a follower DURING a fan-out operation. Now you need to reclassify him. How do you handle the transition?" 
A: The threshold is NOT applied in real-time at exact follower counts.

   We maintain a celebrity_users SET in Redis (or a flag in the users table).
   A background job runs daily — OR triggered at follower milestones:
     IF user.followerCount crosses 10K threshold:
       SET is_celebrity = true in MySQL users table
       SADD celebrity_users {userId} in Redis
       Remove from push fan-out path going forward.
     Keep historical push-fanned posts in followers' feeds (don't delete them).

   During transition window (before job runs):
     A few extra fan-out writes may occur. Acceptable.
     Brief overlap is harmless — we don't need atomic instant reclassification.

   Key insight: This is an EVENTUAL CONSISTENCY problem, not a correctness problem.
   A few extra writes during transition << building complex atomic reclassification logic.

   Past fan-out writes age out naturally:
     When feed:{followerId} reaches 500-entry cap → oldest entries evicted.
     No active cleanup of historical fan-out writes needed.
What the interviewer is testing: Do you understand that eventual consistency is acceptable here? Can you avoid over-engineering a solution that doesn't need strong consistency?

Senior Q&A 2 — Race Conditions (Double Like)

Q: "Alice likes a post. The request fails mid-flight. She taps like again. The post now shows 2 likes from Alice. How do you prevent this double-like?" 
A: Idempotency via Redis Lua script (atomic check-and-set).

   Two data structures per post:
     likes:{postId}     INT  → atomic INCR counter
     liked_by:{postId}  SET  → set of userIds who liked

   On LIKE action (Lua script — runs atomically on Redis):
     if redis.call('SISMEMBER', 'liked_by:' .. postId, userId) == 1 then
       return 0  -- already liked: return 409 CONFLICT to client
     end
     redis.call('SADD', 'liked_by:' .. postId, userId)
     redis.call('INCR', 'likes:' .. postId)
     return 1  -- success

   On UNLIKE action (Lua script):
     if redis.call('SISMEMBER', 'liked_by:' .. postId, userId) == 0 then
       return 0  -- not liked: return 409
     end
     redis.call('SREM', 'liked_by:' .. postId, userId)
     redis.call('DECR', 'likes:' .. postId)
     return 1

   WHY LUA SCRIPT: Redis executes Lua atomically — no other command
   runs between SISMEMBER and SADD/INCR. Eliminates race condition.
   Without Lua: two concurrent requests could both pass SISMEMBER
   check before either writes SADD → double-like possible.

Senior Q&A 3 — Post Deletion

Q: "User deletes a post. But their post was already fan-out pushed to 100,000 followers' Redis feed caches. How do you remove it?" 
A: Three options — Instagram uses Option 1 (lazy delete):

   Option 1 — Lazy Delete (Instagram's approach) ✓
     Mark post as DELETED in Cassandra (is_deleted = true).
     When feed is rendered: filter out deleted postIds before returning to client.
     Simple. No mass Redis cleanup. Deleted posts NEVER shown to users.
     Cost: 1 extra Cassandra read per post in top-20 (trivial).

   Option 2 — Active Cleanup (expensive, rarely needed)
     On delete: scan all 100K followers' feed caches, ZREM postId from each.
     100K ZREM operations per delete: expensive but fast if deletions are rare.
     Too expensive at scale for the 99% of posts never deleted.

   Option 3 — Tombstone TTL
     SET deleted:{postId} 1 EX {feedTTL}    ← Redis key with expiry
     Feed rendering: SISMEMBER deleted:{postId} → exclude if true.
     Middle ground — still O(1) check per post.

   RECOMMENDED ANSWER: Option 1 (lazy delete).
     99% of posts are never deleted.
     Adding a check for the 1% deletion case at read time:
       ~1ms extra per 20-item feed. Trivial overhead.
     Clean, simple logic. No background cleanup jobs.
     Correctness: deleted post is never shown (Cassandra authoritative).

"To summarize, Instagram's core design is driven by 5 decisions: 1. WRITE PATH: Post Service saves to Cassandra, publishes to Kafka. Client uploads media directly to S3 via presigned URL. STORAGE: Cassandra (posts, social graph — high write throughput, no JOINs). Redis (feed cache, like counters, celeb cache — sub-ms reads). MySQL (users — ACID).
