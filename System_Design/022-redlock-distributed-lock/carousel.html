5 Bank Vaults — The Redlock Analogy

Imagine 5 bank vaults (Redis nodes). To claim a lock, you must physically lock at least 3 of 5 (majority). Vaults 4 & 5 can crash — you still hold majority, lock stays valid.

▼
Majority = 3 of 5 locked → LOCK ACQUIRED (survives 2 node failures)

Why not just lock ONE vault (simple Redis SETNX)?

If that single Redis node crashes while you hold the lock: either everything gets stuck, or the lock vanishes and another process grabs it — two processes now run the "exclusive" operation simultaneously.

Even Redlock isn't bulletproof: if your process pauses longer than the TTL (GC pause), the lock expires and someone else takes it. The defense is a fencing token — covered later in this deck.

Fix — Lua Script Atomic Check-and-Delete

SET lock:payment "random_token_A" EX 30 NX

-- Lua (atomic):
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
-- Only deletes if token matches: you only delete YOUR lock
The Algorithm

Redlock: 5 Independent Redis Nodes

SET ok
R
Node 3
SET ok

timeout
R
Node 5
timeout
1. t_start = now_ms()
2. for each of 5 nodes (parallel):
     SET lock:key <token> PX 10000 NX   (~50ms timeout/node)
3. acquired_count = successful SETs
4. elapsed = now_ms() - t_start
   clock_drift = max(2ms, elapsed * 0.01)     # 1% + 2ms
   remaining_validity = 10000 - elapsed - clock_drift
   if acquired_count >= 3 AND remaining_validity > 0:
       LOCK ACQUIRED — valid for remaining_validity ms
   else:
       release partial locks (Lua), random backoff, retry
5. Release: Lua check-and-delete on all 5 nodes
Majority rule: need ⌊N/2⌋ + 1 = 3 of 5 successful SETs, AND remaining_validity > 0.
Fencing Tokens

Fencing Tokens — Rejecting Stale Writes

Client B

Acquires Redlock, token=34
t=10

▼
Storage: last_seen_token=34 → 33 < 34 → REJECTED [SAFE!]
Fencing token = monotonically increasing integer from the lock service. Storage rejects any write where token < highest_seen_token. ZooKeeper: zxid. etcd: lease revision. Redlock does NOT provide fencing tokens natively — must add externally (e.g. Redis INCR).

Production Patterns

Redisson · ShedLock · PostgreSQL Advisory

Redisson RedissonRedLock (Java)

RedissonRedLock redLock = new RedissonRedLock(lock1,lock2,lock3,lock4,lock5);
boolean ok = redLock.tryLock(200, 30_000, TimeUnit.MILLISECONDS);
if (ok) { try { runBillingJob(); } finally { redLock.unlock(); } }

ShedLock (Spring @SchedulerLock)

@Scheduled(cron = "0 0 * * * *")
@SchedulerLock(name="billing_job", lockAtMostFor="PT30M", lockAtLeastFor="PT5M")
public void runBillingJob() { billingService.processAllPendingInvoices(); }

PostgreSQL Advisory Lock

@Transactional
public void processPayment(long id){
  jdbc.execute("SELECT pg_advisory_xact_lock(" + id + ")");
  // ... process ... auto-released on commit/rollback
}
// non-blocking: pg_try_advisory_xact_lock(id) -> true/false
Heartbeat Pattern

Extending TTL for Long-Running Jobs

Lock TTL = 30s. Heartbeat thread resets TTL every 10s (1/3 interval).
boolean acquired = redis.set(key, token, nx().px(30000));
if (acquired) {
  heartbeat.scheduleAtFixedRate(() -> {
    if (token.equals(redis.get(key))) redis.pexpire(key, 30000);
  }, 10, 10, SECONDS);
  try { runLongDataExport(); }        // may take 5 min
  finally { heartbeatTask.cancel(false); /* Lua release */ }
}
t=0 ──▶ t=10 (renew) ──▶ t=20 (renew) ──▶ t=30 (renew) ──▶ job done, release
