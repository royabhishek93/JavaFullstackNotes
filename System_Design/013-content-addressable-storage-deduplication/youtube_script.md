Today I'm showing you content-addressable storage, and why it gives you deduplication completely for free."

[Screen cue: A 1GB file icon with a tiny 4MB highlighted "changed chunk" glowing, next to a "1GB upload avoided" checkmark.]

## THE PROBLEM (0:30–2:00)
"Think about it this way — normal storage names files by what a human calls them: vacation-dot-jpg, summer-photo-dot-jpg, photo-dot-jpg. If three different users upload the exact same two-megabyte photo under three different names, you store it three separate times — six megabytes for one unique file. Content-addressable storage flips this: instead of naming the file by what the user calls it, you compute a cryptographic hash — SHA-256 — of the file's actual bytes, and THAT hash becomes the storage address. If two uploads produce the identical hash, they ARE the identical content, so you only ever store it once. This exact idea underpins Google Drive and Dropbox's deduplication, every object in a Git repository, every layer of a Docker image, and the entire architecture of IPFS."

[Screen cue: Draw three users uploading the "same" photo under different filenames, all converging into ONE stored blob labeled with its SHA-256 hash.]

## THE SOLUTION (2:00–5:00)
"Now watch what happens step by step. User A uploads vacation-dot-jpg — the system computes its hash, checks if that hash already exists in the blob store, finds nothing, stores the two megabytes at a path derived from the hash, and writes a small metadata record linking Alice's filename to that hash. User B uploads summer-photo-dot-jpg — same bytes, same hash — the system checks, finds the blob ALREADY exists, stores zero additional bytes, and just writes a metadata record pointing Bob's filename at the existing hash. Three uploads, one physical copy, sixty-six percent storage saved. But real systems go one level deeper: chunked content-addressable storage. Dropbox splits every file into four-megabyte chunks, and hashes each chunk independently. When you edit page five of a one-gigabyte file, only the chunk containing that edit gets a new hash — the other two hundred fifty-five chunks are completely unchanged and already sitting in storage. Only that one four-megabyte chunk needs to be uploaded and stored. The file's metadata is simply an ordered list of chunk hashes, and reconstructing the file means fetching each chunk by its hash and concatenating them in order."

[Screen cue: Draw a 1GB file split into a grid of 256 small chunk boxes, with just ONE chunk highlighted red as "changed" and the rest green as "unchanged, already stored".]

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"Here's the trap: teams implement content-addressable storage but forget the garbage collection half of the problem — you can't just delete a blob when one user deletes their file, because two OTHER users might still reference that exact same blob. The fix is reference counting: a separate table tracks how many metadata records point at each content hash. When Alice deletes her photo, the reference count for that hash drops from three to two — the actual bytes stay completely intact because Bob and Carol still reference them. Only when the reference count reaches exactly zero does a garbage collection pass reclaim the physical storage — this is precisely how Git's own garbage collector decides which objects are safe to prune. Second trap, and this one is a security consideration people frequently miss: because blobs are SHARED across users by design, you must still verify OWNERSHIP before serving a blob reference — a user can't feasibly guess another user's SHA-256 hash to steal their file, since the hash space is astronomically large, but you still need to check that the requesting user actually has a metadata record pointing at that blob, not just that the blob exists somewhere in storage. And a subtler trap: naive content-addressable storage hashes the WHOLE file, so editing even one byte anywhere produces a completely different hash for the entire file, forcing a full re-upload — this is exactly why the chunk-level approach exists, splitting the file first and hashing each piece independently, so a tiny edit only invalidates the one small chunk that actually changed."

[Screen cue: Split diagram — a reference-count table showing count dropping from 3→2→1→0, then garbage collection reclaiming the blob only at zero; then whole-file hashing (1 tiny edit = 1 new hash for everything) vs chunk hashing (1 tiny edit = 1 new chunk hash only).]

## REAL WORLD (8:00–9:30)
"Think about a cloud-storage platform serving India at scale, similar to Google Drive or a Google Drive clone — with hundreds of millions of users uploading common templates, screenshots of the same viral WhatsApp forward, or the same shared PDF, deduplication rates of twenty to fifty percent are completely typical, meaning a platform that looks like it stores one petabyte of logical data might physically store only six hundred to eight hundred terabytes. Think about how developers pull Docker images every single day — if two different microservice images both use the same Ubuntu base layer, that base layer is stored and downloaded exactly ONCE across every image that references it, which is why `docker pull` for your fifth microservice image is often nearly instant, since most of its layers are already on disk. And think about a Notion or Google Docs-style version history feature — storing one hundred versions of a ten-megabyte document doesn't cost one gigabyte, because unchanged blocks are shared across every version; it costs roughly ten megabytes plus just the handful of blocks that actually changed."
