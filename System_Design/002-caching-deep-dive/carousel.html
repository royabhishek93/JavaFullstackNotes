No cache: 1,000 users → 1,000 identical 2s DB queries. With cache: 1 query, then 1ms responses for everyone else.

Cache-Aside (Lazy Loading)

Pattern 1 — Most Common

App checks Redis first. Miss → load from DB → store with TTL (e.g. 5 min).

✓ Only caches what's actually requested (efficient memory use)

✕ Cache miss = 2 trips (cache + DB) — latency spike on first request

Use for: product catalog, user profiles, configuration data

Write-Through

Pattern 2 — Always Fresh

Every write updates the DB AND Redis simultaneously.

✓ Cache is never stale

✕ Every write hits both stores (more write latency); caches data that may never be read

Use for: inventory counts, stock levels — must be fresh for purchase decisions

Write-Behind (Write-Back)

Pattern 3 — Deferred Writes

Writes go to Redis only. A background process flushes to the DB every N seconds.

✓ Ultra-fast writes; fewer DB transactions (batched)

✕ Data loss if cache crashes before flush — not durable

Use for: view counters, like counts — losing 10s of data is acceptable

Refresh-Ahead

Pattern 4 — Proactive Warming

Before a hot entry expires, a background job pre-fetches fresh data — the cache never actually goes cold.

✓ Zero misses on hot items; predictable, scheduled DB load

Use for: top 10,000 products during a sale, refreshed every ~4 minutes

Cache Stampede (Thundering Herd)

The #1 Production Trap

Popular key expires under load → thousands miss simultaneously → all hammer the DB → CPU 100% → 10s+ latency → crash.

Fix 1: TTL jitter — randomize 270-330s instead of a flat 300s, spreads expiry over 60s

Fix 2: Mutex lock — only 1 thread refreshes, others wait ~50ms then read fresh cache

Fix 3: Caffeine refreshAfterWrite — serves stale instantly while refreshing in the background

Cache Penetration & CDN Leaks

Two More Traps

Penetration: attacker spams non-existent IDs → guaranteed miss every time → DB overload. Fix: cache the NULL result, or use a Bloom filter (10M capacity, ~1% false-positive) to reject bad IDs before Redis.

CDN leak: caching a page with "Welcome back, Abhishek!" means the next visitor sees Abhishek's session. Fix: cache only the shell/static assets; fetch user-specific data client-side via an uncached API.

Decision Tree & Interview Answer

Quick Reference

Read-heavy, tolerate brief staleness? → Cache-Aside

Must never be stale (inventory)? → Write-Through

High-frequency, loss-tolerant (counters)? → Write-Behind

Predictably hot (sale items)? → Refresh-Ahead

"I layer caching: CDN for static assets, Redis for shared application data, Caffeine local cache for the hottest items. Cache-aside for catalogs, write-through for inventory, write-behind for counters. The most dangerous failure mode is cache stampede — fix with TTL jitter, mutex locks, or Caffeine's refreshAfterWrite. Cache penetration is fixed by caching null results or a Bloom filter."
