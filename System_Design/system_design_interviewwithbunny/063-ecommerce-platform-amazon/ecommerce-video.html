Opening — When Interviewer Says "Design Amazon"

"The core challenge here is inventory consistency — preventing overselling when thousands of users simultaneously attempt to buy the last item in stock. Unlike most systems where eventual consistency is fine, the checkout flow requires strong consistency: we cannot let two users both successfully purchase the same last unit.

Every design decision in the checkout path is driven by: 'what happens if this step fails — does inventory stay permanently locked?'

Let me clarify requirements first."

Product Catalog — MongoDB + Flexible Schema

Why MongoDB (not PostgreSQL)?

Different product types have completely different attributes:

  • Phones: RAM, storage, processor, display size
  • Books: author, ISBN, publisher, edition
  • Clothing: size, color, material, fit

Flexible schema avoids 200-column sparse tables or EAV anti-pattern. New category = just insert a document with new fields.

Product Hierarchy

  • Category → Electronics > Phones
  • Product Group → iPhone 15 Pro
  • SKU / Variant → 256GB, Titanium Black
  • Seller Listing → price, qty per seller

MongoDB Document Schema

{ "_id": "PROD_ABC", "title": "Apple iPhone 15 Pro", "category": "electronics/phones", "price": 999.99, "images": ["s3://bucket/img1.jpg"], "rating": 4.7, "reviews_count": 12450, "specifications": { // FLEXIBLE FIELD "RAM": "8GB", "storage": "256GB", "chip": "A17 Pro", "display": "6.1-inch OLED" }, "variants": [{ "sku": "IP15P-256-BLK", "color": "Titanium Black", "storage": "256GB" }] }

Search — Elasticsearch + CDC Pipeline

ES Query Strategy

GET /products/_search { "query": { "bool": { "must": [{ "multi_match": { "query": "laptop", "fields": ["title^3", "description", "brand"] // title^3 = 3x boost }}], "filter": [ {"term": {"category": "electronics"}}, {"range": {"price": {"lte": 1000}}}, {"range": {"qty": {"gt": 0}}} ] }}, "aggs": { // Faceted filter counts "brands": {"terms":{"field":"brand"}}, "price_ranges": {"range":{ "field":"price", "ranges":[{"to":500},{"from":500,"to":1000}] }} } }

CDC Sync Pipeline

MongoDB product update

→ oplog change stream (Kafka Connect MongoDB Source)

→ Kafka topic: product.changes

→ ES indexer: bulk API, 100 events/2s batch

Lag: 1–2 seconds — eventual, acceptable

If ES down → indexer pauses at Kafka offset, replays on recovery. No data lost. No code change in Product Svc.

Redis Search Cache

  • Key: search:{hash(query+filters+sort)}
  • TTL: 10 minutes · Hit rate: 60–70%
  • Top 10K queries pre-warmed 1hr before sales
  • Cluster: 10 nodes, 5 primary shards → 100K QPS

Inventory Management — Preventing Overselling

Key insight: Never deduct qty during checkout. Use reserved_qty column. Actual deduction happens ONLY after payment.success webhook.

Layer 1 — Redis SETNX (1ms pre-filter)

# Fast early rejection — before touching DB SETNX lock:inventory:{product_id} {session_id} EX 30 → Returns 1: lock acquired, proceed to DB → Returns 0: another checkout in progress → HTTP 409 "Product being reserved" # WHY: Rejects 9,999 of 10,000 concurrent # checkouts in 1ms without touching Postgres # EX 30 = auto-expire prevents deadlock # if service crashes mid-checkout

Layer 2 — PostgreSQL FOR UPDATE

-- ACID row-level exclusive lock SELECT qty, reserved_qty FROM inventory WHERE product_id = ? FOR UPDATE; available = qty - reserved_qty IF available < cart_qty: ROLLBACK DEL redis lock RETURN 400 "Out of stock" UPDATE inventory SET reserved_qty = reserved_qty + cart_qty COMMIT;
available = qty − reserved_qty ·  Deduct qty ONLY after payment.success ·  Background job releases stale reservations after 15 min

Cart Service — Redis Cache + PostgreSQL Source of Truth

Add to Cart — Upsert Pattern

-- PostgreSQL: handles concurrent add-to-cart INSERT INTO cart_items (cart_id, product_id, qty, price) VALUES (?, 'PROD_ABC', 2, 899.00) ON CONFLICT (cart_id, product_id) DO UPDATE SET qty = cart_items.qty + 2, updated_at = now(); -- Redis write-through cache HSET cart:{userId} product:ABC '{"qty":2,"price":899}' EXPIRE cart:{userId} 604800 -- 7 days

Get Cart — Redis First

1. HGETALL cart:{userId} → <1ms on hit

2. On miss → SELECT from PostgreSQL, warm Redis

Cart keyed by user_id, not session → cross-device sync on login

Guest → Login Migration

  • Guest cart: Redis only, key=session:{id}, TTL=24h
  • On login: merge guest cart into user's DB cart
  • Conflict resolution: keep higher qty per item

Price Change Handling

  • Cart stores price at time of adding
  • At checkout: re-validate current price from Product Svc
  • Show user: "Price changed $899→$799, continue?"
  • Cart does NOT guarantee stock availability
  • Real inventory check happens at checkout ONLY

Flash Sale — 1M Users, 1000 Units, Zero Overselling

Pre-Sale Prep (1hr before)

  • Pre-allocate flash_sale_inventory table — 1000 rows, status='available'
  • Warm Redis + CDN caches for sale products
  • Auto-scale Checkout Svc: 50 → 250 instances
  • Redis counter: SET flash_sale:{pid}:remaining 1000

Virtual Waiting Room

  • Cloudflare Waiting Room gates users at 1K/sec
  • Released users get JWT token (5-min TTL)
  • Backend rejects requests without valid token
  • Blocks bots and thundering herd on DB

SKIP LOCKED Checkout — No Contention

-- Step 1: Redis instant sold-out check (1ms) DECR flash_sale:{pid}:remaining IF result < 0: RETURN "Sold out" // no DB hit -- Step 2: PostgreSQL — each user grabs -- next UNLOCKED row, no blocking! BEGIN; SELECT queue_position FROM flash_sale_inventory WHERE product_id = ? AND status = 'available' ORDER BY queue_position LIMIT 1 FOR UPDATE SKIP LOCKED; // KEY CLAUSE UPDATE flash_sale_inventory SET status='reserved', user_id=?, reserved_at=NOW() COMMIT; -- Background: release if not paid in 5 min

Recommendation Engine — 30–40% of Revenue

Strategy 1 — Collaborative Filtering

Item-based ("Users who bought X also bought Y"):

Co-purchase matrix: count how often A and B are purchased together. Jaccard similarity = co-purchases / sqrt(total_A × total_B)

ALS Matrix Factorization: Sparse 100M users × 10M products interaction matrix → user_factors × product_factors. Top 100 recs/user stored in Redis, Spark job nightly.

Strategy 2 — Content-Based

BERT embeddings on (title + description + category) → 768-dim vector per product

User profile vector = avg of recently viewed product vectors

ES kNN search → products nearest to user profile vector

Hybrid Scoring Formula

final_score = 0.4 × collaborative_filter + 0.3 × content_based + 0.2 × trending (24h views) + 0.1 × business_rules (margin boost, overstock boost) Return top 20 by final_score Apply diversity (mix categories)

Serving Architecture

  • Pre-compute: nightly Spark batch → SET recs:{uid} Redis TTL 24h
  • API: Redis lookup + trending blend = <100ms p95
  • Cold-start users: global trending + editorial picks
  • A/B test: 50/50 split → track CTR + conversion rate

📈 Scaling & Trade-offs

Scaling Strategy — Microservices + CQRS

Microservices Split

  • User Svc — auth, profile, addresses (MySQL)
  • Product Svc — catalog CRUD (MongoDB)
  • Search Svc — ES queries + Redis cache
  • Cart Svc — PostgreSQL + Redis HASH
  • Checkout Svc — orchestrator, stateless
  • Inventory Svc — qty source of truth (Postgres)
  • Payment Svc — Stripe integration
  • Notification Svc — email/SMS/push via Kafka

CQRS for Read Scale

Write path: MongoDB (product writes) → Kafka CDC → ES indexer

Read path: ES handles 100K QPS search reads independently of MongoDB write load

Order CQRS: MySQL primary for writes → read replica for order history queries

Horizontal Scaling Points

  • Checkout Svc: stateless → 5–100× scale for flash sales
  • Search Svc: stateless → scale behind ALB
  • ES cluster: 10 nodes, 5 primary shards, auto-rebalance
  • Kafka: partition-level parallelism per consumer group
  • Notification Svc: 20 consumer workers for burst events

Connection Pooling (PgBouncer)

10 Checkout instances × 200 logical connections = 2000 logical

→ PgBouncer maps to 200 actual DB connections

PostgreSQL max_connections = 5000. Prevents exhaustion during 100× scale-up.

🎯 Interview Prep

Senior Trap Q1 — "How do you prevent overselling during a flash sale?"

Wrong answer: "Use optimistic locking / version number." At 10K concurrent users on 1 item, optimistic locking causes thundering herd — all fail, all retry, DB is overwhelmed.

Correct Answer — 5-Layer Defense

1
Virtual Waiting Room — gates users at 1K/sec. 99% of concurrent traffic rejected before hitting any service.
2
Redis DECR counter — DECR flash_sale:{pid}:remaining in <1ms. Instant sold-out detection, no DB involved.
3
Redis SETNX lock — one checkout at a time per product. Rejects 9,999/10,000 concurrent checkouts in 1ms before touching PostgreSQL.
4
PostgreSQL SELECT FOR UPDATE — ACID row lock. Even if Redis lock expired, DB guarantees only one transaction modifies reserved_qty at a time.
5
reserved_qty column — stock held in checkout window. Deducted ONLY after payment.success. Payment failure = release reservation, inventory auto-restores.
Say this: "The key insight is never deducting qty during checkout — only incrementing reserved_qty. Actual qty deduction happens after payment confirmation. If anything fails, inventory auto-restores via background job at 15-minute timeout."
🎯 Interview Prep

Senior Trap Q2 — "How do you handle cart abandonment at scale?"

Context: 60–70% cart abandonment rate industry-wide. At 10M MAU, abandoned cart recovery can drive 5–15% revenue lift.

Detection Pipeline

  • Kafka event: cart.abandoned published when user active >30 min ago AND cart not checked out
  • Scheduled job queries Redis for carts with TTL >1 day + no recent checkout attempt
  • Filter: only users opted into marketing communications

Recovery Sequence

  • T+1hr: push notification "Items waiting in cart!"
  • T+24hr: email with cart summary + current prices
  • T+48hr: 5–10% coupon for high-value carts (>$100)
  • Subject line personalised via ML model (+23% open rate)

Scale Math

  • 10M users × 70% abandon = 7M abandoned carts/day
  • Kafka consumer group: 20 workers @ >100K events/sec
  • SES bulk email API: 10K emails/batch, rate-limited
  • Push via FCM/APNs — fire-and-forget, no ack needed

Key Design Point

  • Abandoned cart does NOT reserve inventory
  • Only checkout triggers reservation
  • Recovery email includes: "Only 3 left in stock!" urgency signal
  • Urgency signal drives 40% higher CTR on recovery emails

Payment Flow — Idempotency & Webhook Safety

Payment Initiation

// Checkout Svc → Stripe stripe.paymentIntents.create({ amount: 149999, // in cents currency: 'usd', metadata: { order_id: 'ORD_123', user_id: 'USR_456' }, idempotency_key: 'ORD_123' // order_id AS idempotency key // Stripe deduplicates on their end }) → returns { client_secret, payment_url } → Store PENDING in payments table → Return payment_url to client

Failure Scenarios

  • Payment declined: release reserved_qty, notify user to retry
  • Stripe webhook retry: retries up to 3 days — idempotency check handles duplicates
  • DB crash mid-webhook: ROLLBACK → Stripe retries → idempotency prevents double-process
  • Double-charge prevention: UNIQUE constraint on payments(order_id)

Webhook Handler — The Critical Path

POST /webhooks/payment (from Stripe) 1. Validate HMAC signature stripe.webhooks.constructEvent(payload, sig_header, webhook_secret) REJECT if invalid → prevents forged webhooks 2. Idempotency check SELECT * FROM payments WHERE payment_id = {event.id} IF status='SUCCESS': RETURN 200 OK 3. SERIALIZABLE transaction UPDATE payments SET status='SUCCESS' UPDATE orders SET status='CONFIRMED' UPDATE inventory SET qty = qty - order_qty, reserved_qty = reserved_qty - order_qty DELETE FROM cart_items COMMIT; 4. Publish Kafka payment.success + order.confirmed 5. RETURN 200 → Stripe stops retrying

Returns & Refunds — State Machine + Inventory Restocking

Return State Machine

User requests return (30-day window) │ ▼ RETURN_REQUESTED │ (seller/ops approves within 24h) ▼ RETURN_APPROVED + prepaid label generated │ (carrier scans pickup) ▼ ITEM_IN_TRANSIT │ (warehouse receives item) ▼ ITEM_RECEIVED → quality check │ ├─ QC PASS ──► REFUNDED │ inventory.qty += returned_qty │ stripe.refunds.create(payment_intent_id) │ └─ QC FAIL ──► PARTIAL_REFUND or REJECTED notify user with reason + photos

Refund Processing

  • Stripe: stripe.refunds.create({payment_intent_id})
  • Partial refund: pass amount parameter
  • Timeline: 5–7 business days to original payment method
  • Idempotent: check refund_id before creating new refund

Inventory Restocking

  • On QC pass: UPDATE inventory SET qty = qty + returned_qty
  • Publish inventory.updated → Kafka → ES re-index qty → Redis invalidate
  • Graded returns: refurbished items → separate warehouse_id with discounted price listing
  • Defective items: qty NOT restored, write-off in inventory audit

Scale Considerations

  • Return rate: 5–30% by category (clothing highest)
  • 1M orders/day × 15% = 150K returns/day
  • Separate Returns Service — decoupled from Order Svc
  • Kafka: order.return_approved → Warehouse generates label
  • SLA: refund initiated within 24hr of QC pass

Interview Cheat Sheet — Phrases That Win the Round

Always Say These

  • Inventory: "reserved_qty is a two-phase commit — increment during checkout, decrement ONLY after payment.success"
  • Locks: "Two-layer: Redis SETNX (1ms pre-filter) + PostgreSQL FOR UPDATE (ACID guarantee)"
  • CDC: "Product Svc doesn't know about ES — CDC decouples them, enables replay on ES recovery"
  • Idempotency: "UNIQUE constraint on payments(order_id) + HMAC webhook signature validation"
  • Kafka: "Decouples checkout from notifications — one slow consumer can't block order confirm"

Never Say These

  • "Use eventual consistency for inventory" (overselling)
  • "MongoDB for orders" (needs strong ACID)
  • "Update qty synchronously in checkout" (payment may fail)
  • "Redis as source of truth for stock" (can lose data on crash)
