🎬 Opening

Opening Script — The Hardest Problem

Say This to Your Interviewer

"Google Docs looks simple — it's just a text box. But the hardest problem is: two users type at the exact same cursor position simultaneously. Who wins? How do both clients converge to the same document without losing either person's edit? That's the core challenge. Everything else — presence, versioning, offline — is secondary."

  • Naive merge: last-write-wins → data loss
  • Locking: only one editor at a time → not collaborative
  • OT: transform ops relative to each other — Google Docs approach
  • CRDT: every character gets a unique ID, ops commute — Figma / Automerge
Senior signal: Mention "strong eventual consistency" — all clients that receive the same set of ops converge to identical state, regardless of apply order.

⚠️ Core Problem

The Concurrent Edit Problem

Document = "abc"  (version 10)

User A: insert('X', pos=0) → "Xabc"   (sends at v10)
User B: insert('D', pos=3) → "abcD"   (sends at v10)

Naive last-write-wins:
  Server applies A first → "Xabc"
  Server applies B at pos 3 of "Xabc" → "XabDc"   ← WRONG
  B intended to insert after 'c', not between 'b' and 'c'

Correct result should be: "XabcD"
Root cause: B's operation was authored against version 10 but applied against version 11 (after A's insert). The position reference is stale. We need to transform B's position to account for A's preceding insert.
🔧 OT

Operational Transformation — How It Works

OT Transform Rules:
  insert before your position  → shift right  (+len)
  delete before your position  → shift left   (-1)
  same position                → server order (timestamp / user_id tiebreak)

Example:
  A: insert('X', 0)  server_version: 11
  B: insert('D', 3)  arrives at v10, server is at v11

  Transform B against A:
    A inserted 1 char at pos 0 (before B's pos 3)
    → B_transformed.pos = 3 + 1 = 4

  Apply B_transformed to "Xabc" → "XabcD" ✓
  • Jupiter protocol: client and server each maintain a state vector; server sequences all ops
  • server_version is the single source of truth — never let clients order ops
  • Critical: without central sequencing, clients diverge permanently
🔧 CRDT

CRDT — Conflict-free Replicated Data Types

Each character gets a unique ID: {site_id, sequence_number}

'abc' → 'a'={1,1}, 'b'={1,2}, 'c'={1,3}

User A (offline): insert 'X' after {1,1} → creates {1,10}
User B (offline): delete {1,1}   (tombstone — mark deleted, keep ID)

Sync — operations COMMUTE (apply in any order):
  A then B: 'a' tombstoned, X anchored after it → 'Xbc'
  B then A: delete 'a', insert X after deleted anchor → 'Xbc'
  Both → identical result ✓

No central server sequencing needed.
  • Logoot / LSEQ: fractional position IDs between characters
  • Tombstones: deleted chars stay in the ID space (never free their position)
  • Memory cost: every char carries an ID + possible tombstone metadata

🔌 WebSocket

WebSocket Architecture

WS  /v1/api/docs/{docId}/edit   (bidirectional stream)

Client → Server:
  { type: 'operation', op: { type, position, content, client_version } }
  { type: 'cursor',    cursor_pos, selection: {start, end} }
  { type: 'sync_request', last_known_version: 42 }

Server → Client:
  { type: 'operation',    transformed_op, user_id }
  { type: 'cursor_update',user_id, name, color, cursor_pos }
  { type: 'user_joined' / 'user_left' }
  { type: 'sync_response',server_ops, current_version }
  • Sticky sessions: IP hash — same user stays on same gateway pod
  • 10K connections/pod — 1M users needs 100 gateway instances
  • Failover: pod dies → client exponential backoff → sends sync_request to catch up
  • vs HTTP polling: 1M users × 1 req/s = 1M req/s; WS sends only on change = 100x less traffic
📦 Operations

Operation Format & Compression

Operation types:
  insert(position, content)   — "insert 'hello' at pos 5"
  delete(position, length)    — "delete 3 chars at pos 10"
  retain(length)              — "keep next N chars" (delta format)
  format(position, length, attrs) — bold/italic/color

Delta compression example:
  Old: "Hello World"
  New: "Hello Beautiful World"
  Delta: [retain(6), insert("Beautiful "), retain(5)]
  Wire: 35 bytes vs 21 bytes full content
  • Debounce 50ms: fast typists batch multiple chars into one op
  • permessage-deflate: WebSocket compression extension, ~70% bandwidth saving
  • Op batching threshold: 5 chars/sec — reduces op-log row count
👥 Presence

Presence & Cursors

Cursor broadcast flow:
  1. User moves cursor → client detects onChange
  2. Throttle: batch every 100ms (90% traffic reduction)
  3. Send: { type:'cursor', user_id, cursor_pos:15, selection:{start:10,end:15} }
  4. Gateway broadcasts to all OTHER clients in the doc room
  5. Redis: HSET cursors:{doc_id} user:{id} '{pos,selection}' EX 300
  6. On disconnect: HDEL cursors:{doc_id} user:{id}, broadcast user_left

Cursor OT transform:
  User A cursor at pos 10, User B inserts 'hello' (5 chars) at pos 5
  → A's cursor must shift: 10 + 5 = 15
NEVER persist cursors in DB. 100 updates/sec/user × 100 editors = 10K writes/sec, all ephemeral. Redis HASH with TTL=5 min, auto-expires on disconnect.
📴 Offline

Offline Mode — Queue, Reconnect, Rebase

Offline:
  1. WebSocket closes (network failure)
  2. Client banner: "Working offline"
  3. Store ops: IndexedDB [{ op_id, type, position, content, client_version }]
  4. Track: last_known_version = 42

Reconnect (exponential backoff: 1s → 2s → 4s → 8s → max 30s):
  1. Send: { type:'sync_request', last_known_version: 42 }
  2. Server: fetch ops 43–50 from op-log, send to client
  3. Client: apply server ops first (replay 43–50 on local doc)
  4. Client: OT-transform local queued ops against server ops
  5. Send transformed ops as batch to server
  6. Conflict: modal → keep local / keep server / manual merge
Version vector: client tracks last_known_version; server sends only the delta. Rebase local ops on top of server ops before re-submitting.
🕐 Versioning

Version History & Snapshots

Snapshot trigger: every 50 ops OR every 5 minutes

Reconciliation Service (Kafka consumer):
  1. Count ops since last snapshot for doc_id
  2. If count >= 50:
     a. Fetch last snapshot from S3 (docs/{doc_id}/v10.txt.gz)
     b. Fetch ops since that version from op-log
     c. Replay ops sequentially → current content
     d. gzip compress (70% size reduction)
     e. PUT S3 docs/{doc_id}/v11.txt.gz
     f. INSERT INTO snapshots (version:11, blob_path)
     g. UPDATE Redis doc:{doc_id}:state TTL=1800

Restore flow:
  POST /v1/api/docs/{docId}/restore { target_version: 10 }
  → fetch v10 from S3 → create 'replace_all' op
  → upload as NEW version (v12) — NEVER mutate history

↩️ Undo/Redo

Undo/Redo in Collaborative Context

Problem: User A types "hello", User B types "world" after.
         User A presses Ctrl+Z — should undo only A's "hello",
         NOT undo B's "world".

Local undo stack:
  Each client maintains: localOps[] = [op1, op2, op3]

Undo steps:
  1. Pop op3 from localOps (A's last op)
  2. Compute inverse: insert → delete, delete → insert
  3. Transform inverse against all server-acknowledged ops
     that arrived AFTER op3
  4. Send transformed inverse as a new op to server
  5. Server applies it, broadcasts to all clients

Key insight: Undo is NOT replaying history — it's a NEW
operation that cancels the effect of the old one.
Compound undo: only undo ops the local user owns, skip ops from other users on the undo stack.
🎓 Senior Q&A 1

Q: 50 Users Type Simultaneously in the Same Paragraph?

Interviewer Question

"What happens when 50 users all edit the same paragraph at the same time?"

  • Each client sends ops optimistically — applies locally before server ack (fast UX)
  • Editor Service receives ops — assigns monotonic server_version to each
  • OT transforms each op against all concurrent ops with higher version
  • Transformed op broadcast to all 49 other clients in the doc room
  • Each client applies the server-transformed op, adjusting local cursor positions
  • Throughput: 50 users × 5 ops/s = 250 ops/s per doc — Kafka handles millions/s
  • Dedicated pod for hot docs avoids latency spikes from noisy neighbors
Convergence guaranteed because server_version is a total order. Every client applies ops in the same server-assigned sequence → identical final state.
🎓 Senior Q&A 2

Q: User Offline 2 Hours, Makes 200 Ops — How to Merge?

  • Offline: 200 ops stored in IndexedDB, last_known_version = 42
  • Reconnect: client sends sync_request with last_known_version: 42
  • Server: fetches ops 43–180 from op-log (138 ops others made)
  • Client step 1: apply server ops 43–180 to the local document
  • Client step 2: OT-transform each of the 200 local ops against ops 43–180
  • Client step 3: send 200 transformed ops as a batch to server
  • Server: applies each, assigns server_version 181–380, broadcasts to others
  • Conflict escalation: if a replace_all collision → show merge UI modal
Why this works: OT transform functions are mathematically proven to produce convergent results given the same total ordered op sequence (Jupiter protocol property).
🎓 Senior Q&A 3

Q: Undo Your Op When Others Edited After You

Timeline:
  v10: User A types insert('hello', 5)   → server_version 11
  v11: User B types insert(' world', 10) → server_version 12
  v12: User C deletes char at pos 3      → server_version 13
  Now: User A presses Ctrl+Z (undo v11)

Steps:
  1. Inverse op: delete(pos=5, len=5)  [inverse of insert('hello',5)]
  2. Transform inverse against ops 12, 13:
     - v12: B inserted 5 chars at pos 10 (after pos 5) → no shift needed
     - v13: C deleted at pos 3 (before pos 5) → shift: 5-1=4
  3. Transformed undo: delete(pos=4, len=5)
  4. Send as new op → server_version 14
  5. Broadcast to all clients
Key: The undo is a brand-new forward op. It never rewrites history. B's and C's edits are fully preserved.

🎬 Closing

Closing Script — What to Say at the End

Say This to Close

"To summarise: the hardest part of Google Docs is conflict resolution. We solved it with OT — the server assigns a total order via server_version, transforms concurrent ops using position-shift rules, and broadcasts the result so all clients converge. We used Redis as the canonical hot copy (90% cache hit), snapshots every 50 ops to keep replay under 65ms, and IndexedDB for offline with a rebase-on-reconnect strategy. CRDT would work too, but at the cost of per-character memory overhead."

Anti-patterns to Mention Avoiding

  • Persisting cursors in DB — Redis HASH TTL=5min only
  • HTTP polling instead of WebSocket — 100x traffic overhead
  • Clients ordering operations — server_version is the only truth
  • Loading the full op-log on doc open — always use snapshot + recent ops
