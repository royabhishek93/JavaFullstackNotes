Why Logging at Scale Is Hard

Picture a company with 1,000 microservices, each running 10 replicas across 3 regions. That's 30,000 processes writing logs simultaneously — easily 1 million log lines per second at peak traffic.

The Observability Triad

📋 Logs
Discrete events — what happened, when, where
→ Elasticsearch / Splunk
📈 Metrics
Aggregated numbers — CPU %, req/s, error rate
→ Prometheus / Datadog
🔗 Traces
Request journeys across services end-to-end
→ Jaeger / Zipkin
Core Challenge: Write throughput (1M logs/sec) vastly exceeds what any database can index in real-time. The architecture must decouple ingestion from indexing without losing a single event.

Functional Requirements

#Requirement
1Ingest logs from multiple sources (FluentBit, OTEL, custom agents) — real-time and batch
2Support both real-time streaming and batch/file-upload ingestion
3Validate, parse, and normalize logs into a standard JSON structure
4User sees logs on dashboard in near real-time (< 5 seconds)
5Advanced search — full-text, regex, filters, time-range queries
6Real-time log tailing (live tail via WebSocket)
7Alerting based on log patterns, thresholds, and anomalies
8Configurable retention policy per client/tenant
9Dashboard with aggregations, charts, service health views

Non-Functional Requirements

DimensionTarget
Scale1TB logs/day ingestion — 100K–1M logs/sec sustained
Search Latency< 5s end-to-end; < 200ms for hot data (last 14 days)
Availability99.9% uptime — always available for ingestion
ConsistencyEventual (AP in CAP) — logs don't need strong consistency
DurabilityZero data loss — Kafka RF=3, Cassandra RF=3, S3 cold backup
RetentionHot: 14 days → Warm: 45 days → Cold: unlimited (S3)
ThroughputKafka 1M msg/s; Flink 32 parallel tasks × 100K events/s each
CAP Choice: AP (Availability > Consistency). Logs are append-only. A 1-second delay between Cassandra write and ES indexing is perfectly acceptable.

Log Agent Design — FluentBit vs Filebeat

FluentBit (preferred)

  • Written in C — 450KB memory footprint
  • Built-in parsers: JSON, Regex, syslog, multiline
  • Backpressure: 10MB disk buffer, 24h retry
  • Native OTEL output plugin
  • Kubernetes DaemonSet sidecar

Filebeat (alternative)

  • Part of Elastic stack — tighter ES integration
  • Higher memory (~50MB) vs FluentBit
  • Module system for common log formats
  • Harvester: tracks file offsets (like tail -f)

Agent Pipeline

Log Collector → tail -f / inotify / stdout
      ↓
Parser       → syslog/JSON/custom → standard schema
      ↓
Buffer       → 10MB disk, retry with exponential backoff (24h)
      ↓
Batch Aggr   → 100 logs OR 10s window → single HTTP POST
      ↓
Sampler      → DEBUG=10%, INFO=50%, WARN/ERROR=100%
      ↓
HTTP POST    → /agents/{agentId}/logs  (Snappy compressed)

Kafka as the Ingestion Buffer

Golden Rule: NEVER write logs directly to Elasticsearch during ingestion. Always buffer through Kafka first.

Why Kafka — 4 Key Reasons

ReasonDetail
Back-pressureIf ES is slow/down, Kafka buffers millions of logs without data loss
ReplayReprocess logs if processing logic changes or fails (rewind offset)
Fan-outSame stream feeds Cassandra, Elasticsearch, and Alert service independently
Peak smoothing1M logs/sec burst → Kafka absorbs; Flink processes at steady 100K/sec

Kafka Configuration

Topics:            raw_logs, alert_topic, es_retry, dlq
Partitions:        100 (keyed by client_id for ordering per tenant)
Replication:       RF=3, min.insync.replicas=2, acks=all
Retention:         48 hours (replay window)
Compression:       Snappy (3:1 ratio)
Throughput:        1M msg/sec sustained

Elasticsearch Indexing Design

Index Strategy — Time-Based Rotation

Index name:  logs-prod-2024-01-15
             logs-prod-2024-01-16  (new index each day)

Primary shards:  10  (sized at ~5GB each for a 50GB/day index)
Replica shards:  1   (tolerate 1 node failure; 2 for critical)

Field Mapping (Schema)

log_id        → keyword   (exact match, unique ID)
timestamp     → date      (range queries, ILM trigger)
log_level     → keyword   (aggregations, filter — never analyzed)
message       → text      (full-text search + standard analyzer)
service_name  → keyword   (aggregations, cardinality ~1K)
host, env     → keyword
namespace     → keyword   (k8s namespace)
pod_name      → keyword
trace_id      → keyword   (distributed tracing correlation)
Inverted Index: ES tokenizes message field → "NullPointerException" stored in inverted index → O(1) lookup across billions of logs. Keyword fields skip tokenization for exact match.

Index Lifecycle Management (ILM)

 Day 0 ──────────────────────────────── Day 14 ──── Day 45 ──── Day 90+
   │                                       │           │            │
   ▼                                       ▼           ▼            ▼
 HOT TIER                            WARM TIER    COLD TIER     DELETE
 Cassandra + ES                      Cassandra    S3 Parquet
 SSD storage                         HDD storage  Glacier
 <200ms search                       1–2s search  10–30s (Athena)
 $0.10/GB/mo                         $0.05/GB/mo  $0.01/GB/mo

ILM Policy Rules

Hot → Warm rollover trigger:  50GB OR 7 days (whichever first)
Warm → Cold:                  Move to S3 Parquet after 45 days
Cold → Delete:                Per-client retention policy (default 90 days)
Cost Example: 1TB/day ingestion
Hot-only storage: $3,000/month
Tiered (hot+warm+cold): $300/month
= 90% cost reduction
NEVER skip ILM — without it, ES indices grow unbounded and the cluster runs out of disk within days at this scale.

Distributed Tracing Integration

The Problem

A user reports checkout failure. The request touched 8 services. How do you find the root cause across 8 separate log streams?

The Solution: trace_id

// OpenTelemetry SDK injects:
{
  "trace_id": "abc-123-xyz",
  "span_id":  "def-456",
  "service":  "payment-svc",
  "msg":      "charge failed"
}

Jaeger / OpenTelemetry Flow

Client Request
    │
    ├─ trace_id generated at API Gateway
    │   (or extracted from X-Trace-ID header)
    │
    ├─ Propagated via HTTP headers to each service
    │   W3C TraceContext: traceparent header
    │
    ├─ Each service logs with trace_id field
    │
    └─ Search: GET /logs?trace_id=abc-123-xyz
       → Returns ALL logs across ALL services
         for this single request, sorted by timestamp
Cassandra schema: logs_by_traceId table has trace_id as partition key — O(1) lookup for all logs in a trace, regardless of how many services touched it.

Log Retention & Compliance (GDPR)

PII Scrubbing in the Flink Pipeline

// Flink enrichment stage — BEFORE writing to storage:
scrub_patterns = [
  r'\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Z]{2,}\b',  // email
  r'\b\d{4}[- ]?\d{4}[- ]?\d{4}[- ]?\d{4}\b',           // credit card
  r'\b\d{3}-\d{2}-\d{4}\b'                               // SSN
]
// Replace with: [REDACTED-EMAIL], [REDACTED-CC], [REDACTED-SSN]

GDPR Deletion Request Flow

 GDPR Request: delete all logs for user@example.com
      │
      ├─ ES:        DELETE by query  (timestamp range + user_id field)
      ├─ Cassandra: Soft-delete 7d → hard delete
      ├─ S3/Athena: Partition scan → rewrite Parquet without matching rows
      └─ Audit log: Deletion events logged for compliance verification
WORM Storage: Audit logs (who accessed what) written to S3 Object Lock — cannot be modified or deleted even by admins. Required for SOC2/HIPAA compliance.

Scaling Elasticsearch

Shard Sizing Rules

Target shard size:    20–50GB  (50GB upper limit before performance degrades)
Primary shards:       10 per daily index
Replica shards:       1 (double storage but allows horizontal read scaling)
Daily index at 1TB:   10 shards × ~100GB → too big → use 20 primaries × 50GB

Scaling Techniques

TechniqueDetail
Horizontal shardingAdd data nodes; ES auto-rebalances shards across nodes
Cross-cluster replicationDR region gets async replica — RPO ~5 minutes
Query cache60s TTL → 80% faster dashboard loads for repeated queries
Dedicated master nodes3 dedicated masters (never data nodes) — prevents split-brain
Frozen tierSearchable snapshots — zero replica, on-demand S3 fetch
Bulk APIFlink sends 5K logs per bulk request — 5× higher throughput than single indexing
Never put master and data roles on same node in production — cluster instability under high indexing load.

Metrics vs Logs vs Traces — When to Use Each

📈 Metrics (Prometheus)
  • Aggregated numerical data
  • CPU %, request rate, error rate
  • Low cardinality labels
  • Alerting on thresholds
  • Dashboards / SLOs
Use when: "Is the system healthy?"
📋 Logs (Elasticsearch)
  • Discrete events with context
  • Error messages, stack traces
  • High cardinality OK
  • Debugging specific failures
  • Compliance/audit trails
Use when: "What exactly went wrong?"
🔗 Traces (Jaeger)
  • Request journey across services
  • Latency per service/span
  • Dependency visualization
  • Performance bottleneck ID
  • Requires instrumentation
Use when: "Which service slowed us down?"
OpenTelemetry unifies all three: single SDK for logs, metrics, and traces. Vendor-agnostic. Exports to any backend. The industry standard going forward.

Multi-Tenancy Design

Index Isolation Strategy

Option A: Index per tenant (recommended for <1000 tenants)
  logs-{client_id}-{date}  e.g., logs-acme-2024-01-15
  → Complete data isolation, easy RBAC, simple deletion
  → Drawback: Many small indices waste ES cluster metadata

Option B: Shared index, filtered by client_id field
  logs-{date}  with client_id as keyword field
  → Fewer indices, simpler cluster management
  → Risk: Noisy neighbor — one large tenant slows everyone's queries

Protecting Against Noisy Neighbors

ControlMechanism
Rate LimitingToken bucket: 10K logs/min per client at API Gateway
Kafka partitioningKeyed by client_id — one slow consumer doesn't block others
RBACES document-level security — tenants can only query their own indices
Query timeoutMax 30s per search query; circuit breaker at 80% heap usage
Storage quotaPer-client retention limit stored in ClientDB.pref

Senior Q&A 1 — Black Friday Log Surge

Q: It's Black Friday. Log volume spikes 10x — 10M logs/sec. Elasticsearch falls behind and consumer lag grows to 50M messages. What do you do?

Response (5-layer answer):

 1. KAFKA ABSORPTION
    → Kafka holds the surge — data is safe, not lost
    → Consumer lag is a performance issue, not a durability issue

 2. AUTO-SAMPLING (Flink)
    → Spike detected via Kafka consumer lag metric
    → DEBUG: 10% → 0.1% (drop 99.9%)
    → INFO:  50% → 1%
    → ERROR/FATAL: always 100% (never sample critical logs)
    → Reduces effective throughput from 10M → ~1M logs/sec

 3. SCALE FLINK HORIZONTALLY
    → Add 32 more Flink task slots (pre-provisioned for Black Friday)
    → Process 2× faster, drain the backlog

 4. ELASTICSEARCH — REDUCE INDEX REFRESH
    → Change refresh_interval from 1s → 30s during surge
    → Trades search freshness (30s delay) for 3× indexing throughput

 5. ES BULK BATCH SIZE UP
    → Increase Flink bulk batch from 5K → 50K logs
    → Fewer round trips, higher throughput

Senior Q&A 2 — GDPR Log Deletion

Q: A user submits a GDPR deletion request. You must remove all logs containing their email address across all storage tiers within 30 days. How do you implement this?

Deletion Pipeline:

 Step 1: FUTURE PREVENTION (immediate)
   → Flink PII scrubber already redacts emails in real-time pipeline
   → Stops new logs from containing raw email going forward

 Step 2: HOT TIER — Elasticsearch (same day)
   → POST /logs-*/_delete_by_query
     { "query": { "term": { "user_id": "usr_789" } } }
   → Or: match email in message field (regex query)
   → Takes minutes for 14-day window

 Step 3: WARM TIER — Cassandra (same day)
   → Soft delete: mark rows deleted=true
   → Hard delete: background job within 7 days
   → TTL on tombstones: 10 days

 Step 4: COLD TIER — S3 Parquet (within 30 days)
   → Athena query to find affected partitions
   → Rewrite Parquet files without matching rows (Spark job)
   → Replace original S3 objects atomically

 Step 5: AUDIT LOG
   → Record deletion event in WORM storage (S3 Object Lock)
   → Proof of compliance for regulators

Senior Q&A 3 — Correlate Bug Without trace_id

Q: A critical bug is reported. It spans 50 microservices but the engineers forgot to propagate trace_id. How do you correlate the logs?

Forensic Correlation Strategy:

 Step 1: NARROW BY TIME WINDOW
   → Find first ERROR in the chain (timestamp T)
   → Search all services in window [T-5s, T+60s]
   → ES query: log_level:ERROR AND timestamp:[T-5s TO T+60s]

 Step 2: CORRELATE BY user_id / session_id / order_id
   → Even without trace_id, business IDs flow through services
   → Search: "order_id=ORD_456" across all services
   → Reconstruct timeline ordered by timestamp

 Step 3: CORRELATE BY IP / request_id / JWT claim
   → API Gateway logs always have client IP + request_id
   → Match downstream service logs with same IP in time window

 Step 4: CAUSAL CHAINING
   → Service A ERROR at T+0ms → Service B first log at T+2ms
   → ~2ms network hop → likely causal
   → Build the call graph manually

 Step 5: ADD trace_id RETROACTIVELY
   → Post-mortem: add OpenTelemetry instrumentation to all 50 services
   → W3C TraceContext propagation via shared middleware/filter
   → Never debug this way again

Closing — Key Takeaways

The Core Architecture Pattern:
Multi-source ingestion → Kafka buffer → Flink stream processing → Hot/Warm/Cold tiered storage → Elasticsearch search

5 Things That Separate Senior Answers

Always buffer through Kafka — never write directly to ES during ingestion
Return 202 Accepted from ingestion API — decouple write latency from indexing
ILM tiering saves 90% storage cost at 1TB/day scale
Flink exactly-once + Kafka RF=3 + agent disk buffer = zero log loss
PII scrubbing happens in the pipeline, not at query time
trace_id propagation via OpenTelemetry is non-negotiable at 50+ services
Quick Cheat Sheet: Kafka = decouple + buffer + replay | Cassandra = write-optimized time-series TTL | Elasticsearch = full-text inverted index ILM | Flink = event-time watermarks stateful dedup exactly-once | S3 = cheap cold storage 11-nines durability Athena queries
