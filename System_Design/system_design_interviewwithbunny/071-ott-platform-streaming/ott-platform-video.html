Upload & Ingestion Pipeline

Backend Team uploads 100 GB master file
  │ presigned S3 multipart upload URL (5 GB parts, parallel)
  ▼
S3 Raw Bucket  (master.mov)
  │ S3 ObjectCreated event triggers Chunker
  ▼
Chunker Service
  ├── splits into 6-10s segments aligned to I-frames
  ├── creates master manifest (.m3u8 for HLS · .mpd for DASH)
  └── publishes chunk events → Kafka topic "video-chunks"
              { titleId, chunkId, segmentNumber, s3Path }
  ▼
Encoder Workers (FFmpeg, auto-scaled ECS tasks)
  ├── consumes Kafka events (each chunk independently)
  ├── encodes: 4K H.265 · 1080p H.264 · 720p H.264 · 480p H.264
  └── writes to S3 Encoded:  title-abc/1080p/seg001.ts
  ▼
On all chunks done:
  MongoDB ← { manifestUrl, status: READY }
  CDN     ← pre-push first 10 segments to top-50 PoPs
  ES      ← via CDC (Debezium → Kafka → ES indexer, ~2s lag)
  • Idempotent encoder: chunk failure retries only that chunk; DLQ after 3 attempts

Adaptive Bitrate Streaming — HLS / DASH

master.m3u8  (master playlist — the "table of contents")
  ├──▶ 1080p/playlist.m3u8 → seg001.ts · seg002.ts · seg003.ts …
  ├──▶  720p/playlist.m3u8 → seg001.ts · seg002.ts …
  └──▶  480p/playlist.m3u8 → seg001.ts …

ABR LOOP — runs at every I-frame boundary (~every 6-10s):
t= 0s  Play pressed → manifest fetched from CDN
       Client measures BW = 3 Mbps → selects 720p playlist
t= 0s  GET cdn/.../720p/seg001.ts  (downloads in ~0.5s, starts playing)
t= 6s  I-frame boundary: re-measure BW = 8 Mbps  ← upgrade opportunity
       PRE-FETCH cdn/.../1080p/seg002.ts (background, while seg001 plays)
t=10s  seg001 ends → 1080p seg002 already buffered → seamless upgrade ✓
t=22s  BW drops to 1.5 Mbps → pre-fetch 480p/seg004 → quality drops, no freeze
  • HLS .m3u8 — mandatory on Apple iOS/Safari; 6-10s segments
  • DASH .mpd — Android, Web, Smart TV; 2-4s segments, faster switching
  • Client maintains 20-30s buffer — even a 15s outage = no visible freeze

CDN Strategy — PoP Placement & Cache Rules

WITHOUT CDN:
  Client → API Gateway → Play Svc → S3 (us-east-1)
  Latency: 200-500ms/segment · 2.5M req/s → origin collapses instantly

WITH CDN:
  Client → CloudFront PoP (Mumbai, 5ms away) → cache HIT
  Latency: ~5ms/segment · Origin sees only 5% = 125K req/s

Cache TTL policy:
  Video segments (.ts)  → 7 days   (immutable; hash in URL; perfect cache)
  Master manifest       → 5 min    (may add quality tier; must expire)
  Thumbnails (.webp)    → 24 hrs
  DRM license           → NOT cached (user + device specific)
  API responses         → NOT cached (authenticated, dynamic)
  • Netflix Open Connect — hardware appliances inside ISPs; sub-5ms; cheaper at Netflix scale
  • CloudFront Origin Shield — request collapsing: 1000 users miss same segment → 1 S3 call
  • CDN pre-warm — push first 10 segments to top-50 PoPs 30 min before major release
  • GeoIP routing: Mumbai users → ap-south PoP; never traverse to us-east-1

  • H.265 (HEVC) — 50% better compression; 4K ≈ 12 GB; higher CPU encode cost

  • Strategy: H.265 for new content, H.264 as device fallback
  • Thumbnails: WebP at 3 sizes (lazy-loaded on scroll), generated at encode time

DRM — Widevine · FairPlay · PlayReady

Three DRM systems (must support all):
  Widevine  → Android · Chrome · Firefox · Smart TV
  FairPlay  → iOS · macOS · Safari  (Apple mandates this exclusively)
  PlayReady → Windows · Edge · Xbox

DRM FLOW:
  1. User presses Play → Play Svc returns { manifestUrl, drmToken }
  2. Client fetches manifest → detects: content is AES-128 encrypted
  3. Client POSTs license request + drmToken → License Server
  4. License Server checks: valid JWT? · subscription ACTIVE? · geo allowed?
  5. Returns content decryption key → delivered to hardware TEE/CDM
  6. CDM decrypts video in secure enclave — app code NEVER sees raw key
  7. 🎬 Video plays; screen recording APIs blocked at OS level

ON SUBSCRIPTION EXPIRY:
  heartbeat → 403 from Play Svc → player shows "Subscription ended"
  Downloaded content → license TTL expired → unplayable automatically
  • Signed URL ≠ DRM — signed URL controls access but bytes are readable once downloaded; DRM encrypts the bytes themselves
  • Entitlement result cached in Redis (5min TTL); DRM license itself is NOT cached

Metadata & Search — Elasticsearch + CDC Pipeline

WHY Elasticsearch over MongoDB for search?
  MongoDB $regex scans every document → slow at 100K req/s
  ES inverted index: "action" → [id1, id5, id9] → µs lookup
  ES also handles: fuzzy match · typos · filters · sort by rating

CDC PIPELINE (MongoDB → Elasticsearch sync):
  MongoDB ──▶ Debezium (tails oplog) ──▶ Kafka ──▶ ES Indexer Consumer
  Lag: ~1-5 seconds    Acceptable — content changes are rare events

WHY CDC over dual-write?
  Dual-write risk: MongoDB write ✓ → ES write ✗ → search broken, no recovery
  CDC: if ES is down, oplog replay catches up on recovery automatically

SEARCH QUERY (ES DSL):
  must:   multi_match("action 2023", fields: [title, description, cast])
  filter: [ country:"IN", status:"PUBLISHED" ]
  sort:   [ rating:desc, popularity:desc ]
  → Returns partial data (id, title, thumbnail, rating) — full detail on click

Recommendation Engine — Two-Tower Model

Input signals:
  watch_history: { videoId, durationWatched, completionPct, timestamp }
  search queries · ratings · device type · time of day

Two-Tower Architecture:
  User Tower: [userId, watch_history, demographics] → 128-dim embedding
  Item Tower: [videoId, genre, cast, description]   → 128-dim embedding

Inference:
  cosine_similarity(user_vec, item_vec) → ranked list of 20 titles
  Results cached in Redis per user  (TTL = 24 hours)

Data pipeline:
  Heartbeat events ──▶ Kafka "video.watched"
       ├──▶ Analytics Service  (view counts, completion rate, trending)
       └──▶ Recommendation Svc (online feature store → nightly batch retrain)
  • Collaborative filtering fallback: "users who watched X also watched Y"
  • Content-based fallback: same genre / director / cast as recently watched
  • Cold start: new user → use country + plan tier as proxy signals
  • Trending list: Redis sorted set, score = view count last 1h (TTL 5min)

Playback State — Resume & Cross-Device Sync

Client sends heartbeat every 30s:
  POST /stream/heartbeat { profileId, videoId, positionSeconds, sessionId }
  → Response: 204 No Content

TWO-LAYER STORAGE:
  Layer 1 — Redis (hot, fast)
    HSET watch_progress:{userId}:{videoId} positionSec {n}  TTL = 7 days
    Sub-millisecond read → instant "Continue Watching" UI

  Layer 2 — Cassandra (persistent, survives Redis restart)
    Background job flushes Redis → Cassandra every 60 seconds
    Partition key = profileId → all history on one node → fast reads
    SELECT * FROM watch_progress WHERE profile_id=? LIMIT 20
    ORDER BY last_watched DESC  (→ "Continue Watching" row)

CROSS-DEVICE RESUME:
  Phone pauses at 20:45 → heartbeat writes positionSec=1245 → Redis + Cassandra
  TV opens same title → Play Svc returns { resumeAt: 1245 }
  Player seeks to 20:45 before first segment loads → seamless experience

WHY NOT PostgreSQL: 20M DAU × 1 heartbeat/30s = 670K writes/s → PostgreSQL max ~50K/s → dies

Offline Download — DRM Key Binding & Device Quota

DOWNLOAD FLOW:
  1. User taps Download → client requests offline DRM license
  2. License server issues license bound to:
       { userId, deviceId, titleId, expiresAt: now + 30 days }
  3. Encrypted .ts segments downloaded to device local storage
  4. License stored in hardware TEE — app code never reads raw key
  5. Player decrypts in CDM only while license is valid

EXPIRY ENFORCEMENT (no server round-trip needed):
  License TTL = 30 days → CDM refuses decryption after expiry
  Subscription cancelled → next Play attempt → License Server returns 403
  → Content unplayable automatically, even if offline

DEVICE QUOTA (Redis):
  Redis key: downloads:{userId} → INCR on download, DECR on delete
  Basic plan:   1 device · max 5 downloads
  Premium plan: 4 devices · max 25 downloads total
  Quota enforced at download-initiation time, not at play time
  • Widevine L1 / FairPlay required for HD offline; L3 allows SD only (software CDM)
  • Offline files useless without license — 30-day TTL = re-subscribe to continue watching

CDN Scaling — Cache Optimization & Pre-positioning

Thundering Herd — New Season Drop

200M users hit Play within 60 seconds:

Hotspot 1: Elasticsearch
  Problem: identical search query "Stranger Things 5" × 10M times
  Fix:     Redis cache top-N search queries (TTL 1min)

Hotspot 2: MongoDB manifest fetch
  Problem: Redis cold → all 5M miss → MongoDB spike
  Fix:     Pre-warm Redis at publish time: SET manifest:{id} {url} EX 86400
           One Redis key serves all 5M users (same manifest)

Hotspot 3: CDN cold cache
  Problem: first 60s — segments not yet at edge PoPs
  Fix A:   CDN Origin Shield (request collapsing)
           1000 misses for same segment → 1 S3 call, not 1000
  Fix B:   Pre-position first 10 segments to top-50 PoPs 30min before launch

Immutable Segment URLs

  • Segments named by content hash: seg_a3f7c.ts — never stale, max TTL, never invalidate
  • Manifest TTL = 5 min; version URL on change (manifest_v2.m3u8)

Senior Q&A 1 — 5M Simultaneous Plays at Launch

"New season drops. 5M users hit Play in 60 seconds. What breaks first?"

Hotspot 1: MANIFEST FETCH
  Redis cold → 5M miss → MongoDB overwhelmed
  Fix: pre-warm manifest key at publish time (TTL 24h)
       Single Redis key absorbs all 5M users — same manifest for all

Hotspot 2: CDN COLD
  Segments not cached at edge; all 5M segment fetches → S3
  Fix A: CDN Origin Shield — 1000 misses → 1 S3 call per segment
  Fix B: Pre-position first 10 segments to top-50 PoPs 30min pre-launch

Hotspot 3: DRM LICENSE SERVER
  5M license requests in 60s → license server overwhelmed
  Fix: horizontal scale (ECS auto-scaling; stateless pods → 500 in ~2min)
       Cache entitlement check in Redis (5min TTL) — separates auth from license

Hotspot 4: CONCURRENT STREAM COUNTER
  5M INCR operations → Redis bottleneck?
  Fix: Redis Cluster (16 shards) → each shard handles 300K ops/s
       stream counter key = streams:active:{userId} — naturally sharded by userId

Senior Q&A 2 — Bandwidth Drops 50 Mbps → 2 Mbps Mid-Stream

"User is watching 4K. Network degrades suddenly. Trace what happens frame by frame."

t= 0s  Playing 4K/seg047 at 15 Mbps · buffer = 30s ahead

t= 6s  I-frame boundary → client measures BW = 2 Mbps
       2 Mbps → picks 480p (needs 1.5 Mbps)
       Immediately issues: GET cdn/.../480p/seg048.ts (background pre-fetch)

t=10s  seg047 (4K) finishes playing
       seg048 (480p) already buffered → quality drops seamlessly · ZERO rebuffer ✓

Why no freeze?
  30s buffer absorbed the quality decision latency completely.
  Pre-fetch fires at 60% through current segment = ~4s headroom.

If BW stays low (2 Mbps for many segments):
  seg049, seg050 … all at 480p until bandwidth recovers

On recovery:
  BW rises → hysteresis: require 3 consecutive segments above threshold
  → gradual upgrade 480p → 720p → 1080p (avoids oscillation on flaky networks)

What NEVER happens: a freeze.
  Only if 30s buffer drains to zero does user see a spinner.
  Client pre-fetches aggressively to prevent this.

Senior Q&A 3 — CDN PoP Content Caching Strategy

"You have 200 CDN PoPs but 500 PB of content. How do you decide what to cache where?"

TIERED CACHE ARCHITECTURE:
  Tier 1 — Edge PoP (~10 TB SSD per PoP)
    Stores: top 500 most-watched titles in that region (last 7 days)
    Fill: proactive nightly push + pull-through on cache miss
    Eviction: LRU; explicit purge on content removal

  Tier 2 — Regional Shield (1 per region, ~100 TB)
    Stores: all in-production titles for that geography
    Edge miss → Regional Shield → avoids origin S3 for most requests

  Tier 3 — S3 Origin (unlimited; all content; very rarely hit)
    Only on Regional Shield miss (<1% of total requests)

CONTENT ROUTING RULES:
  Popular new content → proactively push to top-50 PoPs pre-launch
  Geo-licensed content → only pushed to relevant region PoPs
  Long-tail (old titles) → cached at Regional Shield only, lazy edge population
  Immutable URLs → never invalidate; segment hash guarantees freshness

CACHE INVALIDATION:
  Segments: NEVER (hash in URL, content-addressed, immutable)
  Manifest: versioned URL on change + short TTL (5min) as safety net

Closing — Wrap Up Like a Senior Engineer

"To wrap up, let me summarize the key decisions and why they matter…"

  • CDN is the architecture — 95% of video traffic never touches your servers; without it you fail at t=0
  • ABR + HLS/DASH — never stream raw MP4; chunks + manifest + adaptive quality = zero buffering at any speed
  • Cassandra for heartbeats — 500K writes/s; MySQL dies; partition by profileId for O(1) reads
  • CDC over dual-write — Debezium tails oplog → Kafka → ES; guaranteed delivery, auto-replay on failure
  • DRM = AES encrypt + TEE — signed URLs are insufficient; decryption key must never leave hardware chip
  • Redis INCR — concurrent stream enforcement is one atomic op; heartbeat TTL handles crash case

Extensions to Mention If Asked

  • Live streaming: RTMP ingest → chunker → LL-HLS (2-3s latency) · separate from VOD path
  • Multi-region DR: RPO <5s (Postgres streaming replication); RTO <10min (Route53 + auto-scale)
  • gRPC internally: Play Svc ↔ DRM Svc (high-freq, binary); REST at the edge (CDN-cacheable, browser-compatible)
