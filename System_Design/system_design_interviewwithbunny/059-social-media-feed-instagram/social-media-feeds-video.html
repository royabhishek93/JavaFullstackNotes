📰 Feed Generation

The Celebrity Problem

Why pure push-fanout breaks for celebrities:

Cristiano Ronaldo posts once → 10M Redis writes + 10M Kafka messages in seconds

  • Fanout Svc becomes a bottleneck (can't keep up)
  • Redis memory spikes — everyone stores that 1 post_id
  • Feed latency degrades for all users on same cluster
  • If they post again before fanout completes → ordering breaks

Detection — flag celebrities in User table:

-- Set celebrity flag when followers exceed threshold
UPDATE users SET is_celebrity = true
WHERE followers_count > 5000;

-- Checked by Fanout Svc before writing to feeds
IF user.is_celebrity → SKIP fanout, write to PostDB only
Never fanout on write for celebrities — this is the #1 red flag interviewers watch for.

Hybrid Approach — Production Reality

┌─────────────────────────────────────────────────────────────────┐
│  Follower Count       Model         Details                     │
├─────────────────────────────────────────────────────────────────┤
│  < 1K followers    → Pure PUSH    Fanout to all immediately     │
│  1K – 5K           → Hybrid       Push to active, skip inactive │
│  > 5K followers    → Pure PULL    No fanout, query on-demand    │
└─────────────────────────────────────────────────────────────────┘

Feed load for a user following mix of normal + celebrity accounts:

Step 1: LRANGE feed:{user_id} 0 99      ← pre-built pushed posts (~80%)
Step 2: For each celebrity followed:
           GET author_latest_post:{celebrity_id}   (Redis cache, TTL=1hr)
           fallback: SELECT post_id FROM PostDB WHERE user_id=celeb LIMIT 20
Step 3: Merge + sort by timestamp (client or Feed Svc)
Step 4: Cache merged result feed:{user_id} TTL=10min
Key insight: Celebrity posts cached centrally — all 10M followers share one Redis key instead of 10M individual entries. Cache hit = 1 read for all.

Timeline Cache Design

Redis key patterns for the feed system:

Key PatternTypePurposeTTL
feed:{user_id}LISTPre-built feed of post_ids (LPUSH, LTRIM 1000)No TTL (evict on write)
likes_count:{post_id}STRINGINCR/DECR — fast counterNo TTL
like:{user_id}:{post_id}STRINGIdempotency check — exists = already liked24h
author_latest_post:{user_id}STRINGCelebrity post cache (single shared entry)1hr
followers_count:{user_id}STRINGDenorm count, synced to PG hourlyNo TTL

Why LIST over ZSET for feed?

  • Feed is insert-at-head, read-from-head — LIST LPUSH/LRANGE is O(1) / O(N)
  • ZSET (sorted set) adds O(log N) overhead and is better for ranked/scored feeds
  • Use ZADD (score = timestamp) if you need re-ranking by engagement

Feed Ranking Algorithm

/**
 * Feed rank score — higher = shown earlier
 *
 * recency_score  = 1 / (hours_since_post + 2)^1.5   [decays over time]
 * engage_score   = (likes + 2×comments + 3×shares) / (reach + 1)
 * affinity_score = interactions_with_author_last_30d / 100.0  [0.0 – 1.0]
 *
 * FINAL_SCORE = (0.5 × recency) + (0.3 × engage) + (0.2 × affinity)
 */
double rankPost(Post p, User viewer) {
    double recency  = 1.0 / Math.pow(hoursSince(p.createdAt) + 2, 1.5);
    double engage   = (p.likes + 2*p.comments + 3*p.shares) / (p.reach + 1.0);
    double affinity = getAffinity(viewer.id, p.authorId);
    return 0.5*recency + 0.3*engage + 0.2*affinity;
}
Implementation: Store score as ZADD score in Redis Sorted Set. ZADD feed_ranked:{user_id} {score} {post_id}
Read: ZREVRANGE feed_ranked:{user_id} 0 19 WITHSCORES

When to recalculate: Re-score in background every 15min for active users; skip inactive users.

⚙️ LLD Deep Dive

Cursor-based Pagination

Why OFFSET pagination fails at scale:

-- OFFSET pagination (BAD at scale):
SELECT * FROM posts ORDER BY created_at DESC LIMIT 20 OFFSET 10000;
-- DB must scan and discard 10,000 rows every request → O(N) cost
-- Also: new posts inserted at top shift all offsets → duplicate/missing items

Cursor-based pagination (production approach):

-- First page:
GET /api/v1/posts/feed?limit=20
→ { posts: [...], next_cursor: "2024-01-15T10:30:00Z_post_abc123" }

-- Next page (client sends cursor):
GET /api/v1/posts/feed?limit=20&cursor=2024-01-15T10:30:00Z_post_abc123

-- Server query:
SELECT * FROM posts
WHERE (created_at, post_id) < (cursor_timestamp, cursor_post_id)
ORDER BY created_at DESC, post_id DESC
LIMIT 20;
-- O(log N) index seek — no full scan, stable pagination
Cursor = opaque base64 token encoding (timestamp, post_id). Client never parses it.

Like / Comment Counters

Like interaction — 3-layer idempotency:

POST /api/v1/posts/{post_id}/like

1. Client-side: debounce 300ms, disable button (optimistic UI update)
2. Redis: SETNX like:{user_id}:{post_id} 1   → if returns 0: already liked → 200 OK
3. Cassandra: INSERT INTO likes (post_id, user_id) ON DUPLICATE KEY IGNORE
              Composite PK (post_id, user_id) → idempotent at DB level
4. Redis: INCR likes_count:{post_id}           → fast read counter
5. Kafka: publish 'post.liked' → Notification Svc
6. Background job every 5min:
   SELECT COUNT(*) FROM likes GROUP BY post_id
   → UPDATE posts SET likes_count = exact_count WHERE drift > 10%
Consistency stance: Accept ±5% drift for <5 min. Not a financial system — eventual consistency is correct here.

Comment counts: Same INCR/DECR pattern. Source of truth in PostgreSQL, Redis holds the hot read value.

🎯 Interview Prep

Senior Trap Q1 — "What happens when a user with 50M followers posts?"

Q: Cristiano Ronaldo (50M followers) posts a photo. Walk me through exactly what happens.

Answer:

  1. Celebrity flag detected — User table has is_celebrity=true (followers_count > 5K)
  2. Fanout is skipped entirely — Post written to Cassandra PostDB only. Zero Redis writes to follower feeds.
  3. Celebrity cache updated — SET author_latest_post:{ronaldo_id} {post_id} EX 3600 — all 50M followers share this 1 Redis key
  4. Feed load (pull path) — When any follower loads their feed: LRANGE (pushed posts) + GET author_latest_post for each celebrity followed → merge → cache result for 10min
  5. Notifications batched — Top 1K most-engaged followers notified immediately. Rest get a digest. Prevents 50M simultaneous FCM pushes.

Result: 1 Cassandra write + 1 Redis SET vs. 50M writes — 50 million times cheaper.

🎯 Interview Prep

Senior Trap Q2 — "How do you handle feed freshness after downtime?"

Q: Your Fanout Service was down for 2 hours. Users' Redis feeds are now stale — posts from those 2 hours are missing. How do you recover?

Answer — multi-layer recovery:

  1. Kafka retention (safety net) — Kafka retains messages for 7 days. On Fanout Svc restart → replay from last committed offset. No messages lost.
  2. Redis TTL fallback — Feed cache TTL = 10 min. On miss, Feed Svc rebuilds from Cassandra PostDB: SELECT posts WHERE user_id IN (following_list) ORDER BY created_at DESC LIMIT 100
  3. Catchup job — After recovery: batch job scans PostDB for posts created during outage window → pushes to follower feeds. Priority: active users first.
  4. User experience — "Pull to refresh" triggers Feed Svc to re-merge (bypasses stale cache). Users naturally expect fresh content on manual refresh.
The system degrades gracefully — users see slightly older feeds, not a crash.
🎯 Interview Prep

Senior Trap Q3 — "How would you rank feeds without recency bias?"

Q: Pure reverse-chronological feeds disadvantage users who post at odd hours. How would you implement ranking that isn't purely time-based?

Answer — multi-factor ranking pipeline:

  1. Compute score offline — Background scoring service reads engagement signals: likes, comments, shares, watch-time, click-through rate within first 30 min of post
  2. Redis ZADD with composite score — ZADD feed_ranked:{user_id} {score} {post_id} where score = weighted combination of recency + engagement + affinity
  3. Re-score periodically — Scores for posts <24hr old recalculated every 15 min. Beyond 24hr, score frozen (saves compute)
  4. Two-phase read — First load latest 200 post_ids (ZREVRANGE), rank them in memory, return top 20 to client
  5. A/B test ranking weights — Store weights in feature flags. Different user cohorts get different ranking. Measure engagement lift.
Affinity score = how often viewer interacts with this author. Prevents close friends' posts from being buried.
