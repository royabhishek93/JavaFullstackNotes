Distributed Job Scheduler

System Design Interview Guide

Design Quartz · Celery Beat · AWS EventBridge · Apache Airflow

⏰ Cron 🔒 Distributed Lock ♻️ At-least-once 👑 Leader Election 🔴 Redis ZPOPMIN 🏗 Cassandra
The design-defining challenge: at-least-once execution with no missed jobs and no stuck jobs. Every architectural decision traces back to three problems: crash recovery · double-execution prevention · thundering herd.

Execution Semantics

At-least-once — every job runs ≥1 time. May run twice on crash+recovery. Jobs must be idempotent. Simpler; default choice.

Exactly-once — each job runs exactly once. Requires Redis SETNX distributed lock + idempotency key. Only needed for non-idempotent jobs.

High Availability Constraints

  • No silent job drops — 99.99% uptime
  • Leader failover in <30 seconds (lock TTL)
  • Stuck job detection within 90 seconds
  • Payload <64KB → Cassandra inline
  • Payload ≥64KB → S3 reference only
  • All timestamps stored as UTC
  • DST transitions handled at job creation time

Job State Machine

┌────────────┐ │ SCHEDULED │ job created, next_run_at computed └──────┬───────┘ │ Scheduler ZADD to Redis ▼ ┌────────────┐ │ ENQUEUED │ in Redis sorted set, not yet picked up └──────┬───────┘ │ Worker ZPOPMIN ▼ ┌────────────┐ │ RUNNING │ worker holds heartbeat, executing └──┬──┬──┬────┘ │ │ └───────────────┐ │ │ ▼ │ │ ┌──────────────┐ │ │ │ TIMEOUT │ exceeded timeout_seconds │ │ └──────┬───────┘ │ ▼ │ retry? │ ┌──────────┐ ▼ │ │ FAILED │──► RUNNING (retry N+1) │ └──────────┘ │ │ │ max_retries exceeded ▼ ▼ ┌──────────┐ ┌──────────────┐ │ SUCCESS │ │ DEAD_LETTER │ → PagerDuty alert, manual re-trigger └──────────┘ └──────────────┘ Also: CANCELLED (user-initiated via POST /jobs/{id}/cancel)

FAILED vs TIMEOUT

FAILED — threw exception / non-zero exit code.
TIMEOUT — exceeded timeout_seconds, forcibly killed.
Different alerts, different runbooks.

DEAD_LETTER

After max_retries exceeded. No more automatic retry. PagerDuty CRITICAL alert fired. Requires manual investigation and re-trigger via API.

⏰ Scheduler Engine

Cron Expression Parsing

5-Field UNIX Cron Format

┌──── minute (0-59) │ ┌──── hour (0-23) │ │ ┌──── day-month (1-31) │ │ │ ┌──── month (1-12) │ │ │ │ ┌──── day-week (0-6, 0=Sun) │ │ │ │ │ * * * * * 0 2 * * * → 2:00 AM daily 0 0 1 * * → midnight 1st of month */15 * * * * → every 15 minutes 0 9 * * 1-5 → 9 AM Mon–Fri

Quartz 6-Field (adds seconds)

0 0 2 * * ? → 2:00:00 AM daily 0 */30 * * * ? → every 30 seconds Industry standard — libraries in all languages

Next-Fire Time Algorithm

  1. Parse cron string into 5 field arrays
  2. Start from current timestamp + 1 second
  3. Match each field left-to-right (min→hour→dom→month→dow)
  4. Roll over to next valid combination on mismatch
  5. Convert result to UTC unix timestamp
  6. Apply deterministic jitter:
    jitter = hash(job_id) % max_jitter_seconds
  7. Store as next_run_at in Cassandra
Deterministic jitter: same job always fires at same offset — predictable (e.g. "this job always fires at 2:03:47"). Prevents thundering herd at midnight.
⏰ Scheduler Engine

Leader Election — The Problem

If every Scheduler node independently enqueues jobs, the same job appears N times in Redis → N workers execute it simultaneously.
WITHOUT LEADER ELECTION: Scheduler-1 reads Cassandra: job_id=abc due at 02:00 Scheduler-2 reads Cassandra: job_id=abc due at 02:00 Scheduler-3 reads Cassandra: job_id=abc due at 02:00 All 3 ZADD job_queue score=02:00 "job_id=abc" (or if ZADD NX not used → 3 copies in sorted set) Workers ZPOPMIN: Worker-A gets job_id=abc → executes ✓ Worker-B gets job_id=abc → executes ← DOUBLE EXECUTION Worker-C gets job_id=abc → executes ← TRIPLE EXECUTION

Problems

  • Duplicate executions — billing disaster
  • N workers consume resources on same job
  • Inconsistent execution history records
  • Thundering herd amplified N times

Requirement

Exactly one Scheduler node should enqueue jobs at any given time — the leader.

Needs fast failover: if the leader dies, a follower must detect within the lock TTL and take over, running a look-back to catch any missed jobs.

⏰ Scheduler Engine

Leader Election — Redis SETNX Solution

ACQUIRING THE LOCK: SET scheduler_leader "scheduler-02" NX EX 30 ↑ ↑ ↑ NX EX TTL=30s NX = SET only if Not eXists Returns OK → you are the leader, proceed to enqueue Returns nil → another node holds the lock, stand by RENEWING (every 15s while still leader): SET scheduler_leader "scheduler-02" XX EX 30 (XX = only update if already exists — prevents hijacking) FAILOVER (leader crashes): TTL expires automatically after 30s scheduler-03: SET scheduler_leader "scheduler-03" NX EX 30 → Returns OK → scheduler-03 is the new leader → Runs LOOK-BACK: find jobs due in past 5 min with no ENQUEUED execution → ZADD immediately
Split-brain safe: Redis is single-process. SETNX is atomic. No two nodes can both receive NX=OK simultaneously.

Failover Timeline

  • Leader dies at t=0
  • Lock auto-expires: t≤30s
  • New leader acquires lock: t≈30s
  • Look-back re-enqueues missed jobs
  • Max job delay: ~30 seconds

The Crash Scenario (At-least-once)

Worker A starts job, network partitions at t=60s → heartbeat expires at t=90s → Monitor re-enqueues → Worker B starts same job with a different execution_id. Both may complete. System records two execution rows with different UUIDs. Business outcome is identical if job is idempotent.

Rule: Default at-least-once. Mark jobs idempotent=false to opt into distributed lock. Idempotency is a contract between job authors and the scheduler.
⏰ Scheduler Engine

Idempotent Job Design Patterns

Pattern 1 — Check-before-act

# "send welcome email" job def run(job_id, execution_id): already_sent = emails.exists( job_id=job_id, date=today() ) if already_sent: return # idempotent skip send_email(user_id) emails.insert(job_id, today())

Pattern 2 — Output key check

# "generate report" job def run(job_id, date): key = f"s3://reports/{date}/{job_id}" if s3.exists(key): return # report already exists report = generate_report() s3.upload(key, report)

Pattern 3 — Distributed Lock (non-idempotent)

# "charge card" — NOT idempotent lock_key = f"job_executing:{job_id}" acquired = redis.set( lock_key, execution_id, nx=True, ex=timeout + buffer ) if not acquired: return # another worker holds lock try: charge_credit_card() finally: redis.delete(lock_key)
Retry with exponential backoff:
Attempt 1: immediate → Attempt 2: 60s → Attempt 3: 120s+jitter → Attempt 4: 240s+jitter → DEAD_LETTER
⚙️ Worker & Recovery

Worker Heartbeat & Job Recovery

Heartbeat Protocol

# Worker execution loop def execute(job_id, worker_id): # 1. Announce: I own this job redis.set( f"job_heartbeat:{job_id}", worker_id, ex=90 ) # 2. Start renewal thread (every 30s) start_renewer(job_id, interval=30) # 3. INSERT running_jobs index row cassandra.insert_running(job_id) # 4. Execute job logic result = run_job(job_id) # 5. Mark complete, remove index row update_status(result) cassandra.delete_running(job_id)

Monitor Service Recovery Flow

Every 30 seconds: 1. SELECT * FROM running_jobs WHERE shard_date = today() 2. For each row: hb = GET job_heartbeat:{job_id} if hb is nil: ← worker died! UPDATE execution → FAILED score = now + (index * 0.1s) ZADD job_queue score job_id (staggered to avoid restart spike) 3. If stuck_count > 10x_normal: → ALERT before re-enqueueing (circuit breaker — root cause may still be active)

Safety Margin

TTL=90s, renewal=30s → 3 missed renewals before timeout. Network blips will not falsely trigger recovery.

⚙️ Worker & Recovery

Priority Queue — Redis Sorted Set

Composite Score (priority + time)

# Encode priority into score priority_offset = (10 - priority) * 1e12 score = priority_offset + fire_time_unix # High priority (9) due at unix=1724200000: score = 1e12 + 1724200000 = 1_001_724_200_000 # Low priority (1) due at same time: score = 9e12 + 1724200000 = 9_001_724_200_000 # ZPOPMIN returns lowest score first # → high-priority always ahead of low # → within same priority: time-ordered
Single sorted set gives time + priority ordering with one atomic ZPOPMIN call.

Kafka Variant — Separate Topics per Priority

PriorityTopicConsumers
High (8-10)high_priority_run50
Medium (5-7)medium_priority_run30
Low (1-4)low_priority_run20

Starvation Prevention — Aging

If low-priority job waits >1 hour → boost priority by 1 every 30 minutes until it executes. Prevents indefinite starvation when high-priority queue is saturated.

⚙️ Worker & Recovery

Dead Job Handling & Missed Schedules

DEAD_LETTER State

  • Job hits max_retries (default 3 = 4 total attempts)
  • Status → DEAD_LETTER, no more auto-retry
  • PagerDuty CRITICAL alert fired immediately
  • Requires manual re-trigger via API
  • Full error message preserved in execution record
  • Alert includes: error_msg, retry history, timeout vs exception

Missed Schedule (Leader Crash Look-back)

New leader on startup: SELECT * FROM jobs_by_next_run WHERE next_run_at BETWEEN (now - 5min) AND now AND status = 'ACTIVE' Check: does ENQUEUED execution already exist for this job? If no → ZADD immediately to Redis

Thundering Herd on Monitor Restart

Monitor down for 2 hours → 1000s of jobs stuck in RUNNING. Re-enqueueing all at once overwhelms workers and downstream services.

Solution: Staggered Re-enqueue

for i, job_id in enumerate(stuck): score = now + (i * 0.1) # 100ms redis.zadd(job_queue, {job_id: score}) # 1000 jobs over ~100 seconds # ≈ 10 jobs/sec steady drain
Circuit breaker: if stuck count >10× normal → alert BEFORE re-enqueueing. Root cause may still be active.
⚙️ Worker & Recovery

Distributed Lock — Prevent Double Execution

THE CRASH SCENARIO (at-least-once without lock): t=0:00 Worker A ZPOPMIN → picks up job123, starts execution t=0:01 Worker A SET job_heartbeat:job123 "worker-A" EX 90 t=1:00 Network partition — Worker A loses Redis connection t=1:30 Heartbeat expires (90s TTL) t=1:31 Monitor detects nil heartbeat → re-enqueues job123 t=1:32 Worker B ZPOPMIN → picks up job123, starts execution t=2:00 Worker A's network recovers → continues executing t=2:30 ⚠ BOTH Worker A and Worker B complete job123 SOLUTION — Redis SETNX per job: Worker A: SET job_executing:job123 exec-uuid-A NX EX 1800 → OK Worker B: SET job_executing:job123 exec-uuid-B NX EX 1800 → nil Worker B: SKIP — another worker holds the execution lock Worker A crashes mid-execution: → Lock TTL expires automatically after timeout+buffer → Monitor re-enqueues; Worker C acquires lock cleanly
Guarantee: At most one lock holder at any point in time. Combined with heartbeat TTL → effectively-exactly-once for non-idempotent jobs.

Lock Key Pattern

Key: job_executing:{job_id}
Value: execution_id (UUID)
TTL: timeout_seconds + buffer
Release: DEL on job completion

Database Schema — Cassandra

CREATE TABLE jobs ( job_id UUID, name VARCHAR, cron_expr VARCHAR, -- null=one-time job_type VARCHAR, -- CRON|ONE_TIME payload TEXT, -- JSON or S3 key max_retries INT, timeout_seconds INT, status VARCHAR, -- ACTIVE|PAUSED next_run_at TIMESTAMP, created_at TIMESTAMP, PRIMARY KEY (job_id) ); CREATE MATERIALIZED VIEW jobs_by_next_run AS SELECT * FROM jobs WHERE status = 'ACTIVE' AND next_run_at IS NOT NULL PRIMARY KEY (status, next_run_at, job_id);
CREATE TABLE job_executions ( job_id UUID, -- PARTITION KEY execution_id TIMEUUID, -- CLUSTERING KEY worker_id VARCHAR, status VARCHAR, started_at TIMESTAMP, finished_at TIMESTAMP, retry_count INT, error TEXT, PRIMARY KEY (job_id, execution_id) ) WITH CLUSTERING ORDER BY (execution_id DESC); -- newest first CREATE TABLE running_jobs ( shard_date DATE, -- PARTITION KEY job_id UUID, -- CLUSTERING KEY execution_id TIMEUUID, worker_id VARCHAR, started_at TIMESTAMP, PRIMARY KEY (shard_date, job_id) );
TIMEUUID clustering key gives natural time-ordering for free. Partition per job_id → O(1) read for any job's execution history. shard_date partition on running_jobs → Monitor reads one partition, never a full scan.

🎯 Interview Prep

Senior Trap Q&A #1 — Double Execution

Q: Worker A picks up job123. Network partitions for 3 minutes. Monitor re-enqueues. Worker B executes. Worker A's network recovers. What happens?

Answer

  • Worker A and B each hold a different execution_id (UUID)
  • Both may complete — system records two rows in job_executions
  • Idempotent job (report → S3 overwrite): no harm, same outcome twice
  • Non-idempotent job (charge card): use distributed lock:
SET job_executing:{jobId} {exec_id} NX EX {timeout} Worker A holds lock → Worker B's SETNX → nil → skips Worker A crashes → TTL auto-releases Worker C acquires cleanly → executes once
Follow-up — split-brain (two schedulers both think they're leader)?
Redis SETNX is atomic — impossible for two nodes to both get NX=OK. Use ZADD NX so even if the same job_id is ZADD'd twice by a confused scheduler, it only appears once in the sorted set with one score.
🎯 Interview Prep

Senior Trap Q&A #2 — Leader Crash & Thundering Herd

Q: Scheduler leader crashes at 2:59am. The 3am cron jobs are never enqueued. What happens?

Answer

  1. Leader lock TTL = 30s. Follower acquires lock within 30 seconds.
  2. New leader runs look-back query: jobs due in past 5 min with no ENQUEUED execution → ZADD to Redis immediately.
  3. 3am jobs start at worst 3:00:30 — 30s delay acceptable for batch jobs.
  4. If sub-second SLA needed: reduce lock TTL to 10s (more frequent renewals).
Q: 10,000 cron jobs all set to "0 2 * * *". How do you prevent thundering herd?

Answer

next_run = cron_time + hash(job_id) % 300 # Result: 10K jobs spread over 5 min # ≈ 33 jobs/sec (vs 10K/sec spike) # Same job → same jitter offset # every execution (predictable)

Expose max_jitter_seconds per job — default 300s, configurable to 0 for precise timing requirements.

🎯 Interview Prep

Senior Trap Q&A #3 — Hot Partitions & Redis Scale

Q: A high-frequency job's job_executions partition accumulates 864M rows/day — Cassandra anti-pattern. How do you fix it?

Three Options

  1. Time-bucket PK: partition key = (job_id, date). One partition per job per day. Matches natural query: "show executions for job X on Aug 21."
  2. Shard suffix: job_id + (hash % N) → N partitions per job. Fan-out reads required.
  3. Aggregate + archive: hourly summaries in Cassandra; raw events → Redshift/BigQuery for deep history.
Start with option 1 — simplest, natural query fit.
Q: Workers auto-scale to 100K instances. Does Redis ZPOPMIN become the bottleneck?

Answer

Redis handles ~100K–1M simple ops/sec. At 10K/sec = 1–10% capacity. Fine.

At 100K workers / high contention:

  1. Batch pop: ZPOPMIN job_queue 10 — 10× fewer round trips.
  2. Priority shards: separate job_queue_high / med / low sorted sets.
  3. Redis Cluster: shard by job_type — linear scale-out across nodes.
Add sharding at 100K+ exec/sec. Single Redis is fine for this design.

Closing & What NOT to Say

The 5-Minute Rapid Answer

"Four services: API Service (CRUD jobs), Scheduler Service (leader-elected, reads Cassandra every 30s, ZADDs to Redis ZSET scored by unix timestamp), Worker Pool (stateless, ZPOPMIN, execute, heartbeat every 30s), Monitor Service (scans expired heartbeats every 30s, marks FAILED, re-enqueues). Redis sorted set for queue, Cassandra as source of truth."
Say this: "ZPOPMIN is atomic — multiple workers cannot grab the same job simultaneously. That is why Redis sorted set, not Kafka. Kafka is FIFO — it cannot answer 'give me all jobs due RIGHT NOW regardless of when they were enqueued.' ZADD NX prevents duplicate entries even if the scheduler adds the same job twice."

What NOT to Say ✗

  • ✗ "Use Kafka as the job queue" — Kafka is FIFO, no time-ordered pop. (OK only with a DB watcher layer — Variant B.)
  • ✗ "Poll DB every second" — 1M × SELECT/sec = catastrophic DB load
  • ✗ "Single cron daemon" — SPOF; server restarts = missed jobs; no scale
  • ✗ "At-most-once is fine" — missing a billing run is worse than running it twice
  • ✗ "Store large payloads in Redis" — bloats memory, slows ZPOPMIN
  • ✗ "Each scheduler node enqueues independently" — N duplicate executions per job
