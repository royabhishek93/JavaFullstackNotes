🎯 Interview Prep

One-Liner Architecture Anchor

Memorise this before your interview:

"Instructor uploads video → S3 presigned URL → FFmpeg transcode (1080p/720p/480p/360p) → HLS 6-sec segments → CloudFront CDN (<2sec startup) → Student watches → Progress batched 30sec → Kafka consumer upserts (last_position_sec resume, max_position_sec completion) → Stripe payment with idempotency → Certificate on 100% completion"

Why this one-liner works

  • Covers the entire lifecycle end-to-end
  • Signals you know async vs sync boundaries
  • Shows two position fields awareness (trap question)
  • Drops Kafka, S3, CloudFront, Stripe — key buzzwords
  • Demonstrates idempotency understanding at payment layer

Critical Gotchas to Pre-empt

  • NEVER sync transcode during upload — 10-15 min for 2 GB
  • HLS + CDN mandatory for <2s — raw S3 alone fails
  • last_position_sec ≠ max_position_sec — rewind trap
  • Payment idempotency has 5 layers, not just UNIQUE constraint
  • course_stats is denormalized — no COUNT(*) in hot path

HLD — Every Service and Its Role

Course Catalog Service

  • CRUD on courses → Course DB (MySQL)
  • Publishes CDC changes → Elasticsearch (full-text search sync)
  • Redis cache: course details 1h TTL, 90% hit rate
  • Reads from course_stats (denormalized) — no COUNT aggregations

Video Playback Service

  • Checks Access table (not just Enrollment) before serving
  • Generates CloudFront signed URL (expires 24h)
  • Returns master.m3u8 → client player handles ABR
  • Separate from Media Uploader Svc (SRP)

User Progress Service

  • Receives batched heartbeats (every 30s)
  • Publishes to Kafka video.progress (100 partitions, key=user_id)
  • Returns 200 OK immediately — async, doesn't block video

Enrollment Service

  • Kafka consumer on payment.completed
  • Idempotency check before INSERT enrollment
  • Updates course_stats.enrolled counter async
  • UNIQUE(user_id, course_id) DB-level guard

Payment Service

  • Creates Stripe PaymentIntent with enrollmentRequestId
  • Verifies Stripe webhook signature
  • Publishes payment.completed to Kafka on success
  • Polling backup: checks Stripe API every 5 min for PENDING

Permission Sync Service

  • Listens to payment/refund/subscription Kafka events
  • payment.completed → INSERT Access (LIFETIME, ACTIVE)
  • refund.issued (30-day window) → UPDATE Access REVOKED
  • subscription.expired → UPDATE Access EXPIRED

Video Upload & Transcoding Pipeline

Instructor → POST /instructor/courses/C123/lessons/L456/video │ ▼ Media Uploader Svc presignedURL = s3.generatePresignedUrl('putObject', { Bucket: 'course-videos-raw', Key: 'courses/C123/lessons/L456/original.mp4', Expires: 3600 }) Response: { uploadURL, videoId: 'V789' } │ ▼ (client uploads DIRECTLY to S3 — bypasses server) S3 PUT {presignedURL} ← chunked, resumable, up to 5 GB │ ▼ S3 event → Lambda (on ObjectCreated) Lambda publishes Kafka 'video.uploaded': { videoId:'V789', courseId:'C123', lessonId:'L456', s3Key, fileSize: 2_000_000_000 } │ ▼ Video Processing Worker (Kafka consumer, Spot instances) 1. Download original.mp4 from S3 2. FFmpeg transcode → 4 resolutions: 1080p 1920×1080 5 Mbps 720p 1280×720 2.5 Mbps 480p 854×480 1 Mbps 360p 640×360 500 Kbps 3. HLS packaging (per resolution): ffmpeg -i 1080p.mp4 -c copy -f hls -hls_time 6 \ -hls_segment_filename '1080p_%03d.ts' 1080p.m3u8 → master.m3u8 + 4 variant playlists + .ts segments 4. Thumbnail extraction: frames at 0s, 5s, 10s (JPEG) 5. Upload all → s3://course-videos-cdn/C123/L456/ 6. UPDATE lessons SET video_url = 'https://cdn.example.com/.../master.m3u8', processing_status = 'COMPLETED', duration_sec = 1200 │ ▼ Notification Svc → email instructor "Video ready"

Why Async?

  • 2 GB video = 10–15 min processing (4 resolutions + HLS)
  • Holding HTTP connection 10+ min = timeouts + terrible UX
  • Async: instructor gets immediate upload confirmation
  • Spot instances = 70% cost reduction vs on-demand

HLS Output Structure

master.m3u8 → 1080p.m3u8 (1080p variant playlist) → 1080p_000.ts (6 sec segment) → 1080p_001.ts → ... → 720p.m3u8 → 480p.m3u8 → 360p.m3u8
Never transcode synchronously during upload. Always: S3 → Lambda → Kafka → Worker pool.

🎓 Course Delivery

HLS Adaptive Bitrate — How It Works

master.m3u8 Structure

#EXTM3U #EXT-X-VERSION:3 #EXT-X-STREAM-INF:BANDWIDTH=5000000, RESOLUTION=1920x1080 1080p.m3u8 #EXT-X-STREAM-INF:BANDWIDTH=2500000, RESOLUTION=1280x720 720p.m3u8 #EXT-X-STREAM-INF:BANDWIDTH=1000000, RESOLUTION=854x480 480p.m3u8 #EXT-X-STREAM-INF:BANDWIDTH=500000, RESOLUTION=640x360 360p.m3u8

variant playlist (1080p.m3u8)

#EXTM3U #EXT-X-TARGETDURATION:6 #EXT-X-VERSION:3 #EXTINF:6.000000, 1080p_000.ts #EXTINF:6.000000, 1080p_001.ts #EXTINF:5.968000, 1080p_002.ts ... #EXT-X-ENDLIST

ABR Decision Logic

  • Player downloads first segment → measures bandwidth
  • Selects highest quality that fits available bandwidth
  • Monitors buffer level every 2 seconds
  • Buffer < 10s → drop quality; Buffer > 30s → raise quality
  • Switches mid-stream: seamless, no buffering
  • User on slow network gets 360p (500 Kbps) not a spinning wheel

Why 6-second segments?

  • Short enough for quick quality switches (~6s lag)
  • Long enough to amortize HTTP overhead
  • Sweet spot: industry standard (Apple, Netflix use 2-10s)
  • Each segment independently cacheable by CDN
  • Seek: jump to segment containing timestamp directly
FFmpeg command: -hls_time 6 -hls_segment_filename '1080p_%03d.ts' — the 6 sets segment duration.
📊 Progress Tracking

Progress Tracking — Event-Driven at Scale

Video player (client-side) Heartbeat every 10 sec: { courseId:'C123', lessonId:'L456', videoId:'V789', position: 120, action:'WATCHING', timestamp } Batching — 3 events per 30 sec: POST /progress/events body: { events: [ {position:120, ts:'10s'}, {position:130, ts:'20s'}, {position:140, ts:'30s'} ]} → Reduces API calls 3× → 1M students × 6 events/min = 6M → 2M calls/min │ ▼ User Progress Service FOR EACH event: kafka.send('video.progress', { key: userId, ← ensures ordering per user value: {userId, courseId, lessonId, videoId, position:140, timestamp} }) Response: 200 OK immediately ← async, non-blocking │ ▼ user_tracking_consumer_svc (10 instances, 100 Kafka partitions, key=user_id) Upsert: INSERT INTO progress (user_id, course_id, lesson_id, video_id, last_position_sec=140, max_position_sec=140) ON CONFLICT (user_id, course_id, lesson_id) DO UPDATE SET last_position_sec = EXCLUDED.last_position_sec, max_position_sec = GREATEST(progress.max_position_sec, EXCLUDED.max_position_sec), updated_at = now() Completion check: IF max_position_sec >= duration_sec * 0.95 UPDATE progress SET status='COMPLETED', completed_at=now() Recompute enrollment completion_status IF completion_status = 100.00: Publish Kafka 'course.completed'

Kafka Partition Strategy

  • 100 partitions on video.progress topic
  • Partition key = user_id — all events for same user → same partition
  • Guarantees ordering per user, parallelism across users
  • 10 consumers × 10K events/sec = 100K events/sec total
  • Auto-scale on lag > 1000 messages

Resume Functionality

GET /me/courses/C123/lessons/L456/progress → { lastPosition: 140, ← resume here duration: 1200, percentWatched: 11.7%, status: 'IN_PROGRESS' } Client: videoPlayer.seek(140)
💡 The idempotent upsert is the key insight — safe to reprocess Kafka events on consumer restart. GREATEST() ensures max never decreases.
📊 Progress Tracking

The Two Position Fields — Senior Trap

last_position_sec

  • Purpose: Where to resume playback
  • Update: Always set to latest position sent
  • Behavior on rewind: Decreases (user rewound to 0s → last=0)
  • Used by: Client seeks to this position on lesson open

max_position_sec

  • Purpose: Farthest point ever watched (completion check)
  • Update: GREATEST(existing, new) — never decreases
  • Behavior on rewind: Stays at previous max
  • Used by: Completion check — if max ≥ duration × 0.95

Concrete Scenario — Why Both Are Needed

Video duration: 1200 sec (20 min) Completion threshold: 1140 sec (95%) Scenario: User watches to 800s → last=800, max=800 User rewinds to 0s → last=0, max=800 User watches to 150s → last=150, max=800 User closes the app Resume: seeks to 150s ← last_position_sec ✓ Completion: 800 < 1140 → IN_PROGRESS (correct, not complete) ← max never decreased on rewind ✓ If ONLY one field (naive approach): After rewind: position=0 Completion check: 0 < 1140 → resets to not complete 😱 User loses their 67% progress record on rewind!
This is the #1 interview trap. If you have only one field you will incorrectly mark 67%-watched lesson as incomplete when user rewinds. Always use both fields.

Enrollment Idempotency — 5 Layers

#LayerMechanismProtects Against
1Client double-clickSame enrollmentRequestId (client UUID) → Stripe returns existing PaymentIntentUser clicks Enroll twice rapidly
2Webhook signatureVerify Stripe HMAC signature → reject unsigned requestsFake/forged webhook
3Kafka consumer DB checkSELECT COUNT(*) before INSERT → skip if already enrolledDuplicate Kafka event / webhook retry
4DB UNIQUE constraintUNIQUE(user_id, course_id) → INSERT fails at DB levelRace condition between two consumers
5Polling backupPayment Svc polls Stripe every 5 min for PENDING payments → manually triggersWebhook lost / delayed

All paths converge

Whether the trigger is webhook, polling, or manual retry — every path runs the same idempotent consumer logic. The outcome is always exactly-once enrollment regardless of which path fires first or how many times it fires.

Key: enrollmentRequestId is client-generated

  • Server NEVER generates idempotency keys — client does
  • Client UUID generated before payment button click
  • Stored in Stripe metadata → returned on any duplicate call
  • This is the interview gotcha — who generates the key?
All 5 layers together: no double charging, no double enrollment, no lost enrollments — even with network partitions, Kafka restarts, or Stripe webhook retries.
🎓 Course Delivery

Quiz System Design

Quiz structure: quiz_id, lesson_id, title pass_score: 70%, time_limit: 600s, attempts_allowed: 3 Questions: question_id, quiz_id, question_text type: MCQ_SINGLE / MULTI_SELECT / FILL / SELECT / TRUE_FALSE / TEXT options: JSON [{id:'A', text:'...'}, ...] correct_answer: 'A', points: 10 Quiz attempt flow: 1. POST .../quiz/start → INSERT quiz_attempts (status='IN_PROGRESS', started_at=now(), attempt_number) → rate limit: check cooldown (24h between retries) 2. GET .../quiz/questions → { questions (shuffled), timeLimit:600, totalPoints:100 } → timer starts client-side 3. POST .../quiz/submit body: { answers: [ {question_id:'Q1', answer:'A'}, {question_id:'Q2', answer:['A','C']} ]} 4. Auto-grading (MCQ): FOR EACH answer: IF answer === correct_answer score += points percentage = (score / total_points) × 100 passed = percentage >= 70 5. UPDATE quiz_attempts SET score=85, percentage=85.0, status='COMPLETED', passed=true, completed_at=now() 6. IF passed: UPDATE progress SET status='COMPLETED' → triggers enrollment completion_status recompute

Retake Policy

  • attempts_left = attempts_allowed - attempts_used
  • If failed + attempts_left > 0 → allow retake
  • Cooldown: 24h between attempts (prevents brute-force)
  • If exhausted → 403 "No attempts remaining, contact instructor"

Rate Limiting at API Gateway

  • Token bucket: 100 req/min per userId (from JWT)
  • Protects against quiz brute-force (guess answers rapidly)
  • Also prevents progress event flooding
  • Prevents course catalog scraping
  • Key = userId, not IP (authenticated requests)

Assignment Grading (Manual)

  • Student submits text/file → stored in S3
  • Instructor reviews and enters score manually
  • On pass: triggers same progress completion flow
🎓 Course Delivery

Certificate Generation Service

Trigger: enrollment.completion_status = 100% How it gets to 100%: user_tracking_consumer_svc detects: max_position_sec >= duration_sec × 0.95 (per lesson) → marks lesson progress status='COMPLETED' → recomputes: completed_lessons / total_lessons × 100 UPDATE enrollments SET completion_status = X.XX → IF completion_status = 100.00: Publish Kafka 'course.completed': { userId, courseId, enrollmentId, completedAt } Certificate Consumer (Kafka listener): 1. Idempotency guard: SELECT COUNT(*) FROM certificates WHERE user_id=? AND course_id=? → count > 0 → SKIP (Kafka retry safety) 2. Generate certificate: certificate_id = UUID template = fetch course template from S3 fill: student_name, course_title, instructor_name, completion_date render → PDF/PNG upload → s3://certificates/{userId}/{courseId}.pdf 3. INSERT certificates ( certificate_id, user_id, course_id, issued_at, s3_url ) 4. Notification Svc → email student: "Congratulations! Download your certificate" → CloudFront signed URL (24h) in email 5. UPDATE enrollments SET certificate_url = signedS3Url

Completion Calculation

  • Each lesson tracked independently in Progress table
  • Video lesson: 95% watched threshold (max_position_sec)
  • Quiz lesson: passed = true (score ≥ pass_score)
  • All lessons must be COMPLETED before certificate issues
  • Formula: (completed_lessons / total_lessons) × 100

Certificate Verification

  • Unique certificate_id (UUID) embedded in PDF
  • Public verification URL: /verify/{certificate_id}
  • Returns: student name, course, date, instructor
  • Shareable on LinkedIn, immune to forgery
Idempotency is critical: Kafka consumer may retry. Guard with SELECT COUNT(*) before issuing — never issue duplicate certificates.
🏛 HLD

Course Discovery & Search — Elasticsearch

CDC Pipeline (Course DB → Elasticsearch): Aggregator CDC service listens to: - INSERT on courses (new course published) - UPDATE on courses (title/desc/price change) - UPDATE on course_stats (rating/enrollment change) → transforms row → Elasticsearch document: { course_id, title, description, tags, category, difficulty, price, rating, students_enrolled, instructor_name, published_status } → upsert into 'courses' ES index Search query: GET /courses?search=machine+learning&category=IT &price=0-50&rating=4&level=BEGINNER &sort=rating Elasticsearch query: { "bool": { "must": [ { "multi_match": { "query": "machine learning", "fields": ["title^3","description","tags^2"], "type": "best_fields" } } ], "filter": [ { "term": { "category": "IT" } }, { "range": { "price": { "lte": 50 } } }, { "range": { "rating": { "gte": 4 } } }, { "term": { "difficulty": "BEGINNER" } }, { "term": { "published_status": "PUBLISHED" } } ] }, "sort": [{ "rating": "desc" }] }

Elasticsearch Features Used

  • Full-text search on title/description/tags with field boosting (title^3)
  • Autocomplete via ngram tokenizer (3-5 char n-grams)
  • Faceted filtering: category, price range, rating, difficulty
  • Complex aggregations (category counts, price histogram) <100ms
  • Relevance scoring with BM25 + field boosts

Redis Cache Layer

  • Popular search results cached (TTL 1h)
  • Key: search:{hash(query+filters)}
  • 90% of searches hit cache (tail queries are unique)
  • Invalidated on course_stats update via CDC
CDC ensures Elasticsearch is always within seconds of Course DB — no manual sync jobs needed.

HLS vs DASH — Top Comparison #1

HLS (HTTP Live Streaming)

  • Developed by Apple (2009), industry standard
  • Manifest: .m3u8 format
  • Segments: .ts (MPEG-TS container)
  • Native support: Safari, iOS, macOS
  • Requires hls.js on Chrome/Firefox (JS library)
  • Segment duration: typically 6-10 sec
  • Encryption: AES-128, Sample-AES
  • DRM: FairPlay (Apple only)
  • Pro: Universal CDN caching, battle-tested, Apple native
  • Con: Higher latency for live (15-30s)

DASH (Dynamic Adaptive Streaming over HTTP)

  • ISO standard (2011), open specification
  • Manifest: .mpd (XML-based)
  • Segments: fMP4 (fragmented MP4) — more efficient
  • Supported by: YouTube, Netflix, Amazon Prime
  • Browser support: Chrome, Firefox (via dash.js)
  • Better compression: fMP4 ~10-15% smaller than .ts
  • DRM: Widevine (Google) + PlayReady (Microsoft)
  • Pro: Open standard, better compression, Widevine support
  • Con: No native iOS support (needs MSE), more complex

Winner for EdTech: HLS

iOS/Safari dominance in education apps + simpler CDN caching + FairPlay DRM makes HLS the right choice for Udemy/Coursera. Use DASH only if targeting primarily Android/Chrome and need Widevine.

PostgreSQL vs MongoDB — Top Comparison #2

PostgreSQL (chosen for core tables)

  • ACID transactions — critical for Payments + Enrollments
  • UNIQUE constraints — double-enrollment prevention
  • Foreign keys — referential integrity (course_id, user_id)
  • DECIMAL precision — payment amounts ($49.99 must be exact)
  • Complex joins — enrollment + progress + course in one query
  • JSONB column — flexible metadata without schema changes
  • Mature replication, read replicas, PgBouncer pooling
  • Use for: Users, Courses, Enrollments, Payments, Progress

MongoDB (consider for)

  • Schema-free — course curriculum changes often (sections/lessons nested)
  • Document model: course + all lessons in one document (no joins)
  • Better for deeply nested: quiz questions, options, metadata
  • Flexible: different lesson types (video/quiz/text) without NULLs
  • Horizontal scaling built-in (sharding native)
  • Risk: No multi-document ACID (prior to v4), joins via $lookup are slow
  • Use for: Course curriculum structure, quiz question bank, comments

Hybrid Decision

PostgreSQL for transactional data (payments, enrollments, progress). MongoDB for document-heavy course content (curriculum, quizzes). Most EdTech platforms use PostgreSQL as primary with JSONB for flexibility.

Senior Trap Q&As — Part 1

Q1: Why not sync transcode on video upload?

Trap: "We can just transcode when instructor uploads and return the URL in the same response."

Answer: 2 GB video = 10-15 minutes of FFmpeg processing (4 resolutions + HLS packaging + thumbnails). Holding an HTTP connection for 10+ minutes causes gateway timeouts, wasted thread resources, and terrible UX. The correct design: client uploads to S3 presigned URL (server not involved), S3 event → Lambda → Kafka → Spot Worker pool. Instructor gets immediate 200 OK, receives email when video is ready. Spot instances reduce compute cost by 70%.

Q2: Why two position fields in Progress table?

Trap: "Just store the current playback position — that's all you need."

Answer: Two distinct semantics: last_position_sec = where to resume (always latest, decreases on rewind), max_position_sec = farthest ever watched (GREATEST update, never decreases). If only one field: user watches to 800s, rewinds to 0, closes app → stored position=0 → system thinks 0% watched, marks lesson incomplete — losing 67% of progress. With two fields: last=0 (resume at 0), max=800 (67% complete — correct). Completion fires when max ≥ duration × 0.95.
🎯 Interview Prep

Senior Trap Q&As — Part 2

Q3: Enrollment just checks Enrollment table for access?

Trap: "Video Playback checks enrollments to decide if user can watch."

Answer: Wrong table. Video Playback checks the Access table (status=ACTIVE), not Enrollments. Why? Enrolled ≠ has active access. User might have enrolled (record exists) but received a refund (access REVOKED) or subscription expired (EXPIRED). The Access table is maintained by Permission Sync Svc via Kafka events: payment.completed → ACTIVE; refund.issued → REVOKED; subscription.expired → EXPIRED. Separating enrollment from access allows correct handling of all scenarios.

Q4: Who generates the idempotency key for payment?

Trap: "The server generates the idempotency key before creating PaymentIntent."

Answer: The client generates enrollmentRequestId (UUID) before the user clicks Enroll. If user double-clicks, both requests carry the same UUID → Stripe returns the same existing PaymentIntent (no second charge). Server-generated keys only protect against server crashes, not client-side double-clicks. This is the pattern used by Stripe's own documentation.

Q5: Why Kafka partition by user_id not course_id for progress?

Trap: "Partition by course_id to keep all progress for one course together."

Answer: Wrong. Partition by user_id. Reason: We need ordering per user (events for same user must arrive in order — last_position_sec must be the latest). user_id partitioning ensures all of one user's events go to the same partition → same consumer → sequential processing. course_id partitioning would put user events on different partitions → out-of-order → last_position_sec might be stale. DB is also sharded by user_id (user's progress on same shard for fast range queries).

Why Kafka? Event-Driven Decoupling

Problems Kafka Solves

  • Video progress: 1M students × 2 events/min = 2M writes/min — sync DB writes would collapse
  • Payment → Enrollment: Stripe webhook fires, enrollment must be created — async decouples them
  • Completion → Certificate: Multiple downstream actions from one event (cert + email + stats)
  • Retries: Consumer can lag, restart, reprocess — idempotent upserts handle it safely

Consumer Scaling

  • 100 partitions = max 100 parallel consumers per topic
  • Auto-scale: if consumer lag > 1000 → add instances
  • Each consumer handles ~10K events/sec
  • Total throughput: 100K events/sec per topic

Guaranteed Exactly-Once Semantics

  • Kafka guarantees at-least-once delivery
  • Consumers must be idempotent for exactly-once effect
  • Progress: ON CONFLICT upsert + GREATEST() → safe to reprocess
  • Enrollment: DB check before INSERT → skip if exists
  • Certificate: SELECT COUNT check before generate → skip if exists
  • UNIQUE constraints catch any remaining race conditions

Topic Retention

  • video.progress: 7 days (replay window for bugs)
  • payment.completed: 30 days (auditing)
  • course.completed: 30 days (idempotency window)
  • video.uploaded: 3 days (transient trigger)
