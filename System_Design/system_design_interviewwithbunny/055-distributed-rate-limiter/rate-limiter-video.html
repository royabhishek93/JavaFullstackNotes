🚦 Distributed Rate Limiter

System Design Interview Guide

Control how many requests a client can make in a time window, at scale, without becoming a bottleneck.

Token Bucket Leaky Bucket Sliding Window Redis Lua Fixed Window Distributed
Core Idea: A rate limiter sits between the Load Balancer and backend services. Every request hits the API Gateway, which extracts the client identity and asks Redis: does this client have budget left? Reject excess requests with HTTP 429.

Real-world users: AWS API Gateway · Stripe · GitHub REST API · Twitter · Twilio

Opening Script — Speak This in 2–3 Minutes

"A rate limiter sits between the Load Balancer and your backend services.
 Every request hits the API Gateway, which extracts the client identity —
 user ID, API key, or IP — and asks Redis: does this client have budget left?

 I'd implement Token Bucket with a Redis Lua script.
 Each user gets a bucket with 100 tokens that refills at 10 tokens/sec.
 The Lua script atomically reads the current token count, calculates how
 many tokens refilled since the last request, deducts one, and returns
 allow or reject. Atomic execution means two simultaneous requests on
 different Gateway instances can never both see 'tokens = 1' and both go.

 On rejection I return HTTP 429 with Retry-After and X-RateLimit-Reset
 headers so the client can back off intelligently.

 Rate-limit policies — who gets 100/min vs 1000/min — live in a Postgres
 table, cached in Redis for an hour so the hot path never touches the DB.

 The whole check adds less than 5 ms to every request."
Key phrase to open with: "Token Bucket in Redis Lua — atomic, burst-friendly, proven at AWS and Stripe, adds under 5ms per request."

Algorithm 1: Fixed Window Counter

TIMELINE  (window = 60 sec, limit = 100 req/window)

  09:59:00         10:00:00          10:01:00
      |                |                 |
      |<-- Window A --->|<-- Window B --->|

  BOUNDARY SPIKE PROBLEM:
     99 req at 10:00:59 ─── last second of Window A ───► allowed (count=99)
    100 req at 10:01:00 ─── first second of Window B ──► allowed (count=100)
    ──────────────────────────────────────────────────────────────────────
    199 requests in 2 seconds  ← violates 100/min spirit!

Redis implementation:
  Key  : rate_limit:{user_id}:{window_start_unix}
  INCR   rate_limit:user123:1706270400
  EXPIRE rate_limit:user123:1706270400 60
  GET    rate_limit:user123:1706270400
  → if value < 100 → allow  else → 429
Pick when: Internal microservice-to-microservice calls, not user-facing
Avoid when: User-facing APIs — boundary abuse is exploitable and deterministic

Algorithm 2: Sliding Window Log

TIMELINE  (window=60s, limit=100, now=10:00:45)

  Redis ZSET — score = unix timestamp, member = request UUID
  ┌────────────────────────────────────────────────────────┐
  │  score=10:00:05  req_id=abc                            │
  │  score=10:00:12  req_id=def                            │
  │  score=10:00:30  req_id=ghi  ← 85 entries total       │
  │  score=10:00:44  req_id=jkl                            │
  └────────────────────────────────────────────────────────┘

  Window boundary: 10:00:45 - 60 = 09:59:45

  ZREMRANGEBYSCORE key 0 09:59:44       ← prune expired entries
  ZCOUNT key 09:59:45 10:00:45          ← count = 85
  85 < 100 → allow
  ZADD key 10:00:45 new_req_uuid        ← record this request

  Memory cost: 50M users × 100 req = 5 BILLION entries in Redis
  → NOT viable for high-traffic public APIs
Pick when: Low-traffic, accuracy-critical APIs (fraud detection, login attempts)
Avoid when: High-traffic — memory explodes O(requests_per_window) per user

Algorithm 3: Sliding Window Counter (Hybrid)

TIMELINE  (window=60s, limit=100, now=10:00:45)

  Previous window (09:59:00–09:59:59): counter = 80
  Current  window (10:00:00–10:00:59): counter = 30
  Elapsed in current window: 45 sec → 75% of window complete

  Weighted count formula:
  ┌─────────────────────────────────────────────────────────┐
  │  weighted = (prev × (1 - elapsed_fraction)) + current   │
  │           = (80  × (1 - 0.75))              + 30        │
  │           = (80  × 0.25)                    + 30        │
  │           = 20 + 30 = 50                               │
  └─────────────────────────────────────────────────────────┘
  50 < 100 → allow

  Redis: only 2 integer keys per user (current + previous window)
    rate_limit:user123:current   = 30   TTL = 60s
    rate_limit:user123:previous  = 80   TTL = 120s

  Memory: 2 integers vs 100 timestamps → ~50× saving vs Sliding Log
Pick when: Good accuracy needed without full log memory cost
Avoid when: Burst support needed (use Token Bucket) or perfect accuracy (use Sliding Log)

Algorithm 4: Token Bucket ★ (Recommended)

BUCKET STATE  (capacity=100 tokens, refill_rate=10 tokens/sec)

  t=0s   [████████████████████] 100 tokens ← full bucket
  t=0s   100 req arrive instantly → ALL 100 ALLOWED (burst!)
         [                    ]   0 tokens
  t=5s   Refill: 5s × 10/s = 50 tokens added
         [██████████          ]  50 tokens
  t=5s   50 more requests → all ALLOWED
         [                    ]   0 tokens
  t=1s   Only 10 tokens refilled → 1st req allowed, 11th → 429

KEY INSIGHT:
  capacity    = max burst  (all at once — empty the bucket instantly)
  refill_rate = sustained throughput  (tokens/sec replenished)

Redis HASH state per user per endpoint:
  rate_limit:user123:/api/users
    tokens      → 95
    last_refill → 1706270445   (unix timestamp, float)
  TTL: 3600 sec (auto-expire inactive buckets → saves memory)

Real-world use: AWS API Gateway · Stripe · GitHub REST API

Algorithm 5: Leaky Bucket

QUEUE MODEL  (capacity=100, leak_rate=10 req/sec)

  Requests
  arriving ──► [■■■■■■■■■■■■■■■■■■■■] ──► Backend (10/sec, fixed)
  randomly      FIFO queue (cap=100)        smooth, constant output

  t=0s   50 requests arrive instantly → queued in bucket
  t=5s   50 processed (10/sec × 5s), bucket now empty
  t=0s   100 requests arrive → bucket at capacity
  t=0s   101st request → bucket full → REJECT 429

CRITICAL DIFFERENCE FROM TOKEN BUCKET:
  Token Bucket  → burst of 100 hits backend ALL AT ONCE
  Leaky Bucket  → burst of 100 exits at 10/sec (smooth, metered output)

Redis implementation:
  LPUSH rate_limit_queue:user123 {req_id}
  LLEN  rate_limit_queue:user123  → if > 100 → reject 429
  Worker: RPOP at fixed interval → forward to backend service
Pick when: Traffic shaping — smoothing bursts before a rate-sensitive downstream (webhooks, 3rd-party APIs)
Avoid when: Synchronous user-facing APIs (queuing adds latency, users wait longer)

Redis Lua Script — Atomic Token Bucket

-- Called via: EVAL script 1 {key} {capacity} {refill_rate} {now}
-- Runs ATOMICALLY inside Redis — no other command can interleave

local key      = KEYS[1]
local capacity = tonumber(ARGV[1])   -- e.g. 100 tokens (burst_capacity)
local rate     = tonumber(ARGV[2])   -- e.g. 10 tokens/sec (refill_rate)
local now      = tonumber(ARGV[3])   -- unix timestamp (float seconds)

local data     = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens   = tonumber(data[1]) or capacity   -- default: full bucket
local last     = tonumber(data[2]) or now

local elapsed  = now - last
local refilled = math.min(capacity, tokens + elapsed * rate)

if refilled >= 1 then
  redis.call('HMSET', key, 'tokens', refilled - 1, 'last_refill', now)
  redis.call('EXPIRE', key, 3600)
  return 1   -- ALLOW request
else
  return 0   -- REJECT → 429 Too Many Requests
end

-- WHY LUA? HMGET + HMSET are two commands. Without Lua:
-- GW1 reads tokens=1, GW2 reads tokens=1, BOTH allow → race condition!
-- With Lua: entire read-compute-write is ONE atomic Redis command.

Redis Sliding Window Log — Lua Script

-- Called via: EVAL script 1 {key} {limit} {window_sec} {now} {req_uuid}
-- ZSET approach: score = unix timestamp, member = unique request UUID

local key        = KEYS[1]
local limit      = tonumber(ARGV[1])   -- e.g. 100 requests
local window     = tonumber(ARGV[2])   -- e.g. 60 seconds
local now        = tonumber(ARGV[3])   -- current unix timestamp
local req_id     = ARGV[4]            -- unique request UUID

local min_score  = now - window        -- rolling window start boundary

-- Step 1: Remove timestamps older than the window
redis.call('ZREMRANGEBYSCORE', key, '-inf', min_score)

-- Step 2: Count requests currently inside the window
local count = redis.call('ZCOUNT', key, min_score, '+inf')

if count < limit then
  -- Step 3: Record this request in the log
  redis.call('ZADD', key, now, req_id)
  redis.call('EXPIRE', key, window + 1)
  return 1   -- ALLOW
else
  return 0   -- REJECT 429
end

-- Memory warning: O(requests_per_window) per user key
-- At 50M users × 100 req = 5B ZSET members — avoid for high-traffic!

Distributed Challenges

ChallengeProblemSolution
Race Condition GW1 and GW2 both read tokens=1 simultaneously, both allow → tokens=-1 Redis Lua script: atomic EVAL, no command can interleave between read and write
Clock Skew Different servers have different clocks → wrong refill calculations across nodes Pass Redis server time via TIME command — never trust client system clock
Shard Routing User's token key must land on the same Redis shard every time Consistent hashing: hash(user_id) → deterministic shard assignment
Replica Lag Reading from replica may show stale token count → double-allow Always EVAL Lua on MASTER; replicas only for read-only policy cache GETs
Network Partition Gateway can't reach Redis → should we allow or block all traffic? Circuit breaker: 10 failures → open circuit 30 sec → fail open (log + alert)
Interviewer trap: "Why not use Redis SETNX for distributed locks?" Answer: Redis is single-threaded — Lua makes the operation atomic WITHOUT locks. Locks add deadlock risk, timeout complexity, and extra round-trip latency.

Distributed Token Bucket — Centralized vs Gossip

Option A — Centralized Redis (Recommended)

All gateways → same Redis Cluster

  GW1 ─┐
  GW2 ─┼─► Redis Cluster ─► exact limit
  GW3 ─┘   (8 shards, consistent hash)

Pros:
  ─ Exact global limit enforced
  ─ Simple implementation
  ─ No synchronization logic needed

Cons:
  ─ Redis becomes bottleneck
    if under-provisioned
  ─ Cross-region adds latency
    (50–100ms for distant regions)

Option B — Gossip / CRDT (Complex)

Each region tracks local count.
Periodically sync deltas globally.

  us-east: 60 req counted locally
  eu-west: 45 req counted locally
  Gossip sync: total ≈ 105 (slight over)

Pros:
  ─ Low latency (local Redis)
  ─ No single point of failure
  ─ No cross-region overhead

Cons:
  ─ Approximate global limit only
  ─ Complex eventual consistency
  ─ Overshoots limit during sync gap
Multi-region recommendation: Option A per-region with per-region quotas (user gets 100/min per region → slight global over-limit acceptable). Use Option B or global Redis only for strict compliance (fintech, healthcare).

  "error":       "rate_limit_exceeded",
  "limit":       100,

  "reset_at":    "2024-04-05T10:01:29Z",   ← ISO 8601 for mobile clients
  "retry_after": 1
}

Retry-After formula : ceil((1 - tokens) / refill_rate)
Reset formula       : now + ceil((1 - tokens) / refill_rate)
Why these headers matter: Clients implement exponential backoff using Retry-After, preventing thundering herd on recovery. Must know all 4 headers in an interview.

Graceful Degradation — Fail Open vs Fail Closed

Fail Open (Recommended for most APIs)

Redis down → ALLOW all requests
Log error + increment alert counter

Circuit Breaker state machine:
  CLOSED ──(10 failures)──► OPEN
    ▲                          │
    └── HALF-OPEN ◄──(30s)────┘
    success?  │  fail?
    CLOSED    │  back OPEN

CLOSED:    Normal operation (Lua EVAL)
OPEN:      Allow all, log errors, alert
HALF-OPEN: Probe 1 request → result
           decides CLOSE or stay OPEN

Pro: Zero availability impact
Con: Brief unmetered access window

Fail Closed (Compliance only)

Redis down → return 503 ALL users

 → Complete availability collapse
 → No user can make ANY request
 → Full outage for all traffic

Use only for:
 ─ Financial APIs (over-limit = fraud)
 ─ Healthcare (compliance mandate)
 ─ Payment processing endpoints

Pro: No abuse window, strict compliance
Con: ALL users blocked during outage

Local fallback: Each gateway keeps an in-memory token bucket during Redis outage. Effective limit = per_instance_limit × num_instances. Rough protection — better than nothing.

Multi-Tier Rate Limiting — CDN → API GW → Service

TIER 1 — CDN / Edge  (Cloudflare, AWS CloudFront)
  ─ IP-based rate limiting at global PoP level
  ─ Blocks DDoS before traffic enters your data center
  ─ Limit: 10,000 req/sec per IP  (coarse infrastructure protection)
  ─ No business logic; pure volume-based filtering

TIER 2 — API Gateway  (YOUR rate limiter — this is what you design)
  ─ User + API-key + endpoint-based limits
  ─ Enforces business rules: Free=100/min, Premium=1000/min
  ─ Redis Lua Token Bucket (atomic, <5ms added latency)
  ─ Returns 429 + Retry-After + X-RateLimit-* headers

TIER 3 — Service Level  (self-protection)
  ─ PaymentSvc limits itself to 500 req/sec regardless of upstream
  ─ Circuit breaker inside each service
  ─ Prevents cascading failure if upstream limits are misconfigured

MULTI-LEVEL CHECK ORDER PER REQUEST:
  1. Check per-IP limit        → exceeded? → 429 immediately
  2. Check per-user limit      → exceeded? → 429 immediately
  3. Check per-endpoint limit  → exceeded? → 429 immediately
  4. Check global cluster cap  → exceeded? → 429 immediately
  5. All pass → forward to backend service

STRICTEST WINS: ANY level exceeded → reject immediately, no further checks

Redis Scaling — Cluster & Memory Math

CAPACITY MATH  (1M rps, 50M active users)

Token state per user per endpoint:
  key size    ≈  40 bytes  (rate_limit:user123:/api/users)
  value size  ≈  30 bytes  (HASH: tokens=int, last_refill=int)
  overhead    ≈ 100 bytes  (Redis per-key overhead)
  total/key   ≈ 170 bytes

50M users × 3 endpoints × 170 bytes = 25.5 GB active keys
  (TTL=3600s; ~5–10% hot at any time → actual ≈ 1.5–2.5 GB)

THROUGHPUT:
  1M rps → 1M Lua EVAL/sec
  Redis single node: ~300K–500K ops/sec
  Need: 1M / 300K ≈ 4 master shards minimum
  With 2× safety headroom → 8 master shards recommended
  Each shard: 1 master + 1 replica (for failover)
  Routing: consistent hash(user_id) → same shard every time

LATENCY BUDGET (target <5ms added per request):
  Policy cache GET  : 0.5 ms  (Redis read replica)
  Lua EVAL          : 1.0 ms  (Redis master write)
  Network roundtrip : 1.0 ms  (co-located in same AZ)
  Total             : ~2.5 ms ✓ within 5ms budget

OPTIMIZATIONS:
  ─ TTL=3600s on inactive buckets: auto-expire → saves memory
  ─ Connection pool: 50 connections per gateway instance
  ─ Pipelining: batch multiple EVAL calls in one round-trip

Senior Q&A 1 — What Happens When Redis Goes Down?

WEAK ANSWER: "Restart Redis."  ← will fail the interview

STRONG ANSWER:

  Two options — both valid, different trade-offs:

  FAIL OPEN (my recommendation for most APIs):
  ─ Allow all requests during Redis outage
  ─ Pro: zero availability impact for users
  ─ Con: brief window of unlimited access (temporary abuse risk)
  ─ OK for: most APIs where temporary burst is acceptable

  FAIL CLOSED (only for compliance-critical services):
  ─ Return 503 Service Unavailable during Redis outage
  ─ Pro: no abuse window, strict compliance enforced
  ─ Con: ALL users blocked — full availability collapse
  ─ OK for: financial APIs, healthcare (over-limit = fraud/compliance)

  IMPLEMENTATION — Circuit Breaker:
  ─ After 10 consecutive Redis timeouts → open circuit for 30 sec
  ─ During open circuit: fail OPEN (allow all, log error, page on-call)
  ─ After 30 sec: half-open → send one probe EVAL request
  ─ Probe success → close circuit (normal operation resumes)
  ─ Probe fails  → stay open for another 30 sec cycle

  LOCAL IN-MEMORY FALLBACK:
  ─ Each gateway maintains local token bucket per user (in-memory)
  ─ During outage: enforce local limits (not global across gateways)
  ─ Effective global limit ≈ per_instance_limit × 40 gateway instances
  ─ Rough, not exact — acceptable for brief outages of <30 sec

Senior Q&A 2 — 10 Nodes, Race to 100 RPS

SCENARIO: 10 API Gateway instances. Limit = 100 req/sec per user.
  GW1 and GW2 both receive a request for user123 at the exact same millisecond.

WEAK ANSWER: "Use distributed locks (SETNX + EXPIRE)."
  WHY IT'S WRONG: Redis is already single-threaded.
  Locks add: deadlock risk + timeout complexity + extra RTT latency.

STRONG ANSWER: Redis Lua Script makes this a non-issue.

WITHOUT LUA (race condition):           WITH LUA (atomic — correct):
  GW1: HGET key tokens → 1               GW1: EVAL lua_script → atomic:
  GW2: HGET key tokens → 1 (race!)         HMGET key tokens,last_refill
  GW1: HMSET tokens=0 → ALLOW             compute refilled tokens
  GW2: HMSET tokens=0 → ALLOW (BUG!)      HMSET tokens=refilled-1
  Result: 2 requests allowed!              EXPIRE key 3600
                                           return 1 (ALLOW)
                                         GW2: EVAL lua_script → atomic:
                                           HMGET key tokens → 0
                                           0 < 1 → return 0 (REJECT)
                                         Result: exactly 1 allowed ✓

Redis executes EVAL as a SINGLE atomic unit.
The entire read-compute-write block runs without any other command
from any client interleaving between steps.
No locks. No deadlocks. No extra round trips.
