MIME Format (RFC 2045)

  • Content-Type: multipart/mixed — root container for mixed content
  • Content-Type: text/plain + text/html — alternative parts
  • Attachments encoded as Base64 inside MIME boundary blocks
  • Message-ID: <uuid@gmail.com> — globally unique per RFC 5322
  • In-Reply-To + References — chain previous message IDs for threading
SMTP is a push protocol — sender connects to receiver's MX server. IMAP is pull — client polls or uses IDLE for push-like behaviour.

Send Path — Compose to Delivery

  1. Compose — attachment upload → S3 virus scan → draft saved (email_id UUID generated)
  2. POST /v1/emails/send — Mail Send Svc validates quota, recipients, anti-spoofing
  3. INSERT outbox — durable DB row (status=PENDING, retry_count=0)
  4. Kafka publish — email.outbound (only email_id, never full body — body stays in DB)
  5. 200 OK to user — optimistic UI; email appears in Sent immediately
  6. Orchestrator consumes — determines priority → routes to smtp.high / normal / low
  7. SMTP Worker — DNS MX lookup → TCP + TLS → EHLO → MAIL FROM → RCPT TO → DATA → QUIT
  8. On 250 OK — UPDATE outbox status=SENT; DELETE row; INSERT mailbox_items (folder=SENT)
  9. On temp failure (4xx) — exponential backoff: 1 min → 5 min → 15 min, max 10 attempts / 24 h
  10. On perm failure (5xx) — status=FAILED; bounce notification to sender; DLQ for ops review
NEVER publish email body to Kafka — Kafka default limit is 1 MB; attachments can be 25 MB. Pass only email_id; workers fetch body from DB.

Receive Path — External Sender to Inbox

  1. External SMTP (Outlook / Yahoo) does DNS MX lookup for gmail.com → gmail-smtp-in.l.google.com
  2. TCP + TLS to Gmail's inbound SMTP server (port 25)
  3. RCPT TO: <recipient@gmail.com> → check local user cache (Redis) then DB
  4. Accept DATA → full email received in memory
  5. Spam / Malware Svc (async via Kafka email.inbound):
    • IP reputation + blacklist (< 10 ms)
    • SPF / DKIM / DMARC validation (DNS, ~50 ms)
    • Bayesian content scoring (~100 ms)
    • Link phishing check + ClamAV virus scan (~200 ms)
  6. Spam score > 0.8 → folder = SPAM; virus → quarantine / reject
  7. Thread detection — check In-Reply-To / References → match existing thread (Redis cache, 7-day TTL) or create new
  8. INSERT mailbox_items — (user_id, email_id, thread_id, folder=INBOX/SPAM, is_read=false)
  9. Publish email.indexed for Elasticsearch; email.received for Notification Svc

Authentication Triad — SPF · DKIM · DMARC

SPFSending IP authorised for domainTXT v=spf1 ip4:74.125.0.0/16 ~allMark spam / reject
DKIMEmail not tampered in transitTXT default._domainkey.gmail.com (public key)Signature mismatch → reject
DMARCSPF / DKIM aligned to From: headerTXT _dmarc.gmail.comp=reject / quarantine / none

DKIM Signing Flow

  • Sender signs selected headers + body hash with private RSA key
  • Adds DKIM-Signature: v=1; a=rsa-sha256; d=gmail.com; s=default; bh=<bodyhash>; b=<sig>
  • Receiver fetches public key from DNS → verifies bh and b match
DMARC alignment: From: domain must match SPF MAIL FROM domain OR DKIM d= domain. With p=reject any mismatch drops the email — strongest anti-phishing posture.

Email Threading

How Gmail Builds Conversation View

  • Every sent email carries Message-ID: <email_id@gmail.com>
  • Replies include In-Reply-To: <parent_message_id> + References: <root> <parent>
  • On receive: check References headers against Redis cache (message_id → thread_id, TTL 7 days)
  • Cache hit (95%) → UPDATE threads SET email_ids = array_append(…), last_updated_at = now()
  • Cache miss → query Threads table; if found update, else create new thread

Threads Schema

threads (thread_id PK, subject, participant_emails text[],
         email_ids uuid[], last_updated_at, message_count)

GIN index on participant_emails for 'emails involving X' queries
Do NOT rely on subject-matching alone — subjects can collide ("Hi", "Re: Meeting"). The References header chain is the authoritative grouping signal.

Attachment Storage

Upload Flow

  1. Client: POST /v1/attachments/upload (multipart/form-data)
  2. Compose Svc streams to S3: s3://email-attachments/{user_id}/{email_id}/{filename}
  3. ClamAV virus scan — if infected → reject 400; else virus_scan_status = CLEAN
  4. Compute SHA-256 hash of file content → deduplication: if hash exists, reuse S3 URL (saves storage)
  5. Response: {attachmentId, storageUrl, size, contentType}
  6. Email send payload carries attachmentId; full body NOT re-uploaded

Access & Lifecycle

  • Download via presigned S3 URL (TTL 1 h) — server never streams bytes, client goes direct
  • S3 lifecycle policy: archive to Glacier after 1 year → 90% cost reduction for cold attachments
  • 25 MB limit enforced at upload; quota deducted from user's 15 GB

Email Deliverability

Sending Reputation Management

  • IP warm-up — new sending IP starts at low volume (100/day) and ramps over weeks; sudden spikes trigger receiver blacklisting
  • Bounce handling — hard bounce (550 User not found) → remove address immediately; soft bounce (452 Mailbox full) → retry with backoff
  • Unsubscribe compliance — CAN-SPAM / GDPR require one-click unsubscribe; bulk senders must honour within 10 days
  • Feedback loops (FBL) — ISPs like Yahoo send spam-complaint reports; auto-suppress complainers
  • Dedicated IP pools — separate IPs for transactional vs marketing; a complaint on marketing IPs doesn't poison transactional delivery

Delta Sync

Senior Q&A 1 — Preventing Tenant IP Blacklisting

Q: How do you prevent one abusive tenant from blacklisting the entire sending IP range?

Answer

  • Dedicated IP pools — segment IPs by tenant reputation tier (gold / silver / bronze). Complaints on one pool don't affect others.
  • Shared → dedicated promotion — new senders start on shared IPs; once volume and reputation are established, graduate to dedicated IPs
  • Per-tenant rate limiting — Kafka consumer checks sending_user quota before dispatching SMTP; abusive tenant throttled without blocking others
  • Complaint monitoring — FBL reports from Yahoo/Outlook feed back in near-real-time; auto-suspend tenant above 0.1% complaint rate
  • Bounce scoring — if bounce rate > 5% for a tenant, move to quarantine queue for manual review
  • DKIM per domain — each customer domain signs with its own DKIM key; receiver sees the customer's domain, not the platform's — reputation travels with the customer, not the IP

Senior Q&A 2 — 10-Year Thread with 500 Replies

Q: How does Gmail handle an email chain 10 years old with 500 replies?

Answer

  • Thread table — email_ids uuid[] stores 500 UUIDs; PostgreSQL arrays scale to thousands of elements cheaply
  • Pagination — inbox listing returns only thread_id + last_email_snippet (not all 500); on expand, fetch paginated: LIMIT 20 ORDER BY sent_at DESC OFFSET n
  • Redis cache — recent message_id → thread_id lookups cached with 7-day TTL; old threads not in cache get a DB lookup (rare, cold path)
  • Search index — Elasticsearch indexes each email individually with thread_id as a keyword filter; query by thread_id returns all matches sorted by date
  • Thread truncation display — UI shows first 3 + last 3 emails, "Show all 494 messages" expansion — only fetched on demand
  • message_count column — maintained with each INSERT so inbox list view never scans the array to get count

Senior Q&A 3 — Deduplication on Retry

Q: SMTP worker retries after a network blip — recipient may get the same email twice. How do you deduplicate?

Sender-side (outbox dedup)

  • Outbox PK (user_id, email_id) — second INSERT on retry is idempotent (upsert / ignore duplicate)
  • Kafka producer uses email_id as idempotent key; Kafka exactly-once producer prevents double-publish to same partition

Receiver-side (mailbox dedup)

  • Message-ID header is globally unique per RFC 5322 (<email_id@gmail.com>)
  • Before INSERT: SELECT 1 FROM mailbox_items WHERE user_id=? AND message_id=? — if exists, skip insert (idempotent receive)
  • Redis set dedup:{user_id}:{message_id} with TTL 48 h for fast pre-check before DB

Attachment dedup

  • SHA-256 hash of file content → if hash exists in S3 manifest, reuse URL (no re-upload)
  • Multiple emails attaching the same PDF share one S3 object — significant storage saving

Closing — Key Takeaways

Interviewer always asks: "How do you guarantee delivery?" → Outbox pattern: INSERT outbox DB first, then Kafka. Worker deletes only after 250 OK. Exponential backoff (1 m → 5 m → 15 m, max 10 / 24 h). Bounce on permanent failure. DLQ for ops.

Five Things to Nail

  1. Outbox → Kafka → SMTP workers — async, durable, at-least-once; never lose an email on crash
  2. SPF + DKIM + DMARC — DNS-based auth triad; p=reject is the gold standard
  3. SLA priority queues — HIGH <1 min (same domain / contacts), NORMAL <5 min, LOW <30 min; worker ratios 50/100/20
  4. Shard by user_id — user's entire mailbox on one shard; Elasticsearch for cross-shard full-text search
  5. Dedup via message_id — globally unique per RFC 5322; Redis pre-check + DB constraint prevents duplicate inbox entries on retry
Storage tip: body in DB, attachments in S3 (presigned URLs), search in Elasticsearch — never mix them up or your Kafka broker and SMTP workers will buckle under 25 MB payloads.
