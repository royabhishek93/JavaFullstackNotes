Seat Contention Problem

SpiderMan premiere — user1 & user2 click L12 at the same millisecond

WITHOUT LOCKING (wrong):
  user1 reads:  status='available' ✓
  user2 reads:  status='available' ✓
  user1 writes: status='booked'   ✓
  user2 writes: status='booked'   ✓  ← DOUBLE BOOKING

Locking Strategies

StrategyMechanismTrade-off
Pessimistic LockSELECT … FOR UPDATE (DB row lock)Correct but blocks DB threads — bad at 50K concurrency
Optimistic LockUPDATE … WHERE version=N AND status='available'Fast; 0 rows updated = conflict → retry
Redis SETNXAtomic SET if Not eXists · EX 600Best: 1ms, atomic, auto-expiry, no DB pressure

Production choice: Redis SETNX as fast path · DB optimistic lock as fallback when Redis unavailable

Redis Distributed Lock

Key pattern: seat:{event_id}:{seat_id}

user1: SET seat:ev123:L12 user1_bk789 NX PX 600000  →  "OK"
user2: SET seat:ev123:L12 user2_bk999 NX PX 600000  →  nil

user2 sees: "Seat L12 is temporarily held. Please choose another."

Lock Lifecycle

  • Acquire: SET key value NX PX 600000 — atomic, OK or nil
  • Heartbeat renewal: PEXPIRE every 2 min while user is on payment page
  • Release on success: DEL seat:ev123:L12 after DB commit
  • Release on failure: DEL immediately on payment failure
  • Auto-expiry: TTL fires if user abandons — seat becomes available again
  • Multi-seat atomicity: Use Redis Lua script to SETNX all seats or none
  • Redis down fallback: DB-level optimistic locking (version column)

Overbooking Prevention — 3 Layers

Layer 1 — Redis SETNX (fast path, 1 ms)

SET seat:ev123:L12 user1 NX PX 600000
→ Only ONE user acquires the lock. All 499,999 others get nil.

Layer 2 — DB Unique Constraint + Optimistic Lock (hard stop)

-- Unique index prevents two confirmed rows for same seat
CREATE UNIQUE INDEX uq_booking_seat
  ON booking_seats (event_id, seat_id)
  WHERE status = 'confirmed';

-- Optimistic lock on seat row
UPDATE seats SET status='booked', version=version+1
WHERE seat_id='L12' AND event_id='ev123'
  AND version=5 AND status='available';
-- 0 rows updated → another transaction won → 409 Conflict

Layer 3 — Payment Idempotency (crash safety)

  • Pass booking_id as idempotency key to Stripe / Razorpay
  • Server crash + retry → same charge result, no double billing
  • On restart: query payment intent status → reconcile DB state

E-Ticket Generation

QR Code Payload

QR = Base64( HMAC-SHA256(
               booking_id + ":" + event_id + ":" + seat_id,
               SECRET_KEY
             ) )

Example:
  booking_id = bk789  |  event_id = ev123  |  seat_id = L12
  QR payload = "bk789:ev123:L12:a3f7c9e2..." (HMAC appended)

Validation at Venue Gate

  • Scanner app calls: GET /v1/ticket/validate?qr={payload}
  • Server recomputes HMAC — match = valid ticket
  • Marks scanned=true to prevent QR reuse
  • Offline-verifiable: HMAC works without DB lookup if SECRET_KEY distributed to gate device

Delivery Pipeline

  • Kafka consumer: booking.confirmed → Notification Service
  • Sends PDF ticket + QR via email; SMS link as fallback

Waitlist System

Queue Design

Redis Sorted Set (score = join timestamp):
  ZADD waitlist:{event_id} {unix_ts_ms} {user_id}
  ZRANK waitlist:{event_id} {user_id}  →  position #47

User sees: "You are #47 in the waitlist for SpiderMan — PVR Juhu 6:30pm"

Seat Release Flow

  • Booking cancelled OR TTL expires → seat returns to AVAILABLE
  • Kafka event: seat.released — Waitlist Service consumes
  • ZPOPMIN waitlist:{event_id} → first user in queue
  • Push / SMS: "Seat available! You have 15 minutes to book."
  • If user doesn't reserve in 15 min → skip, notify next user

Edge Cases

  • User unreachable → skip to next after timeout
  • Multiple seats released → batch notify in FIFO order
  • User on waitlist already has confirmed booking → skip them

Flash Sale — IPL / Taylor Swift Traffic

Problem: 5 M users click "Book" simultaneously. 50 K seats. All in 1 second.

Virtual Waiting Room

User hits page → ZADD sale_queue:{event_id} {timestamp_ms} {user_id}
User gets back: "You are #247,891 in queue"

Process first N users (N = total seats):
  Positions 1 … 50,000  → allowed into reserve flow
  Positions 50,001+      → "Sorry, sold out"

Additional Controls

  • Rate limiting: 1 reserve attempt per user per event per minute
  • Bot protection: CAPTCHA on queue entry for mega-events
  • Dedicated Kafka partition per flash-sale event (flash_sale.ev123)
  • CDN: Event page fully cached at edge — zero origin load for browsing
  • Pre-warm Redis: Load seat map into seatmap:{event_id} before sale opens
  • Auto-scale app servers 30 min before scheduled sale opening

Database Schema (MySQL / PostgreSQL)

CREATE TABLE seats (
  seat_id   VARCHAR(20),
  event_id  UUID,
  row       CHAR(3),
  number    INT,
  category  ENUM('gold','silver','platinum'),
  price     DECIMAL(10,2),
  status    ENUM('available','held','booked') DEFAULT 'available',
  version   INT DEFAULT 0,          -- optimistic lock
  PRIMARY KEY (seat_id, event_id)
);

CREATE TABLE bookings (
  booking_id   UUID PRIMARY KEY,
  user_id      UUID NOT NULL,
  event_id     UUID NOT NULL,
  status       ENUM('pending','confirmed','cancelled','expired'),
  total_price  DECIMAL(10,2),
  payment_id   VARCHAR(255),
  expires_at   TIMESTAMP,            -- now + 10 min (pending)
  confirmed_at TIMESTAMP
);

-- Hard stop: no two confirmed rows for same seat at same event
CREATE UNIQUE INDEX uq_booking_seat
  ON booking_seats (event_id, seat_id) WHERE status = 'confirmed';

CREATE INDEX idx_bookings_event ON bookings(event_id, status);
CREATE INDEX idx_seats_event_status ON seats(event_id, status);

Senior Q&A #1 — What if Redis Dies Mid-Lock?

"What happens if Redis crashes while a user holds a seat lock?"

Weak answer: "Redis can't crash — we'll run a primary." ❌

Strong Answer

  • TTL auto-expires. The key had EX 600 — after crash & restart, the key is gone. Seat becomes available again within TTL window (worst case: 10 min).
  • DB-level optimistic lock takes over as fallback:
UPDATE seats SET status='booked', version=version+1
WHERE seat_id='L12' AND event_id='ev123'
  AND version=5 AND status='available';
-- 0 rows updated → conflict → 409 returned to user
  • Redis is a speed optimisation, not a correctness requirement. The DB is the source of truth — always.
  • Redis Sentinel / Redis Cluster reduces risk of total unavailability.
  • If Redis fully down → fall back to DB pessimistic lock path. Slower but correct.

Senior Q&A #2 — 500K Users Click Same Seat

"IPL Final — 500,000 users click L12 in the same second. What happens?"

Without Queue (naive)

  • 500K SETNX commands hit Redis simultaneously
  • Redis is single-threaded — queues and executes atomically
  • Exactly 1 user gets OK, the other 499,999 get nil → 409 returned
  • Correct, but 500K HTTP connections → thundering herd on app servers

With Virtual Waiting Room (production)

User enters page → ZADD sale_queue:ev123 {timestamp} {user_id}
Gets back: "You are #247,891 in queue"

Only first 50,000 (= seat count) are processed:
  → allowed into reserve flow one batch at a time
  → remaining users see "Sold out"

App servers protected · Redis not hammered by raw SETNX storm
  • Rate-limit queue entry: 1 join per user per event
  • Process 500 users/sec from queue → sustainable SETNX rate

Closing Script

"To summarise what I've designed…"

  • CAP split stated explicitly: AP for search (Elasticsearch + CDC) · CP for booking (ACID + Redis SETNX)
  • Distributed locking: Redis SETNX EX 600 — exactly one user wins any seat; auto-expiry on abandonment
  • Two-phase booking: Reserve (soft hold, Redis) → Confirm (payment + DB ACID commit)
  • Idempotency: booking_id as idempotency key to payment gateway — crash-safe, no double charges
  • Overbooking prevention: Redis fast path + DB unique constraint + optimistic version lock
  • Flash sale handling: Virtual waiting room (Redis sorted set) + rate limiting per user
  • High concurrency: Redis seat map cache, CDN for media, read replicas for browse traffic
  • Failure recovery: Redis down → DB fallback; payment crash → reconcile via idempotency key

Key sentence to say aloud: "Redis is the speed layer. The database is the source of truth. Correctness is never sacrificed for performance."
