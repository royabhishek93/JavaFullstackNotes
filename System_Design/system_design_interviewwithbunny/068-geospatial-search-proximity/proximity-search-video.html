🎬 Opening

Opening Script — The Proximity Problem

Say This to Your Interviewer

"Proximity search is the backbone of Yelp (find restaurants nearby), Uber (find drivers), and Tinder (find people). The naive approach — compute distance to every record — is O(N) and fails at scale. The real challenge: how do we index 500 million GPS coordinates so any radius query returns in under 200 ms, while handling 100 K live location updates per second?"

Three Distinct Flavours

  • Yelp / Airbnb — Static locations, rich metadata (category, rating), complex filters. Freshness: hours. Index once, query millions of times.
  • Uber / Rapido — Real-time moving objects. Location changes every 5 s. Freshness: seconds. Write-heavy (100K GPS pings/s).
  • Tinder / Bumble — Privacy-first. Show distance ("2 km away"), never exact coordinates. Freshness: minutes.
Senior signal: Clarify write vs read ratio and freshness requirement before picking a data store. The answer changes completely based on whether objects move.

❌ Anti-Pattern

Naive SQL Approach — Why It Fails

-- Tempting but WRONG: function on column kills the index
SELECT id, name,
  SQRT(POW(lat - 37.77, 2) + POW(lng + 122.41, 2)) AS dist
FROM restaurants
WHERE SQRT(POW(lat - 37.77, 2) + POW(lng + 122.41, 2)) < 0.05
ORDER BY dist LIMIT 20;
-- Result: FULL TABLE SCAN — 500M rows × trig ops = ~4 minutes

Performance Without vs With Spatial Index

RowsFull Scan (no index)Spatial IndexSpeedup
100K~50 ms<1 ms50x
10M~5 s~10 ms500x
500M>4 min~50 ms5000x
The Two-Step Fix: (1) Bounding box via spatial index — O(log N), eliminates 90% of rows. (2) Haversine exact distance only for survivors. delta = radius_km / 111. For 5 km: delta = 0.045°.
🔢 Geohash

Geohash Deep Dive — Encoding & Precision

Encoding

lat =  37.7749  → bits: 01011010...
lng = -122.419  → bits: 10011101...
  interleave    → 0110011101...

Proximity Property

  • Nearby locations share a common prefix
  • '9q8yy9mz' and '9q8yy9mt' are 1 block apart
  • Shorter prefix = larger cell (zoom out)

⚠️ Edge Case

Geohash Boundary Problem — Must Query 9 Cells

  ┌──────────────┬──────────────┬──────────────┐
  │  9q8yx       │  9q8yy       │  9q8yz       │
  │              │     ● User   │              │
  │    ●─────────┼──────────────┼──────────────┤
  │  Point B     │  Point A     │              │
  │  50 m away!  │              │              │
  ├──────────────┼──────────────┼──────────────┤
  │  9q8yw       │  9q8yt       │  9q8tu       │
  └──────────────┴──────────────┴──────────────┘

  Point A: '9q8yyzzz'   Point B: '9q8z0000'
  Different 5th char — only 50 m apart but LIKE '9q8yy%' misses B!

The Fix — Always Query 9 Cells

  • Use a geohash library: geohash.neighbors('9q8yy') → returns 8 adjacent cells
  • Query: WHERE geohash IN ('9q8yy','9q8yz','9q8yx','9q8yw','9q8yv','9q8yt','9q8ys','9q8yq','9q8yu')
  • Post-filter all candidates with Haversine to get exact circle (not just the box)
Interviewer trap: Single-cell query silently drops results near boundaries. Always state the 9-cell pattern. Larger cells (shorter hash) reduce boundary risk but increase candidate count.
🌲 QuadTree

QuadTree Deep Dive — Recursive Spatial Partitioning

  Root (whole world)
  ├── NW quadrant  [NYC, Boston, ...]
  │   ├── NW-NW   ← prune (circle doesn't intersect)
  │   ├── NW-NE   ← prune
  │   ├── NW-SW   ← recurse deeper
  │   └── NW-SE   [leaf: 87 pts] → Haversine filter
  ├── NE quadrant  ← prune
  ├── SW quadrant  ← prune
  └── SE quadrant  ← prune

  Search: O(log N + K)  K = result count
  Pruning eliminates 75%+ of tree per query

Insert / Update / Delete

OperationActionCost
InsertTraverse to leaf by coords; if >100 pts → split into 4O(log N)
Update (driver moved)Remove old + insert new (2 ops)O(log N)
DeleteMark deleted; periodic rebuildO(log N)
Use when: In-memory single server, <1M points, game engines, hot-region cache. Never use when: distributed DB, billions of points, server restart (tree lost).

🗄️ PostGIS

R-Tree / PostGIS — Exact Spatial Queries

Setup

CREATE EXTENSION postgis;

CREATE TABLE restaurants (
  id       SERIAL PRIMARY KEY,
  name     VARCHAR(255),
  location GEOGRAPHY(POINT, 4326),
  category VARCHAR(100),
  rating   DECIMAL(2,1)
);

-- GIST index = R-tree structure
-- O(log N) spatial lookup
CREATE INDEX idx_loc_gist
  ON restaurants USING GIST (location);

Radius Query (ST_DWithin)

SELECT name,
  ST_Distance(location,
    ST_GeogFromText(
     'SRID=4326;POINT(77.608 12.97)')
  ) AS dist_m
FROM restaurants
WHERE ST_DWithin(
  location,
  ST_GeogFromText(
    'SRID=4326;POINT(77.608 12.97)'),
  5000       -- 5 km in metres
)
AND category = 'Fast Food'
AND rating >= 4.0
ORDER BY dist_m LIMIT 20;
How ST_DWithin works: (1) Bounding box check via GIST R-tree — O(log N), fast. (2) Exact Vincenty distance check (±0.5 mm) only for candidates. PostGIS handles both steps automatically.
⚡ Redis GEO

Redis GEO Commands — ZSET with 52-bit Geohash Score

Core Commands

-- Add / update (upsert)
GEOADD drivers 77.5946 12.9716 "d1"
GEOADD drivers 77.6100 12.985  "d1"  # update

-- Find 10 nearest drivers within 5km
GEORADIUS drivers 77.59 12.97 5 km
  WITHDIST ASC COUNT 10
-- [("d1","0.5km"), ("d2","1.2km")]

-- Distance between two members
GEODIST drivers "d1" "d2" km

-- Delete / TTL
ZREM drivers "d1"
EXPIRE drivers:online 3600

Internal Mechanism

  • Data stored as ZSET — score = 52-bit geohash integer
  • GEORADIUS: encode center → geohash range → ZRANGEBYLEX O(log N) → Haversine filter
  • No separate data structure — geospatial is a superset of sorted set

Location Update Pipeline — 100K GPS Pings/s

  DRIVER APP  (GPS ping every 5 s)
    |  POST /location {driver_id, lat, lng, ts}
    v

    |
    v
  LOCATION SERVICE
    |── GEOADD drivers:{region} lng lat driver_id  → Redis (sync, <1ms)
    |── SET driver:{id}:meta {status,ts} TTL=30s    → Redis (mark online)
    |── Publish {driver_id,lat,lng,ts}              → Kafka topic: loc.updates

Why Kafka in the middle? Decouples fast Redis writes from slow DB writes. Redis absorbs 100K/s; DB writer batches 6M writes/min → 1K batch inserts/min. Prevents DB overload.
📚 Read Path

Read Path Optimization — Three-Tier Cache

  • Tier 1 — Redis GEO: Top 1000 active/popular locations per city. TTL = 10 min. Serves 80% of queries in <5 ms. GEORADIUS for real-time drivers.
  • Tier 2 — Elasticsearch: 100M+ docs. Complex filters (category + rating + text). ~50 ms. Handles cache misses with rich filtering.
  • Tier 3 — PostGIS: Source of truth. All locations + full metadata. ~100 ms. ACID, complex shapes. Handles rare misses.

Cache warming: Background job analyses query logs, identifies top 100 geo-cells per city, pre-populates Redis before peak hours (7 PM).
🔥 Hotspot

Hotspot Handling — Manhattan / Mumbai Dense Cells

The Problem

  • Geohash precision 6 = ~1.2 km cells. Manhattan has 5000+ restaurants per cell.
  • A single GEORADIUS on a dense Redis key returns 5000 candidates → excessive Haversine work.
  • QuadTree leaf nodes overflow (capacity = 100) → O(N) splits → tree unbalanced.

Solutions

  • Dynamic cell splitting (QuadTree): When a leaf exceeds threshold, split into 4 children. Redistribute points. Automatically adapts to density.
  • Longer geohash in dense areas: Switch from precision 5 to precision 7 in NYC/Mumbai. Smaller cells, fewer candidates per query.
  • Result LIMIT: Always LIMIT 20 or COUNT 20. User sees first page only; computing all 5000 matches is wasted work.
  • Rate limiting per geohash cell: Throttle writes to Redis keys for hot cells. Batch updates every 1 s instead of every ping.
  • Separate Redis instances per city cluster: NYC_redis, MUMBAI_redis — isolate hot regions.

🗺️ Sharding

Sharding by Geohash Prefix — Geo-Locality

  Strategy 1 — Geographic Regions
    US-West DB | US-East DB | EU DB | Asia DB
    + Simple routing, isolated failures
    - Unbalanced (NYC >> Montana), cross-region queries

  Strategy 2 — Geohash Prefix Sharding
    Shard 0: geohash starts with '9','b'
    Shard 1: geohash starts with 'c','d'
    ...16 shards → 1024 prefixes
    + Even distribution
    - Radius query may span 2 shards at boundary

  Strategy 3 — Hybrid (RECOMMENDED)
    Region first → geohash prefix within region
    US-East: shard by '9q','9r' vs '9w','9x'

Query Routing

  • Small radius (<10 km): Hits 1–2 shards — no scatter-gather needed
  • Large radius (>50 km): Fan out to 3–5 shards, merge sorted by distance
  • Buffer zones: 10 km overlap between shard boundaries — eliminates cross-shard edge cases
Geo-locality benefit: NYC queries hit only US-East shard. Per-shard dataset shrinks 5–10×. Latency drops from 500 ms (full scan) to 100 ms (regional shard).

🧑‍💻 Senior Q&A

Q: User at Geohash Boundary — Misses Restaurants 100 m Away?

Question

"A user is at the edge of geohash cell '9q8yy'. A restaurant 80 m away sits in cell '9q8yx'. Your query only searches LIKE '9q8yy%'. The user never sees it. How do you fix this?"

Model Answer

  • Root cause: Geohash cells are squares. Points near a cell boundary can be geographically close but hash to entirely different prefixes.
  • Fix — 9-cell query: Always fetch the center cell plus its 8 neighbours using a geohash library. geohash.neighbors('9q8yy') returns ['9q8yz','9q8yx','9q8yw','9q8yv','9q8yt','9q8ys','9q8yq','9q8yu'].
  • Post-filter: Haversine-filter all candidates to exact circle. The 9 cells form a square box; the circle query eliminates corners.
  • Precision choice: Use a cell size slightly larger than the search radius. For 500 m search, use precision 6 (±610 m). This guarantees the entire circle fits within the 9-cell block.
  • Alternative: PostGIS ST_DWithin + GIST index handles this automatically with no 9-cell logic needed.
🧑‍💻 Senior Q&A

Q: Scale to 500M Driver Location Updates per Hour?

Question

"500 million driver GPS pings arrive per hour — roughly 140K/s at peak. Walk me through your write path."

Model Answer

  • Throttle at source: App sends GPS every 5 s only if movement > 50 m. Reduces writes by 60% in traffic jams.
  • Kafka ingestion: 140K msg/s → 14 partitions × 10K/s. Partition by driver_id for ordering. Kafka handles 1M msg/s easily with proper sizing.
  • Redis writes: GEOADD is O(log N). 140K GEOADD/s across 10 regional Redis instances = 14K/s per instance — well within Redis capacity (~500K ops/s).
  • DB writes: Batch Kafka consumer writes every 60 s → 8.4M rows/batch insert → PostgreSQL COPY UNLOGGED or time-series DB (TimescaleDB) handles 100K rows/s.
  • Elasticsearch: Bulk index every 30 s. 4.2M docs/batch at 100K docs/s ingestion rate — within ES limits.
Key: Redis absorbs the real-time spike. DB write is batched and decoupled via Kafka. The two rates are completely independent.
🧑‍💻 Senior Q&A

Q: Design Privacy-Preserving Proximity (Tinder — Distance, Not Location)

Question

"Tinder shows '3 km away' but must never reveal exact GPS to another user. Design the proximity system."

Model Answer — Fuzzy Geohash Approach

  • Store each user at geohash precision 4 (±20 km cell centroid) in Redis — not exact coords.
  • On search: server computes Haversine between requester's precise location and target's stored cell centroid → round to nearest 1 km bucket → return "2 km away".
  • Location fuzzing: Add random Gaussian noise (±200 m) before storing, re-randomise every 15 min. Prevents triangulation attacks.
  • Never in API response: Strip lat/lng from all API payloads. Return only pre-computed distance string.
  • Opt-out: Allow users to disable proximity entirely — store flag, return "Nearby" string only.
Anti-trilateration: If an attacker queries from 3 known positions and intersects circles, they can pinpoint you. Noise + rounding + TTL rotation prevents this. Apple/Google also recommend fuzzing for apps using CoreLocation.
