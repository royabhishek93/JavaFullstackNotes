Opening Script — Framing the Problem

Say This to Your Interviewer

"The fundamental challenge here is correctness under failure. In distributed systems, the rule is: anything that can fail, will fail. For a payment system that means: money must never be created from nothing, lost, or moved twice. Every single design decision I make will be driven by the question: what happens when this component fails mid-operation?"

Why This System Is Unique

  • Not a CRUD app — it is a distributed state machine enforcing exactly-once execution of money movement
  • External parties — banks, card networks you do not fully control or transact with atomically
  • Hardest problems — NOT performance (100 TPS is trivial for MySQL); they are correctness under failure
  • Partial writes — bank debits the customer, your DB write fails; now what?
  • Network timeouts — bank processed the payment, you never got the response
  • Double charges — client retries after timeout; ensure idempotency at every layer
Senior signal: Open with failure modes, not happy-path features. Interviewers at staff/principal level are testing whether you instinctively think about correctness first.

Idempotency Key Design — Preventing Double Charges

Most Important Correctness Guarantee: A client-generated UUID included in every API call. The server uses this to detect and suppress duplicate requests — no re-charge, no matter how many retries.

How It Works

  1. Client generates UUID v4 per payment attempt
  2. Included in HTTP header: Idempotency-Key: <UUID>
  3. Server checks Redis: GET idempotencyKey
  4. HIT → return cached response, skip all processing
  5. MISS → process payment, store result in Redis (TTL 24h)
  6. UNIQUE constraint on DB column as second safety net

Why Redis (not MySQL)?

  • O(1) lookup, sub-millisecond latency
  • TTL handles automatic expiry (24 hours)
  • ~150 MB for 1M payments/day — trivial footprint
  • DB query on every request = 5-10ms overhead + hot read table

API Contract

POST /api/v1/payments
Idempotency-Key: user_123_txn_abc789
{
  "fromAccountId": "acc_alice_001",
  "toAccountId":   "acc_bob_002",
  "amount":        50000,
  "currency":      "INR"
}

// First call → 202 Accepted
{ "paymentId": "pay_9f2a", "status": "INITIATED" }

// Retry with SAME key → 409 Conflict
// Returns original response (cached from Redis)
{ "paymentId": "pay_9f2a", "status": "SUCCESS" }
Duplicate key in DB: Even if Redis misses (cache eviction), the UNIQUE constraint on idempotency_key column prevents double-insert at DB layer.

Saga Pattern for Distributed Transactions

Why NOT 2PC: External bank APIs (SWIFT, NEFT, Visa) don't support a PREPARE phase. They either execute or they don't. 2PC holds locks indefinitely if a participant is unavailable. Use Saga + compensating transactions instead.

Saga Steps — Happy Path

  1. Payment Service: INSERT payment (INITIATED) + outbox event — local ACID TX
  2. Outbox Relay: publish event to Kafka
  3. Payment Processor: UPDATE → PROCESSING
  4. Call external bank API (async, non-blocking)
  5. On SUCCESS: UPDATE → SUCCESS + INSERT ledger entries — local ACID TX

Compensating Transactions — Failure Path

  1. Bank call fails: UPDATE payment → FAILED
  2. If funds were already moved: issue reverse payment (compensating TX)
  3. INSERT new ledger entries: CREDIT source, DEBIT destination (undo)
  4. Notify user of failure
  5. Daily reconciliation as final safety net

Cross-Shard Saga (At Scale)

Shard A (source account):
  Step 1: DEBIT source — local ACID ✓

Shard B (destination account):
  Step 2: CREDIT dest — local ACID ✓

  If Step 2 FAILS:
    Compensating TX on Shard A:
    RE-CREDIT source account
    Mark payment FAILED

Double-Entry Ledger Accounting

Core Principle: Every financial event records both source (DEBIT) and destination (CREDIT). Sum of all entries = 0 always. Ledger is append-only — never UPDATE a ledger row.

Example: Rs.500 from Alice → Bob

entry_idpayment_idaccountamounttype
1001pay_abcacc_alice50000DEBIT
1002pay_abcacc_bob50000CREDIT

DEBIT 50000 + CREDIT (-50000) = 0

Why Append-Only?

  • Immutable audit trail — legal and regulatory requirement
  • To correct an error: add a new reversing entry
  • Original entry stays forever; auditors see full history
  • Balance = SUM of all entries for an account

Balance Calculation

-- Current balance (source of truth)
SELECT SUM(
  CASE entry_type
    WHEN 'CREDIT' THEN  amount
    WHEN 'DEBIT'  THEN -amount
  END
) AS balance
FROM ledger_entries
WHERE account_id = :accountId;

-- accounts.balance is a materialized view
-- (maintained for fast reads)
-- If accounts.balance diverges from ledger SUM
-- → ledger wins, reconstruct accounts.balance
Never store money as FLOAT. 0.1 + 0.2 = 0.30000000000000004 in IEEE 754. Always use BIGINT in smallest unit: Rs.10.50 → 1050 paise.

Fraud Detection — Velocity Checks + ML Scoring

Two-Layer Architecture

Layer 1: Synchronous Pre-checks (<5ms)

  • Velocity check: >5 payments in 1 minute from same device?
  • Blacklist check: account/IP on fraud blacklist?
  • Amount threshold: unusually large amount for user?
  • Geographic anomaly: payment from new country?
  • Implemented in Redis with sliding window counters
  • Blocks obvious fraud before any DB write

Layer 2: Async ML Scoring (200–500ms)

  • Payment accepted (202), fraud check runs in parallel
  • ML model scores risk 0.0–1.0
  • Score > 0.8 → payment set to FRAUD_BLOCKED
  • Push notification to user, account review triggered
  • Score < 0.3 → proceed automatically

Velocity Check in Redis

-- Sliding window: 5 payments / 60 sec
-- Key: velocity:{accountId}:{minute_bucket}

INCR velocity:acc_alice:20240101_1030
EXPIRE velocity:acc_alice:20240101_1030 60

-- If count > 5 → reject synchronously

-- ML Feature Vector (sent to fraud service):
{
  "accountAge": 730,      // days
  "avgTxnAmount": 1200,   // paise avg
  "txnCount24h": 3,
  "newDevice": false,
  "countryMismatch": false,
  "amountZScore": 1.2     // stddevs from mean
}
Trade-off: Async fraud check means a small window where a fraudulent payment may start processing before being blocked. Mitigated by the synchronous pre-checks catching 95%+ of fraud before the ML model runs.

Reconciliation Service — The Final Safety Net

Purpose: Even with idempotency, outbox pattern, and saga, bugs can slip through. Daily reconciliation compares our internal ledger against bank statements to catch every discrepancy.

Reconciliation Flow (Nightly Batch)

  1. Download bank statement CSV/API for T-1 day
  2. For each bank transaction: find matching ledger entry by bank_reference_id
  3. Amounts must match exactly (BIGINT comparison)
  4. Every bank txn must have a corresponding SUCCESS ledger entry
  5. Every SUCCESS ledger entry must exist in bank statement
  6. Mismatches categorized: missing, extra, amount mismatch
  7. Alert ops team, freeze account pending investigation
NEVER auto-correct mismatches. A balance discrepancy means something fundamentally wrong happened — a bug, security incident, or bank error. Always require human review.

Settlement Windows

  • Card payments: T+1 or T+2 settlement
  • UPI/NEFT (India): real-time or T+0
  • SWIFT international: T+2 to T+5
  • Saga compensating window: T+1 day max

Retry — Exponential Backoff + Circuit Breaker

Exponential Backoff Strategy

// Bank API call with exponential backoff
// NEVER retry with a new paymentId — always
// same payment_id (bank idempotency key)

attempt 1:  wait 0s   → call bank
attempt 2:  wait 1s   → call bank
attempt 3:  wait 2s   → call bank
attempt 4:  wait 4s   → call bank
attempt 5:  wait 8s   → call bank
max:        wait 30s  → PENDING, alert ops

// Formula: min(2^attempt * 1000ms, 30000ms)
// + jitter: random(0, 1000ms) to avoid
//   thundering herd

// Total backoff: ~63 seconds before giving up
// On final timeout: payment → PENDING_CONFIRMATION
// Schedule status-poll background job

Circuit Breaker Pattern

  CLOSED (normal)
    ├─ Requests flow to bank
    ├─ Track failure rate
    └─ >50% failures in 10s?
              │ OPEN
              ▼
  OPEN (tripped)
    ├─ Requests fail fast (no bank call)
    ├─ Return 503 immediately
    └─ After 30s cooldown?
              │ HALF-OPEN
              ▼
  HALF-OPEN (probing)
    ├─ Allow 1 test request
    ├─ Success → CLOSED
    └─ Failure → OPEN again
Why Circuit Breaker for payments: If HDFC bank API is down, returning fast failures prevents thread exhaustion (no 3000 threads each waiting 30s for a bank timeout). Payments in flight are marked PENDING and retried when circuit closes.
🔒 Compliance

PCI-DSS Compliance Requirements

Golden Rule: Your application should NEVER see or store raw card numbers (PAN) or CVV. Use client-side tokenization — card data goes directly to the card network, never through your servers.

Tokenization Flow

  1. Payment form uses Stripe.js-like SDK embedded in client
  2. User enters card details — SDK intercepts, sends directly to card network
  3. Card network returns a single-use token (e.g., tok_abc123)
  4. Your API receives ONLY the token — never the raw card number
  5. Store only: token, last 4 digits, card brand, expiry month/year
  6. For recurring: card network issues permanent network token
  7. Token is merchant-scoped — useless to an attacker
PCI-DSS scope reduction: By never touching raw card data, you dramatically reduce compliance scope. You still need PCI Level 1 for the processing environment, but card storage is completely out of scope.

Database Schema — Key Tables

-- Store money as BIGINT (paise/cents). NEVER FLOAT.
CREATE TABLE payments (
  payment_id       VARCHAR(36) PRIMARY KEY,
  idempotency_key  VARCHAR(64) UNIQUE NOT NULL,
  amount           BIGINT      NOT NULL,  -- paise
  currency         CHAR(3)     NOT NULL,  -- ISO 4217
  from_account_id  BIGINT      NOT NULL,
  to_account_id    BIGINT      NOT NULL,
  status           ENUM('INITIATED','PROCESSING',
                        'AUTHORIZED','CAPTURED',
                        'SETTLED','FAILED',
                        'REFUNDED','PENDING') NOT NULL,
  bank_reference_id VARCHAR(100),
  created_at       TIMESTAMP DEFAULT NOW(),
  updated_at       TIMESTAMP DEFAULT NOW()
                   ON UPDATE NOW()
);

CREATE TABLE accounts (
  account_id  BIGINT AUTO_INCREMENT PRIMARY KEY,
  user_id     BIGINT NOT NULL,
  balance     BIGINT NOT NULL DEFAULT 0,
  currency    CHAR(3) NOT NULL,
  version     INT    NOT NULL DEFAULT 0, -- optimistic lock
  status      ENUM('ACTIVE','FROZEN','CLOSED') NOT NULL,
  created_at  TIMESTAMP DEFAULT NOW()
);
-- Append-only. NEVER UPDATE a ledger row.
CREATE TABLE ledger_entries (
  entry_id        BIGINT AUTO_INCREMENT PRIMARY KEY,
  payment_id      VARCHAR(36) NOT NULL,
  account_id      BIGINT      NOT NULL,
  amount          BIGINT      NOT NULL,
  entry_type      ENUM('DEBIT','CREDIT') NOT NULL,
  running_balance BIGINT,  -- snapshot after entry
  created_at      TIMESTAMP DEFAULT NOW()
);

CREATE TABLE outbox_events (
  event_id    BIGINT AUTO_INCREMENT PRIMARY KEY,
  payment_id  VARCHAR(36) NOT NULL,
  event_type  VARCHAR(50) NOT NULL,
  payload     JSON,
  published   BOOLEAN NOT NULL DEFAULT false,
  created_at  TIMESTAMP DEFAULT NOW()
);

-- CRITICAL: Optimistic lock deduction query
UPDATE accounts
  SET balance = balance - :amount,
      version = version + 1
WHERE account_id = :id
  AND version    = :expectedVersion
  AND balance   >= :amount
  AND status     = 'ACTIVE';
-- rows_affected = 0 → conflict → retry or fail
📈 Scaling

Scaling — Stripe at 1M Transactions / Minute

Reality check: At 100 TPS (our target), a single MySQL primary is fine. Stripe processes ~17K TPS globally. The bottlenecks are not what you expect.

Bottleneck 1: MySQL Balance Updates

  • Problem: 10K+ TPS → single primary is a bottleneck
  • Solution: Shard by account_id
  • Same-shard payments: local ACID transaction
  • Cross-shard payments: Saga pattern
  • Shard A debit → Shard B credit → compensate on failure

Bottleneck 2: Bank API I/O

  • Problem: 100-3000ms bank calls block threads
  • Solution: Non-blocking async HTTP (Java: WebClient/Netty)
  • 10 threads handle 1000+ concurrent bank calls
  • Timeout: 30s → mark PENDING → status-poll retry

Bottleneck 3: Status Query Reads

  • Problem: 1M users polling status every 2s = 500K reads/s
  • Solution: Cache status in Redis on every state change
  • Better: WebSockets / SSE to push status update

🎯 Interview Prep

Senior Trap Q&A 1 — Bank API Timeout

Q: Bank API times out after 30s. Payment is in PROCESSING. Customer is staring at a spinner. What do you do?
A:
  1. Mark payment status as PENDING_CONFIRMATION — do not keep client waiting
  2. Return current status to client immediately (202/200 with PENDING status)
  3. Schedule background job to poll bank status API using our merchant_reference_id (= payment_id)
  4. Use exponential backoff: 1s, 2s, 4s, 8s, 16s, 30s, then alert ops after 24h
  5. Bank status returns COMPLETED → update to SUCCESS, insert ledger entries, push notification to user
  6. Bank status returns FAILED → update to FAILED, verify no balance deduction, notify user
Critical: NEVER retry the original payment initiation with the same payment_id as a NEW request — that is how you double-charge. Only use the status query endpoint (GET /charge/{paymentId}) with the idempotent bank reference. If bank status API also times out repeatedly after 24h → escalate to manual ops review.
Q: DB write of SUCCESS status fails AFTER the bank confirmed and debited the customer. What now?
A: This is the "lost update" scenario — most dangerous failure case.
  • Payment Processor reads Kafka at-least-once → retries processing this payment
  • Before new bank call: call bank status API with original payment_id
  • Bank returns COMPLETED with its reference ID → update DB to SUCCESS with proof
  • If DB keeps failing (outage): payment stays PROCESSING in DB, but customer was debited
  • Nightly reconciliation catches it: bank statement entry has no SUCCESS ledger entry → alert ops

Senior Trap Q&A 2 — Concurrent Payments

Q: User has Rs.100. Submits two payments of Rs.80 simultaneously from two devices. How does your system guarantee at most one succeeds?
A: Optimistic locking on the accounts table. 
-- Both requests read: account version=5, balance=10000 paise
-- Both attempt deduction:

UPDATE accounts
  SET balance = 2000, version = 6
WHERE account_id = X
  AND version = 5      -- optimistic check
  AND balance >= 8000;

-- Request A executes first: rows_affected = 1 ✓
--   → version is now 6, balance = 2000

-- Request B executes next: version=5 no longer matches
--   rows_affected = 0 → CONFLICT
--   → Re-read balance: 2000 paise
--   → 2000 < 8000 → INSUFFICIENT_FUNDS ✗
Important edge case: The INITIATED step does an early fast-fail balance check, but the definitive deduction with optimistic lock happens in the SUCCESS commit step. Do NOT hold the lock from INITIATED through the bank call (100-3000ms). The optimistic lock is only taken at the final ledger insert — no locks held during I/O.

Senior Trap Q&A 3 — PCI-DSS + Refund Design

Q: PCI-DSS requires cardholder data is never stored in your systems unless encrypted. How does your architecture handle this?
  1. Payment form uses client-side SDK (Stripe.js) — card data sent directly to card network's secure tokenization endpoint
  2. SDK returns a single-use token. Your API receives ONLY the token — you NEVER see the raw PAN or CVV
  3. Store: token, last 4 digits (display only), card brand, expiry month/year
  4. For recurring charges: card network issues permanent network token
  5. Token is merchant-scoped — useless to an attacker outside your merchant account
  6. Result: your application servers are out of PCI-DSS card storage scope
Q: How do you handle refunds for a payment that has already been settled?
A: A refund is a NEW payment record — never modify the original.
  • Create new payment with type=REFUND, reference to original payment_id
  • Refund goes through full pipeline: idempotency check, outbox, bank API (reverse transfer / card refund)
  • Insert two new ledger entries: CREDIT source account (customer gets money back), DEBIT destination (merchant)
  • Original payment + original ledger entries remain immutable forever
  • Partial refunds: same approach — refund payment for partial amount
  • Audit trail: compliance team sees full history — original, refund, any re-refunds

What NOT to Say — Instant Fails

StatementWhy It's Wrong
"I'll use MongoDB for the payments DB" Multi-document transactions weaker than MySQL ACID. Two concurrent balance reads can both see sufficient funds → double-spend. Financial data needs ACID. Say MySQL or PostgreSQL.
"Store payment amount as FLOAT/DOUBLE" 0.1 + 0.2 = 0.30000000000000004 in IEEE 754. Rounding errors accumulate → ledger never balances. Always BIGINT in smallest denomination (paise, cents).
"Call bank API while holding DB transaction open" Bank takes 100-3000ms. MySQL holds row locks for 3 seconds → blocks all payments on same accounts → deadlock cascade at scale. Commit DB first, then call bank async.
"Use 2PC across our system and the external bank" External banks don't implement PREPARE phase. 2PC holds locks until coordinator decides — bank unavailability means infinite lock hold. Use Saga + compensating transactions.
"UPDATE the ledger entry to correct it" Legally immutable. Financial regulations (RBI, PCI-DSS) require immutable audit trail. Create a new reversing CREDIT/DEBIT entry. Original entry stays forever.
"Use SELECT FOR UPDATE on accounts" Lock held during entire bank API call (up to 3 seconds). Two concurrent payments serialize completely. Timeouts → lock cascade. Use optimistic locking (version column) instead.
"Auto-correct reconciliation mismatches" A mismatch means something fundamentally wrong — bug, security incident, or bank error. Auto-correcting masks the root cause. Alert ops, freeze account, require human review.

Summary — The Five Pillars

Closing Script — Say This to Wrap Up

"To summarize: a production-grade payment system rests on five correctness pillars: (1) Idempotency Layer — Redis check prevents any duplicate charge regardless of retries. (2) ACID Database — MySQL guarantees payment and ledger entries commit atomically or not at all. (3) Double-Entry Bookkeeping — every payment creates a DEBIT and CREDIT; the ledger is append-only and immutable. (4) Outbox Pattern — event and payment written in same MySQL transaction; relay publishes to Kafka; no silent event loss. (5) Saga + Reconciliation — Saga handles cross-bank failures with compensating transactions; daily reconciliation is the final safety net that catches everything else."

1. Idempotency
Redis + DB UNIQUE constraint. Client UUID per attempt. TTL 24h.
2. ACID (MySQL)
No MongoDB. No Cassandra. ACID is non-negotiable for money.
3. Double-Entry
Append-only ledger. 1 DEBIT + 1 CREDIT per payment. Sum = 0.
4. Outbox + Kafka
Same DB TX for payment + event. Relay publishes. At-least-once.
5. Saga + Reconcile
No 2PC. Compensating TXs on failure. Daily ledger vs bank audit.
Key Design Insight
Volume is NOT the challenge. Correctness under failure is everything.
