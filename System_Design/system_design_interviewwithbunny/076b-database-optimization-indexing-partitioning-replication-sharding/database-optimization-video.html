📋 Why It Matters

The Cost of Slow Queries

Every growing application hits a wall — a simple database that works fine at 100 req/s starts showing cracks at 1,000 and crumbles at 2,500. Performance is a non-functional requirement that must be designed in, not bolted on.

Business Impact

  • Slow login = user drops off immediately
  • Delayed writes = lost registrations & revenue
  • Cascading timeouts = entire service down
  • Customer complaints spike → brand damage

Typical Growth Pattern

  • 100 req/s — default DB, zero tuning
  • 1,000 req/s — small lag appears
  • 1,500 req/s — users complain
  • 2,500 req/s — system needs re-arch
The 6-step optimization ladder (in order): Query Tuning → Indexing → Vertical Scaling → Read Replication → Partitioning → Sharding. Never jump straight to sharding — exhaust simpler options first.

🗂 Indexing

B-Tree Index Internals

Indexing transforms a full-table scan — O(n) linear search — into a B-Tree traversal at O(log n). Think of it like the index at the back of a book: you look up a keyword to find the page, not scan every page.

B-Tree on users.email (1,000 rows shown) Root ────────────────────────────────────── │ [1 .. 1000] │ └──────────────────────────────────────────┘ ┌──────────────┴──────────────┐ [1..500] [501..1000] ┌──────┴──────┐ ┌──────┴──────┐ [1..250] [251..500] [501..750] [751..1000] │ │ │ │ leaf pages leaf pages leaf pages leaf pages (row ptrs) (row ptrs) (row ptrs) (row ptrs) Looking up user_id=376: Root → [1..500] → [251..500] → leaf → row 3 comparisons vs 1,000 linear scans ✓

What Indexing Improves

  • Read latency: O(n) → O(log n)
  • Range scans via sorted leaf pages
  • JOIN performance on FK columns
  • ORDER BY / GROUP BY if index covers sort key

Write Overhead Added

  • Every INSERT / UPDATE / DELETE must rebalance the tree
  • More indexes = higher write latency
  • Extra disk I/O and memory for index pages
  • Bulk loads slow significantly with many indexes
🗂 Indexing

Index Types

Composite Index

Index on multiple columns — column order matters. Follows left-prefix rule: an index on (a, b, c) serves queries on a, (a,b), (a,b,c) but NOT on (b) alone.

CREATE INDEX idx_user_country_age ON users(country, age); -- Uses index: WHERE country='IN' AND age > 25 -- Skips index: WHERE age > 25 -- no left prefix

Covering Index

Index contains all columns the query needs — DB never touches the main table. Eliminates the "heap fetch" step entirely.

CREATE INDEX idx_cover ON users(email) INCLUDE (name, avatar); -- Query answered from index only: SELECT name, avatar FROM users WHERE email='x@y.com'

Partial Index

Index only a subset of rows matching a predicate. Smaller, faster, avoids indexing NULL or inactive data.

CREATE INDEX idx_active_users ON users(email) WHERE status = 'active'; -- 90% of rows are inactive → tiny index

Hash Index

O(1) exact-match lookup but cannot do range scans or ORDER BY. Ideal for equality filters on UUID / token columns.

CREATE INDEX idx_token ON sessions USING hash(token); -- Perfect: WHERE token = $1 -- Useless: WHERE token > $1
🗂 Indexing

When NOT to Index

Indexes are not free. Over-indexing is a common anti-pattern that quietly degrades write-heavy services and wastes storage.

Rule of thumb: Do NOT index a column if the query touches more than ~10–15% of table rows. A full scan can be faster than random index lookups in that case (index selectivity too low).
ScenarioWhy indexing hurts
Low-cardinality columns (e.g., status ENUM with 3 values)Index selectivity near zero — DB skips it and scans anyway
Write-heavy tables (event logs, audit trails)Every insert rebuilds index pages; throughput tanks
Small tables (under a few thousand rows)Full scan costs less than B-Tree traversal + heap fetch
Rarely queried columnsIndex maintains itself for zero payoff
Too many indexes on one tableEach UPDATE re-indexes all N indexes; latency multiplies
Columns with frequent bulk updatesFragmentation forces periodic REINDEX/VACUUM
Interview answer: "I monitor pg_stat_user_indexes (Postgres) or sys.dm_db_index_usage_stats (SQL Server) for zero-scan indexes and drop unused ones as part of routine maintenance."

Good Candidates

  • Primary keys (auto-indexed)
  • Foreign keys used in JOINs
  • High-cardinality WHERE columns (email, UUID)
  • Columns in ORDER BY + LIMIT queries

Poor Candidates

  • Boolean flags (true/false only)
  • Status columns (pending/active/done)
  • Gender, country on small tables
  • Columns never in WHERE / JOIN / ORDER BY
🗂 Indexing

Reading EXPLAIN Query Plans

EXPLAIN ANALYZE shows the execution plan the query planner chose and the actual runtime stats. Knowing how to read it is a senior-engineer skill tested in interviews.

-- Postgres: run this to see actual stats EXPLAIN ANALYZE SELECT name, email FROM users WHERE email = 'a@b.com'; -- BAD output (no index): Seq Scan on users (cost=0.00..18450.00 rows=1 width=36) (actual time=23.4..89.2 ms rows=1) Filter: (email = 'a@b.com') Rows Removed by Filter: 999999 -- GOOD output (with index): Index Scan using idx_users_email on users (cost=0.43..8.45 rows=1 width=36) (actual time=0.08..0.09 ms rows=1) Index Cond: (email = 'a@b.com')

Red Flags in EXPLAIN

  • Seq Scan on large tables — missing index
  • Hash Join with high cost — missing FK index
  • Rows Removed by Filter very high — low selectivity
  • Sort node — missing ORDER BY index
  • Estimated rows ≠ actual rows — stale statistics, run ANALYZE

Green Flags in EXPLAIN

  • Index Scan / Index Only Scan — index used
  • Low actual time (<1 ms for point lookups)
  • Rows estimate close to actual — fresh statistics
  • Nested Loop on small inner sets — optimal JOIN
  • cost estimates low and proportional to result set
Run ANALYZE <table> when query planner makes poor choices — stale statistics cause wrong plan selection.
✂️ Partitioning

Horizontal vs Vertical Partitioning

Partitioning logically splits a table into smaller chunks so queries scan less data. Unlike replication (which copies everything), partitioning distributes data — each record lives in exactly one partition.

Horizontal Partitioning (Row-based)

Split rows across partitions using a partition key. The schema stays the same in each partition — only the data differs.

users table (10M rows total) Partition 1: users_a_e (rows A–E emails) Partition 2: users_f_m (rows F–M emails) Partition 3: users_n_z (rows N–Z emails) -- Query only scans one partition: WHERE email LIKE 'g%' → Partition 2 only

Vertical Partitioning (Column-based)

Split columns into separate tables. Hot columns (frequently read) stay in the main table; cold/large columns move to a separate table joined on PK.

-- Before: one fat table users(id, email, name, avatar_blob, bio_text, preferences_json) -- After: hot + cold split users_core(id, email, name) -- hot users_profile(user_id, avatar_blob, bio_text, preferences_json) -- cold
In system design interviews, "partitioning" almost always means horizontal partitioning. Vertical partitioning is more of a schema normalization technique.
Key difference from replication: partitioning reduces data per node — replication copies the same data to all replicas. Partitioning improves search cost; replication improves read throughput and availability.
✂️ Partitioning

Partition Strategies

Range Partitioning

Rows go into partitions based on a value falling within a contiguous range. Natural for time-series and date-based data.

PARTITION BY RANGE(created_at): orders_2023: Jan–Dec 2023 orders_2024: Jan–Dec 2024 orders_2025: Jan–Dec 2025 -- Range scan on current month only: WHERE created_at >= '2025-01-01' → touches orders_2025 only ✓

Watch out: Hot partition problem — all writes go to the current partition.

Hash Partitioning

Apply a hash function to the partition key and assign to a bucket. Distributes data evenly — good for preventing hotspots.

PARTITION BY HASH(user_id) PARTITIONS 8; hash(user_id) % 8 = 0 → shard_0 hash(user_id) % 8 = 1 → shard_1 ... hash(user_id) % 8 = 7 → shard_7 -- Lookup goes to exactly one partition: WHERE user_id = 123456 → shard_2 only

List Partitioning

Rows are assigned to a partition based on an explicit list of values. Best for geographic or categorical data with a known, finite set.

PARTITION BY LIST(country): partition_apac: IN ('IN', 'JP', 'SG', 'AU') partition_emea: IN ('GB', 'DE', 'FR', 'AE') partition_amer: IN ('US', 'CA', 'BR', 'MX')
Choosing the wrong partition key degrades performance instead of improving it. Always ask: "What column appears in the WHERE clause of the most-frequent queries?"
✂️ Partitioning

Partition Pruning

Partition pruning is the query planner's ability to skip irrelevant partitions entirely and only scan partitions that can contain matching rows. This is what makes partitioning fast.

Table: orders partitioned by RANGE(year) Partitions: p_2022, p_2023, p_2024, p_2025 SELECT * FROM orders WHERE year = 2024; -- Planner PRUNES: p_2022, p_2023, p_2025 -- Planner SCANS: p_2024 only (25% of data) -- Bad query — prevents pruning: SELECT * FROM orders WHERE YEAR(created_at)=2024 -- Function wrapping breaks partition pruning! -- All partitions scanned → no benefit

What Enables Pruning

  • WHERE clause directly compares the partition key
  • Literal values or bind parameters (not functions)
  • Range predicates on range-partitioned tables
  • Equality predicates on hash/list partitions

What Breaks Pruning

  • Wrapping partition key in a function: YEAR(date), LOWER(email)
  • Implicit type cast on the partition key
  • Using a non-partition column in the WHERE clause only
  • OR conditions that span all partitions
Interview tip: "Partition pruning only works when the query's WHERE clause directly filters on the partition key without any function transformation — I always store dates as DATE type and query them as dates, not via YEAR() functions."
Postgres calls this "constraint exclusion" for static partitions and "partition pruning" for native declarative partitions. Check via EXPLAIN — pruned partitions do not appear in the plan.
🔄 Replication

Master-Replica Replication

When 80% of your traffic is reads, replication is the highest-leverage optimization. Separate read traffic from write traffic by introducing dedicated read replicas.

User Onboarding Service │ ├── Registration (WRITE) ──────► Master DB │ │ └── Login / Profile (READ) ──► Load │ async replication Balancer │ ────────────────► │ ▼ ┌───────────┐ │ Replica 1 │ 1,000 read req/s ├───────────┤ │ Replica 2 │ 1,000 read req/s └───────────┘ Total capacity: 1,000 writes/s + 2,000 reads/s

Benefits

  • Read throughput scales linearly with replica count
  • Master not burdened by heavy analytical queries
  • Replicas double as hot standbys for failover
  • Increased data durability — data on multiple nodes

Replication Modes

  • Async (default): Master acks write before replica confirms. Fast but eventual consistency.
  • Semi-sync: At least one replica acknowledges before master acks. Balance of speed + durability.
  • Sync: All replicas must confirm. Zero lag but slow writes.
Added bonus: replication gives you high availability. If one replica fails, others serve reads. If master fails, a replica is promoted. You get both scale and resilience from one architectural move.
🔄 Replication

Replication Lag + Read-Your-Writes Problem

Async replication introduces a window of inconsistency. A user writes to the master, then immediately reads from a replica that hasn't yet received the update — they see stale data.

t=0ms: User updates profile photo → Write sent to Master ✓ t=5ms: User reloads profile page → Read routed to Replica → Replica not yet synced! → User still sees old photo ✗ t=50ms: Replica catches up → User now sees new photo ✓ This window (0–50ms) is "replication lag"

Read-Your-Writes Violation

A user cannot see their own recent write when immediately reading from a lagging replica. Classic symptom: "I just updated my bio but it shows the old text."

Solutions

  • Sticky routing: Send a user's reads to master for N seconds after a write
  • Write-then-read to master: Route reads to master for the writing user
  • Read your write token: Client passes last-write LSN; replica serves only if caught up
  • Sync replication: Zero lag but higher write latency

Monotonic Read Consistency

Related problem: a user refreshing sees data go backwards if routed to different replicas at different lag levels. Solution: pin a user's session to one replica.

Monitoring Lag

Postgres: SELECT * FROM pg_stat_replication;
MySQL: SHOW SLAVE STATUS\G
Alert when Seconds_Behind_Master > 5s.

🔄 Replication

Multi-Master Replication Trade-offs

Multi-master (active-active) allows writes to go to any node. Solves write-scalability and geo-redundancy but introduces the hardest problem in distributed systems: write conflict resolution.

Single-Master (Standard)

  • All writes to one node — no conflicts possible
  • Simple operational model
  • Write throughput limited to one machine
  • Master failure requires promotion of replica
  • Best for: most OLTP applications

Multi-Master

  • Writes accepted on any node — higher write throughput
  • Works across geo-regions (low-latency local writes)
  • Conflict resolution required (last-write-wins, CRDTs, manual)
  • Complex failover and split-brain risk
  • Best for: global apps, collaborative editing
Conflict scenario: User A in Mumbai and User B in London both update the same row at the same millisecond. Both masters accept the write. Now they must reconcile — which value wins?

Last Write Wins (LWW)

Higher timestamp wins. Simple but can discard valid concurrent writes. Used by Cassandra.

CRDTs

Data structures that always merge correctly (e.g., counters, sets). Used by Redis, Riak. No conflicts by design.

Application Merge

Push conflict to application layer. E.g., Google Docs uses OT/CRDT to merge concurrent edits.

⚡ Sharding

Sharding Strategies

Sharding = splitting data AND infrastructure across multiple database servers. Unlike partitioning (multiple partitions on one server), each shard is a separate physical node.

Range Sharding

Shard 1: user_id 1 – 1,000,000 Shard 2: user_id 1M – 2,000,000 Shard 3: user_id 2M – 3,000,000 + Simple range scans - Hotspot: new users always hit Shard N

Hash Sharding

shard = hash(user_id) % N N=4 shards: user_id=101 → hash % 4 = 1 → Shard 1 user_id=205 → hash % 4 = 3 → Shard 3 + Even distribution, no hotspot - Re-sharding requires remapping ALL keys

Consistent Hashing (Production Choice)

Place shards on a ring (0–2³²). Each key maps to the next clockwise shard. Adding/removing a shard only remaps ~1/N of keys instead of all of them.

0 ┌────┐ 270 │ │ 90 Shards: A(0°), B(90°), C(180°), D(270°) └────┘ 180 key_hash=50° → Shard B (next clockwise from 50°) key_hash=200° → Shard D Add Shard E at 135°: only keys 90°–135° remapped → 1/4 of data moves instead of everything ✓
Interview: "I'd choose consistent hashing for any production sharding setup because it minimises data movement during topology changes — critical for zero-downtime scaling."
⚡ Sharding

Shard Key Selection Pitfalls

The shard key is the most critical decision in any sharding design. A wrong choice causes hotspots, cross-shard queries, and re-sharding pain that is almost impossible to fix without downtime.

PitfallExampleImpact
Hotspot shardShard by created_at range — all new writes go to latest shardOne shard overwhelmed; others idle
Low cardinality keyShard by country with only 5 countriesUneven distribution; can't add more shards
Cross-shard queriesShard by user_id but query by emailScatter-gather across all shards — slow
Changing keyShard by mutable attribute (e.g., user's city)Row must move shards on update
No monotonic IDsShard by auto-increment PK with range shardingNew rows always go to last shard

Good Shard Key Properties

  • High cardinality — enough distinct values for even distribution
  • Immutable — value never changes after insert
  • Present in most queries — avoids cross-shard scatter
  • Uniform write distribution — not time-monotonic

Common Good Choices

  • user_id (UUID) — high cardinality, immutable, in most queries
  • tenant_id — SaaS apps, isolates tenants cleanly
  • order_id (hash) — uniform distribution on e-commerce
  • hashed timestamp bucket — spread time-based load
Scatter-gather: if a query has no shard key in the WHERE clause, the database must query ALL shards and merge results. At scale this is O(N × query cost) — catastrophically slow.
⚙️ Optimizations

Connection Pooling

Opening a new DB connection is expensive — TCP handshake, TLS, auth, and session setup can take 5–50ms. At high throughput, establishing fresh connections per request wastes more time than the query itself.

Without Pooling (naïve): Request → [open conn 20ms] → [query 1ms] → [close conn] → Response Effective query time: 21ms ✗ With Pooling (PgBouncer / HikariCP): Request → [borrow idle conn 0.1ms] → [query 1ms] → [return conn] → Response Effective query time: 1.1ms ✓ Pool state: ┌────────────────────────────────────┐ │ [conn1:idle] [conn2:busy] [conn3:idle] │ │ [conn4:idle] [conn5:busy] │ │ Min: 5 Max: 20 Current: 5 │ └────────────────────────────────────┘

Pool Sizing Formula

Too small → requests queue. Too large → DB overwhelmed with context switches.

pool_size ≈ num_cores × 2 + effective_spindle_count -- HikariCP recommendation: -- For 4-core DB: pool ~9–10 connections -- Not 100+ connections as many apps do!

Popular Poolers

  • PgBouncer — Postgres, lightweight, session/transaction/statement modes
  • HikariCP — JVM apps (Spring Boot default), ultra-fast
  • c3p0 / DBCP — legacy Java, still used
  • RDS Proxy — AWS managed pooler for RDS/Aurora
Interview: "I size connection pools using the HikariCP formula and set connectionTimeout to fail fast rather than queue indefinitely — queuing masks overload problems."
⚙️ Optimizations

N+1 Query Problem & Solutions

The N+1 problem is one of the most common performance killers in ORM-backed applications. It occurs when fetching N parent records and then issuing N separate queries to fetch their related children.

-- The problem: fetching 100 users with their orders -- ORM generates: SELECT * FROM users; -- 1 query SELECT * FROM orders WHERE user_id = 1; -- query 2 SELECT * FROM orders WHERE user_id = 2; -- query 3 ... SELECT * FROM orders WHERE user_id = 100; -- query 101 -- 101 round-trips to DB for 100 users! -- The fix: JOIN or eager-load in one shot SELECT u.*, o.* FROM users u JOIN orders o ON o.user_id = u.id WHERE u.id IN (1, 2, ..., 100); -- 1 query ✓

Solutions

  • Eager loading: User.includes(:orders) in ActiveRecord, @EntityGraph in JPA
  • Batch loading: DataLoader pattern — collect all IDs, fire one IN query
  • JOIN query: Write the JOIN explicitly for complex cases
  • GraphQL DataLoader: Batches N+1 at the resolver layer

Detection

  • Enable query logging and look for identical queries with different IDs
  • Use Bullet gem (Rails) or Hibernate statistics
  • APM tools (Datadog, New Relic) flag N+1 automatically
  • Count DB round-trips per API call in load tests

Caching Patterns

Caching reduces DB load by serving repeated reads from memory. The pattern you choose determines consistency guarantees and write behaviour.

Read-Through (Cache-Aside)

Read request: App → Cache HIT? → return data ✓ App → Cache MISS → DB → populate cache → return -- App manages cache population -- Lazy loading: only cache what's needed -- Risk: cache stampede on cold start

Write-Through

Write request: App → Cache → DB (synchronous) -- Both updated in same transaction -- Strong consistency: cache never stale -- Slower writes (2 ops per write) -- Cache may hold rarely-read data

Write-Behind (Write-Back)

Write request: App → Cache (return immediately) ↓ async (batched later) DB -- Fastest writes (acknowledge immediately) -- Risk: data loss if cache crashes -- Use for: high-write, loss-tolerant data

Cache Invalidation Strategies

  • TTL (Time-To-Live) — expire after fixed time
  • Event-driven — invalidate on DB update event
  • Version tags — cache key includes version number
  • LRU eviction — least-recently-used evicted first

"There are only two hard things in CS: cache invalidation and naming things."

Query Optimization Patterns

Query optimization is always the first step — cheapest to implement, no infrastructure changes needed. Poor queries can negate the benefit of indexes, partitioning, and even sharding.

Anti-Patterns to Avoid

-- 1. SELECT * (fetches unused columns) SELECT * FROM users WHERE email='a@b.com' -- 2. Functions on indexed columns WHERE LOWER(email) = 'a@b.com' ← breaks index -- 3. LIKE with leading wildcard WHERE name LIKE '%john%' ← full scan -- 4. Implicit type cast WHERE user_id = '12345' ← cast breaks index

Optimized Equivalents

-- 1. Select only needed columns SELECT name, avatar FROM users WHERE email='a@b.com' -- 2. Store email lowercase at insert time WHERE email = 'a@b.com' ← uses index ✓ -- 3. Full-text search for substring matches WHERE to_tsvector(name) @@ plainto_tsquery('john') -- 4. Match types explicitly WHERE user_id = 12345 ← integer literal ✓

Pagination Pattern

-- BAD: OFFSET gets worse at high page # SELECT * FROM orders LIMIT 20 OFFSET 10000 -- DB scans 10,020 rows to return 20! -- GOOD: keyset pagination SELECT * FROM orders WHERE id > last_seen_id ORDER BY id LIMIT 20

Batch Operations

-- BAD: N individual inserts INSERT INTO events(data) VALUES ('a'); INSERT INTO events(data) VALUES ('b'); -- GOOD: bulk insert INSERT INTO events(data) VALUES('a'),('b'),('c'),('d'); ← 1 round-trip

Schema Design for Performance

Schema decisions made at day 1 are among the hardest to undo at scale. Design for your query patterns, not just normalization theory.

Normalisation vs Denormalisation

Normalised (3NF)Denormalised
No redundancyControlled redundancy
Complex JOINsFewer JOINs, faster reads
Simple writesMultiple update targets
OLTP defaultOLAP / read-heavy APIs

Data Type Choices

  • Use INT/BIGINT for IDs — smaller, faster than VARCHAR UUIDs
  • Use UUID v7 when globally unique IDs needed (time-ordered, shard-friendly)
  • Store timestamps as TIMESTAMPTZ — avoids timezone bugs
  • Prefer ENUM over VARCHAR for fixed categories — storage + constraint
  • Avoid TEXT/JSON blobs in frequently-queried columns — unpredictable size

User Table — Before vs After Optimization

-- BEFORE (common anti-pattern) users(id VARCHAR(36), email VARCHAR(255), full_data JSON, created_at VARCHAR) -- Problems: VARCHAR UUID slow to join, JSON unindexable, VARCHAR date unsortable -- AFTER users( id BIGSERIAL PRIMARY KEY, -- fast integer PK email VARCHAR(254) UNIQUE NOT NULL, -- index auto-created name VARCHAR(100) NOT NULL, status user_status_enum NOT NULL, -- ENUM, not VARCHAR created_at TIMESTAMPTZ DEFAULT now() -- proper timestamp );
Soft deletes (deleted_at TIMESTAMP) are common but dangerous at scale — they double the effective table size. Use a partial index: WHERE deleted_at IS NULL.

Senior Trap Q&A — Set 1: Indexing & Replication

Q: "If indexing is so good, why not index every column?"

A: Every index costs write performance — on INSERT, UPDATE, or DELETE, the database must update all index trees for that table. Too many indexes means each write triggers multiple B-Tree rebalances, degrading write throughput significantly. Additionally, each index consumes memory and disk. I'd only index columns that appear in WHERE, JOIN ON, or ORDER BY clauses of frequent, high-cardinality queries, and I'd monitor pg_stat_user_indexes for unused indexes to drop them.
Q: "You added a read replica. A user says 'I just updated my profile but it shows the old data.' What's happening?"

A: This is the read-your-writes consistency violation caused by replication lag. The write went to the master, but the subsequent read was routed to a replica that hadn't yet received the async replication update. Fixes depend on SLA: for strict consistency I'd route that user's reads to the master for a short window after any write, or pass the master's WAL LSN to the client and have replicas serve the read only once they've applied up to that LSN. For looser requirements, a small TTL-based sticky session to master is simpler.
Q: "What's the difference between a covering index and a composite index?"

A: A composite index covers multiple columns in the index key — the query planner uses it for filtering and ordering. A covering index goes further: it includes all columns that the query needs (via INCLUDE clause in Postgres), so the database can satisfy the entire query from the index without ever touching the main table heap — this is called an "index-only scan" and is significantly faster for read-heavy workloads.
🎯 Interview Prep

Senior Trap Q&A — Set 2: Partitioning & Sharding

Q: "What's the difference between partitioning and sharding?"

A: Partitioning logically divides a table's data into smaller chunks (partitions) that still reside on the same database server. Sharding goes further — each shard is a completely separate database server (or cluster). Multiple partitions can live on a single shard, but not vice versa. Partitioning reduces scan cost by allowing partition pruning. Sharding distributes both data and write load across machines, enabling horizontal scale-out beyond a single server's limits.
Q: "Why is consistent hashing preferred over simple modular hash sharding?"

A: With modular hashing (hash % N), adding or removing a shard requires remapping nearly all keys — every key's shard assignment changes. At scale, this means a re-sharding event moves the majority of your data, causing massive I/O and potentially hours of downtime. Consistent hashing places shards on a ring so only ~1/N of keys need to move when a shard is added or removed. This makes topology changes minimally disruptive — essential for live, zero-downtime systems.
Q: "How would you handle a hot partition problem?"

A: Hot partitions occur when one partition receives disproportionate traffic — typically from range sharding on monotonically increasing keys like timestamps or auto-increment IDs. Solutions: (1) Switch to hash-based partitioning to distribute writes uniformly. (2) Add a random suffix or time bucket to the partition key to spread load. (3) Use consistent hashing with virtual nodes — each physical shard handles multiple virtual positions on the ring, preventing single hot spots even with slight key skew.

Senior Trap Q&A — Set 3: Advanced Scenarios

Q: "When would you use write-behind caching vs write-through? What's the risk?"

A: Write-through keeps cache and DB always in sync — every write updates both synchronously. This gives strong consistency but adds write latency. Write-behind (write-back) acknowledges the write immediately after updating the cache, and flushes to the DB asynchronously in batches — this is much faster but introduces data loss risk if the cache node crashes before flushing. I'd use write-behind for high-write, loss-tolerant data like analytics counters or view counts, and write-through for anything with strict durability requirements like financial transactions.
Q: "Your DB has 100M rows. Queries are slow despite indexes. What would you check?"

A: In order: (1) EXPLAIN ANALYZE — is the planner choosing the right index? Are statistics stale? Run ANALYZE. (2) Index selectivity — is the WHERE column high-cardinality? (3) Query patterns — any function wrapping the index column? Leading-wildcard LIKE? (4) Partition pruning — if partitioned, is the WHERE clause on the partition key? (5) Table bloat — excessive dead rows from updates/deletes; VACUUM FULL or pg_repack. (6) Lock contention — check pg_locks for blocking queries. (7) Consider partitioning if it isn't already done.
Q: "How do you scale writes beyond what a single master can handle?"

A: The options in escalating complexity: (1) Vertical scale the master (CPU/RAM/NVMe SSDs). (2) Move heavy analytics/reporting queries to replicas to free master capacity. (3) Horizontal write scaling via sharding — split data across multiple masters, each owning a subset. (4) Multi-master replication for geo-distributed writes (with conflict resolution). (5) Event sourcing + CQRS — separate write model (append-only event log) from read model; the event log can be partitioned across Kafka topics trivially.

Summary — The Complete Optimization Ladder

Always present database optimization as a progressive decision ladder in interviews. Jumping straight to sharding shows you don't understand the cost/complexity tradeoffs.

6-Step Optimization Ladder

1
Query Tuning — SELECT specific columns, avoid SELECT *, use proper types, keyset pagination. Zero infra cost.
2
Indexing — B-Tree for range/equality, Hash for exact match, Partial for subsets, Covering to eliminate heap fetch. Read ↑, Write ↓.
3
Vertical Scaling — Bigger machine. Quick win, but has a ceiling and costs money fast.
4
Read Replication — Master for writes, replicas for reads. Solves 80% of read-heavy scaling problems. Watch for replication lag.
5
Partitioning — Logically split large tables. Reduces scan cost via partition pruning. Choose partition key carefully.
6
Sharding — Distribute data + infrastructure. Last resort. Use consistent hashing. Pick immutable, high-cardinality shard key.

Bonus Techniques

  • Connection pooling (always on by default in production)
  • Caching (Redis / Memcached) for hot read data
  • N+1 elimination via eager loading / DataLoader
  • Schema design — right types, indexes, denormalization where needed

Interview Delivery Tips

  • Start with business impact — "slow queries mean users drop off"
  • Show the ladder — don't jump to sharding immediately
  • Quantify: mention O(log n) vs O(n), 80:20 read/write ratio
  • Acknowledge trade-offs for every technique you propose
  • End with: "I'd profile first with EXPLAIN ANALYZE before making any architectural change"
