📋 Requirements

Opening — The 30-Second Pitch

Say this in your first 30 seconds to signal depth before the interviewer asks anything.
"Search hotels via Elasticsearch geo → Check availability in PostgreSQL → Book room with Redis distributed lock → Process payment with idempotency key → Confirm via Kafka events."

What this pitch signals

Elasticsearch — geo search, full-text hotel discovery, filter by amenities & price range. Eventual consistency is fine here.

Redis SETNX — distributed lock prevents two users booking the same room simultaneously (ms-level fast fail).

PostgreSQL FOR UPDATE — ACID guarantee, zero double-booking. Strong consistency is non-negotiable for inventory.

Idempotency key = booking_id sent to payment gateway. Same key within 24h → same payment intent, no double charge.

Key insight: Search path = Availability (ES, eventual OK). Booking path = Consistency (PostgreSQL ACID, no shortcuts).

Search Path

Elasticsearch for geo + text. Redis caches popular queries (TTL 10 min). Eventual consistency is acceptable.

Booking Path

Redis SETNX lock → PostgreSQL FOR UPDATE → ACID transaction. Zero compromise on consistency.

🏨 Booking Flow

Room Availability — Date-Range Query

ES returns hotels by geo + filters. A separate DB call checks availability after hotel selection — never mix the two.

SQL: Find available rooms for a date range

SELECT r.room_id, r.room_type, r.capacity, p.price FROM rooms r JOIN room_availability a ON r.room_id = a.room_id JOIN price_calendar p ON r.room_id = p.room_id AND p.date = a.date WHERE a.hotel_id = {id} AND a.date BETWEEN '2025-02-01' AND '2025-02-05' GROUP BY r.room_id HAVING COUNT(CASE WHEN a.status = 'Available' THEN 1 END) = {num_nights} -- ALL nights must be available

row_availability table design

One row per (room_id, date) — simple model. Index on (room_id, date, status) makes the above query fast.

Why not ES for availability?

Availability changes on every booking → constant reindexing = expensive + eventual inconsistency. ES is for discovery, PostgreSQL is for inventory.

The HAVING clause ensures every night in the range is Available — one blocked date rejects the room.

Dynamic Pricing Engine

price_calendar table

CREATE TABLE price_calendar ( hotel_id UUID, room_id UUID, date DATE, price DECIMAL(10,2), currency CHAR(3) DEFAULT 'USD', PRIMARY KEY (hotel_id, room_id, date) );

Price Factors

  • Demand: Weekend / holiday surcharges
  • Lead time: Last-minute discounts
  • Occupancy: >80% booked → price rises
  • Seasonality: Peak travel months
  • Events nearby: Concert / conference

Pre-computation Strategy

  • Pricing engine runs daily batch job
  • Writes next 365 days of prices
  • Real-time override via events (surge pricing)
  • Redis cache: price:{room_id}:{date} TTL 1h

Price Snapshot at Booking

Store amount in bookings at creation time. Protects user from price changes after hold is acquired.

Currency Handling

Store in hotel's local currency. Convert to user's currency at display time using exchange rate service (not stored).

Never recalculate price at payment time — use the snapshotted amount from the PENDING_PAYMENT booking row.

Booking State Machine

SEARCHING ──► HOLD (Redis lock acquired) │ ▼ PENDING_PAYMENT (booking row created, room_avail = Booked) │ ┌───────┴────────┐ ▼ ▼ CONFIRMED EXPIRED (payment not made within 15 min) │ │ ▼ ▼ CHECKED_IN room released → Available │ ▼ CHECKED_OUT │ ▼ REVIEWED (optional terminal) Any state ──► CANCELLED (subject to refund policy)

→ PENDING_PAYMENTRedis lock + DB transactionroom_avail = Booked

🏨 Booking Flow

Inventory & Overbooking Prevention

The Critical Booking Path (4 layers)

1. SETNX lock:hotel:{hotel_id}:room:{room_id}:{checkIn}:{checkOut} {booking_attempt_id} EX 30 → returns 0? → 409 "Room being booked, try again" → returns 1? → proceed 2. Double-check with pessimistic DB lock: SELECT status FROM room_availability WHERE room_id={id} AND date BETWEEN {checkIn} AND {checkOut} FOR UPDATE -- ACID guarantee → any date not 'Available'? → DEL lock → return "Not available" 3. Atomic Transaction: BEGIN; INSERT INTO bookings (..., status='PENDING_PAYMENT'); UPDATE room_availability SET status='Booked', booking_id={id} WHERE room_id={id} AND date BETWEEN {dates}; COMMIT; 4. DEL lock -- release (auto-expires after 30s if service crashes)

Controlled Overbooking

Allow up to 5% overbook like airlines. If overbooked on check-in day → hotel upgrades or relocates guest to partner hotel.

Race Example

User A + B both try room_123. A's SETNX wins → B gets 409 immediately → A commits → B retries, sees "not available". Zero double booking.

🗄 DB Schema

Database Schema — Critical Tables

-- Most critical table: one row per room per date CREATE TABLE room_availability ( hotel_id UUID, room_id UUID, date DATE, status ENUM('Available','Booked','Maintenance'), booking_id UUID NULL, PRIMARY KEY (hotel_id, room_id, date) ); CREATE INDEX idx_avail ON room_availability(room_id, date, status); -- Bookings: snapshot amount + policy at creation time CREATE TABLE bookings ( booking_id UUID PRIMARY KEY, user_id UUID, hotel_id UUID, room_id UUID, check_in DATE, check_out DATE, status ENUM('PENDING_PAYMENT','CONFIRMED','CANCELLED',...), amount DECIMAL(10,2), cancellation_policy JSONB, -- snapshot at booking time! payment_id UUID NULL, created_at TIMESTAMPTZ ); -- Payments: idempotency enforced by DB CREATE TABLE payments ( payment_id VARCHAR(255) PRIMARY KEY, -- from gateway booking_id UUID UNIQUE, -- UNIQUE = no double charge amount DECIMAL(10,2), status ENUM('SUCCESS','FAILED','REFUNDED'), gateway_response JSONB );
📈 Scaling

Redis Caching Strategy

Key patterns and TTLs

-- Distributed lock (booking critical path) lock:hotel:{hotelId}:room:{roomId}:{checkIn}:{checkOut} Value: {booking_attempt_id} EX 30s ← auto-release on crash -- Search cache (hot path) search:{hash(location,filters)} TTL 10min ← 60-70% hit rate hotel:{hotelId}:details TTL 30min user:{userId}:bookings TTL 5min -- Payment timeout enforcement booking:{bookingId}:expires EX 900 ← 15 min payment window → on expiry: Cron/TTL listener → release room, set booking EXPIRED -- Price cache price:{roomId}:{date} TTL 1h

Why SETNX works as a lock

SETNX key value EX 30 is atomic. Only one caller gets 1; all others get 0 immediately. EX ensures auto-release if service crashes — prevents deadlock.

Payment Expiry

Cron job runs every minute. Finds bookings in PENDING_PAYMENT with created_at < now()-15min. Releases rooms atomically.

Never use Redis as the sole consistency layer — always follow SETNX with a PostgreSQL FOR UPDATE check. Redis can fail or have network partitions.

📈 Scaling

Architectural Trade-offs

Microservices vs Monolith

Microservices: Independent scaling — Search Svc scales 10× without touching Booking Svc. Fault isolation. Complex deployment.

Row-per-date vs Aggregate Availability

Row-per-date: Simple queries, more rows (10M rooms × 365 = 3.65B rows/yr). Aggregate: Fewer rows, complex updates with concurrency.

Specific Room vs Room Type Booking

Type-based (real-world): User books "Deluxe", system assigns specific room at check-in. Simpler lock key, better occupancy.

Synchronous vs Async Payment

Sync: Simpler, but payment gateway adds latency to booking path. Async (chosen): Booking returns payment_url immediately; webhook confirms later.

Push vs Poll for Notifications

Kafka async events (chosen): booking.created → Notification Svc sends email/SMS/push. Decoupled, retry-able, no booking latency impact.

Dates: DATE vs TIMESTAMP

check_in/check_out: DATE (hotel local) — no tz conversion. created_at/payment_deadline: TIMESTAMPTZ (UTC) — absolute moment.

🎯 Interview Prep

Senior Q&A — How do you prevent double booking?

This is the #1 question in hotel/ticket booking system design interviews.

Multi-layer answer (say all 4 layers)

1

Redis SETNX — fast rejection in 1-2ms. Lock key includes full date range: lock:hotel:{id}:room:{id}:{checkIn}:{checkOut}

2

SELECT ... FOR UPDATE on room_availability — pessimistic DB lock. ACID guarantee within PostgreSQL.

3

Atomic transaction — INSERT booking + UPDATE room_availability in one BEGIN/COMMIT block.

4

Auto-expiry — Redis lock EX 30s, so if service crashes mid-booking, lock releases automatically. No deadlock.

Race condition walk-through

User A & B both try room_123 for Feb 1-5 simultaneously.
A's SETNX returns 1 (wins lock) → B's SETNX returns 0 → B gets 409 immediately.
A does FOR UPDATE → transaction → commits → releases lock.
B retries → sees room status = 'Booked' → returns "Not available".
Zero double booking. Zero deadlock risk.

Common mistake: Using only Redis lock without the DB FOR UPDATE. Redis can fail or have network partition — always back it up with DB-level lock.

Senior Q&A — How do you prevent double charging?

4-layer idempotency defense

1

Idempotency key = booking_id sent to payment gateway. Same key within 24h → gateway returns same payment_intent, no new charge.

2

UNIQUE INDEX on payments(booking_id) — second INSERT fails gracefully with constraint violation.

3

Webhook handler check — always query SELECT * FROM payments WHERE booking_id = {id} before processing.

4

Validate webhook signature — HMAC verification prevents replay attacks from malicious actors.

Webhook handler (idempotent)

Webhook payment.success received: 1. Validate HMAC signature 2. SELECT * FROM payments WHERE booking_id = {id} → exists? → return 200 (already processed, ignore) → not exists? BEGIN; INSERT INTO payments (..., status='SUCCESS'); UPDATE bookings SET status='CONFIRMED', payment_id={id}; COMMIT; 3. Publish: payment.success + booking.confirmed → Kafka
Always return 200 for duplicate webhooks — returning 4xx/5xx causes the gateway to retry, creating a loop.

Senior Q&A — How do you scale search to 100M/day?

The math

100M/day = 1,157/sec avg
Peak 3× = 3,500/sec
100 instances × 50 req/sec = 5,000 cap
→ Scale up at CPU >70%

Redis cache (biggest win)

Cache key: hash(location, filters) TTL 10min. Popular destinations = 60-70% cache hit rate. Real DB load: ~350-460/sec.

Full scaling strategy

1

Geo routing — Route to nearest datacenter (us-east-1 / eu-west-1 / ap-south-1). Cuts latency 500ms → 50ms.

2

ES geo sharding — Shard by region (US/EU/Asia), 5 primary shards + 1 replica per region.

3

Filter context in ES — Use filter (not query) context. Results are cached at the shard level, no scoring overhead.

4

100 Search Svc instances — Auto-scale at CPU >70%. Stateless → trivial horizontal scale.

5

Read replicas — 5 PostgreSQL replicas per region for hotel details queries.

Mention the cache hit rate math: "Even at 60% cache hit, we only serve 1,400/sec from ES at peak — well within a 5-node ES cluster's capacity."

Senior Q&A — Cancellations & Modifications

Cancellation flow

1

Validate user owns the booking

2

Read snapshotted cancellation_policy from booking row (never live hotel policy)

3

Calculate refund by hours_until_checkin

4

Atomic: UPDATE bookings status='CANCELLED' + UPDATE room_avail status='Available' in one transaction

5

Async refund via payment gateway webhook

6

Publish booking.cancelled → Notification Svc

Refund tiers

≥ 24h before check-in
100% refund

12–24h before check-in
50% refund

< 12h before check-in
0% refund

Modification (date change)

1. Acquire new lock for new dates (SETNX) 2. SELECT FOR UPDATE on new dates 3. BEGIN; release old dates → book new dates → update booking; COMMIT; 4. Charge price difference OR issue partial refund
Always snapshot cancellation_policy into the booking at creation. If the hotel changes its policy later, the user is protected by the original terms.

Senior Q&A — DR Strategy & Resilience

DR Setup

  • Primary: us-east-1 (active)
  • Warm standby: us-west-2
  • Streaming replication lag: < 5 seconds
  • Route53 health checks → auto failover
  • Failover time: 2–5 minutes
  • RPO = 5 seconds, RTO = 5 minutes
  • Monthly DR drills

Circuit Breaker Pattern

  • Booking Svc → Payment Svc: CB with 30s timeout
  • If Payment Svc down: return booking_id + retry URL
  • User can retry payment; booking remains PENDING
  • Kafka retry with exponential backoff (3 retries)
  • DLQ for failed notifications (process later)

Redis failure scenarios

Redis lock service down? Fall back to DB-only locking (SELECT FOR UPDATE). Slower (no fast-fail), but booking still works correctly. Degrade gracefully, never block transactions.

ES down? Fall back to PostgreSQL full-text search (slower, ~500ms). Return partial results. Hotel discovery degrades gracefully — booking path unaffected.

Key phrase: "Graceful degradation" — each service failure has a fallback. Never design a single point of failure in the booking critical path.

Closing — Key Takeaways

The Core Insight

Two separate consistency requirements: Search = Availability (eventual OK, use ES). Booking = Consistency (ACID always, PostgreSQL + Redis lock).

Anti-double-booking Stack

Redis SETNX (fast fail) → PostgreSQL FOR UPDATE (ACID) → Atomic transaction → Auto-expiry. Four layers, zero gaps.

Idempotency Everywhere

booking_id as payment idempotency key + UNIQUE DB constraint. Webhook handler always checks before processing. Return 200 for duplicates.

Snapshot Critical Data

Snapshot price + cancellation_policy at booking creation. User is protected from future changes. Audit trail preserved.

One-liner to close: "The system separates search (ES, eventual) from booking (PostgreSQL ACID + Redis lock), uses Kafka for async notifications, and employs idempotency keys with DB UNIQUE constraints to prevent any double charges — giving us correctness at scale."
