Opening Script

"Zomato is a three-sided marketplace connecting customers, restaurants, and delivery partners. Before I start designing, I want to clarify the scope."

"The two hardest technical problems here are:"

  1. Real-time delivery partner assignment — geospatial problem at scale. 500K active partners, GPS updating every 5 seconds.
  2. Live order tracking — customer needs to see the partner moving on a map in near-real-time.

Clarifying questions to ask:

  • Are we building food delivery only or also restaurant discovery?
  • Do we need real-time partner tracking on a map?
  • What's the peak order volume — India or global scale?
  • Live ETA updates or just static estimate at order placement?
  • Do we need scheduled/pre-orders?

Functional Requirements

  • Customers search restaurants by location, cuisine, rating
  • Customers browse menus and place orders
  • Restaurants receive orders in real-time and can accept / reject
  • System auto-assigns nearest available delivery partner
  • Customers track partner location on map in real-time
  • Push / SMS notifications for every order state change
  • Customers rate restaurant and delivery partner post-delivery
  • Surge pricing applied during peak demand periods
  • Payment via card, wallet, COD; idempotent charge
  • Cancellation within a window with automatic refund

Out of scope: restaurant owner onboarding portal, scheduled orders, restaurant analytics dashboard

Restaurant Assignment & Discovery

  • Customer search: Elasticsearch geo_distance query — filters by lat/lon radius, cuisine, rating, is_open
  • Delivery zone check: PostGIS polygon query — is delivery address inside restaurant's delivery zone?
  • Capacity / availability: MySQL is_open flag refreshed from operating hours schedule
  • Auto-accept: large chains (McDonald's, Pizza Hut) use auto-accept; boutique restaurants use manual accept on tablet
  • Geohash proximity: 7-char geohash (~150m cell) tags every restaurant; nearby restaurants fetched by geohash prefix

Order routed to restaurant via:

  1. REST call to Restaurant Service → WebSocket push to tablet
  2. 30-second accept window; if no ACK → order auto-cancelled with refund
  3. Restaurant sends back estimated_prep_minutes → seeds ETA calculation

ETA Calculation

Components of delivery ETA:

  • Restaurant prep time — provided by restaurant on acceptance (e.g. 20 min)
  • Partner travel to restaurant — distance from partner GPS to restaurant / estimated speed
  • Restaurant to customer distance — Google Maps Distance Matrix API for road distance
  • Traffic factor — real-time traffic multiplier from Maps API
  • Partner historical speed — ML model trained on partner's past deliveries (time-of-day aware)

ETA = prep_time + travel_to_rest + travel_to_customer

Updated every 30 seconds on tracking screen via SSE push.

Do NOT use: straight-line distance / average speed — gives terrible estimates. Use Google Maps + ML model. ETA inaccuracy > ±5 min erodes user trust significantly.

Surge Pricing Algorithm

  1. Geohash partitioning: encode restaurant lat/lon as 7-char geohash (~150m × 150m cell)
  2. Demand/supply calculator (runs every 60 seconds): 
    demand = orders placed in cell in last 10 min
supply = ONLINE partners currently in cell
ratio  = demand / supply
ratio > 2.0 → multiplier = 1.5×
ratio > 3.0 → multiplier = 2.0×
  3. Redis store: SETEX surge:{geohash7} 120 1.5
    Expires in 2 min → stale surges auto-clear
  4. Order creation: GET surge:{geohash7} (<1ms) → apply to delivery_fee → store surge_multiplier on order row
  5. UI: show "Surge pricing: 1.5×" badge in restaurant search results — same Redis GET at search layer

Never read surge multiplier from DB on order creation — adds latency to critical path

Search Query (geo_distance + text + filters):

  • geo_distance filter — within 5 km of customer
  • term filter — cuisine_tags, is_open=true
  • range filter — avg_rating ≥ 4.0
  • Sort: composite score of distance × rating × is_promoted

Elasticsearch synced from MySQL via Kafka CDC (Debezium). New restaurants appear in search within minutes — eventual consistency is acceptable for discovery.

Menu & Inventory

Read pattern — heavily cached:

  • Key: restaurant:menu:{restaurantId} in Redis, TTL 30 min
  • 99% of menu reads served from Redis — zero DB load
  • Cache invalidated on menu update via Kafka event

Restaurant-side inventory updates:

  • Restaurant tablet can toggle is_available per item (e.g. "Biryani sold out")
  • Update: MySQL write → Kafka event → Redis cache invalidation → Elasticsearch update
  • Order Service validates item availability at order creation (re-reads from Redis, not DB)

Price snapshot:

order_items.unit_price stores price at order time — menu price changes don't affect placed orders

200K restaurants × 50 items avg = 10M menu items. All read-heavy. Redis cache is mandatory.

Payment Flow

  1. Customer places order with payment_method_id
  2. Order Service calls Payment Service with idempotency key = order_id + attempt_number
  3. Payment Service calls Razorpay / Stripe API — charge(amount, payment_intent_id)
  4. On success: MySQL payments row → status=CAPTURED
  5. Kafka event: payment-captured → Order Service proceeds

Wallet / COD handling:

  • Wallet: debit wallet balance atomically (Redis DECRBY + MySQL write in transaction)
  • COD: order placed without charge; collect_on_delivery=true flag set

Refund flow:

Cancellation → Kafka order-cancelled → Payment Svc calls Stripe refund API with original payment_intent_id → customer notified

Idempotency key prevents double-charge if network retry happens after payment captured

Scaling Strategy

GPS Updates — 100K GEOADD/sec

  • Shard Redis by city: Mumbai partners → Mumbai Redis, Delhi → Delhi Redis
  • Each city Redis handles 5K–20K partners; single instance << 100K ops/sec limit
  • GEORADIUS scoped to city — restaurant in Mumbai only queries Mumbai Redis

MySQL Orders at Peak (500 orders/sec)

  • Partition orders table by city_id — hot city doesn't block others
  • Read replicas serve all GET /orders queries
  • Archive orders older than 7 days to S3 Parquet → active table stays small and fast

Cassandra Location History

  • Write to Cassandra every 30 sec (not every 5 sec) — 6× write reduction
  • 5–10 node cluster, sharded by partner_id, 30-day TTL per row

SSE at Scale — 500K concurrent connections

10 SSE Push pods × 50K connections each; consistent hashing on order_id → pod routing via Kafka consumer groups

Key Trade-offs

DecisionChoiceTrade-off
Partner location store Redis GEO Sub-ms geo query, not durable — OK, next GPS in 5s
Location history Cassandra Durable, 100K writes/sec; not MySQL (unbounded table growth)
Customer tracking SSE Simpler than WebSocket; auto-reconnects; one-directional is all we need
Partner app comms WebSocket Bidirectional needed (send GPS + receive dispatch); not polling (167K req/sec)
Restaurant search Elasticsearch Geo + text + facets in one query; eventual consistency fine for discovery
Surge multiplier Redis key O(1) <1ms read; not DB (latency on critical path)
Order / payments MySQL ACID Strong consistency for financial data; not Cassandra (eventual too risky)

Window-based cancellation:

Mid-delivery partner cancellation (nightmare scenario):

  • GEORADIUS centered on partner's current GPS (food is with them), not restaurant
  • Supervisor notified; auto-refund issued; partner account flagged
  • Too many mid-delivery cancellations → automatic account suspension

Senior Q&A 1 — Partner App Goes Offline Mid-Delivery

Q: "A delivery partner's phone dies mid-delivery. What happens to the customer's order tracking?"

Answer:

  • Location updates stop: Redis GEO entry for this partner goes stale (no new GEOADD)
  • SSE stream to customer: last known position remains on map; ETA freezes
  • Grace period: Location Service detects no GPS ping for 60 sec → marks partner as "location unavailable"
  • Customer notification: "We've temporarily lost track of your delivery — your food is still on the way"
  • Order is NOT reassigned: food is already physically with the partner
  • Partner phone recovers: WebSocket reconnects → GPS resumes → SSE stream resumes for customer
  • Cassandra gap: location history has a gap for the offline window — noted in dispute records

Key insight: GPS loss does not change order state — physical possession of food is the source of truth, not location signal

Senior Q&A 2 — Restaurant Accepts But Kitchen Is Full

Q: "A restaurant accepts an order even though their kitchen queue is already overloaded. How do you prevent bad ETAs?"

Answer:

  • Acceptance-time prep estimate: restaurant provides estimated_prep_minutes when accepting — they should overestimate if busy
  • Dynamic prep time: track rolling average of actual vs estimated prep time per restaurant; if consistently underestimating → auto-inflate future ETAs
  • Order throttling: if restaurant's kitchen queue exceeds threshold (e.g. 10 active orders) → platform temporarily marks restaurant as busy — new orders rejected at API level
  • SLA tracking: if actual delivery > estimated + 10 min → automatic partial refund coupon issued to customer
  • Restaurant health score: chronic overacceptance → lower search ranking, reduced visibility

Root fix: restaurants need better kitchen capacity tooling. Platform-side: queue depth monitoring + auto-throttle is the engineering answer

Senior Q&A 3 — Massive Dinner Rush in a Single City

Q: "It's 8pm on Diwali in Mumbai. 10× normal order volume hits the city's systems. Walk me through what breaks and how you handle it."

What could fail and how to handle:

  • MySQL writes spike: Mumbai city partition absorbs load; auto-scaling on write replicas; circuit breaker on order placement — queue orders with 5s delay vs. hard reject
  • Redis GEOADD saturated: city-sharded Redis handles this — Mumbai instance pre-scaled; 100K ops/sec headroom
  • Partner shortage → surge pricing kicks in: demand/supply calculator detects high ratio → 2× multiplier activates → more partners come online
  • Kafka consumer lag: Notification Service auto-scales consumer instances; non-critical notifications (e.g. "rate your meal") deprioritized — DELIVERED notifications stay high priority
  • SSE pod saturation: K8s HPA scales SSE pods; new connections routed to new pods via Kafka consumer group rebalance
  • ETA accuracy degrades: real-time traffic API returns high-traffic routes; ML model trained on festival traffic handles this gracefully

Closing Script

"Let me summarize what this design demonstrates."

Systems demonstrated:

  • Real-time geospatial system — Redis GEO with 100K GEOADD/sec, city-sharded, GEORADIUS partner assignment
  • Event-driven order flow — Kafka fan-out from single order event to notifications, analytics, Cassandra writer, SSE push
  • ETA pipeline — prep time + Maps API + ML model + live GPS → ±2 min accuracy
  • Surge pricing — geohash-7 cells, demand/supply ratio, Redis O(1) read on critical path
  • Three-sided marketplace coordination — customer SSE tracking, partner WebSocket dispatch, restaurant WebSocket notifications — all decoupled via Kafka
  • Consistency boundaries — MySQL ACID for orders/payments; Redis for real-time state; Elasticsearch for eventual discovery
