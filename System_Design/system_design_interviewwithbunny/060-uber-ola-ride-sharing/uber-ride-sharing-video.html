📍 Location Engine

Location Service — Driver GPS Updates

Driver app → WS /v1/driver/location  (JWT auth, persistent connection)
    ↓
Every 3–5 seconds: {driver_id, lat, lon, timestamp, speed}
    ↓
Location Update Svc:
    GEOADD drivers:available {lon} {lat} {driver_id}   (if AVAILABLE)
    SET location:{driver_id} '{lat,lon}' EX 60          (1-min TTL)
    PUBLISH driver_location:{driver_id} to Redis Pub/Sub
    Produce Kafka: driver.location_updated → Trip Update Consumer
Bandwidth Optimisations
  • Skip update if moved < 10 m (stationary)
  • Reduce to 1 update/10 s if speed < 5 km/h
  • Protocol Buffers vs JSON → 50% size reduction
Heartbeat & Auto-Offline
  • Heartbeat every 30 s via WebSocket
  • Miss 2 min → GEOREM + auto-offline
  • TTL refreshed on each heartbeat
📍 Location Engine

Geohash Proximity Search — Finding Nearby Drivers

Redis GEORADIUS command:
GEORADIUS drivers:available -122.4194 37.7749 5km WITHDIST ASC COUNT 10
→ O(log N), ~10 ms for 1M drivers
→ Returns: [(D1, 0.8km), (D2, 1.2km), (D3, 2.5km)]

Filter by vehicle type:
  Option A: SISMEMBER drivers:sedan {driver_id}     (per-result check)
  Option B: Separate indexes per type
            GEOADD drivers:available:sedan / :suv / :bike

Geofencing — driver arrived at pickup:
  distance(driver_loc, pickup_loc) < 50m  [Haversine formula]
  → UPDATE trips SET status='DRIVER_ARRIVED'
  → Push + WebSocket: "Your driver has arrived!"

Radius expansion if no drivers found:
  5km → 10km → 20km  (exponential backoff on search radius)
Sharding: US-West · US-East · EU · APAC → each region owns its own Redis geospatial instance. Cross-region queries are extremely rare.

📍 Location Engine

Surge Pricing Engine

Background job runs every 60 s per geohash cell (5 km × 5 km):

available_drivers = GEORADIUS drivers:available {cell_center} 5km COUNT
pending_requests  = SELECT COUNT(*) FROM ride_requests
                    WHERE status='PENDING' AND pickup IN area
                    AND created_at > now() - 10min

demand_ratio = pending_requests / available_drivers

demand_ratio < 1.2   →  1.0×  (no surge)
1.2 – 2.0            →  1.2×
2.0 – 3.0            →  1.5×
3.0 – 5.0            →  1.8×
≥ 5.0                →  up to 3.0×  ← MAX CAP (anti-price gouging)

Smoothing (prevent sudden jumps):
  new_surge = 0.7 × old_surge + 0.3 × calculated_surge
  e.g. old=1.5, calc=2.0 → new = 0.7×1.5 + 0.3×2.0 = 1.65×

SET surge_multiplier:{geohash} 1.65 EX 120  (2-min TTL)
Rider MUST explicitly accept surge before the request is confirmed. Never silently charge a higher fare.
⚙️ LLD

Trip Service LLD — Creating & Tracking Trips

Step 1 — Fare Estimation:
  POST /v1/api/fare/estimate {pickup, drop, vehicle_type}
  Ride Svc → Google Distance Matrix → {distance: 5.2 km, duration: 12 min}
  base_rate:       $2.50
  distance_rate:   5.2 km × $1.50  = $7.80
  time_rate:       12 min × $0.30  = $3.60
  subtotal:                          $13.90
  surge (1.5×):                      $20.85  ← from Redis
  SET fare_estimate:{request_id} EX 300  (5-min TTL)

Step 2 — Ride Request:
  POST /v1/api/ride/request {request_id, pickup, drop, vehicle_type}
  Validate fare_estimate in Redis + payment method
  INSERT ride_requests (status: PENDING)
  SET ride_request:{request_id} EX 600  (10-min TTL — expires if no driver)
  Publish Kafka: ride.requested

Step 3 — Driver Accepts:
  BEGIN TRANSACTION
    INSERT INTO trips (status: MATCHED)
    UPDATE ride_requests SET status='MATCHED'
    UPDATE drivers SET current_trip_id
  COMMIT
  DELETE Zookeeper lock
  Notify rider via Kafka → Notification Svc
⚙️ LLD

Driver Location Storage — Redis GEOADD / GEORADIUS

Redis Geospatial Commands:

# Add / update driver position
GEOADD drivers:available {lon} {lat} {driver_id}

# Find nearest drivers within 5 km
GEORADIUS drivers:available -122.4194 37.7749 5km
          WITHDIST ASC COUNT 10
# → O(log N), ~10 ms for 1M entries

# Remove driver from available pool (assigned / offline)
GEOREM drivers:available {driver_id}

# Track last known position (separate key with TTL)
SET location:{driver_id} '{"lat":37.77,"lon":-122.41}' EX 60

Redis Key TTLs:
  drivers:available        → geospatial index (evicted on offline/busy)
  driver:{id}:status       → EX 300  (5 min, refreshed by 30 s heartbeat)
  location:{id}            → EX 60   (1 min, updated every 3–5 s)
  surge_multiplier:{hash}  → EX 120  (2 min)
  fare_estimate:{id}       → EX 300  (5 min)
  ride_request:{id}        → EX 600  (10 min)
Never trust Redis alone. Redis = speed. DB = truth. Always validate driver status in PostgreSQL before final assignment.
⚙️ LLD

Real-Time Push — WebSocket & Notifications

Rider app → WS /v1/trip/{trip_id}/track
  WebSocket Gateway SUBSCRIBE driver_location:{driver_id}  (Redis Pub/Sub)
  Forward to rider: {type: 'driver_location', lat, lon, eta_min}
  Rider app: smooth marker animation + ETA countdown

Architecture: Kafka events → Notification Svc → FCM / APN
  App FOREGROUND  → WebSocket (<100 ms, direct Redis Pub/Sub)
  App BACKGROUND  → FCM (Android) / APN (iOS)  (1–3 s)
  CRITICAL fails  → SMS fallback via Twilio

Push priorities + TTL:
  ride_matched        HIGH   10 min   driver_arrived    HIGH  5 min
  trip_started        HIGH   —        trip_completed    NORMAL —
  driver_ride_offered HIGH   30 sec   promotion         LOW   24 hr
WebSocket Scaling
  • 10K connections per instance
  • 200K connections = 20 instances
  • Sticky sessions via IP hash (not RR)
Failure Handling
  • Invalid token → mark inactive in DB
  • Retry: 1 s → 2 s → 4 s (3 retries)
  • DLQ → SMS via Twilio as last resort
⚙️ LLD

Payment Integration — Trip Completion

Driver taps "Complete Trip"
  POST /v1/api/ride/{trip_id}/complete
    ↓
Calculate final fare:
  actual_distance = from location history OR Google Maps
  total_time      = now() - start_time
  final_fare      = (base + distance×rate + time×rate) × surge_multiplier
    ↓
BEGIN TRANSACTION
  UPDATE trips SET status='COMPLETED', end_time, actual_fare, distance, duration
  UPDATE drivers SET status='AVAILABLE', current_trip_id=NULL
COMMIT
  GEOADD drivers:available {lon} {lat} {driver_id}  ← back in pool
    ↓
Stripe payment:
  POST to Payment Gateway (charge saved card / UPI / wallet)
  INSERT INTO payments (trip_id, amount, stripe_payment_id, status='COMPLETED')
    ↓
Publish Kafka: trip.completed
  → Analytics consumer (Flink/Spark → data warehouse)
  → Driver payout consumer (weekly settlement)
  → Receipt consumer → email/SMS fare breakdown
Payment schema: payment_method ENUM(card, wallet, cash, upi) · currency varchar(3) · stripe_payment_id · status ENUM(PENDING, COMPLETED, FAILED, REFUNDED)

📈 Scaling & Trade-offs

Geographic Sharding Strategy

Trips table — shard by geohash of pickup_location:
  Each shard handles a specific geographic area
  SF rider queries SF shard; NYC rider queries NYC shard
  Cross-region queries extremely rare (very low shard fan-out)
  → most queries stay local to rider's region

Drivers table — shard by driver_id HASH:
  Horizontal scaling with even distribution
  Driver lookups by ID go to single shard

Redis — per-region clusters:
  US-West | US-East | EU | APAC → own Redis geospatial instance
  Region determined by driver's last known location

Kafka partitioning:
  driver.location_updated → partition key = driver_id  (100 partitions)
  trip.* events           → partition key = trip_id

  Consumer groups:
    location-persistence  → writes location history to DB
    analytics             → aggregates real-time metrics
    notifications         → sends FCM / APN push
Why geohash sharding for trips? Geospatial locality = most joins and queries (driver ↔ rider ↔ trip) involve entities in the same small area. Keeps shard traffic local.

WebSocket Scaling

Redis Caching TTLs
  • Driver location: EX 60 s
  • Driver status: EX 300 s
  • Surge multiplier: EX 120 s

  • Trip details: EX 7200 s
Rate Limiting (API GW)
  • Riders: 10 ride requests / hour
  • Drivers: 1 status update / second
  • Location updates: 1 per 3 s per driver
  • CDN for media: 95% cache hit rate

🎯 Interview Prep

Senior Trap Q1 — 500K Drivers Sending Location Updates

"How do you handle driver location updates at 500K concurrent drivers?"
Scale:
  500K drivers × 1 update/5s = 100K location events / second

WebSocket Gateway Layer:
  Each WS server: 10K persistent connections
  500K drivers → 50 WebSocket gateway instances
  LB: IP-hash sticky sessions per driver
  Failover: driver app auto-reconnects (exponential backoff, 1–2 s)

Write path (Location Update Svc):
  1. GEOADD drivers:available {lon} {lat} {driver_id}  — Redis O(log N)
  2. SET location:{driver_id} EX 60                    — O(1)
  3. Kafka produce: driver.location_updated            — async, non-blocking
  4. PUBLISH driver_location:{id} to Redis Pub/Sub     — async

Kafka handles 100K events/sec:
  100 partitions, partitioned by driver_id
  Consumer groups: persistence | analytics | fraud detection

Bandwidth optimisations at source:
  Skip if moved < 10 m | Reduce to 1/10 s if speed < 5 km/h
  Protocol Buffers (50% smaller than JSON)
🎯 Interview Prep

Senior Trap Q2 — Matching Service Goes Down Mid-Ride

"What happens if the matching service crashes in the middle of a ride?"
Key insight: ride state is durable, not in-memory

Once MATCHED:
  Trip record committed to PostgreSQL (ACID) ✓
  Zookeeper lock already RELEASED after match ✓
  Driver status = BUSY in both Redis + DB ✓
  Rider has WebSocket to Location Update Svc (different service) ✓
  → Matching Svc crash has ZERO effect on in-progress trips

Matching Svc only required for: PENDING → MATCHED transition
  → Only NEW ride requests are affected by downtime

Recovery:
  Kubernetes auto-restarts Matching Svc pod (typically < 30 s)
  Kafka retains ride.requested events (7-day retention)
  On restart: consume backlog — pending requests retry automatically
  Zookeeper ephemeral locks auto-expired on session timeout (30 s)
  → no orphaned locks after restart

For riders waiting during outage:
  ride_request Redis key TTL = 600 s (10 min buffer)
  Matching retried on Svc recovery — rider sees "Searching for driver…"

Senior Trap Q3 — Preventing Surge Price Manipulation

"How do you prevent drivers from gaming the surge pricing system?"
Attack vectors:
  1. Driver clusters go offline to inflate demand_ratio → trigger surge
     then go back online to grab surge rides
  2. Fake GPS — driver location jumps (not physically moving)
  3. Collusion — driver + rider same person, farming bonuses

Defences:

1. Surge smoothing (already built-in):
   new_surge = 0.7×old + 0.3×new  — sudden offline spike takes multiple
   60-second cycles to move multiplier (3–4 min to reach cap)
   → too slow for rapid on/off manipulation to be profitable

2. Heartbeat continuity check:
   Rapid OFFLINE→ONLINE transitions flagged in analytics
   Pattern: driver offline <5 min in high-demand zone → ML flag

3. Fake GPS detection (fraud pipeline):
   Location jump > physically possible speed → flag
   Kafka: driver.location_updated → Flink → anomaly detector
   Flagged trips sent to manual review queue (DLQ)

4. Max cap = 3.0× (absolute ceiling — reduces incentive)

5. Collusion detection:
   ML model on historical patterns: same IP, same device family,
   suspiciously frequent shared trips, bonus farming patterns
