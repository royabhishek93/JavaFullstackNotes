The Core Design Challenge — CAP Duality

Two Services, Opposite CAP Needs

  • Market data (price feed) — 100M users reading prices → must be highly Available (AP)
  • Order placement / fund mgmt — wrong balance or duplicate trade = financial loss → must be Consistent (CP)
The interview insight: Deliver stock prices to millions in <50ms while guaranteeing no two orders overdraft the same account and no order is lost.

Rapid Answer Script (2–3 min)

  • Split into microservices with strict CAP boundary
  • Price path (AP): Price Ingester → InfluxDB + Redis PubSub → WebSocket → client ~20ms
  • Order path (CP): Order Svc → lock funds (SELECT FOR UPDATE) → Kafka → Validator → Exchange Gateway → NSE/BSE via FIX
  • State: PENDING → VERIFIED → PLACED → EXECUTED / REJECTED
  • Key insight: lock funds at PENDING, settle actual at EXECUTED

Flow: Exchange → Client (~20ms)

Exchange Gateway — FIX Protocol Deep Dive

Why FIX, Not REST?

  • FIX = Financial Information eXchange — binary TCP protocol
  • REST is HTTP (app layer). FIX is TCP (transport layer) → lower latency
  • NSE/BSE simply don't accept REST — industry standard
  • FIX tag-value pairs: Tag35=D = NewOrderSingle, Tag35=8 = ExecutionReport

Connection Pool

  • Maintain 400–500 persistent FIX connections to NSE/BSE
  • Grouped by symbol (RELIANCE, TCS, INFY on same connection)
  • Reuse connections — TCP handshake takes 3–5ms per order avoided
  • Load balance: distribute by symbol hash

FIX Message Format

Tag 35 = D NewOrderSingle Tag 55 = RELIANCE Symbol Tag 54 = 1 Side: Buy Tag 38 = 10 Quantity Tag 40 = 1 OrdType: Market Tag 11 = ORD123 ClOrdID Execution Report (response): Tag 35 = 8 ExecutionReport Tag 150 = 2 ExecType: Filled Tag 31 = 2459.00 LastPx (executed) Tag 32 = 10 LastQty

Order Matching Engine — Price-Time Priority

Price-Time Priority Algorithm

  • Primary sort: Price — best bid (highest BUY price) matches best ask (lowest SELL price)
  • Secondary sort: Time — earlier orders at same price matched first (FIFO)
  • Match when: best_bid_price ≥ best_ask_price

Order Book Structure

BUY side (BIDS) SELL side (ASKS) ───────────────── ───────────────── ₹2460 × 500 qty ₹2461 × 200 qty ← best ask ₹2459 × 1000 qty ₹2462 × 800 qty ₹2458 × 300 qty ₹2463 × 400 qty ↑ best bid MARKET BUY 10 → matches ₹2461 SELL immediately LIMIT BUY 10 @ 2459 → sits in book if price > 2459

Match Types

OrderBehavior

LIMITQueue in order book; execute only at specified price
STOP-LOSSDormant; activates as MARKET order when trigger price hit
IOCImmediate or Cancel — fill whatever possible, cancel rest
NSE's matching engine (NEAT) processes at 100K+ orders/second. Our Exchange Gateway maintains persistent FIX connections — NSE assigns exchange_order_id on acknowledgement.

Order Types — Market, Limit, Stop-Loss

MARKET Order

  • Execute immediately at best available price
  • price = NULL in orders table
  • Fund lock: estimated = qty × current_Redis_price + commission
  • Settlement: unlock estimated, deduct actual difference
BUY 10 RELIANCE at market → executes at ₹2459.00 (may differ from cached ₹2458.75)

LIMIT Order

  • Execute only at specified price or better
  • price = 3500.00 stored in orders table
  • SELL: lock shares (quantity -= 5, locked_quantity += 5)
  • BUY: lock funds at limit price estimate
SELL 5 TCS @ 3500 LIMIT → sits in exchange book → auto-cancel at 3:30 PM (GTC: stays open next day)

STOP-LOSS Order

  • Trigger price stored; dormant until hit
  • Activates as MARKET order when triggered
  • Order Tracker polls exchange every ~10s
  • Can bypass Kafka for time-sensitive execution
RELIANCE @ ₹2400 stop-loss → if price drops to 2400 → auto SELL at market price
Limit order end-of-day: NSE sends cancellation via FIX at 3:30 PM. Order Tracker updates status='CANCELLED'. Locked shares/funds auto-restored. Cron at 3:31 PM reconciles any stuck orders.

Market Data Feed — WebSocket Architecture

InfluxDB — Historical Charts

  • Measurement: stock_prices (symbol, exchange, price, volume)
  • 100K+ writes/sec — LSM tree append-only (no B-tree bottleneck)
  • Auto-downsampling: 1-min → 5-min → 1-hour → daily candles
  • 1-year chart query: <100ms

Redis PubSub — Live Prices

  • Price Ingester: PUBLISH stock_price '{symbol, price, change}'
  • WebSocket servers: SUBSCRIBE stock_price channel
  • Fan-out <10ms latency, no persistence, in-memory only
  • Client subscribes to only their watchlist symbols (10 stocks)

WebSocket Gateway Scaling

  • Auto-scale: >10K connections per server → spin up new instance
  • Sticky sessions: user_id hash → always same server
  • Consistent hash load balancer (preserves WebSocket state)
  • Each server: ~10K WebSocket connections

Fund Locking — Overdraft Prevention (SELECT FOR UPDATE)

SCENARIO: User has ₹50,000. Two simultaneous BUY orders: Order A: 20 RELIANCE × ₹2,459 = ₹49,180 Order B: 5 TCS × ₹3,500 = ₹17,500 Total required: ₹66,680 > ₹50,000 → would overdraft without locking ───────────────────────────────────────────────────────────────────── WITHOUT LOCKING (WRONG): Both check balance (₹50K ≥ both amounts independently), both pass, both execute → OVERDRAFT. ───────────────────────────────────────────────────────────────────── WITH SELECT FOR UPDATE (CORRECT): Order A: BEGIN TRANSACTION SELECT available_balance FROM funds WHERE user_id=X FOR UPDATE ← ROW LOCKED. Order B's SELECT FOR UPDATE WAITS. balance=₹50K ≥ ₹49,180 ✓ UPDATE funds SET available_balance -= 49180, locked_balance += 49180 COMMIT ← lock released Order B: ← now runs, reads post-commit balance = ₹820 ₹820 < ₹17,500 → ROLLBACK → 400 'Insufficient funds' ───────────────────────────────────────────────────────────────────── Isolation level: SERIALIZABLE ← prevents dirty + phantom reads Funds table layout: available_balance ← cash free for trading locked_balance ← cash locked in pending BUY orders total_balance ← computed: available + locked

Portfolio & Real-Time P&L — Never Store Current P&L

Why P&L is Never Stored

  • P&L = current_value − total_investment
  • current_price changes every second
  • If stored: must UPDATE portfolio rows 8-10K times/sec per user → billions of DB writes
  • Instead: store only quantity, avg_buy_price, total_investment
  • Compute P&L on every GET using Redis stock_price:{symbol}

Portfolio Table

PK: (user_id, stock_symbol) quantity INT ← available for selling locked_quantity INT ← locked in pending SELL avg_buy_price DECIMAL total_investment DECIMAL ← current_value: NEVER STORED ← profit_loss: NEVER STORED

P&L Calculation on GET

For each holding: current_price = Redis GET stock_price:RELIANCE → ₹2460.00 current_value = 10 × 2460.00 = ₹24,600 profit_loss = 24,600 − 24,590 = +₹10 (+0.04%) day_change = (2460 − prev_close 2455) / 2455 = +0.20% Aggregate: total_investment = ₹2,45,000 current_value = ₹2,48,500 total_P&L = +₹3,500 (+1.43%)
Redis fallback: If Redis down → fall back to InfluxDB / PostgreSQL stocks.current_price. P&L may be ~1s stale but correct. No financial risk (user is viewing, not trading).

Risk Management — 4-Stage Validation Pipeline (<50ms)

Stage 1 — Duplicate Prevention

Redis SETNX order_lock:{orderId} 1 EX 30 Returns 0 → duplicate, reject immediately Returns 1 → proceed (lock acquired for 30s)

Stage 2 — Fund/Exposure Check

SELECT SUM(quantity × price) FROM orders WHERE user_id={id} AND status IN ('PENDING','PLACED') IF total_exposure > 10 × available_balance → reject (over-leveraged)

Stage 3 — Circuit Breaker

IF stock_price moved >10% in last 5 min → reject ALL orders for this stock Prevents orders during extreme market events (e.g. circuit limit hit on BSE)

Stage 4 — Compliance

  • KYC status = VERIFIED (from image)
  • User not blocked/restricted for this stock
  • Insider trading checks (flagged securities)
  • SEBI regulatory limits
5 Validator instances × 50 Kafka partitions = horizontal scale. All 4 stages run in parallel where possible. Total <50ms.
⚙️ LLD

Settlement Flow — T+1 / T+2 & Fund Reconciliation

Execution vs Settlement

  • Trade execution — order matched at exchange (near real-time)
  • T+1 settlement — funds/shares transferred next business day (equity intraday)
  • T+2 settlement — delivery trades (SEBI mandate for equity delivery in India)
  • Platform credits shares/funds immediately in portfolio for UX; reconciles with depository (CDSL/NSDL) on T+1/T+2

Market vs Estimated Price Settlement

Estimated (at order placement): 10 × ₹2458.75 + ₹20 commission = ₹24,607.50 → locked_balance += 24607.50 Actual (at execution, price slipped): 10 × ₹2459.00 + ₹20 = ₹24,610.00 Difference: ₹2.50 extra UPDATE funds SET locked_balance -= 24607.50 ← unlock all available_balance -= 2.50 ← deduct difference

3 Parallel Post-Execution Consumers

  • Order Tracker Svc — UPDATE orders SET status=EXECUTED, INSERT into trades
  • Portfolio Svc — UPDATE quantity, weighted avg_buy_price
  • Notification Svc — Push (FCM/APNS) + WebSocket + Email

SELL Order Settlement

  • SELL executed → locked_quantity -= 5 (already deducted from available)
  • Funds: available_balance += (5 × 3500 − commission) = +₹17,480
  • If SELL cancelled: locked_quantity -= 5, quantity += 5 (restore shares)

Audit Trail — Immutable Event Log

Why Audit Trail Matters

  • SEBI mandates full trade audit for every order
  • Every state transition must be logged immutably
  • Dispute resolution: prove exact execution price and time
  • Insider trading detection: flag unusual patterns
  • Tax reporting: ITR-2 capital gains computation

Kafka as Audit Log

  • All order events published to Kafka (immutable append-only log)
  • Topics: new_orders, verified_orders, order_status, rejected_orders
  • Retention: 7 years (SEBI requirement)
  • Separate audit consumer → write to cold storage (S3/Glacier)

Trade Record (trades table)

CREATE TABLE trades ( trade_id UUID PRIMARY KEY, order_id UUID FK → orders, stock_symbol VARCHAR(20), trade_type ENUM(BUY, SELL), quantity INT, executed_price DECIMAL(10,2), ← actual exchange price executed_at TIMESTAMPTZ, exchange ENUM(NSE, BSE), commission_fee DECIMAL(8,2), exchange_trade_id VARCHAR(50) ← assigned by NSE/BSE );
Idempotency: exchange_trade_id is unique. Even if Kafka delivers order_status twice, INSERT INTO trades will fail on duplicate exchange_trade_id — guaranteeing at-most-once trade recording.

Scaling — NSE: 100K Orders/Sec, 10M+ Users

Database Sharding

  • Orders & Portfolio: sharded by user_id
  • All user's orders on same shard → fast user-scoped queries
  • 10 shards: each handles ~100K users (1M total)
  • Cross-shard queries: only for admin/analytics (acceptable slow)

Read Replicas

  • 1 master (writes: order execution, fund updates, trade inserts)
  • 5 read replicas (reads: portfolio, watchlist, order history)
  • 95% of traffic → replicas. Replication lag <1s (acceptable)

9. WS Auto-Scale

10. Price Cache

99% hit rate. Pre-warm top 100 stocks. Popular charts cached 5min TTL.

11. Rate Limiting

10 orders/sec per user. 100 req/sec per API. 100K orders/min global.

12. Async Notify

Kafka 'order_status' non-blocking. Retry + DLQ. <1s push notification.

Top Comparison 1 — LMAX Disruptor vs Apache Kafka

LMAX Disruptor

  • Lock-free ring buffer in memory (single JVM process)
  • Latency: ~25 nanoseconds per message
  • Used by: high-frequency trading (HFT) engines
  • No persistence — data lost on crash
  • Single producer / multiple consumer pattern
  • Throughput: 6M+ events/sec on single machine
Use when: ultra-low latency is paramount, all processing fits on one machine (HFT, prop trading)

Apache Kafka

  • Distributed, replicated, durable message log
  • Latency: 2–10ms per message (much higher)
  • Used by: Zerodha, most retail trading platforms
  • Persistence: configurable retention (7 years for audit)
  • Horizontal scale: add partitions + consumers
  • Throughput: 1M+ messages/sec across cluster
Use when: durability + audit trail matter, distributed teams, multiple consumers, scale > single machine

LMAX Disruptor is the choice for HFT engines running at nanosecond latency where persistence is handled separately."

Q1 — "How do you prevent overdraft with simultaneous orders?"

"Fund locking with SELECT FOR UPDATE + SERIALIZABLE isolation. User has ₹50K. Two simultaneous BUY orders of ₹49,180 and ₹17,500. Without locking, both read ₹50K, both pass, overdraft. With SELECT FOR UPDATE, Order A locks the row. Order B waits. A commits, balance = ₹820. B reads ₹820 < ₹17,500 → ROLLBACK → 400 Insufficient funds."

Pessimistic vs Optimistic

  • Pessimistic (SELECT FOR UPDATE): Use for funds — high contention, correctness critical, row-level lock
  • Optimistic (version column): Use for portfolio updates — lower contention, retries acceptable

Why SERIALIZABLE?

  • Prevents dirty reads (no read of uncommitted data)
  • Prevents non-repeatable reads (stable within transaction)
  • Prevents phantom reads (no new rows appear mid-transaction)
  • Highest isolation = fully serial execution guarantee

Q2 — "Market order estimated ₹2458.75 but executes at ₹2459.00. How?"

"Two-step fund settlement. Lock estimated cost at placement. Settle actual cost at execution. Deduct only the difference."
STEP 1 — At order placement: Estimated: 10 × ₹2458.75 + ₹20 commission = ₹24,607.50 UPDATE funds SET available_balance -= 24607.50 locked_balance += 24607.50 STEP 2 — At execution (exchange confirms ₹2459.00): Actual: 10 × ₹2459.00 + ₹20 = ₹24,610.00 Difference: ₹2.50 more UPDATE funds SET locked_balance -= 24607.50 ← unlock full estimated amount available_balance -= 2.50 ← deduct only the difference If price IMPROVED (executed at ₹2458.50): Actual: 10 × ₹2458.50 + ₹20 = ₹24,605.00 UPDATE funds SET locked_balance -= 24607.50 ← unlock estimated available_balance += 2.50 ← REFUND the improvement This handles: price slippage, price improvement, and exact match uniformly.

Q3 — "What is FIX protocol? Why not REST to send orders to NSE?"

"FIX (Financial Information eXchange) is a binary TCP protocol for order routing. Every major exchange globally uses it. REST is HTTP (application layer). FIX is TCP (transport layer) — lower latency, no HTTP overhead, persistent connections."

REST Problems for Exchange

  • New TCP connection per request (or HTTP keep-alive, still heavier)
  • HTTP headers add ~500 bytes overhead per message
  • JSON serialization latency vs binary FIX tags
  • NSE/BSE simply do not accept REST — industry standard

FIX Advantages

  • Persistent TCP connection — no handshake overhead per order
  • Binary tag-value pairs: Tag35=D (place), Tag35=8 (execution report)
  • 400–500 connections pooled by symbol — all RELIANCE orders on same conn
  • TCP handshake saved: 3–5ms per order, 100K orders/min = significant

Q4 — "Why not store P&L? What if Redis goes down?"

"P&L = current_value − total_investment = quantity × current_price − quantity × avg_buy_price. current_price changes every second. Storing P&L means updating portfolio for every user × every stock × every second = billions of DB writes/second. Not feasible. Also instantly stale between writes."

What IS Stored

  • quantity — how many shares owned
  • avg_buy_price — weighted average cost
  • total_investment — quantity × avg_buy_price
  • prev_close — for day change % (stocks table)

Redis Failure Fallback

  • Primary: Redis GET stock_price:{symbol} (TTL 1s)
  • Fallback 1: InfluxDB — latest price from time-series
  • Fallback 2: PostgreSQL stocks.current_price — slightly stale
  • P&L may be ~1s stale — acceptable (user viewing, not trading)
  • Redis is clustered (Redis Sentinel / Redis Cluster) — rare failures

Q5 — "How do you handle a LIMIT order that never executes?"

"Three outcomes: executes (normal flow), day-order expires (NSE cancellation FIX at 3:30 PM → restore funds/shares), or GTC (Good Till Cancelled — stays in exchange book across days)."

Day-Order Expiry (3:30 PM IST)

  1. NSE sends FIX cancellation notification
  2. Exchange Gateway → Kafka 'order_status' status='CANCELLED'
  3. Order Tracker: UPDATE orders SET status='CANCELLED'
  4. Portfolio Svc: locked_quantity -= 5, quantity += 5 (SELL)
  5. Funds Svc: locked_balance -= estimated, available += estimated (BUY)

Reconciliation Cron (3:31 PM)

SELECT * FROM orders WHERE status IN ('PENDING','PLACED') AND placed_at < today_market_close For each: verify with exchange → still open? keep as PLACED → cancelled/filled? reconcile
This catches any Kafka event that was dropped or delayed. Belt-and-suspenders approach for financial reconciliation.
