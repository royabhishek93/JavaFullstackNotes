📁 Upload & Sync

Chunking Strategy — Why 5 MB Chunks?

File: vacation.mp4  (500 MB)
  ↓
Client Chunker splits into N × 5 MB chunks:
  chunk_0  [0–5 MB]     SHA-256 → a3f1...
  chunk_1  [5–10 MB]    SHA-256 → b92c...
  chunk_2  [10–15 MB]   SHA-256 → a3f1...  ← same hash as chunk_0!
  ...
  chunk_99 [495–500 MB] SHA-256 → c44e...
Why chunks?
  • Parallel upload: 3 chunks simultaneously
  • Resumable: only re-upload failed chunks
  • Dedup at chunk level (not file level)
  • Delta sync: re-upload only changed chunks
Why 5 MB chunk size?
  • Matches S3 multipart minimum (5 MB)
  • Balance: too small = many requests; too large = expensive retries
  • Good dedup granularity for large media files
  • ~100 chunks per 500 MB file — manageable metadata
Client components: Watcher (detects changes) → Chunker (splits + hashes) → Upload Manager (parallel, 3 at a time, retries) → Sync Engine (push/pull)
📁 Upload & Sync

Content-Based Deduplication — SHA-256 per Chunk

Dedup Svc receives: { uploadId, chunkIndex, chunkHash: "a3f1..." }

SELECT * FROM Chunks WHERE checksum = 'a3f1...'

FOUND  → return existing object_key (s3://bucket/chunks/a3f1...)
         client SKIPS upload — chunk already in S3
NOT FOUND → generate pre-signed PUT URL → client uploads to S3
             INSERT Chunks (chunk_id, object_key, checksum, size_bytes)
Storage savings example: 
File A (20 MB):  4 shared chunks + 1 new chunk
File B (17 MB):  all 4 chunks already in S3 (hash match)
                 → File B stored at near-zero additional cost

Two users upload the same 1 GB video:
  First upload: 1 GB written to S3
  Second upload: 0 bytes written (all chunk hashes match)
  → 100% dedup savings
Interview tip: The Chunks table IS the dedup key. Two FileVersions can share the same chunk_id — they point to the same S3 blob. No data duplication at the object level.

Delta Sync — Only Changed Chunks Uploaded on Edit

User edits report.docx (50 MB file, 10 chunks of 5 MB each):
  Only paragraph 2 changed → affects chunk_3

Old version: [c0, c1, c2, c3_old, c4, c5, c6, c7, c8, c9]
New version: [c0, c1, c2, c3_new, c4, c5, c6, c7, c8, c9]
                               ↑
                         only this chunk differs
Client-side delta detection
  • Watcher detects file modified
  • Chunker re-splits and re-hashes all chunks
  • Compares new hash array vs Local Metadata Index
  • Only chunk_3 hash changed → upload only chunk_3
Server-side delta (on commit)
  • New FileVersion row created
  • New FileVersionChunks: 9 rows reuse old chunk_ids
  • 1 new chunk_id for chunk_3_new
  • Old chunks remain in S3 (versioning intact)
Bandwidth saved: 50 MB file edit → only 5 MB uploaded (1 chunk). Without delta sync: 50 MB re-upload every edit.
📁 Upload & Sync

Upload Flow — Step-by-Step (LLD)

Step 1 — Initiate
  POST /files/upload/init  { fileName, fileSize, parentFolderId }
  Response: { fileId, uploadId, chunkSize: 5MB, existingChunks: [] }
  Server creates upload session in Redis (chunk bitmap, retry count)

Step 2 — Chunk & Hash (client-side)
  Chunker splits file into N chunks (5 MB each)
  Computes SHA-256 per chunk → hash array [h0, h1, h2 ... hN]

Step 3 — Get Pre-signed URL per chunk
  POST /upload/chunk-url  { uploadId, chunkIndex, chunkHash }
  Uploader Svc: validate uploadId + permission
    → Dedup Svc: hash already in S3? YES → skip / NO → issue signed URL
  Response: { signedUrl: "https://s3.amazonaws.com/..." } OR { skip: true }

Step 4 — Upload chunks in parallel (3 at a time)
  Client PUT each chunk directly to S3 via pre-signed URL
  Resume: re-call init with resumeUploadId → server returns existingChunks bitmap

Step 5 — Commit
  POST /uploads/{uploadId}/commit
  Uploader Svc: creates FileVersion + FileVersionChunks records in MetaDB

Step 6 — Emit Sync Event
  Uploader Svc → Kafka (change event: fileId, versionId, ownerId)
  Sync Svc consumes → fanout to all connected devices
📁 Upload & Sync

Download & Sync Flow

Download Flow:
  GET /files/{fileId}/download
  Read Svc fetches current_version_id from MetaDB
  Looks up FileVersionChunks → ordered list of chunk object_keys
  Generates signed S3 GET URLs (TTL 15 min) per chunk
  Client downloads chunks in parallel → reassembles in order → file

Sync Flow (cross-device):
  Device A uploads → Kafka event published
  Sync Svc consumes → checks which other devices own this file
    Push path (active sessions):  WebSocket / SSE → notify Device B
    Pull path (device was offline): Device B polls /sync/changes?since=<timestamp>
        → returns list of changed fileIds + new versionIds
  Device B: for each changed file → diff local chunks vs new version chunks
      → download only missing/changed chunks
      → reassemble → update local file
CDN acceleration
  • Frequently accessed files served from CDN edge
  • Read Svc issues CDN-signed URL if file is cacheable
  • Cache key = object_key (immutable chunks)
Bandwidth optimisation
  • Chunks are content-addressed → immutable
  • CDN hit rate very high for popular shared files
  • Parallel chunk download → max throughput
🔄 Metadata & Conflicts

Metadata Service — File Tree, Directory Structure, Versioning

File Metadata Svc owns: File · Folder · FileVersion · Chunk · Permission

Directory tree (self-referential Folder table):
  Folder: folder_id | parent_folder_id (NULL = root) | owner_id | name

File record:
  File: file_id | parent_folder_id (FK) | owner_id | name
        current_version_id | created_at | is_deleted

Versioning: every commit creates a new FileVersion row
  FileVersions: version_id | file_id | size_bytes | created_at
  FileVersionChunks (join): version_id | chunk_index | chunk_id
  → current_version_id on File points to latest
  → previous versions retained until retention policy cleanup

List folder contents (breadcrumb):
  SELECT * FROM Files  WHERE parent_folder_id = :folderId AND is_deleted = false
  SELECT * FROM Folders WHERE parent_folder_id = :folderId

Restore version:
  UPDATE Files SET current_version_id = :oldVersionId WHERE file_id = :fileId
  → no chunk copying needed — just pointer swap
Strong consistency required: File names, current_version_id, and permissions must be immediately consistent. Use PostgreSQL with read replicas for scale.
🔄 Metadata & Conflicts

Conflict Resolution Strategies

Last-Write-Wins (LWW)
  • Server uses commit timestamp to determine winner
  • Simpler; no user intervention needed
  • Good for binary files (images, videos, PDFs)
  • Risk: silent data loss if two edits collide
  • Dropbox default for binary files
Conflict Copy / Manual Merge
  • Both versions kept; user prompted to resolve
  • Conflict file named "report (Conflicted copy).docx"
  • Better for text/document files
  • Google Docs: OT (Operational Transform) for real-time co-edit
Conflict detection:
  Client sends: { fileId, basedOnVersionId: "v5" }
  Server checks: current_version_id == "v5" ?
    YES → clean merge, apply update, create v6
    NO  → conflict! current = v7 (someone else edited)
          → LWW: overwrite with new version
          → Merge: create conflict copy, notify both users
Interview tip: Mention OT (Operational Transform) or CRDT for collaborative editing (Google Docs), but LWW + conflict copy for basic file sync (Dropbox model).

Access Control — Owner / Editor / Viewer, Shared Links

Permissions table:
  permission_id | resource_type (file|folder) | resource_id
  userId | role ENUM(owner, editor, viewer) | created_at

Permission inheritance:
  Folder permission cascades to all children
  File-level permission overrides folder permission if more restrictive

Share a file:
  POST /api/v1/files/{fileId}/share
  Body: { userId: "u456", role: "editor" }
  INSERT INTO Permissions (resource_type:'file', resource_id: fileId, userId, role)

Public shared link (viewer, no auth):
  POST /api/v1/files/{fileId}/share-link
  Response: { shareToken: "xK9aQ...", url: "https://drive.example.com/share/xK9aQ" }
  Tokens stored hashed in DB; TTL optional

Permission check (on every request):
  Metadata Svc middleware checks: does userId have >= required_role on resource?
  Folder: check resource_id + all parent_folder_ids (walk up tree)
Quota enforcement: On upload init, Validator Svc checks user's consumed quota vs limit. Quota includes all versions, not just current. Stored in User DB and updated on commit.

🗄 DB Schema

Database Schema — Quick Reference

-- Core file entity
Files: file_id uuid PK | parent_folder_id uuid FK | owner_id uuid FK
       name varchar(255) | size_bytes bigint | current_version_id uuid FK
       created_at timestamp | is_deleted boolean | metadata jsonb
INDEX (parent_folder_id, is_deleted)  -- folder listing
INDEX (owner_id, created_at)          -- user's files

-- Version tracking (immutable, append-only)
FileVersions: version_id uuid PK | file_id uuid FK | size_bytes bigint | created_at timestamp

-- Chunk map per version (join table)
FileVersionChunks: version_id uuid FK | chunk_index int | chunk_id uuid FK
PRIMARY KEY (version_id, chunk_index)

-- Dedup table (heart of the system)
Chunks: chunk_id uuid PK | object_key varchar(512)  -- s3://bucket/path
        size_bytes int | checksum varchar(64) | created_at timestamp
UNIQUE INDEX (checksum)  -- dedup lookup by hash

-- Sharing / permissions
Permissions: permission_id uuid PK | resource_type varchar(10)
             resource_id uuid | userId uuid FK
             role ENUM(owner, editor, viewer) | created_at timestamp
INDEX (resource_id, resource_type)  -- check access for a resource
Redis (upload session state): chunk bitmap (which chunks done), retry count, temp upload metadata — TTL-based, avoids polluting MetaDB.
📈 Scaling

Scaling — Google Drive: 2B File Operations / Day

Back-of-envelope:
  2B ops/day  = ~23,000 ops/sec (average)
  Peak 3×     = ~70,000 ops/sec
  Avg file    = 1 MB → 2 PB/day new data (theoretical max)
  With dedup  = 70–80% reduction → ~400 TB/day net new storage

Metadata Svc scaling:
  PostgreSQL primary + read replicas (most ops are reads)
  Connection pooling via PgBouncer
  Shard MetaDB by owner_id hash (user's data stays on one shard)

S3 / Blob Store scaling:
  S3 natively scales to unlimited objects
  Multi-AZ replication for durability (11 nines)
  Lifecycle policies: move old versions to S3 Glacier (cold tier)

Kafka scaling:
  100 partitions for file change events (partitioned by file_id)
  Sync Svc consumers: scale horizontally per partition

CDN:
  Cloudfront / Akamai for read-heavy popular files
  Immutable chunks → perfect CDN fit (never stale)
  Cache-Control: max-age=31536000 (1 year) per chunk
Hotspot prevention: Viral shared files flood one S3 prefix. S3 auto-partitions by key prefix — use random prefix or hash-based object_keys, not sequential names.

Senior Trap Q1 — Why Pre-signed URLs Instead of Proxying Uploads?

"Why not just upload file chunks to your backend and have the backend write to S3?"
Problem with proxying:
  500 MB file upload at 10 MB/s = 50 seconds of backend server holding the connection
  10K concurrent uploads × 500 MB = 5 TB of data flowing through backend
  Backend becomes bandwidth bottleneck; cost × 2 (upload + forward to S3)
  Each server tied up for duration of upload — poor concurrency

Pre-signed URL approach:
  Backend issues short-lived URL (TTL 15 min): POST /upload/chunk-url
    → signs S3 URL with backend credentials (< 1 ms)
  Client uploads DIRECTLY to S3 — backend never touches the bytes
  Backend only handles:
    - Upload init (lightweight DB write)
    - Chunk-URL issuance (crypto operation)
    - Commit (DB write)
  S3 handles: all bandwidth, buffering, retries, multipart assembly

Cost impact at scale (Google Drive):
  2B chunks/day × avg 5 MB = 10 PB/day bandwidth
  Through backend: ~$100K+/day in egress
  Direct to S3:    $0 ingress to S3 within AWS region
Rule of thumb: Never proxy large binary uploads. Issue signed URLs and let the client talk directly to object storage.

Senior Trap Q2 — How Exactly Does Resumable Upload Work?

"Walk me through exactly what happens when a user's connection drops mid-upload and they reconnect."
Upload in progress:
  uploadId: "upload_123"
  File: 500 MB → 100 chunks (5 MB each)
  Chunks uploaded so far: 1–43 (stored as bitmap in Redis)
  Redis: "upload_session:upload_123" → { chunkBitmap: [1..43], fileId, ... } EX 86400

Connection drops mid chunk_44 upload.

On reconnect — client calls:
  POST /files/upload/init
  Body: { fileName: "vacation.mp4", fileSize: 524288000, resumeUploadId: "upload_123" }

Server:
  1. Looks up Redis: upload_session:upload_123
  2. Finds chunkBitmap: [1..43] completed
  3. Returns: { uploadId: "upload_123", existingChunks: [1,2,...,43] }

Client:
  Skips chunks 1–43
  Resumes from chunk_44

What if Redis session expired (after 24h)?
  Server returns: { existingChunks: [] }  ← treat as fresh upload
  S3: Dedup Svc will catch duplicate chunks anyway (hash match → skip upload)
  Net result: slightly more re-hashing client-side, but no duplicate storage

Senior Trap Q3 — Two Devices Edit the Same File Simultaneously

"User edits report.docx on both laptop and phone at the same time. What happens?"
Both devices started from version v5:

Laptop uploads first → commits → creates v6
  File.current_version_id = "v6"

Phone tries to commit (still based on v5):
  POST /uploads/{uploadId}/commit
  Body: { fileId, basedOnVersionId: "v5" }

Server detects conflict:
  SELECT current_version_id FROM Files WHERE file_id = :fileId
  → "v6" ≠ "v5"  ← CONFLICT!

Resolution strategies:
  Option A — Last-Write-Wins:
    Phone's upload overwrites v6 → becomes v7
    Laptop's v6 retained in FileVersions (can be restored)
    Silent overwrite — Dropbox default for binary files

  Option B — Conflict Copy:
    Phone's version saved as "report (Phone's conflicted copy 2026-08-30).docx"
    Both v6 (laptop) and v7 (phone) exist as separate files
    User resolves manually → Google Drive / Dropbox model for text files

  Option C — OT/CRDT (Google Docs):
    Real-time co-editing with Operational Transform
    Changes merged at character level — no conflict file
    Requires stateful server; much higher complexity
Interview tip: Start with LWW + conflict copy (Dropbox model). Mention OT only when asked about real-time collaboration.

🎯 Interview Prep

More Interview Q&As

Q: Why Redis for upload session state, not the MetaDB?
Fast TTL-based storage for chunk bitmap and retry count. Transient data — avoid polluting the main MetaDB. TTL auto-cleans abandoned uploads.
Q: How does versioning work under the hood?
Each commit creates a new FileVersion row + FileVersionChunks rows (9 reused, 1 new for delta). current_version_id on File points to latest. Restore = pointer swap in one UPDATE. Old chunks retained in S3 until retention cleanup.
Q: How do you handle quota?
User quota tracked in User DB. Validator Svc checks fileSize against remainingQuota on upload init AND at commit. Quota includes all versions (not just current). Hard stop returns HTTP 507 (Insufficient Storage).
Q: What does Kafka do here?
After commit, Uploader Svc publishes a change event to Kafka. Sync Svc subscribes and fans out to all connected devices. Decouples upload flow from sync — upload doesn't block waiting for sync propagation.
Q: Why eventual consistency for sync but strong for metadata?
Metadata (name, version, permissions) must be immediately consistent to prevent conflicts. Cross-device sync can tolerate a 1–2 second delay — user expectation is near-real-time, not instant.

Closing — Interview Wrap-Up

🔪
Chunking: 5 MB chunks enable parallel upload (3×), resumable uploads, chunk-level dedup, and delta sync in one design decision
🔑
Deduplication: SHA-256 hash per chunk → Chunks table is the dedup key. Two files sharing the same blob pay zero extra storage cost
⚡
Pre-signed URLs: Client uploads directly to S3 — backend never touches bytes, saving ~100K+/day in bandwidth at Google scale
🔄
Delta sync: Edit 1 chunk in a 500 MB file → upload 5 MB, not 500 MB. Metadata versioning is a pointer swap — no chunk copying
📊
Dual consistency: Strong for metadata (PostgreSQL ACID), eventual for sync (Kafka fanout). Explicit, justified CAP trade-off
🏗
Kafka backbone: Decouples upload from sync propagation — Uploader Svc publishes, Sync Svc fans out to all devices asynchronously
Closing line: "The key insight is treating the Chunks table as the single source of truth for dedup — two files sharing the same SHA-256 hash never store duplicate bytes. Combine that with delta sync and pre-signed URLs, and you get a system that stores petabytes efficiently and uploads at near-S3 raw speed."
