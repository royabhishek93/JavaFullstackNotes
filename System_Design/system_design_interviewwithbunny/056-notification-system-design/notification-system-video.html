HLD — Every Service and Its Role

API Gateway & Load Balancer

  • JWT / API key authentication
  • Rate limiting: 100 req/min per client
  • Route to Notification Svc
  • Round-robin across Notification Svc instances

Template Service

  • CRUD on templates → Template DB (Postgres)
  • Immutable versioning (new version on update)
  • Redis cache: template:{id}:{v} TTL 1h — 95% hit rate

User Preference Service

  • CRUD on preferences → UserPref DB
  • Redis cache: user_pref:{userId} TTL 24h
  • On update: publishes to user.preference Kafka topic
  • User Pref Consumer invalidates Redis cache

Notification Service (Core Orchestrator)

  • Validates template + user preferences
  • Renders template (fills {{variables}})
  • Writes Notifications + Outbox atomically
  • CDC Publisher polls outbox → Kafka

Delivery Consumers (Dlvy Cons)

  • Email consumers: 20 instances (critical:10, std:20, promo:5)
  • SMS consumers: 15 instances
  • Push consumers: 10 instances
  • Idempotency check + rate limit + provider call

Reporting Service

  • Real-time: Redis counters INCR sent_count:{date}
  • Batch: Hourly Spark/Flink aggregation
  • Stored in InfluxDB / BigQuery for dashboards
  • Metrics: delivery %, open rate, click rate, bounce rate

Templates change rarely. Redis cache with 1h TTL achieves 95% hit rate. Only 5% of requests hit the DB. At 1M notif/min, this saves 950K DB queries/min.

Preference Check is Mandatory

  • channels.sms = false → never send SMS
  • types.promotional = false → skip all marketing
  • do_not_disturb = true → skip ALL channels
  • Legal: GDPR, CAN-SPAM, TCPA compliance

LLD Step 2 — Transactional Outbox Pattern

The Problem Without Outbox

Naive approach (BROKEN): 1. INSERT notifications (status=PENDING) ✅ 2. Kafka.publish("NOTIF789") ← CRASH 💥 Result: DB has NOTIF789 as PENDING Kafka never got it CDC/Publisher never finds it Alice NEVER gets her email Zero error logged. Silent loss. 😱 Also broken the other way: 1. Kafka.publish("NOTIF789") ✅ 2. INSERT notifications ← CRASH 💥 Kafka fires. Consumer tries to process. notification_id not in DB → error/lost

The Fix — One Atomic Transaction

BEGIN TRANSACTION; INSERT INTO notifications ( notification_id: 'NOTIF789', user_id: 'user123', template_id: 'order_confirmation', channel: 'EMAIL', payload: {subject, body, to:'alice@...'}, status: 'PENDING', priority: 'high', created_at: now() ); INSERT INTO notifications_outbox ( outbox_id: uuid_generate_v4(), notification_id: 'NOTIF789', event_type: 'notification.created', payload: {notification_id, channel, priority}, published: false, ← CDC watches this created_at: now() ); COMMIT; ← Both succeed OR both fail — atomically CDC Publisher (polls every 100ms): SELECT * FROM outbox WHERE published=false LIMIT 1000 ORDER BY created_at; → Kafka.send(topic, key:notification_id) → UPDATE outbox SET published=true If Kafka fails: stays false, retried next poll
💡 Interview must-say: "If DB COMMIT succeeded, the message is in the outbox. CDC Publisher will EVENTUALLY publish it to Kafka — retrying until success. This guarantees at-least-once delivery even across service crashes, network failures, or Kafka restarts."

Why Separate Topics Matter

LLD Step 4 — Consumer Processing Pipeline

Consumer subscribes to notifications.standard.email Receives message: { notification_id: "NOTIF789", channel: "EMAIL", payload: { subject: "Order ORD456 confirmed", body: "Hi Alice...", to: "alice@example.com" }, priority: "high" } Step 1 — Idempotency check: SELECT COUNT(*) FROM delivery_status WHERE notification_id='NOTIF789' AND channel='EMAIL' → 0 rows → proceed (first time) → 1 row → SKIP (already sent, Kafka duplicate) Why needed? LLD Step 7 — Retry Mechanism + Exponential Backoff + DLQ

Temporary failures → RETRY: Provider timeout (no response in 10s) HTTP 429 Too Many Requests HTTP 5xx Server Error Network connection refused Exponential backoff: Attempt 1 fails → Publish to notifications.retry {notification_id, retry_count:1, scheduled_at: now()+1min} Attempt 2 fails (1 min later) → retry_count: 2 scheduled_at: now()+5min Attempt 3 fails (5 min later) → retry_count: 3 scheduled_at: now()+15min Attempt 4 fails (15 min later) → retry_count >= 3 → MOVE TO DLQ Permanent failures → NO RETRY: Email bounced (550 User not found) Invalid phone number User unsubscribed (honor preference) APNS 410 Gone (app uninstalled) → UPDATE delivery_status SET status='FAILED', error_message='Invalid email address' Dead Letter Queue (DLQ): notifications.dlq Kafka topic Ops team alerted via PagerDuty Manual investigation → root cause Fixed? → replay from DLQ

Why Exponential Backoff?

If Twilio is overloaded (HTTP 429):

  • Retry every 1s → makes overload WORSE
  • Wait 1m, 5m, 15m → gives Twilio time to recover
  • Spreads retry load over time
  • Industry standard across all distributed systems

CREATE TABLE notifications_outbox ( outbox_id UUID PRIMARY KEY, notification_id UUID NOT NULL REFERENCES notifications(notification_id), event_type VARCHAR(50), -- e.g. 'notification.created' payload JSONB, -- {notification_id, channel, priority} published BOOLEAN DEFAULT FALSE, -- CDC Publisher polls WHERE published=false published_at TIMESTAMPTZ, created_at TIMESTAMPTZ DEFAULT now() ); -- CDC Publisher query (every 100ms): SELECT * FROM notifications_outbox WHERE published = false ORDER BY created_at ASC LIMIT 1000; -- After Kafka publish succeeds: UPDATE notifications_outbox SET published = true, published_at = now() WHERE outbox_id = $1;
Outbox + Notifications in one transaction = the foundation of at-least-once delivery. If Postgres commits, the outbox row exists forever until CDC publishes it.

Scheduled Notifications & Async Webhook Processing

⏰ Scheduled Notifications — How it Works

POST /api/v1/notifications { templateId: "black_friday_promo", scheduledAt: "2026-11-29T09:00:00Z" ← future time } → status: SCHEDULED, saved to DB Scheduler job (cron, runs every 1 minute): SELECT * FROM notifications WHERE status = 'SCHEDULED' AND scheduled_at <= now() LIMIT 10000 → publish to Kafka (normal flow) → UPDATE status = 'PENDING' Index: (status, scheduled_at) Makes this fast even at 1M+ rows. Without index: full table scan = slow.

WHY scheduled → PENDING (not direct to SENT)?

When the scheduler fires, it re-enters the normal Kafka pipeline. This means: preference checks still happen at delivery time, not at scheduling time. If a user opted out between scheduling and delivery — we catch it. Scheduling is just a delayed trigger, not a bypass.

🎯 Interview Prep

⭐ Q1 — "How do you ensure no notification is lost?"

Interviewers ALWAYS ask this. Your answer must cover all 5 points below.

1. The Problem (dual-write failure)

Naive: write DB then publish to Kafka. If Kafka fails after DB commit → notification stuck. If DB fails after Kafka publish → notification lost. Either way: silent failure.

2. Outbox Pattern (single transaction)

INSERT notifications + INSERT outbox in ONE transaction. Either both commit or both rollback. No inconsistency possible.

3. CDC Publisher (at-least-once to Kafka)

Polls outbox WHERE published=false every 100ms. Publishes to Kafka. Marks published=true. If CDC crashes after Kafka success but before mark: same message published twice on restart → idempotency handles it.

4. Idempotent Consumers (prevent duplicates)

Consumer checks: SELECT COUNT(*) FROM delivery_status WHERE notification_id + channel. If exists → already sent → skip. Kafka at-least-once may deliver same message twice; idempotency prevents double emails.

5. Result: Effectively Exactly-Once

At-least-once delivery (Outbox + CDC) + Idempotent consumers = exactly-once to the user. Message never lost. Message never duplicated.

How to say it: "We use the Transactional Outbox pattern — DB write and outbox row in one atomic transaction. CDC Publisher polls outbox to Kafka. Idempotent consumers prevent duplicates. This gives us at-least-once delivery with no silent losses, combined with idempotency for exactly-once semantics from the user's perspective."

WHY This Architecture? — Scenario-First Explanations

WHY not call SendGrid directly from Order Service?

"If Order Service calls SendGrid directly:"

  • If SendGrid is down → the order itself fails. Notification failure kills the core transaction.
  • If Order Service crashes mid-send → did the email go? You don't know.
  • 100K orders/min hits SendGrid's rate limit → emails drop silently.
  • Can't prioritize OTP over newsletter — same code path.

"Kafka decouples the concerns. Order Service fires-and-forgets. Delivery is now independent, scalable, and observable."

WHY dedicated Notification Platform vs per-team integration?

  • Single compliance layer — GDPR opt-outs, CAN-SPAM, TCPA enforced in one place, not 50 teams
  • Single rate limiter — if 5 teams each have their own SendGrid integration, you'll hit rate limits 5x faster
  • Single retry logic — don't reimplement exponential backoff in every service
  • Single observability — one dashboard for all notification delivery rates

WHY Kafka and not a simple DB queue?

  • Replay: if Email Consumer had a bug, rewind to last hour. DB queue deletes on read — no replay.
  • Scale: 100 partitions = 100 parallel consumers. DB queues struggle above 10K/sec.
  • Priority lanes: separate topics per priority. A DB queue is FIFO — no priority isolation.
  • Retention: 7-day message retention. If consumers are down 6 hours, messages wait safely.

WHY Outbox Pattern and not just "write DB then Kafka"?

Naive dual-write window of failure: ① DB write succeeds ② App crashes before Kafka publish ③ Notification stuck PENDING forever ④ User never gets their password reset email ⑤ Zero error logged. Silent loss. 😱 Outbox closes this window: ① DB write + outbox row = ONE transaction ② Either both commit or neither does ③ CDC polls outbox until Kafka confirmed ④ No crash can lose a committed message

Technology Choice — Kafka vs RabbitMQ

Kafka

  • Log-based, durable retention (configurable, default 7 days)
  • Replay — rewind consumer offset on failure or bug fix
  • 100 partitions = 100 parallel consumers max
  • Pull-based consumers (consumer controls pace)
  • 1M+ msgs/sec per broker cluster
  • Priority via separate topics
  • High operational complexity
Pick Kafka when: scale >100K/day, replay is needed, priority isolation required, or long message retention is needed.

Realistic Example 1 — Kafka

Zomato sends 2M order notifications on Sunday evening. SMS Consumer crashes at 8PM due to a Twilio API change. After fix + deploy, consumer rewinds to its last committed offset and replays the missed 40 minutes of messages. No data lost. With RabbitMQ, those messages would have been ACK'd and deleted on first delivery attempt.

RabbitMQ

  • Queue-based — messages deleted on ACK
  • No native replay (once ACK'd, gone)
  • Push-based consumers (broker pushes messages)
  • Flexible exchange types: direct, topic, fanout, headers
  • Built-in per-message TTL and DLQ
  • ~50K msgs/sec per queue
  • Lower ops complexity, excellent UI
Pick RabbitMQ when: complex per-message routing rules, small team, <100K/day volume, or you need per-message TTL out of the box.

Realistic Example 2 — RabbitMQ

An internal HR SaaS sends 5,000 monthly payslip notifications. Topic exchange routes by department. Dead letter queues catch failures. Ops team manages via the RabbitMQ management UI. Volume never exceeds 1K/day. No need for Kafka's operational complexity — RabbitMQ is operationally simpler and fits perfectly here.

🪤 Senior Trap Q2 — "User unsubscribes at 9am. Gets promotional email at 9:01am. How do you fix this?"

This tests cache consistency knowledge. Most candidates either over-engineer it (add DB read to every send) or miss it entirely.

The Root Cause

Timeline: 09:00:00 — User hits PUT /preferences → email=false 09:00:00 — DB updated: email=false ✅ 09:00:00 — But Redis cache NOT invalidated 😱 09:00:00 — Redis: user_pref:user123 still has email=true TTL remaining: 23h 59m 09:01:00 — Black Friday campaign fires 09:01:00 — Notification Svc checks Redis → email=true 09:01:00 — Email sent. User furious. GDPR violation.

3 Solutions Ranked by Correctness

  1. Option 1 — Cache invalidation on write (implement this): On PUT /preferences DB write, immediately DEL user_pref:{userId} from Redis. Next cache miss fetches fresh data. Window: milliseconds.
  2. Option 2 — Kafka-driven invalidation (also implement): Preference change publishes to user.preference Kafka topic. User Pref Consumer does Redis SET with new value asynchronously.
  3. Option 3 — Fresh check at consumer for unsubscribe: Add a flag on the notification: "check_preferences_fresh=true" for any campaign. Consumer re-reads from DB (not Redis) before sending. Expensive but legally safe.

The Strong Answer

"I implement Option 1 and Option 2 together. Option 1 gives immediate cache invalidation on write. Option 2 ensures eventual propagation even if the synchronous DEL failed. For the unsubscribe case specifically, I'd also add a fresh preference check at the consumer side because the legal consequence of sending a promotional email after unsubscription — a GDPR/CAN-SPAM violation — is much worse than a few extra DB reads."

What Makes This a Senior Trap

  • Junior: "Use shorter TTL." (reduces window but doesn't eliminate it)
  • Mid-level: "Invalidate cache on preference update." (Option 1 only)
  • Senior: Three-layer defense + explain why unsubscribe warrants Option 3 (legal risk > DB cost). Shows you understand regulatory consequences, not just technical correctness.

🪤 Senior Trap Q3 — "Consumer is down for 2 hours. It restarts. What happens?"

The Problem — Thundering Herd

Consumer group down for 2 hours. 2 hours × 500K notifications/hr = 1M backlog in Kafka. Consumer restarts with 30 workers. All 30 workers see 1M messages. All 30 start hammering SendGrid simultaneously. Without mitigation: 30 workers × 50 emails/sec = 1,500/sec burst But SendGrid is capped at 50/sec Token bucket fires: 1,450/sec rejected Consumers sit in 100ms sleep loops Effective throughput: same 50/sec, just noisier

3 Mitigations

  1. Rate limiter is the natural ceiling: Token bucket caps at 50/sec regardless of consumer count. The system self-throttles. Messages process over time without DB pressure spike.
  2. Stagger consumer startup: In Kubernetes, use initialDelaySeconds per pod. Add startup rate limit in consumer code — process N messages in first 60s, then ramp to full speed.
  3. Staleness check: Check now() - notification.created_at > staleness_threshold. A 2-hour-old Black Friday flash sale email is worse to send than not send. Mark it CANCELLED. Don't burn provider quota on expired promotions.

The Strong Answer (say this)

"Three things protect us. First, the rate limiter is already the ceiling — regardless of how many consumers restart simultaneously, we can't exceed SendGrid's 50/sec limit. Second, I stagger pod startup and add a ramp-up in consumer code. Third, and this is the senior-level insight — I add a staleness check. If a promotional notification is 2 hours old, sending it now is likely worse for the user experience than not sending it. Mark those CANCELLED and reserve provider quota for in-time messages."

Bonus: OTP Specific Handling

OTPs expire in 5 minutes (Redis TTL). After 2-hour downtime, ALL OTPs in the backlog are already expired. Don't even try to send them. Add check: if notification.type == OTP and otp:{userId}:{purpose} key doesn't exist in Redis (expired) → mark FAILED with reason "OTP_EXPIRED". Alert ops so they can track how many users were affected.

🪤 Senior Trap Q4 — "At 1M notifications/min, when does the DB become the bottleneck?"

Live Math (do this in the interview)

1M notifications/min = 16,667/sec Per notification: 2 DB writes INSERT notifications (status=PENDING) INSERT notifications_outbox (published=false) Total: 33,334 writes/sec to Postgres Well-tuned Postgres (modern hardware): 10,000 – 50,000 writes/sec possible Verdict: We're at the edge. Need mitigations. Connection math: 30 Notification Svc pods × 10 connections = 300 Without PgBouncer: 300 DB connections → overhead With PgBouncer: 30 logical connections → fast Outbox CDC batch: 1000 records per poll → batch Kafka publish 1000 UPDATE published=true in one query NOT 1000 individual writes → 1000x fewer DB round-trips

5 Mitigations

  1. PgBouncer connection pooling: 30 pods × 10 DB connections → pool to 30 Postgres connections. Reduces connection overhead dramatically.
  2. Shard by user_id hash: If genuinely bottlenecked, shard notifications table 4-ways. Each shard handles ~8K writes/sec.
  3. Cassandra for delivery_status: Append-heavy, rarely-updated-after-write. Cassandra handles 100K+ writes/sec trivially.
  4. Smooth bulk campaigns: Promotional emails have 30-min SLA. Throttle campaign sender to 10K/min instead of 1M/min. DB never sees the spike.
  5. Monthly partitions: Each partition is ~80M rows vs 1B total. Inserts to current partition only → no global index lock contention.
Senior insight: "At Black Friday I'd also ask — do ALL 1M notifications need to go in 1 minute? Promotional emails have 30-minute SLA. We can smooth the campaign over 100 minutes, reducing peak write rate by 100x."

Compliance — GDPR · CAN-SPAM · TCPA (These Will Be Asked)

🇪🇺 GDPR (EU)

  • Right to erasure: DELETE by external_user_id. We store no PII — only client's user_id. Client handles their own PII deletion.
  • Payload erasure: On erasure request, null the payload column — rendered content with name/email removed. Keep skeleton row for audit.
  • Consent required for marketing. user_preferences.types.promotional=true = consent given.
  • Data residency: EU users → EU-region Kafka + DB. Geo-distribute by user location.
Design: never store raw email/phone in notifications table. Store only external_user_id. The client maps it. We stay clean.

🇺🇸 CAN-SPAM (Email)

  • Unsubscribe link required in every commercial email. Injected automatically at template rendering — teams can't forget it.
  • Must honor unsubscribe within 10 days. We honor within milliseconds — preference update is real-time.
  • Must include physical address in footer (noreply@amazon.com + address).
  • No deceptive subject lines (our system doesn't control subject content — client does — but flag suspicious templates).
Enforcement: Notification Svc auto-injects unsubscribe footer for notification_type=promotional regardless of template content.

🇺🇸 TCPA (SMS)

  • Prior written consent required for marketing SMS. Store consent_granted=true in user_preferences before sending any promotional SMS.
  • Honor STOP replies: Twilio forwards STOP to our webhook → immediately set sms_channel=false in user_preferences.
  • "Reply STOP to unsubscribe" must appear in every marketing SMS — auto-appended by SMS Svc.
  • No SMS between 9pm-8am recipient's local time (DND window).
TCPA violations: $500-$1500 per SMS. For 1M users, one mistake = $500M liability. This is why preference checks are non-negotiable.
