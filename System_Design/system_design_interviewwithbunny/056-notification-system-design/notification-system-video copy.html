2. Non-Functional Requirements & CAP Theorem

Scale

  • Peak: 1M+ notifications/minute (Black Friday, breaking news)
  • 1B+ users (Amazon, Meta scale)
  • Multiple channels simultaneously

CAP Theorem Choice

Availability >> Consistency

  • Eventual consistency for delivery status acceptable
  • OTP delivered even if status DB is slightly stale
  • User sees "SENT" before "DELIVERED" — that's fine
  • Never sacrifice availability: dropped notification = lost revenue

3. Core Entities — 7 Data Models

Entity 1: User + Client user_id, email, phone device_tokens[] ← FCM token, APNS token per device preferences {channels, types, do_not_disturb} Entity 2: NotificationPreferences user_id channels {email:true, sms:false, push:true, inapp:true} types {promotional:false, transactional:true, alerts:true} do_not_disturb: false Entity 3: NotificationContent (main job record) notification_id, user_id, external_user_id template_id, channel (EMAIL/SMS/PUSH/INAPP) payload {variables}, status, priority scheduled_at, created_at, metadata Entity 4: Template template_id, version ← composite PK (immutable) subject "Order {{order_id}} confirmed" body "Hi {{name}}, your order..." variables[] ['name','order_id'] is_active
Entity 5: DeliveryStatus (per-channel tracking) delivery_id, notification_id channel, provider (Twilio/SendGrid/FCM/APNS) provider_message_id ← Twilio SID, SendGrid msg ID status (SENT/DELIVERED/FAILED/BOUNCED/OPENED/CLICKED) sent_at, delivered_at, error_message, retry_count Entity 6: Notifications_outbox (Outbox Pattern) outbox_id, notification_id event_type 'notification.created' payload {notification_id, channel, priority} published boolean DEFAULT false ← CDC polls this published_at, created_at Entity 7: Notifications (main table — same as Entity 3) notification_id, user_id, external_user_id template_id, channel, payload, status priority (critical/high/normal/low) scheduled_at, metadata
Entity 6 (outbox) + Entity 7 (notifications) are written atomically in one transaction — the core of reliability.

HLD — Every Service and Its Role

API Gateway & Load Balancer

  • JWT / API key authentication
  • Rate limiting: 100 req/min per client
  • Route to Notification Svc
  • Round-robin across Notification Svc instances

Template Service

  • CRUD on templates → Template DB (Postgres)
  • Immutable versioning (new version on update)
  • Redis cache: template:{id}:{v} TTL 1h — 95% hit rate

User Preference Service

  • CRUD on preferences → UserPref DB
  • Redis cache: user_pref:{userId} TTL 24h
  • On update: publishes to user.preference Kafka topic
  • User Pref Consumer invalidates Redis cache

Notification Service (Core Orchestrator)

  • Validates template + user preferences
  • Renders template (fills {{variables}})
  • Writes Notifications + Outbox atomically
  • CDC Publisher polls outbox → Kafka

Delivery Consumers (Dlvy Cons)

  • Email consumers: 20 instances (critical:10, std:20, promo:5)
  • SMS consumers: 15 instances
  • Push consumers: 10 instances
  • Idempotency check + rate limit + provider call

Reporting Service

  • Real-time: Redis counters INCR sent_count:{date}
  • Batch: Hourly Spark/Flink aggregation
  • Stored in InfluxDB / BigQuery for dashboards
  • Metrics: delivery %, open rate, click rate, bounce rate

6. LLD Step 1 — Request Validation & Template Rendering

Amazon calls: POST /api/v1/notifications { templateId: "order_confirmation", recipientId: "user123", variables: {name:"Alice", order_id:"ORD456"}, channels: ["email","push"], priority: "high" } API Gateway: 1. Verify JWT token → Amazon authorized ✅ 2. Rate limit: <100/min per client ✅ 3. Route to Notification Service Notification Service: 1. Fetch template from Redis / Template DB: SELECT * FROM templates WHERE template_id='order_confirmation' AND is_active=true → {subject:"Order {{order_id}} confirmed", body:"Hi {{name}}...", variables:['name','order_id']} 2. Validate variables: required: ['name','order_id'] provided: {name:"Alice",order_id:"ORD456"} ✅ missing? → 400 "Missing variable: name" 3. Redis: GET user_pref:user123 → {email:true, sms:false, push:true, promotional:false, transactional:true} cache miss? → query UserPref DB → SET TTL 24h 4. Filter channels: email → channel:true + type:transactional ✅ SEND sms → channel:false ❌ SKIP push → channel:true + type:transactional ✅ SEND 5. Render template: subject: "Order ORD456 confirmed" body: "Hi Alice, your order ORD456..." 6. Generate UUID: notification_id = "NOTIF789"

Template Cache Hit Rate

Templates change rarely. Redis cache with 1h TTL achieves 95% hit rate. Only 5% of requests hit the DB. At 1M notif/min, this saves 950K DB queries/min.

Preference Check is Mandatory

  • channels.sms = false → never send SMS
  • types.promotional = false → skip all marketing
  • do_not_disturb = true → skip ALL channels
  • Legal: GDPR, CAN-SPAM, TCPA compliance
Redis key patterns used here:
user_pref:{userId} → preferences JSON, TTL 24h
template:{id}:{version} → template JSON, TTL 1h

LLD Step 2 — Transactional Outbox Pattern

The Problem Without Outbox

Naive approach (BROKEN): 1. INSERT notifications (status=PENDING) ✅ 2. Kafka.publish("NOTIF789") ← CRASH 💥 Result: DB has NOTIF789 as PENDING Kafka never got it CDC/Publisher never finds it Alice NEVER gets her email Zero error logged. Silent loss. 😱 Also broken the other way: 1. Kafka.publish("NOTIF789") ✅ 2. INSERT notifications ← CRASH 💥 Kafka fires. Consumer tries to process. notification_id not in DB → error/lost

The Fix — One Atomic Transaction

BEGIN TRANSACTION; INSERT INTO notifications ( notification_id: 'NOTIF789', user_id: 'user123', template_id: 'order_confirmation', channel: 'EMAIL', payload: {subject, body, to:'alice@...'}, status: 'PENDING', priority: 'high', created_at: now() ); INSERT INTO notifications_outbox ( outbox_id: uuid_generate_v4(), notification_id: 'NOTIF789', event_type: 'notification.created', payload: {notification_id, channel, priority}, published: false, ← CDC watches this created_at: now() ); COMMIT; ← Both succeed OR both fail — atomically CDC Publisher (polls every 100ms): SELECT * FROM outbox WHERE published=false LIMIT 1000 ORDER BY created_at; → Kafka.send(topic, key:notification_id) → UPDATE outbox SET published=true If Kafka fails: stays false, retried next poll
💡 Interview must-say: "If DB COMMIT succeeded, the message is in the outbox. CDC Publisher will EVENTUALLY publish it to Kafka — retrying until success. This guarantees at-least-once delivery even across service crashes, network failures, or Kafka restarts."

LLD Step 3 — Kafka Topics & Priority Queues

CDC Publisher determines topic by priority + channel: priority=critical + sms → notifications.critical.sms priority=critical + email → notifications.critical.email priority=high + email → notifications.standard.email priority=normal + push → notifications.standard.push priority=low + email → notifications.promotional.email bulk campaign + email → notifications.bulk.email any failure → notifications.retry retry exhausted → notifications.dlq pref update → user.preference ALL 7 Kafka topics: notifications.critical.{channel} OTP, fraud alerts notifications.standard.{channel} orders, shipping notifications.promotional.{channel}marketing notifications.bulk.{channel} campaigns notifications.retry failed + backoff notifications.dlq dead letter queue user.preference pref cache updates

Why Separate Topics Matter

Without priority: OTP waits behind 10K marketing emails. Same queue = same consumers = same speed.

With separate topics: OTP critical topic has 20 dedicated consumers, zero marketing emails competing. OTP always <10s regardless of marketing backlog.

100 Kafka partitions per topic = 100 parallel consumers max. Autoscale: if lag > 1000 → add consumers.

LLD Step 4 — Consumer Processing Pipeline

Consumer subscribes to notifications.standard.email Receives message: { notification_id: "NOTIF789", channel: "EMAIL", payload: { subject: "Order ORD456 confirmed", body: "Hi Alice...", to: "alice@example.com" }, priority: "high" } Step 1 — Idempotency check: SELECT COUNT(*) FROM delivery_status WHERE notification_id='NOTIF789' AND channel='EMAIL' → 0 rows → proceed (first time) → 1 row → SKIP (already sent, Kafka duplicate) Why needed? Kafka at-least-once may redeliver on consumer restart or network retry. Without this: Alice gets 5 identical emails. Step 2 — Rate limit check (Token Bucket): key: rate_limit:email:sendgrid Redis Lua script (atomic): tokens = GET key or capacity (100) if tokens >= 1: DECR key return "proceed" else: return "wait 100ms, retry" ← backpressure: consumer slows, Kafka buffers Step 3 — Provider routing: EMAIL → Email Svc Provider (SendGrid/AmazonSES) SMS → SMS Svc Provider (Twilio/MSG91) PUSH → inAPP Svc Provider (FCM/APNS) OTP → OTP Svc (dedicated, high priority)

SendGrid Webhook Events

LLD Step 7 — Retry Mechanism + Exponential Backoff + DLQ

Temporary failures → RETRY: Provider timeout (no response in 10s) HTTP 429 Too Many Requests HTTP 5xx Server Error Network connection refused Exponential backoff: Attempt 1 fails → Publish to notifications.retry {notification_id, retry_count:1, scheduled_at: now()+1min} Attempt 2 fails (1 min later) → retry_count: 2 scheduled_at: now()+5min Attempt 3 fails (5 min later) → retry_count: 3 scheduled_at: now()+15min Attempt 4 fails (15 min later) → retry_count >= 3 → MOVE TO DLQ Permanent failures → NO RETRY: Email bounced (550 User not found) Invalid phone number User unsubscribed (honor preference) APNS 410 Gone (app uninstalled) → UPDATE delivery_status SET status='FAILED', error_message='Invalid email address' Dead Letter Queue (DLQ): notifications.dlq Kafka topic Ops team alerted via PagerDuty Manual investigation → root cause Fixed? → replay from DLQ

Why Exponential Backoff?

If Twilio is overloaded (HTTP 429):

  • Retry every 1s → makes overload WORSE
  • Wait 1m, 5m, 15m → gives Twilio time to recover
  • Spreads retry load over time
  • Industry standard across all distributed systems

7. Database Schema — Notifications + Outbox Tables

CREATE TABLE notifications ( notification_id UUID PRIMARY KEY, user_id UUID NOT NULL, external_user_id VARCHAR(255), template_id UUID REFERENCES templates, channel ENUM('EMAIL','SMS','PUSH','INAPP'), payload JSONB, -- {subject, body, to, variables} status ENUM( 'PENDING','SCHEDULED','SENT', 'DELIVERED','FAILED','CANCELLED' ) DEFAULT 'PENDING', priority ENUM('critical','high','normal','low'), scheduled_at TIMESTAMPTZ, ← NULL = send now created_at TIMESTAMPTZ DEFAULT now(), metadata JSONB ← campaign_id, tags ); -- Indexes for common queries: CREATE INDEX idx_notif_user_created ON notifications(user_id, created_at); CREATE INDEX idx_notif_status_sched ON notifications(status, scheduled_at); -- scheduler polls: WHERE status='SCHEDULED' -- AND scheduled_at <= now() CREATE INDEX idx_notif_template ON notifications(template_id); -- Partitioned by created_at (monthly): -- notifications_2026_01, notifications_2026_02... -- Old partitions archived to S3 after 6 months
CREATE TABLE notifications_outbox ( outbox_id UUID PRIMARY KEY, notification_id UUID NOT NULL REFERENCES notifications(notification_id), event_type VARCHAR(50), -- e.g. 'notification.created' payload JSONB, -- {notification_id, channel, priority} published BOOLEAN DEFAULT FALSE, -- CDC Publisher polls WHERE published=false published_at TIMESTAMPTZ, created_at TIMESTAMPTZ DEFAULT now() ); -- CDC Publisher query (every 100ms): SELECT * FROM notifications_outbox WHERE published = false ORDER BY created_at ASC LIMIT 1000; -- After Kafka publish succeeds: UPDATE notifications_outbox SET published = true, published_at = now() WHERE outbox_id = $1;
Outbox + Notifications in one transaction = the foundation of at-least-once delivery. If Postgres commits, the outbox row exists forever until CDC publishes it.

DB Schema — Templates + User Preferences

CREATE TABLE templates ( template_id UUID NOT NULL, version INT NOT NULL, PRIMARY KEY (template_id, version), -- Composite PK = immutable versioning -- Never UPDATE a row; INSERT new version name VARCHAR(255), channel ENUM('EMAIL','SMS','PUSH','INAPP'), subject TEXT, ← "Order {{order_id}} confirmed" body TEXT, ← "Hi {{name}}, your order..." variables JSONB, ← ['name','order_id'] is_active BOOLEAN DEFAULT TRUE, created_at TIMESTAMPTZ DEFAULT now() ); -- On template update: -- INSERT with version = old_version + 1 -- SET old version is_active = false -- A/B testing: -- Route 50% requests to version 1 -- Route 50% requests to version 2 -- Compare delivery/open rates -- Redis cache: -- key: template:{id}:{version} -- TTL: 3600 (1 hour) -- Hit rate: ~95%
CREATE TABLE user_preferences ( client_id VARCHAR(100) NOT NULL, external_user_id VARCHAR(255) NOT NULL, PRIMARY KEY (client_id, external_user_id), -- Composite PK: one pref per user per client -- 'amazon' user 'alice' is different from -- 'uber' user 'alice' channels JSONB DEFAULT '{ "email": true, "sms": true, "push": true, "inapp": true }', types JSONB DEFAULT '{ "promotional": true, "transactional": true, "alerts": true }', do_not_disturb BOOLEAN DEFAULT FALSE, updated_at TIMESTAMPTZ DEFAULT now() ); -- On preference update: -- 1. ⭐ Interview Q1 — "How do you ensure no notification is lost?"

Interviewers ALWAYS ask this. Your answer must cover all 5 points below.

1. The Problem (dual-write failure)

Naive: write DB then publish to Kafka. If Kafka fails after DB commit → notification stuck. If DB fails after Kafka publish → notification lost. Either way: silent failure.

2. Outbox Pattern (single transaction)

INSERT notifications + INSERT outbox in ONE transaction. Either both commit or both rollback. No inconsistency possible.

3. CDC Publisher (at-least-once to Kafka)

Polls outbox WHERE published=false every 100ms. Publishes to Kafka. Marks published=true. If CDC crashes after Kafka success but before mark: same message published twice on restart → idempotency handles it.

4. Idempotent Consumers (prevent duplicates)

Consumer checks: SELECT COUNT(*) FROM delivery_status WHERE notification_id + channel. If exists → already sent → skip. Kafka at-least-once may deliver same message twice; idempotency prevents double emails.

5. Result: Effectively Exactly-Once

At-least-once delivery (Outbox + CDC) + Idempotent consumers = exactly-once to the user. Message never lost. Message never duplicated.

How to say it: "We use the Transactional Outbox pattern — DB write and outbox row in one atomic transaction. CDC Publisher polls outbox to Kafka. Idempotent consumers prevent duplicates. This gives us at-least-once delivery with no silent losses, combined with idempotency for exactly-once semantics from the user's perspective."

⭐ Interview Q2 — "How do you handle rate limiting at 1M+ notifications/min?"

Token Bucket — Redis Lua Script

-- Atomic Lua script (thread-safe): local key = KEYS[1] -- rate_limit:email:sendgrid local capacity = ARGV[1] -- 100 tokens (max burst) local refill_rate = ARGV[2] -- 100 per second local tokens = redis.call('GET', key) or capacity if tonumber(tokens) >= 1 then redis.call('DECR', key) redis.call('EXPIRE', key, 10) -- reset after idle return 1 -- proceed else return 0 -- rate limited, consumer waits end -- Consumer behavior when rate limited: -- Option A: sleep 100ms, retry (simple) -- Option B: push back to Kafka topic -- (better: allows other consumers to work)

Complete Strategy (5 parts)

  • 1. Token bucket per provider — Redis atomic, matches exact limits
  • 2. Backpressure — consumers slow → Kafka buffers (millions capacity)
  • 3. Multi-provider failover — SendGrid (50/s) + SES (50/s) = 100/s combined
  • 4. Batching — SendGrid bulk API: 1 call = 1000 emails → 50K/s effective
  • 5. OTP bypass — critical notifications skip rate limiter entirely

Monitoring & Alerting

  • Track: token bucket hits (how often consumers wait)
  • Alert: rate limit events >10% of time → upgrade provider tier
  • Metric: Kafka consumer group lag (leading indicator)
