Opening — Why This Problem Matters

Every major platform needs real-time ranking. The challenge is not just sorting — it is sorting continuously at massive scale while keeping results fresh.

Interviewer's real test: Can you navigate the exact-vs-approximate trade-off, explain time-decay, and design a Redis ZSET that handles millions of updates per second without becoming a bottleneck?
  • Gaming: Fortnite kills leaderboard — 250M players, sub-10ms rank query
  • Streaming: Spotify Top 50 — top songs by region, updated daily
  • Social: Twitter trending — approximate counts, ~1h staleness acceptable
  • Video: YouTube trending — time-decay score, hourly recompute

This guide walks the full stack: requirements → HLD → deep-dive algorithms → scale → senior Q&A.

Count-Min Sketch — Approximate Frequency

When you have billions of distinct items and need approximate counts in constant space.

Structure: 2D array of w×d counters
  w = width (e.g. 1000 buckets)
  d = depth (e.g. 5 hash functions)

On event for item X:
  for i in range(d):
    col = hash_i(X) % w
    table[i][col] += 1

Query count(X):
  return min(table[i][hash_i(X) % w] for i in range(d))
Key property: Always overestimates — never underestimates. Bounded error: with 99% probability, estimate ≤ true_count + ε × N (where N = total events).
MetricValue
Memory~1 MB for billions of items (vs 1 GB Redis ZSET for 10M items)
Accuracy95%+ overlap with exact top-K at ε=0.001
Use caseTwitter trending, viral video detection, approximate top-K

Pair with a Min-Heap of size K: if CMS estimate > heap.min → replace heap entry. Result: approximate top-K in O(log K) per event.

HeavyKeeper — Modern Top-K Algorithm

HeavyKeeper (2018) is the state-of-the-art for space-efficient approximate top-K, used in Redis Streams and network monitoring.

Structure: d × w buckets, each bucket = (fingerprint, count)

On event for item X:
  fp = fingerprint(X)   ← short hash for identity check
  for each row i:
    j = hash_i(X) % w
    if bucket[i][j].fp == fp:
        bucket[i][j].count += 1   ← item already tracked
    elif bucket[i][j].count == 0:
        bucket[i][j] = (fp, 1)    ← empty slot, take it
    else:
        // Decay with probability 1/count^b  (b≈1.08)
        if random() < 1 / bucket[i][j].count^b:
            bucket[i][j].count -= 1
            if count == 0: bucket[i][j] = (fp, 1)
Why better than Count-Min Sketch: exponential decay evicts low-frequency items, preserving slots for heavy hitters. Better recall for true top-K at same memory budget.

Redis Streams Top-K: uses HeavyKeeper internally for TOPK.ADD and TOPK.LIST commands.

Redis Sorted Set (ZSET) Design

The workhorse for real-time leaderboards. Every entry is a (member, score) pair, always sorted by score.

# Write — O(log N)
ZINCRBY leaderboard:global:alltime 1 V123

# Read top-K — O(log N + K)
ZREVRANGE leaderboard:global:alltime 0 9 WITHSCORES
→ [("V123", 1000000), ("V456", 950000), ...]

# Get a user's rank — O(log N)
ZREVRANK leaderboard:global:alltime V123
→ 42  (0-indexed → rank #43)

# Get score — O(1)
ZSCORE leaderboard:global:alltime V123

# Cursor-based pagination (stable during live updates)
ZREVRANGEBYSCORE leaderboard:global:alltime {cursor} -inf LIMIT 0 10
Score tie-breaking: store as float — score + timestamp/1e12 — entity that reached the score first ranks higher. Deterministic and semantically correct.

Memory: ~100 bytes/entry → 10M entries ≈ 1 GB per ZSET

Time-Windowed Leaderboards

Use separate ZSET keys per time bucket with TTL for automatic cleanup.

# Key taxonomy
leaderboard:global:alltime              → no TTL
leaderboard:global:daily:2026-01-25    → TTL 7 days
leaderboard:global:weekly:2026-W04     → TTL 90 days
leaderboard:global:monthly:2026-01     → TTL 365 days
leaderboard:trending                   → TTL 24h, rebuilt hourly

# On each score event — update all relevant windows
PIPELINE
  ZINCRBY leaderboard:global:alltime     1 V123
  ZINCRBY leaderboard:global:daily:{D}  1 V123
  ZINCRBY leaderboard:global:weekly:{W} 1 V123
  ZINCRBY leaderboard:music:US:alltime   1 V123
EXEC   ← 1 network RTT, all atomic
Weekly aggregation from daily ZSETs: ZUNIONSTORE leaderboard:global:weekly:W04 7 leaderboard:daily:Mon ... leaderboard:daily:Sun WEIGHTS 1 — runs every Monday midnight, single atomic command.

Key explosion: 5 regions × 10 categories × 4 windows = 200 leaderboards × 1 GB = 200 GB. Fix: lazy init + expire unused after 30 days.

Kafka Partitioning Strategy

Partition by entity_id hash — all events for the same item go to the same partition, preserving ordering.

Topic: score.updated
Partitions: 100
Partition key: hash(entity_id) % 100

Consumer groups:
  redis-consumer      → 1 consumer per partition
                        ZINCRBY on every event (<100ms lag)
  db-consumer         → batch INSERT to Score DB (~1s lag)
  analytics-consumer  → Flink → InfluxDB / aggregated DB

Message schema:
  {
    event_id:    uuid(),
    entity_id:   "V123",
    score_delta: +1,
    timestamp:   epoch_ms,
    region:      "US",
    category:    "music"
  }
Why entity_id as partition key? Ensures ordering for dedup (same user, same video within 5 min). Prevents out-of-order ZINCRBY causing wrong total. 100 partitions × 10K/sec = 1M events/sec capacity.

Scaling trigger: if Kafka consumer lag > 1 minute → add more consumer instances (auto-scale).

Stream Processing with Flink

Flink handles real-time aggregation for analytics layer and batch-style top-K computation.

// Flink tumbling window — aggregate per 1-minute bucket
DataStream<ScoreEvent> events = kafka.source("score.updated");

events
  .keyBy(e -> e.entityId)
  .window(TumblingProcessingTimeWindows.of(Time.seconds(60)))
  .aggregate(new SumAggregator())
  .addSink(new RedisZSetSink());   // ZINCRBY per window

// Emit top-K every 1 second
events
  .keyBy(e -> e.leaderboardId)
  .process(new TopKProcessFunction(K=1000))
  .addSink(new RedisSink());
Window TypeUse Case
Tumbling (fixed)Hourly/daily score aggregation — clean buckets
Sliding"Last 24 hours" trending — overlapping windows
SessionPer-user engagement session scoring
Micro-batch trick: buffer 100 events → single ZADD with multiple members → 100× fewer Redis round trips vs one ZINCRBY per event.

Sharding Redis for Global Scale

A single Redis node handles ~10 GB and ~100K ops/sec. At scale you need a cluster.

Redis Cluster (10 nodes: 5 masters + 5 replicas)
  16384 hash slots distributed across masters
  Shard key: leaderboard_id (CRC16 % 16384)

Strategy A — Shard by leaderboard_id
  leaderboard:US:alltime   → node 3
  leaderboard:IN:alltime   → node 7
  Problem: global top-K needs cross-shard merge

Strategy B — Local top-K per shard → merge
  Each Kafka consumer shard maintains local top-K
  Ranking Service reads from all shards:
    ZREVRANGE shard-1:leaderboard 0 99   (top 100 each)
    ZREVRANGE shard-2:leaderboard 0 99
    ...
  Merge K lists → true global top-K
  (K-way merge: O(K × shards × log shards))
Separate cluster per region: each region (US, IN, EU) gets its own Redis cluster — isolates load, avoids cross-region latency. Global top-K merged at application layer on read.

Trending Detection — Rate of Change

Trending is not about the highest absolute count — it is about the fastest-rising items with recency bonus.

Hacker News time-decay formula:
  trending_score = engagement / (age_hours + 2)^1.8

  engagement = views + (likes×10) + (comments×20) + (shares×30)

Example:
  Video A: 10M views, 7 days old
    → 10,000,000 / (168 + 2)^1.8 ≈ 13,895

  Video B: 500K views, 3 hours old
    → 500,000 / (3 + 2)^1.8   ≈ 95,763

  → Video B ranks HIGHER (trending, not popular)

Batch recompute (recommended approach):
  Cron hourly → compute for all videos < 7 days old only
  DEL leaderboard:trending
  ZADD leaderboard:trending {score} {entity_id}   (top 1000)
  EXPIRE leaderboard:trending 7200   ← 2h TTL safety net
  ZREMRANGEBYSCORE leaderboard:trending -inf {threshold}
Reddit Hot alternative: log10(ups) + age_seconds / 45000 — logarithmic diminishing returns + linear decay. More stable front page, less spike-prone than Hacker News formula.

Gaming Prevention & Fraud Detection

Without anti-gaming, bots and coordinated attacks will corrupt your leaderboard within hours of launch.

Attack VectorDefense
Same user double-countingRedis dedup: SET view_dedup:{user}:{entity} 1 EX 300 (5-min TTL)
IP-based bot farmRate limit per IP: max 60 events/min (sliding window counter in Redis)
Coordinated click fraudAnomaly score: if entity goes 0→top-10 in <60s → flag for review
Account farmingRequire authenticated user_id; new accounts get reduced event weight
Score injectionServer-side validation only — never trust client-sent scores
Velocity anomaly detection: track event_rate per entity over 5-min sliding window. If rate > mean + 3σ → increment anomaly counter. If anomaly_score > threshold → quarantine (stop ZINCRBY) pending human/ML review.

Cheat-resistant game leaderboards: sign all score submissions with server-side HMAC. Replay-protected via monotonic sequence number per user session.

-- Raw score events (source of truth)
CREATE TABLE scores (

  score_delta    INT,            -- +1 view, +10 like, +100 match win
  leaderboard_id VARCHAR(100),   -- 'global', 'US', 'music'

  timestamp      TIMESTAMPTZ,
  metadata       JSONB           -- user_id, device, session
);
CREATE INDEX ON scores (leaderboard_id, timestamp);
CREATE INDEX ON scores (entity_id);
-- Shard by hash(entity_id) across 10 shards

-- Pre-computed batch snapshots
CREATE TABLE leaderboard_snapshots (
  leaderboard_id VARCHAR(100),
  rank           INT,
  entity_id      VARCHAR(100),
  score          BIGINT,
  snapshot_date  DATE,
  PRIMARY KEY (leaderboard_id, rank)

Shard by entity_id hash — not by score. Score-based sharding = hotspot: top entities all land on the same shard. Entity_id hash distributes evenly. Cross-shard aggregation handled by batch jobs.

Senior Q&A 1 — Count-Min Sketch vs Exact Counting

Q: When would you choose Count-Min Sketch over exact Redis ZSET counting? What are the failure modes?

Answer framework: Memory constraint → CMS. Accuracy requirement → exact. Consequence of error → determines threshold.
Count-Min SketchRedis ZSET (Exact)
Memory~1 MB for billions of items~1 GB for 10M items
Accuracy95%+ overlap with exact top-K100% exact
Failure modeHash collisions inflate counts (always overestimates)Memory pressure → eviction → silent data loss
Use whenTrending (rank 100 vs 101 OK), 1B+ items, approximate fineGaming (prizes), financial (payouts), exact rank needed

CMS failure modes to mention: (1) heavily skewed distribution worsens error — most slots collide on popular items. (2) Deletion not supported — cannot remove items (use Count-Min-Mean for deletions). (3) No persistence — in-process memory only.

Senior Q&A 2 — How to Handle a Viral Item at #1

Q: A music video goes from 0 views to #1 on the global leaderboard in 60 seconds. What happens in your system? What could go wrong?

This question tests: hot partition handling, anomaly detection, and whether you understand Redis ZINCRBY under write storm conditions.
  • Kafka hot partition: all events for entity_id hash to the same partition → that partition's consumer becomes CPU-bound. Fix: detect hot partitions via lag monitoring → temporarily repartition or add sub-partitioning.
  • Redis write amplification: 1M ZINCRBY/sec on one key → Redis single-threaded → latency spike. Fix: Redis pipelining + batch ZADD from consumer (batch 100 events → 1 command).
  • Anomaly detection trigger: velocity check fires → item quarantined. Must tune threshold to distinguish genuine viral from bot. Use separate human-review queue for items exceeding 3σ velocity.
  • Cache invalidation cascade: app-level top-100 cache becomes stale instantly. Short TTL (10s) limits staleness window. CDN cache must be purged via cache-key versioning.

Recovery: once confirmed genuine, drain quarantine queue and retroactively apply ZINCRBY. Idempotency key prevents double-counting.

Senior Q&A 3 — Cheat-Resistant Leaderboard for 10M Concurrent Players

Q: Design a cheat-resistant game leaderboard for 10M concurrent players competing for real prizes.

Key constraint: prizes make fraud high-value — attackers are motivated. Never trust client-sent scores.
  • Server-authoritative scoring: game server signs score events with HMAC-SHA256(secret, player_id + score + match_id + timestamp). Client cannot forge or replay.
  • Replay prevention: include monotonic match_id. Score Service rejects duplicate match_id (Redis SET match_id EX 86400).
  • Score validation: server checks score plausibility — if max possible score in match duration is 1000, reject score=9999.
  • Anomaly detection: track score_velocity per player. P99.9 threshold = max physically possible improvement rate. Exceed → flag + suspend from leaderboard pending review.
  • Segregate leaderboard writes: flagged players go to shadow leaderboard — they see themselves ranked but are excluded from prize leaderboard.
  • Audit trail: every score event stored in append-only DB. Prize adjudication can replay full history.

Scale: 10M concurrent = ~500K score events/sec peak (50 events/player/session). Kafka 50 partitions + 50 Redis consumers handles this comfortably.

Closing — Interview Playbook

Walk into any top-K / leaderboard question with this mental model and you will cover the full depth the interviewer is probing for.

4-step answer arc: Requirements (functional + NFR) → HLD (Kafka → Redis ZSET → DB) → Deep dive (ZSET commands, time windows, trending formula) → Trade-offs (exact vs approx, Redis vs DB).
  • Always mention: eventual consistency, ZINCRBY atomicity, Kafka partition-by-entity_id, TTL for time windows
  • Distinguish yourself: bring up HeavyKeeper vs Count-Min Sketch, time-decay formula, key explosion problem + lazy-init fix
  • Scale story: 100 Kafka partitions → 100 Redis consumers → Redis Cluster (5 masters + 5 replicas) → CDN edge caching
  • Failure story: Redis crash → serve DB fallback → rebuild in 10 min → nightly reconciliation prevents silent drift
  • Anti-patterns to avoid: SELECT COUNT(*) WHERE score > X (O(N) DB scan), single Redis node for global leaderboard, trusting client scores

Remember: Fortnite, Spotify, YouTube, Twitter — all use Kafka as backbone. Difference is what the consumer does with events. That is the system design answer.
