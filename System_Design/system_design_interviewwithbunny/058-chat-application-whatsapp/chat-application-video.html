Six major components

  • Connection layer — WebSocket servers, persistent client connections
  • Chat service — validates, persists, routes messages
  • Message store — Cassandra: high-write, time-ordered, TTL
  • Presence service — online/offline via Redis Pub/Sub
  • Media service — S3 + CDN, pre-signed URLs
  • Notification service — APNs / FCM for offline users

Key design decisions

  • Sequence IDs per conversation for ordering
  • ACK-based delivery: ✓ received, ✓✓ delivered, ✓✓ blue = read
  • Redis Streams for hot delivery path (<1ms)
  • Kafka for durable async integrations (search, analytics)
  • Write-fanout for groups ≤ 256 members
  • WebSocket with consistent hashing (sticky sessions)

Connection Management — WebSocket

Why WebSocket over HTTP polling?

  • Full-duplex TCP — client and server both push at any time
  • Single persistent connection handles send + receive + ACKs
  • No HTTP header overhead on every message (~800 bytes saved per msg)
  • Better on mobile — fewer connections, saves battery
  • At 500M users × 40 polls/min = crushes servers without WS

WebSocket Lifecycle

  • HTTP GET /ws → 101 Switching Protocols
  • Heartbeat ping every 30 seconds
  • Server closes dead connections after 90s with no ping
  • Client reconnects with exponential backoff + jitter (2–5s)
  • On reconnect: fetch pending messages from Cassandra

Sticky Sessions via Consistent Hashing

User A always connects to WebSocket Server #3. Consistent hashing on user_id → same server node. Redis registry maps: user_id → ws_server_id

Why sticky sessions?

  • Chat Service needs to know which WS server holds a user's connection
  • Redis lookup: GET user:{id}:ws_server → server address
  • Message delivery goes to that server's Redis Stream inbox
  • On disconnect, Redis key expires (TTL = 60s heartbeat)

Scale

  • 64-core server with 256 GB RAM → ~640K concurrent WS connections
  • 400M peak connections → ~625 WS servers needed
  • Tune: SO_REUSEPORT, ulimit, multiple ports per machine

Online Path (happy path)

  1. Client sends message over WebSocket
  2. Chat Service persists to Cassandra first
  3. Chat Service publishes to recipient's Redis Stream inbox
  4. Sender receives single tick (server ACK)
  5. Recipient's WS server delivers; client ACKs back
  6. Sender gets double tick (delivered)

Offline Path

  1. Cassandra stores message with status = PENDING
  2. Notification Service fires FCM/APNs push
  3. On reconnect, client fetches PENDING from Cassandra
  4. Delivered in order by sequence ID
  5. Client ACKs each; status advances to DELIVERED
Guarantee: Cassandra write completes before sender ACK — zero message loss after single tick.

Delivery Receipts — Three-Tick System

The Three States

SymbolStateMeaningTriggered by
✓SENTServer received & persistedChat Service writes to Cassandra
✓✓ greyDELIVEREDRecipient device got messageClient device sends DELIVERY_ACK
✓✓ blueREADRecipient opened conversationClient sends READ_ACK on screen display
Why not exactly-once? ACKs can be lost in transit. Re-sending ACK with same message_id is idempotent — state transitions (PENDING → DELIVERED → READ) are monotonic, never go backward.

Implementation Details

  • SENT tick: Returned immediately when Chat Service ACKs the Cassandra write
  • DELIVERED tick: Recipient device sends DELIVERY_ACK{message_id} over WS
  • READ tick: Sent when conversation is scrolled into view on recipient screen
  • Batch ACKs: Read receipt can batch multiple message IDs (load conversation = bulk READ_ACK)
  • Privacy: User can disable read receipts (blue tick blocked) — WhatsApp supports this

Group Read Receipts

  • Show "Delivered to N / Read by N" count
  • Store per-member delivery record in Cassandra
  • Sender queries aggregated delivery state on demand (not pushed)
  • Avoids N×M real-time events flooding the sender

Message Ordering — Cassandra Partition Design

Partition Key = conversation_id

-- Cassandra table
CREATE TABLE messages (
  conv_id    TEXT,
  seq_id     BIGINT,   -- server-assigned sequence
  message_id UUID,     -- client idempotency key
  sender_id  TEXT,
  content    BLOB,     -- ciphertext
  msg_type   TEXT,     -- TEXT | IMAGE | VIDEO
  status     TEXT,     -- PENDING | DELIVERED | READ
  created_at TIMESTAMP,
  PRIMARY KEY ((conv_id), seq_id, message_id)
) WITH CLUSTERING ORDER BY (seq_id DESC);

-- Fetch last 50 messages
SELECT * FROM messages
WHERE conv_id = '123'
ORDER BY seq_id DESC
LIMIT 50;

Why this partition design?

  • Partition by conv_id: All messages in one conversation stored together → fast range reads
  • Cluster by seq_id DESC: Newest messages first without client-side sorting
  • seq_id not timestamp: Two messages at same millisecond won't collide; seq_id is monotonic per conversation
  • message_id UUID: Client-generated; deduplication key for retries

Hot partition mitigation

  • Add time-bucket to partition key for very active conversations:
  • PRIMARY KEY ((conv_id, bucket), seq_id)
  • bucket = YYYYMM → max ~30 days of messages per partition
  • Keep partition size < 100MB (Cassandra recommendation)
Discord publicly migrated MongoDB → Cassandra for exactly this pattern — 1B+ messages/day on this schema design.

Snowflake ID — Distributed Sequence Generation

Snowflake ID Structure (64-bit)

Bit layout (64 bits total):
┌────────────┬──────────┬───────────┬─────────┐
│  41 bits   │ 10 bits  │  12 bits  │  1 bit  │
│ timestamp  │ node_id  │ sequence  │  sign   │
│ (ms since  │(data ctr │ (per-ms   │  (0)    │
│  epoch)    │ + worker)│  counter) │         │
└────────────┴──────────┴───────────┴─────────┘

Properties:
- Monotonically increasing per node
- ~4096 IDs/ms per worker node
- 1024 worker nodes supported
- ~69 years of timestamps
- Sortable by time globally (approximately)
Twitter, Discord, Instagram all use Snowflake variants. seq_id in Cassandra = Snowflake ID → ordering + deduplication in one value.

Why not UUID v4 for ordering?

  • UUID v4 is random — no temporal ordering
  • Cassandra secondary index on timestamp is expensive
  • Snowflake embeds time → range queries work on primary key

Why not auto-increment (MySQL)?

  • Single point of failure for ID generation
  • Doesn't scale across distributed Chat Service instances
  • Requires a round-trip to DB before message is persisted

Per-conversation sequence (alternative)

  • Redis INCR on key seq:{conv_id} → atomic per-conversation counter
  • Guarantees strict per-conversation ordering (no gaps)
  • Trade-off: Redis INCR is a synchronous bottleneck per message
  • At WhatsApp scale: shard counters by conv_id hash

Group Chat Fan-out — Write vs Read

Fan-out on Write (WhatsApp approach)

  • One message → push copy to each member's inbox immediately
  • 256 members → 256 Cassandra writes + 256 Redis Stream entries
  • Simple delivery: each user has their own queue
  • Low read latency: no membership lookup on read path
  • Works great for groups ≤ 256 members
✅ Simple delivery logic
✅ Low read latency
✅ Easy per-member delivery state
❌ 256× write amplification
❌ Expensive for large groups

Fan-out on Read (Twitter/YouTube approach)

  • Store message once; each member fetches when they open chat
  • Must compute group membership on every read
  • O(1) write cost regardless of group size
  • Higher read latency (membership join + message fetch)
  • Better for 100K+ follower broadcast channels
✅ Single write per message
✅ Scales to huge groups
❌ Complex read path
❌ Higher read latency
Recommendation: Fan-out on WRITE for groups ≤ 256 (WhatsApp/Messenger model). Fan-out on READ or hybrid for Telegram channels (100K+ members). The product constraint (256 member limit) makes write-fanout tractable.

Online Presence — Redis Heartbeat Design

Presence Data Model (Redis)

-- On WebSocket connect:
HSET user:{id}:presence
  status "online"
  ws_server "ws-node-42"
  last_seen 1700000000
EXPIRE user:{id}:presence 60

-- Heartbeat every 30s (client ping):
EXPIRE user:{id}:presence 60

-- On disconnect:
HSET user:{id}:presence
  status "offline"
  last_seen {now}

-- Broadcast to interested parties:
PUBLISH presence:{id} "offline:{timestamp}"
Key TTL = 60s. If client crashes without disconnect, presence auto-expires. No zombie "online" users after network failure.

Presence Fan-out

  • User A goes online → PUBLISH to presence:{A} channel
  • All WebSocket servers subscribed to contacts of A receive the event
  • Those servers push presence update to connected contacts
  • Rate limit: max 1 presence update/sec per user (avoid flapping)

Privacy & "Last Seen"

  • Store last_seen_at timestamp on disconnect in Redis + PostgreSQL
  • User can hide last seen (privacy setting in DB)
  • If hidden: always return "last seen recently"
  • Mutual privacy: if you hide yours, you can't see others'

Why Redis over ZooKeeper?

  • Sub-millisecond pub/sub — presence changes in <1ms
  • Simple HSET/EXPIRE pattern; no ZK node lifecycle complexity
  • Redis doubles as cache — no second system needed
  • Eventually consistent presence is acceptable (stale by seconds)

End-to-End Encryption — Signal Protocol

Key Components

  • X3DH (Extended Triple Diffie-Hellman): Initial key agreement without both parties online simultaneously
  • Double Ratchet Algorithm: Generates new encryption key per message — forward secrecy & break-in recovery
  • Curve25519: Elliptic curve for key generation (fast, secure)
  • AES-256-CBC + HMAC-SHA256: Symmetric encryption of message content

1:1 Message Encryption Flow

1. Alice uploads public keys to server:
   - Identity Key (IK): long-term
   - Signed Prekey (SPK): medium-term
   - One-Time Prekeys (OPKs): single-use

2. Bob fetches Alice's keys from server
3. Bob computes shared secret via X3DH
4. Bob encrypts message with shared secret
5. Server stores ciphertext only
6. Alice decrypts with her private keys

Group Chat Encryption — Sender Key

  • Each device has a Sender Key per group
  • On joining group: receive all members' Sender Keys via 1:1 encrypted messages
  • Encrypt group message with your own Sender Key — O(1) not O(n)
  • Each recipient decrypts using the sender's distributed key

Implications for System Design

  • Server stores only ciphertext — cannot read messages
  • No server-side search (Elasticsearch can't index ciphertext)
  • Push notifications use generic text: "You have a new message"
  • Key rotation: new Sender Key when member leaves group (forward secrecy)
  • New member cannot read historical messages (by design)
Trade-off: E2EE prevents content moderation, spam detection, and search on server side. Must be called out in interview as an explicit design constraint.

Media Sharing — Pre-signed S3 + CloudFront CDN

Upload Flow (Direct-to-S3)

1. Client → Chat Service:
   POST /media/upload-url
   {type: "image", size: 2MB}

2. Chat Service → S3:
   generate_presigned_url(
     bucket="whatsapp-media",
     key="media/{conv_id}/{uuid}.jpg",
     expiry=900  # 15 minutes
   )

3. Chat Service → Client:
   {upload_url: "https://s3.amazonaws.com/...?sig=..."}

4. Client → S3 directly:
   PUT {upload_url} (image bytes)
   -- Chat Service never touches media bytes --

5. Client → Chat Service:
   Send message with media_key reference only
Media bytes never flow through Chat Service. Reduces load and egress cost.

Download via CDN

  • CloudFront CDN with 400+ edge locations globally
  • Image served from node <20ms away vs 200ms to origin
  • Target cache hit ratio: >90% for popular media
  • S3 bucket is private — CDN uses signed cookies

Media Processing Pipeline

  • Upload triggers Lambda → compress thumbnail (100px)
  • Store: original + thumbnail in S3
  • Message contains: thumbnail_url + full_url (both pre-signed)
  • Chat loads thumbnail; user taps → fetch full resolution

Scale & Cost

  • 10% of messages have media → 10B media/day
  • Avg 100KB compressed → 1 PB/day (!) → S3 Intelligent-Tiering
  • Media older than 90 days → Glacier (10× cheaper)
  • S3 durability: 99.999999999% (11 nines)
  • Multi-region replication for DR

Push Notifications — Offline Delivery

Offline Detection

  • Redis lookup: GET user:{id}:presence
  • If key missing or status = "offline" → send push notification
  • If key exists and status = "online" → deliver via WebSocket only
  • Race condition: user goes offline between check and WS delivery → client fetches missed messages on reconnect from Cassandra

Push Notification Flow

Chat Service:
  if recipient.isOffline():
    NotificationService.send({
      device_token: user.fcm_token,
      title: "New message",      # generic (E2EE)
      body: "You have a message",
      data: {conv_id, message_id}
    })

Device wakes:
  → Opens app → WebSocket reconnects
  → Fetches pending messages from Cassandra
  → Sends DELIVERY_ACK for each

Cassandra Schema — Production-Grade Design

Messages Table

CREATE TABLE messages (
  conv_id    TEXT,
  bucket     INT,     -- YYYYMM (hot partition fix)
  seq_id     BIGINT,  -- Snowflake or Redis INCR
  message_id UUID,    -- client dedup key
  sender_id  TEXT,
  content    BLOB,    -- AES-256 ciphertext
  msg_type   TEXT,
  media_key  TEXT,    -- S3 reference if media
  status     TEXT,
  created_at TIMESTAMP,
  PRIMARY KEY ((conv_id, bucket), seq_id, message_id)
) WITH CLUSTERING ORDER BY (seq_id DESC)
  AND default_time_to_live = 31536000; -- 1 year

Pending Messages Index

CREATE TABLE pending_messages (
  recipient_id TEXT,
  seq_id       BIGINT,
  conv_id      TEXT,
  message_id   UUID,
  PRIMARY KEY ((recipient_id), seq_id)
) WITH CLUSTERING ORDER BY (seq_id ASC)
  AND default_time_to_live = 2592000; -- 30 days

Why this design works at scale

  • Partition by (conv_id, bucket): Bounds partition size to ~1 month of messages
  • Cluster by seq_id DESC: Latest messages retrieved without full scan
  • TTL on table level: Auto-purge old messages — no manual cleanup jobs
  • pending_messages table: Separate table for O(1) offline fetch per recipient
  • Replication factor 3: ONE for writes (fast), QUORUM for reads (consistent)

Scaling Strategy

WebSocket Layer

  • 64-core server with tuned Linux → 640K concurrent connections
  • 400M peak connections ÷ 640K = ~625 WS servers
  • Stateless behind load balancer (consistent hashing by user_id)
  • Redis registry: user:{id} → ws_server_id
  • Auto-scale by monitoring connection count + CPU
  • Multi-region: route user to nearest datacenter

Kafka Partitioning

  • Partition key = conversation_id → ordering preserved per conv
  • Each partition processed by one Chat Service instance (ordering guarantee)
  • 700K events/sec ÷ 100K/broker = ~7 Kafka brokers minimum
  • Replication factor 3 for fault tolerance
  • Retention: 7 days (covers long offline periods)

Cassandra Cluster

  • Write throughput: 10K–50K writes/sec per node
  • 700K msg/sec ÷ 30K = ~24 nodes minimum (add margin → 200 nodes for storage)
  • RF=3: 1.6 PB text × 3 = 4.8 PB raw storage
  • Add nodes: Cassandra re-balances automatically via vnodes
  • Hot partition detection: monitor partition size metrics

Chat Service (Stateless)

  • 100 stateless instances → horizontal scale trivially
  • Each instance consumes from Kafka partition(s)
  • Circuit breaker (Hystrix) prevents cascading failures

Redis Streams

  • One stream per WebSocket server (not per user)
  • Consumer groups + XACK for at-least-once delivery tracking
  • Pending entries claimed after 30s timeout (crash recovery)
  • Stream MAXLEN cap to bound memory usage

Typing Indicators & Last Seen

Typing Indicators — Ephemeral Design

NEVER persist typing events to Cassandra! Typing fires every keystroke — 10+ events/sec per active user. At 500M users, that's billions of writes/sec to the DB. Catastrophic.

Correct Implementation

1. User A starts typing:
   WS Server A receives TYPING_START{conv_id}

2. WS Server A:
   PUBLISH conv:{conv_id}:events "typing:A:start"

3. User B's WS Server:
   Subscribed to conv:{conv_id}:events
   Pushes typing indicator to B's client

4. Client-side timer: 3 seconds no new TYPING_START
   → auto-stop indicator (no TYPING_STOP needed)

5. Rate limit: client sends TYPING_START max 1/2s
   → prevents flooding on fast typists

Last Seen

  • On disconnect: HSET user:{id}:presence last_seen {ts}
  • PostgreSQL: persist last_seen_at for durability (Redis may flush)
  • Client requests: GET /users/{id}/last-seen
  • Privacy check: if target has hidden last seen → return "last seen recently"
  • Mutual privacy rule: cannot see others' if yours is hidden

Senior Q&A — Ordering in Group Chats

Q: "How do you guarantee message ordering when multiple Chat Service instances write to the same group conversation concurrently?"

The trap: Saying "we use Cassandra timestamps" — wall-clock timestamps from different servers can collide or be out of order due to clock skew.

Strong answer:

  • Kafka partition = ordering unit: Partition by conversation_id → all messages for conv123 go to the same Kafka partition → processed by exactly one Chat Service instance at a time → no concurrent writes for same conversation
  • Single logical writer per conversation: The Kafka consumer for that partition is the sequencer — it assigns monotonically increasing seq_id before writing to Cassandra
  • Client reorder buffer: If client receives seq 5 before seq 4 (two delivery paths racing), buffer for 500ms then request resync for gap
  • Cassandra clustering key = seq_id (not timestamp): seq_id is assigned by the sequencer, not the clock
Ordering guarantee: per-conversation, not global. Kafka partition = sequencer. This is the industry-standard approach (Slack, Discord use variants of this).

Senior Q&A — 1000-Member Group Fan-out

Q: "WhatsApp limits groups to 256 members, but your design has to support Telegram-style groups of 1000+ members. How do you handle fanout?"

The trap: Saying "just scale up write-fanout" — 1000 Cassandra writes + 1000 Redis Stream entries per message × 700K msg/sec = catastrophic write amplification.

Strong answer — Hybrid Fanout:

  • For online members (active in last 5 min): Fan-out on write — push to their Redis Stream inbox immediately. Bounded by "active" subset, not full 1000
  • For offline members: Store one message in Cassandra. On reconnect, client reads from group message log (fan-out on read) — fetch messages since last_read_seq
  • Cassandra stores message once: conv_messages table has one row. member_cursors table tracks (conv_id, user_id) → last_read_seq
  • Write amplification now: 1 Cassandra write + N_online Redis entries (N_online ≪ 1000 for large groups)
  • Thundering herd protection: If all 1000 members reconnect simultaneously (post-outage), jitter reconnect delay + rate-limit history fetches + serve from Cassandra replicas
Telegram uses this hybrid model. The key insight: write fanout only to the hot (online) subset; let offline members pull from durable store on reconnect.

Senior Q&A — Offline 7 Days & Message TTL

Q: "A user is offline for 7 days, then reconnects. How do you deliver their 500 pending messages? What if they're offline for 31 days — do messages get lost?"

Strong answer:

7-Day Offline Reconnect

  1. User reconnects → WebSocket established
  2. Client sends SYNC{last_seq_id_seen}
  3. Chat Service queries Cassandra: SELECT * FROM pending_messages WHERE recipient_id=? AND seq_id > ? LIMIT 100
  4. Deliver in batches of 100, wait for client ACK before next batch
  5. After all delivered: send bulk DELIVERY_ACK
  6. Redis Streams: expired after 7 days (TTL), but Cassandra is source of truth — this is fine

31-Day Offline (Beyond TTL)

  • Cassandra TTL = 30 days on pending_messages
  • Messages in messages table: TTL = 1 year (delivered) or 30 days (undelivered)
  • After 30 days: undelivered messages are purged — by design, not a bug
  • Notify user on reconnect: "Some messages from over 30 days ago may not be available"
  • WhatsApp does the same: messages stored on server 30 days max
State this clearly: "Our SLA guarantees delivery if the user reconnects within 30 days. Beyond that, messages are expired by TTL as a storage cost and privacy trade-off."
