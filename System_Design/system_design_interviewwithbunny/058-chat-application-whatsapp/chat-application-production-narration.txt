We are building a chat application like WhatsApp. The goal is simple for users: messages should feel instant, appear in the right order, and never disappear when the network is poor or the receiver is offline. In production, that means we must separate live delivery from durable storage. A live connection makes chat fast. Durable storage makes it reliable.

Start with the basic user problem. During a busy event, many people may send messages at once. Every message can include text, a photo, a group recipient, delivery status, and encryption metadata. The system must accept the message once, save it safely, and deliver it to every intended device. A message should not be lost just because one WebSocket server or mobile network disconnects.

WebSocket is the usual transport for real-time chat. It is a persistent two-way connection. The client can send a message and the server can immediately push a reply, a new incoming message, a typing event, or a delivery acknowledgement. This is more suitable than repeatedly polling an HTTP endpoint because chat needs both directions all the time.

Now look at the high-level design, or HLD. Clients connect through a load balancer to a fleet of WebSocket servers. Those servers own live sockets but do not own message truth. Chat Service validates incoming commands, assigns sequence information, saves the durable message, and creates delivery work. Cassandra stores message history. Redis helps route fast delivery and track temporary presence. Push services wake offline devices. S3 and a CDN handle media.

With many WebSocket servers, we need to know where a user is connected. Redis holds a small connection registry. It maps a user device to the server currently holding its socket. A heartbeat refreshes a short TTL. When a recipient is online, Chat Service looks up this registry and sends delivery work to the correct WebSocket server. If no registry exists, the recipient is offline.

Let us follow a message sent by user A. The sender sends a WebSocket command containing a client-generated message ID. The WebSocket server validates authentication and forwards it to Chat Service. Chat Service assigns a per-conversation sequence and writes the message to Cassandra. Only after the durable write succeeds does it acknowledge the sender. This first acknowledgement is the single tick: the server accepted the message.

Cassandra is a good message store because chat history is append-heavy and usually read by conversation and time. We store messages using a conversation identifier and a time bucket as the partition key, then order rows by server sequence or timestamp. This lets the application load the last fifty messages for one conversation efficiently without scanning every message in the system.

For an online recipient, Chat Service publishes delivery work to Redis Streams. There is usually one stream per WebSocket server rather than one stream per user. The WebSocket server reads its stream through a consumer group and pushes the message over the live socket. Pending entries can be retried after a worker problem. Redis Streams are for fast delivery work; Cassandra remains the durable message source of truth.

Delivery status is based on acknowledgements. Single tick means the server saved the message. Double tick means the recipient device received it. Read means the recipient opened it. Delivery is at least once, so a retry can happen. The message ID makes the operation idempotent. The client keeps a local list of IDs and does not render the same message twice. That gives users an exactly-once experience without pretending the network guarantees exactly-once delivery.

Offline delivery uses a different route. The message is already safe in Cassandra. It remains pending for the recipient. Notification Service sends a small push through FCM or APNs to wake the device. Push is not proof that the message arrived. When the user reconnects, the app loads pending messages from Cassandra in order and sends delivery acknowledgements after the device really receives them.

Presence and typing are different from messages. They are temporary information. A Redis heartbeat and TTL can show a user as online. Redis Pub/Sub can send typing events to the active conversation. It is acceptable if a typing indicator is a little late or disappears. It is not acceptable if a durable message disappears, so presence must never be used as the source of truth for messages.

Groups create fanout work. For a normal group, Chat Service saves the message once and creates a delivery task for each member. This is fanout on write. It produces more writes, but members see the message quickly when they open the chat. For very large groups, such as millions of followers, we would use a hybrid or fanout-on-read design to avoid creating millions of delivery tasks immediately.

Media is a separate flow. Photos and videos should not travel through the normal WebSocket message channel. The client requests a short-lived pre-signed upload URL, uploads bytes directly to S3, and then sends a small chat message containing the encrypted media reference. Receivers download through a CDN. This keeps large files away from the Chat Service and the live message path.

End-to-end encryption changes what the server can see. The sender device encrypts the message before it leaves the device. The server stores ciphertext and routes it using metadata such as conversation and recipient IDs. The recipient device decrypts. This protects privacy, but it means the server cannot freely search plaintext messages or perform ordinary content moderation on them.

Now switch to low-level design, or LLD. WebSocketConnectionManager owns live sockets. ChatService owns validation, sequence assignment, and durable message acceptance. MessageRepository owns Cassandra reads and writes. DeliveryRouter decides online versus offline delivery. ConnectionRegistry looks up active devices. Keeping these responsibilities separate prevents one service from becoming a large and fragile collection of unrelated logic.

DeliveryRouter uses the connection registry to choose a path. If the recipient is online, it writes to the Redis Stream owned by the recipient WebSocket server. If the recipient is offline, it keeps the message pending and asks NotificationService to send a push. Both paths use the same message ID, so retries are safe. This is a simple strategy decision based on connection state.

Message order is scoped to a conversation. We do not try to create one global order for every user in the world. Each conversation receives increasing sequence numbers. If a client gets sequence one-oh-one and one-oh-three before one-oh-two, it briefly buffers the later message and renders them in sequence. Sender retries use the same ID, so duplicated network sends do not make duplicated chat bubbles.

Failures are normal. A WebSocket server can crash, but it should not lose durable messages because the messages were already written to Cassandra. Clients reconnect with exponential backoff and small random delay. The new WebSocket server refreshes the Redis registry. Pending messages are fetched from Cassandra. Redis Stream consumer groups can reclaim delivery work from a failed consumer. This is why persistence comes before delivery.

Operate the platform with metrics. Watch delivery latency, open WebSocket connection counts, reconnect rates, Redis Stream pending entries, Cassandra write latency, push success, and group fanout delay. A growing pending backlog tells you delivery workers are not keeping up. A high reconnect rate might mean a regional network issue. Good metrics make the system debuggable when users report delayed messages.

Finally, scale components by their own pressure. WebSocket servers scale by live connection count. Cassandra scales by message writes and history reads. Redis Streams scale by delivery throughput. S3 and the CDN handle media bytes. Kafka can deliver durable events to slower independent systems such as analytics, audit, and search indexing. The complete design gives users a simple experience: send, receive, reconnect, and trust that the conversation is still there.
