📋 Requirements

Opening Script

"The core challenge is not storage — it's generating billions of globally unique short codes without collisions, and serving 100,000+ redirects/sec with sub-5ms latency. The write path is easy; the read path (redirecting) is where the design lives. Let me confirm requirements first."
This opening signals you understand the hard part. Never say "I'd use a database to store a mapping" — that's junior level.

5 Core Components (mention upfront)

1. Short Code Gen
Zookeeper range → Base62 encode. Zero collisions, zero network calls on hot path.
2. Storage Layer
MySQL sharded by short_code hash. Small rows (~500 B), pure point lookups.
3. Redirect Cache
Redis LRU. 80% of traffic served from ~10 GB hot set. Cache-aside pattern.
4. Redirect Type
302 = analytics. 301 = max performance. Mention the trade-off explicitly.
5. Analytics Pipeline — Kafka async decouples click tracking from redirect. ClickHouse aggregates billions of events in seconds.

Base62 Encoding Deep Dive

Why Base62?

  • Chars: 0-9, a-z, A-Z = 62 total
  • All URL-safe — no percent-encoding needed
  • 7 chars = 62⁷ = 3.5 trillion unique codes
  • ~95 years at 100M URLs/day
  • Human-readable and compact in links

Why NOT alternatives?

  • Base64: + and / are not URL-safe
  • UUID: 36 chars — defeats "short" URL purpose
  • MD5 prefix: collision risk 13%+ at 1B URLs
  • Hex: only 16 chars, needs 10+ chars for same space
Input integer: 125 Charset: "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ" 125 ÷ 62 = 2 remainder 1 → charset[1] = '1' 2 ÷ 62 = 0 remainder 2 → charset[2] = '2' Result: "21" → left-padded to 7 chars: "0000021" String toBase62(long id) { char[] chars = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ".toCharArray(); StringBuilder sb = new StringBuilder(); while (id > 0) { sb.append(chars[(int)(id % 62)]); id /= 62; } return sb.reverse().toString(); }

⚙️ LLD Deep Dive

Hash Collision Handling

Birthday paradox: at 1B URLs stored, using 7-char Base62 codes from hash gives ~13% collision probability. Even 0.001% is catastrophic — wrong URL redirects.

Zookeeper Range Eliminates This Entirely

Sequential integers encoded to Base62 are mathematically guaranteed unique. Ranges never overlap (ZK uses atomic compare-and-swap on a global counter node). No DB uniqueness check needed. No retry logic needed.

If Hash-Based (Hypothetical — Interviewer Pushes)

Strategy 1 — Append & Re-hash

On collision: append attempt counter and re-hash.
sha1(longUrl + attempt).substring(0,7)
Max 3 retries; 500 beyond that.

Strategy 2 — Uniqueness Check

SELECT from DB before INSERT to verify not taken. If taken, fall back to counter-based code. Adds 1 DB round-trip per creation (~5ms) — acceptable at 1,157/sec but adds latency tail.

Always close with: "This is exactly why I'd use Zookeeper range allocation — it makes collisions structurally impossible with no retry logic."

301 vs 302 Redirect — The Interview Trap

301 — Moved Permanently

  • Browser caches redirect forever
  • Repeat clicks bypass your server entirely
  • Cannot count those clicks
  • CDN caches indefinitely too
  • Use when: analytics NOT required, max throughput

302 — Found (Temporary)

  • Browser does NOT cache the redirect
  • Every click reaches your server
  • Enables full click tracking
  • Supports expiry enforcement
  • Use when: analytics ARE required
Never say "I'll use 301 to reduce server load" without first asking if analytics are needed. This is a fail — 301 makes click counting impossible for repeat visitors.
410 Gone for expired URLs — not 404. 404 = "never existed." 410 = "existed, but is permanently gone." Clients and crawlers handle them differently. Interviewers test this.

⚡ Optimizations

Rate Limiting Design

Write — POST /shorten

  • Free: 100 URLs/day per user
  • Pro: 10,000 URLs/day
  • Unauthed IP: 10 creates/min
  • Return 429 Too Many Requests

Read — GET /{code}

  • No per-user limit (public redirects)
  • Anti-abuse: 1,000 req/min per IP
  • DDoS: CDN + API Gateway layer

Redis Sliding Window Counter

Key: rl:{userId}:{minute_bucket} Value: integer (INCR) TTL: 60 seconds bucket = floor(currentEpochMs / 60000) key = "rl:" + userId + ":" + bucket count = INCR key if count == 1: EXPIRE key 60 if count > LIMIT: return 429 Too Many Requests
Two-layer defense: API Gateway handles gross limits (Kong, AWS API GW). Redis handles fine-grained per-user limits. Mention both.
⚡ Optimizations

Analytics Service

Core principle: Analytics must NEVER block the redirect. Send 302 first — Kafka publish is fire-and-forget. Acceptable lag: 30–60 seconds for dashboards.

Kafka Click Event

Published after every redirect:
short_code, clicked_at, ip_hashed, country, referrer, user_agent

Topic: url.click.events
Partitioned by short_code (ordering per URL)

ClickHouse Storage

Columnar OLAP — aggregates billions of rows in seconds.
Partition by: toYYYYMM(clicked_at)
Order by: (short_code, clicked_at)

Trending URLs (Advanced Feature)

Kafka → Flink sliding 5-min window → count events per short_code → on threshold: ZADD trending:urls {score} {code} → dashboard reads ZREVRANGE top-10 in O(log n)
Never do: UPDATE url_mappings SET click_count = click_count + 1 — hot URLs (100K+ clicks/sec) cause catastrophic row-level lock contention in MySQL.
⚡ Optimizations

Caching Strategy

Redis — L2 Cache

  • Pattern: Cache-Aside (lazy/pull-through)
  • Eviction: allkeys-lru
  • Working set: ~10–20 GB
  • TTL: match URL expiry (or 24h if no expiry)
  • Key: url:{shortCode} → longUrl

L1 In-Process Cache

  • Caffeine (JVM) in each app server
  • Top 100K hottest URLs in heap
  • Sub-microsecond — faster than Redis network hop
  • Fallback when Redis is degraded

CDN Edge Cache (301 only)

For non-analytics URLs: CDN caches at edge PoPs. Origin never involved for repeat clicks. Essential at 1B RPS scale.

Zipf Distribution

Top 20% of URLs = 80% of traffic. A 10–20 GB Redis cluster absorbs the entire hot working set. >80% cache hit rate.

📈 Scaling

Scaling — Horizontal Sharding

Problem: Single MySQL cannot handle 115K RPS reads + 90 TB across 5 years. Even with read replicas, primary becomes the write bottleneck.

Shard by hash(short_code)

shardIndex = hash(shortCode) % NUM_SHARDS

  • Any redirect → exactly one shard
  • No cross-shard queries needed ever
  • Even distribution via hash
  • 10 shards × 9 TB = manageable

Why NOT shard by user_id?

  • Viral URL on one user → hot shard
  • Marketing campaign = one user's shard overwhelmed
  • Redirect query doesn't know user_id at lookup time
BottleneckSolution
115K RPS readsRedis LRU cache → 80%+ hit rate → MySQL sees only ~20K RPS
90 TB storage10 MySQL shards (RDS Multi-AZ), each ~9 TB
URL expiry cleanupNightly batch: DELETE WHERE expires_at < NOW() - INTERVAL 7 DAYS (batches of 1K rows)
📈 Scaling

Custom Aliases & Expiry

Custom Alias Design

  • Same url_mappings table, same PK column
  • Check uniqueness before insert → 409 Conflict if taken
  • Namespace separation: auto-codes = zero-padded 7 chars; aliases must be ≥ 4 chars and not match that pattern
  • is_custom_alias = TRUE flag for reporting

Expiry Design

  • expires_at TIMESTAMP NULL — NULL = permanent
  • Redis TTL = URL expiry time
  • On cache miss → MySQL → check expires_at < NOW()
  • Return 410 Gone (not 404) for expired
  • Nightly batch cleanup with 7-day grace period
POST /api/v1/urls: {"longUrl":"...","customAlias":"my-link","ttlDays":30}
Conflict response: {"error":"ALIAS_TAKEN","message":"Choose another."}
De-dup is per-user only (check long_url_hash per user_id). Two different users can have separate short codes for the same long URL — for independent analytics tracking.

🎯 Interview Prep

Senior Trap Q&A #1

"How do you prevent hash collisions at scale — what happens when two different long URLs produce the same short code?"

Correct Answer

Use Zookeeper range allocation, not hashing. Sequential integers encoded to Base62 are mathematically unique — there is no collision to prevent. The question assumes MD5/hash-based generation.

If interviewer insists on hash-based (hypothetical)

  • Append attempt counter + re-hash: sha1(longUrl + attempt).substring(0,7)
  • SELECT before INSERT to verify code not already taken
  • Cap at 3 retries; return 500 beyond that
  • Birthday paradox at 1B URLs = 13%+ collision probability — this is why we don't use hashing
Zookeeper failure mode: server holds 1M IDs in memory (~14 min supply). At exhaustion, circuit-break URL creation with 503 rather than risk ID space corruption. Pro-tip: refresh range at 10% remaining threshold.
🎯 Interview Prep

Senior Trap Q&A #2

"How would you handle 301 cache poisoning — a bad actor creates a URL to a safe domain, gets it cached everywhere, then tries to exploit the cached behavior?"

The Problem with 301

Browsers and CDNs cache 301 indefinitely. Once a redirect is cached to a destination, you cannot push an update to those clients. If you need to deactivate a URL, cached clients will continue redirecting to the old destination.

Defense Strategy

  • Use 302 by default — eliminates browser-level permanent caching
  • If using CDN for 301: set Cache-Control: max-age=86400 (24h max)
  • Immutable URL semantics: once created, long_url cannot be changed — only the URL can be deactivated (returns 410)
  • Ownership enforcement: only creator can delete/deactivate
This tests whether you understand CDN caching behavior and prefer immutable URL semantics. Senior engineers design for deactivation — 410 Gone is the correct signal to CDNs to purge the entry.

Senior Trap Q&A #3

"How would you scale this to handle 1 billion redirects per second — 10× the current design?"

What breaks at 1B RPS?

  • Redis tops out at ~100–500M ops/sec
  • MySQL origin sees too many cache misses
  • Single-region: global latency > 10ms target
  • Kafka partition throughput ceiling

Solutions (priority order)

  1. Push redirects to CDN edge (CloudFront / Fastly) — handles 90%+ with zero origin involvement
  2. Multi-region Redis with active-active replication (us-east, eu-west, ap-se)
  3. MySQL → Vitess cluster (50+ shards)
  4. Add Kafka partitions + ClickHouse nodes linearly
Zookeeper range allocation already scales linearly — each server is independent. Write rate at 10× is ~11K/sec (Vitess handles it). ID generation requires no changes at 1B RPS.
