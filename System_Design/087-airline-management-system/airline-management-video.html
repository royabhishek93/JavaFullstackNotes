The Journey: Search to Boarding Pass

Every airline booking follows a precise choreography across distributed systems. Let's trace it end-to-end.

1
Passenger searches — enters origin, destination, date. System queries GDS + internal inventory for available flights and fares.
2
Fare selection — results sorted by price, duration, stops. Pricing engine applies yield management rules in real time.
3
Seat selection — seat map fetched; a soft lock (15 min TTL) placed on chosen seat to prevent double-booking during checkout.
4
Passenger details — name, passport, contact; linked to existing frequent-flyer profile if present.
5
Payment — payment service charges card; on success seat lock upgrades to hard lock (permanent).
6
PNR issued — unique 6-char alphanumeric Passenger Name Record generated; itinerary stored; confirmation email + SMS sent.
7
Online check-in — opens 24h before departure; seat assignment confirmed; boarding pass generated (QR + barcode, BCBP format).
8
Airport ops — gate assignment, baggage tags, crew briefed via ACARS; real-time departure board updated.

Flight Search Flow

Search Request

  • Input: origin, destination, date, passengers, cabin class
  • Validated against IATA airport codes (e.g., DEL, BOM, JFK)
  • Cache key = hash(origin+dest+date+class)
  • Cache TTL: 60 seconds (fares change frequently)

Availability Query

  • Direct flights: query Elasticsearch flights index
  • Connecting flights: graph traversal on route graph
  • GDS fallback: Amadeus / Sabre API for partner airlines
  • Seat count: live query from Seat Inventory Service

Pricing Engine

  • Base fare from GDS or airline inventory
  • Taxes + surcharges appended (YQ, YR fuel levy)
  • Fare classes: Y (full), B, M, Q, ... W (discounted)
  • Dynamic pricing adjusts by load factor & days-to-departure

Sort & Filter

  • Sort: price ↑, duration ↑, departure time
  • Filter: stops, airline, departure window, cabin
  • Results paginated; scroll triggers next GDS page
  • Price guarantee lock: hold fare for 15 min (optional)
💡 Elasticsearch powers full-text route search + geo-distance queries for nearby airports within 100km radius.

Seat Inventory & Locking — Phase 1: Soft Lock

Airlines face the classic distributed reservation problem: two passengers must never land in the same seat.

Seat States

  • AVAILABLE — free to select
  • SOFT_LOCKED — selected, TTL 15 min
  • HARD_LOCKED — paid & confirmed
  • BLOCKED — crew / special use

Soft Lock Mechanism

  • On seat selection → Redis SET seat:{flightId}:{seatId} userId EX 900
  • 900 seconds (15 min) TTL auto-expires stale holds
  • Lua script for atomic check-and-set (no race condition)
  • Only one session can hold a seat key at a time

Seat Map API

  • GET /flights/{id}/seat-map returns grid with state per seat
  • Aircraft config: rows × columns (e.g., Boeing 737: 30×6)
  • Color-coded: window/middle/aisle, emergency exit rows
  • Soft-locked seats shown as "held" to other passengers
  • Countdown timer shown in UI to create urgency
Passenger A selects 14A SETNX seat:AI101:14A → "sessionA" EX 900 → OK (lock acquired) Passenger B selects 14A SETNX seat:AI101:14A → "sessionB" EX 900 → FAIL (seat held) → UI: "Seat no longer available"

Seat Inventory & Locking — Phase 2: Hard Lock

Payment → Hard Lock Promotion

  • Payment service calls Seat Inventory Service with booking ID
  • Transactional update: Redis key deleted + DB row updated atomically
  • DB: UPDATE seats SET status='CONFIRMED', booking_id=? WHERE id=? AND status='SOFT_LOCKED'
  • Optimistic locking: version field incremented
  • If payment fails → soft lock remains until TTL expires naturally

Concurrency Edge Cases

  • Session crash mid-payment → TTL expires → seat freed
  • Double-submit prevention via idempotency key on booking API
  • Race between TTL expiry & payment → DB constraint wins
  • Distributed Redis (Redlock) for multi-region deployments

Two-Phase Flow Summary

Phase 1 — Soft Lock (selection) User selects seat │ ▼ Redis SETNX key EX 900 │ success │ fail ▼ ▼ Show seat locked "Seat taken" UI │ ▼ (15 min TTL starts) Phase 2 — Hard Lock (post-payment) Payment succeeds │ ▼ DB UPDATE + Redis DEL │ ▼ Booking confirmed PNR generated

PNR Generation — Passenger Name Record

What is a PNR?

  • Industry-standard booking reference (IATA standard)
  • 6-character alphanumeric code (A-Z, 0-9 excluding I, O to avoid confusion)
  • Unique per booking per airline; cross-airline via interline PNR
  • Examples: ABC123, X7KP2Q
  • Stored in GDS & airline system; retrievable by name + PNR

PNR Contents (Itinerary)

  • Passenger details (name, contact, passport)
  • Flight segments (flight no, date, origin, destination)
  • Seat assignments per segment
  • Fare basis & ticket number
  • SSR codes: VGML (vegan meal), WCHR (wheelchair), etc.
  • OSI: Other Service Information (VIP, unaccompanied minor)

Generation Algorithm

// Collision-resistant PNR generator function generatePNR(): chars = "ABCDEFGHJKLMNPQRSTUVWXYZ23456789" candidate = random 6-char string from chars // Check uniqueness in DB (very rare collision) while pnr_exists(candidate): candidate = random 6-char string return candidate // ~1 billion unique values // Alternatively: base-36 encode(snowflake_id) // guarantees uniqueness without DB check

Storage & Lookup

  • Primary key in bookings table
  • Redis cache: PNR → booking_id (TTL 24h post-departure)
  • GDS pushes copy to Amadeus/Sabre for interoperability
  • Lookup: surname + PNR (IATA check-in standard)

Overbooking Strategy

Airlines intentionally sell more seats than available because ~5-15% of passengers historically no-show. It's a revenue optimization — not a bug.

How It Works

  • Aircraft has 180 physical seats → system allows 196 bookings (~8-9% overbook)
  • Overbook factor computed by Revenue Management from historical no-show rates per route/season
  • PROTECTED_SEATS field on flight: seats held back for premium pax / upgrades
  • Overbooking disabled within 24h of departure automatically

Volunteer Compensation Protocol

  • At gate: ask for volunteers to take later flight
  • Compensation: travel voucher, meal, hotel, miles
  • If no volunteers: IDB (Involuntary Denied Boarding)
  • IDB rules: EU261 / DOT regulations mandate cash compensation
  • Algorithm selects IDB candidates: latest booking, lowest fare, no connections

Overbooking Model

// Simplified overbooking calculation Input: capacity = 180 seats historical_noshow_rate = 0.08 // 8% std_deviation = 0.03 // Expected no-shows at full booking expected_noshow = 180 × 0.08 = 14.4 // Buffer: 1 std dev above expected overbook_buffer = 180 × (0.08 + 0.03) = 19.8 max_bookings = 180 + floor(overbook_buffer) = 199 seats bookable // Adjusted dynamically as cancellations arrive

Dynamic Pricing & Revenue Management

Yield Management

  • Goal: maximize revenue per available seat mile (RASM)
  • Fare buckets: Y, B, M, H, Q, V, W — each with seat quota
  • As low-fare buckets fill, system opens higher-fare buckets only
  • EMSR (Expected Marginal Seat Revenue) model for optimal allocation

Load Factor Pricing

  • <60% load → promotional fares, discounts
  • 60-80% load → normal fares
  • 80-95% load → premium pricing, no discounts
  • >95% load → highest fare tier only

Time-to-Departure Curve

Days before Fare multiplier departure ──────────── ──────────────── 180+ days 0.6x (early bird) 90 days 0.8x 60 days 1.0x (base) 30 days 1.3x 14 days 1.6x 7 days 2.0x 3 days 2.5x (last minute) 0 days 1.2x (distress sale)

Factors Used

  • Day of week (Fri/Sun peak)
  • Holiday / event calendar
  • Competitor pricing (scraped / GDS monitor)
  • Historical demand patterns (ML model)

Flight Operations

Crew Scheduling

  • Pilots & cabin crew assigned per flight 48h in advance
  • Constraints: rest requirements (FAR/EASA regulations), qualifications per aircraft type, seniority rules
  • Optimization: constraint satisfaction solver (CSP)
  • Disruption recovery: crew swap algorithm on delay/cancel

Gate Assignment

Delay Cascade Management

Miles Accrual

  • Miles credited within 24–72h of flight completion

Cancellation & Refund

Fare Class Rules

  • Non-refundable — Q, V, W class: no cash refund; credit shell only
  • Partially refundable — M, H class: base fare refunded minus cancellation fee
  • Fully refundable — Y, B, J, F class: full refund within 7-10 business days
  • IRCTC-style: cancellation window matters; >7 days = 0% penalty

Credit Shell

  • Non-refundable tickets → credit issued to passenger wallet
  • Valid for 12 months for same airline bookings
  • Stored as CREDIT_SHELL record tied to passenger profile
  • Applied at checkout via payment method selection

Cancellation Flow

Airline-Initiated Cancel

  • Flight cancelled by airline → mandatory full refund (EU261)
  • Auto-rebook on next available flight (opt-in)
  • Compensation: meals, hotel if delay >3h (EU routes)

GDS Integration — Amadeus / Sabre / Travelport

What is a GDS?

  • Global Distribution System — intermediary between airlines and travel agents / OTAs
  • Aggregates inventory from 400+ airlines in one API
  • Big three: Amadeus (Europe), Sabre (Americas), Travelport
  • Charges per-segment booking fee (~$3-5 per booking)

NDC vs EDIFACT

  • EDIFACT (legacy) — 1980s UN data standard; still used by most GDS for airline messaging; binary, complex parsing
  • NDC (New Distribution Capability) — IATA XML standard (2012+); modern REST/XML; supports rich content, bundles, ancillaries
  • Airlines migrating to NDC to bypass GDS fees and personalize offers

GDS Integration Layer

Booking Service │ ▼ GDS Adapter (Strategy pattern) ├── AmadeusAdapter (REST/NDC) ├── SabreAdapter (EDIFACT/SOAP) └── TravelportAdapter AmadeusAdapter: search() → /v2/shopping/flight-offers book() → /v1/booking/flight-orders cancel() → DELETE /v1/booking/flight-orders/{id} Circuit breaker wraps each adapter Fallback: internal inventory only

Inventory Sync

  • Airline pushes availability updates to GDS every 30 sec via AV (Availability) messages
  • GDS notifies airline of external bookings via PNR mirror
  • Reconciliation job runs hourly to detect discrepancies

Scaling Architecture & Key Trade-offs

Search Service Scaling

  • Stateless pods; auto-scale on CPU/RPS (K8s HPA)
  • Elasticsearch cluster: 3 shards × 2 replicas per index
  • CDN-cached results for popular routes (60s TTL)
  • Read replica pool fronted by PgBouncer (connection pooling)

Booking Bottleneck

  • Seat lock = bottleneck: all writes for one flight → same Redis shard
  • Redis Cluster: hash slot per flight_id
  • DB: SELECT FOR UPDATE NOWAIT; backpressure via Kafka queue
  • Cross-region: Redlock adds ~80ms (acceptable for booking path)

Senior Q&A 1 — Overbooking at the Gate

Q: How do you resolve overbooking when no one volunteers to give up their seat?

IDB Selection Algorithm

  • IDB = Involuntary Denied Boarding
  • Rank passengers: latest_booking_time DESC, fare_paid ASC, has_connection DESC
  • Latest bookings + cheapest fare + no onward connections selected first
  • Protected: unaccompanied minors, disabled passengers, medical cases
  • Algorithm runs in Gate Management Service on flight.overbooked.v1 Kafka event

Volunteer Flow (First Attempt)

  • Gate agent announces compensation offer (voucher + hotel + meal)
  • Passengers self-select via kiosk or mobile app in-airport
  • Increasing compensation auction: starts at $200, escalates every 10 min
  • Overbooking closes automatically within 24h of departure

Regulatory Compliance

  • EU261/2004 — cash mandatory: €250 short / €400 medium / €600 long-haul
  • DOT (US) — 200% of one-way fare (max $775) for <4h delay; 400% (max $1,550) longer
  • Compensation auto-calculated and issued as bank transfer or voucher immediately
  • Rebooking offer sent for next available flight via notification service

System Updates

  • Booking status → DENIED_BOARDING
  • Compensation record linked to booking_id
  • GDS notified; new PNR created for rebooking segment
  • Full audit log preserved for regulatory reporting

Senior Q&A 2 — Holiday Search Peak (10× Traffic)

Q: How do you handle 10× normal search traffic during Diwali / Christmas flash sales?

Pre-Emptive Scaling

  • Search is stateless → horizontal pod autoscaling (K8s HPA) on CPU/RPS
  • Elasticsearch scales via replica promotion (no re-indexing needed)
  • Diwali/Christmas windows known in advance → pre-warm caches 2h before
  • Pre-compute top-500 routes; cache results at CDN edge (60s TTL)

Graceful Degradation Layers

  • Layer 1 — extend CDN TTL to 5 min: stale fares, zero DB load for browsing
  • Layer 2 — circuit breaker drops GDS calls; return internal inventory only
  • Layer 3 — shed lowest-priority traffic (fare scraper crawlers via UA detection)
  • Layer 4 — virtual queue: "You're #847 in line" UX for booking flow

Read vs Write Separation

  • Search hits read replicas (5 per region) — fully isolated from booking writes
  • Seat count in search: approximate (cached); exact only at seat selection step
  • Seat inventory lock path unchanged — kept lean as the critical path
  • Rate limiting: 10 searches/sec/IP via API Gateway (prevents fare scraping)

Kafka Backpressure

  • Booking service publishes to Kafka; downstream consumers process at own pace
  • No synchronous fan-out to loyalty/notification during peak
  • DLQ + exponential backoff retry ensures no booking is lost even if consumers lag
  • Monitoring: consumer lag alerts at 10K messages queued

Senior Q&A 3 — PNR Across Airlines (Codeshare)

Q: How does a PNR work when a passenger books through a different airline — interline or codeshare?

Interline PNR Chain

  • Carrier A creates its own PNR (e.g., ABC123 on Air India)
  • Carrier B creates its own PNR (e.g., XY9876 on Lufthansa)
  • Both PNRs contain a cross-reference field pointing to the other
  • GDS (Amadeus) maintains the master itinerary linking all segments
  • Passenger sees one booking reference; airlines see their own PNR internally

Codeshare Specifics

  • Flight AI 4521 is operated by LH 783
  • Marketing carrier (Air India) sells; operating carrier (Lufthansa) flies
  • Seat inventory owned entirely by operating carrier
  • Booking flows through GDS to operating carrier's inventory system
  • Both airlines' systems must hold a PNR record for the passenger

Check-in & Disruptions

  • Each airline's check-in system verifies only its own segment independently
  • Passenger checks in with operating carrier's kiosk/app per leg
  • Disruption coordination via SSR/OSI messages through GDS message layer
  • Rebooking requires cross-airline operations coordination

Technical Flow

Booking Service → GDS (Amadeus) GDS → Carrier A PNR created (ABC123) GDS → Carrier B PNR created (XY9876) GDS links: ABC123 ↔ XY9876 Check-in (Carrier A leg): Carrier A: GET /pnr/ABC123 Validates → boarding pass for leg 1 Check-in (Carrier B leg): Carrier B: GET /pnr/XY9876 Validates → boarding pass for leg 2 Delay on leg 2: GDS broadcasts SSR message → Carrier A Auto-rebooking offer sent via notification svc
