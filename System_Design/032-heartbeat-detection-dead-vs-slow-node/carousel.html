Scenario A — Real Death

Basic heartbeat timeline when Node A actually dies

t=0s  → Node A crashes (OOM / power loss)
↓
t=1–4s → Node B: no PING... missed heartbeat counter climbing
↓
t=5s  → 5 missed heartbeats → mark SUSPECT
↓
t=10s → still silent → declare DEAD, begin failover
↓
t=15s → failover complete, Node B is new primary

Total undetected downtime: 10–15 seconds. Detection is never instant.

Gossip protocol (Cassandra, Consul, Redis Cluster): each node tells 3 random peers/sec. State spreads in O(log N) rounds — 100 nodes fully informed in ~5 rounds (3→9→27→81→100).

5 / 10
Under The Hood

What gossip actually exchanges (Cassandra-style)

10.0.0.1 → { status: UP, generation: 42, version: 1001 }
10.0.0.3 → { status: DOWN, generation: 15, version: 200  }
  • version — increments every heartbeat; stops climbing → node presumed DOWN
  • generation — resets only on restart; distinguishes "just restarted" from "long silent"
  • Merge rule: whichever side has the higher version for a node wins — no coordinator needed
6 / 10
Beyond Binary

Phi Accrual: a suspicion score, not alive/dead

gap = 1.5s
Phi ≈ 2
probably just slow
gap = 3.0s
Phi ≈ 10
almost certainly dead

Tracks the historical mean/stddev of heartbeat intervals and adapts automatically — avoids false positives from Java GC pauses (5–30s). Used by Cassandra and Akka.

7 / 10
Where Engineers Get It Wrong

Three anti-patterns

Timeout too short — GC pause / jitter → false failover → split brain. Fix: raise timeout or use Phi Accrual.
Timeout too high — real crash undetected for too long → real downtime. Fix: lower it, but test vs. real GC/network jitter first.
Declaring dead on 1 missed beat — causes "flapping." Fix: require 3 consecutive missed heartbeats.
R

Redis Sentinel default: 30s down-after-milliseconds — often too slow to catch, yet borderline for GC pauses.

Cheat Sheet

Decision tree: tuning your timeout

Stable network, GC tuned (G1GC/ZGC)? → timeout 3×–5× heartbeat interval
↓
Unpredictable jitter / long GC pauses? → use Phi Accrual instead of fixed timeout
↓
Always require ≥3 consecutive missed heartbeats before declaring dead
"You can never know for certain if a remote node is dead or just slow. Heartbeat detection is a statistical bet: if I haven't heard in N seconds, it's more likely dead than slow. The timeout trades false positives (unnecessary failovers) against false negatives (slow failure detection)."
