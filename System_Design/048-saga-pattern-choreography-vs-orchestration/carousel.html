Saga Pattern

Slide 1 / 10 — The Hook

0 locks

Order placement touches 3 databases — inventory, payment, shipment. 2PC locks all three until the slowest one answers. Saga replaces the lock with local transactions + compensating rollbacks — and eventual, not instant, atomicity.

Each service locks only its own DB. If a step fails, compensating transactions run backward. No coordinator ever freezes the whole system.

The Idempotency Trap

Compensating Transactions Must Be Safe to Retry

BAD "Refund $100" — called twice on retry → user gets $200 back.

GOOD

SET status='REFUNDED', amount=100 WHERE payment_id='pay-123' AND status != 'REFUNDED' -- 2nd call: already REFUNDED → no-op

Dedup pattern: INSERT INTO processed_saga_steps(step_id) ... ON DUPLICATE KEY IGNORE

Semantic Undo, Not Literal Undo

"Remove item from cart" is a compensating action, not a literal DB rollback. Every forward step needs a matching semantic undo step.

Real World

Indian Tech Saga Flows

Swiggy: order → payment → restaurant confirm → driver assign. Restaurant rejects → compensate payment + release driver, in exact reverse order.

PhonePe / Paytm: debit source → convert currency → credit destination. Conversion fails → orchestrator credits source back automatically via Temporal.

Flipkart: flash-sale checkout — reserve inventory → charge → confirm. PaymentFailed → choreography saga releases stock within milliseconds.

Decision Tree & Interview Answer

Quick Reference

2-3 simple linear steps? → Choreography + Kafka events. 5+ steps, branching, retries? → Orchestration + Temporal/Conductor. Either way: every forward step needs an idempotent, semantic compensating step.

"Saga replaces 2PC's distributed lock with a sequence of local transactions. If a step fails, we run compensating transactions to undo completed steps. No distributed lock means no blocking on coordinator failure — at the cost of eventual consistency instead of atomic consistency."
