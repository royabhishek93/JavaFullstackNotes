# Saga Pattern — Choreography vs Orchestration — YouTube Script
Duration: ~10 min | Target: Engineers 3–10 YOE | Episode: 48 of 93

## HOOK (0:00–0:30)
"Order placement touches three services — inventory, payment, shipment — each with its own database. You can't wrap a normal transaction around all three. Your first instinct is two-phase commit, distributed locks, everyone waits for everyone. But one slow service now freezes the whole system. Today I'm showing you the Saga pattern — the alternative every senior engineer reaches for instead of 2PC — and the exact moment engineers pick the wrong saga type and regret it in production."

[Screen cue: Split screen — a "2PC" kitchen manager freezing all chefs, versus a "Saga" relay race baton being passed runner to runner.]

## THE PROBLEM (0:30–2:00)
"Think of it this way. 2PC is like getting all chefs to agree before anyone starts cooking — the kitchen manager gathers everyone, asks 'can you all commit to finishing this dish?', everyone says yes, manager says go. If anyone drops the pan, everyone stops and reverses. Coordinated, but slow — and if the manager faints mid-way, everyone's frozen, holding locks, going nowhere. A Saga is a relay race instead. Runner 1 completes their leg, passes the baton to Runner 2, who passes to Runner 3. If Runner 3 drops the baton, Runner 2 runs backward to undo their leg, then Runner 1 runs backward. Each step is independent — no manager freezing everyone. Formally: a Saga is a sequence of local transactions, where each step publishes an event that triggers the next step. If a step fails, compensating transactions undo the previous steps. The key insight — there's no distributed lock. Each service only locks its own database for its own local transaction. Atomicity becomes eventual: the system eventually converges to either 'all done' or 'all undone' — not instantly atomic, but it never blocks on a coordinator crash."

[Screen cue: Draw the relay-race baton diagram next to the 2PC frozen-chefs diagram, then overlay the formal definition text.]

## THE SOLUTION (2:00–5:00)
"There are two ways to build a saga, and picking the wrong one for your flow is the first mistake. Choreography is event-driven with no central coordinator. Order Service inserts an order as PENDING — a local transaction — then publishes OrderCreated to Kafka. Inventory Service listens, decrements stock — another local transaction — and publishes StockReserved on success or StockReservationFailed on failure. Payment Service listens for StockReserved, debits the account, publishes PaymentCompleted or PaymentFailed. Order Service listens for those events and flips the order to CONFIRMED or CANCELLED. On the unhappy path, if PaymentFailed fires, Inventory Service listens for that same event and runs a compensating transaction — restore the stock it decremented earlier. Nobody is 'in charge' — every service just reacts to events. Orchestration flips this around: a central Saga Orchestrator, a stateful service or workflow engine, calls each step in sequence and tracks a state machine. Step 1: orchestrator calls Inventory — 'reserve stock' — succeeds, move to Step 2. Step 2: orchestrator calls Payment — 'charge user' — fails, insufficient funds. Now the orchestrator itself drives the rollback: it calls Inventory's compensating transaction, 'release the reservation,' and there's no Step 1 to undo further because inventory was the first step. The orchestrator persists its own state — saga_id, current_step, status COMPENSATING, and a list of steps with their compensation actions — so it always knows exactly where it is. Choreography works beautifully for two-to-three step simple flows, like a notification chain: send, track, done. Orchestration is what you reach for once you're past five services with branching logic — the entire flow lives in one place instead of being scattered across a dozen event subscriptions."

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"First trap: choosing choreography for a complex flow. It gives you loose coupling and no single point of failure, sure — but the moment you have more than three or four services all reacting to each other's events, nobody can trace the full flow anymore. You end up grepping through six codebases trying to figure out why an order got stuck, you risk circular event loops, and adding one new service means updating everyone's event subscriptions. That's exactly why orchestration wins for complex, multi-step business flows — the tradeoff is you now have to build and operate the orchestrator itself, and it becomes a new coupling point everyone depends on. Second trap, and this is the one that bites hardest in interviews and in production: non-idempotent compensating transactions. Picture this bad compensating transaction — 'refund $100 to user' — called twice because of a network retry, and now the user has $200 refunded. Completely wrong. The correct version is conditional: 'set payment status=REFUNDED, refund amount=$100 WHERE payment_id=pay-123 AND status != REFUNDED.' Call it twice — the second call finds status already REFUNDED and simply no-ops. The implementation pattern that makes this bulletproof: give every saga step a unique step ID, like saga-456-step-2-compensate, and before processing, insert that ID into a processed_saga_steps table with ON DUPLICATE KEY IGNORE. If it's a duplicate, the step already ran — skip it, return success. Third trap: treating compensation as a literal undo instead of a semantic undo. 'Remove item from cart' is NOT the same as rolling back the original INSERT — you'd lose your audit trail entirely. The correct compensating action is 'mark item as removed,' which keeps the row and its history intact for debugging and compliance later. And in the actual interview conversation, when someone asks you 'order placement deducts inventory, charges the user, and creates a shipment — how do you keep this atomic across three services?' — the answer isn't 2PC. It's: I'd use an orchestration saga, the orchestrator calls reserve-inventory, then charge-payment, then create-shipment in sequence, and if shipment creation fails, it calls payment's compensating transaction first — refund — then inventory's — release. And I wouldn't hand-roll the state machine myself; I'd reach for a workflow engine like Temporal, because it persists every step's state in its own database, so if the orchestrator process itself crashes mid-saga, it resumes exactly where it left off instead of leaving the saga stuck forever. If your team is already on the Netflix stack, Conductor gives you the same durable-execution idea but as a declarative JSON or BPMN workflow instead of code. If you're deep in the Java event-sourcing world, Axon Framework bakes saga support directly into the framework. And if you're all-in on AWS, Step Functions is the managed version of the same orchestrator concept. For the simplest cases — two or three steps — you don't even need a framework; a single saga_status column on the Order table, walking through STARTED, INVENTORY_RESERVED, PAYMENT_DONE, COMPLETED, is enough."

## REAL WORLD (8:00–9:30)
"Think about Swiggy's order flow — place order, charge payment, restaurant confirms, driver gets assigned. If a restaurant rejects the order two minutes in, after the driver's already been tentatively assigned, that's a four-step saga: the compensating transactions have to cancel the payment charge and release the driver assignment, in that exact reverse order — get the sequence wrong and you've got a driver sitting idle waiting for an order that no longer exists. Picture PhonePe or Paytm handling a cross-bank money transfer — debit the source account, convert currency if it's international, credit the destination. If the currency conversion step fails partway through, at say a few hundred thousand transactions a day running through that pipeline, an orchestration saga via a tool like Temporal is what guarantees the source account gets credited back automatically instead of that money just vanishing into a stuck intermediate state. And imagine Flipkart's checkout during a flash sale — reserve inventory, process payment, confirm the order — if payment fails on even a small fraction of a million concurrent checkout attempts, a choreography saga listening for that PaymentFailed event is what releases the reserved stock back into the pool within milliseconds, instead of that inventory sitting locked and unsellable for the rest of the sale."

Five-plus services with branching and retries, reach for orchestration and a real workflow engine like Temporal.
