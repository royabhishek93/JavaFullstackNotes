One Platform. Thousands of Tenants. Zero Cross-Contamination.

Tenant Isolation RLS Silo vs Pool Rate Limiting RBAC Data Residency
  • A single deployment serves multiple customers — each called a tenant
  • The hardest challenge: data isolation — tenant A must never see tenant B's data
  • Three isolation strategies: Silo (DB per tenant), Bridge (schema per tenant), Pool (shared tables + RLS)
  • Default recommendation: schema-per-tenant (balance of cost, isolation, compliance)
  • Tenant identified via subdomain (acme.app.com), JWT claim, or custom header
  • Noisy neighbor is the #1 operational risk — mitigated via rate limits, bulkheads, query timeouts
  • Supported by SAP BTP, AWS, Azure and all major cloud SaaS platforms

Opening Script

"A multitenant SaaS platform is how Slack, Salesforce, and Jira serve thousands of companies from a single deployment. The core challenge is not building the features — it's ensuring tenant A's data is completely invisible to tenant B, even when they share the same database instance."

Real-world examples:

  • Slack: your workspace data never leaks to another company's workspace — schema isolation per org
  • Salesforce: pioneered the Pool model with discriminator columns + row-level security at massive scale
  • Jira (Atlassian Cloud): schema-per-tenant for isolation; migrated from on-premise to SaaS multitenancy
  • GitHub: organization-level tenancy — billing, users, repos all scoped per org with plan enforcement

Clarifying Questions to Ask:

  • How many tenants? Dozens (Silo OK) or 10K+ (Pool/Bridge required)?
  • Compliance requirements? HIPAA/PCI-DSS → must use Silo model
  • Multi-region? Data residency constraints per tenant (GDPR)?
  • Feature differentiation per plan? (free vs pro vs enterprise)
  • Onboarding self-service or provider-managed?

Tiered approach: FREE → Pool  |  PRO → Bridge  |  ENTERPRISE → Silo

Silo Model — DB per Tenant

How it works: Each tenant gets a completely separate RDS instance, provisioned via CDK/Terraform on-demand.

  RDS Instance A        RDS Instance B        RDS Instance C
  (tenant: acme)        (tenant: globex)      (tenant: initech)
  db.t3.medium          db.r6g.large          db.r6g.xlarge
  Multi-AZ: true        Multi-AZ: true        Custom backup policy
  Encrypted at rest     Encrypted at rest     eu-central-1 region

Pros:

  • Complete data isolation — no shared infrastructure at DB layer; satisfies "dedicated environment" audits
  • Compliance: HIPAA, PCI-DSS, FINRA — each tenant has its own encryption key (KMS CMK)
  • Per-tenant backup/restore schedules and independent PITR windows
  • Noisy neighbor: impossible — dedicated compute, IO, and memory per tenant
  • Custom PostgreSQL settings, extensions, and data retention policies per tenant

Cons:

  • Cost: each RDS instance ~$100–$500+/month minimum — only viable for Enterprise pricing
  • Operational overhead: 100 tenants = 100 RDS instances to patch, monitor, and back up
  • Slow provisioning — RDS instance creation takes 5–15 minutes (vs seconds for schema)
  • Dynamic DataSource per tenant — JVM must manage N separate HikariCP connection pools

Pool Model — Shared Tables with tenant_id

How it works: All tenants share identical tables. Every row carries a tenant_id discriminator column.

  CREATE TABLE orders (
    id         BIGSERIAL    PRIMARY KEY,
    tenant_id  VARCHAR(100) NOT NULL,   -- ← discriminator column
    order_no   VARCHAR(50),
    total      DECIMAL(10,2),
    created_at TIMESTAMP    NOT NULL DEFAULT NOW()
  );
  CREATE INDEX idx_orders_tenant ON orders(tenant_id);
  -- Every query MUST include WHERE tenant_id = ?

Pros:

  • Lowest cost — one schema, one migration run, one connection pool for all tenants
  • Simple schema management — one DDL change applies to all tenants simultaneously
  • Scales to millions of tenants in theory — no per-tenant provisioning overhead

Cons & Risks:

  • Data leak risk: one missing WHERE clause exposes every tenant's data simultaneously
  • Noisy neighbor: one tenant's 10M-row table scan degrades performance for all others
  • Table bloat: single table holds all tenant data — heavy vacuum and index maintenance
  • Backup: cannot restore a single tenant without restoring the entire shared database

Row Level Security — PostgreSQL RLS

RLS enforces tenant isolation at the database engine level — even if app code omits the WHERE clause, the DB silently filters rows to the current tenant.

  -- 1. Enable RLS on every shared table
  ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

  -- 2. Policy: rows visible only when tenant_id matches session variable
  CREATE POLICY tenant_isolation ON orders
    FOR ALL TO app_user
    USING (tenant_id = current_setting('app.current_tenant'));

  -- 3. Spring sets the variable at the start of every request:
  --    SET LOCAL app.current_tenant = 'acmecorp';
  --    SET LOCAL = scoped to current transaction, auto-reset on commit/rollback

Spring Boot AOP integration:

  @Before("@within(org.springframework.stereotype.Repository)")
  public void setTenantContext() {
    em.createNativeQuery(
      "SET LOCAL app.current_tenant = '"
      + TenantContextHolder.getTenantId() + "'"
    ).executeUpdate();
  }
  • SET LOCAL scope auto-resets — no stale tenant context between pooled connections
  • Works transparently with Hibernate, JDBC, and native queries
  • Acts as the second line of defense after app-layer tenant filtering
  • Use FORCE ROW LEVEL SECURITY to apply even to table owners / superusers

Tenant Identification — Three Strategies

Strategy 1: Subdomain (Recommended for user-facing SaaS)

  acme.app.com   → tenantId = "acme"
  globex.app.com → tenantId = "globex"

  Route 53: *.app.com → CloudFront (single wildcard record)
  Gateway extracts "acme" from Host header → validates → injects X-Tenant-ID

Strategy 2: JWT Claim (Standard for API consumers)

  JWT payload:
  { "sub": "user-123", "tenantId": "acme", "role": "MANAGER",
    "permissions": ["ORDER_READ", "REPORT_READ"] }
  Lambda authorizer validates token → injects X-Tenant-ID header downstream

Strategy 3: Custom Header (B2B machine-to-machine)

  X-Tenant-ID: acmecorp   ← for service-to-service or API integrations

Spring Boot — TenantContextHolder (ThreadLocal):

  public class TenantContextHolder {
    private static final ThreadLocal<String> TENANT = new ThreadLocal<>();
    public static void set(String t)  { TENANT.set(t); }
    public static String getTenantId(){ return TENANT.get(); }
    public static void clear()        { TENANT.remove(); }  // MUST call in finally
  }

Each tenant has its own independent set of users and roles. A user's role in Tenant A is fully independent of their role in Tenant B.

  { "tenantId": "acme", "userId": "u42", "role": "MANAGER",
    "permissions": ["REPORT_READ", "USER_INVITE", "ORDER_READ"] }

  public List<Report> getReports(@PathVariable String tenantId) { ... }

  • Tenant admin cannot grant permissions beyond what their plan allows

Data Residency & Compliance

GDPR Requirement: EU tenant data must be stored and processed within EU regions only — logs included.

  Tenant signup includes region preference:
  { "tenantId": "acme-eu", "region": "eu-west-1", "plan": "ENTERPRISE" }

  platform.tenants table:
    tenant_id | display_name | home_region  | db_endpoint
    acme-eu   | Acme Europe  | eu-west-1    | eu-rds.proxy.aws.com
    acme-us   | Acme USA     | us-east-1    | us-rds.proxy.aws.com

Per-tenant region routing in Spring Cloud Gateway:

  String region = tenantRegistry.getRegion(tenantId); // "eu-west-1"
  String target = regionEndpointMap.get(region);      // EU service URL
  exchange.getRequest().mutate().header("X-Target-Region", region);

Compliance checklist:

  • GDPR: EU data in EU; right-to-erasure within 30 days; audit log of all data accesses
  • HIPAA: Silo model (dedicated DB); encryption at rest + in transit; BAA with AWS signed
  • SOC 2: CloudTrail, immutable audit logs, access reviews, multi-AZ DR plan tested
  • CCPA: California tenants — consent management, data export API, opt-out flows
  • Encrypt with CMK in tenant's home region KMS — never cross-region key usage

Schema Migration — Flyway Per Tenant

Problem: With 10,000 tenants on schema-per-tenant, a new migration must run on all 10K schemas without downtime.

Expand-Contract Pattern (zero-downtime DDL):

  Release N — Expand (backward-compatible — old app version still works):
    ALTER TABLE orders ADD COLUMN status VARCHAR(50) NULL;

  Background job — batched backfill (no table lock):
    UPDATE orders SET status = 'ACTIVE'
    WHERE status IS NULL LIMIT 1000;
    -- Repeat until done; run across all 10K schemas in parallel

  Release N+1 — App reads new column (DB still has it nullable):
    Old code ignores column; new code uses it — both versions coexist safely

  Release N+2 — Contract (after 100% backfill confirmed complete):
    ALTER TABLE orders ALTER COLUMN status SET NOT NULL;
    -- Safe: all rows populated, no NULLs remain

Parallel migration runner across 10K tenants:

  ExecutorService pool = Executors.newFixedThreadPool(50);
  tenants.forEach(t ->
    pool.submit(() -> flyway(t.getSchema()).migrate()));
  pool.shutdown();
  pool.awaitTermination(30, MINUTES);
  • Each migration must be idempotent — safe to re-run on failure without side effects
  • Failed tenant schemas are logged and retried — never block the entire batch

Feature Flags Per Tenant

Use cases: gradual rollout, beta group, plan-gated features, emergency kill switch for incidents.

  platform.tenant_features table:
  tenant_id | feature_key       | enabled | config_json
  acme      | NEW_DASHBOARD     | true    | {"variant": "v2"}
  globex    | NEW_DASHBOARD     | false   | null
  *         | LEGACY_EXPORT     | true    | null   ← default for all tenants

Spring Boot feature flag service (cached):

  @Service
  public class FeatureFlagService {
    @Cacheable(value = "features", key = "#tenantId + ':' + #feature")
    public boolean isEnabled(String tenantId, String feature) {
      return featureRepo.isEnabled(tenantId, feature)
          .or(() -> featureRepo.isEnabled("*", feature))
          .orElse(false);
    }
  }

  // In controller:
  if (featureFlags.isEnabled(tenantId, "NEW_DASHBOARD")) { ... }
  • Gradual rollout: enable for 5% of tenants; monitor error rate; expand to 25% → 100%
  • Plan-gating: ENTERPRISE-only features check plan + feature flag in combination
  • Kill switch: disable a broken feature for all tenants in seconds — single DB UPDATE
  • Cache with 30s TTL — near-instant propagation without per-request DB hit on hot path

DB Schema DDL + RLS Policy

  -- Platform schema (shared — created once at deployment)
  CREATE TABLE platform.tenants (
    tenant_id     VARCHAR(100) PRIMARY KEY,
    display_name  VARCHAR(255) NOT NULL,
    schema_name   VARCHAR(100) NOT NULL UNIQUE,
    plan          VARCHAR(50)  NOT NULL DEFAULT 'FREE',
    status        VARCHAR(50)  NOT NULL DEFAULT 'PENDING_PROVISIONING',
    home_region   VARCHAR(50)  NOT NULL DEFAULT 'us-east-1',
    subscribed_at TIMESTAMP    NOT NULL DEFAULT NOW(),
    provisioned_at TIMESTAMP
  );

  -- Per-tenant schema (Bridge model — created dynamically per tenant)
  -- After provisioning: SET search_path TO tenant_acme, public;
  CREATE TABLE orders (
    id         BIGSERIAL    PRIMARY KEY,
    order_no   VARCHAR(50)  NOT NULL,
    total      DECIMAL(10,2),
    created_at TIMESTAMP    NOT NULL DEFAULT NOW()
  );
  -- No tenant_id needed — schema boundary provides isolation

  -- Pool model only (shared table): add RLS on top of discriminator column
  ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
  CREATE POLICY tenant_isolation ON orders
    FOR ALL TO app_user
    USING (tenant_id = current_setting('app.current_tenant'));

  -- Grant access for provisioned tenant schema:
  GRANT USAGE ON SCHEMA tenant_acme TO app_user;
  ALTER DEFAULT PRIVILEGES IN SCHEMA tenant_acme
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_user;

Senior Q&A — "One tenant has 10M rows; shared DB is slowing down"

"This is the most common production issue in multitenant SaaS. Here is the escalating response strategy:"

Immediate mitigation (within hours):

  • Apply per-tenant statement_timeout at request level — kills runaway queries within 3–30 seconds
  • Rate limit the tenant via Bucket4j — throttle their request rate without affecting other tenants
  • Add missing indexes on hot query patterns: CREATE INDEX CONCURRENTLY — no table lock

Short-term (within days):

  • Route heavy read workloads for this tenant to a read replica
  • Partition their large table: PARTITION BY RANGE (created_at) — monthly partitions
  • Archive data older than 2 years to S3 + Athena (cold storage, retain queryability)

Long-term upgrade (Silo promotion):

  • Upgrade tenant from Bridge → Silo: provision dedicated RDS, migrate their schema
  • Zero-downtime cutover: dual-write both schemas → verify sync → flip search_path → decommission old
  • Tenant pays Enterprise pricing; dedicated instance cost is justified by contract value

Senior Q&A — "Enterprise customer requires EU data residency"

"A German enterprise signs up. Their legal team says: all data must stay in EU, logs included. No US-region processing allowed."

Architecture response:

  1. Tenant record: home_region = "eu-west-1"

  2. DNS + routing:
     acme-de.app.com → Route 53 Geo-routing → eu-west-1 CloudFront + API GW
     (Never routes EU requests through US PoPs via Lambda@Edge processing)

  3. Dedicated EU RDS:
     Schema provisioned in Frankfurt RDS cluster (eu-central-1)
     OR dedicated Silo RDS instance in eu-west-1 for full isolation

  4. All logs stay in EU:
     CloudWatch log group in eu-west-1
     S3 audit logs → Frankfurt bucket with WORM Object Lock policy

  5. Auth: separate Cognito User Pool in eu-west-1
     (not the US pool — JWT issuance stays in EU)

  6. All async background jobs execute in eu-west-1 ECS cluster only
  • Sign AWS Data Processing Addendum (DPA) — required for GDPR controller/processor relationship
  • Encrypt with CMK in eu-west-1 KMS — never reference cross-region keys
  • CloudTrail + VPC Flow Logs → S3 in eu-west-1 only; no replication to US

Senior Q&A — "Schema migration for 10K tenants, zero downtime"

"New version adds a NOT NULL column to the orders table. 10,000 tenant schemas. No maintenance window. How do you do it?"

Expand-Contract Pattern — three-release deployment:

  Release N — Expand (backward-compatible — old app still runs):
    ALTER TABLE orders ADD COLUMN status VARCHAR(50) NULL;
    -- Old code: ignores the column entirely. New code: writes it.

  Between releases — Backfill (no locks, batched):
    UPDATE orders SET status = 'ACTIVE'
    WHERE status IS NULL LIMIT 1000;
    -- Scheduled job, runs across all 10K schemas via 50-thread pool
    -- Fully idempotent; safe to re-run

  Release N+1 — App reads column (still nullable in DB):
    Both old and new app versions deployed; both work correctly

  Release N+2 — Contract (all rows confirmed backfilled):
    ALTER TABLE orders ALTER COLUMN status SET NOT NULL;
    -- No data hazard: every row populated; constraint enforced cleanly
  • Parallel Flyway across 10K schemas with 50-thread pool: ~15 min total
  • Each schema tracks its own Flyway history table — independent versioning
  • Failed schemas are logged and retried; idempotency guarantees no double-apply
  • Alert if >1% of tenant migrations fail — halt batch, investigate before continuing

Four key architectural decisions to remember:

  • Schema-per-tenant as default — upgradable to Silo without changing application code
  • RLS as second line of defense — isolation enforced at DB engine, not just app layer
