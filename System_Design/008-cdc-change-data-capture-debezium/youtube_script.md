# Change Data Capture with Debezium — YouTube Script
Duration: ~10 min | Target: Engineers 3–10 YOE | Episode: 9 of 20

## HOOK (0:00–0:30)
"Your application writes to Postgres, then publishes a Kafka event right after — two separate operations. The moment Kafka is unavailable for even one hundred milliseconds during that gap, your database and your downstream services are now permanently out of sync, and nothing in your code will ever tell you that happened. Today I'm showing you Change Data Capture with Debezium — the technique that makes this class of bug structurally impossible, without touching a single line of your application code."

[Screen cue: A two-step diagram — DB write ✓, Kafka publish ✗ — with a red "OUT OF SYNC, FOREVER" label.]

## THE PROBLEM (0:30–2:00)
"Think about it this way — imagine your database is a busy kitchen, and every chef is required by regulation to write down exactly what they did. That's the Write-Ahead Log, the WAL — Postgres writes every change there BEFORE applying it to the actual table, purely so it can recover after a crash. Debezium's trick is simple: it connects to Postgres as if it were just another read replica, taps into that same WAL stream, and converts every INSERT, UPDATE, and DELETE into a structured Kafka event. You never touch your application code, and it doesn't matter where the change came from — your Java service, a migration script, or a DBA running a hotfix directly on the database — Debezium sees all of it, because it's reading the log, not intercepting your app."

[Screen cue: Draw Postgres → WAL → Debezium connector → Kafka, with a chef-writing-a-logbook visual metaphor fading into the technical diagram.]

## THE SOLUTION (2:00–5:00)
"Now watch what happens when an order gets placed. An INSERT into the orders table generates a WAL entry with the before-and-after state of that row. Debezium reads that entry through Postgres's logical decoding plugin and publishes it to a Kafka topic named something like postgres-dot-public-dot-orders, with an op code — 'c' for create, 'u' for update, 'd' for delete. From there, ANY number of independent consumers can react: an Elasticsearch sync consumer upserts the order into your search index within about a hundred milliseconds; a Redis consumer deletes the stale cache entry so the next read repopulates it fresh; an analytics loader batches events into a data warehouse every fifteen minutes; and an audit log consumer appends every single change to an immutable compliance record. One WAL stream, any number of downstream systems, all staying in sync automatically. And when Debezium first connects to an existing database with, say, ten million rows, it runs an initial snapshot — reading the whole table once, publishing each row as a 'read' event — before switching over to live WAL streaming, so you get both the historical backfill and the ongoing stream with zero gaps."

[Screen cue: Draw one Kafka topic fanning out to four consumers — Elasticsearch, Redis, Analytics warehouse, Audit log — each with its own lag number labeled.]

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"Here's the trap that CDC alone doesn't fully solve: you still need your DB write and your published event to be logically atomic, and raw CDC just streams whatever's in the table — it doesn't give you control over the event's shape or routing. The fix is the Outbox Pattern: instead of publishing to Kafka directly, your application writes an extra row into an 'outbox' table, in the exact SAME database transaction as the business write. Either both the order AND the outbox row commit together, or neither does — true atomicity, enforced by the database itself, not by hoping two separate systems both succeed. Debezium then picks up that outbox table's inserts exactly like any other table, and Debezium's Outbox Router transform routes the event to the right Kafka topic based on the event type, using the aggregate ID as the Kafka key so all events for the same order land on the same partition, preserving order. Second trap, and this one bites teams operationally: Debezium tracks its position using a Postgres replication slot, and if your Kafka consumer falls behind or dies, that slot's WAL backlog keeps growing — and Postgres literally cannot reclaim that WAL disk space until the slot catches up. I've seen this fill a production disk. The fix is monitoring `pg_replication_slots` for slot lag directly, alerting when it crosses roughly five hundred megabytes, and having a documented runbook: if it's a genuine emergency, you drop the slot to save the database and re-run Debezium's initial snapshot to resync from scratch."

[Screen cue: Split diagram — the outbox pattern (one atomic DB transaction containing both the order row and the outbox row), then a disk-usage graph climbing toward 100% labeled "replication slot backlog".]

## REAL WORLD (8:00–9:30)
"Think about a payments platform like PhonePe or Paytm — CDC streams every balance change from the accounts table straight to a fraud-detection service in real time, well under two hundred milliseconds, without the payment service needing to know fraud detection even exists. Think about Flipkart or Myntra keeping a product search index in sync — CDC from the products and orders tables feeds Elasticsearch so search results reflect the latest price and stock instantly, and feeds a Redis cache invalidator so a stock-out event clears the cache the moment it happens, no application code changes required. And think about a centralized audit-logging setup, similar to what a Swiggy or Zomato-scale platform would run — CDC captures every single database change across many services automatically, building a compliance-grade 'who changed what, when' record without every team having to remember to write audit-log code by hand."
