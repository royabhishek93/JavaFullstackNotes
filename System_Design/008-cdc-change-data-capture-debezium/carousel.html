Snapshot Mode

Handling Existing Data

Phase 1 — Snapshot: read the whole table once, publish each row as a "read" event.

Phase 2 — Streaming: switch to live WAL streaming from that point, zero gaps, zero data loss.

The Outbox Pattern

True Atomicity

Same DB transaction: INSERT orders + INSERT outbox. Both commit or neither does.

Debezium streams the outbox table like any other — the Outbox Router routes by event type, keyed by aggregate ID for ordering.

Replication Slot Lag

The #1 Operational Trap

If the Kafka consumer falls behind, Postgres cannot reclaim WAL disk space until the slot catches up.

✓ Alert above ~500MB   ✕ Emergency >5GB — drop slot, re-snapshot

Decision Tree & Interview Answer

Quick Reference

Need atomicity with your own event schema? → Outbox + CDC. Can't touch legacy app code? → Raw CDC. Simple, low-scale? → Polling is fine.

"CDC with Debezium reads PostgreSQL's Write-Ahead Log — the same mechanism used for crash recovery — and publishes every INSERT, UPDATE, and DELETE as a Kafka event, solving the dual-write atomicity problem without changing a single line of application code."
