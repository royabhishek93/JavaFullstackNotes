# Distributed Transactions & Saga Pattern — YouTube Script
Duration: ~10 min | Target: Engineers 3–10 YOE | Episode: 5 of 20

## HOOK (0:00–0:30)
"Three microservices — Order, Inventory, Payment — and a coordinator that crashes exactly between Phase 1 and Phase 2 of a two-phase commit. The result: two services hold locks forever, waiting for a COMMIT message that will never arrive. This isn't a hypothetical — it's exactly why two-phase commit is banned in most microservice architectures today. Today I'll show you the Saga pattern that replaced it, and the 'lost update' bug that catches almost every team that implements it for the first time."

[Screen cue: Diagram of 3 services with a coordinator icon that suddenly shows a "crash" spark between two arrows.]

## THE PROBLEM (0:30–2:00)
"Think about it this way — @Transactional in Spring Boot works by grabbing ONE database connection and wrapping your SQL in a single begin-commit block. But in microservices, Order Service has its own database, Inventory Service has its own database, Payment Service has its own database. @Transactional has zero visibility into what Payment Service's database is doing — there's no magic annotation that atomically commits or rolls back across three separate databases. The old-school answer was two-phase commit: a coordinator asks every participant 'can you commit?' in Phase 1, and if everyone says yes, sends 'commit' to everyone in Phase 2. But if the coordinator crashes between those two phases, the participants that already said yes are stuck holding locks forever — this is a blocking protocol, and it simply doesn't survive real-world network partitions at microservice scale."

[Screen cue: Draw the 2PC prepare/commit sequence, then freeze-frame on the crash moment with a red "STUCK" label on two of the three services.]

## THE SOLUTION (2:00–5:00)
"Now watch what happens when you use the Saga pattern instead. A saga is a sequence of local transactions, each with its OWN compensating transaction that can undo it. If step three fails, you run the compensating action for step two, then step one, and the system returns to a consistent state — no cross-service locks, no coordinator bottleneck. There are two flavors. Choreography is fully event-driven: Order Service creates an order and publishes 'OrderCreated' to Kafka; Inventory Service listens, reserves stock, publishes 'StockReserved'; Payment Service listens, charges the card, publishes 'PaymentCompleted' or 'PaymentFailed.' If payment fails, Inventory Service listens for 'OrderCancelled' and releases the stock it reserved — that release IS the compensating transaction. This is loosely coupled and has no single point of failure, but for a ten-step business flow, tracing what actually happened means chasing events across five different services. Orchestration flips that: a central coordinator, like an Axon Framework Saga class, explicitly sends each command and reacts to each event — reserve stock, then charge payment, then if payment fails, explicitly send 'release stock' and 'cancel order.' You lose a little coupling purity, but you gain one place to see the entire flow, which matters enormously once you have more than two or three steps."

[Screen cue: Draw two side-by-side flows — the choreography event chain (arrows looping between 3 services) vs the orchestration star pattern (1 coordinator issuing commands to 3 services).]

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"Here's a subtle bug that catches almost everyone: publishing a Kafka event and saving to the database are NOT atomic. You save an order to Postgres, then publish 'OrderPlaced' to Kafka — but if Kafka is briefly unavailable at that exact moment, you might have committed the order without ever publishing the event, or worse, published the event before the database transaction actually commits, so a downstream service reads the event and can't find the order yet. The fix is the transactional outbox pattern: write the event to an OUTBOX table in the SAME database transaction as the order itself — now they're truly atomic, both succeed or both fail. A separate relay process polls the outbox every hundred milliseconds and publishes to Kafka, retrying safely if Kafka is briefly down. Now the second trap — sagas provide zero ACID isolation, and intermediate states are visible to other concurrent operations. Imagine Saga A reserves five iPhones, bringing available stock from ten down to five, while payment is still processing. Saga B, running concurrently, sees five available and reserves all five more, bringing stock to zero. Saga A's payment then fails, so it compensates by releasing its five iPhones back — available now shows five, but physically there are zero iPhones left, because Saga B already shipped its five. This is a lost update, a dirty read across sagas. The fix is semantic locking — flag the inventory record as 'processing' so other sagas retry later — or restructure the flow to reserve inventory only AFTER payment succeeds, which avoids holding a reservation during the riskiest step. And the third trap is the hardest one: compensating transactions aren't always possible. If your saga ships a physical package as step three, and step two then fails, you can't call the courier and un-ship a package that's already out for delivery. The fix is ordering your steps so irreversible actions — physical shipment, sending an email — always happen LAST, only after every reversible step has already succeeded, so there's nothing left to compensate."

[Screen cue: Split diagram — the outbox pattern (DB write + outbox row in one transaction, then a relay arrow to Kafka), then the "lost update" timeline showing Saga A and Saga B both touching the same inventory count.]

## REAL WORLD (8:00–9:30)
"Think about Swiggy or Zomato placing an order — restaurant acceptance, inventory/kitchen capacity, and payment charge are exactly the kind of three-step flow that's built as a choreographed saga, with a 'kitchen declined' event triggering a payment refund as the compensating action. Picture Paytm or PhonePe processing a transaction — the transactional outbox pattern is exactly how they'd guarantee that a payment confirmation event is never published to downstream systems unless the ledger update has truly committed first. And think about a Flipkart or Myntra order that's already been handed to a courier — if the warehouse then discovers the item is actually out of stock, they can't un-ship a package in transit, which is precisely the 'compensating transaction not always possible' trap; the real-world fix is a manual return/refund workflow instead of an automatic rollback."
