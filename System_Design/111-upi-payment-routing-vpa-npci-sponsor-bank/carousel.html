The Problem

Two ways to move money — both broken

CREDIT FIRST → money created before debit confirmed = money that never existed
vs.
DEBIT FIRST, CREDIT FAILS → payer's money stuck in limbo, going nowhere
UPI needs a mechanism that guarantees neither of these can happen — permanently

Concept 4 · Idempotency

RRN retry 3
↓ all collapse into ↓
UNIQUE
(rrn)
transactions table
App-level "does RRN exist?" check alone is NOT enough — racing retries can both pass it
Real guarantee = DB-level UNIQUE(rrn) constraint. Loser catches DataIntegrityViolationException → reads winner's row.
RRN plays the exact role of an idempotency key at every hop in the chain

Interview Insight

Two different failure classes. Two different mechanisms.

Retry Problem

Same client resending the same logical payment. Fixed by RRN dedup + UNIQUE(rrn) at the DB.

Consistency Problem

Debit succeeds, credit fails. Fixed by auto-reversal — which itself needs its OWN linked, idempotent RRN so the reversal can't double-credit either.

"Two different failure classes that need two different mechanisms — it's important not to conflate them."

Cheat Sheet

Use it when. Skip it when.

USE two-phase + auto-reversal when:
✓ real-time (seconds) confirmation needed
✓ multiple banks must interoperate via one router
✓ money can never be created early or lost silently
✓ retries expected at every hop
SKIP it (use batch / RTGS) when:
✗ low volume → batch netting is fine (B2B payroll)
✗ high-value transfers justify RTGS overhead
✗ single bank's own ledger — no switch needed at all
"The guarantee has to live in the database constraint." — the interview answer that separates senior from mid-level
