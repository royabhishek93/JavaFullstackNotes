Slide 2 · The Problem

Full Table Scan — The Bottleneck

Without an index, the database has no shortcut. It must open every disk page in the table heap and inspect every row, one by one, until it finds (or rules out) a match.

Slide 4 · Exact-Match Only

Hash Index — O(1) Equality Lookup

Instead of a tree, build a hash map: hash(key) → row pointer. Fastest possible lookup for equality — but gives no ordering at all.

"alice@x.com"
→
hash 0xA3F1
→
bucket[5]
→
row 1041 · O(1)
WHERE email = 'alice@x.com' ✓ O(1) fastest possible WHERE age > 30 ✗ no ordering WHERE age BETWEEN 20 AND 35 ✗ not supported ORDER BY age ✗ not supported -- collisions: bucket becomes linked list; worst case O(N)
  • MySQL InnoDB: no user-created hash index — but Adaptive Hash Index (AHI) auto-built internally for hot B-tree pages
  • MySQL MEMORY engine: supports hash indexes
  • PostgreSQL: supports hash indexes explicitly
  • Redis: its entire data model IS a hash map
  • Practical rule: don't choose hash explicitly — use B-tree, engines optimize internally

Slide 5 · Multi-Column Index

Composite Index — The Left-Prefix Rule

An index on multiple columns together. MySQL can only use consecutive columns starting from the left — it stops at the first column missing from the WHERE clause.

CREATE INDEX idx_orders_status_date ON orders(status, created_at, user_id); -- └first┘ └second┘ └third┘

✓ Can use the index

WHERE status = 'pending' uses (status) WHERE status='pending' AND created_at > '2024' uses (status, created_at) WHERE status='pending' AND created_at > '2024' AND user_id = 42 uses all 3 columns

✗ Cannot use the index

WHERE created_at > '2024' skips leftmost column WHERE user_id = 42 skips both left columns WHERE created_at > '2024' AND user_id = 42 skips leftmost column

Slide 6 · Column Ordering

Equality Before Range — Orders Table Example

Rule: put equality columns before range columns. MySQL stops using the index at the first range column it hits.

BAD order: CREATE INDEX i ON orders(created_at, status); -- WHERE status='pending' -- AND created_at > '2024' -- → uses only created_at (range first), -- then filters status manually SLOW
GOOD order: CREATE INDEX i ON orders(status, created_at); -- WHERE status='pending' -- AND created_at > '2024' -- → uses status (equality) then -- narrows by created_at range FAST

Real example — designing the orders index

orders
SELECT * FROM orders WHERE user_id = 42 AND status = 'pending' AND created_at > '2024-01-01' ORDER BY created_at DESC; CREATE INDEX idx_orders_user_status_date ON orders(user_id, status, created_at); -- 1) user_id : equality, most selective (millions→dozens) -- 2) status : equality, narrows further (~10% pending) -- 3) created_at: range, last — also satisfies ORDER BY

Slide 8 · Traps

Why MySQL Ignores Your Index — & 5 Anti-Patterns

Interview: "Your query has an index but still full-scans — why?"

  • Function on indexed column: WHERE YEAR(created_at)=2024 — tree is sorted by raw value, not the function result. Fix: created_at BETWEEN '2024-01-01' AND '2024-12-31'
  • Low cardinality / >30% of rows match: optimizer decides a full scan beats random index lookups (e.g. status with only 3 values)
  • Missing composite index: separate idx(user_id) + idx(status) may use only one, then filter the rest in memory — a composite (user_id,status) handles both in one traversal

5 Index Anti-Patterns

  • 1. Index on every column — every INSERT updates every index; 10 indexes = 10x write amplification; index data can exceed table size
  • 2. Duplicate indexes — idx(col1) is redundant once idx(col1,col2) exists; MySQL won't auto-dedupe
  • 3. Function in WHERE on indexed column — WHERE LOWER(email)='x' ignores index on email; fix with functional index ((LOWER(email)))
  • 4. Boolean / low-cardinality column indexed alone — WHERE is_deleted=false matches 95% of rows → useless; use as 2nd column in a composite instead
  • 5. Too many covering indexes — wider indexes need more RAM; only cover your most critical hot queries
