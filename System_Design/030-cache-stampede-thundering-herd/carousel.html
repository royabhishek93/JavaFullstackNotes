Cache Stampede / Thundering Herd — the protection mechanism that becomes the outage.

The Problem

A cache miss at 2 AM with 10 users is harmless. A cache miss at peak traffic with 50K concurrent users is fatal: DB CPU → 100%, connection pool exhausted, every user times out.

Solution 1

Mutex Lock — Serialize the Recompute

SET lock NX EX 30
→
1 query only

green = lock winner (queries DB) · yellow = sleep 100ms, retry, then cache hit

  • Request 1 wins the lock → queries DB → populates cache → releases lock (Lua script, atomic).
  • 49,999 others fail to lock → sleep ~100ms → retry cache → hit.
  • Tradeoff: every non-winner eats +100–200ms latency. If winner crashes, lock TTL (30s) prevents deadlock.
Solution 2

Probabilistic Early Expiry (PER)

Refresh before expiry using randomness — so the stampede moment never arrives.

T=3550s (50s left) → 1 in 500 requests recomputes T=3560s (40s left) → 1 in 200 requests recomputes T=3590s (10s left) → 1 in 50 requests recomputes T=3600s → cache already refreshed. No stampede.

Formula: -delta × beta × log(random()) > remaining_ttl → recompute now.
Typical: delta=0.1 (100ms compute time), beta=1.0.

Result: 1–2 DB queries per hour instead of 50,000 in one second. No stale window. No lock contention.

Solution 3

Stale-While-Revalidate — Two TTLs

0–5 min: FRESH
serve instantly
5–10 min: STALE
serve instantly + async refresh
10 min: HARD
sync recompute
  • First request past soft TTL gets stale value + triggers ONE background refresh.
  • Every other request in that window: instant stale value, zero wait.
  • Result: 1 DB query per refresh cycle, regardless of concurrency. No user ever waits.
Solution 4

Pre-Warming — Beat the Predictable Spike

Cron @ T-60s
→
compute
→
R
cache populated

For known events — ticket sales, product launches — run a scheduled job 60 seconds before the event to populate the cache. The expiry moment never coincides with peak traffic.

Ticket Booking: seat availability cache is warmed before every scheduled sale start, so the worst-case expiry moment (sale start) never happens under a cold cache.

Deep Dive — Where Engineers Get It Wrong

Traps & Anti-Patterns

  • No TTL jitter: 10 leaderboards all set to 3600s expire in sync → 10 stampedes. Fix: 3600 + random(0,300).
  • Missing lock TTL: lock holder crashes → lock never releases → full outage.
  • Releasing a lock you don't own: must use unique UUID + Lua script check-and-delete, not a bare DEL.
  • Mutex on high-traffic paths: 49,999 requests silently absorb +100ms latency each cycle.
  • SWR where staleness is unacceptable: financial/live-price data needs PER, not stale-while-revalidate.
  • Treating predictable spikes as unpredictable: known sale time → pre-warm, don't just rely on reactive locks.

Real World

Where This Shows Up at Scale

  • Flipkart (Big Billion Days): 50K+ concurrent reads/sec on top SKU product pages — mutex + pre-warming prevents synchronized DB hits.
  • Paytm / PhonePe: flash cashback offer goes live at an exact second → classic pre-warming scenario.
  • Zomato: "trending restaurants" tolerates a few minutes of staleness → stale-while-revalidate.
  • Reddit: went down from a trending-post cache expiry storm. Facebook published a paper on thundering herd at Memcached scale.
Decision Tree
Is the spike predictable (sale, launch)? YES → Pre-Warm cache 60s before event NO ↓ Can users tolerate stale data (secs-mins)? YES → Stale-While-Revalidate NO ↓ Is concurrency very high (>10K reqs)? YES → Probabilistic Early Expiry NO → Mutex Lock Always layer: TTL jitter on every write.
"A cache stampede is when your protection mechanism delivers the fatal blow — the solution is to ensure your cache never actually expires during peak load by proactively refreshing it before it does."
