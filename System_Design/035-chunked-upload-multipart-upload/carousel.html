The Problem

One HTTP request, four ways to fail

1. Network Drop
Drops at 990MB of 1GB → server discards everything → client restarts from byte 0.
2. Mobile Speed
4G ≈ 6.25 MB/s → 1GB takes 160 seconds. Odds of zero interruption: low. Expect 3–5 retries.
3. Server Memory
Naive buffering: 10 concurrent uploads = 10GB RAM → OOM crash on an 8GB server.
4. LB Timeout
AWS ALB default timeout: 60s. A 170s upload gets killed before it can ever finish.

The Solution — Step 3

Complete upload & resume after failure

CompleteMultipartUpload: client sends all 103 part numbers + ETags → backend forwards to S3 → S3 stitches parts into one final object.

Resumable uploads

Phone sleeps at 60% (parts 1–60 done). Client stored {uploadId, completedParts, ETags} in localStorage.
On resume: check localStorage → call S3 ListParts to confirm → continue from part 61.
Only ~400MB re-uploaded, not the full 1GB.

Deep Dive — Trap #2

Abandoned uploads cost you money forever

S3 stores incomplete multipart uploads indefinitely by default. A user starts a 1GB upload, quits at part 3 — those parts sit in S3, billed, forever.
Fix — S3 Lifecycle Policy: 
{
  "Rules": [{
    "AbortIncompleteMultipartUpload":
      { "DaysAfterInitiation": 7 }
  }]
}

One rule. Miss it, and thousands of partial uploads quietly inflate your storage bill.

Decision Tree & Interview Quote

What to say when they ask

File < 100MB? → single PUT is fine.
File 100MB – 5GB? → multipart recommended, presigned URLs.
File > 5GB? → multipart REQUIRED, presigned URLs, resumable via localStorage + ListParts.
"For anything over 100MB, use S3 multipart with presigned URLs — your servers never touch the bytes, chunks upload in parallel, and a dropped connection retries one chunk not the whole file."
