Why UPI is Architecturally Unique

The 3-Tier Model

  • PSP (App layer): PhonePe, GPay — routing + UX only, holds no money
  • NPCI Switch: Central router connecting 300+ banks, enforces 30s timeout
  • Banks (CBS): Actually hold and move money — sender + receiver banks
  • Sponsor Bank: TPAPs are not banks — they need Yes Bank / Axis Bank as regulated NPCI connector

PSP Can vs Cannot

  • ✓ Route payment instructions via sponsor bank to NPCI
  • ✓ Resolve VPA to bank account mapping
  • ✓ Query NPCI for transaction status
  • ✗ Cannot hold customer funds
  • ✗ Cannot access bank accounts directly
  • ✗ Cannot see or decrypt UPI PIN — ever

Availability & Durability

  • Uptime: 99.99% — NPCI mandates this for all PSPs
  • Data retention: 7 years (RBI regulatory mandate)
  • Zero data loss: Outbox pattern persists txn before forwarding to NPCI
  • Idempotency: No double-debit on any retry or network failure

Security (Critical)

  • UPI PIN NEVER reaches PSP servers — encrypted on-device via bank SDK
  • Device binding: IMEI + SIM combination tied to registered device
  • All PSP ↔ Sponsor Bank traffic over mutual TLS
  • Amount stored as BIGINT in paise — no floating-point arithmetic
  • Account numbers encrypted at rest — only last 4 digits for display

Regulatory Compliance (RBI / NPCI)

  • KYC verification required before enabling payments
  • Per-transaction limit: ₹1 lakh default (₹5L for verified merchants)
  • 24×7 operation including bank holidays — unlike NEFT/RTGS
  • Reconcile daily with NPCI settlement CSV file
  • Dispute resolution via CMS within T+3 business days

VPA Resolution — The First Step in Every Payment

What is a VPA?

  • Format: user@bankhandle — e.g., alice@oksbi, 9876@paytm
  • Portable: User can change linked bank account at any time — VPA stays the same
  • Resolves to: {bankCode, accountNo, IFSC, user display name}
  • Case-insensitive: stored lowercase in DB and Redis keys

Resolution Flow

1Check Redis key vpa:{vpa} — cache HIT (95%) → return in <1ms
2Cache MISS → query NPCI VPA registry API (~50ms round-trip)
3Store result in Redis with 5-minute TTL
4VPA bank change → immediately DEL Redis key (write-through invalidation)

Why 5-Minute TTL — Not Shorter, Not Longer

  • vs 24h TTL: User changes VPA bank → stale cache → "account not found" failures for up to 24h
  • vs no cache: 10K NPCI API calls/sec at peak → NPCI throttles us immediately
  • 5 min sweet spot: stale recovery in <5min + 95% NPCI call reduction

Redis Key Schema

vpa:alice@oksbi → { bankCode: "SBI", accountNo: "XXXX1234", // partial ifsc: "SBIN0001234", userName: "Alice Kumar" } TTL: 300s txn_dedup:txn_abc123 → "1" TTL: 86400s // 24h dedup window
Pre-warm nightly: batch job refreshes top 1M frequently-used VPAs to eliminate cold-start penalty after Redis restart.

MPIN & 2FA — UPI's Security Architecture

The Golden Rule: PIN Never Leaves the Device

  • Bank SDK renders a custom keyboard overlay — not a standard Android/iOS keyboard
  • PIN encrypted ON-DEVICE using a key only the customer's bank holds
  • Output: encryptedCredential = Encrypt(PIN + timestamp + deviceId + txnId, bankPubKey)
  • PSP receives this blob — PSP cannot decrypt it
  • Blob travels: PSP → Sponsor Bank → NPCI → Sender Bank (HDFC decrypts and validates)

Device Binding (Registration)

1App sends silent SMS from device → verifies this SIM is physically in this device
2Bank registers IMEI + SIM combination as trusted device
3Bank SDK provisions cryptographic key pair on device secure enclave
4User sets UPI PIN — hashed at bank, never stored at PSP

Challenge-Response Flow

Bank SDK on device receives challenge: {txnId, amount, timestamp, nonce} Produces: credential = ENCRYPT( PIN || timestamp || deviceId || txnId, bank_public_key // provisioned at registration ) This blob → PSP → Sponsor Bank → NPCI → HDFC (sender's bank) → HDFC DECRYPTS with its own private key → validates PIN correctness + txnId match → authorizes the debit

Why This Model is Mandatory

  • A single PSP breach cannot compromise PINs — PSP never had them
  • Even PhonePe/Google employees cannot see customer PINs
  • NPCI mandates device-side encryption — regulatory, not optional
Instant fail: "PSP stores and verifies UPI PIN." This shows fundamental misunderstanding of UPI security architecture.

Idempotency — Exactly-Once Semantics Across PSPs

The Problem

  • Mobile retry: user taps "Pay" twice, or app retries on network timeout
  • PSP pod restarts between DB write and NPCI call — does it re-submit?
  • NPCI callback dropped — PSP marks FAILED, but bank has SUCCESS
  • At 10K TPS with 0.1% retry rate = 10 duplicate attempts/sec

Layer 1: Client-Generated txnId

  • Client generates UUID before calling the API, persists locally
  • Server: SET txn_dedup:{txnId} 1 NX EX 86400
  • NX = only set if not exists → atomic check-and-set in Redis
  • Key already exists → return existing txn status, do NOT re-submit to NPCI
  • 24h TTL covers all retry windows + NPCI settlement cycle

Layer 2: Outbox Pattern

-- Atomic: txn record + outbox in same TX BEGIN TRANSACTION; INSERT INTO transactions (txn_id, status, ...) VALUES (...); INSERT INTO outbox_events (txn_id, published) VALUES (..., false); COMMIT; -- Outbox relay (separate process): SELECT * FROM outbox_events WHERE published = false; -- publish to Kafka, then mark published=true

Layer 3: NPCI RRN Dedup

  • NPCI deduplicates on our txnId (their RRN field) at the switch level
  • Bank CBS: duplicate DEBIT with same txnId → returns original result, no re-processing
  • Three independent layers: Redis NX + MySQL PK + NPCI RRN

Settlement & Reconciliation — The T+1 Reality

What "Real-Time" Actually Means

  • User experience: Credit appears instantly in receiver's app balance
  • Actual interbank settlement: T+1 (next business day at RBI)
  • The immediate credit is an internal bank credit — pending RBI settlement
  • NPCI runs net settlement with RBI daily — netting offsets between all banks

Daily Settlement Flow

1Throughout day: individual debit/credit instructions via IMPS (24×7)
2End of day: NPCI computes net position per member bank
3Banks with net debit pay into RBI settlement pool (RTGS)
4Banks with net credit receive from RBI settlement pool
5PSP receives NPCI settlement CSV for nightly reconciliation

PSP Reconciliation

  • Compare our CREDIT_SUCCESS txns vs NPCI settlement file daily
  • In NPCI SUCCESS, not in our DB: missed callback → force-update to SUCCESS, notify customer
  • In our DB as SUCCESS, absent from NPCI: phantom txn → escalate to ops immediately
  • Amount mismatch: critical incident — freeze PSP operations until resolved

Failure Handling — Timeouts, Partial Failures, Auto-Reversal

Scenario 1: NPCI Timeout (30s)

1Update txn status → PENDING in MySQL immediately
2Notify Alice: "Payment processing — do NOT retry"
3ZADD pending_poll {now+30s} txnId → delayed queue in Redis
4Poller calls NPCI status API (idempotent — safe to repeat)
5SUCCESS → update CREDIT_SUCCESS, notify both parties
6FAILED → update FAILED, confirm no debit, allow retry
7PENDING again → backoff: 30s → 1m → 5m → 15m → 1h
8After 24h → TIMEOUT_FINAL, alert ops, open CMS dispute

Scenario 2: Debit OK, Credit Failed

  • Alice's Rs.500 debited from HDFC successfully
  • Bob's bank (Paytm Payments Bank) is temporarily unavailable
  • NPCI cannot complete the credit instruction
  • NPCI auto-reversal: NPCI initiates DEBIT_REVERSAL to HDFC within T+1
  • Our system receives DEBIT_REVERSAL callback → update txn to DEBIT_REVERSED
  • Notify Alice: "Payment failed. Rs.500 reversed within 24–48 hours"

Scenario 3: PSP Pod Crash

  • NPCI SUCCESS callback arrives during pod restart → 5xx → callback dropped
  • Defense 1: Outbox relay on restart re-publishes unpublished events (idempotent)
  • Defense 2: Pending poller catches PENDING → polls NPCI status API
  • Defense 3: Nightly NPCI reconciliation catches any remaining gaps

UPI AutoPay — Recurring Payments & Mandate Lifecycle

What is a UPI Mandate?

  • UMN (Unique Mandate Number): NPCI-issued identifier for the pre-authorization
  • Customer pre-authorizes future debits — no per-transaction PIN required after setup
  • Use cases: SIP investments, Netflix subscriptions, loan EMIs, insurance premiums
  • Frequencies: DAILY, WEEKLY, MONTHLY, YEARLY, ON_DEMAND
  • Max amount cap set at creation — each execution must be ≤ cap

Mandate Lifecycle States

1PENDING_APPROVAL — customer receives mandate approval notification
2ACTIVE — customer approves with UPI PIN (one-time authorization)
3Scheduler triggers execution on due date — no PIN needed per execution
4PAUSED — customer temporarily pauses mandate in app
5CANCELLED — customer or merchant revokes; NPCI notified

Mandate Schema

TABLE mandates ( mandate_id UUID PK, umn VARCHAR UNIQUE, -- NPCI-issued customer_vpa VARCHAR, merchant_vpa VARCHAR, amount BIGINT, -- paise, max cap frequency ENUM(DAILY, WEEKLY, MONTHLY, YEARLY, ON_DEMAND), start_date DATE, end_date DATE, status ENUM(PENDING_APPROVAL, ACTIVE, PAUSED, CANCELLED), last_executed_at TIMESTAMP );

Execution Rules

  • Pre-notification: 24h before execution PSP must notify customer (RBI mandate)
  • Retry window: 7 days if first execution attempt fails
  • NPCI limit: 1 mandate notification per customer per 24h window

Fraud Detection — Velocity, Device Fingerprint, Anomaly

Real-Time Velocity Checks (Redis)

-- Per-user daily counter user_velocity:{userId}:{date} → count TTL: midnight reset Limits enforced: Max 20 payments/min per VPA Max 5 payments/min per device_id Max ₹1L per transaction (NPCI limit) Max ₹2L per day per account If count > threshold → reject with "RATE_LIMIT_EXCEEDED"

Device Fingerprint Signals

  • New device + new VPA + high-value txn in <5min → flag for review
  • Same device_id, multiple IP geographies in 1h → SIM swap alert
  • Device absent from trusted list → require OTP re-verification
  • Root/jailbreak detection via Play Integrity API attestation

Streaming Anomaly Detection (Flink)

  • Kafka payment events → Apache Flink streaming job (sliding 5-min window)
  • Signals computed:
    • TPS spike concentration: % of traffic from top-100 source IPs
    • Rs.1 test transactions spiking → card enumeration pattern
    • New device registrations + immediate high-value collect approvals
    • Single receiver VPA getting >1000 payments/hr → mule account flag
  • Score above threshold → hold txn for async manual review

Diwali Spike vs DDoS

  • Legitimate spike: High total TPS + normal per-user distribution across millions of users
  • DDoS / fraud burst: High TPS concentrated in a small set of source IPs or device_ids
  • Strategy: backpressure legitimate excess into Kafka queue; reject concentrated fraud patterns pre-NPCI

Database Schema — Transactions Table DDL

CREATE TABLE transactions ( txn_id VARCHAR(36) NOT NULL, -- PSP-generated UUID upi_ref_id VARCHAR(50) UNIQUE, -- NPCI-assigned RRN; NULL until NPCI responds sender_vpa VARCHAR(100) NOT NULL, receiver_vpa VARCHAR(100) NOT NULL, amount BIGINT NOT NULL, -- paise: Rs.500 = 50000 status ENUM( 'INITIATED','DEBIT_ATTEMPT','DEBIT_SUCCESS', 'CREDIT_ATTEMPT','CREDIT_SUCCESS', 'DEBIT_REVERSED','FAILED','PENDING','TIMEOUT' ) NOT NULL, bank_response_code VARCHAR(10), -- 00=success, Z9=reversal failure_reason VARCHAR(255), device_id VARCHAR(100), -- fraud signal ip_address VARCHAR(45), -- hashed for privacy created_at TIMESTAMP NOT NULL, settled_at TIMESTAMP NULL, PRIMARY KEY (txn_id) ) ENGINE=InnoDB PARTITION BY HASH(txn_id) PARTITIONS 10; CREATE INDEX idx_sender ON transactions (sender_vpa, created_at DESC); CREATE INDEX idx_receiver ON transactions (receiver_vpa, created_at DESC); CREATE INDEX idx_pending ON transactions (status, created_at) WHERE status IN ('PENDING', 'TIMEOUT');
Shard key = HASH(txn_id) % 10, NOT user_id. Sharding by user_id hot-spots the shard for viral merchants (Flipkart VPA receiving millions of payments). Hash sharding distributes load evenly.

Scaling — 4 Key Bottlenecks at 10B Txns/Month

Bottleneck 1: NPCI Gateway at 10K TPS

  • Stateless NPCI Gateway Service → scale to 50+ pods on Kubernetes HPA during peak
  • Persistent TLS connection pool to sponsor bank: 100 connections per pod (avoid handshake overhead)
  • Kafka partitioned by sender_vpa: 100 partitions = 100 parallel consumers, ordered per user
  • Redis pipeline: dedup check + TTL set in single round-trip (<1ms)

Bottleneck 2: VPA Resolution at 10K/sec

  • Redis cache: 95% hit rate → 500 NPCI calls/sec (vs 10K without)
  • Write-through invalidation: VPA bank change → DEL vpa:{vpa} immediately
  • Nightly pre-warm: refresh top 1M VPAs in Redis to eliminate cold-start
  • Redis cluster: 3 shards × 2 replicas for HA

Bottleneck 3: MySQL Growth (420 TB / 7yr)

  • 10 shards by HASH(txn_id) % 10 — avoids hot-spotting popular merchant VPAs
  • Monthly partitions per shard (84 partitions over 7 years)
  • Archive transactions >12 months → S3 Parquet via nightly job
  • Cold data queries via Athena (SQL on S3); users rarely need >12 months
  • Each shard: ~500 GB hot data; 42 TB cold in S3

Bottleneck 4: Pending Txn Poller

  • 0.1% timeout rate × 10K TPS = 10 new PENDING txns/sec
  • Redis sorted set: ZADD pending_txns {now+30s} txnId
  • Poller: ZRANGEBYSCORE pending_txns 0 {now} → batch poll NPCI
  • Backoff: 30s → 1min → 5min → 15min → 1hr → 24h escalate to ops

Senior Q&A 1 — Bank Timeout: Alice's Money May Have Left Her Account

"NPCI returns TIMEOUT after 30 seconds. Alice's Rs.500 may or may not have been debited. Walk me through your system's response, step by step."

Immediate Actions (T+30s)

1Update txn status → PENDING in MySQL
2Show Alice: "Payment processing — do NOT retry"
3ZADD pending_txns {now+30s} txnId in Redis sorted set

Polling Resolution

4Poller calls NPCI status API with original txnId (idempotent)
5SUCCESS → update CREDIT_SUCCESS → notify Alice + Bob
6FAILED → update FAILED → confirm no debit / reversal → allow retry
7PENDING again → backoff: 30s → 1m → 5m → 15m → 1h
8After 24h → TIMEOUT_FINAL → alert ops → open CMS dispute

The Critical Constraint

NEVER initiate a new payment while the original txnId is PENDING. The bank may have already debited Alice. A second initiation = potential double-debit.
  • Only poll status of the existing txnId — safe and idempotent
  • Bank CBS deduplication on txnId prevents double-processing
  • Only generate a new txnId after confirmed FAILED (never while PENDING)

After 24 Hours Unresolved

  • Mark TIMEOUT_FINAL (terminal state) in MySQL
  • Page on-call ops team immediately via PagerDuty
  • Auto-create CMS dispute reference with NPCI
  • Bank investigation → customer resolution within T+3

Senior Q&A 2 — Duplicate Transaction from Client Retry

"Alice's app crashes mid-payment and auto-retries. The original request already reached your server and was forwarded to NPCI. How do you prevent double-debit?"

Defense 1: Client-Generated txnId (Redis NX)

  • Client generates UUID txnId before the first call; persists to local storage
  • On retry: client sends the exact same txnId
  • Server: SET txn_dedup:{txnId} 1 NX EX 86400
  • NX = only set if not exists → atomic check-and-set, single round-trip
  • Key exists → return existing txn status, do NOT re-submit to NPCI

Defense 2: MySQL Primary Key Constraint

-- txn_id is PRIMARY KEY INSERT INTO transactions (txn_id, ...) VALUES ('txn_abc', ...); -- Duplicate key error on second attempt -- → catch error, return existing row status -- Durable fallback if Redis is unavailable

Defense 3: NPCI RRN Deduplication

  • Even if we submit twice, NPCI deduplicates on txnId (their RRN field)
  • Second identical request → NPCI returns original txn result, no re-processing
  • This is the last-resort layer — should never reach it in normal operation

What NOT To Do

Never generate a new txnId on retry. A new txnId = new transaction. If the original already hit the bank, the customer gets double-debited.
  • App must persist txnId to local storage before the API call
  • On crash-recovery: check local storage for in-flight txnId, poll its status first
  • Only generate a new txnId after the original confirms FAILED or SUCCESS
Three independent layers — Redis NX + MySQL PK + NPCI RRN — provide exactly-once semantics from app all the way to the bank.

Senior Q&A 3 — PSP Cluster Crashes Between Debit and Credit

"Your NPCI Gateway cluster goes down after NPCI debits Alice but before confirming credit to Bob. Alice's money is in limbo. What happens? Who makes the customer whole?"

NPCI Continues Without the PSP

  • NPCI is stateful — it has the debit instruction and tracks the flow independently
  • NPCI attempts to credit Bob's bank independently of PSP state
  • If PSP pod restarts, NPCI retries the result callback (best-effort)
  • If PSP still down after timeout: NPCI records the definitive txn result in its own state
  • If credit succeeded: txn is complete at bank level; PSP just needs to sync up
  • If credit failed: NPCI auto-reversal kicks in — Alice's debit reversed within T+1

PSP Recovery Path

1Cluster restarts — txn is in PENDING state (set before pod crashed)
2Outbox relay on startup: finds unpublished outbox events, re-publishes to Kafka (idempotent)
3Pending poller: finds PENDING txns, calls NPCI status API with txnId
4NPCI returns definitive status → update MySQL + send notifications

Nightly Safety Net

  • Daily NPCI settlement file reconciliation catches any remaining gaps
  • Any txn in NPCI SUCCESS but PSP FAILED → force-correct + notify customer proactively
Key insight: PSP crash doesn't lose money. NPCI and banks hold definitive state. PSP converges to it via polling + nightly reconciliation. Design for convergence, not prevention of failure.

A/B Routing — Multi-Sponsor Bank Strategy

Why Multiple Sponsor Banks?

  • PhonePe uses Yes Bank as sponsor; Yes Bank outage = PhonePe payments down
  • Solution: partner with multiple sponsors (Yes Bank + ICICI Bank)
  • Route across sponsors to eliminate single-point-of-failure
  • Different sponsors have different NPCI throughput quotas — distribute load
  • At 10K TPS, a 2-minute outage = 1.2M failed transactions

Health-Based Routing

1Health check: Monitor sponsor bank API latency + error rate (15s rolling window)
2Split: Route 90% to primary sponsor, 10% to secondary (canary)
3Auto-failover: Primary error rate >5% for 30s → flip to 100% secondary
4Recovery: Gradual shift back 10% → 50% → 90% after primary stabilizes

A/B Routing for Feature Rollouts

  • New UPI 2.0 feature (credit line on UPI) → route 5% of traffic to new flow
  • Feature flag in Redis: ab_flag:{userId} → "new_flow" or "old_flow"
  • Sticky routing: same user always hits same flow within a session
  • Compare success rate + P99 latency across cohorts in ClickHouse dashboards

RRN Namespace per Sponsor Bank

  • Different sponsor banks use different RRN (reference number) formats
  • When routing a txn to a new sponsor, generate a new bank-specific RRN
  • Our internal txnId stays stable — bank RRN is separate
  • Store sponsor_bank_rrn as a distinct column for reconciliation
Multi-sponsor bank routing is production-critical for any tier-1 PSP. It's the difference between a 2-minute bank blip and a customer-visible outage.

5 Instant-Fail Anti-Patterns

  • ✗ "PSP stores and verifies UPI PIN" — PIN is encrypted on-device via bank SDK; PSP never sees it
  • ✗ "PSP directly accesses bank accounts" — always PSP → Sponsor Bank → NPCI → Bank, never direct
  • ✗ "Use Cassandra for transactions" — ACID required; txnId dedup fails with eventual consistency
  • ✗ "On NPCI timeout, retry the payment" — risks double-debit; poll status of original txnId only
  • ✗ "Real-time = instant interbank settlement" — user credit is instant; RBI interbank settlement is T+1
Study order: (1) 3-tier model PSP → Sponsor → NPCI → Banks. (2) PIN security — device SDK, PSP never sees it. (3) TIMEOUT handling — PENDING + polling backoff. (4) Idempotency — client txnId + Redis NX + NPCI RRN. (5) T+1 settlement reality vs instant user credit.
