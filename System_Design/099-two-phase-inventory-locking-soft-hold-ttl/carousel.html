Two-Phase Inventory Locking

Slide 1 / 9 — The Hook

3 min hold →
2-8ms DB lock

A user browsing checkout for 3 minutes shouldn't hold a database row lock for 3 minutes.

Pessimistic Lock = Pool Exhaustion

The Problem

seat F12
FOR UPDATE

SELECT ... FOR UPDATE held for the ENTIRE checkout (30-180s). 500 concurrent buyers on 1 seat = instant connection pool exhaustion.

Phase 1 — Soft Hold

The Solution

R
SET NX EX 600

One atomic Redis command. No DB touched. Self-expires in 10 min if user abandons checkout — zero cleanup code.

Phase 2 — Confirm

Only on Payment Success

INSERT + COMMIT
2-8ms

The ONLY moment a real DB lock exists — single-digit milliseconds, not minutes.

Two Users Race for the Same Seat

NX Resolves It Instantly

Alice's SET arrives first → succeeds. Bob's SET 3ms later → key already exists → NX fails → Bob gets 409 instantly.

No distributed lock manager needed — NX is atomic by Redis's single-threaded design.

The Dangerous Race

Confirm Arrives as TTL Expires

T+598s: Alice's payment responds. T+600s: TTL fires, seat freed. T+600.4s: Carol grabs it. T+601s: Alice's stale confirm arrives.

✕ Naive GET+DEL destroys Carol's legitimate hold.

The Atomic Fix

Lua Check-and-Confirm

if GET(key) == myToken then DEL(key); return 1 else return 0 end

Runs as ONE atomic step — mismatch means reject Alice, Carol's hold stays untouched.

Quick Reference
