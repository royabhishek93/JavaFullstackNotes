🎟️ Booking Flow — Steps 1 & 2: Select & Lock

STEP 1: GET SEAT MAP
User → GET /shows/123/seats
  ├─ Cache hit? → Redis returns in 50ms ✅
  └─ Cache miss → Booking Svc → PostgreSQL → cache update

STEP 2: INITIATE BOOKING (Acquire Row Lock)
User → POST /bookings { showId:123, seatIds:[5] }

  BEGIN TRANSACTION (READ_COMMITTED + FOR UPDATE)
  │
  ├─ SELECT * FROM seat_availability
  │  WHERE show_id=123 AND seat_id=5
  │  FOR UPDATE;          ← Exclusive row lock acquired
  │                       ← User B BLOCKS here if same seat
  │
  ├─ Check status = AVAILABLE?
  │   NO  → ROLLBACK → 409 "Seat already taken"
  │   YES → continue
  │
  ├─ INSERT INTO booking (status=PENDING, expires_at=NOW()+15m)
  ├─ UPDATE seat_availability SET status='RESERVED'
  └─ COMMIT              ← Lock released

Response: { bookingId: 999, expiresIn: "15 minutes" }

💳 Booking Flow — Steps 3 & 4: Payment & Real-Time

STEP 3: CONFIRM PAYMENT
User → POST /bookings/999/confirm { paymentToken }
  │
  ├─ Validate booking not expired → YES → release seat, 410
  │
  ├─ Call Stripe.charge($50, idempotency_key="booking_999_1")
  │   FAIL  → release seat, mark FAILED, return error
  │   SUCCESS → continue
  │
  ├─ BEGIN TRANSACTION
  │   UPDATE booking SET status='CONFIRMED', payment_id='stripe_123'
  │   UPDATE seat_availability SET status='BOOKED'
  │   UPDATE show SET available_seats = available_seats - 1
  │   COMMIT
  │
  └─ Async (Kafka + Redis):
      ├─ Kafka.publish("booking.confirmed") → email/SMS workers
      ├─ Redis.publish("show:123:update")   → WebSocket servers
      └─ Generate QR ticket

STEP 4: REAL-TIME UPDATE (Other Users)
Redis Pub/Sub "show:123:update"
  → 3 WebSocket server instances
    → Push to all browsers watching Show 123
      → User B sees: Seat 5 now BOOKED (real-time)

⏰ Step 5: Seat Expiry & Background Cleanup

SCENARIO: User selected seats but abandoned checkout

Timeline:
  10:00 AM → User clicks seat 5
             booking.status = PENDING
             seat_availability.reserved_until = 10:15 AM

  10:16 AM → Cron Job runs (every 5 minutes)
             ┌─────────────────────────────────────────┐
             │ SELECT booking_id FROM booking           │
             │ WHERE status = 'PENDING'                 │
             │   AND expires_at < NOW()                │
             └──────────────┬──────────────────────────┘
                            │ For each expired booking:
                            ▼
             BEGIN TRANSACTION
               UPDATE seat_availability
               SET status = 'AVAILABLE', reserved_until = NULL
               WHERE booking_id IN (...)

               UPDATE booking
               SET status = 'CANCELLED'
               WHERE booking_id IN (...)
             COMMIT
✅ Seats automatically freed — other users can book
✅ No orphaned RESERVED seats accumulating in DB
✅ Redis updated via Pub/Sub → real-time UI refresh
💡 Alternative: Redis TTL key triggers expiry event (sub-second precision)

🔐 Concurrency Control — Pessimistic Locking

USER A                              USER B
 │ Click Seat 5                      │ Click Seat 5
 ▼                                   ▼
BEGIN TX                           BEGIN TX
 │                                   │
 │ SELECT * FROM seat_availability   │ SELECT * FROM seat_availability
 │ WHERE show_id=123 AND seat_id=5   │ WHERE show_id=123 AND seat_id=5
 │ FOR UPDATE;                       │ FOR UPDATE;
 │                                   │
 ▼ LOCK ACQUIRED ✅                  ▼ BLOCKED ⏳ (waits for User A)
 │
 │ status = AVAILABLE? YES
 │ UPDATE → status = 'RESERVED'
 ▼
COMMIT  ← lock released
                                    │ UNBLOCKED
                                    ▼ LOCK ACQUIRED
                                    │ status = AVAILABLE? NO ❌
                                    │ ROLLBACK
                                    ▼ Error: "Seat already taken"
Key SQL: SELECT * FROM seat_availability WHERE show_id=? AND seat_id=? FOR UPDATE; — acquires exclusive row lock; competing transactions must wait until commit/rollback.

⚖️ Optimistic vs Pessimistic Locking

Pessimistic — FOR UPDATE

SELECT * FROM seat_availability
WHERE seat_id = 5
FOR UPDATE;
-- User B BLOCKS until commit
✅ Safe for high-contention seats (hot show)
✅ No retry logic needed
❌ Lock wait → reduced throughput
❌ Deadlock risk under extreme concurrency

Optimistic — Version Column

UPDATE seat_availability
SET status='BOOKED',
    version = version + 1
WHERE seat_id = 5
  AND version = 10;
-- 0 rows affected = retry
✅ No blocking — better throughput
✅ Great for low-contention scenarios
❌ Requires retry on conflict (ABA problem)
❌ Starvation risk if contention is high
Production choice: Pessimistic (FOR UPDATE) for seat booking — contention is expected; fairness matters. Optimistic for show-level counters where conflicts are rare.

💳 Payment Atomicity — 3-Phase Commit

PHASE 1: RESERVE          PHASE 2: CHARGE          PHASE 3: CONFIRM
──────────────────        ───────────────          ─────────────────
 booking = PENDING    →    Stripe.charge()    →    booking = CONFIRMED
 seat    = RESERVED        idempotency_key         seat    = BOOKED
 expires = NOW()+15m       webhook registered      Kafka event
                                                   QR ticket generated

ROLLBACK TRIGGERS:
 Phase 1: seat taken, show full
 Phase 2: payment declined, timeout → exponential retry
 Phase 3: server crash → webhook retries 10x (Stripe)

FAILURE: Payment Success, Server Crashes Before Confirm
 Solution: Stripe webhook POST /webhook/payment-success
           Server recovers, checks idempotency_key
           Re-runs Phase 3 idempotently

DOUBLE SUBMISSION (user clicks Pay twice):
 Request 1: idempotency_key = "booking_999_attempt_1"
 Request 2: idempotency_key = "booking_999_attempt_1" ← SAME
 Result: Stripe deduplicates → charged once only ✅

NETWORK TIMEOUT (response lost):
 Client polls: GET /bookings/999/status → checks actual state

⚠️ Payment Failure Scenarios & Handling

1. Payment declined → Release seat (AVAILABLE), return 402. User can retry with another card.
2. Payment gateway timeout → Poll gateway status with exponential backoff (1s, 2s, 4s, max 3 attempts). Release seat only if confirmed failed.
3. Payment success, server crash → Stripe retries webhook up to 10x with exponential backoff. Server recovers, processes ticket idempotently.
4. Seat hold expired mid-payment → Validate booking not expired before charging. Return 410 Gone, user must restart.
5. Duplicate charge (user refresh) → Idempotency key = "booking_{id}_attempt_{n}". Same key = same result, no double charge.
6. Cancellation refund → Policy: >4h before showtime = full refund. Stripe refund API → wallet/original method within 24h.
Saga pattern: Each phase has a compensating transaction. Reserve → compensate = release. Charge → compensate = refund. This prevents money-without-ticket scenarios.

🧠 Redis Cache Key Design

# 1. SEARCH RESULTS (Hot Data)
Key:   "search:city:{cityId}:date:{date}"
Value: [movieId:123, movieId:456, ...]
TTL:   300s (5 mins)

# 2. SEAT MAP (Critical — Write-Through)
Key:   "show:{showId}:seats"
Value: { "seat_1":"AVAILABLE", "seat_5":"RESERVED", ... }
TTL:   30s  ← stale is acceptable; source of truth is DB

# 3. SHOW AVAILABILITY COUNTER
Key:   "show:{showId}:available_seats"
Value: 150
TTL:   30s

# 4. USER SESSION / CART
Key:   "session:{userId}"
Value: { cart:[seat_5], expiresAt:... }
TTL:   900s (15 mins)

# INVALIDATION ON BOOKING:
Event: Seat booked
  → Redis HSET show:{id}:seats seat_5 "BOOKED"
  → Redis DECR show:{id}:available_seats
  → Redis PUBLISH show:{id}:update → WebSocket servers

🗄️ Why Three Different Databases?

DatabaseUsed ForWhy This DB
PostgreSQLBookings, Payments, SeatsACID strict · FOR UPDATE · SERIALIZABLE · JSONB
MySQLMovies, Theaters, ScreensRead-heavy · 10+ replicas · mature replication · catalog data
ElasticsearchSearch & Geo FiltersFull-text · faceted filters · geo-distance · no joins
Q: Why not one DB for everything?
✅ Different consistency needs: ACID for booking, eventual OK for search
✅ Workload fit: Postgres for concurrent writes, MySQL for read scale, ES for text search
✅ Blast radius isolation: search outage doesn't break booking
✅ Cost: ES search is 10× faster than SQL LIKE; MySQL replicas cheaper for static data
⚠️ Trade-off: more ops complexity + need MySQL→ES sync via Kafka (~5s lag — acceptable)

🗃️ Schema — booking & seat_availability (PostgreSQL)

CREATE TABLE booking (
    booking_id   BIGINT PRIMARY KEY,
    user_id      BIGINT NOT NULL,
    show_id      BIGINT NOT NULL,
    total_seats  INT,
    total_price  DECIMAL(12,2),
    booking_status ENUM('PENDING','CONFIRMED','CANCELLED'),
    created_at   TIMESTAMP,
    expires_at   TIMESTAMP,       -- 15-min seat hold
    payment_id   VARCHAR(255),    -- nullable until confirmed
    FOREIGN KEY (user_id) REFERENCES users(user_id),
    FOREIGN KEY (show_id) REFERENCES shows(show_id),
    INDEX idx_user_show (user_id, show_id),
    INDEX idx_expires_at (expires_at)  -- expiry cron query
);

CREATE TABLE seat_availability (
    show_id        BIGINT,
    seat_id        BIGINT,
    status         ENUM('AVAILABLE','RESERVED','BOOKED'),
    reserved_until TIMESTAMP,     -- cleared on commit/expiry
    booking_id     BIGINT,
    PRIMARY KEY (show_id, seat_id),
    FOREIGN KEY (booking_id) REFERENCES booking(booking_id),
    INDEX idx_status (status)
);

CREATE TABLE booking_seat (
    booking_seat_id BIGINT PRIMARY KEY,
    booking_id BIGINT,
    seat_id    BIGINT,
    FOREIGN KEY (booking_id) REFERENCES booking(booking_id)
        ON DELETE CASCADE,
    UNIQUE (booking_id, seat_id)
);

🔬 Isolation Levels — Which One for Booking?

LevelDirty ReadNon-RepeatablePhantomPerformance
READ_UNCOMMITTEDYES ❌YES ❌YES ❌⚡⚡⚡
READ_COMMITTEDNo ✅YES ❌YES ❌⚡⚡
REPEATABLE_READNo ✅No ✅YES (MySQL)⚡
SERIALIZABLENo ✅No ✅No ✅🐢
Production answer: READ_COMMITTED + FOR UPDATE — NOT full SERIALIZABLE
✅ FOR UPDATE acquires exclusive row lock — User B blocks until User A commits
✅ Prevents the actual race condition (double-booking specific seat rows)
❌ SERIALIZABLE is 5× slower: 2k vs 10k bookings/sec; deadlock rate 5–10%
❌ SERIALIZABLE prevents phantom reads we don't have (we lock specific rows, not ranges)
💡 Stripe, Google Cloud Spanner, PostgreSQL 98% of real cases → READ_COMMITTED + FOR UPDATE

🎤 Senior Interview Q&A — Part 1

Q: How do you prevent double-booking?
Row-level lock with FOR UPDATE inside a DB transaction. Only one transaction holds the lock at a time. Alternative: optimistic locking (version field) for low-contention seats.
Q: Two users pay for the same seat simultaneously — who's charged?
User 1 acquires lock, books, commits. User 2's transaction sees RESERVED and rolls back before hitting the payment gateway — so only User 1 is charged. Payment gateway never gets called for User 2.
Q: Design for 1M users on Avengers release day.
Pre-booking 1 week ahead · Token-bucket rate limiting · 3-tier queue (accept / queue / reject) · Kafka async processing · Redis cache for seat maps (TTL 30s) · CDN for static assets · City-sharded DB · HPA auto-scale booking pods.
Q: How do you keep search < 200ms at scale?
Elasticsearch for full-text + geo filters. Redis cache for popular searches (5 min TTL). MySQL read replicas for catalog. Denormalised schema (no joins). Paginate results (20/page).
