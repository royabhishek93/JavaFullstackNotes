❤️ Likes & Comments System Design

Facebook / Instagram Scale

Redis INCR Idempotency Sharding Cassandra Kafka Counter Cache
Core Insight: Likes and comments look trivially simple — until a viral post receives 100,000 likes/sec on a single counter. The like count is NOT stored in the posts table. These two decisions drive the entire design:
  • Redis counters — atomic INCR, sub-millisecond, handles 1M ops/sec per key
  • Cassandra comment partitions — partition key = postId, all comments in one scan
  • Kafka async notifications — decouple like action from push delivery
  • Bloom filter for liked-by — O(1) check, constant memory regardless of likers
  • Write-back pattern — Redis = hot layer, Cassandra = durable cold layer
Scale Target: Instagram — 500M DAU
Likes/Day: 4.2 billion (48,600/sec avg)

Opening: The Counter Problem

Scenario: Cristiano Ronaldo posts a World Cup celebration photo. Within 24 hours: 50 million likes. Peak rate: 100,000 likes/sec in the first 10 minutes — all hitting a single post ID.

Why This Is Hard

Naive approach:
  UPDATE posts SET like_count = like_count + 1 WHERE post_id = ?

At 100K likes/sec this means:
  → 100K concurrent UPDATE statements on ONE row
  → Database acquires row lock for each UPDATE
  → All 100K requests queue behind the lock
  → Average wait: hundreds of milliseconds
  → Database throughput collapses → 503 errors

What Actually Happens at Scale

  • Row-level locking serializes all like writes — throughput limited to ~1,000/sec
  • Connection pool exhaustion — threads pile up waiting on the lock
  • Timeout cascade — likes start failing, retry storms make it worse
  • The posts table is also serving reads for feed — it's completely overwhelmed
Key Insight: The like count must NOT live in the posts table. It must live in a structure built for atomic counters: Redis INCR.

Functional Requirements

Likes

  • User can like / unlike a post (idempotent)
  • Like count displayed on post (approximate OK)
  • Has-user-liked check before rendering heart icon
  • Notification to post owner on like (async)
  • List of users who liked a post (paginated)
  • Like / unlike a comment

Comments

  • Post, edit, delete a comment on a post
  • Reply to a comment (2-level threading)
  • Paginate comments (cursor-based, 20/page)
  • Load more replies per comment (10/page)
  • Sort: most recent (default) + top by likes
  • Async toxicity filtering on submit

Like Idempotency — One Like Per User

Problem: User double-taps, network retry, or malicious client sends multiple POST /like requests. Each must result in exactly one like — never double-counting.

Implementation: Redis SET + NX

-- Check membership before incrementing (Lua script, atomic):
local key = "liked_by:" .. KEYS[1] .. ":" .. (tonumber(ARGV[1]) % 100)
local already = redis.call('SISMEMBER', key, ARGV[1])

if already == 1 then
  return {0, redis.call('GET', 'likes:' .. KEYS[1])}  -- ALREADY_LIKED
end

redis.call('SADD', key, ARGV[1])
local newCount = redis.call('INCR', 'likes:' .. KEYS[1])
return {1, newCount}  -- SUCCESS

Why Lua Script?

  • Redis executes Lua scripts atomically — no other command can interleave
  • SISMEMBER + SADD + INCR as one unit prevents TOCTOU race condition
  • If two simultaneous like requests arrive, only one succeeds — the other returns ALREADY_LIKED

API Response

POST /v1/posts/{postId}/like
→ 200 OK:       { "likeCount": 843, "hasLiked": true }
→ 409 Conflict: { "error": "ALREADY_LIKED", "likeCount": 843 }

Redis Like Counter Design

Key Schema

likes:{postId}              → STRING  (integer counter, INCR/DECR)
liked_by:{postId}:{n}       → SET     (n = userId % 100, sharded)
comment_likes:{commentId}   → STRING  (integer counter)
comment_count:{postId}      → STRING  (integer counter)
comment_rate:{userId}:{postId} → STRING (rate limit, EX 60 seconds)

Atomic Like Toggle — Lua Script

-- LIKE operation (called on POST /like):
EVAL """
  local liked = redis.call('SISMEMBER', KEYS[2], ARGV[1])
  if liked == 1 then return {-1, redis.call('GET', KEYS[1])} end
  redis.call('SADD', KEYS[2], ARGV[1])
  return {1, redis.call('INCR', KEYS[1])}
""" 2 likes:{postId} liked_by:{postId}:{userId%100} {userId}

-- UNLIKE operation (called on DELETE /like):
EVAL """
  local liked = redis.call('SISMEMBER', KEYS[2], ARGV[1])
  if liked == 0 then return {-1, redis.call('GET', KEYS[1])} end
  redis.call('SREM', KEYS[2], ARGV[1])
  local count = tonumber(redis.call('GET', KEYS[1]))
  if count > 0 then redis.call('DECR', KEYS[1]) end
  return {1, redis.call('GET', KEYS[1])}
""" 2 likes:{postId} liked_by:{postId}:{userId%100} {userId}
Why Redis over DB counter: Redis INCR = atomic, single-threaded, sub-ms. SQL UPDATE with row lock = serialized writes, kills throughput at 100K likes/sec.

Counter Persistence — Write-Back Pattern

The Problem

  • Redis stores live counts — sub-ms reads and writes
  • Redis can lose data on crash (without persistence)
  • Cassandra is durable but slower for counter updates
  • Solution: Redis = hot cache, Cassandra = durable cold store

Write-Back Job (every 5 min)

1. SCAN Redis for keys: likes:*
2. For each key: GETDEL (atomic get + delete)
3. ADD delta to Cassandra counter:
   UPDATE like_counts
   SET count = count + delta
   WHERE post_id = ?
4. Any likes arriving after GETDEL
   go into a fresh Redis key

Better: Kafka Double-Write

On each LIKE action:
  INCR likes:{postId}      ← Redis sync
  publish like-event       ← Kafka async

Kafka consumer
(like-count-persister):
  Batch 1000 events
  → single Cassandra write
  ~ flush every 100ms

Recovery on Redis Crash

  • Enable Redis AOF persistence (fsync=everysec) — max 1 sec data loss
  • Kafka topic retained 7 days — replay last 5 min to recompute exact count
  • Cassandra = ground truth; Redis = rebuildable cache

Unlike Race Condition & TOCTOU Fix

Problem: Double-Unlike Goes Negative

Timeline: counter = 1
  Thread A: GET likes:{postId} → 1   (checks > 0, OK to decrement)
  Thread B: GET likes:{postId} → 1   (checks > 0, OK to decrement)
  Thread A: DECR likes:{postId} → 0
  Thread B: DECR likes:{postId} → -1  ← WRONG!

Fix: Atomic Lua Script — Guard Before Decrement

EVAL """
  -- Guard 1: Check user actually liked this post
  local shard = tonumber(ARGV[1]) % 100
  local liked = redis.call('SISMEMBER',
    'liked_by:' .. KEYS[1] .. ':' .. shard, ARGV[1])
  if liked == 0 then
    return {-1, redis.call('GET', 'likes:' .. KEYS[1])}
  end

  -- Guard 2: Only decrement if counter > 0
  local count = tonumber(redis.call('GET', 'likes:' .. KEYS[1]))
  if count and count > 0 then
    redis.call('DECR', 'likes:' .. KEYS[1])
  end
  redis.call('SREM',
    'liked_by:' .. KEYS[1] .. ':' .. shard, ARGV[1])
  return {1, redis.call('GET', 'likes:' .. KEYS[1])}
""" 1 {postId} {userId}
Idempotency key for out-of-order requests: Store like_ts:{userId}:{postId} in Redis. Reject any request with timestamp older than stored value — prevents network-reordered unlike/like from corrupting state.

Threaded Comments Design

Data Model

Comment {
  post_id          UUID  ← partition key
  comment_id       TIMEUUID ← clustering key
  user_id          BIGINT
  parent_comment_id TIMEUUID  ← NULL = top-level
  content          TEXT
  is_deleted       BOOLEAN  ← soft delete only
  is_hidden        BOOLEAN  ← toxicity flag
  like_count       (Redis counter)
  created_at       TIMESTAMP
}

Depth Limit: 2 Levels

  • Top-level comment: parent_comment_id = NULL
  • Reply: parent_comment_id = comment_id of parent
  • No reply-to-reply (Instagram model, not Reddit)
  • Simplifies queries: no recursive CTE needed

Sort Modes

Recent First (default)

SELECT * FROM comments
WHERE post_id = ?
  AND parent_comment_id = NULL
  AND comment_id > {cursor}
ORDER BY comment_id DESC
LIMIT 20

Top Comments

  • Cassandra cannot sort by dynamic like_count
  • Read top 500 recent from Cassandra
  • Fetch comment_likes:{id} for each (Redis pipeline)
  • Sort in application layer by like count
  • Cache result: top_comments:{postId} TTL 5 min

Comment Pagination — Cursor-Based

Why NOT OFFSET Pagination

Problem with OFFSET:
  User loads page 2 (OFFSET 20). Meanwhile 3 new comments inserted.
  Page 2 now starts at what was page 1's last 3 → user sees DUPLICATES.
  Or comments shift → user MISSES comments between pages.
  Also: OFFSET N = scan and discard N rows → O(N) cost, gets slower with depth.

Cursor-Based Pagination

First page:
  GET /v1/posts/{postId}/comments?sort=recent&limit=20
  → Returns 20 comments + nextCursor: "7234891234559999"

Next page:
  GET /v1/posts/{postId}/comments?cursor=7234891234559999&limit=20
  Cassandra query:
    SELECT * FROM comments
    WHERE post_id = ? AND comment_id < {cursor}
    ORDER BY comment_id DESC LIMIT 20

Load replies for a comment:
  GET /v1/posts/{postId}/comments/{commentId}/replies?cursor=&limit=10
  SELECT * FROM comments
  WHERE post_id = ? AND parent_comment_id = {commentId}
  AND comment_id > {cursor}
  ORDER BY comment_id ASC LIMIT 10
TIMEUUID as cursor: time-ordered, globally unique, stable under concurrent inserts. New comments on page 1 never shift existing cursors. Infinite scroll works correctly.

Response Shape

{
  "comments": [{ "commentId": "...", "content": "...", "replyCount": 3 }],
  "nextCursor": "7234891234559990"
}

Notifications — Like & Comment Events

Flow: Async via Kafka

Like Service
  → INCR Redis counter (sync, fast path)
  → publish like.created to Kafka (async, fire-and-forget)

Kafka: like-events topic (retention 7 days)

Notification Service (Kafka consumer):
  → reads like.created event
  → checks throttle: notifications:{postId}:{ownerId} EX 600 (10 min)
  → if not throttled: send push via FCM / APNs
  → if throttled: batch count, send "and 9,999 more liked" after TTL

Notification Throttle — Celebrity Problem

Problem: Ronaldo post gets 1M likes in 10 min = 1M push notifications.
         Post owner's phone explodes, notification service overloaded.

Solution:
  Redis key: notif_throttle:{postId}:{ownerUserId} EX 600
  If key not set: send notification immediately, SET key = 1
  If key is set: INCR key (batch count only, no push)
  After TTL (10 min): send batched "X more people liked your post"

@Mention Notifications

  • Parse comment text for @username patterns on comment submit
  • Resolve usernames → user_ids via User Service
  • Publish mention.created events for each mentioned user
  • Dedup: if same user mentioned multiple times in same comment → one notification

Like Aggregation for Feed Ranking

Engagement Score for Feed Algorithm

Engagement Score = (likes × 1.0)
                 + (comments × 1.5)
                 + (shares × 2.0)
                 + (saves × 2.5)
                 × time_decay_factor

time_decay_factor = e^(-λ × hours_since_post)
  where λ controls how fast freshness decays

Like Velocity Signal

like_velocity:{postId} → Redis Sorted Set (timestamp → count)

On each like:
  ZADD like_velocity:{postId} {timestamp} {userId}
  ZREMRANGEBYSCORE like_velocity:{postId} 0 (now - 3600)
  → keep only likes in last 1 hour

Velocity = ZCARD like_velocity:{postId}
  → "likes per last hour" feeds ranking algorithm

Feed Ranking Service

  • Reads like count from Redis: likes:{postId}
  • Reads velocity: like_velocity:{postId} ZCARD
  • Combines with comment count, share count, save count
  • Applies user affinity score (how much does this user interact with this author?)
  • Updates feed ranking every 1 minute for active posts, 10 minutes for older
Instagram Insight: A post with 10K likes in 1 hour outranks a post with 50K likes that received them over 3 days. Velocity is more valuable than raw count for ranking.

Scaling — Celebrity Post (50M Likes)

Bottleneck 1: liked_by SET Hot Key

Problem:
  100K SADD/sec to liked_by:{postId}
  At 10M likers: SET = 10M × 8 bytes = 80MB in ONE Redis key
  Redis is single-threaded per key → contention at 100K SADD/sec

Solution 1 — Shard the SET (100 sub-keys):
  liked_by:{postId}:{userId % 100}
  → 100 keys, each handles 1K SADD/sec (100K / 100)
  → has-user-liked: SISMEMBER liked_by:{postId}:{userId % 100}  ← O(1)
  → list all likers: SUNION liked_by:{postId}:0 .. :99  ← avoid, expensive

Solution 2 — Bloom Filter (probabilistic):
  10M users, 1% false positive rate → ~12MB (vs 80MB for exact SET)
  "Has user liked?" → no false negatives (99% accuracy for "has liked")
  Use case: rendering the heart icon state  ← Bloom filter ideal here
  Trade-off: 1% of users incorrectly see filled heart (phantom like)
             Acceptable for social media

Bottleneck 2: Redis Cluster Sharding

Shard by postId mod N (where N = number of Redis shards):
  Shard 0 handles posts: 0, N, 2N, ...
  Shard 1 handles posts: 1, N+1, 2N+1, ...

Use consistent hashing to avoid resharding all keys on cluster resize.
Redis Cluster built-in: hash slot = CRC16(key) % 16384

Deep Dive — Top Comments Sort

Problem: Cassandra sorts by clustering key (TIMEUUID = time-ordered). It CANNOT sort by like_count because like_count is dynamic and not a clustering key.

Solution: Application-Layer Sort with Redis Cache

GET /comments?sort=top flow:

Step 1: Check Redis cache
  GET top_comments:{postId}
  → Cache HIT (TTL 5 min): return cached JSON immediately

Step 2: Cache MISS — compute top comments
  a. Read top 500 recent comments from Cassandra (fast: one partition scan)
     SELECT * FROM comments WHERE post_id=? LIMIT 500

  b. Pipeline Redis: for each of 500 comments:
     GET comment_likes:{commentId}
     → Returns 500 like counts in one round trip

  c. Sort 500 comments by like_count in application layer (in-memory)

  d. Take top 20, serialize to JSON

  e. SET top_comments:{postId} {json} EX 300  (5-min cache)

  f. Return top 20 comments

Step 3: Cache Invalidation
  On new comment inserted: DEL top_comments:{postId}
  On comment liked: DEL top_comments:{postId}  (or lazy invalidation via TTL)
This is exactly what YouTube does: "Top comments" = periodically computed, not real-time. A 5-minute staleness is acceptable for social media comment ranking.

Scalability Bottlenecks

Bottleneck 3: Comment Write Amplification

Problem: 5,787 comments/sec; viral post → millions of comments.
         One Cassandra partition per postId → partition grows very large.

Solution:
  - Cassandra handles large partitions well (not a HOT partition, just LARGE)
  - If comment_count > 10M: introduce bucket sub-partition
    PRIMARY KEY ((post_id, bucket), comment_id)
    where bucket = comment_count / 1_000_000
  - Compaction strategy: TWCS (TimeWindowCompactionStrategy)
    → comments are write-heavy, time-ordered → minimizes write amplification

Bottleneck 4: Read Amplification on Viral Post

Problem: 10M users load a viral post simultaneously.
         Each load fetches top 20 comments → 10M Cassandra reads for same data.

Solution:
  - Redis cache: top_comments:{postId} TTL 5 min (L1 cache)
  - CDN caching: top-20 comments cached at edge, TTL 30 seconds (L0 cache)
  - For ultra-viral posts: pre-compute + push to CDN edge nodes proactively
  - Cache key invalidation: DEL top_comments:{postId} on new comment

Bottleneck 5: API Gateway Rate Limiting

Per-user rate limits:
  Like actions:   100/min per user
  Comments:       3/min per user per post (Redis INCR with EX 60)
  Comment reads:  1000/min per user

Redis sliding window: comment_rate:{userId}:{postId} INCR EX 60
  → 429 Too Many Requests if count >= 3

What NOT to Say (Anti-Patterns)

Anti-Pattern 1

Store like count in the posts table

100K likes/sec all hitting UPDATE posts SET like_count = like_count + 1 WHERE id = ? — row lock serializes all writes. Database melts at ~1,000/sec throughput.

Anti-Pattern 2

Use MySQL for comments at scale

500M inserts/day on a single MySQL table. No natural sharding strategy. Cassandra's partition-per-post model is architecturally correct here.

Anti-Pattern 3

Hard delete comments

Breaks reply chains (orphaned replies still reference deleted parent). Breaks notification deep-links. Breaks audit trail. Always soft delete (is_deleted = true).

Anti-Pattern 4

Sync ML toxicity check on comment submit

ML inference = 50–200ms added to every comment POST. Use Kafka to make it async. Comment shows immediately; if toxic, hidden within seconds.

Anti-Pattern 5

OFFSET pagination for comments

OFFSET N scans and discards N rows. Unstable under concurrent inserts — new comment shifts all pages → users see duplicates/gaps. Use cursor-based pagination.

Anti-Pattern 6

Redis pub/sub for notifications

Redis pub/sub doesn't persist messages. If Notification Service is down when event fires, notification is lost forever. Use Kafka for durability (7-day retention).

Anti-Pattern 7

Exact like count with strong consistency

Requires distributed locking, kills throughput. Approximate counts ("1.2M") with 5-sec lag are completely acceptable for social media.

Senior Q&As — 15 YOE Level

Q1: Redis crashes before write-back runs. How do you handle?

A: Two approaches. Enable Redis AOF persistence (fsync=everysec) — limits data loss to 1 second. Kafka like-event topic has 7-day retention — replay last 5 minutes to recompute exact count. Cassandra is ground truth; Redis is a cache always rebuildable from Kafka.

Q2: User likes then immediately unlikes. Unlike arrives BEFORE like due to network jitter. Out-of-order requests?

A: Idempotency key + timestamp. Redis key like_ts:{userId}:{postId} stores timestamp of last accepted action. If incoming request timestamp < stored timestamp → reject as stale. Client generates timestamp at action time, not at network delivery time.

Q3: Write-back job reads counter then new likes arrive before the reset. TOCTOU race?

A: Use GETDEL (atomic get-and-delete). Any likes after GETDEL go into a fresh counter key. In Cassandra: UPDATE like_counts SET count = count + delta (ADD delta, not SET absolute) so multiple write-back jobs are safe without coordination.

Q4: Add reaction types (love, haha, wow, sad, angry) like Facebook?

A: Redis keys become reaction:{postId}:{reactionType} — 6 keys per post. reacted_by:{postId}:{userId} stores which reaction type (STRING, not SET). Switching reactions: DECR old type + INCR new type in one Lua script. Write-back job writes 6 counter values per post to Cassandra.

Q5: "3 mutual friends liked this" annotation — how to implement?

A: At post render time: fetch following:{userId} from Social Graph Service (cached in Redis SET). Intersect with recent likers of the post. SINTERSTORE into temp key, SRANDMEMBER to pick 3 names. Expensive per post — precompute at feed generation time and cache per-user.

The 60-Second Summary

  • Like counts → Redis INCR (atomic, 1M ops/sec), write-back to Cassandra every 5 min
  • Idempotency → Lua script: SISMEMBER check before SADD + INCR
  • liked_by at scale → Shard SET into 100 sub-keys, or Bloom filter (12 MB vs 80 MB)
  • Comments → Cassandra, partition=postId, clustering=TIMEUUID
  • Pagination → cursor-based (TIMEUUID), never OFFSET
  • Top comments → app-layer sort of top 500, cached in Redis TTL 5 min
  • Notifications → async Kafka → FCM/APNs, throttle to 1 notif/10 min per post
  • Toxicity → async ML via Kafka, never blocks comment submit
  • Unlike safety → Lua script guards: SISMEMBER + count > 0 before DECR
The single most important insight: The like counter cannot live in the posts table. Redis INCR is the only structure that handles 100K atomic increments/sec on one key without contention. Everything else follows from this.
