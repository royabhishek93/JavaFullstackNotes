Read consistency R=1 trusts whichever single node answers. If that node hasn't replicated yet → stale read. W + R = 1 + 1 = 2 ≤ N=3.

The Core Concept

N, W, R — the majority-vote knobs

  • N = total replicas of your data (e.g., 3)
  • W = write quorum — how many nodes must confirm the write
  • R = read quorum — how many nodes must respond to the read

Like 3 senators: a decision is valid if 2 of 3 agree. You don't need all 3 — just a majority. Tolerates 1 senator being unavailable, prevents deadlock.

Why It Works

The overlap proof

WRITE SET (W=2)
READ SET (R=2)
≥1 node always overlaps → has fresh data

Write went to [1,2]. Read from [2,3] → overlap [2] ✓. Read from [1,3] → overlap [1] ✓. Read from [1,2] → overlap both ✓. Every case has ≥1 overlapping node.

Common combos: Read ONE + Write QUORUM (write-heavy feeds), Read QUORUM + Write QUORUM (financial data). Never: Read ALL + Write ONE.

Deep Dive — Where Engineers Get It Wrong

Read repair & hidden traps

  • Disagreeing replicas → coordinator picks latest timestamp, returns it, then background-repairs the stale node
  • read_repair_chance default 10% — triggers repair even with no visible mismatch
  • QUORUM waits for the 2nd-slowest node (~200ms), not the fastest (~10ms at ONE)
  • W=ALL, R=ALL: 1 node down → every op fails. "Never use in practice."
  • Hinted handoff: coordinator stores an IOU for a down node, replays it when it returns

Cheat Sheet

Decision tree

Need speed only? → ONE / ONE
Need balance? → ONE (read) / QUORUM (write)
Need strong consistency? → QUORUM / QUORUM
Money movement itself? → Use MySQL/Postgres, not Cassandra

"QUORUM on both reads and writes guarantees that at least one node in the read set was written to. That node has fresh data. The cost is you wait for the (N/2)+1th response instead of the first."

Architect's one-liner: "W+R greater than N is the quorum overlap guarantee — at least one node that was written to is always in your read set, so you always get fresh data."
