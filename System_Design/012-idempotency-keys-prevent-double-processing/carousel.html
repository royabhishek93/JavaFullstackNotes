The Fix

Same key on both. Second attempt returns the cached order #1001 — no reprocessing.

Server-Side Table

Implementation

idempotency_keys(key_value PK, user_id, response, status_code, expires_at)

Lookup key → found? Return cached response. Not found? Process, then store result with 24h TTL.

The Race Condition Trap

Two Retries, Same Instant

Both check "key exists?" → both see NO → both process → 2 orders anyway.

✓ Fix: INSERT ... ON DUPLICATE KEY as a lock — only 1 request "wins" the insert.

Cache Failures Too

The Subtle Trap

First attempt fails "insufficient funds" — if you only cache successes, the retry re-runs the balance check.

If balance changed since, retry might now silently SUCCEED — a different outcome for what the user believes was 1 operation.

Scope Keys to the User

Security Trap

Key alone as the lookup = one user could reuse/guess another user's key.

✓ Always scope: (key_value + user_id) together.

Naturally Idempotent vs Not

Comparison

PUT, DELETEYes (by HTTP spec)No

Decision Tree & Interview Answer

Quick Reference

Is the endpoint POST and state-changing? → Add idempotency key. GET/PUT/DELETE? → Already safe to retry.

"The client generates a UUID once, before the first attempt, and sends it on every retry — the server caches the result by that UUID so retries are free and double-processing is impossible."
