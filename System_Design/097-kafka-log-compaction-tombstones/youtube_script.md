# Kafka Log Compaction & Tombstones — YouTube Script

## HOOK (0:00–0:30)
"A Kafka topic tracking 'current session state per user' gets written to every few seconds for years, and somehow it never grows to an unbounded size. Not because Kafka deletes old data on a timer — because a background janitor thread is quietly walking the log, keeping exactly ONE row per key, forever. Today I'm showing you log compaction, and the one setting — delete.retention.ms — that determines whether a 3-day-down consumer silently misses a delete."

[Screen cue: A whiteboard covered in rows for "Alice", collapsing down to just her single latest row.]

## THE PROBLEM (0:30–2:00)
"Think about it this way — imagine a whiteboard tracking every employee's current desk. Every time someone moves, instead of erasing the old row, a clerk just writes a NEW row at the bottom: Alice to Desk 12, later Alice to Desk 45, later Alice to Desk 9. After a year, the whiteboard is covered in stale rows nobody cares about — all that matters is Alice's CURRENT desk. A normal Kafka topic with `cleanup.policy=delete` is exactly that append-only whiteboard: it keeps everything for a fixed time window, say 7 days, then deletes the whole thing regardless of key. A compacted topic instead has a background janitor — the log cleaner thread — that periodically walks the log and, for every key, keeps only the MOST RECENT row, deleting all the older duplicates in place, while every surviving row keeps its ORIGINAL offset. The topic still behaves like a log — offsets keep increasing, order is preserved — it just converges toward 'one row per key, forever.'"

[Screen cue: Draw the before/after compaction table — 7 records with 4 marked 'stale' collapsing to 3 records, offsets 3, 5, 6 preserved with gaps at 0,1,2,4.]

## THE SOLUTION (2:00–5:00)
"Now watch what happens when someone actually needs to DELETE a key entirely — say Alice leaves the company. You can't just stop writing about her, because her last known row would sit on the whiteboard forever, and the janitor would keep preserving it as 'the latest row for that key.' The fix is a tombstone: a record with Alice's key but a NULL value. The janitor treats a tombstone as the latest value too, so it deletes any older rows for that key — but it KEEPS the tombstone itself around for a configurable window, `delete.retention.ms`, defaulting to 24 hours, specifically so any consumer reading recently still learns 'Alice was deleted' and can react, like evicting her from a local cache. Only after that retention window elapses does the janitor purge the tombstone itself, at which point Alice's key vanishes from the topic completely. This exact mechanism is what powers Kafka Streams KTable changelogs — when your app crashes and restarts, it rebuilds its RocksDB store by replaying the compacted changelog topic from offset zero, and because compaction guarantees 'current value per key survives forever,' nothing is lost even if the app was down for days. Config topics and feature-flag topics use the same pattern — every service bootstraps its config by consuming a compacted topic from offset zero on startup."

[Screen cue: Draw the tombstone lifecycle — write tombstone → compaction keeps it (within 24h) → compaction purges it (after 24h) — with a clock overlay showing the retention window.]

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"Here's the trap that catches teams handling a multi-day outage: if a consumer instance is down for LONGER than `delete.retention.ms`, it comes back online, replays the changelog from its last committed offset, and simply NEVER SEES some of the tombstones that were written and already purged during its downtime. The practical effect: its local state for those deleted keys never gets evicted — it silently believes deleted sessions or deleted users are still active, forever, until something else happens to overwrite that key. The fix is straightforward but easy to overlook: size `delete.retention.ms` around your worst-case consumer downtime, not the 24-hour default — if deploys or incident recovery could take a consumer offline for 3 days, set the retention to a full week, accepting a bit more disk usage for tombstones sticking around longer, in exchange for the correctness guarantee that no consumer silently misses a delete. Second trap: compaction is NOT real-time. Kafka doesn't rewrite a segment on every single write — that would be prohibitively expensive. Instead, a background cleaner thread checks a `dirty_ratio` — dirty bytes over total bytes — against `min.cleanable.dirty.ratio`, defaulting to 0.5, and only compacts a segment once that threshold is exceeded. Critically, the ACTIVE segment currently being written to is NEVER compacted, so at any given moment a consumer reading the partition MAY see multiple stale duplicate values for the same key that just haven't been cleaned up yet — 'latest value survives' is an EVENTUAL guarantee, not an instantaneous one. And third: compaction only helps if key cardinality is BOUNDED. If your key is a random UUID generated per event, every key appears exactly once, there are never any duplicates to collapse, and the topic simply never shrinks — compaction is the wrong tool entirely for an unbounded-cardinality event log; use `cleanup.policy=delete` instead."

## REAL WORLD (8:00–9:30)
"Think about a ride-hailing platform like Ola or Uber tracking 'current driver location/status per driver ID' — a compacted topic keeps exactly one current-state row per driver, and when a driver logs off, a tombstone removes them cleanly, with the retention window sized to survive a typical deployment window without any consumer missing that logout. Think about Swiggy or Zomato's feature-flag and config rollout system — every service instance bootstraps its live configuration by replaying a compacted `app-config` topic from offset zero on startup, keeping the topic small forever even after years of config changes, without needing a separate database just for config. And think about a Kafka Streams-based real-time aggregation service, similar to what a payments platform like Paytm or PhonePe might run internally — a KTable changelog topic backing account balance state is compacted, so a crashed and restarted aggregation service rebuilds its complete balance state from the changelog with zero data loss, regardless of how long ago each account was last updated."
