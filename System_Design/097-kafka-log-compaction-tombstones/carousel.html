Kafka Log Compaction

Slide 1 / 9 — The Hook

A "current state per user" topic gets written to for years and never grows unbounded.

1 row per key. Forever.

Delete vs Compact

The Problem

cleanup.policy=delete: whole segments dropped after a time window, regardless of key.

cleanup.policy=compact: background thread keeps only the LATEST value per key, forever.

Before / After Compaction

The Solution

Before: 7 records, 3 unique keys, 4 stale duplicates (57% dirty)

After: 3 records survive at their ORIGINAL offsets (3, 5, 6) — order preserved, gaps allowed.

Tombstone Lifecycle

Deleting a Key

Write NULL value = tombstone. Compaction keeps it for delete.retention.ms (default 24h), then purges it entirely.

Within that window: any consumer replaying sees "this key was deleted" and can react.

KTable Changelogs

Real Use Case

App crashes and restarts → rebuild RocksDB store by replaying the compacted changelog from offset 0.

Compaction guarantees "current value per key" survives — no data lost even after days down.

The Downtime Trap

Where Engineers Get It Wrong

Consumer
down 3 days

If delete.retention.ms = 24h (default), tombstones written & purged during that window are NEVER seen. Deleted keys look "still active" forever.

Compaction Isn't Real-Time

Two More Traps

Active segment is NEVER compacted — stale duplicates can persist until it rolls.

Unbounded key cardinality (random UUID per event) = topic never shrinks. Compaction is the wrong tool there.

Decision Tree & Interview Answer

Quick Reference

Need "current value per key forever"? → compact. Bounded key cardinality? → compact works. Unbounded? → delete instead.

"For a KTable like this, I'd back it with cleanup.policy=compact rather than time-based deletion. For logout, I produce a record with a null value — that's a tombstone. I'd size delete.retention.ms around worst-case consumer downtime, not the default."
