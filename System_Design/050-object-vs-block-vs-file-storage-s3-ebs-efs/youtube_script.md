# Object vs Block vs File Storage — YouTube Script
Duration: ~10 min | Target: Engineers 3–10 YOE | Episode: 50 of series

## HOOK (0:00–0:30)
"Picture this: an engineer stores fifty million user profile photos directly inside a Postgres BYTEA column, because 'it's just easier, one database, one place.' Six months later, the nightly backup job that used to finish in twenty minutes now takes fourteen hours, replication lag spikes into minutes, and the DBA is ready to quit. The fix isn't a bigger database — the fix is realizing storage is not one thing. It's three completely different technologies — object, block, and file — and picking the wrong one is exactly why EFS can quietly cost you thirteen times more than S3 for the identical gigabyte. Today: S3 versus EBS versus EFS, when to use each, and the exact trap that breaks backups, budgets, and video streaming at scale."

[Screen cue: A Postgres backup progress bar frozen at "14 hours remaining", then a cost comparison ticking $0.023 → $0.30 per GB with a "13x" stamp.]

## THE PROBLEM (0:30–2:00)
"Think of it this way. Object storage — S3 — is like a postal warehouse. You ship a package, you get a tracking number, and you can retrieve that exact package with that number from anywhere in the world. But you can't open the package and swap out one page — you pull the whole thing, modify it, and ship a new version back. It scales to billions of packages and it's cheap. Block storage — EBS — is like the hard drive inside your own laptop. It's formatted with a filesystem, so a program can open a file, seek to byte five thousand, write four bytes, and save — genuinely fast, genuinely random access. But it's bolted to ONE machine. Unplug it and hand it to another computer, and you have to unmount and remount it first. File storage — EFS or NFS — is like a shared network drive at the office. Multiple machines mount the exact same directory at the same time, no copying required, everyone sees everyone else's changes instantly. But it's slower than a local disk and you're paying for the network round trip on every single read. Three tools, three completely different jobs — and most storage outages I've seen come from an engineer treating one like the other."

[Screen cue: Three side-by-side icons — a shipped package (object), a laptop hard drive (block), a shared office network drive (file) — each with a one-line caption.]

## THE SOLUTION (2:00–5:00)
"So here's how each one actually works under the hood. Object storage — S3 — stores a key mapped to a binary blob plus metadata: content type, size, an ETag hash. You access it purely over HTTP — GET to download, PUT to upload, DELETE to remove, no partial writes allowed. Under the hood, that object gets replicated across three or more availability zones automatically, stored in erasure-coded chunks, giving you eleven nines of durability — that's 99.999999999%. Best use cases: user uploads, videos, images, backups, data lake storage, and CDN origin. Block storage — EBS — is a network-attached SSD, but from the OS's point of view it behaves exactly like a local hard drive. MySQL can literally fseek to an offset and fwrite four thousand ninety-six bytes — partial writes, no problem. You get snapshots to S3 for point-in-time backup, and on the io2 tier you get up to sixty-four thousand IOPS for serious database workloads. There's even a multi-attach mode where an io2 volume connects to up to sixteen EC2 instances — but that requires a cluster-aware filesystem like Oracle RAC, which is rare, so don't assume EBS is naturally shared. Best use cases: MySQL and Postgres data files, OS root volumes, any workload needing low-latency random I/O on a single machine. File storage — EFS — mounts over NFS onto multiple EC2 instances simultaneously; write from instance one, and instance two sees it immediately in the same shared directory. Best use cases: shared configuration files across a fleet, ML training data read by multiple GPU boxes at once, WordPress media shared across a web cluster, and CI/CD artifact sharing. Now put the numbers side by side: object storage latency sits at fifty to two hundred milliseconds but throughput is essentially unlimited gigabytes per second; block storage is sub-millisecond latency but capped around four gigabytes per second and sixty-four terabytes per volume; file storage sits in between at one to ten milliseconds but auto-scales in capacity. And cost: S3 is two point three cents per gigabyte per month, EBS gp3 is eight to ten cents, EFS is thirty cents — file storage is roughly thirteen times the price of object storage for the exact same data."

[Screen cue: Draw the comparison table live — Object, Block, File as three columns — latency, throughput, cost, durability, POSIX filesystem support, filling in row by row.]

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"First trap, and it's the one from the hook: storing binary files directly inside a relational database. The moment you put a twenty-five-megabyte attachment or a product photo into a BYTEA or BLOB column, every single backup has to move that binary data too, replication has to ship it to every replica, and your database size explodes for data that never needed relational query features in the first place. The fix: S3 holds the bytes, the database holds the address — that's the entire architect's one-liner, and it's the single most common junior mistake across every system that touches files. Second trap: using EBS for something that needs to be served to thousands of concurrent users, like video streaming. EBS is attached to exactly one EC2 instance — it cannot fan out to serve a video to a hundred thousand simultaneous viewers, and even if you tried, you're paying block-storage prices for what should be dirt-cheap object storage. I've seen teams reach for EBS purely out of familiarity — 'it's just a filesystem, I know how to use it' — and build themselves into a wall the moment traffic scales past one server. Third trap: reaching for EFS when you didn't actually need a shared filesystem at all. EFS exists for the specific case where multiple servers need the SAME directory at the SAME time — shared configs, shared ML datasets. If your actual requirement is just 'store this file and fetch it later by an identifier,' that's S3's entire job description, at roughly a thirteenth of the cost. And a smaller but real fourth trap: routing every file upload THROUGH your application server instead of using a pre-signed URL. If your backend proxies every byte of every video upload, your servers become the bandwidth bottleneck for the whole platform. The fix is simple — issue a pre-signed URL, let the client upload directly to S3, and your backend never touches the actual file bytes."

[Screen cue: Split screen — left side shows a bloated Postgres backup file ballooning in size with binary blobs highlighted red; right side shows an EC2 instance with a single EBS volume trying and failing to stream video to a stadium-sized crowd icon.]

## REAL WORLD (8:00–9:30)
"Think about Zomato or Swiggy's restaurant photo pipeline — hundreds of thousands of restaurants, each with a menu full of food photos, easily tens of millions of images at an average of two megabytes each. That's dozens of terabytes of pure binary data, and serving it from object storage at two point three cents a gig instead of block storage at eight to ten cents isn't a rounding error at that scale — it's a four-times cost difference on the exact same bytes, plus S3 can be hit directly by a CDN edge node without ever touching an application server. Now picture Flipkart during Big Billion Days — millions of SKUs, each with five to ten product images, so tens of millions of objects that need to be served instantly to a traffic spike of shoppers nationwide. Try serving that off EBS attached to one EC2 instance and you have an outage before the sale even opens; object storage plus a CDN in front is the only architecture that survives that spike. And think about PhonePe or Paytm generating transaction receipts and monthly statements — millions of PDF files that need to be write-once, read-occasionally, and never modified in place. Those get stored in S3 as objects, while the actual transaction records — amount, timestamp, user ID, status — live in a Postgres database on EBS, because THOSE rows genuinely need fast random-access queries and transactional guarantees. Bytes in the object store, structured data on the block-storage database — same split, three different Indian platforms."

## OUTRO + NEXT EPISODE (9:30–10:00)
"So the decision tree is simple: if it's a file you fetch by URL and never partially modify — user uploads, videos, backups — that's S3, object storage, and it's the cheapest option by far. If it's database data files that need sub-millisecond random I/O on one machine — that's EBS, block storage. And if multiple servers genuinely need to share the SAME live filesystem at the SAME time — that's EFS, file storage, and you'll pay roughly thirteen times the price of S3 for that convenience, so only reach for it when you actually need it.
