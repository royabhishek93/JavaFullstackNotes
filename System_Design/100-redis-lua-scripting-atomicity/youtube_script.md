## HOOK (0:00–0:30)

In that gap, a completely different client acquires the exact same lock you're about to delete — and your DEL just destroyed someone else's legitimate lock. Today I'm showing you the exact Redis feature that closes this gap entirely: Lua scripting, and why 'check then act' from application code is a bug waiting to happen."

## THE PROBLEM (0:30–2:00)
"Think about it this way — Redis is like a single bank teller serving one customer's full request before starting the next. If your ENTIRE request is one Redis command, you're safe — Redis guarantees each individual command is atomic. But if your 'request' is actually two separate trips to the teller window — GET the lock owner, walk away to compare it in your own code, then come back and DEL it — the teller served other customers in between your two trips. Someone else could have already acquired that same key. Your comparison, done outside Redis, is now stale. This is a classic check-then-act race condition, and it's exactly what happens with plain GET-then-DEL from application code trying to safely release a distributed lock."

[Screen cue: Draw the bank teller window with two separate "trips" — GET, then a gap where other customers are served, then DEL.]

## THE SOLUTION (2:00–5:00)
"Now watch the fix: instead of two separate trips to Redis, you hand it a single written note describing the ENTIRE procedure — 'check the value, and only if it matches my token, then delete it.' That note is a Lua script, and Redis executes it as one indivisible unit, server-side, with its single-threaded command loop guaranteeing absolutely no other client's command can execute in the middle. You call it with EVAL, passing the script text, then a count of how many following arguments are KEYS versus plain ARGV values — that KEYS-versus-ARGV split matters beyond style, because Redis Cluster uses KEYS to determine which shard the script's data lives on and reject scripts that would span multiple shards incorrectly. The canonical safe-unlock script is exactly three lines: get the current value at the lock key, compare it to the token this client believes it owns, and only if it matches, delete it and return success — otherwise return zero without touching anything. Because production doesn't want to resend the full script text on every single call, you load it once with SCRIPT LOAD, which returns a SHA1 hash, and call EVALSHA with that hash afterward — at ten thousand unlock calls per second, that's the difference between two megabytes per second of script-text overhead and about zero point four megabytes per second of just the hash and arguments."

[Screen cue: Draw the EVAL command structure breaking down script/numkeys/KEYS/ARGV, then the SCRIPT LOAD → EVALSHA flow with the SHA1 hash cached client-side.]

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"Here's the trap on the operational side that causes real outages: Redis is single-threaded for command execution, and a Lua script counts as ONE command from the scheduler's perspective — meaning for the entire duration a script runs, Redis cannot process ANY other client's command, not reads, not writes, nothing, even on completely unrelated keys. I've seen this cause a real production incident: someone writes a 'one-time cleanup script' that does `KEYS session:*` — which could match millions of keys — and loops deleting each one inside the script. That script can run for five to thirty seconds, during which your ENTIRE production traffic is frozen, health checks fail, connections time out, and on-call gets paged. The fix is never looping over an unbounded key pattern inside a script — use SCAN, which is cursor-based and non-blocking, from application code instead, batching deletes across multiple small calls. The safety budget: keep scripts well under one millisecond of actual execution time; anything approaching ten milliseconds under load is a red flag, because a script that takes even five milliseconds blocks out roughly five hundred to a thousand other commands' worth of Redis's single-node throughput ceiling for its own duration. Second trap: the NOSCRIPT error. If Redis restarts, or fails over to a replica that never saw your SCRIPT LOAD call, EVALSHA returns NOSCRIPT because the script cache is gone — production clients MUST catch this specific error and fall back to a full EVAL, which both executes the script AND re-populates the cache, or you get a hard failure on every call until someone notices."

## REAL WORLD (8:00–9:30)
"Think about a distributed lock release used across almost every Indian fintech or e-commerce backend — PhonePe, Flipkart, whoever — releasing a Redis-based lock safely absolutely requires this exact check-then-delete Lua pattern, because a naive release could unlock a completely different service's freshly-acquired lock on the same key. Think about a rate limiter protecting a public API at Swiggy or Zomato scale — the sliding-window counter pattern, incrementing a counter and conditionally setting its expiry only on the very first request in a window, needs to be one atomic script; done as three separate round trips, you get race conditions where the expiry either never gets set or gets reset incorrectly under concurrent load. And think about the atomic 'confirm this booking hold' step in a ticket platform like BookMyShow — exactly the same Lua check-and-confirm pattern protects against double-booking a seat when a hold's TTL expires at almost the same instant a payment confirmation arrives."
