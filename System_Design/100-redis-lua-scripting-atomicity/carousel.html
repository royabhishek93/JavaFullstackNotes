Redis atomicity covers EACH command, not the gap between them. Another client's SET can slide into that gap.

Safe: One Atomic Lua Script

The Solution

if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('DEL',KEYS[1]) else return 0 end

Runs as ONE indivisible unit — no other client's command can interleave, even from a competing lock acquisition.

EVAL Command Structure

KEYS vs ARGV

EVAL "<script>" numkeys key1 arg1

KEYS[] tells Redis Cluster which shard the data lives on — critical for routing. ARGV[] is just plain values.

SCRIPT LOAD + EVALSHA

Production Pattern

Load once → get SHA1 hash. Call EVALSHA with the hash on every subsequent call — no resending script text.

At 10K calls/sec: EVAL ≈ 2MB/sec overhead vs EVALSHA ≈ 0.4MB/sec.

Second Example: Atomic Rate Limiter

Sliding Window Counter

INCR then conditionally EXPIRE on the FIRST request only — as 3 separate commands, this races. As 1 Lua script, it's atomic.

The Blocking Trap

Where Engineers Get It Wrong

✕ A script looping over unbounded KEYS session:* can freeze Redis's ENTIRE single thread for 5-30 seconds — real outage cause.

✓ Use SCAN from app code instead; keep scripts sub-millisecond.

Quick Reference

Need to read a value AND conditionally act atomically? → Lua script. A single native command already does it? → Just use that instead.
