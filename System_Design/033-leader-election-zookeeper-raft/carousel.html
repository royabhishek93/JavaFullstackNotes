The Problem

5 Nodes. Who Gets to Write?

Without a single leader, every write is a race

A
B
C
D
E

If all 5 nodes accept writes independently, two nodes can write different values to the same key simultaneously — split brain. The fix: designate exactly ONE leader. All writes funnel through it; the leader replicates to followers.

  • Must always elect exactly one leader — never zero, never two
  • Must elect a leader even if some nodes are down
  • Must detect leader death and re-elect automatically, no human on call
This is the leader election problem — ZooKeeper and Raft are the two dominant answers

Chain Watching & Failover

Why followers watch their neighbor, not the leader

B (0002)
NEW LEADER
C (0003)
D (0004)

Each follower watches only the node one position below it — B watches A, C watches B, D watches C. If every follower watched the leader directly, all 4 would fire simultaneously when it dies (thundering herd on ZooKeeper).

  • t=0: Node A disconnects
  • t=1: ZooKeeper detects via session timeout (10–30s)
  • t=2: ephemeral znode 0001 auto-deleted
  • t=3: Node B notified, confirms it's now lowest → becomes leader
Total re-election time ≈ ZK session timeout (10–30s); writes rejected until then
Raft

Three Roles, One Heartbeat

Leader → Follower → Candidate

Leader
Follower 1
Follower 2

Leader continuously sends heartbeats. Every heartbeat resets a follower's election timeout — a random value between 150ms and 300ms. If a follower goes that long with zero heartbeats, it assumes the leader is dead and becomes a Candidate.

All nodes start as Followers — there is no manual designation

Total election time: ~150ms — vs. ZooKeeper's 10–30s session timeout
Raft — Deep Dive

The Split Vote Trap

Why the timeout MUST be randomized

Without randomization: if all 4 followers share the same fixed timeout, all 4 become Candidates at once. Each votes for itself. No one reaches a majority. Stalemate.

N2201ms
N3267ms

With randomization (150–300ms range): one node almost always fires first and wins before others even start their clocks. Rare ties simply reset to a new random timeout and retry.

Randomized timeout = the single mechanism that avoids permanent stalemate
Raft — Deep Dive

Stale Nodes Can't Win

Raft's safety guarantee against data loss

Node E
log=85
Node B
log=100

Node E was partitioned and only replicated up to entry 85; Nodes B, C, D have all 100 entries. When E requests votes, every voter checks: is candidate's log at least as current as mine? 85 < 100 → DENY. E cannot win, no majority — no data loss.

Later, Node B (log=100) requests votes, gets granted by C and D, and wins — carrying the full committed log forward.

Vote rule = higher/equal term AND equal-or-greater log recency — both must hold
