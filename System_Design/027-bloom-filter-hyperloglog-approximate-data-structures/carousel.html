HyperLogLog — The Election Exit Poll

Leading-Zeros Counting Estimates Cardinality

100M voters — instead of collecting every ID (800MB, hours), interview 10,000 random voters and extrapolate (10K records, minutes, ±0.5%).

stream: u1,u7,u3,u1,u2,u7,u4,u1,u3,u5
hash(u1)=0b1011... lz=0 hash(u7)=0b0100... lz=1
hash(u3)=0b0010... lz=2 hash(u4)=0b0001... lz=3 ← max
hash(u2)=0b1100... lz=0 hash(u5)=0b0110... lz=1

max_leading_zeros = 3 → estimate = 2³ × 0.72 ≈ 5.76 ≈ 6

Actual distinct: u1,u2,u3,u4,u5,u7 = 6 ✓ exact in this tiny example

Real HLL uses 2¹⁴=16,384 registers + harmonic mean to reduce variance.

Rule: false positives must only cost extra work, never a correctness or security violation.

Decision Tree & Interview Answer

The Architect's One-Liner

  • Need membership + false positives OK, false negatives never? → Bloom Filter
  • Need distinct count, ~0.81% error acceptable? → HyperLogLog
  • Need exact answer or exact stored value? → HashSet / Redis SET
  • Frequent deletions or security-sensitive check? → Never Bloom Filter
  • Streaming, can't pre-aggregate, millions+ distinct? → HyperLogLog
"Bloom filters tell you what definitely isn't there — eliminating unnecessary lookups at scale — and HyperLogLog tells you approximately how many distinct things are there — both trading a tunable sliver of accuracy for orders-of-magnitude savings in memory."
