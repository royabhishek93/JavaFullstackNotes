🎤 Interview Opening — How to Begin

Interviewer says: "Design a parking lot system." — Deceptively simple. Interviewers at FAANG expect you to probe beyond one lot: handle concurrent entries, multi-lot city rollout, real-time availability boards, and payment atomicity at peak load.

Questions You Should Ask

  • Single city or multi-city lot network?
  • Hourly billing, slab pricing, or daily cap?
  • Pre-booking / reserved slots needed?
  • EV charging slots with separate pricing?
  • Real-time display board integration?
  • Payment must be synchronous or async?

Depth Signals That Impress

  • Prevent two cars claiming same last slot
  • Slot + ticket state machine consistency
  • Idempotent exit API (duplicate scan safety)
  • WebSocket push to display boards
  • Saga pattern for payment rollback
  • Consistent hashing for multi-lot sharding
Your opener: "I'll start with LLD — entities, class diagram, design patterns, concurrency model — then zoom to HLD: multi-lot coordination, caching, payment flow, and how we scale to 10M+ slots."

✅ Functional Requirements

Single-Lot Core

  • Multiple floors & slot types: Bike / Car / Truck / EV
  • Entry: find nearest valid slot, issue ticket with timestamp
  • Exit: scan ticket, compute fee, process payment, free slot
  • Prevent double assignment of the same slot
  • Support VIP, Handicapped, EV reserved slot classes
  • Multiple pricing: hourly, flat first hour, daily cap
  • Payment: card / wallet / UPI — generate receipt
  • Real-time slot availability count per floor

Distributed / HLD Variant

  • 100+ lots across multiple cities
  • Pre-booking up to 24 hours in advance
  • Central availability service with <1s staleness
  • Mobile app search: nearby lots, filter by vehicle type
  • Dynamic / surge pricing during peak hours
  • Analytics: occupancy trends, revenue reports
  • Push notifications: booking confirm, expiry alert
  • IoT sensor feed for real-time occupancy (future)

Key State Machines

  • Slot: AVAILABLE → OCCUPIED → AVAILABLE
  • Ticket: ACTIVE → CLOSED | LOST
  • Payment: PENDING → SUCCESS | FAILED

Out of Scope (State This!)

  • Valet parking management
  • License plate AI / OCR recognition
  • In-lot turn-by-turn navigation
  • Multi-tenant lot-owner admin portal

🎯 Slot Assignment — Strategy Pattern

Interface & Implementations

interface SlotAssignmentStrategy { findSlot( floors: List<Floor>, type: SlotType ): Optional<ParkingSlot> } // Strategy 1 — default for walk-in class NearestEntranceStrategy implements SlotAssignmentStrategy { // Iterates floor 1→N, returns first free } // Strategy 2 — for pre-booking spread class RandomSpreadStrategy implements SlotAssignmentStrategy { // Random slot to reduce hotspot on F1 } // Strategy 3 — accessibility mandate class HandicappedFirstStrategy implements SlotAssignmentStrategy { // Nearest slot with HANDICAPPED flag }

Context: SlotAssignmentService

class SlotAssignmentService { private strategy: SlotAssignmentStrategy setStrategy(s: SlotAssignmentStrategy) { this.strategy = s } assignSlot(lot, vehicleType): Slot { return strategy.findSlot( lot.getFloors(), vehicleType.getSlotType() ) } }
Why Strategy here? The assignment algorithm varies by vehicle type, time of day, and lot policy. We can swap strategies at runtime — e.g. switch to RandomSpread during peak hours to balance floor utilisation.
Index trick: Maintain a Map<SlotType, Queue<Slot>> per floor for O(1) next-available lookup rather than scanning all slots.

🚦 Entry & Exit Flow — Ticket Lifecycle

Entry Flow — POST /v1/entry

1Validate vehicle type & plate format
2Check no active ticket already exists for this plate in lot
3Run SlotAssignmentStrategy → get candidate slot
4Atomic CAS: UPDATE slot SET status=OCCUPIED WHERE status=AVAILABLE
5If CAS fails (race) → retry next candidate slot
6INSERT ParkingTicket (ACTIVE, entryTime=now, idempotency_key)
7Publish SlotOccupied event → WebSocket / Kafka
8Return ticketId to barrier controller

Exit Flow — POST /v1/exit

1Fetch ACTIVE ticket by ticketId (idempotency_key check)
2Set exitTime = now; compute duration in minutes
3Run PricingStrategy → calculate fee
4Create PENDING Payment record with idempotency key
5Charge via payment gateway (Stripe/PayPal)
6On SUCCESS: UPDATE ticket.status=CLOSED, slot.status=AVAILABLE
7Lift barrier; publish SlotFreed event
8On payment FAILURE: ticket stays ACTIVE, barrier stays down
Critical invariant: Exactly one ACTIVE ticket per slot. Exactly one OCCUPIED slot per active ticket. These two constraints together prevent all race conditions.

💰 Pricing — Strategy Pattern

Interface & Implementations

interface PricingStrategy { calculate(durationMins: Long, slotType: SlotType): BigDecimal } // $2/hr — simple walk-in billing class HourlyPricingStrategy { calculate(mins, type) { hours = ceil(mins / 60.0) return hourlyRate[type] * hours } } // First hour flat, then per 30 min class SlabPricingStrategy { calculate(mins, type) { if(mins <= 60) return flatRate extra = ceil((mins-60)/30.0) return flatRate + extra*slabRate } } // Cap at daily max — long stays class DailyMaxPricingStrategy { calculate(mins, type) { hourly = HourlyPricingStrategy... return min(hourly, dailyMax) } } // Peak hours surge multiplier class SurgePricingDecorator { calculate(mins, type) { base = delegate.calculate(mins, type) return base * surgeMultiplier } }

Context: PricingService

class PricingService { strategy: PricingStrategy setStrategy(s) { this.strategy = s } computeFee(ticket): BigDecimal { mins = Duration.between( ticket.entryTime, now()).toMinutes() return strategy.calculate( mins, ticket.slotType) } }

⚡ Concurrency — Last Slot Race Condition

The Problem

T1 reads slot #42 → AVAILABLE
T2 reads slot #42 → AVAILABLE
T1 writes OCCUPIED ✓
T2 writes OCCUPIED ✓ <— double assignment!

Solution 1 — Optimistic Lock (DB)

-- Atomic conditional update (CAS) UPDATE parking_slots SET status = 'OCCUPIED', version = version + 1 WHERE id = ? AND status = 'AVAILABLE' AND version = ?; -- affected rows = 0 → lost race, retry

Solution 2 — Redis SETNX

// Distributed lock — 10s TTL String key = "slot:lock:" + slotId; Boolean acquired = redis.set(key, requestId, SET_IF_NOT_EXISTS, 10, SECONDS); if (!acquired) retryNextSlot();

Solution 3 — Redlock (Multi-node)

// Redisson Redlock — quorum across // 5 independent Redis nodes RLock lock = redisson.getLock(key); if (lock.tryLock(5, 10, SECONDS)) { try { if (isAvailable(slotId)) reserveSlot(slotId); } finally { lock.unlock(); } } else { retryNextSlot(); }

Concurrent Entry Scenario

1Car A & B both request last slot on Floor 1
2Car A acquires Redis lock first → marks OCCUPIED
3Car B's CAS returns 0 rows → retries Floor 1 slot #43
4Both get distinct tickets and distinct slots
DB unique constraint as final safety net: UNIQUE(slot_id) on active tickets. Even if lock fails, the DB write will throw a constraint violation.

🗄️ Caching Strategy — Redis Layers

L1 — Availability Counter (Hot)

Key: lot:{lotId}:avail:{slotType} Value: 45 // integer count TTL: 30 seconds Op: INCR / DECR on entry/exit event

L2 — Booking Detail Cache

Key: booking:{bookingId} Value: {userId, spotId, status, ...} TTL: 1 hour

L3 — Search Results Cache

Key: search:{lat}:{lon}:{r}:{type} Value: [list of available lots + counts] TTL: 5 minutes

Cache Invalidation Strategy

Write-through: On every booking create/cancel → update DB then update cache atomically.
Event-driven: Kafka consumer listens for SlotOccupied / SlotFreed events → DECR / INCR availability counter.
TTL fallback: Stale data self-expires. Acceptable for search cache; not for booking confirmation.

Redis Failure Handling

  • Fallback: query DB directly (slower but correct)
  • Redis Sentinel: automatic failover to replica
  • Circuit breaker: stop trying Redis after 3 failures
  • Stale cache served with "updating…" warning

💳 Payment Flow — Fee Calc → Charge → Barrier Lift

Happy Path Steps

1Driver scans ticket at exit terminal
2System computes duration → runs PricingStrategy → fee = $8.50
3Display fee to driver, accept payment method
4Create PENDING Payment with idempotency_key = ticketId + attempt
5Call Stripe / PayPal — receive payment_intent_id
6Webhook confirms SUCCESS → update Payment.status = SUCCESS
7Close ticket, free slot, lift barrier
8Emit SlotFreed event → WebSocket push + Redis INCR

Failure Scenarios & Saga Rollback

Payment timeout: Ticket stays ACTIVE, barrier stays down. Driver retries — idempotency key prevents double charge.
Barrier opens but DB write fails: Retry worker re-closes ticket within 30s grace. Slot freed on timeout.
Stripe webhook delayed: Polling job reconciles payment_intent status after 60s.
Idempotency key format: exit:{ticketId}:{attemptNo} — Stripe rejects duplicate charges with the same key.
PCI-DSS: Never store raw card numbers. Tokenise via Stripe. Store only stripe_payment_id in your DB.

📈 Scaling — 10M Slots, Consistent Hashing, Partitioning

Sharding Strategy

Shard key: lot_id
Most queries are scoped to a single lot. Sharding by lot_id keeps related data co-located and avoids cross-shard joins.
-- Consistent hash ring — 4 shards Shard 1: hash(lot_id) % 4 == 0 → DB-1 Shard 2: hash(lot_id) % 4 == 1 → DB-2 Shard 3: hash(lot_id) % 4 == 2 → DB-3 Shard 4: hash(lot_id) % 4 == 3 → DB-4 -- Virtual nodes prevent hotspots -- Adding DB-5: rebalance only ~20%

Database Tier

WAll writes → Primary PostgreSQL
RReads → Replica pool (2+ replicas)
AAnalytics → dedicated read replica

🧩 Design Patterns — Applied in Parking Lot

Strategy

Where: SlotAssignmentStrategy, PricingStrategy
Why: Algorithm varies by vehicle type, time of day, and lot policy. Swap at runtime without touching core service.

Observer

Where: AvailabilityObserver (Kafka → WebSocket)
Why: Decouple slot-state changes from display boards, analytics writers, and mobile push — each is an independent observer.

Factory

Where: VehicleFactory, PricingStrategyFactory
Why: Centralise object creation logic. New vehicle or pricing type → add one class, update factory — no change to callers.

Singleton

Where: ParkingLotManager (Spring @Bean), Redis connection pool
Why: One managed instance of the lot registry per JVM. Spring IoC handles this naturally via @Component.

Decorator

Where: SurgePricingDecorator wraps any base PricingStrategy
Why: Add surge multiplier without modifying HourlyPricingStrategy or SlabPricingStrategy classes.

Builder

Where: ParkingTicket.Builder, BookingRequest.Builder
Why: Complex objects with optional fields. Avoids telescoping constructors. Makes test data creation clean.

⚖️ Trade-offs & Design Decisions

DecisionChosen ApproachTrade-off
Slot locking Optimistic + Redis SETNX Lower contention vs. pessimistic lock; retry logic adds complexity
Consistency model Strong (ACID bookings) No double-booking; higher write latency than eventual consistency
Availability cache Redis INCR/DECR Sub-ms reads; possible stale count on Redis crash (self-heals in 30s)
Real-time push WebSocket via Kafka Sub-50ms updates; requires persistent TCP connection management

State these trade-offs proactively — interviewers want to see you understand why you chose each approach, not just what you chose.

🔴 Senior Q&A 1 — Concurrent Reservation Under Load

Q: "Your lot has 1 CAR slot left. 500 users simultaneously try to book it. Walk me through exactly what happens and how your system remains correct and performant."

What Happens — Step by Step

1500 requests hit Booking Service pods (Kubernetes HPA — 20 pods)
2Each pod tries redis.set("slot:lock:42", reqId, NX, EX 10)
3Exactly 1 pod acquires the lock — others get null (rejected atomically)
4Winner runs DB CAS: UPDATE slot SET status='OCCUPIED' WHERE status='AVAILABLE'
5499 rejections return HTTP 409 CONFLICT with "slot_unavailable" code
6Client UX shows "sold out" and suggests nearest alternative lot

Safety Guarantees

Redis SETNX is atomic — no two pods can both get "acquired = true" for the same key.
DB partial unique index on (slot_id) WHERE status='ACTIVE' is the final backstop. Even if Redis fails, the DB INSERT will throw a constraint violation for the second attempt.
TTL on Redis lock (10s): If the winner pod crashes before unlocking, the lock auto-expires — no deadlock.
Don't use: Java synchronized — works only within one JVM, useless in a multi-pod deployment.

🌍 Senior Q&A 2 — Scaling to Multi-city (10M+ Slots)

Q: "You've designed a single-city system. How would you extend it to 50 cities, 10M+ slots, and 200K daily bookings without a redesign?"

Architecture Changes

1City-level DB shards: Each city = its own shard group (Primary + 2 Replicas). Paris outage never affects NYC.
2Consistent hashing on lot_id: Virtual nodes — adding a shard rebalances only ~20% of keys.
3Multi-region deployment: US-East, EU-West, AP-South — Route 53 geo-routing to nearest region.
4Global Redis cluster: Per-city Redis for availability counters; no cross-city replication needed.
5Elasticsearch per region: Geo-search index kept in the same region as users searching it.

⚡ Senior Q&A 3 — EV Charging Slots

Q: "How would you extend your parking lot design to support EV charging stations — including tracking charging sessions, billing for electricity, and managing charger availability separately from parking slots?"

New Entities

class ChargingStation id: UUID slotId: UUID // FK → parking_slots chargerType: LEVEL_2 | DC_FAST powerKw: Float status: AVAILABLE | IN_USE | FAULT class ChargingSession id: UUID stationId: UUID ticketId: UUID startTime: Instant endTime: Instant? energyKwh: Float // from meter API electricityFee: BigDecimal parkingFee: BigDecimal

🏁 Closing — Key Takeaways

LLD Core Principles

  • Strategy Pattern — swap slot assignment & pricing at runtime
  • Observer Pattern — decouple slot changes from display/push
  • Factory Pattern — clean vehicle and strategy creation
  • Optimistic Lock — CAS on slot row, no table-level lock
  • Idempotency keys — safe retry on exit and payment APIs
  • Partial unique index — DB enforces 1 active ticket per slot
Critical invariant to state:
"Exactly one ACTIVE ticket per slot AND exactly one OCCUPIED slot per active ticket."

HLD Scale Principles

  • Redis SETNX — distributed lock across pods
  • Kafka events — async fan-out to WebSocket, analytics
  • lot_id sharding — consistent hash, city-level isolation
  • WebSocket push — real-time boards <50ms latency
  • Saga + idempotency — payment consistency without 2PC
  • Multi-region — Route 53 geo-routing, per-city Redis
Interview closing line: "The hardest problems here are the last-slot race condition and payment atomicity at the barrier. I've addressed both with distributed locking + DB constraints and the Saga pattern with idempotency keys."
