16ms

That's the entire time budget Google Docs gives itself to make your keystroke feel instant — before the server has even seen it. Two people type in the same sentence, at the same time. Here's how they don't corrupt each other's edit.

The Index-Shift Problem

Two Cursors, One Sentence

"Hello"
Alice: insert @2
"Hello"
Bob: delete @3

Both edits reference the same starting document. Apply Bob's delete blindly after Alice's insert lands, and position 3 no longer points at the character he meant — Alice's insert already shifted it right.

The Operation Model

Every Edit Is a Tagged Operation

insert(pos, text) delete(pos, length)

Not the whole document — a tiny delta, tens of bytes, tagged with the revision number the client last saw ("I made this against revision 10").

This is the foundation server-authoritative OT builds on: one server, one revision log, clients apply locally & optimistically first.

Transform & Converge

xform(opA, opB) → opA'

insert(2,"X")
⇄
delete(3,1)

Server commits Alice's insert first → doc is "HeXllo". Bob's delete(3,1) is transformed to delete(4,1) because Alice's insert shifted the target character right one slot.

✓ Alice, Bob, and the server all converge on "HeXlo" — this convergence guarantee is the TP2 property.

4 transform cases: Insert/Insert, Insert/Delete, Delete/Insert, Delete/Delete. Delete/Delete overlap is the genuinely hard case — you must compute the range intersection so you don't double-delete.

Server transforms each incoming op against every committed op the client missed, applies it, bumps the revision, then broadcasts the transformed op — never the client's raw original.

Trap: Offline Reconnect

The Local-View "Jump" Bug

Alice's wifi drops 8 seconds mid-edit. She queues 3 local ops against her stale revision. On reconnect, if her client doesn't transform its OWN queued ops against what she missed, her screen visibly jumps when the correction arrives — a classic bug in early Etherpad/Google Wave clients.

Fix (Google Docs, ShareDB): cap the client to ONE in-flight op; buffer further keystrokes into a single composed op until ACK.

Trap: Transform Cost Blowup

O(N) Missed Operations

Normal sync
N = 1-5
10 min offline
N = hundreds

Fix: production systems snapshot the document periodically — a badly-behind client re-fetches the snapshot + current revision instead of replaying the full op log.

Cautionary tale: Google Wave's own transform bugs — a subtly wrong transform silently diverges documents, no crash, no warning — were a documented factor in the project's struggles.

Decision Tree & Interview Answer

Quick Reference

Need real-time collab with a server already in place? → OT. Need offline-first or peer-to-peer with no central authority? → CRDTs. Can't invest in exhaustively testing transform correctness? → reconsider OT.

"I'd model every edit as a small operation — insert or delete — tagged with the revision the client last saw. The core insight is that two operations created concurrently reference stale positions once both are applied, so I need a transform function that rewrites one op so applying them in either order converges to the same document — that's the TP2 property, not just an empirical hope. I'd make this server-authoritative so one place enforces ordering, and I'd flag reconnect behavior up front: cap clients to one in-flight op, and snapshot the document periodically so a badly-behind client re-syncs instead of replaying the entire op log."
