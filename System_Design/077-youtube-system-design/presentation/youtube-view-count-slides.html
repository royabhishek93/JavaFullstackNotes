Flink vs Kafka Streams — Which Aggregator?
Both do the 30-second windowed aggregation — but they are very different tools
🟠 Kafka Streams LIBRARY
Just a Java dependency — runs inside your app. No extra cluster.
KStream<String, ViewEvent> views =
  builder.stream("view-events");
views.groupByKey()
  .windowedBy(TimeWindows
    .of(Duration.ofSeconds(30)))
  .count()
  .toStream()
  .to("view-count-deltas");
✅ No extra infra  ·  Low ops overhead
✅ Perfect for: simple windowed counting
⚠️ Limited: no complex multi-stream joins
🔴 Apache Flink CLUSTER
Separate infrastructure — its own set of servers, deployed independently.
Your App Servers → Kafka → Flink Cluster
                       ↓
          Redis + Bigtable + Fraud Queue
✅ Multi-stream joins for fraud detection
✅ Exactly-once with checkpointing

⚠️ Higher ops overhead — separate cluster
Simple rule:  Basic counting only → Kafka Streams  ·  Complex fraud logic, multi-stream → Flink  ·  On GCP → Dataflow / Beam
Why Redis INCRBY Needs No Locks
The single-threaded model explained
🔴 Multi-Thread Database PROBLEM
Thread A reads count → 1000
Thread B reads count → 1000  ← before A writes
Thread A writes → 1001
Thread B writes → 1001  ← overwrites A
Final: 1001 ✗  ·  Should be 1002  ·  One write LOST
🟢 Redis — Single Thread SOLUTION
INCRBY 1 → reads 1000, writes 1001 ✓
INCRBY 1 → reads 1001, writes 1002 ✓
INCRBY 847 → reads 1002, writes 1849 ✓
One thread. Commands queue. Zero overlap. Zero race condition.
Always correct  ·  No locks  ·  100K ops/sec
💡  Sounds like a limitation — one thread. But Redis is entirely in memory. That one thread handles 100,000+ operations per second.
Bank analogy: one cashier, very long queue — no lock on the drawer needed.
Cassandra — Write Path
Append-only · never modify old data · clean up in the background
Step 1
📔
Commit Log
Sequential write · Disk
Written to disk first, before anything else. If the server crashes — data is safe. Recovered on restart.
Step 2
⚡
MemTable
In-memory · RAM
Data in RAM — immediately readable. Sorted by key. Held until ~128 MB fills up.
Step 3
💾
SSTable
Immutable file · Disk
Never modified once written. Updates create a new file. Old files stay until compaction.
⚡ The golden rule: append-only. No locking. No finding old rows. Just write a new file. This is why Cassandra handles millions of writes/sec.
🧹 Background — Compaction + Bloom Filter
Compaction merges SSTables periodically — keeps newest version, removes deleted data, fewer files = faster reads.
Bloom Filter: each SSTable has a tiny helper — "Is your data definitely NOT in me?" → skip that file. Instead of checking 50 files, you check 2–3.
Bigtable — Architecture
One giant sorted table, cut into pieces · data lives in GCS, not on the server
🎯
Master Node
Manages tablet assignments · does NOT serve data · traffic controller only
Tablet Server 1
Tablets A–G
Tablet Server 2
Tablets G–M
Tablet Server 3
Tablets M–Z
☁️ Google Cloud Storage — Actual Data Lives Here
SSTables for all tablets · Shared Write-Ahead Log · NOT on the server's local disk
This is the most important design decision in Bigtable.
❌ What happens when Tablet Server 2 crashes?
TS2 crashes → Master detects in seconds
→ Reassigns Tablets G–M to a new server (TS4)
→ TS4 reads data from GCS — already there, nothing to copy
→ Recovery in seconds, not minutes

Traditional DB: server crashes → data stuck on local disk → copy needed → minutes
Bigtable or Cassandra — Which to Pick?
Both handle petabyte-scale · the decision is about your cloud strategy
☁️ Pick Bigtable
When: You're on Google Cloud Platform
✅ Fully managed — Google runs it, zero ops
✅ Native integration with Dataflow, BigQuery
✅ YouTube is GCP-native — obvious fit
✅ Row key design handles time-series perfectly
⚠️ GCP-only — locked to one cloud
Real world: YouTube · Google Analytics · Google Maps
🔶 Pick Cassandra
When: Multi-cloud or on your own servers
✅ Open-source — not locked to any cloud
✅ Masterless — no single point of failure
✅ Tunable consistency (ONE / QUORUM / ALL)
✅ CQL for flexible queries
⚠️ You manage it — higher ops overhead
Real world: Netflix · Discord · Apple iCloud
Both handle this exact problem equally well at scale.
The only question: where are you running?  GCP → Bigtable. Everywhere else → Cassandra.

The Day YouTube's Counter Broke
December 2012 — Gangnam Style and the 32-bit integer overflow
🎵
Gangnam Style — PSY
The first video in YouTube history to break the view counter
1,000,000,000
✅ 1 Billion views — world record
2,000,000,000
✅ 2 Billion views — still going
2,147,483,647
❌ FROZEN — counter stopped
⚠️  2,147,483,647 = 2³¹ − 1 = INT max
YouTube stored view counts as a 32-bit signed integer. Gangnam Style overflowed it.
The counter froze. YouTube engineers had to stop it, migrate the column, and restart.
✅  Fix: BIGINT (64-bit) — max value: 9,223,372,036,854,775,807
That's 9.2 quintillion. No video is breaking that counter.
This is exactly why we design with BIGINT from day one.
