Upload Pipeline (Write Path)

  • Any logged-in user uploads up to 2 GB
  • Raw video → S3 → Kafka → FFmpeg transcoder
  • 4 quality levels + HLS manifest produced
  • Untrusted input: malware scan + copyright check required
  • Status transitions: PROCESSING → READY → PUBLISHED

Watch Pipeline (Read Path)

  • 100M+ daily viewers across every timezone
  • CDN absorbs 90 % of all video segment traffic
  • HLS + ABR — quality adapts per measured bandwidth
  • P99 video start time target: < 200 ms
  • Average session: 7 minutes, 5 videos watched per day
Key insight: Unlike Netflix (curated library), YouTube allows any user to upload. The ingestion pipeline must validate untrusted input, run copyright detection, and scale to 500 hours uploaded every minute.

Upload Flow — Presigned S3 + Kafka

1

Request presigned URL — POST /api/v1/videos/upload-url. Backend generates a temporary S3 presigned URL (15-min TTL) and returns videoId. Upload API responds in < 10 ms.

2

Client uploads directly to S3 — Browser or mobile app does a PUT straight to S3 using the presigned URL. No backend involved. Supports chunked multipart for large files (> 100 MB). Resumable on failure.

3

Save metadata — After S3 upload, client calls POST /api/v1/videos with title, description, tags, visibility. Video DB status set to PROCESSING.

4

Kafka event published — Video Service publishes video.uploaded event to Kafka. Upload API returns 202 Accepted immediately — no waiting for transcoding.

5

Processor consumes event — FFmpeg worker pool picks up the Kafka message, downloads raw S3 object, begins transcoding. On completion, status updated to READY and manifest URL stored in Video DB.

Why presigned URL?

  • 2 GB video via backend = 16 GB/sec at 8 uploads/sec
  • Backend becomes bandwidth bottleneck instantly
  • Presigned URL: browser uploads directly to S3
  • Backend only issues the URL (one 10 ms API call)

Why Kafka (not synchronous)?

  • Transcoding takes 1–10 minutes per video
  • User cannot wait — Kafka decouples upload from processing
  • On transcoder crash, Kafka replays the event
  • Failed after 3 retries → Dead Letter Queue (DLQ)

How ABR Quality Switching Works

1Client fetches master.m3u8 → gets list of quality playlists
2Starts at lowest quality to begin playback fast
3Every 6–10 s, measures download throughput of last segment
4If bandwidth > 2× current bitrate → step up one quality level
5If bandwidth drops below current bitrate → step down
6Switching is seamless — no re-download, no buffering

CDN Segment Delivery

  • Each 6 s segment is immutable — TTL 7 days at edge
  • Manifest file TTL: 30 s (it references the same immutable segments)
  • First request populates the CDN edge cache
  • Subsequent viewers served entirely from edge — no origin hit
  • CDN hit rate target: > 95%

CDN Strategy — CloudFront + Google Global Cache

Tiered CDN Architecture

1

Edge PoPs (200+ locations) — CloudFront / Akamai caches 6 s video segments near users. Serves > 90% of all video traffic. Latency: 5–15 ms from Mumbai PoP vs 200+ ms from US origin.

2

GGC — Google Global Cache — Boxes deployed inside ISP networks (Jio, Airtel, Comcast). Traffic never leaves the ISP's data centre. Eliminates peering costs entirely for those ISPs.

3

Regional Shield (Origin Shield) — Single aggregation layer between edges and S3 origin. Collapses many cache misses from hundreds of PoPs into one origin request, protecting S3 from traffic spikes.

  • Long-tail videos cached only at nearest regional PoP

  • Stale-while-revalidate for manifests: serve stale, refresh async
  • Pre-warm CDN for scheduled big events (Super Bowl, concerts)

Metadata & Search — Elasticsearch + Autocomplete Trie

Why Elasticsearch, Not MySQL LIKE?

  • 800M+ videos — SQL LIKE is an O(n) full table scan
  • Elasticsearch uses inverted indexes: "cooking" → [vid1, vid7, vid42]
  • Lookup in microseconds regardless of corpus size
  • Supports fuzzy match (typos), stemming, synonyms
  • Relevance scoring with BM25 — title > description > tags
  • Filter by upload date, duration, view count, language

Search Ranking Signals

  • Text relevance — BM25 score on title / description / tags
  • Engagement — view count, like ratio, comments
  • Freshness — recency decay (older videos rank lower)
  • Personalisation — boost videos from subscribed channels
  • CTR signal — historical click-through rate for that query

Autocomplete Trie (Prefix Search)

Trie for "sys": s └── y └── s └── t [score:9500] "system design" └── e └── m [score:8800] └── " " [score:8800] ├── d → "system design" └── a → "system architecture" Top-k per prefix stored in Redis: autocomplete:sys → ["system design","systems","system architecture"] TTL: 5 minutes (refresh from Elasticsearch aggregation)
Serving: Autocomplete served from Redis (sub-ms). Full search query goes to Elasticsearch cluster (p99 < 50 ms). Results ranked and returned with thumbnails, duration, view count.

Recommendation Engine — Two-Tower Model

Stage 1 — Candidate Generation

1

Watch history features — last 50 videos watched, avg session length, preferred categories, watch-time-weighted embeddings

2

Two-tower neural network — User tower encodes user features; Item tower encodes video features. Inner product gives relevance score.

3

ANN lookup — Approximate Nearest Neighbour (FAISS / ScaNN) retrieves top 500 candidates from 800M videos in < 10 ms.

Stage 2 — Ranking

  • Deep ranking model scores all 500 candidates
  • Features: predicted watch time, predicted like probability, freshness
  • Output: ranked list of top 50 videos

Stage 3 — Re-rank & Serve

  • Diversity filter — avoid 10 videos from same channel
  • Policy filters — remove age-restricted, sensitive content
  • Freshness boost — surface some new videos to avoid filter bubble
  • Sponsored slots — inject monetised recommendations
  • Final top-20 stored in Redis: reco:{userId} → JSON (TTL 1 hr)

Offline Training Pipeline

  • Apache Spark batch job runs nightly on watch history
  • Training data: (userId, videoId, watchedFraction) tuples
  • Collaborative filtering — "users who watched X also watched Y"
  • Model served via TensorFlow Serving; updated daily

View Count at Scale — Redis INCR + Batch Flush

The Problem

  • 1 billion views / day = ~11,500 writes per second
  • Each view fires POST /api/v1/videos/{id}/view
  • MySQL can handle ~50K writes/sec, but at high cost & hot rows
  • A single video (viral) could get 100K+ views/sec alone
  • Direct DB writes create a hot-row contention bottleneck

Solution — Redis Write-Back Pattern

1

View event arrives → Redis atomic INCR views:vid:{videoId}. Sub-millisecond. Redis handles 1M+ writes/sec.

2

Deduplication — Only count after 30 s of continuous watch. Set cookie per session; ignore duplicate POSTs within 5 min.

3

Background flush job — Every 60 s, a cron sweeps all views:vid:* keys, batches UPDATE videos SET view_count = view_count + delta to MySQL, then resets Redis counter.

4

Read path — View count served from Redis (fast) or MySQL fallback. Eventual consistency: count may lag by up to 60 s.

Redis Key Structure

views:vid:abc123 → 1,482,930 (INCR on each view) reco:u:usr456 → [vid1,vid7] (TTL 1 hr) session:usr456 → JWT data (TTL 15 min) lock:like:vid:abc → 1 (TTL 5 s — mutex) autocomplete:sys → [...] (TTL 5 min)
Interview Q: "Why not just use MySQL?" — At 11,500 writes/sec on one view_count column, MySQL row-level locks create severe contention. Redis INCR is lock-free and atomic at RAM speed.
For a viral video with 100K views/sec: Redis handles it effortlessly. MySQL would need distributed counters + sharding for just that one video.

Like / Dislike & Comments

Like / Dislike — Preventing Race Conditions

  • Idempotency key — primary key (user_id, video_id) in likes table prevents duplicates at DB level
  • Optimistic locking — UPDATE videos SET like_count = like_count + 1 WHERE video_id = ? AND version = ?; retry on version mismatch
  • Redis buffer — like delta cached in Redis, flushed to MySQL every 30 s (same write-back pattern as view counts)
  • Toggle support — INSERT ON DUPLICATE KEY UPDATE; DELETE on un-like
  • Dislike count hidden from public (YouTube changed this in 2021); still stored internally for recommendation signals

Threaded Comments

  • Table: comments(id, video_id, user_id, parent_id, text, like_count, created_at)
  • parent_id = NULL → top-level comment; non-null → reply
  • Max nesting depth: 1 level (replies only, no sub-replies on YouTube)
  • Fetch top-level comments sorted by Top / Newest via index on (video_id, like_count DESC)
  • Load replies lazily (click "View N replies")
  • Spam filter: rate limit + ML toxicity classifier before insert
  • High-volume videos: comments stored in Cassandra (write-optimised)
Scale note: MrBeast videos can get 500K+ comments. Cassandra partitioned by video_id handles the write burst. MySQL used for smaller channels where ACID matters more.

Channel Subscriptions & Notifications

Fan-out on Write (small channels)

1

2

Notification Service consumes event → reads subscriptions table → fetches all subscriber user IDs

3

4

Works well for channels with < 1M subscribers

Fan-out on Read (mega channels)

  • MrBeast has 310M subscribers — writing 310M rows synchronously would take hours
  • Hybrid approach: store the video event in a channel_events feed table once
  • On subscriber app open, notification service fetches recent events for all subscribed channels
  • Bell icon badge updated on pull, not push
  • Dedicated "Subscriptions" feed tab uses this pull model

Scaling Strategy — Sharding + Caching

Database Sharding

  • videos table → shard by video_id % N (uniform distribution)
  • subscriptions table → shard by channel_id (fan-out queries need all subs of one channel on one shard)
  • comments table → Cassandra partitioned by video_id — all comments for a video in one partition
  • watch_history → Cassandra partitioned by user_id — resume position lookups in one partition
  • Hot shard protection: consistent hashing with virtual nodes; automatic rebalancing

Read Scaling — Replicas + Caching

  • MySQL: 1 primary (writes) + 3 read replicas per shard
  • Video manifest URL cached in Redis (TTL 1 hr) — 99% of watch requests served from Redis, never hitting MySQL
  • User profile cached in Redis (TTL 15 min)
  • Elasticsearch cluster: 3 primaries + 2 replicas each; auto-scale reads

Content Moderation — Hash Dedup + ML Classifier

Stage 1 — Hash-Based Deduplication (Content ID)

1

Perceptual hash — pHash computed on key frames of uploaded video. Detects visually similar content even after re-encoding or watermark addition.

2

Audio fingerprint — Acoustic fingerprint (similar to Shazam) compared against reference database of 500M+ copyrighted works.

3

Lookup — Hamming distance search in fingerprint DB. If distance < threshold → match found → copyright holder notified.

4

Content ID decision — Rights holder can: Block video / Monetise it (run their ads) / Track viewership. Result applied automatically.

Stage 2 — ML Moderation Pipeline

5

NSFW classifier — Vision model scores each key frame for adult content, violence, graphic imagery. Threshold triggers human review queue.

6

Hate speech / misinformation — NLP model analyses transcript (auto-generated captions). Flags policy-violating speech.

7

Human review — Borderline cases routed to Trust & Safety reviewers. Final decision: remove / age-restrict / add advisory label.

Storage for Moderation

  • content_hash column on videos table — quick exact duplicate check before any ML
  • Fingerprint index: inverted file index with product quantisation (IVF-PQ) for billion-scale similarity search
  • Moderation decisions stored in video_moderation table with audit trail

Monetisation — Dynamic Ad Insertion (DAI)

What is DAI?

  • Ads are stitched into the HLS stream server-side — ad segments become part of the same .m3u8 manifest
  • No client-side ad injection; ad blockers cannot detect or skip easily
  • Each viewer gets a personalised ad stream — different ad for different users watching the same video
  • Ad pods inserted at pre-marked cue points in the manifest: #EXT-X-CUE-OUT:DURATION=30
  • Supports pre-roll (before video), mid-roll (during), post-roll

Ad Auction Flow

1

Viewer plays video → Ad Server receives bid request with user segment, video category, device, geo

2

Real-time bidding (RTB) auction runs in < 100 ms — DSPs submit bids via OpenRTB protocol

3

Winning ad creative (VAST tag URL) returned to manifest stitcher

4

Stitcher fetches ad segments, inserts into HLS manifest dynamically

5

Ad impression and completion events fired back to advertiser

Senior Q&A 1 — MrBeast Uploads a 4K 60fps Video

"MrBeast uploads a 50 GB 4K 60fps video. Walk me through everything that happens from the moment he clicks Upload."

The Upload Challenge

  • 50 GB raw file — standard presigned URL (15-min TTL) will expire mid-upload on slow connections
  • Single HTTP PUT fails for files > 5 GB on S3
  • Must be fault-tolerant — connection drops halfway should be resumable
  • Transcoding a 4K 60fps 2-hour video takes > 2 hours on a single FFmpeg worker

Solution: S3 Multipart Upload

1

POST /initiate-multipart-upload → S3 returns an UploadId

2

File split into 100 MB chunks — each chunk gets its own presigned URL (TTL: 6 hrs)

3

Browser uploads chunks in parallel (8 concurrent) — resumes from last successful chunk on retry

4

All parts uploaded → CompleteMultipartUpload assembles them in S3

Parallel Transcoding Strategy

5

Kafka event fires → 5 FFmpeg workers spin up in parallel (one per quality level: 360p, 480p, 720p, 1080p, 4K)

6

Each worker processes the same raw S3 file independently; no inter-worker coordination needed

7

Workers run on EC2 Spot (p3 GPU instances for AV1 encoding). 4K AV1: ~45 min per quality level on GPU

8

As soon as 360p finishes (< 5 min), video goes live at low quality. Higher qualities unlock progressively.

Result: MrBeast's video is watchable in 360p within 5 minutes of upload completing. Full 4K available within ~50 minutes. 310M subscribers notified via fan-out on read (pull model).

Senior Q&A 2 — Handling 500 Hours Uploaded Every Minute

"How does your transcoding pipeline handle 500 hours of video uploaded every minute without falling behind?"

The Math

  • 500 hours uploaded / min = 8.3 hours uploaded / second
  • Transcoding ratio (1:1): 1 hour video → ~1 hour CPU time at 1080p
  • With 5 quality levels: 1 hour video → 5 hours CPU time
  • Problem: We need to process 8.3 × 5 = 41.5 CPU-hours per second
  • That means ~41,500 CPU cores running continuously just to keep up

Kafka as the Control Plane

  • Kafka topic video.transcode.jobs acts as durable work queue
  • Kafka consumer lag = SLA health metric (target: lag < 1K messages)
  • Auto-scaling trigger: Kafka lag → scale out FFmpeg worker fleet
  • If lag spikes: AWS Auto Scaling launches new Spot instances in < 2 min
  • On Spot reclamation: checkpoint saves progress; new worker resumes

Elastic Transcoder Fleet

1

Spot instance fleet — 70% cheaper than on-demand. AWS MediaConvert or custom FFmpeg fleet on EC2 Spot.

2

Priority queues — Verified creators (1M+ subs) get faster queue. New channels share standard queue.

3

Segment-level parallelism — Split 2-hour video into 10-minute segments; each segment transcoded independently. 12× parallelism per video.

4

GPU acceleration — NVENC (NVIDIA) for H.264; libaom-av2 GPU for AV1. 10–20× faster than CPU-only FFmpeg.

Cost control: Only scale up transcoding fleet when Kafka lag is high. Scale back to zero overnight (upload volume drops 80%). Spot savings: ~$2M/month at YouTube scale.

Senior Q&A 3 — Cold Start Recommendation Problem

"A new user signs up and watches zero videos. What do you recommend on their homepage? How do you bootstrap the recommendation engine?"

The Cold Start Problem

  • Two-tower model requires watch history vectors — new user has none
  • Collaborative filtering needs past behaviour — none available
  • Cannot personalise without any signal
  • Risk: show boring defaults → user churns immediately

Strategy 1 — Onboarding Interest Selection

  • After signup, show 10–15 topic tiles: Gaming, Music, Tech, Food…
  • User selects 3+ interests → explicit signal for cold start
  • Map topic selections to video category seeds in Elasticsearch
  • Also ask: "Are you here to watch or also to upload?"

Strategy 2 — Global Trending Feed

  • Pre-computed trending:global and trending:{country} lists in Redis (TTL 15 min)
  • Trending score = (views_last_24h / age_hours^1.5) — HackerNews-style decay
  • Show trending videos until first 3 videos watched → model activates

Strategy 3 — Implicit Signals (First Session)

1

Device + locale — phone in India at 8 PM → Bollywood music, cricket highlights likely

2

Referral source — User arrived from a shared video link → recommend same channel

3

Search intent — First search query is a powerful signal; pivot recommendations immediately

4

Exploration bonus — Intentionally serve varied topics (5% random); click = strong signal

Result: Within 3–5 watched videos, the two-tower model has enough embedding signal to personalise. Cold start phase exits in < 10 minutes for an engaged new user.

Closing — Key Takeaways

The Four Core Insights

1

Two pipelines, not one — Upload (write) and Watch (read) are architecturally separate. Design them independently.

2

CDN is the product — 90% of YouTube's value is in getting video to users fast. CDN placement and TTL strategy is a core design decision, not an afterthought.

3

Kafka decouples everything — Upload, transcoding, search indexing, notification, and recommendation updates all flow through Kafka. Each service scales independently.

4

Redis absorbs hot writes — View counts, like buffers, recommendation caches, manifest caches — Redis handles every write-intensive hot path before MySQL ever sees it.
