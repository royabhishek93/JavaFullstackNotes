Key System Challenges
Massive Scale
2.4 EB storage needed over 5 years. 300 GB/sec peak bandwidth. Must handle 30K concurrent video streams. Requires distributed architecture with CDN, sharding, and caching.
Low Latency
Video must start playing in <2 seconds. Global users need fast access. Solution: CDN with 200+ edge locations, 90% cache hit rate, adaptive bitrate streaming (HLS/DASH).
Video Processing
Transcode every video to 5-7 formats (360p, 480p, 720p, 1080p, 4K). Processing time ≈ video duration. Use distributed workers with Kafka queue, FFmpeg for transcoding.
System Requirements Summary
  • 100M DAU, 500M video views/day, 30K concurrent streams at peak
  • 2.4 EB storage (5 years), 300 GB/sec peak bandwidth
  • <2 sec video start time, 99.99% uptime (52 min downtime/year)
  • Multi-format transcoding: 360p to 4K (5-7 quality levels)

Architecture Decisions
Microservices Architecture
6 core services (Video, User, Comment, Search, Recommend, Analytics) scale independently. Video Service handles 10x traffic of User Service. Each has own database, deployed separately, no shared state.
Event-Driven with Kafka
Async processing critical for video upload. User uploads → immediate response. Kafka decouples upload from transcoding (takes 5-30 min). 100+ workers process queue in parallel. No blocking.
CDN for Global Performance
CloudFront with 200+ edge locations. 90% cache hit = only 10% requests hit origin. User in Tokyo gets video from Tokyo edge in 20ms vs 200ms from US. Saves bandwidth costs 10x.
Key Architecture Patterns
  • Microservices: 6 core services, independent scaling, fault isolation
  • Event-Driven: Kafka for async processing, 100+ worker instances
  • CDN: 90% cache hit rate, <2 sec video start time globally
  • Polyglot Persistence: PostgreSQL (metadata), MongoDB (logs), Redis (cache), S3 (videos)

Upload Pipeline Design Decisions
Presigned URL Upload
Direct client → S3 upload bypasses API servers. No bandwidth through API = lower costs. Presigned URL expires in 1 hour, scoped to specific path. Multipart upload enables resumable uploads.
Async Processing with Kafka
User doesn't wait for transcoding (10+ min). Upload completes in 2 min, returns immediately. Kafka ensures every video gets processed even if workers restart. Consumer groups prevent duplicate processing.
Parallel Transcoding
Process 360p, 720p, 1080p in parallel on multi-core EC2 (16 vCPU). Sequential would take 30 min. Parallel takes 10 min (limited by slowest quality). FFmpeg preset=fast balances speed vs quality.
Video Upload Key Points
  • Multipart upload: 500MB video uploads in 2 min (direct to S3, 100 chunks)
  • Async transcoding: User gets response in 2 min, processing takes 12 min in background
  • FFmpeg pipeline: 360p/720p/1080p in parallel, 10 min total (1:1 ratio)
  • Scalability: 100 workers process 500 videos/hour, auto-scale based on Kafka lag

Streaming Optimizations
HLS Protocol Choice
HLS (HTTP Live Streaming) over DASH because: works on all devices (iOS, Android, Web), uses standard HTTP (no special protocols), proxy-friendly, reliable. 10-second segments balance latency vs overhead.
90% Cache Hit Rate
Top 1% of videos (hot) account for 80% of traffic. These cache everywhere. Regional edges serve next 10%. Cold videos (89%) generate only 10% of traffic, served from S3. Result: massive cost savings.
Adaptive Bitrate Benefit
User on 2 Mbps watches 480p smoothly. User on 10 Mbps gets 1080p. Same video, different qualities. Prevents buffering (worst user experience). Player switches quality every 10 seconds based on measured bandwidth.

  • HLS adaptive streaming: Player switches 360p/720p/1080p based on bandwidth

Database Design Decisions
Sharding by user_id
Videos belong to users, so co-locate them. Query "Show my videos" hits single shard. Shard by video_id would require cross-shard queries. 16 shards = 6.25M users each, room to grow to 100M total.
Separate Logs from Metadata
Video views = 500M/day = high write load. PostgreSQL can't handle this. MongoDB optimized for writes, horizontal scaling. Keeps PostgreSQL fast for reads. Polyglot persistence = right tool for right job.
Cache Strategy
Top 1% videos account for 80% traffic. Cache these in Redis (1 hour TTL). Cache hit = 2ms response vs 50ms DB query. Reduces DB load from 30K RPS to 6K RPS (80% reduction). Critical for scale.
Database Key Points
  • PostgreSQL: Metadata (users, videos, comments) with 16 shards by user_id hash
  • MongoDB: Logs & analytics (500M views/day), TTL indexes auto-delete old data
  • Redis: Cache hot videos (1% = 80% traffic), reduces DB load by 80%
  • Elasticsearch: Search with <50ms latency, BM25 ranking, autocomplete
