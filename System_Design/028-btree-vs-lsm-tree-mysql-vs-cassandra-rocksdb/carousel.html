B-Tree vs LSM Tree

The Hook — Two Ways to Run a Library

You're a librarian. A new book arrives every second. How do you shelve it?

B-Tree (MySQL)
Tree of sorted shelves
vs
LSM Tree (Cassandra)
Drop-on-table, package later

Option A: walk to the right shelf, and if it's full — split it into two, re-link the parent. Sometimes cascades 3-4 levels up. disruptive writes

Option B: drop the new book on a table near the door (MemTable). Once 100 pile up, bundle them into a sorted package (SSTable) in the back room. Merge packages later (compaction). always fast writes

Finding a book: 3 steps either way — the difference is what happens when a NEW book arrives

Leaf nodes are doubly linked (←→) — range scans just follow the chain. All row data lives at leaf level (clustered index).

O(log N) = 3-4 disk reads for a table of millions of rows

Page Split — The Hidden Write Cost

Parent may also be full → split cascades up 2-3 more levels. At high write throughput: constant splits → fragmentation → slower reads over time.

Fix: OPTIMIZE TABLE / rebuild index — an expensive, often offline operation on large tables.

Write = append to WAL + insert into MemTable RAM tree → ACK. Sub-millisecond, no searching, no splits.

Each SSTable carries a Bloom Filter: NO → skip file, 0 disk reads. MAYBE → read file to confirm.

Sequential writes are ~10x faster than random writes on SSD and HDD alike. Winner for writes: LSM — always.

Compaction — The Hidden Cost

The Write Cost Doesn't Disappear — It's Deferred

WRITE: ~1ms
(WAL + MemTable)
looks free!
→ hours/days later →
COMPACTION
reads all L0, merges,
writes L1, deletes L0
Compaction is a background I/O storm. It can consume 30-50% of disk I/O bandwidth. Reads slow down while it runs. You need 2x your data size in free disk space for it to complete.

Production practice: monitor compaction queue depth (growing queue = writing faster than compacting).

Size-tiered compaction: merges similar-size SSTables — good for write-heavy workloads.
Leveled compaction: smaller SSTables, better read performance — RocksDB's default.

Decision Framework

Which Storage Engine Do I Pick?

Write throughput > 50K/sec?
├─ YES → Simple data model (KV / wide-column)?
├─ YES → Cassandra / DynamoDB / HBase (LSM)
activity feeds, IoT sensors, time-series, leaderboard ingestion
└─ NO → Kafka + batch writes into Cassandra
└─ NO → Need complex queries / joins / ACID?
├─ YES → MySQL / PostgreSQL (B-Tree)
payments, e-commerce orders, accounts, bookings
└─ NO → Need full-text search?
├─ YES → Elasticsearch (inverted index)
└─ NO → Redis (hot) + MySQL (persistence)
