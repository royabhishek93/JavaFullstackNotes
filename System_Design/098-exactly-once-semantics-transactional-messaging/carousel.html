The Two Generals Problem

The Problem

A messenger crossing an unreliable valley can always be captured. No amount of acknowledgment rounds removes the LAST uncertain message.

Exactly-once delivery over a network is mathematically impossible — Kafka's guarantee is something narrower.

Idempotent Producer

Fix 1 — PID + Sequence Number

Every message tagged with Producer ID + sequence number. Broker recognizes a retry of the same sequence and drops the duplicate silently.

Solves: "my retry after a lost ack creates a duplicate."

Transactions

Fix 2 — Atomic Produce + Offset Commit

Ties "produce output B" and "commit consumed offset A" into ONE atomic unit via 2-phase marker writes.

isolation.level=read_committed consumers only see B after the commit marker lands.

Zombie Fencing

Preventing Split-Brain

Zombie
epoch=3
New instance
epoch=4

Zombie tries to write under stale epoch=3 → REJECTED (ProducerFencedException). Only epoch=4 can write.

The External Side-Effect Trap

Where EOS Actually Ends

Service charges a card → crashes BEFORE committing Kafka offset → message redelivered → card charged AGAIN.

Kafka did exactly what it promised. The double-charge is entirely OUTSIDE Kafka's visibility.

The Fix

Idempotency Key at the External Boundary

Generate a stable key from the order ID → pass it to the payment gateway's OWN idempotency mechanism.

2 independent mechanisms: Kafka EOS (internal) + idempotency key (external side effect).

Decision Tree & Interview Answer

Quick Reference

Kafka-to-Kafka pipeline? → Full EOS. Any external API call as a side effect? → ALSO add an idempotency key at that boundary.

"EOS in Kafka guarantees exactly-once WITHIN Kafka's own bookkeeping. The moment a consumer calls an external payment gateway as a side effect, that action is no longer covered — the fix is an idempotency key at that boundary, tied to something immutable like the order ID."
