Vector Clocks & Write Conflict Detection 1 / 10
The Problem

Wall clocks drift. Order gets reversed.

Server A: 10:00:00.100
Server B: 10:00:00.095
A's clock says "later" —
but B's write actually happened first.
LWW = wrong pick

Last-Write-Wins trusts timestamps to decide the winner. If clocks drift even a few ms between datacenters, LWW can keep the wrong version and silently drop the real one.

Vector clocks answer a different question: not "which happened first in real time" but "did A happen BEFORE B, or were they concurrent?"

The Solution — Structure

One counter per node. Increment your own. Merge by max.

A
{A:0,B:0,C:0}
B
{A:0,B:0,C:0}
C
{A:0,B:0,C:0}
A writes → {A:1,B:0,C:0}
B writes → {A:0,B:1,C:0}
A sends to B
merge = max
{A:3,B:2,C:0}

Receiving node merges by taking the max of each position, then increments its own counter. This is how causal knowledge propagates through the cluster.

The Rule

Happened-before vs. Concurrent

CaseRuleResult
X={A:1,B:0,C:0}
Y={A:2,B:1,C:0}		Every X[i] ≤ Y[i], at least one <X → Y (no conflict)
X={A:2,B:0}
Y={A:1,B:1}		A: 2>1, B: 0<1 — neither dominatesCONCURRENT (conflict)
"X happens-before Y: all X[i] ≤ Y[i] AND at least one strictly less. If neither vector dominates the other, they're concurrent — flag it."

This is the exact same logic as Git: one branch containing the other = fast-forward. Two branches diverging from the same commit = possible merge conflict.

Cheat Sheet

Decision tree + the exact interview line

Compare two clocks X, Y

All X[i] ≤ Y[i]? → happened-before, keep Y

Neither dominates? → CONCURRENT

Need correctness? → return all versions, app merges

Need auto-merge? → use a CRDT (counter/set)
"Vector clocks track which writes causally preceded others. If two writes both increment different nodes' counters from the same base, neither happened-before the other — they're concurrent — and you have a conflict to resolve. Timestamps alone can't detect this because clocks drift."
