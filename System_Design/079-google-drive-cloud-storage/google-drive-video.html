📁 Upload & Dedup

Chunking Strategy — Why 5 MB Chunks

Problem: 15 GB files can't go in one HTTP request. LB timeout at 30–120s, network drop = restart from scratch, server buffers entire file in memory.

How It Works

  • Client splits file into 5 MB chunks client-side
  • Computes SHA-256 hash per chunk locally
  • Checks existingChunks[] on INIT → skips already-uploaded
  • Uploads up to 3 chunks in parallel
  • Each chunk has its own presigned S3 URL (TTL: 5 min)

Why 5 MB (Not 1 MB or 50 MB)?

  • Too small (1 MB): too many S3 PUT calls, overhead dominates
  • Too large (50 MB): retry cost high, progress bar jumpy
  • 5 MB: balances retry cost, parallelism, and S3 PUT count

Benefits of Chunking

  • Resumable: only re-upload failed chunks, not whole file
  • Parallel: 3 chunks simultaneously = 3× throughput
  • Progress: real upload progress indicator
  • Dedup: identical chunks (across files/users) stored once
  • Delta sync: on file edit, re-upload only changed chunks

Our Servers Never See File Bytes

  • Backend generates presigned S3 URL per chunk
  • Client uploads chunk directly to S3
  • 100M DAU × 10 MB would be 1 TB/sec through our LB — impossible
📁 Upload & Dedup

Content-Based Deduplication

If two users upload the same file (identical hash), S3 stores it only once. Both users' metadata points to the same S3 object. Effective storage can be 30–50% less than raw file count.

File-Level Dedup

  • INIT request includes fileHash (SHA-256 of full file)
  • Server queries: SELECT * FROM files WHERE checksum = ?
  • If match found → skip upload entirely
  • Create new FileVersion record pointing to existing S3 chunks
  • Quota still charged to the new user

Chunk-Level Dedup

  • Each chunk has a SHA-256 hash
  • Before uploading, server checks: SELECT s3_key FROM chunks WHERE chunk_hash = ?
  • If chunk already exists → return existing s3_key, skip upload
  • Common in slides, legal docs — same boilerplate = same chunk

Why SHA-256?

  • Deterministic — same content always → same hash
  • Collision probability: astronomically low (2⁻²⁵⁶)
  • Detects corruption: 1 byte change → completely different hash
  • Used by Git, S3 ETags, Bitcoin — battle-tested

DB Index for Dedup

-- Fast dedup check on upload INIT
CREATE INDEX idx_files_checksum
  ON files(checksum);

CREATE INDEX idx_chunks_hash
  ON chunks(chunk_hash);

Dedup check happens before quota reservation — if identical file exists, no quota consumed.

📁 Upload & Dedup

Delta Sync — Upload Only What Changed

A 100 MB document with 1 changed paragraph → only ~5 MB re-uploaded, not 100 MB. Enabled by the Local Metadata Index (SQLite on each device).

How Delta Sync Works

  1. User edits file → File Watcher (inotify/FSEvents) fires
  2. Chunker re-hashes all chunks of the modified file
  3. Compares each hash to Local Metadata Index (SQLite)
  4. Chunks with unchanged hash → SKIP
  5. Chunks with changed hash → UPLOAD only those
  6. INIT request returns existingChunks = [0,1,...,11,13,...,19]
  7. Only chunk 12 uploaded → 5 MB instead of 100 MB

Local Metadata Index

  • SQLite database on each device
  • Stores: { chunkIndex → SHA-256 hash } per file per version
  • Updated after every successful chunk upload
  • Makes delta sync possible without server round-trips

Example: 100 MB File Edit

20 chunks × 5 MB = 100 MB

Chunk 0–11:  hash unchanged → SKIP
Chunk 12:    hash changed   → UPLOAD (5 MB)
Chunk 13–19: hash unchanged → SKIP

Result: 5 MB uploaded instead of 100 MB
Savings: 95% bandwidth reduction

🔄 Sync & Conflict

Download & Sync Flow

Scenario 1: Device Online (Push Sync)

  1. Device A commits upload → Validator confirms
  2. MySQL metadata saved → Kafka event published
  3. Sync Service reads event: { fileId, ownerId, version: 2 }
  4. Fetches all devices linked to ownerId from DB
  5. Push notification to each device: "file-123 updated to v2"
  6. Each device's Sync Engine calls GET /files/{id}/download
  7. Server returns presigned S3 URL (or CDN URL)
  8. Device downloads, updates Local Metadata Index

Scenario 2: Device Reconnects (Pull Sync)

  1. Device B was offline for 3 hours. Reconnects.
  2. Sync Engine calls: POST /sync/pull?since=T
  3. Server queries: SELECT * FROM file_events WHERE owner_id=? AND created_at > T
  4. Returns: { changed: ["file-123"], deleted: ["file-789"] }
  5. Device downloads only changed files

Download API

GET /api/v1/files/{id}/download
→ {
  "downloadUrl": "https://cdn.example.com/...",
  "expiresIn": 300
}

CDN (CloudFront) caches popular files at edge PoPs — shared company docs downloaded by 1000 employees served from edge, not S3 us-east-1.

Metadata Service — File Tree & Namespace

A folder is NOT a real directory. It is just a metadata record with type=FOLDER. Creating a folder = inserting one row in MySQL. No actual directory structure in S3.

Folder APIs

MethodEndpointPurpose
POST/api/v1/foldersCreate folder (1 DB row)
GET/api/v1/folders/{id}/contentsList files + subfolders
PATCH/api/v1/folders/{id}Rename / move
DELETE/api/v1/folders/{id}Soft-delete + all children

Directory Structure in DB

folders table (MySQL)
├── folder_id UUID (PK)
├── name VARCHAR(255)
├── owner_id UUID (FK → users)
└── parent_folder_id UUID (nullable)

files table
└── parent_folder_id UUID (FK → folders)

Namespace Design

  • parent_folder_id = NULL → root folder
  • Full path reconstructed by traversing parent chain
  • Moving a file = UPDATE parent_folder_id — one DB write
  • Deleting a folder = soft-delete row + all child rows
  • No cascade deletes in DB — done in application layer for audit trail

Why Not a Real Directory in S3?

  • S3 has no real directories — objects have flat keys
  • Rename/move in S3 = copy + delete — expensive at scale
  • Our approach: rename = 1 MySQL UPDATE, S3 key unchanged
  • S3 key format: files/{fileId}/{chunkIndex} — never changes

File Versioning — Snapshot + Delta Log

How Versioning Works

  • Every successful upload creates a new FileVersion record
  • Old versions kept for rollback (not deleted from S3)
  • Only N most recent versions stored (configurable, e.g., 100)
  • Older versions moved to S3 Glacier for cost savings

Version Table Schema

file_versions (MySQL)
├── version_id   UUID (PK)
├── file_id      UUID (FK → files)
├── version_num  INT NOT NULL
├── size_bytes   BIGINT
├── s3_path      VARCHAR(500)
├── checksum     VARCHAR(64)  ← SHA-256
├── created_by   UUID (FK → users)
└── created_at   TIMESTAMP

Version Rollback API

GET  /api/v1/files/{id}/versions
→ list all versions

POST /api/v1/files/{id}/restore
{ "versionId": "ver-abc" }
→ sets current_version = versionId
   creates new FileVersion pointing to old chunks
   (does not delete intervening versions)

Storage Lifecycle

  • Current version: S3 Standard (~$0.023/GB)
  • Recent versions (30d): S3 Standard-IA (~$0.012/GB)
  • Older versions (90d+): S3 Glacier (~$0.004/GB)
  • Lifecycle rules configured in S3 automatically

With dedup: if two versions share unchanged chunks → same S3 objects referenced → minimal extra storage cost per version.

🔄 Sync & Conflict

Conflict Resolution — Offline Edits

Two devices edit the same file offline. Both sync when reconnected. Never silently lose data — use conflict copies.

Conflict Detection

  • Each FileVersion has: { versionNumber, deviceId, modifiedAt }
  • When Device B syncs, server checks: is Device B's base version still the latest?
  • No conflict: Device A synced, Device B's base = latest → merge/overwrite
  • Conflict: both A and B modified same base version → conflict copy

Conflict Resolution Strategy

  • Create two files:
    report.pdf (Device A's version — latest)
    report (conflicted copy — DeviceB 2024-01-15).pdf
  • Notify user: "Conflict found. Please resolve."
  • Both versions kept — user decides which to keep

Online vs Offline Conflict

ScenarioBehaviour
Both online, sequential editsLast-write-wins — later version stored, earlier kept as prev version
Both online, simultaneous editDB transaction detects same base version → conflict copy created
One offline, syncs laterOffline device version compared to latest — conflict copy if diverged
Auto-merge possible?Out of scope (Google Docs level). Drive just creates conflict copy.

This is exactly how Google Drive and Dropbox handle conflicts. Conflict copies are the safest UX — never silently lose data.

Access Control — Sharing & Permissions

Permission Model

  • VIEW — read-only, can download
  • COMMENT — can add comments, can't edit
  • EDIT — full read/write, can upload new versions
  • Permissions set per file or folder
  • Folder permissions cascade to all children

Share API

POST /api/v1/files/{id}/share
{ "userId": "user_bob", "role": "EDIT" }

GET /api/v1/files/{id}/share-link
→ { "url": "https://drive.example.com/f/abc123",
    "role": "VIEW", "expiresAt": "2024-12-31" }

Permission Check — Walk Up Parent Chain

  1. Check permissions for { resource_id: F, user_id: X }
  2. If not found: check F's parent folder G
  3. If not found: check G's parent folder H
  4. Continue until root or explicit permission found
  5. No permission found at root → deny

Permission Caching (Redis)

  • Cache key: perm:{userId}:{fileId} → { allowed: true/false, role }
  • TTL: 5 minutes — balance freshness vs DB load
  • On permission change to parent: invalidate all child-resource cache entries
  • Sub-millisecond permission check on every API call

📈 Scaling

Scaling — Google Drive at 1 Billion Users

Bottleneck 1: Storage (250 PB)

  • S3 lifecycle: Standard → IA (90d) → Glacier (1yr)
  • Cross-user dedup: if 1000 users upload same file → 1 S3 object
  • Result: effective storage 30–50% less than raw file count

Bottleneck 2: Sync Fan-Out

  • Power user has 50 devices. Each upload → 50 push notifications
  • 100M DAU × 5 changes/day × avg 3 devices = 1.5B notifications/day
  • Sync Service: horizontally scalable, stateless, Kafka consumer
  • Scale Sync Service instances to match Kafka consumer lag

Bottleneck 3: Metadata DB Sharding

  • 500B files × 1KB = 500 TB metadata
  • Shard MySQL by owner_id (user ID)
  • All a user's files are on the same shard → no cross-shard joins
  • 100 shards × 5 TB per shard = manageable
  • Read replicas per shard for read-heavy workloads

Bottleneck 4: Upload Throughput

  • Presigned URLs → client uploads directly to S3, bypasses backend
  • Our servers handle only metadata (tiny payloads)
  • S3 Transfer Acceleration for users far from S3 region
  • Regional S3 buckets: INIT response includes uploadRegion

🎯 Interview Prep

Senior Q&A — Race Conditions

Q: "User has 10 MB quota left. Uploads two 8 MB files simultaneously. Both pass the quota check. Total = 16 MB. How do you prevent this?"
A: This is a classic check-then-act race condition. Fix: Redis atomic reservation with a Lua script. 
-- On INIT (before any upload starts):
EVAL (runs atomically on Redis server):
  current = GET quota:{userId}
  if current + fileSize > quotaLimit: return -1  -- deny
  SET quota:{userId} (current + fileSize)
  return 1  -- approved

-- Lua script = single atomic Redis operation, no race possible
-- On upload failure: DECRBY quota:{userId} fileSize  (release)
-- On commit success: UPDATE users SET quota_used = quota_used + fileSize
Q: "Validator Service crashes after all chunks uploaded but before metadata written to MySQL?"
A: Idempotent retry. All data still intact:
  • Chunks: in S3 (not deleted yet)
  • Chunk hashes: in Redis with TTL=24h (not expired)
  • Validator can re-run validation from scratch — same result every time
  • Fix: Kafka retries the commit event. DLQ after 5 retries.
  • Client polls GET /files/{id}/status → still shows PROCESSING
  • If corrupt chunk found: notify client with { badChunks: [7, 12] } → re-upload only those

Senior Q&A — Geo & Failure Modes

Q: "User is in Mumbai. S3 bucket is in us-east-1. How do you make their 10 GB upload fast?"
A: Two options:
  • Option A — S3 Transfer Acceleration: AWS routes upload via CloudFront edge (Mumbai PoP) → AWS private backbone → us-east-1 S3. AWS backbone is much faster than public internet. Cost: ~2× more per GB. Best for large files.
  • Option B — Regional S3 Buckets: INIT response includes { uploadRegion: "ap-south-1" }. Presigned URL points to ap-south-1 bucket (~10ms latency). S3 Cross-Region Replication copies to primary bucket. Metadata written after replication completes. Server picks region from user's IP geolocation.
Q: "How do folder permissions cascade to child files?"
A: Permission check walks up the parent chain at query time.
  • "Can userId X read file F?" → check permissions for { resource_id: F, user_id: X }
  • If not found → check F's parent folder G → check G's parent H → … until root
  • Optimization: cache result in Redis perm:{userId}:{fileId} with TTL: 5 min
  • On any permission change to parent → invalidate all child-resource cache entries

Senior Q&A — What NOT to Say

✗ "I'll route the file upload through my backend server"
100M DAU × 10 MB = 1 TB/sec through your servers. Impossible. Use presigned URLs — client uploads directly to S3.
✗ "Just upload in one HTTP POST request"
15 GB files timeout at LB (30–120s). Network drop = restart from scratch. No progress indicator. Must use 5-step chunked upload protocol.
✗ "A folder is a real directory in S3"
S3 has no directories. A folder = just a row in MySQL. parent_folder_id creates the hierarchy. No S3 mkdir.
✗ "Use Cassandra for all metadata because it scales"
File metadata needs JOINs: files + permissions + versions. Cassandra has no joins. Use MySQL. Cassandra IS correct for chunks table (no joins, high writes).
✗ "I'll poll for sync every 5 seconds"
100M devices × every 5s = 20M requests/sec just for polling. Use OS file watchers (inotify/FSEvents) + Kafka push. Polling is a last resort fallback only.
✗ "On network failure, restart the upload from zero"
This is why chunked upload exists. Server stores which chunks are done (Redis). Client checks existingChunks on re-INIT. Resumes from the first failed chunk.

Closing — 60-Second Rapid Answer

"I'd design Google Drive with five pieces:

1. FILE UPLOAD (Chunked, direct to S3): Files up to 15 GB — split into 5 MB chunks client-side. SHA-256 per chunk. Backend generates presigned S3 URL per chunk. Client uploads directly to S3. Our servers never see file bytes. Validator confirms hashes. Metadata saved to MySQL.

2. SYNC ACROSS DEVICES (Kafka + push/pull): After commit, Kafka event → Sync Service → push notification to all linked devices. Each device downloads only CHANGED chunks (delta sync: re-hash, compare to local metadata index). Offline devices poll on reconnect.

3. STORAGE (S3 + MySQL + Cassandra + Redis): S3 for file bytes (250 PB). MySQL for metadata (folders, files, versions, permissions — needs JOINs). Cassandra for chunks (pure lookup by file_id, high writes). Redis for upload session state and quota reservation.

4. DEDUPLICATION: File-level: hash entire file on INIT. Same hash exists → skip upload, create version pointing to old chunks. Chunk-level: same chunk across files/users → stored once. 30–50% storage savings.

5. SHARING + PERMISSIONS: VIEW / COMMENT / EDIT per file/folder per user. Folder permissions cascade to all children. Cached in Redis (5-min TTL). Permission check walks up parent chain. Permission check on every API call."
