THE PROBLEM

Writing Directly to a Data Page Is Dangerous

UPDATE accounts SET balance=900 overwrites bytes in-place on page 5. A crash mid-write leaves a page that is neither the old value nor the new one.
1000 → writing → 900
CRASH mid-write = "19_0" garbage
  • No way to tell if it should say 900 or 1900 or something else
  • At thousands of random-page writes/sec, this happens constantly
  • Unacceptable for money, orders, or file metadata
3 / 10
THE SOLUTION

Log First. Data Page Second.

Write-Ahead Log: append the change, fsync it, THEN return success.
Transaction: balance 1000 → 900
1. Append WAL: LSN=1234, txn=567, 1000→900
2. fsync WAL to disk (durable)
3. Return "commit successful" to client

  • LSN — Log Sequence Number, monotonically increasing position in the WAL stream
  • PostgreSQL splits WAL into 16MB segment files under pg_wal/
  • A checkpoint (default every 5 min) flushes dirty pages — WAL before that LSN is safe to delete
  • Recovery only needs to replay from the last checkpoint forward, not from the beginning

synchronous_commit = off Is Not Free
