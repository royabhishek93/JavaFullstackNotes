This is the hot partition problem: you split data across shards/partitions to distribute load, but if the partitioning key is uneven, one partition drowns while the rest idle — and total-throughput monitoring still says "all systems normal."

Lesson

Time-based shard keys are almost always a bad idea — "today" is always hot, "history" is always cold, no matter how many shards you add.

Better Shard Keys

hash(user_id) hash(order_id)
→ uniform distribution across all shards.

Redis can handle ~500K req/sec per node in aggregate — but 10M users hitting one product page in 10 minutes all hash to node 2 for that key. Even with 3 Redis nodes, one node absorbs 100% of the viral traffic — "add more Redis nodes" does not fix this; you must change how the hot key itself is distributed.

Solution 1

Salt / Random Prefix on the Partition Key

Producer side (Java)

public String buildPartitionKey(String userId, boolean isCelebrity) { if (isCelebrity) { int salt = ThreadLocalRandom.current().nextInt(10); return userId + "_" + salt; // "user_12345_7" } return userId; }

Fan-out across partitions

user_12345
▶
+ salt 0-9
▶
spread across 6 partitions

Trade-off: Ordering Is Broken

Before salting: all events for user X in one partition → ordering guaranteed.

After salting: events for user_12345_3 and user_12345_7 may arrive out of order relative to each other.

To process ALL of a user's events (e.g. Ronaldo), consumers must now read from every partition and aggregate.

Fix: Sequence Number

Add a monotonic sequence number to each event; re-sort on the consumer side to restore per-user ordering.

Cell-Based Sharding — Alice trades 10K tx/sec

account_cells (account_id, cell_id)
Alice split across 10 cells (0-9) · random write picks cell 7 → no single hot row.
INSERT INTO account_cells (account_id, cell_id, balance) VALUES ('alice', 7, 99.50) ON CONFLICT ... DO UPDATE SET balance += EXCLUDED.balance; -- read: aggregate all cells SELECT account_id, SUM(balance) AS total_balance FROM account_cells WHERE account_id='alice' GROUP BY account_id;

Adaptive Rate Limiting / Backpressure

max.poll.records: 100 fetch.max.wait.ms: 100 pause.on.lag: true # custom
If partition lag > 1M records: pause consumer on that partition.

Prevents OOM from processing 50M messages at once.
Decision Framework

Hot Partition Mitigation by Layer

LayerSymptomRoot CauseSolution
KafkaOne partition's lag grows, others flatSkewed key (user_id, merchant_id)Salt key OR dedicated topic
DB shardOne node 95% CPU, others 10%Time-based key / single hot entityhash(entity_id) OR cell-based
Cache (Redis)One node saturated, others idleViral item hashes to one nodeLocal cache (Caffeine) top-N keys
CDN / HTTPOne origin overwhelmedPopular resource not cachedCDN cache + stale-while-revalidate
Load balancerSticky sessions → uneven loadSession affinity same nodeRound-robin OR IP-hash + migration

Kafka Limits

Single partition max: ~50MB/s write, ~150MB/s read.
Safe range: 10MB/s write, 30MB/s read.
>5x average → hot.

Redis Limits

~500K simple ops/sec (GET/SET), ~200K complex (ZRANGE, GEORADIUS).
>50K req/sec on one key → local cache.

PostgreSQL Limits

~5K writes/sec (indexed), ~50K reads/sec (buffer hits).
>3x average → re-shard / read replicas.

"The hot partition problem is where your load distribution assumption fails — you assumed uniform traffic per key but got power-law distribution, so you fix it either by splitting the hot key across multiple partitions with a salt or by giving predictably hot entities their own dedicated partition tier that can scale independently."
