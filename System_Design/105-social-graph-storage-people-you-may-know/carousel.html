Social Graph Storage & PYMK

Slide 1 / 9 — The Hook

1B users
300B edges

"Who follows Alice" can become a scatter query across dozens of shards if you store the graph naively.

One Table Scatters

The Problem

Table sharded by user_id: Alice's outgoing edges live on ONE shard. Everyone who follows HER is scattered across whichever shard THEY live on.

Bidirectional Storage

The Solution

connections_by_user
connections_by_friend

Write every connection TWICE, atomically. 2x storage → O(1) reads BOTH directions, 2-8ms.

Neo4j for Multi-Hop

When Cassandra Isn't Enough

"Shortest intro path to a hiring manager" — Cassandra needs a NEW partition read per hop, exploding combinatorially.

Neo4j's index-free adjacency: 10-80ms for a 3-4 hop query, even at 50M nodes.

PYMK Candidate Generation

2nd-Degree Fan-Out

For each of your friends, fetch THEIR friends. Count mutual-connection paths per candidate. Rank by count, take top 50.

The Scary Math

Where It Explodes

250,000 → 250 TRILLION

500×500 pairs for ONE user, naively, ×1B users. Blows out even a distributed Spark cluster.

Mitigations

Making It Tractable

✓ Cap fan-out to ~200 most active connections per user

✓ Sample connections for super-connectors (30K+ recruiters)

✓ Combiners pre-aggregate before final shuffle

Decision Tree & Interview Answer

Quick Reference

1-hop reads dominate? → Bidirectional Cassandra. Multi-hop path-finding needed? → Add Neo4j as a derived store. Graph-wide feature (PYMK)? → Always offline batch.

"I would never compute PYMK live on a page load. A full 2-hop fan-out generates up to 250,000 candidate pairs per user before dedup — I'd run it as an offline Spark GraphX batch job nightly, cache the top-50 per user, serve reads in single-digit milliseconds."
