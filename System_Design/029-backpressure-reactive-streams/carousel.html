"Our service crashes every time there's a traffic spike. We're losing messages. What's going on?"

→
Watering can (Consumer)
2 liters/second

No backpressure water overflows the can everywhere. In software: in-memory buffer fills, OutOfMemoryError, consumer crashes, all buffered messages lost.

With backpressure the can signals "slow down — I can only take 2L/sec." The hose throttles. Nobody drowns.

Signal travels differently: same-process reactive streams call request(N); across services, Kafka consumer just stops polling; HTTP returns 429/503.

Reactive Streams — The Pull Model

Consumer Controls the Rate, Not the Producer

PUSH (no backpressure): Producer decides when to send → consumer has no say → overwhelmed → OOM.

PULL (backpressure):

Subscriber
— request(3) →
Publisher
Subscriber
← item1,2,3 —
Publisher

Publisher CANNOT send item4 until Subscriber asks for it. Consumer paces the entire pipeline.

Reactive Streams contract (Java):

interface Publisher<T> { subscribe(Subscriber<T> s); } interface Subscriber<T> { onSubscribe(Subscription); onNext(T); onError(Throwable); onComplete(); } interface Subscription { request(long n); cancel(); }

Project Reactor, RxJava, Akka Streams all implement this spec.

Project Reactor — Right vs Wrong

flatMap vs concatMap vs Bounded flatMap(n)

PatternBehaviorVerdict
.flatMap(fn)1,000,000 concurrent subscriptions immediately✗ OOM
.concatMap(fn)Waits for each to complete before next; sequentialSlow but safe
.flatMap(fn, 10)Max 10 concurrent; producer waits when full✓ Right balance
// ✅ bounded parallelism — memory bounded, throughput × 10 Flux.range(1, 1_000_000) .flatMap(i -> callSlowDownstream(i), 10) .subscribe(); // ✅ explicit pull model source.subscribe(new BaseSubscriber<Order>() { protected void hookOnSubscribe(Subscription s) { request(10); } protected void hookOnNext(Order o) { processOrder(o); request(1); // ask for exactly one more } });

concatMap: use when order matters, throughput requirement is low. Bounded flatMap(n): best general-purpose balance.

Consumer group: each instance gets a subset of partitions. Max useful consumers = partition count. Adding instances triggers automatic rebalance.

Decision Tree & Series Finale

Choosing a Backpressure Strategy

Is data loss acceptable?
├─ YES → Bounded drop-on-overflow (analytics, logs)
└─ NO → Same JVM as consumer?
├─ YES → LinkedBlockingQueue (block on full)
└─ NO → HTTP service-to-service?
├─ YES → Circuit breaker + 503 + bulkhead
└─ NO → Kafka/SQS + HPA autoscale on lag
"Backpressure is the consumer's ability to signal 'slow down' to the producer — Kafka naturally handles it by decoupling production rate from consumption rate, with lag as the visible signal that triggers autoscaling."
