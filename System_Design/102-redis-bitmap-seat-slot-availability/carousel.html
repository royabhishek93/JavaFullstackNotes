Redis Bitmaps

Slide 1 / 9 — The Hook

900KB → 1.25KB

10,000 stadium seats as separate Redis keys vs one bitmap. A ~700x memory difference for the same information.

Per-Entry Overhead Adds Up

The Problem

10,000 separate keys, each carrying ~90 bytes of key-name + object-header overhead — for 1 bit of actual data each.

A Bitmap stores raw bits directly in one String, with near-zero per-entry cost.

SETBIT / GETBIT

The Solution

00101100

SETBIT seats:section-A 4821 1 books a seat — one bit flip, no new key.

Aggregate Operations

BITCOUNT & BITPOS

BITCOUNT seats:section-A → total booked seats, whole section, in microseconds.

BITPOS seats:section-A 0 → first available seat, instantly.

Combining Constraints

BITOP AND

BITOP AND result available wheelchair aisle

Finds seats matching ALL 3 conditions in one bitwise operation — no composite DB index needed.

Sparse ID Spaces Break Bitmaps

The Trap

Track 50M sparse user IDs as bit offsets → Redis allocates up to the HIGHEST bit set.

✕ 1 user with ID 49,999,999 forces a 6.25MB allocation for that key alone.

Atomic Check-Then-Book

Race Protection

if GETBIT(key,offset)==0 then SETBIT(key,offset,1); return 1 else return 0 end

Two users can't both win the same seat — one atomic Lua step, not two separate commands.

Decision Tree & Interview Answer

Quick Reference

Dense, bounded, integer-indexable space? → Bitmap. Sparse/unbounded IDs? → Bloom filter. Cardinality estimate only? → HyperLogLog.
