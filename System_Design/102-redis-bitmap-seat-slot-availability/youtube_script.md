## THE PROBLEM (0:30–2:00)
"Think about it this way — for every seat in a stadium, you need exactly one fact: booked or not. That's one bit. But the instinct of most developers is to model this as 10,000 database rows, or 10,000 separate Redis keys, or a hash with 10,000 fields. Each of those carries real per-entry overhead — a row header, a key name string, dictionary pointer metadata — that dwarfs the actual single bit of information you're trying to store. A Redis Bitmap exploits a simple fact instead: a Redis String is just a sequence of bytes, and Redis lets you address and flip individual BITS within that byte sequence directly. Think of it like one very long string of light switches on a wall — 'is seat 4821 booked' is just 'is switch 4821 on,' and you don't need a separate labeled switch-box for each one; they're all just positions along one wire."

[Screen cue: Draw a wall of 16 light switches, some on some off, mapping directly to a 2-byte binary string underneath.]

## THE SOLUTION (2:00–5:00)
"Now watch the actual commands. Booking seat 4821 is one line: `SETBIT seats:section-A 4821 1` — it doesn't create a new key or field, it flips one bit within the existing string, growing it automatically if needed. Checking if it's booked: `GETBIT seats:section-A 4821`. But the real superpower is the aggregate operations. `BITCOUNT seats:section-A` gives you the total booked count across ALL ten thousand seats in one command, using hardware-optimized popcount instructions, completing in low microseconds. `BITPOS seats:section-A 0` finds the very first available seat instantly. And here's where it gets genuinely powerful: to find a seat that's simultaneously available AND wheelchair-accessible AND an aisle seat, you maintain three separate bitmaps — one per attribute — and run `BITOP AND` across all three into a scratch key, then `BITPOS` on the result to get the first seat matching ALL three conditions at once. No looping over ten thousand rows in application code, no composite database index — just a single bitwise AND across three one-kilobyte strings."

[Screen cue: Draw three parallel bitmaps — available, wheelchair, aisle — combining via BITOP AND into a single result bitmap, with BITPOS finding the first matching seat highlighted.]

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"Here's the trap: bitmaps are a phenomenal fit for a DENSE, BOUNDED ID space — seat zero through ninety-nine ninety-nine, where every single index genuinely exists. But apply the exact same pattern to a SPARSE or unbounded ID space, and it backfires badly. Imagine tracking 'which of our 50 million registered user IDs logged in today' using the raw user ID as the bit offset. Redis allocates a CONTIGUOUS string covering bit zero through the highest bit offset you've ever set — so if even one user with ID 49,999,999 logs in, Redis allocates roughly 6.25 megabytes for that ONE key, even if only three users ever actually log in that day. If your ID space is sparse or non-sequential — random UUIDs, Snowflake IDs — a bitmap wastes enormous memory representing gaps nobody cares about, and you can't even use non-integer IDs as bit offsets at all. For that exact use case — tracking membership across a huge, sparse, growing ID space — a Bloom filter is the right structure instead, trading a small tunable false-positive rate for handling effectively unbounded ID spaces in a fixed memory budget. And if you only need a cardinality ESTIMATE, like 'how many unique visitors today' rather than per-ID membership, HyperLogLog is the better fit. The second trap is atomicity for the actual booking action: two users can't both win the same seat in a race, so the check-then-book step needs a small Lua script doing a GETBIT check and conditional SETBIT in one atomic operation, not two separate commands from application code."

## REAL WORLD (8:00–9:30)
"Think about BookMyShow or a similar stadium/theater ticketing platform in India — modeling seat availability, wheelchair-accessibility, and aisle-seat attributes as separate bitmaps lets a 'find me a matching seat' query resolve via a single BITOP AND across the whole section in microseconds, even during a ticket-drop traffic spike. Think about a habit-tracking or attendance feature at scale — 365 days a year is exactly 365 bits, about 46 bytes per user per year, so even 100 million users tracked for a full year comes out to roughly 4.3 gigabytes total, trivially manageable on a single well-provisioned Redis instance, versus a naive per-day-row schema that would balloon into billions of rows. And think about a flight or bus seat-map service for a platform like an Indian travel booking app — the exact same dense, bounded seat-index pattern applies, just with a different fixed capacity per vehicle instead of per stadium section."
