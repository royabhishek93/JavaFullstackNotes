Slide 1 · The Hook

Elasticsearch vs PostgreSQL Full-Text Search

"We already have PostgreSQL. Do we really need Elasticsearch?" — Maybe not. It depends on what kind of tool you're building.

PostgreSQL FTSa searchable notebook

Great at storing structured data. tsvector + GIN gives solid keyword search, stemming, ranking — for free, with zero extra infrastructure.

Elasticsearcha Google-quality search appliance

A dedicated search engine bolted alongside your notebook: distributed, faceted search, typo tolerance, autocomplete, vector search — but a whole separate system to run.

The real question: does your use case justify the added complexity of a second system?

Slide 2 · The Problem

Same Data, Two Possible Paths

One product catalog. Two very different ways to make it searchable — the choice depends on scale and required features.

Path A — Keyword Search In-Place

PostgreSQLtsvector + GIN

Add a tsvector column, index it with GIN, query with ts_rank. One system, ACID, immediately consistent.

Path B — Dedicated Search Cluster

Elasticsearch Clustersharded, replicated nodes

A separate, purpose-built cluster: faceted search, fuzzy matching, sub-10ms latency at huge scale — synced from PostgreSQL.

Most production systems use both: PostgreSQL as source of truth, Elasticsearch as the read-optimized search index.

Slide 3 · PostgreSQL FTS Mechanics

tsvector + GIN Index + ts_rank

PostgreSQL10-100ms @ 10M rows
-- 1. Generated tsvector column (computed on write, stored on disk)
ALTER TABLE products ADD COLUMN search_vector tsvector
  GENERATED ALWAYS AS (to_tsvector('english', title || ' ' || description)) STORED;

-- 2. GIN index: lexeme -> row locations
CREATE INDEX products_search_gin_idx ON products USING GIN(search_vector);

-- 3. Query with relevance ranking
SELECT id, title, ts_rank(search_vector, query) AS rank
FROM products, plainto_tsquery('english', 'wireless headphones') query
WHERE search_vector @@ query
ORDER BY rank DESC LIMIT 10;

-- Typo tolerance needs a SEPARATE extension + index
CREATE EXTENSION pg_trgm;
CREATE INDEX products_trgm_idx ON products USING GIN(title gin_trgm_ops);

GIN build time: ~10 min / 10M rows. Index size: ~30-40% of source text. Fuzzy matching (pg_trgm) is a second, separate index — a second maintenance cost.

Slide 7 · Decision Checklist

Do You Actually Need Elasticsearch?

If 3+ boxes below are checked, Elasticsearch is justified. Otherwise, stay on PostgreSQL FTS.

  • ?Document count > 10M?
  • ?Need faceted search — filter by N attributes in one query?
  • ?Need autocomplete / search-as-you-type?
  • ?Need relevance tuning (boost by popularity, freshness, margin)?
  • ?Search QPS > 500 on a database shared with OLTP?
  • ?Need vector / semantic search at scale (>1M vectors)?
  • ?Need multi-language stemming (Arabic, Chinese, Japanese)?
  • ?Sub-10ms latency required at large scale?

Slide 10 · Decision Flowchart & Recommendation

Choosing the Right Search Architecture

Do you need full-text search? → YES
How many documents?
< 1M → PostgreSQL FTS. Done.
1M – 10M → PostgreSQL FTS (monitor, plan ES migration)
> 10M → lean Elasticsearch
Need faceted search (aggregations)? → YES: Elasticsearch · NO: PostgreSQL may work
Need sub-10ms latency at scale? → YES: Elasticsearch · NO: PostgreSQL FTS
Need semantic / vector search? → <1M vectors: pgvector · >1M vectors: Elasticsearch (HNSW)
Elasticsearch operational experience? → NO + scale allows: PostgreSQL FTS · YES / managed available: Elasticsearch
"PostgreSQL as source of truth, Elasticsearch as search index — pick Elasticsearch only when document count, faceted search, or latency truly demand it."
