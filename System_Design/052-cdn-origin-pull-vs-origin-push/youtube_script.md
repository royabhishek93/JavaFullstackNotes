# CDN Origin Pull vs Origin Push — YouTube Script
Duration: ~10 min | Target: Engineers 3–10 YOE | Episode: 52

## HOOK (0:00–0:30)
"Ten million people try to stream a movie premiere at the exact same second. If your CDN has never cached that video before, every single one of those ten million requests turns into a cache miss — and all of them slam your origin server at once. That's not a hypothetical. That's what happens if you get CDN strategy wrong on launch day. Today I'm breaking down the two ways a CDN gets your content to its edge nodes — origin pull and origin push — and the exact traps that turn a viral launch into an outage."

[Screen cue: A world map lighting up with thousands of dots simultaneously, all arrows converging on one single "ORIGIN" server icon that starts flashing red.]

## THE PROBLEM (0:30–2:00)
"Here's the setup. A CDN — Content Delivery Network — is just a network of servers spread around the world that cache your content close to users. Without one, every user in Tokyo fetching your video from a server in New York pays a 150 millisecond round trip. Put a CDN node in Tokyo, and that same user gets served in 5 milliseconds — thirty times faster. But here's the question nobody asks until it bites them: how does that Tokyo CDN node get your content in the first place? It doesn't come pre-loaded. There are exactly two strategies. Origin pull is lazy — the CDN node has nothing until a user asks for it. First request: cache miss, CDN fetches from your origin, caches it, serves it. Every request after that is a cache hit, straight from the edge. Origin push is eager — you proactively push content to every CDN node before a single user has asked for it. By the time the first user in Tokyo requests it, it's already sitting there. Zero cache misses, anywhere, for anyone. Sounds simple. It's the choice of WHEN you push versus pull, and getting it backwards is exactly what causes your origin server to fall over."

[Screen cue: Split screen — left side "Origin Pull: lazy, fetch on demand" with a clock ticking on first request; right side "Origin Push: eager, pre-warmed" with all edges already green before any user connects.]

## THE SOLUTION (2:00–5:00)
"Let's walk through origin pull first, because it's the default for basically every CDN. First request from Tokyo: GET /videos/movie.mp4, CDN node checks its cache, MISS, so it forwards the request to your origin server in New York, waits 150 milliseconds, gets the file, caches it locally with whatever TTL your Cache-Control header specified — say, 7 days — and finally serves it to that first user at 150ms. Every subsequent user in Tokyo for the next 7 days? 5 milliseconds, straight from cache. That's origin pull working exactly as designed — one slow request pays the cost, everyone else benefits. Now flip it: origin push. Before you even launch, you upload the new movie to S3, and immediately call your CDN's API — something like POST /invalidations with the video path — which pre-warms all 200-plus edge nodes worldwide. The CDN proactively fetches the file into every single edge before any user has asked. User 1 in Tokyo, worldwide: GET request hits CDN Tokyo, HIT, because it was pre-warmed. 5 milliseconds, no cold start, no cache miss latency, for literally the very first user anywhere. That's the fundamental trade-off: pull is simple and works great for unpredictable long-tail content — you don't waste bandwidth pre-warming things nobody watches. Push costs you a big proactive fetch across every edge, but you eliminate the cache-miss penalty entirely for content you KNOW will be popular. The production rule: if you know in advance content will go viral — a scheduled movie premiere, a major product launch — push it. For everything else — the millions of long-tail files nobody can predict — pull, and let the CDN warm itself naturally."

[Screen cue: Two side-by-side sequence diagrams — Origin Pull showing "MISS → fetch 150ms → cache → HIT 5ms for user 2+" and Origin Push showing "pre-warm 15-30min BEFORE launch → HIT 5ms for user 1".]

## DEEP DIVE — WHERE ENGINEERS GET IT WRONG (5:00–8:00)
"Here's trap number one: the cache miss storm. You publish a viral video and 100,000 users worldwide try to watch it at the same instant. The CDN has never cached it anywhere. Every single one of those requests hits a different edge node, every edge node sees a cache miss, and all 100,000 of them simultaneously fetch from your origin at once. Your origin — one server, or one small cluster — just got hit with 100,000 concurrent requests it was never built to handle. It falls over. There are three fixes, and you need to know all three. First: request coalescing — if a CDN node gets 1,000 simultaneous requests for the exact same URL, it doesn't make 1,000 calls to your origin. It makes ONE call, holds the other 999 requests waiting, and serves all of them the moment the origin replies. Second: pre-warming — this is origin push again, for content you know in advance will be viral, like our movie premiere example. Third, and this is the one people miss: origin shield. You designate one CDN region — say us-east-1 — as the shield. Every other edge node worldwide doesn't talk to your origin directly anymore; it talks to the shield. The shield hits your origin once per cache miss and serves every other edge from ITS warm cache. That turns your origin's request rate from 'N edge nodes hammering you' down to 'exactly 1 shield hitting you.' Trap number two is cache invalidation — and there's a famous quote for this: 'there are only two hard things in computer science: cache invalidation and naming things.' Say you cached a product page with a 24-hour TTL, then you change the price. For the next 24 hours, users see the OLD price from cache. Support tickets flood in. You've got three options. Short TTL — cache for just 60 seconds — simple, but now you're hitting origin 60 times more often than a 1-hour TTL. Explicit purge — call the CDN API to invalidate that specific URL the moment the price changes; CloudFront propagates that in about 30 seconds, but it costs you money, roughly half a cent per thousand invalidation paths. Or the best option for static assets: cache busting. Embed a content hash directly in the URL — slash assets slash app dot ABC123 dot JS. When the file changes, it gets a NEW hash, which means a NEW url. The old URL stays cached forever — that's fine, nobody's fetching it anymore. The new URL was never cached, so it's fetched fresh automatically. Set the TTL to one full year because a given hash literally never changes. Zero invalidation calls needed, ever. Trap number three — and this trips people up on cache headers specifically — Cache-Control: no-cache does NOT mean 'don't cache.' It means 'cache it, but revalidate with the origin on every single request using an ETag.' If you actually want zero caching for user-specific data, you need Cache-Control: no-store. Mixing those two up either wastes an unnecessary origin round-trip on every request, or worse, leaks one user's cached response to a different user."

## REAL WORLD (8:00–9:30)
"Think about a Hotstar-style premiere in India — a new IPL match or a big movie drops and ten million-plus concurrent viewers try to stream within the same five minutes. Run the actual math on this: a two-hour movie at 720p breaks into roughly one thousand four hundred forty HLS segments at ten megabytes each — that's 14.4 gigabytes per edge node. Multiply that across 220-plus edge locations worldwide and you're pre-warming 3.17 terabytes of video into the CDN, in a 15-to-30-minute window, BEFORE a single viewer connects. Get that pre-warm window wrong and ten million viewers all hit an unwarmed origin at the exact same second. Picture Swiggy or Zomato serving restaurant menu images and static assets — those are long-tail, totally unpredictable which restaurant's photo gets viewed next — that's origin pull with an origin shield, targeting a greater than 95 percent cache hit rate on static assets, so a sudden spike in one city's food delivery traffic doesn't stampede the origin directly. And imagine Flipkart or Myntra during a flash sale, pushing out banner images and product photos with a fresh price — if they used a 24-hour TTL with no invalidation strategy, millions of users would see yesterday's discounted price hours into the sale; a CloudFront-style explicit purge propagates in about 30 seconds, which is exactly why cache-busted, hashed URLs for static assets plus explicit purge for time-sensitive pricing pages matters at that scale."

## OUTRO + NEXT EPISODE (9:30–10:00)
"So here's the one-liner to remember: origin pull is lazy, fetching from origin on the first miss per edge — it's your default for unpredictable, long-tail content. Origin push is eager, pre-warming content before users ever show up — use it when you already know something's going to be huge. And no matter which one you pick, layer an origin shield underneath to protect your origin from a cache-miss storm, and use cache-busted URLs for anything static so you almost never need to invalidate at all.
