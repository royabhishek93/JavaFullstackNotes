State Interface (Java)

interface ElevatorState {

    void addRequest(Elevator e, Request r);
    Direction getDirection();
}
// 5 concrete states:

// MovingDownState, DoorOpenState,

Why State Pattern?

  • Elevator delegates move() to current state object
  • addRequest() behaves differently per state
  • No giant if/else chains — each state is a class
  • Add new state = add new class only (Open/Closed)
  • setState() triggers notifyObservers() for displays

FCFS — First Come First Serve Scheduling

How It Works

  • Process requests in exact arrival order
  • Elevator serves floor A, then B, then C — no reordering
  • Simple FIFO queue — easy to implement

Starvation Example

Queue: [10, 1, 10, 1, 10, 1]
Elevator @ floor 5:
  → 10  (5 floors up)
  → 1   (9 floors down)  ← wasteful!
  → 10  (9 floors up)
  → 1   (9 floors down)
Total: 32 floors for 4 requests

Problems

  • Lots of direction reversals — high energy waste
  • Starvation: floor 5 waits while elevator ping-pongs
  • No benefit from locality of requests
  • Does not group same-direction requests

When to Use

  • Very low traffic (1–2 requests at a time)
  • Fair ordering required by policy (hospital, VIP)
  • Baseline for comparing other algorithms

Fix starvation: aging — increase request priority every 30 sec. Force assignment when wait exceeds threshold (e.g., 3 minutes).

SCAN — The Classic Elevator Algorithm

Sweep from one end to the other, serving all requests along the way. Borrowed from disk scheduling.

Algorithm

Elevator @ floor 5, going UP
Pending:  [2, 4, 8, 11, 14]

Pass UP:   serve 8 → 11 → 14
  → reach top floor (20)  ← always!
  → reverse direction DOWN
Pass DOWN: serve 4 → 2
  → reach bottom floor (1)  ← always!
  → reverse direction UP

SCAN vs FCFS

FCFS: 32 floors travel
SCAN: 5→14 (9 up) + 14→2 (12 down)
    = 21 floors  (~34% fewer moves)

Properties

  • No mid-sweep direction reversals
  • Predictable: worst case = 2 × building height
  • Prevents starvation — every floor visited each sweep
  • Requests at ends of sweep wait longest (unfair to extremes)
  • Dead run: goes to end floor even with no requests there

Java Data Structures

TreeSet<Integer> upRequests;   // ascending
TreeSet<Integer> downRequests; // descending
// Moving UP:   serve upRequests.first()
// Moving DOWN: serve downRequests.first()

SCAN wastes travel going to floor boundary when no requests exist there — LOOK fixes this.

LOOK — SCAN Without the Dead Runs

LOOK is identical to SCAN except it reverses at the last actual request, not the building boundary.

SCAN vs LOOK Comparison

Building: 20 floors  |  Pending: [2, 8, 11]

SCAN:  5→8→11→20 (dead run!) →8→2
       travel = 15 + 18 = 33 floors

LOOK:  5→8→11 (reverse here!) →8→2
       travel = 6  +  9 = 15 floors

LOOK saves ~55% travel in this case

Core Difference

  • SCAN: sweep to physical floor boundary
  • LOOK: sweep to logical boundary (last pending request)
  • LOOK = SCAN with early reversal

LOOK Implementation

def next_floor(self):
    if self.direction == 'UP':
        above = [f for f in pending
                 if f > self.current_floor]
        if above:
            return min(above)
        else:
            self.direction = 'DOWN'  # reverse!
            return self.next_floor()
    else:
        below = [f for f in pending
                 if f < self.current_floor]
        if below:
            return max(below)
        else:
            self.direction = 'UP'   # reverse!
            return self.next_floor()

LOOK is the preferred algorithm for most real-world elevator firmware. Use it as your default answer in interviews.

Multi-Elevator Dispatch Strategies

Nearest Car (Priority Order)

  1. Idle elevator closest to request floor
  2. Moving elevator passing request in same direction
  3. Moving elevator that will return on reversal
  4. Least-loaded busy elevator (fallback)
cost(e, req) =
  abs(e.floor - req.floor)
  + penalty_for_direction_change
  + queue_length × weight_factor

Concurrency Safety

  • AtomicInteger for thread-safe floor tracking
  • synchronized addRequest() on each elevator
  • Redis distributed lock for fleet-level dispatch

Zone-Based (Skyscraper)

100 floors, 10 elevators:
  E1:  Floors  1–10  (lobby zone)
  E2:  Floors 11–20
  ...
  E10: Floors 91–100 (sky lobby)
Express:
  EA:  Floors 1, 50, 100 (bypass)

Dynamic Rebalancing

  • Morning rush: bias 7 elevators to lobby→office zones
  • Lunchtime: redistribute to restaurant floors
  • Zone spill: if zone elevator full > 60 sec, reassign

Destination Dispatch: passenger enters destination before boarding; system groups by floor and assigns specific car. Used in Otis Compass, Schindler PORT.

Request Processing — Hall Call vs Car Call

Hall Call (Floor Button)

  • Pressed on a floor by waiting passenger
  • Specifies direction: UP or DOWN only
  • Sent to ElevatorController for dispatch
  • Multiple elevators may be candidates
  • Assignment can change until elevator arrives

Car Call (Cabin Button)

  • Pressed inside the elevator cabin
  • Specifies exact destination floor
  • Bound to that specific elevator car
  • Cannot be reassigned to another elevator

Request Merging (Key Optimization)

Elevator going UP, current floor = 3
Pending upRequests: {5, 8, 12}

Hall call: floor 7, direction UP
  → insert 7 → serve 3→5→7→8→12
  → zero extra travel cost!

Car call: floor 6 (passenger inside)
  → insert 6 → serve 3→5→6→7→8→12

Request Lifecycle

PENDING → ASSIGNED → IN_SERVICE → COMPLETED
         (dispatch)  (elevator    (passenger
                      en route)    boards)

Merging same-direction requests in one pass is the core efficiency of LOOK/SCAN over FCFS.

void onFireAlarm() {

Smart Dispatch — ML-Based Optimization

Strategy Pattern: plug in MLDispatchStrategy without changing Elevator or Controller code.

Time-of-Day Patterns

08:00–09:30  Morning Rush
  → Pre-position 70% of elevators at lobby
  → Lobby → office floors (10–30) priority
  → Express: skip floors 2–9

12:00–13:00  Lunchtime
  → Redistribute to restaurant floors
  → Increase down-direction capacity

  → Office floors → lobby burst

Emergency Mode & Maintenance Lockout

EmergencyState Behavior

class EmergencyState implements ElevatorState {
    public void addRequest(Elevator e, Request r) {
        log.warn("EMERGENCY: request ignored");
    }
    public void move(Elevator e) {
        if (e.getCurrentFloor() != GROUND) {
            e.setCurrentFloor(
              e.getCurrentFloor() - 1);
        } else {
            e.getDoor().open(); // stay open
        }
    }
    public Direction getDirection() {
        return Direction.DOWN;
    }
}

Fire Alarm Trigger Chain

FireAlarmSystem → ElevatorController
  → ALL elevators → EmergencyState
  → All elevators descend to GROUND
  → Hall call buttons DISABLED
  → Doors stay open at ground floor
  → Reset only by Fire Marshal code

MaintenanceState

  • Triggered by: technician keyswitch, fault detection
  • Ignores all hall calls and car calls entirely
  • Door controlled manually by technician only
  • Display: shows OUT OF SERVICE to all floors
  • Exit: requires admin PIN + full health check pass

MAINTENANCE can only exit via explicit admin command — never triggered by a passenger event.

    requested_at     TIMESTAMP DEFAULT NOW(),

Design Patterns Used — Full Summary

State Pattern

  • ElevatorState interface → 5 concrete states
  • Elevator delegates move() and addRequest() to state
  • Add new state = add new class (Open/Closed Principle)

Strategy Pattern

  • ElevatorSelectionStrategy → NearestElevator, ZoneBased, ML
  • SchedulerStrategy → FCFS, SCAN, LOOK, SSTF, DestDispatch
  • Swap at runtime: controller.setStrategy(new LookStrategy())
  • A/B test schedulers in production without restart

Observer Pattern

  • ElevatorObserver → FloorDisplay, Controller, MobileGateway
  • Elevator calls notifyObservers() on every state/floor change
  • Decouples elevator logic from UI and external systems

Command Pattern

  • Button press → Request command object (floor, direction, source)
  • Queued in ElevatorController for async dispatch
  • Supports: cancel, retry, priority override, audit log

Singleton

  • ElevatorSystem — building-scoped singleton via getInstance()
  • Single dispatch authority; thread-safe via synchronized

Trade-off Analysis

DecisionOption AOption BWinner & Why
Scheduling FCFS (simple) LOOK (efficient) LOOK — 30–55% less travel, no starvation
SCAN vs LOOK SCAN (to ends) LOOK (last request) LOOK — dead runs to boundaries waste energy
LOOK vs SSTF SSTF (greedy nearest) LOOK (sweep) LOOK — SSTF starves far floors without aging
Dispatcher Centralized cloud Edge per building Hybrid — edge for latency, cloud for ML
Request Queue Single queue Two TreeSets (up/down) Two TreeSets — O(log n) insert, O(1) next floor
Concurrency Single thread Thread per elevator Thread per elevator — isolated failures

Key insight: Two TreeSets (upRequests ascending, downRequests descending) make LOOK trivially efficient — just call .first() to get next floor in either direction. O(log n) insert, O(1) next.

Senior Q&A 1 — 100-Floor Skyscraper Design

Q: You have 10 elevators in a 100-floor skyscraper. Peak hour: 200 people arrive at lobby every minute. Design the dispatch strategy.
Answer:
  • Zone partition — assign each elevator a 10-floor zone (E1: 1–10, E2: 11–20, …, E10: 91–100)
  • Peak rebalancing — bias 7 elevators to lobby→office zones (floors 1–70), 3 for upper floors
  • Destination Dispatch — lobby kiosk: passenger enters floor, system groups by zone, assigns specific car → fewer stops per trip
  • Pre-positioning — move 8 elevators to lobby at 08:55 based on historical Monday pattern data
  • Batch filling — don't dispatch until car is >80% capacity (group control reduces total trips)
  • Express elevators — dedicate 2 cars as non-stop: floors 1→50, 1→100 (sky lobby bypass)
  • Starvation guard — if any floor waits >3 min, override zone assignment and force dispatch

Senior Q&A 2 — Peak Hour Rush

Q: It is 9:00 AM Monday. 500 employees arrive in 30 minutes. Average office is floors 10–30. How do you optimize elevator throughput?
Answer:
  • ML pre-positioning — model detects Mon 09:00 pattern; moves 80% of elevators to lobby by 08:50
  • Express upward priority — disable DOWN requests from lobby floors during 08:45–09:30 window
  • Destination Dispatch kiosks — open at 08:45; first elevator dispatched within 30 sec with full load
  • Dynamic zone shift — double-assign elevators to floors 10–30 (peak office density zone)
  • Cascade dispatch — as elevator doors close, immediately dispatch next car to lobby
  • Capacity math — 10 elevators × 15 persons × 12 trips/hr = 1,800 persons/hr throughput
  • Starvation protection — aging mechanism ensures floor 35+ gets service within 3 minutes

Senior Q&A 3 — Elevator Stuck Between Floors

Q: An elevator is stuck between floors 7 and 8. Passengers are inside. Walk through the full recovery sequence.
Recovery sequence:
  1. Detect — position sensor mismatch auto-triggers MaintenanceState; all car calls disabled immediately
  2. Communicate — intercom activates automatically; operator speaks to passengers to calm them
  3. Alert — emergency dispatch: nearest technician notified via SMS + maintenance app push notification
  4. Slow-speed rescue — motor creeps car to floor 7 (nearest floor below) at <0.3 m/s on backup UPS power
  5. Manual door release — technician uses emergency key; door opens at floor 7 landing level
  6. Reroute — adjacent elevator immediately reassigned to serve floor 8 passengers
  7. Log — incident written to maintenance_logs with fault_type, description, timestamp, elevator_id
  8. Lockout — car stays in MAINTENANCE until mechanical inspection passes and admin unlocks

Closing — What Signals Seniority

Algorithm Decisions

  • LOOK > SCAN > FCFS — always recommend LOOK as default
  • Two TreeSets (up ascending, down descending) = natural LOOK data structure
  • Zone-based + Destination Dispatch for 100-floor skyscrapers
  • ML pre-positioning for peak-hour efficiency (Strategy Pattern)
