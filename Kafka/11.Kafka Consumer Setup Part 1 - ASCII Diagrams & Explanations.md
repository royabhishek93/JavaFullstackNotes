## 1. The 5 Required Properties

These five properties are the bare minimum to start a consumer. Everything else has a sensible default.

```
application.properties — minimum consumer config
────────────────────────────────────────────────────────────────────

  spring.kafka.bootstrap-servers=broker1:9092,broker2:9092
        │
        └─► Entry point to fetch cluster metadata (first contact only)

  spring.kafka.consumer.group-id=order-consumer-group
        │
        └─► Which consumer group this consumer belongs to

  spring.kafka.consumer.key-deserializer=StringDeserializer
  spring.kafka.consumer.value-deserializer=JsonDeserializer
        │
        └─► Producer serialized key+value → consumer must deserialize back

  spring.kafka.consumer.properties.spring.json.value-default-type=
        com.eda.consumer.model.Order
        │
        └─► Required only when value-deserializer is JSON
            "If you don't know which class to map to, use this one"
```

## 2. Group Coordinator Discovery

Before reading a single message, the consumer must find the broker that manages its group. This is a hash calculation using the group ID and the `__consumer_offsets` topic.

```
Kafka cluster: __consumer_offsets topic has 50 partitions

  hash("order-consumer-group") % 50  →  partition 23

  Broker 1 holds partitions  1–25   ← leader of partition 23
  Broker 2 holds partitions 26–50

  ┌─────────────────────────────────────────────────────┐
  │  __consumer_offsets                                 │
  │  ┌───┬───┬───┬───┬───┬──────┬───┬───┬───┬───┐      │
  │  │ 1 │ 2 │...│23 │...│ 25  │26 │...│50 │   │      │
  │  └───┴───┴───┴─┬─┴───┴──────┴───┴───┴───┴───┘      │
  │                │ leader = Broker 1                   │
  └────────────────┼────────────────────────────────────┘
                   │
                   ▼
            GROUP COORDINATOR = Broker 1
            (manages "order-consumer-group")
```

## 3. Consumer Joins the Group — Rebalance

When a new consumer joins, the group coordinator triggers a rebalance to redistribute topic partitions fairly among all consumers.

```
BEFORE: 2 consumers in group, topic has 3 partitions
────────────────────────────────────────────────────────────────────
  order-events topic
  ┌──────┬──────┬──────┐
  │  P0  │  P1  │  P2  │
  └──┬───┴──┬───┴──────┘
     │      │      └──────────────────── no owner yet
     ▼      ▼
  Consumer1  Consumer2
  (P0, P1)   (P2)    ← previous assignment


AFTER: 3rd consumer joins → rebalance triggered
────────────────────────────────────────────────────────────────────
  Consumer sends to Group Coordinator:
    "I want to join group: order-consumer-group
     I am interested in topic: order-events"

  Group Coordinator reassigns:
  ┌──────┬──────┬──────┐
  │  P0  │  P1  │  P2  │
  └──┬───┴──┬───┴──┬───┘
     ▼      ▼      ▼
   Con-1   Con-2   Con-3   ← new balanced assignment
```

## 4. The Minimal Consumer Code

Three things is all you write. Spring Boot handles the rest.

```
Step 1: pom.xml
────────────────────────────────────────────────────────────────────
  <dependency>
    <groupId>org.springframework.kafka</groupId>
    <artifactId>spring-kafka</artifactId>
  </dependency>


Step 2: application.properties  (the 5 properties from section 1)


Step 3: @KafkaListener on a method
────────────────────────────────────────────────────────────────────

  @Component
  public class OrderEventListener {

      @KafkaListener(topics = "order-events")
      public void consume(Order order) {
          // your business logic — called once per event
      }
  }

  ┌─────────────────────────────────────────────────────┐
  │  What you wrote:  application.properties            │
  │                 + @KafkaListener                    │
  │                                                     │
  │  What Spring Boot does: everything else             │
  └─────────────────────────────────────────────────────┘
```

## 5. ConsumerRecord — What Each Event Looks Like

When you need more than just the value, accept a `ConsumerRecord` in your listener method. It contains the full event envelope.

```
  ConsumerRecord<String, Order>
  ┌──────────────────────────────────────────────────────┐
  │  topic     : "order-events"                          │
  │  partition : 2                                       │
  │  offset    : 101                                     │
  │  key       : "order-332700"           ← String       │
  │  value     : Order { id:332700, ... } ← deserialized │
  │  headers   : [ type-id: "com.eda.producer.Order" ]   │
  │  timestamp : 1700000000000                           │
  └──────────────────────────────────────────────────────┘

  Method signature to receive the full record:
    public void consume(ConsumerRecord<String, Order> record)
```

## 6. Spring Boot Abstraction Layers

Spring Boot auto-creates three components so you never have to. Understanding them helps you configure advanced scenarios.

```
  Spring Boot startup
  │
  ├─► 1. ConsumerFactory bean
  │        │  reads application.properties
  │        │  knows how to create KafkaConsumer objects
  │        └─► DefaultKafkaConsumerFactory
  │
  ├─► 2. ConcurrentKafkaListenerContainerFactory bean
  │        │  wraps ConsumerFactory
  │        └─► used to create KafkaListenerContainers
  │
  └─► 3. @EnableKafka  (auto-added by Spring Boot)
           │  triggers KafkaListenerAnnotationBeanPostProcessor
           │  scans your classes for @KafkaListener
           │
           └─► For EACH @KafkaListener found:
                 ┌──────────────────────────────────────┐
                 │  KafkaListenerContainer              │
                 │  ┌────────────────────────────────┐  │
                 │  │  KafkaConsumer (1 per listener)│  │
                 │  │  ┌──────────────────────────┐  │  │
                 │  │  │  poll loop + commit logic │  │  │
                 │  │  └──────────────────────────┘  │  │
                 │  └────────────────────────────────┘  │
                 │  your @KafkaListener method          │
                 └──────────────────────────────────────┘

  Rule: 2 @KafkaListeners → 2 KafkaListenerContainers → 2 KafkaConsumers
```

## 7. The Poll Loop Internals

The KafkaListenerContainer runs an infinite loop. On the very first call, it performs group join and offset setup. Every call after that just fetches new data.

```
  while (true) {
      records = consumer.poll(...)
  }

  FIRST POLL CALL:
  ──────────────────────────────────────────────────────
  ① Send JoinGroup request → Group Coordinator
       ↓ receives: partition assignment (e.g. P2)

  ② Request last committed offset for assigned partition
       Group Coordinator checks __consumer_offsets
       ↓ returns: offset 100 (last processed)

  ③ Send fetch request to partition leader broker
       "Give me order-events P2 starting at offset 101"
       ↓ receives: records 101–150

  SUBSEQUENT POLL CALLS:
  ──────────────────────────────────────────────────────
  ③ only — just fetch next batch, no group coordination

  AFTER RECEIVING RECORDS:
  ──────────────────────────────────────────────────────
  ┌─────────────────────────────────────────────────────┐
  │  if auto-commit=true AND commit-interval passed:    │
  │      commit offset NOW  ← before processing!        │
  │      ⚠ risk: offset committed before processing,    │
  │        crash → data loss                            │
  │                                                     │
  │  for each record:                                   │
  │      invoke @KafkaListener method (business logic)  │
  │                                                     │
  │  if auto-commit=false (manual):                     │
  │      commitSync()   ← blocks until broker confirms  │
  │      commitAsync()  ← fire and forget               │
  └─────────────────────────────────────────────────────┘
```

## 8. Heartbeat and Rebalance on Crash

A background thread in the consumer sends heartbeats to the group coordinator. If heartbeats stop, the coordinator assumes the consumer is dead and triggers a rebalance.

```
  HEALTHY CONSUMER:
  ──────────────────────────────────────────────────────
  Consumer                        Group Coordinator
     │  ── heartbeat ──────────►  │  "alive"
     │  ── heartbeat ──────────►  │  "alive"
     │  ── heartbeat ──────────►  │  "alive"
     │                            │

  CONSUMER CRASHES / LEAVES:
  ──────────────────────────────────────────────────────
  Consumer                        Group Coordinator
     │  [crash / leave group]     │
     │                            │  ← heartbeat timeout
     │                            │  session.timeout exceeded
     │                            │  ↓
     │                            │  REBALANCE triggered
     │                            │  remaining consumers
     │                            │  get reassigned partitions

  Key config:
    heartbeat.interval.ms    — how often heartbeat is sent
    session.timeout.ms       — how long before declared dead
```

## 9. Auto Offset Reset — Latest vs Earliest

When a consumer starts for the first time with no previously committed offset, this setting determines where it begins reading.

```
  Topic: order-events, Partition P2
  ┌─────────────────────────────────────────────────────┐
  │  offset:  0   1   2   3   4 ... 98  99  100         │
  │           ●───●───●───●───●─...─●───●───●  ◄ latest │
  │           ▲                                         │
  │         earliest                                    │
  └─────────────────────────────────────────────────────┘

  auto-offset-reset = latest   (DEFAULT)
  ──────────────────────────────────────────────────────
  Consumer starts → no previous offset found
  → start from offset 100 (the next new message)
  → all past messages are SKIPPED

  auto-offset-reset = earliest
  ──────────────────────────────────────────────────────
  Consumer starts → no previous offset found
  → start from offset 0 (the very beginning)
  → reads ALL historical messages

  Practical impact:
    consumer already running + new event arrives   → reads it (both modes)
    consumer starts AFTER events were published    → latest misses them ✗
                                                   → earliest reads them ✓
```

## 10. Complete Consumer Startup Flow

```
  Step 1:  @KafkaListener found → KafkaListenerContainer created
  Step 2:  KafkaConsumer object created via ConsumerFactory
  Step 3:  Connect to bootstrap server → fetch cluster metadata
  Step 4:  hash(group.id) % 50 → find partition of __consumer_offsets
  Step 5:  Connect to leader of that partition → Group Coordinator found
  Step 6:  Send JoinGroup request to Group Coordinator
  Step 7:  Group Coordinator runs rebalance → assigns partitions
  Step 8:  Consumer receives partition assignment (e.g. P2)
  Step 9:  Ask Group Coordinator for last committed offset of P2
  Step 10: Send fetch request to partition P2 leader broker
  Step 11: Receive records → process → commit offset
  Step 12: Repeat step 10–11 forever ↺

  Background thread running in parallel:
  Step B:  Send heartbeat to Group Coordinator every N ms
           If heartbeat stops → Group Coordinator triggers rebalance
```

## 11. Quick Reference

```
Concept                   What it is                              Key point
────────────────────────  ──────────────────────────────────────  ─────────────────────────────────────
bootstrap-servers         Entry-point brokers                     Only used for first metadata fetch
group.id                  Consumer group name                     hash(group.id) % 50 → coordinator
key-deserializer          Undoes producer's key serialization     Must match what producer used
value-deserializer        Undoes producer's value serialization   JSON → need default-type too
default-type              Fallback class for JSON deserialization  Required when value-deserializer=JSON
ConsumerRecord            Full event envelope                     topic, partition, offset, key, value
@KafkaListener            Marks method as event handler           One listener = one KafkaConsumer
ConsumerFactory           Creates KafkaConsumer objects           Auto-created by Spring Boot
KafkaListenerContainer    Owns the poll loop                      One per @KafkaListener
Group Coordinator         Broker managing the consumer group       Hosts the relevant __consumer_offsets partition
Rebalance                 Redistribute partitions among consumers  Triggered on join/leave/crash
Heartbeat                 Proof-of-life signal to coordinator     Stops → session timeout → rebalance
auto-offset-reset=latest  Start from newest message (default)     Skips past messages
auto-offset-reset=earliest Start from oldest message             Reads all historical data
auto-commit               Commit offset automatically every N ms  ⚠ commits before processing — avoid in prod
commitSync()              Manual commit, waits for confirmation   Safe, but blocks
commitAsync()             Manual commit, fire and forget          Faster, no guarantee
```
