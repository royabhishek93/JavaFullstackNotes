The Two Config Settings That Cause Problems

When retries > 0 AND max.in.flight.requests.per.connection > 1 are both set, two serious problems can occur: duplicate messages and message reordering. These configs are related — understanding both is the foundation for understanding idempotence.

Producer configuration: retries = 3 ┌──────────────────────────────────────────────────────────────────────┐ │ If broker doesn't acknowledge a batch, the producer sends it again │ │ up to 3 times before giving up. │ └──────────────────────────────────────────────────────────────────────┘ max.in.flight.requests.per.connection = 5 ┌──────────────────────────────────────────────────────────────────────┐ │ Up to 5 batches can be "in flight" at the same time — sent but │ │ not yet acknowledged. The producer doesn't wait for ack before │ │ sending the next batch. │ └──────────────────────────────────────────────────────────────────────┘ BOTH enabled together: ┌───────────────────┐ ┌───────────────────┐ │ retries > 0 │ AND │ in-flight > 1 │ ──► PROBLEMS └───────────────────┘ └───────────────────┘

Problem 1 — Duplicate Message

When a batch reaches the broker successfully but the acknowledgement is lost on the way back, the producer retries — and the broker has no way to know it already wrote that event.

NORMAL FLOW (no problem): ───────────────────────────────────────────────────────────────────────── Producer Broker ───────── ────── │── Batch [event-1] ──────────────────────────► │ writes event-1 at offset 1 │◄─ ACK ──────────────────────────────────────── │ ✓ done — one copy in log DUPLICATE PROBLEM: ───────────────────────────────────────────────────────────────────────── Producer Broker ───────── ────── │── Batch [event-1] ──────────────────────────► │ writes event-1 at offset 1 │◄── ACK ─── ✗ LOST (network issue) ───────── │ │ │ │ (producer waits... timeout!) │ │ retries > 0, so retry... │ │ │ │── Batch [event-1] again ────────────────────► │ writes event-1 at offset 2 │◄─ ACK ──────────────────────────────────────── │ ✓ producer thinks first send was OK now │ LOG RESULT: ┌───────────────────────────────────────────────────┐ │ offset 1 → event-1 ← first write │ │ offset 2 → event-1 ← DUPLICATE │ └───────────────────────────────────────────────────┘ Broker has no way to detect it already stored event-1.

Problem 2 — Message Reordering

When max.in.flight > 1, two batches can be in-flight simultaneously. If batch-1 is lost and batch-2 arrives first, and then batch-1 is retried — events end up in the wrong order in the log.

SCENARIO: Producer sends batch-1 (event-1) and batch-2 (event-2) simultaneously Producer Broker ───────── ────── │── Batch-1 [event-1: "order-created"] ──────► │ │── Batch-2 [event-2: "payment-made"] ──────► │ BATCH-1 IS LOST (network issue) ───────────────────────────────────────────────────────────────────────── │ Batch-1 ✗ never arrived │ │── Batch-2 ────────────────────────────────────► │ writes event-2 at offset 1 │◄─ ACK for batch-2 ──────────────────────────── │ PRODUCER RETRIES BATCH-1 ───────────────────────────────────────────────────────────────────────── │ (no ack for batch-1, timeout hit...) │ │── Batch-1 retry ──────────────────────────────► │ writes event-1 at offset 2 │◄─ ACK for batch-1 ──────────────────────────── │ LOG RESULT: ┌─────────────────────────────────────────────────────────────────────┐ │ offset 1 → event-2 "payment-made" ← HAPPENED FIRST in log │ │ offset 2 → event-1 "order-created" ← HAPPENED SECOND in log │ └─────────────────────────────────────────────────────────────────────┘ WRONG ORDER: payment was recorded before the order was even created! WHY: Broker has no way to know that batch-1 was supposed to come before batch-2. It just writes whatever arrives.

The Solution — Idempotent Producer

Setting enable.idempotence=true solves both the duplicate problem and the reordering problem at once. In Kafka 3+, this is the default.

spring.kafka.producer.properties.enable.idempotence=true ┌──────────────────────────────────────────────────────────────────────┐ │ Kafka version < 3 → default FALSE, must set manually │ │ Kafka version >= 3 → default TRUE, nothing to configure │ └──────────────────────────────────────────────────────────────────────┘ What idempotence adds: ┌─────────────────────────────┐ ┌─────────────────────────────┐ │ BEFORE (no idempotence) │ │ AFTER (idempotence=true) │ ├─────────────────────────────┤ ├─────────────────────────────┤ │ Broker: no memory of │ │ Broker: tracks each │ │ what it already stored │ │ producer + each partition │ │ │ │ with sequence numbers │ │ retries → duplicates ✗ │ │ retries → safe ✓ │ │ in-flight > 1 → reorder ✗ │ │ ordering guaranteed ✓ │ └─────────────────────────────┘ └─────────────────────────────┘

How Idempotence Works — Step 1: Producer Gets a PID

When the producer application starts up, it immediately requests a unique Producer ID (PID) from the cluster. This ID is used to identify this producer instance for the lifetime of the application run.

STARTUP FLOW: ───────────────────────────────────────────────────────────────────────── Producer App Broker Controller ──────────── ────── ────────── │ │ │ │── "Give me a unique ID" ──► │ │ │ │── forward request ──► │ │ │ │ generates next │ │ │ available PID │ │ │ e.g. 1001 │ │◄─ return PID 1001 ─── │ │◄── PID = 1001 ───────────── │ │ │ │ │ ┌──────────────────────────────────────────────────────────────────┐ │ Producer now holds: PID = 1001 │ │ │ │ NOTE: This PID is NOT stored anywhere permanently. │ │ Controller just increments a counter and returns the value. │ │ If the producer restarts → it gets a NEW PID (loophole — see │ │ section 11). │ └──────────────────────────────────────────────────────────────────┘

How Idempotence Works — Step 2: Sequence Numbers in Record Accumulator

The record accumulator creates batches per topic-partition. With idempotence enabled, each batch also carries the PID, a base sequence number, and a last sequence number. Each individual event inside the batch gets its own sequence number.

Record Accumulator (with idempotence=true): ───────────────────────────────────────────────────────────────────────── ┌─────────────────────────────────────────────────────────────────────┐ │ BATCH 1 — Topic A, Partition P0 │ │ ┌────────────────────────────────────────────────────────────────┐ │ │ │ HEADER: PID=1001 │ base_seq=0 │ last_seq=2 │ │ │ ├────────────────────────────────────────────────────────────────┤ │ │ │ event-1 seq=0 │ │ │ │ event-2 seq=1 │ │ │ │ event-3 seq=2 │ │ │ └────────────────────────────────────────────────────────────────┘ │ └─────────────────────────────────────────────────────────────────────┘ ┌─────────────────────────────────────────────────────────────────────┐ │ BATCH 2 — Topic A, Partition P1 (own separate sequence) │ │ ┌────────────────────────────────────────────────────────────────┐ │ │ │ HEADER: PID=1001 │ base_seq=0 │ last_seq=1 │ │ │ ├────────────────────────────────────────────────────────────────┤ │ │ │ event-8 seq=0 │ │ │ │ event-9 seq=1 │ │ │ └────────────────────────────────────────────────────────────────┘ │ └─────────────────────────────────────────────────────────────────────┘ ┌─────────────────────────────────────────────────────────────────────┐ │ BATCH 3 — Topic B, Partition P0 (own separate sequence) │ │ ┌────────────────────────────────────────────────────────────────┐ │ │ │ HEADER: PID=1001 │ base_seq=0 │ last_seq=3 │ │ │ ├────────────────────────────────────────────────────────────────┤ │ │ │ event-1 seq=0 │ │ │ │ event-2 seq=1 │ │ │ │ event-3 seq=2 │ │ │ │ event-4 seq=3 │ │ │ └────────────────────────────────────────────────────────────────┘ │ └─────────────────────────────────────────────────────────────────────┘ KEY RULE: Sequences are maintained PER TOPIC PER PARTITION. Topic A P0 and Topic A P1 each have their own independent counter.

How Idempotence Works — Step 3: Broker Validates With an In-Memory Map

When a batch arrives, the broker checks its in-memory map to see whether the base sequence is exactly what it expected next. If yes, accept and update the map. If no, reject and force a retry.

BROKER IN-MEMORY MAP (keyed by PID + Topic + Partition): ┌──────────────┬─────────┬───────────┬───────────────────┐ │ Producer ID │ Topic │ Partition │ last_seq written │ ├──────────────┼─────────┼───────────┼───────────────────┤ │ 1001 │ A │ P0 │ 2 │ │ 1001 │ A │ P1 │ 1 │ │ 1001 │ B │ P0 │ 3 │ └──────────────┴─────────┴───────────┴───────────────────┘ VALIDATION LOGIC ON EACH INCOMING BATCH: ───────────────────────────────────────────────────────────────────────── Batch arrives: PID=1001, Topic A, P0, base_seq=0 1. Look up map: PID=1001, Topic A, P0 2. No entry found → this is the FIRST request 3. Expect base_seq = 0 ✓ matches 4. Accept batch, write events to log 5. Insert into map: last_seq = 2 Next batch arrives: PID=1001, Topic A, P0, base_seq=3 1. Look up map: PID=1001, Topic A, P0 → last_seq = 2 2. Expected next base_seq = 2 + 1 = 3 3. Incoming base_seq = 3 ✓ matches 4. Accept batch, write to log 5. Update map: last_seq = 5 RETRY arrives (duplicate): PID=1001, Topic A, P0, base_seq=3 AGAIN 1. Look up map: PID=1001, Topic A, P0 → last_seq = 5 2. Expected next base_seq = 5 + 1 = 6 3. Incoming base_seq = 3 ✗ does NOT match (too old) 4. REJECT — duplicate detected ✓ problem solved OUT-OF-ORDER batch arrives: PID=1001, Topic A, P0, base_seq=6 (but seq=3 batch hasn't arrived yet) 1. Look up map: last_seq = 2 2. Expected next = 3 3. Incoming base_seq = 6 ✗ does NOT match (gap detected) 4. REJECT — producer must retry in order ✓ reordering prevented

How Sequence Numbers Fix the Reordering Problem

With idempotence, the same scenario from section 3 now plays out differently — the out-of-order batch is rejected, forcing the producer to send things in the correct sequence.

SAME SCENARIO as section 3, but now with idempotence=true: Producer (PID=1001) Broker ─────────────────── ────── │── Batch-1 [event-1, seq=0, base=0, last=0] ─► │ │── Batch-2 [event-2, seq=0, base=0, last=0] ─► │ │ (Topic A P0) (Topic A P1) │ BATCH-1 IS LOST (same network issue as before) ───────────────────────────────────────────────────────────────────────── │ Batch-1 ✗ never arrived │ │── Batch-2 (Topic A P1) ───────────────────────► │ │ │ checks map for PID=1001 │ │ Topic A P1 → no entry │ │ expects base_seq=0 ✓ │◄─ ACK for batch-2 ───────────────────────────── │ map: Topic A P1 last=0 PRODUCER RETRIES BATCH-1 ───────────────────────────────────────────────────────────────────────── │ (no ack for batch-1, timeout hit...) │ │── Batch-1 retry (Topic A P0, base=0) ──────────► │ │ │ checks map for PID=1001 │ │ Topic A P0 → no entry │ │ expects base_seq=0 ✓ │◄─ ACK for batch-1 ───────────────────────────── │ map: Topic A P0 last=0 LOG RESULT: ┌─────────────────────────────────────────────────────────────────────┐ │ Topic A Partition P0: offset 1 → event-1 "order-created" ✓ │ │ Topic A Partition P1: offset 1 → event-2 "payment-made" ✓ │ └─────────────────────────────────────────────────────────────────────┘ NOTE: The broker enforces seq=0 must come before seq=1. If batch-2 (seq=1) arrived before batch-1 (seq=0) on the SAME partition, the broker would reject batch-2 until batch-1 arrives first.

Idempotence Constraints — Three Required Settings

When enable.idempotence=true, Kafka enforces three related settings. These are automatically applied in Kafka 3+ but worth knowing for interviews.

┌─────────────────────────────────────────────────────────────────────┐ │ Constraint 1: acks = all │ ├─────────────────────────────────────────────────────────────────────┤ │ │ │ acks=1 (leader only) acks=all (leader + all ISR) │ │ ┌──────────────────────┐ ┌──────────────────────────────────┐ │ │ │ Leader ✓ │ │ Leader ✓ │ │ │ │ Follower-1 ✗ crash │ │ Follower-1 ✓ │ │ │ │ Follower-2 ✗ crash │ │ Follower-2 ✓ │ │ │ │ │ │ │ │ │ │ If leader crashes → │ │ Either all replicas have it │ │ │ │ event is lost │ │ or none do. Safe. │ │ │ └──────────────────────┘ └──────────────────────────────────┘ │ │ With acks=1 + idempotence, a crash can still cause duplicates. │ └─────────────────────────────────────────────────────────────────────┘ ┌─────────────────────────────────────────────────────────────────────┐ │ Constraint 2: retries = MAX_INT (Integer.MAX_VALUE) │ ├─────────────────────────────────────────────────────────────────────┤ │ │ │ Without idempotence: retries are risky → can cause duplicates │ │ With idempotence: retries are SAFE → broker deduplicates │ │ │ │ So retries is set to MAX_INT — retry as many times as needed. │ │ The sender thread retries indefinitely without risk. │ └─────────────────────────────────────────────────────────────────────┘ ┌─────────────────────────────────────────────────────────────────────┐ │ Constraint 3: max.in.flight.requests.per.connection <= 5 │ ├─────────────────────────────────────────────────────────────────────┤ │ │ │ The broker maintains an ordering buffer for 5 sequences only. │ │ │ │ ┌───────────────────────────────────────────────────────────────┐ │ │ │ Per topic-partition, broker holds a window of 5 in-flight │ │ │ │ sequences in its validation buffer: │ │ │ │ │ │ │ │ [ seq-0 | seq-1 | seq-2 | seq-3 | seq-4 ] ← buffer of 5 │ │ │ │ │ │ │ │ If in-flight > 5, the 6th batch falls outside the buffer │ │ │ │ → ordering guarantee is LOST │ │ │ │ → Kafka throws an exception when idempotence=true and │ │ │ │ max.in.flight > 5 │ │ │ └───────────────────────────────────────────────────────────────┘ │ │ │ │ Kafka docs: buffer of 5 was chosen after testing many iterations. │ │ More than 5 = too much complexity + memory per partition. │ └─────────────────────────────────────────────────────────────────────┘

Exactly-Once Semantics at Producer Level

Combining these guarantees, idempotence achieves exactly-once delivery per producer session — each event lands in the broker log exactly one time, no matter how many retries occur.

THREE DELIVERY SEMANTICS: At-most-once At-least-once Exactly-once ───────────── ───────────────── ──────────────────────────── retries = 0 retries > 0 retries > 0 acks = 0 acks = 1 or all acks = all enable.idempotence = true max.in.flight <= 5 ┌────────────┐ ┌──────────────┐ ┌──────────────────────────┐ │ May lose │ │ May write │ │ Writes event exactly │ │ messages │ │ duplicates │ │ once — no loss, no dup │ └────────────┘ └──────────────┘ └──────────────────────────┘ SCOPE: Exactly-once here is PRODUCER-LEVEL only. ┌──────────────────────────────────────────────────────────────────────┐ │ Covers: producer → broker (same session, same PID) │ │ Does NOT cover: producer restart → gets new PID → can re-write │ │ Does NOT cover: consumer re-processing after failure │ │ │ │ For full end-to-end exactly-once → use Kafka Transactions │ └──────────────────────────────────────────────────────────────────────┘

The Loophole — Producer Restart Gets a New PID

Idempotence only works within a single producer session. If the producer restarts, the controller issues a brand-new PID and the broker can no longer detect cross-session duplicates.

PRODUCER RESTART SCENARIO: ───────────────────────────────────────────────────────────────────────── Session 1: PID = 1001 ────────────────────────────────────────────────────────────────────── Producer sends: Topic A, P0, PID=1001, base_seq=3, last_seq=5 Broker writes: event-1, event-2, event-3 at offsets ... Broker map: PID=1001 | Topic A | P0 | last_seq=5 Producer CRASHES before receiving ACK Session 2: PID = 2001 (NEW PID after restart) ────────────────────────────────────────────────────────────────────── Producer retries the same batch: Topic A, P0, PID=2001, base_seq=3, last_seq=5 Broker lookup: PID=2001 | Topic A | P0 → NO ENTRY (new PID) Broker expects: base_seq = 0 (first request for this PID) ┌─────────────────────────────────────────────────────────────────────┐ │ RESULT: Broker accepts the batch again → DUPLICATE written ✗ │ │ │ │ WHY: The PID changed. The broker's map is keyed by PID. │ │ The old map entry for PID=1001 is useless. │ │ The broker has no way to link PID=2001 to PID=1001. │ └─────────────────────────────────────────────────────────────────────┘ WHY DOESN'T CONTROLLER REMEMBER OLD PIDs? ────────────────────────────────────────── Idempotence design: controller only increments a counter. It does NOT maintain a "this producer ↔ this PID" registry. PID is meant to be ephemeral — valid for one session only. THE FIX → KAFKA TRANSACTIONS ────────────────────────────────────────────────────────────────────── With transactions, the producer has a stable transactional.id that persists across restarts. The controller maps transactional.id → PID and issues the SAME logical identity even after restart. ┌──────────────────────────────────────────────────────────────────┐ │ transactional.id = "payment-service-producer-1" │ │ │ │ Restart 1: transactional.id → PID=1001 (epoch=0) │ │ Restart 2: transactional.id → PID=1001 (epoch=1) ← same PID, │ │ new epoch │ │ │ │ Old epoch batches are FENCED — broker rejects them. │ └──────────────────────────────────────────────────────────────────┘ Covered separately after consumer and consumer group setup.

Batching — batch.size and linger.ms

Before sending, the producer accumulates events into batches inside the record accumulator. These two settings control when a batch is flushed.

Record Accumulator (in-memory buffer): ┌─────────────────────────────────────────────────────────────────────┐ │ Topic A, Partition P0: [ event-1 | event-2 | event-3 | ... ]│ │ Topic A, Partition P1: [ event-8 | event-9 ] │ │ Topic B, Partition P0: [ event-X ] │ └─────────────────────────────────────────────────────────────────────┘ batch.size (default: 16 KB) ───────────────────────────────────────────────────────────────────── Maximum size of a single batch. When the batch reaches this size, it is sent immediately — no waiting. ┌──────────────────────────────────────────────────────────────────┐ │ batch filling up: │ │ [ev1][ev2][ev3]...[evN] ──► FULL (16 KB hit) ──► SEND NOW │ └──────────────────────────────────────────────────────────────────┘ linger.ms (default: 0 ms) ───────────────────────────────────────────────────────────────────── How long to wait before sending an INCOMPLETE batch. A value of 0 means send immediately. A higher value batches more events together. linger.ms = 0ms linger.ms = 5ms ┌──────────────────────┐ ┌──────────────────────────────┐ │ [ev1] → SEND │ │ [ev1] → wait... │ │ [ev2] → SEND │ │ [ev1, ev2] → wait... │ │ [ev3] → SEND │ │ [ev1, ev2, ev3] → 5ms up │ │ 3 batches, 3 trips │ │ → SEND 1 batch, 1 trip ✓ │ └──────────────────────┘ └──────────────────────────────┘ Low latency, low throughput Higher latency, higher throughput TUNING TRADE-OFF: ┌──────────────────────────────────────────────────────────────────────┐ │ High-throughput pipeline: linger.ms=5–20, batch.size=32–64KB │ │ Low-latency pipeline: linger.ms=0, batch.size=16KB │ └──────────────────────────────────────────────────────────────────────┘

Buffer Memory and Compression — buffer.memory and compression.type

Once batches are ready, they wait in the send buffer before being dispatched. If the buffer fills up, the producer blocks. Compression reduces the byte size of each batch before it leaves the buffer.

buffer.memory (default: 32 MB) ───────────────────────────────────────────────────────────────────── Total memory allocated to the producer's record accumulator. If full, the producer BLOCKS until space frees up (or times out). ┌──────────────────────────────────────────────────────────────────────┐ │ buffer.memory = 32 MB │ │ ┌─────────────────────────────────────────────────┐ │ │ │ batch(A,P0) │ batch(A,P1) │ batch(B,P0) │ ... │ │ │ └─────────────────────────────────────────────────┘ │ │ │ │ If broker is slow and batches pile up: │ │ Buffer full → producer.send() BLOCKS → back-pressure │ └──────────────────────────────────────────────────────────────────────┘ compression.type (options: none | gzip | snappy | lz4 | zstd) ───────────────────────────────────────────────────────────────────── Applied to the batch as a whole before sending. More events in a batch = better compression ratio (repetitive data compresses well). ┌──────────────────────────────────────────────────────────────────────┐ │ │ │ Record Accumulator │ │ ┌──────────────────────────────────────────────┐ │ │ │ batch: [event-1, event-2, event-3 ... ] │ 100 KB raw │ │ └────────────────────┬─────────────────────────┘ │ │ │ compression.type = snappy │ │ ▼ │ │ ┌──────────────────────────────────────────────┐ │ │ │ compressed batch: ████████████████░░░░░░░░ │ ~40 KB │ │ └────────────────────┬─────────────────────────┘ │ │ │ │ │ ▼ sent to broker │ │ 60% less network bytes ✓ │ └──────────────────────────────────────────────────────────────────────┘ COMPRESSION COMPARISON: ┌──────────────┬────────────────┬─────────────────────────────────────┐ │ Algorithm │ Ratio │ Best use case │ ├──────────────┼────────────────┼─────────────────────────────────────┤ │ none │ no reduction │ testing / already-compressed data │ │ snappy │ moderate │ balanced speed + size │ │ lz4 │ moderate │ best speed, decent size │ │ gzip │ high │ smallest size, more CPU │ │ zstd │ highest │ best ratio with low CPU (Kafka 2+) │ └──────────────┴────────────────┴─────────────────────────────────────┘
