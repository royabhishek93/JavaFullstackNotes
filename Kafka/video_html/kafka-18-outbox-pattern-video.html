The Dual-Write Problem

When a service must write to both a database and Kafka in a single request, the two systems are independent — either can succeed while the other fails, leaving data inconsistent.

HAPPY PATH (both succeed — no problem): createOrder() ├──► DB.save(order) ✓ order stored └──► kafka.publish(event) ✓ downstream notified FAILURE CASE 1 — DB succeeds, Kafka fails: createOrder() ├──► DB.save(order) ✓ order stored └──► kafka.publish(event) ✗ FAILED payment-service, inventory-service → NEVER notified order exists in DB but no downstream update ✗ FAILURE CASE 2 — Kafka succeeds, DB fails: createOrder() ├──► DB.save(order) ✗ FAILED (rolled back) └──► kafka.publish(event) ✓ event published! payment-service, inventory-service → update themselves but order does NOT exist in DB ✗ (more dangerous — ghost event)

This is called the dual-write problem: writing to two independent systems in one request has no atomicity guarantee.

Why @Transactional Alone Does Not Fix It

Wrapping both writes in @Transactional seems to solve it — if Kafka fails, the DB rolls back. But there is a hidden gap: the network acknowledgement.

@Transactional createOrder() { orderRepo.save(order); ← step 1: DB write succeeds try { kafka.send(event); ← step 2: message travels to broker │ ┌──────────┴───────────────────────┐ │ broker received message ✓ │ │ but ACK packet lost on network │ │ producer never gets the ACK ✗ │ └──────────────────────────────────┘ // producer thinks: "send FAILED" → throws exception } catch (e) { // @Transactional sees the exception → rolls back DB } } RESULT: ┌──────────────────────────────────────┐ │ DB: order ROLLED BACK ✗ │ │ Kafka: event PUBLISHED ✓ │ └──────────────────────────────────────┘ → Kafka event exists but DB order does not ← still inconsistent!

Two-Phase Commit (2PC) also fails: Kafka simply does not support the 2PC protocol — it cannot act as a participant in a distributed transaction. There is no "prepare" phase in Kafka.

The Outbox Pattern — The Correct Solution

Instead of writing to Kafka directly, write the event details into a dedicated outbox table in the same database transaction. A separate relay process then reads that table and publishes to Kafka.

BEFORE (dual-write — dangerous): createOrder() ├──► orders table (DB) ─┐ two INDEPENDENT systems └──► Kafka broker ─┘ no atomicity between them AFTER (outbox pattern — safe): createOrder() ┌─ ONE DB TRANSACTION ─┐ ├──► orders table (DB) │ both writes in │ └──► outbox_events table (DB) ────┘ the same DB │ └──────────────────────┘ │ │ (later, separately) ▼ ┌──────────────────────────────────────────────────┐ │ Relay Process (scheduler or CDC) │ │ reads outbox_events ──────────────► Kafka │ └──────────────────────────────────────────────────┘

Both writes go to the same database, so they participate in a single ACID transaction — either both commit or both roll back. Kafka is never touched during the user request.

Outbox Table Structure

The outbox table stores everything the relay needs to construct and publish a Kafka message.

┌────────────────────────────────────────────────────────────────────────┐ │ outbox_events table │ ├─────────────────┬──────────────────────────────────────────────────────┤ │ Column │ Purpose │ ├─────────────────┼──────────────────────────────────────────────────────┤ │ id │ Unique event UUID — used for deduplication │ │ aggregate_type │ Entity type → determines the Kafka topic │ │ │ e.g. "ORDER" → topic: order-events │ │ aggregate_id │ Entity ID → used as the Kafka message KEY │ │ │ same aggregate_id → same partition → ordering ✓ │ │ event_type │ What happened: ORDER_CREATED, ORDER_CANCELLED │ │ payload │ Full JSON body to publish as the Kafka message value │ │ created_at │ Timestamp — used for ORDER BY in polling queries │ │ published │ false = not yet sent │ true = sent ← polling only │ │ published_at │ When it was sent ← polling only │ └─────────────────┴──────────────────────────────────────────────────────┘ Example row: id = "uuid-abc-123" aggregate_type = "ORDER" → Kafka topic: order-events aggregate_id = "customer-K1" → Kafka key: customer-K1 event_type = "ORDER_CREATED" payload = { "orderId": 42, "amount": 500 } published = false Why aggregate_id as key? customer-K1: ORDER_CREATED ──► partition-3 ─┐ customer-K1: ORDER_CANCELLED ──► partition-3 ─┘ same partition → ordering guaranteed: created always before cancelled ✓

Polling Relay (Scheduler) Flow

A scheduled job runs every N seconds, reads unpublished rows from the outbox table ordered by created_at, publishes them to Kafka, and marks each row as published.

Every 2 seconds: ┌──────────────────────────────────────────────────────────────────┐ │ @Scheduled(fixedDelay = 2000) │ │ │ │ SELECT * FROM outbox_events │ │ WHERE published = false │ │ ORDER BY created_at ← preserve insertion order│ │ LIMIT 10; ← process in small batch │ │ │ │ for each event: │ │ kafka.send(topic, aggregateId, payload) ──► Kafka ✓ │ │ event.published = true │ │ event.published_at = now() │ │ outboxRepo.save(event) ← mark as done in DB │ │ if any error → BREAK immediately ← preserve order! │ └──────────────────────────────────────────────────────────────────┘ Timeline example (2-second poll interval): ───────────────────────────────────────────────────────────────────── 10:00:00.000 event inserted (published=false) 10:00:01.000 event inserted (published=false) 10:00:02.000 scheduler fires → reads 2 rows → publishes → marks done 10:00:04.000 scheduler fires → 0 unpublished rows → nothing to do

Why BREAK on first error? If events 1, 2, 3 share the same Kafka key (same customer), skipping a failed event 1 and publishing 2 then 3 would break ordering. Always stop at the first failure so no gaps appear in the sequence.

At-Least-Once Delivery and Idempotency

The relay guarantees that every event is published at least once — but it can publish the same event more than once if the published=true update fails after a successful Kafka send.

DUPLICATE SCENARIO: ───────────────────────────────────────────────────────────────── Run 1: Read row (published = false) kafka.send(event) ✓ published to Kafka outboxRepo.save(published = true) ✗ DB update FAILS (crash/timeout) Run 2 (next scheduler tick, 2 seconds later): Read SAME row (still published = false — DB was never updated) kafka.send(event) ✓ published to Kafka AGAIN Consumer receives event TWICE: ┌──────────────────────────────────────────────┐ │ msg-1: { orderId: 42, type: ORDER_CREATED }│ ← first delivery │ msg-2: { orderId: 42, type: ORDER_CREATED }│ ← duplicate! └──────────────────────────────────────────────┘ CONSUMER MUST BE IDEMPOTENT: ┌──────────────────────────────────────────────────────────────┐ │ onMessage(event) { │ │ if (alreadyProcessed(event.id)) { │ │ return; ← skip duplicate using the unique event id │ │ } │ │ process(event); │ │ markProcessed(event.id); │ │ } │ └──────────────────────────────────────────────────────────────┘ Use event.id (UUID) as the deduplication key.

Polling Disadvantages

Polling works but comes with several operational challenges that grow as the system scales.

┌──────────────────────────────┬──────────────────────────────────────────┐ │ Problem │ What goes wrong │ ├──────────────────────────────┼──────────────────────────────────────────┤ │ Constant DB load │ Scheduler hits the DB every 2 seconds │ │ │ even when there are zero new events │ ├──────────────────────────────┼──────────────────────────────────────────┤ │ Polling gap / latency │ Event created at 10:00:00 but published │ │ │ at 10:00:02 — always N-second delay │ ├──────────────────────────────┼──────────────────────────────────────────┤ │ Multi-instance conflict │ 3 app instances → 3 schedulers running │ │ │ all read and publish the same rows │ │ │ Need distributed locking (e.g. ShedLock) │ ├──────────────────────────────┼──────────────────────────────────────────┤ │ Duplicate publishing │ Publish succeeds, mark-as-done fails │ │ │ → same event published twice │ │ │ → consumers must be idempotent │ ├──────────────────────────────┼──────────────────────────────────────────┤ │ Table cleanup │ outbox_events grows indefinitely │ │ │ Need a separate archive / delete job │ └──────────────────────────────┴──────────────────────────────────────────┘ Multi-instance conflict diagram: outbox_events table ┌──────┬─────────────┬───────────┐ │ id │ payload │ published │ ├──────┼─────────────┼───────────┤ │ 1 │ order-100 │ false │◄─── Scheduler-1 reads row 1 │ 2 │ order-101 │ false │◄─── Scheduler-2 reads row 1 (same!) │ 3 │ order-102 │ false │◄─── Scheduler-3 reads row 1 (same!) └──────┴─────────────┴───────────┘ → All three publish the same event ✗ (triple duplicate)

These problems are why CDC (Change Data Capture) — covered in the next topic — is the preferred approach in production systems.
