The Big Picture — One Line of Code, Five Internal Stages

Calling kafkaTemplate.send(topic, key, value) looks simple, but your message passes through five stages inside the producer before any network call to the broker happens.

Your application code: kafkaTemplate.send("order-events", orderId, orderObject) │ ▼ ┌─────────────────────────────────────────────────────────────────┐ │ KAFKA PRODUCER (internal) │ │ │ │ ┌───────────┐ ┌───────────┐ ┌────────────────────┐ │ │ │ Stage 1 │ │ Stage 2 │ │ Stage 3 │ │ │ │Serializer │─►│Partitioner│─►│ Record Accumulator │ │ │ └───────────┘ └───────────┘ └────────────────────┘ │ │ │ │ │ ┌─────────┴─────────┐ │ │ ▼ ▼ │ │ ┌──────────┐ ┌─────────────┐ │ │ │ Stage 4 │ │ Stage 5 │ │ │ │Compression │Sender Thread│ │ │ └──────────┘ └─────────────┘ │ └─────────────────────────────────────────────────────────────────┘ │ ▼ Kafka Broker

If serialization fails at Stage 1, the message never moves to Stage 2. Each stage is a gate.

Stage 1 — Serializer: Java Object → Bytes

Kafka stores only bytes on disk. It has no idea whether your value is a String, Integer, or a custom POJO. The serializer converts both key and value into byte arrays before anything else happens.

Your code sends: key = "ORDER-001" (Java String) value = Order{ id, amount } (Java POJO) │ ▼ ┌───────────────────────────────────────────────┐ │ SERIALIZER STAGE │ │ │ │ key ─── StringSerializer ──► [98 79 68 …] │ │ value ── JsonSerializer ──► [7B 22 69 …] │ │ │ │ If serialization fails → message is DROPPED │ │ It does NOT move to Stage 2. │ └───────────────────────────────────────────────┘ Built-in serializers (no code needed): StringSerializer ← for String keys/values IntegerSerializer ← for Integer keys/values LongSerializer ← for Long JsonSerializer ← for any POJO / JSON object Custom serializer (write your own): implement Serializer<T> override: serialize(String topic, T data) → byte[] Use cases for custom serializer: ✓ Remove sensitive fields before sending ✓ Encrypt data before converting to bytes ✓ Apply a proprietary binary format

Stage 2 — Partitioner: Which Partition Does This Message Go To?

After serialization, the partitioner decides which partition of the topic this message belongs to. It takes the topic, key bytes, value bytes, and cluster metadata as input — and returns a single partition number.

Input to partitioner: topic = "order-events" keyBytes = [98 79 68 …] valueBytes = [7B 22 69 …] cluster = metadata (knows how many partitions exist) │ ▼ ┌──────────────────────────────────────────────────────────┐ │ PARTITIONER STAGE │ │ │ │ Case 1: Partition explicitly provided in .send() call │ │ kafkaTemplate.send(topic, partition, key, value) │ │ → use that partition directly, no formula needed │ │ │ │ Case 2: Key is provided │ │ partition = hash(keyBytes) % numberOfPartitions │ │ → same key ALWAYS → same partition ✓ │ │ │ │ Case 3: No key, no explicit partition │ │ → round robin (Kafka < 2.4) │ │ → sticky partitioning (Kafka >= 2.4) ← explained next│ └──────────────────────────────────────────────────────────┘ │ ▼ partition number (e.g. P-1)

No-Key Partitioning: Round Robin vs Sticky (Kafka 2.4+)

When no key is provided, the pre-2.4 round-robin approach creates many small batches, wasting network calls. Kafka 2.4 replaced it with sticky partitioning for better throughput.

SETUP: topic "order-events", 3 partitions (P0, P1, P2), no key on any event ── PRE-KAFKA 2.4: ROUND ROBIN ────────────────────────────────────────── E1 → P0 E2 → P1 E3 → P2 E4 → P0 E5 → P1 Record Accumulator batches: ┌─────────────────────────────────────────────────────┐ │ Batch A: order-events/P0 [ E1, E4 ] (size=2) │ │ Batch B: order-events/P1 [ E2, E5 ] (size=2) │ │ Batch C: order-events/P2 [ E3 ] (size=1) │ └─────────────────────────────────────────────────────┘ Problem: 3 small batches → 3 network calls ✗ ── KAFKA 2.4+: STICKY PARTITIONING ───────────────────────────────────── Step 1: First event arrives. No key. Randomly pick one partition. Let's say P1 is chosen. Store in memory: "order-events → P1" Step 2: E1 arrives → check sticky memory → P1 ✓ E2 arrives → check sticky memory → P1 ✓ E3 arrives → check sticky memory → P1 ✓ E4 arrives → check sticky memory → P1 ✓ E5 arrives → check sticky memory → P1 ✓ Record Accumulator batch: ┌─────────────────────────────────────────────────────┐ │ Batch A: order-events/P1 [ E1,E2,E3,E4,E5 ] │ └─────────────────────────────────────────────────────┘ Result: 1 full batch → 1 network call ✓ When does sticky memory change? → When the current batch is CLOSED (full or linger.ms expired) → The next batch randomly picks a new partition (could be same or different)

Stage 3 — Record Accumulator: In-Memory Batch Buffer

The Record Accumulator is an in-memory buffer inside the producer. It holds events in separate batches per topic-partition. Your application thread puts events here and immediately returns — it does NOT wait for the network call.

Topic: order-events has 3 partitions. Two brokers. Broker-1 is leader for P0 and P2. Broker-2 is leader for P1. ┌──────────────────────────────────────────────────────────────┐ │ RECORD ACCUMULATOR │ │ (in-memory buffer, inside producer) │ │ │ │ order-events / P0 ┌──────────────────────────────────────┐ │ │ │ E1 │ E4 │ E7 │ E10 │ ... │ │ │ └──────────────────────────────────────┘ │ │ │ │ order-events / P1 ┌──────────────────────────────────────┐ │ │ │ E2 │ E5 │ E8 │ │ │ │ └──────────────────────────────────────┘ │ │ │ │ order-events / P2 ┌──────────────────────────────────────┐ │ │ │ E3 │ E6 │ E9 │ │ │ │ └──────────────────────────────────────┘ │ └──────────────────────────────────────────────────────────────┘ Why batches are grouped by topic-partition: P0 → Broker-1 P1 → Broker-2 P2 → Broker-1 You can't mix P0 and P1 events in one batch — they go to different brokers. Batching by topic-partition lets the Sender Thread make one request per broker. Application thread lifecycle: kafkaTemplate.send(...) → put into accumulator → return Future → FREE Application thread is DONE. It does not block waiting for broker ack.

Controlling the Batch: batch.size and linger.ms

Two configuration properties control when a batch is considered "ready to send."

┌────────────────────────────────────────────────────────────────────┐ │ TWO TRIGGERS THAT CLOSE A BATCH │ │ │ │ Trigger 1: batch.size (default = 16 KB) │ │ ───────────────────────────────────────────────────────────── │ │ Maximum memory allocated per batch. │ │ Once the batch reaches 16 KB → CLOSED → ready to send. │ │ │ │ Example: each event = 1 KB → batch holds ~16 events │ │ [ E1 ][ E2 ][ E3 ]…[ E16 ] → FULL → send it │ │ │ │ │ │ Trigger 2: linger.ms (default = 0 ms) │ │ ───────────────────────────────────────────────────────────── │ │ Maximum time to wait for more events to fill the batch. │ │ Even if batch is not full, after linger.ms → CLOSED → send. │ │ │ │ Example: linger.ms = 10 │ │ Low traffic: only 5 events arrived in 10 ms │ │ [ E1 ][ E2 ][ E3 ][ E4 ][ E5 ] ←timer expires→ send anyway │ └────────────────────────────────────────────────────────────────────┘ Whichever trigger fires first closes the batch: Timeline: ─────────────────────────────────────────────────────────────────► t=0ms batch opens, E1 added t=2ms E2 added t=5ms E3 added t=10ms linger.ms expires → batch closed, sent (only 3 events) OR t=3ms batch fills to 16 KB → batch closed, sent immediately

Stage 4 — Compression: Shrink the Batch Before Sending

Batches that are ready to send are compressed before going over the network. Compression reduces both network bandwidth and disk space on the broker (which stores compressed batches as-is).

Batch BEFORE compression: ┌──────────────────────────────────────┐ │ order-events/P0 [ E1..E16 ] 64 KB │ └──────────────────────────────────────┘ │ ▼ compression algorithm (e.g. Snappy) │ ▼ ┌──────────────────────────────────────┐ │ order-events/P0 [ E1..E16 ] 18 KB │ ← ~70% smaller └──────────────────────────────────────┘ Advantages: ✓ Reduced network bandwidth (producer → broker) ✓ Broker stores compressed batches → less disk space ✓ Higher throughput for the same hardware Available algorithms: none ← default, no compression gzip ← best compression ratio, higher CPU snappy ← balanced: good ratio, low CPU (recommended) lz4 ← fastest, slightly worse ratio zstd ← modern, excellent ratio Config: spring.kafka.producer.properties.compression.type=snappy

Stage 5 — Sender Thread: Who Actually Sends to the Broker

Your application thread never makes the network call to the broker. Once it puts events into the Record Accumulator, it is free. A separate Sender Thread (managed by Kafka internally) polls the accumulator for ready batches and sends them.

┌─────────────────────────────────────────────────────────────────┐ │ APPLICATION THREAD │ │ │ │ kafkaTemplate.send(...) │ │ │ │ │ ├── serialize key & value │ │ ├── decide partition │ │ ├── append to RecordAccumulator batch ◄── LAST STEP │ │ └── return CompletableFuture ←── THREAD IS FREE NOW │ └─────────────────────────────────────────────────────────────────┘ │ (accumulator has ready batches) │ ┌─────────────────────────────────▼───────────────────────────────┐ │ SENDER THREAD (Kafka-managed, runs continuously) │ │ │ │ 1. Poll RecordAccumulator for ready (closed) batches │ │ 2. Identify leader broker for each batch's partition │ │ 3. Group batches that go to the SAME broker │ │ 4. Send ONE request per broker (not one per batch) │ │ 5. On success → invoke callback (complete the Future) │ │ 6. On transient failure → retry (up to retries config) │ └─────────────────────────────────────────────────────────────────┘ │ ▼ Kafka Brokers

Sender Thread: Grouping Batches by Broker Leader

Instead of sending one network request per batch, the Sender Thread groups all batches destined for the same broker leader into a single request — dramatically reducing network overhead.

SETUP: 3 partitions, 2 brokers Broker-1 is leader for P0 and P2 Broker-2 is leader for P1 Ready batches in RecordAccumulator: Batch-A: order-events / P0 → leader = Broker-1 Batch-B: order-events / P1 → leader = Broker-2 Batch-C: order-events / P2 → leader = Broker-1 Sender Thread groups by leader: ┌─────────────────────────────────────────────────────────────┐ │ For Broker-1: Batch-A + Batch-C → ONE request │ │ For Broker-2: Batch-B → ONE request │ └─────────────────────────────────────────────────────────────┘ │ │ ▼ ▼ Broker-1 Broker-2 Without grouping: 3 requests (one per batch) With grouping: 2 requests (one per broker) One request to Broker-1 can carry: → multiple batches → each batch carries multiple events So ONE network call delivers hundreds of events.

Max In-Flight Requests: Parallel Pipelines Per Connection

The Sender Thread opens a TCP connection to each broker. On each connection it can send multiple requests without waiting for the previous one to be acknowledged — these are "in-flight" requests.

max.in.flight.requests.per.connection = 5 (default) Sender Thread ──── TCP connection ────► Broker-1 │ Request-1 sent ──────────────────────►│ (in flight) Request-2 sent ──────────────────────►│ (in flight) Request-3 sent ──────────────────────►│ (in flight) Request-4 sent ──────────────────────►│ (in flight) Request-5 sent ──────────────────────►│ (in flight) Request-6: BLOCKED — wait for ack before sending Broker-1 processes them and sends acks back: ◄──────── ack for Request-2 (done) ◄──────── ack for Request-1 (done) ◄──────── ack for Request-4 (done) ... With 3 brokers, max simultaneous in-flight requests: 5 per connection × 3 brokers = 15 requests cluster-wide Why this matters: Each request = multiple batches = many events 15 parallel requests = very high throughput

The Reordering Risk: max.in.flight > 1 + retries > 0

When in-flight requests can fail and retry, they may arrive at the broker out of order. This is an important reliability concern.

CONFIG: max.in.flight.requests.per.connection = 5, retries = 3 SCENARIO: ───────────────────────────────────────────────────────────────── Sender Thread sends two requests to Broker-1 (both in flight): Request-A [E1, E2, E3] ──────────────────────────► Broker-1 Request-B [E4, E5, E6] ──────────────────────────► Broker-1 Broker-1 processes Request-B successfully: Kafka log: E4 (offset 0), E5 (offset 1), E6 (offset 2) ✓ Request-A hits a transient error (network glitch): Broker-1 returns error to Sender Thread ✗ Sender Thread retries Request-A: Kafka log: E4 (offset 0), E5 (offset 1), E6 (offset 2), E1 (offset 3), E2 (offset 4), E3 (offset 5) ✗ WRONG ORDER Expected order: E1 E2 E3 E4 E5 E6 Actual order: E4 E5 E6 E1 E2 E3 ← reordering! ───────────────────────────────────────────────────────────────── SOLUTION: enable.idempotence = true With idempotency ON: Each request gets a sequence number. Broker detects out-of-order delivery and holds Request-B until Request-A is successfully retried. Order is preserved. ✓ ───────────────────────────────────────────────────────────────── NOTE: Idempotency is covered as a separate topic.
