What Is the Controller?

The controller is just a regular broker with extra responsibilities — it acts as the coordinator and brain of the entire Kafka cluster, managing topic creation, leader election, and broker health tracking.

Kafka Cluster ┌──────────────────────────────────────────────────────────┐ │ │ │ ┌─────────────────────────────────────────────────┐ │ │ │ CONTROLLER (special broker) │ │ │ │ │ │ │ │ Responsibilities: │ │ │ │ ─ Create / delete topics │ │ │ │ ─ Elect partition leader and follower │ │ │ │ ─ Detect broker failures (via heartbeats) │ │ │ │ ─ Notify all brokers about any change │ │ │ │ ─ Maintain cluster metadata log │ │ │ └─────────────────────────────────────────────────┘ │ │ │ ▲ │ │ heartbeats │ │ heartbeats │ │ ▼ │ │ │ ┌──────────┐ ┌──────────┐ ┌──────────┐ │ │ │ Broker 1 │ │ Broker 2 │ │ Broker 3 │ │ │ └──────────┘ └──────────┘ └──────────┘ │ └──────────────────────────────────────────────────────────┘ A broker can have dual responsibility: Option A: controller only (single role) Option B: controller + handle producer/consumer requests (dual role)

Cluster Metadata Log

The controller keeps a file called the cluster metadata log — a record of everything happening in the cluster: which broker holds which topic, which partition is the leader, which is the follower.

Cluster Metadata Log (held by controller) ┌─────────────────────────────────────────────────────┐ │ Topic: order-events │ │ Partition 0 → Leader: Broker 1, Follower: Broker 2│ │ Partition 1 → Leader: Broker 2, Follower: Broker 3│ │ Partition 2 → Leader: Broker 3, Follower: Broker 1│ │ │ │ Topic: payment-events │ │ Partition 0 → Leader: Broker 2, Follower: Broker 1│ │ │ │ Brokers alive: Broker 1 ✓ Broker 2 ✓ Broker 3 ✓ │ └─────────────────────────────────────────────────────┘ Controller pushes this info to ALL brokers so every broker stays up to date. Any change flows through the controller first.

When you ask Kafka to create a topic (from code or the CLI), the request travels through a broker to the active controller, which decides all the leader/follower assignments.

The Single-Controller Problem

Having only one controller is a single point of failure — if it crashes, no one can create topics, detect broker failures, or recover lost partitions.

┌───────────────────────────────────────────────────────────┐ │ SINGLE CONTROLLER PROBLEM │ │ │ │ Controller fails ──► cluster metadata: LOST │ │ ──► new topic creation: IMPOSSIBLE │ │ ──► broker failure detected by: NOBODY│ │ ──► partition leader election: STOPPED│ │ │ │ = cluster becomes UNAVAILABLE │ └───────────────────────────────────────────────────────────┘ Naive fix: add more controllers New problem: who controls the controllers? ┌───────────────────────────────────────────────────────────┐ │ Controller 1 ──► Controller 2 ──► another controller?? │ │ │ │ Infinite loop problem — we need a different solution. │ └───────────────────────────────────────────────────────────┘

KRaft — Kafka's Built-In Solution

KRaft (Kafka Raft) is Kafka's own consensus system built directly into the controller. It replaced the old external dependency called Zookeeper (deprecated in Kafka 3.x+).

OLD WAY — Zookeeper (legacy, deprecated in Kafka 3.x) ┌───────────────────────────────────────────────────┐ │ Kafka Cluster │ Zookeeper Cluster │ │ ┌────────────────┐ │ ┌───────────────────┐ │ │ │ Broker 1 │◄──►│ │ Zookeeper Node 1 │ │ │ │ Broker 2 │◄──►│ │ Zookeeper Node 2 │ │ │ │ Controller │◄──►│ │ Zookeeper Node 3 │ │ │ └────────────────┘ │ └───────────────────┘ │ │ │ External system — │ │ │ deploy + monitor + maintain separately │ └────────────────────────┴──────────────────────────┘ NEW WAY — KRaft (modern, built-in, no external dependency) ┌───────────────────────────────────────────────────┐ │ Kafka Cluster │ │ ┌─────────────────────────────────────────────┐ │ │ │ Controller 1 (active) ← KRaft built-in │ │ │ │ Controller 2 (standby) ← KRaft built-in │ │ │ │ Controller 3 (standby) ← KRaft built-in │ │ │ └─────────────────────────────────────────────┘ │ │ Broker 1 Broker 2 Broker 3 │ └───────────────────────────────────────────────────┘ KRaft uses the Raft consensus algorithm. Zookeeper used the ZAP consensus algorithm.

Quorum — How Controllers Agree

Controllers never make decisions alone — every change must be approved by a majority (quorum) of controllers before it is committed. This prevents split-brain scenarios.

Quorum formula: (n / 2) + 1 where n = number of controllers With 3 controllers: quorum = 2 With 5 controllers: quorum = 3 Example: metadata change needs to be agreed upon ──────────────────────────────────────────────────────── Controller 1 (active): "Shall we commit this change?" │ ├──► Controller 2 (standby): "YES, I agree" ✓ │ └──► Controller 3 (standby): "YES, I agree" ✓ Active controller got 2 votes out of 3 → quorum reached ✓ Decision: COMMITTED ──────────────────────────────────────────────────────── Failure case: Controller 1 (active): "Shall we commit?" │ ├──► Controller 2: "YES" ✓ │ └──► Controller 3: (no response — crashed) ✗ Still got 2 votes out of 3 → quorum still reached ✓ Cluster continues working even with one controller down.

KRaft Topic Creation Flow (with Quorum)

When KRaft is used, every metadata change goes through a quorum vote before being committed. Controllers store the change locally first, then commit only after the majority agrees.

1. Admin CLI sends: create topic order-events (3 partitions, RF=2) │ ▼ 2. Any broker receives the request │ ▼ 3. Broker forwards to ACTIVE CONTROLLER (Controller 1) │ ▼ 4. Controller 1 creates topic metadata (leader/follower assignments) │ ▼ 5. Controller 1 writes to its LOCAL metadata log at offset 100 (NOT committed yet — high watermark is still 99) │ ├──► 6a. Controller 2 KRaft: writes offset 100 locally, replies YES ✓ │ └──► 6b. Controller 3 KRaft: writes offset 100 locally, replies YES ✓ │ ▼ 7. Controller 1 receives majority (2/3) → COMMITS offset 100 High watermark advances: 99 → 100 8. Controller 1 sends committed heartbeat to standby controllers → They commit offset 100 too (already have the record, just mark committed) 9. Controller 1 pushes updated metadata to ALL brokers → Every broker now knows the new topic layout

High Watermark — The Committed Offset

The high watermark is the last offset that has been committed — meaning a quorum of nodes agreed on it. Everything at or below the high watermark is safe and durable.

Controller's local metadata log: ┌────────────────────────────────────────────────────────┐ │ Offset 98: [broker joined] ← committed ✓ │ │ Offset 99: [partition leader change] ← committed ✓ │ │ │ │ High Watermark = 99 (last committed offset) │ │ │ │ Offset 100: [new topic created] ← NOT committed yet│ │ waiting for quorum... │ └────────────────────────────────────────────────────────┘ Once quorum is reached: │ Offset 100: [new topic created] ← committed ✓ │ │ High Watermark = 100 │ Think of it like a bookmark: "Everything up to page 100 is confirmed and agreed upon."

ISR — In-Sync Replicas

For every partition, the controller tracks the ISR list — the set of replicas (leader + followers) that are fully caught up with the leader's latest data.

Topic: order-events, Partition 1 Replication Factor: 3 (1 leader + 2 followers) ┌──────────────┐ polls for updates ┌──────────────┐ │ Broker 1 │◄───────────────────────►│ Broker 2 │ │ (LEADER) │ │ (follower) │ │ offset: 9 │◄───────────────────────►│ offset: 9 │ └──────────────┘ polls for updates └──────────────┘ ▲ │ polls for updates ▼ ┌──────────────┐ │ Broker 3 │ │ (follower) │ │ offset: 9 │ └──────────────┘ ISR list for this partition: [Broker 1, Broker 2, Broker 3] ← all caught up Now Broker 3 stops sending poll requests for 30+ seconds: ┌──────────────┐ ┌──────────────┐ │ Broker 1 │ │ Broker 2 │ │ (LEADER) │◄───────────────────────►│ (follower) │ │ offset: 15 │ still polling │ offset: 15 │ └──────────────┘ └──────────────┘ ┌──────────────┐ │ Broker 3 │ ← no poll requests → lagging too far behind │ (follower) │ │ offset: 9 │ └──────────────┘ Leader updates ISR → passes to Controller → Controller updates metadata ISR list for this partition: [Broker 1, Broker 2] (Broker 3 removed)

How the Leader Tracks Follower Lag

Followers are pull-based — they continuously send fetch/poll requests to the leader. If a follower goes silent for too long, the leader removes it from the ISR.

Normal state — follower stays in ISR: ──────────────────────────────────────────────────────── Follower → "hey, any new data?" (every few ms) Leader → "yes, here is offset 10, 11, 12" Follower → "got it, any more?" Leader → "not yet" Follower → "ok, I'll ask again" (keeps asking) Follower is within 30-second lag window → stays IN ISR ✓ Lagging state — follower removed from ISR: ──────────────────────────────────────────────────────── Follower → [silent for > 30 seconds] Leader → "Broker 3 hasn't called in 30s — it's lagging" → Removes Broker 3 from ISR → Notifies controller → controller updates metadata Config: replica.lag.time.max.ms = 30000 (default ~30s)

Acknowledge Settings (acks)

Producers can choose how much confirmation to wait for before considering a message successfully sent. This is a trade-off between speed and safety.

Producer publishes event to Broker 2 (leader of partition 1) ISR = [Broker 1 (leader), Broker 2 (follower), Broker 3 (follower)] Wait — in this example Broker 2 is leader: ISR = [Broker 2 (leader), Broker 1 (follower), Broker 3 (follower)] ───────────────────────────────────────────────────────────────── acks = 0 (fire and forget) ───────────────────────────────────────────────────────────────── Producer ──► Broker 2: "here is the event" Producer: doesn't even wait for response ← fastest, no guarantee ───────────────────────────────────────────────────────────────── acks = 1 (wait for leader only) ───────────────────────────────────────────────────────────────── Producer ──► Broker 2: "here is the event" Broker 2 writes to its log Broker 2 ──► Producer: "success" Producer: happy ✓ (followers may not have it yet) ───────────────────────────────────────────────────────────────── acks = all (wait for all ISR replicas) ───────────────────────────────────────────────────────────────── Producer ──► Broker 2 (leader): "here is the event" Broker 2 writes to its log Broker 2 waits for ISR followers... Broker 1 polls → writes → "done" ✓ Broker 3 polls → writes → "done" ✓ All ISR confirmed ──► Producer: "success" ✓ Safest, but slowest

Minimum In-Sync Replicas (min.insync.replicas)

This config sets a floor — the producer will fail rather than accept a write when too few replicas are available, preventing data loss in degraded conditions.

Config: min.insync.replicas = 2 Scenario A — 2 ISR replicas (meets the minimum): ───────────────────────────────────────────────────────── ISR = [Broker 1 (leader), Broker 2 (follower)] Producer sends event with acks=all Both write successfully → ✓ success Scenario B — only 1 ISR replica (below minimum): ───────────────────────────────────────────────────────── Broker 2 and Broker 3 are both lagging / crashed ISR = [Broker 1 (leader)] ← only 1 replica Producer sends event with acks=all Leader checks: min.insync.replicas=2 but ISR has only 1 → Request REJECTED ✗ (NotEnoughReplicasException) Why is this useful? ┌─────────────────────────────────────────────────────────┐ │ Without min.insync.replicas: │ │ Leader writes alone → broker crashes → data LOST │ │ │ │ With min.insync.replicas = 2: │ │ System refuses to write → producer retries or alerts │ │ No write is better than a write that gets lost │ └─────────────────────────────────────────────────────────┘ Note: ISR can never be empty because the leader is ALWAYS in ISR.
