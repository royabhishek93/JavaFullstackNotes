Complete Producer Write Flow — Overview

When a producer publishes one event, it goes through several steps: get metadata, calculate which partition to write to, find the leader broker, write the event, and wait for acknowledgement.

PRODUCER WRITE FLOW (end to end) ───────────────────────────────────────────────────────────────────── Step 1: Producer creates the event { topic: "order-events", key: "order-123", value: {...}, acks: all } Step 2: Producer needs metadata (which broker holds which partition leader?) └─► ask any broker → broker asks controller if needed → receives: "partition 1 leader = Broker 2" Step 3: Calculate target partition hash("order-123") % 3 = 1 ← partition 1 Step 4: Look up leader from metadata partition 1 → leader = Broker 2 Step 5: Send write request directly to Broker 2 Step 6: Broker 2 writes the event to its partition 1 log segment file → offset 101 written Step 7: Broker 2 checks acks setting → "all" waits for all ISR replicas (Broker 1 and Broker 3) to confirm Step 8: Followers poll → write → respond "done" Broker 2 sends "published successfully" back to producer ✓

Metadata — What the Producer Needs

Before writing, the producer needs a map of the cluster: which broker is the leader for each partition. This metadata can expire and be refreshed.

Producer metadata cache: ┌────────────────────────────────────────────────────────────┐ │ Topic: order-events │ │ Partition 0 → Leader: Broker 1 │ │ Partition 1 → Leader: Broker 2 ◄── I need to write here│ │ Partition 2 → Leader: Broker 3 │ └────────────────────────────────────────────────────────────┘ How producer gets metadata: ───────────────────────────────────────────────────────────── Producer ──► Any broker: "give me metadata for order-events" │ │ if broker has it → returns directly │ if broker's copy is expired: │ │ │ ▼ │ Active Controller: "here is the latest metadata" │ │ ▼ ▼ Producer ◄── Broker: "here is the metadata" Producer caches this locally and reuses until it expires.

Partition Calculation

The producer uses the message key to deterministically decide which partition to write to. Same key always lands in the same partition.

Topic: order-events (3 partitions) hash(key) % number_of_partitions = target partition ┌────────────────────────────────────────────────────────┐ │ key = "order-123" → hash = 4892731 % 3 = 1 → P1 │ │ key = "order-456" → hash = 9123456 % 3 = 0 → P0 │ │ key = "order-123" → hash = 4892731 % 3 = 1 → P1 │ ← same key │ key = null → round-robin across P0, P1, P2 │ └────────────────────────────────────────────────────────┘ WHY this matters: ┌────────────────────────────────────────────────────────┐ │ Same key → same partition → same consumer reads it │ │ Guarantees ORDER for all events of one key │ │ │ │ order-123: placed → paid → shipped → delivered │ │ All go to P1 → consumed in order ✓ │ └────────────────────────────────────────────────────────┘

The Write — Broker Appends to Segment Log

Once the producer calls the leader broker, the event is appended to the correct partition's segment file at the next sequential offset.

Broker 2 — Topic: order-events — Partition 1 ┌───────────────────────────────────────────────────────┐ │ segment-0000000000000000000.log │ │ ┌──────────────────────────────────────────────────┐ │ │ │ offset 98: { key: "order-100", value: {...} } │ │ │ │ offset 99: { key: "order-101", value: {...} } │ │ │ │ offset 100: { key: "order-102", value: {...} } │ │ │ │ offset 101: { key: "order-123", value: {...} } │ ◄── new event appended here │ └──────────────────────────────────────────────────┘ │ └───────────────────────────────────────────────────────┘ Kafka only APPENDS — never inserts, never modifies. Always sequential writes → very fast on disk.

Complete Consumer Read Flow — Overview

A consumer joining a group goes through its own multi-step dance: find the group coordinator, join the group, discover its assigned partition, find the last processed offset, then start fetching.

CONSUMER READ FLOW (end to end) ───────────────────────────────────────────────────────────────────── Step 1: Consumer starts, wants to join group "notification-service" Step 2: Find which partition of __consumer_offsets handles this group hash("notification-service") % 50 = 23 → partition 23 of __consumer_offsets → Broker 3 holds the leader replica of partition 23 Step 3: Consumer gets cluster metadata (same as producer does) → learns which broker holds each topic/partition leader Step 4: Consumer invokes Broker 3 → "I want to join notification-service group" Broker 3 is now acting as GROUP COORDINATOR for this group Step 5: Group coordinator assigns consumer a partition → consumer 3 gets: order-events partition 2 Step 6: Consumer asks group coordinator: "what was my last committed offset?" → Group coordinator reads __consumer_offsets → returns: "start from 101" Step 7: Consumer invokes leader broker for order-events partition 2 → "fetch me 200 bytes starting at offset 101" → Broker 2 (leader of order-events P2) returns offsets 101–500 Step 8: Consumer processes events 101–500 Step 9: Consumer commits offset 500 back to group coordinator (Broker 3) Group coordinator writes to __consumer_offsets partition 23 Step 10: Consumer loops back to Step 7 → polls again from 501 ↺

What Is a Group Coordinator?

The group coordinator is just a regular broker that happens to hold the leader replica of the __consumer_offsets partition assigned to your consumer group. It manages all group membership and offset bookkeeping.

__consumer_offsets topic (50 partitions, spread across brokers) ┌────┬────┬────┬─────┬────┬────┬────┐ │ P0 │ P1 │ P2 │ ... │P23 │ ...│P49 │ └────┴────┴────┴─────┴────┴────┴────┘ │ Leader = Broker 3 Consumer group: "notification-service" hash("notification-service") % 50 = 23 → Partition 23 → Leader = Broker 3 → Broker 3 IS the group coordinator for "notification-service" Every call for this group ALWAYS goes to Broker 3: ┌────────────────────────────────────────────────────────┐ │ join group request → Broker 3 │ │ fetch last offset → Broker 3 │ │ commit processed offset→ Broker 3 │ │ heartbeat → Broker 3 │ └────────────────────────────────────────────────────────┘ Different group → different hash → different partition → different coordinator broker

Consumer Offset — Where Progress Is Stored

The consumer's position is stored inside Kafka itself (in __consumer_offsets), not in the consumer application. This allows any consumer instance to pick up where another left off.

__consumer_offsets partition 23 — segment file contents: Key (what to look up): Value (what was stored): ┌──────────────────────────────┐ ┌─────────────────────┐ │ group: notification-svc │ → │ last offset: 500 │ │ topic: order-events │ │ │ │ partition: 2 │ │ │ └──────────────────────────────┘ └─────────────────────┘ Consumer 3 crashes → Consumer 4 takes over partition 2: Consumer 4: "what was the last offset for notification-svc / order-events / P2?" Group coordinator: "500" Consumer 4: starts fetching from 501 ✓ Consumer-side metadata (group membership, partition assignment) lives here. Cluster metadata (broker, topic, partition leaders) lives in controller. They are separate and stored separately.

The Polling Loop

Kafka consumers are pull-based — they ask for data, Kafka does not push it. The consumer keeps polling in an infinite loop.

Consumer polling loop: ───────────────────────────────────────────────────────────────── ┌───────────────────────────────────────────────────────────┐ │ │ │ ┌──────────────────────────────────────────────────┐ │ │ │ poll(order-events P2, from=501, max=200 bytes) │ │ │ └──────────────────────────────────────────────────┘ │ │ │ │ │ ▼ │ │ Broker 2 returns offsets 501–900 │ │ │ │ │ ▼ │ │ consumer.process(events 501–900) │ │ │ │ │ ▼ │ │ commitOffset(900) → group coordinator │ │ │ │ │ └──────────────────────────────────────► │ loop ↺ │ poll again from 901 │ └───────────────────────────────────────────────────────────┘ Kafka: pull-based (consumer asks when ready) vs. Push-based: server decides when to send (consumer may be overwhelmed)

Log Compaction — Delete Policy

The default cleanup strategy is delete: old segments are removed based on time or total size. This keeps disk usage bounded.

cleanup.policy = delete (default) retention.ms = 604800000 (7 days) retention.bytes = 1073741824 (1 GB per partition) Partition segments over time: ┌────────────────┬────────────────┬────────────────┬─────────────┐ │ segment-1 │ segment-2 │ segment-3 │ segment-4 │ │ (8 days old) │ (5 days old) │ (3 days old) │ (1 day old)│ │ 400 MB │ 400 MB │ 150 MB │ 50 MB │ └────────────────┴────────────────┴────────────────┴─────────────┘ │ │ retention.ms check: 8 days > 7 days → DELETE ✗ │ ▼ result after cleanup: ┌────────────────┬────────────────┬─────────────┐ │ segment-2 │ segment-3 │ segment-4 │ │ (5 days old) │ (3 days old) │ (1 day old)│ │ 400 MB │ 150 MB │ 50 MB │ └────────────────┴────────────────┴─────────────┘ Size check: total = 600 MB < 1 GB → no size-based deletion needed If total exceeded 1 GB, the OLDEST segment would be deleted. Rule: deletion always works on entire SEGMENTS, not individual records.

Log Compaction — Compact Policy

The compact strategy keeps only the latest value for each key. Perfect for "current state" topics where only the most recent record per key matters (e.g., user profiles, product prices).

cleanup.policy = compact Segment before compaction: ┌──────────────────────────────────────────────────────────┐ │ offset 100: key=user-1, value=version-1 │ │ offset 101: key=user-2, value=version-1 │ │ offset 102: key=user-1, value=version-2 ← newer user-1 │ │ offset 103: key=user-3, value=version-1 │ │ offset 104: key=user-2, value=version-2 ← newer user-2 │ │ offset 105: key=user-1, value=version-3 ← newest user-1│ └──────────────────────────────────────────────────────────┘ │ │ background compaction job runs (async, non-blocking) ▼ Segment after compaction: ┌──────────────────────────────────────────────────────────┐ │ offset 103: key=user-3, value=version-1 ← only entry │ │ offset 104: key=user-2, value=version-2 ← latest │ │ offset 105: key=user-1, value=version-3 ← latest │ └──────────────────────────────────────────────────────────┘ user-1: had 3 versions → kept only version-3 ✓ user-2: had 2 versions → kept only version-2 ✓ user-3: had 1 version → kept as-is ✓ Important: compaction is ASYNC — not instant, writes never blocked.

Page Cache — Write Optimization

Kafka does not write directly to disk. It first writes to the OS page cache (RAM) and lets the operating system flush to disk asynchronously. This removes the bottleneck of synchronous disk writes.

WITHOUT page cache (slow): ───────────────────────────────────────────────────────── Producer → Kafka → write to disk ← blocking disk I/O, slow WITH page cache (Kafka's approach): ───────────────────────────────────────────────────────── Producer ──► Kafka ──► OS page cache (RAM) │ │ async flush (OS handles this) ▼ Disk (non-blocking for Kafka) ┌─────────────────────────────────────────────────────────┐ │ Kafka trusts the OS to manage cache efficiently │ │ Writes are non-blocking → extremely high throughput │ │ Follower reads also served from page cache (RAM fast) │ └─────────────────────────────────────────────────────────┘

Sequential Writes — Why Disk Is Fast for Kafka

Random disk writes are slow because the disk head must jump around. Kafka avoids this completely — it only ever appends to the end of a file, making every write sequential.

Random writes (databases, typical apps): ───────────────────────────────────────────────────────── Write record at position 1024 → disk head moves ─────────► Write record at position 45 → disk head moves ◄──────── Write record at position 3200 → disk head moves ──────────► = lots of head movement = slow Sequential writes (Kafka's append-only model): ───────────────────────────────────────────────────────── offset 100 ──► offset 101 ──► offset 102 ──► offset 103 [append] [append] [append] [append] disk head keeps moving in ONE direction = very fast ✓ Kafka rules that make this possible: ┌─────────────────────────────────────────────────────────┐ │ ✗ Never insert a record in the middle │ │ ✗ Never modify an existing record │ │ ✗ Never update a record in place │ │ ✓ Only ever append at the end with a new offset │ └─────────────────────────────────────────────────────────┘

Zero Copy — Read Optimization

When a consumer fetches data, Kafka uses a special OS system call called sendfile to skip copying data into Kafka's own memory — data goes straight from disk to the network.

Normal file serving (WITHOUT zero copy): ───────────────────────────────────────────────────────── Disk │ 1. read into OS page cache (RAM) ▼ OS page cache (RAM) │ 2. copy into Kafka JVM user space ▼ Kafka JVM (user space) │ 3. copy to network buffer ▼ Network → Consumer = 3 hops, data copied multiple times, wastes memory + CPU Kafka's zero copy (sendfile system call): ───────────────────────────────────────────────────────── Disk │ 1. read into OS page cache (RAM) ▼ OS page cache (RAM) │ 2. sendfile() ── bypasses Kafka JVM entirely ▼ Network → Consumer = 2 hops, Kafka JVM never touches the data ┌─────────────────────────────────────────────────────────┐ │ Benefits of zero copy: │ │ ─ Saves one full data copy │ │ ─ Saves Kafka JVM memory │ │ ─ Saves CPU cycles │ │ ─ Much higher read throughput │ └─────────────────────────────────────────────────────────┘

Performance Summary — Read and Write Together

WRITE PATH (producer → Kafka) ┌──────────────────────────────────────────────────────────────┐ │ Producer writes event │ │ │ │ │ ▼ │ │ Broker appends to OS page cache (RAM) ← non-blocking │ │ │ │ │ │ async │ │ ▼ │ │ Disk (sequential append) ← best-case disk I/O pattern │ │ │ │ Optimizations: page cache + sequential write │ └──────────────────────────────────────────────────────────────┘ READ PATH (Kafka → consumer) ┌──────────────────────────────────────────────────────────────┐ │ Consumer sends fetch request │ │ │ │ │ ▼ │ │ Data loaded into OS page cache (if not already there) │ │ │ │ │ │ sendfile() — zero copy │ │ ▼ │ │ Network → Consumer (Kafka JVM never touched the data) │ │ │ │ Optimization: zero copy (sendfile system call) │ └──────────────────────────────────────────────────────────────┘
