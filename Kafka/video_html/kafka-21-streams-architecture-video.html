What Is a Stream?

A stream is an infinite sequence of events — no start, no end, just a continuous flow.

Normal batch processing: Wait until 3pm → pick up ALL events → process them all at once Stream processing: Event arrives NOW → process it NOW → next event → process it NOW → ... order-1 ──► process ──► output order-2 ──► process ──► output order-3 ──► process ──► output order-4 ──► process ──► output ...forever...

Kafka Streams is just a JAR file you add to your application — it's not a cluster or server. Add the dependency → your app becomes a stream processor.

Topology — The Blueprint

A Topology is the logical map of how data flows through your application: from where it enters, what happens to it, and where it exits.

Think of it like an assembly line in a factory:

Factory analogy: Raw material → Cut → Paint → Package → Ship Kafka Streams topology: Source topic → Processor 1 → Processor 2 → Processor 3 → Sink topic

It is a DAG (Directed Acyclic Graph) — data always flows forward, never loops back.

Source ──► ProcessorA ──► ProcessorB ──► Sink │ └──────────► ProcessorC ──► Sink 2

Key components:

┌────────────────────────────────────────────────────────────────┐ │ TOPOLOGY │ │ │ │ ┌────────────┐ ┌───────────────────────────┐ ┌──────┐ │ │ │ SOURCE │───►│ PROCESSORS │───►│ SINK │ │ │ │ │ │ (your business logic) │ │ │ │ │ │ reads from │ │ filter, map, group, │ │writes│ │ │ │ Kafka topic│ │ count, join, aggregate │ │ to │ │ │ │ │ │ │ │topic │ │ │ └────────────┘ └───────────────────────────┘ └──────┘ │ │ │ │ │ ▼ (if stateful) │ │ ┌──────────┐ │ │ │ RocksDB │ ← local state store │ │ └──────────┘ │ └────────────────────────────────────────────────────────────────┘

Task — Unit of Parallelism

A Task is the smallest unit of work. Multiple tasks run in parallel — that's how Kafka Streams scales.

Topic: order-events (2 partitions) ┌────────────────────────────────┐ │ Partition-0 │ Partition-1 │ └────────┬───────┴───────┬───────┘ │ │ ▼ ▼ Task-0 Task-1 ┌──────────────┐ ┌──────────────┐ │ full │ │ full │ │ topology │ │ topology │ │ Source P-0 │ │ Source P-1 │ │ Processor │ │ Processor │ │ Sink │ │ Sink │ └──────────────┘ └──────────────┘ Number of tasks = number of partitions in source topic Task-0 and Task-1 run IN PARALLEL

Key points:

  • Each task gets the complete topology to execute
  • Within one task, events are processed one by one (no parallelism inside a task)
  • Tasks are distributed across your application instances (threads)

The Repartition Problem

Repartition is needed when events for the same key are spread across multiple partitions.

Goal: Count orders per product ID

Topic: order-events (key = orderId, NOT productId) ──────────────────────────────────────────────────────────────── Partition-0: Partition-1: { orderId:O1, product:P1 } { orderId:O3, product:P1 } { orderId:O2, product:P2 } { orderId:O4, product:P2 } Task-0 sees P1: 1 order Task-1 sees P1: 1 order Task-1 sees P2: 1 order Task-1 sees P2: 1 order Which task has the CORRECT total for P1? Task-0 says: P1=1 ← WRONG Task-1 says: P1=1 ← WRONG Real answer: P1=2 ← neither task can see this! PROBLEM: data for P1 is SPLIT across 2 partitions → 2 different tasks → wrong aggregation

Repartition — The Solution

Re-publish events using product ID as the key so all events for the same product go to the same partition.

STEP 1: Sub-Topology 0 — Re-key and re-publish ──────────────────────────────────────────────────────────────── Source: order-events (key=orderId) │ ▼ selectKey(productId) ← repartition step │ ▼ publishes to internal repartition topic (key=productId) ┌────────────────────────────────────────────┐ │ repartition-topic (auto-created by Kafka) │ │ Partition-0: ALL P1 orders │ │ Partition-1: ALL P2 orders │ └────────────────────────────────────────────┘ (same key = same partition, guaranteed by Kafka) STEP 2: Sub-Topology 1 — Read re-partitioned topic and count ──────────────────────────────────────────────────────────────── Source: repartition-topic (key=productId) │ ▼ groupByKey → count │ ▼ Sink: product-order-count topic Task-0 reads Partition-0: ALL P1 orders → P1=2 ✓ Task-1 reads Partition-1: ALL P2 orders → P2=2 ✓

Sub-Topology — What It Is

When a repartition step is in your topology, Kafka Streams automatically splits it into multiple sub-topologies internally. You don't create sub-topologies — Kafka does it for you.

YOUR TOPOLOGY (what you write): ──────────────────────────────────────────────────────────────── source(order-events) → selectKey(productId) ← repartition step here → groupByKey → count → sink(product-order-count) WHAT KAFKA CREATES INTERNALLY: ──────────────────────────────────────────────────────────────── Sub-Topology 0: source: order-events processor: selectKey(productId) sink: repartition-topic ← auto-created topic Sub-Topology 1: source: repartition-topic ← reads from auto-created topic processor: groupByKey → count sink: product-order-count

Rule: Each sub-topology creates one task per partition of its source topic.

Task Count Calculation (Full Example)

Setup: order-events topic: 2 partitions (P-0, P-1) repartition-topic: 2 partitions (P-0, P-1) ← same count as source Sub-Topology 0 source = order-events (2 partitions) → 2 tasks Sub-Topology 1 source = repartition-topic (2 partitions) → 2 tasks Total tasks = 4 Task-0-0 (sub-topology 0, partition 0) Task-0-1 (sub-topology 0, partition 1) Task-1-0 (sub-topology 1, partition 0) Task-1-1 (sub-topology 1, partition 1)

These 4 tasks get distributed across your application threads:

RocksDB — Local State Store

Each stateful task maintains its own RocksDB — a key-value store saved to local disk.

Task-0-0 Task-1-0 ┌──────────────────────┐ ┌──────────────────────┐ │ Sub-Topology 0 │ │ Sub-Topology 1 │ │ processor... │ │ groupByKey → count │ │ │ │ │ │ ┌────────────────┐ │ │ ┌────────────────┐ │ │ │ RocksDB │ │ │ │ RocksDB │ │ │ │ order-store │ │ │ │ count-store │ │ │ │ (local disk) │ │ │ │ (local disk) │ │ │ └────────────────┘ │ │ └────────────────┘ │ └──────────────────────┘ └──────────────────────┘ RocksDB = key-value file on YOUR machine's disk Each task has its OWN RocksDB — they don't share

Change Log Topic — Crash Recovery for State

Problem: If the machine dies, RocksDB (local disk) is gone. How to recover?

Solution: Every write to RocksDB is also published to a changelog topic in Kafka.

Task writes to RocksDB: ┌──────────────────────────────────────────────────────────────┐ │ count-store (RocksDB): { P1: 3, P2: 5 } │ │ │ │ │ │ every update also goes to Kafka │ │ ▼ │ │ count-store-changelog topic: │ │ [ {P1:1}, {P1:2}, {P2:1}, {P1:3}, {P2:2}, {P2:5} ] │ └──────────────────────────────────────────────────────────────┘ Machine crashes: Local RocksDB ✗ (gone with the machine) New machine takes over the task: 1. Reads count-store-changelog topic from beginning 2. Replays all events → rebuilds RocksDB: { P1:3, P2:5 } 3. Continues processing from where the old task left off ✓

Partition alignment: Each task reads/writes to the same partition number in the changelog as its source partition.

Task-1-0 (sub-topology 1, partition 0): reads from: repartition-topic P-0 writes to: count-store-changelog P-0 ← same partition number Task-1-1 (sub-topology 1, partition 1): reads from: repartition-topic P-1 writes to: count-store-changelog P-1 ← same partition number

Application Startup Flow

Step 1: App starts with group.id = "stream-analytics" Step 2: Find group coordinator → hash("stream-analytics") % 50 → partition 23 Step 3: Connect to broker holding __consumer_offsets partition 23 Step 4: Send JoinGroup request — coordinator waits for ALL instances to join Step 5: Stream Partition Assigner runs: - Discovers your topology - Creates sub-topologies - Creates tasks - Creates repartition topic (if needed) - Creates changelog topics (if needed) - Distributes tasks to instances Step 6: Your instance gets assigned tasks (e.g. Task-0-0, Task-1-0) Step 7: For each task — restore RocksDB from changelog topic Step 8: Fetch last committed offset for source partitions Step 9: Start reading events → process through topology → commit offset Step 10: Repeat forever ↺
