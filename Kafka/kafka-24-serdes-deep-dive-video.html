What Is SerDes?

SerDes is short for Serializer + Deserializer — two things packaged into one object that handles both converting Java objects into raw bytes (for writing) and converting raw bytes back into Java objects (for reading).

Kafka topics and RocksDB always store data as raw bytes. Your Java code works with typed objects: String, Long, Order, etc. SerDes bridges the gap in both directions. Java object ──[ Serializer ]──► bytes (write to Kafka / RocksDB) bytes ──[ Deserializer ]──► Java object (read from Kafka / RocksDB) Serdes = Serializer + Deserializer bundled together: Serdes.String() contains: ┌──────────────────────────────────────────────────┐ │ StringSerializer (String ──► bytes) │ │ StringDeserializer (bytes ──► String) │ └──────────────────────────────────────────────────┘ When reading → framework calls Deserializer internally When writing → framework calls Serializer internally

Five Places SerDes Is Needed in a Topology

Every time data crosses the boundary between a Java object and raw bytes, SerDes is required. A typical topology has five such boundaries.

┌──────────────────────────────────────────────────────────────────────┐ │ TOPOLOGY │ │ │ │ [1] SOURCE │ │ Read from Kafka topic │ │ bytes ──► Java object needs DESERIALIZER │ │ │ │ │ ▼ │ │ PROCESSOR PIPELINE │ │ (filter, map, groupBy, join, count …) │ │ │ │ │ ├──────────────────────────────────────────────────────┐ │ │ │ │ │ │ ▼ ▼ │ │ [4] ROCKSDB WRITE [5] ROCKSDB READ│ │ Java object ──► bytes bytes ──► Java │ │ (KTable, count, aggregate) (join, lookup) │ │ needs SERIALIZER needs DESERIALIZER│ │ │ │ │ ▼ │ │ [3] REPARTITION (if present) │ │ Write to internal repartition topic │ │ Java object ──► bytes needs SERIALIZER │ │ │ │ │ ▼ │ │ [2] SINK │ │ Write to output Kafka topic │ │ Java object ──► bytes needs SERIALIZER │ └──────────────────────────────────────────────────────────────────────┘ Simple rule: Reading (from topic or RocksDB) ──► Deserializer Writing (to topic or RocksDB) ──► Serializer

Built-In SerDes

Kafka Streams ships with ready-made SerDes for all common Java primitive types — no custom code needed for these.

┌──────────────────┬──────────────────────┬──────────────────────────┐ │ SerDes object │ Java type │ Typical use │ ├──────────────────┼──────────────────────┼──────────────────────────┤ │ Serdes.String() │ String │ keys, names, JSON text │ │ Serdes.Long() │ Long │ counts, timestamps │ │ Serdes.Integer() │ Integer │ IDs, quantities │ │ Serdes.Double() │ Double │ prices, scores │ │ Serdes.Float() │ Float │ measurements │ │ Serdes.Short() │ Short │ small integers │ │ Serdes.Boolean() │ Boolean │ flags │ │ Serdes.Bytes() │ byte[] │ raw bytes pass-through │ └──────────────────┴──────────────────────┴──────────────────────────┘ For custom Java objects (Order, Customer, Payment): → use the built-in JSON SerDes already provided by the framework, or → write your own (covered in section 6)

Default SerDes — Set Once in application.properties

You can declare a default SerDes in application.properties so you do not have to repeat it on every builder call. This only works well when every step in the topology uses the same key and value type throughout.

application.properties: spring.kafka.streams.properties.default.key.serde= org.apache.kafka.common.serialization.Serdes$StringSerde spring.kafka.streams.properties.default.value.serde= org.apache.kafka.common.serialization.Serdes$StringSerde WITHOUT default SerDes — must specify on every call: ────────────────────────────────────────────────────────────────── builder.stream("orders", Consumed.with(Serdes.String(), Serdes.String())) .to("output", Produced.with(Serdes.String(), Serdes.String())); Materialized.as("store") .withKeySerde(Serdes.String()) .withValueSerde(Serdes.String()); WITH default SerDes — minimal: ────────────────────────────────────────────────────────────────── builder.stream("orders") .to("output"); ← no SerDes needed, defaults apply WHY default SerDes is rarely useful in practice: ────────────────────────────────────────────────────────────────── Source: key=String, value=String ← default works ✓ After count(): key=String, value=Long ← default breaks ✗ The moment your value type changes mid-pipeline (e.g. after a count, aggregate, or map), the default no longer fits. Explicit per-operation SerDes is safer and clearer.

Per-Operation SerDes — Explicit and Highest Priority

Providing SerDes directly on each operation overrides any default. This is the recommended approach for production pipelines.

KStream (source — reading, so Consumed.with): builder.stream( "order-events", Consumed.with(Serdes.String(), Serdes.String()) ) KTable (source + RocksDB — both Consumed and Materialized): builder.table( "order-events", Consumed.with(Serdes.String(), Serdes.String()), Materialized .<String, String, KeyValueStore<Bytes, byte[]>>as("order-store") .withKeySerde(Serdes.String()) .withValueSerde(Serdes.String()) ) Sink (writing to topic — Produced.with): .to("output-topic", Produced.with(Serdes.String(), Serdes.String())) Priority order (highest wins): ┌──────────────────────────────────────────────────────────────┐ │ [1] Per-operation SerDes (explicit on each call) ← HIGHEST │ │ [2] Default SerDes (application.properties) ← lowest │ └──────────────────────────────────────────────────────────────┘ Always use per-operation SerDes when the key or value type changes at any point in the pipeline.

Custom SerDes — Handling Your Own Java Objects

For domain objects like Order or Customer you create three classes: a Serializer, a Deserializer, and a Serdes wrapper that combines them.

STEP 1 — Serializer (Java object ──► bytes) ────────────────────────────────────────────────────────────────── class JsonSerializer<T> implements Serializer<T> { byte[] serialize(String topic, T data) { return objectMapper.writeValueAsBytes(data); } ↑ } Jackson converts any object to JSON bytes STEP 2 — Deserializer (bytes ──► Java object) ────────────────────────────────────────────────────────────────── class JsonDeserializer<T> implements Deserializer<T> { Class<T> targetClass; ← must know the target type T deserialize(String topic, byte[] data) { return objectMapper.readValue(data, targetClass); } ↑ } Jackson converts JSON bytes back to typed object Serializer does NOT need targetClass (it already has the object); Deserializer DOES (bytes have no type info) STEP 3 — Serdes wrapper (combines both into one) ────────────────────────────────────────────────────────────────── class JsonSerde<T> implements Serde<T> { ┌────────────────────────────────────────────┐ │ JsonSerializer<T> ← used when writing │ │ JsonDeserializer<T> ← used when reading │ └────────────────────────────────────────────┘ Serializer<T> serializer() { return jsonSerializer; } Deserializer<T> deserializer() { return jsonDeserializer; } } USAGE — pass the custom Serdes just like a built-in one: ────────────────────────────────────────────────────────────────── builder.stream( "order-events", Consumed.with( Serdes.String(), ← key is a plain String new JsonSerde<>(Order.class) ← value is an Order object ) ) .to("output", Produced.with( Serdes.String(), new JsonSerde<>(Order.class) ));

Deserialization Error Handling

A deserialization error occurs when bytes in a topic cannot be converted to the expected Java type — for example, reading a JSON blob as a Long. Three strategies are available.

COMMON CAUSES OF DESERIALIZATION FAILURE ────────────────────────────────────────────────────────────────── Type mismatch: topic has JSON string, you read it as Long ✗ Corrupted bytes: garbage bytes, not valid JSON at all ✗ Schema change: new required field added, old consumer breaks ✗ THREE HANDLERS ────────────────────────────────────────────────────────────────── [1] LogAndFailExceptionHandler (DEFAULT — nothing to configure) ┌──────────────────────────────────────────────────────────────┐ │ Bad record arrives │ │ → log the error │ │ → throw exception → stream thread dies │ │ → if all threads die → application shuts down │ └──────────────────────────────────────────────────────────────┘ Safest option: nothing is silently lost. application.properties (explicit): default.deserialization.exception.handler= org.apache.kafka.streams.errors.LogAndFailExceptionHandler [2] LogAndContinueExceptionHandler ┌──────────────────────────────────────────────────────────────┐ │ Bad record arrives │ │ → log the error │ │ → skip the bad record, continue with next ✓ │ │ → bad record is LOST FOREVER ✗ │ └──────────────────────────────────────────────────────────────┘ application.properties: default.deserialization.exception.handler= org.apache.kafka.streams.errors.LogAndContinueExceptionHandler [3] Custom handler (RECOMMENDED for production) ┌──────────────────────────────────────────────────────────────┐ │ class MyHandler implements DeserializationExceptionHandler │ │ Handle(context, record, exception) { │ │ errorCount++; │ │ if (errorCount > MAX_ERRORS) return FAIL; │ │ else return CONTINUE; │ │ } ↑ or route bad record to a dead-letter topic │ │ } │ └──────────────────────────────────────────────────────────────┘ You decide: fail fast, skip, or send bad records elsewhere. application.properties: default.deserialization.exception.handler= com.example.MyHandler

Serialization Error Handling

A serialization error occurs when a Java object cannot be converted to bytes — for example, an object with a circular reference that Jackson cannot traverse. Two strategies are available.

COMMON CAUSES OF SERIALIZATION FAILURE ────────────────────────────────────────────────────────────────── Type mismatch: sending Order object but SerDes expects Long ✗ Circular reference: A → B → A → B → … (infinite loop in object) ✗ Record too large: object exceeds topic's max.message.bytes ✗ TWO HANDLERS ────────────────────────────────────────────────────────────────── [1] DefaultProductionExceptionHandler (DEFAULT) ┌──────────────────────────────────────────────────────────────┐ │ Serialization fails │ │ → always fail │ │ → stream thread dies │ │ → if all threads die → application shuts down │ └──────────────────────────────────────────────────────────────┘ application.properties (explicit): default.production.exception.handler= org.apache.kafka.streams.errors.DefaultProductionExceptionHandler [2] Custom handler (RECOMMENDED for production) ┌──────────────────────────────────────────────────────────────┐ │ class MyProdHandler implements ProductionExceptionHandler │ │ Handle(producerRecord, exception) { │ │ if (exception is RecordTooLargeException) │ │ return CONTINUE; ← skip oversized, keep going │ │ else │ │ return FAIL; ← crash on unexpected errors │ │ } │ │ } │ └──────────────────────────────────────────────────────────────┘ Inspect the exception type and decide per case. application.properties: default.production.exception.handler= com.example.MyProdHandler

RocksDB state store → Materialized.with(Serdes.String(), statsSerde) 4. (no join here, but a join would need the OTHER side's Serde too) 5. Sink: delivery-rate-per-min → Produced.with(Serdes.String(), statsSerde)

Scenario-first: "Every one of these must agree, or you get a ClassCastException/deserialization error at 2am in production, not at compile time. I never rely on the app-wide default Serde — I specify it explicitly at every single boundary, treating the default purely as a fallback."

Cross Questions Interviewers Ask

Q: Why does a repartition topic need its own explicit Serde configuration? A: The repartition step re-serializes records to a NEW internal topic — if that step relies on the app-wide default Serde and your aggregation produces a different value type, you get a silent mismatch that only surfaces as a runtime error once real data flows through. Q: What's the practical difference between LogAndFail and LogAndContinue as deserialization exception handlers? A: LogAndFail crashes the stream thread on a bad record — nothing is silently lost, but the app stops (safest default). LogAndContinue skips the bad record and keeps going — the app stays up, but that record's data is gone forever unless you've separately routed it to a DLQ. Q: Why would you ever need a custom production exception handler instead of the default? A: The default fails the thread on ANY serialization error — but some errors (like RecordTooLarge for a genuinely disposable record) might be safe to skip and continue, while others (schema violations) should still fail loudly. A custom handler lets you make that distinction per exception type.

Senior Trap Questions (15 YOE)

Trap 1 — "A teammate skips specifying Materialized.with(keySerde, valueSerde) on a stateful aggregation, relying on the app-wide default serde. Why might this quietly bite you later?" Answer: "The app-wide default is a reasonable starting point, but the moment ANY single stateful operation needs a DIFFERENT value type than the default (e.g., an aggregation producing a custom DeliveryStats object instead of a raw string/long), relying on the default silently mis-serializes or throws a runtime ClassCastException — often only once that specific code path executes in production, well after deployment." Trap 2 — "Your topology switched from LogAndFail to LogAndContinue 'to keep the app running through bad data,' and now your delivery-rate numbers are quietly under-counting with no errors in the logs. Explain the connection." Answer: "LogAndContinue silently DROPS any record that fails deserialization — the aggregation simply never sees it, so your counts are systematically low with zero visible errors, because 'continue' was chosen over 'fail loudly.' For a business-facing metric, LogAndFail (or a custom handler routing to a DLQ) is almost always the safer choice — silent data loss is worse than a visible crash you can alert on."

WHY We Chose Each Decision

- Why explicit SerDes at every boundary, never relying on app-wide defaults: the five SerDes points rarely share exactly one type end-to-end — being explicit turns a runtime surprise into a compile-time or registration-time check. - Why LogAndFail over LogAndContinue as our default exception handler: visible failure over silent, undetectable data loss for a business-facing metric. - Why a custom production exception handler for select error types: distinguishes genuinely safe-to-skip errors from ones that must fail loudly. - Why Avro SerDes matching the producer schema, not a Streams-internal-only format: keeps the same schema-evolution governance across the whole pipeline.

Top 2 Technologies — Handling Bad Records During Deserialization

LogAndFailExceptionHandler (default) vs Custom Handler Routing to a DLQ Why pick LogAndFail (safe default): nothing silently lost — a bad record stops the thread, forcing visible investigation before more data flows. Why pick Custom DLQ routing: keeps the stream running through bad records while still preserving them for later inspection, rather than either losing them (LogAndContinue) or halting entirely (LogAndFail). Example 1 (LogAndFail): Notification System's delivery-rate topology during initial rollout — surfaces any schema/data issues loudly and early. Example 2 (Custom DLQ): The same topology once mature, where a rare bad record shouldn't halt real-time reporting for everyone — route it to a DLQ topic and keep the aggregation running.
