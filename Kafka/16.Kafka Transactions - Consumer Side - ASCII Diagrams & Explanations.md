# Kafka Transactions — Consumer Side — ASCII Diagrams & Explanations

Topics: isolation.level, read_committed, read_uncommitted, LSO, Last Stable Offset, Control Records, .txn index, Aborted Transactions, EOS, Exactly-Once Semantics

---

## 1. Three States a Record Can Be In

Every record in a Kafka partition log that was written inside a transaction is in one of three states. Non-transactional records have no state — they are always visible.

```
Partition log (order-events, partition P2):

  offset 0: PID=5, epoch=0, is_transactional=true, is_control=false  [data record]  ─┐
  offset 1: PID=5, epoch=0, is_transactional=true, is_control=false  [data record]   ├── OPEN (no control record yet)
                                                                                      ─┘
  offset 2: PID=8, epoch=1, is_transactional=true, is_control=false  [data record]  ─┐
  offset 3: PID=8, epoch=1, is_transactional=true, is_control=true   COMMIT          ┘── COMMITTED

  offset 4: PID=9, epoch=0, is_transactional=true, is_control=false  [data record]  ─┐
  offset 5: PID=9, epoch=0, is_transactional=true, is_control=true   ABORT           ┘── ABORTED

  Non-transactional record (written without a transaction):
  offset 6: is_transactional=false                                   [data record]  ──── always visible

  State       Meaning                              Consumer (read_committed) sees it?
  ──────────  ───────────────────────────────────  ───────────────────────────────────
  OPEN        transaction started, not finished    ✗  wait
  COMMITTED   COMMIT control record present        ✓  visible
  ABORTED     ABORT control record present         ✗  skip
  (none)      non-transactional record             ✓  always visible
```

## 2. Control Records — The COMMIT and ABORT Markers

Control records are special log entries written by the transaction coordinator when a transaction finishes. They are never delivered to consumers — the broker filters them out before sending.

```
What a control record looks like in the log:

  ┌──────────────────────────────────────────────────────────────┐
  │  PID = 5                                                     │
  │  epoch = 0                                                   │
  │  is_transactional = true                                     │
  │  is_control = true          ← this makes it a control record │
  │  control_type = COMMIT      ← or ABORT                       │
  └──────────────────────────────────────────────────────────────┘

Normal data record in the log:

  ┌──────────────────────────────────────────────────────────────┐
  │  PID = 5                                                     │
  │  epoch = 0                                                   │
  │  is_transactional = true                                     │
  │  is_control = false         ← regular data record            │
  │  [your key / value payload]                                  │
  └──────────────────────────────────────────────────────────────┘

                          BROKER
                            │
                 filters out is_control=true
                            │
              ┌─────────────┴──────────────────┐
              │  delivers to consumer:          │
              │  ✓ data records                 │
              │  ✓ non-transactional records    │
              │  ✗ control records (filtered)   │
              └─────────────────────────────────┘
```

## 3. isolation.level — read_uncommitted vs read_committed

The isolation level is set on the consumer and controls how it handles transactional records.

```
application.properties (consumer):
  spring.kafka.consumer.properties.isolation.level=read_committed
  (default is read_uncommitted if you do not set this)

                    ┌─────────────────────────────────────────────────────────┐
                    │                 PARTITION LOG                           │
                    │  off 0: PID=5  txnal=true  [order-A]     ← COMMITTED   │
                    │  off 1: PID=5  txnal=true  [order-B]     ← COMMITTED   │
                    │  off 2: PID=8  txnal=true  [order-C]     ← OPEN        │
                    │  off 3: PID=9  txnal=true  [order-D]     ← ABORTED     │
                    │  off 4: txnal=false        [order-E]     ← non-txnal   │
                    └─────────────────────────────────────────────────────────┘
                               │                          │
               read_uncommitted                    read_committed
               (default)                                  │
                    │                                      │
    sees: 0, 1, 2, 3, 4                    sees: 0, 1, 4  only
    (all records except                    (committed + non-txnal only;
     control records)                       skips open and aborted)

  read_uncommitted  ─  fast, simple, may read data from transactions that later abort
  read_committed    ─  safe, used for EOS; waits for open txns, skips aborted ones
```

## 4. LSO — Last Stable Offset

LSO is a pointer maintained by the broker. It always points to the first record that belongs to an open (not yet committed or aborted) transaction.

```
Partition log state:

  offset 0: PID=5, txnal=true   [record]  ─┐ transaction T1
  offset 1: PID=5, txnal=true   [record]   │ OPEN — no control record yet
  offset 2: PID=5, txnal=true   [record]  ─┘

  offset 3: PID=9, txnal=true   [record]  ─┐ transaction T2
  offset 4: PID=9, control=true  COMMIT   ─┘ COMMITTED

  offset 5: PID=7, txnal=true   [record]    transaction T3 — also OPEN

        LSO = 0   ← points to the FIRST record of the earliest open transaction

  When T1 commits or aborts:
        LSO = 5   ← advances to the first record of the next open transaction

  When T3 commits or aborts:
        LSO = 6   ← no more open transactions; LSO = (next empty offset = HW)

  ┌──────────────────────────────────────────────────────────────────────┐
  │  LSO  ≤  High Watermark (HW)                                         │
  │  HW   = the next offset to be written (all replicas have caught up)  │
  │  LSO  = the safe read boundary for read_committed consumers          │
  │                                                                      │
  │  read_uncommitted consumer reads up to: HW                          │
  │  read_committed   consumer reads up to: LSO                         │
  └──────────────────────────────────────────────────────────────────────┘
```

## 5. How LSO Blocks Open Transactions

When using `read_committed`, the consumer uses the LSO as its read boundary. It reads all offsets below LSO, then stops and waits.

```
Partition log example:

  off 0: PID=5, txnal=true   [data]  ─┐ T1 — COMMITTED  (ctrl at off 2)
  off 1: PID=5, txnal=true   [data]   │
  off 2: PID=5, ctrl=true    COMMIT  ─┘

  off 3: PID=8, txnal=true   [data]  ─┐ T2 — OPEN ← first open record
                                       │             LSO = 3
  off 4: PID=9, txnal=true   [data]  ─┐ T3 — COMMITTED (ctrl at off 5)
  off 5: PID=9, ctrl=true    COMMIT  ─┘

Consumer with read_committed:

  Broker says: LSO = 3

  read offset 0?  0 < LSO(3) → YES ✓
  read offset 1?  1 < LSO(3) → YES ✓
  read offset 2?  control record → broker already filtered it out, not delivered
  read offset 3?  3 < LSO(3) → 3 is NOT less than 3 → STOP

  Consumer stops at offset 3. It will NOT jump ahead to read offset 4 or 5.

  WHY? Kafka guarantees in-order delivery within a partition.
  Skipping offset 3 would break ordering. Consumer must wait for T2 to
  either commit or abort before it can read offset 3 and beyond.

  Once T2 commits/aborts → LSO advances → consumer resumes from offset 3.
```

## 6. The .txn Index File — Skipping Aborted Records

LSO handles open transactions, but what about records that belong to an already-aborted transaction? The broker maintains a separate index file (`.txn` / transaction index) for this.

```
Partition log:

  off 0: PID=5, txnal=true   [data]  ─┐ T1 — COMMITTED
  off 1: PID=5, txnal=true   [data]   │
  off 2: PID=5, ctrl=true    COMMIT  ─┘

  off 3: PID=8, txnal=true   [data]  ─┐ T2 — ABORTED
  off 4: PID=8, ctrl=true    ABORT   ─┘

  off 5: PID=9, txnal=true   [data]  ─┐ T3 — COMMITTED
  off 6: PID=9, ctrl=true    COMMIT  ─┘

.txn index file (maintained by broker, one per partition log segment):

  ┌──────────────────────────────────────────────────────────────────┐
  │  AbortedTransactionEntry:                                        │
  │    producer_id   = 8                                             │
  │    epoch         = 1                                             │
  │    first_offset  = 3   ← where the aborted transaction starts   │
  │    last_offset   = 4   ← offset of the ABORT control record     │
  └──────────────────────────────────────────────────────────────────┘

  Broker sends this abort index to the consumer along with the fetch response.

Consumer checks each record against the abort index:

  off 0: PID=5  →  not in abort index  → READ ✓
  off 1: PID=5  →  not in abort index  → READ ✓
  off 3: PID=8  →  PID=8 matches, offset 3 is inside [3..4]  → SKIP ✗
  off 5: PID=9  →  not in abort index  → READ ✓

  Note: control records (off 2, 4, 6) are never sent by the broker.
```

## 7. Full Consumer Read — Combined LSO + Abort Index

A complete walkthrough showing how `read_committed` uses both LSO and the abort index together.

```
Partition log (no open transactions, LSO = 9):

  off 0: PID=5,  txnal=true              [data-A]   T1 COMMITTED
  off 1: PID=5,  txnal=true              [data-B]   T1 COMMITTED
  off 2: PID=5,  ctrl=true   COMMIT                 (filtered by broker)
  off 3: PID=8,  txnal=true              [data-C]   T2 ABORTED
  off 4: PID=8,  ctrl=true   ABORT                  (filtered by broker)
  off 5: PID=8,  txnal=true              [data-D]   T4 COMMITTED  (same producer, new txn)
  off 6: PID=9,  txnal=true              [data-E]   T3 COMMITTED
  off 7: PID=9,  ctrl=true   COMMIT                 (filtered by broker)
  off 8: PID=8,  ctrl=true   COMMIT                 (filtered by broker)

  .txn abort index: { PID=8, epoch=1, first_offset=3, last_offset=4 }
  LSO = 9  (all transactions closed)

Broker delivers to consumer (after filtering control records):
  off 0, off 1, off 3, off 5, off 6  + abort index

Consumer applies read_committed logic:

  off 0: 0 < 9 ✓  |  PID=5 not aborted  →  DELIVER  ✓
  off 1: 1 < 9 ✓  |  PID=5 not aborted  →  DELIVER  ✓
  off 3: 3 < 9 ✓  |  PID=8, offset 3 inside [3..4]  →  SKIP    ✗
  off 5: 5 < 9 ✓  |  PID=8, offset 5 outside [3..4] →  DELIVER ✓
  off 6: 6 < 9 ✓  |  PID=9 not aborted  →  DELIVER  ✓

  Consumer delivers: off 0, off 1, off 5, off 6
  Consumer skips:    off 3 (aborted)
```

## 8. EOS — Exactly-Once Semantics (Read-Process-Write)

EOS solves the read-process-write duplicate problem. The fix is to tie the downstream publish and the offset commit into one atomic transaction so they always succeed or fail together.

```
THE PROBLEM:

  Consumer reads offset 50 → processes → publishes to output-topic → commit offset
                                                                            │
                                                                      commit LOST
                                                                            │
  Consumer polls again → gets offset 50 again → processes AGAIN → publishes AGAIN
  ✗ duplicate in output-topic

THE FIX — tie write + offset commit into one transaction:

  Consumer                   Kafka (as both consumer and producer)
       │
       │  read record (offset 50)
       │──────────────────────────────────────────────────────►
       │◄────────────────────────────────────────────────────── record delivered
       │
       │  [optional: process / transform]
       │
       │  beginTransaction()                                   (producer role)
       │
       │  send(output-topic, result).join()  ──────────────────► output-topic broker
       │◄────────────────────────────────────────────────────── ACK
       │
       │  sendOffsetsToTransaction(                            ← buffers offset, does NOT commit yet
       │      {input-topic/P0, offset=51},                      offset commit is part of the transaction
       │      consumerGroupId
       │  )
       │
       │  commitTransaction()  ──────────────────────────────► PREPARE_COMMIT written
       │                        ─────────────────────────────► COMMIT control record → output-topic
       │                        ─────────────────────────────► offset 51 committed to __consumer_offsets
       │◄─────────────────────────────────────────────────────── success
       │
  If any step fails → abortTransaction() → output-topic write is rolled back
                                         → offset is NOT committed → replay from offset 50

Required properties for EOS on a consumer that also produces:

  consumer:
    isolation.level        = read_committed
    enable.auto.commit     = false      ← manual offset management via transaction

  producer (same app, since it publishes output):
    transaction-id-prefix  = some-stable-prefix
    (idempotency and acks=all are enabled automatically with transactions)
```

## 9. High Watermark vs LSO — Side by Side

```
  ┌─────────────────────────────────────────────────────────────────────────┐
  │  PARTITION LOG                                                          │
  │                                                                         │
  │  off 0  [data]                                    ─┐                   │
  │  off 1  [data]                                     │  all replicated   │
  │  off 2  [data - committed txn]                     │  HW = 6           │
  │  off 3  [data - open txn start]  ← LSO = 3         │                   │
  │  off 4  [data - open txn]                          │                   │
  │  off 5  [data - committed txn]                    ─┘                   │
  │  off 6  (next empty slot)                                               │
  │                                                                         │
  │  HW  (High Watermark) = 6   ← all replicas have offsets 0..5           │
  │  LSO (Last Stable Offset) = 3   ← first record of an open transaction  │
  │                                                                         │
  │  read_uncommitted consumer reads up to: HW  → sees off 0,1,2,3,4,5    │
  │  read_committed   consumer reads up to: LSO → sees off 0,1,2 then WAIT │
  └─────────────────────────────────────────────────────────────────────────┘

  LSO is always ≤ HW.
  When there are no open transactions, LSO = HW (consumer reads everything).
```

## 10. Quick Reference

```
Concept                  What it is                                    Key point
───────────────────────  ────────────────────────────────────────────  ─────────────────────────────────────────
Control record           COMMIT or ABORT marker appended to log        is_control=true; broker never delivers it
read_uncommitted         Default isolation level                        Reads all records (open, committed, aborted)
read_committed           Safe isolation level                           Reads only committed + non-transactional
LSO                      Last Stable Offset                             Pointer to the first open-transaction record
HW                       High Watermark                                 Latest fully-replicated offset
LSO vs HW                LSO ≤ HW                                       read_committed stops at LSO; read_uncommitted goes to HW
.txn index               Per-segment abort index file on broker        Tells consumer which offset ranges to skip
AbortedTransactionEntry  Entry in .txn index                           {PID, first_offset, last_offset (ctrl record)}
Open transaction         Transaction begun, not yet committed/aborted  Consumer waits; does not skip ahead
EOS                      Exactly-Once Semantics                         No duplicates in read-process-write pattern
sendOffsetsToTransaction Ties offset commit into the producer txn      Offset only committed when transaction commits
enable.auto.commit=false Required for EOS                              Offset must be committed inside the transaction

EOS requirements (consumer that also publishes):
  consumer side → isolation.level=read_committed + enable.auto.commit=false
  producer side → transaction-id-prefix set (idempotency + acks=all auto-enabled)

How aborted records are skipped:
  1. Broker builds .txn index when an ABORT control record is written
  2. Broker sends abort index to consumer in the fetch response
  3. Consumer checks each record's (PID, offset) against the index
  4. If offset falls inside an aborted range → skip; otherwise → deliver

How open transactions are skipped:
  1. Broker tracks LSO in memory (advances when open transactions close)
  2. Consumer with read_committed only reads offsets < LSO
  3. Consumer stops and waits until LSO advances (i.e., open txn closes)
```
