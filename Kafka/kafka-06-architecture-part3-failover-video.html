What Happens When the Active Controller Fails?

The standby controllers are always watching for heartbeats from the active controller. When heartbeats stop, they immediately start a new election using the KRaft (Raft) consensus algorithm.

Initial state: ┌──────────────────────────────────────────────────────────┐ │ Controller 1 (ACTIVE) ── sends heartbeats ──► │ │ Controller 2 (standby) ◄── receiving heartbeats │ │ Controller 3 (standby) ◄── receiving heartbeats │ └──────────────────────────────────────────────────────────┘ Controller 1 crashes: ┌──────────────────────────────────────────────────────────┐ │ Controller 1 ✗ (crashed — no more heartbeats) │ │ Controller 2 ── "no heartbeat from C1... election!" │ │ Controller 3 ── "no heartbeat from C1... election!" │ └──────────────────────────────────────────────────────────┘ Election via KRaft (Raft voting): ───────────────────────────────────────────────────────── Controller 2 requests votes Controller 3 votes for Controller 2 ✓ Controller 2 votes for itself ✓ Result: Controller 2 gets 2/2 available votes → wins New state: ┌──────────────────────────────────────────────────────────┐ │ Controller 1 ✗ (still crashed) │ │ Controller 2 (NEW ACTIVE) ← took over seamlessly │ │ Controller 3 (standby) │ └──────────────────────────────────────────────────────────┘ Impact: NONE — cluster continues working without interruption. Topic creation, broker monitoring, leader election all continue.

What Happens When a Leader Partition Fails?

If the broker holding a partition leader crashes, the controller detects it (missed heartbeat), selects a new leader from the ISR, and updates all brokers.

Initial state (partition 0, replication factor 3): ┌────────────────┐ ┌────────────────┐ ┌────────────────┐ │ Broker 1 │ │ Broker 2 │ │ Broker 3 │ │ P0 LEADER ★ │ │ P0 follower │ │ P0 follower │ └────────────────┘ └────────────────┘ └────────────────┘ ISR for P0 = [Broker 1, Broker 2, Broker 3] Broker 1 crashes: ┌────────────────┐ ┌────────────────┐ ┌────────────────┐ │ Broker 1 ✗ │ │ Broker 2 │ │ Broker 3 │ │ (no heartbeat)│ │ P0 follower │ │ P0 follower │ └────────────────┘ └────────────────┘ └────────────────┘ Controller detects: no heartbeat from Broker 1 │ ▼ Controller picks new leader from ISR (picks Broker 2) │ ▼ Controller updates cluster metadata: P0 leader → Broker 2 (was Broker 1) ISR for P0 → [Broker 2, Broker 3] (Broker 1 removed) │ ▼ Controller pushes updated metadata to all brokers New state: ┌────────────────┐ ┌────────────────┐ ┌────────────────┐ │ Broker 1 ✗ │ │ Broker 2 │ │ Broker 3 │ │ (crashed) │ │ P0 LEADER ★ │ │ P0 follower │ └────────────────┘ └────────────────┘ └────────────────┘ Impact: Producers and consumers reconnect to Broker 2 for P0. No data loss. Automatic recovery. ✓

What Happens When a Follower Partition Fails?

A follower failure is less dramatic — the leader simply notices the follower has stopped sending fetch requests and removes it from the ISR. The cluster keeps running normally.

Initial state (partition 0, replication factor 3): ┌────────────────┐ ┌────────────────┐ ┌────────────────┐ │ Broker 1 │ │ Broker 2 │ │ Broker 3 │ │ P0 LEADER ★ │◄──│ P0 follower │ │ P0 follower │ │ offset: 15 │ │ polls leader │◄───│ polls leader │ └────────────────┘ └────────────────┘ └────────────────┘ ISR for P0 = [Broker 1, Broker 2, Broker 3] Broker 3 crashes — stops sending fetch requests to leader: ┌────────────────┐ ┌────────────────┐ ┌────────────────┐ │ Broker 1 │ │ Broker 2 │ │ Broker 3 ✗ │ │ P0 LEADER ★ │◄──│ P0 follower │ │ (no fetch │ │ "no fetch from│ │ polls leader │ │ requests) │ │ Broker 3" │ │ │ │ │ └────────────────┘ └────────────────┘ └────────────────┘ Leader Broker 1 detects: Broker 3 has not sent a fetch request within replica.lag.time.max.ms (default ~30 seconds) │ ▼ Leader removes Broker 3 from ISR Notifies controller → controller updates metadata ISR for P0 = [Broker 1, Broker 2] ← Broker 3 removed Writes continue with acks=all using the remaining ISR ✓ When Broker 3 recovers: Broker 3 restarts → resumes polling leader → catches up Leader: "Broker 3 is fetching again and is caught up" Leader adds Broker 3 back to ISR → notifies controller ✓ Impact: System continues normally. No data loss. ✓

Can a Topic Fail?

A topic is just a logical category — a name and a folder. It has no hardware to fail. What actually fails are partitions (and the brokers that hold them).

What a topic actually IS: ┌─────────────────────────────────────────────────────────────┐ │ Topic "order-events" │ │ = just a name / label │ │ = a logical container │ │ │ │ Its PARTITIONS are the physical things that can fail: │ │ │ │ Partition 0 → stored on Broker 1 (leader) + Broker 2 │ │ Partition 1 → stored on Broker 2 (leader) + Broker 3 │ │ Partition 2 → stored on Broker 3 (leader) + Broker 1 │ └─────────────────────────────────────────────────────────────┘ "Topic fails" → WRONG framing. Partitions fail. "Partition 0 leader fails" → CORRECT framing. What can actually fail: ┌───────────────────────┬──────────────────────────────────────┐ │ Component │ Can it fail? │ ├───────────────────────┼──────────────────────────────────────┤ │ Topic │ ✗ No — it is just a name │ │ Partition leader │ ✓ Yes — broker can crash │ │ Partition follower │ ✓ Yes — broker can crash │ │ Broker │ ✓ Yes — machine can go down │ │ Active controller │ ✓ Yes — but standby takes over │ └───────────────────────┴──────────────────────────────────────┘

Consumer Crash Before Committing Offset

If a consumer crashes mid-processing before it commits the offset, the next consumer to pick up that partition will re-read and re-process those events.

Consumer 1 — assigned order-events partition 0 Step 1: Fetches events 100–199 Step 2: Processes event 100... 101... 102... 150... Step 3: CRASH at event 150 — offset never committed Last committed offset in __consumer_offsets: 99 Consumer 1 restarts: ───────────────────────────────────────────────────────── Consumer 1 asks group coordinator: "What is my last committed offset for order-events P0?" Group coordinator: "99" Consumer 1: starts fetching from 100 again ┌─────────────────────────────────────────────────────────┐ │ Events 100–149 are processed TWICE │ │ This is called "at-least-once" delivery │ │ │ │ Your application must handle duplicate events │ │ (make processing idempotent — same result if run twice)│ └─────────────────────────────────────────────────────────┘ Timeline: ────────────────────────────────────────────────────────── fetch 100–199 → process 100–150 → CRASH [restart] fetch 100–199 → process 100–199 → commit 199 ✓

Consumer Heartbeat Timeout (max.poll.interval.ms)

If a consumer is so busy processing that it forgets to heartbeat the group coordinator, the coordinator assumes it is dead, reassigns its partition, and later rejects its commit.

Config: max.poll.interval.ms = 300000 (5 minutes) Meaning: group coordinator expects a heartbeat at least every 5 minutes Consumer 1 — assigned order-events partition 0 ───────────────────────────────────────────────────────── t=0:00 Consumer 1 fetches events 1–500 → starts processing t=4:00 Consumer 1 still processing (long-running task) t=5:00 ← max.poll.interval.ms exceeded — no heartbeat sent Group coordinator: "Consumer 1 is dead" Group coordinator: reassigns partition 0 to Consumer 2 t=5:30 Consumer 2 starts processing partition 0 from last offset t=6:00 Consumer 1 finally finishes processing events 1–500 Consumer 1 tries to commit offset 500 to group coordinator Group coordinator: REJECTED ✗ "You are no longer part of this group" ┌─────────────────────────────────────────────────────────┐ │ Result: events 1–500 get processed TWICE │ │ Consumer 1 and Consumer 2 both processed them │ │ │ │ Fix options: │ │ ─ Increase max.poll.interval.ms for slow processors │ │ ─ Reduce records fetched per poll (max.poll.records) │ │ ─ Make processing faster │ └─────────────────────────────────────────────────────────┘ Full timeline: ────────────────────────────────────────────────────────── Consumer 1: fetch → [long processing] → commit REJECTED ✗ └─► re-joins group → gets new partition assigned Consumer 2: [reassigned] → fetch from last offset → processes again

What Happens When a Broker Fails?

A broker failure combines both leader partition failure and follower partition failure — the controller handles everything automatically.

Setup: 3 brokers, topic with 6 partitions, replication factor 3 ┌──────────────────────────────────────────────────────────────┐ │ Broker 1 │ Broker 2 │ Broker 3 │ │ P0 leader ★ │ P1 leader ★ │ P2 leader ★ │ │ P1 follower │ P2 follower │ P0 follower │ │ P2 follower │ P0 follower │ P1 follower │ └──────────────────────────────────────────────────────────────┘ Broker 1 crashes: ───────────────────────────────────────────────────────────────── Who detects it? The ACTIVE CONTROLLER How? Broker 1 stops sending heartbeats to controller. Controller's response (two actions in parallel): ACTION 1: For each partition where Broker 1 WAS the leader: ────────────────────────────────────────────────────────── P0 leader was Broker 1 → pick new leader from ISR ISR had [B1, B2, B3] → B1 down → pick B2 P0 new leader = Broker 2 ACTION 2: For each partition where Broker 1 WAS a follower: ────────────────────────────────────────────────────────── P1: ISR was [B1, B2, B3] → remove B1 → ISR = [B2, B3] P2: ISR was [B1, B2, B3] → remove B1 → ISR = [B2, B3] Controller updates cluster metadata and pushes to all brokers. New state after recovery: ┌──────────────────────────────────────────────────────────────┐ │ Broker 1 ✗ │ Broker 2 │ Broker 3 │ │ (crashed) │ P0 leader ★ (new) │ P2 leader ★ │ │ │ P1 leader ★ │ P1 follower │ │ │ P2 follower │ P0 follower │ └──────────────────────────────────────────────────────────────┘ Impact: No data loss. Automatic recovery. Producers and consumers reconnect to new leaders transparently. ✓

At-Least-Once Delivery and Idempotency

Because consumers can re-process events after a crash or timeout, Kafka guarantees at-least-once delivery by default — every event is processed at least once, but possibly more.

Delivery guarantees in Kafka: ───────────────────────────────────────────────────────────────── at-most-once: event may be lost, never processed twice (commit before processing — risky) at-least-once: event processed at least once, possibly twice ← Kafka default (commit after processing — safe but duplicates possible) exactly-once: every event processed exactly once (requires Kafka transactions — more complex) ───────────────────────────────────────────────────────────────── at-least-once example (Kafka default behavior): Fetch events 100–199 │ ▼ Process events 100–199 │ ▼ CRASH before commit OR Heartbeat timeout │ │ ▼ ▼ Re-read from 100 again Another consumer reads from 100 HOW TO HANDLE DUPLICATES: ┌─────────────────────────────────────────────────────────────┐ │ Make your processing IDEMPOTENT │ │ = running the same event twice produces the same result │ │ │ │ Example: "set user balance to $50" ← idempotent ✓ │ │ Example: "add $10 to user balance" ← NOT idempotent ✗ │ │ (running twice adds $20 total) │ └─────────────────────────────────────────────────────────────┘

Architecture — Where Each Failure Actually Bites

"Failures aren't abstract in production — each one maps to a specific customer-visible symptom. Let me connect the dots for the Notification System."

Broker crash (holds P7 leader for notifications.critical.sms) │ ▼ Controller elects new leader from ISR — seconds of blip Producer/consumer refresh metadata, resume ─────► OTP still lands <10s ✓ Consumer crash (email-workers, mid-batch of 500) │ ▼ Group coordinator reassigns partitions after max.poll.interval.ms New consumer re-reads from last COMMITTED offset ─► possible duplicate emails UNLESS delivery_status idempotency check catches it

Scenario-first: "Broker failures are largely invisible to the business — Kafka's replication absorbs them. Consumer failures are NOT invisible — they're the actual source of the duplicate-delivery risk that idempotent consumers exist to solve."

Scenario-first: "This is precisely why idempotency isn't optional — it's the literal failure mode, not a theoretical edge case, every time a slow consumer gets fenced mid-batch."

Cross Questions Interviewers Ask

Q: Why doesn't a follower partition crash affect availability at all? A: The leader keeps serving reads/writes uninterrupted; the follower simply re-joins and catches up via replication once it recovers — it was never in the critical path for live traffic. Q: Why can two consumers briefly BOTH think they own partition 5 during a rebalance? A: A "zombie" consumer (still alive but presumed dead due to a missed heartbeat) may keep processing after being fenced out — it just can't successfully commit anymore. Idempotent processing, not the fencing mechanism alone, is the real safety net. Q: Why does raising max.poll.interval.ms "fix" spurious rebalances but isn't a free lunch? A: It gives slow batches more room before being presumed dead, but it also means a TRULY dead consumer takes longer to be detected and its partitions reassigned — a direct trade between false-positive rebalances and recovery speed on real failures.

Senior Trap Questions (15 YOE)

Trap 1 — "Two consumers in the SAME group are somehow both processing messages from partition 5. How is that possible if Kafka enforces 1:1?" Answer: "A zombie consumer — fenced out by the coordinator but still alive and mid-processing (stuck in GC or a slow network call). It doesn't know it's been fenced until its next commit attempt is rejected. This is exactly why idempotent processing at the business layer, not just Kafka's 1-consumer-per-partition rule, is the actual safety net." Trap 2 — "Your consumer lag graph shows a slow, steady climb over 3 days, not a spike. First hypothesis?" Answer: "A sustained processing-rate deficit, not a transient failure — either incoming volume genuinely grew, or per-record latency crept up (a downstream API like SendGrid getting slower). I wouldn't reflexively add consumers if the bottleneck is a shared rate-limited dependency — more consumers just wait on the same token bucket."

WHY We Chose Each Decision

- Why replication (RF=3) at all: broker and follower failures become invisible non-events instead of outages. - Why idempotent consumers regardless of failure type: at-least-once delivery guarantees mean SOME duplication is structurally possible — the fix belongs at the consumer, not by trying to eliminate every possible rebalance. - Why size max.poll.interval.ms to realistic worst-case batch time: avoids the false-positive-rebalance-causes-duplicates spiral. - Why controller-driven (not consumer-driven) failure detection for brokers: centralizes the "who's alive" decision so brokers, producers, and consumers all agree on the same view of cluster health.

Top 2 Technologies — Consumer Rebalance Protocol

Eager Rebalancing (legacy default) vs Cooperative Sticky Assignor Why pick Cooperative Sticky (our choice): only reassigns the SPECIFIC partitions that changed — unaffected consumers keep processing throughout the rebalance, dramatically shrinking the "stop the world" window. Why pick Eager: simpler mental model, fine for small consumer groups where a brief full-group pause has negligible business impact. Example 1 (Cooperative Sticky): Notification System's 20-instance email-workers group — a single instance restarting shouldn't pause the other 19 mid-processing. Example 2 (Eager, acceptable): A 2-consumer internal batch-analytics group processing hourly, where a few extra seconds of pause during rebalance is imperceptible to any downstream consumer.
