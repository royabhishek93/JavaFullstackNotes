Topics: Active Controller Failure, Leader Partition Failure, Follower Partition Failure, Topics Cannot Fail, Consumer Crash, Consumer Heartbeat Timeout, Broker Failure

## 1. What Happens When the Active Controller Fails?

The standby controllers are always watching for heartbeats from the active controller. When heartbeats stop, they immediately start a new election using the KRaft (Raft) consensus algorithm.

```
  Initial state:
  ┌──────────────────────────────────────────────────────────┐
  │  Controller 1  (ACTIVE)  ── sends heartbeats ──►         │
  │  Controller 2  (standby) ◄── receiving heartbeats        │
  │  Controller 3  (standby) ◄── receiving heartbeats        │
  └──────────────────────────────────────────────────────────┘

  Controller 1 crashes:
  ┌──────────────────────────────────────────────────────────┐
  │  Controller 1  ✗  (crashed — no more heartbeats)         │
  │  Controller 2  ── "no heartbeat from C1... election!"   │
  │  Controller 3  ── "no heartbeat from C1... election!"   │
  └──────────────────────────────────────────────────────────┘

  Election via KRaft (Raft voting):
  ─────────────────────────────────────────────────────────
  Controller 2 requests votes
  Controller 3 votes for Controller 2  ✓
  Controller 2 votes for itself         ✓
  Result: Controller 2 gets 2/2 available votes → wins

  New state:
  ┌──────────────────────────────────────────────────────────┐
  │  Controller 1  ✗  (still crashed)                        │
  │  Controller 2  (NEW ACTIVE) ← took over seamlessly       │
  │  Controller 3  (standby)                                 │
  └──────────────────────────────────────────────────────────┘

  Impact: NONE — cluster continues working without interruption.
  Topic creation, broker monitoring, leader election all continue.
```

## 2. What Happens When a Leader Partition Fails?

If the broker holding a partition leader crashes, the controller detects it (missed heartbeat), selects a new leader from the ISR, and updates all brokers.

```
  Initial state (partition 0, replication factor 3):
  ┌────────────────┐    ┌────────────────┐    ┌────────────────┐
  │   Broker 1     │    │   Broker 2     │    │   Broker 3     │
  │  P0 LEADER ★  │    │  P0 follower   │    │  P0 follower   │
  └────────────────┘    └────────────────┘    └────────────────┘

  ISR for P0 = [Broker 1, Broker 2, Broker 3]

  Broker 1 crashes:
  ┌────────────────┐    ┌────────────────┐    ┌────────────────┐
  │   Broker 1  ✗  │    │   Broker 2     │    │   Broker 3     │
  │  (no heartbeat)│    │  P0 follower   │    │  P0 follower   │
  └────────────────┘    └────────────────┘    └────────────────┘

  Controller detects: no heartbeat from Broker 1
         │
         ▼
  Controller picks new leader from ISR (picks Broker 2)
         │
         ▼
  Controller updates cluster metadata:
    P0 leader  → Broker 2  (was Broker 1)
    ISR for P0 → [Broker 2, Broker 3]  (Broker 1 removed)
         │
         ▼
  Controller pushes updated metadata to all brokers

  New state:
  ┌────────────────┐    ┌────────────────┐    ┌────────────────┐
  │   Broker 1  ✗  │    │   Broker 2     │    │   Broker 3     │
  │  (crashed)     │    │  P0 LEADER ★  │    │  P0 follower   │
  └────────────────┘    └────────────────┘    └────────────────┘

  Impact: Producers and consumers reconnect to Broker 2 for P0.
  No data loss. Automatic recovery. ✓
```

## 3. What Happens When a Follower Partition Fails?

A follower failure is less dramatic — the leader simply notices the follower has stopped sending fetch requests and removes it from the ISR. The cluster keeps running normally.

```
  Initial state (partition 0, replication factor 3):
  ┌────────────────┐    ┌────────────────┐    ┌────────────────┐
  │   Broker 1     │    │   Broker 2     │    │   Broker 3     │
  │  P0 LEADER ★  │◄──│  P0 follower   │    │  P0 follower   │
  │  offset: 15    │    │  polls leader  │◄───│  polls leader  │
  └────────────────┘    └────────────────┘    └────────────────┘

  ISR for P0 = [Broker 1, Broker 2, Broker 3]

  Broker 3 crashes — stops sending fetch requests to leader:
  ┌────────────────┐    ┌────────────────┐    ┌────────────────┐
  │   Broker 1     │    │   Broker 2     │    │   Broker 3  ✗  │
  │  P0 LEADER ★  │◄──│  P0 follower   │    │  (no fetch     │
  │  "no fetch from│    │  polls leader  │    │   requests)    │
  │   Broker 3"   │    │                │    │                │
  └────────────────┘    └────────────────┘    └────────────────┘

  Leader Broker 1 detects: Broker 3 has not sent a fetch request
  within replica.lag.time.max.ms (default ~30 seconds)
         │
         ▼
  Leader removes Broker 3 from ISR
  Notifies controller → controller updates metadata

  ISR for P0 = [Broker 1, Broker 2]  ← Broker 3 removed

  Writes continue with acks=all using the remaining ISR ✓

  When Broker 3 recovers:
  Broker 3 restarts → resumes polling leader → catches up
  Leader: "Broker 3 is fetching again and is caught up"
  Leader adds Broker 3 back to ISR → notifies controller ✓

  Impact: System continues normally. No data loss. ✓
```

## 4. Can a Topic Fail?

A topic is just a logical category — a name and a folder. It has no hardware to fail. What actually fails are partitions (and the brokers that hold them).

```
  What a topic actually IS:
  ┌─────────────────────────────────────────────────────────────┐
  │  Topic "order-events"                                       │
  │  = just a name / label                                      │
  │  = a logical container                                      │
  │                                                             │
  │  Its PARTITIONS are the physical things that can fail:      │
  │                                                             │
  │  Partition 0 → stored on Broker 1 (leader) + Broker 2      │
  │  Partition 1 → stored on Broker 2 (leader) + Broker 3      │
  │  Partition 2 → stored on Broker 3 (leader) + Broker 1      │
  └─────────────────────────────────────────────────────────────┘

  "Topic fails" → WRONG framing. Partitions fail.
  "Partition 0 leader fails" → CORRECT framing.

  What can actually fail:
  ┌───────────────────────┬──────────────────────────────────────┐
  │  Component            │  Can it fail?                        │
  ├───────────────────────┼──────────────────────────────────────┤
  │  Topic                │  ✗  No — it is just a name           │
  │  Partition leader     │  ✓  Yes — broker can crash           │
  │  Partition follower   │  ✓  Yes — broker can crash           │
  │  Broker               │  ✓  Yes — machine can go down        │
  │  Active controller    │  ✓  Yes — but standby takes over     │
  └───────────────────────┴──────────────────────────────────────┘
```

## 5. Consumer Crash Before Committing Offset

If a consumer crashes mid-processing before it commits the offset, the next consumer to pick up that partition will re-read and re-process those events.

```
  Consumer 1 — assigned order-events partition 0

  Step 1: Fetches events 100–199
  Step 2: Processes event 100... 101... 102... 150...
  Step 3: CRASH at event 150 — offset never committed
          Last committed offset in __consumer_offsets: 99

  Consumer 1 restarts:
  ─────────────────────────────────────────────────────────
  Consumer 1 asks group coordinator:
    "What is my last committed offset for order-events P0?"
  Group coordinator: "99"
  Consumer 1: starts fetching from 100 again

  ┌─────────────────────────────────────────────────────────┐
  │  Events 100–149 are processed TWICE                     │
  │  This is called "at-least-once" delivery                │
  │                                                         │
  │  Your application must handle duplicate events          │
  │  (make processing idempotent — same result if run twice)│
  └─────────────────────────────────────────────────────────┘

  Timeline:
  ──────────────────────────────────────────────────────────
  fetch 100–199 → process 100–150 → CRASH
  [restart]
  fetch 100–199 → process 100–199 → commit 199 ✓
```

## 6. Consumer Heartbeat Timeout (max.poll.interval.ms)

If a consumer is so busy processing that it forgets to heartbeat the group coordinator, the coordinator assumes it is dead, reassigns its partition, and later rejects its commit.

```
  Config: max.poll.interval.ms = 300000  (5 minutes)
  Meaning: group coordinator expects a heartbeat at least every 5 minutes

  Consumer 1 — assigned order-events partition 0
  ─────────────────────────────────────────────────────────
  t=0:00  Consumer 1 fetches events 1–500 → starts processing
  t=4:00  Consumer 1 still processing (long-running task)
  t=5:00  ← max.poll.interval.ms exceeded — no heartbeat sent
          Group coordinator: "Consumer 1 is dead"
          Group coordinator: reassigns partition 0 to Consumer 2

  t=5:30  Consumer 2 starts processing partition 0 from last offset

  t=6:00  Consumer 1 finally finishes processing events 1–500
          Consumer 1 tries to commit offset 500 to group coordinator

          Group coordinator: REJECTED ✗
          "You are no longer part of this group"

  ┌─────────────────────────────────────────────────────────┐
  │  Result: events 1–500 get processed TWICE               │
  │  Consumer 1 and Consumer 2 both processed them          │
  │                                                         │
  │  Fix options:                                           │
  │  ─ Increase max.poll.interval.ms for slow processors    │
  │  ─ Reduce records fetched per poll (max.poll.records)   │
  │  ─ Make processing faster                               │
  └─────────────────────────────────────────────────────────┘

  Full timeline:
  ──────────────────────────────────────────────────────────
  Consumer 1: fetch → [long processing] → commit REJECTED ✗
                                          └─► re-joins group → gets new partition assigned
  Consumer 2:         [reassigned] → fetch from last offset → processes again
```

## 7. What Happens When a Broker Fails?

A broker failure combines both leader partition failure and follower partition failure — the controller handles everything automatically.

```
  Setup: 3 brokers, topic with 6 partitions, replication factor 3

  ┌──────────────────────────────────────────────────────────────┐
  │  Broker 1    │  Broker 2    │  Broker 3                      │
  │  P0 leader ★ │  P1 leader ★ │  P2 leader ★                  │
  │  P1 follower │  P2 follower │  P0 follower                   │
  │  P2 follower │  P0 follower │  P1 follower                   │
  └──────────────────────────────────────────────────────────────┘

  Broker 1 crashes:
  ─────────────────────────────────────────────────────────────────
  Who detects it?  The ACTIVE CONTROLLER
  How?             Broker 1 stops sending heartbeats to controller.

  Controller's response (two actions in parallel):

  ACTION 1: For each partition where Broker 1 WAS the leader:
  ──────────────────────────────────────────────────────────
  P0 leader was Broker 1 → pick new leader from ISR
    ISR had [B1, B2, B3] → B1 down → pick B2
    P0 new leader = Broker 2

  ACTION 2: For each partition where Broker 1 WAS a follower:
  ──────────────────────────────────────────────────────────
  P1: ISR was [B1, B2, B3] → remove B1 → ISR = [B2, B3]
  P2: ISR was [B1, B2, B3] → remove B1 → ISR = [B2, B3]

  Controller updates cluster metadata and pushes to all brokers.

  New state after recovery:
  ┌──────────────────────────────────────────────────────────────┐
  │  Broker 1 ✗  │  Broker 2          │  Broker 3              │
  │  (crashed)   │  P0 leader ★ (new) │  P2 leader ★           │
  │              │  P1 leader ★       │  P1 follower           │
  │              │  P2 follower       │  P0 follower           │
  └──────────────────────────────────────────────────────────────┘

  Impact: No data loss. Automatic recovery. Producers and consumers
  reconnect to new leaders transparently. ✓
```

## 8. All Failure Scenarios Side by Side

```
  FAILURE SCENARIO SUMMARY
  ──────────────────────────────────────────────────────────────────────
  Failure              Detected by       Recovery mechanism
  ───────────────────  ────────────────  ────────────────────────────────
  Active controller    Standby ctrlrs    KRaft election → new active ctrl
  Leader partition     Controller        New leader elected from ISR
  Follower partition   Partition leader  Leader removes from ISR; adds back when recovered
  Topic                N/A               Topics cannot fail — partitions fail
  Consumer crash       Group coordinator Re-read from last committed offset (at-least-once)
  Consumer heartbeat   Group coordinator Partition reassigned; stale commit rejected
  timeout
  Broker               Controller        Leader partitions: new leader elected
                                         Follower partitions: removed from ISR
  ──────────────────────────────────────────────────────────────────────

  In every case: no manual intervention needed, cluster self-heals.
```

## 9. At-Least-Once Delivery and Idempotency

Because consumers can re-process events after a crash or timeout, Kafka guarantees **at-least-once** delivery by default — every event is processed at least once, but possibly more.

```
  Delivery guarantees in Kafka:
  ─────────────────────────────────────────────────────────────────
  at-most-once:   event may be lost, never processed twice
                  (commit before processing — risky)

  at-least-once:  event processed at least once, possibly twice  ← Kafka default
                  (commit after processing — safe but duplicates possible)

  exactly-once:   every event processed exactly once
                  (requires Kafka transactions — more complex)

  ─────────────────────────────────────────────────────────────────
  at-least-once example (Kafka default behavior):

  Fetch events 100–199
       │
       ▼
  Process events 100–199
       │
       ▼
  CRASH before commit              OR    Heartbeat timeout
       │                                        │
       ▼                                        ▼
  Re-read from 100 again               Another consumer reads from 100

  HOW TO HANDLE DUPLICATES:
  ┌─────────────────────────────────────────────────────────────┐
  │  Make your processing IDEMPOTENT                            │
  │  = running the same event twice produces the same result    │
  │                                                             │
  │  Example: "set user balance to $50"  ← idempotent ✓        │
  │  Example: "add $10 to user balance"  ← NOT idempotent ✗    │
  │           (running twice adds $20 total)                    │
  └─────────────────────────────────────────────────────────────┘
```
