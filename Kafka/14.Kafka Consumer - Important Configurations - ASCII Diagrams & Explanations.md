Topics: auto.offset.reset, fetch.min.bytes, fetch.max.wait.ms, max.partition.fetch.bytes, fetch.max.bytes, max.poll.records, heartbeat.interval.ms, session.timeout.ms, max.poll.interval.ms, Partition Assignment Strategies, Offset Commit Modes

## 1. auto.offset.reset — Where to Start Reading

When a consumer joins a group for the first time and there is **no committed offset** for its partition, this setting decides where it begins reading.

```
  New consumer joins. No offset stored in __consumer_offsets yet.
  Group coordinator asks: "Where should this consumer start?"

  ┌──────────────────────────────────────────────────────────────────┐
  │  Partition P0 already has 500 messages (offsets 0 → 499)         │
  │                                                                  │
  │  ◄─── earliest ────────────────────────────── latest ───►        │
  │       offset 0                                offset 499         │
  │         │                                        │               │
  │         ▼                                        ▼               │
  │  ┌─────────────────┐                  ┌───────────────────────┐  │
  │  │  earliest       │                  │  latest (default)     │  │
  │  │  Read ALL 500   │                  │  Read only NEW msgs   │  │
  │  │  existing msgs  │                  │  after joining        │  │
  │  └─────────────────┘                  └───────────────────────┘  │
  │                                                                  │
  │  ┌─────────────────────────────────────────────────────────────┐ │
  │  │  none                                                       │ │
  │  │  Throw exception — force the developer to decide manually   │ │
  │  └─────────────────────────────────────────────────────────────┘ │
  └──────────────────────────────────────────────────────────────────┘

  Decision tree:
  ┌───────────────────────────────────────────────────────────┐
  │  Do I need to process all existing history?               │
  │         │ YES                        │ NO                 │
  │         ▼                            ▼                    │
  │     earliest                      latest                  │
  │                                                           │
  │  Do I want an error if offset is missing?                 │
  │         │ YES                                             │
  │         ▼                                                 │
  │       none                                                │
  └───────────────────────────────────────────────────────────┘

  spring.kafka.consumer.auto-offset-reset=earliest   # or latest / none
```

## 2. fetch.min.bytes and fetch.max.wait.ms — Controlling Response Timing

Instead of responding immediately with just one record, the broker can **wait** until it has gathered a minimum amount of data — reducing network round trips when traffic is low.

```
  Consumer sends fetch request to broker.
  Broker has collected data from the requested partitions.
  Now it decides: should I send the response now or wait for more data?

  ┌──────────────────────────────────────────────────────────────────┐
  │  Broker decision logic (both conditions checked together):       │
  │                                                                  │
  │  Condition 1: data accumulated >= fetch.min.bytes?               │
  │    YES → send response immediately  ✓                            │
  │    NO  → wait...                                                 │
  │                                     ▼                            │
  │  Condition 2: waited >= fetch.max.wait.ms?                       │
  │    YES → send whatever is available (even if < min bytes)  ✓     │
  │    NO  → keep waiting...                                         │
  └──────────────────────────────────────────────────────────────────┘

  HIGH TRAFFIC:
  ────────────────────────────────────────────────────────────────────
  fetch request ──► broker fills min.bytes quickly ──► responds fast ✓

  LOW TRAFFIC (e.g., off-peak hours):
  ────────────────────────────────────────────────────────────────────
  fetch request ──► only a few bytes accumulated
                          │
                          ▼  wait...
                    max.wait.ms timer expires
                          │
                          ▼
                    respond with whatever is available  ✓  (no hang)

  Defaults:
    fetch.min.bytes     = 1       (respond as soon as 1 byte is ready)
    fetch.max.wait.ms   = 500ms   (never wait more than 500ms)

  Tuning tip: increase fetch.min.bytes to reduce calls in low-traffic systems.
```

## 3. max.partition.fetch.bytes and fetch.max.bytes — Capping Data Size

One fetch request can ask for data from **multiple partitions across multiple brokers** — these two settings cap how much data is returned at each level.

```
  Consumer has 3 partitions assigned (2 on broker-1, 1 on broker-2).
  It sends ONE fetch request to each broker.

  ┌──────────────────────────────────────────────────────────────────┐
  │  Consumer                                                        │
  │    │                                                             │
  │    ├──► Broker-1 fetch request:                                  │
  │    │      "give me topic-A/P0, topic-A/P1, topic-B/P1"          │
  │    │                                                             │
  │    └──► Broker-2 fetch request:                                  │
  │           "give me topic-C/P0"                                   │
  └──────────────────────────────────────────────────────────────────┘

  Inside Broker-1:
  ┌──────────────────────────────────────────────────────────────────┐
  │  topic-A / P0  ──► max.partition.fetch.bytes = 1 MB  ← per part │
  │  topic-A / P1  ──► max.partition.fetch.bytes = 1 MB             │
  │  topic-B / P1  ──► max.partition.fetch.bytes = 1 MB             │
  │                                          ┌──────────────────┐    │
  │  Combined response ──────────────────────► fetch.max.bytes  │    │
  │  (sum of all parts)                      │ max = 52 MB      │    │
  │                                          │ (safety ceiling) │    │
  │                                          └──────────────────┘    │
  └──────────────────────────────────────────────────────────────────┘

  ┌──────────────────────────────────────────────────────────┐
  │  max.partition.fetch.bytes  │  per partition limit        │
  │  default: 1 MB              │                             │
  ├──────────────────────────────┼────────────────────────────┤
  │  fetch.max.bytes            │  total broker response cap  │
  │  default: 52 MB             │                             │
  └──────────────────────────────┴────────────────────────────┘
```

## 4. max.poll.records — Processing Batch Size From the Buffer

The broker may return far more records than you want to process at once. `max.poll.records` slices those records out of an **internal buffer** so you work on a manageable batch each poll cycle.

```
  Broker returns 2,000 records (50 MB) in one fetch response.
  Consumer does NOT process all 2,000 at once.

  ┌────────────────────────────────────────────────────────────────┐
  │                Consumer Internal Buffer                        │
  │  ┌──────────────────────────────────────────────────────────┐  │
  │  │  record-0  record-1  record-2  ...  record-1999           │  │
  │  └──────────────────────────────────────────────────────────┘  │
  │         ▲                                                      │
  │         │  max.poll.records = 500                              │
  │         │                                                      │
  │  poll() ──► take 500 records from buffer                       │
  │  process all 500 in @KafkaListener ──► commit offset           │
  │                                                                │
  │  poll() again ──► take next 500 from buffer  (no network call) │
  │  process all 500 in @KafkaListener ──► commit offset           │
  │                                                                │
  │  poll() again ──► take next 500 from buffer  (no network call) │
  │  ... repeat until buffer empty ...                             │
  │                                                                │
  │  poll() again ──► buffer empty → network call to broker        │
  └────────────────────────────────────────────────────────────────┘

  Key point: max.poll.records controls your batch size, not how much
  the broker sends. The broker may send more — extras sit in the buffer.

  spring.kafka.consumer.max-poll-records=500   (default: 500)
```

## 5. heartbeat.interval.ms and session.timeout.ms — Consumer Liveness

The consumer sends a **heartbeat pulse** on a background thread to tell the group coordinator it is still alive. These two settings control how often the pulse is sent and how long the coordinator waits before declaring the consumer dead.

```
  ┌──────────────────────────────────────────────────────────────────────┐
  │  Consumer (background thread)       Group Coordinator (broker)       │
  │                                                                      │
  │  every heartbeat.interval.ms                                         │
  │  ┌────────────────┐                 ┌──────────────────────────────┐ │
  │  │ "I am alive"   │────────────────►│ heartbeat received ✓         │ │
  │  └────────────────┘    3 seconds    │ reset session timer          │ │
  │                                     └──────────────────────────────┘ │
  │  every heartbeat.interval.ms                                         │
  │  ┌────────────────┐                                                  │
  │  │ "I am alive"   │────────────────► ... ✓                           │
  │  └────────────────┘                                                  │
  │                                                                      │
  │  Consumer CRASHES                                                     │
  │  ┌────────────────┐                                                  │
  │  │  (no pulse)    │                 ┌──────────────────────────────┐ │
  │  │  (no pulse)    │                 │ waiting...                   │ │
  │  │  (no pulse)    │                 │ session.timeout.ms = 45s     │ │
  │  │  ...           │                 │ timer expires!               │ │
  │  └────────────────┘                 │ → assume consumer DEAD       │ │
  │                                     │ → trigger rebalance          │ │
  │                                     └──────────────────────────────┘ │
  └──────────────────────────────────────────────────────────────────────┘

  Rule: session.timeout.ms must be GREATER than heartbeat.interval.ms
        so a single missed pulse does not immediately trigger rebalance.

  Typical values:
    heartbeat.interval.ms  =  3,000  ms  (3 seconds)
    session.timeout.ms     = 45,000  ms  (45 seconds)
```

## 6. max.poll.interval.ms — Detecting a Stuck Consumer

A consumer can be **sending heartbeats** (background thread is alive) but **not calling poll()** (main thread is stuck processing). This setting catches that case.

```
  Consumer sends heartbeat every 3s → group coordinator sees: "alive ✓"
  Consumer is stuck in @KafkaListener processing 500 records...

  ┌──────────────────────────────────────────────────────────────────────┐
  │  Time 0:00   poll() called — 500 records fetched                    │
  │  Time 0:03   heartbeat sent ✓  coordinator: "alive"                 │
  │  Time 0:06   heartbeat sent ✓  coordinator: "alive"                 │
  │  Time 0:09   heartbeat sent ✓  coordinator: "alive"                 │
  │  ...                                                                 │
  │  Time 5:00   max.poll.interval.ms expires!                           │
  │              coordinator: "poll not received in 5 minutes"           │
  │              → assume consumer is STUCK                              │
  │              → trigger rebalance                                     │
  │              → partitions reassigned to other consumers              │
  └──────────────────────────────────────────────────────────────────────┘

  heartbeat alone is NOT enough — poll() must also happen regularly.

  ┌────────────────────────────────────────────────────────────────────┐
  │  heartbeat.interval.ms   consumer says: "I am alive"               │
  │  session.timeout.ms      coordinator waits for heartbeat           │
  │  max.poll.interval.ms    coordinator waits for poll() call         │
  └────────────────────────────────────────────────────────────────────┘

  Tip: if your processing is legitimately slow (e.g., DB writes per record),
  increase max.poll.interval.ms or reduce max.poll.records so each batch
  finishes faster.

  spring.kafka.consumer.properties.max.poll.interval.ms=300000  (5 min default)
```

## 7. Partition Assignment Strategies

When consumers join a group, the group coordinator runs an assignment algorithm to divide topic partitions among them. The algorithm you pick affects both initial assignment and how rebalance behaves.

```
  Setup: 3 consumers (C1, C2, C3), 6 partitions (P0–P5)

  RANGE ASSIGNER  (default)
  ────────────────────────────────────────────────────────────────────
  Sort consumers alphabetically, sort partitions numerically.
  Divide: 6 partitions ÷ 3 consumers = 2 each.
  C1: P0, P1    C2: P2, P3    C3: P4, P5


  ROUND ROBIN ASSIGNER
  ────────────────────────────────────────────────────────────────────
  Distribute one partition at a time in a circle.
  C1: P0, P3    C2: P1, P4    C3: P2, P5


  STICKY ASSIGNER
  ────────────────────────────────────────────────────────────────────
  Starts like round robin. Main advantage: smarter rebalance.

  C3 crashes → need to rebalance.

  Range/Round Robin (eager):         Sticky:
  ┌─────────────────────────────┐    ┌─────────────────────────────┐
  │ C1: DROP P0, P3             │    │ C1: KEEPS P0, P3            │
  │ C2: DROP P1, P4             │    │ C2: KEEPS P1, P4            │
  │ C3: crashed                 │    │ C3: crashed                 │
  │ full recalculation runs     │    │ only P2, P5 need reassigning│
  │ C1 might get totally new    │    │ C1: P0, P3, P2              │
  │ partitions — cache cleared  │    │ C2: P1, P4, P5              │
  └─────────────────────────────┘    │ existing cache untouched ✓  │
                                     └─────────────────────────────┘


  COOPERATIVE STICKY ASSIGNER  (recommended)
  ────────────────────────────────────────────────────────────────────
  Like sticky, but consumers do NOT stop reading during rebalance.

  Eager rebalancers (Range, Round Robin, Sticky):
    rebalance starts → ALL consumers STOP reading → assignment done → resume
    ┌──────────────────────────────────────────────────────┐
    │ C1: stop ■  C2: stop ■  rebalance...  C1: start ►   │
    │ gap in processing while rebalance runs               │
    └──────────────────────────────────────────────────────┘

  Cooperative Sticky:
    Step 1: decide which partitions can stay with their current consumer
    Step 2: only the partitions that need to MOVE are paused
    ┌────────────────────────────────────────────────────────────────┐
    │ C1: keeps reading P0, P3  ──────────────────────────────────►  │
    │ C2: keeps reading P1, P4  ──────────────────────────────────►  │
    │ P2, P5: brief pause while assigned to C1 and C2               │
    │ much less processing gap  ✓                                    │
    └────────────────────────────────────────────────────────────────┘

  spring.kafka.consumer.properties.partition.assignment.strategy=
    org.apache.kafka.clients.consumer.CooperativeStickyAssignor
```

## 8. Offset Commit Modes — Auto vs Manual

Kafka can commit offsets automatically on a timer, or you can take full control and commit only after you know your processing succeeded.

```
  AUTO COMMIT  (simplest, least control)
  ────────────────────────────────────────────────────────────────────
  enable.auto.commit = true
  auto.commit.interval.ms = 5000  (commit every 5 seconds)

  Background thread commits offsets every 5s regardless of whether
  your @KafkaListener finished successfully.
  Risk: message read but not processed → offset committed → message lost  ✗


  MANUAL COMMIT MODES  (enable.auto.commit = false)
  ────────────────────────────────────────────────────────────────────

  BATCH (default manual mode):
    poll() returns 500 records
    process all 500
    framework commits once after all 500 are done  ✓
    (1 commit per poll batch)

  RECORD:
    process record-1 → commit
    process record-2 → commit
    ...500 commits for 500 records  ✗  (high overhead)

  COUNT:
    acknowledge.count = 10
    commit after every 10 records processed  ✓  (balance)

  TIME:
    acknowledge.time = 5000ms
    commit every 5 seconds worth of processing  ✓

  MANUAL:
    you call acknowledgment.acknowledge() in your listener
    framework waits for full batch to complete, then commits once

  MANUAL_IMMEDIATE:
    you call acknowledgment.acknowledge() per record
    framework commits immediately on each call  ✗  (highest overhead)

  ┌─────────────────────────────────────────────────────────────────┐
  │  Use BATCH (default) unless you have a specific reason to       │
  │  commit more or less frequently. It balances safety and         │
  │  performance for most applications.                             │
  └─────────────────────────────────────────────────────────────────┘
```

## Quick Reference

```
Configuration                  Default      What it controls
─────────────────────────────  ───────────  ───────────────────────────────────────────────────
auto.offset.reset              latest       Start position when no offset exists: earliest/latest/none
fetch.min.bytes                1 byte       Min data broker accumulates before responding
fetch.max.wait.ms              500 ms       Max time broker waits to reach fetch.min.bytes
max.partition.fetch.bytes      1 MB         Max bytes fetched per partition in one request
fetch.max.bytes                52 MB        Max total bytes returned by one broker in one response
max.poll.records               500          Records pulled from internal buffer per poll() call
heartbeat.interval.ms          3,000 ms     How often consumer sends "I am alive" pulse
session.timeout.ms             45,000 ms    How long coordinator waits before declaring consumer dead
max.poll.interval.ms           300,000 ms   How long coordinator waits between poll() calls
enable.auto.commit             true         Whether offset commits happen on a timer automatically
auto.commit.interval.ms        5,000 ms     Frequency of automatic offset commits

Assignment strategy comparison:
  Range               default   simple, full rebalance stops all consumers  ✗
  Round Robin         manual    even spread, full rebalance stops all  ✗
  Sticky              manual    less partition movement on rebalance  ✓
  CooperativeStickyAssignor  recommended   least disruption, only moved partitions pause  ✓

Key relationships:
  heartbeat.interval.ms  <  session.timeout.ms   (pulse faster than timeout)
  max.poll.records (small) + max.poll.interval.ms (higher)   for slow processing
  fetch.min.bytes (higher) + fetch.max.wait.ms (higher)      to batch in low traffic
```
