auto.offset.reset — Where to Start Reading

When a consumer joins a group for the first time and there is no committed offset for its partition, this setting decides where it begins reading.

fetch.min.bytes and fetch.max.wait.ms — Controlling Response Timing

Instead of responding immediately with just one record, the broker can wait until it has gathered a minimum amount of data — reducing network round trips when traffic is low.

Consumer sends fetch request to broker. Broker has collected data from the requested partitions. Now it decides: should I send the response now or wait for more data? ┌──────────────────────────────────────────────────────────────────┐ │ Broker decision logic (both conditions checked together): │ │ │ │ Condition 1: data accumulated >= fetch.min.bytes? │ │ YES → send response immediately ✓ │ │ NO → wait... │ │ ▼ │ │ Condition 2: waited >= fetch.max.wait.ms? │ │ YES → send whatever is available (even if < min bytes) ✓ │ │ NO → keep waiting... │ └──────────────────────────────────────────────────────────────────┘ HIGH TRAFFIC: ──────────────────────────────────────────────────────────────────── fetch request ──► broker fills min.bytes quickly ──► responds fast ✓ LOW TRAFFIC (e.g., off-peak hours): ──────────────────────────────────────────────────────────────────── fetch request ──► only a few bytes accumulated │ ▼ wait... max.wait.ms timer expires │ ▼ respond with whatever is available ✓ (no hang) Defaults: fetch.min.bytes = 1 (respond as soon as 1 byte is ready) fetch.max.wait.ms = 500ms (never wait more than 500ms) Tuning tip: increase fetch.min.bytes to reduce calls in low-traffic systems.

max.poll.records — Processing Batch Size From the Buffer

The broker may return far more records than you want to process at once. max.poll.records slices those records out of an internal buffer so you work on a manageable batch each poll cycle.

Broker returns 2,000 records (50 MB) in one fetch response. Consumer does NOT process all 2,000 at once. ┌────────────────────────────────────────────────────────────────┐ │ Consumer Internal Buffer │ │ ┌──────────────────────────────────────────────────────────┐ │ │ │ record-0 record-1 record-2 ... record-1999 │ │ │ └──────────────────────────────────────────────────────────┘ │ │ ▲ │ │ │ max.poll.records = 500 │ │ │ │ │ poll() ──► take 500 records from buffer │ │ process all 500 in @KafkaListener ──► commit offset │ │ │ │ poll() again ──► take next 500 from buffer (no network call) │ │ process all 500 in @KafkaListener ──► commit offset │ │ │ │ poll() again ──► take next 500 from buffer (no network call) │ │ ... repeat until buffer empty ... │ │ │ │ poll() again ──► buffer empty → network call to broker │ └────────────────────────────────────────────────────────────────┘ Key point: max.poll.records controls your batch size, not how much the broker sends. The broker may send more — extras sit in the buffer. spring.kafka.consumer.max-poll-records=500 (default: 500)

heartbeat.interval.ms and session.timeout.ms — Consumer Liveness

The consumer sends a heartbeat pulse on a background thread to tell the group coordinator it is still alive. These two settings control how often the pulse is sent and how long the coordinator waits before declaring the consumer dead.

┌──────────────────────────────────────────────────────────────────────┐ │ Consumer (background thread) Group Coordinator (broker) │ │ │ │ every heartbeat.interval.ms │ │ ┌────────────────┐ ┌──────────────────────────────┐ │ │ │ "I am alive" │────────────────►│ heartbeat received ✓ │ │ │ └────────────────┘ 3 seconds │ reset session timer │ │ │ └──────────────────────────────┘ │ │ every heartbeat.interval.ms │ │ ┌────────────────┐ │ │ │ "I am alive" │────────────────► ... ✓ │ │ └────────────────┘ │ │ │ │ Consumer CRASHES │ │ ┌────────────────┐ │ │ │ (no pulse) │ ┌──────────────────────────────┐ │ │ │ (no pulse) │ │ waiting... │ │ │ │ (no pulse) │ │ session.timeout.ms = 45s │ │ │ │ ... │ │ timer expires! │ │ │ └────────────────┘ │ → assume consumer DEAD │ │ │ │ → trigger rebalance │ │ │ └──────────────────────────────┘ │ └──────────────────────────────────────────────────────────────────────┘ Rule: session.timeout.ms must be GREATER than heartbeat.interval.ms so a single missed pulse does not immediately trigger rebalance. Typical values: heartbeat.interval.ms = 3,000 ms (3 seconds) session.timeout.ms = 45,000 ms (45 seconds)

max.poll.interval.ms — Detecting a Stuck Consumer

A consumer can be sending heartbeats (background thread is alive) but not calling poll() (main thread is stuck processing). This setting catches that case.

Consumer sends heartbeat every 3s → group coordinator sees: "alive ✓" Consumer is stuck in @KafkaListener processing 500 records... ┌──────────────────────────────────────────────────────────────────────┐ │ Time 0:00 poll() called — 500 records fetched │ │ Time 0:03 heartbeat sent ✓ coordinator: "alive" │ │ Time 0:06 heartbeat sent ✓ coordinator: "alive" │ │ Time 0:09 heartbeat sent ✓ coordinator: "alive" │ │ ... │ │ Time 5:00 max.poll.interval.ms expires! │ │ coordinator: "poll not received in 5 minutes" │ │ → assume consumer is STUCK │ │ → trigger rebalance │ │ → partitions reassigned to other consumers │ └──────────────────────────────────────────────────────────────────────┘ heartbeat alone is NOT enough — poll() must also happen regularly. ┌────────────────────────────────────────────────────────────────────┐ │ heartbeat.interval.ms consumer says: "I am alive" │ │ session.timeout.ms coordinator waits for heartbeat │ │ max.poll.interval.ms coordinator waits for poll() call │ └────────────────────────────────────────────────────────────────────┘ Tip: if your processing is legitimately slow (e.g., DB writes per record), increase max.poll.interval.ms or reduce max.poll.records so each batch finishes faster. spring.kafka.consumer.properties.max.poll.interval.ms=300000 (5 min default)

Partition Assignment Strategies

When consumers join a group, the group coordinator runs an assignment algorithm to divide topic partitions among them. The algorithm you pick affects both initial assignment and how rebalance behaves.

Setup: 3 consumers (C1, C2, C3), 6 partitions (P0–P5) RANGE ASSIGNER (default) ──────────────────────────────────────────────────────────────────── Sort consumers alphabetically, sort partitions numerically. Divide: 6 partitions ÷ 3 consumers = 2 each. C1: P0, P1 C2: P2, P3 C3: P4, P5 ROUND ROBIN ASSIGNER ──────────────────────────────────────────────────────────────────── Distribute one partition at a time in a circle. C1: P0, P3 C2: P1, P4 C3: P2, P5 STICKY ASSIGNER ──────────────────────────────────────────────────────────────────── Starts like round robin. Main advantage: smarter rebalance. C3 crashes → need to rebalance. Range/Round Robin (eager): Sticky: ┌─────────────────────────────┐ ┌─────────────────────────────┐ │ C1: DROP P0, P3 │ │ C1: KEEPS P0, P3 │ │ C2: DROP P1, P4 │ │ C2: KEEPS P1, P4 │ │ C3: crashed │ │ C3: crashed │ │ full recalculation runs │ │ only P2, P5 need reassigning│ │ C1 might get totally new │ │ C1: P0, P3, P2 │ │ partitions — cache cleared │ │ C2: P1, P4, P5 │ └─────────────────────────────┘ │ existing cache untouched ✓ │ └─────────────────────────────┘ COOPERATIVE STICKY ASSIGNER (recommended) ──────────────────────────────────────────────────────────────────── Like sticky, but consumers do NOT stop reading during rebalance. Eager rebalancers (Range, Round Robin, Sticky): rebalance starts → ALL consumers STOP reading → assignment done → resume ┌──────────────────────────────────────────────────────┐ │ C1: stop ■ C2: stop ■ rebalance... C1: start ► │ │ gap in processing while rebalance runs │ └──────────────────────────────────────────────────────┘ Cooperative Sticky: Step 1: decide which partitions can stay with their current consumer Step 2: only the partitions that need to MOVE are paused ┌────────────────────────────────────────────────────────────────┐ │ C1: keeps reading P0, P3 ──────────────────────────────────► │ │ C2: keeps reading P1, P4 ──────────────────────────────────► │ │ P2, P5: brief pause while assigned to C1 and C2 │ │ much less processing gap ✓ │ └────────────────────────────────────────────────────────────────┘ spring.kafka.consumer.properties.partition.assignment.strategy= org.apache.kafka.clients.consumer.CooperativeStickyAssignor

Offset Commit Modes — Auto vs Manual

Kafka can commit offsets automatically on a timer, or you can take full control and commit only after you know your processing succeeded.

AUTO COMMIT (simplest, least control) ──────────────────────────────────────────────────────────────────── enable.auto.commit = true auto.commit.interval.ms = 5000 (commit every 5 seconds) Background thread commits offsets every 5s regardless of whether your @KafkaListener finished successfully. Risk: message read but not processed → offset committed → message lost ✗ MANUAL COMMIT MODES (enable.auto.commit = false) ──────────────────────────────────────────────────────────────────── BATCH (default manual mode): poll() returns 500 records process all 500 framework commits once after all 500 are done ✓ (1 commit per poll batch) RECORD: process record-1 → commit process record-2 → commit ...500 commits for 500 records ✗ (high overhead) COUNT: acknowledge.count = 10 commit after every 10 records processed ✓ (balance) TIME: acknowledge.time = 5000ms commit every 5 seconds worth of processing ✓ MANUAL: you call acknowledgment.acknowledge() in your listener framework waits for full batch to complete, then commits once MANUAL_IMMEDIATE: you call acknowledgment.acknowledge() per record framework commits immediately on each call ✗ (highest overhead) ┌─────────────────────────────────────────────────────────────────┐ │ Use BATCH (default) unless you have a specific reason to │ │ commit more or less frequently. It balances safety and │ │ performance for most applications. │ └─────────────────────────────────────────────────────────────────┘

Architecture — Two Different Tuning Profiles in One System

"These configs aren't one-size-fits-all — the Notification System runs completely different tuning for OTP consumers versus bulk-campaign consumers, and that difference is deliberate."

OTP consumer (notifications.critical.sms, 20 dedicated workers): fetch.min.bytes=1 ← don't wait to batch, urgency matters fetch.max.wait.ms=100 ← respond almost immediately max.poll.records=50 ← small batches, fast turnaround per poll max.poll.interval.ms=30000 ← tight, detect a stuck OTP worker fast Bulk campaign consumer (notifications.bulk.email, 2 workers): fetch.min.bytes=65536 ← wait for a meaningful batch, efficiency matters fetch.max.wait.ms=2000 ← acceptable to wait up to 2s for a fuller batch max.poll.records=2000 ← large batches, fewer round-trips max.poll.interval.ms=600000 ← generous, large batches take longer to process

Scenario-first: "If I used the OTP consumer's tight settings for bulk campaigns, I'd be making far more, smaller network round-trips than necessary — wasteful for a workload where a few seconds of extra latency is invisible to the business. Config tuning is a per-workload decision, not a global default."

Cross Questions Interviewers Ask

Q: Why must heartbeat.interval.ms always be well below session.timeout.ms? A: The consumer needs several heartbeat opportunities within one timeout window — if they were close together, a single missed/delayed heartbeat could trigger an unnecessary rebalance. Q: Why is max.poll.interval.ms a SEPARATE setting from session.timeout.ms? A: Heartbeats run on a background thread independent of your processing loop in modern Kafka clients — session.timeout.ms governs heartbeat-based liveness, while max.poll.interval.ms specifically bounds how long actual record PROCESSING can take before the consumer is presumed stuck, even if heartbeats are still firing fine. Q: Why prefer CooperativeStickyAssignor over the plain Sticky assignor? A: Sticky minimizes partition movement but still does a full "stop the world" rebalance. Cooperative additionally lets UNAFFECTED consumers keep processing throughout the rebalance — only the specific reassigned partitions pause.

Senior Trap Questions (15 YOE)

Trap 1 — "You raised max.poll.records to improve bulk-consumer throughput, and now that consumer keeps getting kicked out of the group during traffic spikes. Explain precisely why, and the two ways to fix it." Answer: "Bigger batches take proportionally longer to process — if that exceeds max.poll.interval.ms, the coordinator presumes the consumer dead and rebalances its partitions away, causing exactly the kind of reprocessing-then-more-rebalancing spiral this is designed to prevent. Fix: either lower max.poll.records back down, or deliberately raise max.poll.interval.ms to match realistic worst-case batch processing time — sized on purpose, not left at a surprising default." Trap 2 — "Your OTP consumer's fetch.min.bytes=1 setting was copied onto the bulk-campaign consumer 'for consistency.' What's the actual cost?" Answer: "fetch.min.bytes=1 means the broker responds to every fetch request almost immediately regardless of how little data is ready — for a high-volume bulk topic, this multiplies network round-trips dramatically compared to waiting to batch a fuller response, directly hurting the bulk consumer's actual throughput for a latency guarantee it never needed in the first place."

WHY We Chose Each Decision

- Why per-workload config profiles (OTP vs bulk) instead of one global default: each workload's actual bottleneck and latency tolerance differs. - Why CooperativeStickyAssignor as the universal default: minimizes rebalance disruption regardless of workload type — no reason not to use it. - Why max.poll.interval.ms is sized to REALISTIC worst-case batch time: prevents the false-positive-rebalance spiral under legitimate load. - Why heartbeat.interval.ms stays well below session.timeout.ms: gives multiple heartbeat opportunities per timeout window, avoiding flaky rebalances.

Top 2 Technologies — Consumer Group Assignor

CooperativeStickyAssignor vs RangeAssignor (Kafka default) Why pick Cooperative Sticky (our choice): only reassigns the SPECIFIC partitions that changed during a rebalance — unaffected consumers keep processing throughout, dramatically shrinking disruption windows. Why pick Range: simplest historically-default behavior, acceptable for small consumer groups where a brief full-group pause is genuinely fine. Example 1 (Cooperative Sticky): Notification System's 20-instance email-workers group — one instance restarting shouldn't pause the other 19. Example 2 (Range, acceptable): A 2-consumer internal batch job running hourly, where a few extra seconds of pause during rebalance is imperceptible.
