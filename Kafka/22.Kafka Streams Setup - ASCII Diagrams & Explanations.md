## 1. The Kafka Streams JAR — Adding the Dependency

Kafka Streams is just a JAR file you include in your project — it is not a server or a cluster you deploy separately. Adding this one dependency turns your Spring Boot application into a stream processor.

```
Your Spring Boot App
┌────────────────────────────────────────────────────────────────┐
│                                                                │
│   pom.xml / build.gradle                                       │
│   ┌────────────────────────────────────────────────────────┐  │
│   │  <dependency>                                          │  │
│   │    <groupId>org.apache.kafka</groupId>                 │  │
│   │    <artifactId>kafka-streams</artifactId>              │  │
│   │  </dependency>                                         │  │
│   └────────────────────────────────────────────────────────┘  │
│                          │                                     │
│                          ▼                                     │
│   ┌──────────────────────────────────────────────────────┐    │
│   │  kafka-streams.jar  (everything you need)            │    │
│   │  ┌────────────┐  ┌─────────────┐  ┌──────────────┐  │    │
│   │  │ StreamsBuilder│  │KafkaStreams│  │TopologyTestDriver│  │    │
│   │  └────────────┘  └─────────────┘  └──────────────┘  │    │
│   └──────────────────────────────────────────────────────┘    │
│                                                                │
│   No separate cluster to run. No extra server to manage.  ✓   │
└────────────────────────────────────────────────────────────────┘
```

## 2. StreamsConfig — Key Properties

Four properties are required to get Kafka Streams running. Think of `application.id` exactly like a consumer `group.id` — it identifies your application group and is used to name the internal topics Kafka creates for you.

```
application.properties
┌──────────────────────────────────────────────────────────────────┐
│                                                                  │
│  spring.kafka.streams.application-id = order-analytics          │
│      │                                                           │
│      │  Like consumer group.id — identifies the application.    │
│      │  Also used as the prefix for auto-created topic names.   │
│      │                                                           │
│  spring.kafka.bootstrap-servers = localhost:9092                 │
│      │                                                           │
│      │  Broker to connect to for metadata. Same as always.      │
│      │                                                           │
│  spring.kafka.streams.properties.num.stream.threads = 2         │
│      │                                                           │
│      │  How many stream processing threads to create inside      │
│      │  this single JVM. Tasks are spread across these threads.  │
│      │                                                           │
│  spring.kafka.streams.state-dir = /tmp/kafka-streams            │
│      │                                                           │
│      └  Path on local disk where RocksDB files are stored.      │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

## 3. @EnableKafkaStreams — Activating the Framework

You add this annotation to one configuration class. It tells the Spring Boot auto-configuration to load all Kafka Streams beans — you do not need to manually create a `KafkaStreams` object or start it yourself.

```
@SpringBootApplication
@EnableKafkaStreams              ← one annotation is all it takes
public class OrderAnalyticsApp {
    public static void main(String[] args) {
        SpringApplication.run(OrderAnalyticsApp.class, args);
    }
}

Without it:                         With it:
┌────────────────────────┐          ┌────────────────────────────────┐
│  No Streams beans      │          │  StreamsBuilder bean     ✓     │
│  Nothing starts        │          │  KafkaStreams object     ✓     │
│  Topology ignored      │          │  Auto start on startup   ✓     │
└────────────────────────┘          │  Graceful shutdown hook  ✓     │
                                    └────────────────────────────────┘
```

## 4. Defining the Topology — What You Write

All you write is the topology. Everything else — sub-topologies, repartition topics, changelog topics, task creation — is handled automatically by the framework. Think of the topology as a recipe: you describe the steps, Kafka executes them.

```
Topology for this example:

  @Bean
  public KStream<String, Order> buildTopology(StreamsBuilder builder) {

    KStream<String, Order> stream =
      builder.stream("order-events")            ← SOURCE
        .filter((k, v) -> v.amount > 100)       ← PROCESSOR 1: filter
        .selectKey((k, v) -> v.productId)       ← PROCESSOR 2: repartition
        .groupByKey()                           ← PROCESSOR 3: group
        .count(Materialized.as("product-count-store"))  ← PROCESSOR 4: count + RocksDB
        .toStream()
        .to("product-counts");                  ← SINK

    return stream;
  }

Data flow (what you define):
─────────────────────────────────────────────────────────────────────
  [order-events]
       │
       ▼
  filter(amount > 100)
       │
       ▼
  selectKey(productId)   ← repartition step — framework splits here
       │
       ▼
  groupByKey → count(stored in "product-count-store" RocksDB)
       │
       ▼
  [product-counts]
```

## 5. Auto-Created Topics — What Kafka Streams Creates for You

When your application starts, Kafka Streams inspects your topology and automatically creates the internal topics it needs. You do not create these manually.

```
BEFORE starting Kafka Streams app:
  Topics in cluster:
  ┌──────────────────────┐
  │  order-events (P0,P1,P2)  ← you created this
  └──────────────────────┘

AFTER starting Kafka Streams app:
  Topics in cluster:
  ┌───────────────────────────────────────────────────────────────┐
  │                                                               │
  │  order-events               (3 partitions)  ← existed before │
  │                                                               │
  │  order-analytics-product-count-store-repartition             │
  │                             (3 partitions)  ← auto-created   │
  │      prefix = application.id ──┘                             │
  │                                                               │
  │  order-analytics-product-count-store-changelog               │
  │                             (3 partitions)  ← auto-created   │
  │      prefix = application.id ──┘                             │
  │      backing up RocksDB for crash recovery                   │
  │                                                               │
  │  __consumer_offsets         (50 partitions) ← Kafka internal │
  │                                                               │
  └───────────────────────────────────────────────────────────────┘

Naming rule:
  {application.id} - {state-store-name} - repartition
  {application.id} - {state-store-name} - changelog
```

## 6. Sub-Topology Split — What Kafka Creates Internally

Because the topology contains a `selectKey` (a repartition step), Kafka Streams automatically splits it into two sub-topologies at runtime. You write one topology; Kafka sees two.

```
YOUR TOPOLOGY (one thing you write):
─────────────────────────────────────────────────────────────────────
  order-events → filter → selectKey(productId) → groupByKey → count → product-counts


WHAT KAFKA CREATES INTERNALLY (two sub-topologies):
─────────────────────────────────────────────────────────────────────

  Sub-Topology 0:
  ┌─────────────────────────────────────────────────────┐
  │  source: order-events          (3 partitions)       │
  │  processor: filter(amount>100)                      │
  │  processor: selectKey(productId)                    │
  │  sink: ...repartition-topic    (3 partitions) ──────┼──► auto-created
  └─────────────────────────────────────────────────────┘
                          │
                          │  (repartition topic is the bridge)
                          ▼
  Sub-Topology 1:
  ┌─────────────────────────────────────────────────────┐
  │  source: ...repartition-topic  (3 partitions)       │
  │  processor: groupByKey → count                      │
  │  state-store: product-count-store (RocksDB)         │
  │  changelog: ...changelog-topic (3 partitions) ──────┼──► auto-created
  │  sink: product-counts                               │
  └─────────────────────────────────────────────────────┘

The split point is ALWAYS at a repartition step.
Kafka creates sub-topologies — you never write them directly.
```

## 7. Task Count — Six Tasks from Three Partitions

Each sub-topology creates one task per partition of its source topic. With 3 partitions and 2 sub-topologies, you get 6 tasks total.

```
Source: order-events (3 partitions)
    │
    ├──► Sub-Topology 0 → 3 tasks (one per partition)
    │    Task-0-0  reads order-events P0
    │    Task-0-1  reads order-events P1
    │    Task-0-2  reads order-events P2
    │
    └──► repartition-topic (3 partitions — same count as source)
         │
         └──► Sub-Topology 1 → 3 tasks (one per partition)
              Task-1-0  reads repartition-topic P0
              Task-1-1  reads repartition-topic P1
              Task-1-2  reads repartition-topic P2

Total tasks = 3 + 3 = 6

Rule:
  tasks per sub-topology = number of partitions in that sub-topology's source topic
  repartition topic partition count = source topic partition count (auto-matched)
```

## 8. Thread Distribution — Six Tasks Across Two Threads

The `num.stream.threads = 2` property creates two stream processing threads inside your single JVM. The 6 tasks are distributed evenly across them.

```
Application Instance (one JVM, two threads)
┌──────────────────────────────────────────────────────────────────┐
│                                                                  │
│  Stream-Thread-1                  Stream-Thread-2               │
│  ┌──────────────────────────┐     ┌──────────────────────────┐  │
│  │  Task-0-0                │     │  Task-0-1                │  │
│  │  reads: order-events P0  │     │  reads: order-events P1  │  │
│  │  ─────────────────────── │     │  ─────────────────────── │  │
│  │  Task-0-2                │     │  Task-1-0                │  │
│  │  reads: order-events P2  │     │  reads: repartition P0   │  │
│  │  ─────────────────────── │     │  ─────────────────────── │  │
│  │  Task-1-1                │     │  Task-1-2                │  │
│  │  reads: repartition P1   │     │  reads: repartition P2   │  │
│  └──────────────────────────┘     └──────────────────────────┘  │
│          3 tasks                          3 tasks                │
└──────────────────────────────────────────────────────────────────┘

Each task runs its COMPLETE sub-topology independently.
Events inside one task are processed one at a time (sequential).
Two tasks on different threads run in PARALLEL.
```

## 9. RocksDB State Directory — File Layout on Disk

Each task that uses a state store (like `count`) gets its own RocksDB directory on local disk. The path is controlled by `state.dir` in your config. You cannot open these files in a text editor — they are binary key-value files.

```
state.dir = /tmp/kafka-streams

/tmp/kafka-streams/
└── order-analytics/                     ← your application.id
    ├── 0_0/                             ← Sub-Topology 0, Partition 0
    │   └── (RocksDB files for task 0-0)
    ├── 0_1/                             ← Sub-Topology 0, Partition 1
    │   └── (RocksDB files for task 0-1)
    ├── 0_2/                             ← Sub-Topology 0, Partition 2
    │   └── (RocksDB files for task 0-2)
    ├── 1_0/                             ← Sub-Topology 1, Partition 0
    │   └── product-count-store/         ← your named state store
    │       └── (binary key-value data)
    ├── 1_1/                             ← Sub-Topology 1, Partition 1
    │   └── product-count-store/
    └── 1_2/                             ← Sub-Topology 1, Partition 2
        └── product-count-store/

Naming pattern:  {sub-topology-id}_{partition-id}/
6 directories = 6 tasks  ✓
```

## 10. Key Transformation at Repartition

When `selectKey(productId)` runs, the event's key changes from the original `orderId` to `productId`. This is what guarantees all orders for the same product end up in the same partition after repartition.

```
BEFORE repartition (in order-events topic):
─────────────────────────────────────────────────────────────────────
  Message in order-events P0:
  ┌─────────────────────────────────────────┐
  │  key:   "O-1"          ← orderId        │
  │  value: { orderId: O-1, productId: P1,  │
  │           amount: 250 }                 │
  └─────────────────────────────────────────┘

AFTER repartition (in repartition topic):
─────────────────────────────────────────────────────────────────────
  Message in ...repartition-topic P0:
  ┌─────────────────────────────────────────┐
  │  key:   "P1"           ← productId  ✓  │
  │  value: { orderId: O-1, productId: P1,  │
  │           amount: 250 }                 │
  └─────────────────────────────────────────┘

  Same payload, different key.
  Now all "P1" events hash to the SAME partition → correct count.

Without repartition:        With repartition:
  P1 split across tasks       P1 owned by one task
  Task-0: P1 = 1  ✗          Task-1-0: P1 = 2  ✓
  Task-1: P1 = 1  ✗
```

## 11. Application Startup Sequence

When you run the application, Kafka Streams goes through a fixed sequence before it begins processing events. The startup is automatic — `@EnableKafkaStreams` handles it.

```
Step 1   App starts → @EnableKafkaStreams loads beans
         │
Step 2   Read StreamsConfig (application.id, bootstrap.servers, threads, state.dir)
         │
Step 3   Discover topology (your @Bean StreamsBuilder method runs)
         │
Step 4   Connect to Kafka broker using bootstrap.servers
         │
Step 5   Join consumer group using application.id as group.id
         │
Step 6   Stream Partition Assigner runs:
         ├── Inspect topology → detect repartition steps
         ├── Create sub-topologies (ST-0, ST-1)
         ├── Create repartition topics  (if not already present)
         ├── Create changelog topics    (if not already present)
         ├── Calculate tasks (6 tasks for 3-partition source)
         └── Assign tasks to threads (3 per thread)
         │
Step 7   For each stateful task → restore RocksDB from changelog topic
         │
Step 8   Fetch last committed offsets for source partitions
         │
Step 9   Start reading events → run through sub-topology → commit offset
         │
Step 10  Repeat forever  ↺
```

## 12. Graceful Shutdown — Runtime Hook

Kafka Streams registers a JVM shutdown hook automatically so it can close cleanly when the process is stopped (Ctrl+C or SIGTERM). No manual code is needed for this when using Spring Boot.

```
  SIGTERM / Ctrl+C received
           │
           ▼
  JVM Shutdown Hook fires
  ┌───────────────────────────────────────────────────────────┐
  │  1. Stop reading new events from source topics            │
  │  2. Finish processing events currently in-flight          │
  │  3. Commit current offsets to __consumer_offsets          │
  │  4. Flush RocksDB writes to local disk                    │
  │  5. Close KafkaStreams object                             │
  │  6. JVM exits cleanly                                     │
  └───────────────────────────────────────────────────────────┘

  Abrupt kill (kill -9):
  ┌───────────────────────────────────────────────────────────┐
  │  Shutdown hook does NOT run                               │
  │  Last committed offset is used on restart        ✓       │
  │  RocksDB rebuilt from changelog topic on restart ✓       │
  │  No data loss — Kafka handles recovery                    │
  └───────────────────────────────────────────────────────────┘
```

## 13. Validating the Setup — Commands to Verify

After starting your Kafka Streams application, these commands let you confirm that everything is working exactly as the architecture predicts.

```
1. Check auto-created topics:
─────────────────────────────────────────────────────────────────────
  kafka-topics.sh --list --bootstrap-server localhost:9092

  Expected output:
  __consumer_offsets
  order-events                                     ← your source
  order-analytics-product-count-store-repartition  ← auto-created ✓
  order-analytics-product-count-store-changelog    ← auto-created ✓
  product-counts                                   ← your sink


2. Check task distribution (describes the consumer group):
─────────────────────────────────────────────────────────────────────
  kafka-consumer-groups.sh --describe --group order-analytics \
    --bootstrap-server localhost:9092

  Expected: 6 rows, 3 reading order-events (P0,P1,P2),
            3 reading repartition topic (P0,P1,P2)
  consumer-id column shows: stream-thread-1 or stream-thread-2  ✓


3. Check repartition topic key change:
─────────────────────────────────────────────────────────────────────
  In order-events:        key = orderId  (e.g. "O-1")
  In repartition topic:   key = productId (e.g. "P1")  ✓


4. Check RocksDB directories on disk:
─────────────────────────────────────────────────────────────────────
  ls /tmp/kafka-streams/order-analytics/

  Expected: 6 directories (0_0, 0_1, 0_2, 1_0, 1_1, 1_2)  ✓
```

## Quick Reference

```
Concept                   What it does                              Key detail
────────────────────────  ────────────────────────────────────────  ──────────────────────────────────
kafka-streams dependency  Adds stream processing to your app        Just a JAR — no separate server
application.id            Identifies your Streams app group         Like consumer group.id
bootstrap.servers         Broker to connect to for metadata         Same as any Kafka client
num.stream.threads        Threads inside one JVM                    Tasks are spread across threads
state.dir                 Where RocksDB files are stored on disk    {dir}/{app-id}/{subtopology}_{partition}
@EnableKafkaStreams        Loads all Kafka Streams beans             One annotation on a config class
StreamsBuilder            Builder object for defining topology      Injected as a Spring bean
KStream                   Represents the stream of events           Obtained via builder.stream(topic)
selectKey(...)            Changes the key of each event             Triggers repartition split
Repartition topic         Bridge between sub-topologies             Auto-named: {app-id}-{store}-repartition
Changelog topic           Kafka backup of RocksDB                   Auto-named: {app-id}-{store}-changelog
Task naming               {sub-topology-id}_{partition-id}          e.g. 1_0 = sub-topology 1, partition 0
Shutdown hook             Registered automatically                  Commits offsets and flushes RocksDB

How many tasks?    → (source partitions) × (number of sub-topologies)
How many threads?  → set by num.stream.threads in config
How many topics?   → 1 repartition + 1 changelog per repartition step (auto-created on startup)
```
