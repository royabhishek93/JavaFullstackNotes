Why Windows? The Infinity Problem

A plain count() answers "how many records have I ever seen for this key?" Windows answer "how many records arrived within a specific time range?"

WITHOUT WINDOWS — count answers "all time": User Alice: 47 orders (since the beginning of time) ← cannot answer "how many orders between 10:00 and 11:00?" WITH WINDOWS — count answers "within a time slice": ┌──────────────────────────────────────────────────────────────┐ │ RocksDB windowed store │ │ key │ window start │ window end │ count │ │ ─────── │ ──────────── │ ────────── │ ───── │ │ Alice │ 10:00 │ 11:00 │ 5 │ │ Alice │ 11:00 │ 12:00 │ 12 │ │ Bob │ 10:00 │ 11:00 │ 3 │ └──────────────────────────────────────────────────────────────┘ Now you can answer: "Alice orders between 10:00–11:00 = 5" ✓

Three Time Concepts

Kafka Streams distinguishes three different timestamps. Know which one your window is using.

┌──────────────────────────────────────────────────────────────────┐ │ Your Order Payload (inside the record VALUE): │ │ { │ │ orderId: "O101", │ │ createdAt: 10:01:32 ← EVENT TIME (when it happened IRL) │ │ amount: 500 │ │ } │ │ │ │ Kafka Record Metadata (outside your value): │ │ { │ │ key: "U07", │ │ value: <payload above>, │ │ timestamp: 10:01:35 ← RECORD TIMESTAMP │ │ } │ │ ↑ either: assigned by the PRODUCER at publish time (default) │ │ or: assigned by the BROKER at log-append time (optional) │ └──────────────────────────────────────────────────────────────────┘ By default: Kafka Streams windows use RECORD TIMESTAMP To use event time: implement TimestampExtractor and read createdAt from the payload. Then configure it in application.properties. STREAM TIME: the highest record timestamp seen so far — moves forward only ┌──────────────────────────────────────────────────────────────────┐ │ record arrives with timestamp 10:00 → stream time = 10:00 │ │ record arrives with timestamp 10:10 → stream time = 10:10 │ │ record arrives with timestamp 11:00 → stream time = 11:00 │ │ LATE record with timestamp 10:30 → stream time stays 11:00 │ │ (never goes backward) │ │ record arrives with timestamp 11:40 → stream time = 11:40 │ └──────────────────────────────────────────────────────────────────┘ Kafka does not use a wall clock. It uses stream time to decide whether a window is still open. That is why stream time matters.

Tumbling Windows — Fixed Size, Non-Overlapping

Tumbling windows divide time into equal back-to-back slices. Each record belongs to exactly one window.

WINDOW SIZE = 10 minutes (no overlaps, no gaps) ────────────────────────────────────────────────────────────────► time 10:00 10:10 10:20 10:30 10:40 ┌─────────┐┌─────────┐┌─────────┐┌─────────┐ │ W1 ││ W2 ││ W3 ││ W4 │ │10:00 ││10:10 ││10:20 ││10:30 │ │ to ││ to ││ to ││ to │ │10:10 ││10:20 ││10:30 ││10:40 │ └─────────┘└─────────┘└─────────┘└─────────┘ Record at 10:07 → belongs to W1 only Record at 10:13 → belongs to W2 only Record at 10:27 → belongs to W3 only Start time is INCLUSIVE ┐ End time is EXCLUSIVE ┘ so a record at exactly 10:10 goes to W2, not W1 No record in a range → no entry created in RocksDB for that window. Empty windows are NOT stored. USE CASES: orders per 5 minutes, revenue per hour, API requests per minute

Window Closing — Without Grace Period

A window closes when stream time moves past the window's end time. Late events that arrive after a window closes are discarded.

WINDOW SIZE = 5 min, NO grace period Events for key "O1": 10:31, 10:32, 10:41, then late event: 10:33 Event │ Stream Time │ Window created/updated │ Window closed? ─────────┼─────────────┼────────────────────────┼────────────────────────────────── 10:31 │ 10:31 │ W1 [10:30–10:35] cnt=1 │ — 10:32 │ 10:32 │ W1 [10:30–10:35] cnt=2 │ — 10:41 │ 10:41 │ W2 [10:40–10:45] cnt=1 │ W1 CLOSED: 10:41 > 10:35 ✗ 10:33 ⚠ │ 10:41 │ W1 would be updated │ W1 already CLOSED → DISCARDED ✗ │ (no change│ │ │ to 10:33)│ │ WINDOW CLOSE RULE: stream time > window end time ┌──────────────────────────────────────────────────────────────┐ │ W1 [10:30–10:35] count=2 CLOSED when event at 10:41 came │ │ W2 [10:40–10:45] count=1 still OPEN │ └──────────────────────────────────────────────────────────────┘

Window Closing — With Grace Period

Grace period extends how long a window stays open after its end time, giving late or out-of-order events a chance to be accepted.

WINDOW SIZE = 5 min, GRACE = 10 min Events for key "O1": 10:31, 10:32, 10:41, then late event: 10:33 Window W1 = [10:30–10:35] W1 stays open until: end(10:35) + grace(10 min) = 10:45 Event │ Stream Time │ W1 open until │ W1 accepts? │ Action ─────────┼─────────────┼───────────────┼─────────────┼───────────────────────── 10:31 │ 10:31 │ 10:45 │ YES │ W1 count=1 10:32 │ 10:32 │ 10:45 │ YES │ W1 count=2 10:41 │ 10:41 │ 10:45 │ YES │ W2 created count=1 │ │ │ │ W1 still OPEN (10:41 < 10:45) 10:33 ✓ │ 10:41 │ 10:45 │ YES ✓ │ W1 count=3 ← accepted! WINDOW CLOSE RULE WITH GRACE: stream time > window end time + grace period ┌──────────────────────────────────────────────────────────────┐ │ W1 [10:30–10:35] count=3 late event accepted thanks to │ │ grace period │ │ W2 [10:40–10:45] count=1 │ └──────────────────────────────────────────────────────────────┘

Hopping Windows — Fixed Size, Overlapping

Hopping windows have a fixed size but advance by a smaller hop interval. Because windows overlap, one record can belong to multiple windows simultaneously.

WINDOW SIZE = 10 min, HOP = 5 min ────────────────────────────────────────────────────────────────► time 10:20 10:25 10:30 10:35 10:40 10:45 10:50 ┌───────────────────┐ │ W1: 10:20–10:30 │ └───────────────────┘ ┌───────────────────┐ │ W2: 10:25–10:35 │ └───────────────────┘ ┌───────────────────┐ │ W3: 10:30–10:40 │ └───────────────────┘ ┌───────────────────┐ │ W4: 10:35–10:45 │ └───────────────────┘ ┌───────────────────┐ │ W5: 10:40–10:50 │ └───────────────────┘ Record at 10:27 → falls in W1 (10:20–10:30) AND W2 (10:25–10:35) Record at 10:41 → falls in W4 (10:35–10:45) AND W5 (10:40–10:50) Closing rule: same as tumbling — stream time > window end time (+ grace if set) USE CASES: "orders in last 1 hour, refreshed every 5 minutes" rolling averages, sliding metrics dashboards

Hopping Windows — With Grace (Late Event Example)

WINDOW SIZE = 10 min, HOP = 5 min, GRACE = 10 min Events: 10:27, 10:28, 10:41, then late event: 10:29 After 10:41 arrives, stream time = 10:41 Window │ End │ Open until (end + grace) │ Open at stream=10:41? ───────────────┼───────┼──────────────────────────┼───────────────────── W1: 10:20–10:30│ 10:30 │ 10:40 │ NO (10:41 > 10:40) ✗ W2: 10:25–10:35│ 10:35 │ 10:45 │ YES (10:41 < 10:45) ✓ W3: 10:30–10:40│ 10:40 │ 10:50 │ YES ✓ W4: 10:35–10:45│ 10:45 │ 10:55 │ YES ✓ Late event 10:29 belongs to W1 (10:20–10:30) and W2 (10:25–10:35): W1 is CLOSED → discarded ✗ W2 is OPEN → accepted ✓ (grace period saved this one) ┌──────────────────────────────────────────────────────────────┐ │ Grace period saved the record for W2 but not for W1 │ └──────────────────────────────────────────────────────────────┘

Session Windows — Activity-Based, No Fixed Size

Session windows group events that occur close together in time. There is no fixed window size — a session grows as long as new events keep arriving within the inactivity gap. When nothing arrives for longer than the gap, the session closes.

INACTIVITY GAP = 5 min Events for one user: 10:27, 10:29, 10:41, 10:43 ────────────────────────────────────────────────────────────────► time 10:27 10:29 10:41 10:43 10:27 arrives: → new session starts [10:27 – 10:27] count=1 10:29 arrives: → gap from 10:27 = 2 min < 5 min (inactivity gap) → SAME session → session expands [10:27 – 10:29] count=2 10:41 arrives: → gap from 10:29 = 12 min > 5 min → NEW session → old session [10:27–10:29] CLOSED (stream time 10:41 > end 10:29) → new session [10:41 – 10:41] count=1 10:43 arrives: → gap from 10:41 = 2 min < 5 min → SAME session as 10:41 → session expands [10:41 – 10:43] count=2 FINAL SESSIONS: ┌───────────────────────────┐ ┌───────────────────────────┐ │ Session 1 │ │ Session 2 │ │ start: 10:27 end: 10:29 │ │ start: 10:41 end: 10:43 │ │ count: 2 │ │ count: 2 │ └───────────────────────────┘ └───────────────────────────┘ Window size: DYNAMIC — grows with each nearby event Close rule: stream time > session end time (+ grace if set) USE CASES: average user session duration on a website, user activity periods

Session Windows — Merging Two Sessions

When a late event bridges the gap between two existing sessions, Kafka Streams merges them into one.

INACTIVITY GAP = 5 min, GRACE = 14 min State before the late event: Session-A: [10:27 – 10:29] count=2 (open until 10:29 + 14 = 10:43) Session-B: [10:36 – 10:36] count=1 (open until 10:36 + 14 = 10:50) Stream time = 10:36 Late event arrives at 10:32: Step 1 — Can 10:32 join Session-A? gap = 10:32 − 10:29 = 3 min < inactivity gap (5 min) → YES ✓ Step 2 — Can 10:32 join Session-B? gap = 10:36 − 10:32 = 4 min < inactivity gap (5 min) → YES ✓ Step 3 — 10:32 bridges both sessions → MERGE BEFORE: [10:27 – 10:29] count=2 [10:36 – 10:36] count=1 Session-A Session-B AFTER MERGE: ┌──────────────────────────────────────────────┐ │ Merged Session │ │ start: 10:27 end: 10:36 │ │ count: 4 (2 + 1 bridging event + 1) │ └──────────────────────────────────────────────┘ The late event became a bridge → two sessions collapsed into one. Open-until time resets to: new end (10:36) + grace (14) = 10:50

Windowed Key Structure

After windowing, the KTable key is no longer a plain key — it becomes a Windowed<K> wrapper containing the original key plus the window boundaries.

PLAIN COUNT (no window): KTable<String, Long> key = "Alice" → value = 47 WINDOWED COUNT: KTable<Windowed<String>, Long> key = Windowed { key="Alice", start=10:00, end=11:00 } → value = 5 key = Windowed { key="Alice", start=11:00, end=12:00 } → value = 12 key = Windowed { key="Bob", start=10:00, end=11:00 } → value = 3 ┌──────────────────────────────────────────────────────────────┐ │ Windowed<K> object: │ │ .key() → original key ("Alice") │ │ .window().start() → window start time in milliseconds │ │ .window().end() → window end time in milliseconds │ └──────────────────────────────────────────────────────────────┘ Serialization: key is no longer a plain String — use a dedicated window serde: WindowedSerdes.timeWindowedSerdeFrom(String.class, windowSizeMs)

Architecture — Tumbling Windows for Delivery-Rate, Bounce-Rate, DLQ-Rate

"Every real-time metric the Notification System's reporting could use — delivery rate per minute, bounce rate per 5 minutes, DLQ rate per hour — uses the SAME windowing choice, and that's deliberate."

delivery-rate-per-min: TumblingWindow(1 min), grace=30s bounce-rate-per-5min: TumblingWindow(5 min), grace=30s dlq-rate-per-hour: TumblingWindow(1 hour), grace=60s All THREE use tumbling, not hopping or session — because all three answer the same kind of question: "what's the rate in THIS discrete, non-overlapping period," not "give me a continuously-updating trailing average."

Scenario-first: "If I used session windows here instead, I'd be answering a completely different question — 'how long was this burst of activity' rather than 'what's the rate in this fixed period.' Windowing choice must match the actual question being asked, not just be a default."

Cross Questions Interviewers Ask

Q: Why tumbling windows for all three of these metrics, not hopping? A: Hopping windows overlap and update more frequently but answer "trailing average over the last N minutes" — none of our metrics need that; each is a discrete per-period rate on a dashboard, which tumbling matches exactly. Q: Why does grace period matter more for the 1-minute window than the 1-hour window, relatively speaking? A: A 30-second grace period is a much larger fraction of a 1-minute window than of a 1-hour window — proportionally, short windows are far more sensitive to realistic event-arrival jitter, so grace period sizing matters more acutely there. Q: Why would session windows be the WRONG choice even for something like "user activity during an incident"? A: Session windows group by INACTIVITY GAPS, not fixed periods — great for "how long did this user's browsing session last," but wrong for "what's the error rate every 5 minutes," which needs discrete, comparable time buckets.

Senior Trap Questions (15 YOE)

Trap 1 — "Your bounce-rate alert fired a false positive — dashboard showed 15% bounce rate, but manual investigation showed the real rate was 4%. First hypothesis?" Answer: "A grace period set too short relative to real-world event arrival jitter — if DELIVERED confirmations for a window are still arriving when the window finalizes, the denominator (total sent) can finalize before all late confirmations land, while the numerator (bounces, which might arrive on a different path/timing) is fully counted — producing an artificially inflated rate. I'd check actual event-time vs processing-time skew during that window before assuming the underlying bounce count is wrong." Trap 2 — "Explain precisely why increasing a window's RETENTION period without also increasing GRACE period does nothing to fix under-counting from late-arriving events." Answer: "They govern different lifecycle phases. Grace period controls whether a late event is still ACCEPTED into the aggregation before finalization — the only knob affecting correctness. Retention controls how long the ALREADY-FINALIZED result stays queryable afterward — purely a storage/query-availability concern with zero effect on whether late data was ever counted. Increasing retention just keeps an under-counted result around longer; it doesn't fix the under-counting."

WHY We Chose Each Decision

- Why tumbling windows for all rate-style metrics: matches the actual question being asked — "rate per discrete period," not a continuously- updating trailing metric or an activity-gap grouping. - Why grace period is tuned relative to window size, not a fixed global value: a 30s grace matters far more proportionally on a 1-minute window than a 1-hour one. - Why NOT session windows for any of these dashboards: session windows answer a fundamentally different question about activity gaps, not fixed-period rates. - Why grace period and retention are tuned independently: they solve different problems — correctness (grace) vs storage/query availability (retention).

Top 2 Technologies — Tumbling vs Hopping Windows

Tumbling Windows vs Hopping Windows Why pick Tumbling (our choice for rate dashboards): fixed, non-overlapping buckets — simplest to reason about for "rate per discrete period" reporting. Why pick Hopping: needed when the actual requirement is a continuously- updating trailing metric (e.g., "rate over the last 5 minutes, refreshed every 30 seconds") rather than discrete periods. Example 1 (Tumbling): Notification System's delivery-rate-per-minute, bounce-rate-per-5min, and DLQ-rate-per-hour dashboards — all discrete, comparable time buckets. Example 2 (Hopping): A real-time fraud-detection system needing a continuously-refreshed "transaction rate over the trailing 10 minutes" signal that updates every minute, not just every 10 minutes.
