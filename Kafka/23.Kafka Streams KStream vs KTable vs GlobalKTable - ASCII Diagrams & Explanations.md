# Kafka Streams KStream vs KTable vs GlobalKTable — ASCII Diagrams & Explanations

Topics: KStream, KTable, GlobalKTable, stream semantics, table semantics, co-partitioning, KStream-KTable join, KStream-GlobalKTable join, when to use each

---

## 1. KStream — Every Event Is Independent

A KStream treats each record it reads as a completely fresh, standalone event — it keeps no memory of records it processed before.

```
Topic: order-events  (three events, all with the same key)
┌──────────────────────────────────────────────────────────┐
│  Offset 0 │ key: 001 │ value: status=created             │
│  Offset 1 │ key: 001 │ value: status=shipped             │
│  Offset 2 │ key: 001 │ value: status=delivered           │
└──────────────────────────────────────────────────────────┘

KStream forwards ALL three events independently:

  (001, created)   ──► processor ──► sink
  (001, shipped)   ──► processor ──► sink
  (001, delivered) ──► processor ──► sink

No history stored.  Key 001 is "new" every single time.
KStream does NOT know it has seen 001 before.
```

---

## 2. KTable — Latest Value Per Key

A KTable reads records one by one just like KStream, but it also maintains a local RocksDB state store that always holds the most recent value for each key — old values are overwritten.

```
Topic: order-events  (same three events as above)
┌──────────────────────────────────────────────────────────┐
│  Offset 0 │ key: 001 │ value: status=created             │
│  Offset 1 │ key: 001 │ value: status=shipped             │
│  Offset 2 │ key: 001 │ value: status=delivered           │
└──────────────────────────────────────────────────────────┘

KTable reads each event AND updates RocksDB:

  read (001, created)   → RocksDB: { 001: created   }  → forward to pipeline
  read (001, shipped)   → RocksDB: { 001: shipped   }  → forward to pipeline
  read (001, delivered) → RocksDB: { 001: delivered }  → forward to pipeline

RocksDB at the end: { 001: delivered }  ← only the latest value survives

Each event still flows through the full topology (just like KStream).
The RocksDB is extra — it is a live "current state" lookup table.
```

---

## 3. KStream vs KTable — Same Events, Different Behaviour

The key difference is not in how many events flow through the topology — it is whether a state store is maintained alongside.

```
INCOMING EVENTS (same for both)
──────────────────────────────────────────────────────────────────
  E1: (001, created)    E2: (001, shipped)    E3: (001, delivered)


KSTREAM — append / log semantics
──────────────────────────────────────────────────────────────────
  E1 ──► pipeline        no state stored
  E2 ──► pipeline        no state stored
  E3 ──► pipeline        no state stored

  Result: 3 records forwarded downstream
  "Every event matters, nothing is remembered"

  Use for: payments, clicks, fraud checks, audit logs


KTABLE — update / compacted semantics
──────────────────────────────────────────────────────────────────
  E1 ──► pipeline  +  RocksDB { 001: created   }
  E2 ──► pipeline  +  RocksDB { 001: shipped   }
  E3 ──► pipeline  +  RocksDB { 001: delivered }

  Result: 3 records forwarded, RocksDB always has current state
  "What is the latest value for this key RIGHT NOW?"

  Use for: order status, user profiles, inventory counts
```

## 4. KStream-KTable Join — Enriching a Stream

When you join a KStream with a KTable, each stream event looks up the KTable's RocksDB to add context — for example, adding a customer's city to an order event.

```
KStream: order-events               KTable: customer-info
┌───────────────────────┐           ┌──────────────────────────────────┐
│ key: SJ │ item: laptop│           │ key: SJ │ city: Delhi            │
│ key: SJ │ item: phone │           │ key: SJ │ city: Bangalore ← latest│
└───────────────────────┘           └──────────────────────────────────┘
                                              │
                                    KTable RocksDB:
                                    { SJ: Bangalore }
                                              │
JOIN at processing time:                      │
  order event (SJ, laptop) arrives ───────────┘
  look up RocksDB for key SJ → Bangalore
  output: (SJ, laptop, Bangalore)   ✓


What if order arrives BEFORE customer data is in RocksDB?
  order event (SJ, laptop) arrives → key SJ not yet loaded
  output: (SJ, laptop, null)        ✗

No priority is given to KTable over KStream.
Events arrive in parallel — an early order simply gets null.
```

## 5. Co-Partitioning — Required for KStream-KTable Join

For the join to always find matching data, both topics must use the same number of partitions and the same partition key — this is called co-partitioning.

```
PROBLEM — different partitioning strategies
──────────────────────────────────────────────────────────────────
  order-topic P0: (SJ, laptop)       customer-topic P0: (RJ, Delhi)
  order-topic P1: (RJ, phone)        customer-topic P1: (SJ, Bangalore)

  Task-0 owns order-P0 + customer-P0
    → order has SJ, customer-P0 has RJ — no match  ✗

  Task-1 owns order-P1 + customer-P1
    → order has RJ, customer-P1 has SJ — wrong task  ✗


SOLUTION — co-partitioning
──────────────────────────────────────────────────────────────────
  Rule 1: same number of partitions in both topics
  Rule 2: same key used in both topics (e.g. customerId)

  order-topic P0: (SJ, laptop)       customer-topic P0: (SJ, Bangalore)
  order-topic P1: (RJ, phone)        customer-topic P1: (RJ, Delhi)
       ↑ key SJ hashes to P0              ↑ key SJ hashes to P0  ✓

  Task-0: SJ order finds SJ customer in its own RocksDB  ✓
  Task-1: RJ order finds RJ customer in its own RocksDB  ✓

When co-partitioning is hard or impossible → use GlobalKTable
```

## 6. GlobalKTable — Full Copy on Every Instance

A GlobalKTable solves the co-partitioning problem by reading ALL partitions of a topic and storing everything in one shared RocksDB that every task in the application can access.

```
countries-topic  (2 partitions)
┌────────────────────────┬────────────────────────┐
│    Partition P0        │    Partition P1         │
│  IN → India            │  US → United States     │
│  UK → United Kingdom   │  DE → Germany           │
└────────────────────────┴────────────────────────┘
            │                          │
            └──────────────────────────┘
                         │  reads ALL partitions
            ┌────────────▼────────────────┐
            │  Global RocksDB             │
            │  { IN: India,               │
            │    UK: United Kingdom,      │
            │    US: United States,       │
            │    DE: Germany }            │
            └─────────────────────────────┘
                         │  shared by ALL tasks in this instance
            ┌────────────┴────────────┐
            ▼                         ▼
         Thread-1                  Thread-2
       ┌──────────┐               ┌──────────┐
       │  Task-0  │               │  Task-1  │
       │ can read │               │ can read │
       │ all keys │               │ all keys │
       └──────────┘               └──────────┘

Each application INSTANCE builds its OWN copy of the global RocksDB.
No changelog topic is created — on restart it re-reads the whole topic.
```

---

## 7. KStream-GlobalKTable Join — No Co-Partitioning Needed

Because every task has the complete lookup table in its global RocksDB, any stream event on any partition can always find its matching entry.

```
order-topic (key = orderId — different from countries key)
  P0: (O1, country=US)
  P1: (O2, country=IN)

Global RocksDB (visible to ALL tasks):
  { US: United States, IN: India, UK: United Kingdom, DE: Germany }

Task-0 processes (O1, country=US):
  look up global RocksDB → finds US → United States  ✓

Task-1 processes (O2, country=IN):
  look up global RocksDB → finds IN → India           ✓

Both tasks succeed — no co-partitioning required.


STARTUP ORDER — GlobalKTable always loads first
──────────────────────────────────────────────────────────────────
  [1] Read ALL partitions of GlobalKTable topic
  [2] Build global RocksDB  ← finished BEFORE stream threads start
  [3] Start KStream / KTable processing threads

  Regular KTable does NOT get this priority — it loads in parallel.
```

## 8. When to Use Each

Choose the right source type based on what the data represents and how you need to use it.

```
Does every individual event matter on its own?
──────────────────────────────────────────────────────────────────
  YES → KStream
  Examples: fraud detection per transaction, click tracking,
            payment processing, order lifecycle audit log


Do you need "what is the current state of key X right now?"
  and co-partitioning with the join topic is feasible?
──────────────────────────────────────────────────────────────────
  YES → KTable
  Examples: current order status, user profile cache,
            running count/total per user


Do you need a lookup or enrichment table and co-partitioning
  is not feasible (different key, different partition count)?
──────────────────────────────────────────────────────────────────
  YES → GlobalKTable   ← keep the dataset SMALL!
  Examples: country codes, currency lookup, product names,
            feature flags, static configuration

  ┌──────────────────────────────────────────────────────────┐
  │  GlobalKTable warning:                                   │
  │  Every application instance reads ALL partitions.        │
  │  Use only for small, mostly-static reference data.       │
  │  Do NOT use for large or rapidly-changing topics.        │
  └──────────────────────────────────────────────────────────┘
```

## 9. Quick Reference

```
Concept                 What it is                               Key rule
──────────────────────  ───────────────────────────────────────  ──────────────────────────────────
KStream                 Append-only stream, no state stored      Each record is fully independent
KTable                  Stream + latest-value RocksDB per key    Old value for a key is overwritten
GlobalKTable            Full topic copy per application instance All tasks share one global RocksDB
KStream-KTable join     Stream enriched from KTable RocksDB      Requires co-partitioning
KStream-GlobalKTable    Stream enriched from global RocksDB      No co-partitioning needed
Co-partitioning         Same partition count + same key          Needed for KTable joins to work
Null join               Order arrives before KTable is loaded    No priority given to KTable
Read-first              GlobalKTable loads before streams start  Lookup data ready before processing
No changelog            GlobalKTable has no changelog topic      Re-reads whole topic on restart
Small data only         GlobalKTable guideline                   Use for static reference datasets
```
