KStream Is a Pipeline Stage, Not a Data Container

A KStream object is a reference point in your topology — it does not hold records. It marks where you can attach the next processing node.

TOPOLOGY TREE — each KStream is a handle you can build from: [order-events topic] │ ▼ builder.stream("order-events") ┌──────┐ ◄── "orders" KStream (reference to source node) │source│ └──────┘ │ ▼ orders.filter(amount > 1000) ┌───────────┐ ◄── "highOrders" KStream (reference to filter node) │ filter │ │amount>1000│ └─────┬─────┘ │ │ ▼ highOrders.mapValues() ▼ orders.filter(amount <= 1000) ┌─────────┐ ┌───────────┐ ◄── "lowOrders" KStream │ map │ │ filter │ │ values │ │amount≤1000│ └─────────┘ └───────────┘ Records do NOT live inside a KStream object. A KStream is just a handle — grab it to add more nodes at that stage. Multiple KStream objects = multiple stages in the SAME pipeline.

filter — Keep or Drop Records

filter keeps a record only if the predicate returns true. Records returning false are dropped immediately and never reach the next node.

INPUT STREAM: ┌──────────────┬──────────────┬──────────────┬──────────────┐ │ key:O1 │ key:O2 │ key:O3 │ key:O4 │ │ amount: 200 │ amount: 1500 │ amount: 800 │ amount: 2000 │ └──────────────┴──────────────┴──────────────┴──────────────┘ FILTER NODE: amount > 1000 ┌──────────────────────────────────────────────────────────────┐ │ O1 (200) → predicate? false → DROPPED ✗ │ │ O2 (1500) → predicate? true → PASSES ✓ │ │ O3 (800) → predicate? false → DROPPED ✗ │ │ O4 (2000) → predicate? true → PASSES ✓ │ └──────────────────────────────────────────────────────────────┘ OUTPUT STREAM: ┌──────────────┬──────────────┐ │ key:O2 │ key:O4 │ │ amount: 1500 │ amount: 2000 │ └──────────────┴──────────────┘ Key unchanged ✓ Value unchanged ✓ Repartition eligible? NO

map — Change Key, Value, or Both

map transforms every record into a new key-value pair. You choose what the new key and new value are — either can change.

INPUT RECORD: ┌─────────────────────────────────┐ │ key: "O101" │ │ value: Order { amount: 500, │ │ userId: "U07" } │ └─────────────────────────────────┘ │ ▼ .map((key, order) → KeyValue.pair("order-" + key, order)) ┌─────────────────────────────────┐ │ key: "order-O101" ← CHANGED │ │ value: Order { amount: 500, │ │ userId: "U07" } │ ← unchanged └─────────────────────────────────┘ WHAT map CAN DO: ┌──────────────────┬──────────────────────────────────────────┐ │ Goal │ What you return │ ├──────────────────┼──────────────────────────────────────────┤ │ Change key only │ KeyValue.pair(newKey, originalValue) │ │ Change value only│ KeyValue.pair(originalKey, newValue) │ │ Change both │ KeyValue.pair(newKey, newValue) │ └──────────────────┴──────────────────────────────────────────┘ Key changed? YES → eligible for repartition later ▲

mapValues — Change Value Only

mapValues transforms only the value. The key stays the same, so no repartition is ever triggered.

INPUT: key: "O101" value: Order { amount: 500, status: "pending" } │ ▼ .mapValues(order → order.withStatus("CONFIRMED")) OUTPUT: key: "O101" value: Order { amount: 500, status: "CONFIRMED" } ↑ key is IDENTICAL — no repartition risk SIGNATURE REMINDER: mapValues( V → VR ) ↑ ↑ old new value value (key is passed through untouched) Repartition eligible? NO — key never changes in mapValues

selectKey — Change Key Only

selectKey assigns a brand-new key while leaving the value unchanged. Because the key changes, the record becomes eligible for repartition downstream.

INPUT: key: "O101" value: Order { userId: "U07", amount: 500 } │ ▼ .selectKey((key, order) → order.getUserId()) OUTPUT: key: "U07" ← NEW KEY (userId extracted from value) value: Order { userId: "U07", amount: 500 } ← unchanged Repartition eligible? YES ▲ (actual repartition happens later when groupByKey or join is called) COMMON PATTERN — prepare for a join or aggregation by user: orders.selectKey((k, order) → order.getUserId()) .groupByKey() ← repartition fires HERE .count()

split / branch — Conditional Routing (if-else-if)

split + branch routes each record to at most one matching branch — like a chain of if-else-if. Once a branch matches, the remaining branches are skipped.

PROBLEM WITH TWO SEPARATE FILTERS — both conditions checked for every record: ┌──────────┐ │ record │─── filter(amount >= 2000) ──► highOrders (checked) │ comes │ │ in │─── filter(amount >= 1000) ──► medOrders (also checked!) └──────────┘ Result: a record with amount=2500 passes BOTH → appears in both streams! SPLIT / BRANCH — only ONE branch fires per record: ┌──────────┐ │ record │ │ comes │ │ in │ └────┬─────┘ │ ▼ orders.split() ┌─────────────────────────────────────────────────────────────┐ │ .branch("premium", (k,v) → v.getAmount() >= 2000) ? │ │ YES ──► premiumOrders KStream stop here ✓ │ │ NO ──► │ │ .branch("high", (k,v) → v.getAmount() >= 1000) ? │ │ YES ──► highOrders KStream stop here ✓ │ │ NO ──► │ │ .defaultBranch("low") │ │ ──► lowOrders KStream │ └─────────────────────────────────────────────────────────────┘ branches.get("premium") → KStream for premium records branches.get("high") → KStream for high records branches.get("low") → KStream for low records

merge — Combining Streams

merge is the reverse of split. It takes two or more streams and joins them into one. The streams must share the same key type and value type.

premiumOrders ───┐ ├──► merge ──► allOrdersAbove1000 highOrders ───┘ BEFORE merge: premiumOrders: [ O5: 3000, O8: 2500 ] highOrders: [ O2: 1500, O9: 1200 ] AFTER merge (arrival order, not sorted): allOrdersAbove1000: [ O5: 3000, O2: 1500, O8: 2500, O9: 1200 ] CHAIN as many as needed: premiumOrders .merge(highOrders) .merge(lowOrders) RULE: key type AND value type must match across all merged streams.

Repartition Eligibility Summary

When a key changes the record is only *eligible* — actual repartition happens when groupByKey or a join is reached downstream.

Operation │ Key changes? │ Value changes? │ Repartition eligible? ──────────────┼──────────────┼────────────────┼────────────────────── filter │ NO │ NO │ NO map │ YES (opt.) │ YES (opt.) │ YES — if key changed mapValues │ NO │ YES │ NO selectKey │ YES │ NO │ YES split/branch │ NO │ NO │ NO merge │ NO │ NO │ NO Repartition is TRIGGERED when: key was changed earlier AND groupByKey or join is encountered Why repartition? All records for the SAME key must end up in the SAME partition so stateful nodes (count, aggregate) see the full picture.

Architecture — The Stateless Half of the Delivery-Rate Topology

"Before any counting happens, the delivery-rate topology runs a purely stateless stage — filter and reshape — and I always try to push as much work as possible into this cheap half."

delivery_status_events │ ▼ filter(status in DELIVERED/FAILED/BOUNCED) ← stateless, cheap ▼ mapValues(evt -> evt.withNormalizedChannel()) ← stateless, cheap │ └──► (only NOW do we hit groupBy → stateful territory)

Scenario-first: "Every record that makes it past this stateless stage is one that will eventually flow through the repartition topic and into RocksDB — filtering early means fewer records pay that more expensive downstream cost. This is a cheap, mechanical optimization that's easy to forget under deadline pressure."

Cross Questions Interviewers Ask

Q: Why does mapValues never trigger a repartition, but selectKey always risks one downstream? A: mapValues explicitly never touches the key — Streams knows partitioning is unaffected. selectKey changes the key, so ANY later groupByKey or join must repartition to guarantee the new key's co-location. Q: What's the actual difference between filter and split/branch when you only care about one condition? A: They're functionally similar for a single condition, but split/branch is for ROUTING to multiple different downstream paths based on several conditions — using it for one simple filter is unnecessary complexity. Q: Why is "KStream is a reference point, not a data container" an important mental model? A: It clarifies that calling .filter() doesn't mutate an existing stream — it returns a NEW KStream reference representing a new stage in the topology, letting you branch multiple independent processing paths from one earlier stage.

Senior Trap Questions (15 YOE)

Trap 1 — "A teammate used map() instead of mapValues() for a transformation that only touches the value, 'because map is more general.' Weeks later, an unrelated repartition topic mysteriously shows up in the topology. Why?" Answer: "map() CAN change the key even if this particular usage didn't intend to — Streams' topology-optimization can't always prove the key is unchanged just by looking at map()'s generic signature, unlike mapValues() which structurally guarantees no key change. Using the most specific operator available isn't just style — it gives Streams (and future readers) a stronger guarantee about repartitioning behavior." Trap 2 — "You added a filter AFTER a groupBy instead of before, 'because the logic read more naturally that way in the code.' What's the actual throughput cost of that ordering choice?" Answer: "Every record — including ones that will be filtered out anyway — now pays the repartition cost (written to and read back from an internal topic) before being discarded. Filtering first means those records never enter the more expensive stateful/repartition path at all. Code readability is a legitimate concern, but for high-volume topologies this ordering has a real, measurable throughput difference."

WHY We Chose Each Decision

- Why filter/mapValues as early as possible in every topology: shrinks what actually needs to flow through the more expensive repartition/ stateful stages downstream. - Why prefer mapValues over map when only the value changes: gives Streams (and readers) a structural guarantee against accidental repartitioning. - Why treat KStream as an immutable reference point, not a mutable container: enables branching multiple independent paths cleanly from one stage. - Why split/branch only for genuine multi-way routing: keeps simple single-condition filters simple, reserving branching for when it's actually needed.

Top 2 Technologies — mapValues vs map for Value-Only Transforms

mapValues (value-only transform) vs map (general key+value transform) Why pick mapValues (our choice when only the value changes): structurally guarantees no key change — Streams never needs to consider repartitioning triggered by this step. Why pick map: needed when you genuinely must change both key and value, or want a single operator handling both in one step. Example 1 (mapValues): Notification System's delivery-rate topology normalizing the channel field within the event value — key stays notification_id throughout. Example 2 (map): A topology that both re-keys by a derived field AND reshapes the value in one step, where using map's combined signature is clearer than two chained operators.
