# Kafka Streams STATEFUL Processing Nodes — ASCII Diagrams & Explanations

Topics: groupByKey, groupBy, count, aggregate, KTable, RocksDB state store, KStream-KTable join, KTable-KTable join, repartition trigger

---

## 1. Why Stateful? The Memory Problem

Stateless nodes process each record in isolation — they remember nothing. Stateful nodes must **remember previous records** to compute a correct result.

```
STATELESS (filter) — no memory needed:
  record-1 ──► filter(amount > 500) ──► pass or drop   (no history needed)
  record-2 ──► filter(amount > 500) ──► pass or drop
  record-3 ──► filter(amount > 500) ──► pass or drop

STATEFUL (count per user) — memory IS needed:
  record-1  user:Alice  ──► How many so far? Must remember!
  record-2  user:Bob    ──► ...
  record-3  user:Alice  ──► Alice count = 2 — only correct if we remembered record-1

SOLUTION: RocksDB state store (local key-value database, one per task, on disk)
  ┌──────────────────────────────────────────┐
  │  RocksDB (per task, local disk)          │
  │  key        │ value                      │
  │  ───────────┼───────                     │
  │  "Alice"    │  2                         │
  │  "Bob"      │  1                         │
  └──────────────────────────────────────────┘

Each task has its OWN RocksDB. They never share state.
Every write to RocksDB is also mirrored to a changelog topic in Kafka
so state can be rebuilt after a crash.
```

## 2. groupByKey vs groupBy — Entry Point to Stateful Processing

`groupByKey` and `groupBy` do **not** count or aggregate. They set metadata — which key to group by — for the downstream nodes (`count`, `aggregate`) to use.

```
groupByKey — use the EXISTING key (no key change, no repartition):
  ┌──────────────────────┐
  │  KStream             │  key = userId  (already what we want)
  │  key:  "U07"         │
  │  value: Order{...}   │
  └──────────┬───────────┘
             │ .groupByKey()
             ▼
  ┌──────────────────────┐
  │  KGroupedStream      │  metadata: "downstream nodes use the current key"
  │  key:  "U07"         │  no repartition needed
  └──────────────────────┘

groupBy — CHANGE the key (always triggers repartition):
  ┌──────────────────────┐
  │  KStream             │  key = orderId  (wrong for our goal)
  │  key:  "O101"        │
  │  value: Order{...}   │
  └──────────┬───────────┘
             │ .groupBy((key, order) → order.getUserId())
             ▼
  ┌──────────────────────────────────────────────────┐
  │  New key = "U07"  (userId)                       │
  │  Repartition INITIATED — internal topic created  │
  │  so all "U07" records land in the same partition │
  └──────────────────────────────────────────────────┘
             │
             ▼
  ┌──────────────────────┐
  │  KGroupedStream      │  metadata: "use userId as group key"
  └──────────────────────┘

SHORTCUT: if you only need to change the key before grouping, you can either
  a) selectKey(…).groupByKey()   — two steps, repartition at groupByKey
  b) groupBy(…)                  — one step, repartition always triggered
```

## 3. count — Event-by-Event State Evolution

`count` reads the current value from RocksDB, increments it by 1, writes it back, and emits an updated KTable row.

```
EVENTS ARRIVING (key = user name):
  ─────────────────────────────────────────────────────────────►  time
  Alice       Bob         Alice       Alice
  (event-1)   (event-2)   (event-3)   (event-4)

ROCKSDB STATE AFTER EACH EVENT:
  ┌──────────────────────────────────────────────────────────────┐
  │ After event-1 (Alice):   { Alice: 1 }                        │
  │ After event-2 (Bob):     { Alice: 1,  Bob: 1 }               │
  │ After event-3 (Alice):   { Alice: 2,  Bob: 1 }               │
  │ After event-4 (Alice):   { Alice: 3,  Bob: 1 }               │
  └──────────────────────────────────────────────────────────────┘

KTABLE OUTPUT (one emission per change):
  ┌──────────┬───────┐
  │ key      │ count │
  ├──────────┼───────┤
  │ Alice    │  1    │  ← emitted after event-1
  │ Bob      │  1    │  ← emitted after event-2
  │ Alice    │  2    │  ← emitted after event-3  (updates Alice row)
  │ Alice    │  3    │  ← emitted after event-4  (updates Alice row)
  └──────────┴───────┘

CODE SHAPE:
  orders
    .groupByKey()
    .count(Materialized.as("order-counter-store"))
  → returns KTable<String, Long>
```

## 4. aggregate — Custom Aggregation Logic

`aggregate` gives you full control. You provide two things: (1) an **initializer** that runs the very first time a key is seen, and (2) an **aggregator** that runs on every subsequent record.

```
GOAL: sum order amounts per user
  Input records: Alice→100, Bob→200, Alice→150, Alice→50

  ── aggregate flow for key "Alice" ──────────────────────────────

  STEP 1 — First time "Alice" appears:
  ┌──────────────────────────────────────────────────────────────┐
  │  RocksDB lookup "Alice" → NOT FOUND                          │
  │  → run initializer()           → returns 0                   │
  │  → run aggregator("Alice", 100, rocksDBval=0)                 │
  │       your logic: 0 + 100 = 100                              │
  │  → write 100 to RocksDB["Alice"]                             │
  └──────────────────────────────────────────────────────────────┘

  STEP 2 — Second Alice record (value=150):
  ┌──────────────────────────────────────────────────────────────┐
  │  RocksDB lookup "Alice" → FOUND → 100                        │
  │  → skip initializer (already initialized)                    │
  │  → run aggregator("Alice", 150, rocksDBval=100)               │
  │       your logic: 100 + 150 = 250                            │
  │  → write 250 to RocksDB["Alice"]                             │
  └──────────────────────────────────────────────────────────────┘

  STEP 3 — Third Alice record (value=50):
  ┌──────────────────────────────────────────────────────────────┐
  │  RocksDB lookup "Alice" → FOUND → 250                        │
  │  → aggregator("Alice", 50, rocksDBval=250)                    │
  │       your logic: 250 + 50 = 300                             │
  │  → write 300 to RocksDB["Alice"]                             │
  └──────────────────────────────────────────────────────────────┘

  FINAL KTABLE STATE:
  ┌────────┬───────┐
  │ key    │ total │
  ├────────┼───────┤
  │ Alice  │  300  │
  │ Bob    │  200  │
  └────────┴───────┘

AGGREGATOR SIGNATURE:
  (K key,  V newRecordValue,  VR currentRocksDBValue)  →  VR updatedValue
        ↑            ↑                  ↑                       ↑
    record key    arriving          read from               written back
                  record            RocksDB                to RocksDB
```

## 5. KStream-KTable Join — Enriching a Stream

Each arriving stream event is matched with the **latest value** for the same key in a KTable. The result is an enriched stream event.

```
KTABLE: user-profiles  (updated separately; always holds latest state)
  ┌──────────┬──────────────────────────────────────────┐
  │ key      │ value                                    │
  ├──────────┼──────────────────────────────────────────┤
  │ "U07"    │ UserProfile { name:"Alice", city:"NY" }  │
  │ "U12"    │ UserProfile { name:"Bob",   city:"LA" }  │
  └──────────┴──────────────────────────────────────────┘

KSTREAM: order-events  (infinite; key must be userId to match the KTable)
  → use selectKey first if key is currently orderId

JOIN FLOW — one arriving event:
  ┌──────────────────────────────────────────────────────────────┐
  │  Stream event arrives:                                        │
  │    key="U07"  value=Order{orderId:"O101", amount:500}         │
  │                                                              │
  │  KTable lookup by key "U07":                                  │
  │    found → UserProfile{name:"Alice", city:"NY"}              │
  │                                                              │
  │  ValueJoiner called:                                          │
  │    (orderValue, profileValue) → EnrichedOrder{               │
  │        orderId:"O101", amount:500,                           │
  │        userName:"Alice", city:"NY"   ← enriched!             │
  │    }                                                         │
  └──────────────────────────────────────────────────────────────┘
          │
          ▼
  OUTPUT KSTREAM: key="U07"  value=EnrichedOrder{...}

KEY RULES:
  KStream key  must equal  KTable key   (join is always by key)
  If KStream key = orderId → selectKey first to change it to userId

  KTable → KStream join is NOT supported.
  A KStream has no fixed boundary, so there is nothing to look up against.
```

## 6. KTable-KTable Join — Merging Two Tables

Two KTables can be joined to produce a third KTable. Whenever either source table updates, the joined result is recomputed automatically.

```
  KTable: user-profiles          KTable: user-preferences
  ┌──────────┬────────────────┐  ┌──────────┬───────────────┐
  │ "U07"    │ Alice / NY     │  │ "U07"    │ theme: dark   │
  │ "U12"    │ Bob   / LA     │  │ "U12"    │ theme: light  │
  └──────────┴────────────────┘  └──────────┴───────────────┘
                   │                          │
                   └────────────┬─────────────┘
                                ▼ .join(...)
                   ┌──────────┬────────────────────────────────┐
                   │ "U07"    │ Alice / NY / theme:dark         │
                   │ "U12"    │ Bob   / LA / theme:light        │
                   └──────────┴────────────────────────────────┘

  OUTPUT: KTable  (automatically re-emits when either source changes)
  RULE: both KTables must use the same key type and same key values
```

## 7. How groupByKey Triggers Repartition

Repartition is needed when a key changed earlier in the topology — it ensures all records for the same new key land in the same partition before stateful nodes run.

```
SCENARIO: selectKey changed key from orderId → userId upstream

  [source topic]  key = orderId
       │
       ▼  orders KStream  ← key was changed by selectKey, repartition PENDING
       │
       ▼ .groupByKey()
  ┌──────────────────────────────────────────────────────────────┐
  │  groupByKey checks: was key changed before this point?       │
  │  YES → repartition initiated NOW                             │
  │                                                              │
  │  1. Records are published to an auto-created topic           │
  │     key=userId → same userId → same partition  (guaranteed)  │
  │                                                              │
  │  2. Sub-Topology 1 reads from that repartition topic         │
  │                                                              │
  │  3. count / aggregate see ALL records for "U07" in one task  ✓│
  └──────────────────────────────────────────────────────────────┘

WITHOUT repartition (wrong):
  Partition-0: U07-order1, U07-order3   → Task-0 counts U07=2
  Partition-1: U07-order2               → Task-1 counts U07=1
  Neither task has the FULL picture!  ✗

WITH repartition (correct):
  Partition-0: U07-order1, U07-order2, U07-order3  → Task-0 counts U07=3  ✓
```

## Quick Reference

```
Operation         │ What it does                           │ Output type          │ Uses RocksDB
──────────────────┼────────────────────────────────────────┼──────────────────────┼──────────────
groupByKey        │ Tell downstream: use the current key.  │ KGroupedStream       │ No
                  │ Triggers repartition if key was changed│                      │
groupBy           │ Change key, always triggers repartition│ KGroupedStream       │ No
count             │ Count records per key                  │ KTable<K, Long>      │ Yes
aggregate         │ Custom aggregation per key             │ KTable<K, VR>        │ Yes
KStream-KTable    │ Enrich each stream event with the      │ KStream<K, VR>       │ Reads KTable
join              │ latest table value for that key        │                      │
KTable-KTable     │ Merge two tables by shared key         │ KTable<K, VR>        │ Yes
join              │                                        │                      │

groupByKey / groupBy  = metadata only (which key to use downstream)
count / aggregate     = do the actual grouping and state management in RocksDB
Initializer runs      = only on FIRST occurrence of a key (RocksDB has no entry yet)
Aggregator runs       = on EVERY record (receives current RocksDB value as input)
```
