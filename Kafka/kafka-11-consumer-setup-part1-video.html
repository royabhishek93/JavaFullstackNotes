Group Coordinator Discovery

Before reading a single message, the consumer must find the broker that manages its group. This is a hash calculation using the group ID and the __consumer_offsets topic.

Kafka cluster: __consumer_offsets topic has 50 partitions hash("order-consumer-group") % 50 → partition 23 Broker 1 holds partitions 1–25 ← leader of partition 23 Broker 2 holds partitions 26–50 ┌─────────────────────────────────────────────────────┐ │ __consumer_offsets │ │ ┌───┬───┬───┬───┬───┬──────┬───┬───┬───┬───┐ │ │ │ 1 │ 2 │...│23 │...│ 25 │26 │...│50 │ │ │ │ └───┴───┴───┴─┬─┴───┴──────┴───┴───┴───┴───┘ │ │ │ leader = Broker 1 │ └────────────────┼────────────────────────────────────┘ │ ▼ GROUP COORDINATOR = Broker 1 (manages "order-consumer-group")

Consumer Joins the Group — Rebalance

When a new consumer joins, the group coordinator triggers a rebalance to redistribute topic partitions fairly among all consumers.

BEFORE: 2 consumers in group, topic has 3 partitions ──────────────────────────────────────────────────────────────────── order-events topic ┌──────┬──────┬──────┐ │ P0 │ P1 │ P2 │ └──┬───┴──┬───┴──────┘ │ │ └──────────────────── no owner yet ▼ ▼ Consumer1 Consumer2 (P0, P1) (P2) ← previous assignment AFTER: 3rd consumer joins → rebalance triggered ──────────────────────────────────────────────────────────────────── Consumer sends to Group Coordinator: "I want to join group: order-consumer-group I am interested in topic: order-events" Group Coordinator reassigns: ┌──────┬──────┬──────┐ │ P0 │ P1 │ P2 │ └──┬───┴──┬───┴──┬───┘ ▼ ▼ ▼ Con-1 Con-2 Con-3 ← new balanced assignment

The Poll Loop Internals

The KafkaListenerContainer runs an infinite loop. On the very first call, it performs group join and offset setup. Every call after that just fetches new data.

while (true) { records = consumer.poll(...) } FIRST POLL CALL: ────────────────────────────────────────────────────── ① Send JoinGroup request → Group Coordinator ↓ receives: partition assignment (e.g. P2) ② Request last committed offset for assigned partition Group Coordinator checks __consumer_offsets ↓ returns: offset 100 (last processed) ③ Send fetch request to partition leader broker "Give me order-events P2 starting at offset 101" ↓ receives: records 101–150 SUBSEQUENT POLL CALLS: ────────────────────────────────────────────────────── ③ only — just fetch next batch, no group coordination AFTER RECEIVING RECORDS: ────────────────────────────────────────────────────── ┌─────────────────────────────────────────────────────┐ │ if auto-commit=true AND commit-interval passed: │ │ commit offset NOW ← before processing! │ │ ⚠ risk: offset committed before processing, │ │ crash → data loss │ │ │ │ for each record: │ │ invoke @KafkaListener method (business logic) │ │ │ │ if auto-commit=false (manual): │ │ commitSync() ← blocks until broker confirms │ │ commitAsync() ← fire and forget │ └─────────────────────────────────────────────────────┘

Heartbeat and Rebalance on Crash

A background thread in the consumer sends heartbeats to the group coordinator. If heartbeats stop, the coordinator assumes the consumer is dead and triggers a rebalance.

HEALTHY CONSUMER: ────────────────────────────────────────────────────── Consumer Group Coordinator │ ── heartbeat ──────────► │ "alive" │ ── heartbeat ──────────► │ "alive" │ ── heartbeat ──────────► │ "alive" │ │ CONSUMER CRASHES / LEAVES: ────────────────────────────────────────────────────── Consumer Group Coordinator │ [crash / leave group] │ │ │ ← heartbeat timeout │ │ session.timeout exceeded │ │ ↓ │ │ REBALANCE triggered │ │ remaining consumers │ │ get reassigned partitions Key config: heartbeat.interval.ms — how often heartbeat is sent session.timeout.ms — how long before declared dead

Auto Offset Reset — Latest vs Earliest

When a consumer starts for the first time with no previously committed offset, this setting determines where it begins reading.

Topic: order-events, Partition P2 ┌─────────────────────────────────────────────────────┐ │ offset: 0 1 2 3 4 ... 98 99 100 │ │ ●───●───●───●───●─...─●───●───● ◄ latest │ │ ▲ │ │ earliest │ └─────────────────────────────────────────────────────┘ auto-offset-reset = latest (DEFAULT) ────────────────────────────────────────────────────── Consumer starts → no previous offset found → start from offset 100 (the next new message) → all past messages are SKIPPED auto-offset-reset = earliest ────────────────────────────────────────────────────── Consumer starts → no previous offset found → start from offset 0 (the very beginning) → reads ALL historical messages Practical impact: consumer already running + new event arrives → reads it (both modes) consumer starts AFTER events were published → latest misses them ✗ → earliest reads them ✓

Complete Consumer Startup Flow

Step 1: @KafkaListener found → KafkaListenerContainer created Step 2: KafkaConsumer object created via ConsumerFactory Step 3: Connect to bootstrap server → fetch cluster metadata Step 4: hash(group.id) % 50 → find partition of __consumer_offsets Step 5: Connect to leader of that partition → Group Coordinator found Step 6: Send JoinGroup request to Group Coordinator Step 7: Group Coordinator runs rebalance → assigns partitions Step 8: Consumer receives partition assignment (e.g. P2) Step 9: Ask Group Coordinator for last committed offset of P2 Step 10: Send fetch request to partition P2 leader broker Step 11: Receive records → process → commit offset Step 12: Repeat step 10–11 forever ↺ Background thread running in parallel: Step B: Send heartbeat to Group Coordinator every N ms If heartbeat stops → Group Coordinator triggers rebalance

Architecture — Wiring Up the email-workers Consumer

"This is the actual consumer setup behind the Notification System's email delivery workers — 20 instances, one group, manual commit."

spring.kafka.consumer.group-id=email-workers spring.kafka.consumer.bootstrap-servers=broker-1:9092,broker-2:9092,broker-3:9092 spring.kafka.consumer.key-deserializer=StringDeserializer spring.kafka.consumer.value-deserializer=ErrorHandlingDeserializer (delegate: Avro) spring.kafka.consumer.enable-auto-commit=false spring.kafka.consumer.auto-offset-reset=earliest ← never skip queued notifications @KafkaListener(topics="notifications.standard.email", groupId="email-workers", concurrency="20") void onMessage(ConsumerRecord<String,NotificationEvent> record, Acknowledgment ack) { // idempotency check → rate limit → call SendGrid → write delivery_status ack.acknowledge(); ← commit AFTER the side effect succeeds }

Scenario-first: "auto-offset-reset=earliest is deliberate here, not the default 'latest.' If this consumer group has never run before (first deploy, or __consumer_offsets was purged), starting from 'latest' would silently skip every notification already queued — earliest guarantees we never drop a backlog on first startup."

Cross Questions Interviewers Ask

Q: Why does group.id determine which broker (group coordinator) a consumer talks to? A: hash(group.id) % 50 picks a partition of __consumer_offsets, and whichever broker leads that partition becomes this group's coordinator — all membership and offset operations for the group route through it. Q: Why is auto-commit dangerous even though it's the simplest option? A: It commits on a fixed timer regardless of whether processing actually finished — a crash between "auto-commit fired" and "side effect completed" silently marks unsent work as done, forever. Q: Why does @KafkaListener with concurrency=20 create 20 separate KafkaConsumer instances, not one shared consumer? A: Kafka's consumer client isn't thread-safe for concurrent poll() calls — Spring creates one full consumer per concurrency thread, each getting its own subset of the group's assigned partitions.

Senior Trap Questions (15 YOE)

Trap 1 — "You deployed a brand-new consumer group to an existing topic with 6 months of history, using auto-offset-reset=earliest, expecting it to 'catch up quickly.' It's still processing a day later. Why?" Answer: "earliest means literally start from the beginning of retained history — 6 months of events at normal processing speed can take far longer than expected to churn through. For a NEW consumer group joining an old topic where historical backlog isn't actually needed, 'latest' or a specific timestamp-based seek is usually the right choice — earliest is for 'never miss anything since this group's own inception,' not 'replay all history.'" Trap 2 — "Two @KafkaListener methods in the same class both set groupId='email-workers' but subscribe to different topics. What actually happens?" Answer: "They're two independent members of the SAME consumer group, each with their own subscription — Kafka's group protocol allows this, but it means partition assignment logic now has to reconcile two different topic subscriptions within one group, which most assignors handle by giving each listener its own dedicated partition set. It works, but it's an unusual pattern that surprises most engineers reading the code later."

WHY We Chose Each Decision

- Why manual commit (Acknowledgment.acknowledge()) instead of auto-commit: ties offset progress to actual side-effect completion, not a timer. - Why earliest as the reset policy: guarantees no silent skip of queued notifications on a fresh consumer group's first startup. - Why concurrency=20 specifically: matches the real downstream bottleneck (SendGrid's rate limit), not an arbitrary "more is better" guess. - Why ErrorHandlingDeserializer wraps the value deserializer: the only interception point that prevents a poison pill from causing an infinite loop.

Top 2 Technologies — Offset Commit Strategy

Manual Commit (Acknowledgment) vs Auto-Commit (enable.auto.commit=true) Why pick Manual (our choice): commit only fires after the side effect (SendGrid call, delivery_status write) genuinely succeeds — no timer-based false "done" markers. Why pick Auto-commit: zero code needed, acceptable when occasional reprocessing or occasional loss on crash is a non-issue. Example 1 (Manual): Notification System's email-workers — a missed commit-after-send would silently lose a real customer notification. Example 2 (Auto-commit): An internal metrics-tailing consumer that just logs event counts for a dashboard — losing a few counts on crash is imperceptible and not worth the extra code.
