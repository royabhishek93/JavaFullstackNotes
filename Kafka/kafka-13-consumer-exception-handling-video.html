Two Places Where Exceptions Can Occur

Every record a consumer fetches passes through exactly two stages before the offset is committed — and an exception at either stage can break your consumer.

Consumer polls from broker │ ▼ ┌─────────────────────────────────────┐ │ Stage 1: Deserialization │ ◄── Exception here = Poison Pill risk │ raw bytes → Java object │ (bad payload, wrong format) └─────────────────────────────────────┘ │ ▼ ┌─────────────────────────────────────┐ │ Stage 2: @KafkaListener │ ◄── Exception here = NullPointer etc. │ your business logic runs here │ (logic bugs, downstream failure) └─────────────────────────────────────┘ │ ▼ Commit offset ✓

The Poison Pill — Infinite Loop Problem

A poison pill is one bad message that causes deserialization to fail every time it is read — because the offset is never committed, the consumer fetches it again and again forever.

SCENARIO: Producer sends plain String "hello", Consumer expects JSON Producer Broker Consumer ┌────────┐ ┌──────────┐ ┌──────────────────────────────┐ │"hello" │─────►│ offset 0 │───────►│ JsonDeserializer("hello") │ └────────┘ └──────────┘ │ ↓ FAILS ✗ │ │ print stack trace │ │ ↓ │ │ poll() again... │ │ ↓ │ │ same offset 0 fetched again │ │ ↓ FAILS ✗ │ │ print stack trace │ │ ↓ │ │ poll() again... ─────────────┘ │ │ INFINITE LOOP — offset never committed └────────────────────────────────────── Even after stopping and restarting the consumer: consumer starts → polls → fetches offset 0 → FAILS again → loop repeats ✗

ErrorHandlingDeserializer — Breaking the Loop

Wrapping your deserializer with ErrorHandlingDeserializer catches the exception before it reaches your code, then logs it and commits the offset so the consumer can move on.

BEFORE (no wrapper): raw bytes ──► JsonDeserializer ──► exception → never committed → infinite loop ✗ AFTER (with ErrorHandlingDeserializer wrapper): raw bytes ──► ErrorHandlingDeserializer ──► JsonDeserializer │ │ │◄──── catches exception ───┘ │ ▼ Default Error Handler logs exception + commits offset ✓ no more infinite loop Configuration in application.properties: spring.kafka.consumer.value-deserializer=ErrorHandlingDeserializer spring.deserializer.value.delegate.class=JsonDeserializer spring.kafka.consumer.key-deserializer=ErrorHandlingDeserializer spring.deserializer.key.delegate.class=StringDeserializer

Default Error Handler — Log and Skip

Without any custom configuration, ErrorHandlingDeserializer uses the built-in DefaultErrorHandler which has zero retries and no storage — it just logs the error and moves on.

┌────────────────────────────────────────────────────────────────┐ │ DefaultErrorHandler (zero config / out of the box) │ │ │ │ max attempts: 0 ← no retry │ │ interval: 0ms ← no delay │ │ recoverer: none ← no DLT, no DB, no alert │ │ │ │ Action: 1. print stack trace │ │ 2. commit offset ← consumer moves forward │ └────────────────────────────────────────────────────────────────┘ │ ▼ Event is SILENTLY LOST ✗ Offset is committed — you can never go back to this message. ⚠ Safe for development. Dangerous in production. Always configure a recoverer in production systems.

Retry With BackOff

You can override the default error handler as a Spring bean and give it a backoff strategy so the consumer retries before giving up.

FIXED BACKOFF (same wait time between every retry) ──────────────────────────────────────────────────────────────── new FixedBackOff(1000L, 2) → interval=1s, maxRetries=2 Attempt-1 FAILS ──► wait 1s ──► Attempt-2 FAILS ──► wait 1s ──► Attempt-3 FAILS │ ▼ Recoverer called (DLT / DB / alert) EXPONENTIAL BACKOFF (wait doubles each retry, capped at a maximum) ──────────────────────────────────────────────────────────────── new ExponentialBackOffWithMaxRetries(5) .setInitialInterval(1000) ← first retry after 1s .setMultiplier(2.0) ← double each time .setMaxInterval(10000) ← never wait more than 10s Attempt-1 FAILS ──► wait 1s Attempt-2 FAILS ──► wait 2s Attempt-3 FAILS ──► wait 4s Attempt-4 FAILS ──► wait 8s Attempt-5 FAILS ──► wait 10s (capped) Attempt-6 FAILS ──────────────────────► Recoverer called ✓ Rule of thumb: Transient errors (timeouts, network blip) → retry helps ✓ Deserialization errors (bad payload) → retry never helps ✗ but DLT still stores the event

Dead Letter Topic (DLT) — Happy Path vs Failure Path

The Dead Letter Topic is a separate Kafka topic where all failed events are stored safely so they are never lost and can be reprocessed or inspected later.

HAPPY PATH ──────────────────────────────────────────────────────────────── order-events ──► Consumer ──► Deserialized OK ──► Process ──► Commit offset ✓ FAILURE PATH (with DLT configured) ──────────────────────────────────────────────────────────────── order-events ──► Consumer ──► Deserialization FAILS │ ▼ Retry 1... Retry 2... all exhausted │ ▼ DeadLetterPublishingRecoverer │ ├──► publishes event to order-events-dlt ✓ │ └──► commit offset ✓ (consumer moves on) DLT topic naming rule (auto-applied by the framework): ┌──────────────────────┬──────────────────────────┐ │ Original topic │ DLT topic │ ├──────────────────────┼──────────────────────────┤ │ order-events │ order-events-dlt │ │ payment-events │ payment-events-dlt │ │ user-signup │ user-signup-dlt │ └──────────────────────┴──────────────────────────┘ You MUST create the DLT topic beforehand — it is not auto-created.

Custom Recovery — DB, Alerts, or Any Action

ConsumerRecordRecoverer is a functional interface — you can pass a lambda to do anything you want when all retries are exhausted: write to a database, send a Slack alert, or call an API.

ConsumerRecordRecoverer is just: void accept(ConsumerRecord<?,?> record, Exception exception) ┌────────────────────────────────────────────────────────────────┐ │ Option A: Dead Letter Topic (framework-provided) │ │ ───────────────────────────────────────────────────────── │ │ ConsumerRecordRecoverer r = new DeadLetterPublishingRecoverer │ │ (kafkaTemplate); │ └────────────────────────────────────────────────────────────────┘ ┌────────────────────────────────────────────────────────────────┐ │ Option B: Custom lambda (write to DB, send alert, log) │ │ ───────────────────────────────────────────────────────── │ │ ConsumerRecordRecoverer r = (record, exception) -> { │ │ database.save(record); // save to DB │ │ alertService.send(exception); // send alert │ │ log.error("Failed: {}", record);// custom log │ │ }; │ └────────────────────────────────────────────────────────────────┘ Both options plug into DefaultErrorHandler the same way: new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 2))

Exception During @KafkaListener Processing

If an exception occurs after deserialization (inside your business logic), there is no infinite loop risk — DefaultErrorHandler is always wired in automatically by Spring Kafka.

order-events ──► Deserialized OK ──► @KafkaListener │ ▼ NullPointerException ✗ │ ▼ DefaultErrorHandler ← auto-present, no config needed logs + commits offset ✓ (no infinite loop) ✓ No wrapper needed — the framework catches it automatically. ✗ But the default still loses the event unless you add a Recoverer. Solution: same DefaultErrorHandler bean you created for deserialization errors works here too — retry + recoverer applies to BOTH exception types. SAME SOLUTION FOR BOTH STAGES: ┌──────────────────────────────────────────────────────────────────────┐ │ @Bean │ │ DefaultErrorHandler errorHandler(DeadLetterPublishingRecoverer r) { │ │ return new DefaultErrorHandler(r, new FixedBackOff(1000L, 2)); │ │ } │ └──────────────────────────────────────────────────────────────────────┘

Architecture — Big Picture: Where Error Handling Sits in the Pipeline

Here's how I'd frame this live: "Before I show you retry configs, let me show you where in the pipeline this even matters — because error handling isn't a bolt-on, it's a parallel path that exists alongside the happy path from day one."

Producer ──► order-events (100 partitions) ──► Consumer Group "order-workers" │ ┌───────────┴────────────┐ ▼ ▼ Stage 1: Deserialize Stage 2: @KafkaListener (ErrorHandlingDeserializer) (business logic) │ │ └───────────┬────────────┘ ▼ DefaultErrorHandler (retry with BackOff) │ retries exhausted ──┴── success ──► commit offset ✓ │ ▼ DeadLetterPublishingRecoverer │ ▼ order-events-dlt (separate topic) │ ┌─────────┴─────────┐ ▼ ▼ Ops dashboard / alert Manual reprocessing job (replay into order-events once root cause fixed)

Scenario-first — why we need this at all: "Imagine we ship without any of this. One malformed JSON payload from an upstream team's bad deploy hits our topic. Without ErrorHandlingDeserializer, that single message freezes the entire partition forever — every consumer restart just re-fetches the same poison pill and dies again. That's not a hypothetical; that's an on-call page at 3am with no obvious root cause until someone thinks to check the raw bytes. This pipeline exists so one bad message costs us a DLT entry, not an outage."

"API Design" — The Error Handler Configuration Contract

There's no REST endpoint here, but the error handler bean IS the contract every consumer team depends on — I treat it with the same rigor as an API signature.

@Bean DefaultErrorHandler errorHandler(KafkaTemplate<?,?> template) { var recoverer = new DeadLetterPublishingRecoverer(template); var backOff = new ExponentialBackOffWithMaxRetries(5); backOff.setInitialInterval(1000); backOff.setMultiplier(2.0); backOff.setMaxInterval(10000); return new DefaultErrorHandler(recoverer, backOff); } Contract every team must honor: - DLT topic MUST be pre-created: {original-topic}-dlt - DLT topic partition count SHOULD match the original topic (recoverer preserves partition by default — mismatch breaks that) - Consumers of the DLT must be idempotent too — recoverer publish can itself be redelivered on producer retry addNotRetryableExceptions(DeserializationException.class) ← tells the handler "don't waste retries on this, go straight to DLT"

Scenario-first: "The line people skip is `addNotRetryableExceptions`. Without it, a deserialization failure — which will NEVER succeed no matter how many times you retry a bad payload — still burns through all 5 exponential backoff attempts, adding up to 31 seconds of pure wasted latency per bad message before it even reaches the DLT. Classifying which exceptions are worth retrying is part of the design, not an afterthought."

ER-Style Relationship Diagram — How the Pieces Relate

ConsumerRecord (topic, partition, offset, key, value, headers) │ │ on failure, wrapped with ▼ DeserializationException ──OR── (business exception from @KafkaListener) │ │ passed to ▼ DefaultErrorHandler (1) ──configured with──> BackOff (1: Fixed or Exponential) │ │ after retries exhausted, calls ▼ ConsumerRecordRecoverer (1, interface) ──implemented by──> DeadLetterPublishingRecoverer │ (or a custom lambda) │ produces ▼ ProducerRecord ──published to──> DLT Topic (1, "{original}-dlt") │ │ header carries ▼ spring.deserialization-exception.value (raw bytes of the bad payload)

Scenario-first: "The relationship that trips people up in interviews: the recoverer doesn't get the deserialized object — it can't, deserialization is what failed. It gets the raw bytes, preserved specifically in a message header, plus the exception object describing why. That's the only way to actually inspect and potentially fix and replay a poison pill later."

Scenario-first: "Notice the offset only commits AFTER the DLT publish succeeds and acks — not before. If the DLT publish itself fails (broker down), the error handler does not commit, and on restart we correctly retry the whole recovery flow rather than silently losing the poison pill entirely."

Senior Trap Questions (15 YOE) — With Model Answers

Trap 1 — "Your DLT topic is growing by 50K messages a day and nobody's looking at it. What's actually wrong?" Model answer: "A DLT with no consumer and no alerting isn't a safety net, it's a silent failure graveyard that LOOKS like a safety net. I always pair a DLT with a monitoring consumer or a lag/ volume alert on that specific topic — the DLT existing is necessary but not sufficient; someone or something must actively watch it." Trap 2 — "You added retries with backoff, but now your consumer's max.poll.interval.ms is being exceeded and triggering rebalances. Explain the connection." Model answer: "Retries with backoff execute synchronously inside the poll-process loop by default — 5 retries with exponential backoff maxing at 10s each can add up to 31+ seconds of blocking time per failing record, on top of normal processing. If that pushes total batch time past max.poll.interval.ms, the consumer gets fenced out mid-retry. I size max.poll.interval.ms to account for worst-case retry duration, not just normal processing time." Trap 3 — "A message keeps hitting the DLT, gets manually fixed and republished to the original topic, and immediately fails again with the exact same error. What did the team miss?" Model answer: "They fixed the payload but not the root cause producing it — likely a buggy producer still shipping the same malformed shape for every new event of that type, so the 'fixed' replay succeeds once but the underlying stream of bad data continues. Before replaying from a DLT, I always confirm the upstream producer bug is actually patched, not just the one message in hand." Trap 4 — "Explain precisely why key-deserialization failures are more dangerous to silently handle than value-deserialization failures." Model answer: "The key often determines the partition and is used for compaction/log-compacted topics and for joins in downstream stream processing. A null or corrupted key can silently break partition-level ordering guarantees or ruin a compacted topic's 'latest value per key' semantics in ways that are much harder to detect than a null value, which usually just means one record's business logic doesn't run."

WHY We Chose Each Decision (Rapid-Fire)

- Why ErrorHandlingDeserializer at all: it's the ONLY interception point before your listener code even runs — without it, a bad payload is an infinite loop, not a catchable exception. - Why exponential backoff over fixed: real downstream failures (a slow DB, a rate-limited API) often need increasing recovery time, not a fixed guess. - Why skip retries for deserialization errors specifically: a malformed payload is deterministic — retrying it 100 times produces the exact same failure 100 times. Retries are for transient problems only. - Why a Dead Letter Topic instead of just logging and dropping: logs get rotated/lost and can't be replayed with a script; a Kafka topic is durable, replayable, and lets ops build tooling around it (dashboards, alerts, manual review queues). - Why the DLT topic must be pre-created, not auto-created: an auto-created DLT often gets default partition/replication settings that don't match your durability requirements — explicit creation forces a deliberate decision.

Top 2 Technologies — Failure Handling Strategy

Dead Letter Topic Pattern vs Seek-to-Current / Pause-and-Retry-in-Place Difference: DLT pattern: move the failed record OUT of the main flow into a separate topic, commit the original offset, keep the partition moving for everyone else. Seek-to-current: rewind the consumer's offset back to the failing record and retry it in place, blocking that partition until it succeeds or a limit is hit. Why pick DLT pattern: - One bad record never blocks the rest of the partition's throughput - Durable, replayable, inspectable via normal Kafka tooling - Scales cleanly — 1000 failures = 1000 DLT entries, no partition-wide stall Why pick Seek-to-current: - Guarantees strict in-order processing is never violated — nothing skips ahead - Simpler mental model for low-volume, latency-tolerant pipelines where blocking one partition briefly is genuinely acceptable When DLT is the better fit: High-throughput topics (order events, clickstreams) where strict per-partition ordering across ALL records isn't required, and availability of the rest of the partition matters more than this one record's placement in the sequence. When Seek-to-current is the better fit: A strictly ordered financial ledger topic where record N+1 must never be processed before record N is confirmed successful, even if that means the whole partition pauses during an incident. Example 1 (DLT): Notification System's email/SMS delivery consumers — a malformed webhook payload goes straight to a DLT, the other 99,999 queued notifications keep flowing uninterrupted. Example 2 (Seek-to-current): A ledger-balance-update consumer for a banking system, where processing transaction 501 before transaction 500 is confirmed could produce an incorrect running balance — here, blocking is the safer choice even at a throughput cost.
