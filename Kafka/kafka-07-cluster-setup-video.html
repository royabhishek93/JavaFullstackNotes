Cluster Topology — What We Are Building

We are creating a cluster of four dedicated nodes: two controllers (manage metadata and leader elections) and two brokers (store data and serve producers/consumers). No node does both jobs.

Kafka Binary Folder Structure

When you download and unzip the Kafka binary (e.g. kafka_4.2.0), you get several folders. The two that matter most for setup are bin (executable scripts) and config (properties files).

kafka_4.2.0/ ├── bin/ ← executable shell scripts (wrappers around Kafka Java API) │ ├── kafka-server-start.sh start a controller or broker node │ ├── kafka-storage.sh generate cluster ID, format node storage │ ├── kafka-topics.sh create / delete / describe topics │ ├── kafka-console-producer.sh publish messages from CLI │ ├── kafka-console-consumer.sh consume messages from CLI │ ├── kafka-metadata-quorum.sh check cluster status │ └── ... (many more) │ ├── config/ ← .properties config files (default templates) │ ├── broker.properties template for a broker-only node │ ├── controller.properties template for a controller-only node │ ├── server.properties template for a combined broker+controller node │ └── consumer.properties template for consumer settings │ ├── libs/ ← Kafka JAR files and dependencies │ (bin scripts call the code inside here) │ └── logs/ ← INFO / WARN / ERROR log output (written when you start any server)

Process Roles — Three Modes a Node Can Run In

Every node declares its role using the process.roles property. In production, controllers and brokers are always separated (dedicated roles). A combined node is only useful for quick local experiments.

process.roles = controller ────────────────────────────────────────────────── ┌─────────────────────────────────┐ │ CONTROLLER NODE │ │ - manages cluster metadata │ │ - runs leader elections │ │ - no data storage │ │ - NOT reachable by producers │ └─────────────────────────────────┘ process.roles = broker ────────────────────────────────────────────────── ┌─────────────────────────────────┐ │ BROKER NODE │ │ - stores topic partitions │ │ - serves producers/consumers │ │ - no cluster metadata logic │ └─────────────────────────────────┘ process.roles = controller,broker ← combined (dev/test only) ────────────────────────────────────────────────── ┌─────────────────────────────────┐ │ COMBINED NODE │ │ - does both jobs above │ │ - NOT recommended in prod │ └─────────────────────────────────┘

Listener — What It Is

A listener is a TCP socket that the node opens to accept connections. You give each listener a logical name (a label). The same node can open many ports; each port gets its own name. These names matter because other config properties reference them by name.

Node with ONE listener: ────────────────────────────────────────────────────────── listeners = CONTROLLER://0.0.0.0:9093 CONTROLLER NODE ┌────────────────────────────────────┐ │ │ │ new ServerSocket(9093) │ │ │ │ │ ▼ waiting for TCP connect │ │ ┌─────────────┐ │ │ │ port 9093 │ label: CONTROLLER│ │ └─────────────┘ │ └────────────────────────────────────┘ Node with TWO listeners: ────────────────────────────────────────────────────────── listeners = BROKER://0.0.0.0:9092,INTERNAL://0.0.0.0:9098 BROKER NODE ┌───────────────────────────────────────┐ │ │ │ ┌────────────┐ label: BROKER │ │ │ port 9092 │ ← for producers │ │ └────────────┘ and consumers │ │ │ │ ┌────────────┐ label: INTERNAL │ │ │ port 9098 │ ← for broker-to- │ │ └────────────┘ broker sync │ └───────────────────────────────────────┘ inter.broker.listener.name = INTERNAL ← use this port for broker sync

Controller Configuration — Key Properties

Each controller node gets its own .properties file placed inside the config/ folder. Controller 1 and Controller 2 are nearly identical — only node.id and the port number differ.

controller1.properties controller2.properties ───────────────────────────── ───────────────────────────── process.roles=controller process.roles=controller node.id=1 node.id=2 ▲ └─ unique in the whole cluster listeners=CONTROLLER:// listeners=CONTROLLER:// 0.0.0.0:9093 0.0.0.0:9193 ▲ ▲ └── TCP socket opened here └── different port controller.listener.names=CONTROLLER controller.listener.names=CONTROLLER ▲ ▲ └─ "use the CONTROLLER listener └─ same name must match for controller-to-controller across both nodes communication" controller.quorum.voters= controller.quorum.voters= 1@localhost:9093, 1@localhost:9093, 2@localhost:9193 2@localhost:9193 ▲ ▲ └─ static list of ALL └─ both controllers keep controllers in the cluster the same full list listener.security.protocol.map= listener.security.protocol.map= CONTROLLER:PLAINTEXT CONTROLLER:PLAINTEXT ▲ ▲ └─ no TLS/auth (dev mode) └─ must match each other log.dirs=/tmp/controller1-logs log.dirs=/tmp/controller2-logs num.partitions=3 num.partitions=3 default.replication.factor=2 default.replication.factor=2 ▲ └─ controller decides partition layout and replication using these defaults when no value is given at topic creation

Broker Configuration — Key Properties

Each broker also gets its own .properties file in config/. Brokers carry some extra properties that controllers do not have: advertised.listeners, inter.broker.listener.name, and consumer offset settings.

broker1.properties ────────────────────────────────────────────────────────────────── process.roles=broker node.id=3 ← IDs 1 and 2 are taken by controllers listeners=BROKER://0.0.0.0:9092 ← port this broker opens advertised.listeners= ← "tell the controller to store BROKER://localhost:9092 THIS address in cluster metadata so producers/consumers can reach me" inter.broker.listener.name=BROKER ← brokers sync with each other on this same port (can be separate) controller.listener.names=CONTROLLER ← when talking to any controller, use the listener named CONTROLLER (must match the name used in controller.properties) listener.security.protocol.map= BROKER:PLAINTEXT, CONTROLLER:PLAINTEXT ← both channels use no encryption log.dirs=/tmp/broker1-logs log.retention.hours=168 ← keep data for 7 days log.segment.bytes=1073741824 ← max 1 GB per segment file offsets.topic.replication.factor=2 ← consumer offset topic replication (broker manages consumer offsets, NOT the controller)

advertised.listeners — How Producers Find the Right Broker

When a producer wants to publish to a topic, it does not know which broker holds the leader partition. This diagram shows the full journey that advertised.listeners enables.

STARTUP (broker registers itself) ────────────────────────────────────────────────────────────── Broker 1 starts │ ▼ Sends its advertised.listeners (localhost:9092) to Controller │ ▼ Controller stores it in Cluster Metadata: ┌───────────────────────────────────────────────────────┐ │ Cluster Metadata │ │ topic: order-events │ │ partition-0: leader=Broker1 address=localhost:9092│ │ partition-1: leader=Broker2 address=localhost:9192│ └───────────────────────────────────────────────────────┘ PUBLISH TIME (producer connects) ────────────────────────────────────────────────────────────── Producer │ 1. connect to any broker (bootstrap) ▼ Broker 1 │ 2. fetch metadata from active controller ▼ Controller │ 3. return cluster metadata ▼ Broker 1 → returns metadata to Producer │ ▼ Producer now knows: partition-0 leader = Broker 1 @ localhost:9092 │ 4. send records directly to Broker 1:9092 ▼ Broker 1 ✓

Cluster Bootstrap — Generate ID and Format Nodes

Before starting any server you must tie all four nodes to the same cluster. This is a two-step one-time operation per cluster: generate one UUID, then stamp every node with it.

STEP 1 — Generate cluster ID (run once) ────────────────────────────────────────────────────────────── $ bin/kafka-storage.sh random-uuid → xAb3Kz9pQmNrLuVwYtCiDe (example UUID) STEP 2 — Format each node's storage (run once per node) ────────────────────────────────────────────────────────────── $ bin/kafka-storage.sh format \ -t xAb3Kz9pQmNrLuVwYtCiDe \ -c config/controller1.properties Repeat for controller2, broker1, broker2 RESULT — meta.properties written to each node's log.dirs ────────────────────────────────────────────────────────────── /tmp/controller1-logs/meta.properties cluster.id=xAb3Kz9pQmNrLuVwYtCiDe node.id=1 /tmp/controller2-logs/meta.properties cluster.id=xAb3Kz9pQmNrLuVwYtCiDe node.id=2 /tmp/broker1-logs/meta.properties cluster.id=xAb3Kz9pQmNrLuVwYtCiDe node.id=3 /tmp/broker2-logs/meta.properties cluster.id=xAb3Kz9pQmNrLuVwYtCiDe node.id=4 ▲ └─ all four nodes share the same cluster.id → they form ONE cluster

Startup Order — Controllers First, Then Brokers

Brokers must find an active controller the moment they start (to load cluster metadata). If you start a broker before any controller is up, the broker has nowhere to register and will fail.

CORRECT startup order ────────────────────────────────────────────────────────────── Terminal 1 Terminal 2 ───────────────────────────── ───────────────────────────── bin/kafka-server-start.sh bin/kafka-server-start.sh config/controller1.properties config/controller2.properties [controller1 STARTED] [controller2 STARTED] │ │ └───────────┬───────────────────┘ │ quorum forms, leader elected ▼ Terminal 3 Terminal 4 ───────────────────────────── ───────────────────────────── bin/kafka-server-start.sh bin/kafka-server-start.sh config/broker1.properties config/broker2.properties [broker1 STARTED, node.id=3] [broker2 STARTED, node.id=4] WRONG startup order ✗ ────────────────────────────────────────────────────────────── Start broker1 first │ ▼ tries to contact controller → no controller up → ERROR

Controller Leader Election

When multiple controllers start, they run a Raft-based quorum election to choose one leader. The leader is the active controller — the single source of truth for cluster metadata. You can inspect who won by checking the quorum-state file.

QUORUM ELECTION AFTER STARTUP ────────────────────────────────────────────────────────────── Controller 1 Controller 2 ┌──────────────┐ ┌──────────────┐ │ starts up │◄─────►│ starts up │ │ │ │ │ │ I want to │ │ I want to │ │ be leader! │ │ be leader! │ └──────┬───────┘ └──────┬───────┘ │ Raft vote │ └──────────┬────────────┘ ▼ Leader = Controller 1 (node.id=1) Follower = Controller 2 (node.id=2) VERIFY via quorum-state file: ────────────────────────────────────────────────────────────── /tmp/controller2-logs/ └── quorum-state { "leaderId": 1, ← node.id 1 won the election "epoch": 1 } VERIFY via CLI: ────────────────────────────────────────────────────────────── $ bin/kafka-metadata-quorum.sh \ --bootstrap-server localhost:9092 describe --status Output: LeaderId: 1 ← active controller CurrentVoters: [1, 2] ← the two controllers CurrentObservers: [3, 4] ← the two brokers ClusterId: xAb3Kz9pQmNrLuVwYtCiDe

Topic Creation and Partition Distribution

Creating a topic requires calling a broker (not the controller directly). The controller then decides which broker holds which partition and which replicas are followers.

TOPIC CREATION COMMAND ────────────────────────────────────────────────────────────── $ bin/kafka-topics.sh \ --bootstrap-server localhost:9092 \ --create \ --topic order-events (no --partitions or --replication-factor given → controller uses defaults from config: 3 partitions, RF=2) RESULT — partition layout decided by controller ────────────────────────────────────────────────────────────── Topic: order-events ┌────────────────────────────────────────────────────┐ │ Partition 0 Leader=4 Replicas=[4,3] ISR=[4,3]│ │ Partition 1 Leader=3 Replicas=[3,4] ISR=[3,4]│ │ Partition 2 Leader=4 Replicas=[4,3] ISR=[4,3]│ └────────────────────────────────────────────────────┘ │ │ ▼ ▼ node.id=4 node.id=3 Broker 2 Broker 1 Replication factor = 2 → every partition stored on 2 brokers ISR = In-Sync Replicas (followers caught up with leader) DESCRIBE command to verify: ────────────────────────────────────────────────────────────── $ bin/kafka-topics.sh \ --bootstrap-server localhost:9092 \ --describe \ --topic order-events

Architecture — Standing Up the 3-Broker Cluster

"Here's how I'd actually stand up the cluster the Notification System runs on — 3 nodes, each acting as both controller voter and broker, KRaft mode."

Node-1 (process.roles=controller,broker, node.id=1) Node-2 (process.roles=controller,broker, node.id=2) Node-3 (process.roles=controller,broker, node.id=3) controller.quorum.voters=1@node1:9093,2@node2:9093,3@node3:9093 Provisioning order: 1. kafka-storage.sh random-uuid → one shared cluster ID 2. kafka-storage.sh format (on EACH node) → stamps meta.properties 3. Start controllers/brokers on all 3 nodes (combined role, any order is fine since each node IS both) 4. kafka-topics.sh --create notifications.critical.sms --partitions 100 --replication-factor 3

Scenario-first: "Running combined controller+broker roles on all 3 nodes is the pragmatic small-cluster choice — dedicated controller-only nodes matter once you're running dozens of brokers, where controller and data-plane resource contention becomes real."

ER Relationship + Sequence — From Empty Disk to Live Topic

ER: Cluster (1) ──has ID from──> kafka-storage.sh random-uuid Node (N) ──formatted with──> meta.properties (cluster.id, node.id) Node ──votes in──> controller.quorum.voters (if process.roles includes controller) SEQUENCE: Admin Node-1 Node-2 Node-3 ActiveController │ storage format (all 3, same cluster ID) │ │──────────►│─────────────►│─────────────►│ │ │ start all 3 nodes │ │───────────────────────────────────────────────────────►│ quorum forms, │ │ Node-1 elected active │ kafka-topics.sh --create notifications.critical.sms │ │──────────────────────────────────────────────────────►│ assigns partition │ │ leaders across all 3

Scenario-first: "Notice topic creation always routes through the active controller, even though the admin CLI can technically contact any broker — that broker just forwards the request. This is the same pattern as everything else in KRaft: brokers serve data, only the controller decides metadata."

Cross Questions Interviewers Ask

Q: Why must every node run kafka-storage.sh format with the SAME cluster ID? A: The cluster ID is how nodes recognize they belong together — mismatched IDs would mean nodes reject each other's Raft messages, effectively forming separate, disconnected clusters. Q: Why separate advertised.listeners from the internal listener a broker binds to? A: The bind address (0.0.0.0 internally, say) is often different from what external clients or other brokers should actually connect to (a DNS name or public IP) — advertised.listeners is the "here's how to reach me" address published in cluster metadata. Q: Why start controllers before brokers in a dedicated-role cluster? A: Brokers need a quorum to register with and fetch initial metadata from — starting them before any controller exists just means they retry/fail until one comes up.

Senior Trap Questions (15 YOE)

Trap 1 — "You ran kafka-storage.sh format on Node-1 and Node-2 with the same cluster ID, but Node-3 was formatted separately months earlier with a different random UUID by mistake. What happens when all 3 start together?" Answer: "Node-3 will refuse to join the quorum — its stamped cluster ID in meta.properties doesn't match what Node-1/Node-2 are advertising, so from Node-3's perspective it thinks it's a member of a DIFFERENT cluster. You'd see it fail to form quorum or reject Raft messages, and the fix is re-running format on Node-3 with the correct shared cluster ID (which wipes its local data — a real operational gotcha if it already held data)." Trap 2 — "advertised.listeners on Node-2 points to an internal-only hostname that external producers can't resolve. What symptom would you actually see, and where would you look first?" Answer: "Producers can successfully fetch initial metadata from ANY broker, but when the metadata says 'partition 7's leader is at that unresolvable hostname,' the actual produce call to Node-2 times out or fails DNS resolution — intermittent, partition-specific failures rather than a clean, obvious full outage. I'd check advertised.listeners on the specific broker leading the failing partitions first, not assume it's a network-wide issue."

WHY We Chose Each Decision

- Why 3 nodes with combined controller+broker roles: matches the actual scale of the Notification System's cluster without unnecessary node count. - Why a shared cluster ID via kafka-storage.sh: gives every node a single, unambiguous identity to agree on before any Raft consensus can happen. - Why start controllers before brokers (conceptually, even in combined-role clusters): brokers need a quorum to register against from their first moment up. - Why RF=3 across all critical topics: tolerates one broker failure without blocking writes or losing acknowledged data.

Top 2 Technologies — Combined vs Dedicated Node Roles

Combined Controller+Broker Nodes vs Dedicated Controller-Only Nodes Why pick Combined (our choice at this scale): fewer total machines to provision and patch, adequate for a 3-node cluster where controller workload is genuinely light. Why pick Dedicated: at large broker counts, controller metadata operations (topic creation, leader elections) can contend with data-plane I/O on the same node — isolating them protects both workloads' latency. Example 1 (Combined): Notification System's 3-node cluster — controller work is a tiny fraction of total load, no reason to isolate it. Example 2 (Dedicated): A 50-broker cluster at a large e-commerce platform running thousands of topics — controller-only nodes are isolated so a burst of topic creation activity never competes with live traffic I/O.
