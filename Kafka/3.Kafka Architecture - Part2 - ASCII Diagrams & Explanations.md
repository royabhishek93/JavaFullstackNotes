# Kafka Architecture Part 2 — ASCII Diagrams & Explanations

Topics: Consumer Groups, Offsets, `__consumer_offsets`, Leader/Follower, Cluster, Commit Strategies

---

## 1. Consumer Groups

A **consumer group** is a team of consumers that split the work of reading a topic together.
Each consumer in the group handles different partitions — no two consumers in the same group read the same partition.

```
                       KAFKA BROKER
             ┌──────────────────────────────┐
             │  Topic: order-events         │
             │  ┌──────┐ ┌──────┐ ┌──────┐ │
             │  │ P-0  │ │ P-1  │ │ P-2  │ │
             └──┴──┬───┴─┴──┬───┴─┴──┬───┘─┘
                   │        │        │
          ┌────────┘   ┌────┘   ┌───┘
          │            │        │
          ▼            ▼        ▼

Group: "notification"              Group: "analytics"
┌──────────────────────┐           ┌──────────────────────┐
│  Consumer1 → P-0     │           │  Consumer4 → P-0     │
│  Consumer2 → P-1     │           │  Consumer5 → P-1,P-2 │
│  Consumer3 → P-2     │           └──────────────────────┘
└──────────────────────┘
```

**Key Rules:**
- Same group → each partition goes to only one consumer
- Different groups → same partition can be read by consumers in both groups simultaneously

## 2. Partition Assignment Scenarios

How partitions get assigned depends on the number of consumers vs partitions:

```
Scenario A: consumers == partitions  (ideal 1-to-1)
──────────────────────────────────────────────────
  P-0 ──► Consumer1
  P-1 ──► Consumer2
  P-2 ──► Consumer3

Scenario B: consumers < partitions  (some consumers handle more)
──────────────────────────────────────────────────────────────────
  P-0 ──► Consumer1
  P-1 ──► Consumer1   ← Consumer1 handles 2 partitions
  P-2 ──► Consumer2

Scenario C: consumers > partitions  (some sit idle)
───────────────────────────────────────────────────
  P-0 ──► Consumer1
  P-1 ──► Consumer2
  P-2 ──► Consumer3
  Consumer4 ← IDLE, no partition assigned!
```

## 3. Offset — The Bookmark

An **offset** is just a number — the position of the last successfully processed message.
Each consumer group tracks its own offset per partition, independently.

```
Topic: order-events, Partition-0
─────────────────────────────────────────────────────────────
Events:  [0][1][2]...[299][300][301]...[499][500][501]...
                          ▲                   ▲
                          │                   │
              analytics group           notification group
              "I've read up to 300"     "I've read up to 500"
```

Same partition, two groups, two different bookmarks — completely independent!

---

## 4. Where Is the Offset Stored? (`__consumer_offsets`)

Kafka stores offsets **inside Kafka itself** — in a special internal topic called `__consumer_offsets`.
Kafka auto-creates this topic with **50 partitions** by default.

```
Step 1: Consumer finishes reading P-0, reaches offset 500

  Consumer (group: notification)
       │
       │  builds this commit message:
       ▼
  ┌─────────────────────────────────────────┐
  │  group_id  = "notification"             │
  │  topic     = "order-events"             │
  │  partition = 0                          │
  │  offset    = 500                        │
  └─────────────────────────────────────────┘

Step 2: Figure out which partition of __consumer_offsets to write to

  hash("notification") % 50  =  23
                                  │
                                  ▼
  ┌──────────────────────────────────────────────────────────┐
  │          __consumer_offsets  (50 partitions)             │
  │   P-0  P-1 ... P-22 [ P-23: notification data ] P-24 ...│
  └──────────────────────────────────────────────────────────┘

Why hash? So the same group ALWAYS maps to the same partition — consistent reads & writes.
Why 50 partitions? Many groups can store offsets in parallel without a bottleneck.
```

## 5. Consumer Crash & Recovery

This is the payoff of storing offsets in Kafka — consumers can resume after a crash with no data loss.

```
BEFORE CRASH:
─────────────────────────────────────────────────────────────
  Consumer1 (notification group) reads order-events P-0
  Reaches offset 500 → commits to __consumer_offsets
  Stored: {notification, order-events, P-0} = 500

  Consumer1  ✗  CRASHES

RECOVERY:
─────────────────────────────────────────────────────────────
  Consumer2 is assigned P-0 (takes over)
       │
       │  1. Compute: hash("notification") % 50 → partition 23
       │  2. Ask broker holding partition 23:
       │     "For group=notification, topic=order-events, P-0 — last offset?"
       │  3. Gets back: 500
       │
       ▼
  Consumer2 starts reading from offset 501  ✓
```

## 6. Kafka Cluster — Multiple Brokers

A **Kafka cluster** is just multiple brokers (servers) working together.
Each broker holds some partitions. No single broker holds everything.

```
┌────────────────────────────────────────────────────────────────────┐
│                         KAFKA CLUSTER                              │
│                                                                    │
│  ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐   │
│  │    Broker 1     │  │    Broker 2     │  │    Broker 3     │   │
│  │                 │  │                 │  │                 │   │
│  │  P-0 (LEADER)   │  │  P-1 (LEADER)   │  │  P-2 (LEADER)   │   │
│  │  P-1 (follower) │  │  P-2 (follower) │  │  P-0 (follower) │   │
│  └─────────────────┘  └─────────────────┘  └─────────────────┘   │
│                                                                    │
│  Topic: order-events  |  3 partitions  |  replication factor = 2  │
└────────────────────────────────────────────────────────────────────┘
```

**Benefits:**
- **Scalability** — load is spread across multiple servers
- **Fault Tolerance** — if one broker dies, others keep running
- **High Availability** — no single point of failure

## 7. Leader vs Follower

For every partition, one broker is the **leader** (does real work) and others are **followers** (silent backups).

```
Producer writes to P-0:
─────────────────────────────────────────────────────────────
  Producer ──────────────────────► Broker 1  (P-0 LEADER)
                                        │
                                        │  replicates automatically
                                        ▼
                                   Broker 3  (P-0 follower)
                                   [stays in sync, never serves clients]

Consumer reads from P-0:
─────────────────────────────────────────────────────────────
  Consumer ──────────────────────► Broker 1  (P-0 LEADER)
                                   Follower is invisible to consumers.

Broker 1 crashes:
─────────────────────────────────────────────────────────────
  Broker 1  ✗  DOWN

  Broker 3's P-0 follower ──────► promotes to NEW LEADER
  Cluster stays up, no data lost  ✓
```

**Leader responsibilities:**
- Handle all producer writes
- Handle all consumer reads
- Maintain partition logs
- Sync data to followers

**Follower responsibilities:**
- Replicate data from leader
- Stay in sync
- Be ready to become leader if needed
- Never serve clients directly

## 8. Who Decides Which Broker Holds What?

A special broker called the **Controller** makes all assignment decisions.

```
Kafka Cluster
┌─────────────────────────────────────────────────────┐
│                                                     │
│  ┌──────────────┐                                   │
│  │  CONTROLLER  │  ← one of the brokers takes       │
│  │  (Broker 1)  │    this special role              │
│  └──────┬───────┘                                   │
│         │  decides:                                 │
│         │  - which broker hosts which partition     │
│         │  - which replica is leader                │
│         │  - which replica is follower              │
│         │  - re-assigns when a broker dies          │
│         ▼                                           │
│    Broker 2,  Broker 3  follow controller's orders  │
└─────────────────────────────────────────────────────┘
```

## 9. Offset Commit Strategies

How and when consumers commit (save) their offset bookmark.

```
AUTO COMMIT  (risky — can lose data)
─────────────────────────────────────────────────────────────────────
Timeline:
  t=0s   Poll → receive events [0..99]
  t=1s   Start processing...
  t=5s   AUTO COMMIT fires → stores "99 processed" in __consumer_offsets
  t=6s   Consumer CRASHES at event 70  ✗

Restart:
  Asks "__consumer_offsets" → gets back 99
  Starts from 100  ← events 70–99 are LOST FOREVER!

Problem: commit happened before processing was done.
```

```
MANUAL COMMIT — full batch  (recommended)
─────────────────────────────────────────────────────────────────────
Timeline:
  t=0s   Poll → receive batch [0..99]
  t=1s   Processing events...
  t=3s   Consumer CRASHES at event 70  ✗

Restart:
  Asks "__consumer_offsets" → gets back last manual commit (e.g. -1 / 0)
  Re-processes events 0–69 (duplicates, but safe)  ✓
  Continues and finishes batch [0..99]
  COMMITS → stores 99 in __consumer_offsets  ✓
  Next poll starts from 100  ✓

Trade-off: possible duplicate processing, but ZERO data loss.
```

```
MANUAL COMMIT — per event  (not recommended)
─────────────────────────────────────────────────────────────────────
  Process event 0 → commit(0)
  Process event 1 → commit(1)
  Process event 2 → commit(2)
  ...

Problem: 1 network call per event → huge overhead when processing
         millions of messages. Kafka is built for high throughput;
         per-event commits kill performance.
```

**Recommendation:** Manual commit with an appropriate batch size based on your use case.

## Quick Reference Card

| Concept | What it is | Key point |
|---|---|---|
| Consumer Group | Team of consumers sharing a topic | Each partition goes to only 1 consumer in a group |
| Offset | Bookmark (message position) | Stored per group, per partition |
| `__consumer_offsets` | Internal Kafka topic | 50 partitions, stores all group offsets |
| Leader partition | The active replica | Handles all reads & writes |
| Follower partition | Backup replica | Syncs silently, takes over if leader dies |
| Controller | Special broker | Assigns leaders/followers, manages cluster |
| Auto commit | Kafka commits on a timer | Risky — can lose messages on crash |
| Manual commit | You decide when to commit | Safe — use batch-level commits |
