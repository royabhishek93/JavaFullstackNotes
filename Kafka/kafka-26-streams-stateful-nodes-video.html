Why Stateful? The Memory Problem

Stateless nodes process each record in isolation — they remember nothing. Stateful nodes must remember previous records to compute a correct result.

STATELESS (filter) — no memory needed: record-1 ──► filter(amount > 500) ──► pass or drop (no history needed) record-2 ──► filter(amount > 500) ──► pass or drop record-3 ──► filter(amount > 500) ──► pass or drop STATEFUL (count per user) — memory IS needed: record-1 user:Alice ──► How many so far? Must remember! record-2 user:Bob ──► ... record-3 user:Alice ──► Alice count = 2 — only correct if we remembered record-1 SOLUTION: RocksDB state store (local key-value database, one per task, on disk) ┌──────────────────────────────────────────┐ │ RocksDB (per task, local disk) │ │ key │ value │ │ ───────────┼─────── │ │ "Alice" │ 2 │ │ "Bob" │ 1 │ └──────────────────────────────────────────┘ Each task has its OWN RocksDB. They never share state. Every write to RocksDB is also mirrored to a changelog topic in Kafka so state can be rebuilt after a crash.

groupByKey vs groupBy — Entry Point to Stateful Processing

groupByKey and groupBy do not count or aggregate. They set metadata — which key to group by — for the downstream nodes (count, aggregate) to use.

groupByKey — use the EXISTING key (no key change, no repartition): ┌──────────────────────┐ │ KStream │ key = userId (already what we want) │ key: "U07" │ │ value: Order{...} │ └──────────┬───────────┘ │ .groupByKey() ▼ ┌──────────────────────┐ │ KGroupedStream │ metadata: "downstream nodes use the current key" │ key: "U07" │ no repartition needed └──────────────────────┘ groupBy — CHANGE the key (always triggers repartition): ┌──────────────────────┐ │ KStream │ key = orderId (wrong for our goal) │ key: "O101" │ │ value: Order{...} │ └──────────┬───────────┘ │ .groupBy((key, order) → order.getUserId()) ▼ ┌──────────────────────────────────────────────────┐ │ New key = "U07" (userId) │ │ Repartition INITIATED — internal topic created │ │ so all "U07" records land in the same partition │ └──────────────────────────────────────────────────┘ │ ▼ ┌──────────────────────┐ │ KGroupedStream │ metadata: "use userId as group key" └──────────────────────┘ SHORTCUT: if you only need to change the key before grouping, you can either a) selectKey(…).groupByKey() — two steps, repartition at groupByKey b) groupBy(…) — one step, repartition always triggered

count — Event-by-Event State Evolution

count reads the current value from RocksDB, increments it by 1, writes it back, and emits an updated KTable row.

EVENTS ARRIVING (key = user name): ─────────────────────────────────────────────────────────────► time Alice Bob Alice Alice (event-1) (event-2) (event-3) (event-4) ROCKSDB STATE AFTER EACH EVENT: ┌──────────────────────────────────────────────────────────────┐ │ After event-1 (Alice): { Alice: 1 } │ │ After event-2 (Bob): { Alice: 1, Bob: 1 } │ │ After event-3 (Alice): { Alice: 2, Bob: 1 } │ │ After event-4 (Alice): { Alice: 3, Bob: 1 } │ └──────────────────────────────────────────────────────────────┘ KTABLE OUTPUT (one emission per change): ┌──────────┬───────┐ │ key │ count │ ├──────────┼───────┤ │ Alice │ 1 │ ← emitted after event-1 │ Bob │ 1 │ ← emitted after event-2 │ Alice │ 2 │ ← emitted after event-3 (updates Alice row) │ Alice │ 3 │ ← emitted after event-4 (updates Alice row) └──────────┴───────┘ CODE SHAPE: orders .groupByKey() .count(Materialized.as("order-counter-store")) → returns KTable<String, Long>

aggregate — Custom Aggregation Logic

aggregate gives you full control. You provide two things: (1) an initializer that runs the very first time a key is seen, and (2) an aggregator that runs on every subsequent record.

GOAL: sum order amounts per user Input records: Alice→100, Bob→200, Alice→150, Alice→50 ── aggregate flow for key "Alice" ────────────────────────────── STEP 1 — First time "Alice" appears: ┌──────────────────────────────────────────────────────────────┐ │ RocksDB lookup "Alice" → NOT FOUND │ │ → run initializer() → returns 0 │ │ → run aggregator("Alice", 100, rocksDBval=0) │ │ your logic: 0 + 100 = 100 │ │ → write 100 to RocksDB["Alice"] │ └──────────────────────────────────────────────────────────────┘ STEP 2 — Second Alice record (value=150): ┌──────────────────────────────────────────────────────────────┐ │ RocksDB lookup "Alice" → FOUND → 100 │ │ → skip initializer (already initialized) │ │ → run aggregator("Alice", 150, rocksDBval=100) │ │ your logic: 100 + 150 = 250 │ │ → write 250 to RocksDB["Alice"] │ └──────────────────────────────────────────────────────────────┘ STEP 3 — Third Alice record (value=50): ┌──────────────────────────────────────────────────────────────┐ │ RocksDB lookup "Alice" → FOUND → 250 │ │ → aggregator("Alice", 50, rocksDBval=250) │ │ your logic: 250 + 50 = 300 │ │ → write 300 to RocksDB["Alice"] │ └──────────────────────────────────────────────────────────────┘ FINAL KTABLE STATE: ┌────────┬───────┐ │ key │ total │ ├────────┼───────┤ │ Alice │ 300 │ │ Bob │ 200 │ └────────┴───────┘ AGGREGATOR SIGNATURE: (K key, V newRecordValue, VR currentRocksDBValue) → VR updatedValue ↑ ↑ ↑ ↑ record key arriving read from written back record RocksDB to RocksDB

KStream-KTable Join — Enriching a Stream

Each arriving stream event is matched with the latest value for the same key in a KTable. The result is an enriched stream event.

KTABLE: user-profiles (updated separately; always holds latest state) ┌──────────┬──────────────────────────────────────────┐ │ key │ value │ ├──────────┼──────────────────────────────────────────┤ │ "U07" │ UserProfile { name:"Alice", city:"NY" } │ │ "U12" │ UserProfile { name:"Bob", city:"LA" } │ └──────────┴──────────────────────────────────────────┘ KSTREAM: order-events (infinite; key must be userId to match the KTable) → use selectKey first if key is currently orderId JOIN FLOW — one arriving event: ┌──────────────────────────────────────────────────────────────┐ │ Stream event arrives: │ │ key="U07" value=Order{orderId:"O101", amount:500} │ │ │ │ KTable lookup by key "U07": │ │ found → UserProfile{name:"Alice", city:"NY"} │ │ │ │ ValueJoiner called: │ │ (orderValue, profileValue) → EnrichedOrder{ │ │ orderId:"O101", amount:500, │ │ userName:"Alice", city:"NY" ← enriched! │ │ } │ └──────────────────────────────────────────────────────────────┘ │ ▼ OUTPUT KSTREAM: key="U07" value=EnrichedOrder{...} KEY RULES: KStream key must equal KTable key (join is always by key) If KStream key = orderId → selectKey first to change it to userId KTable → KStream join is NOT supported. A KStream has no fixed boundary, so there is nothing to look up against.

KTable-KTable Join — Merging Two Tables

Two KTables can be joined to produce a third KTable. Whenever either source table updates, the joined result is recomputed automatically.

KTable: user-profiles KTable: user-preferences ┌──────────┬────────────────┐ ┌──────────┬───────────────┐ │ "U07" │ Alice / NY │ │ "U07" │ theme: dark │ │ "U12" │ Bob / LA │ │ "U12" │ theme: light │ └──────────┴────────────────┘ └──────────┴───────────────┘ │ │ └────────────┬─────────────┘ ▼ .join(...) ┌──────────┬────────────────────────────────┐ │ "U07" │ Alice / NY / theme:dark │ │ "U12" │ Bob / LA / theme:light │ └──────────┴────────────────────────────────┘ OUTPUT: KTable (automatically re-emits when either source changes) RULE: both KTables must use the same key type and same key values

How groupByKey Triggers Repartition

Repartition is needed when a key changed earlier in the topology — it ensures all records for the same new key land in the same partition before stateful nodes run.

SCENARIO: selectKey changed key from orderId → userId upstream [source topic] key = orderId │ ▼ orders KStream ← key was changed by selectKey, repartition PENDING │ ▼ .groupByKey() ┌──────────────────────────────────────────────────────────────┐ │ groupByKey checks: was key changed before this point? │ │ YES → repartition initiated NOW │ │ │ │ 1. Records are published to an auto-created topic │ │ key=userId → same userId → same partition (guaranteed) │ │ │ │ 2. Sub-Topology 1 reads from that repartition topic │ │ │ │ 3. count / aggregate see ALL records for "U07" in one task ✓│ └──────────────────────────────────────────────────────────────┘ WITHOUT repartition (wrong): Partition-0: U07-order1, U07-order3 → Task-0 counts U07=2 Partition-1: U07-order2 → Task-1 counts U07=1 Neither task has the FULL picture! ✗ WITH repartition (correct): Partition-0: U07-order1, U07-order2, U07-order3 → Task-0 counts U07=3 ✓

Architecture — Where count()/aggregate() Actually Do the Work

"Here's the stateful stage of the delivery-rate topology — where groupByKey's 'metadata only' promise turns into real RocksDB reads and writes."

(after filter + rekey by channel, repartitioned) │ ▼ groupByKey ← metadata only: "use current key (channel) downstream" ▼ windowedBy(1 min) ▼ aggregate(DeliveryStats::new, DeliveryStats::update) │ ├─ Initializer (DeliveryStats::new) → runs ONLY on first event │ for a given (channel, window) combination └─ Aggregator (DeliveryStats::update) → runs on EVERY event, reads current RocksDB value, writes updated value back ▼ KTable<(channel,window), DeliveryStats> → toStream() → sink topic

Scenario-first: "The Initializer/Aggregator split matters operationally: the Initializer is cheap and rare (once per new key), while the Aggregator runs on every single record and is what actually drives your RocksDB read/write load — that's the part to profile if this stage becomes a bottleneck."

Cross Questions Interviewers Ask

Q: Why does groupBy ALWAYS trigger a repartition but groupByKey only SOMETIMES does? A: groupBy lets you supply a brand-new key selector — Streams can't guarantee that new key is already co-located correctly, so it always repartitions. groupByKey reuses the existing key; a repartition is only needed if an EARLIER step already changed that key without Streams having re-partitioned yet. Q: Why is a KStream-KTable join's KTable side described as "reads KTable" rather than "uses RocksDB" like count/aggregate? A: The join READS the KTable's already-materialized RocksDB state per incoming stream record — it doesn't independently manage its own new state store the way count/aggregate do; it depends on state built by an earlier aggregation step. Q: What actually happens if two different keys hash to the same RocksDB entry space? A: They don't — RocksDB entries are keyed by the full (possibly windowed) key, so distinct keys always get distinct entries; there's no collision risk analogous to a hash table bucket collision here.

Senior Trap Questions (15 YOE)

Trap 1 — "Your Aggregator function has a subtle bug: it occasionally returns a NEW object instead of mutating and returning the EXISTING accumulator. Under heavy load, aggregated counts intermittently come out wrong. Why?" Answer: "If the Aggregator doesn't consistently return the properly updated state (e.g., accidentally resets fields on a new object construction instead of adding to the existing accumulator), each call can silently DISCARD prior accumulated state rather than building on it — since RocksDB just stores whatever the Aggregator returns. This is a correctness bug in application logic, not something Kafka Streams can detect or prevent — the framework trusts your Aggregator's output completely." Trap 2 — "A colleague claims groupByKey never needs a repartition 'because the name doesn't mention re-keying.' Give a concrete counter-example where it DOES trigger one." Answer: "If an EARLIER step in the same topology used selectKey() or map() to change the key, and groupByKey is called afterward without an intervening repartition already having happened, Streams still needs to repartition at that groupByKey call to guarantee correct co-partitioning — the operation's own name doesn't exempt it from needing one if the key was changed upstream and never yet physically repartitioned."

WHY We Chose Each Decision

- Why aggregate() over count() for delivery-rate stats: need a richer breakdown (sent/delivered/failed) than a simple count can provide. - Why groupByKey is preferred over groupBy when the key is already correct: avoids an unnecessary repartition when one isn't structurally required. - Why the Initializer/Aggregator split matters for profiling: the Aggregator is what runs per-record and drives actual RocksDB load — the Initializer's cost is comparatively negligible. - Why we trust but carefully test Aggregator correctness: Kafka Streams has no way to detect a logically-buggy Aggregator that silently discards prior state.

Top 2 Technologies — count() vs aggregate() for Metrics

count() vs aggregate() (custom accumulator) Why pick count(): simplest possible operator when you genuinely only need a raw count per key/window — no custom logic needed. Why pick aggregate(): needed when the metric is richer than a count — a breakdown, a running sum with multiple fields, or any custom accumulation logic. Example 1 (count()): A simple "number of DLQ events per hour" alert metric — a raw count is all that's needed. Example 2 (aggregate()): Notification System's delivery-rate stats needing sent/delivered/failed/bounced broken out per channel per window — requires a custom DeliveryStats accumulator.
