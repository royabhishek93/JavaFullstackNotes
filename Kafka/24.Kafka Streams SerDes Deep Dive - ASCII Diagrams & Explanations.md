# Kafka Streams SerDes Deep Dive — ASCII Diagrams & Explanations

Topics: SerDes, Serializer, Deserializer, built-in SerDes, custom SerDes, default SerDes, per-operation SerDes, deserialization error handler, serialization error handler, DeserializationExceptionHandler

## 1. What Is SerDes?

SerDes is short for **Ser**ializer + **De**serializer — two things packaged into one object that handles both converting Java objects into raw bytes (for writing) and converting raw bytes back into Java objects (for reading).

```
Kafka topics and RocksDB always store data as raw bytes.
Your Java code works with typed objects: String, Long, Order, etc.
SerDes bridges the gap in both directions.

  Java object  ──[ Serializer ]──►  bytes      (write to Kafka / RocksDB)
  bytes        ──[ Deserializer ]──► Java object (read from Kafka / RocksDB)

  Serdes = Serializer + Deserializer bundled together:

  Serdes.String() contains:
  ┌──────────────────────────────────────────────────┐
  │  StringSerializer    (String ──► bytes)          │
  │  StringDeserializer  (bytes  ──► String)         │
  └──────────────────────────────────────────────────┘

  When reading  → framework calls Deserializer internally
  When writing  → framework calls Serializer internally
```

## 2. Five Places SerDes Is Needed in a Topology

Every time data crosses the boundary between a Java object and raw bytes, SerDes is required. A typical topology has five such boundaries.

```
┌──────────────────────────────────────────────────────────────────────┐
│                           TOPOLOGY                                   │
│                                                                      │
│  [1] SOURCE                                                          │
│  Read from Kafka topic                                               │
│  bytes ──► Java object          needs DESERIALIZER                  │
│         │                                                            │
│         ▼                                                            │
│  PROCESSOR PIPELINE                                                  │
│  (filter, map, groupBy, join, count …)                               │
│         │                                                            │
│         ├──────────────────────────────────────────────────────┐    │
│         │                                                       │    │
│         ▼                                                       ▼    │
│  [4] ROCKSDB WRITE                                   [5] ROCKSDB READ│
│  Java object ──► bytes                               bytes ──► Java  │
│  (KTable, count, aggregate)                          (join, lookup)  │
│  needs SERIALIZER                                    needs DESERIALIZER│
│         │                                                            │
│         ▼                                                            │
│  [3] REPARTITION (if present)                                        │
│  Write to internal repartition topic                                 │
│  Java object ──► bytes          needs SERIALIZER                    │
│         │                                                            │
│         ▼                                                            │
│  [2] SINK                                                            │
│  Write to output Kafka topic                                         │
│  Java object ──► bytes          needs SERIALIZER                    │
└──────────────────────────────────────────────────────────────────────┘

Simple rule:
  Reading  (from topic or RocksDB)  ──► Deserializer
  Writing  (to topic or RocksDB)    ──► Serializer
```

## 3. Built-In SerDes

Kafka Streams ships with ready-made SerDes for all common Java primitive types — no custom code needed for these.

```
┌──────────────────┬──────────────────────┬──────────────────────────┐
│  SerDes object   │  Java type           │  Typical use             │
├──────────────────┼──────────────────────┼──────────────────────────┤
│ Serdes.String()  │  String              │  keys, names, JSON text  │
│ Serdes.Long()    │  Long                │  counts, timestamps      │
│ Serdes.Integer() │  Integer             │  IDs, quantities         │
│ Serdes.Double()  │  Double              │  prices, scores          │
│ Serdes.Float()   │  Float               │  measurements            │
│ Serdes.Short()   │  Short               │  small integers          │
│ Serdes.Boolean() │  Boolean             │  flags                   │
│ Serdes.Bytes()   │  byte[]              │  raw bytes pass-through  │
└──────────────────┴──────────────────────┴──────────────────────────┘

For custom Java objects (Order, Customer, Payment):
  → use the built-in JSON SerDes already provided by the framework, or
  → write your own (covered in section 6)
```

## 4. Default SerDes — Set Once in application.properties

You can declare a default SerDes in application.properties so you do not have to repeat it on every builder call. This only works well when every step in the topology uses the same key and value type throughout.

```
application.properties:
  spring.kafka.streams.properties.default.key.serde=
      org.apache.kafka.common.serialization.Serdes$StringSerde
  spring.kafka.streams.properties.default.value.serde=
      org.apache.kafka.common.serialization.Serdes$StringSerde


WITHOUT default SerDes — must specify on every call:
──────────────────────────────────────────────────────────────────
  builder.stream("orders", Consumed.with(Serdes.String(), Serdes.String()))
      .to("output", Produced.with(Serdes.String(), Serdes.String()));

  Materialized.as("store")
      .withKeySerde(Serdes.String())
      .withValueSerde(Serdes.String());


WITH default SerDes — minimal:
──────────────────────────────────────────────────────────────────
  builder.stream("orders")
      .to("output");   ← no SerDes needed, defaults apply


WHY default SerDes is rarely useful in practice:
──────────────────────────────────────────────────────────────────
  Source:           key=String, value=String  ← default works  ✓
  After count():    key=String, value=Long    ← default breaks ✗

  The moment your value type changes mid-pipeline (e.g. after a
  count, aggregate, or map), the default no longer fits.
  Explicit per-operation SerDes is safer and clearer.
```

## 5. Per-Operation SerDes — Explicit and Highest Priority

Providing SerDes directly on each operation overrides any default. This is the recommended approach for production pipelines.

```
KStream (source — reading, so Consumed.with):
  builder.stream(
      "order-events",
      Consumed.with(Serdes.String(), Serdes.String())
  )

KTable (source + RocksDB — both Consumed and Materialized):
  builder.table(
      "order-events",
      Consumed.with(Serdes.String(), Serdes.String()),
      Materialized
          .<String, String, KeyValueStore<Bytes, byte[]>>as("order-store")
          .withKeySerde(Serdes.String())
          .withValueSerde(Serdes.String())
  )

Sink (writing to topic — Produced.with):
  .to("output-topic", Produced.with(Serdes.String(), Serdes.String()))


Priority order (highest wins):
  ┌──────────────────────────────────────────────────────────────┐
  │  [1] Per-operation SerDes (explicit on each call) ← HIGHEST  │
  │  [2] Default SerDes       (application.properties) ← lowest  │
  └──────────────────────────────────────────────────────────────┘

Always use per-operation SerDes when the key or value type
changes at any point in the pipeline.
```

## 6. Custom SerDes — Handling Your Own Java Objects

For domain objects like Order or Customer you create three classes: a Serializer, a Deserializer, and a Serdes wrapper that combines them.

```
STEP 1 — Serializer  (Java object ──► bytes)
──────────────────────────────────────────────────────────────────
  class JsonSerializer<T> implements Serializer<T> {
      byte[] serialize(String topic, T data) {
          return objectMapper.writeValueAsBytes(data);
      }           ↑
  }               Jackson converts any object to JSON bytes


STEP 2 — Deserializer  (bytes ──► Java object)
──────────────────────────────────────────────────────────────────
  class JsonDeserializer<T> implements Deserializer<T> {
      Class<T> targetClass;   ← must know the target type

      T deserialize(String topic, byte[] data) {
          return objectMapper.readValue(data, targetClass);
      }           ↑
  }               Jackson converts JSON bytes back to typed object
                  Serializer does NOT need targetClass (it already has
                  the object); Deserializer DOES (bytes have no type info)


STEP 3 — Serdes wrapper  (combines both into one)
──────────────────────────────────────────────────────────────────
  class JsonSerde<T> implements Serde<T> {
      ┌────────────────────────────────────────────┐
      │  JsonSerializer<T>    ← used when writing  │
      │  JsonDeserializer<T>  ← used when reading  │
      └────────────────────────────────────────────┘
      Serializer<T>   serializer()   { return jsonSerializer;   }
      Deserializer<T> deserializer() { return jsonDeserializer; }
  }


USAGE — pass the custom Serdes just like a built-in one:
──────────────────────────────────────────────────────────────────
  builder.stream(
      "order-events",
      Consumed.with(
          Serdes.String(),              ← key is a plain String
          new JsonSerde<>(Order.class)  ← value is an Order object
      )
  )
  .to("output", Produced.with(
      Serdes.String(),
      new JsonSerde<>(Order.class)
  ));
```

## 7. Deserialization Error Handling

A deserialization error occurs when bytes in a topic cannot be converted to the expected Java type — for example, reading a JSON blob as a Long. Three strategies are available.

```
COMMON CAUSES OF DESERIALIZATION FAILURE
──────────────────────────────────────────────────────────────────
  Type mismatch:   topic has JSON string, you read it as Long      ✗
  Corrupted bytes: garbage bytes, not valid JSON at all            ✗
  Schema change:   new required field added, old consumer breaks   ✗


THREE HANDLERS
──────────────────────────────────────────────────────────────────

  [1] LogAndFailExceptionHandler  (DEFAULT — nothing to configure)
  ┌──────────────────────────────────────────────────────────────┐
  │  Bad record arrives                                          │
  │  → log the error                                             │
  │  → throw exception → stream thread dies                      │
  │  → if all threads die → application shuts down              │
  └──────────────────────────────────────────────────────────────┘
  Safest option: nothing is silently lost.
  application.properties (explicit):
    default.deserialization.exception.handler=
        org.apache.kafka.streams.errors.LogAndFailExceptionHandler


  [2] LogAndContinueExceptionHandler
  ┌──────────────────────────────────────────────────────────────┐
  │  Bad record arrives                                          │
  │  → log the error                                             │
  │  → skip the bad record, continue with next  ✓               │
  │  → bad record is LOST FOREVER               ✗               │
  └──────────────────────────────────────────────────────────────┘
  application.properties:
    default.deserialization.exception.handler=
        org.apache.kafka.streams.errors.LogAndContinueExceptionHandler


  [3] Custom handler  (RECOMMENDED for production)
  ┌──────────────────────────────────────────────────────────────┐
  │  class MyHandler implements DeserializationExceptionHandler  │
  │      Handle(context, record, exception) {                    │
  │          errorCount++;                                       │
  │          if (errorCount > MAX_ERRORS)  return FAIL;          │
  │          else                          return CONTINUE;      │
  │      }   ↑ or route bad record to a dead-letter topic        │
  │  }                                                           │
  └──────────────────────────────────────────────────────────────┘
  You decide: fail fast, skip, or send bad records elsewhere.
  application.properties:
    default.deserialization.exception.handler=
        com.example.MyHandler
```

## 8. Serialization Error Handling

A serialization error occurs when a Java object cannot be converted to bytes — for example, an object with a circular reference that Jackson cannot traverse. Two strategies are available.

```
COMMON CAUSES OF SERIALIZATION FAILURE
──────────────────────────────────────────────────────────────────
  Type mismatch:      sending Order object but SerDes expects Long ✗
  Circular reference: A → B → A → B → … (infinite loop in object) ✗
  Record too large:   object exceeds topic's max.message.bytes     ✗


TWO HANDLERS
──────────────────────────────────────────────────────────────────

  [1] DefaultProductionExceptionHandler  (DEFAULT)
  ┌──────────────────────────────────────────────────────────────┐
  │  Serialization fails                                         │
  │  → always fail                                               │
  │  → stream thread dies                                        │
  │  → if all threads die → application shuts down              │
  └──────────────────────────────────────────────────────────────┘
  application.properties (explicit):
    default.production.exception.handler=
        org.apache.kafka.streams.errors.DefaultProductionExceptionHandler


  [2] Custom handler  (RECOMMENDED for production)
  ┌──────────────────────────────────────────────────────────────┐
  │  class MyProdHandler implements ProductionExceptionHandler   │
  │      Handle(producerRecord, exception) {                     │
  │          if (exception is RecordTooLargeException)           │
  │              return CONTINUE;  ← skip oversized, keep going  │
  │          else                                                │
  │              return FAIL;      ← crash on unexpected errors  │
  │      }                                                       │
  │  }                                                           │
  └──────────────────────────────────────────────────────────────┘
  Inspect the exception type and decide per case.
  application.properties:
    default.production.exception.handler=
        com.example.MyProdHandler
```

## 9. Quick Reference

```
Concept                           What it is                              Key point
────────────────────────────────  ──────────────────────────────────────  ───────────────────────────────────
SerDes                            Serializer + Deserializer in one object  Read → deserialize; Write → serialize
Built-in SerDes                   String, Long, Integer, Double, etc.      Covers all Java primitives out of box
Custom SerDes                     3 classes: Ser + Deser + Serde wrapper   Use JsonSerde for domain objects
5 SerDes boundaries               Source, Sink, Repartition, RocksDB W/R  Every read/write crossing needs SerDes
Default SerDes (app.properties)   Applied when no explicit SerDes given    Lowest priority; breaks when type changes
Per-operation SerDes              Set directly on each builder call        Highest priority; always recommended
LogAndFail (default deser)        Log + crash the thread on bad record     Nothing silently lost; safest default
LogAndContinue (deser)            Skip bad record and keep going           Bad record lost forever — use carefully
Custom deser handler              Your logic: FAIL / CONTINUE / DLQ        Route bad records to dead-letter topic
DefaultProductionHandler          Always fail on serialization error       Thread dies on any serialization issue
Custom production handler         Inspect exception, decide per case       Can CONTINUE on RecordTooLarge etc.
```
