Worked ExampleOrder Counting

Overview

This example counts how many orders each product receives.

The input topic is order-events. Each event contains a product ID and an order amount.

The processing requirement is:

Read order-events | v Keep orders greater than $100 | v Use productId as the key | v Count orders for each product | v Write results to product-counts

Kafka Cluster: Input Topic

Kafka stores the input topic in partitions.

+----------------------------------------------------------------+ | KAFKA CLUSTER | | | | Topic: order-events | | | | +----------------+ +----------------+ +----------------+ | | | Partition P0 | | Partition P1 | | Partition P2 | | | | order events | | order events | | order events | | | +----------------+ +----------------+ +----------------+ | | | +----------------------------------------------------------------+

Kafka chooses a partition using the record key. Records with the same key are normally sent to the same partition.

What is happening?

Kafka breaks the order-events topic into three smaller ordered logs. Each partition stores some of the order messages. Kafka Streams can read these partitions separately, which allows several workers to process orders at the same time.

Complete Topology

The topology is the complete processing plan. It shows all processing steps before Kafka Streams divides the work into tasks.

+----------------------------------------------------------------+ | TOPOLOGY | | | | Source: order-events | | | | | v | | Filter amount > $100 | | | | | v | | Change key to productId | | | | | v | | Group by key | | | | | v | | Count orders | | | | | +---------------------> State Store | | | product-count-store | | v | | Output: product-counts | | | +----------------------------------------------------------------+

The topology is a plan. It is not one worker and it is not one partition.

What is happening?

The topology says what Kafka Streams must do with every order. First it reads the event, removes orders that are not greater than $100, changes the key to productId, groups events with the same product ID, counts them, and writes the result. The topology is only the plan at this stage.

Why Repartitioning Is Needed

Assume the incoming events are keyed by orderId, but the application wants to count by productId.

Before changing the key: orderId 101 -> product P1 orderId 102 -> product P1 orderId 103 -> product P2

The grouping key is changing from orderId to productId, so Kafka Streams must redistribute records by the new key.

order-events | v Filter amount > $100 | v Change key to productId | v Repartition by productId | v Group by key and count

If records are already keyed by productId, this repartition step is usually not needed.

What is happening?

The original key is orderId, but the count is needed by productId. Kafka uses the key to choose a partition, so orders for the same product might be in different partitions when the key is orderId. Kafka Streams changes the key and sends the records to a repartition topic. The new key makes sure the same product is routed consistently.

Sub-Topologies

The repartition topic separates the topology into two independent sections. These sections are called sub-topologies.

+-----------------------------------+ | Sub-topology 0 | | | | Source: order-events | | | | | v | | Filter amount > $100 | | | | | v | | Change key to productId | | | | | v | | Output: repartition topic | +-----------------------------------+ | v +-----------------------------------+ | Sub-topology 1 | | | | Source: repartition topic | | | | | v | | Group by key | | | | | v | | Count | | | | | +--> State store | | | product-count-store | | v | | Output: product-counts | +-----------------------------------+

A sub-topology is simply one independent section of the complete topology.

What is happening?

The first sub-topology reads the original topic, filters the events, changes their keys, and writes them to the repartition topic. The second sub-topology starts by reading that repartition topic, then groups and counts the records. The repartition topic connects the two sections.

Kafka Cluster After Repartitioning

Kafka now contains the original topic and the internal repartition topic.

+---------------------------------------------------------------------+ | KAFKA CLUSTER | | | | +---------------------------+ +-------------------------------+ | | | Topic: order-events | | Internal topic: repartition | | | | | | | | | | +----+ +----+ +----+ | | +----+ +----+ +----+ | | | | | P0 | | P1 | | P2 | | | | P0 | | P1 | | P2 | | | | | +----+ +----+ +----+ | | +----+ +----+ +----+ | | | +---------------------------+ +-------------------------------+ | | | +---------------------------------------------------------------------+

The repartition topic receives records using productId as the key. Therefore, all records for the same product are routed consistently.

What is happening?

The original order-events topic is still present. Kafka Streams creates the internal repartition topic as an additional topic. It writes the filtered events there after assigning productId as the key. The repartition topic also has partitions, so the next sub-topology can process it in parallel.

Tasks Are Created From Partitions

A task is a worker for a particular sub-topology and its partitions.

Sub-topology 0 reads order-events: +----------------+ +----------------+ | order-events | | Task 0_0 | | Partition P0 | ----> | Sub-topology 0 | +----------------+ | Source: P0 | +----------------+ +----------------+ +----------------+ | order-events | | Task 0_1 | | Partition P1 | ----> | Sub-topology 0 | +----------------+ | Source: P1 | +----------------+ +----------------+ +----------------+ | order-events | | Task 0_2 | | Partition P2 | ----> | Sub-topology 0 | +----------------+ | Source: P2 | +----------------+

The task runs the nodes belonging to its sub-topology for its assigned partition.

What is happening?

Kafka Streams creates one task for each partition in this simple example. Task 0_0 reads partition P0 and runs sub-topology 0 on those records. Task 0_1 does the same for P1, and task 0_2 does it for P2. The tasks follow the same steps, but each task handles different records.

Task 0_0: order-events P0 -> Filter -> Change key -> Write repartition topic Task 0_1: order-events P1 -> Filter -> Change key -> Write repartition topic Task 0_2: order-events P2 -> Filter -> Change key -> Write repartition topic

Tasks for the Second Sub-Topology

The second sub-topology reads the repartition topic.

+----------------------+ +----------------+ | repartition topic | | Task 1_0 | | Partition P0 | ----> | Sub-topology 1 | +----------------------+ | Source: P0 | +----------------+ +----------------------+ +----------------+ | repartition topic | | Task 1_1 | | Partition P1 | ----> | Sub-topology 1 | +----------------------+ | Source: P1 | +----------------+ +----------------------+ +----------------+ | repartition topic | | Task 1_2 | | Partition P2 | ----> | Sub-topology 1 | +----------------------+ | Source: P2 | +----------------+

These tasks run the second part of the plan:

Task 1_0: repartition P0 -> Group by productId -> Count -> State store -> product-counts Task 1_1: repartition P1 -> Group by productId -> Count -> State store -> product-counts Task 1_2: repartition P2 -> Group by productId -> Count -> State store -> product-counts

What is happening?

These tasks read the already-repartitioned records. Because the records now use productId as their key, all events for one product reach the same task. That task can calculate the correct count for that product and send the updated count to the output topic.

Stream Threads Execute Tasks

A stream thread executes one or more tasks. A task is the work; a thread is the execution path running that work.

+-----------------------------------+ | Kafka Streams application | | | | Stream Thread 1 | | | | | +--> Task 0_0 | | +--> Task 0_1 | | | | Stream Thread 2 | | | | | +--> Task 0_2 | | +--> Task 1_0 | | | | Stream Thread 3 | | | | | +--> Task 1_1 | | +--> Task 1_2 | | | +-----------------------------------+

The exact assignment can change during a rebalance. Kafka Streams distributes available tasks among the application instances and stream threads.

What is happening?

A stream thread is the execution path that runs tasks. It is not a separate copy of the data. In this example, Thread 1 runs two tasks and the other threads run the remaining tasks. If an application instance stops, Kafka can assign its tasks to another instance during a rebalance.

RocksDB State Store

The Count step must remember the current count for each product. Kafka Streams stores this local state in a state store, usually backed by RocksDB.

Product events | v +------------------+ | Group by product | +------------------+ | v +------------------+ | Count | +------------------+ | +------------------------------+ | | v v +------------------------+ +----------------------+ | RocksDB | | Output topic | | product-count-store | | product-counts | | | | | | P1 -> 2 | | P1 -> 2 | | P2 -> 1 | | P2 -> 1 | +------------------------+ +----------------------+

You normally do not use RocksDB directly. Kafka Streams manages it through the state-store APIs.

What is happening?

The count operation needs to remember the current count for each product. When an event for P1 arrives, Kafka Streams reads the old count, adds one, and stores the new count in the local product-count-store. RocksDB is the local storage engine used behind that store. Kafka Streams manages this storage for you.

Changelog Topic: State Recovery

RocksDB is local to the application instance. Kafka Streams copies state changes to a changelog topic so the state can be rebuilt after a crash.

+------------------------+ +-------------------------------+ | Local RocksDB | | Kafka changelog topic | | product-count-store | ----> | product-count-store-changelog | | | | | | P1 -> 2 | | P1 -> 2 | | P2 -> 1 | | P2 -> 1 | +------------------------+ +-------------------------------+

After a failure:

Application crashes | v Another instance receives the task | v Reads the changelog topic | v Rebuilds local RocksDB state | v Continues processing

What is happening?

RocksDB is local, so it can disappear when an application instance fails. Kafka Streams writes every state change to the changelog topic as well. A replacement task reads that changelog, rebuilds its local state, and then continues from the correct Kafka offset.

One Connected End-to-End Picture

All the pieces now fit together:

+------------------+ +-------------------+ +----------------------+ | Kafka topic | | Sub-topology 0 | | Internal Kafka topic | | order-events | --> | Read | --> | repartition | | P0, P1, P2 | | Filter | | P0, P1, P2 | +------------------+ | Change key | +----------------------+ +-------------------+ | v +-------------------+ +----------------------+ | Sub-topology 1 | --> | State store | | Group by key | | RocksDB | | Count | | product-count-store | +-------------------+ +----------------------+ | v +-------------------+ | Output topic | | product-counts | +-------------------+ | +----> Changelog topic for recovery

Reading the diagram from left to right

1. Kafka stores incoming orders in the order-events topic and its partitions. 2. Sub-topology 0 filters the orders and changes their key to productId. 3. The repartition topic places records with the same product key together. 4. Sub-topology 1 groups and counts those records. 5. The count is stored locally in RocksDB and sent to product-counts. 6. The changelog topic keeps a recoverable copy of the local state.

Final Mental Model

Topic partitions | v Tasks are created for the partitions | v Threads execute the tasks | v Tasks run processor nodes from the topology | +--> Repartition topic when the key changes | +--> RocksDB state store for stateful operations | +--> Changelog topic to recover local state | v Output topic contains the result

In one sentence:

> A topology is the plan, sub-topologies are independent sections, tasks apply > those sections to partitions, threads execute the tasks, repartition topics > move records to the correct key-based partition, and RocksDB stores local > state that Kafka can recover from a changelog topic.

Architecture — Mapping the Order-Counting Example to Our System

"This exact 'count orders per product' pattern is structurally identical to what we'd build for delivery-rate-per-channel — same shape, different domain."

Order-counting example: Notification-reporting equivalent: order-events (keyed by ID) → delivery_status_events (keyed by notif ID) filter(amount > $100) → filter(status in DELIVERED/FAILED) rekey by productId → rekey by channel count per product → count per channel per window product-counts topic → delivery-rate-per-min topic

Scenario-first: "Recognizing this structural similarity is exactly what separates someone who's memorized Kafka Streams syntax from someone who understands the pattern — filter, rekey, aggregate, sink is a repeatable shape you can apply to almost any 'count/sum grouped by some dimension' problem."

Cross Questions Interviewers Ask

Q: Why does this topology need a repartition step at all, when the input is already partitioned by ID? A: Counting per PRODUCT requires all events for a given product to be processed by the SAME task — but the input is partitioned by order ID, not product ID, so Streams must physically re-key and re-write the data to guarantee that co-location. Q: Why filter BEFORE the rekey step in this example, not after? A: Filtering first shrinks what actually needs to flow through the (expensive) repartition topic — filtering after would mean paying the repartition cost for records that get thrown away anyway. Q: What would change if we needed the count across ALL TIME instead of a rolling window? A: Drop the windowedBy() step entirely and aggregate directly into an unwindowed KTable — the trade-off is the state store then grows unbounded instead of having natural window-based cleanup.

Senior Trap Questions (15 YOE)

Trap 1 — "Someone points out that swapping this example's product-counting topology for a completely unwindowed aggregation 'simplifies the code.' What operational cost does that hide?" Answer: "An unwindowed KTable's state store grows without bound for the lifetime of every distinct key ever seen — for a high-cardinality key like product ID over years of operation, that's a genuinely large, ever-growing RocksDB footprint with no natural cleanup mechanism, unlike a windowed store where old windows expire via retention." Trap 2 — "You applied this exact topology shape to a NEW use case with a much higher-cardinality rekey field (say, rekeying by a random session ID instead of product ID). What breaks down?" Answer: "High-cardinality rekeys mean the repartition topic and resulting state store fan out across far more distinct keys, each needing its own state — this can blow up state store size and repartition topic volume compared to a naturally low-cardinality dimension like product or channel. The pattern still works, but the cost profile changes significantly."

WHY We Chose Each Decision

- Why this filter→rekey→aggregate→sink shape generalizes so well: it's the minimal set of operations needed for any "group and count/sum" problem. - Why windowed aggregation over unbounded KTable for rate-style metrics: bounds state store growth via natural retention-based cleanup. - Why filter before rekey, always: shrinks the expensive repartition step to only what's actually needed downstream. - Why recognizing structural pattern reuse matters: lets you apply one well-understood topology shape across many different reporting needs.

Top 2 Technologies — Windowed vs Unbounded Aggregation

Windowed Aggregation vs Unbounded KTable Aggregation Why pick Windowed (our choice for rate metrics): natural, retention-based cleanup — old windows expire automatically, bounding state store size. Why pick Unbounded: needed when the actual business question is a lifetime total, not a rolling rate (e.g., "total orders ever placed by this customer"). Example 1 (Windowed): Notification System's delivery-rate-per-minute — only recent windows matter for the live dashboard. Example 2 (Unbounded): A lifetime "total notifications ever sent to this user" counter used for a customer-support lookup tool.
