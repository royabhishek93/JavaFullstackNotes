## 2. Fetch Request Optimization — One Request Per Broker

When a consumer is assigned multiple partitions, it does NOT send one network request per partition. It sends one request per broker, bundling all partitions that broker leads.

```
  Topic: order-events (3 partitions)
  ┌──────────────────────────────────────────────────┐
  │  P0 leader = Broker 1                            │
  │  P1 leader = Broker 2                            │
  │  P2 leader = Broker 1                            │
  └──────────────────────────────────────────────────┘

  Consumer assigned P0, P1, P2:
  ──────────────────────────────────────────────────────
  ✗ WRONG mental model (3 separate requests):
    Consumer → Broker 1 (P0)
    Consumer → Broker 2 (P1)
    Consumer → Broker 1 (P2)

  ✓ ACTUAL behavior (1 request per broker):
    Consumer ──► Broker 1:  "Give me P0 from offset 5,
                              AND P2 from offset 12"   (1 request)
    Consumer ──► Broker 2:  "Give me P1 from offset 8" (1 request)

    Broker 1 responds → Broker 2 responds
    Consumer merges both responses into one ConsumerRecords object
    Then iterates record by record
```

## 3. ConsumerRecords Structure After Merge

After the poll returns, all records from all partitions are merged into one object and iterated one by one.

```
  ConsumerRecords (merged result of all broker responses)
  ┌────────────────────────────────────────────────────────┐
  │  topic: order-events, partition: P0                    │
  │  ┌────────────────┐ ┌────────────────┐                 │
  │  │ ConsumerRecord │ │ ConsumerRecord │  ← 2 records    │
  │  │ offset:5 key:A │ │ offset:6 key:B │                 │
  │  └────────────────┘ └────────────────┘                 │
  │                                                        │
  │  topic: order-events, partition: P2                    │
  │  ┌────────────────┐                                    │
  │  │ ConsumerRecord │  ← 1 record                        │
  │  │ offset:12 key:C│                                    │
  │  └────────────────┘                                    │
  │                                                        │
  │  topic: order-events, partition: P1                    │
  │  ┌────────────────┐ ┌────────────────┐                 │
  │  │ ConsumerRecord │ │ ConsumerRecord │  ← 2 records    │
  │  │ offset:8 key:D │ │ offset:9 key:E │                 │
  │  └────────────────┘ └────────────────┘                 │
  └────────────────────────────────────────────────────────┘
  Iterated one by one: A → B → C → D → E
  @KafkaListener method invoked once per record
```

## 4. Use Case 1 — One Consumer, Multiple Topics (Manual Mapping)

Declare multiple topics in the `@KafkaListener` annotation. Accept `ConsumerRecord<String, String>` and map JSON to the right class yourself.

```
  application.properties:
  ────────────────────────────────────────────────────────
    value-deserializer = StringDeserializer   ← NOT JSON
    (no default-type needed — no JSON deserializer)

  @KafkaListener code:
  ────────────────────────────────────────────────────────
    @KafkaListener(topics = {"order-events", "payment-events"})
    public void consume(ConsumerRecord<String, String> record) {

        if (record.topic().equals("order-events")) {
            Order o = objectMapper.readValue(record.value(), Order.class);
        } else if (record.topic().equals("payment-events")) {
            Payment p = objectMapper.readValue(record.value(), Payment.class);
        }
    }

  Data flow:
  ────────────────────────────────────────────────────────
  order-events  ──► Consumer ──► raw JSON string
                                    │ objectMapper.readValue()
                                    ▼
                                  Order object

  payment-events ─► Consumer ──► raw JSON string
                                    │ objectMapper.readValue()
                                    ▼
                                  Payment object

  Tradeoff: more code, full control over which class to use
```

## 5. JSON Deserialization Flow — The Full Decision Tree

This flow runs inside the JSON deserializer for EVERY event when `value-deserializer = JsonDeserializer`. Understanding it unlocks all auto-mapping scenarios.

```
  New event arrives at consumer
          │
          ▼
  Is value-deserializer = JsonDeserializer?
  ──────────────────────────────────────────
  NO  → deserialize as String/bytes, done. This flow does not apply.
  YES → continue ↓

          ▼
  Is spring.json.use-type-header = true? (DEFAULT = true)
  ──────────────────────────────────────────────────────────────
  NO (false) ──────────────────────────────────────────────────►┐
                                                                │
  YES ↓                                                         │
                                                                │
  Does the event header contain a type-id key?                  │
  ──────────────────────────────────────────────────────────────│
  NO ──────────────────────────────────────────────────────────►┤
                                                                │
  YES ↓                                                         │
  type-id = "com.eda.producer.Order"                            │
                                                                │
  Is a type mapping configured?                                 │
  (spring.json.type.mapping=producer-order:com.eda.consumer.Order)  │
  ────────────────────────────────────────────────────────────  │
  YES ──► map "com.eda.producer.Order" → Order.class            │
         deserialize JSON → Order object                        │
         invoke @KafkaListener method  ✓                        │
                                                                │
  NO ↓                                                          │
                                                                │
  Is "com.eda.producer.Order" in trusted packages?              │
  (spring.json.trusted-packages=com.eda.producer)               │
  ────────────────────────────────────────────────────────────  │
  YES ──► load class "com.eda.producer.Order" from classpath    │
         found? ──► deserialize JSON → Order object  ✓         │
         NOT found? ──► ClassNotFoundException  ✗              │
                                                                │
  NO ──► IllegalArgumentException: not in trusted packages ✗   │
                                                                │
  ◄──────────────────────────────────────────────────────────── ┘
  Use default-type config
  (spring.json.value-default-type=com.eda.consumer.model.Order)
  ────────────────────────────────────────────────────────────
  → deserialize JSON → default class object
  → invoke @KafkaListener method ✓
```

## 6. Type-ID Header — When Producers Add It

The producer's `JsonSerializer` can embed the source class path into the event header under key `type-id`. This lets the consumer know what kind of object was serialized.

```
  Producer side:
  ──────────────────────────────────────────────────────
  spring.kafka.producer.properties.spring.json.add-type-headers=true
  (this is the DEFAULT — you don't need to write it)

  KafkaTemplate<String, Object> template;   ← generic Object
  template.send("order-events", order);

  Published event header:
  ┌──────────────────────────────────────────────────────┐
  │  headers: { type-id: "com.eda.producer.model.Order" }│
  │  value:   { "id": 332700, "amount": 500 }            │
  └──────────────────────────────────────────────────────┘

  ⚠ Caveat: type-id is added when you use a generic type (Object).
    If you declare KafkaTemplate<String, Order> with the specific
    class, type-id may NOT be added. Always verify your headers.
```

## 7. Use Case 1 — Auto Mapping With Type Mapping Config

Instead of checking `record.topic()` manually, let the JSON deserializer do the conversion automatically using a type mapping.

```
  application.properties:
  ────────────────────────────────────────────────────────────────
    value-deserializer = JsonDeserializer
    default-type = com.eda.consumer.model.Order   ← fallback

    spring.kafka.consumer.properties.spring.json.type.mapping=\
      com.eda.producer.model.Order:com.eda.consumer.model.Order,\
      com.eda.producer.model.Payment:com.eda.consumer.model.Payment

    (no trusted-packages needed when mapping is provided)

  @KafkaListener code:
  ────────────────────────────────────────────────────────────────
    @KafkaListener(topics = {"order-events", "payment-events"})
    public void consume(ConsumerRecord<String, Object> record) {

        if (record.topic().equals("order-events")) {
            Order o = (Order) record.value();   ← just a cast, no parsing
        } else if (record.topic().equals("payment-events")) {
            Payment p = (Payment) record.value();
        }
    }

  Data flow:
  ────────────────────────────────────────────────────────────────
  event arrives → type-id in header = "com.eda.producer.model.Order"
                       │
                       ▼  type mapping lookup
                  "com.eda.consumer.model.Order"
                       │
                       ▼  JSON deserializer maps automatically
                  Order object ready in record.value()
                       │
                       ▼  your code just casts it
```

## 8. Use Case 2 — Multiple Consumers, Different Topics (Shared Factory Problem)

Creating two `@KafkaListener`s — one for orders, one for payments — hits a problem when `use-type-header=false`: both consumers share one `ConsumerFactory`, which has only one `default-type`.

```
  application.properties:
  ────────────────────────────────────────────────────────────────
    spring.json.use-type-header=false
    spring.json.value-default-type=com.eda.consumer.model.Order

  Two @KafkaListeners:
  ────────────────────────────────────────────────────────────────
    @KafkaListener(topics = "order-events")
    public void consumeOrder(Order order) { ... }

    @KafkaListener(topics = "payment-events")
    public void consumePayment(Payment payment) { ... }

  What Spring Boot creates:
  ────────────────────────────────────────────────────────────────
  ┌──────────────────────────────────────────────────┐
  │  ONE ConsumerFactory (from application.properties)│
  │  default-type = Order.class                      │
  │        │               │                         │
  │        ▼               ▼                         │
  │  KafkaConsumer-1  KafkaConsumer-2                │
  │  (order-events)   (payment-events)               │
  │                        │                         │
  │                        ▼                         │
  │              uses same default-type = Order ✗    │
  └──────────────────────────────────────────────────┘

  Result when payment event arrives:
    deserializer tries to map payment JSON → Order.class
    FAILS — wrong type ✗
```

## 9. Use Case 2 — Solution: Custom ConsumerFactory Per Listener

Create two separate `ConsumerFactory` beans, each with its own `default-type`. Wire each factory to its own `ConcurrentKafkaListenerContainerFactory`, then point each `@KafkaListener` at the right factory.

```
  @Configuration class:
  ────────────────────────────────────────────────────────────────

  @Bean
  ConsumerFactory<String, Order> orderConsumerFactory(KafkaProperties props) {
      Map<String, Object> config = props.buildConsumerProperties();
      config.put(JsonDeserializer.VALUE_DEFAULT_TYPE, Order.class); ← override
      return new DefaultKafkaConsumerFactory<>(config);
  }

  @Bean
  ConsumerFactory<String, Payment> paymentConsumerFactory(KafkaProperties props) {
      Map<String, Object> config = props.buildConsumerProperties();
      config.put(JsonDeserializer.VALUE_DEFAULT_TYPE, Payment.class); ← override
      return new DefaultKafkaConsumerFactory<>(config);
  }

  @Bean ConcurrentKafkaListenerContainerFactory orderFactory(...) {
      factory.setConsumerFactory(orderConsumerFactory);
      return factory;
  }

  @Bean ConcurrentKafkaListenerContainerFactory paymentFactory(...) {
      factory.setConsumerFactory(paymentConsumerFactory);
      return factory;
  }

  Result:
  ────────────────────────────────────────────────────────────────
  ┌──────────────────────────────┐  ┌──────────────────────────────┐
  │  orderConsumerFactory        │  │  paymentConsumerFactory       │
  │  default-type = Order.class  │  │  default-type = Payment.class │
  │        │                     │  │        │                      │
  │        ▼                     │  │        ▼                      │
  │  KafkaConsumer               │  │  KafkaConsumer                │
  │  (order-events)        ✓     │  │  (payment-events)       ✓     │
  └──────────────────────────────┘  └──────────────────────────────┘

  @KafkaListener(topics = "order-events",
                 containerFactory = "orderFactory")
  public void consumeOrder(Order order) { ... }

  @KafkaListener(topics = "payment-events",
                 containerFactory = "paymentFactory")
  public void consumePayment(Payment payment) { ... }
```

## 10. Use Case 3 — Multiple Consumers Reading the Same Topic (Concurrency)

To spin up multiple consumers for one topic within a single application, set `concurrency` in `application.properties`. Spring Boot creates that many `KafkaConsumer` objects for the same `@KafkaListener`.

```
  application.properties:
  ────────────────────────────────────────────────────────────────
    spring.kafka.listener.concurrency=3

  @KafkaListener(topics = "order-events")
  public void consume(Order order) { ... }

  What Spring Boot creates:
  ────────────────────────────────────────────────────────────────
  ConcurrentKafkaListenerContainerFactory
  concurrency = 3
        │
        ├──► KafkaConsumer-1  ──► order-events P0 (assigned by coordinator)
        ├──► KafkaConsumer-2  ──► order-events P1
        └──► KafkaConsumer-3  ──► order-events P2

  Group coordinator decides which consumer gets which partition.
  You only say "I want 3 consumers" — assignment is automatic.

  Rule: concurrency > number of partitions → extra consumers sit idle
  ────────────────────────────────────────────────────────────────
  Topic has 3 partitions, concurrency=5:
    Consumer-1 ──► P0  ✓
    Consumer-2 ──► P1  ✓
    Consumer-3 ──► P2  ✓
    Consumer-4 ──► (no partition)  idle ✗
    Consumer-5 ──► (no partition)  idle ✗
```

## 11. Summary — All Three Use Cases Side by Side

```
  USE CASE 1: one consumer, multiple topics
  ────────────────────────────────────────────────────────────────
  Code:   topics = {"order-events", "payment-events"} in one @KafkaListener
  Check:  record.topic() to route to the right class
  Note:   one KafkaConsumer reads both topics

  USE CASE 2: multiple consumers, different topics
  ────────────────────────────────────────────────────────────────
  Code:   two @KafkaListeners, each with its own topic
  If use-type-header=true + mapping:  works with default setup
  If use-type-header=false:           must create custom ConsumerFactory per listener

  USE CASE 3: multiple consumers, same topic
  ────────────────────────────────────────────────────────────────
  Code:   spring.kafka.listener.concurrency=N in application.properties
  Result: N KafkaConsumers created, group coordinator assigns partitions
  Limit:  max useful concurrency = number of partitions in the topic
```

## 12. Quick Reference

```
Concept                        What it does                                    Key point
─────────────────────────────  ──────────────────────────────────────────────  ──────────────────────────────────────
topics = {t1, t2}              Subscribe one consumer to multiple topics       One KafkaConsumer reads both
ConsumerRecord<K, V>           Full event envelope                             Has topic, partition, offset, key, value, headers
Fetch per broker               Consumer sends 1 request per broker             Bundles all partitions that broker leads
use-type-header=true (default) Read class info from event header type-id       Lets deserializer pick the right class automatically
use-type-header=false          Ignore header, use default-type instead         All events deserialized to same class
type-id header                 Producer embeds source class path in header     Added when KafkaTemplate uses generic Object type
spring.json.type.mapping       Map producer class path → consumer class        Avoids trusted-packages and class-not-found issues
trusted-packages               List of packages the deserializer may load      Required when using type-id without type.mapping
default-type                   Fallback class when no header/mapping found     Always required when value-deserializer=JSON
Custom ConsumerFactory         Override default-type per listener              Solution for use-type-header=false + multiple types
containerFactory               Points @KafkaListener at a specific factory     Required when you have multiple factories
concurrency=N                  Creates N KafkaConsumers for one @KafkaListener Group coordinator assigns partitions automatically
Max useful concurrency         Equals number of partitions in the topic        Extra consumers above that count stay idle
```
