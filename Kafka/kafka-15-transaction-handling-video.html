Three Problems That Transactions Solve

Transactions exist to fix three specific failure scenarios in Kafka producers.

PROBLEM 1 — Duplicate on producer restart (idempotency gap) ───────────────────────────────────────────────────────────── Producer crashes → restarts → gets NEW producer ID Old PID lost → sequence numbers reset → duplicates possible PROBLEM 2 — Partial write (atomicity gap) ───────────────────────────────────────────────────────────── Goal: publish order-event AND payment-event AND inventory-event together order-event ──► broker ✓ written payment-event ──► broker ✓ written inventory-event ──► broker ✗ FAILED Result: order placed, payment taken, but stock NOT reserved ← inconsistent! PROBLEM 3 — Read-process-write duplicate (consumer-side) ───────────────────────────────────────────────────────────── Consumer reads offset 50 → processes → publishes new event → tries to commit offset │ offset commit LOST │ Consumer polls again → gets offset 50 again → processes AGAIN → publishes AGAIN ✗ duplicate event published to downstream topic

Transaction ID (transactional.id)

A transaction ID is a stable, human-assigned string that uniquely identifies a producer instance across restarts.

application.properties: spring.kafka.producer.transaction-id-prefix=order-svc- Spring Boot appends "0" automatically → final ID = "order-svc-0" ┌─────────────────────────────────────────┐ │ Rules for transaction-id-prefix │ │ │ │ ✓ Must be STABLE across restarts │ │ ✓ Must be UNIQUE per producer instance │ │ ✗ Never use random UUID ← breaks EOS │ └─────────────────────────────────────────┘ Multiple instances of the same app: Instance 1 → order-svc-pod-abc (use Kubernetes hostname) Instance 2 → order-svc-pod-def Instance 3 → order-svc-pod-ghi Each instance MUST have a different transaction ID (reason: zombie fencing — explained in section 5)

Finding the Transaction Coordinator

The transaction coordinator is the single broker responsible for managing all transactions for a given producer. It is found via a hash of the transaction ID, exactly like how consumer group coordinators are found.

KAFKA CLUSTER ┌─────────────────────────────────────────────────────────────────┐ │ │ │ __transaction_state (internal topic, 50 partitions) │ │ ┌──────┬──────┬──────┬──────┬──────────────────────┐ │ │ │ P-0 │ P-1 │ P-2 │ ... │ P-49 │ │ │ └──┬───┴──┬───┴──┬───┴──────┴──────────────────────┘ │ │ │ │ │ │ │ Broker1 Broker2 Broker3 ← each broker leads some partitions │ └─────────────────────────────────────────────────────────────────┘ Producer with transactional.id = "order-svc-0" Step 1: send FindCoordinator request to ANY broker, pass transaction ID Step 2: that broker computes: partition = hash("order-svc-0") mod 50 → e.g. partition 23 Step 3: broker looks up who is leader of __transaction_state partition 23 → Broker 2 is the leader Step 4: broker replies: "your transaction coordinator is Broker 2" Step 5: producer connects directly to Broker 2 for all future transaction calls Producer ──FindCoordinator──► any broker ──► "use Broker 2" Producer ◄───────────────────────────────────────────────── Producer ──all transaction requests──────────► Broker 2

The __transaction_state Topic — What Gets Stored

For each producer with a transaction ID, the transaction coordinator stores a record in __transaction_state. This is the brain of the transaction system.

Row stored in __transaction_state (partition 23 for "order-svc-0"): ┌───────────────────┬────────────┬───────┬───────────────────────────────────┬─────────────┐ │ transaction_id │ pid (PID) │ epoch │ state │ partitions │ ├───────────────────┼────────────┼───────┼───────────────────────────────────┼─────────────┤ │ "order-svc-0" │ 5 │ 0 │ EMPTY → ONGOING → PREPARE_COMMIT │ [topic-A/0,│ │ │ │ │ → COMMITTED │ topic-B/2]│ │ │ │ │ EMPTY → ONGOING → PREPARE_ABORT │ │ │ │ │ │ → ABORTED │ │ └───────────────────┴────────────┴───────┴───────────────────────────────────┴─────────────┘ field meaning ────────────── ────────────────────────────────────────────────────────────── transaction_id the stable string you set in application.properties pid producer ID — a number assigned by the broker (like idempotency) epoch version counter — increments each time producer (re)initialises state current phase of the transaction lifecycle partitions which topic-partitions are touched by the active transaction timeout max time a transaction can stay ONGOING before auto-abort State flow: EMPTY ──begin──► ONGOING ──commit request──► PREPARE_COMMIT ──► COMMITTED └──abort request──► PREPARE_ABORT ──► ABORTED Once PREPARE_COMMIT or PREPARE_ABORT is written → point of no return Even if broker crashes, on recovery it must finish in that direction

Producer ID, Epoch, and Zombie Fencing

When a producer first connects, it calls initTransactions() to get a producer ID. The epoch (version number) is the key to blocking "zombie" producers — old instances that come back after being replaced.

INIT PRODUCER ID REQUEST (happens once at startup): Producer ──InitProducerID(txn-id="order-svc-0")──► Transaction Coordinator │ check __transaction_state │ ┌─────────────────────────────────────┤ │ First time ever? │ │ → generate PID=5, epoch=0 │ │ → write to __transaction_state │ │ → return PID=5, epoch=0 │ │ │ │ Seen this txn-id before? │ │ → abort any ONGOING transaction │ │ → INCREMENT epoch (0 → 1) │ │ → return same PID=5, epoch=1 │ └─────────────────────────────────────┘ ZOMBIE FENCING — why epoch matters: Time 0: Producer-1 starts → PID=5, epoch=0 → begins transaction (network pause — Producer-1 appears dead to orchestrator) Time 1: Kubernetes spawns Producer-2 (same txn-id "order-svc-0") → calls initTransactions → Coordinator aborts Producer-1's open transaction → epoch 0 → 1 → Producer-2 gets PID=5, epoch=1 Time 2: Old Producer-1 revives and tries to commit (PID=5, epoch=0) → Coordinator checks: current epoch is 1, request says 0 → REJECT with ProducerFencedException ✗ ← zombie blocked! epoch acts like a fencing token — only the holder of the latest epoch is valid

Transaction State Machine

The states a transaction moves through, and what triggers each transition.

┌──────────┐ │ EMPTY │ ← initial state / after last commit or abort └────┬─────┘ │ beginTransaction() ▼ ┌──────────┐ │ ONGOING │ ← events are being sent └────┬─────┘ commit() │ abort() ┌──────────────┘──────────────────┐ ▼ ▼ ┌──────────────────┐ ┌─────────────────┐ │ PREPARE_COMMIT │ │ PREPARE_ABORT │ └────────┬─────────┘ └────────┬────────┘ │ send COMMIT control │ send ABORT control │ records to all brokers │ records to all brokers ▼ ▼ ┌──────────────────┐ ┌─────────────────┐ │ COMMITTED │ │ ABORTED │ └──────────────────┘ └─────────────────┘ │ │ └──────────────┬───────────────────┘ ▼ EMPTY (ready for next transaction) KEY RULE: transaction is single-threaded per producer. While a transaction is ONGOING, you cannot begin another one.

Begin Transaction — Sending Events

Before each send, an interceptor notifies the transaction coordinator which partition will be touched, so it can update the "partitions involved" list.

Producer Transaction Coordinator Partition Leader (Broker) │ │ │ │──beginTransaction()──────► │ │ │ │ state: EMPTY → ONGOING │ │ │ │ │──(interceptor) AddPartitionToTxn(order-events/P2)──────► │ │ │ │ partitions: [order-events/P2] │ │ │ state: still ONGOING │ │◄──OK──────────────────────┘│ │ │ │ │ │──send(order-event, key, value).join()─────────────────────►│ │ │ │ appends to log: │ │ │ PID=5, epoch=0, │ │ │ is_transactional=true │ │ │ [record data] │◄──ACK─────────────────────────────────────────────────────┘│ │ │ │ │──(interceptor) AddPartitionToTxn(payment-events/P1)──────►│ │ │ partitions: [order-events/P2, │ │ │ payment-events/P1]│ │◄──OK──────────────────────┘│ │ │ │ │ │──send(payment-event, ...).join()──────────────────────────►│ (payment broker) │◄──ACK─────────────────────────────────────────────────────┘│ IMPORTANT: always call .join() (or .get()) on each send Future when inside a transaction — this makes your thread wait for the broker ACK. Without it, a failure is detected too late to abort the transaction correctly.

Commit Flow — Two-Phase Commit

Committing a transaction is a two-phase process. The coordinator writes "prepare commit" first (point of no return), then sends commit control records to every affected partition.

Producer Transaction Coordinator Brokers holding touched partitions │ │ │──commitTransaction()─────►│ │ │ 1. write PREPARE_COMMIT to __transaction_state │ │ ← point of no return │ │ │ │──commit control record──► order-events/P2 leader │ │ │ append to log: │ │ │ PID=5, epoch=0, │ │ │ is_control=true, COMMIT │ │◄──done──────────────────────┘│ │ │ │ │──commit control record──► payment-events/P1 leader │ │ │ append to log: │ │ │ PID=5, epoch=0, │ │ │ is_control=true, COMMIT │ │◄──done──────────────────────┘│ │ │ │ │ 2. write COMMITTED to __transaction_state │◄──success────────────────┘│ Partition log (order-events P2) after commit: offset 0: PID=5, epoch=0, is_transactional=true, is_control=false [order record] offset 1: PID=5, epoch=0, is_transactional=true, is_control=true COMMIT ← control record

Abort Flow

Abort is identical to commit, just with ABORT control records instead of COMMIT. No data is deleted — Kafka is append-only. The abort marker tells consumers to skip those records.

Producer Transaction Coordinator Brokers │ │ │──abortTransaction()──────►│ (triggered by exception inside execute-in-transaction) │ │ 1. write PREPARE_ABORT to __transaction_state │ │ │ │──abort control record──► order-events/P2 leader │ │ │ append: PID=5, epoch=0, │ │ │ is_control=true, ABORT │ │◄──done──────────────────────┘│ │ │ 2. write ABORTED to __transaction_state │◄──success────────────────┘│ Partition log (order-events P2) after abort: offset 0: PID=5, epoch=0, is_transactional=true, is_control=false [order record] offset 1: PID=5, epoch=0, is_transactional=true, is_control=true ABORT ← control record NOTE: the original data record at offset 0 is still physically in the log. The ABORT control record at offset 1 is what tells consumers to ignore offset 0.

Architecture — Transactions Wrapping the CDC Publisher

"Here's the real scenario that justifies transactions for the Notification System: one outbox row that must fan out to a primary topic AND an audit topic atomically."

CDC Publisher (transactional.id="cdc-publisher-1", stable across restarts) │ ▼ initTransactions() → fenced any zombie old instance via epoch bump ▼ beginTransaction() │ send(notifications.standard.email, event) │ send(notifications.audit.trail, auditEvent) ▼ commitTransaction() → Coordinator writes COMMIT marker to BOTH partitions │ ▼ read_committed consumers see BOTH records together, or neither

Scenario-first: "Without the transaction, a crash between the two sends leaves the audit topic silently missing an entry that the main topic has — an inconsistency invisible until someone reconciles the two topics manually. The transaction makes that inconsistency structurally impossible."

Cross Questions Interviewers Ask

Q: Why must transactional.id be STABLE across restarts, not a random UUID? A: Fencing works by the coordinator recognizing "this transactional.id now has a newer epoch" — a random id per restart means Kafka can't tell the old (possibly still-alive) instance apart from a totally new producer, defeating the whole zombie-fencing mechanism. Q: What's the actual difference between transactions here and the idempotent producer we covered earlier? A: Idempotence is session-scoped — it only protects against in-flight retries within one producer's lifetime. Transactions add cross-topic atomicity AND survive producer restarts via the coordinator-tracked PID/epoch. Q: Why hash(txn-id) mod 50 to find the coordinator, same pattern as consumer group coordinators? A: Consistent hashing spreads transaction-state load across 50 partitions of __transaction_state, and guarantees the SAME producer always talks to the SAME coordinator broker for its transaction lifecycle.

Senior Trap Questions (15 YOE)

Trap 1 — "A colleague migrates from a fixed transactional.id to a random UUID per pod restart 'to avoid ID collisions.' Two weeks later exactly-once semantics silently broke. Why?" Answer: "Random transactional.id per restart means Kafka can no longer fence out the PREVIOUS instance of the same logical producer — fencing depends on recognizing 'this id has a newer epoch now, reject the old one.' With a fresh random id every restart, the old (possibly still partially alive during a slow shutdown) and new instances look like two completely unrelated producers, both able to write — reintroducing the exact duplicate-write risk transactions exist to prevent." Trap 2 — "Your transaction has been stuck in PREPARE_COMMIT for 10 minutes — the producer that started it appears to have crashed. What resolves it, and why does this matter for consumers?" Answer: "transaction.timeout.ms (broker-side) eventually forces an abort of a stuck transaction — this exists specifically so one dead producer can't permanently block progress. Until that timeout fires, any read_committed consumer is stuck behind the Last Stable Offset on that partition, unable to read ANYTHING past the stuck transaction, even unrelated committed data written after it started."

WHY We Chose Each Decision

- Why transactions on top of idempotence: idempotence alone doesn't survive a producer restart or provide multi-topic atomicity — transactions add both. - Why transactional.id must be stable per logical producer: it's the only way Kafka's fencing mechanism can distinguish a restarted instance from a brand-new, unrelated producer. - Why hash-based coordinator assignment: spreads transaction-state load while guaranteeing consistent coordinator routing per producer. - Why transaction.timeout.ms exists: bounds how long a stuck/crashed producer can block read_committed consumers via the LSO.

Top 2 Technologies — Multi-Topic Write Atomicity

Kafka Transactions vs Best-Effort Multi-Send (no transaction) Why pick Transactions (our choice): guarantees a multi-topic publish is atomic — all topics see the event, or none do, even across producer crashes. Why pick best-effort: simpler code, acceptable when eventual consistency between the two writes is tolerable or reconciled by a separate process. Example 1 (Transactions): Notification System's CDC Publisher fanning out a single outbox event to both the main topic and an audit trail topic. Example 2 (Best-effort, acceptable): A low-stakes "also log this to a metrics topic" secondary write where losing an occasional metric on crash has zero real business impact.
