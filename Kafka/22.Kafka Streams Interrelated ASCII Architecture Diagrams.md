# Kafka Streams: Interrelated ASCII Architecture Diagrams

This example counts how many orders each product receives.

The input topic is `order-events`. Each event contains a product ID and an
order amount.

The processing requirement is:

```text
Read order-events
    |
    v
Keep orders greater than $100
    |
    v
Use productId as the key
    |
    v
Count orders for each product
    |
    v
Write results to product-counts
```

## 1. Kafka Cluster: Input Topic

Kafka stores the input topic in partitions.

```text
+----------------------------------------------------------------+
|                         KAFKA CLUSTER                          |
|                                                                |
|  Topic: order-events                                           |
|                                                                |
|  +----------------+  +----------------+  +----------------+    |
|  | Partition P0   |  | Partition P1   |  | Partition P2   |    |
|  | order events   |  | order events   |  | order events   |    |
|  +----------------+  +----------------+  +----------------+    |
|                                                                |
+----------------------------------------------------------------+
```

Kafka chooses a partition using the record key. Records with the same key are
normally sent to the same partition.

### What is happening?

Kafka breaks the `order-events` topic into three smaller ordered logs. Each
partition stores some of the order messages. Kafka Streams can read these
partitions separately, which allows several workers to process orders at the
same time.

## 2. Complete Topology

The topology is the complete processing plan. It shows all processing steps
before Kafka Streams divides the work into tasks.

```text
+----------------------------------------------------------------+
|                         TOPOLOGY                               |
|                                                                |
|  Source: order-events                                          |
|             |                                                  |
|             v                                                  |
|       Filter amount > $100                                     |
|             |                                                  |
|             v                                                  |
|       Change key to productId                                  |
|             |                                                  |
|             v                                                  |
|       Group by key                                             |
|             |                                                  |
|             v                                                  |
|       Count orders                                             |
|             |                                                  |
|             +---------------------> State Store                |
|             |                       product-count-store        |
|             v                                                  |
|       Output: product-counts                                   |
|                                                                |
+----------------------------------------------------------------+
```

The topology is a plan. It is not one worker and it is not one partition.

### What is happening?

The topology says what Kafka Streams must do with every order. First it reads
the event, removes orders that are not greater than `$100`, changes the key to
`productId`, groups events with the same product ID, counts them, and writes the
result. The topology is only the plan at this stage.

## 3. Why Repartitioning Is Needed

Assume the incoming events are keyed by `orderId`, but the application wants to
count by `productId`.

```text
Before changing the key:

orderId 101 -> product P1
orderId 102 -> product P1
orderId 103 -> product P2
```

The grouping key is changing from `orderId` to `productId`, so Kafka Streams
must redistribute records by the new key.

```text
order-events
     |
     v
Filter amount > $100
     |
     v
Change key to productId
     |
     v
Repartition by productId
     |
     v
Group by key and count
```

If records are already keyed by `productId`, this repartition step is usually
not needed.

### What is happening?

The original key is `orderId`, but the count is needed by `productId`. Kafka
uses the key to choose a partition, so orders for the same product might be in
different partitions when the key is `orderId`. Kafka Streams changes the key
and sends the records to a repartition topic. The new key makes sure the same
product is routed consistently.

## 4. Sub-Topologies

The repartition topic separates the topology into two independent sections.
These sections are called sub-topologies.

```text
+-----------------------------------+
| Sub-topology 0                    |
|                                   |
| Source: order-events              |
|       |                           |
|       v                           |
| Filter amount > $100              |
|       |                           |
|       v                           |
| Change key to productId           |
|       |                           |
|       v                           |
| Output: repartition topic         |
+-----------------------------------+
                 |
                 v
+-----------------------------------+
| Sub-topology 1                    |
|                                   |
| Source: repartition topic         |
|       |                           |
|       v                           |
| Group by key                      |
|       |                           |
|       v                           |
| Count                             |
|       |                           |
|       +--> State store            |
|       |    product-count-store    |
|       v                           |
| Output: product-counts            |
+-----------------------------------+
```

A sub-topology is simply one independent section of the complete topology.

### What is happening?

The first sub-topology reads the original topic, filters the events, changes
their keys, and writes them to the repartition topic. The second sub-topology
starts by reading that repartition topic, then groups and counts the records.
The repartition topic connects the two sections.

## 5. Kafka Cluster After Repartitioning

Kafka now contains the original topic and the internal repartition topic.

```text
+---------------------------------------------------------------------+
|                            KAFKA CLUSTER                            |
|                                                                     |
|  +---------------------------+   +-------------------------------+  |
|  | Topic: order-events       |   | Internal topic: repartition   |  |
|  |                           |   |                               |  |
|  | +----+ +----+ +----+     |   | +----+ +----+ +----+             |  |
|  | | P0 | | P1 | | P2 |     |   | | P0 | | P1 | | P2 |             |  |
|  | +----+ +----+ +----+     |   | +----+ +----+ +----+             |  |
|  +---------------------------+   +-------------------------------+  |
|                                                                     |
+---------------------------------------------------------------------+
```

The repartition topic receives records using `productId` as the key. Therefore,
all records for the same product are routed consistently.

### What is happening?

The original `order-events` topic is still present. Kafka Streams creates the
internal repartition topic as an additional topic. It writes the filtered
events there after assigning `productId` as the key. The repartition topic also
has partitions, so the next sub-topology can process it in parallel.

## 6. Tasks Are Created From Partitions

A task is a worker for a particular sub-topology and its partitions.

```text
Sub-topology 0 reads order-events:

+----------------+       +----------------+
| order-events   |       | Task 0_0       |
| Partition P0   | ----> | Sub-topology 0 |
+----------------+       | Source: P0     |
                         +----------------+

+----------------+       +----------------+
| order-events   |       | Task 0_1       |
| Partition P1   | ----> | Sub-topology 0 |
+----------------+       | Source: P1     |
                         +----------------+

+----------------+       +----------------+
| order-events   |       | Task 0_2       |
| Partition P2   | ----> | Sub-topology 0 |
+----------------+       | Source: P2     |
                         +----------------+
```

The task runs the nodes belonging to its sub-topology for its assigned
partition.

### What is happening?

Kafka Streams creates one task for each partition in this simple example. Task
`0_0` reads partition `P0` and runs sub-topology 0 on those records. Task `0_1`
does the same for `P1`, and task `0_2` does it for `P2`. The tasks follow the
same steps, but each task handles different records.

```text
Task 0_0:
order-events P0 -> Filter -> Change key -> Write repartition topic

Task 0_1:
order-events P1 -> Filter -> Change key -> Write repartition topic

Task 0_2:
order-events P2 -> Filter -> Change key -> Write repartition topic
```

## 7. Tasks for the Second Sub-Topology

The second sub-topology reads the repartition topic.

```text
+----------------------+       +----------------+
| repartition topic    |       | Task 1_0       |
| Partition P0         | ----> | Sub-topology 1 |
+----------------------+       | Source: P0     |
                               +----------------+

+----------------------+       +----------------+
| repartition topic    |       | Task 1_1       |
| Partition P1         | ----> | Sub-topology 1 |
+----------------------+       | Source: P1     |
                               +----------------+

+----------------------+       +----------------+
| repartition topic    |       | Task 1_2       |
| Partition P2         | ----> | Sub-topology 1 |
+----------------------+       | Source: P2     |
                               +----------------+
```

These tasks run the second part of the plan:

```text
Task 1_0:
repartition P0 -> Group by productId -> Count -> State store -> product-counts

Task 1_1:
repartition P1 -> Group by productId -> Count -> State store -> product-counts

Task 1_2:
repartition P2 -> Group by productId -> Count -> State store -> product-counts
```

### What is happening?

These tasks read the already-repartitioned records. Because the records now use
`productId` as their key, all events for one product reach the same task. That
task can calculate the correct count for that product and send the updated
count to the output topic.

## 8. Stream Threads Execute Tasks

A stream thread executes one or more tasks. A task is the work; a thread is the
execution path running that work.

```text
+-----------------------------------+
| Kafka Streams application         |
|                                   |
|  Stream Thread 1                  |
|       |                           |
|       +--> Task 0_0               |
|       +--> Task 0_1               |
|                                   |
|  Stream Thread 2                  |
|       |                           |
|       +--> Task 0_2               |
|       +--> Task 1_0               |
|                                   |
|  Stream Thread 3                  |
|       |                           |
|       +--> Task 1_1               |
|       +--> Task 1_2               |
|                                   |
+-----------------------------------+
```

The exact assignment can change during a rebalance. Kafka Streams distributes
available tasks among the application instances and stream threads.

### What is happening?

A stream thread is the execution path that runs tasks. It is not a separate
copy of the data. In this example, Thread 1 runs two tasks and the other threads
run the remaining tasks. If an application instance stops, Kafka can assign its
tasks to another instance during a rebalance.

## 9. RocksDB State Store

The `Count` step must remember the current count for each product. Kafka
Streams stores this local state in a state store, usually backed by RocksDB.

```text
Product events
     |
     v
+------------------+
| Group by product |
+------------------+
     |
     v
+------------------+
| Count            |
+------------------+
     |
     +------------------------------+
     |                              |
     v                              v
+------------------------+   +----------------------+
| RocksDB                |   | Output topic         |
| product-count-store    |   | product-counts       |
|                        |   |                      |
| P1 -> 2                |   | P1 -> 2              |
| P2 -> 1                |   | P2 -> 1              |
+------------------------+   +----------------------+
```

You normally do not use RocksDB directly. Kafka Streams manages it through the
state-store APIs.

### What is happening?

The count operation needs to remember the current count for each product. When
an event for `P1` arrives, Kafka Streams reads the old count, adds one, and
stores the new count in the local `product-count-store`. RocksDB is the local
storage engine used behind that store. Kafka Streams manages this storage for
you.

## 10. Changelog Topic: State Recovery

RocksDB is local to the application instance. Kafka Streams copies state
changes to a changelog topic so the state can be rebuilt after a crash.

```text
+------------------------+       +-------------------------------+
| Local RocksDB          |       | Kafka changelog topic         |
| product-count-store   | ----> | product-count-store-changelog |
|                        |       |                               |
| P1 -> 2                |       | P1 -> 2                       |
| P2 -> 1                |       | P2 -> 1                       |
+------------------------+       +-------------------------------+
```

After a failure:

```text
Application crashes
        |
        v
Another instance receives the task
        |
        v
Reads the changelog topic
        |
        v
Rebuilds local RocksDB state
        |
        v
Continues processing
```

### What is happening?

RocksDB is local, so it can disappear when an application instance fails. Kafka
Streams writes every state change to the changelog topic as well. A replacement
task reads that changelog, rebuilds its local state, and then continues from the
correct Kafka offset.

## 11. One Connected End-to-End Picture

All the pieces now fit together:

```text
+------------------+     +-------------------+     +----------------------+
| Kafka topic      |     | Sub-topology 0    |     | Internal Kafka topic |
| order-events     | --> | Read              | --> | repartition           |
| P0, P1, P2       |     | Filter            |     | P0, P1, P2            |
+------------------+     | Change key        |     +----------------------+
                         +-------------------+                |
                                                              v
                         +-------------------+     +----------------------+
                         | Sub-topology 1    | --> | State store           |
                         | Group by key      |     | RocksDB               |
                         | Count             |     | product-count-store   |
                         +-------------------+     +----------------------+
                                  |
                                  v
                         +-------------------+
                         | Output topic     |
                         | product-counts   |
                         +-------------------+
                                  |
                                  +----> Changelog topic
                                         for recovery
```

### Reading the diagram from left to right

1. Kafka stores incoming orders in the `order-events` topic and its partitions.
2. Sub-topology 0 filters the orders and changes their key to `productId`.
3. The repartition topic places records with the same product key together.
4. Sub-topology 1 groups and counts those records.
5. The count is stored locally in RocksDB and sent to `product-counts`.
6. The changelog topic keeps a recoverable copy of the local state.

## Final Mental Model

```text
Topic partitions
       |
       v
Tasks are created for the partitions
       |
       v
Threads execute the tasks
       |
       v
Tasks run processor nodes from the topology
       |
       +--> Repartition topic when the key changes
       |
       +--> RocksDB state store for stateful operations
       |
       +--> Changelog topic to recover local state
       |
       v
Output topic contains the result
```

In one sentence:

> A topology is the plan, sub-topologies are independent sections, tasks apply
> those sections to partitions, threads execute the tasks, repartition topics
> move records to the correct key-based partition, and RocksDB stores local
> state that Kafka can recover from a changelog topic.
