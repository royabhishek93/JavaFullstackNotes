Adding a single Maven/Gradle dependency gives you everything needed — the high-level Spring abstraction layer sits on top of the low-level Kafka client library.

Bootstrap Servers — First Contact with the Cluster

The producer does not know the cluster layout when it starts. The bootstrap server list is used only once — on startup — to fetch metadata. After that, the producer uses its own cached metadata.

application.properties: spring.kafka.bootstrap-servers=localhost:9092,localhost:9094 FIRST STARTUP: ┌─────────────────────────────────────────────────────────────────┐ │ Producer starts. Does not know: │ │ - Which broker is leader for order-events P0? │ │ - Which broker is leader for order-events P1? │ │ │ │ Step 1: Connect to ANY bootstrap broker (e.g. localhost:9092) │ │ Step 2: Ask for cluster metadata │ │ Step 3: Broker returns full metadata: │ │ topic "order-events": 4 partitions │ │ P0 leader = Broker-3 (host:port) │ │ P1 leader = Broker-4 (host:port) …etc │ │ Step 4: Producer caches this metadata locally │ └─────────────────────────────────────────────────────────────────┘ SUBSEQUENT CALLS: ┌─────────────────────────────────────────────────────────────────┐ │ Producer checks its own metadata cache: │ │ "order-events P0 → Broker-3" → connect directly ✓ │ │ Bootstrap servers are no longer needed. │ └─────────────────────────────────────────────────────────────────┘ Why list TWO bootstrap servers? If Broker-1 is down when producer starts, Broker-2 is the fallback. You only need ONE to be reachable — but listing two adds resilience.

Metadata Cache Refresh

The metadata cached on startup can become stale (brokers added, partitions moved, leader elections). The producer refreshes it periodically.

Config: spring.kafka.producer.properties.metadata.max.age.ms=300000 (5 minutes, default) Timeline: ──────────────────────────────────────────────────────────────► t=0 Producer starts, fetches metadata from bootstrap server t=5 min Cache expires → producer asks broker for fresh metadata t=10 min Cache expires → refresh again …repeats… If a leader election happens between refreshes: Producer sends to old leader → gets "Not a Leader" error → Producer immediately triggers early metadata refresh → Retries with updated leader address ✓ Default of 5 minutes is fine for most apps. You only need to change it if your cluster topology changes very frequently.

Creating a Topic from Spring Boot at Startup

Instead of running shell scripts to create topics, you can define them as Spring beans. On startup, Spring Boot checks whether the topic exists and creates it if not.

@Configuration class KafkaProducerConfig { @Bean fun orderEventsTopic(): NewTopic = TopicBuilder.name("order-events") .partitions(4) .replicas(2) .config(TopicConfig.RETENTION_MS_CONFIG, "604800000") // 7 days .config(TopicConfig.CLEANUP_POLICY_CONFIG, "delete") .config(TopicConfig.MIN_IN_SYNC_REPLICAS_CONFIG, "2") .config(TopicConfig.SEGMENT_BYTES_CONFIG, "1073741824") // 1 GB .build() } ┌─────────────────────────────────────────────────────────────────┐ │ APPLICATION STARTUP │ │ │ │ Spring sees @Bean returning NewTopic │ │ │ │ │ ▼ │ │ KafkaAdmin checks cluster: does "order-events" exist? │ │ │ │ │ ├── YES → do nothing ✓ │ │ └── NO → send CreateTopics request to active controller │ │ cluster creates topic with given config ✓ │ └─────────────────────────────────────────────────────────────────┘ Config priority: Explicit value in TopicBuilder ► overrides broker/controller defaults Omitted config ► falls back to broker.properties defaults (e.g. if you skip .replicas(), the default.replication.factor from controller.properties is used)

The Minimal Producer: One Config, One Line

All the five internal stages (serializer, partitioner, accumulator, compression, sender) have sensible defaults. The only mandatory configuration is which broker to connect to.

Minimum required: ┌─────────────────────────────────────────────────────────┐ │ application.properties │ │ │ │ spring.kafka.bootstrap-servers=localhost:9092 │ └─────────────────────────────────────────────────────────┘ Minimum required code: ┌─────────────────────────────────────────────────────────┐ │ @Autowired │ │ private KafkaTemplate<String, Any> kafkaTemplate │ │ │ │ kafkaTemplate.send("order-events", key, value) │ └─────────────────────────────────────────────────────────┘ That is literally all that is needed to publish an event. Everything else is optional tuning.

Serializers: Key and Value Configuration

Kafka requires both the key and value to be serialized to bytes. You configure a serializer class for each separately in application.properties.

spring.kafka.producer.key-serializer= org.apache.kafka.common.serialization.StringSerializer spring.kafka.producer.value-serializer= org.springframework.kafka.support.serializer.JsonSerializer ┌──────────────────────────────────────────────────────────────┐ │ SERIALIZATION FLOW │ │ │ │ key = "ORDER-001" ──► StringSerializer ──► byte[] │ │ │ │ value = Order( ──► JsonSerializer ──► byte[] │ │ id="O-001", { │ │ amount=500, → "id":"O-001", │ │ status="NEW" "amount":500, │ │ ) "status":"NEW" │ │ } │ └──────────────────────────────────────────────────────────────┘ Built-in serializers: StringSerializer → for String IntegerSerializer → for Integer / Int LongSerializer → for Long JsonSerializer → for any POJO (converts to JSON bytes) @Autowired type hint tells Spring which generic types to expect: KafkaTemplate<String, Order> key type ───────┘ └─── value type Spring auto-wires a KafkaTemplate configured for these types.

Sending With a Key — Use Case 1

When you provide a key, Kafka guarantees all messages with the same key go to the same partition. This is essential for ordering (e.g. all events for the same order ID stay in sequence).

SERVICE LAYER: val key = order.orderId // e.g. "O-1001" val value = order // POJO val future = kafkaTemplate.send("order-events", key, value) future.whenComplete { result, ex -> if (ex == null) { // SUCCESS println("partition=${result.recordMetadata.partition()}") println("offset=${result.recordMetadata.offset()}") } else { // FAILURE println("Failed: ${ex.message}") } } ┌───────────────────────────────────────────────────────────────┐ │ THREAD TIMELINE │ │ │ │ Application Thread: │ │ .send() → serialize → partition → accumulator │ │ → return Future → FREE to do other work │ │ │ │ Sender Thread (background): │ │ batch ready? → group by broker → network send │ │ → broker ack → complete Future → whenComplete fires │ └───────────────────────────────────────────────────────────────┘ RecordMetadata returned on success: .partition() ← which partition stored the event .offset() ← position within that partition's log

Acknowledgment Modes (acks)

The acks config tells the broker how many replicas must confirm receipt before it sends an acknowledgment back to the producer. This is the core reliability vs. throughput trade-off.

spring.kafka.producer.acks=all (or 0, 1, all / -1) ┌──────────────────────────────────────────────────────────────────┐ │ acks = 0 — FIRE AND FORGET │ │ │ │ Producer → Broker-1 (leader) → no ack waited │ │ │ │ Producer does not wait for ANY response. │ │ Fastest throughput. Messages can be LOST if broker crashes. │ │ Use only when data loss is acceptable (e.g. metrics/logs). │ └──────────────────────────────────────────────────────────────────┘ ┌──────────────────────────────────────────────────────────────────┐ │ acks = 1 — LEADER ONLY │ │ │ │ Producer → Broker-1 (leader) → written to leader disk │ │ → ack sent back to producer ✓ │ │ Follower replication: NOT waited │ │ │ │ If leader crashes BEFORE followers replicate → data LOST. │ │ Good balance of speed and safety for non-critical data. │ └──────────────────────────────────────────────────────────────────┘ ┌──────────────────────────────────────────────────────────────────┐ │ acks = all (same as acks = -1) — ALL IN-SYNC REPLICAS │ │ │ │ Producer → Broker-1 (leader) → written to leader │ │ → replicated to all ISR followers │ │ → ack sent back only after ALL ISR │ │ have confirmed ✓ │ │ │ │ No data loss as long as at least one ISR is alive. │ │ Slightly lower throughput. Required for financial / critical │ │ data. Pair with min.insync.replicas=2 for maximum safety. │ └──────────────────────────────────────────────────────────────────┘ Summary: acks=0 → fastest, can lose data acks=1 → medium, lose data only on leader crash before replication acks=all → safest, no loss if ISR has >= min.insync.replicas members

Custom Serializer — Use Case 2

Sometimes you need to transform or filter data before it reaches Kafka — for example, stripping sensitive fields. You implement the Serializer<T> interface and provide only the fields you want.

REQUIREMENT: Send only orderId + productId. Hide customerId, amount, status. Full Order POJO: What should be sent: ┌──────────────────────────┐ ┌──────────────────────────────┐ │ orderId = "O-1001" │ │ orderId = "O-1001" ✓ │ │ customerId = "C-777" │ → │ productId = "PID-3" ✓ │ │ productId = "PID-3" │ │ customerId = omitted ✗ │ │ quantity = 2 │ │ amount = omitted ✗ │ │ amount = 500.00 │ │ status = omitted ✗ │ │ status = "NEW" │ └──────────────────────────────┘ └──────────────────────────┘ Custom serializer class: class OrderSummarySerializer : Serializer<Order> { override fun serialize(topic: String, order: Order): ByteArray { val summary = mapOf( "orderId" to order.orderId, "productId" to order.productId // customerId, amount, status intentionally excluded ) return ObjectMapper().writeValueAsBytes(summary) } } Wire it up in application.properties: spring.kafka.producer.value-serializer= com.eda.producer.OrderSummarySerializer ┌─────────────────────────────────────────────────────────────────┐ │ SERIALIZER STAGE with custom class │ │ │ │ KafkaProducer.java internally calls: │ │ valueSerializer.serialize(topic, orderObject) │ │ │ │ → Your OrderSummarySerializer.serialize() is invoked │ │ → Returns byte[] of {"orderId":"O-1001","productId":"PID-3"} │ │ → Sensitive fields never leave the producer ✓ │ └─────────────────────────────────────────────────────────────────┘

Multiple KafkaTemplate Beans — Different Serializers Per Service

application.properties holds one set of serializer config. If different parts of your app need different serializers, create additional KafkaTemplate beans programmatically and inject them with @Qualifier.

PROBLEM: ┌─────────────────────────────────────────────────────────────────┐ │ application.properties can hold only ONE value-serializer. │ │ OrderService needs JsonSerializer │ │ SalesService needs OrderSummarySerializer (custom) │ │ → You cannot satisfy both from properties alone. │ └─────────────────────────────────────────────────────────────────┘ SOLUTION: programmatic bean override @Configuration class KafkaProducerConfig { @Bean("customSerializerKafkaTemplate") fun customSerializerKafkaTemplate( configs: KafkaProperties ): KafkaTemplate<String, Any> { // Step 1: load ALL producer props from application.properties val props = configs.buildProducerProperties() // Step 2: override ONLY the value-serializer props[ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG] = OrderSummarySerializer::class.java // Step 3: build a factory and wrap in KafkaTemplate val factory = DefaultKafkaProducerFactory<String, Any>(props) return KafkaTemplate(factory) } } ┌─────────────────────────────────────────────────────────────────┐ │ BEAN WIRING │ │ │ │ OrderService: │ │ @Autowired │ │ lateinit var kafkaTemplate: KafkaTemplate<String, Any> │ │ // uses JsonSerializer from application.properties ✓ │ │ │ │ SalesService: │ │ @Autowired │ │ @Qualifier("customSerializerKafkaTemplate") │ │ lateinit var kafkaTemplate: KafkaTemplate<String, Any> │ │ // uses OrderSummarySerializer (custom bean) ✓ │ └─────────────────────────────────────────────────────────────────┘ Rule: application.properties serializer = default for all auto-wired KafkaTemplates that have no @Qualifier. The @Bean override is isolated to the bean name you give it.

Sending Without a Key — Sticky Partition in Practice

When you omit the key, the overloaded .send(topic, value) method is used. The partitioner applies sticky partitioning (Kafka 2.4+) — filling one partition's batch fully before switching.

kafkaTemplate.send("order-events", orderObject) // no key ┌─────────────────────────────────────────────────────────────────┐ │ PARTITIONER (no key path) │ │ │ │ Check sticky memory: "order-events" → P2 (random at start) │ │ │ │ E1 → P2 (sticky) │ │ E2 → P2 (sticky) │ │ E3 → P2 (sticky) │ │ …until batch for P2 closes (batch.size or linger.ms)… │ │ │ │ New batch opens: randomly pick again → P0 this time │ │ E_n+1 → P0 (new sticky) │ └─────────────────────────────────────────────────────────────────┘ Comparison in this session: With key (orderId): "O-1001" → hash("O-1001") % 4 → always P3 "O-1002" → hash("O-1002") % 4 → always P1 Ordering guaranteed per orderId ✓ Without key: Sticky until batch full → switch randomly No ordering guarantee across different batches ✗ Higher throughput for keyless events ✓

Cross Questions Interviewers Ask

Q: Why does a topic need to exist before the producer can reliably send to it? A: If auto-topic-creation is disabled (production best practice), sending to a non-existent topic fails — TopicBuilder beans at startup let Spring Boot create/verify required topics deterministically before traffic flows. Q: Why would you register multiple KafkaTemplate beans in one service? A: Different topics may need genuinely different value types (Avro NotificationEvent vs a plain String for a simple ack topic) — one generically-typed template can't safely serialize both. Q: Why does metadata.max.age.ms matter even though the producer caches metadata? A: It bounds how stale the cached "who leads this partition" view can get — without a refresh, a producer could keep sending to a broker that's no longer the actual leader after a failover, until an error forces a refresh anyway.

Senior Trap Questions (15 YOE)

Trap 1 — "A new engineer removes 2 of 3 brokers from bootstrap-servers to 'simplify config,' pointing only at broker-1. Two weeks later, broker-1 has a planned maintenance window and the producer fails to start. Why, and what did they misunderstand?" Answer: "bootstrap-servers is ONLY used for that initial metadata fetch — once connected, the producer discovers all brokers via metadata and doesn't depend on broker-1 specifically afterward. But if broker-1 is down at STARTUP with no other entries to try, the producer has nothing to bootstrap from at all. Listing multiple brokers isn't about steady-state operation — it's about surviving exactly this cold-start scenario." Trap 2 — "Your custom serializer works fine in tests but throws intermittent ClassCastExceptions in production under load. What's the likely root cause?" Answer: "A non-thread-safe serializer implementation — Kafka producer clients can invoke serialize() concurrently across multiple sends if your application uses the same KafkaTemplate/producer instance from multiple threads. Any shared mutable state inside a custom Serializer (a reused buffer, a non-thread-safe formatter) surfaces exactly as flaky, load-dependent failures like this."

WHY We Chose Each Decision

- Why list all 3 brokers in bootstrap-servers: survives a cold start where any single listed broker happens to be down. - Why Avro over plain JSON for the value serializer: Schema Registry governance catches breaking changes at registration time, not at runtime. - Why separate typed KafkaTemplate beans per topic shape: compile-time type safety instead of runtime casting risk. - Why TopicBuilder beans at startup: deterministic, verified topic existence before any traffic flows, instead of relying on auto-create.

Top 2 Technologies — Producer-Side Serialization

Avro (Confluent Schema Registry) vs Plain JsonSerializer Why pick Avro (our choice): compact wire format, Schema Registry enforces compatibility at registration time, catches breaking changes before deploy. Why pick plain JSON: zero setup overhead, human-readable payloads, fine for early prototyping or internal-only topics with no external consumers. Example 1 (Avro): Notification System's NotificationEvent — 20+ consuming services depend on schema stability; Avro + registry makes that safe. Example 2 (JSON): A brand-new internal debug topic used only by one team during a 2-week spike investigation — not worth registry overhead yet.
