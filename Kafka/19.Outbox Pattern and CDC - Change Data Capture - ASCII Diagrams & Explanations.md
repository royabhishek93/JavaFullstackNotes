# Outbox Pattern and CDC — Change Data Capture — ASCII Diagrams & Explanations

Topics: CDC, Change Data Capture, WAL, Binlog, Logical Replication, Replication Slot, Debezium, Kafka Connect, Publication, Polling vs CDC

---

## 1. Push vs Pull — The Core Idea

In polling, your code repeatedly asks the database for changes. In CDC, the database streams changes to you the moment they happen — no scheduler, no repeated queries.

```
POLLING (pull model):
  ┌──────────────────────┐   every 2 sec: "any new rows?"   ┌──────────┐
  │  Your Scheduler      │ ─────────────────────────────►   │    DB    │
  │  (custom code)       │ ◄─────────────────────────────   │          │
  └──────────────────────┘   DB returns unpublished rows    └──────────┘
  Problems: constant DB load, polling gap, multi-instance conflicts

CDC (push model):
  ┌──────────────────────┐                                   ┌──────────┐
  │  Debezium            │ ◄──── DB streams every INSERT ──  │    DB    │
  │  (infrastructure)    │       UPDATE, DELETE immediately   │          │
  └──────────────────────┘                                   └──────────┘
  No scheduler. No delay. No constant DB load. No custom code.
```

## 2. How Databases Record Every Change — WAL and Binlog

Before a database modifies a table it first records the change in a **transaction log file**. This is the source of truth for crash recovery and replication. CDC reads this same file.

```
POSTGRES — Write-Ahead Log (WAL):
  ┌───────────────────────────────────────────────────────────────────┐
  │  INSERT INTO outbox_events (aggregate_type, payload, ...)         │
  │         │                                                         │
  │         ▼  step 1 — written FIRST                                 │
  │  ┌──────────────────────────────────┐                             │
  │  │  WAL file  (on disk)             │                             │
  │  │  op:    INSERT                   │                             │
  │  │  table: outbox_events            │                             │
  │  │  row:   { id, payload, ... }     │                             │
  │  └──────────────────────────────────┘                             │
  │         │                                                         │
  │         ▼  step 2 — updated AFTER                                 │
  │  ┌──────────────────────────────────┐                             │
  │  │  Table pages  (actual data)      │                             │
  │  └──────────────────────────────────┘                             │
  └───────────────────────────────────────────────────────────────────┘

MYSQL uses a Binlog file — same concept, different name.

WHY THE LOG FILE EXISTS:
  Crash recovery:   replay WAL from last checkpoint → table restored  ✓
  DB replication:   master sends WAL to slave databases               ✓
  CDC:              Debezium subscribes like a slave, reads WAL       ✓
```

## 3. WAL Level — Why "logical" Is Required

By default the WAL stores low-level binary page offsets that only another Postgres instance can decode. CDC needs human-readable column names and values — that requires changing the WAL level to **logical**.

```
WAL level: replica  (default — binary format)
  ┌──────────────────────────────────────────────────────────┐
  │  page 5, offset 120: changed from 0xAB to 0xCD           │
  │  page 8, offset 44:  changed from 0x00 to 0x01           │
  └──────────────────────────────────────────────────────────┘
  Another Postgres slave: can decode this  ✓
  Debezium (CDC):         cannot decode this  ✗

WAL level: logical  (required for CDC)
  ┌──────────────────────────────────────────────────────────┐
  │  op:             INSERT                                   │
  │  table:          outbox_events                           │
  │  id:             "uuid-abc-123"                          │
  │  aggregate_type: "ORDER"                                 │
  │  aggregate_id:   "customer-K1"                           │
  │  payload:        { "orderId": 42, "amount": 500 }        │
  └──────────────────────────────────────────────────────────┘
  Debezium can read this and publish to Kafka  ✓

How to change:
  SHOW wal_level;                             ← check current level
  ALTER SYSTEM SET wal_level = logical;       ← update it
  (restart Postgres for the change to take effect)
```

## 4. Debezium Attaches as a Replication Follower

Postgres already has a mechanism to stream the WAL to slave databases — a **replication slot**. Debezium registers itself in that same slot, exactly like a DB slave, and receives every WAL entry in real time.

```
NORMAL DB REPLICATION (no CDC):
  ┌────────────────┐  WAL stream   ┌──────────┐
  │  Master        │ ────────────► │  Slave-1 │
  │  Postgres      │ ────────────► │  Slave-2 │
  └────────────────┘               └──────────┘

WITH CDC — Debezium registers as another replication subscriber:
  ┌────────────────┐  WAL stream   ┌──────────┐
  │  Master        │ ────────────► │  Slave-1 │
  │  Postgres      │ ────────────► │  Slave-2 │
  │                │ ────────────► │ Debezium │◄─ replication slot
  └────────────────┘               └──────────┘
                                       │
                                       ▼  decodes WAL binary → logical
                                       │  (using pgoutput plugin)
                                       ▼
                                    Kafka  (Debezium acts as producer)

Replication slot created by Debezium at startup:
  name:        debezium_slot
  plugin:      pgoutput        ← decodes binary WAL to readable format
  publication: cdc_publication ← table-level filter (see next section)
```

## 5. Postgres Publication — Table-Level Filter

A **publication** tells Postgres which tables to include in the WAL stream sent to a CDC subscriber. Without it, every INSERT, UPDATE, DELETE on every table would be streamed to Debezium unnecessarily.

```
  Your database: 100 tables
  ┌──────────────────────────────────────────────────────────────┐
  │  orders  users  products  payments  inventory  ...  (×100)   │
  │                        outbox_events  ◄────────────────────  │
  └──────────────────────────────────────────────────────────────┘
                                  ▲ only this table

  CREATE PUBLICATION cdc_publication
      FOR TABLE public.outbox_events;

  Effect on the WAL stream sent to Debezium:
  ─────────────────────────────────────────────────────────────────
  INSERT into orders           → filtered out  ✗  (not in publication)
  INSERT into users            → filtered out  ✗
  INSERT into products         → filtered out  ✗
  INSERT into outbox_events    → INCLUDED      ✓  → Debezium receives it

  Two levels of filtering working together:
  ┌──────────────────────────────────────────────────────────┐
  │  Level 1 — Postgres side:  publication (cdc_publication) │
  │  Level 2 — Debezium side:  table.include.list            │
  │  Both point to public.outbox_events                      │
  └──────────────────────────────────────────────────────────┘
```

## 6. Debezium Connector Configuration

A single properties file wires together the database connection, the replication slot, the publication, and the mapping of outbox table columns to Kafka message fields.

```
  debezium-postgres-connector.properties
  ─────────────────────────────────────────────────────────────────
  name=outbox-connector               ← any name for this connector

  # Which Debezium plugin to use (swap to MySQL plugin for MySQL)
  connector.class=io.debezium.connector.postgresql.PostgresConnector

  # DB connection
  database.hostname=localhost
  database.port=5432
  database.user=postgres
  database.password=secret
  database.dbname=outbox_cdc_db

  # Level-2 filter — only watch this table
  table.include.list=public.outbox_events

  # Replication slot settings
  slot.name=debezium_slot
  plugin.name=pgoutput           ← decodes WAL binary → logical format

  # Use the publication we created manually in Postgres
  publication.auto.create.mode=disabled
  publication.name=cdc_publication

  # Read existing rows first, then stream new ones
  snapshot.mode=initial

  # Map outbox table columns to Kafka message fields
  transforms=outbox
  transforms.outbox.type=...EventRouter
  transforms.outbox.table.field.event.id=id             ← deduplication key
  transforms.outbox.table.field.event.key=aggregate_id  ← Kafka message key
  transforms.outbox.table.field.event.payload=payload   ← Kafka message value
  transforms.outbox.route.by.field=aggregate_type       ← determines topic
  transforms.outbox.route.topic.replacement=\${routedByValue}-events
  #  aggregate_type = "ORDER"  →  topic: ORDER-events

  snapshot.mode=initial explained:
    outbox_events already has 100 rows when CDC starts
    ┌────────────────────────────────────────────────────────┐
    │  Phase 1 — snapshot: read all 100 existing rows, send  │
    │  Phase 2 — streaming: receive new inserts via WAL      │
    └────────────────────────────────────────────────────────┘
```

## 7. End-to-End CDC Data Flow

This is the complete path from an incoming HTTP request to downstream services consuming the event from Kafka — with zero polling code.

```
  HTTP POST /order
       │
       ▼
  ┌────────────────────────────────────────────────────────┐
  │  OrderService  @Transactional                          │
  │                                                        │
  │  orderRepo.save(order)          ─┐                     │
  │  outboxRepo.save(outboxEvent)   ─┘  ONE DB transaction │
  └────────────────────────────────────────────────────────┘
       │  both rows committed atomically
       ▼
  ┌────────────────────────────────────────────────────────┐
  │  POSTGRES                                              │
  │  ┌──────────────────────────────────────────────────┐  │
  │  │  orders table:        { id:42, amount:500, ... } │  │
  │  └──────────────────────────────────────────────────┘  │
  │  ┌──────────────────────────────────────────────────┐  │
  │  │  outbox_events table:                            │  │
  │  │  { aggregate_type:"ORDER", aggregate_id:"K1",    │  │
  │  │    payload:{ orderId:42 } }                      │  │
  │  └──────────────────────────────────────────────────┘  │
  │  ┌──────────────────────────────────────────────────┐  │
  │  │  WAL file (logical level):                       │  │
  │  │  op: INSERT  table: outbox_events  row: {...}    │  │
  │  └──────────────────────────────────────────────────┘  │
  └──────────────────────────┬─────────────────────────────┘
                             │  replication slot stream
                             ▼
  ┌────────────────────────────────────────────────────────┐
  │  Kafka Connect  +  Debezium Postgres Plugin            │
  │                                                        │
  │  1. Reads WAL via replication slot (debezium_slot)     │
  │  2. pgoutput decodes binary WAL → logical format       │
  │  3. EventRouter transform maps columns:                │
  │       key   ← aggregate_id   ("K1")                   │
  │       value ← payload        ({ orderId: 42 })         │
  │       topic ← aggregate_type + "-events" ("ORDER-events")│
  │  4. Publishes to Kafka (acts as a Kafka producer)      │
  └────────────────────────────┬───────────────────────────┘
                               │
                               ▼
  ┌────────────────────────────────────────────────────────┐
  │  Kafka Topic: ORDER-events                             │
  │  key "K1" → same partition every time → order kept    │
  │  ┌────────┬────────┬────────┐                         │
  │  │ msg-1  │ msg-2  │ msg-3  │  ...                    │
  │  └────────┴────────┴────────┘                         │
  └──────────────────┬─────────────────────────────────────┘
                     │
         ┌───────────┴────────────┐
         ▼                        ▼
  ┌──────────────────┐    ┌──────────────────────┐
  │ payment-service  │    │  inventory-service    │
  └──────────────────┘    └──────────────────────┘
```

No scheduler. No polling query. No `published` column. The infrastructure does all the work once configured.

## 8. Polling vs CDC — Side-by-Side Comparison

Both approaches solve the dual-write problem using the same outbox table. They differ in how the relay from the outbox table to Kafka is implemented.

```
                                POLLING              CDC (Debezium)
  ────────────────────────────  ───────────────────  ────────────────────────────
  Custom code required          Yes (scheduler)  ✗   No  ✓
  Constant DB load              Yes (every N sec) ✗   No (event-driven)  ✓
  Event delivery latency        Up to N seconds  ✗   Milliseconds  ✓
  Multi-instance locking        Needed (ShedLock) ✗   Handled by Debezium  ✓
  published column needed       Yes              ✗   No  ✓
  Table cleanup job needed      Yes              ✗   Not required  ✓
  At-least-once delivery        Yes              ✓   Yes  ✓
  Idempotent consumer needed    Yes              ✓   Yes  ✓
  Simple to understand          Yes              ✓   More setup required  ✗
  Infrastructure dependency     None             ✓   Kafka Connect + Debezium  ✗
  Works with any DB             Yes              ✓   DB must support logical WAL  ✗
  Scales automatically          No (needs work)  ✗   Yes (Kafka Connect scales)  ✓

  What stays the same in both:
  ┌───────────────────────────────────────────────────────────────┐
  │  ► Same outbox table schema (minus published/published_at)    │
  │  ► Same @Transactional boundary in the application           │
  │  ► Same at-least-once delivery guarantee                     │
  │  ► Same requirement for idempotent consumers                 │
  │  ► Both solve the dual-write problem correctly               │
  └───────────────────────────────────────────────────────────────┘
```

## Quick Reference

```
Concept                    What it is                               Key point
─────────────────────────  ───────────────────────────────────────  ────────────────────────────────────
CDC                        Change Data Capture — push model         DB notifies you on every change
Debezium                   CDC tool implemented as Kafka plugin      Reads WAL/Binlog, publishes to Kafka
WAL (Postgres)             Write-Ahead Log file                     Every change written here before table
Binlog (MySQL)             Binary Log file                          Same concept as WAL, different name
WAL level: replica         Default — binary page offsets only       Debezium cannot read this  ✗
WAL level: logical         Adds table, column, value metadata       Debezium can read this  ✓
Replication slot           Subscription point in Postgres           Debezium registers here at startup
pgoutput                   WAL binary decoder plugin                Converts raw WAL → logical format
Publication                Postgres-side table filter               Controls which tables enter WAL stream
table.include.list         Debezium-side table filter               Second-level filter in connector config
snapshot.mode=initial      Read existing rows, then stream          Ensures no pre-existing data is missed
EventRouter transform      Maps outbox columns to Kafka fields      aggregate_id→key, payload→value, etc.
aggregate_type             Outbox column for routing                Determines the Kafka topic name
aggregate_id               Outbox column for partitioning           Used as Kafka message key
published column           Tracks send status                       Polling only — not needed with CDC
Kafka Connect              Kafka's connector hosting framework      Runs the Debezium plugin process
At-least-once              Delivery guarantee (both approaches)     Consumer must always be idempotent
```
