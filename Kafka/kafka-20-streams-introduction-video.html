What We Had So Far (Plain Kafka Consumer)

The basic Kafka flow — producer writes, consumer reads, processes, done.

Producer Broker Consumer ──────── ────────── ────────── event-1 ──────────► [P-0: e1,e2,e3] ──────► read e1 → send notification event-2 ──────────► read e2 → send notification event-3 ──────────► read e3 → send notification

Each event is handled independently — no memory of what came before. This is called stateless processing.

Stateless vs Stateful Processing

STATELESS (plain Kafka consumer) ───────────────────────────────────────────────────────── Event arrives → process it → done Output depends ONLY on the current event. Example: "Order placed → send confirmation email" (no need to remember past events) Event 1: order#1 → send email for order#1 ✓ Event 2: order#2 → send email for order#2 ✓ Event 3: order#3 → send email for order#3 ✓ STATEFUL (what Kafka Streams enables) ───────────────────────────────────────────────────────── Output depends on CURRENT event + PREVIOUS events combined. You must REMEMBER state from past messages. Example: "What is the total revenue for each customer so far?" Event 1: C1 paid ₹50 → C1 total = ₹50 Event 2: C2 paid ₹30 → C2 total = ₹30 Event 3: C1 paid ₹70 → C1 total = ₹50 + ₹70 = ₹120 ← needs memory!

Plain Kafka consumer was built for stateless. Stateful needs something more — Kafka Streams.

Real-World Problem 1 — Real-Time Aggregation

Requirement: Find total revenue per customer in real-time as events stream in.

Incoming events (topic: order-events): { customer: C1, amount: ₹50 } { customer: C2, amount: ₹30 } { customer: C1, amount: ₹70 } { customer: C3, amount: ₹90 } Expected running result: C1 → ₹120 C2 → ₹30 C3 → ₹90

Naive Approach A: In-Memory Map

Consumer ┌─────────────────────────────────────┐ │ Map<customerId, totalRevenue> │ │ ┌──────┬─────────┐ │ │ │ C1 │ ₹120 │ │ │ │ C2 │ ₹30 │ │ │ │ C3 │ ₹90 │ │ │ └──────┴─────────┘ │ │ (lives in JVM heap) │ └─────────────────────────────────────┘

Problem 1: App Crash → State Lost

Events processed so far: 1,00,000 In-memory map built: { C1: ₹5000, C2: ₹3000, ... } App CRASHES ✗ Memory gone ✗ Restart: Map is empty → must replay from offset 0 → slow & expensive!

Problem 2: Multiple Instances → Partial Data

Topic: order-events ┌──────────────────────────────────────┐ │ Partition-0 Partition-1 │ │ C1, C2 events C3, C4 events │ └─────────┬──────────────┬─────────────┘ │ │ ▼ ▼ Consumer 1 Consumer 2 ┌────────────┐ ┌────────────┐ │ Map: │ │ Map: │ │ C1: ₹50 │ │ C3: ₹90 │ ← each has PARTIAL data! │ C2: ₹30 │ │ C4: ₹20 │ └────────────┘ └────────────┘ Consumer 1 gets an order for C3 — C3 data is on Consumer 2! They can't see each other's map. ✗

Real-World Problem 1 — Naive Approach B: Store State in MySQL

Instead of in-memory, use a database.

Event arrives: { C1, ₹20 } │ ▼ SELECT revenue FROM customers WHERE id = 'C1' ← network call │ ▼ (returns ₹10) UPDATE customers SET revenue = ₹30 WHERE id = 'C1' ← network call

Problem: Database Becomes the Bottleneck

Event throughput: 1,00,000 events/second Per event: 1 SELECT + 1 UPDATE = 2 DB calls Total: 1,00,000 × 2 = 2,00,000 DB calls/second ✗ Database cannot handle this — it becomes the bottleneck! Kafka's whole point is high throughput; DB kills it.

Real-World Problem 2 — Window Operations

Requirement: Total revenue in the last 5 minutes only (not all time).

Timeline: ───────────────────────────────────────────────────────────────────► t=0 t=5min t=10min │ │ │ [C1:₹50][C2:₹30] │ [C1:₹70][C3:₹90] │ ↑ │ ↑ These should │ Only these count expire after 5 min │ in the current 5-min window

What you'd have to build manually:

For every event: 1. Record its timestamp 2. Check all stored events — evict entries older than 5 minutes 3. Re-aggregate what's left 4. Handle the fact that different consumers have PARTIAL window data Consumer 1 window: C1:₹50, C2:₹30 ← partial! Consumer 2 window: C1:₹70, C3:₹90 ← partial! Combined answer is split across 2 instances ✗

You'd need to build timestamp tracking, expiry logic, and cross-instance merging yourself — massive overhead.

Real-World Problem 3 — Joining Two Topics (Stream Enrichment)

Requirement: For each order, look up the customer's name from a customer profile topic.

Topic: order-events Topic: customer-profile ───────────────────── ──────────────────────── { orderId: O1, cId: C4 } { cId: C1, name: "Alice" } { orderId: O2, cId: C2 } { cId: C2, name: "Bob" } { orderId: O3, cId: C1 } { cId: C3, name: "Carol" } { cId: C4, name: "Dave" } Goal: enrich order with customer name O1 → { orderId: O1, customer: "Dave" } O2 → { orderId: O2, customer: "Bob" } O3 → { orderId: O3, customer: "Alice" }

Manual approach: maintain a lookup map

Consumer must: 1. Read customer-profile topic and build a map: { C1→Alice, C2→Bob... } 2. When order arrives, look up customer name in the map ┌───────────────────────────────────────────────────────────┐ │ In-memory lookup map (customer profile) │ │ { C1: Alice, C2: Bob, C3: Carol, C4: Dave } │ └───────────────────────────────────────────────────────────┘ App CRASHES → map gone → replay from offset 0 ✗

With Multiple Consumers — Cross-Partition Lookup Fails

Both topics split across 2 partitions: Consumer A reads: Consumer B reads: order-events P-0 order-events P-1 cust-profile P-0 cust-profile P-1 Consumer A local map: Consumer B local map: { C1: Alice, C2: Bob } { C3: Carol, C4: Dave } Consumer A gets order for C4 Consumer B gets order for C1 C4 data is on Consumer B ✗ C1 data is on Consumer A ✗ No way to cross-lookup without a shared distributed store!

Architecture — Where Streams Could Replace Batch Reporting

"Today the Reporting Service uses Redis counters plus an hourly Spark/Flink batch job. Let's explore replacing the batch layer with Kafka Streams for real-time delivery-rate aggregation."

delivery_status_events (one event per SENT/DELIVERED/FAILED) │ ▼ Kafka Streams app (embedded in the Reporting Service JVM) │ filter(status in DELIVERED/FAILED) → groupBy(channel) │ → windowedBy(1 min) → aggregate → KTable ▼ delivery-rate-per-min topic → Dashboard consumer

Scenario-first: "Compare to the batch job: it wakes up hourly, so 'delivery rate right now' is always up to 59 minutes stale. Streams computes it continuously — the cost is now owning a stateful application with local state that must survive restarts correctly, which is real operational weight, not free."

Cross Questions Interviewers Ask

Q: Why is Kafka Streams "just a library," not a separate cluster like Spark or Flink? A: It runs embedded in your own JVM application — scaling out means running more instances of your app; Kafka's consumer group protocol handles distributing work across them, no separate Streams cluster needed. Q: When would you keep the batch job even after adopting Streams for some metrics? A: Batch is often better for large historical reprocessing/backfills and complex joins across large static datasets — Streams shines at continuous, low-latency aggregation over live topics, not heavy one-off analysis. Q: Why is "each event independent" vs "need memory across events" the right first question to ask? A: It's the fastest way to rule OUT Streams for something like simple fan-out delivery (plain consumer is simpler and sufficient) and rule it IN for anything needing running totals, joins, or windows.

Senior Trap Questions (15 YOE)

Trap 1 — "You scaled from 3 to 6 instances of your Streams app expecting 2x throughput. You got almost no improvement. Why?" Answer: "Kafka Streams parallelism is capped by the number of PARTITIONS in the source topic — you can't have more actively-working tasks than partitions. If the source topic has only 6 partitions and you already had 6 tasks running across 3 instances, adding 3 more instances just gives each instance fewer tasks — total parallelism doesn't increase because the ceiling was partition count, not instance count." Trap 2 — "A colleague suggests using Kafka Streams for the email-workers delivery consumer itself, to 'get built-in state management for free.' What's wrong with that idea?" Answer: "The delivery worker's core job is calling an external HTTP API (SendGrid) and recording the result — a side-effecting operation, not a data transformation/aggregation. Kafka Streams' DSL and state-store model are built for the latter; forcing an external-API-calling workload into it fights the framework rather than leveraging it, and a plain consumer with custom idempotency logic remains the better fit."

WHY We Chose Each Decision

- Why explore Streams for reporting, not more Redis counters: Redis INCR gives point-in-time counts but no native windowing or replay-based recovery. - Why keep the batch job for historical analysis: Streams isn't suited for heavy one-off backfills across large historical datasets. - Why NOT use Streams for delivery workers: that workload is external-API side effects, not data transformation — the wrong tool for the job. - Why embed Streams in the existing service rather than a new microservice: avoids adding a new deployable unit when the existing lifecycle already fits.

Top 2 Technologies — Stream Processing Layer

Kafka Streams vs Plain Kafka Consumer (for building a metric pipeline) Why pick Kafka Streams: built-in windowing, state stores, and crash-recoverable aggregation — reimplementing this manually on a plain consumer is significant, error-prone work. Why pick Plain Consumer: when the logic truly has no state/aggregation need — just read and act per record, like the delivery workers. Example 1 (Kafka Streams): Notification System's hypothetical real-time delivery-rate-per-minute aggregation — genuinely needs windowed state. Example 2 (Plain Consumer): Notification System's actual email/SMS/push delivery workers — no aggregation, just per-record external API calls.
