# Kafka Cluster Setup — ASCII Diagrams & Explanations

Topics: Cluster Topology, Folder Structure, Process Roles, Listeners, Controller Config, Broker Config, advertised.listeners, Cluster ID, Bootstrap Sequence, Leader Election, Topic Creation

---

## 1. Cluster Topology — What We Are Building

We are creating a cluster of four dedicated nodes: two controllers (manage metadata and leader elections) and two brokers (store data and serve producers/consumers). No node does both jobs.

```
              KAFKA CLUSTER
┌─────────────────────────────────────────────────────┐
│                                                     │
│   CONTROLLERS (metadata plane)                      │
│   ┌─────────────────┐   ┌─────────────────┐         │
│   │  Controller 1   │   │  Controller 2   │         │
│   │  node.id = 1    │◄──►  node.id = 2    │         │
│   │  port 9093      │   │  port 9193      │         │
│   └─────────────────┘   └─────────────────┘         │
│          ▲                      ▲                   │
│          │  brokers register    │                   │
│          │  on startup          │                   │
│   BROKERS (data plane)          │                   │
│   ┌─────────────────┐   ┌─────────────────┐         │
│   │   Broker 1      │   │   Broker 2      │         │
│   │  node.id = 3    │   │  node.id = 4    │         │
│   │  port 9092      │   │  port 9192      │         │
│   └─────────────────┘   └─────────────────┘         │
│         ▲  ▲                   ▲  ▲                 │
│         │  │                   │  │                 │
│      Producer              Consumer                 │
└─────────────────────────────────────────────────────┘
```

## 2. Kafka Binary Folder Structure

When you download and unzip the Kafka binary (e.g. kafka_4.2.0), you get several folders. The two that matter most for setup are `bin` (executable scripts) and `config` (properties files).

```
kafka_4.2.0/
├── bin/                   ← executable shell scripts (wrappers around Kafka Java API)
│   ├── kafka-server-start.sh       start a controller or broker node
│   ├── kafka-storage.sh            generate cluster ID, format node storage
│   ├── kafka-topics.sh             create / delete / describe topics
│   ├── kafka-console-producer.sh   publish messages from CLI
│   ├── kafka-console-consumer.sh   consume messages from CLI
│   ├── kafka-metadata-quorum.sh    check cluster status
│   └── ... (many more)
│
├── config/                ← .properties config files (default templates)
│   ├── broker.properties           template for a broker-only node
│   ├── controller.properties       template for a controller-only node
│   ├── server.properties           template for a combined broker+controller node
│   └── consumer.properties         template for consumer settings
│
├── libs/                  ← Kafka JAR files and dependencies
│                            (bin scripts call the code inside here)
│
└── logs/                  ← INFO / WARN / ERROR log output
                             (written when you start any server)
```

## 3. Process Roles — Three Modes a Node Can Run In

Every node declares its role using the `process.roles` property. In production, controllers and brokers are always separated (dedicated roles). A combined node is only useful for quick local experiments.

```
process.roles = controller
──────────────────────────────────────────────────
  ┌─────────────────────────────────┐
  │         CONTROLLER NODE         │
  │  - manages cluster metadata     │
  │  - runs leader elections        │
  │  - no data storage              │
  │  - NOT reachable by producers   │
  └─────────────────────────────────┘

process.roles = broker
──────────────────────────────────────────────────
  ┌─────────────────────────────────┐
  │           BROKER NODE           │
  │  - stores topic partitions      │
  │  - serves producers/consumers   │
  │  - no cluster metadata logic    │
  └─────────────────────────────────┘

process.roles = controller,broker   ← combined (dev/test only)
──────────────────────────────────────────────────
  ┌─────────────────────────────────┐
  │       COMBINED NODE             │
  │  - does both jobs above         │
  │  - NOT recommended in prod      │
  └─────────────────────────────────┘
```

## 4. Listener — What It Is

A listener is a TCP socket that the node opens to accept connections. You give each listener a logical name (a label). The same node can open many ports; each port gets its own name. These names matter because other config properties reference them by name.

```
Node with ONE listener:
──────────────────────────────────────────────────────────
  listeners = CONTROLLER://0.0.0.0:9093

              CONTROLLER NODE
              ┌────────────────────────────────────┐
              │                                    │
              │  new ServerSocket(9093)             │
              │         │                          │
              │         ▼  waiting for TCP connect │
              │   ┌─────────────┐                  │
              │   │  port 9093  │  label: CONTROLLER│
              │   └─────────────┘                  │
              └────────────────────────────────────┘

Node with TWO listeners:
──────────────────────────────────────────────────────────
  listeners = BROKER://0.0.0.0:9092,INTERNAL://0.0.0.0:9098

              BROKER NODE
              ┌───────────────────────────────────────┐
              │                                       │
              │   ┌────────────┐  label: BROKER       │
              │   │  port 9092 │  ← for producers     │
              │   └────────────┘    and consumers     │
              │                                       │
              │   ┌────────────┐  label: INTERNAL     │
              │   │  port 9098 │  ← for broker-to-    │
              │   └────────────┘    broker sync       │
              └───────────────────────────────────────┘

  inter.broker.listener.name = INTERNAL   ← use this port for broker sync
```

## 5. Controller Configuration — Key Properties

Each controller node gets its own `.properties` file placed inside the `config/` folder. Controller 1 and Controller 2 are nearly identical — only `node.id` and the port number differ.

```
controller1.properties                controller2.properties
─────────────────────────────         ─────────────────────────────
process.roles=controller              process.roles=controller
node.id=1                             node.id=2
                                      ▲
                                      └─ unique in the whole cluster

listeners=CONTROLLER://               listeners=CONTROLLER://
  0.0.0.0:9093                          0.0.0.0:9193
         ▲                                       ▲
         └── TCP socket opened here              └── different port

controller.listener.names=CONTROLLER  controller.listener.names=CONTROLLER
         ▲                                       ▲
         └─ "use the CONTROLLER listener         └─ same name must match
            for controller-to-controller            across both nodes
            communication"

controller.quorum.voters=             controller.quorum.voters=
  1@localhost:9093,                     1@localhost:9093,
  2@localhost:9193                      2@localhost:9193
         ▲                                       ▲
         └─ static list of ALL                   └─ both controllers keep
            controllers in the cluster              the same full list

listener.security.protocol.map=       listener.security.protocol.map=
  CONTROLLER:PLAINTEXT                  CONTROLLER:PLAINTEXT
         ▲                                       ▲
         └─ no TLS/auth (dev mode)               └─ must match each other

log.dirs=/tmp/controller1-logs        log.dirs=/tmp/controller2-logs
num.partitions=3                      num.partitions=3
default.replication.factor=2          default.replication.factor=2
         ▲
         └─ controller decides partition layout and replication
            using these defaults when no value is given at topic creation
```

## 6. Broker Configuration — Key Properties

Each broker also gets its own `.properties` file in `config/`. Brokers carry some extra properties that controllers do not have: `advertised.listeners`, `inter.broker.listener.name`, and consumer offset settings.

```
broker1.properties
──────────────────────────────────────────────────────────────────
process.roles=broker
node.id=3                           ← IDs 1 and 2 are taken by controllers

listeners=BROKER://0.0.0.0:9092     ← port this broker opens

advertised.listeners=               ← "tell the controller to store
  BROKER://localhost:9092              THIS address in cluster metadata
                                       so producers/consumers can reach me"

inter.broker.listener.name=BROKER   ← brokers sync with each other
                                       on this same port (can be separate)

controller.listener.names=CONTROLLER ← when talking to any controller,
                                       use the listener named CONTROLLER
                                       (must match the name used in
                                        controller.properties)

listener.security.protocol.map=
  BROKER:PLAINTEXT,
  CONTROLLER:PLAINTEXT              ← both channels use no encryption

log.dirs=/tmp/broker1-logs
log.retention.hours=168             ← keep data for 7 days
log.segment.bytes=1073741824        ← max 1 GB per segment file

offsets.topic.replication.factor=2  ← consumer offset topic replication
                                       (broker manages consumer offsets,
                                        NOT the controller)
```

## 7. advertised.listeners — How Producers Find the Right Broker

When a producer wants to publish to a topic, it does not know which broker holds the leader partition. This diagram shows the full journey that `advertised.listeners` enables.

```
STARTUP (broker registers itself)
──────────────────────────────────────────────────────────────
  Broker 1 starts
       │
       ▼
  Sends its advertised.listeners (localhost:9092) to Controller
       │
       ▼
  Controller stores it in Cluster Metadata:
  ┌───────────────────────────────────────────────────────┐
  │  Cluster Metadata                                     │
  │  topic: order-events                                  │
  │    partition-0:  leader=Broker1  address=localhost:9092│
  │    partition-1:  leader=Broker2  address=localhost:9192│
  └───────────────────────────────────────────────────────┘

PUBLISH TIME (producer connects)
──────────────────────────────────────────────────────────────
  Producer
    │  1. connect to any broker (bootstrap)
    ▼
  Broker 1
    │  2. fetch metadata from active controller
    ▼
  Controller
    │  3. return cluster metadata
    ▼
  Broker 1 → returns metadata to Producer
    │
    ▼
  Producer now knows:  partition-0 leader = Broker 1 @ localhost:9092
    │  4. send records directly to Broker 1:9092
    ▼
  Broker 1   ✓
```

## 8. Cluster Bootstrap — Generate ID and Format Nodes

Before starting any server you must tie all four nodes to the same cluster. This is a two-step one-time operation per cluster: generate one UUID, then stamp every node with it.

```
STEP 1 — Generate cluster ID (run once)
──────────────────────────────────────────────────────────────
  $ bin/kafka-storage.sh random-uuid
  → xAb3Kz9pQmNrLuVwYtCiDe   (example UUID)

STEP 2 — Format each node's storage (run once per node)
──────────────────────────────────────────────────────────────
  $ bin/kafka-storage.sh format \
      -t xAb3Kz9pQmNrLuVwYtCiDe \
      -c config/controller1.properties

  Repeat for controller2, broker1, broker2

RESULT — meta.properties written to each node's log.dirs
──────────────────────────────────────────────────────────────
  /tmp/controller1-logs/meta.properties
    cluster.id=xAb3Kz9pQmNrLuVwYtCiDe
    node.id=1

  /tmp/controller2-logs/meta.properties
    cluster.id=xAb3Kz9pQmNrLuVwYtCiDe
    node.id=2

  /tmp/broker1-logs/meta.properties
    cluster.id=xAb3Kz9pQmNrLuVwYtCiDe
    node.id=3

  /tmp/broker2-logs/meta.properties
    cluster.id=xAb3Kz9pQmNrLuVwYtCiDe
    node.id=4
                    ▲
                    └─ all four nodes share the same cluster.id
                       → they form ONE cluster
```

## 9. Startup Order — Controllers First, Then Brokers

Brokers must find an active controller the moment they start (to load cluster metadata). If you start a broker before any controller is up, the broker has nowhere to register and will fail.

```
CORRECT startup order
──────────────────────────────────────────────────────────────

  Terminal 1                      Terminal 2
  ─────────────────────────────   ─────────────────────────────
  bin/kafka-server-start.sh       bin/kafka-server-start.sh
    config/controller1.properties   config/controller2.properties
  [controller1 STARTED]           [controller2 STARTED]
        │                               │
        └───────────┬───────────────────┘
                    │  quorum forms, leader elected
                    ▼
  Terminal 3                      Terminal 4
  ─────────────────────────────   ─────────────────────────────
  bin/kafka-server-start.sh       bin/kafka-server-start.sh
    config/broker1.properties       config/broker2.properties
  [broker1 STARTED, node.id=3]    [broker2 STARTED, node.id=4]


WRONG startup order   ✗
──────────────────────────────────────────────────────────────
  Start broker1 first
       │
       ▼  tries to contact controller → no controller up → ERROR
```

## 10. Controller Leader Election

When multiple controllers start, they run a Raft-based quorum election to choose one leader. The leader is the **active controller** — the single source of truth for cluster metadata. You can inspect who won by checking the quorum-state file.

```
QUORUM ELECTION AFTER STARTUP
──────────────────────────────────────────────────────────────
  Controller 1          Controller 2
  ┌──────────────┐       ┌──────────────┐
  │  starts up   │◄─────►│  starts up   │
  │              │       │              │
  │  I want to   │       │  I want to   │
  │  be leader!  │       │  be leader!  │
  └──────┬───────┘       └──────┬───────┘
         │   Raft vote           │
         └──────────┬────────────┘
                    ▼
          Leader = Controller 1 (node.id=1)
          Follower = Controller 2 (node.id=2)

VERIFY via quorum-state file:
──────────────────────────────────────────────────────────────
  /tmp/controller2-logs/
  └── quorum-state
        {
          "leaderId": 1,        ← node.id 1 won the election
          "epoch": 1
        }

VERIFY via CLI:
──────────────────────────────────────────────────────────────
  $ bin/kafka-metadata-quorum.sh \
      --bootstrap-server localhost:9092 describe --status

  Output:
  LeaderId:          1               ← active controller
  CurrentVoters:     [1, 2]          ← the two controllers
  CurrentObservers:  [3, 4]          ← the two brokers
  ClusterId:         xAb3Kz9pQmNrLuVwYtCiDe
```

## 11. Topic Creation and Partition Distribution

Creating a topic requires calling a broker (not the controller directly). The controller then decides which broker holds which partition and which replicas are followers.

```
TOPIC CREATION COMMAND
──────────────────────────────────────────────────────────────
  $ bin/kafka-topics.sh \
      --bootstrap-server localhost:9092 \
      --create \
      --topic order-events

  (no --partitions or --replication-factor given →
   controller uses defaults from config: 3 partitions, RF=2)

RESULT — partition layout decided by controller
──────────────────────────────────────────────────────────────
  Topic: order-events
  ┌────────────────────────────────────────────────────┐
  │  Partition 0   Leader=4   Replicas=[4,3]  ISR=[4,3]│
  │  Partition 1   Leader=3   Replicas=[3,4]  ISR=[3,4]│
  │  Partition 2   Leader=4   Replicas=[4,3]  ISR=[4,3]│
  └────────────────────────────────────────────────────┘
              │                    │
              ▼                    ▼
        node.id=4             node.id=3
        Broker 2              Broker 1

  Replication factor = 2 → every partition stored on 2 brokers
  ISR = In-Sync Replicas (followers caught up with leader)

DESCRIBE command to verify:
──────────────────────────────────────────────────────────────
  $ bin/kafka-topics.sh \
      --bootstrap-server localhost:9092 \
      --describe \
      --topic order-events
```

## 12. CLI Testing — Producer and Consumer

Once the cluster is running you can test it without writing any Java application by using the console scripts that ship with Kafka.

```
PRODUCER (publish messages from terminal)
──────────────────────────────────────────────────────────────
  $ bin/kafka-console-producer.sh \
      --bootstrap-server localhost:9092 \
      --topic order-events

  > hello
  > this is a test message
  > how are you
                    ▲
                    type a line and hit Enter to publish one event

CONSUMER (read messages in another terminal)
──────────────────────────────────────────────────────────────
  $ bin/kafka-console-consumer.sh \
      --bootstrap-server localhost:9092 \
      --topic order-events \
      --from-beginning

  hello                  ← reads all events from the start
  this is a test message
  how are you

FLOW
──────────────────────────────────────────────────────────────
  Producer terminal           Kafka Cluster           Consumer terminal
  ┌──────────────┐   publish  ┌──────────────┐  read  ┌──────────────┐
  │ console-     │──────────► │  order-events│──────► │ console-     │
  │ producer.sh  │            │  (3 partitions│        │ consumer.sh  │
  └──────────────┘            └──────────────┘        └──────────────┘
                                      ▲
                              note: producer connects to any broker,
                              metadata lookup routes to correct leader
```

## Quick Reference

```
Concept                         What it does                              Key rule
──────────────────────────────  ────────────────────────────────────────  ────────────────────────────────────
process.roles                   Declares node type (controller/broker)    Set once; no overlap in production
node.id                         Unique integer for each node in cluster   Must be unique across ALL nodes
listeners                       TCP sockets this node opens               Each port gets a logical label/name
controller.listener.names       Which listener to use for ctrl↔ctrl talk  Label must match across all controllers
advertised.listeners            Address broker advertises to controller   Stored in cluster metadata for clients
inter.broker.listener.name      Which listener brokers use to sync        Can be same or different from client port
controller.quorum.voters        Static list of all controller nodes       format: id@host:port, comma-separated
listener.security.protocol.map  Encryption mode per listener label        PLAINTEXT (dev) or SSL (production)
log.dirs                        Where node persists its data files        Each node must have its own directory
kafka-storage.sh random-uuid    Generates the cluster ID                  Run once per cluster lifetime
kafka-storage.sh format         Stamps a node with the cluster ID         Run for every node before first start
meta.properties                 Written to log.dirs after format step     Holds cluster.id + node.id
kafka-server-start.sh           Starts a node (controller or broker)      Start controllers before brokers
kafka-metadata-quorum.sh        Shows leader, voters, observers           Voters = controllers, Observers = brokers
kafka-topics.sh --create        Creates a topic via a broker              Cannot create directly on controller
num.partitions                  Default partition count for new topics     Set in controller config
default.replication.factor      Default replica count for new topics       Set in controller config
offsets.topic.replication.factor Replication for consumer offset topic    Set in broker config, NOT controller
log.retention.hours             How long segments are kept (default 7d)   Deletes whole segments, not individual events
log.segment.bytes               Max size of one log segment file          Default cap is 1 GB
```
