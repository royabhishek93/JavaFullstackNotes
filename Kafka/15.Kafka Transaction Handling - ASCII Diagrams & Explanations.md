# Kafka Transaction Handling — ASCII Diagrams & Explanations

Topics: transactional.id, Transaction Coordinator, __transaction_state, Producer ID, Epoch, Zombie Fencing, Begin/Commit/Abort, Two-Phase Commit, EOS

---

## 1. Three Problems That Transactions Solve

Transactions exist to fix three specific failure scenarios in Kafka producers.

```
PROBLEM 1 — Duplicate on producer restart (idempotency gap)
─────────────────────────────────────────────────────────────
  Producer crashes → restarts → gets NEW producer ID
  Old PID lost → sequence numbers reset → duplicates possible

PROBLEM 2 — Partial write (atomicity gap)
─────────────────────────────────────────────────────────────
  Goal: publish order-event AND payment-event AND inventory-event together

  order-event     ──► broker  ✓  written
  payment-event   ──► broker  ✓  written
  inventory-event ──► broker  ✗  FAILED

  Result: order placed, payment taken, but stock NOT reserved  ← inconsistent!

PROBLEM 3 — Read-process-write duplicate (consumer-side)
─────────────────────────────────────────────────────────────
  Consumer reads offset 50 → processes → publishes new event → tries to commit offset
                                                                       │
                                                                  offset commit LOST
                                                                       │
  Consumer polls again → gets offset 50 again → processes AGAIN → publishes AGAIN
  ✗ duplicate event published to downstream topic
```

## 2. Transaction ID (transactional.id)

A transaction ID is a stable, human-assigned string that uniquely identifies a producer instance across restarts.

```
application.properties:
  spring.kafka.producer.transaction-id-prefix=order-svc-

Spring Boot appends "0" automatically → final ID = "order-svc-0"

                     ┌─────────────────────────────────────────┐
                     │  Rules for transaction-id-prefix        │
                     │                                         │
                     │  ✓  Must be STABLE across restarts      │
                     │  ✓  Must be UNIQUE per producer instance │
                     │  ✗  Never use random UUID  ← breaks EOS │
                     └─────────────────────────────────────────┘

Multiple instances of the same app:
  Instance 1 → order-svc-pod-abc  (use Kubernetes hostname)
  Instance 2 → order-svc-pod-def
  Instance 3 → order-svc-pod-ghi

  Each instance MUST have a different transaction ID
  (reason: zombie fencing — explained in section 5)
```

## 3. Finding the Transaction Coordinator

The transaction coordinator is the single broker responsible for managing all transactions for a given producer. It is found via a hash of the transaction ID, exactly like how consumer group coordinators are found.

```
KAFKA CLUSTER
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  __transaction_state  (internal topic, 50 partitions)           │
│  ┌──────┬──────┬──────┬──────┬──────────────────────┐           │
│  │ P-0  │ P-1  │ P-2  │ ... │ P-49                 │           │
│  └──┬───┴──┬───┴──┬───┴──────┴──────────────────────┘           │
│     │      │      │                                             │
│   Broker1 Broker2 Broker3   ← each broker leads some partitions │
└─────────────────────────────────────────────────────────────────┘

Producer with transactional.id = "order-svc-0"

Step 1: send FindCoordinator request to ANY broker, pass transaction ID
Step 2: that broker computes:
          partition = hash("order-svc-0") mod 50  →  e.g. partition 23
Step 3: broker looks up who is leader of __transaction_state partition 23
          → Broker 2 is the leader
Step 4: broker replies: "your transaction coordinator is Broker 2"
Step 5: producer connects directly to Broker 2 for all future transaction calls

  Producer ──FindCoordinator──► any broker ──► "use Broker 2"
  Producer ◄─────────────────────────────────────────────────
  Producer ──all transaction requests──────────► Broker 2
```

## 4. The __transaction_state Topic — What Gets Stored

For each producer with a transaction ID, the transaction coordinator stores a record in `__transaction_state`. This is the brain of the transaction system.

```
Row stored in __transaction_state (partition 23 for "order-svc-0"):

  ┌───────────────────┬────────────┬───────┬───────────────────────────────────┬─────────────┐
  │  transaction_id   │  pid (PID) │ epoch │  state                            │  partitions │
  ├───────────────────┼────────────┼───────┼───────────────────────────────────┼─────────────┤
  │  "order-svc-0"    │  5         │  0    │  EMPTY → ONGOING → PREPARE_COMMIT │  [topic-A/0,│
  │                   │            │       │                  → COMMITTED       │   topic-B/2]│
  │                   │            │       │  EMPTY → ONGOING → PREPARE_ABORT   │             │
  │                   │            │       │                  → ABORTED         │             │
  └───────────────────┴────────────┴───────┴───────────────────────────────────┴─────────────┘

  field           meaning
  ──────────────  ──────────────────────────────────────────────────────────────
  transaction_id  the stable string you set in application.properties
  pid             producer ID — a number assigned by the broker (like idempotency)
  epoch           version counter — increments each time producer (re)initialises
  state           current phase of the transaction lifecycle
  partitions      which topic-partitions are touched by the active transaction
  timeout         max time a transaction can stay ONGOING before auto-abort

State flow:
  EMPTY ──begin──► ONGOING ──commit request──► PREPARE_COMMIT ──► COMMITTED
                         └──abort  request──► PREPARE_ABORT  ──► ABORTED

  Once PREPARE_COMMIT or PREPARE_ABORT is written → point of no return
  Even if broker crashes, on recovery it must finish in that direction
```

## 5. Producer ID, Epoch, and Zombie Fencing

When a producer first connects, it calls `initTransactions()` to get a producer ID. The epoch (version number) is the key to blocking "zombie" producers — old instances that come back after being replaced.

```
INIT PRODUCER ID REQUEST (happens once at startup):

  Producer ──InitProducerID(txn-id="order-svc-0")──► Transaction Coordinator
                                                              │
                                              check __transaction_state
                                                              │
                        ┌─────────────────────────────────────┤
                        │  First time ever?                   │
                        │  → generate PID=5, epoch=0          │
                        │  → write to __transaction_state     │
                        │  → return PID=5, epoch=0            │
                        │                                     │
                        │  Seen this txn-id before?           │
                        │  → abort any ONGOING transaction    │
                        │  → INCREMENT epoch (0 → 1)          │
                        │  → return same PID=5, epoch=1       │
                        └─────────────────────────────────────┘

ZOMBIE FENCING — why epoch matters:

  Time 0:  Producer-1 starts → PID=5, epoch=0 → begins transaction
           (network pause — Producer-1 appears dead to orchestrator)

  Time 1:  Kubernetes spawns Producer-2 (same txn-id "order-svc-0")
           → calls initTransactions
           → Coordinator aborts Producer-1's open transaction
           → epoch 0 → 1
           → Producer-2 gets PID=5, epoch=1

  Time 2:  Old Producer-1 revives and tries to commit (PID=5, epoch=0)
           → Coordinator checks: current epoch is 1, request says 0
           → REJECT with ProducerFencedException  ✗  ← zombie blocked!

  epoch acts like a fencing token — only the holder of the latest epoch is valid
```

## 6. Transaction State Machine

The states a transaction moves through, and what triggers each transition.

```
                        ┌──────────┐
                        │  EMPTY   │  ← initial state / after last commit or abort
                        └────┬─────┘
                             │  beginTransaction()
                             ▼
                        ┌──────────┐
                        │ ONGOING  │  ← events are being sent
                        └────┬─────┘
               commit()      │        abort()
              ┌──────────────┘──────────────────┐
              ▼                                 ▼
  ┌──────────────────┐               ┌─────────────────┐
  │  PREPARE_COMMIT  │               │  PREPARE_ABORT  │
  └────────┬─────────┘               └────────┬────────┘
           │  send COMMIT control              │  send ABORT control
           │  records to all brokers           │  records to all brokers
           ▼                                 ▼
  ┌──────────────────┐               ┌─────────────────┐
  │    COMMITTED     │               │     ABORTED     │
  └──────────────────┘               └─────────────────┘
           │                                  │
           └──────────────┬───────────────────┘
                          ▼
                       EMPTY  (ready for next transaction)

  KEY RULE: transaction is single-threaded per producer.
  While a transaction is ONGOING, you cannot begin another one.
```

## 7. Begin Transaction — Sending Events

Before each send, an interceptor notifies the transaction coordinator which partition will be touched, so it can update the "partitions involved" list.

```
Producer                 Transaction Coordinator         Partition Leader (Broker)
   │                            │                               │
   │──beginTransaction()──────► │                               │
   │                            │ state: EMPTY → ONGOING        │
   │                            │                               │
   │──(interceptor) AddPartitionToTxn(order-events/P2)──────► │ │
   │                            │ partitions: [order-events/P2] │
   │                            │ state: still ONGOING          │
   │◄──OK──────────────────────┘│                               │
   │                            │                               │
   │──send(order-event, key, value).join()─────────────────────►│
   │                            │                               │ appends to log:
   │                            │                               │ PID=5, epoch=0,
   │                            │                               │ is_transactional=true
   │                            │                               │ [record data]
   │◄──ACK─────────────────────────────────────────────────────┘│
   │                            │                               │
   │──(interceptor) AddPartitionToTxn(payment-events/P1)──────►│
   │                            │ partitions: [order-events/P2, │
   │                            │              payment-events/P1]│
   │◄──OK──────────────────────┘│                               │
   │                            │                               │
   │──send(payment-event, ...).join()──────────────────────────►│ (payment broker)
   │◄──ACK─────────────────────────────────────────────────────┘│

IMPORTANT: always call .join() (or .get()) on each send Future when inside
a transaction — this makes your thread wait for the broker ACK. Without it,
a failure is detected too late to abort the transaction correctly.
```

## 8. Commit Flow — Two-Phase Commit

Committing a transaction is a two-phase process. The coordinator writes "prepare commit" first (point of no return), then sends commit control records to every affected partition.

```
Producer               Transaction Coordinator          Brokers holding
                                                        touched partitions
   │                           │
   │──commitTransaction()─────►│
   │                           │ 1. write PREPARE_COMMIT to __transaction_state
   │                           │    ← point of no return
   │                           │
   │                           │──commit control record──► order-events/P2 leader
   │                           │                                │ append to log:
   │                           │                                │ PID=5, epoch=0,
   │                           │                                │ is_control=true, COMMIT
   │                           │◄──done──────────────────────┘│
   │                           │
   │                           │──commit control record──► payment-events/P1 leader
   │                           │                                │ append to log:
   │                           │                                │ PID=5, epoch=0,
   │                           │                                │ is_control=true, COMMIT
   │                           │◄──done──────────────────────┘│
   │                           │
   │                           │ 2. write COMMITTED to __transaction_state
   │◄──success────────────────┘│

Partition log (order-events P2) after commit:

  offset 0: PID=5, epoch=0, is_transactional=true, is_control=false  [order record]
  offset 1: PID=5, epoch=0, is_transactional=true, is_control=true   COMMIT  ← control record
```

## 9. Abort Flow

Abort is identical to commit, just with ABORT control records instead of COMMIT. No data is deleted — Kafka is append-only. The abort marker tells consumers to skip those records.

```
Producer               Transaction Coordinator          Brokers
   │                           │
   │──abortTransaction()──────►│  (triggered by exception inside execute-in-transaction)
   │                           │ 1. write PREPARE_ABORT to __transaction_state
   │                           │
   │                           │──abort control record──► order-events/P2 leader
   │                           │                               │ append: PID=5, epoch=0,
   │                           │                               │ is_control=true, ABORT
   │                           │◄──done──────────────────────┘│
   │                           │ 2. write ABORTED to __transaction_state
   │◄──success────────────────┘│

Partition log (order-events P2) after abort:

  offset 0: PID=5, epoch=0, is_transactional=true, is_control=false  [order record]
  offset 1: PID=5, epoch=0, is_transactional=true, is_control=true   ABORT   ← control record

NOTE: the original data record at offset 0 is still physically in the log.
The ABORT control record at offset 1 is what tells consumers to ignore offset 0.
```

## 10. Full Transaction Lifecycle (Complete Picture)

```
 PRODUCER APP                  TRANSACTION COORDINATOR         BROKER(S)
 ────────────                  ───────────────────────         ─────────
  startup
    │
    ├─1─ find coordinator ────────────────────────────────────────────────►
    │◄──────────────────────────────────────────── "your coordinator is B2"
    │
    ├─2─ initTransactions() ─────────────────────► write to __txn_state:
    │                                              {txn-id, PID=5, epoch=0, EMPTY}
    │◄────────────────────────────────────────────── return PID=5, epoch=0
    │
  per transaction (repeats):
    │
    ├─3─ beginTransaction()     (local only, no network call)
    │
    ├─4─ AddPartitionToTxn ─────►  update partitions in __txn_state
    │    send(event-A).join() ──────────────────────────────────────────► Broker
    │                                                                      append log
    │◄──────────────────────────────────────────────────────────────────── ACK
    │
    ├─5─ AddPartitionToTxn ─────►  update partitions in __txn_state
    │    send(event-B).join() ──────────────────────────────────────────► Broker
    │◄──────────────────────────────────────────────────────────────────── ACK
    │
    ├─6─ commitTransaction() ───►  write PREPARE_COMMIT
    │                          ──────────────────────────────────────────► send COMMIT control records
    │                              write COMMITTED
    │◄──────────────────────────── success
    │
    └─ (loop back to step 3 for next transaction)
```

## 11. Spring Boot — Key Configuration

```
# application.properties (producer)

# Required: assign a stable transaction ID
spring.kafka.producer.transaction-id-prefix=order-svc-

# Optional: override the default 60-second timeout
spring.kafka.producer.properties.transaction.timeout.ms=60000

# In code — wrap sends inside execute-in-transaction:
kafkaTemplate.executeInTransaction(ops -> {
    ops.send("order-events",   key, orderEvent).join();
    ops.send("payment-events", key, paymentEvent).join();
    return true;   // commit
    // any RuntimeException thrown here triggers abort automatically
});
```

## 12. Quick Reference

```
Concept                  What it is                                    Key point
───────────────────────  ────────────────────────────────────────────  ──────────────────────────────────────
transactional.id         Stable string ID assigned to a producer       Must NOT change on restart (no UUID)
Transaction Coordinator  Broker that manages transaction lifecycle      Determined by hash(txn-id) mod 50
__transaction_state      Internal Kafka topic, 50 partitions           Stores PID, epoch, state, partitions
PID (Producer ID)        Number that identifies a producer to broker   Same PID returned for same txn-id
Epoch                    Version counter for a producer's PID          Increments on each initTransactions()
Zombie fencing           Blocking a revived old producer               Old epoch rejected with ProducerFencedException
EMPTY                    Transaction not started yet                   Initial and post-commit/abort state
ONGOING                  Transaction in progress                       Events are being sent
PREPARE_COMMIT           Point of no return toward commit              Written before sending COMMIT control records
PREPARE_ABORT            Point of no return toward abort               Written before sending ABORT control records
Control record           Special log entry marking COMMIT or ABORT     is_control=true; broker never sends to consumer
executeInTransaction()   Spring helper wrapping begin/commit/abort     Provide a lambda; .join() each send inside it
Two-phase commit         Write PREPARE first, then send control recs   Survives broker crashes mid-commit

Problems solved by transactions:
  Partial write          → group all sends in one transaction; all succeed or all abort
  PID loss on restart    → PID stored in __transaction_state against txn-id; same PID returned after restart
  Read-process-write dup → tie publish + offset commit into one atomic transaction (covered in consumer side)
```
