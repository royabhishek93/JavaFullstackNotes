Consumer Groups

A consumer group is a team of consumers that split the work of reading a topic together. Each consumer in the group handles different partitions — no two consumers in the same group read the same partition.

KAFKA BROKER ┌──────────────────────────────┐ │ Topic: order-events │ │ ┌──────┐ ┌──────┐ ┌──────┐ │ │ │ P-0 │ │ P-1 │ │ P-2 │ │ └──┴──┬───┴─┴──┬───┴─┴──┬───┘─┘ │ │ │ ┌────────┘ ┌────┘ ┌───┘ │ │ │ ▼ ▼ ▼ Group: "notification" Group: "analytics" ┌──────────────────────┐ ┌──────────────────────┐ │ Consumer1 → P-0 │ │ Consumer4 → P-0 │ │ Consumer2 → P-1 │ │ Consumer5 → P-1,P-2 │ │ Consumer3 → P-2 │ └──────────────────────┘ └──────────────────────┘

Key Rules:

  • Same group → each partition goes to only one consumer
  • Different groups → same partition can be read by consumers in both groups simultaneously

Partition Assignment Scenarios

How partitions get assigned depends on the number of consumers vs partitions:

Scenario A: consumers == partitions (ideal 1-to-1) ────────────────────────────────────────────────── P-0 ──► Consumer1 P-1 ──► Consumer2 P-2 ──► Consumer3 Scenario B: consumers < partitions (some consumers handle more) ────────────────────────────────────────────────────────────────── P-0 ──► Consumer1 P-1 ──► Consumer1 ← Consumer1 handles 2 partitions P-2 ──► Consumer2 Scenario C: consumers > partitions (some sit idle) ─────────────────────────────────────────────────── P-0 ──► Consumer1 P-1 ──► Consumer2 P-2 ──► Consumer3 Consumer4 ← IDLE, no partition assigned!

Offset — The Bookmark

An offset is just a number — the position of the last successfully processed message. Each consumer group tracks its own offset per partition, independently.

Topic: order-events, Partition-0 ───────────────────────────────────────────────────────────── Events: [0][1][2]...[299][300][301]...[499][500][501]... ▲ ▲ │ │ analytics group notification group "I've read up to 300" "I've read up to 500"

Same partition, two groups, two different bookmarks — completely independent!

Where Is the Offset Stored? (__consumer_offsets)

Kafka stores offsets inside Kafka itself — in a special internal topic called __consumer_offsets. Kafka auto-creates this topic with 50 partitions by default.

Step 1: Consumer finishes reading P-0, reaches offset 500 Consumer (group: notification) │ │ builds this commit message: ▼ ┌─────────────────────────────────────────┐ │ group_id = "notification" │ │ topic = "order-events" │ │ partition = 0 │ │ offset = 500 │ └─────────────────────────────────────────┘ Step 2: Figure out which partition of __consumer_offsets to write to hash("notification") % 50 = 23 │ ▼ ┌──────────────────────────────────────────────────────────┐ │ __consumer_offsets (50 partitions) │ │ P-0 P-1 ... P-22 [ P-23: notification data ] P-24 ...│ └──────────────────────────────────────────────────────────┘ Why hash? So the same group ALWAYS maps to the same partition — consistent reads & writes. Why 50 partitions? Many groups can store offsets in parallel without a bottleneck.

Consumer Crash & Recovery

This is the payoff of storing offsets in Kafka — consumers can resume after a crash with no data loss.

BEFORE CRASH: ───────────────────────────────────────────────────────────── Consumer1 (notification group) reads order-events P-0 Reaches offset 500 → commits to __consumer_offsets Stored: {notification, order-events, P-0} = 500 Consumer1 ✗ CRASHES RECOVERY: ───────────────────────────────────────────────────────────── Consumer2 is assigned P-0 (takes over) │ │ 1. Compute: hash("notification") % 50 → partition 23 │ 2. Ask broker holding partition 23: │ "For group=notification, topic=order-events, P-0 — last offset?" │ 3. Gets back: 500 │ ▼ Consumer2 starts reading from offset 501 ✓

Kafka Cluster — Multiple Brokers

A Kafka cluster is just multiple brokers (servers) working together. Each broker holds some partitions. No single broker holds everything.

┌────────────────────────────────────────────────────────────────────┐ │ KAFKA CLUSTER │ │ │ │ ┌─────────────────┐ ┌─────────────────┐ ┌─────────────────┐ │ │ │ Broker 1 │ │ Broker 2 │ │ Broker 3 │ │ │ │ │ │ │ │ │ │ │ │ P-0 (LEADER) │ │ P-1 (LEADER) │ │ P-2 (LEADER) │ │ │ │ P-1 (follower) │ │ P-2 (follower) │ │ P-0 (follower) │ │ │ └─────────────────┘ └─────────────────┘ └─────────────────┘ │ │ │ │ Topic: order-events | 3 partitions | replication factor = 2 │ └────────────────────────────────────────────────────────────────────┘

Benefits:

  • Scalability — load is spread across multiple servers
  • Fault Tolerance — if one broker dies, others keep running
  • High Availability — no single point of failure

Leader vs Follower

For every partition, one broker is the leader (does real work) and others are followers (silent backups).

Producer writes to P-0: ───────────────────────────────────────────────────────────── Producer ──────────────────────► Broker 1 (P-0 LEADER) │ │ replicates automatically ▼ Broker 3 (P-0 follower) [stays in sync, never serves clients] Consumer reads from P-0: ───────────────────────────────────────────────────────────── Consumer ──────────────────────► Broker 1 (P-0 LEADER) Follower is invisible to consumers. Broker 1 crashes: ───────────────────────────────────────────────────────────── Broker 1 ✗ DOWN Broker 3's P-0 follower ──────► promotes to NEW LEADER Cluster stays up, no data lost ✓

Leader responsibilities:

  • Handle all producer writes
  • Handle all consumer reads
  • Maintain partition logs
  • Sync data to followers

Follower responsibilities:

  • Replicate data from leader
  • Stay in sync
  • Be ready to become leader if needed
  • Never serve clients directly

Who Decides Which Broker Holds What?

A special broker called the Controller makes all assignment decisions.

Kafka Cluster ┌─────────────────────────────────────────────────────┐ │ │ │ ┌──────────────┐ │ │ │ CONTROLLER │ ← one of the brokers takes │ │ │ (Broker 1) │ this special role │ │ └──────┬───────┘ │ │ │ decides: │ │ │ - which broker hosts which partition │ │ │ - which replica is leader │ │ │ - which replica is follower │ │ │ - re-assigns when a broker dies │ │ ▼ │ │ Broker 2, Broker 3 follow controller's orders │ └─────────────────────────────────────────────────────┘

Offset Commit Strategies

How and when consumers commit (save) their offset bookmark.

AUTO COMMIT (risky — can lose data) ───────────────────────────────────────────────────────────────────── Timeline: t=0s Poll → receive events [0..99] t=1s Start processing... t=5s AUTO COMMIT fires → stores "99 processed" in __consumer_offsets t=6s Consumer CRASHES at event 70 ✗ Restart: Asks "__consumer_offsets" → gets back 99 Starts from 100 ← events 70–99 are LOST FOREVER! Problem: commit happened before processing was done.
MANUAL COMMIT — full batch (recommended) ───────────────────────────────────────────────────────────────────── Timeline: t=0s Poll → receive batch [0..99] t=1s Processing events... t=3s Consumer CRASHES at event 70 ✗ Restart: Asks "__consumer_offsets" → gets back last manual commit (e.g. -1 / 0) Re-processes events 0–69 (duplicates, but safe) ✓ Continues and finishes batch [0..99] COMMITS → stores 99 in __consumer_offsets ✓ Next poll starts from 100 ✓ Trade-off: possible duplicate processing, but ZERO data loss.
MANUAL COMMIT — per event (not recommended) ───────────────────────────────────────────────────────────────────── Process event 0 → commit(0) Process event 1 → commit(1) Process event 2 → commit(2) ... Problem: 1 network call per event → huge overhead when processing millions of messages. Kafka is built for high throughput; per-event commits kill performance.

Recommendation: Manual commit with an appropriate batch size based on your use case.

Architecture — How Consumer Groups Power the Notification System

"Let me ground this in a real system before we go further. My Notification Service has 100 partitions on `notifications.standard.email`, and I run a consumer group called `email-workers` with 20 instances against it — this is where everything we just covered actually earns its keep."

notifications.standard.email (100 partitions) │ ▼ Consumer Group "email-workers" (20 instances) Consumer-1 → P0-P4 Consumer-2 → P5-P9 ... Consumer-20 → P95-P99 │ ▼ each commits progress independently, per partition, to __consumer_offsets (group_id=email-workers, topic, partition) → offset Group "sms-workers" reading the SAME topic? Not applicable here — but if it did, it would maintain a COMPLETELY separate offset, proving groups don't interfere.

Scenario-first: "Why 20 consumers, not 100 (one per partition)? Because email is throughput-bound by SendGrid's rate limit, not by Kafka — adding more consumers than the downstream API can absorb just means more idle workers. I size consumer count to the actual bottleneck, not to the partition count."

ER Relationship + Sequence — The Offset's Life

ER: ConsumerGroup (1) ──assigned──> Partition (N, via GroupCoordinator) Partition (1) ──tracked in──> __consumer_offsets (group_id,topic,partition)→offset SEQUENCE — crash and recovery: Consumer-7 GroupCoordinator __consumer_offsets Consumer-12 │ reads P42, commits offset 500 │ │ │────────────────────────────────────► │ │ │ CRASHES │ │ │ heartbeat missed → reassign P42 │ │ │──────────────────────►│ │ │ "give me last offset for P42" │ │◄──────────────────────│ 500 │ │ Consumer-12 resumes at 501 ✓

Scenario-first: "This is the exact reason offsets are stored per GROUP, not per consumer instance — Consumer-12 has never touched partition 42 before, but it can pick up exactly where Consumer-7 left off because the group, not the individual worker, owns that bookmark."

Cross Questions Interviewers Ask

Q: Why can't two consumers in the same group read the same partition? A: It would mean two workers independently committing offsets for the same partition — a race condition with no clear "true" progress marker. Kafka enforces 1:1 per group specifically to keep offset tracking unambiguous. Q: What happens if consumers > partitions? A: Extra consumers sit completely idle — there's nothing left to assign them. This is why I size consumer count to partition count and actual throughput need, not just "more must be faster." Q: Why 50 partitions for __consumer_offsets specifically? A: It's a Kafka default balancing parallel offset-commit throughput against operational overhead — many groups can commit concurrently without bottlenecking on one partition.

Senior Trap Questions (15 YOE)

Trap 1 — "You have 100 partitions and 20 consumers, evenly split 5-per-consumer. Traffic to 3 specific partitions is way higher than the rest. What happens?" Answer: "Those 3 partitions' consumer becomes a hot spot — it's handling 5 partitions but 2 of them dominate its time, effectively starving the other 3. Partition-level skew isn't fixed by adding more consumers; it's fixed by a better partition key or by isolating hot keys onto dedicated partitions." Trap 2 — "A consumer commits offset 500, then immediately crashes before actually finishing side effects for records 495-499. What's the risk?" Answer: "If commit happened before the side effect (calling SendGrid, say) completed, those records are now presumed done but never actually sent — a silent loss. This is exactly why I commit AFTER the side effect succeeds, never before, regardless of batching strategy."

WHY We Chose Each Decision

- Why consumer groups over one giant single consumer: horizontal scale — 20 workers process 20x faster than 1, with automatic failover built in. - Why offsets live in Kafka itself, not an external DB: no extra system to keep consistent with Kafka's own partition assignment and failover logic. - Why manual commit after processing, not auto-commit on a timer: ties "done" to actual completion, not to wall-clock time. - Why group-level (not consumer-level) offset tracking: any surviving group member can resume a crashed member's work with zero special-casing.

Top 2 Technologies — Where to Track Consumer Progress

Kafka-native __consumer_offsets vs External offset store (e.g. a DB table) Why pick Kafka-native (our choice): zero extra infrastructure, offsets live right alongside the data they describe, rebalance-aware out of the box. Why pick external store: needed when you must commit an offset atomically WITH a non-Kafka side effect (e.g. a DB write) in the same transaction — Kafka's own offset store can't participate in an external DB transaction. Example 1 (Kafka-native): Notification System's email-workers group — pure Kafka-to-provider-API flow, no need for atomicity with a DB write. Example 2 (external store): A consumer that updates a Postgres "processed orders" table — storing the offset in that SAME Postgres transaction guarantees the DB update and "I've processed this" are atomic together.
