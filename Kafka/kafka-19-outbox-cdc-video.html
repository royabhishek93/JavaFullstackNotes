Push vs Pull — The Core Idea

In polling, your code repeatedly asks the database for changes. In CDC, the database streams changes to you the moment they happen — no scheduler, no repeated queries.

POLLING (pull model): ┌──────────────────────┐ every 2 sec: "any new rows?" ┌──────────┐ │ Your Scheduler │ ─────────────────────────────► │ DB │ │ (custom code) │ ◄───────────────────────────── │ │ └──────────────────────┘ DB returns unpublished rows └──────────┘ Problems: constant DB load, polling gap, multi-instance conflicts CDC (push model): ┌──────────────────────┐ ┌──────────┐ │ Debezium │ ◄──── DB streams every INSERT ── │ DB │ │ (infrastructure) │ UPDATE, DELETE immediately │ │ └──────────────────────┘ └──────────┘ No scheduler. No delay. No constant DB load. No custom code.

How Databases Record Every Change — WAL and Binlog

Before a database modifies a table it first records the change in a transaction log file. This is the source of truth for crash recovery and replication. CDC reads this same file.

POSTGRES — Write-Ahead Log (WAL): ┌───────────────────────────────────────────────────────────────────┐ │ INSERT INTO outbox_events (aggregate_type, payload, ...) │ │ │ │ │ ▼ step 1 — written FIRST │ │ ┌──────────────────────────────────┐ │ │ │ WAL file (on disk) │ │ │ │ op: INSERT │ │ │ │ table: outbox_events │ │ │ │ row: { id, payload, ... } │ │ │ └──────────────────────────────────┘ │ │ │ │ │ ▼ step 2 — updated AFTER │ │ ┌──────────────────────────────────┐ │ │ │ Table pages (actual data) │ │ │ └──────────────────────────────────┘ │ └───────────────────────────────────────────────────────────────────┘ MYSQL uses a Binlog file — same concept, different name. WHY THE LOG FILE EXISTS: Crash recovery: replay WAL from last checkpoint → table restored ✓ DB replication: master sends WAL to slave databases ✓ CDC: Debezium subscribes like a slave, reads WAL ✓

WAL Level — Why "logical" Is Required

By default the WAL stores low-level binary page offsets that only another Postgres instance can decode. CDC needs human-readable column names and values — that requires changing the WAL level to logical.

WAL level: replica (default — binary format) ┌──────────────────────────────────────────────────────────┐ │ page 5, offset 120: changed from 0xAB to 0xCD │ │ page 8, offset 44: changed from 0x00 to 0x01 │ └──────────────────────────────────────────────────────────┘ Another Postgres slave: can decode this ✓ Debezium (CDC): cannot decode this ✗ WAL level: logical (required for CDC) ┌──────────────────────────────────────────────────────────┐ │ op: INSERT │ │ table: outbox_events │ │ id: "uuid-abc-123" │ │ aggregate_type: "ORDER" │ │ aggregate_id: "customer-K1" │ │ payload: { "orderId": 42, "amount": 500 } │ └──────────────────────────────────────────────────────────┘ Debezium can read this and publish to Kafka ✓ How to change: SHOW wal_level; ← check current level ALTER SYSTEM SET wal_level = logical; ← update it (restart Postgres for the change to take effect)

Debezium Attaches as a Replication Follower

Postgres already has a mechanism to stream the WAL to slave databases — a replication slot. Debezium registers itself in that same slot, exactly like a DB slave, and receives every WAL entry in real time.

NORMAL DB REPLICATION (no CDC): ┌────────────────┐ WAL stream ┌──────────┐ │ Master │ ────────────► │ Slave-1 │ │ Postgres │ ────────────► │ Slave-2 │ └────────────────┘ └──────────┘ WITH CDC — Debezium registers as another replication subscriber: ┌────────────────┐ WAL stream ┌──────────┐ │ Master │ ────────────► │ Slave-1 │ │ Postgres │ ────────────► │ Slave-2 │ │ │ ────────────► │ Debezium │◄─ replication slot └────────────────┘ └──────────┘ │ ▼ decodes WAL binary → logical │ (using pgoutput plugin) ▼ Kafka (Debezium acts as producer) Replication slot created by Debezium at startup: name: debezium_slot plugin: pgoutput ← decodes binary WAL to readable format publication: cdc_publication ← table-level filter (see next section)

Postgres Publication — Table-Level Filter

A publication tells Postgres which tables to include in the WAL stream sent to a CDC subscriber. Without it, every INSERT, UPDATE, DELETE on every table would be streamed to Debezium unnecessarily.

Your database: 100 tables ┌──────────────────────────────────────────────────────────────┐ │ orders users products payments inventory ... (×100) │ │ outbox_events ◄──────────────────── │ └──────────────────────────────────────────────────────────────┘ ▲ only this table CREATE PUBLICATION cdc_publication FOR TABLE public.outbox_events; Effect on the WAL stream sent to Debezium: ───────────────────────────────────────────────────────────────── INSERT into orders → filtered out ✗ (not in publication) INSERT into users → filtered out ✗ INSERT into products → filtered out ✗ INSERT into outbox_events → INCLUDED ✓ → Debezium receives it Two levels of filtering working together: ┌──────────────────────────────────────────────────────────┐ │ Level 1 — Postgres side: publication (cdc_publication) │ │ Level 2 — Debezium side: table.include.list │ │ Both point to public.outbox_events │ └──────────────────────────────────────────────────────────┘

Debezium Connector Configuration

A single properties file wires together the database connection, the replication slot, the publication, and the mapping of outbox table columns to Kafka message fields.

debezium-postgres-connector.properties ───────────────────────────────────────────────────────────────── name=outbox-connector ← any name for this connector # Which Debezium plugin to use (swap to MySQL plugin for MySQL) connector.class=io.debezium.connector.postgresql.PostgresConnector # DB connection database.hostname=localhost database.port=5432 database.user=postgres database.password=secret database.dbname=outbox_cdc_db # Level-2 filter — only watch this table table.include.list=public.outbox_events # Replication slot settings slot.name=debezium_slot plugin.name=pgoutput ← decodes WAL binary → logical format # Use the publication we created manually in Postgres publication.auto.create.mode=disabled publication.name=cdc_publication # Read existing rows first, then stream new ones snapshot.mode=initial # Map outbox table columns to Kafka message fields transforms=outbox transforms.outbox.type=...EventRouter transforms.outbox.table.field.event.id=id ← deduplication key transforms.outbox.table.field.event.key=aggregate_id ← Kafka message key transforms.outbox.table.field.event.payload=payload ← Kafka message value transforms.outbox.route.by.field=aggregate_type ← determines topic transforms.outbox.route.topic.replacement=\${routedByValue}-events # aggregate_type = "ORDER" → topic: ORDER-events snapshot.mode=initial explained: outbox_events already has 100 rows when CDC starts ┌────────────────────────────────────────────────────────┐ │ Phase 1 — snapshot: read all 100 existing rows, send │ │ Phase 2 — streaming: receive new inserts via WAL │ └────────────────────────────────────────────────────────┘

Polling vs CDC — Side-by-Side Comparison

Both approaches solve the dual-write problem using the same outbox table. They differ in how the relay from the outbox table to Kafka is implemented.

POLLING CDC (Debezium) ──────────────────────────── ─────────────────── ──────────────────────────── Custom code required Yes (scheduler) ✗ No ✓ Constant DB load Yes (every N sec) ✗ No (event-driven) ✓ Event delivery latency Up to N seconds ✗ Milliseconds ✓ Multi-instance locking Needed (ShedLock) ✗ Handled by Debezium ✓ published column needed Yes ✗ No ✓ Table cleanup job needed Yes ✗ Not required ✓ At-least-once delivery Yes ✓ Yes ✓ Idempotent consumer needed Yes ✓ Yes ✓ Simple to understand Yes ✓ More setup required ✗ Infrastructure dependency None ✓ Kafka Connect + Debezium ✗ Works with any DB Yes ✓ DB must support logical WAL ✗ Scales automatically No (needs work) ✗ Yes (Kafka Connect scales) ✓ What stays the same in both: ┌───────────────────────────────────────────────────────────────┐ │ ► Same outbox table schema (minus published/published_at) │ │ ► Same @Transactional boundary in the application │ │ ► Same at-least-once delivery guarantee │ │ ► Same requirement for idempotent consumers │ │ ► Both solve the dual-write problem correctly │ └───────────────────────────────────────────────────────────────┘

Architecture — What Switching to Debezium Would Actually Look Like

"If our polling publisher ever hits its scale ceiling, here's exactly what I'd stand up instead — CDC reading directly off Postgres's WAL, replacing the 100ms poll entirely."

Notification Service (unchanged: same outbox table, same TX boundary) │ BEGIN TX → INSERT notifications + notifications_outbox → COMMIT ▼ Postgres WAL (logical level) — records the INSERT the instant it commits │ ▼ Debezium (Kafka Connect plugin) subscribed via replication slot │ publication scoped to notifications_outbox ONLY ▼ EventRouter transform: aggregate_id→key, payload→value, aggregate_type→topic ▼ Kafka (same topics, same consumers — zero downstream changes needed)

Scenario-first: "The beauty of this migration is that NOTHING downstream changes — delivery consumers, idempotency checks, everything stays identical. Only the publisher mechanism swaps, because the outbox table's contract (self-contained payload, aggregate_id as key) was designed to support either approach from day one."

Cross Questions Interviewers Ask

Q: Why must the outbox payload be fully self-contained, regardless of polling or CDC? A: If the publisher needs a second DB lookup to build the Kafka message, that joined data could change between the outbox write and the actual publish — a race condition. Denormalize into the payload at write time, always. Q: Why does switching to CDC eliminate the need for the published column entirely? A: Debezium tracks its own read position against the Postgres WAL's log sequence number, completely independent of any column in your table — it never re-reads a row it's already streamed. Q: What operational risk does CDC introduce that polling doesn't have? A: A stuck or lagging Kafka Connect connector is a new, more sophisticated failure mode — silently starving the pipeline in a way that's harder to diagnose than "the polling job's query got slow."

Senior Trap Questions (15 YOE)

Trap 1 — "You migrate from polling to Debezium CDC. Two weeks later, someone asks why outbox rows are still accumulating forever in the table even though Kafka is receiving events fine." Answer: "Because the published boolean and its implicit cleanup logic were tied to the polling publisher's workflow — once you switch to CDC, nothing sets published=true anymore since Debezium never touches that column. If cleanup depended on WHERE published=true, it silently stops working. Fix: a NEW cleanup strategy — a TTL-based purge job on created_at, independent of the now-unused published flag." Trap 2 — "Explain a scenario where CDC is objectively the WRONG choice, even at very high scale." Answer: "If the team has zero operational experience running Kafka Connect, with no dedicated platform team to own connector health and WAL retention tuning — CDC introduces a new failure mode (a stuck/lagging connector silently starving the pipeline) that's genuinely harder to debug than 'the polling job's query is slow.' At very high scale with a small team, I'd rather horizontally shard the polling publisher than adopt a new operational paradigm the team isn't ready to run reliably."

WHY We Chose Each Decision

- Why the outbox contract (self-contained payload, aggregate_id key) supports BOTH polling and CDC: lets us migrate publisher mechanisms later without touching downstream consumers at all. - Why logical WAL level is required for CDC: the default binary format is undecodable by anything except another Postgres replica. - Why a publication scoped to just the outbox table: avoids flooding Debezium (and downstream Kafka) with irrelevant table changes. - Why a NEW cleanup job is needed post-migration: the published flag's cleanup logic silently stops working once CDC takes over.

Top 2 Technologies — CDC Implementation

Debezium (Kafka Connect plugin) vs Custom WAL-reading service Why pick Debezium (our choice if migrating): battle-tested, handles replication slot management, snapshot mode, and schema mapping out of the box — avoids reinventing WAL-parsing logic. Why pick Custom: only justified by extremely unusual requirements Debezium's connector model genuinely can't express — rare in practice. Example 1 (Debezium): Notification System's hypothetical CDC migration — standard Postgres outbox table, exactly Debezium's core use case. Example 2 (Custom, rare): A team needing to CDC a proprietary, non-standard database with no existing Debezium connector and no plugin ecosystem support.
