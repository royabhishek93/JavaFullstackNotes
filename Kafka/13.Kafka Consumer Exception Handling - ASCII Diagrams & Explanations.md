# Kafka Consumer Exception Handling — ASCII Diagrams & Explanations

Topics: Poison Pill, Deserialization Exception, ErrorHandlingDeserializer, DefaultErrorHandler, FixedBackOff, ExponentialBackOff, Dead Letter Topic, ConsumerRecordRecoverer

---

## 1. Two Places Where Exceptions Can Occur

Every record a consumer fetches passes through exactly two stages before the offset is committed — and an exception at either stage can break your consumer.

```
  Consumer polls from broker
           │
           ▼
  ┌─────────────────────────────────────┐
  │  Stage 1: Deserialization           │ ◄── Exception here = Poison Pill risk
  │  raw bytes → Java object            │     (bad payload, wrong format)
  └─────────────────────────────────────┘
           │
           ▼
  ┌─────────────────────────────────────┐
  │  Stage 2: @KafkaListener            │ ◄── Exception here = NullPointer etc.
  │  your business logic runs here      │     (logic bugs, downstream failure)
  └─────────────────────────────────────┘
           │
           ▼
    Commit offset  ✓
```

---

## 2. The Poison Pill — Infinite Loop Problem

A **poison pill** is one bad message that causes deserialization to fail every time it is read — because the offset is never committed, the consumer fetches it again and again forever.

```
SCENARIO: Producer sends plain String "hello", Consumer expects JSON

  Producer        Broker              Consumer
  ┌────────┐      ┌──────────┐        ┌──────────────────────────────┐
  │"hello" │─────►│ offset 0 │───────►│ JsonDeserializer("hello")    │
  └────────┘      └──────────┘        │        ↓ FAILS ✗             │
                                      │ print stack trace            │
                                      │        ↓                     │
                                      │ poll() again...              │
                                      │        ↓                     │
                                      │ same offset 0 fetched again  │
                                      │        ↓ FAILS ✗             │
                                      │ print stack trace            │
                                      │        ↓                     │
                                      │ poll() again... ─────────────┘
                                      │
                                      │ INFINITE LOOP — offset never committed
                                      └──────────────────────────────────────

  Even after stopping and restarting the consumer:
    consumer starts → polls → fetches offset 0 → FAILS again → loop repeats ✗
```

---

## 3. ErrorHandlingDeserializer — Breaking the Loop

Wrapping your deserializer with `ErrorHandlingDeserializer` catches the exception before it reaches your code, then logs it and **commits the offset** so the consumer can move on.

```
BEFORE (no wrapper):
  raw bytes ──► JsonDeserializer ──► exception → never committed → infinite loop ✗

AFTER (with ErrorHandlingDeserializer wrapper):
  raw bytes ──► ErrorHandlingDeserializer ──► JsonDeserializer
                        │                           │
                        │◄──── catches exception ───┘
                        │
                        ▼
               Default Error Handler
               logs exception + commits offset  ✓  no more infinite loop

Configuration in application.properties:
  spring.kafka.consumer.value-deserializer=ErrorHandlingDeserializer
  spring.deserializer.value.delegate.class=JsonDeserializer

  spring.kafka.consumer.key-deserializer=ErrorHandlingDeserializer
  spring.deserializer.key.delegate.class=StringDeserializer
```

---

## 4. Default Error Handler — Log and Skip

Without any custom configuration, `ErrorHandlingDeserializer` uses the built-in `DefaultErrorHandler` which has **zero retries and no storage** — it just logs the error and moves on.

```
  ┌────────────────────────────────────────────────────────────────┐
  │  DefaultErrorHandler  (zero config / out of the box)           │
  │                                                                │
  │  max attempts:  0   ← no retry                                 │
  │  interval:      0ms ← no delay                                 │
  │  recoverer:     none ← no DLT, no DB, no alert                 │
  │                                                                │
  │  Action:   1. print stack trace                                │
  │            2. commit offset  ←  consumer moves forward         │
  └────────────────────────────────────────────────────────────────┘
           │
           ▼
  Event is SILENTLY LOST  ✗
  Offset is committed — you can never go back to this message.

  ⚠  Safe for development. Dangerous in production.
     Always configure a recoverer in production systems.
```

## 5. Retry With BackOff

You can override the default error handler as a Spring bean and give it a backoff strategy so the consumer retries before giving up.

```
FIXED BACKOFF  (same wait time between every retry)
────────────────────────────────────────────────────────────────
  new FixedBackOff(1000L, 2)  →  interval=1s, maxRetries=2

  Attempt-1 FAILS ──► wait 1s ──► Attempt-2 FAILS ──► wait 1s ──► Attempt-3 FAILS
                                                                           │
                                                                           ▼
                                                                    Recoverer called
                                                                    (DLT / DB / alert)


EXPONENTIAL BACKOFF  (wait doubles each retry, capped at a maximum)
────────────────────────────────────────────────────────────────
  new ExponentialBackOffWithMaxRetries(5)
    .setInitialInterval(1000)   ← first retry after 1s
    .setMultiplier(2.0)         ← double each time
    .setMaxInterval(10000)      ← never wait more than 10s

  Attempt-1 FAILS ──► wait  1s
  Attempt-2 FAILS ──► wait  2s
  Attempt-3 FAILS ──► wait  4s
  Attempt-4 FAILS ──► wait  8s
  Attempt-5 FAILS ──► wait 10s  (capped)
  Attempt-6 FAILS ──────────────────────► Recoverer called  ✓

  Rule of thumb:
    Transient errors (timeouts, network blip) → retry helps  ✓
    Deserialization errors (bad payload)      → retry never helps  ✗
                                                but DLT still stores the event
```

## 6. Dead Letter Topic (DLT) — Happy Path vs Failure Path

The **Dead Letter Topic** is a separate Kafka topic where all failed events are stored safely so they are never lost and can be reprocessed or inspected later.

```
HAPPY PATH
────────────────────────────────────────────────────────────────
  order-events ──► Consumer ──► Deserialized OK ──► Process ──► Commit offset  ✓


FAILURE PATH  (with DLT configured)
────────────────────────────────────────────────────────────────
  order-events ──► Consumer ──► Deserialization FAILS
                                         │
                                         ▼
                              Retry 1... Retry 2... all exhausted
                                         │
                                         ▼
                           DeadLetterPublishingRecoverer
                                         │
                                         ├──► publishes event to order-events-dlt  ✓
                                         │
                                         └──► commit offset  ✓  (consumer moves on)


  DLT topic naming rule (auto-applied by the framework):
  ┌──────────────────────┬──────────────────────────┐
  │  Original topic      │  DLT topic               │
  ├──────────────────────┼──────────────────────────┤
  │  order-events        │  order-events-dlt         │
  │  payment-events      │  payment-events-dlt       │
  │  user-signup         │  user-signup-dlt          │
  └──────────────────────┴──────────────────────────┘
  You MUST create the DLT topic beforehand — it is not auto-created.
```

## 7. Inside the DLT Flow — ConsumerRecord Structure

When deserialization fails, the framework builds a `ConsumerRecord` with the bad field set to `null` and the raw bytes stored in a **header**, then passes it to the recoverer.

```
  poll() returns raw bytes for one record
           │
           ▼
  ┌────────────────────────────────────────────────────────────────┐
  │  ErrorHandlingDeserializer catches the exception               │
  │                                                                │
  │  Builds ConsumerRecord:                                        │
  │  ┌──────────────────────────────────────────────────────────┐  │
  │  │  topic:      "order-events"                              │  │
  │  │  partition:  2                                           │  │
  │  │  key:        "order-123"  ← deserialized OK  ✓           │  │
  │  │  value:      null         ← deserialization FAILED  ✗    │  │
  │  │  header:  spring.deserialization-exception.value         │  │
  │  │           = raw bytes of the bad value                   │  │
  │  └──────────────────────────────────────────────────────────┘  │
  │  Also creates: DeserializationException object                 │
  └────────────────────────────────────────────────────────────────┘
           │  passes (ConsumerRecord, DeserializationException)
           ▼
  ┌────────────────────────────────────────────────────────────────┐
  │  DefaultErrorHandler — runs retries with BackOff               │
  │  all retries exhausted → calls recoverer.accept(record, ex)    │
  └────────────────────────────────────────────────────────────────┘
           │
           ▼
  ┌────────────────────────────────────────────────────────────────┐
  │  DeadLetterPublishingRecoverer.accept(record, exception)       │
  │                                                                │
  │  new ProducerRecord(                                           │
  │    topic  = record.topic() + "-dlt",   ← "order-events-dlt"   │
  │    key    = record.key()    or rawKeyBytes from header,        │
  │    value  = rawValueBytes from header  ← the bad payload       │
  │  )                                                             │
  │  kafkaTemplate.send(producerRecord)                            │
  └────────────────────────────────────────────────────────────────┘
           │
           ▼
  order-events-dlt  ✓  (bad event stored, nothing lost)
  offset committed  ✓  (consumer moves forward)

  Header presence rules:
  ┌─────────────────────────────┬────────────────┬─────────────────────────────┐
  │  What failed                │  value field   │  header                     │
  ├─────────────────────────────┼────────────────┼─────────────────────────────┤
  │  value deserialization      │  null          │  exception.value = rawBytes  │
  │  key deserialization        │  proper object │  exception.key   = rawBytes  │
  │  both key + value           │  null, null    │  exception.key + exception.value│
  └─────────────────────────────┴────────────────┴─────────────────────────────┘
```

## 8. Custom Recovery — DB, Alerts, or Any Action

`ConsumerRecordRecoverer` is a **functional interface** — you can pass a lambda to do anything you want when all retries are exhausted: write to a database, send a Slack alert, or call an API.

```
  ConsumerRecordRecoverer is just:
    void accept(ConsumerRecord<?,?> record, Exception exception)

  ┌────────────────────────────────────────────────────────────────┐
  │  Option A: Dead Letter Topic (framework-provided)              │
  │  ─────────────────────────────────────────────────────────     │
  │  ConsumerRecordRecoverer r = new DeadLetterPublishingRecoverer  │
  │                                    (kafkaTemplate);            │
  └────────────────────────────────────────────────────────────────┘

  ┌────────────────────────────────────────────────────────────────┐
  │  Option B: Custom lambda (write to DB, send alert, log)        │
  │  ─────────────────────────────────────────────────────────     │
  │  ConsumerRecordRecoverer r = (record, exception) -> {          │
  │      database.save(record);          // save to DB             │
  │      alertService.send(exception);   // send alert             │
  │      log.error("Failed: {}", record);// custom log             │
  │  };                                                            │
  └────────────────────────────────────────────────────────────────┘

  Both options plug into DefaultErrorHandler the same way:
    new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 2))
```

## 9. Exception During @KafkaListener Processing

If an exception occurs **after** deserialization (inside your business logic), there is no infinite loop risk — `DefaultErrorHandler` is always wired in automatically by Spring Kafka.

```
  order-events ──► Deserialized OK ──► @KafkaListener
                                              │
                                              ▼
                                    NullPointerException  ✗
                                              │
                                              ▼
                              DefaultErrorHandler  ← auto-present, no config needed
                              logs + commits offset  ✓  (no infinite loop)

  ✓ No wrapper needed — the framework catches it automatically.
  ✗ But the default still loses the event unless you add a Recoverer.

  Solution: same DefaultErrorHandler bean you created for deserialization errors
  works here too — retry + recoverer applies to BOTH exception types.

  SAME SOLUTION FOR BOTH STAGES:
  ┌──────────────────────────────────────────────────────────────────────┐
  │  @Bean                                                               │
  │  DefaultErrorHandler errorHandler(DeadLetterPublishingRecoverer r) { │
  │      return new DefaultErrorHandler(r, new FixedBackOff(1000L, 2));  │
  │  }                                                                   │
  └──────────────────────────────────────────────────────────────────────┘
```

## Quick Reference

```
Concept                        What it does                              Key point
─────────────────────────────  ────────────────────────────────────────  ──────────────────────────────────
Poison Pill                    One bad message → consumer stuck forever  Offset never committed → infinite loop
ErrorHandlingDeserializer      Wrapper around your deserializer          Catches exception, stops infinite loop
DefaultErrorHandler (default)  Log + commit offset                       Zero retries, event is lost silently
DefaultErrorHandler (custom)   Your bean with BackOff + Recoverer        Add retry and DLT/DB/alert logic
FixedBackOff(1000L, 2)         Wait 1s between retries, max 2 retries   Good for transient failures
ExponentialBackOffWithMaxRetries  Doubles wait time up to a max limit    Good when downstream may be slow
ConsumerRecordRecoverer        Functional interface called after retries  Provide lambda for DB/alert/custom
DeadLetterPublishingRecoverer  Framework impl of ConsumerRecordRecoverer  Writes to {topic}-dlt automatically
Dead Letter Topic (DLT)        Kafka topic storing all failed events     Named as original-topic + "-dlt"
ConsumerRecord.value = null    Value deserialization failed              Raw bytes are in the header instead
ConsumerRecord.key = null      Key deserialization failed                Raw bytes are in the header instead

When does retry help?          Transient (timeout, network)     ✓
When does retry NOT help?      Deserialization failure           ✗  (bad payload won't fix itself)
Where to always store failed?  Dead Letter Topic or DB           ✓  never silently lose events
```
