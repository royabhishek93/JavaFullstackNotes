# Kafka Streams Introduction — ASCII Diagrams & Explanations

Topics: Stateless vs Stateful Processing, Real-time Aggregation Problems, Window Operations, Stream Joins, Why Kafka Streams

---

## 1. What We Had So Far (Plain Kafka Consumer)

The basic Kafka flow — producer writes, consumer reads, processes, done.

```
  Producer                  Broker                  Consumer
  ────────                ──────────               ──────────
  event-1  ──────────►  [P-0: e1,e2,e3]  ──────►  read e1 → send notification
  event-2  ──────────►                            read e2 → send notification
  event-3  ──────────►                            read e3 → send notification
```

Each event is handled **independently** — no memory of what came before.
This is called **stateless processing**.

---

## 2. Stateless vs Stateful Processing

```
STATELESS (plain Kafka consumer)
─────────────────────────────────────────────────────────
  Event arrives  →  process it  →  done
  Output depends ONLY on the current event.

  Example: "Order placed → send confirmation email"
           (no need to remember past events)

  Event 1: order#1  →  send email for order#1  ✓
  Event 2: order#2  →  send email for order#2  ✓
  Event 3: order#3  →  send email for order#3  ✓


STATEFUL (what Kafka Streams enables)
─────────────────────────────────────────────────────────
  Output depends on CURRENT event + PREVIOUS events combined.
  You must REMEMBER state from past messages.

  Example: "What is the total revenue for each customer so far?"

  Event 1: C1 paid ₹50  →  C1 total = ₹50
  Event 2: C2 paid ₹30  →  C2 total = ₹30
  Event 3: C1 paid ₹70  →  C1 total = ₹50 + ₹70 = ₹120  ← needs memory!
```

Plain Kafka consumer was built for stateless. Stateful needs something more — **Kafka Streams**.

## 3. Real-World Problem 1 — Real-Time Aggregation

**Requirement:** Find total revenue per customer in real-time as events stream in.

```
Incoming events (topic: order-events):
  { customer: C1, amount: ₹50 }
  { customer: C2, amount: ₹30 }
  { customer: C1, amount: ₹70 }
  { customer: C3, amount: ₹90 }

Expected running result:
  C1 → ₹120
  C2 → ₹30
  C3 → ₹90
```

**Naive Approach A: In-Memory Map**

```
  Consumer
  ┌─────────────────────────────────────┐
  │  Map<customerId, totalRevenue>      │
  │  ┌──────┬─────────┐                │
  │  │  C1  │  ₹120   │                │
  │  │  C2  │  ₹30    │                │
  │  │  C3  │  ₹90    │                │
  │  └──────┴─────────┘                │
  │  (lives in JVM heap)               │
  └─────────────────────────────────────┘
```

**Problem 1: App Crash → State Lost**

```
  Events processed so far: 1,00,000
  In-memory map built:  { C1: ₹5000, C2: ₹3000, ... }

  App CRASHES  ✗
  Memory gone  ✗

  Restart:
  Map is empty  →  must replay from offset 0  →  slow & expensive!
```

**Problem 2: Multiple Instances → Partial Data**

```
  Topic: order-events
  ┌──────────────────────────────────────┐
  │  Partition-0       Partition-1       │
  │  C1, C2 events     C3, C4 events     │
  └─────────┬──────────────┬─────────────┘
            │              │
            ▼              ▼
      Consumer 1      Consumer 2
      ┌────────────┐  ┌────────────┐
      │ Map:       │  │ Map:       │
      │  C1: ₹50  │  │  C3: ₹90  │  ← each has PARTIAL data!
      │  C2: ₹30  │  │  C4: ₹20  │
      └────────────┘  └────────────┘

  Consumer 1 gets an order for C3 — C3 data is on Consumer 2!
  They can't see each other's map.  ✗
```

## 4. Real-World Problem 1 — Naive Approach B: Store State in MySQL

Instead of in-memory, use a database.

```
  Event arrives: { C1, ₹20 }
       │
       ▼
  SELECT revenue FROM customers WHERE id = 'C1'    ← network call
       │
       ▼ (returns ₹10)
  UPDATE customers SET revenue = ₹30 WHERE id = 'C1' ← network call
```

**Problem: Database Becomes the Bottleneck**

```
  Event throughput: 1,00,000 events/second

  Per event:  1 SELECT + 1 UPDATE  =  2 DB calls

  Total:      1,00,000 × 2  =  2,00,000 DB calls/second  ✗

  Database cannot handle this — it becomes the bottleneck!
  Kafka's whole point is high throughput; DB kills it.
```

## 5. Real-World Problem 2 — Window Operations

**Requirement:** Total revenue in the last 5 minutes only (not all time).

```
Timeline:
───────────────────────────────────────────────────────────────────►
  t=0                    t=5min              t=10min
  │                        │                   │
  [C1:₹50][C2:₹30]         │  [C1:₹70][C3:₹90] │
        ↑                  │        ↑
        These should        │        Only these count
        expire after 5 min  │        in the current 5-min window
```

**What you'd have to build manually:**

```
  For every event:
  1. Record its timestamp
  2. Check all stored events — evict entries older than 5 minutes
  3. Re-aggregate what's left
  4. Handle the fact that different consumers have PARTIAL window data

  Consumer 1 window:  C1:₹50, C2:₹30    ← partial!
  Consumer 2 window:  C1:₹70, C3:₹90   ← partial!

  Combined answer is split across 2 instances  ✗
```

You'd need to build timestamp tracking, expiry logic, and cross-instance merging yourself — massive overhead.

## 6. Real-World Problem 3 — Joining Two Topics (Stream Enrichment)

**Requirement:** For each order, look up the customer's name from a customer profile topic.

```
  Topic: order-events           Topic: customer-profile
  ─────────────────────         ────────────────────────
  { orderId: O1, cId: C4 }      { cId: C1, name: "Alice" }
  { orderId: O2, cId: C2 }      { cId: C2, name: "Bob"   }
  { orderId: O3, cId: C1 }      { cId: C3, name: "Carol" }
                                { cId: C4, name: "Dave"  }

  Goal: enrich order with customer name
  O1 → { orderId: O1, customer: "Dave"  }
  O2 → { orderId: O2, customer: "Bob"   }
  O3 → { orderId: O3, customer: "Alice" }
```

**Manual approach: maintain a lookup map**

```
  Consumer must:
  1. Read customer-profile topic and build a map: { C1→Alice, C2→Bob... }
  2. When order arrives, look up customer name in the map

  ┌───────────────────────────────────────────────────────────┐
  │  In-memory lookup map (customer profile)                  │
  │  { C1: Alice, C2: Bob, C3: Carol, C4: Dave }              │
  └───────────────────────────────────────────────────────────┘
             App CRASHES  →  map gone  →  replay from offset 0  ✗
```

**With Multiple Consumers — Cross-Partition Lookup Fails**

```
  Both topics split across 2 partitions:

  Consumer A  reads:              Consumer B  reads:
  order-events   P-0              order-events   P-1
  cust-profile   P-0              cust-profile   P-1

  Consumer A local map:           Consumer B local map:
  { C1: Alice, C2: Bob }          { C3: Carol, C4: Dave }

  Consumer A gets order for C4    Consumer B gets order for C1
  C4 data is on Consumer B  ✗    C1 data is on Consumer A  ✗

  No way to cross-lookup without a shared distributed store!
```

## 7. Summary of All Problems with Plain Kafka Consumer

```
Problem                 Root Cause                    Manual Fix Needed?
──────────────────────  ────────────────────────────  ──────────────────
App crash → state lost  State in JVM heap             Rebuild from offset 0
Multiple instances      Partial data per partition    Distributed state sharing
DB bottleneck           1 DB call per event           Batch / cache strategy
Window operations       No built-in time tracking     Timestamp + expiry logic
Stream joins            No built-in topic join        Maintain lookup maps
Cross-instance joins    Data partitioned differently  Distributed coordination
```

**If you solve all of this manually, you've just built a stream processing framework from scratch.**

## 9. Key Use Cases for Kafka Streams

```
Use Case                  Example
──────────────────────    ─────────────────────────────────────────────
Real-time aggregation     Total revenue per customer as orders arrive
Leaderboard               Live ranking by score updated per event

```

## 10. Quick Mental Model

```
          Plain Kafka Consumer         Kafka Streams
          ──────────────────────       ─────────────────────────────
Purpose   Read & process events        Read, process & transform events
State     No built-in state            Built-in state stores (crash-safe)
Windows   Manual timestamp tracking    Built-in window operations
Joins     Manual lookup maps           Built-in stream/table joins
Scaling   Partial data per consumer    Partition-aware, coordinated
Recovery  Replay from offset 0         State backed by Kafka changelog topic

Rule of thumb:
  Each event is independent?      →  use plain Kafka consumer
  Need memory across events?      →  use Kafka Streams
```
