# Kafka Schema Registry — ASCII Diagrams & Explanations

Topics: Schema Registry, Avro, Schema Evolution, BACKWARD Compatibility, FORWARD Compatibility, FULL Compatibility, Transitive, Subject Naming, Wire Format, AvroSerializer, AvroDeserializer, GenericRecord, SpecificRecord, Schema Versioning, Caching

---

## 1. Why Raw JSON Fails in Production

Without a schema contract, producer and consumer can drift apart silently — field changes, type changes, or removals cause data loss, wrong defaults, or runtime exceptions with no warning.

```
FIVE WAYS JSON BREAKS IN PRODUCTION
────────────────────────────────────────────────────────────────────────────
  Producer V2           Consumer V1              What Happens?
  ────────────────────  ───────────────────────  ──────────────────────────
1 added: shippingAddr   no shippingAddress field  Jackson ignores (silent)
                                                  OR throws if STRICT mode  ✗

2 removed: totalAmount  expects totalAmount        Jackson sets 0 (default)
                        (double)                   Business logic runs
                                                   with totalAmount = 0.0   ✗

3 renamed: totalAmount  expects totalAmount        amount→ no match
           → amount     (double)                   totalAmount = 0 silently  ✗

4 changed: quantity     expects quantity (int)     JsonMappingException
           int → string                            thrown at runtime        ✗

5 multiple consumers    C1 wants all fields        No contract enforced.
  with different        C2 wants orderId+total     Producer changes freely
  expectations          C3 wants orderId+address   → old consumers break    ✗

RESULT: No validation. No contract. Producer changes schema → consumers break silently.
```

## 2. What Is a Schema and Schema Registry

A **schema** is a formal contract — it names every field and its type. A **schema registry** stores that contract, tracks every version change, and blocks producer updates that would break consumers.

```
WITHOUT schema registry:
  Producer ──[raw JSON bytes]──► Kafka ──[raw JSON bytes]──► Consumer
               no contract                  no validation

WITH schema registry:
                    ┌──────────────────────────────────────────┐
                    │           Schema Registry                │
                    │  - stores schema + all versions          │
                    │  - runs compatibility check on change    │
                    │  - blocks breaking changes               │
                    │  - assigns unique schema IDs             │
                    └───────────────┬──────────────────────────┘
                                    │ validate BEFORE publish
                                    ▼
  Producer ──[validated, typed]──► Kafka ──[schemaId + payload]──► Consumer
               contract enforced                schema recoverable

Schema Registry purpose in one sentence:
  Bring validation BEFORE the producer sends an event.
  If the new schema would break a consumer → exception → event NOT published.
```

## 3. Avro Schema — The .avsc Contract

An Avro schema is defined in a `.avsc` file (JSON format). A Maven plugin reads it at compile time and generates a Java class — not a plain POJO, but one that includes a `getSchema()` method the AvroSerializer needs.

```
src/main/avro/order.avsc  (the contract you write)
┌────────────────────────────────────────────────────────────────┐
│  {                                                             │
│    "type":      "record",           ← object (not primitive)  │
│    "name":      "Order",            ← becomes Java class name │
│    "namespace": "com.eda.schema",   ← becomes Java package    │
│    "fields": [                                                 │
│      { "name": "orderId",     "type": "string" },             │
│      { "name": "customerId",  "type": "string" },             │
│      { "name": "productId",   "type": "string" },             │
│      { "name": "quantity",    "type": "int"    },             │
│      { "name": "totalAmount", "type": "double" }              │
│    ]                                                           │
│  }                                                             │
└────────────────────────────────────────────────────────────────┘
         │
         │  mvn clean compile  ← Maven Avro plugin runs
         ▼
  target/generated-sources/avro/com/eda/schema/Order.java
  ┌────────────────────────────────────────────────────────────┐
  │  class Order extends SpecificRecordBase {                  │
  │    String orderId, customerId, productId;                  │
  │    int quantity;   double totalAmount;                     │
  │                                                            │
  │    Schema getSchema() { ... }  ← AvroSerializer uses this │
  │    static Order.Builder newBuilder() { ... }               │
  │  }                                                         │
  └────────────────────────────────────────────────────────────┘
  NOT a plain POJO — extends SpecificRecordBase.
  AvroSerializer recognises it because of that base class.

  pom.xml requirements:
  ┌────────────────────────────────────────────────────────────┐
  │  dependency: org.apache.avro  ← parses .avsc              │
  │  dependency: kafka-avro-serializer  ← serialize/deserialize│
  │  plugin: avro-maven-plugin    ← generates Java class      │
  └────────────────────────────────────────────────────────────┘
```

## 4. Schema Registry Setup and the _schemas Topic

The Confluent Schema Registry is a separate process. It talks to Kafka because it stores all schema data inside a special Kafka topic called `_schemas` — schema + version + compatibility type all live there.

```
schema-registry.properties
┌──────────────────────────────────────────────────────────────────┐
│  listeners=http://0.0.0.0:8085                                   │
│  kafkastore.bootstrap.servers=localhost:9092,localhost:9093      │
│  kafkastore.topic=_schemas    ← keep the default name           │
└──────────────────────────────────────────────────────────────────┘
                    │ connects on startup
                    ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │  KAFKA BROKER                                                   │
  │                                                                 │
  │  _schemas topic  (1 partition, created automatically)          │
  │  ┌─────────────────────────────────────────────────────────┐   │
  │  │  subject:       order-event-value                       │   │
  │  │  version:       1                                       │   │
  │  │  schemaId:      1001                                    │   │
  │  │  schema:        { orderId:str, customerId:str, ... }    │   │
  │  │  compatibility: BACKWARD  (default)                     │   │
  │  └─────────────────────────────────────────────────────────┘   │
  └─────────────────────────────────────────────────────────────────┘

Correct start order:
  1. Start controller(s)
  2. Start broker(s)
  3. Start schema registry  → connects → creates _schemas topic
  4. Start producer / consumer apps

Test that schema registry is running:
  GET http://localhost:8085/subjects   → returns [] if empty (healthy)
```

## 5. Producer Flow — First Send (Schema Registration)

The very first time a producer sends an event, the AvroSerializer has no cached schema ID. It registers the schema with the registry, gets back a schema ID, caches it, then builds and sends the message.

```
Producer:  kafkaTemplate.send("order-event", key, orderObject)
                                                      │
                             ┌────────────────────────▼─────────────────────────┐
                             │               AvroSerializer                      │
                             │                                                   │
                             │  Step 1: orderObject.getSchema()                 │
                             │          → returns full Avro schema definition   │
                             │                                                   │
                             │  Step 2: hash(schema)                            │
                             │          → check local cache: NOT FOUND          │
                             └────────────────────────┬─────────────────────────┘
                                                      │ HTTP POST
                                                      │ /subjects/order-event-value/versions
                                                      │ body: { schema: "..." }
                             ┌────────────────────────▼─────────────────────────┐
                             │              Schema Registry                      │
                             │                                                   │
                             │  Is subject order-event-value known?  NO          │
                             │  → first registration                            │
                             │  → write to _schemas topic:                      │
                             │       subject:  order-event-value               │
                             │       version:  1                                │
                             │       schemaId: 1001                             │
                             │       compat:   BACKWARD (default)              │
                             │  → return schemaId: 1001                         │
                             └────────────────────────┬─────────────────────────┘
                                                      │ schemaId = 1001
                             ┌────────────────────────▼─────────────────────────┐
                             │          AvroSerializer (continues)               │
                             │                                                   │
                             │  Step 3: cache[schemaHash] = 1001               │
                             │                                                   │
                             │  Step 4: build wire-format message               │
                             │          → see Section 6                         │
                             └────────────────────────┬─────────────────────────┘
                                                      │
                                                      ▼
                                               Kafka Broker  ✓
```

## 6. Message Wire Format (Magic Byte + Schema ID + Payload)

Every message serialized with AvroSerializer has a 5-byte prefix: 1 magic byte followed by 4 bytes for the schema ID. The payload contains **values only** — field names are never written to the wire.

```
┌───────────┬──────────────────────────┬────────────────────────────────┐
│  1 byte   │         4 bytes          │           N bytes              │
│           │                          │                                │
│  Magic    │       Schema ID          │          Payload               │
│  Byte     │                          │  (field values, no names)      │
│  = 0x00   │  e.g.  1001              │                                │
└───────────┴──────────────────────────┴────────────────────────────────┘

Magic byte = 0x00  (currently always zero — Confluent wire protocol v0)
  Tells deserializer: "next 4 bytes = schema ID, then payload begins."
  If a future version uses 0x01 the deserializer will adjust its parsing.

Payload — values only, field names are NOT present:
┌──────────┬───────────┬────────────┬─────┬───────┐
│ "ORD-55" │ "CUST-01" │ "PROD-007" │  2  │ 55.0  │
│ orderId  │customerId │ productId  │ qty │ total │
└──────────┴───────────┴────────────┴─────┴───────┘
  Field names omitted → smaller message on every event.
  Schema ID lets the deserializer look up the structure.
  Field ORDER in the .avsc file is the contract — it must match exactly.

JSON vs Avro comparison (same data):
  JSON:  { "orderId":"ORD-55", "customerId":"CUST-01", ... }  ← names + values
  Avro:  [magicByte][schemaId]["ORD-55"]["CUST-01"][...]       ← values only
```

## 7. Producer Flow — Schema Change + Compatibility Check

On every send after the first, if the schema hash is new (schema changed), the serializer tries to register the new version. The registry runs a compatibility check and throws an exception if the change would break consumers.

```
Example: producer changes quantity from int → string in order.avsc
         mvn clean compile → new Order.java with quantity as String

Producer calls send() again
         │
         AvroSerializer
         │  getSchema() → new schema definition (quantity=string)
         │  hash(new schema) → different from cached hash → NOT in cache
         │  HTTP POST /subjects/order-event-value/versions { new schema }
         │
         Schema Registry
         │  subject order-event-value EXISTS → version 1 already present
         │  compatibility = BACKWARD
         │
         │  BACKWARD check logic:
         │    Assume consumer is on NEW schema (quantity=string)
         │    It reads an OLD Kafka message (quantity=int)
         │    Can it deserialize int as string?  NO  ✗
         │
         └──► HTTP 409 Conflict
              "String not compatible with writer type int."
                   │
                   ▼
         AvroSerializer throws exception
         Producer gets error
         Event is NOT published to Kafka  ✓  (consumer protected)

What WOULD be allowed (backward-safe changes):
  ┌────────────────────────────────────────────┬──────┐
  │  Change                                    │  OK? │
  ├────────────────────────────────────────────┼──────┤
  │  Add new field WITH a default value        │  ✓   │
  │  Remove an existing field                  │  ✓   │
  │  Add new field WITHOUT a default value     │  ✗   │
  │  Change a field type                       │  ✗   │
  └────────────────────────────────────────────┴──────┘
```

## 8. Consumer Flow — Fetching Schema from Registry

When a consumer receives bytes, the AvroDeserializer reads the magic byte and schema ID, fetches the full schema from the registry (or its local cache), then uses field order from the schema to decode each value in the payload.

```
Kafka returns bytes to consumer
        │
        ▼
┌──────────────────────────────────────────────────────────────────┐
│                       AvroDeserializer                            │
│                                                                  │
│  Step 1: Read byte[0] → magic byte = 0x00                       │
│          → protocol v0: next 4 bytes are schema ID              │
│                                                                  │
│  Step 2: Read bytes[1..4] → schema ID = 1001                    │
│                                                                  │
│  Step 3: local cache lookup for schemaId 1001 → NOT FOUND       │
│          → HTTP GET http://localhost:8085/schemas/ids/1001       │
│          ← registry returns full schema                         │
│          → cache[1001] = schema  (no more HTTP calls for 1001)  │
│                                                                  │
│  Step 4: Read payload bytes[5..] using schema field order:      │
│          field 1: orderId     (string) → read N bytes           │
│          field 2: customerId  (string) → read N bytes           │
│          field 3: productId   (string) → read N bytes           │
│          field 4: quantity    (int)    → read 4 bytes           │
│          field 5: totalAmount (double) → read 8 bytes           │
│                                                                  │
│  Step 5: Return GenericRecord (default)                         │
│          OR return Order object (if specific.avro.reader=true)  │
└──────────────────────────────────────────────────────────────────┘
        │
        ▼
  consumer.value()  →  record or Order object

application.properties (consumer):
  spring.kafka.consumer.value-deserializer=
    io.confluent.kafka.serializers.KafkaAvroDeserializer
  spring.kafka.consumer.properties.schema.registry.url=
    http://localhost:8085
```

## 9. GenericRecord vs SpecificRecord

By default the deserializer returns a `GenericRecord` — like a loosely-typed map. Set `specific.avro.reader=true` and provide the same `.avsc` on the consumer side to receive a typed `Order` object instead.

```
GENERIC RECORD (default, no .avsc needed on consumer):

  GenericRecord rec = consumerRecord.value();
  String id  = rec.get("orderId").toString();   ← cast required
  int    qty = (Integer) rec.get("quantity");   ← cast required
  ← no compile-time type safety

SPECIFIC RECORD (specific.avro.reader=true):

  Consumer also has order.avsc + maven plugin → generates Order.java
  Order order = consumerRecord.value();
  String id  = order.getOrderId();    ← type-safe getter  ✓
  int    qty = order.getQuantity();   ← no casting        ✓

How the deserializer decides which to return:
  ┌─────────────────────────────────────────────────────────────────┐
  │  specific.avro.reader = true?                                   │
  │           │                                                     │
  │          YES                                                    │
  │           │                                                     │
  │           ▼                                                     │
  │  Read schema from registry:                                     │
  │    name      = "Order"                                          │
  │    namespace = "com.eda.schema"                                 │
  │           │                                                     │
  │           ▼                                                     │
  │  Look for class com.eda.schema.Order in consumer classpath      │
  │           │                                                     │
  │     found ──► map to Order object  ✓                           │
  │   missing ──► return GenericRecord                             │
  └─────────────────────────────────────────────────────────────────┘

application.properties (consumer):
  spring.kafka.consumer.properties.specific.avro.reader=true
```

## 10. Caching — Producer and Consumer

Both the AvroSerializer and AvroDeserializer maintain a local in-memory cache. The schema registry is only called once per unique schema version per application lifetime — not on every message.

```
PRODUCER CACHE  (AvroSerializer)
  key:   hash(schema definition string)
  value: schemaId  (e.g. 1001)

  send()
    │
    ▼
  hash(schema) ──► in cache? ──YES──► use cached schemaId → serialize → send
                        │
                       NO
                        ▼
                  HTTP POST to schema registry
                  receive schemaId
                  cache[hash] = schemaId
                        │
                        ▼
                  serialize → send

CONSUMER CACHE  (AvroDeserializer)
  key:   schemaId  (e.g. 1001)
  value: full schema definition

  receive bytes
    │
    ▼
  read schemaId ──► in cache? ──YES──► use cached schema → deserialize
                        │
                       NO
                        ▼
                  HTTP GET /schemas/ids/{schemaId}
                  receive schema
                  cache[schemaId] = schema
                        │
                        ▼
                  deserialize payload

RESULT: HTTP calls to the schema registry are rare.
  Typically: one call per unique schema version per running application instance.
```

## 11. Schema Compatibility — BACKWARD (Default)

BACKWARD is the default compatibility mode. The registry assumes the consumer will upgrade to the **new schema** — then checks whether it can still read **old messages** already sitting in Kafka.

```
BACKWARD question:  consumer on NEW schema  ─reads─►  OLD Kafka messages.
                    Will anything break?

Example: OLD schema (V1) has only { orderId: int }
         Producer wants to publish with NEW schema (V2)

  ┌────────────────────────────────┬───────────────────────────────┬──────┐
  │  Change in V2                  │  Consumer V2 reads V1 message │  OK? │
  ├────────────────────────────────┼───────────────────────────────┼──────┤
  │  Add field WITH default        │  Field missing in old msg     │  ✓   │
  │  status: string = "pending"    │  → consumer uses "pending"    │      │
  ├────────────────────────────────┼───────────────────────────────┼──────┤
  │  Add field WITHOUT default     │  Field missing in old msg     │  ✗   │
  │  status: string  (no default)  │  → no value, no default       │      │
  ├────────────────────────────────┼───────────────────────────────┼──────┤
  │  Remove existing field         │  Extra field in old msg       │  ✓   │
  │  remove orderId from V2        │  → consumer ignores it        │      │
  ├────────────────────────────────┼───────────────────────────────┼──────┤
  │  Change type                   │  int in old msg payload       │  ✗   │
  │  quantity: int → string        │  → consumer expects string    │      │
  └────────────────────────────────┴───────────────────────────────┴──────┘

Summary for BACKWARD:
  ✓ Add field with default value
  ✓ Remove any existing field
  ✗ Add field without default value
  ✗ Change a field type
```

---

## 12. Schema Compatibility — FORWARD

FORWARD compatibility protects consumers that are **still on the old schema**. The registry checks whether an old consumer can safely read **new messages** published with the updated schema.

```
FORWARD question:  consumer on OLD schema  ─reads─►  NEW Kafka messages.
                   Will anything break?

Example: OLD schema (V1) has { orderId: int }
         Producer wants to publish with NEW schema (V2)

  ┌────────────────────────────────┬───────────────────────────────┬──────┐
  │  Change in V2                  │  Consumer V1 reads V2 message │  OK? │
  ├────────────────────────────────┼───────────────────────────────┼──────┤
  │  Add new field                 │  Consumer has no such field   │  ✓   │
  │  status: string = "pending"    │  → unknown field, ignored     │      │
  ├────────────────────────────────┼───────────────────────────────┼──────┤
  │  Remove field that has default │  Field absent in new msg      │  ✓   │
  │  (consumer still declares it)  │  → consumer uses its default  │      │
  ├────────────────────────────────┼───────────────────────────────┼──────┤
  │  Remove field WITHOUT default  │  Field absent in new msg      │  ✗   │
  │                                │  → consumer has no fallback   │      │
  ├────────────────────────────────┼───────────────────────────────┼──────┤
  │  Change type                   │  Consumer expects int         │  ✗   │
  │  quantity: int → string        │  → message has string bytes   │      │
  └────────────────────────────────┴───────────────────────────────┴──────┘

Summary for FORWARD:
  ✓ Add any new field (old consumers ignore unknown fields)
  ✓ Remove field that carries a default value
  ✗ Remove field without a default value
  ✗ Change a field type
```

## 13. Schema Compatibility — FULL and Transitive Variants

FULL means both BACKWARD and FORWARD must pass. The transitive variants extend any of these checks to compare against **all previous versions**, not just the immediately preceding one.

```
FULL = BACKWARD + FORWARD combined
  Every change must be safe from both directions:
    → consumer on NEW schema reading OLD messages  (backward safe)
    → consumer on OLD schema reading NEW messages  (forward safe)

  Summary for FULL:
    ✓ Add field WITH default value   (safe both ways)
    ✗ Add field WITHOUT default value  (fails BACKWARD)
    ✗ Remove field without default     (fails FORWARD)
    ✗ Change type                      (fails both)

TRANSITIVE variants — how many past versions are compared:

  Non-transitive  →  new schema compared to LAST version only
  Transitive      →  new schema compared to ALL previous versions

  ┌──────────────────────────────────────────────────────────────────┐
  │  V1 ──► V2 ──► V3 ──► V4   (producer now publishing V4)         │
  │                                                                  │
  │  BACKWARD:             V4 checked against V3 only               │
  │  BACKWARD_TRANSITIVE:  V4 checked against V3, V2, and V1        │
  │                                                                  │
  │  FORWARD:              V4 checked against V3 only               │
  │  FORWARD_TRANSITIVE:   V4 checked against V3, V2, and V1        │
  │                                                                  │
  │  FULL:                 V4 checked against V3 only (both dirs)   │
  │  FULL_TRANSITIVE:      V4 checked against V3, V2, V1 (both)    │
  └──────────────────────────────────────────────────────────────────┘

Use transitive when you need to guarantee that any consumer on any
old version can safely interact with the newest messages in Kafka.
Six levels in total:
  BACKWARD · FORWARD · FULL · BACKWARD_TRANSITIVE · FORWARD_TRANSITIVE · FULL_TRANSITIVE
```

## 14. Subject Naming Strategies

A **subject** is the label under which the schema registry groups version history. The naming strategy controls how that label is formed from topic name and record name.

```
SUBJECT = the registry key that groups schema versions in _schemas topic

  ┌───────────────────────┬───────────────────────────────┬─────────────────────────┐
  │  Strategy             │  Subject format               │  Use case               │
  ├───────────────────────┼───────────────────────────────┼─────────────────────────┤
  │ TopicNameStrategy     │ {topic}-value                 │  DEFAULT.               │
  │ (default)             │ {topic}-key                   │  One schema per topic.  │
  │                       │ e.g. order-event-value        │  Common choice.         │
  ├───────────────────────┼───────────────────────────────┼─────────────────────────┤
  │ RecordNameStrategy    │ {namespace}.{RecordName}      │  Same record reused     │
  │                       │ e.g. com.eda.schema.Order     │  across many topics.    │
  │                       │                               │  Schema shared.         │
  ├───────────────────────┼───────────────────────────────┼─────────────────────────┤
  │ TopicRecord           │ {topic}-{namespace}.          │  Different record types │
  │ NameStrategy          │ {RecordName}                  │  per topic, but each    │
  │                       │ e.g. order-event-             │  combination isolated.  │
  │                       │      com.eda.schema.Order     │                         │
  └───────────────────────┴───────────────────────────────┴─────────────────────────┘

TopicNameStrategy example from the transcript:
  topic:  order-event
  key   → subject: order-event-key    (StringSerializer — no Avro subject needed)
  value → subject: order-event-value  (KafkaAvroSerializer — schema stored here)

Setting a strategy in application.properties (producer or consumer):
  spring.kafka.producer.properties.value.subject.name.strategy=
    io.confluent.kafka.serializers.subject.TopicNameStrategy
    io.confluent.kafka.serializers.subject.RecordNameStrategy
    io.confluent.kafka.serializers.subject.TopicRecordNameStrategy
```

## 15. Setting Compatibility Levels (Global and Per-Subject)

The default is BACKWARD. You can change it globally in the registry properties file, or override it per subject using the REST API — useful when different topics need different rules.

```
GLOBAL setting (applies to every subject):

  schema-registry.properties:
  ┌────────────────────────────────────────────────────────────────┐
  │  schema.compatibility.level=FULL                               │
  └────────────────────────────────────────────────────────────────┘
  Valid values:
    BACKWARD (default) · FORWARD · FULL · NONE
    BACKWARD_TRANSITIVE · FORWARD_TRANSITIVE · FULL_TRANSITIVE

PER-SUBJECT OVERRIDE (REST API):

  Override one subject while others keep the global setting:

  PUT  http://localhost:8085/config/order-event-value
  Body: { "compatibility": "FORWARD" }

  ┌─────────────────────────────────────────────────────────────┐
  │  Global: FULL                                               │
  │                                                             │
  │  order-event-value  ← overridden to FORWARD                │
  │  payment-event-value ← still uses global FULL              │
  │  user-event-value    ← still uses global FULL              │
  └─────────────────────────────────────────────────────────────┘

Useful REST endpoints:
  GET  /subjects                              → list all subjects
  GET  /subjects/{subject}/versions           → list all versions
  GET  /subjects/{subject}/versions/{version} → get schema at version
  GET  /schemas/ids/{id}                      → get schema by ID
  GET  /config/{subject}                      → get compatibility for subject
  PUT  /config/{subject}                      → set compatibility for subject
```

## 16. Complete Flow — Producer to Consumer

The full end-to-end picture showing how producer, schema registry, Kafka broker, and consumer all interact through the schema lifecycle.

```
┌────────────────────────────────────────────────────────────────────────────────┐
│                           COMPLETE SCHEMA REGISTRY FLOW                        │
└────────────────────────────────────────────────────────────────────────────────┘

PRODUCER SIDE
┌────────────────────────────────────────────────────────────────────────────────┐
│                                                                                │
│  order.avsc ──► mvn compile ──► Order.java (extends SpecificRecordBase)        │
│                                                                                │
│  kafkaTemplate.send("order-event", key, orderObject)                           │
```

## 17. Quick Reference

```
Concept                  What it is                             Key point
───────────────────────  ─────────────────────────────────────  ────────────────────────────────────
Schema                   Formal definition: field names + types  Contract between producer & consumer
Schema Registry          Stores schemas + versions + compat       Validates before producer publishes
.avsc file               Avro schema definition (JSON format)    Compile → Java class via Maven plugin
_schemas topic           Kafka topic inside the broker           Registry persists all data here
Subject                  Registry key grouping schema versions   Default: {topic}-value / {topic}-key
SchemaId                 Unique int assigned per schema version  1001, 1002, ... stored in 4 bytes
Magic byte               First byte of every Avro message        Always 0x00 (Confluent wire protocol)
Wire format              [magic 1B][schemaId 4B][values only]    Field names NOT on the wire
AvroSerializer           Registers schema, encodes to bytes      Runs on producer, value serializer
AvroDeserializer         Fetches schema by ID, decodes bytes     Runs on consumer, value deserializer
GenericRecord            Loosely-typed result (default)          Access fields by string name
SpecificRecord           Typed result (Order object)             Needs .avsc + specific.avro.reader=true
Producer cache           hash(schema) → schemaId                 Avoids repeated registry calls
Consumer cache           schemaId → schema                       Avoids repeated registry calls

BACKWARD (default)       Consumer on new schema reads old msgs   Add field+default ✓  Remove field ✓
FORWARD                  Consumer on old schema reads new msgs   Add any field ✓  Remove field+default ✓
FULL                     Both BACKWARD and FULL must pass        Add field+default ✓  only
*_TRANSITIVE             Check new schema vs ALL past versions   Without: check vs last version only

TopicNameStrategy        {topic}-value / {topic}-key             Default — one schema per topic
RecordNameStrategy       {namespace}.{RecordName}                Reuse same schema across topics
TopicRecordNameStrategy  {topic}-{namespace}.{RecordName}        Per-topic isolation with record name

Set global compat:       schema.compatibility.level=BACKWARD     In schema-registry.properties
Set per-subject compat:  PUT /config/{subject}                   REST API override
```
