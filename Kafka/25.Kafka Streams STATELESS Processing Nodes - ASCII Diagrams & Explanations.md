# Kafka Streams STATELESS Processing Nodes — ASCII Diagrams & Explanations

Topics: filter, map, mapValues, selectKey, split/branch, merge, KStream topology stage, repartition eligibility

---

## 1. KStream Is a Pipeline Stage, Not a Data Container

A KStream object is a **reference point** in your topology — it does not hold records. It marks where you can attach the next processing node.

```
TOPOLOGY TREE — each KStream is a handle you can build from:

  [order-events topic]
        │
        ▼ builder.stream("order-events")
     ┌──────┐   ◄── "orders" KStream  (reference to source node)
     │source│
     └──────┘
        │
        ▼ orders.filter(amount > 1000)
  ┌───────────┐  ◄── "highOrders" KStream  (reference to filter node)
  │  filter   │
  │amount>1000│
  └─────┬─────┘
        │                       │
        ▼ highOrders.mapValues() ▼ orders.filter(amount <= 1000)
   ┌─────────┐              ┌───────────┐  ◄── "lowOrders" KStream
   │  map    │              │  filter   │
   │ values  │              │amount≤1000│
   └─────────┘              └───────────┘

Records do NOT live inside a KStream object.
A KStream is just a handle — grab it to add more nodes at that stage.
Multiple KStream objects = multiple stages in the SAME pipeline.
```

## 2. filter — Keep or Drop Records

`filter` keeps a record only if the predicate returns `true`. Records returning `false` are **dropped immediately** and never reach the next node.

```
INPUT STREAM:
  ┌──────────────┬──────────────┬──────────────┬──────────────┐
  │ key:O1       │ key:O2       │ key:O3       │ key:O4       │
  │ amount: 200  │ amount: 1500 │ amount: 800  │ amount: 2000 │
  └──────────────┴──────────────┴──────────────┴──────────────┘

  FILTER NODE: amount > 1000
  ┌──────────────────────────────────────────────────────────────┐
  │  O1 (200)  → predicate? false → DROPPED  ✗                   │
  │  O2 (1500) → predicate? true  → PASSES   ✓                   │
  │  O3 (800)  → predicate? false → DROPPED  ✗                   │
  │  O4 (2000) → predicate? true  → PASSES   ✓                   │
  └──────────────────────────────────────────────────────────────┘

OUTPUT STREAM:
  ┌──────────────┬──────────────┐
  │ key:O2       │ key:O4       │
  │ amount: 1500 │ amount: 2000 │
  └──────────────┴──────────────┘

Key unchanged ✓   Value unchanged ✓   Repartition eligible? NO
```

## 3. map — Change Key, Value, or Both

`map` transforms every record into a new key-value pair. You choose what the new key and new value are — either can change.

```
INPUT RECORD:
  ┌─────────────────────────────────┐
  │ key:  "O101"                    │
  │ value: Order { amount: 500,     │
  │                userId: "U07" }  │
  └─────────────────────────────────┘
           │
           ▼ .map((key, order) → KeyValue.pair("order-" + key, order))
  ┌─────────────────────────────────┐
  │ key:  "order-O101"  ← CHANGED  │
  │ value: Order { amount: 500,     │
  │                userId: "U07" }  │  ← unchanged
  └─────────────────────────────────┘

WHAT map CAN DO:
  ┌──────────────────┬──────────────────────────────────────────┐
  │ Goal             │ What you return                          │
  ├──────────────────┼──────────────────────────────────────────┤
  │ Change key only  │ KeyValue.pair(newKey,    originalValue)  │
  │ Change value only│ KeyValue.pair(originalKey, newValue)     │
  │ Change both      │ KeyValue.pair(newKey,    newValue)       │
  └──────────────────┴──────────────────────────────────────────┘

Key changed? YES → eligible for repartition later  ▲
```

## 4. mapValues — Change Value Only

`mapValues` transforms only the value. The key stays the same, so **no repartition is ever triggered**.

```
INPUT:
  key: "O101"  value: Order { amount: 500, status: "pending" }
           │
           ▼ .mapValues(order → order.withStatus("CONFIRMED"))
OUTPUT:
  key: "O101"  value: Order { amount: 500, status: "CONFIRMED" }
       ↑ key is IDENTICAL — no repartition risk

SIGNATURE REMINDER:
  mapValues( V → VR )
             ↑     ↑
          old    new
          value  value    (key is passed through untouched)

Repartition eligible? NO — key never changes in mapValues
```

---

## 5. selectKey — Change Key Only

`selectKey` assigns a brand-new key while leaving the value unchanged. Because the key changes, the record becomes **eligible for repartition downstream**.

```
INPUT:
  key: "O101"       value: Order { userId: "U07", amount: 500 }
           │
           ▼ .selectKey((key, order) → order.getUserId())
OUTPUT:
  key: "U07"   ← NEW KEY (userId extracted from value)
  value: Order { userId: "U07", amount: 500 }   ← unchanged

Repartition eligible? YES ▲
(actual repartition happens later when groupByKey or join is called)

COMMON PATTERN — prepare for a join or aggregation by user:
  orders.selectKey((k, order) → order.getUserId())
        .groupByKey()   ← repartition fires HERE
        .count()
```

## 6. split / branch — Conditional Routing (if-else-if)

`split` + `branch` routes each record to **at most one** matching branch — like a chain of if-else-if. Once a branch matches, the remaining branches are skipped.

```
PROBLEM WITH TWO SEPARATE FILTERS — both conditions checked for every record:
  ┌──────────┐
  │ record   │─── filter(amount >= 2000) ──► highOrders  (checked)
  │  comes   │
  │   in     │─── filter(amount >= 1000) ──► medOrders   (also checked!)
  └──────────┘
  Result: a record with amount=2500 passes BOTH → appears in both streams!

SPLIT / BRANCH — only ONE branch fires per record:
  ┌──────────┐
  │ record   │
  │  comes   │
  │   in     │
  └────┬─────┘
       │
       ▼ orders.split()
  ┌─────────────────────────────────────────────────────────────┐
  │  .branch("premium", (k,v) → v.getAmount() >= 2000) ?        │
  │       YES ──► premiumOrders KStream          stop here  ✓   │
  │       NO  ──►                                               │
  │  .branch("high",    (k,v) → v.getAmount() >= 1000) ?        │
  │       YES ──► highOrders KStream             stop here  ✓   │
  │       NO  ──►                                               │
  │  .defaultBranch("low")                                      │
  │       ──► lowOrders KStream                                  │
  └─────────────────────────────────────────────────────────────┘

  branches.get("premium") → KStream for premium records
  branches.get("high")    → KStream for high records
  branches.get("low")     → KStream for low records
```

## 7. merge — Combining Streams

`merge` is the reverse of split. It takes two or more streams and joins them into one. The streams must share the **same key type and value type**.

```
  premiumOrders  ───┐
                    ├──► merge ──► allOrdersAbove1000
  highOrders     ───┘

  BEFORE merge:
    premiumOrders: [ O5: 3000,  O8: 2500 ]
    highOrders:    [ O2: 1500,  O9: 1200 ]

  AFTER merge (arrival order, not sorted):
    allOrdersAbove1000: [ O5: 3000,  O2: 1500,  O8: 2500,  O9: 1200 ]

  CHAIN as many as needed:
    premiumOrders
      .merge(highOrders)
      .merge(lowOrders)

  RULE: key type AND value type must match across all merged streams.
```

## 8. Repartition Eligibility Summary

When a key changes the record is only *eligible* — actual repartition happens when `groupByKey` or a `join` is reached downstream.

```
  Operation     │ Key changes? │ Value changes? │ Repartition eligible?
  ──────────────┼──────────────┼────────────────┼──────────────────────
  filter        │     NO       │      NO        │       NO
  map           │  YES (opt.)  │   YES (opt.)   │  YES — if key changed
  mapValues     │     NO       │     YES        │       NO
  selectKey     │     YES      │      NO        │       YES
  split/branch  │     NO       │      NO        │       NO
  merge         │     NO       │      NO        │       NO

  Repartition is TRIGGERED when:
    key was changed earlier  AND  groupByKey or join is encountered

  Why repartition? All records for the SAME key must end up in the SAME
  partition so stateful nodes (count, aggregate) see the full picture.
```

## Quick Reference

```
Operation    │ What it does                          │ Key changes │ Value changes
─────────────┼───────────────────────────────────────┼─────────────┼──────────────
filter       │ Drop records where predicate = false  │ No          │ No
map          │ Replace key and/or value freely       │ Optional    │ Optional
mapValues    │ Replace value only                    │ No          │ Yes
selectKey    │ Replace key only                      │ Yes         │ No
split/branch │ Route to first matching branch only   │ No          │ No
merge        │ Combine 2+ same-typed streams into one│ No          │ No

KStream = a reference point in the topology tree, NOT a data container
Multiple KStream objects = multiple stages you can extend from
Repartition fires when: key changed + groupByKey/join is reached downstream
```
