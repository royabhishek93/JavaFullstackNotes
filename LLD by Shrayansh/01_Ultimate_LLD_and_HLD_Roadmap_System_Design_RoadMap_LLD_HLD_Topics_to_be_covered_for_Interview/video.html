Architect answer

“The endpoint submits intent, not raw database fields. I require an idempotency key for transport retries and an expected version where a stale command would violate each technology choice must trace to a requirement and a failure mode.”

  • Version makes write conflicts observable.

Technology Choices

Two technology decisions for DesignRoadmap

Category 1: Core model - incremental vertical slices

  • Why pick A: it protects each technology choice must trace to a requirement and a failure mode where the decision is made.
  • When A wins: contested or financially meaningful state needs an explainable write path.
  • Two examples: final seat confirmation; wallet or ledger settlement.

Category 1: Alternative - big-bang component design

  • Why pick B: it addresses a separate concern such as latency, integration, or delivery.
  • When B wins: it is bounded away from the durable source of truth.
  • Two examples: cached availability; asynchronous subscriber notification.

Category 2: PostgreSQL

  • Difference: relational constraints, transactions, and durable audit.
  • Pick it for: final state and reconciliation.
  • Examples: unique seat allocation; versioned inventory decrement.

Category 2: Redis

  • Difference: in-memory TTL and low latency, not durable relational truth.
  • Pick it for: a bounded cache, hold, lock, or rate limit.
  • Examples: 5-minute seat hold; API retry throttling.
Decision rule: PostgreSQL records the final answer; Redis accelerates a temporary answer. For DesignRoadmap, never let a cache become the only authority for each technology choice must trace to a requirement and a failure mode.

Senior Traps

15 YOE traps for DesignRoadmap

Trap: “The API has an idempotency key. Are duplicate side effects impossible?”
Answer: “No. It deduplicates a command at this boundary. Every asynchronous consumer still needs its own idempotent business key or processed-event record.”
Trap: “Can Redis alone enforce each technology choice must trace to a requirement and a failure mode?”
Answer: “Not as the durable source of truth. It can optimize a hold, cache, or rate limit, but final correctness belongs in the transactional write model.”
Trap: “Why not retry every conflict automatically?”
Answer: “A retry can apply a decision to changed state. I retry only when the command is demonstrably safe; otherwise I surface conflict and let the caller re-evaluate.”

State and Failure

Failure handling for DesignRoadmap

REQUESTED ---> VALIDATING ---> ACCEPTED ---> COMPLETED | | | | | invalid | stale / timeout | downstream fail | v v v v REJECTED CONFLICT PENDING_RETRY COMPENSATED

Senior decision

“I distinguish a business rejection from a technical retry. A request that breaks each technology choice must trace to a requirement and a failure mode is rejected. A transient provider failure is recorded with enough context for a bounded retry or compensation.”

Production signals

  • Version-conflict rate and idempotency hits
  • Outbox age and failed delivery count
  • Invariant violation attempts by action type
  • Time spent in pending-retry state
Why model state explicitly: an enum or state object makes recovery visible. A boolean like `isDone` cannot explain whether work failed, is retrying, or needs compensation.
