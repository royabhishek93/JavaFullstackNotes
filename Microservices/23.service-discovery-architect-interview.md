# Service Discovery — Architect Interview Script

> **Interview Frequency:** 65% | **Difficulty:** ⭐⭐⭐ | **Study Time:** 10 minutes

---

## Opening — When Interviewer Asks "How Do Your Services Find Each Other?"

"This question comes up the moment you have more than a handful of services running
on auto-scaling infrastructure. Let me walk through the problem first, then the
solutions I've actually used in production."

---

## Part 1 — The Problem (Hardcoded IPs Don't Work)

"Imagine `OrderService` needs to call `PaymentService`. In a simple world, you'd
hardcode the IP: `http://10.0.1.15:8080/pay`. That works — until autoscaling kicks in."

```
DAY 1 — hardcoded IP works:

  OrderService ──────► http://10.0.1.15:8080  (PaymentService instance)


DAY 2 — autoscaling adds/removes instances, IPs change:

  OrderService ──────► http://10.0.1.15:8080   ✗ (instance terminated, IP gone)

  Actual live instances:
     PaymentService-1  10.0.4.22:8080   (new)
     PaymentService-2  10.0.4.31:8080   (new)
     PaymentService-3  10.0.4.9:8080    (new)

  OrderService has NO idea these exist. Hardcoded config is now stale. 💥
```

"So the real question isn't 'how do I call another service' — it's **'how do I find
the current, healthy list of instances for a service name, right now?'** That's
service discovery."

---

## Part 2 — Client-Side vs Server-Side Discovery

"There are two fundamentally different models. I've used both, and the choice depends
on your infra."

### Client-Side Discovery (Eureka + Ribbon/Spring Cloud LoadBalancer)

```
  ┌─────────────┐   1. "who is PaymentService?"   ┌──────────────────┐
  │ OrderService │ ───────────────────────────────►│ Service Registry │
  │              │                                  │ (Eureka)         │
  │              │◄─────────────────────────────────│                  │
  │              │   2. [10.0.4.22, 10.0.4.31,      └──────────────────┘
  │              │       10.0.4.9]                          ▲
  │              │                                          │ heartbeat
  │  3. client picks one (round-robin/random)                │ every 30s
  │     and calls it directly ─────────────────────► PaymentService-1..3
  └─────────────┘
```
- Client does the load-balancing decision itself.
- Requires a client library (Eureka client, load-balancer logic) in every service.
- Registry can become stale if heartbeats lag.

### Server-Side Discovery (DNS + Load Balancer / Kubernetes Service)

```
  ┌─────────────┐    call by name: payment-service       ┌────────────────┐
  │ OrderService │ ──────────────────────────────────────►│  Load Balancer │
  │ (no registry │                                        │ or K8s kube-   │
  │  logic)      │                                        │ proxy / iptables│
  └─────────────┘                                         └────────────────┘
                                                                   │
                                                    picks a healthy pod
                                                                   ▼
                                        PaymentService-1 / -2 / -3 (pods)
```
- Client just calls a stable name (`payment-service.default.svc.cluster.local`).
- The platform (K8s, ALB, Envoy) does discovery + load balancing.
- Simpler for application code — no client library needed.

## Part 3 — How Registration & Health Checks Actually Work

"The registry is only useful if it's accurate. Here's the lifecycle I always explain
when asked how a dead instance gets removed."

```
INSTANCE LIFECYCLE:

  t=0s   PaymentService-2 starts ──► registers itself with Eureka
                                       (or K8s marks pod Ready after readiness probe passes)

  t=30s  heartbeat/renew lease ──► registry marks it healthy

  t=60s  heartbeat/renew lease ──► still healthy

  t=75s  PaymentService-2 crashes ──► no more heartbeats

  t=90s  Eureka: lease expired (default eviction ~90s) ──► removed from registry
         K8s: liveness probe fails 3x ──► pod restarted/removed from Service endpoints
                                          (usually within 10-30s, much faster than Eureka)

  Result: OrderService's next registry lookup no longer returns the dead instance.
```

"This is a common trap — **Eureka's default self-preservation + 90s eviction window
means a dead node can still receive traffic for up to a minute or two.** Kubernetes
readiness/liveness probes are much faster and are one reason most new systems on K8s
skip Eureka entirely and rely on the platform's built-in discovery."

## Part 4 — What I Actually Use in Production

```
                 STACK                          DISCOVERY MECHANISM
  ─────────────────────────────────────────────────────────────────────────
  Kubernetes                    →  K8s Service (ClusterIP) + CoreDNS + kube-proxy
  AWS ECS / Fargate              →  AWS Cloud Map + ALB target groups
  Spring Cloud (legacy/VM-based) →  Eureka + Spring Cloud LoadBalancer
  Service Mesh (Istio/Linkerd)   →  Sidecar (Envoy) does discovery via mesh control plane
  Serverless (Lambda)            →  API Gateway / EventBridge (no instance discovery needed)
```

"On Kubernetes I don't run Eureka at all — CoreDNS + Services already solve this for
free. I only reach for Eureka on VM-based Spring Boot fleets that predate Kubernetes."

### Spring Cloud Eureka — Minimal Example

```java
// PaymentService — registers itself
@SpringBootApplication
@EnableEurekaClient
public class PaymentServiceApplication { }

// application.yml
eureka:
  client:
    service-url:
      defaultZone: http://eureka-server:8761/eureka/
  instance:
    lease-renewal-interval-in-seconds: 10
    lease-expiration-duration-in-seconds: 30   // tighter than default 90s

// OrderService — calls by logical name, not IP
@FeignClient(name = "payment-service")   // resolved via Eureka
public interface PaymentClient {
    @PostMapping("/pay")
    PaymentResponse pay(@RequestBody PaymentRequest req);
}
```

### Kubernetes Service — Minimal Example

```yaml
apiVersion: v1
kind: Service
metadata:
  name: payment-service
spec:
  selector:
    app: payment-service
  ports:
    - port: 80
      targetPort: 8080
# OrderService just calls: http://payment-service/pay
# CoreDNS resolves "payment-service" -> ClusterIP -> healthy pod
```

## Common Pitfalls

```
❌ Pitfall 1: Hardcoding IPs or using a single static LB hostname per environment
   config file that nobody updates after infra changes.

❌ Pitfall 2: Using Eureka's default 90s eviction window in a payment-critical path
   → dead instances keep getting traffic for up to 90s.

❌ Pitfall 3: Client-side discovery without caching the registry response
   → hammering the registry on every single request.

❌ Pitfall 4: No readiness probe on Kubernetes
   → pod marked "Ready" before it can actually serve traffic → 502s during rollout.

❌ Pitfall 5: Forgetting discovery is also needed for *dependencies* outside your
   cluster (databases, third-party APIs) — those need their own health-aware routing
   (e.g., Route 53 health checks), not just service-to-service discovery.
```

---

## 🛑 When NOT to Use a Dedicated Discovery Service

- ✅ You're on Kubernetes → CoreDNS + Services already give you this for free.
- ✅ You have 2-3 services and a single environment → a simple ALB + DNS entry is enough.
- ❌ Don't add Eureka/Consul on top of Kubernetes "just in case" — it's redundant
  infrastructure that now needs its own HA and monitoring.

## TRAP QUESTIONS

---

### TRAP-1 — "Why not just use a hardcoded list of IPs behind a config server?"

> **You say:**
>
> "That works until you autoscale or an instance gets replaced — the config server
> becomes stale the moment infrastructure changes, and now you need a process to keep
> it in sync, which is exactly what a discovery mechanism automates. At that point
> you've built a worse version of service discovery yourself."

---

### TRAP-2 — "What happens if the registry itself (Eureka/Consul) goes down?"

> **You say:**
>
> "Client-side discovery libraries cache the last known healthy instance list locally,
> so existing traffic keeps flowing even if the registry is briefly unavailable — you
> just can't discover *new* instances or evict dead ones during the outage. This is why
> Eureka is designed to be AP (available, eventually consistent) rather than CP — it
> favors serving stale data over refusing to serve at all. On Kubernetes, CoreDNS and
> etcd have their own HA story, so the registry itself is rarely a single point of failure
> in practice."

---

### TRAP-3 — "How do you handle discovery across two Kubernetes clusters in different regions?"

> **You say:**
>
> "Plain CoreDNS only resolves within a cluster. For cross-cluster/cross-region calls
> I use either a service mesh with multi-cluster support (Istio's East-West gateway) or
> a global DNS layer (Route 53 latency-based routing) in front of each cluster's ingress.
> I explicitly avoid exposing raw pod IPs across regions — traffic goes through the
> region's edge/gateway first."

---

### TRAP-4 — "Client-side vs server-side discovery — which do you prefer and why?"

> **You say:**
>
> "Server-side, when the platform supports it well — like Kubernetes Services or an
> ALB. It keeps discovery logic out of application code, so every language/team gets
> it for free. I only reach for client-side discovery (Eureka) on VM-based fleets where
> there's no platform-level load balancer doing this already."

---

### TRAP-5 — "Your service just scaled from 3 to 10 pods. How fast do callers know about the new 7?"

> **You say:**
>
> "On Kubernetes, as soon as the new pod passes its readiness probe, kube-proxy updates
> the Service's endpoint list — typically within a few seconds. With Eureka, a new
> instance registers immediately, but I tune `lease-renewal-interval` down from the
> 30s default so it doesn't take a full minute for slow clients' local caches to refresh."

---

## Interview Answer (60-Second Summary)

> "Service discovery solves the problem of finding a healthy instance of a service
> when the pool of instances constantly changes due to autoscaling and deployments.
> There are two models: client-side, where the calling service queries a registry
> like Eureka and load-balances itself, and server-side, where the platform — a load
> balancer or Kubernetes Service with CoreDNS — does the discovery and routing
> transparently. On Kubernetes I rely entirely on the built-in Service/CoreDNS
> mechanism backed by readiness and liveness probes; I only introduce Eureka or Consul
> for VM-based fleets that don't have a platform-level equivalent. The key production
> concern is how fast dead instances are evicted — I always tighten the default
> lease/eviction windows for latency-sensitive paths like payments."
