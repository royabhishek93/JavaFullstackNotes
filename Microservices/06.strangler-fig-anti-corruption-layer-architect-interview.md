# Strangler Fig + Anti-Corruption Layer
## AWS + Spring Boot — Architect's Interview Script (15 Years Experience)

> These two patterns almost always appear together. Strangler Fig is HOW you migrate.
> Anti-Corruption Layer is HOW you protect your new system while migrating.

---

## Opening — When Interviewer Asks About These Patterns

---

"Both of these patterns come from the same world — legacy migration.
Every company I've worked at has had a monolith they needed to move away from.
These two patterns are how you do that safely, without a big-bang rewrite.

Let me walk through the Strangler Fig first — that's the migration strategy.
Then the Anti-Corruption Layer — that's the protection mechanism you need alongside it."

# PART A: STRANGLER FIG PATTERN

---

## 1 — The Problem: Big Bang Rewrite Kills Companies

---

"The naive approach to migrating a legacy monolith is: rewrite everything,
deploy on day X, flip the switch.

That approach has a name — it's called a Big Bang Rewrite.
And it has a well-documented history of catastrophic failures."

```
BIG BANG REWRITE — what can go wrong:

  ┌──────────────────────────────────────────────────────────────┐
  │  Month 1-12:  Team rewrites monolith in microservices        │
  │  Month 12:    New system deployed alongside old              │
  │  Month 12:    Traffic switched 100% to new system            │
  │                                                              │
  │  Month 12 + 1 day:                                           │
  │  ├── Edge cases in billing not covered                       │
  │  ├── Legacy business logic misunderstood                     │
  │  ├── Performance regressions under real load                 │
  │  ├── Data migration errors discovered in prod                │
  │  └── Rollback to old system... which is now 12 months stale │
  └──────────────────────────────────────────────────────────────┘

  The risk is enormous. You've been building in isolation for a year.
  Any mismatch between your understanding and reality only surfaces at go-live.
```

---

## 2 — The Strangler Fig Metaphor

---

"The pattern is named after the strangler fig tree — a tropical plant that
wraps around a host tree, grows alongside it, and eventually replaces it
entirely. The host tree rots away from the inside. The fig becomes the tree.

Same idea with your monolith."

```
STRANGLER FIG in nature:

  Year 1:  [FIG seed sprouts on HOST tree]
  Year 5:  [FIG wraps around HOST, both alive]
  Year 20: [FIG is fully grown, HOST has rotted away]
           [Only the FIG remains — from the outside it looks like one tree]


STRANGLER FIG in software:

  Phase 1: [NEW microservice] wraps [OLD monolith]
           Both running, new handles small slice of traffic

  Phase 2: [NEW microservices] growing, more routes migrated
           Monolith handles less and less

  Phase 3: [NEW microservices] handle everything
           Monolith decommissioned — nobody noticed the switchover
```

---

## 3 — The Core Mechanism: The Facade

---

"The key to making Strangler Fig work is a Facade — a routing layer
that sits in front of both old and new systems. The client never knows
which system handled the request."

```
STRANGLER FIG architecture:

  Clients
    │
    ▼
┌───────────────────────────────────────────────────────────────┐
│                    FACADE / PROXY                             │
│            (Spring Cloud Gateway or nginx)                    │
│                                                               │
│  Route: /api/payment/**  ──────────────────► NEW Microservice │
│  Route: /api/orders/**   ──────────────────► NEW Microservice │
│  Route: /api/**          ──────────────────► OLD Monolith     │
│          (everything else, still migrating)                   │
└───────────────────────────────────────────────────────────────┘
         │                              │
         ▼                              ▼
  ┌─────────────┐               ┌──────────────────┐
  │ OLD Monolith│               │  NEW Microservice │
  │  (Java EE,  │               │  (Spring Boot,   │
  │   Oracle DB)│               │   RDS Postgres)   │
  └─────────────┘               └──────────────────┘
```

## 4 — Step-by-Step Migration Strategy

---

"I've run this migration at two companies. Here's the exact sequence I follow:"

```
MIGRATION PHASES:

  ┌─────────────────────────────────────────────────────────────────┐
  │  PHASE 1: Install the Facade (Zero Risk)                        │
  │                                                                 │
  │  Before:  Client ──────────────────────► Monolith              │
  │  After:   Client ──► Facade ───100%───► Monolith              │
  │                                                                 │
  │  Facade routes 100% to monolith. Nothing changes functionally.  │
  │  This is your control point for all future routing.            │
  └─────────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────────┐
  │  PHASE 2: Extract First Service (Low Risk Feature)              │
  │                                                                 │
  │  Pick the simplest, most isolated feature first                 │
  │  Example: User Profile (read-heavy, no complex dependencies)    │
  │                                                                 │
  │  Facade:                                                        │
  │    /api/users/**       ──────────► NEW User Service  ✓ new     │
  │    /api/**             ──────────► Monolith          (rest)    │
  │                                                                 │
  │  Run both in parallel for 2 weeks. Compare responses.          │
  │  Switch 5% → 10% → 50% → 100% using feature flags.            │
  └─────────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────────┐
  │  PHASE 3: Extract Core Services (Medium Risk)                   │
  │                                                                 │
  │  /api/payment/**       ──────────► NEW Payment Service          │
  │  /api/orders/**        ──────────► NEW Order Service            │
  │  /api/users/**         ──────────► NEW User Service             │
  │  /api/**               ──────────► Monolith (shrinking)         │
  └─────────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────────┐
  │  PHASE 4: Decommission (The Fig Has Won)                        │
  │                                                                 │
  │  All routes → microservices                                     │
  │  Monolith receives no traffic                                   │
  │  Monolith decommissioned                                        │
  │  Facade stays — it's now your API Gateway                       │
  └─────────────────────────────────────────────────────────────────┘
```

## 5 — Spring Cloud Gateway Implementation

---

"In Spring Boot the facade is Spring Cloud Gateway with dynamic routing
backed by a database. This way I can change routing without a deployment."

```java
// Dynamic route configuration stored in database
// Routes loaded at startup + refreshable at runtime

@Configuration
public class StranglerFigRouteConfig {

    @Bean
    public RouteLocator stranglerFigRoutes(RouteLocatorBuilder builder) {
        return builder.routes()

            // MIGRATED: Payment routes → New microservice
            .route("payment-service-new", r -> r
                .path("/api/payment/**")
                .filters(f -> f
                    .rewritePath("/api/payment/(?<segment>.*)", "/${segment}")
                    .addRequestHeader("X-Migrated", "true")
                )
                .uri("lb://payment-service"))

            // MIGRATED: User routes → New microservice
            .route("user-service-new", r -> r
                .path("/api/users/**")
                .uri("lb://user-service"))

            // IN PROGRESS: Orders — canary 10% to new, 90% to monolith
            .route("order-service-canary", r -> r
                .path("/api/orders/**")
                .and().weight("order-group", 10)   // 10% to new
                .uri("lb://order-service-new"))

            .route("order-service-legacy", r -> r
                .path("/api/orders/**")
                .and().weight("order-group", 90)   // 90% to monolith
                .uri("http://monolith.internal:8080"))

            // LEGACY: Everything else → Monolith
            .route("monolith-catchall", r -> r
                .path("/**")
                .uri("http://monolith.internal:8080"))

            .build();
    }
}
```

```
CANARY DEPLOYMENT — gradual traffic shift:

  Week 1:   New orders service: 5%  │ Monolith: 95%  — watch error rates
  Week 2:   New orders service: 10% │ Monolith: 90%  — load test
  Week 3:   New orders service: 25% │ Monolith: 75%  — compare responses
  Week 4:   New orders service: 50% │ Monolith: 50%  — parity confirmed
  Week 5:   New orders service: 100%│ Monolith: 0%   — decommission route
```

## 6 — Shadow Mode (Run Both, Compare Responses)

---

"One technique I always use during migration — shadow mode.
The new service receives a copy of every request, processes it,
but its response is discarded. Only the monolith's response returns to the client.
This lets me verify correctness before cutting over."

```
SHADOW MODE flow:

                          ┌──────────────────────────────┐
                          │           FACADE              │
  Client Request ────────►│                              │
                          │  ┌──────────────────────┐   │
                          │  │ Route to Monolith    │   │──────► Client Response
                          │  └──────────────────────┘   │
                          │  ┌──────────────────────┐   │
                          │  │ Mirror to New Service │   │──► response DISCARDED
                          │  └──────────────────────┘   │    (comparison only)
                          └──────────────────────────────┘

  Comparison job runs async:
  ┌────────────────────────────────────────────────────────┐
  │  Monolith response:    { "total": 150.00, "tax": 12.5 }│
  │  New service response: { "total": 150.00, "tax": 12.5 }│
  │  Match: ✓                                              │
  │                                                        │
  │  Monolith response:    { "discount": 10.0 }            │
  │  New service response: { "discount": 0.0  }            │
  │  Match: ✗ — ALERT — business logic bug in new service  │
  └────────────────────────────────────────────────────────┘
```

```java
@Component
public class ShadowModeFilter implements GlobalFilter {

    @Value("${shadow.enabled:false}")
    private boolean shadowEnabled;

    @Autowired
    private ShadowComparisonService comparisonService;

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        if (!shadowEnabled || !isShadowRoute(exchange)) {
            return chain.filter(exchange);
        }

        // Fire shadow request async — don't block main response
        ServerHttpRequest shadowRequest = buildShadowRequest(exchange.getRequest());
        Mono.fromRunnable(() -> comparisonService.compareAsync(
            exchange.getRequest(),
            shadowRequest
        )).subscribeOn(Schedulers.boundedElastic()).subscribe();

        return chain.filter(exchange); // main response unaffected
    }
}
```

# PART B: ANTI-CORRUPTION LAYER

---

## 7 — Why You Need It (The Domain Corruption Problem)

---

"Here's the thing about the Strangler Fig — during migration, your new
microservice still needs to talk to the old monolith. It reads data from
the legacy database, calls the legacy API, maybe publishes to legacy queues.

The danger is that the legacy system's model — its concepts, its naming,
its data structures — starts to bleed into your clean new service.
That's what Eric Evans called 'corruption' in Domain-Driven Design."

```
WITHOUT Anti-Corruption Layer — domain corruption:

  Legacy monolith domain model:
  ┌──────────────────────────────────────────┐
  │  Table: CUST_ACCT                        │
  │  Columns: CUST_ID, ACCT_TYP_CD,         │
  │           ACCT_STS_FLG, CRDT_LMT_AMT    │
  │  (1980s banking system abbreviations)    │
  └──────────────────────────────────────────┘
              │
              │ Direct mapping
              ▼
  ┌──────────────────────────────────────────┐
  │  New CustomerService domain model:       │
  │  class Customer {                        │
  │      String custId;         // legacy!  │
  │      String acctTypCd;      // legacy!  │
  │      boolean acctStsFlg;    // legacy!  │
  │      BigDecimal crdtLmtAmt; // legacy!  │
  │  }                                       │
  │  ← Your clean domain is now corrupted   │
  └──────────────────────────────────────────┘

  Six months later:
  ├── Your domain model is shaped by legacy constraints
  ├── Business rules from 1985 leak into new code
  ├── Impossible to evolve independently
  └── New team members can't understand the model
```

```
WITH Anti-Corruption Layer — domain protected:

  Legacy model ──► ACL (translator) ──► Clean domain model

  ┌──────────────┐   ┌─────────────────────┐   ┌──────────────────────┐
  │  CUST_ACCT   │   │  Anti-Corruption     │   │  Customer (clean)    │
  │              │   │  Layer               │   │                      │
  │  CUST_ID     │──►│  maps/translates/    │──►│  customerId: UUID    │
  │  ACCT_TYP_CD │   │  validates/enriches  │   │  accountType: enum   │
  │  ACCT_STS_FLG│   │                      │   │  status: Status      │
  │  CRDT_LMT_AMT│   │  LegacyCustomerMapper│   │  creditLimit: Money  │
  └──────────────┘   └─────────────────────┘   └──────────────────────┘

  Your domain stays clean. Legacy can change. Only ACL needs updating.
```

## 8 — Three Responsibilities of an ACL

---

"The Anti-Corruption Layer has three jobs — and I always implement all three:"

```
ACL RESPONSIBILITIES:

  ┌──────────────────────────────────────────────────────────────┐
  │  1. TRANSLATION                                              │
  │     Convert legacy concepts to your domain concepts         │
  │     CUST_STS_FLG = 'A' → Status.ACTIVE                     │
  │     ACCT_TYP_CD = '01' → AccountType.CHECKING               │
  └──────────────────────────────────────────────────────────────┘

  ┌──────────────────────────────────────────────────────────────┐
  │  2. VALIDATION                                               │
  │     Reject or correct bad data from legacy before it        │
  │     enters your domain                                       │
  │     Legacy allows null credit limits → ACL defaults to 0    │
  │     Legacy allows negative balances in weird states         │
  │       → ACL normalizes to 0 with a flag                     │
  └──────────────────────────────────────────────────────────────┘

  ┌──────────────────────────────────────────────────────────────┐
  │  3. ISOLATION                                                │
  │     If legacy changes its schema/API, only the ACL breaks   │
  │     Your domain service is completely unaffected            │
  │     One class to fix instead of 50 files to update         │
  └──────────────────────────────────────────────────────────────┘
```

## 9 — Full Spring Boot Implementation

---

### The Clean Domain Model (protected)

```java
// Your clean domain — never touches legacy naming
public class Customer {
    private CustomerId id;          // value object
    private String fullName;
    private AccountType accountType;
    private CustomerStatus status;
    private Money creditLimit;
    private EmailAddress email;
}

public enum CustomerStatus { ACTIVE, SUSPENDED, CLOSED }
public enum AccountType    { CHECKING, SAVINGS, PREMIUM }

// Value object — not just a String
public record Money(BigDecimal amount, Currency currency) {
    public Money {
        if (amount.compareTo(BigDecimal.ZERO) < 0)
            throw new IllegalArgumentException("Money cannot be negative");
    }
}
```

### The Legacy Response (what the old system returns)

### The Anti-Corruption Layer

```java
@Component  // This IS the ACL
public class LegacyCustomerAdapter {

    private final LegacyCustomerApiClient legacyClient;   // talks to old system
    private final LegacyCustomerMapper mapper;

    // Entry point — domain service calls this, never calls legacy directly
    public Optional<Customer> findById(CustomerId id) {
        try {
            LegacyCustomerResponse raw = legacyClient.getCustomer(id.value());
            return Optional.of(mapper.toDomain(raw));
        } catch (LegacyApiException e) {
            log.warn("Legacy system error for customer {}: {}", id, e.getMessage());
            return Optional.empty();
        }
    }

    public List<Customer> findByStatus(CustomerStatus status) {
        String legacyStatusCode = mapper.toLegacyStatus(status); // reverse mapping
        List<LegacyCustomerResponse> raws = legacyClient.getByStatus(legacyStatusCode);
        return raws.stream()
            .map(mapper::toDomain)
            .collect(toList());
    }
}

@Component
public class LegacyCustomerMapper {

    public Customer toDomain(LegacyCustomerResponse raw) {
        return Customer.builder()
            .id(new CustomerId(raw.custId))
            .fullName(translateName(raw.custNm))
            .accountType(translateAccountType(raw.acctTypCd))
            .status(translateStatus(raw.acctStsFLg))
            .creditLimit(translateMoney(raw.crdtLmtAmt))
            .email(new EmailAddress(raw.emlAddr))
            .build();
    }

    private AccountType translateAccountType(String code) {
        return switch (code) {
            case "01" -> AccountType.CHECKING;
            case "02" -> AccountType.SAVINGS;
            case "03" -> AccountType.PREMIUM;
            default   -> throw new DomainTranslationException(
                "Unknown account type code: " + code);
        };
    }

    private CustomerStatus translateStatus(String flag) {
        return switch (flag) {
            case "A" -> CustomerStatus.ACTIVE;
            case "S" -> CustomerStatus.SUSPENDED;
            case "C" -> CustomerStatus.CLOSED;
            default  -> {
                log.warn("Unknown status flag '{}' — defaulting to SUSPENDED", flag);
                yield CustomerStatus.SUSPENDED;  // safe default
            }
        };
    }

    private Money translateMoney(String rawAmount) {
        if (rawAmount == null || rawAmount.isBlank()) {
            return Money.ZERO;  // validation: legacy allows null
        }
        try {
            BigDecimal amount = new BigDecimal(rawAmount.replace(",", ""));
            // validation: legacy can store negative — normalize it
            return new Money(amount.max(BigDecimal.ZERO), Currency.USD);
        } catch (NumberFormatException e) {
            log.error("Unparseable credit limit '{}' — defaulting to zero", rawAmount);
            return Money.ZERO;
        }
    }

    // Reverse mapping — for writing back to legacy
    public String toLegacyStatus(CustomerStatus status) {
        return switch (status) {
            case ACTIVE    -> "A";
            case SUSPENDED -> "S";
            case CLOSED    -> "C";
        };
    }
}
```

### The Domain Service (completely clean)

```java
@Service
@RequiredArgsConstructor
public class CustomerService {

    // Depends on PORT (interface) not on legacy adapter directly
    private final CustomerRepository customerRepository;   // → new DB
    private final LegacyCustomerAdapter legacyAdapter;     // → ACL → old system

    public Customer getCustomer(CustomerId id) {
        // Try new system first, fall back to legacy during migration
        return customerRepository.findById(id)
            .orElseGet(() -> legacyAdapter.findById(id)
                .orElseThrow(() -> new CustomerNotFoundException(id)));
    }
}
```

```
DEPENDENCY DIRECTION:

  CustomerService
        │ depends on
        ▼
  LegacyCustomerAdapter (ACL interface)
        │ depends on
        ▼
  LegacyCustomerApiClient (legacy HTTP client)
        │ calls
        ▼
  Old Monolith API

  CustomerService NEVER imports anything legacy.
  If legacy changes: only LegacyCustomerAdapter + LegacyCustomerMapper change.
```

## 10 — ACL for Events / Kafka (Not Just HTTP)

---

"The ACL pattern applies to events too — not just REST calls.
Your legacy system might publish Kafka events with old field names and formats.
You need an ACL on the consumer side."

```
LEGACY EVENT (published by monolith):

  Topic: CUST_EVENTS
  Payload: {
    "EVT_TYP": "ACCT_UPD",
    "CUST_ID": "12345",
    "OLD_STS": "A",
    "NEW_STS": "S",
    "RSN_CD": "PMT_FAIL",
    "TS": "20240115143022"    ← timestamp as YYYYMMDDHHMMSS string!
  }


ACL CONSUMER translates to clean domain event:

  CustomerStatusChangedEvent {
    customerId:  CustomerId("12345")
    oldStatus:   CustomerStatus.ACTIVE
    newStatus:   CustomerStatus.SUSPENDED
    reason:      StatusChangeReason.PAYMENT_FAILURE
    occurredAt:  Instant.parse(...)   ← proper Instant
  }
```

```java
@Component
public class LegacyCustomerEventConsumer {

    private final LegacyEventMapper eventMapper;
    private final CustomerEventHandler domainHandler;

    @KafkaListener(topics = "CUST_EVENTS", groupId = "customer-service")
    public void consume(String rawPayload) {
        // ACL: translate raw legacy event to clean domain event
        LegacyCustEvent legacyEvent = deserialize(rawPayload);
        DomainEvent domainEvent = eventMapper.toDomainEvent(legacyEvent);

        // Domain handler only sees clean events
        domainHandler.handle(domainEvent);
    }
}

@Component
public class LegacyEventMapper {

    public DomainEvent toDomainEvent(LegacyCustEvent raw) {
        return switch (raw.evtTyp) {
            case "ACCT_UPD" -> new CustomerStatusChangedEvent(
                new CustomerId(raw.custId),
                translateStatus(raw.oldSts),
                translateStatus(raw.newSts),
                translateReason(raw.rsnCd),
                parseTimestamp(raw.ts)
            );
            default -> new UnknownLegacyEvent(raw.evtTyp);
        };
    }

    private Instant parseTimestamp(String ts) {
        // legacy format: YYYYMMDDHHMMSS
        return LocalDateTime.parse(ts, DateTimeFormatter.ofPattern("yyyyMMddHHmmss"))
            .toInstant(ZoneOffset.UTC);
    }
}
```

## 11 — How They Work Together

---

"The reason Strangler Fig and Anti-Corruption Layer are almost always
discussed together is that the Strangler Fig tells you WHEN and HOW to
migrate traffic — incrementally over time. The ACL tells you HOW to keep
your new system clean while it still needs the old one.

You can't have one without the other during a migration."

```
COMBINED ARCHITECTURE during migration:

  Client Request
       │
       ▼
  ┌──────────────────────────────────────────────────────────────┐
  │  Spring Cloud Gateway (STRANGLER FIG FACADE)                 │
  │  ├── /api/payment/** ──────────────────► New Payment Svc     │
  │  ├── /api/users/**   ──────────────────► New User Svc        │
  │  └── /api/**         ──────────────────► Old Monolith        │
  └──────────────────────────────────────────────────────────────┘
                                   │
                 ┌─────────────────┘
                 │  New services still need legacy data
                 ▼
  ┌──────────────────────────────────────────────────────────────┐
  │  ANTI-CORRUPTION LAYER                                       │
  │  ├── LegacyCustomerAdapter   (translates customer model)     │
  │  ├── LegacyOrderAdapter      (translates order model)        │
  │  └── LegacyEventConsumer     (translates Kafka events)       │
  └──────────────────────────────────────────────────────────────┘
                 │
                 ▼
  ┌──────────────────────────────────────────────────────────────┐
  │  OLD MONOLITH  /  LEGACY DATABASE                            │
  └──────────────────────────────────────────────────────────────┘

  As more services migrate, the ACL adapters are deleted one by one.
  When the monolith is decommissioned, the ACL disappears entirely.
```

## 13 — Failure Scenarios

---

```
┌─────────────────────────────────┬──────────────────────────────────────────┐
│  Scenario                       │  How Handled                             │
├─────────────────────────────────┼──────────────────────────────────────────┤
│  Legacy adds new field           │  ACL's @JsonIgnoreProperties ignores it  │
│  to API response                │  Domain model unchanged                  │
├─────────────────────────────────┼──────────────────────────────────────────┤
│  Legacy renames a field         │  Only ACL mapper updated                 │
│                                 │  Domain service: zero changes            │
├─────────────────────────────────┼──────────────────────────────────────────┤
│  Legacy returns unexpected      │  ACL validates + defaults/rejects        │
│  null or malformed data         │  Never reaches domain with bad data      │
├─────────────────────────────────┼──────────────────────────────────────────┤
│  New migration has a bug        │  Strangler Fig: roll back 1 route        │
│  in production                  │  All other routes unaffected             │
│                                 │  Monolith still serving as fallback      │
├─────────────────────────────────┼──────────────────────────────────────────┤
│  Legacy goes down               │  Circuit breaker in ACL fires            │
│  temporarily                    │  Returns cached or empty response        │
│                                 │  New system continues for its data       │
├─────────────────────────────────┼──────────────────────────────────────────┤
│  Data inconsistency during      │  Shadow mode comparison flags diffs      │
│  migration period               │  before route switch happens             │
└─────────────────────────────────┴──────────────────────────────────────────┘
```

## 14 — The 60-Second Interview Answer

---

### Strangler Fig

> "Strangler Fig is how you migrate a monolith to microservices without
> a big-bang rewrite. You put a facade — Spring Cloud Gateway — in front
> of the monolith. Then you extract one feature at a time into new microservices,
> shifting traffic gradually using canary routing — 5%, 10%, 50%, 100%.
> The client never knows which system is serving them. Over time, the monolith
> receives less and less traffic until it can be decommissioned.
> The key advantage: every migration step is individually reversible.
> If the new payment service has a bug, I reroute 100% back to the monolith
> in one config change."

### Anti-Corruption Layer

> "The Anti-Corruption Layer is the protection mechanism that keeps your new
> microservice's domain model clean while it still needs to talk to legacy systems.
> Without it, the legacy system's data structures — its abbreviations, its 1980s codes,
> its bad data — bleed directly into your new code.
> The ACL is a translation layer that maps between worlds. Legacy returns ACCT_TYP_CD = '01'
> — the ACL translates that to AccountType.CHECKING before it ever reaches your domain.
> When the legacy schema changes, only the ACL changes. Your domain service is untouched.
> It applies to REST, to database queries, and to Kafka events from legacy systems."

---

## 15 — Data Migration Strategy (The Hardest Part)

---

"When I say this is the hardest part of the Strangler Fig migration,
I mean it. Routing traffic is easy — Spring Cloud Gateway, done in an hour.
But the data? The data is where migrations fail.

The monolith's database has years of production data. Your new microservice
needs its own database — database-per-service is the whole point.
So how does the new service get the data it needs while the monolith
is still the source of truth?"

```
THE DATA OWNERSHIP PROBLEM:

  Phase: Orders service is 10% migrated to new service

  ┌──────────────────────────────────────────────────────────────┐
  │  10% of order requests ──► New Order Service ──► NEW DB      │
  │  90% of order requests ──► Old Monolith      ──► LEGACY DB   │
  │                                                              │
  │  Problem: Customer support queries old DB for order history  │
  │           But 10% of new orders are only in new DB           │
  │           Reports pulling from old DB miss 10% of orders     │
  └──────────────────────────────────────────────────────────────┘
```

### Strategy 1: Dual-Write (Write to Both During Migration)

```
DUAL-WRITE pattern:

  New Order Service
       │
       ├──► Write to NEW DB  (primary)
       │
       └──► Write to LEGACY DB (via ACL)  ← keep legacy in sync

  ┌────────────────────────────────────────────────────────────┐
  │  Pros: Legacy stays in sync, reports/support tools work    │
  │  Cons: Two writes = two transactions = consistency risk    │
  │        What if NEW DB succeeds but LEGACY DB fails?        │
  └────────────────────────────────────────────────────────────┘
```

```java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository newRepository;          // new DB
    private final LegacyOrderAdapter legacyAdapter;       // ACL → old DB

    @Transactional
    public Order createOrder(CreateOrderCommand cmd) {
        Order order = Order.create(cmd);

        // Primary write — new DB
        newRepository.save(order);

        // Dual write — keep legacy in sync during migration
        try {
            legacyAdapter.syncCreate(order);  // best-effort
        } catch (LegacyWriteException e) {
            // Log and alert — don't fail the primary transaction
            // Use outbox pattern to retry legacy sync
            log.error("Legacy sync failed for order {} — queuing retry", order.getId());
            outboxRepository.save(OutboxEvent.legacySync(order));
        }

        return order;
    }
}
```

### Strategy 2: Change Data Capture (CDC) with Debezium + MSK

```
CDC PATTERN — most robust for large data volumes:

  LEGACY DB (Oracle/Postgres)
       │
       │  Debezium reads transaction log (WAL / redo log)
       │  Every INSERT/UPDATE/DELETE captured as event
       ▼
  ┌──────────────────────────────────────────────────────────┐
  │  Amazon MSK (Kafka)                                      │
  │  Topic: legacy.orders.changes                            │
  │  { op: "INSERT", before: null, after: { ORDER_ID: ... } }│
  └────────────────────────┬─────────────────────────────────┘
                           │
                           ▼ ACL consumer translates
  ┌──────────────────────────────────────────────────────────┐
  │  New Order Service (CDC consumer)                        │
  │  ├── Translates legacy event via ACL                     │
  │  ├── Upserts into new DB                                 │
  │  └── Handles reordering with event sequence numbers      │
  └──────────────────────────────────────────────────────────┘

  Pros: Zero-touch on legacy codebase, handles backfill + realtime
  Cons: Eventual consistency (seconds lag), Debezium ops overhead
```

```java
@Component
public class LegacyOrderCdcConsumer {

    private final LegacyOrderMapper mapper;
    private final OrderRepository orderRepository;

    @KafkaListener(topics = "legacy.orders.changes")
    public void onLegacyChange(DebeziumOrderEvent event) {
        switch (event.getOperation()) {
            case INSERT, UPDATE -> {
                Order order = mapper.toDomain(event.getAfter());
                orderRepository.upsert(order);  // idempotent upsert
            }
            case DELETE -> orderRepository.markDeleted(event.getBefore().getOrderId());
        }
    }
}
```

### Strategy 3: Backfill + Event Sync (Initial Load + Ongoing)

```
TWO-PHASE data migration:

  PHASE A: Backfill (one-time, before go-live)
  ┌────────────────────────────────────────────────────────────┐
  │  Batch job reads ALL legacy orders                         │
  │  Translates via ACL mapper                                 │
  │  Inserts into new DB                                       │
  │  Timestamp-based checkpointing (resume if fails)           │
  └────────────────────────────────────────────────────────────┘

  PHASE B: Ongoing sync (after backfill, until decommission)
  ┌────────────────────────────────────────────────────────────┐
  │  CDC (Debezium) or dual-write keeps new DB in sync         │
  │  New service reads from its own DB (fast, independent)     │
  │  Legacy still authoritative for un-migrated services       │
  └────────────────────────────────────────────────────────────┘

  PHASE C: Cutover
  ┌────────────────────────────────────────────────────────────┐
  │  Stop CDC / dual-write                                     │
  │  New service is now authoritative                          │
  │  Legacy DB kept read-only as archive for 90 days           │
  │  Then decommissioned                                       │
  └────────────────────────────────────────────────────────────┘
```

## 16 — Feature Flags for Traffic Control

---

"Rather than hardcoding weights in Spring Cloud Gateway config,
I use feature flags to control migration traffic at runtime —
no redeployment needed, instant rollback if something goes wrong."

```
WITHOUT feature flags:          WITH feature flags (AWS AppConfig):

  Change routing:                 Change routing:
  1. Edit gateway config          1. Update flag in AWS AppConfig console
  2. Commit to git                2. Gateway polls AppConfig every 60s
  3. CI/CD pipeline (10 min)      3. Route changes in < 60 seconds
  4. Deployment                   4. Zero deployment needed
  5. Health checks                5. Instant rollback = flip flag back
  Total: ~15-20 minutes           Total: < 1 minute
```

```java
@Configuration
public class FeatureFlagRouteConfig implements ApplicationListener<RefreshEvent> {

    @Autowired AppConfigClient appConfig;

    @Bean
    @RefreshScope   // re-evaluated when AppConfig refreshes
    public RouteLocator dynamicRoutes(RouteLocatorBuilder builder) {
        MigrationFlags flags = appConfig.getFlags("migration-flags");

        return builder.routes()
            .route("orders-new", r -> r
                .path("/api/orders/**")
                .and().weight("orders", flags.getOrdersNewWeight())   // from AppConfig
                .uri("lb://order-service"))

            .route("orders-legacy", r -> r
                .path("/api/orders/**")
                .and().weight("orders", flags.getOrdersLegacyWeight())
                .uri("http://monolith.internal:8080"))
            .build();
    }
}
```

```yaml
# AWS AppConfig — migration-flags.json
{
  "ordersNewWeight":    10,   ← change this at runtime, no deploy
  "ordersLegacyWeight": 90,
  "shadowModeEnabled":  true,
  "dualWriteEnabled":   true
}
```

## 17 — Idempotency During Migration

---

"During the migration period, a request can potentially be processed
by both the old and new system — especially during canary rollouts
or when a retry crosses the routing boundary. You must design
the new service to be idempotent."

```
IDEMPOTENCY RISK during migration:

  t=0s  Request hits new service (10% canary)
  t=1s  New service processes, response slow
  t=3s  Client retries (timeout)
  t=3s  Retry hits OLD monolith (90% canary)
  t=3s  Monolith also processes the same order

  Result: ORDER CREATED TWICE ← catastrophic for payments
```

```java
@Service
public class OrderService {

    private final OrderRepository repository;

    public Order createOrder(CreateOrderCommand cmd) {
        // Idempotency key from client (UUID per request attempt)
        return repository.findByIdempotencyKey(cmd.getIdempotencyKey())
            .orElseGet(() -> {
                Order order = Order.create(cmd);
                order.setIdempotencyKey(cmd.getIdempotencyKey());
                return repository.save(order);
            });
    }
}
```

```
IDEMPOTENCY KEY flow:

  Client generates UUID before sending: X-Idempotency-Key: abc-123

  Request 1 ──► New Service ──► DB: save(order, idempotencyKey="abc-123") ✓
  Request 2 ──► Old Monolith ──► ignores (monolith checks its own idempotency store)
  Request 3 ──► New Service ──► DB: findBy(idempotencyKey="abc-123") → return existing ✓

  Guaranteed: exactly one order created, regardless of routing
```

## 18 — ACL as Standalone Service vs Inline

---

"Interviewers often ask: should the ACL be a separate deployed service
or live inside each microservice? Here's how I decide:"

```
ACL INLINE (inside each microservice):

  ┌──────────────────────────────────────────────────┐
  │  Order Service                                   │
  │  ├── Order domain logic                          │
  │  ├── LegacyOrderAdapter    ← ACL lives here      │
  │  └── LegacyOrderMapper     ← ACL lives here      │
  └──────────────────────────────────────────────────┘

  Use when:
  ├── ACL logic is specific to this service's domain
  ├── Only this service calls the legacy API
  └── Team owns both the service and the ACL (same codebase)


ACL AS SEPARATE SERVICE (standalone):

  ┌──────────────────┐    ┌───────────────────────┐    ┌──────────┐
  │  Order Service   │───►│  Legacy ACL Service   │───►│ Monolith │
  │  User Service    │───►│  (shared translator)  │    └──────────┘
  │  Payment Service │───►│                       │
  └──────────────────┘    └───────────────────────┘

  Use when:
  ├── Multiple services call the same legacy API
  ├── Legacy API requires shared auth/session management
  ├── You want a single place to own legacy API contract
  └── Legacy is being called by 5+ new services

  Risk: Creates a shared dependency — a new bottleneck.
  Own team must maintain it. SLA must be very high.
```

## 19 — Contract Testing (Verify ACL Correctness)

---

"How do you know your ACL mapper is correct? You need contract tests.
I use Spring Cloud Contract or Pact to verify that the ACL correctly
translates legacy responses to domain objects — and that these
contracts are automatically verified on every pipeline run."

```
CONTRACT TEST flow:

  Legacy API publishes a contract (or you write one based on observation):
  ┌────────────────────────────────────────────────────────────┐
  │  Given: Legacy returns ACCT_TYP_CD = "01"                  │
  │  Then:  ACL must produce AccountType.CHECKING              │
  │                                                            │
  │  Given: Legacy returns CRDT_LMT_AMT = null                 │
  │  Then:  ACL must produce Money.ZERO (not NullPointerException)│
  │                                                            │
  │  Given: Legacy returns ACCT_STS_FLG = "X" (unknown)        │
  │  Then:  ACL must produce CustomerStatus.SUSPENDED + alert  │
  └────────────────────────────────────────────────────────────┘
```

```java
@SpringBootTest
class LegacyCustomerMapperContractTest {

    private final LegacyCustomerMapper mapper = new LegacyCustomerMapper();

    @Test
    void translatesAccountTypeCode01ToChecking() {
        LegacyCustomerResponse raw = new LegacyCustomerResponse();
        raw.acctTypCd = "01";
        raw.acctStsFLg = "A";
        raw.crdtLmtAmt = "5000.00";

        Customer customer = mapper.toDomain(raw);

        assertThat(customer.getAccountType()).isEqualTo(AccountType.CHECKING);
    }

    @Test
    void defaultsNullCreditLimitToZero() {
        LegacyCustomerResponse raw = new LegacyCustomerResponse();
        raw.acctTypCd = "01";
        raw.acctStsFLg = "A";
        raw.crdtLmtAmt = null;     // legacy allows this

        Customer customer = mapper.toDomain(raw);

        assertThat(customer.getCreditLimit()).isEqualTo(Money.ZERO);
    }

    @Test
    void handlesUnknownStatusFlagGracefully() {
        LegacyCustomerResponse raw = new LegacyCustomerResponse();
        raw.acctTypCd = "01";
        raw.acctStsFLg = "X";   // unknown flag

        Customer customer = mapper.toDomain(raw);

        // Safe default — should never throw
        assertThat(customer.getStatus()).isEqualTo(CustomerStatus.SUSPENDED);
    }
}
```

## 20 — Event-Driven Strangler Fig

---

"Everything I've shown so far is HTTP-based routing — request in, response out.
But many systems are event-driven. The Strangler Fig applies there too."

```
EVENT-DRIVEN STRANGLER FIG:

  BEFORE migration:
  ┌────────────┐  OrderPlaced event  ┌──────────────────────────┐
  │  Monolith  │────────────────────►│ Monolith Event Handlers  │
  └────────────┘                     │ ├── Inventory update     │
                                     │ ├── Email notification   │
                                     │ └── Loyalty points       │
                                     └──────────────────────────┘

  DURING migration (event routing):
  ┌────────────┐  OrderPlaced        ┌──────────────────────────┐
  │  Monolith  │────────────────────►│   Kafka Topic            │
  └────────────┘                     └────────────┬─────────────┘
                                                  │
                         ┌────────────────────────┼──────────────────────┐
                         ▼                        ▼                      ▼
              ┌──────────────────┐   ┌──────────────────┐   ┌───────────────────┐
              │ NEW Inventory    │   │ OLD Email Handler │   │ NEW Loyalty Svc   │
              │ Service (migrated│   │ (still in mono)   │   │ (migrated)        │
              └──────────────────┘   └──────────────────┘   └───────────────────┘
              (consumes from Kafka)  (Monolith still handles) (consumes from Kafka)

  Migrate event consumers one at a time.
  Old monolith keeps consuming until each handler is migrated.
  No routing facade needed — Kafka consumer groups handle isolation.
```

```java
// New service consuming events published by old monolith
// ACL translates the event format
@KafkaListener(topics = "legacy.order.events", groupId = "inventory-service")
public void handleOrderPlaced(String rawEvent) {
    // ACL translates legacy event format to domain event
    OrderPlacedEvent event = legacyEventMapper.toOrderPlaced(rawEvent);
    inventoryService.reserveStock(event.getOrderId(), event.getLineItems());
}
```
