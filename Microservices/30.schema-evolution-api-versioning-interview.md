# Schema Evolution & API Versioning — Interview Script (15 Years Experience)

> Speak naturally. Pause at diagrams. Show confidence, not textbook recitation.

---

## Opening — When Interviewer Asks "How Do You Change an API/Schema Without Breaking Consumers?"

---

"This question comes up constantly once you have more than one team consuming your
service, and the answer is different depending on whether we're talking about a
synchronous REST/gRPC contract or an asynchronous event schema on Kafka — but the
underlying principle is the same: never break what a consumer is currently relying on,
and make incompatible changes explicit and versioned, never silent."

---

## Part 1 — Compatibility Types (the vocabulary that shows depth)

---

```
BACKWARD COMPATIBLE:
  New schema can read data written by the OLD schema.
  → Consumers upgrade first, safely, before producers change.

FORWARD COMPATIBLE:
  OLD schema can read data written by the NEW schema.
  → Producers upgrade first; old consumers keep working, ignoring new fields.

FULL COMPATIBLE:
  Both directions hold. This is the target for anything with independently
  deployed producers and consumers — which is every microservices system.
```

```
SAFE vs UNSAFE CHANGES (this is what interviewers actually probe):

  SAFE (backward + forward compatible):
    - Add a new OPTIONAL field with a default value
    - Add a new enum value (if consumers handle "unknown" gracefully)
    - Deprecate a field (stop writing it) but don't remove it yet

  UNSAFE (breaking):
    - Remove a field a consumer still reads
    - Rename a field (equivalent to remove + add, from the wire's perspective)
    - Change a field's type (string → int)
    - Make an optional field required
    - Change the MEANING of a field without changing its name (silent breakage —
      the worst kind, because nothing fails at the schema level, just the business logic)
```

## Part 2 — REST/gRPC API Versioning Strategies

---

```
STRATEGY 1 — URI Versioning:
  /api/v1/orders   →   /api/v2/orders
  Simple, explicit, cache-friendly. Downside: URL sprawl, v1 and v2 code
  often diverge into two maintained implementations.

STRATEGY 2 — Header Versioning:
  GET /orders
  Accept: application/vnd.company.orders.v2+json
  Keeps URLs stable; version is a content-negotiation detail. Harder to
  test with a browser URL bar, but cleaner REST semantics.

STRATEGY 3 — Additive-only, no version number at all:
  Never remove/rename fields, only add optional ones with defaults.
  Consumers ignore fields they don't understand.
  This is what I push teams toward FIRST, because most 'breaking changes'
  are actually avoidable with careful additive design — versioning is the
  fallback for the genuinely unavoidable breaking case, not the default tool.
```

"My decision rule: try to avoid needing a new version at all through additive design.
When a change is genuinely incompatible — e.g. splitting one field into two — I version
the endpoint, keep the old version alive with a documented deprecation date, and track
which consumers are still calling it via access logs/analytics before killing it."

## Part 3 — Event Schema Evolution (Kafka/Avro — the part people forget)

---

"REST API versioning gets all the attention, but the harder case in practice is
event schemas on Kafka, because a producer's message might sit in the topic for
days before a consumer reads it, and multiple consumer versions could be reading
the same topic simultaneously during a rolling deploy."

```
SCHEMA REGISTRY FLOW:

  Producer                    Schema Registry                  Consumer
     │                              │                              │
     │──register schema v2──────────►│                              │
     │◄──check compatibility─────────│                              │
     │   (registry validates v2                                     │
     │    against v1 using the                                      │
     │    configured compatibility                                  │
     │    mode BEFORE allowing it)                                  │
     │                                                               │
     │──publish message (schema id embedded, not full schema)───────►│
     │                                                    fetches schema
     │                                                    by id from registry,
     │                                                    deserializes safely
```

```
COMPATIBILITY MODES (Confluent Schema Registry / Avro):

  BACKWARD:        new schema can read old data     (default, most common)
  FORWARD:         old schema can read new data
  FULL:            both directions
  NONE:            no checking (dangerous, only for prototyping)

  The registry REJECTS a schema registration that violates the configured
  mode — this catches a breaking change at DEPLOY TIME, before a single bad
  message ever reaches a topic, not after consumers start throwing
  deserialization exceptions in production.
```

"Why Avro over plain JSON for this: Avro schemas are explicit and structural,
so the registry can mechanically check compatibility. With raw JSON, there's no
schema to check against — you just find out a field was removed when a downstream
consumer NPEs in production."

## Part 4 — Production Scenario

---

"We had an 'order.created' event consumed by 6 different services — fraud, shipping,
analytics, notifications, inventory, and a partner webhook relay. One team wanted to
rename `customer_email` to `customer_contact_email` for clarity. Naively renaming would
have silently broken 6 consumers on their own release schedules, with zero warning.

Instead:
1. We added the NEW field `customer_contact_email` (additive, non-breaking) while
   STILL populating `customer_email` (the old field).
2. Schema Registry validated this as BACKWARD compatible — old consumers reading
   only `customer_email` kept working unaffected.
3. We updated each of the 6 consuming teams' code on their own schedule to read
   the new field, with alerts if the old field was ever accessed after a target date.
4. Only after all 6 confirmed migration did we stop writing `customer_email` —
   itself another schema version bump, still backward compatible since it's a removal
   of an already-deprecated, unread field.

This 'expand-contract' pattern — add new, dual-write, migrate consumers, remove old —
is exactly how I handle any breaking-looking change without ever actually breaking anyone."
```

## Interview Traps & Cross-Questions

---

```
Q: "Why not just tell every team to redeploy at the same time when the schema changes?"
A: "That defeats the whole point of independently deployable microservices — a
    synchronized deploy across N teams is a coordination bottleneck and a single
    point of failure for the release. The expand-contract pattern removes the need
    for synchronized deploys entirely."

Q: "Is JSON Schema validation the same as what Avro/Protobuf schema registries do?"
A: "JSON Schema can validate structure, but there's typically no CENTRAL registry
    enforcing compatibility checks at publish time the way Confluent Schema Registry
    does for Avro/Protobuf — with raw JSON you usually find out about a break at
    runtime in the consumer, not at publish time in the producer."

Q: "What's the risk of NEVER removing deprecated fields?"
A: "Schema/payload bloat over time, and ambiguity about which field is the 'real'
    source of truth. I set a deprecation window with a hard removal date, tracked via
    consumer access metrics, rather than deprecating forever with no cleanup."
```

## Quick Reference Card

```
CHANGE TYPE                       SAFE?    STRATEGY
─────────────────────────────────────────────────────────────────────
Add optional field w/ default      YES      just do it
Add enum value                     USUALLY  only if consumers handle "unknown"
Remove a field still in use        NO       expand-contract: deprecate, migrate, then remove
Rename a field                     NO       add new field, dual-write, migrate, remove old
Change field type                  NO       new field with new type, deprecate old
Genuinely incompatible redesign    NO       new API version (URI or header), sunset old
```
