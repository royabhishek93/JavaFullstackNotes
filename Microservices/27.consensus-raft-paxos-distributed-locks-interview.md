## Opening — When Interviewer Asks "How Does Raft/Paxos Actually Work?"

---

"Most engineers can say 'Raft is used by etcd, Paxos is the theoretical original' —
and that's true, but a senior-level answer explains the actual mechanism: how do a
set of nodes that can't fully trust the network agree on one value, or one leader,
without a single point of failure? Let me build it up from the core problem."

---

## Part 1 — The Core Problem: Agreement Without a Single Source of Truth

---

"If you have one node, there's no consensus problem — it just decides. The problem
appears the moment you have multiple nodes and the network between them is unreliable —
messages can be delayed, dropped, or nodes can crash and restart.

Consensus algorithms guarantee: despite all that, every non-crashed node ends up agreeing
on the same value, and once a value is agreed, it never changes (safety), and progress
is eventually made (liveness) as long as a majority of nodes are up."

```
THE PROBLEM:

  Node A ──X── Node B      (message lost)
  Node A ─────► Node C     (message delivered)

  If A proposes "leader = A" and only C hears it — does the cluster agree?
  Consensus algorithms answer this with QUORUM: a majority must acknowledge
  before anything is considered "decided". With 5 nodes, quorum = 3.
```

## Part 2 — Raft: The One You'll Actually Be Asked About

---

"Raft was explicitly designed to be understandable — Paxos is provably correct but
famously hard to reason about in a real implementation. Raft breaks the problem into
three sub-problems: leader election, log replication, and safety."

```
RAFT NODE STATES:

   ┌──────────┐  times out,     ┌───────────┐  wins majority   ┌────────┐
   │ Follower │ ─────────────► │ Candidate │ ───────────────► │ Leader │
   └──────────┘  starts election└───────────┘   of votes       └────────┘
        ▲                              │                            │
        │        sees higher term /    │                            │
        └──────── loses election ──────┘                            │
        ▲                                                            │
        └──────────────── new leader's heartbeat ────────────────────┘
```

### Leader Election (the part interviewers probe most)

```
RAFT ELECTION TIMELINE (5 nodes, election timeout randomized 150-300ms):

  t=0    All nodes are Followers. Leader (Node A) sends heartbeats every 50ms.
  t=200  Node A crashes. Heartbeats stop.
  t=340  Node C's randomized election timeout fires first (no heartbeat received).
         Node C: term++ (term 5→6), votes for itself, becomes Candidate,
                 sends RequestVote(term=6) to B, D, E.
  t=345  B, D, E: haven't voted this term yet → grant vote to C.
  t=350  Node C has 3 of 5 votes (itself + B + D) = majority → becomes LEADER.
         Node C immediately sends heartbeats to reset everyone's election timers.

  WHY RANDOMIZED TIMEOUTS MATTER:
  If all followers had the same timeout, they'd all become candidates
  simultaneously, split the vote, and no one gets a majority — repeated
  forever. Randomization means one node almost always times out first.
```

### Log Replication (how actual writes are agreed on)

```
RAFT LOG REPLICATION:

  Client ──"SET x=5"──► Leader
                            │
                            │  1. Leader appends to its own log (uncommitted)
                            │  2. Leader sends AppendEntries to all followers
                            ▼
        Follower B ◄── AppendEntries ──► Follower C ◄── AppendEntries ──► Follower D
             │                                │                               │
        appends to log                  appends to log                 appends to log
        ACK                              ACK                            ACK
             └────────────────┬───────────────┘                               │
                               ▼                                              │
                Leader has ACKs from B, C (+ itself) = 3/5 = MAJORITY         │
                              │                                               │
                LEADER COMMITS the entry, applies to its state machine        │
                LEADER responds SUCCESS to client                            │
                              │                                               │
                Next heartbeat tells followers "commit index = N" ───────────┘
                followers apply the entry to their own state machines too
```

"The client only gets a success response after majority replication — that's what
makes it durable even if the leader immediately crashes afterward: a new leader will
be elected from a node that has that committed entry, because election requires
a candidate's log to be at least as up to date as a majority."

## Part 3 — Paxos: Why It Exists and Why Nobody Reads the Original Paper Twice

---

"Paxos solves the same problem with roles named Proposer, Acceptor, Learner instead of
Leader/Follower, using a two-phase Prepare/Promise then Accept/Accepted protocol —
conceptually similar to two-phase commit but built for fault tolerance, not just
atomicity across shards.

I don't reimplement Paxos — I recognize it's *underneath* Google Chubby and inside
Cassandra's lightweight transactions (`IF NOT EXISTS`). The interview-relevant point
is: Paxos proves the theory, Raft makes it operationally usable, and ZAB (Zookeeper
Atomic Broadcast) is Zookeeper's own Raft-like variant tuned for its log/watch model."

```
CONSENSUS ALGORITHM MAP:

  Paxos  ──────► Google Chubby (lock service)
                 Cassandra (lightweight transactions, `IF NOT EXISTS`)

  Raft   ──────► etcd ──────► every Kubernetes control plane
                 CockroachDB, HashiCorp Consul (raft mode)

  ZAB    ──────► Zookeeper ──────► historically Kafka's controller election
                                    (Kafka 3.3+ replaced this with KRaft — its own Raft)
```

## Part 4 — Distributed Locks: The Redlock Debate

---

"Separate from consensus for leader election, teams often need a simple mutual-exclusion
lock — 'only one instance processes this job'. The naive approach is `SETNX` in Redis
with a TTL. That works for a single Redis node, but it gets contentious once people ask
about Redis Cluster / multi-node setups — this is where the Redlock debate comes in,
and it's a great way to show depth."

```
REDLOCK ALGORITHM (Redis's proposal for multi-node locking):

  Client tries to acquire the SAME lock key on 5 independent Redis masters:

  Master 1: SET lock:job1 client-id NX PX 10000  → OK
  Master 2: SET lock:job1 client-id NX PX 10000  → OK
  Master 3: SET lock:job1 client-id NX PX 10000  → OK (network slow, took 3s)
  Master 4: SET lock:job1 client-id NX PX 10000  → FAILED (already locked)
  Master 5: SET lock:job1 client-id NX PX 10000  → OK

  Client got lock on 3/5 (majority) within the TTL window → LOCK ACQUIRED

  "The debate: Martin Kleppmann (author of 'Designing Data-Intensive Applications')
  argued Redlock is unsafe under GC pauses / clock drift — a client can believe it
  holds the lock after its TTL has already expired elsewhere, and a second client
  acquires it, so BOTH think they hold the lock. Redis's antirez countered with
  fencing tokens as the fix. My takeaway for an interview: I say both sides accurately,
  then explain the actual mitigation I use."
```

```
FENCING TOKENS — the fix for the Redlock unsafety:

  Every lock acquisition returns a MONOTONICALLY INCREASING token (33, 34, 35...).
  The client must pass this token to the resource it's protecting (e.g. storage service).
  The resource REJECTS any write with a token lower than the highest it has already seen.

  Client A: acquires lock, gets token=34, pauses (GC/network stall)...
  Client B: lock TTL expires, B acquires lock, gets token=35, writes with token=35
  Client A: wakes up, writes with token=34 ──► REJECTED (34 < 35, stale client)

  This is why "just add a lock" isn't sufficient — the resource itself must
  understand fencing tokens, or the lock alone doesn't give real safety.
```

"In practice, for 90% of cases — 'don't run this cron job twice' — I don't need
Redlock's multi-master complexity at all. A single Redis instance (or ElastiCache
with Multi-AZ failover) with `SET NX PX` plus ShedLock's `lockAtMostFor` is enough,
because the failure mode I'm protecting against is duplicate execution, not
Byzantine-level safety. I only reach for ZooKeeper/etcd-backed locks (which use
real consensus, not ad-hoc quorum) when correctness under network partition truly
matters — e.g., financial ledger writes."

## Part 5 — Decision Framework (What I Actually Reach For)

---

```
Q1: Do you need a value/leader agreed across a cluster with strict fault tolerance?
    │
    YES ──► Raft-backed store (etcd, Consul) or Zookeeper (ZAB)
    │
    NO
    │
Q2: Do you just need "only one worker runs this job" semantics?
    │
    YES ──► Redis SETNX + TTL (ShedLock). Accept the small unsafety window;
    │       the cost of a rare double-run is low.
    │
    NO
    │
Q3: Is the lock protecting something where a double-write causes real damage
    (money movement, inventory double-allocation)?
    │
    YES ──► Add fencing tokens at the resource layer, regardless of which lock
            mechanism you use. The lock alone is never sufficient here.
```

## Interview Traps & Cross-Questions

---

```
Q: "Why does Raft use randomized election timeouts instead of a fixed timeout?"
A: "Fixed timeouts cause all followers to become candidates at the same instant,
    splitting votes indefinitely with no majority winner. Randomization makes one
    node very likely to time out first and win before others even start."

Q: "Can a Raft cluster with 5 nodes survive 2 node failures?"
A: "Yes — quorum is majority, (5/2)+1 = 3. It tolerates 2 failures. A 3-node cluster
    only tolerates 1 failure. This is why cluster sizes are always odd — even
    counts waste a node without adding fault tolerance (a 4-node cluster still
    only tolerates 1 failure, same as 3-node, but costs more)."

Q: "Is Redlock actually unsafe, yes or no?"
A: "Under adversarial conditions — long GC pauses, clock drift, network delays
    exceeding the TTL — yes, it can allow two clients to believe they hold the
    lock. For typical use (advisory locks preventing duplicate job runs), the
    risk window is small and the impact tolerable. For correctness-critical
    resources, fencing tokens or a real consensus-backed lock service are required."

Q: "What's the actual difference between Paxos and 2PC (Two-Phase Commit)?"
A: "2PC assumes the coordinator doesn't crash — if it does mid-protocol,
    participants can block indefinitely holding locks. Paxos/Raft are designed
    to survive coordinator (leader) crashes and still make progress, because
    any node can become the new leader and continue, as long as a majority
    is reachable."
```
