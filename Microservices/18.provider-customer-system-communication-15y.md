## 3) How Systems Communicate Day to Day

You: "For daily operations, customer systems call my API for acceptance, and they receive final state through webhook or event subscription. Polling is fallback, not primary."

### Typical flow I speak

```text
1) Customer -> POST /v1/orders (Idempotency-Key)
2) Product -> 202 Accepted + requestId
3) Product -> publish OrderAccepted event
4) Worker  -> process downstream actions
5) Product -> publish OrderCompleted or OrderFailed
6) Customer -> webhook handler updates status
7) Customer -> can poll GET /v1/orders/{id} if webhook delayed
```

You: "This model avoids client timeouts and still gives predictable completion tracking."

## 4) API Contract Strategy

You: "At this level, API contract quality matters more than fancy infra choices."

You: "My standards are:"

1. Versioned APIs with deprecation window.
2. Idempotency key on every mutating endpoint.
3. Correlation id propagated across all hops.
4. Structured error model with retryable vs non-retryable classification.
5. Backward-compatible event schema evolution.

You: "If contract evolution is weak, every customer onboarding becomes a production risk."

---

## 5) Reliability Model I Defend

You: "I commit to at-least-once delivery and enforce idempotent consumers. I do not casually promise global exactly-once across distributed systems."

### Outbox reliability pattern

```text
Product Transaction:
  - write business row
  - write outbox row
Commit

Outbox Publisher:
  - read unsent outbox rows
  - publish to bus
  - mark sent
```

You: "Outbox removes the gap between state change and event publication."

### Retry and failure policy

1. Retry transient failures with exponential backoff and jitter.
2. Cap retries to avoid storms.
3. Move poison events to DLQ.
4. Replay from DLQ through controlled pipeline.

## 6) Multi-Tenant Database Design

You: "For multitenancy database design, I choose isolation model first, then optimize for cost and operations."

### Model options

1. Shared DB, shared schema.
You: "Fastest and cheapest. Every table must carry tenant_id."

2. Shared DB, schema per tenant.
You: "Better isolation, but migrations get harder with many tenants."

3. DB per tenant.
You: "Strongest isolation and compliance posture, highest operational overhead."

You: "Most SaaS products start with shared schema and move selected tenants to stronger isolation tiers later."

### Core schema pattern (shared schema)

```text
TABLE tenants (
  tenant_id      BIGINT PRIMARY KEY,
  tenant_name    VARCHAR(120) NOT NULL,
  tier           VARCHAR(20) NOT NULL,
  status         VARCHAR(20) NOT NULL,
  created_at     TIMESTAMP NOT NULL
);

TABLE orders (
  tenant_id      BIGINT NOT NULL,
  order_id       BIGINT NOT NULL,
  external_ref   VARCHAR(120) NOT NULL,
  status         VARCHAR(30) NOT NULL,
  amount_cents   BIGINT NOT NULL,
  created_at     TIMESTAMP NOT NULL,
  updated_at     TIMESTAMP NOT NULL,
  PRIMARY KEY (tenant_id, order_id)
);

TABLE idempotency_keys (
  tenant_id        BIGINT NOT NULL,
  idempotency_key  VARCHAR(120) NOT NULL,
  request_hash     VARCHAR(128) NOT NULL,
  response_blob    TEXT NOT NULL,
  expires_at       TIMESTAMP NOT NULL,
  PRIMARY KEY (tenant_id, idempotency_key)
);
```

### Index strategy I mention

```text
orders:
  INDEX idx_orders_tenant_created (tenant_id, created_at DESC)
  INDEX idx_orders_tenant_status  (tenant_id, status, created_at DESC)
  UNIQUE idx_orders_tenant_ref    (tenant_id, external_ref)

idempotency_keys:
  INDEX idx_idemp_expiry          (expires_at)
```

You: "I keep tenant_id as leading column in hot indexes so query paths stay tenant-safe and performant."

## 9) Timeouts, Errors, and Communication Semantics

You: "Every integration should define communication semantics clearly."

1. 200 or 201 for immediate completion.
2. 202 for accepted and processing asynchronously.
3. 4xx for business validation failures, non-retryable.
4. 429 or 5xx for retryable failures with retry-after guidance.

You: "If I do not classify errors explicitly, customers build wrong retry behavior and amplify incidents."

---

## 10) Failure Scenarios I Always Mention

You: "Senior answers are judged by failure handling quality."

### Case A: Provider API down
- Circuit breaker opens.
- Customer receives graceful retry-later response.

### Case B: Event bus delay
- Outbox publisher retries.
- Lag SLO alert fires.

### Case C: Duplicate delivery
- Consumer dedup using message id and idempotency key.

### Case D: Partial completion
- Compensation workflow or reconciliation flow.

### Case E: Region outage
- Failover runbook.
- Controlled replay after recovery.

5. DLQ depth and drain time.

## 12) Cross-Questions and My Spoken Answers

Q: "Why not only synchronous calls?"
You: "Long operations would cause timeouts and cascading failures. Sync for acceptance, async for completion is safer."

Q: "How do you prevent duplicate order creation?"
You: "Idempotency key enforced server-side with deterministic replay response."

Q: "How do you keep provider and customer state consistent?"
You: "Outbox plus idempotent consumers plus reconciliation jobs."

Q: "How do you evolve contracts without breaking old tenants?"
You: "Additive changes in same version, explicit version bump for breaking changes, and migration window."

Q: "How do you prevent cross-tenant leaks?"
You: "Tenant_id in key paths, policy-enforced predicates, and tenant-boundary tests in CI."

Q: "What delivery guarantee do you promise externally?"
You: "At-least-once with idempotent consumer contract."

Q: "What do you explicitly not promise?"
You: "Global exactly-once across arbitrary downstream systems."

## 13) Top 10 Trap Questions and What Not to Say

1. Trap: "Can you guarantee exactly-once everywhere?"
Strong answer: "At-least-once plus idempotency is practical and reliable."
What not to say: "Exactly-once is easy."

2. Trap: "Why not make everything sync?"
Strong answer: "It increases timeout and cascade risk for long workflows."
What not to say: "Async is too hard so we avoid it."

3. Trap: "How do retries not create duplicates?"
Strong answer: "Idempotency keys plus dedup store and deterministic response replay."
What not to say: "Client should not retry."

4. Trap: "Webhook fails, then what?"
Strong answer: "Retry with signed callbacks and polling fallback."
What not to say: "Customer should contact support manually."

5. Trap: "How do you isolate tenants?"
Strong answer: "Auth, data model, quotas, and queue fairness together."
What not to say: "Only DB partitioning is enough."

6. Trap: "How do you know system health?"
Strong answer: "Latency, lag, retry success, DLQ, and tenant fairness metrics."
What not to say: "CPU and memory are enough."

7. Trap: "How do you do DR?"
Strong answer: "RPO or RTO targets, tested failover, and replay control."
What not to say: "Backups mean DR is solved."

8. Trap: "How to handle one huge tenant?"
Strong answer: "Re-home to dedicated shard or DB while keeping API contract stable."
What not to say: "Just scale vertically forever."

9. Trap: "How do you secure service-to-service calls?"
Strong answer: "TLS, OAuth2 or mTLS, least privilege, audit trails."
What not to say: "Internal network is trusted by default."

10. Trap: "How do you avoid retry storms?"
Strong answer: "Jittered backoff, retry caps, per-tenant retry budgets, circuit breakers."
What not to say: "More retries always improve reliability."

## 15) Experience-Level Tricky Cross-Questions (With Spoken Answers)

### Q1) Tell me about one production incident caused by retries and how you fixed it permanently.
You: "We had downstream timeouts and clients retried aggressively, which created duplicate side effects. I contained impact using circuit breakers and retry caps, then fixed it permanently using idempotency keys, deterministic response replay, jittered backoff, and per-tenant retry budgets."

### Q2) What metric gave earliest signal before outage became customer-visible?
You: "Consumer lag acceleration and queue age percentile moved first. API error rate came later."

### Q3) How do you prove tenant isolation in audits, not just claim it?
You: "I show evidence at policy, data, and test layers: tenant-scoped authz policies, tenant-bound query/audit logs, and automated tenant-boundary test reports."

### Q4) How do you migrate one tenant from shared DB to dedicated DB with zero downtime?
You: "CDC replication, dual-read validation, controlled write cutover behind feature flag, and rollback window until consistency checks pass."

### Q5) How do you handle webhook replay attacks and clock skew?
You: "HMAC signature, timestamp validation, nonce cache, short validity window, and explicit clock-skew tolerance."

### Q6) What breaks first when one tenant spikes 20x traffic suddenly?
You: "Fairness and downstream throttles usually break before CPU. I protect using tenant quotas, weighted scheduling, and burst controls."

### Q7) How do you do per-tenant cost attribution and billing reconciliation?
You: "Every request/event carries tenant id and cost tags. I aggregate compute, storage, egress, and third-party calls into a tenant usage ledger, then reconcile with billing."

### Q8) How do you rollback a bad event schema deployment already consumed by clients?
You: "Keep compatibility path alive, publish adapter transforms, replay safely, then phase out broken schema after verification."

### Q9) How do you design replay so old events do not trigger current business rules incorrectly?
You: "Replay runs in version-aware mode with effective-date policy checks, so historical events are processed with historical semantics."

### Q10) How do you enforce data residency for tenants in different regions?
You: "Tenant policy metadata drives region-pinned writes and storage. Replication is policy-filtered, and control plane rejects non-compliant flows."

### Q11) How do you do tenant-specific encryption key rotation without mass downtime?
You: "Envelope encryption with dual-key decrypt window, background re-encryption, then old-key retirement after verification."

### Q12) How do you test failover runbook under load, not just in quiet environment?
You: "Run game days with production-like traffic and measure actual RTO, lag recovery, duplicate rate, and business completion latency."

### Q13) What is your strategy when queue is healthy but downstream provider is rate-limiting?
You: "Adaptive concurrency plus downstream-aware throttling, retry-after respect, and priority-based shaping to protect critical flows."

### Q14) How do you avoid priority inversion between premium and standard tenants?
You: "Weighted fair scheduling with reservation floors and hard caps so premium gets guarantees without starving standard tiers."

### Q15) What consistency guarantees are different for read APIs vs write workflows?
You: "Reads are eventual with freshness bounds. Writes are durability plus idempotent acceptance and completion semantics."

### Q16) How do you cap blast radius of one buggy customer integration?
You: "Tenant kill switch, strict quotas, schema validation gates, and per-tenant circuit breakers."

### Q17) How do you handle contract drift when partner team ignores deprecation timeline?
You: "Governance milestones, usage dashboards, escalation path, hard freeze dates, and isolated legacy lane until migration completes."

### Q18) What are your hard non-goals that product/business must accept?
You: "No global exactly-once across arbitrary external systems, no unlimited retries, and no zero-latency promise under regional failures."

### Q19) How do you detect silent data loss in event-driven pipelines?
You: "Sequence audits, canary events, expected-vs-observed counters per stage, checksums, and periodic reconciliation jobs."

### Q20) If audit asks show one order lifecycle end-to-end now, what evidence do you show?
You: "I show one correlation id across API log, auth decision, DB write, outbox row, publish record, consumer execution log, state transition history, and final customer notification proof."
