# Blue-Green & Canary Deployments — Interview Script (15 Years Experience)

> Speak naturally. Pause at diagrams. Show confidence, not textbook recitation.
> Complements [03.service-mesh-istio-springboot-aws-architect-interview.md](03.service-mesh-istio-springboot-aws-architect-interview.md), which
> mentions "traffic shifting (canary)" briefly at the mesh level; this file covers

---

## Opening — When Interviewer Asks "How Do You Deploy a New Version Without Downtime or Risk?"

---

"The naive approach — stop the old version, start the new one — causes downtime and,
worse, gives you no way to back out cheaply if the new version has a bug. Blue-green
and canary are the two standard answers, and they solve slightly different problems:
blue-green is about a SAFE, INSTANT rollback; canary is about LIMITING BLAST RADIUS
by exposing the new version to a small slice of traffic first."

---

## Part 1 — Blue-Green Deployment

---

```
BLUE-GREEN MECHANICS:

  BEFORE:                              DURING CUTOVER:
  ┌─────────────┐                      ┌─────────────┐
  │  BLUE (v1)   │◄── 100% traffic     │  BLUE (v1)   │   idle, kept warm
  │  (live)      │                      │  (standby)   │   for instant rollback
  └─────────────┘                      └─────────────┘
                                              │
  ┌─────────────┐                      ┌─────────────┐
  │  GREEN (v2)  │   idle,              │  GREEN (v2)  │◄── 100% traffic
  │  (standby)   │   fully deployed,    │  (live)      │    (cutover happened
  └─────────────┘   fully tested       └─────────────┘     via LB/DNS switch,
                     before cutover                         essentially instant)

  ROLLBACK if GREEN has a problem: flip the load balancer/DNS back to BLUE.
  Since BLUE was never torn down, this is SECONDS, not a redeploy.
```

"The key property: BOTH versions run simultaneously, fully deployed, and the cutover
is a traffic-routing change (load balancer target group swap, DNS change), not a
redeploy. That's what makes rollback near-instant — you're not waiting for a new
deployment to roll out again, you're just flipping a switch back."

```
THE PART PEOPLE FORGET — DATABASE MIGRATIONS:

  If GREEN's new code requires a schema change, and BLUE is still potentially
  live (for rollback), the schema change must be BACKWARD COMPATIBLE with
  BLUE's old code too, for the whole window both versions coexist.
  This is the same "expand-contract" principle as schema evolution
  (see 30.schema-evolution-api-versioning-interview.md) — add new columns/
  tables additively, don't drop/rename anything BLUE still depends on,
  until BLUE is fully decommissioned after a successful cutover.
```

```
AWS IMPLEMENTATION (typical):

  Route 53 / ALB target group weighting:
    Target Group BLUE  (v1 tasks) ◄── 100% ──┐
                                               ├── ALB
    Target Group GREEN (v2 tasks) ◄── 0%   ──┘

  Cutover: update ALB listener rule to point 100% at GREEN's target group.
  Rollback: revert the listener rule back to BLUE — no redeploy needed.

  ECS/CodeDeploy has native Blue/Green deployment support that automates
  exactly this target-group swap, plus automated rollback on CloudWatch
  alarm triggers (e.g. error rate spike right after cutover).
```

## Part 2 — Canary Deployment

---

"Blue-green is all-or-nothing at cutover — 100% of traffic moves at once. Canary
deployment instead sends a SMALL PERCENTAGE of traffic to the new version first,
and gradually increases it while watching metrics, so a bug affects the minimum
number of users before you catch it."

```
CANARY ROLLOUT PROGRESSION:

  Stage 1:  v1 (stable) ── 95% traffic
            v2 (canary)  ── 5% traffic    ← watch error rate/latency closely

  Stage 2 (after 5% looks healthy, e.g. 30 min):
            v1 (stable) ── 75% traffic
            v2 (canary)  ── 25% traffic

  Stage 3 (after 25% looks healthy):
            v1 (stable) ── 0% traffic
            v2 (now the new stable) ── 100% traffic

  AT ANY STAGE — if error rate/latency degrades beyond a threshold:
  automatically roll BACK to 0% canary traffic, investigate.
```

```
WHAT DECIDES "IS THE CANARY HEALTHY" (this is the part interviewers probe):

  Automated analysis compares canary metrics against the stable baseline,
  not just absolute thresholds:

    canary_error_rate (5% of traffic)   vs   stable_error_rate (95% of traffic)
    canary_p99_latency                   vs   stable_p99_latency

  If canary's error rate is statistically significantly worse than
  stable's — not just "above some fixed number" which might be normal
  variance — automatically HALT the rollout and roll back. Tools like
  Argo Rollouts / Flagger automate this analysis step using Prometheus
  metrics queries, not manual eyeballing of a dashboard.
```

## Part 3 — Blue-Green vs Canary: When to Use Which

---

```
                    BLUE-GREEN                    CANARY
────────────────────────────────────────────────────────────────────────
Blast radius         100% at cutover (all-or-       Small % initially,
                     nothing switch)                 grows gradually
Rollback speed        instant (flip traffic route)   instant (route back to 0%)
Infra cost            2x capacity needed              slightly more than 1x
                     (both versions fully live)       (small canary fleet)
Best for              simpler apps, infrequent          high-traffic services where
                     releases, want simple binary       gradual exposure catches subtle
                     safety net                         bugs (perf regression, edge
                                                        cases) before they hit everyone
Complexity            simpler to reason about           requires automated metric
                                                        analysis to be safe (manual
                                                        canary judgment doesn't scale)
```

"In practice I've combined them: canary the rollout gradually within a single
environment, but keep the PREVIOUS stable version's infrastructure warm (blue-green
style) as the ultimate fallback if something is caught late that the canary stages
didn't detect."

## Part 4 — Production Scenario

---

"At an e-commerce platform doing frequent releases (multiple times a day), pure
blue-green was too coarse — a subtle bug affecting 2% of checkout flows (e.g. a
specific payment method edge case) wouldn't show up in smoke tests but would hit
100% of users the instant cutover happened. We moved to canary via Argo Rollouts on
Kubernetes: 5% → 25% → 50% → 100%, each stage gated by an automated Prometheus query
comparing canary error rate against the stable baseline over a 10-minute window,
with automatic rollback if canary's checkout error rate exceeded stable's by more
than 2x. This caught 3 subtle regressions over 6 months at the 5% stage, each
affecting a small fraction of users for under 15 minutes, instead of every user
for the time it would've taken to notice and manually roll back a blue-green cutover."

## Interview Traps & Cross-Questions

---

```
Q: "Isn't canary just a slower, more complicated blue-green?"
A: "No — blue-green's binary switch means a bug affects 100% of traffic the
    instant cutover happens, discoverable only after the fact. Canary's whole
    point is limiting how many users are exposed to a bad version BEFORE
    you've fully confirmed it's safe — it's a genuinely different risk
    profile, not just a slower version of the same idea."

Q: "Does canary deployment require Kubernetes specifically?"
A: "No — the concept is infrastructure-agnostic (weighted ALB target groups,
    weighted DNS, service mesh traffic splitting all work), but Kubernetes-
    native tools like Argo Rollouts/Flagger have become the most common way
    to implement the automated metric-gated progression, since K8s already
    has a rich metrics/observability ecosystem to hook into."

Q: "What's the biggest operational cost of blue-green you'd flag to a team
    considering it?"
A: "Running 2x full capacity during the cutover window, and ensuring any
    database/schema changes remain compatible with BOTH versions for that
    whole window — teams often plan the traffic-routing half well but forget
    the schema-compatibility half, and get a production incident from BLUE
    (still receiving some traffic during a slow rollback) hitting a
    column GREEN's migration already dropped."
```
