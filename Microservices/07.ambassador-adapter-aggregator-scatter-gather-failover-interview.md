# PATTERN 1: AMBASSADOR

---

## 1 — What Problem It Solves

---

"The Ambassador pattern is about offloading cross-cutting concerns from your
service into a proxy that runs alongside it — a sidecar.

Every service needs retry logic, circuit breakers, authentication headers,
TLS termination, logging of outbound calls. If you implement all that
in every service, you duplicate it 50 times. When you need to change the
retry policy, you redeploy 50 services.

The Ambassador moves all that shared logic into a proxy that lives next to
your service — same host, same pod. Your service talks to localhost.
The Ambassador handles everything else."

```
WITHOUT Ambassador — cross-cutting logic duplicated everywhere:

  ┌─────────────────────────────────────────────────────────────┐
  │  Service A                                                  │
  │  ├── business logic                                         │
  │  ├── retry logic (copy-pasted)                              │
  │  ├── circuit breaker (copy-pasted)                          │
  │  ├── auth header injection (copy-pasted)                    │
  │  └── TLS cert management (copy-pasted)                      │
  └─────────────────────────────────────────────────────────────┘
  ┌─────────────────────────────────────────────────────────────┐
  │  Service B  (exact same boilerplate)                        │
  │  ├── business logic                                         │
  │  ├── retry logic (copy-pasted)                              │
  │  ├── ...                                                    │
  └─────────────────────────────────────────────────────────────┘

  50 services = 50 copies of the same cross-cutting code.
  One policy change = 50 redeployments.


WITH Ambassador — cross-cutting logic in one place:

  ┌───────────────────────────────────────────────────────────┐
  │  ECS Task / K8s Pod                                       │
  │  ┌─────────────────┐       ┌──────────────────────────┐  │
  │  │   Service A     │       │   Ambassador Proxy        │  │
  │  │                 │       │   (Envoy / custom)        │  │
  │  │  business logic │──────►│  ├── retry (3x, backoff)  │  │
  │  │  (talks to      │       │  ├── circuit breaker      │  │
  │  │   localhost)    │       │  ├── auth header inject   │  │
  │  └─────────────────┘       │  ├── TLS termination      │  │
  │                            │  └── outbound logging     │  │
  │                            └────────────────┬─────────  │  │
  └────────────────────────────────────────────┼───────────┘
                                               │
                                               ▼
                                       External Services
```

## 2 — Implementation Options in AWS

---

```
OPTION A: Envoy as sidecar (Kubernetes / ECS with Service Mesh)

  ECS Task:
  ┌──────────────────────────────────────────────────────────┐
  │  Container 1: Your Spring Boot Service                   │
  │  Container 2: Envoy Proxy (Ambassador)                   │
  │                                                          │
  │  Service talks to localhost:8080                         │
  │  Envoy intercepts, handles retry/CB/mTLS                 │
  │  AWS App Mesh manages Envoy config centrally             │
  └──────────────────────────────────────────────────────────┘


OPTION B: Spring Boot custom Ambassador (lightweight, no service mesh)

  Same process — a @Component that wraps outbound calls
  and handles all cross-cutting concerns.
```

```java
// Spring Boot Ambassador — wraps all outbound HTTP calls
@Component
@Slf4j
public class HttpAmbassador {

    private final RestTemplate restTemplate;
    private final CircuitBreakerRegistry cbRegistry;
    private final RetryRegistry retryRegistry;

    // Every outbound call goes through the Ambassador
    public <T> T call(String serviceName, String url,
                      HttpMethod method, Object body, Class<T> responseType) {

        CircuitBreaker cb    = cbRegistry.circuitBreaker(serviceName);
        Retry          retry = retryRegistry.retry(serviceName);

        Supplier<T> decoratedCall = Decorators
            .ofSupplier(() -> executeWithAuth(url, method, body, responseType))
            .withCircuitBreaker(cb)
            .withRetry(retry)
            .decorate();

        try {
            return decoratedCall.get();
        } catch (CallNotPermittedException e) {
            throw new ServiceUnavailableException(serviceName + " circuit open");
        }
    }

    private <T> T executeWithAuth(String url, HttpMethod method,
                                   Object body, Class<T> type) {
        HttpHeaders headers = new HttpHeaders();
        headers.set("Authorization", "Bearer " + tokenProvider.getServiceToken());
        headers.set("X-Correlation-Id", MDC.get("correlationId"));

        HttpEntity<Object> entity = new HttpEntity<>(body, headers);
        return restTemplate.exchange(url, method, entity, type).getBody();
    }
}

// Service uses Ambassador — zero cross-cutting concern code
@Service
public class OrderService {

    private final HttpAmbassador ambassador;

    public Inventory checkInventory(String productId) {
        return ambassador.call(
            "inventory-service",
            "http://inventory-service/api/inventory/" + productId,
            HttpMethod.GET, null, Inventory.class
        );
    }
}
```

# PATTERN 2: ADAPTER

---

## 4 — What Problem It Solves

---

"The Adapter pattern is about making incompatible interfaces work together.
It's the electrical plug adapter of software — two things that can't directly
connect, connected through a middle piece that translates between them.

In microservices, I use it when a new service needs to interact with a legacy
system, a third-party API, or any service with a different contract than
what my domain expects."

```
ADAPTER pattern — making incompatible interfaces work:

  YOUR DOMAIN             ADAPTER                  LEGACY / THIRD PARTY
  ────────────────        ────────────────────     ──────────────────────
  processPayment()  ──►  PaymentAdapter.charge()  ──►  Stripe.createCharge()
  (your interface)       (translates call)              (their interface)

  WITHOUT adapter:              WITH adapter:
  ┌──────────────────────┐      ┌──────────────────────┐
  │  OrderService        │      │  OrderService        │
  │  stripeApi.create    │      │  paymentPort.charge  │ ← your interface
  │  Charge(amount,      │      └──────────┬───────────┘
  │  currency, source,   │                 │
  │  description, ...)   │      ┌──────────▼───────────┐
  │  ← Stripe-specific   │      │  StripePaymentAdapter│ ← adapter
  └──────────────────────┘      │  (translates)        │
                                └──────────┬───────────┘
  If you swap Stripe for              ┌────▼────────────┐
  PayPal: change 50 files.            │  Stripe API     │
                                      └─────────────────┘
                                If you swap: change 1 adapter.
```

## 5 — Spring Boot Implementation

---

```java
// Step 1: Define YOUR domain interface (the Port)
public interface PaymentGateway {
    PaymentResult charge(Money amount, PaymentMethod method, String description);
    RefundResult  refund(String paymentId, Money amount);
    PaymentStatus getStatus(String paymentId);
}

// Step 2: Stripe Adapter (implements your interface, wraps Stripe SDK)
@Component("stripeAdapter")
public class StripePaymentAdapter implements PaymentGateway {

    private final StripeClient stripe;

    @Override
    public PaymentResult charge(Money amount, PaymentMethod method, String description) {
        // Translate YOUR domain model → Stripe's model
        ChargeCreateParams params = ChargeCreateParams.builder()
            .setAmount(amount.toCents())             // Stripe uses cents
            .setCurrency(amount.getCurrency().getCode().toLowerCase())
            .setSource(method.getToken())
            .setDescription(description)
            .build();

        try {
            Charge charge = Charge.create(params);
            // Translate Stripe's response → YOUR domain model
            return PaymentResult.success(charge.getId(), amount);
        } catch (CardException e) {
            return PaymentResult.declined(e.getCode(), e.getMessage());
        } catch (StripeException e) {
            throw new PaymentGatewayException("Stripe error: " + e.getMessage(), e);
        }
    }
}

// Step 3: PayPal Adapter (swap without changing OrderService at all)
@Component("paypalAdapter")
public class PayPalPaymentAdapter implements PaymentGateway {

    private final PayPalHttpClient paypal;

    @Override
    public PaymentResult charge(Money amount, PaymentMethod method, String description) {
        // Translate YOUR domain model → PayPal's model (completely different API)
        OrderRequest order = new OrderRequest();
        order.checkoutPaymentIntent("CAPTURE");
        // ... PayPal-specific setup
        HttpResponse<Order> response = paypal.execute(new OrdersCreateRequest().requestBody(order));
        return PaymentResult.success(response.result().id(), amount);
    }
}

// Step 4: Service depends on interface — never on Stripe or PayPal directly
@Service
public class OrderService {

    private final PaymentGateway paymentGateway;  // injected by Spring

    public OrderConfirmation checkout(Cart cart, PaymentMethod method) {
        PaymentResult result = paymentGateway.charge(cart.total(), method, "Order #" + cart.getId());
        // Zero Stripe/PayPal code here. Swap payment providers: 0 changes to OrderService.
        return OrderConfirmation.from(result);
    }
}
```

```
SWAP ADAPTERS via Spring configuration:

  # application.yml
  payment:
    gateway: stripe   # change to "paypal" → zero code change

  @Configuration
  public class PaymentConfig {
      @Bean
      public PaymentGateway paymentGateway(
              @Value("${payment.gateway}") String provider,
              StripePaymentAdapter stripe,
              PayPalPaymentAdapter paypal) {
          return switch (provider) {
              case "stripe" -> stripe;
              case "paypal" -> paypal;
              default -> throw new IllegalStateException("Unknown gateway: " + provider);
          };
      }
  }
```

# PATTERN 3: AGGREGATOR

---

## 6 — What Problem It Solves

---

"When you decompose a monolith into microservices, a single page or screen
often needs data from multiple services. The product detail page needs
product info, pricing, inventory, reviews, and recommendations — each from
a different service.

You don't want the frontend making 5 separate API calls.
You don't want to merge all those services back together.

The Aggregator sits between frontend and services, calls all of them,
and returns a single composed response."

```
WITHOUT Aggregator — frontend makes multiple calls:

  Browser
    │
    ├──────────────────────────────► Product Service    (call 1: 100ms)
    ├──────────────────────────────► Pricing Service    (call 2: 80ms)
    ├──────────────────────────────► Inventory Service  (call 3: 120ms)
    ├──────────────────────────────► Reviews Service    (call 4: 200ms)
    └──────────────────────────────► Recommendation Svc (call 5: 150ms)

  Total time: 650ms (sequential) or network overhead (parallel)
  Browser code: complex coordination + error handling × 5
  Mobile apps: 5 round trips on mobile network = painful


WITH Aggregator — one call, one response:

  Browser
    │
    ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  Product Detail Aggregator                                  │
  │                                                             │
  │  Calls all 5 services IN PARALLEL:                          │
  │  ├──► Product Service    ─────────────────────► result 1   │
  │  ├──► Pricing Service    ───────────────────► result 2     │
  │  ├──► Inventory Service  ─────────────────────► result 3   │
  │  ├──► Reviews Service    ───────────────────────► result 4 │
  │  └──► Recommendation Svc ───────────────────────► result 5 │
  │                                                             │
  │  Merges all responses into one ProductDetailResponse        │
  └─────────────────────────────────────────────────────────────┘
    │
    └──────────────────────────────────────────────────► Browser

  Total time: max(all calls) = 200ms  (not 650ms)
  Browser code: one API call, one response object
```

---

## 7 — Spring Boot Implementation (Parallel Calls with CompletableFuture)

---

```java
@Service
@RequiredArgsConstructor
public class ProductDetailAggregator {

    private final ProductServiceClient    productClient;
    private final PricingServiceClient    pricingClient;
    private final InventoryServiceClient  inventoryClient;
    private final ReviewsServiceClient    reviewsClient;
    private final RecommendationClient    recommendationClient;

    public ProductDetailResponse aggregate(String productId, String userId) {

        // Launch ALL calls in parallel — don't wait between them
        CompletableFuture<Product>          productFuture =
            CompletableFuture.supplyAsync(() -> productClient.getProduct(productId));

        CompletableFuture<Price>            pricingFuture =
            CompletableFuture.supplyAsync(() -> pricingClient.getPrice(productId, userId));

        CompletableFuture<InventoryStatus>  inventoryFuture =
            CompletableFuture.supplyAsync(() -> inventoryClient.getStatus(productId));

        CompletableFuture<List<Review>>     reviewsFuture =
            CompletableFuture.supplyAsync(() -> reviewsClient.getTopReviews(productId, 5));

        CompletableFuture<List<Product>>    recommendFuture =
            CompletableFuture.supplyAsync(() -> recommendationClient.getSimilar(productId));

        // Wait for ALL to complete (with timeout)
        CompletableFuture.allOf(
            productFuture, pricingFuture, inventoryFuture, reviewsFuture, recommendFuture
        ).get(3, TimeUnit.SECONDS);   // overall SLA: 3 seconds max

        // Compose the unified response
        return ProductDetailResponse.builder()
            .product(productFuture.join())
            .price(pricingFuture.join())
            .inventory(inventoryFuture.join())
            .reviews(reviewsFuture.join())
            .recommendations(recommendFuture.join())
            .build();
    }
}
```

### Partial Response — Don't fail if one service is down

```java
// Production version: partial response if non-critical service fails
public ProductDetailResponse aggregateWithFallback(String productId, String userId) {

    // Critical — must have these
    CompletableFuture<Product> productFuture =
        CompletableFuture.supplyAsync(() -> productClient.getProduct(productId));

    CompletableFuture<Price> pricingFuture =
        CompletableFuture.supplyAsync(() -> pricingClient.getPrice(productId, userId));

    // Nice-to-have — degrade gracefully if unavailable
    CompletableFuture<List<Review>> reviewsFuture =
        CompletableFuture.supplyAsync(() -> reviewsClient.getTopReviews(productId, 5))
            .exceptionally(ex -> {
                log.warn("Reviews service down — returning empty list");
                return Collections.emptyList();   // graceful degradation
            });

    CompletableFuture<List<Product>> recommendFuture =
        CompletableFuture.supplyAsync(() -> recommendationClient.getSimilar(productId))
            .exceptionally(ex -> Collections.emptyList());

    CompletableFuture.allOf(productFuture, pricingFuture).get(2, TimeUnit.SECONDS);

    return ProductDetailResponse.builder()
        .product(productFuture.join())              // fails if product unavailable
        .price(pricingFuture.join())                // fails if pricing unavailable
        .reviews(reviewsFuture.getNow(emptyList())) // empty if service down
        .recommendations(recommendFuture.getNow(emptyList()))
        .build();
}
```

```
PARTIAL RESPONSE strategy:

  Critical services (product, pricing):
  ├── Fail if unavailable → 503 to client
  └── SLA: 2 seconds max

  Non-critical services (reviews, recommendations):
  ├── Return empty/cached if unavailable
  └── Never fail the main response

  This is the "graceful degradation" mindset at the API layer.
```

# PATTERN 4: SCATTER-GATHER

---

## 8 — What Problem It Solves

---

"Scatter-Gather is a specialisation of the Aggregator — but where the
Aggregator calls different services for different data, Scatter-Gather
sends the SAME request to multiple services and gathers all responses.

Classic use case: price comparison. You want to check prices from
10 suppliers simultaneously, collect all responses, and return
the cheapest option. Or: search across multiple data sources in parallel
and merge the results."

```
AGGREGATOR vs SCATTER-GATHER:

  AGGREGATOR:
    Request ──► [Product Service]      ─┐
                [Pricing Service]      ─┤ different data from different services
                [Inventory Service]    ─┘
                        │
                   Merge response


  SCATTER-GATHER:
    Request ──► [Supplier A] ─┐
                [Supplier B] ─┤ same request to multiple instances
                [Supplier C] ─┤
                [Supplier D] ─┘
                      │
              Gather + process all responses
              (find cheapest / merge results / rank)
```

```
SCATTER-GATHER architecture:

  Price Check Request (productId: ABC123)
           │
           ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  ScatterGatherService                                       │
  │                                                             │
  │  SCATTER — send to all suppliers simultaneously:            │
  │  ├──────────────────────────────────► Supplier A: $45.99   │
  │  ├──────────────────────────────────► Supplier B: $42.00   │
  │  ├──────────────────────────────────► Supplier C: $48.50   │
  │  ├──────────────────────────────────► Supplier D: timeout  │
  │  └──────────────────────────────────► Supplier E: $41.50   │
  │                                                             │
  │  GATHER — collect responses within deadline (e.g. 2s):      │
  │  ├── Supplier A: received ✓                                 │
  │  ├── Supplier B: received ✓                                 │
  │  ├── Supplier C: received ✓                                 │
  │  ├── Supplier D: TIMEOUT — excluded from results            │
  │  └── Supplier E: received ✓                                 │
  │                                                             │
  │  PROCESS — find cheapest: Supplier E at $41.50             │
  └─────────────────────────────────────────────────────────────┘
           │
           └──────────────────────────────────────► Response: $41.50 (Supplier E)
```

---

## 9 — Spring Boot Implementation

---

```java
@Service
@RequiredArgsConstructor
public class PriceScatterGatherService {

    private final List<SupplierClient> supplierClients;  // all supplier adapters
    private final ExecutorService executor = Executors.newFixedThreadPool(20);

    public PriceComparisonResult findBestPrice(String productId) {
        long deadline = 2000L; // gather all responses within 2 seconds

        // SCATTER — send same request to all suppliers in parallel
        List<CompletableFuture<SupplierPrice>> futures = supplierClients.stream()
            .map(client -> CompletableFuture
                .supplyAsync(() -> client.getPrice(productId), executor)
                .orTimeout(deadline, TimeUnit.MILLISECONDS)
                .exceptionally(ex -> {
                    log.warn("Supplier {} timed out or failed", client.getName());
                    return null;   // null = supplier excluded from results
                })
            )
            .collect(toList());

        // GATHER — wait for all (up to deadline)
        CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();

        // PROCESS — filter nulls, find cheapest
        List<SupplierPrice> responses = futures.stream()
            .map(CompletableFuture::join)
            .filter(Objects::nonNull)       // exclude timeouts
            .collect(toList());

        if (responses.isEmpty()) {
            throw new NoSuppliersAvailableException("All suppliers timed out");
        }

        SupplierPrice best = responses.stream()
            .min(Comparator.comparing(SupplierPrice::getAmount))
            .orElseThrow();

        return PriceComparisonResult.builder()
            .bestPrice(best)
            .allResponses(responses)
            .respondedCount(responses.size())
            .totalQueried(supplierClients.size())
            .build();
    }
}
```

### Scatter-Gather for Search (Merge + Rank)

```java
@Service
public class SearchScatterGatherService {

    // Send same search query to multiple sources, merge and rank results
    public SearchResponse search(SearchQuery query) {

        // SCATTER
        CompletableFuture<List<SearchResult>> productsFuture =
            CompletableFuture.supplyAsync(() -> productSearchClient.search(query));

        CompletableFuture<List<SearchResult>> articlesFuture =
            CompletableFuture.supplyAsync(() -> articleSearchClient.search(query));

        CompletableFuture<List<SearchResult>> videosFuture =
            CompletableFuture.supplyAsync(() -> videoSearchClient.search(query))
                .orTimeout(1500, TimeUnit.MILLISECONDS)
                .exceptionally(ex -> emptyList());

        // GATHER + PROCESS — merge and rank by relevance score
        List<SearchResult> merged = Stream.of(
                productsFuture.join(),
                articlesFuture.join(),
                videosFuture.join()
            )
            .flatMap(Collection::stream)
            .sorted(Comparator.comparingDouble(SearchResult::getRelevanceScore).reversed())
            .limit(20)
            .collect(toList());

        return new SearchResponse(merged);
    }
}
```

```
KEY DESIGN DECISIONS in Scatter-Gather:

  1. DEADLINE vs WAIT-FOR-ALL
     ├── Deadline: "respond in 2s with whoever answered"  → price comparison
     └── Wait-for-all: "need all results before processing" → data audit

  2. MISSING RESPONSES
     ├── Exclude: supplier didn't respond → ignore them (price comparison)
     └── Fail: must have all results → error if any missing (compliance audit)

  3. RESULT PROCESSING
     ├── Best-of: cheapest price, highest score
     ├── Merge: combine search results, deduplicate
     └── Quorum: need majority agreement (distributed consensus check)
```

# PATTERN 5: FAILOVER

---

## 10 — What Problem It Solves

---

"Failover is automatic switching from a failed primary to a backup.
When the primary fails — hardware, software, region — the system
detects the failure and routes traffic to a standby, transparently to users.

The key word is AUTOMATIC. Manual failover doesn't count.
If it requires a human to flip a switch at 3am, that's not failover —
that's an incident."

```
FAILOVER types:

  ACTIVE-PASSIVE:
  ┌─────────────────────────────────────────────────────────────┐
  │  Primary (Active)   ◄── all traffic                         │
  │  Secondary (Passive) ── standby, no traffic                 │
  │                                                             │
  │  Primary fails → Secondary promoted → takes all traffic     │
  │  Recovery time: seconds to minutes (depends on detection)   │
  │  Cost: Secondary sits idle (wasted resource)                │
  └─────────────────────────────────────────────────────────────┘

  ACTIVE-ACTIVE:
  ┌─────────────────────────────────────────────────────────────┐
  │  Primary   ◄── 50% traffic                                  │
  │  Secondary ◄── 50% traffic                                  │
  │                                                             │
  │  Primary fails → Secondary takes 100% traffic              │
  │  Recovery time: milliseconds (already warm, already serving)│
  │  Cost: both fully provisioned                               │
  └─────────────────────────────────────────────────────────────┘

  WHICH TO USE:
  Active-Passive → databases (write conflicts unsafe with two primaries)
  Active-Active  → stateless services, read replicas, CDN
```

## 11 — Multi-Layer Failover Architecture on AWS

---

```
AWS MULTI-REGION FAILOVER:

  ┌───────────────────────────────────────────────────────────────┐
  │  Route 53 (DNS Failover)                                      │
  │  ├── Health checks: us-east-1 ALB every 10 seconds            │
  │  ├── Primary:   api.company.com → us-east-1 ALB               │
  │  └── Failover:  api.company.com → eu-west-1 ALB               │
  │      (DNS TTL: 60s — failover detectable in 60-120 seconds)   │
  └──────────────────────┬────────────────────────────────────────┘
           Primary ──────┘
           │
  ┌────────▼──────────────────────────────────────────────────────┐
  │  us-east-1 (Primary Region)                                   │
  │  ├── ALB → ECS Services                                       │
  │  ├── RDS Primary (writer)                                     │
  │  └── ElastiCache Primary                                      │
  └───────────────────────────────────────────────────────────────┘

  Failover region (us-east-1 goes down):
  ┌───────────────────────────────────────────────────────────────┐
  │  eu-west-1 (Failover Region)                                  │
  │  ├── ALB → ECS Services (pre-warmed, scaled)                  │
  │  ├── RDS Read Replica → promoted to writer                    │
  │  └── ElastiCache replica → promoted                           │
  └───────────────────────────────────────────────────────────────┘

  FAILOVER SEQUENCE:
  t=0s   us-east-1 ALB stops responding
  t=10s  Route 53 health check fails (first check)
  t=30s  Route 53 health check fails (third check — threshold)
  t=30s  Route 53 switches DNS to eu-west-1
  t=90s  DNS TTL expires for most clients (60s TTL)
  t=90s  Traffic flowing to eu-west-1
  t=120s RDS read replica promotion complete
  t=120s Full service restored in eu-west-1
```

## 12 — Spring Boot Service-Level Failover

---

"Beyond region-level failover, I implement failover at the service call level.
When Service A calls Service B and B fails, A falls back to Service C or cache."

```java
@Service
@Slf4j
public class InventoryService {

    private final PrimaryInventoryClient  primaryClient;
    private final FallbackInventoryClient fallbackClient;
    private final RedisCache              cache;

    // Failover chain: Primary → Fallback → Cache → Default
    @CircuitBreaker(name = "inventory", fallbackMethod = "inventoryFallback")
    public InventoryStatus checkInventory(String productId) {
        return primaryClient.check(productId);   // try primary first
    }

    // Called when circuit is OPEN or primary throws
    public InventoryStatus inventoryFallback(String productId, Exception ex) {
        log.warn("Primary inventory failed — trying fallback service");

        try {
            return fallbackClient.check(productId);  // try secondary
        } catch (Exception e) {
            log.warn("Fallback inventory also failed — checking cache");

            return cache.get("inventory:" + productId, InventoryStatus.class)
                .orElseGet(() -> {
                    log.warn("No cache — returning default (in-stock assumed)");
                    return InventoryStatus.assumeInStock();  // last resort default
                });
        }
    }
}
```

    │
    ▼

    │  fails
    ▼
  [Fallback Service]
    │  also fails
    ▼

    │  cache miss
    ▼

  Each step has a timeout.
  Never block indefinitely waiting for a dead service.

## 16 — The 60-Second Answer for Each

---

### Ambassador
> "Ambassador is a sidecar proxy that handles cross-cutting concerns — retry,
> circuit breaker, auth, TLS — on behalf of your service. Your service talks
> to localhost, the Ambassador handles the network. Policy changes are
> centralized — no code deployment needed when retry rules change.
> On AWS I use App Mesh with Envoy sidecars in ECS tasks."

### Adapter
> "Adapter makes incompatible interfaces work together by translating between
> your domain model and an external system's model. Your service depends on
> YOUR interface — PaymentGateway.charge(). The Stripe Adapter implements that
> interface and translates internally. Swap Stripe for PayPal — zero changes
> to your business logic, one new adapter class."

### Aggregator
> "Aggregator composes responses from multiple services into a single response.
> Instead of the frontend making 5 calls, the Aggregator makes them in parallel
> — total time is max(all calls), not the sum. Non-critical services degrade
> gracefully with empty responses — the page still loads, just without reviews."

### Scatter-Gather
> "Scatter-Gather sends the same request to multiple service instances simultaneously
> and processes all responses. Classic use: price comparison — send to 10 suppliers
> in parallel, gather within 2 seconds, return the cheapest. Slow suppliers are
> excluded via timeout, not waited on. The processing step — cheapest, merge,
> rank — is the business logic."

### Failover
> "Failover is AUTOMATIC switching to a backup when the primary fails.
> Manual failover doesn't count as a pattern — that's just an incident.
> On AWS I layer it: Route 53 health checks for region-level failover,
> RDS Multi-AZ for database failover, circuit breaker fallback chains
> at the service level. And critically — I test it. A failover never tested
> is a failover that won't work at 3am."
