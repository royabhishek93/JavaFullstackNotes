## Opening — When Interviewer Asks "Tell me about Load Shedding"

---

"Load shedding is something every architect eventually learns the hard way —

Let me walk you through how I think about it — the problem first,
then the layered solution I use in production."

## Part 1 — Setting the Scene (The Problem)

---

"Imagine your payment service is running fine at 500 requests per second.
Black Friday hits. Traffic spikes to 5000 requests per second.

Without load shedding, here's what happens:"

```
CASCADING FAILURE without Load Shedding:

  t=0s   500 rps  ──► [ Payment Service ]  ──► Database  ✓ healthy
                       200 threads available

  t=5s   5000 rps ──► [ Payment Service ]  ──► Database
                       5000 requests queuing
                       Thread pool exhausted
                       DB connection pool exhausted
                       Response times: 30s+

  t=10s  Timeouts everywhere
         Client retries ──► MORE traffic
         System at 10,000 rps now
         JVM heap fills up
         GC pauses → stop-the-world

  t=15s  ┌─────────────────────────────────────────┐
         │   TOTAL OUTAGE — 503 for ALL requests   │
         │   Including your health check endpoint  │
         │   ALB marks ALL instances as unhealthy  │
         │   ZERO requests served                  │
         └─────────────────────────────────────────┘
```

"The system tried to serve everyone — and ended up serving nobody.

With load shedding, here's what should have happened:"

```
CONTROLLED DEGRADATION with Load Shedding:

  t=0s   500 rps  ──► [ Payment Service ]  ──► Database  ✓ healthy

  t=5s   5000 rps incoming
         ├── 1000 rps ACCEPTED ──► processed normally
         └── 4000 rps REJECTED ──► fast 429 response (< 5ms)

  Result:
  ┌─────────────────────────────────────────────────────┐
  │  80% of users: fast error with Retry-After header  │
  │  20% of users: normal successful response          │
  │  System: HEALTHY, threads free, DB not overloaded  │
  └─────────────────────────────────────────────────────┘

  A fast 429 is infinitely better than a 30-second timeout.
  Users can retry. A crashed system can't serve anyone.
```

## Part 2 — Three Different Tools, Three Different Problems

---

"Before I walk through implementation, I want to clarify something
that trips up a lot of engineers — and sometimes interviewers themselves.

Load shedding, rate limiting, and circuit breakers are three different tools.
They're often confused because they all reject requests."

```
┌─────────────────────────────────────────────────────────────────────┐
│  WHAT EACH TOOL PROTECTS                                            │
├──────────────────┬──────────────────────────────────────────────────┤
│  Rate Limiting   │  Protects against a specific USER/CLIENT         │
│                  │  sending too many requests                       │
│                  │  "User123 gets 100 req/min"                      │
├──────────────────┼──────────────────────────────────────────────────┤
│  Load Shedding   │  Protects the SYSTEM when total load is          │
│                  │  beyond its capacity — regardless of who sends   │
│                  │  "My service CPU is at 90% — reject everyone"    │
├──────────────────┼──────────────────────────────────────────────────┤
│  Circuit Breaker │  Protects a DOWNSTREAM service from being        │
│                  │  hammered when it's already failing              │
│                  │  "Stripe is down — stop calling Stripe"          │
└──────────────────┴──────────────────────────────────────────────────┘

You need all three. They solve different problems at different layers.
```

## Part 3 — The Layered Architecture I Use in Production

---

"I always implement load shedding in layers — each layer handles a different
kind of overload. No single layer can handle everything."

```
REQUEST FLOW through layers:

  Internet
      │
      ▼
  ┌───────────────────────────────────────────────────────────┐
  │  Layer 1: AWS WAF                                         │
  │  ├── DDoS protection                                      │
  │  ├── IP-based rate limits (2000 req / 5 min per IP)       │
  │  └── Blocks malicious patterns before they hit your app   │
  └───────────────────────┬───────────────────────────────────┘
                          │ (legitimate traffic passes)
  ┌───────────────────────▼───────────────────────────────────┐
  │  Layer 2: API Gateway / ALB                               │
  │  ├── Burst limit: 500 concurrent requests                 │
  │  ├── Sustained limit: 1000 req/sec                        │
  │  └── Per-route throttling for expensive endpoints         │
  └───────────────────────┬───────────────────────────────────┘
                          │ (within burst/rate limits)
  ┌───────────────────────▼───────────────────────────────────┐
  │  Layer 3: Spring Cloud Gateway                            │
  │  ├── Per-user rate limiting (Redis token bucket)          │
  │  ├── Per-route configuration                              │
  │  └── Returns 429 with Retry-After header                  │
  └───────────────────────┬───────────────────────────────────┘
                          │ (within per-user limits)
  ┌───────────────────────▼───────────────────────────────────┐
  │  Layer 4: Resilience4j inside each Microservice           │
  │  ├── Bulkhead: isolate thread pools per operation         │
  │  ├── Rate Limiter: per-instance cap                       │
  │  └── Circuit Breaker: protect downstream services         │
  └───────────────────────┬───────────────────────────────────┘
                          │ (critical paths only)
  ┌───────────────────────▼───────────────────────────────────┐
  │  Layer 5: SQS Queue (async flows)                         │
  │  ├── Absorb traffic spikes completely                     │
  │  ├── Decouple ingestion from processing                   │
  │  └── Consumer processes at controlled rate                │
  └───────────────────────────────────────────────────────────┘
```

## Part 4 — Layer 1: AWS WAF

---

"WAF is your outermost shield. It operates before traffic even reaches
your application load balancer. The key thing here is DDoS absorption
and IP-based rate limiting.

I always set this up — even for internal services — because it's
managed by AWS and costs almost nothing compared to an outage."

```
AWS WAF RULE — Rate limit by IP:

  Rule: RateLimitPerIP
  ├── Condition: any request
  ├── Aggregate: by SOURCE IP address
  ├── Limit: 2000 requests per 5-minute window
  └── Action: BLOCK (returns 403)

  Why 5 minutes?
  ┌──────────────────────────────────────────────────────────┐
  │  A legitimate user hitting your API at 1 req/sec         │
  │  = 300 requests in 5 minutes — well under 2000           │
  │                                                          │
  │  A bot hammering your API at 100 req/sec                 │
  │  = 30,000 requests in 5 minutes — blocked               │
  └──────────────────────────────────────────────────────────┘

  Always add AWS Managed Rules on top:
  ├── AWSManagedRulesCommonRuleSet  (SQL injection, XSS)
  └── AWSManagedRulesKnownBadInputsRuleSet
```

## Part 5 — Layer 2: API Gateway Throttling

---

"API Gateway has two throttling concepts that are easy to confuse —
burst limit and rate limit. Understanding both is important."

```
TOKEN BUCKET algorithm — how API Gateway throttles:

  Bucket capacity: 500 tokens  (burst limit)
  Refill rate:     1000 tokens/second  (rate limit)

  Scenario 1: Sudden spike
  ┌────────────────────────────────────────────────────────┐
  │  t=0s  Bucket: [500 tokens full]                       │
  │  t=0s  800 requests arrive simultaneously              │
  │        500 served (bucket emptied)                     │
  │        300 rejected with 429                           │
  │  t=1s  Bucket refills: +1000 tokens                    │
  │  t=1s  Next 1000 requests can be served                │
  └────────────────────────────────────────────────────────┘

  Scenario 2: Sustained overload
  ┌────────────────────────────────────────────────────────┐
  │  5000 rps sustained                                    │
  │  1000 rps served (rate limit)                          │
  │  4000 rps rejected with 429                            │
  │  System CPU stays healthy                              │
  └────────────────────────────────────────────────────────┘

  Per-route tightening for expensive endpoints:
  ┌────────────────────────────────────────────────────────┐
  │  /api/payment/process   → burst: 50,  rate: 100 rps   │
  │  /api/reports/generate  → burst: 10,  rate: 20 rps    │
  │  /api/products          → burst: 500, rate: 1000 rps  │
  │  /health                → burst: 1000 (never throttle)│
  └────────────────────────────────────────────────────────┘
```

## Part 6 — Layer 3: Spring Cloud Gateway + Redis Rate Limiter

---

"Spring Cloud Gateway is where I implement per-user, per-route business logic.
The key here is the Redis token bucket — it's distributed, so it works
across all gateway instances. A user can't bypass the limit by hitting a
different gateway pod."

```
SPRING CLOUD GATEWAY rate limiting flow:

  User A (userId=123) ──► Gateway Pod 1 ──► Redis checks bucket for user:123
  User A (userId=123) ──► Gateway Pod 2 ──► Redis checks bucket for user:123
                                             (same bucket! distributed ✓)

  Without Redis:
  ┌──────────────────────────────────────────────────────┐
  │  Gateway Pod 1: User A used 90/100 requests          │
  │  Gateway Pod 2: User A used 0/100 requests (!)       │
  │  User A can hit 200 requests by using both pods      │
  └──────────────────────────────────────────────────────┘

  With Redis (shared state):
  ┌──────────────────────────────────────────────────────┐
  │  Redis key: rate_limiter.user:123.tokens = 10        │
  │  All gateway pods read/write the same counter        │
  │  User A is correctly limited to 100 across all pods  │
  └──────────────────────────────────────────────────────┘
```

```yaml
# application.yml — Spring Cloud Gateway
spring:
  cloud:
    gateway:
      routes:
        - id: payment-service
          uri: lb://payment-service
          predicates:
            - Path=/api/payment/**
          filters:
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 100     # tokens/sec refill
                redis-rate-limiter.burstCapacity: 200     # max bucket size
                redis-rate-limiter.requestedTokens: 1
                key-resolver: "#{@userKeyResolver}"
```

```java
@Configuration
public class RateLimiterConfig {

    // Limit per authenticated user
    @Bean
    public KeyResolver userKeyResolver() {
        return exchange -> Mono.justOrEmpty(
            exchange.getRequest().getHeaders().getFirst("X-User-Id")
        ).defaultIfEmpty("anonymous");
    }
}
```

```
RESPONSE when rate limit hit:

  HTTP 429 Too Many Requests
  Headers:
    X-RateLimit-Remaining: 0
    X-RateLimit-Replenish-Rate: 100
    X-RateLimit-Burst-Capacity: 200
    Retry-After: 1

  Always return Retry-After. It tells the client when to retry,
  preventing immediate retry storms that make the problem worse.
```

## Part 7 — Layer 4A: Bulkhead Pattern (Thread Pool Isolation)

---

"Bulkhead is named after the watertight compartments in a ship.
If one compartment floods, the others stay dry. Same idea.

This is the pattern I care about most in production because it
prevents one slow endpoint from killing the entire service."

```
WITHOUT Bulkhead — a slow endpoint kills everything:

  Tomcat shared thread pool: 200 threads

  ┌─────────────────────────────────────────────────────────┐
  │  /api/payment/process    ████████████████████ 180 threads│
  │  (slow Stripe API call,                                  │
  │   5 seconds each)                                        │
  │                                                          │
  │  /api/account/balance    ██ 15 threads                   │
  │                                                          │
  │  /health                 █ 5 threads (barely!)           │
  └─────────────────────────────────────────────────────────┘

  Result: Payment slowness → ALL threads busy → health check
          times out → ALB marks service DOWN → full outage
          (even though account balance endpoint is perfectly fine)


WITH Bulkhead — failure is contained:

  ┌──────────────────────┐  ┌──────────────────────┐
  │ Payment thread pool  │  │ Account thread pool  │
  │ Max: 50 threads      │  │ Max: 30 threads      │
  │ ████████████████████ │  │ ████ healthy         │
  │ FULL — rejecting     │  │                      │
  └──────────────────────┘  └──────────────────────┘
  ┌──────────────────────┐
  │ Health thread pool   │
  │ Max: 10 threads      │
  │ █ always responds    │  ← ALB sees healthy ✓
  └──────────────────────┘

  Payment is overloaded? Payment callers get 503.
  Health check? Always responds. ALB keeps routing to this instance.
  Account balance? Still works perfectly.
```

```yaml
# application.yml
resilience4j:
  bulkhead:
    instances:
      paymentProcessor:
        maxConcurrentCalls: 50       # max 50 simultaneous payment calls
        maxWaitDuration: 10ms        # wait 10ms for a free slot, then reject
      accountService:
        maxConcurrentCalls: 30
        maxWaitDuration: 5ms
```

```java
@Service
public class PaymentService {

    @Bulkhead(name = "paymentProcessor", fallbackMethod = "bulkheadFallback")
    public PaymentResponse processPayment(PaymentRequest request) {
        return stripeClient.charge(request);  // slow external call
    }

    // Called when all 50 slots are full
    public PaymentResponse bulkheadFallback(PaymentRequest req,
                                             BulkheadFullException ex) {
        throw new ResponseStatusException(
            HttpStatus.SERVICE_UNAVAILABLE,
            "Payment processing at capacity. Please retry in a moment."
        );
    }
}
```

## Part 8 — Layer 4B: Circuit Breaker (Protect Downstream)

---

"The circuit breaker is specifically about protecting external dependencies —
Stripe, a third-party API, another microservice. When that downstream
service starts failing, you want to stop hammering it immediately.

Two reasons: one, you protect the downstream from getting worse.
Two, you protect yourself from threads piling up waiting for timeouts."

```
CIRCUIT BREAKER state machine:

  ┌─────────────────────────────────────────────────────────────┐
  │                                                             │
  │   CLOSED ──────────────────────────────────────────────►   │
  │   (normal)    50% failure rate                  OPEN       │
  │               in last 10 calls                  (shedding) │
  │                                                    │        │
  │                                        30 second   │        │
  │                                        wait        │        │
  │                                                    ▼        │
  │   CLOSED ◄────────────── 5/5 success ──── HALF-OPEN        │
  │   (recovered)            test calls       (probing)         │
  │                                                             │
  │              any failure ─────────────────► OPEN again     │
  └─────────────────────────────────────────────────────────────┘

  CLOSED state: All requests pass through, failures tracked
  OPEN state:   Requests IMMEDIATELY return fallback (no call made)
  HALF-OPEN:    5 test requests allowed through to check recovery
```

```
TIMELINE example — Stripe goes down:

  t=0s   Normal operation — all calls succeed
  t=10s  Stripe starts failing — 5/10 calls fail (50%)
  t=11s  CIRCUIT OPENS
         ├── No more calls to Stripe
         ├── All requests get fallback immediately
         └── Stripe gets a chance to recover (no more load from us)
  t=41s  HALF-OPEN — 5 test calls allowed
  t=42s  All 5 succeed — CIRCUIT CLOSES
  t=42s  Normal operation resumes

  Without circuit breaker:
  t=10s  Failures start
  t=11s  Still calling Stripe (threads waiting 30s timeout each)
  t=12s  Thread pool fills with waiting threads
  t=13s  Our service is now also down (collateral damage)
```

```yaml
resilience4j:
  circuitbreaker:
    instances:
      stripeGateway:
        slidingWindowSize: 10
        failureRateThreshold: 50           # open at 50% failure rate
        waitDurationInOpenState: 30s
        permittedNumberOfCallsInHalfOpenState: 5
        slowCallDurationThreshold: 3s      # 3s+ = treated as failure
        slowCallRateThreshold: 80          # open if 80% of calls are slow
```

```java
@Service
public class StripePaymentClient {

    @CircuitBreaker(name = "stripeGateway", fallbackMethod = "paymentFallback")
    @Retry(name = "stripeGateway")           // retry before circuit opens
    @TimeLimiter(name = "stripeGateway")     // 3s timeout per call
    public CompletableFuture<PaymentResponse> charge(PaymentRequest request) {
        return CompletableFuture.supplyAsync(() -> stripeApi.charge(request));
    }

    // Circuit is OPEN — return graceful fallback
    public CompletableFuture<PaymentResponse> paymentFallback(
            PaymentRequest request, Exception ex) {
        // Queue for retry when circuit closes
        retryQueue.enqueue(request);
        return CompletableFuture.completedFuture(
            PaymentResponse.pending(request.getId(),
                "Payment queued — will process shortly")
        );
    }
}
```

## Part 9 — Layer 5: SQS Queue-Based Load Leveling

---

"This is my favorite pattern for handling spikes — and it's the one
most teams don't reach for early enough.

The idea is simple: decouple how fast you accept requests from
how fast you process them. A queue is a shock absorber."

```
SYNCHRONOUS — breaks under traffic spikes:

  ┌──────────┐         ┌───────────────┐         ┌──────────┐
  │  Users   │──1000rps──► Payment API  │──1000rps──► Database │
  └──────────┘         └───────────────┘         └──────────┘
                              OVERLOADED              OVERLOADED
                              (threads exhausted)     (connections exhausted)


QUEUE-BASED LOAD LEVELING — absorbs any spike:

  ┌──────────┐         ┌─────────────┐    ┌────────────┐    ┌──────────┐
  │  Users   │──1000rps──► API Layer  │───►│  SQS Queue │───►│ Consumer │──► DB
  └──────────┘         └─────────────┘    └────────────┘    └──────────┘
              accepts all       202 Accepted  buffers spike    100 rps
              immediately       returned                       controlled

  Spike of 10,000 rps hits:
  ┌────────────────────────────────────────────────────────────┐
  │  API accepts all 10,000 → puts into SQS immediately        │
  │  Returns 202 Accepted + tracking ID to every caller        │
  │  Consumer drains queue at 100 rps (database stays healthy) │
  │  Queue depth: 10,000 → 9,900 → 9,800 → ... → 0            │
  │  All payments eventually processed. Zero data loss.        │
  └────────────────────────────────────────────────────────────┘

  The user gets a fast 202 response, not a 503.
  You can send a push notification / email when done.
```

```java
// Controller — accepts immediately
@PostMapping("/payment/process")
public ResponseEntity<Map<String, String>> submitPayment(
        @RequestBody PaymentRequest request) {

    String messageId = sqsTemplate.send(builder -> builder
        .queue("payment-processing.fifo")
        .payload(request)
        .messageGroupId("user-" + request.getUserId())   // FIFO per user
        .messageDeduplicationId(request.getIdempotencyKey()) // no duplicates
    );

    return ResponseEntity.accepted().body(Map.of(
        "status",     "ACCEPTED",
        "trackingId", messageId,
        "message",    "Your payment is being processed"
    ));
}

// Consumer — controlled drain rate
@SqsListener(value = "payment-processing.fifo",
             acknowledgementMode = SqsAcknowledgementMode.ON_SUCCESS)
public void processPayment(PaymentRequest request) {
    PaymentResponse result = stripeClient.charge(request);
    notificationService.notify(request.getUserId(), result);
    // message auto-acked on success, re-queued on exception
}
```

```yaml
spring:
  cloud:
    aws:
      sqs:
        listener:
          max-concurrent-messages: 10      # process 10 at a time
          max-messages-per-poll: 10        # fetch 10 per SQS poll
          # = controlled 10 rps through to database
```

## Part 10 — Adaptive Load Shedding (CPU/Memory Based)

---

"The final layer is adaptive — the service monitors its own health
and starts shedding when it detects it's getting overloaded.
This is your emergency brake."

```
ADAPTIVE SHEDDING logic:

  Every request:
  ┌────────────────────────────────────────────────────────┐
  │  Check CPU load                                        │
  │  ├── CPU < 70%  → pass all requests through            │
  │  ├── CPU 70-90% → start shedding low-priority requests │
  │  └── CPU > 90%  → shed everything except /health       │
  └────────────────────────────────────────────────────────┘

  Request priority tiers:
  ┌──────────────────┬────────────────────────────────────┐
  │  CRITICAL (never shed)  │ /health, /payment/process   │
  │  NORMAL (shed at 90%)   │ /account/update, /orders    │
  │  LOW (shed at 70%)      │ /reports, /search, /export  │
  └──────────────────┴────────────────────────────────────┘
```

```java
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class AdaptiveLoadSheddingFilter implements Filter {

    private final OperatingSystemMXBean osMXBean =
        (OperatingSystemMXBean) ManagementFactory.getOperatingSystemMXBean();

    @Override
    public void doFilter(ServletRequest req, ServletResponse res,
                         FilterChain chain) throws IOException, ServletException {

        double cpu = osMXBean.getCpuLoad();
        HttpServletRequest httpReq = (HttpServletRequest) req;
        String uri = httpReq.getRequestURI();

        if (cpu > 0.90 && !isCritical(uri)) {
            shed((HttpServletResponse) res, "System under heavy load");
            return;
        }

        if (cpu > 0.70 && isLowPriority(uri)) {
            shed((HttpServletResponse) res, "Non-critical requests temporarily paused");
            return;
        }

        chain.doFilter(req, res);
    }

    private void shed(HttpServletResponse res, String msg) throws IOException {
        res.setStatus(503);
        res.setHeader("Retry-After", "5");
        res.setContentType("application/json");
        res.getWriter().write("{\"error\":\"" + msg + "\",\"retryAfter\":5}");
    }

    private boolean isCritical(String uri) {
        return uri.startsWith("/health") ||
               uri.startsWith("/actuator") ||
               uri.startsWith("/payment/process");
    }

    private boolean isLowPriority(String uri) {
        return uri.startsWith("/reports") ||
               uri.startsWith("/export") ||
               uri.startsWith("/search");
    }
}
```

## Part 11 — Observability (What I Add in Every Production System)

---

"This is the part junior engineers skip and then can't debug the incident.
I always add three things: request rejection metrics, system health gauges,
and a 'no-leader / overload' alert."

```
METRICS TO TRACK:

  load.shed.count        ← how many requests were shed (by reason)
  load.shed.rate         ← shedding rate over time (spike indicator)
  system.cpu.usage       ← correlated with shedding events
  bulkhead.available     ← how full your thread pool isolation is
  circuitbreaker.state   ← CLOSED=0 / OPEN=1 / HALF_OPEN=2
  sqs.queue.depth        ← backlog building up?

CLOUDWATCH DASHBOARD layout:

  ┌─────────────────────┬─────────────────────┬──────────────────────┐
  │  Request Rate       │  Rejection Rate     │  Circuit Breaker     │
  │  ────────────────   │  ────────────────   │  State per service   │
  │  ██████████████     │  ░░░░░░▓▓▓▓▓░░░░   │  Stripe:  CLOSED ✓  │
  │  normal load        │  spike visible      │  Orders:  OPEN  ✗   │
  └─────────────────────┴─────────────────────┴──────────────────────┘
  ┌─────────────────────┬─────────────────────┬──────────────────────┐
  │  CPU Usage          │  SQS Queue Depth    │  Bulkhead Available  │
  │  ────────────────   │  ────────────────   │  Payment: 45/50 full │
  │  70%──────▶90%      │  0──▶5000──▶0       │  Account: 10/30 full │
  └─────────────────────┴─────────────────────┴──────────────────────┘

CRITICAL ALERTS:

  1. load.shed.rate > 20% for 2 minutes
     → "Sustained load shedding — investigate capacity"

  2. circuitbreaker.state{service="stripe"} == 1 (OPEN)
     → "Stripe circuit open — payments falling back to queue"

  3. sqs.queue.depth > 10,000
     → "Payment queue backing up — scale consumers or alert ops"
```

```java
@Component
@RequiredArgsConstructor
public class LoadSheddingMetrics {

    private final MeterRegistry registry;

    public void recordShed(String reason, String endpoint) {
        registry.counter("load.shed.count",
            "reason",   reason,
            "endpoint", endpoint
        ).increment();
    }

    @Scheduled(fixedDelay = 5000)
    public void recordSystemMetrics() {
        double cpu = osMXBean.getCpuLoad();
        registry.gauge("system.cpu.usage", cpu);
    }
}
```

## Part 12 — Failure Scenarios I've Seen in Production

---

"A good interviewer will push on edge cases. Here's every failure mode
and how the layered approach handles each one."

```
┌───────────────────────────────┬──────────────────────────────────────────┐
│  Scenario                     │  How Handled                             │
├───────────────────────────────┼──────────────────────────────────────────┤
│  Sudden 10x traffic spike     │  WAF + API GW absorbs first wave         │
│                               │  Gateway rate limits per user            │
│                               │  SQS queues overflow for async paths     │
├───────────────────────────────┼──────────────────────────────────────────┤
│  Downstream API (Stripe) slow │  Bulkhead limits waiting threads         │
│                               │  Circuit breaker opens after 50% failure │
│                               │  Fallback queues for retry               │
├───────────────────────────────┼──────────────────────────────────────────┤
│  Database overloaded          │  SQS queue absorbs ingestion             │
│                               │  Consumer rate limits DB calls           │
│                               │  Connection pool bulkheaded              │
├───────────────────────────────┼──────────────────────────────────────────┤
│  One endpoint is memory leak  │  Bulkhead isolates its thread pool       │
│                               │  Other endpoints unaffected              │
│                               │  Health check still responds (ALB ok)    │
├───────────────────────────────┼──────────────────────────────────────────┤
│  Redis (rate limiter) down    │  Gateway fails OPEN (allows traffic)     │
│                               │  Adaptive CPU filter kicks in instead    │
│                               │  Don't fail CLOSED — that's worse        │
├───────────────────────────────┼──────────────────────────────────────────┤
│  Retry storm after outage     │  Exponential backoff in client           │
│                               │  Retry-After header tells clients when   │
│                               │  Circuit breaker half-open limits probe  │
└───────────────────────────────┴──────────────────────────────────────────┘
```

## Part 13 — The 60-Second Interview Answer

---

"If I had to summarize load shedding in 60 seconds, here's exactly what I'd say:"

---

> "Load shedding is about intentionally rejecting requests to protect the system
> under overload — unlike rate limiting which is per-client, load shedding is
> system-wide based on system health.
>
> I implement it in five layers.
>
> AWS WAF at the edge handles DDoS and IP-based abuse before anything hits my app.
> API Gateway throttles with a token bucket — burst and sustained limits per route.
> Spring Cloud Gateway adds per-user, per-route rate limiting backed by Redis so
> it works correctly across all gateway instances.
> Inside each microservice, Resilience4j handles bulkheads to isolate thread pools —
> so one slow endpoint can't take down the whole service — and circuit breakers to
> stop calling failing downstream services immediately.
> For async flows like payments and notifications, I put SQS in front —
> decouple ingestion from processing entirely. A spike of 10,000 requests
> becomes a controlled drain of 100 per second. Every caller gets a fast 202,
> not a 503.
>
> The core insight is: a fast 429 or 202 is infinitely better than a 30-second
> timeout followed by total system collapse. Controlled degradation always beats
> uncontrolled outage."
