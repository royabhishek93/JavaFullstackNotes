# Distributed Tracing & Observability — Architect Interview Script

> **Interview Frequency:** 72% | **Difficulty:** ⭐⭐⭐⭐ | **Study Time:** 12 minutes

---

## Opening — When Interviewer Asks "How Do You Debug a Slow Request Across 6 Services?"

"This is one of my favorite questions because it separates people who've only run a
monolith from people who've operated microservices in production. Let me set the scene."

---

## Part 1 — The Problem (One Request, Many Services, No Idea Where It's Slow)

"A customer complains: 'checkout took 4 seconds.' In a monolith, you'd check one log
file. In microservices, that single checkout request touched 6 services."

```
Customer request: POST /checkout

  API Gateway ──► OrderService ──► InventoryService ──► PaymentService
                        │                                     │
                        └──► PricingService            FraudCheckService

  Total latency: 4000ms.  Which of these 6 services is the bottleneck?
  Each service has its OWN log file, on its OWN pod, with NO shared request ID.
  You cannot answer this question with logs alone.
```

"This is exactly the gap that **observability** — logs, metrics, and traces working
together — is designed to close."

---

## Part 2 — The Three Pillars

```
┌─────────────┬────────────────────────────────┬─────────────────────────────┐
│  Pillar      │  Answers                       │  Tooling                    │
├─────────────┼────────────────────────────────┼─────────────────────────────┤
│  Logs        │ "What exactly happened?"       │ ELK / Loki / CloudWatch Logs│
│  Metrics     │ "How much / how often / is it  │ Prometheus + Grafana,       │
│              │  degrading over time?"         │ CloudWatch Metrics          │
│  Traces      │ "Where in the call chain did   │ Jaeger, Zipkin, AWS X-Ray,  │
│              │  the time go?"                 │ Tempo, Datadog APM          │
└─────────────┴────────────────────────────────┴─────────────────────────────┘

  Metrics tell you something is wrong (p99 latency spiked).
  Traces tell you WHERE it went wrong (PaymentService's DB call).
  Logs tell you WHY it went wrong (connection pool exhausted, query timeout).

  You need all three. Metrics alone can't pinpoint a service.
  Logs alone can't show the end-to-end path. Traces tie it all together.
```

---

## Part 3 — Anatomy of a Trace

"A trace is just a tree of timed operations, called spans, all sharing one trace ID."

```
TRACE ID: 7f3a9c2e (one checkout request)

  Span: API Gateway            [0ms ───────────────────────────── 4000ms]
    └─ Span: OrderService       [50ms ──────────────────────── 3900ms]
         ├─ Span: PricingService        [100ms ── 250ms]        (150ms)
         ├─ Span: InventoryService      [260ms ── 400ms]        (140ms)
         └─ Span: PaymentService        [410ms ─────────────── 3850ms]  ← 3.4s here!
              └─ Span: DB query (charge)   [420ms ── 3840ms]    ← THE bottleneck

  Each span has: span ID, parent span ID, service name, operation name,
  start time, duration, and tags (http.status, error=true/false, db.statement).
```

"Now the answer is obvious — PaymentService's database call is eating 3.4 seconds.
Without tracing, you'd be grepping six log files hoping to spot the pattern."

---

## Part 4 — Context Propagation (The Part People Get Wrong)

"The trace only stays connected if the trace ID is passed forward on every hop —
HTTP headers for synchronous calls, message headers for async/Kafka."

```
SYNCHRONOUS (HTTP) — W3C Trace Context header:

  OrderService ──► PaymentService
  Header: traceparent: 00-7f3a9c2e...-b7d1f2a3...-01
                        │              │
                     trace ID       parent span ID

  PaymentService reads this header, creates a CHILD span with the same trace ID.
  If it doesn't propagate the header, PaymentService starts a NEW disconnected trace.
  ⚠ This is the #1 real-world tracing bug: async HTTP clients or manual RestTemplate
  calls that don't carry the header forward.


ASYNCHRONOUS (Kafka) — trace ID goes in message headers, not the payload:

  OrderService ──► produce("order-placed", headers={traceparent: 00-7f3a9c2e...})
                                    │
                                    ▼
                        PaymentService consumer reads headers,
                        continues the SAME trace as a new span,
                        even though it happened seconds later, in a different process.
```

## Part 5 — OpenTelemetry Architecture (What I Actually Deploy)

"OpenTelemetry (OTel) is the vendor-neutral standard now — I don't hand-roll tracing
per vendor anymore."

```
  ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
  │ OrderService│   │PaymentService│  │InventoryServ│
  │ + OTel SDK  │   │ + OTel SDK   │  │ + OTel SDK  │
  └──────┬──────┘   └──────┬──────┘   └──────┬──────┘
         │  spans exported   │                 │
         └─────────┬─────────┴─────────────────┘
                    ▼
         ┌────────────────────────┐
         │  OTel Collector         │  ← receives, batches, samples, routes
         │  (sidecar or gateway)   │
         └───────────┬────────────┘
                      │
        ┌─────────────┼──────────────┐
        ▼             ▼              ▼
     Jaeger      Prometheus       CloudWatch
   (traces)      (metrics)      (logs/metrics)
```

"The Collector matters because it decouples 'how apps emit telemetry' from 'where it
ends up' — I can switch from Jaeger to Tempo without touching application code."

### Spring Boot Example (Micrometer Tracing + OTel)

```java
// build.gradle
implementation 'io.micrometer:micrometer-tracing-bridge-otel'
implementation 'io.opentelemetry:opentelemetry-exporter-otlp'

// application.yml
management:
  tracing:
    sampling:
      probability: 0.1   // sample 10% of requests, see sampling section below
  otlp:
    tracing:
      endpoint: http://otel-collector:4318/v1/traces

// Correlation ID automatically injected into every log line:
// 2026-08-31 10:15:02 [traceId=7f3a9c2e,spanId=b7d1f2a3] Processing payment...

// Manual span for a custom operation (rarely needed, auto-instrumentation covers most):
@Autowired Tracer tracer;

Span span = tracer.nextSpan().name("fraud-check").start();
try (Tracer.SpanInScope ws = tracer.withSpan(span)) {
    fraudService.check(order);
} finally {
    span.end();
}
```

## Part 6 — Sampling (You Cannot Trace Every Request at Scale)

```
HEAD-BASED SAMPLING (decide at the START of the request):
  - Cheapest: flip a coin (e.g., 10%) at the entry point, propagate the decision downstream.
  - Risk: a rare, important error might just not get sampled ("bad luck").

TAIL-BASED SAMPLING (decide at the END, after seeing the whole trace):
  - Collector buffers all spans for a trace, then decides:
      "keep 100% of traces with errors or latency > 1s, keep 1% of normal ones."
  - Needs more memory/buffering in the Collector, but never misses the interesting cases.

  Rule of thumb I use in production:
  - Head-based 5-10% baseline for cost control.
  - ALWAYS keep 100% of traces where http.status >= 500 or latency > SLA (tail-based rule).
```

## Common Pitfalls

```
❌ Pitfall 1: Trace context not propagated across a Kafka hop
   → trace silently "breaks" into two disconnected traces; nobody notices until
     they try to debug a real incident and can't follow the chain.

❌ Pitfall 2: Sampling 100% of traffic "to be safe"
   → tracing backend storage costs and Collector CPU explode at scale.

❌ Pitfall 3: Adding trace ID to logs but not correlating dashboards to it
   → engineers still grep logs manually instead of clicking from a trace into the logs.

❌ Pitfall 4: No clock sync (NTP) across hosts
   → span timestamps drift, trace timelines look impossible (child starts before parent).

❌ Pitfall 5: Treating tracing as "nice to have" and adding it after an incident
   → you need it BEFORE the incident to actually debug the incident.
```

---

## 🛑 When to Invest Less in Tracing

- ✅ Single-service / monolith with good structured logging → traces add less value.
- ✅ Very low traffic internal tools → simpler correlation-ID-in-logs may suffice.
- ❌ Don't skip metrics + alerting even if you skip tracing — SLO breach detection
  matters more than root-cause tooling when you're just starting out.

## TRAP QUESTIONS

---

### TRAP-1 — "Isn't a correlation ID in your logs basically the same as distributed tracing?"

> **You say:**
>
> "A correlation ID gets you grep-ability across services — you can find every log
> line for one request. But it doesn't give you timing, parent-child relationships,
> or a visual waterfall of where time was spent. Tracing is a superset: a trace ID
> is essentially a structured correlation ID, plus spans that record duration and
> hierarchy, so you can see PaymentService's DB call took 3.4s out of a 4s total,
> not just that all these log lines belong together."

---

### TRAP-2 — "Won't adding tracing to every request hurt performance?"

> **You say:**
>
> "Span creation itself is cheap — microseconds — the real cost is exporting and
> storing every trace, which is why we sample. I use head-based sampling around
> 5-10% for baseline traffic, combined with a tail-based rule that always keeps
> traces with errors or SLA-breaching latency. That keeps overhead low while
> guaranteeing we never miss the traces that actually matter."

---

### TRAP-3 — "Two services show different total durations for the same trace. Why?"

> **You say:**
>
> "Almost always clock skew between hosts — if NTP isn't properly synced, one host's
> clock can be tens of milliseconds off, which shows up as impossible span overlaps.
> The fix is enforcing NTP/chrony sync across all nodes, and some tracing backends
> also do skew correction heuristics, but the root fix is clock hygiene."

---

### TRAP-4 — "How do you avoid vendor lock-in with your tracing setup?"

> **You say:**
>
> "By instrumenting with OpenTelemetry instead of a vendor SDK directly. The OTel
> Collector receives spans/metrics in a vendor-neutral format and can export to
> Jaeger, Tempo, Datadog, or CloudWatch — I can change the backend by changing
> Collector config, without touching a single line of application code."

---

### TRAP-5 — "A trace shows PaymentService took 3.4 seconds, but PaymentService's own metrics show p99 latency of 200ms. What's going on?"

> **You say:**
>
> "That's usually queueing time being misattributed, or a specific slow dependency
> hidden inside an otherwise fast p99. I'd look at the span tags — is this a retry?
> Is there a lock wait? Is the DB span itself 3.4s, meaning it's a slow *query*, not
> slow PaymentService code? p99 is an aggregate — a single trace can absolutely be
> a tail-latency outlier that the aggregate metric smooths over, which is exactly
> why traces and metrics are complementary, not redundant."

---

## Interview Answer (60-Second Summary)

> "Observability rests on three pillars — logs, metrics, and traces. Metrics tell you
> something is wrong, like a p99 latency spike; traces tell you where in the call
> chain it happened; logs tell you why. In microservices, a single request touches
> multiple services, so I rely on a shared trace ID propagated via the W3C
> traceparent header over HTTP, and via message headers over Kafka, so every hop's
> span links into one end-to-end trace. I instrument with OpenTelemetry so I'm not
> locked into one vendor, ship spans through an OTel Collector, and use head-based
> sampling for cost control combined with a tail-based rule that always retains
> error and SLA-breaching traces. The single most common failure I watch for is a
> broken trace — usually an async hop, like Kafka, where context propagation was
> forgotten."

## Quick Reference Card

```
CONCEPT              PURPOSE                          TOOLING EXAMPLES
──────────────────────────────────────────────────────────────────────────
Trace ID              Ties all spans of 1 request      W3C Trace Context (traceparent)
Span                   One timed operation              OTel SDK auto-instrumentation
Head-based sampling    Cheap, decided upfront           OTel SDK sampler config
Tail-based sampling    Never miss errors/slow traces    OTel Collector tail_sampling
Metrics                Aggregate health/alerts          Prometheus, Micrometer, CloudWatch
Logs + correlation ID  Detailed "why" per request       ELK, Loki, structured JSON logs
Collector              Vendor-neutral routing layer     OpenTelemetry Collector
Backends               Storage + visualization          Jaeger, Tempo, Zipkin, X-Ray, Datadog
```
