# Configuration Management (Spring Cloud Config / Consul / Vault) — Interview Script (15 Years Experience)

> Speak naturally. Pause at diagrams. Show confidence, not textbook recitation.
> Complements [26.authn-authz-security-architect-interview.md](26.authn-authz-security-architect-interview.md)'s secrets-management section —
> that file covers WHY secrets shouldn't be static; this file covers the actual
> tools and patterns for externalized configuration in general, secrets included.

---

## Opening — When Interviewer Asks "How Do You Manage Configuration Across Dozens of Microservices?"

---

"The naive approach — config baked into each service's properties file, redeployed
to change a value — doesn't scale past a handful of services, and it's actively
dangerous for secrets (they end up in git history, in built container images). The
mature answer separates THREE concerns: non-secret config, secrets, and service
discovery/coordination data — each has a tool built for it, and conflating them
is a common mistake."

---

## Part 1 — The Twelve-Factor Principle Underneath All of This

---

```
THE CORE RULE (from the Twelve-Factor App methodology):

  Configuration that VARIES between environments (dev/staging/prod) —
  database URLs, feature flags, API endpoints, credentials — must be
  externalized from the code/artifact, NOT baked into it.

  WHY: the exact same built artifact (JAR, container image) should be
  deployable to any environment unchanged — if you rebuild a different
  JAR per environment because config is hardcoded, you've broken the
  guarantee that what you tested in staging is bit-for-bit what runs
  in production.
```

## Part 2 — Spring Cloud Config: Centralized Non-Secret Configuration

---

```
SPRING CLOUD CONFIG FLOW:

  Git repo (config-repo):
    order-service.yml
    order-service-prod.yml
    payment-service.yml
    application.yml   (shared defaults across all services)

       │
       ▼
  Config Server ◄── reads from git, exposes as an HTTP API
       │
       ▼
  Order Service (on startup) ──GET /order-service/prod──► Config Server
                              ◄── merged config for this service+profile──│

  BENEFIT: config changes are just a git commit — reviewable, versioned,
  auditable, rollback-able via git revert, without rebuilding the app's
  artifact at all.

  DYNAMIC REFRESH (without restarting the service):
  Config Server + Spring Cloud Bus (backed by Kafka/RabbitMQ) can push a
  "refresh" event to all running instances when config changes, updating
  @RefreshScope beans live — useful for feature flags/tunable thresholds
  without a redeploy.
```

"I use this for things like: circuit breaker timeout thresholds, feature flag
percentages, rate limit values, non-sensitive external API URLs — anything that
changes independently of code and benefits from a git-reviewed change history."

## Part 3 — HashiCorp Vault: Secrets, Specifically

---

"Spring Cloud Config git-backed storage is NOT appropriate for secrets — even a
private git repo keeps secrets in history forever, readable by anyone with repo
access, with no fine-grained access control or rotation. Vault is purpose-built
for exactly this."

```
VAULT DYNAMIC SECRETS (the feature that matters most):

  STATIC SECRET (what most teams start with — still better than git, but limited):
    Vault stores a password, app reads it. If leaked, it's valid until
    someone manually rotates it.

  DYNAMIC SECRET (what makes Vault genuinely different):
    App requests DB credentials from Vault ──► Vault creates a BRAND NEW,
    UNIQUE database user on the fly, with a short TTL (e.g. 1 hour) ──►
    hands those short-lived credentials to the app.

    ┌──────────────────────────────────────────────────────────────┐
    │  App:  vault read database/creds/order-service-role           │
    │  Vault: creates DB user "v-orderservice-8x2j1" with           │
    │         password "randomly-generated", TTL=1hr, then           │
    │         AUTOMATICALLY REVOKES/deletes that DB user after       │
    │         the TTL expires (or on-demand revocation)              │
    └──────────────────────────────────────────────────────────────┘

    If this credential leaks (log dump, memory dump, whatever), the
    blast radius is capped at 1 hour AND it's traceable to exactly
    which app instance requested it — unlike a shared static password
    every instance uses forever.
```

```
VAULT ACCESS CONTROL VIA APP IDENTITY (no static Vault credentials either):

  Kubernetes Pod ──(uses its own K8s ServiceAccount token, auto-issued,
                     short-lived)──► Vault
                                       │ validates the K8s ServiceAccount
                                       │ token against the K8s API,
                                       │ maps it to a Vault policy
                                       ▼
                                   grants access ONLY to the secrets
                                   this specific service's policy allows

  This is "auth via workload identity" — no static Vault token or
  password is ever embedded in the app at all, closing the same
  bootstrapping-secret problem that plagues naive secrets management
  (see the secrets flow in 26.authn-authz-security-architect-interview.md).
```

## Part 4 — Consul: Service Discovery + Distributed KV + Coordination

---

"Consul overlaps a bit with both of the above but its core job is different:
service discovery (which I cover in depth in
23.service-discovery-architect-interview.md) plus a distributed key-value store
often used for coordination flags, and health-check-aware routing."

```
CONSUL'S THREE ROLES:

  1. SERVICE REGISTRY — services register themselves, Consul health-checks
     them, other services discover healthy instances (same problem
     23.service-discovery-architect-interview.md solves, Consul is one
     of the tools that can do it).

  2. DISTRIBUTED KV STORE — similar surface to Spring Cloud Config, but
     often used for smaller, more dynamic coordination flags (e.g. "is
     maintenance mode on") rather than large structured application config.

  3. DISTRIBUTED LOCKS/SESSIONS — Consul sessions can back the same kind
     of leader-election/mutual-exclusion patterns as ZooKeeper/etcd (see
     27.consensus-raft-paxos-distributed-locks-interview.md) — Consul
     itself runs on the Raft consensus algorithm internally.
```

## Part 5 — Decision Framework

---

```
Q1: Is this a SECRET (password, API key, certificate private key)?
    │
    YES ──► Vault (or AWS Secrets Manager/Parameter Store SecureString on AWS).
    │       Prefer DYNAMIC secrets over static where the backend supports it.
    │
    NO
    │
Q2: Is this non-secret config that varies by environment and should be
    git-reviewable (timeouts, feature flags, endpoint URLs)?
    │
    YES ──► Spring Cloud Config (or a cloud-native equivalent: AWS AppConfig,
    │       Parameter Store standard params).
    │
    NO — this is about FINDING/discovering healthy service instances, or
    a small distributed coordination flag/lock
    │
    ──► Consul (or, on Kubernetes, the built-in service discovery + a
        ConfigMap for the coordination-flag use case).
```

## Part 6 — Production Scenario

---

"We had a real incident where a database password lived in a Kubernetes ConfigMap
(NOT even a Secret — a plain ConfigMap, base64 isn't encryption anyway) committed
to the same git repo as application manifests. It leaked when a contractor's laptop
with repo access was compromised. Root cause fix: migrated to Vault with dynamic DB
credentials issued per-pod via Kubernetes ServiceAccount auth, 1-hour TTL. Even in a
repeat scenario — a leaked pod log accidentally containing a credential — the
credential would be auto-revoked within an hour and scoped to exactly one pod's
access level, instead of a permanent, shared password valid indefinitely for
every service that happened to read that ConfigMap."

## Interview Traps & Cross-Questions

---

```
Q: "Why not just put secrets in Kubernetes Secrets instead of Vault?"
A: "Kubernetes Secrets are base64-ENCODED by default, not encrypted — anyone
    with API read access to that namespace can trivially decode them. K8s
    supports encryption-at-rest for Secrets with additional configuration,
    but even then, they're static, long-lived, and don't offer Vault's
    dynamic/short-TTL credential issuance or fine-grained audit trail of
    WHO accessed WHICH secret WHEN."

Q: "Does using Spring Cloud Config for feature flags scale well for
    very-high-frequency flag changes (e.g. a live experiment toggled
    every few minutes)?"
A: "Git-backed config with a refresh event works but isn't designed for
    high-frequency toggling — for that specific use case I'd reach for a
    purpose-built feature flag service (LaunchDarkly, or a simple Redis-
    backed flag store) instead, and reserve Spring Cloud Config for
    genuinely infrequent, reviewable configuration changes."

Q: "What happens to already-running app instances if Vault or the Config
    Server is temporarily unreachable?"
A: "Design for graceful degradation: apps should cache the last known
    good config/credentials in memory and continue operating, only failing
    if a REFRESH is needed and the config source is down — not fail
    immediately just because the config source had a blip. For Vault's
    dynamic DB credentials specifically, the app holds a valid, unexpired
    lease and keeps working until that lease's TTL is actually up."
```
