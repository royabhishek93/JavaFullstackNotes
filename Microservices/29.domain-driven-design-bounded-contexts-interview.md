> Speak naturally. Pause at diagrams. Show confidence, not textbook recitation.

## Opening — When Interviewer Asks "How Do You Decide Where Microservice Boundaries Go?"

---

"This is where a lot of candidates give a vague answer like 'split by business capability' —
true, but not specific. The actual tool I use to find those boundaries is Domain-Driven
Design — specifically the concept of a Bounded Context. Let me explain what that means
and how I've applied it."

---

## Part 1 — The Core Problem: The Same Word Means Different Things

---

"Take the word 'Customer'. In a real e-commerce platform:

- To the Sales team, a Customer is a lead with a sales pipeline stage, an assigned rep.
- To the Shipping team, a Customer is a delivery address and a set of preferences.
- To the Billing team, a Customer is a payment method, a tax ID, an invoice history.

If you model 'Customer' as one giant shared entity used by every team, every team's
change to that entity risks breaking every other team. That's the actual root cause
of a lot of 'distributed monoliths' — the code is split into services, but the data
model is still one shared, tightly coupled 'Customer' table everyone reads and writes."

```
ONE SHARED "CUSTOMER" MODEL (the trap):

     ┌──────────────────────────────────────────────┐
     │              Customer (shared table)          │
     │  id, name, address, payment_method,           │
     │  sales_stage, assigned_rep, tax_id,            │
     │  delivery_prefs, loyalty_points, ...           │
     └──────────────────────────────────────────────┘
            ▲              ▲              ▲
            │              │              │
      Sales Service   Shipping Service  Billing Service
      (adds a column   (adds a column    (adds a column
       for its need)    for its need)     for its need)

  Every team is scared to change the schema — it might break someone else.
  This is a distributed monolith: separate deployables, same coupled data model.
```

---

## Part 2 — Bounded Context: Same Word, Different Meaning, On Purpose

---

"A Bounded Context is an explicit boundary within which a specific model — including
its vocabulary — is consistent and valid. Outside that boundary, the same word can mean
something entirely different, and that's not a bug, it's the point."

```
BOUNDED CONTEXTS (the fix):

  ┌─────────────────────┐   ┌─────────────────────┐   ┌─────────────────────┐
  │   Sales Context      │   │  Shipping Context    │   │  Billing Context     │
  │                      │   │                      │   │                      │
  │  Customer =          │   │  Customer =          │   │  Customer =          │
  │  { lead_id,          │   │  { delivery_address,  │   │  { payment_method,    │
  │    sales_stage,      │   │    delivery_prefs }   │   │    tax_id,           │
  │    assigned_rep }    │   │                      │   │    billing_address } │
  └─────────────────────┘   └─────────────────────┘   └─────────────────────┘
       owns its own              owns its own               owns its own
       database/schema           database/schema             database/schema

  Each team owns their model completely. No shared "master Customer table"
  that everyone is afraid to touch. This maps directly onto microservice
  boundaries — one bounded context = (usually) one deployable service.
```

"This is the actual technique I use to find service boundaries — not 'split by noun',
but 'find where the meaning and lifecycle of a concept diverges between teams'."

---

## Part 3 — Aggregates: The Consistency Boundary Inside a Bounded Context

---

"Inside a bounded context, DDD gives you another tool: the Aggregate. An aggregate is
a cluster of objects that must be consistent with each other, treated as one unit for
writes, with a single Aggregate Root as the only entry point external code is allowed
to reference directly."

```
ORDER AGGREGATE:

  ┌───────────────────────────────────────────────────┐
  │  Order  (AGGREGATE ROOT — external code can only    │
  │          reference the Order, never reach inside)  │
  │    │                                                │
  │    ├── OrderLine[]   (can't exist without an Order) │
  │    ├── status         (PENDING/SHIPPED/CANCELLED)    │
  │    └── invariant: sum(OrderLine.price) == Order.total│
  └───────────────────────────────────────────────────┘

  External code does:  order.addLine(item)  ─► order enforces its own invariant
  External code does NOT: orderLineRepository.insert(line) directly — that could
  violate the total-matches-lines invariant, since nothing enforces it.

  The aggregate boundary is also usually the TRANSACTION boundary — one aggregate,
  one transaction. If you need to update two aggregates together, that's exactly
  where the Saga pattern (see 12.distributed-transactions-saga-vs-2pc.md) comes in —
  cross-aggregate consistency is handled via eventual consistency, not one big ACID
  transaction that spans aggregate roots.
```

## Part 4 — Context Mapping: How Bounded Contexts Talk to Each Other

---

"Once you have separate contexts, they still need to integrate. DDD names the actual
integration relationships, which gives you precise language for design reviews instead
of vague 'they call each other's API' descriptions."

```
COMMON CONTEXT MAP RELATIONSHIPS:

  Customer/Supplier:
    Order Context (customer) depends on Inventory Context (supplier) for stock checks.
    Supplier has to consider the customer's needs when changing its API.

  Conformist:
    Reporting Context just accepts Billing Context's model as-is, no translation layer,
    because it has no leverage to ask Billing to change anything for it.

  Anti-Corruption Layer (ACL):
    New Order Context talks to a legacy mainframe Inventory system through a
    translation layer that converts the legacy's ugly model into a clean one —
    this is literally the pattern in 06.strangler-fig-anti-corruption-layer-architect-interview.md,
    now named with its proper DDD origin.

  Shared Kernel:
    Two contexts explicitly share a small common library (e.g. a Money value object
    with currency-safe arithmetic) — used sparingly, since it re-introduces coupling.
```

```
CONTEXT MAP DIAGRAM (example e-commerce platform):

  ┌────────────┐  Customer/Supplier   ┌────────────────┐
  │   Order     │◄─────────────────────│   Inventory     │
  │  Context    │                      │   Context       │
  └─────┬──────┘                      └────────────────┘
        │ ACL
        ▼
  ┌────────────┐                       ┌────────────────┐
  │  Legacy      │                      │   Billing       │
  │  Mainframe   │      Conformist      │   Context       │
  └────────────┘      ┌──────────────►│                 │
                       │               └────────────────┘
                 ┌────────────┐
                 │ Reporting   │
                 │ Context     │
                 └────────────┘
```

## Part 5 — Production Scenario: How I've Actually Used This

---

"When we split a monolithic order management system, the temptation was to draw
service boundaries around database tables — 'Orders Service', 'Products Service',
'Users Service' — a purely technical/CRUD split. Instead, we ran event-storming
sessions with domain experts from each business team and asked: where does the
vocabulary and the rules genuinely diverge?

We found 'Inventory' meant something different to Warehouse Ops (physical stock count,
bin locations) vs Merchandising (what's listed for sale, price, promotions). We split
those into two bounded contexts even though a naive technical split would have kept
one 'Product' table. That single decision avoided a recurring conflict where a
warehouse stock adjustment was accidentally triggering price/listing changes downstream,
because they'd been sharing one table and one meaning of 'Product' before the split."

## Interview Traps & Cross-Questions

---

```
Q: "Isn't 'one microservice per database table' good enough for service boundaries?"
A: "No — that's a technical decomposition, not a domain one. It tends to recreate
    a distributed monolith because services still need to call each other
    constantly for every business operation, since the real domain boundary
    (where meaning/rules diverge) doesn't line up with table boundaries.
    DDD's bounded context is found by talking to domain experts, not by
    looking at the schema."

Q: "Should every bounded context be its own microservice?"
A: "Not necessarily one-to-one at first. I've started multiple bounded contexts
    inside one deployable (a 'modular monolith') when the team is small, keeping
    the code-level module boundaries clean via bounded context lines, and only
    split into separate services later when scaling/team/deployment needs justify
    the operational cost — this is the same reasoning as
    19.microservices-vs-monolith.md's 'premature microservices' pitfall."

Q: "What's the difference between an Aggregate and a Bounded Context?"
A: "Bounded Context is a boundary around a whole subdomain's model and language —
    can contain many aggregates. Aggregate is a much smaller, specific consistency/
    transaction boundary within that context, e.g. Order and OrderLine together.
    Confusing the two is common — Aggregate is tactical DDD, Bounded Context is
    strategic DDD."

Q: "How do you handle a query that needs data spanning two bounded contexts?"
A: "Don't reach across and join their databases directly — that recreates coupling.
    Either the requesting context subscribes to events from the other and keeps
    its own read-optimized local copy (same idea as CQRS's read model, see
    25.cqrs-pattern-architect-interview.md), or an aggregator/BFF layer composes
    the two contexts' APIs at request time for less latency-sensitive cases."
```

## Quick Reference Card

```
CONCEPT              MEANING                                    MAPS TO
──────────────────────────────────────────────────────────────────────────────
Bounded Context       explicit model/vocabulary boundary          ~ one microservice
                       ("Customer" means X here, Y elsewhere)      (or module in a monolith)
Aggregate             consistency/transaction boundary             ~ one entity graph,
                       inside a context                             one DB transaction
Aggregate Root        sole entry point into an aggregate            ~ the only repository
                                                                     exposed externally
Context Map           how contexts relate/integrate                 ~ your service
                       (Customer/Supplier, ACL, Conformist,          dependency diagram,
                        Shared Kernel)                               named precisely
Ubiquitous Language    shared vocabulary between devs & domain       ~ naming in code
                       experts, consistent within one context        matches business terms
```
