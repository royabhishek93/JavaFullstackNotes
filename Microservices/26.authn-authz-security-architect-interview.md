# AuthN/AuthZ & Zero Trust Security — Interview Script (15 Years Experience)

> Speak naturally. Pause at diagrams. Show confidence, not textbook recitation.

---

## Opening — When Interviewer Asks "How Do You Secure Communication Between Microservices?"

---

"This is one of those questions where people jump straight to 'we use mTLS' and stop.
That's transport security — it proves *which service* is talking, not *which user*
or *what they're allowed to do*. A mature answer separates three different problems:
authentication, authorization, and secrets management. Let me walk through all three."

---

## Part 1 — Setting the Scene (The Problem)

---

"Say we're building an e-commerce platform. A mobile app calls the API Gateway,
which fans out to Order Service, Payment Service, and Inventory Service.

Three questions have to be answered on every hop:

1. Who is this? (Authentication)
2. What are they allowed to do? (Authorization)
3. How do services identify each other, not just the end user? (Service identity)"

```
REQUEST FLOW WITH SECURITY LAYERS:

  Mobile App ──(1)──► API Gateway ──(2)──► Order Service ──(3)──► Payment Service
                          │                     │                      │
                    validates JWT          validates JWT           validates JWT
                    (user identity)     + service mTLS cert     + service mTLS cert
                          │                     │                      │
                    checks scopes         checks scopes           checks scopes
                    "orders:write"        "orders:write"          "payments:charge"
```

---

## Part 2 — Authentication: OAuth2 + OIDC + JWT

---

"For user-facing auth, I don't invent anything — I use OAuth2 for delegated authorization
and OpenID Connect (OIDC) on top of it for authentication. OAuth2 alone answers 'can this
app access this resource'; OIDC adds the identity layer — 'who is this user'.

The flow I use for a mobile app is Authorization Code + PKCE — never Implicit flow,
that's deprecated because tokens leak through browser redirects."

```
AUTHORIZATION CODE + PKCE FLOW:

  Mobile App                Auth Server (Keycloak/Cognito/Auth0)         API Gateway
      │                              │                                       │
      │──1. redirect w/ code_challenge──►│                                   │
      │◄─────2. login page───────────────│                                   │
      │──3. user credentials─────────────►│                                   │
      │◄─────4. auth code─────────────────│                                   │
      │──5. code + code_verifier─────────►│                                   │
      │◄─────6. access_token (JWT) +──────│                                   │
      │        refresh_token                                                 │
      │                                                                      │
      │──7. API call w/ "Authorization: Bearer <JWT>"──────────────────────►│
      │                                                              8. validates
      │                                                                 JWT signature
      │                                                                 + expiry + scopes
```

"The access token is a JWT — a signed, self-contained claim set. The gateway validates
the signature against the auth server's public key (JWKS endpoint) — no network call
to the auth server needed on every request. That's the whole point: stateless validation."

```
JWT STRUCTURE (decoded):

  HEADER:   { "alg": "RS256", "kid": "key-2024-01" }
  PAYLOAD:  {
              "sub": "user-8821",
              "scope": "orders:write payments:read",
              "tenant": "acme-corp",
              "exp": 1735689600,     ← short-lived, 15 min typical
              "iss": "https://auth.company.com"
            }
  SIGNATURE: RSA-signed with auth server's private key
```

## Part 3 — Authorization: From Coarse Roles to Fine-Grained Policy

---

"Authentication tells you who — authorization decides what they can do. I've used three
levels of maturity across different companies, and I pick based on complexity of rules."

```
AUTHORIZATION MATURITY LADDER:

  Level 1 — RBAC (Role-Based Access Control)
    if (user.hasRole("ADMIN")) { allow }
    → Good enough for 80% of internal tools. Breaks down when rules
      depend on context ("only if amount < $500 AND same region").

  Level 2 — Scopes / Claims embedded in JWT
    if (jwt.scopes.contains("orders:write")) { allow }
    → What most REST APIs use. Coarse but stateless — no DB lookup.

  Level 3 — ABAC / Policy engine (OPA / Cedar)
    allow if: user.department == resource.department
              AND time.hour between 9 and 18
              AND request.amount < user.approval_limit
    → Needed when rules combine multiple attributes dynamically.
      I've used Open Policy Agent (OPA) as a sidecar — service calls
      it with the request context, gets allow/deny in <5ms.
```

```
OPA SIDECAR PATTERN:

  ┌─────────────────────┐      POST /v1/data/orders/allow      ┌─────────────────┐
  │   Order Service      │─────────────────────────────────────►│  OPA Sidecar    │
  │                      │      { user, action, resource }      │  (Rego policy)  │
  │  if (!allowed) 403   │◄──────────────────────────────────────│                 │
  └─────────────────────┘      { "allow": true/false }          └─────────────────┘

  Policy lives as code, versioned in git, deployed independently
  of the service — auditors love this because rules are reviewable diffs.
```

## Part 4 — Service-to-Service Identity (Not the Same as User Identity)

---

"This is the trap a lot of candidates fall into — they think mTLS solves authorization.
It doesn't. mTLS proves *which service* is calling (via its certificate), it says nothing
about *which user* initiated the request or what they're allowed to do.

In production I run both, layered:

- mTLS at the mesh level (Istio/Envoy) — proves service identity, encrypts the wire.
- JWT propagated through the call chain — proves user identity, carries the original scopes.

If Payment Service only checked the mTLS cert, then Order Service — once compromised —
could charge anyone for anything, because it's a 'trusted' service. The user's JWT has
to travel with the request so Payment Service can re-validate the actual permission."

```
DOUBLE-LAYER AUTH ACROSS THE MESH:

  Order Service ────────────► Payment Service
       │                            │
       │  mTLS cert: "order-svc"    │  validates cert = known service (Istio)
       │  Header: Authorization:    │
       │    Bearer <original JWT>   │  validates JWT = original user + scope
       │                            │  (NOT just "some trusted service called me")
```

## Part 5 — Zero Trust: The Mental Model Shift

---

"Traditional security is perimeter-based — firewall at the edge, everything inside
the VPC is 'trusted'. Zero Trust flips that: never trust, always verify, regardless
of network location. Every request — even between two pods in the same cluster —
must prove identity and be authorized.

Concretely, this means:

- No implicit trust from network position (a pod in the same VPC is not automatically trusted)
- mTLS everywhere, even internal traffic
- Short-lived credentials over long-lived static ones
- Least-privilege IAM roles per service, not one shared service account"

```
PERIMETER MODEL vs ZERO TRUST:

  PERIMETER (old):                      ZERO TRUST (now):
  ┌───────────────────────┐             ┌──────┐ mTLS ┌──────┐ mTLS ┌──────┐
  │  Firewall              │             │ Svc A│◄────►│ Svc B│◄────►│ Svc C│
  │  ┌─────┐ ┌─────┐      │             └──────┘      └──────┘      └──────┘
  │  │Svc A│ │Svc B│ (trust  │            each hop independently verified,
  │  └─────┘ └─────┘  each   │            even inside the same VPC/cluster
  │        other implicitly) │
  └───────────────────────┘
```

## Part 6 — Secrets Management (Where I've Seen Teams Get Burned)

---

"Every AWS incident post-mortem I've been part of that involved a breach — the root
cause was a leaked static secret: an API key committed to git, or a DB password in
a Kubernetes ConfigMap in plaintext.

My rule: secrets never live in application config, source control, or environment
variables baked into images. They come from a vault at runtime, with automatic rotation."

```
SECRETS FLOW (AWS example):

  Application Pod                    AWS Secrets Manager / Vault
       │                                       │
       │──1. IAM role assumed (no static keys)─►│
       │◄─2. short-lived secret (DB password)───│
       │                                       │
       │   secret cached in memory only         │
       │   auto-rotated every 30 days by AWS    │
       │   app re-fetches on rotation event      │
       │                                       │
       │   NEVER logged, NEVER in env var        │
       │   dumps, NEVER in git                   │
```

"For Kubernetes specifically, I use the Secrets Store CSI Driver to mount secrets
from Vault/AWS Secrets Manager directly as files — not as K8s Secrets, which are
only base64-encoded, not encrypted, by default."

## Part 7 — Production Scenario (What I've Actually Built)

---

"At [previous role], we had a partner API — external companies calling our platform.
We couldn't use browser-based OAuth flows since there's no user. So we used
Client Credentials Grant — machine-to-machine OAuth2:

- Partner registers, gets client_id + client_secret
- Partner calls our token endpoint, gets a short-lived JWT (5 min TTL)
- Every API call carries that JWT
- Our gateway validates signature, checks scopes tied to that partner's tier
- Rate limiting keyed off client_id, not IP — partners share NAT gateways"

```
CLIENT CREDENTIALS GRANT (M2M):

  Partner System              Auth Server              API Gateway
       │                          │                         │
       │──POST /token────────────►│                         │
       │  client_id + secret      │                         │
       │◄─────JWT (5 min)─────────│                         │
       │                                                    │
       │──API call w/ Bearer JWT───────────────────────────►│
       │                                          validates scope
       │                                          "partner:tier2:read"
```

## Interview Traps & Cross-Questions

---

```
Q: "Why not just use API keys for everything?"
A: "API keys are static, long-lived, and rarely rotated — one leak means indefinite
    compromise. JWTs are short-lived and scoped; a leaked token expires in minutes.
    I still use API keys for very low-risk, read-only public endpoints, nothing more."

Q: "If mTLS already encrypts and authenticates service-to-service, why also pass a JWT?"
A: "mTLS proves *service* identity. JWT proves *user* identity and carries authorization
    scope. A compromised-but-trusted service without the JWT check could act on behalf
    of any user. This is the classic 'confused deputy' problem."

Q: "How do you handle token revocation for JWTs, since they're stateless?"
A: "Short TTLs (5-15 min) minimize the blast radius. For hard revocation — e.g. a user
    disables their account mid-session — I keep a small denylist in Redis checked at
    the gateway, or accept the short window until natural expiry for lower-risk actions."

Q: "What's the risk with storing JWT in localStorage vs an httpOnly cookie?"
A: "localStorage is readable by any JS on the page — vulnerable to XSS token theft.
    httpOnly, Secure, SameSite=Strict cookies aren't readable by JS at all. I use
    cookies for browser clients and Authorization headers for native/mobile/service
    clients where there's no XSS vector."

Q: "How do you avoid every service reimplementing JWT validation logic?"
A: "Validation happens once at the edge (API Gateway/mesh sidecar), which then forwards
    trusted identity headers downstream. Or every service uses a shared auth library
    validating against the same JWKS endpoint — never hand-rolled signature checks."
```

## Quick Reference Card

```
CONCERN                  MECHANISM                      WHERE ENFORCED
──────────────────────────────────────────────────────────────────────────
User authentication      OAuth2 Auth Code + PKCE / OIDC   Auth server + Gateway
Service identity          mTLS (mesh-issued certs)         Service mesh sidecar
Coarse authorization      JWT scopes/claims                Gateway or service
Fine-grained authz        OPA/Cedar policy engine          Sidecar or in-process
M2M authentication        OAuth2 Client Credentials        Gateway
Secrets at rest           Vault / AWS Secrets Manager       Runtime injection

```
