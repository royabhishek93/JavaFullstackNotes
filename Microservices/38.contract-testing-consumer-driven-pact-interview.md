# Contract Testing (Consumer-Driven Contracts / Pact) — Interview Script (15 Years Experience)

> Speak naturally. Pause at diagrams. Show confidence, not textbook recitation.

---

## Opening — When Interviewer Asks "How Do You Test Integration Between Independently Deployed Services Without Slow, Flaky End-to-End Tests?"

---

"Full end-to-end tests that spin up every microservice to verify one integration
point are slow, flaky (any one of 10 services being down fails the whole suite), and
don't scale as the number of services grows quadratically with integration points.
Contract testing solves a narrower but much more practical problem: verify that a
consumer and a provider agree on the shape of their interaction, WITHOUT either
one needing the other running during the test."

---

## Part 1 — The Problem With Both Extremes

---

```
NO INTEGRATION TESTING AT ALL:
  Order Service changes its response shape, Payment Service (which reads
  a field from it) breaks in PRODUCTION — the first signal is a real
  customer-facing incident, not a test failure in CI.

FULL END-TO-END TESTING (spin up everything):
  ┌──────────────────────────────────────────────────────────┐
  │  CI pipeline starts: Order Service, Payment Service,      │
  │  Inventory Service, User Service, a test database,        │
  │  a test Kafka cluster... all just to verify ONE           │
  │  interaction between 2 of them.                            │
  │                                                             │
  │  Flaky: if ANY of the 5 services has a startup issue,      │
  │  the whole test suite fails, unrelated to the actual        │
  │  thing being tested.                                        │
  │  Slow: minutes to spin up, per CI run, multiplied by        │
  │  every team doing this.                                     │
  └──────────────────────────────────────────────────────────┘
```

---

## Part 2 — Consumer-Driven Contract Testing: The Middle Ground

---

"The insight: the CONSUMER defines exactly what it needs from the provider — a
'contract' — as part of its own test suite, without the provider needing to be
running. That contract is then replayed against the REAL provider separately,
in the provider's own pipeline, to verify the provider still honors it."

```
CONSUMER-DRIVEN CONTRACT FLOW (Pact, the most common tool):

  STEP 1 — Consumer writes a test against a MOCK of the provider:

    Payment Service test:
      "GIVEN Order Service returns an order with status=CONFIRMED
       WHEN Payment Service calls GET /orders/123
       THEN it expects a JSON body with { id, status, total }"

    Running this test against a Pact MOCK generates a CONTRACT FILE
    (a JSON document describing exactly this expected interaction) —
    no real Order Service was ever called.

  STEP 2 — Contract is published to a Pact Broker (shared service):

    Payment Service CI ──publish contract──► Pact Broker ◄──provider CI reads it

  STEP 3 — Provider's OWN CI pipeline verifies the contract against the
  REAL Order Service (this time genuinely running, but ONLY one service,
  not the whole graph):

    Pact Broker ──"here's what Payment Service expects"──► Order Service test
                                                              runner replays the
                                                              exact interaction
                                                              against the real
                                                              Order Service code
                                                              and asserts the
                                                              response matches

  STEP 4 — Pact Broker records: "Order Service version 4.2 satisfies
  Payment Service version 2.1's contract" — this becomes a queryable
  compatibility matrix.
```

---

## Part 3 — The "Can I Deploy?" Question — Where This Pays Off

---

"The real payoff isn't just catching mismatches early — it's answering a specific,
previously-unanswerable question before a deploy: 'is it safe for me to deploy this
version of Order Service, given every consumer that depends on it?'"

```
CAN-I-DEPLOY CHECK:

  Order Service wants to deploy version 4.3.
  Pact Broker knows:
    - Payment Service v2.1's contract: VERIFIED against Order Service v4.3 ✓
    - Shipping Service v1.5's contract: VERIFIED against Order Service v4.3 ✓
    - Analytics Service v3.0's contract: NOT YET VERIFIED against v4.3 ✗
                                          (still failing — a breaking change
                                           this new version introduced)

  `pact-broker can-i-deploy --pacticipant OrderService --version 4.3`
  → answers NO, and tells you EXACTLY which consumer would break —
    BEFORE you deploy, not after an incident.
```

---

## Part 4 — Production Scenario

---

"On a platform with ~25 microservices and dozens of cross-service dependencies, we'd
had 3 production incidents in one quarter, each caused by a provider team changing a
response shape without realizing a downstream consumer depended on the exact old shape.
We introduced Pact for the highest-traffic integration points first (not all 25 services
at once — that's too much to roll out simultaneously). Each consumer team wrote
contracts for what they actually used; each provider team added a 'verify contracts'
step to their CI pipeline, gated their deploy on `can-i-deploy`. Within 2 quarters,
similar incidents dropped to zero for the covered integration points, and provider
teams reported feeling more confident making changes because they had concrete proof
of who depended on what, instead of guessing or grepping through Slack history."

## Interview Traps & Cross-Questions

---

```
Q: "Isn't this just mocking — what makes it different from a regular unit test
    with a stub?"
A: "A regular mock/stub only tests the CONSUMER's own logic in isolation — it
    proves nothing about whether the REAL provider actually behaves as the mock
    assumed. Contract testing's second half — replaying the SAME contract
    against the real provider in the provider's own pipeline — is what closes
    that gap. Without step 2, you just have an unverified assumption baked
    into a mock."

Q: "Why not just rely on strict API versioning to avoid this problem entirely?"
A: "Versioning (see 30.schema-evolution-api-versioning-interview.md) handles
    INTENTIONAL, known breaking changes. Contract testing catches ACCIDENTAL
    breakage — a provider team not realizing a specific field, still on the
    'same' version, is depended upon by a consumer in a way they didn't
    anticipate. The two are complementary, not alternatives."

Q: "Does contract testing replace end-to-end tests entirely?"
A: "No — I keep a SMALL number of true end-to-end/smoke tests for the most
    critical user journeys (e.g. 'can a user complete checkout at all'), but
    use contract testing for the bulk of service-to-service interaction
    verification, since it's faster, less flaky, and scales linearly with
    the number of integration points instead of combinatorially."
```
