# Leader Election — Interview Script (15 Years Experience)

> Speak naturally. Pause at diagrams. Show confidence, not textbook recitation.

---

## Opening — When Interviewer Asks "Tell me about Leader Election"

---

"So, Leader Election is something I've dealt with multiple times across different companies,
and honestly it's one of those problems that sounds simple on the surface but has real depth.

Let me walk you through how I think about it — starting from the problem, then how I've
solved it in production."

---

## Part 1 — Setting the Scene (The Problem)

---

"Imagine you're building a subscription service — think Netflix, YouTube Premium.
You've got a service in the middle that handles payment renewals.

At some point your traffic grows, and you scale that service horizontally — say 5 instances.

Now here's the issue..."

```
BEFORE scaling — works fine:

   Stripe ──────► [ Payment Service ] ──────► Database
                                               (charge once ✓)


AFTER scaling — problem appears:

   Stripe ──────► [ Instance 1 ] ──────┐
                  [ Instance 2 ] ──────┤
                  [ Instance 3 ] ──────┼──────► Database
                  [ Instance 4 ] ──────┤       (charge 5 times! ✗)
                  [ Instance 5 ] ──────┘
```

"All 5 instances receive the same renewal trigger and all 5 try to charge the customer.
That's catastrophic for a payment system.

So the solution is — elect one instance as the Leader. Only the leader processes the request.
The other 4 sit on standby as Followers."

```
AFTER leader election — correct:

   Stripe ──────► [ Instance 1  LEADER  ] ──────► Database
                  [ Instance 2  follower ]          (charge once ✓)
                  [ Instance 3  follower ]
                  [ Instance 4  follower ]
                  [ Instance 5  follower ]
```

---

## Part 2 — Why It's Hard (Split-Brain)

---

"Now here's where it gets interesting — and this is what interviewers really want to hear.

The hard part isn't electing a leader. The hard part is what happens when the leader
appears to die but actually hasn't."

```
SPLIT-BRAIN scenario:

   [ Instance 1  LEADER ]                [ Instance 2 ]
           |                                    |
           |      ~~~~~ network cut ~~~~~       |
           |                                    |
       still alive                     "Instance 1 is dead!"
       still processing                elects itself as leader


Result: TWO leaders, BOTH processing payments.
That's the split-brain problem.
```

"The way we solve this is through TTL-based leases.

The leader doesn't just win an election once — it must continuously heartbeat to renew
its lock, say every 10 seconds. The lock has a TTL of 30 seconds.

If Instance 1 loses network connectivity, it can't renew its lock.
After 30 seconds, the lock expires.
Now Instance 2 safely wins the election — because the lock store guarantees
only one node can hold that lock at any given time."

```
LEASE-BASED ELECTION timeline:

t=0s   Instance 1 acquires lock (TTL=30s)
t=10s  Instance 1 renews lock   (TTL reset to 30s)
t=20s  Instance 1 renews lock   (TTL reset to 30s)
t=25s  Instance 1 crashes ──────────────────────────┐
t=30s  --- no renewal ---                            │
t=55s  Lock EXPIRES (30s after last renewal)         │
t=56s  Instance 2 acquires lock — becomes LEADER ◄───┘
```

## Part 3 — The Algorithms (Show You Know the Theory)

---

"Computer scientists solved this formally through consensus algorithms.

The two you'll hear most often are Paxos and Raft.

Paxos is the theoretical foundation — Google built Chubby on top of it.
Raft is the more readable version — easier to reason about — and it's what
etcd uses, which is what runs inside every Kubernetes cluster.

Zookeeper uses its own variant called ZAB — Zookeeper Atomic Broadcast.

In practice though — I never implement these algorithms directly.
That would be like implementing a sort algorithm instead of using Arrays.sort().

What I do is use tools that already implement them — Zookeeper, etcd —
and integrate those into my Spring Boot services."

```
CONSENSUS ALGORITHM MAP:

  Paxos  ──────► Google Chubby (internal)
                 Cassandra (lightweight transactions)

  Raft   ──────► etcd ──────► Kubernetes (uses etcd internally)
                 CockroachDB

  ZAB    ──────► Zookeeper ──────► Kafka (historically)
                                   Uber (leader election)
                                   HBase
```

## Part 4 — How I Pick the Tool in Production

---

"In 15 years I've seen teams over-engineer this constantly.
People reach for Zookeeper when ShedLock would've done the job in an afternoon.

So here's my decision framework — I walk through these questions in order:"

```
ARCHITECT DECISION TREE:

  Q1: Are you only solving duplicate scheduled jobs?
      │
      YES ──────► ShedLock + Redis
      │           (done in 30 minutes, battle-tested)
      │
      NO
      │
  Q2: Do you need leader/follower events in your application logic?
      │
      YES ──────► Spring Integration + RedisLockRegistry
      │           (leader granted/revoked events you can react to)
      │
      NO
      │
  Q3: Serverless? No Redis? Lambda-based?
      │
      YES ──────► DynamoDB conditional writes
      │           (atomic putItem with condition expression)
      │
      NO
      │
  Q4: Do you already run Kafka (MSK) or Kubernetes (EKS)?
      │
      YES ──────► Zookeeper (Curator) or etcd (jetcd)
      │           (Zookeeper is already there if you use MSK)
      │
      NO ───────► Go back to ShedLock. Don't add Zookeeper for this alone.
```

"The rule I live by: Zookeeper and etcd solve 10x more complexity than Redis-based election.
Only justify that operational overhead if the infrastructure is already there."

## Part 5 — Walking Through the Implementation

---

### "Let me show you the ShedLock approach first — the one I use most often."

```
SHEDLOCK FLOW:

  Startup:
  ┌─────────────────────────────────────────────────────────┐
  │  All 5 instances start up                               │
  │  Each tries to acquire a Redis lock named "renewal-job" │
  │  Redis: only one SETNX wins (atomic)                    │
  │  Winner runs the job, others skip                       │
  └─────────────────────────────────────────────────────────┘

  @Scheduled(cron = "0 0 2 * * *")
  @SchedulerLock(
      name           = "subscriptionRenewal",
      lockAtMostFor  = "PT25M",   ← kill lock after 25min even if node crashes
      lockAtLeastFor = "PT5M"     ← hold min 5min, prevents re-run on restart
  )
  public void processRenewals() {
      // guaranteed: only ONE instance runs this
      paymentService.processAll();
  }

  Redis key at runtime:
  ┌─────────────────────────────────────────────────────────┐
  │  KEY:   shedlock:subscriptionRenewal                    │
  │  VALUE: { lockUntil: "2024-01-01T02:25:00Z",           │
  │           lockedAt:  "2024-01-01T02:00:00Z",           │
  │           lockedBy:  "payment-service-ip-10-0-1-23" }  │
  └─────────────────────────────────────────────────────────┘
```

---

### "For the Spring Integration approach — when I need events in the app:"

```
SPRING INTEGRATION + REDIS FLOW:

  All instances compete continuously (not just at cron time):

  ┌──────────────┐     SETNX leader:locks:payment-processor      ┌───────────────┐
  │  Instance 1  │ ─────────────────────────────────────────────►│               │
  │  Instance 2  │ ─────────────── FAILED (lock taken) ─────────►│  ElastiCache  │
  │  Instance 3  │ ─────────────── FAILED (lock taken) ─────────►│   (Redis)     │
  └──────────────┘                                                └───────────────┘
         │
         │  OnGrantedEvent fires on Instance 1
         ▼
  ┌──────────────────────────────────────────────────────────┐
  │  @Component LeaderContext                                │
  │                                                          │
  │  onApplicationEvent(OnGrantedEvent) → isLeader = true   │
  │  onApplicationEvent(OnRevokedEvent) → isLeader = false  │
  └──────────────────────────────────────────────────────────┘
         │
         │  Application code checks flag:
         ▼
  @Scheduled(fixedDelay = 60_000)
  public void processRenewals() {
      if (!leaderContext.isLeader()) return;  // followers bail immediately
      paymentService.processAllDueRenewals(); // only leader reaches here
  }

  Instance crashes:
  ┌─────────────────────────────────────────────────────────┐
  │  Instance 1 crashes                                     │
  │  Redis TTL (30s) expires                                │
  │  Instance 2 wins SETNX                                  │
  │  OnGrantedEvent fires on Instance 2                     │
  │  Instance 2 becomes leader                              │
  └─────────────────────────────────────────────────────────┘
```

---

### "For Zookeeper — when we're already on MSK (Kafka):"

```
ZOOKEEPER ELECTION INTERNALS (Curator LeaderLatch):

  /myapp/leader-election/payment-processor/
       │
       ├── latch-0000000001  ◄── Instance A  (LEADER — lowest seq#)
       ├── latch-0000000002  ◄── Instance B  (watching 0001)
       ├── latch-0000000003  ◄── Instance C  (watching 0002)
       └── latch-0000000004  ◄── Instance D  (watching 0003)

  Each node watches the node directly BEFORE it (not the leader).
  This prevents the "herd effect" — only 1 node reacts to each failure.

  Instance A crashes:
  ┌─────────────────────────────────────────────────────────┐
  │  ZNode latch-0000000001 is deleted                      │
  │  Instance B was watching 0001 → gets notified           │
  │  Instance B has lowest seq# now → becomes LEADER        │
  │  Instance C now watches 0002 (Instance B's node)        │
  └─────────────────────────────────────────────────────────┘

  isLeader() callback fires on Instance B:
  ┌─────────────────────────────────────────────────────────┐
  │  @Override                                              │
  │  public void isLeader() {                               │
  │      log.info("NODE IS NOW LEADER");                    │
  │      startProcessingPayments();                         │
  │  }                                                      │
  │                                                         │
  │  @Override                                              │
  │  public void notLeader() {                              │
  │      log.warn("LOST LEADERSHIP");                       │
  │      stopProcessingPayments();                          │
  │  }                                                      │
  └─────────────────────────────────────────────────────────┘
```

"The reason Zookeeper is stronger here is that it also gives you node membership —
I can call `leaderLatch.getParticipants()` and get every node in the cluster,
not just who the leader is. That's powerful for cluster-wide coordination."

## Part 7 — Handling Every Failure Scenario

---

"A good interviewer will push on failure modes. Here's how I walk through them:"

```
FAILURE SCENARIOS:

  ┌──────────────────────────────┬──────────────────────────────────────────┐
  │ Scenario                     │ What Happens                             │
  ├──────────────────────────────┼──────────────────────────────────────────┤
  │ Leader OOM crash             │ TTL expires (30s) → follower wins        │
  │ Leader loses Redis network   │ Can't renew → TTL expires → steps down   │
  │ Redis goes down              │ No leader = no processing (SAFE)         │
  │                              │ Better than 2 leaders charging twice     │
  │ Split-brain                  │ Old leader can't renew → expires         │
  │                              │ New leader wins atomic lock              │
  │ Leader graceful shutdown     │ @PreDestroy releases lock immediately    │
  │                              │ Failover in seconds, not 30s             │
  │ New node starts mid-cycle    │ Tries SETNX → fails → waits → retries   │
  └──────────────────────────────┴──────────────────────────────────────────┘

  GRACEFUL SHUTDOWN code I always add:

  @PreDestroy
  public void releaseLeadership() {
      if (leaderContext.isLeader()) {
          leaderInitiator.stop();  // releases Redis lock immediately
          log.info("Released leadership on shutdown");
          // failover happens in seconds, not when TTL expires
      }
  }
```

"I always add two things to any leader election setup — a metric and an alert.

```
CLOUDWATCH DASHBOARD:

  ┌─────────────────────────────────────────────────────┐
  │  leader.status per node                             │
  │                                                     │
  │  instance-1:  ████████████░░░░  (was leader, lost)  │
  │  instance-2:  ░░░░░░░░████████  (became leader)     │

CRITICAL ALERT:

  IF sum(leader.status across all instances) == 0

  Alert fired in 60 seconds, we caught it before customers noticed.
```

## Part 9 — The Answer That Wins the Interview

---

"If I had to summarize this in 60 seconds for an interviewer, here's exactly what I'd say:"

---

> "Leader election ensures exactly one node in a horizontally scaled system acts as coordinator.
>
> The core challenge is split-brain — a network partition can make followers think the leader
> is dead while it's still alive, causing two leaders to run simultaneously.
>
> We solve this with TTL-based leases — the leader must heartbeat to renew a distributed lock.
> If it can't renew, the lock expires and a new election happens.
> The lock store guarantees atomicity — only one node can acquire it at a time.
>
> In production, I use ShedLock with ElastiCache for scheduled jobs — it handles all of this
> out of the box, it's battle-tested, and I've deployed it on systems doing millions of
> transactions a day.
>
> If I'm already running Kafka on MSK, I use Apache Curator against Zookeeper — it's already
> there and gives me richer cluster membership APIs.
>
> I never implement Paxos or Raft from scratch — that's like writing your own sort algorithm."
