## Opening — When Interviewer Asks "Walk Me Through How a Container Actually Differs From a VM"

---

"People use 'container' and 'lightweight VM' interchangeably, but the isolation
mechanism is fundamentally different, and that difference is exactly why containers
start in milliseconds while VMs take minutes. Let me explain the actual OS-level
primitives, then how Kubernetes orchestrates many containers across many machines."

## Part 1 — Containers vs VMs: The Actual Mechanism

---

```
VIRTUAL MACHINE:                          CONTAINER:

┌─────────────────────────┐              ┌─────────────────────────┐
│   App A     │  App B     │              │   App A     │  App B     │
│  ┌────────┐ │ ┌────────┐ │              │  ┌────────┐ │ ┌────────┐ │
│  │Guest OS│ │ │Guest OS│ │              │  │ (just   │ │ │ (just   │ │
│  │(full,  │ │ │(full,  │ │              │  │  the    │ │ │  the    │ │
│  │ separate│ │ │separate│ │              │  │  app +  │ │ │  app +  │ │
│  │ kernel!)│ │ │kernel!)│ │              │  │  deps)  │ │ │  deps)  │ │
│  └────────┘ │ └────────┘ │              │  └────────┘ │ └────────┘ │
├─────────────┴────────────┤              ├─────────────┴────────────┤
│      Hypervisor            │              │   Container Runtime       │
├───────────────────────────┤              │   (containerd/CRI-O)      │
│      Host OS                │              ├───────────────────────────┤
└───────────────────────────┘              │   HOST OS KERNEL          │
                                            │   (SHARED by all           │
                                            │    containers — this is    │
                                            │    the key difference)     │
                                            └───────────────────────────┘

  VM: each guest has its OWN kernel — full OS boot, full isolation,
      heavyweight (minutes to start, GBs of overhead per instance).

  Container: ALL containers on a host SHARE the host's kernel — isolation
      comes from kernel features (namespaces + cgroups, both Linux
      kernel primitives), not a separate OS. This is why containers
      start in milliseconds and have near-zero overhead per instance.
```

```
THE TWO LINUX KERNEL FEATURES THAT MAKE THIS WORK:

  NAMESPACES — isolate WHAT a process can SEE:
    PID namespace:      container sees only its own processes (PID 1
                        inside the container might be PID 48213 on the host)
    Network namespace:   container gets its own network interface/IP,
                        isolated from the host's
    Mount namespace:     container sees its own filesystem view
    (+ UTS, IPC, user namespaces for hostname, IPC, and UID isolation)

  CGROUPS (control groups) — limit HOW MUCH a process can USE:
    "This container gets at most 512MB memory, 0.5 CPU cores"
    Enforced by the KERNEL, not the application — if a container's
    process tries to exceed its memory cgroup limit, the kernel's OOM
    killer terminates it, the same mechanism used for any process,
    just scoped per-container.

  A container is, mechanically: a normal Linux process, with namespaces
  restricting what it can see and cgroups restricting what it can use —
  there's no separate "container kernel" at all.
```

## Part 2 — Docker Images: Layers, Not a Single Blob

---

```
IMAGE LAYERING:

  Dockerfile:
    FROM openjdk:17-slim          ← Layer 1 (base OS + JDK, large, rarely changes)
    COPY pom.xml .                 ← Layer 2 (dependency manifest)
    RUN mvn dependency:go-offline  ← Layer 3 (downloaded deps, changes when
                                      pom.xml changes)
    COPY src/ src/                 ← Layer 4 (source code, changes every build)
    RUN mvn package                ← Layer 5 (compiled artifact)

  EACH INSTRUCTION = a new, cached, immutable LAYER. Docker reuses
  unchanged layers from cache on rebuild — if only src/ changed, layers
  1-3 are reused from cache, only 4-5 rebuild. This is why the ORDER of
  Dockerfile instructions matters: put things that change LEAST OFTEN
  (base image, dependencies) FIRST, things that change MOST OFTEN
  (application source) LAST, to maximize cache hits and minimize
  rebuild/push time.

  Multiple containers running from the SAME image SHARE the underlying
  read-only layers on disk (via a union filesystem) — only a thin,
  per-container writable layer is unique to each running instance.
```

## Part 3 — Kubernetes: Orchestrating Containers Across Many Machines

---

"A single Docker host is fine for one machine. Kubernetes exists because real systems
run dozens to thousands of containers across many machines, needing scheduling,
self-healing, service discovery, and rolling updates — none of which plain Docker
provides by itself."

```
KUBERNETES CORE OBJECTS:

  Pod:          smallest deployable unit — one or more containers that
                ALWAYS run together on the same node, sharing network/
                storage (e.g. an app container + a sidecar, like the
                Istio Envoy sidecar from 03.service-mesh-istio-...).

  Deployment:   declares "I want N replicas of this Pod spec running" —
                Kubernetes CONTINUOUSLY reconciles actual state toward
                this desired state (if a Pod dies, a new one is
                scheduled automatically, without a human intervening).

  Service:      a stable network identity/DNS name + IP that load-
                balances across a Deployment's Pods, even as individual
                Pods are replaced — this is what
                23.service-discovery-architect-interview.md refers to
                as "Kubernetes service discovery".

  ConfigMap/    externalized configuration/secrets injected into Pods —
  Secret:       see 41.configuration-management-spring-cloud-config-vault-interview.md
                for why raw K8s Secrets aren't sufficient for real secrets.

  Ingress:      routes external HTTP(S) traffic into the cluster to the
                right Service, based on hostname/path.
```

```
THE RECONCILIATION LOOP (the core Kubernetes mental model):

  You declare DESIRED STATE:  "3 replicas of order-service:v2.1"
                                       │
                                       ▼
  Kubernetes CONTROL PLANE continuously compares desired vs ACTUAL state:

    ┌─────────────────────────────────────────────────────────┐
    │  Desired: 3 replicas        Actual: 2 replicas running    │
    │  (1 Pod crashed)             (node OOM-killed it)          │
    │                                                             │
    │  Control plane's SCHEDULER picks a healthy node,            │
    │  schedules a REPLACEMENT Pod automatically — no human       │
    │  had to notice the crash or manually redeploy.               │
    └─────────────────────────────────────────────────────────┘

  This is the same reconciliation-loop pattern underlying almost every
  Kubernetes behavior — rolling updates, horizontal pod autoscaling,
  self-healing — it's always "declare desired state, let a controller
  continuously reconcile toward it", never an imperative one-time script.
```

## Part 4 — Rolling Updates (How a Deployment Actually Rolls Out)

---

```
DEFAULT ROLLING UPDATE STRATEGY:

  Deployment has 4 replicas of v1. You update the image to v2.

  Step 1: Kubernetes starts 1 NEW Pod (v2), keeping all 4 v1 Pods running
          (maxSurge=1 — allowed to briefly exceed desired replica count)
  Step 2: once the new v2 Pod passes its READINESS PROBE (an HTTP health
          check confirming it's actually ready to serve traffic, not
          just "process started"), Kubernetes terminates 1 OLD v1 Pod
          (maxUnavailable=1 — allowed to briefly go below desired count)
  Step 3: repeat — start another v2, wait for readiness, kill another v1
  Step 4: continue until all 4 Pods are v2, zero downtime throughout,
          because there's ALWAYS at least 3-4 Pods (mix of v1/v2) serving
          traffic at every point in the rollout.

  READINESS PROBES are what make this safe — without one, Kubernetes
  would send traffic to a v2 Pod that's still starting up (e.g. still
  loading a cache, still connecting to a DB pool), causing errors during
  every rollout. This is a very common production gotcha for teams new
  to K8s — they define a container but forget the readiness probe.
```

## Part 5 — Production Scenario

---

"We had a recurring issue where deployments caused a brief spike in 502 errors,
despite Kubernetes's rolling update supposedly being zero-downtime. Root cause:
our Spring Boot app took ~8 seconds to fully initialize (DB connection pool warmup,
cache preload) but we had NO readiness probe configured — Kubernetes considered a
Pod 'ready' the instant its container process started, immediately routing traffic
to it before it could actually handle requests. Fix: added a readinessProbe hitting
Spring Boot Actuator's /actuator/health/readiness endpoint, which only returns 200
once the app has genuinely finished its startup sequence — Kubernetes then correctly
withheld traffic from new Pods until they were truly ready, and the 502 spike during
every deployment disappeared entirely."

## Interview Traps & Cross-Questions

---

```
Q: "What's the difference between a liveness probe and a readiness probe?"
A: "Liveness answers 'is this container alive, or should Kubernetes KILL and
    restart it' (e.g. detects a deadlock/hung process). Readiness answers
    'is this container ready to RECEIVE TRAFFIC right now' (e.g. still
    warming up, or a dependency is temporarily down) — a Pod can be alive
    but not ready, and Kubernetes should route traffic away from it
    without killing/restarting it in that case. Confusing the two is a
    very common production misconfiguration."

Q: "If containers share the host kernel, is container isolation as
    strong as VM isolation?"
A: "Not as strong by default — a kernel vulnerability could theoretically
    be exploited across container boundaries since they share one kernel,
    whereas a VM escape requires breaking hypervisor-level isolation, a
    different and generally harder attack surface. This is why highly
    sensitive multi-tenant workloads sometimes use gVisor or Firecracker
    (lightweight VMs, used by AWS Lambda/Fargate) for an extra isolation
    layer beyond plain container namespaces/cgroups."

Q: "Why does Kubernetes use a declarative model instead of just running
    deployment scripts imperatively?"
A: "Declarative desired-state + continuous reconciliation means the
    system self-heals from ANY divergence — a Pod crashing, a node
    dying, someone manually deleting a resource — all get corrected
    automatically back to the declared state. An imperative script only
    handles the specific sequence of events it was written for; it
    doesn't continuously enforce a target state afterward."
```
