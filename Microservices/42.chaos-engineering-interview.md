---

## Opening — When Interviewer Asks "How Do You Know Your System Is Actually Resilient?"

---

"Most teams design for resilience — circuit breakers, retries, bulkheads — but never
actually TEST that those mechanisms work under real failure conditions, in production-
like environments, until an actual incident happens and they find out the hard way.
Chaos engineering is the practice of deliberately injecting failure into a system,
in a controlled way, to verify your resilience assumptions are actually true, before
a real outage forces you to find out."

---

## Part 1 — The Core Idea: Hypothesis-Driven Experiments, Not Random Destruction

---

"A common misconception: chaos engineering is 'randomly break things and see what
happens'. It's actually the opposite — a disciplined, scientific process."

```
CHAOS ENGINEERING PROCESS:

  1. DEFINE STEADY STATE:
     "Checkout success rate is normally 99.5%, p99 latency is 300ms"
     (measurable, normal, healthy behavior — your baseline)

  2. FORM A HYPOTHESIS:
     "If the Payment Service's primary AZ goes down, the circuit breaker
      should open within 5 seconds and traffic should failover to the
      secondary AZ, keeping checkout success rate above 99%"

  3. INJECT REAL FAILURE (not simulated — actually kill something):
     Terminate Payment Service instances in one AZ, or inject network
     latency, or block a dependency's port.

  4. OBSERVE:
     Did checkout success rate actually stay above 99%? Did the circuit
     breaker actually open within 5 seconds, or did it take 45 seconds
     because a timeout was misconfigured?

  5. LEARN & FIX:
     If the hypothesis was WRONG (circuit breaker took 45s, not 5s), that's
     the actual point — you found a real gap BEFORE a real customer-facing
     incident forced you to find it at 3am.
```

## Part 2 — Principles of Chaos Engineering (from Netflix's original formulation)

---

```
1. START SMALL, IN A CONTROLLED BLAST RADIUS:
   Never start chaos experiments in full production with 100% of traffic
   exposed. Start in staging, then production with a tiny percentage of
   traffic, with an immediate "abort" mechanism (a kill switch) if the
   blast radius turns out bigger than expected.

2. RUN EXPERIMENTS IN PRODUCTION EVENTUALLY (this is the controversial part):
   Staging environments rarely have production's real traffic patterns,
   real data volume, real infrastructure quirks. Netflix's core insight:
   confidence only comes from testing in the environment that actually
   matters — but ALWAYS with the blast-radius controls from principle 1.

3. AUTOMATE EXPERIMENTS TO RUN CONTINUOUSLY:
   A one-time chaos test proves resilience on that day, with that code.
   Continuous chaos testing (e.g. Netflix's Chaos Monkey randomly killing
   instances in production, always, as a standing background process)
   catches REGRESSIONS — a refactor 6 months later that silently broke
   the failover logic gets caught by the next automated run, not by
   a real customer-facing outage.

4. MINIMIZE BLAST RADIUS:
   Every experiment should have a scoped, bounded impact and a fast abort
   path — this isn't "move fast and break production", it's "controlled,
   reversible, monitored failure injection".
```

## Part 4 — Production Scenario

---

"On a payments platform, we'd designed a circuit breaker to fail over to a secondary
payment processor if the primary was down — documented, code-reviewed, unit-tested
with mocks. We ran a chaos experiment: during low-traffic hours, with a scoped 2%
of real traffic, we blocked outbound network access to the primary processor's
endpoint using AWS Fault Injection Simulator.

RESULT: the circuit breaker DIDN'T open as expected — a misconfigured timeout meant
requests hung for 30 seconds before failing, instead of failing fast at the intended
2-second threshold, and the retry logic actually amplified load onto the ALREADY
degraded primary rather than immediately routing to the secondary. This was a real,
previously-unknown gap between our documented resilience design and its actual
behavior — found in a controlled 2% experiment during business hours with an
engineer watching dashboards, instead of during a real primary-processor outage at
peak Black Friday traffic, which is exactly when it would have mattered most and
been most costly to discover live."

## Part 5 — Game Days (The Human/Process Side)

---

"Chaos engineering isn't purely automated — 'Game Days' are scheduled, team-wide
exercises simulating a real incident, testing not just the SYSTEM's resilience but
the TEAM's incident response process."

```
GAME DAY STRUCTURE:

  1. Pick a realistic failure scenario ("primary region's RDS instance fails")
  2. Inject it (or simulate it) in a controlled environment
  3. On-call responds AS IF it were real — follows runbooks, pages people,
     uses the actual incident response process
  4. Afterward: retrospective — was the runbook accurate? Did the right
     people get paged? Did dashboards show the right signal fast enough?
     Did anyone reach for a stale/outdated runbook?

  This catches PROCESS gaps (a runbook referencing a decommissioned tool,
  an on-call rotation with a gap, an alert that doesn't actually page
  anyone) that pure automated chaos testing can't catch, since those are
  human/process failures, not code failures.
```

## Interview Traps & Cross-Questions

---

```
Q: "Isn't running chaos experiments in production reckless?"
A: "Only if done without blast-radius controls. Netflix's own guidance is
    explicit: start with a tiny, scoped blast radius (a single canary
    instance, a small percentage of traffic), always have an automated
    abort mechanism, and only expand scope once you've built confidence.
    The alternative — never testing in production — means your FIRST
    real test of resilience under real production conditions is an
    actual, uncontrolled incident, which is strictly riskier."

Q: "How is this different from just having good unit/integration tests
    for your resilience code (circuit breakers, retries)?"
A: "Unit tests verify the CODE does what you wrote it to do, typically
    with mocked dependencies. Chaos engineering verifies the whole SYSTEM
    — real network behavior, real timeout configuration, real
    infrastructure interaction, real monitoring/alerting — actually
    behaves as designed under REAL failure, which is exactly the gap
    where the payment processor example above was caught; the unit
    tests for that circuit breaker passed just fine."

Q: "What's the very first chaos experiment you'd run on a new system?"
A: "Something with SMALL, well-understood blast radius and HIGH confidence
    value — typically terminating a single instance and confirming
    auto-scaling/load balancer health checks correctly route around it.
    That's low-risk, tests a fundamental assumption most systems rely on,
    and builds organizational trust in the practice before attempting
    riskier experiments like AZ or region failure."
```
