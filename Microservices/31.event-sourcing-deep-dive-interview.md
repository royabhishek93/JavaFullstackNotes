## Opening — When Interviewer Asks "What Is Event Sourcing, Really?"

---

"CQRS and Event Sourcing get mentioned together so often that people conflate them —
they're independent. CQRS is about splitting read and write models. Event Sourcing is
a specific way of persisting the WRITE side: instead of storing current state
('balance = 500'), you store every state-changing event that ever happened
('deposited 300', 'withdrew 100', ...), and current state is derived by replaying them."

---

## Part 1 — State Storage vs Event Storage

---

```
TRADITIONAL STATE STORAGE:

  accounts table:
  ┌────────────┬─────────┐
  │ account_id │ balance │
  ├────────────┼─────────┤
  │ acct-1     │ 500     │   ← only the CURRENT value. History is gone
  └────────────┴─────────┘      unless you separately maintain an audit log.


EVENT SOURCING:

  event_store (append-only, immutable):
  ┌────┬────────────┬──────────────────┬────────────────┬───────────┐
  │ seq│ account_id │ event_type       │ payload        │ timestamp │
  ├────┼────────────┼──────────────────┼────────────────┼───────────┤
  │ 1  │ acct-1     │ AccountOpened    │ {initial: 0}   │ t0        │
  │ 2  │ acct-1     │ MoneyDeposited   │ {amount: 300}  │ t1        │
  │ 3  │ acct-1     │ MoneyWithdrawn   │ {amount: 100}  │ t2        │
  │ 4  │ acct-1     │ MoneyDeposited   │ {amount: 300}  │ t3        │
  └────┴────────────┴──────────────────┴────────────────┴───────────┘

  current balance = replay all events for acct-1 in order:
    0 + 300 - 100 + 300 = 500

  Nothing is ever UPDATEd or DELETEd — only appended. The full history of
  HOW you got to 500 is preserved forever, not just the final number.
```

## Part 2 — Why Bother? (The actual business reasons, not just "it's cool")

---

```
1. FULL AUDIT TRAIL FOR FREE
   Every state change is already recorded with a timestamp and reason —
   no separate audit-log table to keep in sync, which is a classic source
   of drift bugs (the audit log says one thing, the actual data says another).

2. TEMPORAL QUERIES
   "What was this account's balance last Tuesday at 3pm?" — replay events
   up to that timestamp. Impossible with plain state storage unless you
   separately snapshot history, which event sourcing gives you natively.

3. REBUILDING READ MODELS AFTER A BUG
   If a read-model projection had a bug for 3 weeks, you don't patch broken
   rows — you fix the projection code and REPLAY the entire event log to
   rebuild a correct read model from scratch. This is a uniquely powerful
   recovery mechanism traditional CRUD storage doesn't give you.

4. NATURAL FIT WITH DOMAIN EVENTS
   Business people already think in events — "order was placed", "payment
   failed", "shipment departed". Event sourcing makes the persistence model
   match the business's own mental model, which also happens to align with
   Domain-Driven Design's aggregates (see 29.domain-driven-design-bounded-contexts-interview.md).
```

## Part 3 — Snapshotting (Solving the "Replay Is Slow" Problem)

---

"The obvious objection: if an account has 2 million events, replaying all of them
on every read is unacceptably slow. The fix is snapshotting."

```
SNAPSHOT PATTERN:

  Instead of replaying ALL events from seq=1 every time:

  ┌─────────────────────────────────────────────────────────┐
  │  Every N events (e.g. every 1000), persist a SNAPSHOT:   │
  │    { account_id: acct-1, balance: 480000, as_of_seq: 9000}│
  └─────────────────────────────────────────────────────────┘

  To rebuild current state:
    1. Load the LATEST snapshot (as_of_seq: 9000, balance: 480000)
    2. Replay only events with seq > 9000 (the incremental ones since the snapshot)
    3. Apply those on top of the snapshot's balance

  This turns "replay 2 million events" into "load 1 snapshot + replay ~200
  recent events" — the snapshot is a performance optimization, NOT the
  source of truth. The event log remains the actual source of truth;
  the snapshot can always be regenerated by replaying from scratch.
```

## Part 4 — Event Versioning (What Happens When the Event Shape Changes)

---

"This is the sharp edge people miss: your event schemas live FOREVER, because you can
never rewrite history. If `MoneyDeposited` changes shape 3 years from now, your replay
code must still understand the OLD shape for old events."

```
EVENT VERSIONING APPROACHES:

  1. UPCASTING — transform old event shapes into the current shape at read time:

     MoneyDeposited_v1: { amount: 300 }
     MoneyDeposited_v2: { amount: 300, currency: "USD" }   ← currency added later

     Upcaster: when reading a v1 event, inject a default currency ("USD",
     the historical default before multi-currency existed) so the replay
     code only ever has to handle the CURRENT shape (v2), never branch
     on every historical version scattered through the application logic.

  2. NEW EVENT TYPE instead of mutating meaning:
     Rather than changing what MoneyDeposited means, introduce
     MoneyDepositedInForeignCurrency as a new, distinct event type once the
     business need diverges enough — same principle as schema evolution's
     "add, don't silently redefine" rule (see 30.schema-evolution-api-versioning-interview.md).
```

## Part 5 — Production Scenario

---

"We used event sourcing for an insurance policy lifecycle system — a policy goes
through underwriting, pricing adjustments, endorsements, claims, renewals, over
years. Regulators periodically asked 'prove exactly how this policy's premium
was calculated on this specific date' — with event sourcing, that's a replay query,
not a forensic data archaeology exercise across years of manual audit-log entries
that may or may not have been kept in sync with the real state."

```
POLICY EVENT STREAM:

  PolicyCreated → PremiumCalculated → EndorsementAdded → ClaimFiled →
  ClaimApproved → PremiumRecalculated → PolicyRenewed → ...

  "Show me the policy state as of March 3rd, 2024, 2pm" =
  replay events with timestamp <= that instant, done — regulators got exact,
  reproducible answers instead of "we believe this is what happened based
  on scattered logs".
```

## Interview Traps & Cross-Questions

---

```
Q: "Isn't event sourcing just a fancy audit log?"
A: "The audit log is a side effect, not the goal. The key difference: in event
    sourcing the event log IS the source of truth — current state is DERIVED,
    never stored as the primary record. A traditional audit log sits alongside
    a mutable state table and can drift out of sync; there's no such drift
    possible here because there's only one thing being written."

Q: "How do you handle a bug where an event was recorded with wrong data?"
A: "You never edit or delete a historical event — that would corrupt the audit
    trail's integrity. Instead you append a COMPENSATING event, e.g.
    'DepositCorrected' that adjusts for the mistake, so the full history —
    including the mistake and its correction — remains visible and truthful."

Q: "Does every aggregate/entity need to be event-sourced?"
A: "No — I reach for it selectively, where audit/temporal/replay value is high
    (financial ledgers, insurance policies, order lifecycles) not for every
    CRUD entity. A simple 'user profile preferences' table gets nothing from
    event sourcing and pays real complexity cost for no benefit."

Q: "How does this interact with CQRS's read model?"
A: "Naturally — the event stream is the write model. A projector subscribes
    to the stream and builds denormalized read models (see
    25.cqrs-pattern-architect-interview.md) asynchronously. If the projection
    logic has a bug, you fix it and replay the whole stream to rebuild a
    correct read model — you can't do that if state itself was the only
    thing ever stored."
```

## Quick Reference Card

```
CONCEPT            PURPOSE                                    ANALOGY
────────────────────────────────────────────────────────────────────────
Event log           append-only source of truth                 git commit history
Snapshot             performance optimization, NOT truth          a cached "checkout"
                     (rebuilds current state faster)              at a specific commit
Upcasting            translate old event shapes to current        git migration script
                     at read time
Compensating event   correct a past mistake without editing        a "revert" commit,
                     history                                       not force-push/rewrite
Projection           read model built by replaying/subscribing     a materialized view
                     to the event stream
```
