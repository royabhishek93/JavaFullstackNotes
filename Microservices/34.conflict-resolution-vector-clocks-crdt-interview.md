## Opening — When Interviewer Asks "How Do You Resolve Conflicts in a Multi-Master System?"

---

"This only comes up once you accept multiple nodes can write the SAME piece of data
concurrently — which is exactly what active-active multi-region replication requires
for low write latency everywhere. The question becomes: when two regions each accept
a write to the same key before either has seen the other's write, how do you reconcile
them afterward? There are three standard approaches, each with a real trade-off."

---

## Part 1 — The Problem, Concretely

---

```
TWO REGIONS, CONCURRENT WRITES TO THE SAME KEY:

  US-EAST                                    EU-WEST
  client writes: cart.items = [A, B]         client writes: cart.items = [A, C]
       │                                            │
       │ (network partition — neither region        │
       │  has seen the other's write yet)           │
       ▼                                            ▼
  US-EAST db: [A, B]                         EU-WEST db: [A, C]

  When the partition heals and replication resumes — which value wins?
  Or should [A, B] and [A, C] somehow be MERGED into [A, B, C]?
  This is the conflict resolution problem.
```

---

## Part 2 — Last-Write-Wins (LWW): Simple, but Silently Loses Data

---

```
LWW using timestamps:

  US-EAST write:  cart.items = [A, B]   @ t=100
  EU-WEST write:  cart.items = [A, C]   @ t=102

  Resolution: EU-WEST's write (t=102) wins because it's "later".
  US-EAST's write [A, B] is SILENTLY DISCARDED.

  RISK: if the user in US-EAST added item B to their cart, and LWW picks
  EU-WEST's version, item B just vanishes with no error, no merge, no trace.
  This is fine for some data (a "last viewed page" timestamp — who cares
  which one wins) and TERRIBLE for others (a shopping cart, an account balance).

  Clock skew makes this worse: if US-EAST's clock is even slightly ahead,
  a write that happened EARLIER in real time can incorrectly "win" because
  its local clock read a later timestamp. This is why distributed systems
  often use logical clocks instead of wall-clock time for ordering (see
  36.clock-synchronization-lamport-timestamps-interview.md).
```

## Part 3 — Vector Clocks: Detecting Conflicts Without Deciding a Winner

---

"Vector clocks don't resolve conflicts — they DETECT them precisely, which is the
first honest step. A vector clock is a counter-per-node attached to each write."

```
VECTOR CLOCK MECHANICS:

  Each write carries a vector: [US-EAST: n, EU-WEST: m] — counts of how many
  writes THAT NODE has seen from each region so far.

  US-EAST writes cart v1: [US-EAST:1, EU-WEST:0]
  This replicates to EU-WEST, which now knows about it.

  EU-WEST writes cart v2 (having seen v1): [US-EAST:1, EU-WEST:1]
  → v2 vector DOMINATES v1's vector (1>=1 AND 1>=0, and strictly greater
    somewhere) → v2 is a proper descendant, NOT concurrent. Safe to say v2
    supersedes v1, no real conflict.

  BUT if EU-WEST writes WITHOUT having seen v1 first:
  EU-WEST writes cart v2': [US-EAST:0, EU-WEST:1]
  → Neither vector dominates the other (US-EAST:1 > US-EAST:0, but
    EU-WEST:0 < EU-WEST:1) → THIS IS A TRUE CONCURRENT CONFLICT.
    The system flags both versions as siblings and can't auto-resolve —
    it hands both to the APPLICATION (or the user) to merge.

  This is literally how Amazon's original Dynamo paper (and Riak, which
  implemented it) handled shopping cart conflicts: rather than silently
  picking a winner (LWW) and losing an item, present BOTH cart versions
  and let application logic union them — because for carts, merging
  [A,B] and [A,C] into [A,B,C] is safe and correct, unlike overwriting.
```

## Part 4 — CRDTs: Data Structures That Merge Automatically, Correctly

---

"CRDTs (Conflict-free Replicated Data Types) go one step further than vector clocks —
instead of just detecting a conflict and punting to the application, the DATA STRUCTURE
itself is designed mathematically so that ANY merge order produces the same, correct
result. No conflict resolution logic needed at the application layer at all."

```
G-COUNTER (Grow-only Counter) — simplest CRDT example:

  Each node keeps its OWN increment count, never decrements, never
  overwrites another node's count:

  US-EAST's view:  {US-EAST: 5, EU-WEST: 3}   (total = 8)
  EU-WEST's view:  {US-EAST: 4, EU-WEST: 3}   (total = 7, hasn't seen
                                                US-EAST's latest increment yet)

  MERGE = take the MAX of each node's counter, per node:
  merged = {US-EAST: max(5,4)=5, EU-WEST: max(3,3)=3}   (total = 8)

  This merge is commutative, associative, idempotent — merge in ANY order,
  ANY number of times, and you get the same correct total. No timestamps,
  no "which one wins" decision needed at all.
```

```
OTHER COMMON CRDTs:

  PN-Counter:       G-Counter that also supports decrement (two G-Counters
                     internally — one for increments, one for decrements)
  OR-Set:            a set supporting add/remove that merges without losing
                     concurrent adds (this is what makes "shared shopping
                     cart" or "collaborative to-do list" mergeable safely)
  LWW-Register:      a single value using per-field timestamps to merge —
                     this is literally what CRDT-based systems use UNDER
                     THE HOOD for fields where LWW's data-loss risk is
                     actually acceptable (e.g. a "display name" field)

  Real systems using CRDTs: Redis (CRDT-based Active-Active in Redis
  Enterprise), Riak, Automerge/Yjs (collaborative text editing — this is
  literally how Google Docs-style concurrent editing merges keystrokes
  from multiple users without a central lock).
```

## Part 5 — Decision Framework

---

```
Q1: Is losing a concurrent write occasionally acceptable for this field?
    (e.g. "last viewed timestamp", a non-critical display preference)
    │
    YES ──► LWW. Simplest, cheapest, no extra metadata.
    │
    NO
    │
Q2: Can the data type be modeled as something with a well-defined,
    mathematically mergeable structure (counter, set, map of LWW-registers)?
    │
    YES ──► CRDT. No application-level merge logic needed, ever.
    │
    NO — the merge logic is genuinely business-specific (e.g. "merge two
    versions of a document with conflicting paragraph edits")
    │
    ──► Vector clocks to DETECT the conflict, then custom application-level
        merge logic (or present both versions to a human) to resolve it.
```

## Interview Traps & Cross-Questions

---

```
Q: "Why not just use wall-clock timestamps everywhere for LWW?"
A: "Clock skew across regions/nodes (even with NTP, drift of tens of
    milliseconds is normal) can make an objectively earlier write appear to
    'win' due to a fast clock, silently discarding a legitimately later
    write. This is exactly why some systems use logical clocks (Lamport
    timestamps, hybrid logical clocks) instead of raw wall-clock time for
    ordering causally related events."

Q: "Do vector clocks scale to thousands of nodes?"
A: "The vector grows with the number of distinct writer nodes, which is a
    real cost — this is why most production uses either cap it to a bounded
    set of known replicas (not one entry per client), or move to CRDTs which
    don't require carrying a full per-node vector at all."

Q: "If CRDTs auto-merge without conflicts, why doesn't everyone just use them?"
A: "Not every data type has a natural CRDT formulation — arbitrary business
    invariants (e.g. 'account balance can never go negative') don't merge
    safely just because the underlying counter type does. CRDTs solve
    STRUCTURAL merge, not business RULE enforcement across concurrent
    writes — you still need to design carefully for invariants that
    span the merged result."
```
