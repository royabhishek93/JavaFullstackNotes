## Part 1 — The Problem: Stateless vs Stateful

---

"Everything we do with a plain Kafka consumer is what's called **stateless processing**.
Each event is independent. The consumer doesn't need to remember anything from before.

Classic examples — send a notification, write to a database, call another service.
Every event stands on its own."

```
STATELESS — plain Kafka consumer handles this perfectly:

  Order arrives ──► [ Consumer ] ──► send email ✓
  Order arrives ──► [ Consumer ] ──► send email ✓
  Order arrives ──► [ Consumer ] ──► send email ✓

  No memory needed. Process and forget.
```

"But now the business asks: **what's the total revenue per customer, in real time?**

That's a fundamentally different problem. The answer to that question depends on
*this* event AND every event before it. That's **stateful processing**."

```
STATEFUL — output depends on history:

  Events arriving:
  ┌──────────────────────────────────────────────────────────┐
  │  t=1: Customer-A  ₹50                                    │
  │  t=2: Customer-B  ₹30                                    │
  │  t=3: Customer-A  ₹70  ← must remember t=1 to answer    │
  │  t=4: Customer-A  ₹20  ← must remember t=1 and t=3      │
  └──────────────────────────────────────────────────────────┘

  Required output (real-time):
  ┌──────────────┬──────────┐
  │  Customer-A  │  ₹140    │  = ₹50 + ₹70 + ₹20
  │  Customer-B  │  ₹30     │
  └──────────────┴──────────┘

  This is NOT possible with a plain Kafka consumer — it was designed for stateless.
```

## Part 2 — What If We Don't Have Kafka Streams? (Three Failed Approaches)

---

"So teams naturally try to solve this without Kafka Streams.
Let me walk you through the three approaches I've seen teams try —
and exactly why each breaks in production."

---

### Approach 1 — In-Memory HashMap

---

```
ATTEMPT 1: Keep state in JVM memory

  @KafkaListener(topics = "orders")
  public void consume(OrderEvent event) {
      revenueMap.merge(
          event.getCustomerId(),
          event.getAmount(),
          Double::sum
      );
  }
  Map<String, Double> revenueMap = new ConcurrentHashMap<>();
```

"Works perfectly in local testing. Breaks the moment you hit production."

```
PROBLEM 1 — Application crash → state gone:

  t=0     : processed 1,00,000 events, map fully built in JVM heap
  t=1hr   : ECS task OOM kill / deployment / pod restart
                             ↓
             revenueMap = {}  ← completely wiped

  To recover: replay ALL events from offset 0
  During replay: reports show wrong data
  Replay time: could be hours if backlog is large

PROBLEM 2 — Multiple instances → split data:

  Order topic (2 partitions):
  ┌─────────────────────┐    ┌─────────────────────┐
  │   Partition 0        │    │   Partition 1        │
  │  A:₹50, B:₹30        │    │  A:₹70, C:₹90        │
  └─────────────────────┘    └─────────────────────┘
            │                           │
   ┌────────────────┐         ┌────────────────┐
   │  Consumer-1    │         │  Consumer-2    │
   │  A→₹50, B→₹30 │         │  A→₹70, C→₹90 │  ← Customer-A is SPLIT
   └────────────────┘         └────────────────┘

  Neither consumer has the full answer for Customer-A.
  No cross-JVM memory sharing. Both have partial truth.
```

---

### Approach 2 — MySQL as State Store

---

```
ATTEMPT 2: Persist state in MySQL

  @KafkaListener(topics = "orders")
  public void consume(OrderEvent event) {
      RevenueRecord r = repo.findById(event.getCustomerId()); // SELECT
      repo.save(r.addAmount(event.getAmount()));              // UPDATE
  }
```

"Now what happens at 1 lakh events per second?"

```
PROBLEM 3 — Database becomes the bottleneck:

  1,00,000 events/sec
       ↓
  1,00,000 SELECT  +  1,00,000 UPDATE  =  2,00,000 DB ops/sec

  MySQL throughput ceiling:  ~5,000-10,000 transactions/sec
  Our requirement:           2,00,000 ops/sec
                              ↓
  Connection pool exhaustion → consumer thread blocks →
  Kafka consumer lag explodes → consumers kicked from group →
  Rebalance loop → no processing happening at all

  MySQL was designed for OLTP, not as a streaming state store.
```

## Part 4 — Core Architecture (What the Interviewer Really Wants)

---

"Let me walk you through the internal model — topology, tasks, RocksDB —
because this is where the depth comes in."

```
TOPOLOGY — the processing pipeline:

  Everything in Kafka Streams is expressed as a Topology.
  A Topology is a DAG (Directed Acyclic Graph) of nodes.

  Three node types:
  ┌───────────────┬──────────────────────────────────────────────────┐
  │  Source Node  │  reads records from a Kafka topic                 │
  │  Processor    │  transforms/filters/aggregates records            │
  │  Sink Node    │  writes records to a Kafka topic                  │
  └───────────────┴──────────────────────────────────────────────────┘

  Example topology:
  [Source: orders topic]
       │
       ▼
  [Filter: amount > 0]
       │
       ▼
  [GroupBy: customerId]  ← repartition happens here if key changed
       │
       ▼
  [Count]  ← stateful, uses RocksDB
       │
       ▼
  [Sink: order-count-output topic]
```

```
TASKS — the unit of parallelism:

  Kafka Streams splits a topology into tasks.
  Number of tasks = number of input topic partitions.

  Order topic: 4 partitions → 4 tasks created

  ┌─────────────────────────────────────────────────────────────────┐
  │  Task-0: owns Partition-0, has its own RocksDB instance         │
  │  Task-1: owns Partition-1, has its own RocksDB instance         │
  │  Task-2: owns Partition-2, has its own RocksDB instance         │
  │  Task-3: owns Partition-3, has its own RocksDB instance         │
  └─────────────────────────────────────────────────────────────────┘

  Tasks are distributed across stream threads and app instances.
  If you have 2 ECS tasks with 2 threads each → each thread handles 1 task.

  IMPORTANT: max parallelism = number of partitions.
  8 app instances with 4 partitions → only 4 do work, 4 idle.
  Adding more instances beyond partition count does nothing.
```

```
ROCKSDB — why it beats MySQL for this job:

  RocksDB is an embedded key-value store (like SQLite but optimized for writes).
  Runs INSIDE your JVM. No network. Pure local disk access.

  Plain consumer with MySQL:        Kafka Streams with RocksDB:
  Consumer ──► network ──► MySQL    Processor ──► local disk
  1-5ms per operation               < 0.1ms per operation
  Max ~10k ops/sec before lock       Handles 1M+ ops/sec

  RocksDB + Changelog:
  ┌─────────────────────────────────────────────────────────────┐
  │  Every write to RocksDB also goes to a Kafka changelog topic │
  │  (compacted topic — keeps only the latest value per key)     │
  │                                                              │
  │  On crash: read changelog topic → rebuild RocksDB state      │
  │  On scale-out: new task reads its partition's changelog       │
  │  Recovery time: seconds (not hours of event replay)          │
  └─────────────────────────────────────────────────────────────┘
```

```
REPARTITION — solving multi-instance partial state:

  Before repartition (key = orderId):
  Partition-0: [order-1: A:₹50], [order-2: B:₹30]
  Partition-1: [order-3: A:₹70], [order-4: C:₹90]

  Task-0 has: A:₹50, B:₹30  ← partial A
  Task-1 has: A:₹70, C:₹90  ← partial A

  When you call groupBy(customerId):
  Kafka Streams creates an internal repartition topic
  Routes ALL events for Customer-A to the SAME partition
  Now one task owns ALL of Customer-A's events

  After repartition (key = customerId):
  Task-0: owns Customer-A → sees A:₹50, A:₹70, A:₹20 → A:₹140 ✓
  Task-1: owns Customer-B, Customer-C → correct totals ✓
```

## Part 5 — KStream vs KTable vs GlobalKTable

---

"This is the question that trips people up — especially the GlobalKTable.
Let me walk through all three clearly."

```
KSTREAM — unbounded stream of independent events:

  Every record is a NEW independent fact.
  KStream<String, Order>:
  ──[A:₹50]──[B:₹30]──[A:₹70]──[C:₹90]──[A:₹20]──►  (never ends)

  Think: append-only log. Every event is preserved.
  Use for: raw events, transformations, enrichment at event level.

KTABLE — materialized view, latest value per key:

  Every new record for a key OVERWRITES the previous value.
  Backed by RocksDB. Replicated to one task per partition.

  KTable<String, Double> (revenue state):
  ┌──────────────┬─────────┐
  │  Customer-A  │  ₹140   │  ← updated as events arrive
  │  Customer-B  │  ₹30    │
  └──────────────┴─────────┘

  IMPORTANT: KTable is partition-scoped.
  Task-0 only sees keys routed to its partition.
  For a join: if the lookup key isn't in this partition → no result.
  That's why joins with KTable require repartition first.

  Use for: aggregations, per-key current state, joins where repartition is ok.

GLOBALKTABLE — replicated to ALL tasks, every partition:

  Unlike KTable, GlobalKTable reads from ALL partitions of its source topic
  and broadcasts the full dataset to every task.

  ┌──────────────────────────────────────────────────────────────┐
  │  KTable:                     GlobalKTable:                   │
  │  Task-0: Customer-A, B       Task-0: ALL customers           │
  │  Task-1: Customer-C, D       Task-1: ALL customers           │
  │                              Task-2: ALL customers           │
  │  Join fails if key not       Join always succeeds —          │
  │  in current partition        full lookup available           │
  └──────────────────────────────────────────────────────────────┘

  Use GlobalKTable when:
  - The lookup table is relatively small (fits in memory per node)
  - You want to avoid repartition overhead
  - Classic use: country codes, currency rates, product catalog

  Use KTable when:
  - The table is large (partitioned is fine)
  - You've already repartitioned by the join key
```

"Here's how I explain this in an interview — when you join an order stream
with customer profiles, if you use KTable you need to repartition orders
by customerId first. That's an extra internal Kafka topic. If your customer
profile table is small — say under 50MB — I use GlobalKTable instead.
Zero repartition, simpler topology, and the join always finds a match."

```
WHEN TO USE WHICH:

  ┌────────────────────┬──────────────┬──────────────────────────────┐
  │                    │  KTable       │  GlobalKTable                 │
  ├────────────────────┼──────────────┼──────────────────────────────┤
  │  Data distribution │  Partitioned  │  Replicated to ALL tasks      │
  │  Memory per node   │  1/N of total │  Full copy on each node        │
  │  Join repartition  │  Required     │  Not needed                   │
  │  Table size        │  Any size     │  Small-medium (< few hundred MB)│
  │  Use case          │  Large state  │  Config, rates, catalog        │
  └────────────────────┴──────────────┴──────────────────────────────┘
```

## Part 6 — Time Concepts (Confuses Most Engineers)

---

"Three time concepts. Most engineers conflate them. Interviewers test this specifically."

```
THREE TIMES:

  ┌──────────────────┬────────────────────────────────────────────────────┐
  │  Event Time      │  When the event ACTUALLY happened in the real world │
  │                  │  Stored INSIDE your payload: order.createdAt        │
  │                  │  Most accurate for business logic                   │
  ├──────────────────┼────────────────────────────────────────────────────┤
  │  Record Time     │  When Kafka received it                             │
  │  (default)       │  Two sub-types:                                     │
  │                  │  • Producer timestamp (default): set by producer    │
  │                  │  • Log append time: set by broker on write          │
  │                  │  Stored in Kafka record METADATA, outside payload   │
  ├──────────────────┼────────────────────────────────────────────────────┤
  │  Stream Time     │  Highest record timestamp SEEN SO FAR               │
  │  (key concept)   │  Always moves FORWARD, never backward               │
  │                  │  Used by Kafka Streams to decide when windows close  │
  └──────────────────┴────────────────────────────────────────────────────┘

  Stream time progression:
  Event at 10:31 → stream time = 10:31
  Event at 10:32 → stream time = 10:32
  Event at 10:41 → stream time = 10:41
  Event at 10:33 → stream time stays 10:41  ← late event, no rollback

  WHY stream time matters:
  Window closes when:  stream_time  >  window_end  [+ grace_period]
  Kafka does NOT use wall clock. It knows only "what timestamps have I seen?"

  To use event time instead of record time:
  Implement TimestampExtractor:
  public class OrderTimestampExtractor implements TimestampExtractor {
      @Override
      public long extract(ConsumerRecord<Object, Object> record, long previousTimestamp) {
          Order order = (Order) record.value();
          return order.getCreatedAt().toEpochMilli();  // use payload timestamp
      }
  }
  // register in application.properties:
  // spring.kafka.streams.properties.default.timestamp.extractor=...OrderTimestampExtractor
```

## Part 7 — Stateless Processing Nodes

---

"Think of the topology as a tree. Stateless nodes process each record independently —
no RocksDB, no memory, just transform and pass forward."

```
FILTER — keep or drop records:

  orders.filter((key, order) -> order.getAmount() > 1000)

  [A:₹50] ──► filter > 1000 ──► dropped ✗
  [A:₹1500] ─► filter > 1000 ──► passes ✓

MAP / MAP VALUES / SELECT KEY:

  map         → change key AND value (eligible for repartition)
  mapValues   → change value only    (no repartition, safer)
  selectKey   → change key only      (eligible for repartition)

  // Change key from orderId to customerId:
  orders.selectKey((orderId, order) -> order.getCustomerId())

  Key rule: whenever key changes → that stream is ELIGIBLE for repartition.
  Repartition doesn't happen immediately — it happens when a downstream
  stateful operation (groupBy / join) actually needs it.

SPLIT/BRANCH vs Multiple Filters — important distinction:

  // BAD: both conditions evaluated for every record
  KStream<> high = orders.filter((k,v) -> v.getAmount() > 2000);
  KStream<> low  = orders.filter((k,v) -> v.getAmount() <= 2000);
  // a record with amount=2500 goes into BOTH streams if both conditions true
  // 2 filter evaluations per record always

  // GOOD: split is if-else — first match wins, rest skipped
  Map<String, KStream<>> branches = orders.split()
      .branch((k,v) -> v.getAmount() > 2000, Branched.as("premium"))
      .branch((k,v) -> v.getAmount() > 500,  Branched.as("regular"))
      .defaultBranch(Branched.as("low"));
  // amount=2500 → "premium" only. Evaluation stops.

  Use split when paths are mutually exclusive.
  Use multiple filters when one record can legitimately appear in multiple streams.

MERGE — combine streams back together:

  KStream<> merged = premiumOrders.merge(regularOrders);
  // prerequisite: same key type, same value type
```

## Part 8 — Stateful Processing Nodes

---

"This is where the real power is. Stateful nodes maintain state in RocksDB."

```
GROUP BY KEY vs GROUP BY:

  groupByKey → use existing key, no key change
               → no repartition (key not changed)

  groupBy    → specify a NEW key
               → repartition will happen when downstream stateful op runs

  orders.groupByKey()                         // use existing key
  orders.groupBy((k, order) -> order.getCustomerId())  // change to customerId

COUNT — simplest stateful op:

  KTable<String, Long> orderCount = orders
      .groupByKey()
      .count(Materialized.as("order-count-store"));
  // RocksDB: Customer-A → 3, Customer-B → 1

AGGREGATE — custom aggregation logic:

  KTable<String, Double> revenue = orders
      .groupBy((k, order) -> order.getCustomerId(),
               Grouped.with(Serdes.String(), orderSerde))
      .aggregate(
          () -> 0.0,                                    // initializer: first time seen
          (customerId, order, currentTotal) ->           // aggregator: update state
              currentTotal + order.getAmount(),
          Materialized.<String, Double, KeyValueStore<Bytes, byte[]>>
              as("revenue-store")
              .withValueSerde(Serdes.Double())
      );

  Flow:
  First event Customer-A ₹50:
    RocksDB lookup → not found → initializer → 0.0
    aggregator: 0.0 + 50 = 50.0 → write to RocksDB
  Second event Customer-A ₹70:
    RocksDB lookup → found → 50.0
    aggregator: 50.0 + 70 = 120.0 → write to RocksDB
```

## Part 9 — Joins (Three Types, Three Rules)

---

"Joins are where architects distinguish themselves. Three join types, very different behaviors."

```
KSTREAM → KTABLE JOIN (enrich events with latest state):

  Use case: order event + customer profile → enriched order

  KStream<String, Order>         orders   = builder.stream("order-events");
  KTable<String, CustomerProfile> profiles = builder.table("customer-profiles");

  // KEY RULE: join key must be the SAME for both sides
  // orders key = orderId → must selectKey to customerId first
  KStream<String, Order> ordersByCustomer = orders
      .selectKey((orderId, order) -> order.getCustomerId());

  KStream<String, EnrichedOrder> enriched = ordersByCustomer.join(
      profiles,
      (order, profile) -> new EnrichedOrder(order, profile.getName())
  );

  Behavior:
  ┌─────────────────────────────────────────────────────────────────┐
  │  Order for Customer-A arrives                                   │
  │  KTable lookup: find Customer-A's latest profile in RocksDB     │
  │  Found → join and enrich                                        │
  │  Not found → LEFT JOIN returns null for profile side            │
  │              INNER JOIN drops the record                        │
  └─────────────────────────────────────────────────────────────────┘

  Types: inner join (default), left join, outer join — same as SQL semantics.

KSTREAM → GLOBALKTABLE JOIN (no repartition needed):

  // Same pattern but with GlobalKTable — no selectKey repartition needed
  // because GlobalKTable has ALL keys available locally on every task
  GlobalKTable<String, CustomerProfile> profiles =
      builder.globalTable("customer-profiles");

  KStream<String, EnrichedOrder> enriched = orders.join(
      profiles,
      (orderId, order) -> order.getCustomerId(),  // key extractor — which key to look up
      (order, profile) -> new EnrichedOrder(order, profile.getName())
  );
  // No repartition topic created. Simpler. Faster. Use for small reference tables.

KSTREAM → KSTREAM JOIN (two event streams, windowed):

  Use case: correlate two event streams — payment event + fraud check event
  Must use a TIME WINDOW — both events must arrive within the window

  KStream<String, PaymentEvent>    payments = builder.stream("payments");
  KStream<String, FraudCheckEvent> frauds   = builder.stream("fraud-checks");

  KStream<String, CorrelatedEvent> correlated = payments.join(
      frauds,
      (payment, fraud) -> new CorrelatedEvent(payment, fraud),
      JoinWindows.ofTimeDifferenceWithNoGrace(Duration.ofMinutes(5)),
      StreamJoined.with(Serdes.String(), paymentSerde, fraudSerde)
  );

  ┌──────────────────────────────────────────────────────────────────┐
  │  Payment-A arrives at 10:00                                      │
  │  FraudCheck-A arrives at 10:03 → within 5-min window → JOINED ✓ │
  │  FraudCheck-A arrives at 10:07 → outside window → NOT JOINED ✗  │
  │                                                                  │
  │  Both streams are buffered in RocksDB until match or expiry      │
  └──────────────────────────────────────────────────────────────────┘

  IMPORTANT: KStream-KStream join uses RocksDB as a windowed buffer.
  Both sides must be co-partitioned (same key, same number of partitions).

JOIN COMPARISON:
  ┌─────────────────────┬──────────────┬─────────────────────────────────┐
  │  Join Type          │  Repartition │  Time window required?           │
  ├─────────────────────┼──────────────┼─────────────────────────────────┤
  │  KStream → KTable   │  Yes (key)   │  No (latest KTable value used)  │
  │  KStream → GKTable  │  No          │  No                             │
  │  KStream → KStream  │  Yes (key)   │  Yes (windowed join)            │
  │  KTable  → KTable   │  Yes (key)   │  No                             │
  └─────────────────────┴──────────────┴─────────────────────────────────┘
```

## Part 10 — Windowing Deep Dive

---

"Three window types. The interviewer will give you a use case and ask which one.
Let me walk you through each with the exact decision logic."

```
STREAM TIME — controls window closure:

  Stream time = highest record timestamp seen so far (always forward)
  Window closes when: stream_time > (window_end + grace_period)

  Kafka doesn't use wall clock. It works on "what events have I seen?"
  A burst of messages at 2am doesn't mean 2am is "now" — stream time is.
```

### Tumbling Window — Fixed size, no overlap

```
TUMBLING — each record in exactly ONE window:

  Window size: 5 minutes. Windows: [10:00-10:05), [10:05-10:10), [10:10-10:15)...
  (start inclusive, end exclusive)

  Events:  [10:31] [10:32]            [10:41] [10:43]
  Windows:  └──10:30-10:35──┘          └──10:40-10:45──┘
              count=2                      count=2

  RocksDB window store (not simple key-value):
  ┌──────────────┬──────────────┬──────────────┬───────┐
  │  Key         │  Win Start   │  Win End     │ Count │
  ├──────────────┼──────────────┼──────────────┼───────┤
  │  Customer-A  │  10:30       │  10:35       │  2    │
  │  Customer-A  │  10:40       │  10:45       │  2    │
  └──────────────┴──────────────┴──────────────┴───────┘

  Return type: KTable<Windowed<String>, Long>
               ↑ not plain String — wrapped with window start + end

  Without grace (closes immediately when stream time passes window end):
  .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(5)))

  With grace (waits for late events):
  .windowedBy(
      TimeWindows.of(Duration.ofMinutes(5)).grace(Duration.ofMinutes(2))
  )
  // window stays open until: stream_time > (window_end + 2 min)
  // a late event arriving 1m 59s after window end → still accepted

  USE CASE: revenue per hour, orders per 5 minutes, API calls per minute
```

### Hopping Window — Fixed size, overlapping

```
HOPPING — record belongs to MULTIPLE windows:

  Size=10min, advance=5min:
  Window-1: [10:00-10:10]
  Window-2: [10:05-10:15]  ← overlap
  Window-3: [10:10-10:20]  ← overlap

  Event at 10:07:
  ─ falls into Window-1 (10:00-10:10) ✓
  ─ falls into Window-2 (10:05-10:15) ✓
  ─ 1 event counted in 2 windows

  .windowedBy(
      TimeWindows.of(Duration.ofMinutes(10))
                 .advanceBy(Duration.ofMinutes(5))
                 .grace(Duration.ofMinutes(1))
  )

  USE CASE: "show me orders in last 1 hour, refresh every 5 minutes"
  — you want a rolling window updated more frequently than its size
  — typical dashboard scenario
```

### Session Window — Event-based, dynamic size

```
SESSION — events close together = one session:

  Inactivity gap: 5 minutes

  Events: [10:27]──[10:29]             (silence > 5min)             [10:41]
              └─── Session-1 ───┘                              └── Session-2 ┘
              start:10:27, end:10:29                           start:10:41, end:10:41
              count: 2                                         count: 1

  Window extends as long as events keep arriving within inactivity gap.
  New session starts after the gap.

  MERGE scenario — bridging event:
  Session-1: [10:27-10:29]    Session-2: [10:36]
  Late event at 10:32 arrives:
    10:32 - 10:29 = 3min < 5min gap → can extend Session-1 end to 10:32
    10:36 - 10:32 = 4min < 5min gap → 10:32 bridges to Session-2
    → MERGE: Session-1 and Session-2 become [10:27-10:36], count=3

  ┌──────────────────────────────────────────────────────────────┐
  │  Sessions can MERGE when a late event bridges two sessions   │
  │  This is unique to session windows — no other type merges    │
  └──────────────────────────────────────────────────────────────┘

  .windowedBy(SessionWindows.ofInactivityGapWithNoGrace(Duration.ofMinutes(5)))

  USE CASE: user session analysis, browse duration, activity burst detection
```

```
WINDOW DECISION GUIDE:

  Q: Fixed time buckets, no overlap?          → Tumbling
  Q: Overlapping rolling window?              → Hopping
  Q: Group by user activity with inactivity?  → Session

  ┌─────────────┬──────────────┬─────────────┬──────────────────────────┐
  │  Type       │  Size        │  Overlap?   │  Classic use case        │
  ├─────────────┼──────────────┼─────────────┼──────────────────────────┤
  │  Tumbling   │  Fixed       │  No         │  Revenue per hour        │
  │  Hopping    │  Fixed       │  Yes        │  1hr window, refresh 5m  │
  │  Session    │  Dynamic     │  No         │  User session duration   │
  └─────────────┴──────────────┴─────────────┴──────────────────────────┘
```

## Part 11 — Interactive Queries (Architect Differentiator)

---

"This is what separates mid-level from architect answers.
Kafka Streams lets you query the RocksDB state directly — without going through a Kafka topic."

```
THE PROBLEM WITHOUT INTERACTIVE QUERIES:

  Normally to get aggregated state:
  Kafka Streams → output topic → another consumer → database → REST API → client
                  (delay)           (latency)

  With Interactive Queries:
  REST API → Kafka Streams RocksDB → response in milliseconds
             (direct, no extra hop)

IMPLEMENTATION:

  // Name your state store
  KTable<String, Double> revenue = orders
      .groupByKey()
      .aggregate(
          () -> 0.0,
          (k, v, total) -> total + v.getAmount(),
          Materialized.as("revenue-store")  ← named store
      );

  // Query it from a REST endpoint:
  @RestController
  public class RevenueQueryController {

      @Autowired
      private KafkaStreams kafkaStreams;

      @GetMapping("/revenue/{customerId}")
      public Double getRevenue(@PathVariable String customerId) {
          ReadOnlyKeyValueStore<String, Double> store =
              kafkaStreams.store(
                  StoreQueryParameters.fromNameAndType(
                      "revenue-store",
                      QueryableStoreTypes.keyValueStore()
                  )
              );
          return store.get(customerId);  // direct RocksDB lookup
      }
  }

  FOR WINDOWED STORES:
  ReadOnlyWindowStore<String, Long> windowStore =
      kafkaStreams.store(
          StoreQueryParameters.fromNameAndType(
              "windowed-order-count",
              QueryableStoreTypes.windowStore()
          )
      );
  // query a specific window:
  WindowStoreIterator<Long> iter = windowStore.fetch(
      "Customer-A",
      Instant.parse("2024-01-01T10:00:00Z"),
      Instant.parse("2024-01-01T11:00:00Z")
  );

MULTI-INSTANCE CONSIDERATION:

  Your key may be in Task-2 on Instance-2, but the REST call hits Instance-1.

  ┌─────────────────────────────────────────────────────────────────────┐
  │  Instance-1                  Instance-2                             │
  │  Task-0 (Partition-0)        Task-1 (Partition-1)                  │
  │  RocksDB: A, B               RocksDB: C, D                         │
  │                                                                      │
  │  GET /revenue/C hits Instance-1 → key C not here                   │
  │  Solution: use kafkaStreams.metadataForKey() to find which instance  │
  │            owns the key, then proxy the request to that instance    │
  └─────────────────────────────────────────────────────────────────────┘

  // Find which host owns a key:
  KeyQueryMetadata metadata = kafkaStreams.queryMetadataForKey(
      "revenue-store", "Customer-C", Serdes.String().serializer()
  );
  HostInfo host = metadata.activeHost();
  // proxy request to host.host() + ":" + host.port()
```

"In production we build a small routing layer in the REST controller —
if the key is local, serve it directly. If it's remote, proxy to the right instance.
This is how you build a zero-latency read API on top of a streaming pipeline."

## Part 12 — Exactly-Once Semantics (EOS)

---

"Interviewers always ask about exactly-once. Here's the honest answer —
including when NOT to use it."

```
THREE PROCESSING GUARANTEES:

  at-most-once:   may lose events, never duplicates
                  → processing.guarantee = at_least_once (and acking before processing)
                  → use when you can tolerate loss (metrics, non-critical events)

  at-least-once:  no data loss, may duplicate
                  → processing.guarantee = at_least_once (default)
                  → safe if your downstream is idempotent

  exactly-once:   no loss, no duplicates — end-to-end
                  → processing.guarantee = exactly_once_v2
                  → Kafka transactions: read + process + write are atomic

EOS MECHANICS:

  Without EOS (at-least-once):
  ┌──────────────────────────────────────────────────────────────────┐
  │  Read from Kafka → Process → Write to output topic → Commit      │
  │  If crash AFTER write but BEFORE commit:                         │
  │    → On restart: re-reads same event                             │
  │    → Processes again → writes DUPLICATE to output topic          │
  └──────────────────────────────────────────────────────────────────┘

  With EOS (exactly_once_v2):
  ┌──────────────────────────────────────────────────────────────────┐
  │  All three wrapped in a Kafka transaction:                       │
  │  BEGIN TRANSACTION                                               │
  │    Read offsets + process + write to output topic                │
  │    Write to changelog topic                                      │
  │    Commit offsets                                                │
  │  COMMIT TRANSACTION (atomic)                                     │
  │                                                                  │
  │  If crash before commit: entire transaction rolled back          │
  │  Consumer of output topic: reads only committed messages         │
  └──────────────────────────────────────────────────────────────────┘

COST OF EOS:

  EOS adds ~20-30% latency overhead (transaction coordination with brokers)
  Requires Kafka 2.5+ and exactly_once_v2 (v1 had scalability issues)

  My production rule:
  ┌─────────────────────────────────────────────────────────────────┐
  │  Use EOS when:  financial transactions, order state, billing     │
  │  Skip EOS when: metrics aggregation, analytics, dashboards       │
  │                 (your downstream is idempotent anyway)           │
  └─────────────────────────────────────────────────────────────────┘
```

## Part 13 — Error Handling (What Junior Engineers Skip)

---

"Production Kafka Streams without error handling is a disaster waiting to happen.
Let me walk you through the three layers I always set up."

```
LAYER 1: Deserialization errors

  When a malformed event arrives, default behavior:
  → Kafka Streams LOG_AND_FAIL → application shuts down
  → one bad message takes down the entire app

  Better: LOG_AND_CONTINUE or send to Dead Letter Topic

  @Bean
  public KafkaStreamsCustomizer kafkaStreamsCustomizer() {
      return kafkaStreams -> kafkaStreams.setUncaughtExceptionHandler(
          exception -> StreamsUncaughtExceptionHandler.StreamThreadExceptionResponse.REPLACE_THREAD
          // restart the thread, don't kill the app
      );
  }

  // In application.yml:
  spring:
    kafka:
      streams:
        properties:
          default.deserialization.exception.handler:
            org.apache.kafka.streams.errors.LogAndContinueExceptionHandler
          # or for DLT: implement DeserializationExceptionHandler

LAYER 2: Processing errors (your business logic throws)

  @Bean
  public KStream<String, Order> ordersStream(StreamsBuilder builder) {
      return builder.stream("orders")
          .mapValues(order -> {
              try {
                  return processOrder(order);
              } catch (Exception e) {
                  // send to dead letter topic
                  deadLetterTemplate.send("orders-dlt", order);
                  return null;  // filter out in next step
              }
          })
          .filter((k, v) -> v != null);
  }

LAYER 3: Uncaught exception handler

  kafkaStreams.setUncaughtExceptionHandler(ex -> {
      if (ex instanceof RecoverableException) {
          return REPLACE_THREAD;    // restart the thread
      }
      return SHUTDOWN_APPLICATION;  // unrecoverable — alert oncall
  });

  THREAD EXCEPTION RESPONSES:
  ┌─────────────────────────┬────────────────────────────────────────┐
  │  REPLACE_THREAD          │  Kill failed thread, start new one     │
  │                          │  App continues, tasks redistributed    │
  ├─────────────────────────┼────────────────────────────────────────┤
  │  SHUTDOWN_CLIENT         │  Graceful shutdown of this instance    │
  │                          │  Other instances take over tasks       │
  ├─────────────────────────┼────────────────────────────────────────┤
  │  SHUTDOWN_APPLICATION    │  Broadcast shutdown to all instances   │
  │                          │  Use for corrupted state / poison pill │
  └─────────────────────────┴────────────────────────────────────────┘
```

## Part 14 — Standby Replicas (Fast Failover)

---

"In production, if a task fails, the new task must restore state from the changelog.
For a large state store, that could take 30-60 seconds. That's processing lag.

Standby replicas pre-warm that state in the background so failover is near-instant."

```
WITHOUT STANDBY REPLICAS:

  Task-0 on Instance-1 crashes:
  ├── Instance-2 assigned Task-0
  ├── Instance-2 downloads changelog from Kafka
  ├── Rebuilds RocksDB (could take seconds to minutes)
  └── Only then: Task-0 resumes processing
  (during this time: Task-0's partition is not being processed)

WITH STANDBY REPLICAS (num.standby.replicas = 1):

  Instance-2 ALREADY has a warm copy of Task-0's state (kept in sync)
  Task-0 on Instance-1 crashes:
  ├── Instance-2 is assigned Task-0
  ├── Applies only the delta (missed events during crash window)
  └── Resumes processing in seconds, not minutes

  spring:
    kafka:
      streams:
        properties:
          num.standby.replicas: 1   # 1 warm copy per task

  COST: each standby replica doubles your RocksDB storage
  BENEFIT: near-zero downtime on task failure
  MY RULE: use standby replicas for any stateful app in production
```

## Part 15 — Parallelism Model

---

"This is a common production gotcha. Teams throw more instances at Kafka Streams
and wonder why throughput doesn't increase."

```
PARALLELISM CEILING = NUMBER OF INPUT PARTITIONS:

  Order topic: 4 partitions

  Scenario 1: 1 instance, 4 threads
  ┌─────────────────────────────────┐
  │  Instance-1                     │
  │  Thread-1 → Task-0 (Partition-0)│
  │  Thread-2 → Task-1 (Partition-1)│
  │  Thread-3 → Task-2 (Partition-2)│
  │  Thread-4 → Task-3 (Partition-3)│
  └─────────────────────────────────┘
  All 4 partitions utilized ✓

  Scenario 2: 2 instances, 2 threads each
  ┌──────────────────────┐  ┌──────────────────────┐
  │  Instance-1          │  │  Instance-2          │
  │  Thread-1 → Task-0   │  │  Thread-1 → Task-2   │
  │  Thread-2 → Task-1   │  │  Thread-2 → Task-3   │
  └──────────────────────┘  └──────────────────────┘
  All 4 partitions utilized ✓

  Scenario 3: 5 instances, 1 thread each
  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
  │  I-1   │ │  I-2   │ │  I-3   │ │  I-4   │ │  I-5   │
  │ Task-0 │ │ Task-1 │ │ Task-2 │ │ Task-3 │ │ IDLE   │
  └────────┘ └────────┘ └────────┘ └────────┘ └────────┘
  Instance-5 sits idle. Wasted compute. ✗

  RULE: max useful parallelism = partition count
  To scale further: increase partition count first (irreversible, plan ahead)

  num.stream.threads (per instance):
  spring.kafka.streams.properties.num.stream.threads=4
  One JVM can handle multiple tasks via threads — you may not need multiple instances
  until you're CPU-bound within a single JVM.
```

## Part 16 — Production Gotchas (War Stories)

---

"These are the things that will absolutely bite you in production.
I've seen every one of these cause incidents."

```
GOTCHA 1: Changing application.id = losing all state

  application-id is used as:
  ├── Consumer group ID
  ├── Changelog topic prefix: <app-id>-<store-name>-changelog
  └── Repartition topic prefix: <app-id>-<topic>-repartition

  If you rename application-id:
  → New consumer group → starts from latest offset (or earliest)
  → New changelog topic → all prior state is gone
  → You've effectively reset your entire streaming app

  Production rule: treat application-id as immutable after first deploy.
  If you MUST change it: use the streams reset tool to wipe old state cleanly.

GOTCHA 2: Rebalancing stops processing

  During a Kafka Streams rebalance (new instance joins, task crashes, deployment):
  → ALL processing stops across ALL tasks while Kafka reassigns partitions
  → Depending on state store size, standby replicas, and partition count:
     could be seconds to minutes of zero processing

  Mitigation:
  ├── num.standby.replicas=1        (warm state, fast restore)
  ├── session.timeout.ms (tune)     (don't trigger rebalance on GC pause)
  └── Deploy one instance at a time (rolling deploy, not all-at-once)

GOTCHA 3: Repartition topic retention

  Internal repartition topics created by Kafka Streams:
  Default retention = whatever your Kafka broker default is (often 7 days)
  If topic fills up → consumer lag alert fires → on-call gets paged

  Production rule: monitor internal topic sizes
  Topic naming: <app-id>-<name>-repartition, <app-id>-<name>-changelog

GOTCHA 4: Partition count mismatch on join

  KStream-KStream join requires BOTH topics to have the SAME partition count
  AND SAME key (co-partitioned)

  If orders has 6 partitions and payments has 4 partitions:
  → Kafka Streams throws TopologyException at startup
  → Fix: repartition one topic to match the other BEFORE the join

GOTCHA 5: State store grows unboundedly

  For aggregations without windowing:
  KTable accumulates state for every key it's ever seen
  Customer churn → old keys never evicted → RocksDB grows forever

  For windowed aggregations: windows expire automatically
  For unbounded KTable: implement periodic compaction or use TTL via custom stores
```

```java
@Configuration
@EnableKafkaStreams
public class RevenueStreamTopology {

    @Bean
    public KStream<String, Order> buildTopology(StreamsBuilder builder) {

        // Source
        KStream<String, Order> orders = builder.stream(
            "order-events",
            Consumed.with(Serdes.String(), new JsonSerde<>(Order.class))
        );

        // GlobalKTable for small reference data (no repartition needed)
        GlobalKTable<String, CustomerProfile> profiles =
            builder.globalTable("customer-profiles",
                Consumed.with(Serdes.String(), new JsonSerde<>(CustomerProfile.class)));

        // Enrich without repartition
        KStream<String, EnrichedOrder> enriched = orders.join(
            profiles,
            (orderId, order) -> order.getCustomerId(),
            (order, profile) -> new EnrichedOrder(order, profile.getName())
        );

        // Aggregate: total revenue per customer
        KTable<String, Double> revenue = enriched
            .groupBy(
                (k, enrichedOrder) -> enrichedOrder.getCustomerId(),
                Grouped.with(Serdes.String(), new JsonSerde<>(EnrichedOrder.class))
            )
            .aggregate(
                () -> 0.0,
                (customerId, order, total) -> total + order.getAmount(),
                Materialized.<String, Double, KeyValueStore<Bytes, byte[]>>
                    as("revenue-store-v1")
                    .withValueSerde(Serdes.Double())
            );

        // Windowed: orders in last 5 minutes
        KTable<Windowed<String>, Long> windowedOrders = enriched
            .groupBy((k, o) -> o.getCustomerId(),
                     Grouped.with(Serdes.String(), new JsonSerde<>(EnrichedOrder.class)))
            .windowedBy(
                TimeWindows.of(Duration.ofMinutes(5)).grace(Duration.ofMinutes(1))
            )
            .count(Materialized.as("windowed-count-v1"));

        // Sink
        revenue.toStream()
            .to("revenue-output", Produced.with(Serdes.String(), Serdes.Double()));

        return orders;
    }

    // Expose state via REST (Interactive Queries)
    @Bean
    public RevenueQueryService revenueQueryService(KafkaStreams kafkaStreams) {
        return new RevenueQueryService(kafkaStreams);
    }
}
```

## Part 19 — The 60-Second Answer

---

> "Kafka Streams solves stateful stream processing — where your output depends on the history
> of events, not just the current one. Think real-time revenue aggregation, leaderboards,
> windowed reporting, stream enrichment.
>
> Without it, you try in-memory HashMaps — they die on crash and give wrong answers with
> multiple instances. You try MySQL — it can't sustain 100k ops per second. You end up
> building your own windowing and crash recovery code, which is just a worse version of
> Kafka Streams.
>
> Kafka Streams is a library in your Spring Boot app — no extra cluster. It uses RocksDB
> on local disk for sub-millisecond state access, backs everything to a Kafka changelog topic,
> and restores state automatically after a crash without full event replay.
>
> The topology model gives you KStream for event-by-event processing and KTable for
> materialized current state. You join them — KStream enriched by KTable lookup,
> or KStream-KStream via windowed joins. For small lookup tables you use GlobalKTable
> to avoid repartition overhead entirely.
>
> For time-bounded queries: Tumbling windows for non-overlapping buckets,
> Hopping for rolling overlapping windows, Session for activity-burst grouping.
>
> In production I run it on ECS Fargate against AWS MSK. Exactly-once for financial flows,
> at-least-once for analytics. Standby replicas for near-zero-downtime failover.
> Interactive queries to expose RocksDB state directly via REST — no extra hop through Kafka.
>
> The gotcha I always warn teams about: application.id is effectively immutable after deploy.
> Change it and you lose all your accumulated state silently."
