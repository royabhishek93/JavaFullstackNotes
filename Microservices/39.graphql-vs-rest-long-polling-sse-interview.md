## Opening — When Interviewer Asks "REST or GraphQL — How Do You Decide?"

---

"This isn't really a 'which is better' question — REST and GraphQL solve different
shaped problems. REST models resources with fixed endpoint shapes; GraphQL lets the
client specify exactly what fields it needs in one request. The decision comes down
to how varied your clients' data needs are, and whether you're willing to take on
GraphQL's operational complexity for that flexibility."

---

## Part 1 — The Core Difference

---

```
REST — fixed shape per endpoint:

  GET /orders/123
  → ALWAYS returns the full order shape the server decided:
    { id, status, items, customer, shipping_address, billing_address,
      payment_method, created_at, updated_at, ... }

  Mobile screen that only needs {id, status, total} still receives
  the ENTIRE payload — OVER-FETCHING.

  A dashboard needing order + customer + shipping in one screen makes
  3 SEPARATE REST calls (or the backend builds a bespoke aggregating
  endpoint just for that one screen) — UNDER-FETCHING, solved by either
  more round trips or endpoint proliferation.


GraphQL — client specifies exact shape, in one request:

  query {
    order(id: "123") {
      id
      status
      total
      customer { name, email }      ← nested, from a DIFFERENT service/resolver
      shipping { address, carrier }  ← nested, from ANOTHER service/resolver
    }
  }

  → returns EXACTLY these fields, nested from potentially different
  backend services, in ONE round trip, no over-fetching, no under-fetching.
```

## Part 2 — What GraphQL Actually Costs You (The Part People Skip)

---

```
1. N+1 QUERY PROBLEM AT THE RESOLVER LEVEL:
   query { orders { customer { name } } }  — fetching 100 orders, each
   resolving its own customer, naively fires 100 separate customer lookups.
   FIX: DataLoader pattern — batch and cache resolver calls within a
   single request, turning 100 individual lookups into 1 batched call.

2. CACHING IS HARDER:
   REST's GET /orders/123 is trivially cacheable by URL (CDN, HTTP cache).
   GraphQL's single POST /graphql endpoint with a varying query body in
   the request isn't cacheable the same simple way — needs
   application-level caching (persisted queries, response caching keyed
   on the query+variables hash) instead of free HTTP-layer caching.

3. QUERY COMPLEXITY / ABUSE RISK:
   A malicious or naive deeply-nested query can force the server to do
   an enormous amount of resolver work from a small request payload —
   REST's fixed endpoints don't have this specific risk shape. GraphQL
   servers need query depth/complexity limits to prevent this.

4. NO FREE HTTP STATUS CODES:
   GraphQL typically returns HTTP 200 even for a field-level error
   (embedded in a "errors" array in the body) — REST's HTTP status codes
   (404, 403, 500) map naturally onto its resource model; GraphQL's error
   handling is a different, less standardized convention per client library.
```

"My actual decision rule: GraphQL earns its complexity when you have genuinely varied
clients with different data needs (mobile vs web vs partner integrations) hitting a
complex, multi-service data graph — think a BFF's job (see
33.api-gateway-bff-pattern-interview.md), but pushed down to the API contract itself.
For a simple service with one consumer and a straightforward resource model, REST is
simpler to build, cache, and secure, and I don't reach for GraphQL by default."

## Part 3 — Real-Time Alternatives Below Full WebSocket

---

"Not every 'real-time-ish' feature needs a full WebSocket connection — there are
two lighter options worth knowing when the interaction is simpler than true
bidirectional messaging."

```
LONG POLLING:

  Client ──GET /updates──► Server
                             │ (server HOLDS the connection open,
                             │  doesn't respond immediately)
                             │ ... waits until new data exists ...
  Client ◄──response with new data───│
  Client immediately re-issues GET /updates ──►  (repeat)

  Simulates push using plain HTTP request/response — works through any
  proxy/firewall that already allows HTTP, no special protocol upgrade
  needed. Cost: each "wait" ties up a server connection/thread, and
  there's request overhead (headers) on every cycle, however brief.
  Good for: infrequent updates, simplicity, environments where WebSocket
  upgrades are blocked by strict corporate proxies.


SERVER-SENT EVENTS (SSE):

  Client ──GET /stream (Accept: text/event-stream)──► Server
  Server keeps the connection open and pushes events over time:

    data: {"orderId": 123, "status": "shipped"}

    data: {"orderId": 124, "status": "delivered"}

  ONE-WAY only (server → client). Built on plain HTTP, auto-reconnects
  natively in browsers (EventSource API handles reconnection for you,
  unlike raw WebSocket where you write your own reconnect logic).
  Good for: live notification feeds, live score updates, log streaming —
  anything push-only where the client never needs to send data back
  over the same connection.


WEBSOCKET (for comparison — see the networking protocols file for full depth):

  Full-duplex, bidirectional, persistent connection. Needed when the
  CLIENT also needs to send frequent messages back (chat, live
  collaborative editing, multiplayer/gaming) — SSE and long polling are
  both push-only from the server's side and don't fit that shape.
```

---

## Part 4 — Decision Framework

---

```
Q1: Does the client need to send frequent messages back over the same
    connection (chat, live cursors, gaming)?
    │
    YES ──► WebSocket
    │
    NO — server just needs to PUSH updates to the client
    │
Q2: Are updates frequent/continuous (live stock ticker, live logs)?
    │
    YES ──► Server-Sent Events (simpler than WebSocket, auto-reconnect,
    │       plain HTTP, one-way is all you need anyway)
    │
    NO — updates are infrequent, or you need to support environments
    that block HTTP upgrades/long-lived streaming connections
    │
    ──► Long polling (simplest, most compatible, acceptable latency
        for infrequent updates)
```

## Interview Traps & Cross-Questions

---

```
Q: "Is GraphQL always better for mobile because it avoids over-fetching?"
A: "It helps, but a well-designed BFF (see 33.api-gateway-bff-pattern-interview.md)
    tailored to mobile's exact needs solves over-fetching too, with REST's
    simpler caching and operational model. GraphQL is one way to solve
    over-fetching, not the only way — I weigh its resolver/caching/query-abuse
    complexity against a purpose-built BFF before defaulting to it."

Q: "Why would you ever use long polling instead of SSE, which sounds strictly better?"
A: "Some older infrastructure/proxies handle plain request/response more
    reliably than long-lived streaming connections, and long polling
    requires zero special client support (just repeated HTTP calls) — SSE
    needs EventSource support or a polyfill in less common client
    environments. For genuinely infrequent updates, the simplicity often
    wins over SSE's marginal efficiency gain."

Q: "Can SSE send binary data or complex structured payloads?"
A: "SSE is text-based (UTF-8) by protocol — you can absolutely send JSON as
    text within the `data:` field (as shown above), but truly binary data
    isn't natively supported the way WebSocket's binary frames are."
```

## Quick Reference Card

```
CHOICE          DIRECTION       TRANSPORT        BEST FOR
─────────────────────────────────────────────────────────────────────────────
REST             request/response  HTTP              simple resource CRUD, easy caching
GraphQL          request/response  HTTP (1 endpoint)  varied clients, complex data graphs
Long polling      server push (via  HTTP              infrequent updates, max compatibility
                 repeated requests)
SSE              server push only  HTTP (streamed)    frequent one-way updates, auto-reconnect
WebSocket         full bidirectional custom protocol   chat, gaming, collaborative editing
```
