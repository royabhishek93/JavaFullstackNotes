## THE STORY: Flipkart Order Placement

> **Start here if you are new. Read this like a story.**

A customer on Flipkart clicks "Place Order." What must happen?

```
FLIPKART ORDER FLOW — WHAT NEEDS TO HAPPEN
============================================

  Customer clicks "Place Order"
         |
         v
  +------------------+
  | OrderService     |  1. Save order to database (MySQL)
  | (Spring Boot)    |  2. Publish "OrderPlaced" event to Kafka
  +------------------+     so that:
         |                   - InventoryService reserves stock
         |                   - NotificationService sends email/SMS
         |                   - PaymentService initiates payment
         v
  +------------------+     +------------------+     +------------------+
  | InventoryService |     | NotificationSvc  |     | PaymentService   |
  | (reserves stock) |     | (sends email/SMS)|     | (initiates pay)  |
  +------------------+     +------------------+     +------------------+

  OrderService must do TWO things:
  - Write to MySQL (database)
  - Write to Kafka (message broker)

  THESE ARE TWO SEPARATE SYSTEMS.
  This is the fundamental problem.
```

## PROBLEM 1 — The Dual-Write Problem

> **This is the core problem the Transactional Outbox pattern solves.**

### WITHOUT Transactional Outbox

> Every developer's first instinct is to write to the database, then publish
> the event. This looks fine. But what happens when something goes wrong between
> those two steps?

```
DUAL-WRITE — THREE FAILURE SCENARIOS
======================================

  SCENARIO A — Happy path (works fine):
  ----------------------------------------
  OrderService:
  1. INSERT order INTO orders_table  -> SUCCESS
  2. Publish to Kafka "OrderPlaced"  -> SUCCESS
  Inventory reserves stock. Email sent. All good.


  SCENARIO B — Kafka is down when you try to publish:
  ----------------------------------------------------
  OrderService:
  1. INSERT order INTO orders_table  -> SUCCESS  (order saved!)
  2. Publish to Kafka "OrderPlaced"  -> FAILURE  (Kafka is down)
  Result:
  - Order IS saved in the database
  - Kafka event NEVER sent
  - Inventory NEVER reserved  <- stock not reserved
  - Customer NEVER gets email  <- no confirmation
  - Payment NEVER initiated   <- order stuck
  - Customer paid but no fulfillment = DISASTER


  SCENARIO C — App crashes between step 1 and step 2:
  ----------------------------------------------------
  OrderService:
  1. INSERT order INTO orders_table  -> SUCCESS
  [server crashes here — OOM, power cut, deployment restart]
  2. Publish to Kafka "OrderPlaced"  -> NEVER HAPPENS
  Same result as Scenario B — silent data loss.
```

**What developers try WITHOUT the outbox pattern:**

```java
// OrderService.java — the NAIVE approach
@Transactional
public Order placeOrder(OrderRequest request) {
    // Step 1: save to database
    Order order = orderRepository.save(new Order(request));

    // Step 2: publish to Kafka
    // If this throws, the @Transactional will rollback the DB write
    // But what if this succeeds and then the DB commit fails?
    // What if the app crashes after line above but before DB commit?
    kafkaTemplate.send("order-placed", new OrderPlacedEvent(order.getId()));

    return order;
    // @Transactional commits here
    // Database commit and Kafka publish are NOT atomic
    // These are two separate systems — they cannot be in one transaction
}
```

> Key insight: **You cannot put a Kafka publish inside a `@Transactional` block
> and expect atomicity.** `@Transactional` only covers the database. Kafka does not
> participate in database transactions. The two operations are independent.

## PROBLEM 2 — Trying to Fix It With Retry (And Why It Fails)

> Some developers add try-catch and retry. This creates a new problem.

```java
// RETRY APPROACH — still broken
@Transactional
public Order placeOrder(OrderRequest request) {
    Order order = orderRepository.save(new Order(request));

    // Retry loop
    int attempts = 0;
    while (attempts < 3) {
        try {
            kafkaTemplate.send("order-placed", new OrderPlacedEvent(order));
            break;
        } catch (Exception e) {
            attempts++;
            if (attempts == 3) {
                // What do you do here?
                // Option A: throw — DB rolls back, but the event may have
                //           already been sent on attempt 1 or 2!
                // Option B: swallow — order saved, event lost silently
                // BOTH OPTIONS ARE WRONG
                throw new RuntimeException("Kafka failed after retries", e);
            }
        }
    }
    return order;
}
```

```
RETRY APPROACH — WHAT CAN GO WRONG
=====================================

  Attempt 1: Kafka send -> network timeout (but message may have arrived!)
  Attempt 2: Kafka send -> SUCCESS (duplicate event!)
  Kafka broker received BOTH attempt 1 and attempt 2

  InventoryService processes event 1: reserve 1 unit of stock
  InventoryService processes event 2: reserve another unit of stock
  Customer ordered 1 item but 2 units reserved.

  OR:

  Attempts 1,2,3 all fail -> throw exception -> @Transactional rollbacks DB
  Order record deleted. Customer's order is gone.
  But Kafka may have received attempt 1 or 2 already.
  Event sent for an order that no longer exists in DB.
```

## THE MENTAL MODEL — What Transactional Outbox Solves

> **Read this once and you will explain the pattern clearly in any interview.**

```
THE OUTBOX MENTAL MODEL
========================

  THE ROOT CAUSE:
  ---------------
  Database commit and Kafka publish are two separate operations.
  One can succeed while the other fails.
  There is no way to make them atomic together natively.


  THE INSIGHT:
  ------------
  What IS atomic with a database write?
  Another database write in the same transaction!

  Instead of: save order + publish to Kafka (two systems, not atomic)
  Do this:    save order + save event to outbox table (one system, atomic!)


  TWO-STEP APPROACH:
  ------------------
  Step 1 (inside @Transactional — atomic):
    - INSERT order into orders table
    - INSERT event into outbox table      <- same transaction!
    Both committed or both rolled back. Always consistent.

  Step 2 (separate process — retryable):
    - Message Relay reads from outbox table
    - Publishes to Kafka
    - Marks event as published in outbox
    If this fails: retry. The event is still in the outbox table.
    Kafka never receives duplicates from a crashed write.


  DATABASE                    KAFKA
  --------                    -----
  orders table    <-- SAME --> outbox table --> Message Relay --> Kafka
  (business data)  TRANSACTION (pending events)  (publisher)
```

## PROBLEM 3 — Two Wrong Answers Interviewers Will Overrule

> **Interviewers often present these two answers to test if you know the gaps.
> Learn both and why they fail before you give the correct outbox answer.**

### Wrong Answer 1 — @Transactional + catch-and-rethrow

> First instinct: wrap everything in @Transactional. If Kafka throws, rethrow the
> exception so Spring rolls back the DB. Looks correct at first glance.

```java
@Transactional
public Order placeOrder(OrderRequest request) {
    Order order = orderRepository.save(Order.from(request));
    try {
        kafkaTemplate.send("order-placed", new OrderPlacedEvent(order));
    } catch (Exception e) {
        throw new RuntimeException(e);  // trigger DB rollback
    }
    return order;
}
```

> **Why this gets overruled:**
>
> The gap is the ACK loss scenario. Kafka has two steps — the producer sends the
> message, and the broker sends an acknowledgement back. What if the message
> REACHED the Kafka broker successfully, but the ACK packet was lost on the network
> on the way back to your application?
>
> Your application receives an exception (timeout waiting for ACK). It throws.
> Spring rolls back the DB. Order does not exist in DB. But Kafka has the event —
> it was published. InventoryService and PaymentService receive the event and try
> to process an order that does not exist in the database.

```
THE ACK LOSS SCENARIO — WHY WRONG ANSWER 1 FAILS
==================================================

  DB:       INSERT order            -> SUCCESS (committed)
  Kafka:    send "OrderPlaced"      -> Message REACHED broker
  Network:  ACK packet from broker  -> LOST (network blip)

  Your app: thinks Kafka failed     -> throws exception
  Spring:   @Transactional rollback -> DB order DELETED

  Reality:
  DB:       order does NOT exist
  Kafka:    OrderPlaced event EXISTS and being consumed downstream

  InventoryService: receives OrderPlaced, tries to reserve stock for order 1234
  DB lookup:        SELECT * FROM orders WHERE id = 1234 -> NOT FOUND
  Result:           data inconsistency — downstream acted on a ghost order
```

---

### Wrong Answer 2 — Two-Phase Commit (2PC)

> Second instinct: use distributed transactions. Use a coordinator that runs a
> "prepare" phase with both DB and Kafka, then a "commit" phase. Classic 2PC.
>
> **Why this gets overruled:**
>
> Kafka does NOT support the two-phase commit protocol. For 2PC to work, all
> participants must understand the prepare/commit/rollback protocol. Kafka only
> supports a simpler transactional API within its own ecosystem — it cannot act
> as a participant in a cross-system XA transaction alongside a relational DB.
>
> So even if you build the coordinator, Kafka cannot respond to the prepare phase.
> The discussion stops there."

```
2PC — WHY IT FAILS WITH KAFKA
================================

  Two-Phase Commit requires:
  1. Coordinator sends PREPARE to all participants
  2. Participants respond READY or ABORT
  3. If all READY: coordinator sends COMMIT to all
  4. All participants commit atomically

  Works for: MySQL + PostgreSQL (both support XA transactions)

  For MySQL + Kafka:
  Coordinator -> MySQL:  PREPARE  -> MySQL: READY
  Coordinator -> Kafka:  PREPARE  -> Kafka: ??? (Kafka does not understand this)

  Kafka does not implement XA / 2PC protocol.
  There is no "prepare" phase in Kafka's protocol.
  This answer is always rejected.

  The only correct answer: Transactional Outbox pattern.
```

## OPENING — "What is the Transactional Outbox pattern and why do you need it?"

> **You say:**
>
> "Let me explain this with the Flipkart order placement flow.
>
> When a customer places an order, OrderService needs to do two things: save the
> order to MySQL, and publish an OrderPlaced event to Kafka so that inventory gets
> reserved and the customer gets a confirmation email.
>
> These are two separate systems. MySQL and Kafka have no shared transaction.
> If we save to MySQL and then publish to Kafka, and Kafka is temporarily down —
> the order is saved but no downstream service ever knows about it. The customer's
> order is orphaned. If the app crashes between the MySQL commit and the Kafka
> publish — same problem, silently.
>
> The Transactional Outbox pattern solves this by never writing to Kafka directly
> from OrderService. Instead, OrderService writes the event to an outbox table in
> MySQL within the same database transaction as the order. Now saving the order
> and recording the event are atomic — they succeed together or fail together.
>
> A separate process called the Message Relay reads from the outbox table and
> publishes to Kafka. If the relay fails, it retries — the event is still in the
> outbox. The relay guarantees at-least-once delivery to Kafka."

```
TRANSACTIONAL OUTBOX — THE BIG PICTURE
========================================

  WITHOUT OUTBOX:                         WITH OUTBOX:
  ---------------                         ------------

  OrderService                            OrderService
  @Transactional                          @Transactional
  |-- save order to MySQL  ✅             |-- save order to MySQL    ✅
  |-- publish to Kafka     ❌ (can fail)  |-- save event to outbox   ✅ (atomic!)
      ^                                       (same MySQL transaction)
      |
      Not atomic with MySQL!                  Message Relay (separate process)
      Failure = silent data loss              |-- read outbox table
                                              |-- publish to Kafka
                                              |-- mark as published
                                              If Kafka fails: retry. Event is safe.


  MYSQL (single system — atomic):         KAFKA (published by relay):
  --------------------------------        ----------------------------
  orders table:                           Topic: order-placed
  | id | status | total |                 Messages: OrderPlaced events
  +----|--------|-------|
  | 1  | PLACED | 5000  |

  outbox table:
  | id | event_type    | payload   | published | created_at |
  |----|---------------|-----------|-----------|------------|
  | 1  | ORDER_PLACED  | {"id":1}  | false     | 2026-08-19 |
```

## PART 1 — "Show me the outbox table structure and the Spring Boot code"

> **You say:**
>
> "The outbox table sits in the same database as your business tables. It has a
> few important columns. Event type identifies what happened. Payload is the
> full JSON of the event — I store it as JSON so the relay can publish it as-is
> without knowing the schema. Published flag tells the relay which events have
> already been sent. Aggregate type and ID help with ordering — for example, all
> events for order ID 1 should be processed in sequence.
>
> In OrderService, the code is straightforward. The @Transactional annotation covers
> both the order insert and the outbox insert. If anything fails, both roll back.
> The order does not exist in the database without its corresponding outbox event,
> and vice versa."

```
OUTBOX TABLE DDL:
------------------
CREATE TABLE outbox_events (
    id            BIGINT AUTO_INCREMENT PRIMARY KEY,
    aggregate_id  VARCHAR(255) NOT NULL,    -- e.g. order ID
    aggregate_type VARCHAR(255) NOT NULL,   -- e.g. "Order"
    event_type    VARCHAR(255) NOT NULL,    -- e.g. "OrderPlaced"
    payload       JSON         NOT NULL,    -- full event as JSON
    published     BOOLEAN      DEFAULT FALSE,
    created_at    TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_published (published, created_at)  -- relay queries this
);
```

```java
// OutboxEvent.java — JPA entity
@Entity
@Table(name = "outbox_events")
public class OutboxEvent {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String aggregateId;
    private String aggregateType;
    private String eventType;

    @Column(columnDefinition = "JSON")
    private String payload;

    private boolean published = false;
    private LocalDateTime createdAt = LocalDateTime.now();
}


// OrderService.java — the correct approach
@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orderRepository;
    private final OutboxEventRepository outboxEventRepository;
    private final ObjectMapper objectMapper;

    @Transactional   // covers BOTH writes below — atomic!
    public Order placeOrder(OrderRequest request) {
        // Step 1: save business data
        Order order = orderRepository.save(Order.from(request));

        // Step 2: save event to outbox — same transaction, not Kafka directly
        OrderPlacedEvent event = new OrderPlacedEvent(
            order.getId(),
            order.getUserId(),
            order.getTotalAmount(),
            order.getItems()
        );

        outboxEventRepository.save(OutboxEvent.builder()
            .aggregateId(order.getId().toString())
            .aggregateType("Order")
            .eventType("OrderPlaced")
            .payload(objectMapper.writeValueAsString(event))
            .build());

        // NO kafkaTemplate.send() here
        return order;
    }
}
```

**One-liner:**
> "One @Transactional covers both the order insert and the outbox insert.
> If the DB fails, both roll back. Kafka is never touched in OrderService."

## PART 2 — "How does the Message Relay work? How does it read and publish?"

> **You say:**
>
> "There are two approaches: polling publisher and CDC.
>
> Polling publisher is the simpler one. A Spring scheduled task runs every few
> seconds, queries the outbox table for unpublished events, publishes them to
> Kafka, and marks them as published. It is simple to implement and works well
> for most use cases. The downside is latency — events are not published instantly
> but within the polling interval, typically 5-10 seconds.
>
> CDC — Change Data Capture — is the production-grade approach at Flipkart's scale.
> We use Debezium, which connects directly to MySQL's binary log (binlog). The
> binlog is a record of every change to the database. Debezium tails this log in
> real time and when it sees an insert into the outbox table, it immediately
> publishes that event to Kafka. Latency is milliseconds. No polling, no database
> load from periodic queries.
>
> The key advantage of CDC is that Debezium runs outside your application process.
> Even if every OrderService instance is down, Debezium keeps reading the binlog
> and publishing events. You do not need your application to be running to drain
> the outbox."

```
TWO RELAY APPROACHES
======================

  APPROACH 1 — POLLING PUBLISHER (simple):
  -----------------------------------------

  // 3-state status model (more production-safe than boolean):
  // TO_BE_PROCESSED -> IN_PROGRESS -> PROCESSED
  // IN_PROGRESS acts as a lock — other relay instances skip these rows

  @Component
  public class OutboxPoller {

      private final OutboxEventRepository outboxRepo;
      private final KafkaTemplate<String, String> kafkaTemplate;

      @Scheduled(fixedDelay = 5000)   // every 5 seconds
      @Transactional
      public void pollAndPublish() {
          // SELECT ... WHERE status = TO_BE_PROCESSED FOR UPDATE SKIP LOCKED
          List<OutboxEvent> pending = outboxRepo
              .findByStatusOrderByCreatedAtAsc(
                  "TO_BE_PROCESSED", PageRequest.of(0, 100));

          // Mark IN_PROGRESS first (acts as distributed lock)
          pending.forEach(e -> e.setStatus("IN_PROGRESS"));
          outboxRepo.saveAll(pending);

          for (OutboxEvent event : pending) {
              try {
                  kafkaTemplate.send(
                      topicFor(event.getAggregateType()),
                      event.getAggregateId(),
                      event.getPayload()).get();   // wait for ACK

                  event.setStatus("PROCESSED");
                  outboxRepo.save(event);
              } catch (Exception e) {
                  // Leave as IN_PROGRESS — a cleanup job resets stale IN_PROGRESS
                  // after a timeout (e.g. IN_PROGRESS for > 5 min = reset to TO_BE_PROCESSED)
                  break;   // stop batch — preserve ordering for this key
              }
          }
      }
  }

  // Outbox status flow:
  // INSERT: TO_BE_PROCESSED
  // Relay picks up: IN_PROGRESS  (locked — other instances skip)
  // Kafka ACK received: PROCESSED (never picked again)
  // Relay crashed mid-batch: stays IN_PROGRESS -> cleanup job resets after timeout

  Latency:    5-10 seconds (polling interval)
  Complexity: Low — just a Spring @Scheduled method
  Use when:   Small scale, near-realtime not required

  POLLING — 5 DISADVANTAGES (interviewer will ask this):
  -------------------------------------------------------
  1. MULTI-INSTANCE ORDERING PROBLEM
     3 app instances = 3 pollers running simultaneously
     All 3 query unpublished rows at the same time
     Instance A picks events 1,2,3 for order-key-1
     Instance B picks event 4 for order-key-1
     Instance B publishes event 4 BEFORE instance A publishes 1,2,3
     Order broken: cancelled before created
     Fix: FOR UPDATE SKIP LOCKED + IN_PROGRESS status lock

  2. POLLING GAP DELAY
     Event created at 10:00:00.000
     Next poll runs at 10:00:05.000
     5 second delay before event reaches Kafka
     Not suitable for real-time requirements

  3. CONSTANT DB LOAD
     Scheduler runs every 5 seconds regardless of whether events exist
     At 3 AM with zero events: still queries DB 12 times per minute
     At Big Billion Days peak: DB already under heavy load + polling adds more

  4. DB CLEANUP REQUIRED
     Outbox table grows indefinitely without cleanup
     Processed rows must be deleted/archived periodically
     At 1M orders/hour = 1M outbox rows/hour = 24M rows/day

  5. DUPLICATE PROCESSING
     Relay publishes to Kafka -> Kafka ACK received
     Before relay updates status to PROCESSED: relay crashes
     Next poll: same row still has TO_BE_PROCESSED or IN_PROGRESS
     Relay publishes again -> duplicate event in Kafka
     Consumer MUST be idempotent (inbox pattern required)

  These 5 disadvantages are why CDC is preferred at Flipkart scale.


  APPROACH 2 — CDC WITH DEBEZIUM (production):
  ----------------------------------------------

  MySQL binlog:                   Debezium connector:
  (record of all DB changes)      (reads binlog in real time)
  |                                |
  | INSERT outbox_events           | Detects insert
  | (id=1, event_type=OrderPlaced) | immediately
  |                                |
  |                                v
  |                           Publishes to Kafka
  |                           Topic: flipkart.outbox.events
  |                           (within milliseconds)

  Debezium runs as a Kafka Connect connector:
  - Connects to MySQL binlog using replication protocol
  - Stateless — no polling queries, no load on MySQL
  - Runs independently — OrderService does not need to be up
  - Survives restarts — picks up from binlog position where it stopped

  Latency:    Milliseconds (real time from binlog)
  Complexity: Medium — Kafka Connect + Debezium setup
  Use when:   High scale, real-time requirements, Flipkart-level traffic


  POLLING vs CDC — DECISION:
  --------------------------
  Polling:   simpler, slight latency, adds DB query load at scale
  CDC:       real-time, no DB load, resilient, preferred for production
```

**One-liner:**
> "Polling is simple — @Scheduled queries outbox every 5s. CDC (Debezium) tails
> the MySQL binlog in real time — millisecond latency, no polling queries,
> runs independent of the application."

## PART 3 — "What about duplicate events? What if the relay publishes the same event twice?"

> **You say:**
>
> "The outbox pattern guarantees at-least-once delivery. It does NOT guarantee
> exactly-once. Here is why duplicates can happen.
>
> The relay reads from the outbox, publishes to Kafka, and marks as published.
> These three steps are not atomic. If the relay crashes after publishing to
> Kafka but before marking as published — it restarts and republishes the same
> event. Kafka receives it twice.
>
> The fix is not to prevent duplicates on the producer side — it is to make
> consumers idempotent on the consumer side.
>
> For InventoryService: it receives OrderPlaced, reserves stock. If the same
> OrderPlaced event arrives again — before reserving stock, check if we already
> processed this event ID. Store processed event IDs in a processed_events table.
> If the event ID is already there, skip it. This is the Inbox pattern — the
> consumer side counterpart to the Outbox.
>
> At Flipkart's scale, we also configure Kafka producers with idempotent delivery
> — the producer assigns a sequence number to each message. If the broker receives
> the same sequence number twice, it deduplicates at the broker level. But consumer
> idempotency is still required as a second layer of defence."

```
DUPLICATE EVENT HANDLING
=========================

  WHY DUPLICATES HAPPEN:
  ----------------------
  Message Relay:
  1. Read event from outbox                  ✅
  2. kafkaTemplate.send("OrderPlaced")       ✅  (Kafka received it)
  3. Mark event as published in outbox       ❌  (relay crashes here!)

  Relay restarts:
  1. Read same event from outbox (still unpublished)
  2. kafkaTemplate.send("OrderPlaced")       ✅  (Kafka receives it AGAIN)
  Kafka now has 2 copies of OrderPlaced for the same order.


  FIX — IDEMPOTENT CONSUMER (Inbox Pattern):
  -------------------------------------------

  CREATE TABLE processed_events (
      event_id      VARCHAR(255) PRIMARY KEY,  -- outbox event UUID
      processed_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
  );


  // InventoryService — idempotent event handler
  @KafkaListener(topics = "order-placed")
  @Transactional
  public void onOrderPlaced(OrderPlacedEvent event) {

      // Check if already processed — same transaction as the business logic
      if (processedEventRepo.existsById(event.getEventId())) {
          log.info("Duplicate event ignored: {}", event.getEventId());
          return;   // skip — already handled
      }

      // Process the event (reserve stock)
      inventoryService.reserveStock(event.getOrderId(), event.getItems());

      // Mark as processed — same transaction as reserveStock
      processedEventRepo.save(new ProcessedEvent(event.getEventId()));
  }

  Both "reserve stock" and "record event ID" in one @Transactional.
  If reservation fails: both roll back. Event ID not recorded. Safe to retry.
  If duplicate arrives: event ID already recorded. Skipped. Stock not double-reserved.


  KAFKA PRODUCER IDEMPOTENCY (additional layer):
  -----------------------------------------------
  spring:
    kafka:
      producer:
        enable-idempotence: true   # assigns sequence numbers
        acks: all                  # wait for all replicas to acknowledge

  Broker deduplicates based on sequence number within a session.
  Consumer idempotency still required for cross-session restarts.
```

**One-liner:**
> "Outbox guarantees at-least-once, not exactly-once. Consumer must be idempotent
> — store processed event IDs in an inbox table, check before processing.
> Both reserve-stock and record-event-ID in one @Transactional."

## PART 4 — "How do you handle ordering of events? Do events arrive in order?"

> **You say:**
>
> "Kafka preserves order within a partition, not across partitions. If all events
> for a given order go to the same Kafka partition, they are processed in order.
>
> The relay controls this by using the aggregate ID — the order ID — as the Kafka
> message key. Kafka routes all messages with the same key to the same partition.
> So all events for order 1234 go to the same partition, in the order they were
> written to the outbox table.
>
> One subtle issue: the outbox table is ordered by created_at, but under high
> concurrency two events can have the same timestamp. Using a database sequence ID
> as the sort key is safer — it is strictly monotonic within the database."

```
EVENT ORDERING — KAFKA PARTITION KEY STRATEGY
===============================================

  Outbox events for order-1234:
  | id  | aggregate_id | event_type         | created_at  |
  |-----|--------------|-------------------|-------------|
  | 101 | order-1234   | OrderPlaced        | 14:00:00.1  |
  | 102 | order-1234   | OrderConfirmed     | 14:00:00.5  |
  | 103 | order-1234   | PaymentInitiated   | 14:00:01.0  |

  Relay publishes with key = aggregate_id:
  kafkaTemplate.send("order-events", "order-1234", payload);
                                      ^
                                      Key ensures all events for
                                      order-1234 go to SAME partition

  Kafka Partition 3: [OrderPlaced] -> [OrderConfirmed] -> [PaymentInitiated]
                     (strictly in order — same partition)

  InventoryService consumes partition 3:
  Processes: OrderPlaced, then OrderConfirmed, then PaymentInitiated
  Correct order guaranteed.

  DIFFERENT orders go to different partitions (by hash of order ID):
  order-1234 -> Partition 3
  order-5678 -> Partition 7
  order-9012 -> Partition 1
  Parallel processing across orders. Sequential within each order.
```

**One-liner:**
> "Use aggregate ID (order ID) as the Kafka message key. All events for the same
> order hash to the same partition — processed in order. Different orders go
> to different partitions — parallel processing."

## PART 5 — "How do you clean up the outbox table? Does it grow forever?"

> **You say:**
>
> "Without cleanup, the outbox table grows forever and queries slow down.
> Two approaches.
>
> Simple approach: a scheduled job deletes published events older than 7 days.
> You keep recent events in case you need to replay or debug. The index on
> published and created_at makes this deletion fast.
>
> Better approach at scale: partition the outbox table by date in MySQL. Each
> day is a separate partition. To clean up, you DROP the old partition — which is
> instant in MySQL because it drops the entire partition file rather than deleting
> rows one by one. Dropping 10 million rows by DELETE takes minutes. Dropping a
> partition takes milliseconds.
>
> At Flipkart's scale during Big Billion Days — millions of orders per hour — the
> outbox table receives tens of millions of rows. Partition pruning is essential."

```
OUTBOX TABLE CLEANUP
======================

  SIMPLE APPROACH (scheduled delete):
  -------------------------------------
  @Scheduled(cron = "0 2 * * *")   // 2 AM daily
  @Transactional
  public void cleanupOutbox() {
      LocalDateTime cutoff = LocalDateTime.now().minusDays(7);
      outboxRepo.deleteByPublishedTrueAndCreatedAtBefore(cutoff);
  }
  Works for small/medium scale. Slow for millions of rows.


  PRODUCTION APPROACH (table partitioning):
  ------------------------------------------
  -- Partition by day
  CREATE TABLE outbox_events (
      id           BIGINT,
      ...
      created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
      PRIMARY KEY (id, created_at)   -- partition key must be in PK
  ) PARTITION BY RANGE (TO_DAYS(created_at)) (
      PARTITION p20260819 VALUES LESS THAN (TO_DAYS('2026-08-20')),
      PARTITION p20260820 VALUES LESS THAN (TO_DAYS('2026-08-21')),
      PARTITION future     VALUES LESS THAN MAXVALUE
  );

  -- Drop old partition (milliseconds, regardless of row count):
  ALTER TABLE outbox_events DROP PARTITION p20260819;

  vs

  -- DELETE old rows (minutes for millions of rows):
  DELETE FROM outbox_events WHERE created_at < '2026-08-20';
```

**One-liner:**
> "Scheduled delete for small scale. Table partitioning by date for production —
> DROP PARTITION is milliseconds regardless of row count.
> Keep 7 days for debugging and potential replay."

## TRAP QUESTIONS

---

### TRAP-1 — "Can't you just use Kafka transactions to solve dual-write?"

> **You say:**
>
> "Kafka transactions (KafkaTransactionManager) only coordinate within Kafka itself —
> you can publish to multiple Kafka topics atomically, or coordinate producer and
> consumer commits. They do NOT span across Kafka and a relational database.
>
> So if you use a Kafka transaction in OrderService, you still have the same problem:
> MySQL commit and Kafka publish are not atomic together. You cannot use KafkaTransactionManager
> to wrap a MySQL `@Transactional` block. They are separate transaction managers.
>
> The only true solution for dual-write across a database and a message broker
> is the outbox pattern — or XA/two-phase commit, which has very high performance
> cost and is not used at Flipkart scale."

```
KAFKA TRANSACTIONS — WHAT THEY DO AND DON'T DO
================================================

  What Kafka transactions DO:
  ---------------------------
  KafkaTemplate (transactional):
  - publish to topic A                     <- atomic
  - publish to topic B                     <- atomic together
  - commit consumer offset for topic C     <- atomic with above
  All or nothing within Kafka itself.

  What Kafka transactions DO NOT DO:
  -----------------------------------
  @Transactional   // MySQL transaction manager
  public void placeOrder(...) {
      orderRepo.save(order);               // MySQL write
      kafkaTemplate.send("order-placed");  // Kafka write
      // These are STILL not atomic.
      // MySQL and Kafka have different transaction managers.
      // Spring cannot commit both atomically.
  }

  The solution is still the outbox pattern.
  Write event to MySQL (atomic with business data).
  Relay publishes to Kafka (separate process, retryable).
```

---

### TRAP-2 — "What if two relay instances run simultaneously and publish the same event twice?"

> **You say:**
>
> "This is a real problem when you run multiple instances of the polling publisher
> for high availability. Both instances query the outbox, both see the same unpublished
> events, both publish them — duplicates.
>
> Fix: use optimistic locking or database-level SELECT FOR UPDATE SKIP LOCKED when
> reading from the outbox. SKIP LOCKED is a MySQL/PostgreSQL feature that skips rows
> already locked by another transaction. Instance 1 locks batch 1. Instance 2 gets
> batch 2. No overlap.
>
> With CDC (Debezium), this problem does not exist. Debezium is a single connector
> reading the binlog — you do not run multiple Debezium connectors for the same table.
> High availability is handled by Kafka Connect's rebalancing, not by multiple readers.
> This is another reason to prefer CDC over polling in production."

```
MULTIPLE RELAY INSTANCES — RACE CONDITION
==========================================

  POLLING (without SKIP LOCKED) — PROBLEM:
  ------------------------------------------
  Instance A: SELECT * WHERE published=false LIMIT 100  -> gets events 1-100
  Instance B: SELECT * WHERE published=false LIMIT 100  -> gets events 1-100
  (same rows! no lock yet)

  Instance A: publish event 1 to Kafka, mark published
  Instance B: publish event 1 to Kafka, mark published  <- DUPLICATE

  FIX — SELECT FOR UPDATE SKIP LOCKED:
  --------------------------------------
  Instance A: SELECT * WHERE published=false FOR UPDATE SKIP LOCKED LIMIT 100
              Locks events 1-100. Instance B skips these.
  Instance B: SELECT * WHERE published=false FOR UPDATE SKIP LOCKED LIMIT 100
              Gets events 101-200. No overlap.

  In Spring Data JPA:
  @Lock(LockModeType.PESSIMISTIC_WRITE)
  @Query("SELECT e FROM OutboxEvent e WHERE e.published = false
          ORDER BY e.createdAt ASC")
  List<OutboxEvent> findUnpublishedWithLock(Pageable pageable);
  // MySQL uses SKIP LOCKED when you add the hint via native query

  CDC (Debezium) — NO RACE CONDITION:
  -------------------------------------
  Single connector reads binlog. No SELECT queries.
  High availability via Kafka Connect leader election.
  One Debezium instance active at a time per connector.
```

### TRAP-3 — "How is Transactional Outbox different from Saga pattern?"

> **You say:**
>
> "They solve different problems and are often used together.
>
> Transactional Outbox solves the dual-write problem — how to reliably publish
> an event when you also write to a database. It is about reliable event delivery
> from a single service.
>
> Saga is a pattern for managing distributed transactions across multiple services.
> When placing an order requires coordinating OrderService, PaymentService, and
> InventoryService — and any of them can fail — Saga manages the sequence of steps
> and the compensating transactions if something fails.
>
> At Flipkart: OrderService uses the Outbox pattern to reliably publish the
> OrderPlaced event. The Saga orchestrator (or choreography) uses those events to
> coordinate the full order flow across multiple services. The Outbox is the
> reliable messaging layer underneath the Saga."

```
OUTBOX vs SAGA — DIFFERENT PROBLEMS
======================================

  TRANSACTIONAL OUTBOX:             SAGA PATTERN:
  (single service concern)          (multi-service coordination)
  ----------------------            --------------------
  "How does OrderService            "How does the entire order placement
  reliably publish an event         flow (order + payment + inventory)
  after writing to its DB?"         succeed or roll back atomically?"

  Scope: one service                Scope: multiple services
  Problem: dual-write               Problem: distributed transaction
  Solution: outbox table +          Solution: choreography (events) or
            message relay                     orchestration (saga coordinator)

  THEY WORK TOGETHER:
  -------------------
  Saga step 1: OrderService creates order
               -> Outbox publishes OrderPlaced reliably
  Saga step 2: PaymentService receives OrderPlaced
               -> Outbox publishes PaymentCompleted reliably
  Saga step 3: InventoryService receives PaymentCompleted
               -> Outbox publishes StockReserved reliably
  [Happy path complete]

  Saga compensating transaction (if InventoryService fails):
               -> Outbox publishes StockReservationFailed
  PaymentService receives it -> reverses payment
               -> Outbox publishes PaymentReversed
  OrderService receives it -> marks order as failed
```

## CDC / DEBEZIUM TRAP QUESTIONS

---

### CDC-TRAP-1 — "If Debezium crashes, does it lose any events?"

> **You say:**
>
> "No — and this is one of the best things about CDC. Let me explain why.
>
> Think of the MySQL binlog like a book with page numbers. Debezium is reading
> this book. Each time it finishes reading a page, it writes down the page number
> it just read into a Kafka topic called connect-offsets. That is its bookmark.
>
> If Debezium crashes mid-read, it loses nothing. When it restarts, it opens
> connect-offsets, finds its last saved bookmark — say page 4892713 — and
> continues reading from exactly that page. The MySQL binlog is still there,
> unchanged. No events skipped, no events lost.
>
> The one scenario that can go wrong: if Debezium stays down for so long that
> MySQL deletes the old binlog files before Debezium gets to read them. MySQL
> cleans up old binlog files automatically — by default after 7 days. If
> Debezium was down for 10 days, it comes back and says 'I need binlog.003 but
> it is gone.' At that point it has to do a full table scan — called a snapshot —
> to rebuild its state, which is expensive.
>
> Prevention: set MySQL binlog retention to at least 7 days and set up alerts
> on Debezium lag so you catch it before the binlog rotates away."

```
DEBEZIUM BOOKMARK SYSTEM — HOW IT WORKS
=========================================

  MySQL server disk:                  Kafka (connect-offsets topic):
  ------------------                  --------------------------------
  binlog.001  (old, may be deleted)
  binlog.002  (old, may be deleted)
  binlog.003  <- Debezium is here     "last read: binlog.003, pos 4892713"
  binlog.004  (future)

  Normal flow:
  Debezium reads binlog.003 pos 4892713: INSERT outbox id=101
  -> publishes to Kafka
  -> writes bookmark: { "file": "binlog.003", "pos": 4892713 }

  Debezium crashes:
  |
  Debezium restarts
  |
  Reads bookmark from connect-offsets: binlog.003 pos 4892713
  Resumes from exactly there
  Event 101 was already published before crash -> no re-publish
  Event 102 (not yet published) -> published now
  Zero events lost. Zero events skipped.


  DANGER SCENARIO — binlog rotation:
  ------------------------------------
  Day 1:  Debezium reading binlog.003
  Day 2:  Debezium crashes (stays down)
  Day 8:  MySQL auto-deletes binlog.001, binlog.002, binlog.003
  Day 9:  Debezium restarts
          Reads bookmark: "I need binlog.003"
          binlog.003 is GONE
          |
          Debezium: falls back to SNAPSHOT MODE
          Full table scan of outbox_events (slow, locks briefly)
          Starts streaming from current binlog position after scan

  FIX: set in MySQL config (my.cnf):
  expire_logs_days = 7   # keep binlogs for 7 days minimum
  Set alert: if Debezium lag > 1 day, page on-call engineer
```

**One-liner:**
> "Debezium bookmarks its position in connect-offsets Kafka topic. Restart = resume
> from bookmark, zero events lost. Only risk: binlog rotates while Debezium is
> down — prevent with binlog retention >= 7 days and lag alerts."

### CDC-TRAP-2 — "Does CDC give exactly-once delivery or can you get duplicates?"

> **You say:**
>
> "CDC is at-least-once, not exactly-once. You can get duplicates. Let me show
> you exactly where.
>
> Debezium does three things in sequence for every event. First, it reads the
> event from the binlog. Second, it publishes to Kafka. Third, it saves its
> bookmark position to the connect-offsets topic.
>
> Steps two and three — publish and save bookmark — are not atomic. Imagine
> Debezium publishes event 101 to Kafka successfully. Kafka receives it. Before
> Debezium can save the bookmark, Debezium crashes. When it restarts, it reads
> its last bookmark — which was before event 101. So it reads event 101 from
> the binlog again and publishes it again. Kafka now has two copies.
>
> This is identical to the duplicate problem with polling. The fix is also
> identical: consumers must be idempotent. When InventoryService receives
> an OrderPlaced event, it checks its processed_events table first. If that
> event ID is already there, it skips processing. This way even if the same
> event arrives 3 times, stock is reserved only once."

```
WHERE DUPLICATES CAN HAPPEN IN CDC
=====================================

  Debezium three steps (in order):
  Step 1: Read from binlog:   INSERT outbox id=101
  Step 2: Publish to Kafka:   topic=order-placed, payload={...}   <- SUCCESS
  Step 3: Save bookmark:      { "file": "binlog.003", "pos": 4892713 }
          ^
          DEBEZIUM CRASHES HERE (before step 3)

  Debezium restarts:
  Reads last bookmark: pos 4892710 (BEFORE event 101)
  Step 1 again: reads event 101 from binlog
  Step 2 again: publishes event 101 to Kafka   <- DUPLICATE

  Kafka: has event 101 twice
  InventoryService: processes it twice -> stock reserved twice -> oversell

  FIX — CONSUMER MUST BE IDEMPOTENT:
  ------------------------------------
  InventoryService:
  @KafkaListener(topics = "order-placed")
  @Transactional
  public void onOrderPlaced(OrderPlacedEvent event) {

      // Check FIRST — before any business logic
      if (processedEventRepo.existsById(event.getEventId())) {
          return;   // already processed, skip silently
      }

      // Reserve stock (business logic)
      inventoryService.reserveStock(event.getOrderId(), event.getItems());

      // Record that we processed this event — same transaction
      processedEventRepo.save(new ProcessedEvent(event.getEventId()));
  }

  Event 101 arrives first time:  not in processed_events -> reserve stock -> save id
  Event 101 arrives second time: found in processed_events -> return immediately
  Stock reserved exactly ONCE regardless of how many times event is delivered.

  Bottom line:
  CDC = at-least-once (same as polling)
  Consumer inbox pattern = required (same as polling)
  CDC advantage = lower latency + no DB polling load, NOT stronger delivery guarantee
```

**One-liner:**
> "CDC is at-least-once. Publish and bookmark-save are not atomic — crash between
> them causes duplicate. Fix: consumer checks processed_events table before acting.
> Same guarantee as polling, just faster and cheaper."

### CDC-TRAP-3 — "Does the outbox table need an is_published column when using CDC?"

> **You say:**
>
> "No — and this is a clean difference from polling. With polling, you need the
> is_published flag because the relay queries the table repeatedly and needs to
> know which rows it has already sent. Without the flag, every query returns
> all rows and you republish everything.
>
> CDC works completely differently. It reads the MySQL binlog — a forward-only
> stream of change events. When you INSERT a row into the outbox table, that
> INSERT appears exactly once in the binlog stream. Debezium reads it once,
> publishes it, and moves forward. It never goes back and re-reads that row.
> So there is no concept of 'is this row published?' — the binlog stream
> itself ensures each insert is seen exactly once.
>
> This means the CDC outbox table can be much simpler — just ID, aggregate_id,
> aggregate_type, event_type, payload, created_at. No status column, no boolean
> flag. You can even DELETE processed rows immediately after they are captured
> in the binlog — Debezium already read them, so deleting does not cause any
> re-processing."

```
is_published — POLLING NEEDS IT, CDC DOES NOT
===============================================

  POLLING reads the TABLE repeatedly:
  ------------------------------------
  Poll 1 (t=0s):  SELECT * WHERE is_published=false -> rows 1,2,3 -> send -> mark true
  Poll 2 (t=5s):  SELECT * WHERE is_published=false -> rows 4,5   -> send -> mark true
  Poll 3 (t=10s): SELECT * WHERE is_published=false -> no rows    -> nothing to do
  Without is_published: Poll 2 would return rows 1,2,3,4,5 again -> republish 1,2,3


  CDC reads the BINLOG (forward-only stream):
  --------------------------------------------
  t=0s: INSERT outbox id=1  -> binlog pos 100 -> Debezium sees it ONCE -> publish
  t=1s: INSERT outbox id=2  -> binlog pos 200 -> Debezium sees it ONCE -> publish
  t=2s: INSERT outbox id=3  -> binlog pos 300 -> Debezium sees it ONCE -> publish
  Debezium never looks back. It only moves forward.
  Row 1 being there with no is_published column is fine — Debezium will never see it again.


  TABLE SCHEMA WITH CDC (minimal, no status column):
  ---------------------------------------------------
  CREATE TABLE outbox_events (
      id             BIGINT AUTO_INCREMENT PRIMARY KEY,
      aggregate_id   VARCHAR(255) NOT NULL,
      aggregate_type VARCHAR(255) NOT NULL,
      event_type     VARCHAR(255) NOT NULL,
      payload        JSON         NOT NULL,
      created_at     TIMESTAMP    DEFAULT CURRENT_TIMESTAMP
      -- No is_published. No status. No processed flag.
  );

  CLEANUP WITH CDC:
  -----------------
  DELETE FROM outbox_events WHERE created_at < NOW() - INTERVAL 1 DAY;
  Safe to run aggressively — Debezium already captured these rows from binlog.
  Deleting them does NOT cause Debezium to re-read or re-publish.
```

**One-liner:**
> "CDC reads binlog forward-only — each INSERT seen exactly once, never re-read.
> is_published flag not needed. Outbox table stays minimal. Rows can be deleted
> immediately after capture — no risk of re-publishing."

### CDC-TRAP-4 — "What MySQL configuration and permissions does Debezium need?"

> **You say:**
>
> "Two parts: MySQL config and MySQL user permissions.
>
> On the MySQL side, binlog must be enabled and in ROW format. ROW format means
> MySQL records the actual data values that changed — the before and after for
> each row. STATEMENT format records the SQL query text, which can be
> non-deterministic — for example if your query uses NOW(), different replicas
> would get different values. Debezium requires ROW format to correctly capture
> what changed. You also need to set binlog_row_image=FULL so Debezium gets
> the complete row, not just the changed columns.
>
> On the permissions side, Debezium needs REPLICATION CLIENT and REPLICATION SLAVE
> — these are standard MySQL replication privileges that allow it to connect to
> the binlog stream the same way a read replica would. It also needs SELECT on
> the tables it monitors for the initial snapshot. It does NOT need INSERT, UPDATE,
> or DELETE on anything — it is read-only by design."

```
MYSQL SETUP FOR DEBEZIUM
=========================

  STEP 1 — MySQL config (my.cnf):
  ---------------------------------
  [mysqld]
  server-id           = 1              # unique ID, required for replication
  log_bin             = mysql-bin      # enable binary logging
  binlog_format       = ROW            # MUST be ROW (not STATEMENT or MIXED)
  binlog_row_image    = FULL           # capture entire row, not just changed cols
  expire_logs_days    = 7              # keep binlogs 7 days for Debezium safety

  WHY ROW format matters:
  STATEMENT: records SQL -> "UPDATE orders SET status='PLACED' WHERE id=1"
             Problem: NOW() gives different results on different machines
  ROW:       records data -> "row id=1 changed: status '' -> 'PLACED'"
             Debezium needs exact values, not SQL text


  STEP 2 — MySQL user for Debezium (least privilege):
  ----------------------------------------------------
  CREATE USER 'debezium'@'%' IDENTIFIED BY '<strong-password>';

  GRANT REPLICATION CLIENT ON *.* TO 'debezium'@'%';
  -- Allows: SHOW MASTER STATUS, SHOW BINARY LOGS

  GRANT REPLICATION SLAVE  ON *.* TO 'debezium'@'%';
  -- Allows: connect to binlog stream (like a replica)

  GRANT SELECT ON flipkart.outbox_events TO 'debezium'@'%';
  -- Allows: initial snapshot read

  -- What Debezium does NOT need:
  -- INSERT, UPDATE, DELETE -> no write access
  -- CREATE, DROP           -> no schema changes
  -- SUPER                  -> not needed in MySQL 5.7+

  Store credentials in Kubernetes Secret, not in Kafka Connect config file:
  kubectl create secret generic debezium-mysql-creds \
    --from-literal=username=debezium \
    --from-literal=password=<strong-password>

  Reference in connector config:
  "database.password": "${file:/secrets/debezium.properties:password}"
```

**One-liner:**
> "MySQL needs: binlog enabled, binlog_format=ROW, binlog_row_image=FULL,
> expire_logs_days=7. Debezium user needs: REPLICATION CLIENT + REPLICATION SLAVE
> + SELECT. No write access. Credentials in Kubernetes secrets."

### CDC-TRAP-5 — "What is snapshot mode? Which mode should you use for an outbox table?"

> **You say:**
>
> "When Debezium connects to MySQL for the very first time, it has a problem.
> The binlog only records changes from this point forward — it does not contain
> the entire history of the table. If the outbox table already has 10,000 rows
> that were inserted before Debezium started, those rows would be invisible to
> Debezium if it just started reading the binlog from now.
>
> Snapshot mode solves this. By default — initial mode — Debezium does a full
> table scan first, publishes all existing rows to Kafka as events, records the
> binlog position at the time of the scan, and then switches to reading the
> binlog from that position onwards. This gives a complete picture including all
> historical data.
>
> But for an outbox table, this is exactly the wrong behavior. Those old rows
> in the outbox are events that were already processed months ago. Re-publishing
> them would cause InventoryService to try to reserve stock for old orders, or
> NotificationService to send duplicate emails to users.
>
> The correct setting for outbox is schema_only mode. This mode reads only the
> table schema — column names and types — on first connect, without reading any
> existing rows. Then it immediately starts streaming from the current binlog
> position. Old rows are never published. Only new inserts from this point
> forward are captured."

```
SNAPSHOT MODES — WHICH ONE FOR OUTBOX?
========================================

  snapshot.mode = initial (DEFAULT — WRONG for outbox):
  -------------------------------------------------------
  Day 1: You start Debezium for the first time.
  Outbox table has 50,000 old processed rows from past 6 months.

  Debezium: "I'll do a full scan first"
  Step 1: reads all 50,000 rows and publishes to Kafka  <- BAD
  Step 2: switches to streaming new inserts

  Result:
  InventoryService gets 50,000 old events -> tries to reserve stock for old orders
  NotificationService sends 50,000 old confirmation emails to users  <- DISASTER


  snapshot.mode = schema_only (CORRECT for outbox):
  ---------------------------------------------------
  Day 1: You start Debezium for the first time.
  Outbox table has 50,000 old rows.

  Debezium: "I'll just read the schema (column names, types)"
  Step 1: reads table structure — does NOT read any row data
  Step 2: immediately starts streaming from current binlog position

  Result:
  Old 50,000 rows: never published
  New orders placed today: published in real time as they are inserted
  No duplicate emails. No old stock reservations.


  KAFKA CONNECT CONNECTOR CONFIG (deploy as JSON to Kafka Connect REST API):
  --------------------------------------------------------------------------
  {
    "name": "flipkart-outbox-connector",
    "config": {
      "connector.class": "io.debezium.connector.mysql.MySqlConnector",
      "database.hostname": "mysql.flipkart.internal",
      "database.port": "3306",
      "database.user": "debezium",
      "database.password": "${file:/secrets/debezium.properties:password}",
      "database.server.id": "12345",
      "database.include.list": "flipkart",
      "table.include.list": "flipkart.outbox_events",
      "snapshot.mode": "schema_only",
      "tombstones.on.delete": "false",
      "transforms": "outbox",
      "transforms.outbox.type":
          "io.debezium.transforms.outbox.EventRouter",
      "transforms.outbox.table.field.event.key": "aggregate_id",
      "transforms.outbox.table.field.event.payload": "payload",
      "topic.prefix": "flipkart"
    }
  }

  EventRouter transform automatically routes events to the right Kafka topic
  based on aggregate_type column — no custom code needed.
  aggregate_type = "Order" -> Kafka topic: flipkart.Order
  aggregate_type = "Payment" -> Kafka topic: flipkart.Payment
```

**One-liner:**
> "snapshot.mode=initial publishes ALL existing rows on first connect — sends
> old processed events again, causes duplicate processing. Use schema_only:
> reads schema only, starts streaming from now. Old rows never published."

```
DEBEZIUM OFFSET STORAGE
=========================

  MySQL binlog:               Kafka Connect:
  (on MySQL server disk)      (internal Kafka topic: connect-offsets)
  |                           |
  | position: file=binlog.003 | Debezium stores:
  |           offset=4892713  | { "file": "binlog.003", "pos": 4892713 }
  |                           |
  Debezium reads here         Debezium persists position after each read

  Debezium crashes:
  |
  Debezium restarts
  |
  Reads connect-offsets topic: last position = binlog.003:4892713
  |
  Resumes from exactly that position
  Zero events lost. Zero events skipped.

  RISK — BINLOG ROTATION:
  |-----------------------
  Debezium down for 10 days
  MySQL binlog retention = 7 days
  MySQL deleted binlog.003
  |
  Debezium: "I need binlog.003 but it does not exist"
  Debezium: falls back to SNAPSHOT mode
  Snapshot: full table scan of outbox table -> rebuild state
  Then: switches back to streaming mode from current binlog position

  PREVENTION: set MySQL binlog_expire_logs_seconds >= 7 days
  And: alert on Debezium lag so you catch downtime early
```

**One-liner:**
> "Debezium stores binlog offset in connect-offsets Kafka topic. Restarts from
> exact position — no loss. Risk: binlog rotation if down too long. Prevent by
> setting MySQL binlog retention >= 7 days."

### CDC-TRAP-2 — "Is CDC exactly-once delivery or at-least-once?"

> **You say:**
>
> "At-least-once. CDC is NOT exactly-once. Here is why.
>
> Debezium reads from the binlog and publishes to Kafka. After publishing, it
> commits its offset to the connect-offsets topic. These two steps — publish and
> commit offset — are not atomic. If Debezium publishes the event to Kafka
> successfully but crashes before committing the offset, on restart it will see
> the same binlog position as uncommitted and publish the same event again. Kafka
> receives it twice.
>
> So consumers must be idempotent — exactly the same inbox pattern I described
> earlier. Store processed event IDs in a processed_events table. Check before
> processing. Both check and business logic in one @Transactional.
>
> Note: this is the same guarantee as polling. Neither CDC nor polling gives
> exactly-once. The difference is that CDC gives much lower latency and no DB
> polling load — but the delivery guarantee is the same."

```
CDC — WHY AT-LEAST-ONCE, NOT EXACTLY-ONCE
==========================================

  Debezium steps for each event:
  1. Read from MySQL binlog: INSERT outbox_events id=101
  2. Publish to Kafka topic: OrderPlaced
  3. Commit offset to connect-offsets: { pos: 4892713 }

  Steps 2 and 3 are NOT atomic.

  Failure scenario:
  Step 2: Kafka receives event 101           <- SUCCESS
  Step 3: Debezium crashes before commit     <- NEVER HAPPENS
  |
  Debezium restarts:
  Last committed offset: 4892710 (before event 101)
  Debezium re-reads binlog from 4892710
  Step 2 again: Kafka receives event 101     <- DUPLICATE

  Consumer receives event 101 twice.
  Without idempotency: InventoryService reserves stock twice.

  FIX: consumer inbox table (same as for polling):
  if (processedEventRepo.existsById(event.getEventId())) return;
```

**One-liner:**
> "CDC is at-least-once, not exactly-once. Publish and offset-commit are not
> atomic — crash between them causes duplicate. Consumer inbox pattern required,
> same as for polling."

### CDC-TRAP-3 — "Does the outbox table need an is_published column for CDC?"

> **You say:**
>
> "No — and this is an important difference between polling and CDC.
>
> Polling needs the is_published flag because the relay queries the table
> repeatedly: SELECT WHERE is_published = false. Without the flag, every poll
> would return all rows and re-publish everything.
>
> CDC reads directly from the MySQL binlog. The binlog records every INSERT,
> UPDATE, DELETE operation on the table. Debezium only sees INSERT events for
> the outbox table — it never re-reads old rows. It just moves forward through
> the binlog. So there is no concept of 'has this row been published?' — Debezium
> saw it exactly once in the binlog stream.
>
> With CDC, the outbox table can be kept minimal: ID, aggregate_type,
> aggregate_id, event_type, payload, created_at. No status column. No
> is_published column. You can even delete rows immediately after they appear
> in the binlog — Debezium already captured them."

```
is_published COLUMN — POLLING vs CDC
======================================

  POLLING (needs is_published):
  ------------------------------
  outbox table: id | payload | is_published | created_at
  Relay query:  SELECT * WHERE is_published = false
  After send:   UPDATE SET is_published = true WHERE id = 101
  Without flag: every poll re-publishes everything. Required.


  CDC (does NOT need is_published):
  ----------------------------------
  MySQL binlog stream (sequential, one-time):
  pos 100: INSERT outbox_events id=101 payload={...}  <- Debezium reads once
  pos 200: INSERT outbox_events id=102 payload={...}  <- Debezium reads once
  pos 300: INSERT outbox_events id=103 payload={...}  <- Debezium reads once

  Debezium never goes back to re-read. Binlog is a forward-only stream.
  No need to mark rows as published — they are seen exactly once in the stream.

  Minimal CDC outbox schema:
  CREATE TABLE outbox_events (
      id            BIGINT AUTO_INCREMENT PRIMARY KEY,
      aggregate_id  VARCHAR(255),
      aggregate_type VARCHAR(255),
      event_type    VARCHAR(255),
      payload       JSON,
      created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
      -- NO is_published column needed
  );

  Cleanup: safe to DELETE rows after they are captured in binlog.
  Debezium already read them. Deleting does not cause re-processing.
```

**One-liner:**
> "CDC reads the binlog stream forward-only — no re-reads of old rows. The
> is_published flag is only needed for polling. CDC outbox table needs no
> status column."

### CDC-TRAP-4 — "What DB privileges does Debezium need on MySQL?"

> **You say:**
>
> "Debezium connects to MySQL using the MySQL replication protocol — the same
> protocol a MySQL replica uses to read from the primary. So it needs replication
> privileges specifically.
>
> The Debezium MySQL user needs: REPLICATION CLIENT to query binlog status,
> REPLICATION SLAVE to actually stream the binlog, and SELECT on the tables it
> monitors (for snapshot mode when it first connects or after losing position).
>
> This is a security consideration in production. The Debezium user must not
> have write access to application tables. And its credentials must be stored
> in Kubernetes secrets, not hardcoded in the Kafka Connect config."

```
DEBEZIUM MYSQL USER PRIVILEGES
================================

  -- Create dedicated Debezium user (least privilege):
  CREATE USER 'debezium'@'%' IDENTIFIED BY '<secret>';

  -- Replication privileges (required):
  GRANT REPLICATION CLIENT ON *.* TO 'debezium'@'%';
  GRANT REPLICATION SLAVE  ON *.* TO 'debezium'@'%';

  -- Read access for snapshot (required on monitored tables):
  GRANT SELECT ON flipkart.outbox_events TO 'debezium'@'%';
  GRANT SELECT ON flipkart.orders        TO 'debezium'@'%';

  -- Flush privileges:
  FLUSH PRIVILEGES;

  What Debezium does NOT need:
  - INSERT / UPDATE / DELETE on any table
  - CREATE / DROP
  - SUPER (unless using MySQL < 5.7)

  Also required in MySQL config (my.cnf):
  [mysqld]
  server-id         = 1
  log_bin           = mysql-bin
  binlog_format     = ROW        # MUST be ROW, not STATEMENT or MIXED
  binlog_row_image  = FULL       # capture full row, not just changed columns
  expire_logs_days  = 7          # keep binlog for 7 days minimum

  binlog_format = ROW is critical:
  STATEMENT format logs the SQL query (non-deterministic queries like NOW() break)
  ROW format logs the actual row values before and after — Debezium requires this
```

**One-liner:**
> "REPLICATION CLIENT + REPLICATION SLAVE + SELECT on monitored tables.
> MySQL must have binlog_format=ROW. Credentials in Kubernetes secrets.
> No write access needed."

### CDC-TRAP-5 — "What is Debezium snapshot mode and when does it trigger?"

> **You say:**
>
> "When Debezium connects to MySQL for the very first time, or after it loses its
> binlog position, it cannot just start reading from the current binlog position —
> it would miss all the existing data. So it first does a snapshot: a consistent
> read of the current table state using a SELECT with a read lock, which gives it
> a baseline. It records the binlog position at that point, then switches to
> streaming mode and reads changes from there.
>
> For the outbox table specifically, snapshot mode is less useful because we do
> not care about historical rows — they are already processed. So for the outbox
> table, you can configure Debezium with snapshot.mode=schema_only, which only
> captures the table schema on first connect and then starts streaming from
> the current binlog position. This avoids re-publishing old outbox events."

```
DEBEZIUM SNAPSHOT MODES
========================

  snapshot.mode = initial (default):
  ------------------------------------
  First connect -> lock table -> SELECT * from outbox_events
  Publishes ALL existing rows to Kafka
  Then switches to streaming mode (binlog)

  Problem for outbox: old events in outbox table get republished
  Consumers may re-process already-handled events.


  snapshot.mode = schema_only (recommended for outbox):
  -------------------------------------------------------
  First connect -> read table SCHEMA only (column names, types)
  Does NOT read existing rows
  Starts streaming from current binlog position immediately
  Old outbox rows: never published by Debezium

  Config in Kafka Connect:
  {
    "connector.class": "io.debezium.connector.mysql.MySqlConnector",
    "database.hostname": "mysql.flipkart.internal",
    "database.port": "3306",
    "database.user": "debezium",
    "database.password": "${file:/secrets/debezium.properties:password}",
    "database.server.id": "12345",
    "database.include.list": "flipkart",
    "table.include.list": "flipkart.outbox_events",
    "snapshot.mode": "schema_only",           // don't re-publish old rows
    "tombstones.on.delete": "false",
    "transforms": "outbox",
    "transforms.outbox.type": "io.debezium.transforms.outbox.EventRouter",
    "transforms.outbox.table.field.event.key": "aggregate_id",
    "transforms.outbox.table.field.event.payload": "payload",
    "topic.prefix": "flipkart"
  }
```

**One-liner:**
> "snapshot.mode=initial re-publishes all existing rows on first connect — wrong
> for outbox. Use schema_only: reads schema only, starts streaming from current
> binlog position, skips old rows."

## QUICK REFERENCE — Key Facts for Interview

| Topic | Plain English | Technical Detail |
|---|---|---|
| What it solves | DB write and event publish cannot be atomic across two systems | Dual-write problem — MySQL and Kafka have separate transaction managers |
| How it works | Write event to DB in same transaction as business data | Outbox table in same DB, relay publishes to Kafka separately |
| Message Relay option 1 | Scheduled job polls and publishes | @Scheduled + SELECT unpublished + kafkaTemplate.send + mark published |
| Message Relay option 2 | CDC reads DB binlog in real time | Debezium tails MySQL binlog, publishes to Kafka in milliseconds |
| Delivery guarantee | At-least-once, NOT exactly-once | Relay can crash after publish but before marking — duplicate possible |
| Duplicate handling | Consumer must be idempotent | Inbox table: store processed event IDs, check before processing |
| Event ordering | All events for same entity go to same Kafka partition | Use aggregate ID (order ID) as Kafka message key |
| Cleanup | Delete old published events | Simple: @Scheduled DELETE; Production: table partitioning + DROP PARTITION |
| Multiple relay instances | Race condition with polling | SELECT FOR UPDATE SKIP LOCKED; CDC avoids this entirely |
| vs Saga | Different problems, used together | Outbox = reliable publish from one service; Saga = multi-service coordination |
| vs Kafka transactions | Kafka transactions do not span MySQL + Kafka | Only XA/2PC can do that — too expensive; use outbox instead |
