# Lambda vs Kappa Architecture (Batch vs Streaming) — Interview Script (15 Years Experience)

> Speak naturally. Pause at diagrams. Show confidence, not textbook recitation.
> Complements [02.kafka-streams-why-need-architect-interview.md](02.kafka-streams-why-need-architect-interview.md), which covers real-time
> stream processing in depth; this file zooms out to where streaming fits against
> batch processing at the architecture level, and the two dominant ways to combine them.

---

## Opening — When Interviewer Asks "How Would You Design a Data Pipeline That Needs Both Real-Time and Historical Accuracy?"

---

"This is really asking: do you need results instantly, correctly, or both — and if
both, how do you avoid building and maintaining two completely separate,
divergent codebases. That's exactly the problem Lambda and Kappa architecture
were each designed to solve, from two different philosophies."

---

## Part 1 — Batch vs Streaming: The Core Trade-off

---

```
BATCH PROCESSING:
  Process large chunks of data on a schedule (hourly, nightly).
  Pros: can reprocess with corrected logic, handles huge historical
        volumes efficiently, simpler to reason about (bounded input).
  Cons: results are always stale by the batch interval (e.g. "yesterday's
        numbers", not "right now").
  Tools: Spark, Hadoop MapReduce, dbt + a warehouse.

STREAM PROCESSING:
  Process each event as it arrives, continuously, no waiting for a batch window.
  Pros: results available within seconds/milliseconds of the event happening.
  Cons: harder to reason about (unbounded input, out-of-order events,
        late-arriving data), reprocessing historical data at scale is
        awkward for a system designed around "one event at a time".
  Tools: Kafka Streams, Flink, Spark Streaming.
```

---

## Part 2 — Lambda Architecture: Run Both, Reconcile Later

---

"Lambda architecture (Nathan Marz) accepts that neither approach alone is enough and
runs BOTH in parallel: a batch layer for the accurate, complete historical view, and
a speed layer for approximate, low-latency recent results — merged at query time."

```
LAMBDA ARCHITECTURE:

  Raw Events ──┬──► BATCH LAYER (Spark/Hadoop, runs hourly/nightly)
               │         │
               │         ▼
               │    Batch View (accurate, complete, but hours stale)
               │
               └──► SPEED LAYER (Kafka Streams/Flink, real-time)
                         │
                         ▼
                    Speed View (approximate, seconds-fresh, covers
                    only the gap since the last batch run)

  QUERY LAYER merges both:
    result = batch_view (everything up to last batch run)
           + speed_view (only the recent gap, real-time)

  Example: "total page views today"
    batch_view says: 1,203,000 (as of last night's batch, midnight)
    speed_view says: +8,400 (today's views since midnight, from streaming)
    merged answer: 1,211,400 (accurate historical + fresh recent)
```

"The well-known criticism, which I raise proactively in interviews because it shows
I understand the trade-off, not just the diagram: you now maintain TWO SEPARATE
codebases implementing the SAME business logic — once in Spark batch jobs, once in
a streaming framework — and keeping them in sync as requirements change is a real,
ongoing maintenance burden. A bug fix applied to one and forgotten in the other
causes the batch and speed views to silently disagree."

---

## Part 3 — Kappa Architecture: Streaming Only, Reprocess by Replaying

---

"Kappa architecture (Jay Kreps, one of Kafka's creators) is a direct response to
Lambda's dual-codebase problem: what if EVERYTHING is a stream, including
'historical batch processing' — which becomes just 'replay the stream from the
beginning through the same streaming logic used for real-time'?"

```
KAPPA ARCHITECTURE:

  Raw Events ──► Kafka (retained long enough to replay — or forever,
                 using infinite/tiered retention)
                     │
                     ▼
              STREAM PROCESSING (single codebase — Kafka Streams/Flink)
                     │
                     ▼
              Materialized View / Output topic

  "REPROCESSING" for a logic bug fix or new requirement:
    1. Deploy the FIXED stream processing logic as a new consumer group
    2. Have it read from the BEGINNING of the retained topic
    3. It rebuilds the entire output view by replaying history through
       the new logic — this is functionally the same as Lambda's batch
       layer, but using the SAME code as the real-time path, not a
       separate Spark job.
    4. Once the replay catches up to "now", swap traffic to the new
       output, retire the old one.

  ONE codebase, ONE set of business logic, applied uniformly to both
  "replaying history" and "processing what's happening right now".
```

## Part 4 — Decision Framework

---

```
Q1: Do you need both a "definitely correct, reprocessable" historical view
    AND a "fast, approximate, real-time" view, with genuinely different
    accuracy/latency requirements per use case (e.g. financial reporting
    needs batch-level correctness, a live dashboard needs speed)?
    │
    YES ──► Lambda may be justified — but budget for maintaining 2 codebases,
    │       or consider whether the more modern trend of unifying batch and
    │       streaming under ONE engine (see below) removes the need.
    │
    NO — a single, unified real-time model is acceptable and Kafka
    retention can hold enough history to replay when needed
    │
    ──► Kappa. Simpler operationally, one codebase, one mental model.


MODERN NOTE (worth mentioning in an interview to show currency):
  Frameworks like Apache Flink and Spark Structured Streaming increasingly
  offer a SINGLE API that runs identically over bounded (batch) and
  unbounded (streaming) data — this is sometimes called the "unified batch
  and streaming" model, and it reduces the practical need to choose Lambda
  vs Kappa at all, since one engine + one API handles both cases without
  requiring either two codebases (Lambda) or "everything must be a Kafka
  replay" (Kappa's constraint).
```

## Part 5 — Production Scenario

---

"At a retail analytics platform, our original design was Lambda: nightly Spark jobs
computed 'accurate' daily sales totals per SKU, while a Kafka Streams job gave a
live, approximate dashboard number throughout the day. We had a recurring pain point:
a promotions logic change (how a discount affects reported revenue) had to be
implemented TWICE — once in the PySpark batch job, once in the Kafka Streams
topology — and they drifted out of sync twice within a year, causing dashboard
numbers to visibly disagree with the next morning's 'official' batch numbers, which
undermined trust in the dashboard.

We migrated to Kappa: Kafka retained 90 days of raw sales events, and ALL logic —
real-time dashboard AND the 'official' end-of-day rollup — ran through the same
Kafka Streams topology. When the promotions logic changed, we deployed once, replayed
the last 90 days through the new logic to rebuild historical rollups, and both the
live dashboard and the official numbers came from the exact same code, guaranteed
to agree."

## Interview Traps & Cross-Questions

---

```
Q: "Isn't Kappa strictly better than Lambda — why would anyone still use Lambda?"
A: "Kappa requires your event log (Kafka) to retain enough history to replay,
    which gets expensive/awkward at very large historical scale (years of
    data) compared to a batch layer reading from cheap object storage
    (S3/data lake). Lambda can also be simpler when the batch and speed
    layers genuinely have DIFFERENT logic on purpose (e.g. batch does
    expensive ML feature engineering that's too slow for real-time; speed
    layer intentionally uses a cheaper approximation) — that's not
    'divergent logic by accident', it's a deliberate trade-off Kappa
    doesn't naturally accommodate."

Q: "How do you handle reprocessing in Kappa if Kafka retention doesn't go
    back far enough?"
A: "Either extend retention (tiered storage, e.g. Kafka's tiered storage
    to S3-backed segments), or replay from a data lake/warehouse copy of
    the raw events into a fresh Kafka topic before running the corrected
    logic over it — the stream processing logic itself doesn't care where
    the events physically came from, only that they arrive in the topic."

Q: "Does 'streaming only' mean you can't ever produce accurate, bounded
    reports (e.g. month-end close)?"
A: "No — a stream processor can absolutely produce a bounded, point-in-time
    correct output (e.g. windowed aggregation closed at month-end) — 'streaming'
    describes the PROCESSING MODEL (continuous, event-at-a-time), not that
    outputs can never be treated as a finalized, bounded report."
```
