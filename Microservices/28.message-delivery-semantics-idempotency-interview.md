# Message Delivery Semantics & Idempotent Consumers — Interview Script (15 Years Experience)

> Speak naturally. Pause at diagrams. Show confidence, not textbook recitation.

---

## Opening — When Interviewer Asks "How Do You Guarantee a Message Is Processed Exactly Once?"

---

"The honest answer is: you almost never get true exactly-once delivery across a network —
what you actually build is at-least-once delivery plus an idempotent consumer, which
*behaves* like exactly-once from the business's point of view. Let me explain why
delivery guarantees and processing guarantees are two different things."

---

## Part 1 — The Three Delivery Semantics

---

```
AT-MOST-ONCE:
  Producer sends, doesn't wait for ack, moves on.
  If the message is lost in transit — it's just gone. No retry.
  Use case: metrics/telemetry pings where losing one is fine.

  Producer ──fire and forget──► [ message may or may not arrive ]


AT-LEAST-ONCE:
  Producer sends, waits for ack. If ack times out or is lost,
  producer RETRIES — possibly sending a duplicate the consumer already got.
  Use case: the default for almost every business system (orders, payments, emails).

  Producer ──msg──► Consumer ──processes──► [ack lost in transit] ──► Producer retries
                                                                          │
                                                                          ▼
                                                              Consumer receives DUPLICATE


EXACTLY-ONCE:
  The message is delivered and processed exactly one time, no more, no less.
  True end-to-end exactly-once across independent systems is effectively impossible
  to guarantee generally (this traces back to the Two Generals Problem) — what
  Kafka's "exactly-once semantics" (EOS) actually guarantees is exactly-once
  WITHIN Kafka (producer→topic→consumer, using transactional producers + idempotent
  producer IDs) — it does NOT extend automatically to an external side effect,
  like calling a payment API or writing to a different database.
```

```
THE TWO GENERALS PROBLEM (why exactly-once across systems is fundamentally hard):

  General A ──"attack at dawn"──► General B
              (message may be lost, and A can never be 100% sure B got it,
               even if B sends an ack back, because THAT ack could be lost too)

  This is why every real system settles for at-least-once + idempotency,
  rather than trying to invent guaranteed exactly-once delivery.
```

## Part 2 — Idempotent Consumers: How You Actually Achieve "Effectively Once"

---

"Since producers will retry and consumers will sometimes see the same message twice,
the consumer has to be built so that processing the same message N times produces
the same result as processing it once. That's what 'idempotent consumer' means."

```
PATTERN 1 — Idempotency Key + Dedup Table:

  Every message carries a unique idempotency key (often the business event ID,
  e.g. "order-8821-created", not a random UUID that changes on retry).

  Consumer flow:
  ┌──────────────────────────────────────────────────────────────┐
  │  1. Extract idempotency_key from message                     │
  │  2. BEGIN TRANSACTION                                        │
  │  3. INSERT INTO processed_events(key) VALUES (?)              │
  │     ON CONFLICT DO NOTHING  ← atomic dedup check              │
  │  4. IF rows_inserted == 0 → already processed, SKIP + ack     │
  │  5. IF rows_inserted == 1 → process the business logic        │
  │  6. COMMIT (both dedup record + business effect atomically)  │
  └──────────────────────────────────────────────────────────────┘

  The critical detail: the dedup check and the business-logic write MUST be
  in the SAME transaction. If they're separate, a crash between them creates
  a window where a retry either double-processes or silently skips.
```

```
PATTERN 2 — Natural Idempotency via Upsert (no dedup table needed):

  Instead of "INSERT INTO account_balance ... (amount +=100)" (NOT idempotent —
  running it twice adds 200), design the operation so replays are naturally safe:

  UPSERT ledger_entry (transaction_id, account_id, amount)
  VALUES ('txn-8821', 'acct-1', 100)
  ON CONFLICT (transaction_id) DO NOTHING;

  Then compute balance = SUM(amount) FROM ledger_entry WHERE account_id = ?
  Replaying the same transaction_id is a no-op. This is how payment ledgers
  (see 10.payment-gateway-system-design.md) avoid double-charging on retries.
```

## Part 3 — Kafka-Specific: Where Duplicates Actually Come From

---

```
CONSUMER-SIDE DUPLICATE SOURCE (the most common one in practice):

  Consumer polls batch of messages ──► processes message ──► CRASHES before
  committing offset ──► consumer group rebalances ──► new consumer instance
  re-reads from LAST COMMITTED OFFSET ──► reprocesses the same message

  ┌───────────────────────────────────────────────────────────────┐
  │  Partition offsets:  ... 45  46  47  48  49  50 ...            │
  │                              ▲               ▲                │
  │                        last committed    message actually     │
  │                        offset = 46        processed (side     │
  │                                            effect ran) but     │
  │                                            crash before commit │
  │  Result: message 47 WILL be redelivered — this is expected     │
  │  at-least-once behavior, not a bug.                            │
  └───────────────────────────────────────────────────────────────┘

  This is exactly why "process message, then commit offset" (not the reverse)
  combined with an idempotent handler is the standard pattern — never commit
  the offset before you're sure the side effect succeeded, or you get
  AT-MOST-ONCE (silent loss) instead of at-least-once.
```

"Kafka's idempotent producer (`enable.idempotence=true`) solves duplicate *writes from
the producer* — it stamps each message with a producer ID + sequence number, and the
broker drops exact retransmits from network retries. That solves producer-side
duplication. It does NOT solve consumer-side duplication from the crash-before-commit
scenario above — that's a separate problem the consumer must handle itself."

## Part 4 — Production Scenario

---

"At a previous role, our notification service consumed 'order.shipped' events and
called SendGrid to email the customer. Early on, we had customers getting the
shipping confirmation email 3-4 times during Kafka rebalances under load. The fix:

1. Every event carried the order_id + a shipment_sequence as idempotency key.
2. Before calling SendGrid, we did an atomic INSERT ... ON CONFLICT DO NOTHING
   into a `sent_notifications` table keyed on that composite key.
3. Only committed the Kafka offset after both the dedup insert AND the SendGrid
   call succeeded — using manual offset commit, not auto-commit.
4. For SendGrid itself, we passed their own idempotency-key header too, since
   even our retry logic (in case of our own crash) could otherwise double-send
   through their API."

```
LAYERED IDEMPOTENCY (belt and suspenders):

  Kafka Consumer                 Our DB                    SendGrid API
       │                            │                            │
       │──check dedup table────────►│                            │
       │◄─not seen before───────────│                            │
       │                                                          │
       │──call w/ idempotency-key header────────────────────────►│
       │◄──────────────────200 OK───────────────────────────────│
       │                                                          │
       │──insert dedup record + commit offset (same txn as above)│
```

## Interview Traps & Cross-Questions

---

```
Q: "Does Kafka's 'exactly-once semantics' mean I never have to worry about duplicates?"
A: "No — Kafka EOS guarantees exactly-once only for Kafka-to-Kafka pipelines
    (e.g. Kafka Streams reading from one topic, writing to another, using
    transactions). The moment your consumer has a side effect outside Kafka —
    an HTTP call, a write to Postgres — you're back to needing your own
    idempotency handling, because that external call and the offset commit
    aren't part of the same transaction."

Q: "Why not just use a random UUID as the idempotency key generated at send time?"
A: "If the UUID is generated fresh on every retry, every retry looks like a new
    unique event — dedup fails completely. The key must be derived from stable
    business identity (order ID + event type, or a client-supplied request ID
    that survives retries), not regenerated per attempt."

Q: "What happens if two different consumer instances process the same message
    concurrently during a rebalance (not a crash, just overlap)?"
A: "This is why the dedup check must be an atomic DB constraint (unique index +
    ON CONFLICT), not a 'SELECT then INSERT if not found' — that has a race
    condition window where both instances pass the SELECT check before either
    INSERTs. The database's unique constraint is the actual source of truth."

Q: "Is at-least-once always the right choice over at-most-once?"
A: "No — depends on the cost of duplication vs the cost of loss. For a 'user
    viewed page' analytics ping, losing a few is fine and cheap (at-most-once,
    fire-and-forget). For 'charge customer' or 'ship order', losing one is
    unacceptable, so at-least-once + idempotency is required even though it's
    more expensive to implement."
```

## Quick Reference Card

```
GUARANTEE          MECHANISM                              FAILURE MODE IF DONE WRONG
──────────────────────────────────────────────────────────────────────────────────
At-most-once        fire-and-forget, no retry               silent message loss
At-least-once        ack + retry on timeout                 consumer sees duplicates
Effectively-once     at-least-once + idempotent consumer     none, if key is stable
                     (dedup table / natural upsert)          and check is atomic

Producer-side dup    Kafka idempotent producer                (handled by broker)
                     (enable.idempotence=true)
Consumer-side dup    manual offset commit AFTER side effect + dedup key check
                     in same transaction as the effect
```
