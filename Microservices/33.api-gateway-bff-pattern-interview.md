# API Gateway & Backend-for-Frontend (BFF) — Interview Script (15 Years Experience)

> Speak naturally. Pause at diagrams. Show confidence, not textbook recitation.
> Related to [07.ambassador-adapter-aggregator-scatter-gather-failover-interview.md](07.ambassador-adapter-aggregator-scatter-gather-failover-interview.md) —
> that file covers the aggregator/scatter-gather PATTERNS; this file covers the
> API Gateway/BFF as an architectural LAYER where those patterns typically live.

---

## Opening — When Interviewer Asks "Why Do You Need an API Gateway?"

---

"Without a gateway, every client — mobile app, web app, partner integrations — talks
directly to N microservices. That means every client has to know service discovery,
handle N different auth mechanisms, and every cross-cutting concern (rate limiting,
logging, auth) gets duplicated N times, once per client type. An API Gateway centralizes
that, and a BFF takes it one step further by tailoring the API per client type."

---

## Part 1 — The Problem Without a Gateway

---

```
WITHOUT A GATEWAY:

  Mobile App ──────┬──► Order Service
                    ├──► Payment Service
                    ├──► Inventory Service
                    └──► User Service

  Web App    ──────┬──► Order Service        (same 4 calls, duplicated logic)
                    ├──► Payment Service
                    ├──► Inventory Service
                    └──► User Service

  PROBLEMS:
  - Every client needs service discovery logic baked in
  - Auth/rate-limiting/logging reimplemented per client
  - A mobile screen needing data from 4 services makes 4 round trips over
    a slow cellular connection — brutal for mobile latency
  - Changing an internal service's location/API shape breaks every client directly
```

```
WITH AN API GATEWAY:

  Mobile App ──┐
  Web App    ──┼──► API Gateway ──┬──► Order Service
  Partner API──┘         │        ├──► Payment Service
                   (auth, rate                          
                    limiting,     ├──► Inventory Service
                    logging,      └──► User Service
                    routing,
                    aggregation
                    all centralized)
```

## Part 2 — What the Gateway Actually Does

---

```
RESPONSIBILITY            EXAMPLE
──────────────────────────────────────────────────────────────────────
Routing                    /orders/* → Order Service, /payments/* → Payment Service
Authentication              validate JWT once, forward trusted identity downstream
                            (see 26.authn-authz-security-architect-interview.md)
Rate limiting               per-client-id limits (see 32.rate-limiting-algorithms-interview.md)
Request aggregation          combine calls to 3 backend services into 1 client response
                            (the Aggregator pattern from 07.ambassador-adapter-...)
Protocol translation         external REST/JSON in, internal gRPC out
Response caching              cache read-heavy, rarely-changing responses at the edge
Circuit breaking/retries      isolate a slow/failing backend from cascading to clients
```

## Part 3 — API Gateway vs BFF (the distinction interviewers actually want)

---

"A single, generic API Gateway serving every client type tends to accumulate client-
specific logic ('if mobile, return fewer fields; if web, include this extra field') —
that turns the gateway into a bloated, hard-to-own piece of shared code every team
is scared to touch. BFF solves this by giving each client type its OWN dedicated
gateway layer, owned by the team that owns that client."

```
GENERIC GATEWAY (one-size-fits-all — gets messy at scale):

  Mobile ──┐
  Web    ──┼──► ONE Gateway (full of if(isMobile) branches) ──► Services
  TV App ──┘


BFF (Backend-for-Frontend — one gateway PER client type):

  Mobile ──► Mobile BFF ──┐
  Web    ──► Web BFF    ──┼──► Order Service
  TV App ──► TV BFF     ──┘    Payment Service
                                Inventory Service

  Mobile BFF returns a lean payload (bandwidth-constrained, small screen)
  Web BFF returns a richer payload (more fields, more embedded relations)
  TV BFF returns a payload shaped for a 10-foot UI, different pagination

  Each BFF is owned by the FRONTEND team that consumes it, not a shared
  platform team — this removes the "gateway is everyone's and no one's"
  ownership problem.
```

## Part 4 — Production Scenario

---

"On a marketplace platform, our mobile app's product listing screen originally called
the generic API gateway, which called Product, Pricing, Inventory, and Reviews services,
then over-fetched a huge nested JSON payload designed for the web app's much richer
detail page. Mobile only needed 6 fields. We introduced a Mobile BFF, owned by the
mobile team, that made the same 4 backend calls but returned only what the mobile
list screen needed — the payload dropped from ~40KB to ~3KB per item, and mobile
could iterate on its own response shape without coordinating a shared gateway
release with the web team."

```
BEFORE (shared gateway, over-fetching):
  Mobile list screen ──► Generic Gateway ──► 40KB nested payload (mostly unused)

AFTER (Mobile BFF):
  Mobile list screen ──► Mobile BFF ──► aggregates same 4 services ──► 3KB payload
                                         tailored exactly to what the screen renders
```

## Interview Traps & Cross-Questions

---

```
Q: "Isn't a BFF just duplicating the API Gateway's job for each client?"
A: "It duplicates the AGGREGATION/shaping logic, deliberately — the point is that
    different clients have genuinely different data and shape needs, and forcing
    one shared response schema onto all of them causes either over-fetching or
    constant contention between frontend teams over what the shared gateway returns.
    Cross-cutting concerns (auth, rate limiting, TLS termination) still typically
    live in a shared edge gateway IN FRONT of the BFFs, so that part isn't duplicated."

Q: "Doesn't a BFF add another network hop and another thing to deploy/monitor?"
A: "Yes — it's a real cost. I only introduce a dedicated BFF once a client type
    has genuinely divergent needs (mobile bandwidth constraints, TV 10-foot UI) —
    for a simple platform with just a web app, one gateway is enough; BFF is a
    scaling decision, not a default."

Q: "Where does authentication actually happen — gateway, BFF, or each backend service?"
A: "JWT signature/expiry validation happens once, typically at the outer edge
    gateway. The trusted identity is then forwarded downstream as a header. Each
    backend service should still independently check the SCOPE/permission for its
    own operation — never assume 'it got past the gateway, so it's fully authorized
    for anything' (see the confused-deputy trap in 26.authn-authz-security-architect-interview.md)."
```

## Quick Reference Card

```
LAYER                OWNED BY               RESPONSIBILITY
─────────────────────────────────────────────────────────────────────
Edge/API Gateway      Platform/infra team     TLS, coarse auth, rate limiting, routing
BFF (per client)      Frontend team           Aggregation, response shaping for that client
Backend services      Domain teams            Business logic, fine-grained authorization
```
