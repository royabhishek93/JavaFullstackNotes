# CQRS (Command Query Responsibility Segregation) — Architect Interview Script

> **Interview Frequency:** 60% | **Difficulty:** ⭐⭐⭐⭐ | **Study Time:** 12 minutes

---

## Opening — When Interviewer Asks "How Would You Scale a Read-Heavy, Write-Complex System?"

"CQRS comes up when interviewers want to test whether you know when to split a
system's read and write paths instead of reflexively doing everything through one
model. Let me start with the problem it solves."

---

## Part 1 — The Problem (One Model Trying to Do Two Jobs)

"Take a product catalog service — like Flipkart's. Writes are complex: updating
price, stock, and applying business rules across multiple tables. Reads are simple
but massive: millions of search/browse requests per minute, and they want data
shaped very differently — denormalized, pre-joined, cached."

```
TRADITIONAL (CRUD) — one model for everything:

  ┌───────────────────────────────────────────────────────┐
  │              ProductService                            │
  │                                                         │
  │   Write path:  validate → update Product, Inventory,   │
  │                Price tables (normalized, transactional) │
  │                                                         │
  │   Read path:   SELECT with 4 JOINs across the SAME     │
  │                normalized tables — slow under high     │
  │                read volume, and every index added to   │
  │                help reads makes writes slower           │
  └───────────────────────────────────────────────────────┘

  Problem: reads and writes have OPPOSITE optimization needs,
  but they're forced to share one schema and one model.
```

---

## Part 2 — The CQRS Split

```
CQRS — separate models for commands (writes) and queries (reads):

  ┌────────────────┐        events         ┌─────────────────────┐
  │  COMMAND SIDE   │ ─────────────────────►│    QUERY SIDE        │
  │                 │  "PriceChanged"        │                      │
  │  Normalized DB  │  "StockUpdated"        │  Denormalized,       │
  │  (writes go     │  "ProductCreated"      │  pre-joined "read    │
  │   here, ACID)   │                        │  model" optimized    │
  │                 │                        │  purely for fast     │
  │  Product        │                        │  search/browse       │
  │  Inventory      │                        │                      │
  │  Price          │                        │  (Elasticsearch /    │
  │                 │                        │   Redis / read-only  │
  │                 │                        │   Postgres replica)  │
  └────────────────┘                        └─────────────────────┘

  Command side: optimized for correctness (fewer, more complex writes).
  Query side:   optimized for speed (many, simple reads), can even use a
                completely different database technology.
```

"The two models don't have to be different databases necessarily — the simplest
version of CQRS is just separate read/write Java classes hitting the same database
but with different queries. The 'separate database' version is CQRS + a sync
mechanism, which is where most of the real complexity lives."

---

## Part 3 — How the Read Model Gets Updated (The Hard Part)

```
OPTION A: Same database, read replicas (SIMPLEST CQRS)

  App writes ──► Primary DB ──(replication)──► Read Replica ──► queries
  Same schema on both sides. Easy to reason about. Replication lag is the
  only eventual-consistency concern.


OPTION B: Separate read store, updated via events (FULL CQRS)

  App writes ──► Command DB (Postgres) ──► emits "ProductPriceChanged" event
                                                      │
                                                      ▼
                                              Kafka topic
                                                      │
                                                      ▼
                                    Projection/Consumer service
                                                      │
                                                      ▼
                                     Read Store (Elasticsearch)
                                     — denormalized doc: {id, name,
                                       price, stock, category, ...}
                                     — this is what search queries hit

  This can reuse the Transactional Outbox pattern to reliably emit the
  event in the same transaction as the write to Command DB.
```

"Notice this is the same reliability problem as the outbox pattern — you must not
lose the event that updates the read side, or your read model silently goes stale
forever. I always pair CQRS with outbox or CDC (Debezium) for that reason."

## Part 4 — Code Sketch (Command Side vs Query Side)

```java
// ── COMMAND SIDE ──────────────────────────────────────
public record ChangePriceCommand(String productId, BigDecimal newPrice) {}

@Service
public class ProductCommandHandler {
    @Transactional
    public void handle(ChangePriceCommand cmd) {
        Product p = productRepo.findById(cmd.productId());
        p.changePrice(cmd.newPrice());          // business rules live here
        productRepo.save(p);
        outboxRepo.save(new OutboxEvent("ProductPriceChanged", cmd));
        // same transaction as the write — reliable, see outbox pattern
    }
}

// ── QUERY SIDE ────────────────────────────────────────
public record ProductSearchResult(String id, String name,
                                   BigDecimal price, int stock) {}

@Service
public class ProductQueryHandler {
    // hits Elasticsearch / denormalized read store — NOT the write DB
    public List<ProductSearchResult> search(String keyword, Filters f) {
        return elasticsearchClient.search(keyword, f);
    }
}

// ── PROJECTION (keeps read store in sync) ─────────────
@KafkaListener(topics = "product-events")
public void onEvent(ProductPriceChangedEvent e) {
    elasticsearchClient.update(e.productId(), doc -> doc.setPrice(e.newPrice()));
}
```

## Part 5 — Eventual Consistency: What Users Actually Experience

```
t=0ms     User A updates price via Command API → 200 OK returned immediately
t=0ms     Command DB committed. Event published to Kafka.
t=0-200ms Event in-flight through Kafka → Projection consumer
t=200ms   Read store (Elasticsearch) updated

  ⚠ Between t=0 and t=200ms, User B searching the catalog sees the OLD price.
  This is the CQRS trade-off: writes return fast, but reads can briefly lag.

  Mitigation for "read-your-own-write" cases (e.g., user edits their own profile
  and immediately views it):
  - Read from the command side / cache for that specific user's own action.
  - Or optimistically update the UI locally, sync in background.
```

## Common Pitfalls

```
❌ Pitfall 1: Adding CQRS to a simple CRUD app "because it's a best practice"
   → doubles the moving parts (2 models, sync pipeline) for zero real benefit.

❌ Pitfall 2: Forgetting the read model needs its OWN error handling/retry
   → if the projection consumer crashes silently, the read store goes stale
     forever and nobody notices until a customer complains about wrong prices.

❌ Pitfall 3: Conflating CQRS with Event Sourcing
   → CQRS is about splitting read/write MODELS. Event Sourcing is about storing
     state as a sequence of events instead of current-state rows. They're often
     used together but are independent decisions.

❌ Pitfall 4: Using the read model for critical consistency-sensitive writes
   → e.g., checking "is this item in stock?" against a denormalized search index
     that's 200ms stale can cause overselling. Inventory decrement should hit the
     command side / source of truth, not the read replica.

❌ Pitfall 5: No monitoring on replication/projection lag
   → "stale read model" becomes a customer-facing bug with zero visibility until
     complaints roll in. Always alert on consumer lag (Kafka) or replication delay.
```

---

## 🛑 When NOT to Use CQRS

- ❌ Low-traffic CRUD apps — one model, one database, is simpler and correct.
- ❌ Systems where reads and writes have similar shape/volume — no benefit to splitting.
- ✅ DO use it when: read and write loads are wildly asymmetric (millions of reads,
  thousands of writes), or read and write models need fundamentally different data
  shapes (normalized transactional vs denormalized/search-optimized).

## TRAP QUESTIONS

---

### TRAP-1 — "Isn't CQRS the same thing as just having a read replica?"

> **You say:**
>
> "A read replica is the simplest form of CQRS — same schema, replicated data,
> separated by replication lag. Full CQRS goes further: the read side can use a
> completely different schema and even a different database technology, like
> Elasticsearch for search versus Postgres for transactional writes, updated via
> events rather than database-level replication. Both share the same core idea —
> physically separating read and write paths — but a read replica alone doesn't let
> you reshape or denormalize the data."

---

### TRAP-2 — "Do you need Event Sourcing to implement CQRS?"

> **You say:**
>
> "No — they're independent. CQRS just means separate read and write models. You can
> implement it with a normal relational write-side and a projection job that pushes
> denormalized copies to a read store, without ever storing an event log. Event
> Sourcing, storing state as an append-only sequence of events, is commonly paired
> with CQRS because the event stream is a natural source to build read projections
> from, but you can absolutely have one without the other."

---

### TRAP-3 — "How do you handle a user who updates data and immediately expects to see it (read-your-own-writes)?"

> **You say:**
>
> "A few options depending on the criticality: route that specific read back to the
> command-side database right after a write, cache the just-written value client-side
> and merge it optimistically, or accept a short-lived banner/spinner while the
> projection catches up. I pick based on how core the flow is — for something like a
> user's own order confirmation, I'd read straight from the source of truth rather
> than the projected read model."

---

### TRAP-4 — "What happens if the projection consumer crashes and falls behind?"

> **You say:**
>
> "The read model goes progressively staler the longer it's down, but the command
> side is completely unaffected since writes don't depend on the read side. The key
> safeguard is monitoring consumer lag and alerting past a threshold, plus designing
> the projection to be idempotent and resumable from its last committed Kafka offset,
> so when it recovers it can safely replay from where it left off without duplicating
> or missing updates."

---

### TRAP-5 — "Would you use CQRS for a payment/inventory-critical write?"

> **You say:**
>
> "The write (command) side is always the source of truth for consistency-critical
> checks like 'is there enough stock' — that logic runs against the transactional
> database with proper locking, never against the denormalized read model, which can
> lag by hundreds of milliseconds. CQRS is about optimizing reads for scale, not
> about relaxing consistency guarantees on the write path."

---

## Interview Answer (60-Second Summary)

> "CQRS splits a system's read path from its write path into separate models,
> because reads and writes often have opposite optimization needs — writes need
> normalized, transactional correctness; reads at scale need denormalized, fast,
> often differently-shaped data. The simplest version is just a read replica; full
> CQRS goes further with a separate read store, like Elasticsearch, kept in sync via
> events, typically published reliably using the transactional outbox pattern. The
> trade-off is eventual consistency — there's a window where the read model lags
> behind the write model — so I only reach for CQRS when read and write volumes or
> shapes are genuinely asymmetric, and I always keep consistency-critical checks,
> like inventory decisions, against the command side, not the projected read model."

## Quick Reference Card

```
CONCEPT                  MEANING
────────────────────────────────────────────────────────────────────────
Command                   A write/intent to change state (validated, transactional)
Query                     A read, served from an optimized read model
Command model             Normalized, ACID, source of truth
Read model / projection    Denormalized, fast, can be a different DB technology
Sync mechanism             Events (Kafka) + outbox/CDC keep read model updated
Eventual consistency       Read model may briefly lag behind writes
Event Sourcing (related,   Storing state as an event log instead of current rows —
 not required)             often paired with CQRS but an independent decision
```
