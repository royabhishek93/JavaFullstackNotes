## Opening — When Interviewer Asks "How Would You Implement Rate Limiting?"

---

"There isn't one 'rate limiting algorithm' — there are about four standard ones,
and picking wrong shows up as either burstiness you didn't intend, or unfairness
at window boundaries. Let me walk through each, then how to make it work when
you have multiple gateway instances, not just one."

---

## Part 1 — The Four Algorithms

---

```
1. FIXED WINDOW COUNTER:
   Count requests in fixed clock windows (e.g. per-minute buckets).

   09:00:00-09:00:59 → count=98 (under limit of 100, OK)
   09:01:00-09:01:59 → count resets to 0

   PROBLEM — boundary burst:
   09:00:59 → 100 requests allowed (right at window's end)
   09:01:00 → 100 MORE requests allowed (new window starts)
   = 200 requests in under 2 seconds, despite a "100/minute" limit.
   Simple to implement, but bursts at window edges.


2. SLIDING WINDOW LOG:
   Store a timestamp for EVERY request in the last window; count entries.

   window = now - 60s ... now
   log = [09:00:03, 09:00:15, 09:00:44, 09:00:58, ...]
   count = entries with timestamp within the last 60s

   Perfectly accurate — no boundary burst — but storing a timestamp per
   request is memory-expensive at high traffic (millions of entries per key).


3. SLIDING WINDOW COUNTER (the practical compromise):
   Weighted average of the current and previous fixed window counts.

   current_window_count=30 (20s into a 60s window, so 20/60 = 33% elapsed)
   previous_window_count=80

   estimated_count = previous_count * (1 - elapsed_fraction) + current_count
                    = 80 * (1 - 0.33) + 30
                    = 53.6 + 30 = 83.6

   Approximates the sliding log's accuracy with fixed window's cheap memory
   (just 2 counters per key, not a full timestamp log). This is what most
   production rate limiters (including Cloudflare's, published in their
   engineering blog) actually use.


4. TOKEN BUCKET:
   A bucket holds tokens, refilled at a steady rate, up to a max capacity.
   Each request consumes 1 token; no tokens = request rejected/delayed.

   capacity=100, refill_rate=10/sec
   ┌────────────────────────────┐
   │ ●●●●●●●●●●●●●●●●●●●●░░░░░ │  73/100 tokens available
   └────────────────────────────┘
   Request arrives → consume 1 token → 72/100 remain
   Every 100ms → +1 token added (10/sec), capped at 100

   KEY PROPERTY: allows short BURSTS up to the full bucket size, then
   throttles to the steady refill rate — unlike fixed window, which allows
   bursts only right at window boundaries, unpredictably. Token bucket's
   burst allowance is a deliberate, tunable parameter (bucket size), not
   an accident of window alignment. This is why it's the most commonly
   chosen algorithm for "give clients some burst tolerance but cap
   sustained throughput".


5. LEAKY BUCKET (brief mention — the inverse framing of token bucket):
   Requests queue into a bucket; the bucket "leaks" (processes) at a
   fixed constant rate regardless of arrival rate. Smooths bursts into a
   perfectly steady output rate — good for protecting a downstream that
   truly cannot handle ANY burst (e.g. a legacy system with a hard fixed
   throughput ceiling), at the cost of added latency for bursty clients.
```

## Part 2 — Distributed Rate Limiting (Multiple Gateway Instances)

---

"None of the above works correctly if you have 10 gateway instances each keeping
their own in-memory counter — a client could get 100 requests through EACH instance,
1000 total, despite a '100/minute' global limit. The fix is a shared counter."

```
CENTRALIZED COUNTER VIA REDIS (the standard approach):

  Gateway 1 ──┐
  Gateway 2 ──┼──► Redis (INCR key, EXPIRE)  ──► single source of truth
  Gateway 3 ──┘        for the counter

  Lua script (atomic, avoids race condition between INCR and EXPIRE):

    local current = redis.call('INCR', KEYS[1])
    if current == 1 then
        redis.call('EXPIRE', KEYS[1], ARGV[1])  -- set TTL only on first request
    end
    if current > tonumber(ARGV[2]) then
        return 0  -- over limit, reject
    end
    return 1  -- allowed

  Running this as a single Lua script makes INCR + conditional EXPIRE +
  limit check ATOMIC — without the script, two gateways could race between
  the INCR and the EXPIRE call, corrupting the TTL.
```

```
TRADE-OFF — Redis roundtrip adds latency to every request:

  For very high QPS gateways, some teams accept slightly LOOSER limits by
  batching: each gateway instance reserves a local allowance (e.g. "give me
  10 tokens") from the central Redis bucket periodically, then serves those
  10 locally without a Redis call per request. Slightly less precise (a
  burst could exceed the true global limit by up to N instances × reserved
  batch size) but dramatically reduces Redis load and per-request latency.
```

## Part 3 — Where to Enforce It

---

```
LAYER               WHAT IT PROTECTS AGAINST                 GRANULARITY
─────────────────────────────────────────────────────────────────────────
CDN/Edge (Cloudflare) Volumetric DDoS, before it reaches you    Per IP, coarse
API Gateway           Per-client/per-API-key fair usage         Per client_id, per route
Service mesh sidecar   Service-to-service overload protection    Per source service
Application code       Business-rule specific limits             Per user action type
                       ("max 3 password resets/hour")
```

"I layer these — CDN-level for blunt DDoS protection, gateway-level for per-tenant
fairness (so one noisy partner can't starve others), and application-level for
business rules that don't map cleanly onto HTTP routes."

## Interview Traps & Cross-Questions

---

```
Q: "Why not just use fixed window counters everywhere — they're simplest?"
A: "They allow up to 2x the intended limit right at window boundaries, which
    is a real vulnerability if the limit exists for cost or protection reasons
    (e.g. protecting a paid third-party API by usage). Sliding window counter
    gets you 90% of the accuracy for a fraction of sliding log's memory cost —
    that's usually the right default."

Q: "How do you rate limit by API key when the same key is used across
    multiple gateway pods behind a load balancer?"
A: "The limit state must live in a shared store (Redis), not per-pod memory —
    otherwise the effective limit is (configured limit × number of pods),
    which silently defeats the purpose of having a limit at all."

Q: "What HTTP response do you return when rate limited, and what should be in it?"
A: "429 Too Many Requests, with a Retry-After header telling the client how
    long to wait, plus X-RateLimit-Limit / X-RateLimit-Remaining headers so
    well-behaved clients can self-throttle proactively instead of hammering
    and retrying blindly."

Q: "Token bucket vs leaky bucket — which allows bursts?"
A: "Token bucket allows bursts up to the bucket size, then throttles to the
    refill rate — good when occasional bursts are fine. Leaky bucket forces
    a perfectly smooth, constant output rate regardless of input burstiness —
    good when the downstream truly cannot handle ANY burst."
```

## Quick Reference Card

```
ALGORITHM              BURST BEHAVIOR          MEMORY COST      TYPICAL USE
─────────────────────────────────────────────────────────────────────────────
Fixed window            up to 2x at boundary     very low         quick/simple, accept imprecision
Sliding window log      none (exact)             high (per-req)   low-traffic, need exactness
Sliding window counter  small approximation error moderate         production default (most common)
Token bucket            deliberate, tunable burst  low             APIs wanting burst tolerance
Leaky bucket            none (smoothed output)    low              protecting fragile downstreams
```
