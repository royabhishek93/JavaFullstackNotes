# SECTION 0 — NEW LEARNER FOUNDATION

```
IF YOU ARE NEW TO THIS TOPIC — START HERE
==========================================

WHAT IS KUBERNETES (EKS)?
  Kubernetes is a system that runs your Docker containers across many
  servers automatically. EKS = Elastic Kubernetes Service = AWS-managed
  Kubernetes. You describe what you want ("run 3 copies of Order Service")
  and Kubernetes makes it happen and keeps it running.

WHAT IS A POD?
  The smallest runnable unit. One pod = one instance of your app.
  Think: pod = one running container = one copy of Order Service.

WHAT IS A NODE?
  The actual server (EC2 instance on AWS) that runs pods.
  One node can run many pods. You need more nodes when pods run out of room.

WHAT IS HPA?
  Horizontal Pod Autoscaler. Watches CPU/memory usage.
  If CPU goes above 70%: adds more pods. If below 30%: removes pods.
  Like hiring more cashiers when queues get long, sending them home when empty.

WHAT IS KEDA?
  Kubernetes Event-Driven Autoscaler.
  Like HPA but smarter: can watch SQS queue depth, Kafka lag, etc.
  Special feature: can scale to ZERO pods (0 cost when no work to do).
  Example: notification sender has 0 pods at 3am, 20 pods at lunch rush.

WHAT IS CPU REQUEST vs CPU LIMIT?
  Request: "minimum CPU I need" — Kubernetes uses this to schedule the pod
           on a node that has at least this much free CPU.
  Limit:   "maximum CPU I am allowed to use."
           If pod tries to use more: Linux THROTTLES it (slows down).
           TRAP: Setting limit = request throttles pods even when node is idle.

  CPU is measured in millicores: 1000m = 1 full CPU core. 500m = half.

WHAT IS IRSA?
  IAM Roles for Service Accounts.
  Gives each Kubernetes pod its own AWS permissions (S3, DynamoDB, etc.)
  without hardcoded passwords. Each service gets only the permissions it needs.

WHAT IS PDB?
  PodDisruptionBudget. A rule: "always keep at least 2 pods running."
  Without it: Kubernetes might stop ALL pods simultaneously during maintenance.
  With it: Kubernetes must maintain minimum healthy pods at all times.
```

# SECTION 1 — THE STORY: Scaling on EKS

```
THREE LEVELS OF SCALING ON EKS
================================

  Level 1 — HPA (Horizontal Pod Autoscaler)
  "Add more pods when CPU is high"
  CPU-based, memory-based, or custom metrics
  Scale time: 1-2 minutes

  Level 2 — KEDA (Kubernetes Event-Driven Autoscaler)
  "Add more pods when business metric is high"
  SQS queue depth, Kafka consumer lag, Redis list length
  Scale time: 30 seconds; can scale to ZERO (cost saving)

  Level 3 — Cluster Autoscaler
  "Add more EC2 nodes when pods can't be scheduled"
  Triggered when pods are Pending (no room on existing nodes)
  Scale time: 2-5 minutes (must provision new EC2 instance)

  THESE WORK TOGETHER:
  Traffic spike → HPA adds pods → pods can't schedule (nodes full)
              → Cluster Autoscaler adds nodes → pods schedule → HPA satisfied
```

## QUESTION: "When do you use HPA vs KEDA? What's the difference?"

```
WHAT YOU SAY:
─────────────
"HPA is the right choice for CPU-bound services. An API service that
processes HTTP requests — as traffic goes up, CPU goes up, HPA adds pods.
The correlation is direct.

KEDA is for when CPU is the WRONG metric. A Swiggy notification consumer
reads from SQS and sends emails. It's mostly waiting for the email API
to respond — CPU stays at 5% even with 100,000 messages queued.
HPA sees 5% CPU and doesn't scale. Customers wait hours for notifications.

With KEDA watching SQS queue depth: 100,000 messages → 20 pods.
Queue drains in minutes, not hours. And when the queue is empty,
KEDA scales the consumer to ZERO — zero pods, zero cost. Only
API services that need to be always-on run 24/7."
```

```
SIGNAL COMPARISON
==================

  Service Type        Right Signal       Wrong Signal
  ──────────────────────────────────────────────────────
  REST API            CPU utilization    SQS depth (no queue)
  SQS Consumer        SQS queue depth    CPU (always low)
  Kafka Consumer      Consumer lag       CPU (always low)
  ML Inference API    GPU utilization    CPU
  Database proxy      Active connections CPU

  SWIGGY EXAMPLE:
  Notification Consumer: KEDA on SQS "swiggy-notifications"
  - targetMessagesPerPod: 500
  - 0 messages → 0 pods (scale to zero)
  - 5000 messages → 10 pods
  - 50000 messages → 20 pods (maxReplicaCount)
```

## QUESTION: "What is the CPU throttling trap in Kubernetes?"

```
THE PROBLEM (Most Common EKS Performance Bug)
=============================================

  You set: cpu request = 500m, cpu limit = 500m
  Traffic spike: pod wants to use 800m CPU
  Node has 4 free cores (4000m spare capacity)

  What SHOULD happen: pod uses 800m freely — node has room
  What ACTUALLY happens: Kubernetes throttles pod to 500m (the limit)

  RESULT:
  - Response time increases 40%
  - Node is 40% idle
  - You're paying for unused capacity
  - Everything looks "healthy" (CPU shows 100% of limit, not 100% of node)
  - CloudWatch shows no alerts — you waste weeks debugging latency

  WHY THIS HAPPENS:
  CPU limits use Linux CFS bandwidth controller.
  Every 100ms period: if pod has used its "quota" → throttled until next period.
  Even a brief 200ms burst above the limit causes throttling.
```

```
THE FIX — CPU vs Memory Rules
================================

  Memory limit = memory request (ALWAYS equal):
    Memory cannot be "given back" once used (unlike CPU)
    If pod leaks memory → OOM kill → pod restarts → you detect the bug
    If no limit → pod eats all node memory → node fails → ALL pods evicted

  CPU limit = much higher than request (OR no limit):
    CPU is compressible — throttled pods just slow down, they don't crash
    Set request accurately (used by scheduler for placement)
    Set limit to 2x-4x request or remove it entirely
    Pods burst freely on idle node capacity

  WHAT YOU SAY:
  "I changed Swiggy's Order API from cpu request=limit=500m to
  request=500m, limit=2000m. P99 latency dropped from 800ms to 200ms
  with no infrastructure change. The node had spare capacity — the
  pods just weren't allowed to use it."
```

## QUESTION: "What is IRSA and why is it better than node IAM roles?"

```
THE PROBLEM WITH NODE IAM ROLES
================================

  Without IRSA:
  EKS Node has IAM Role: "swiggy-node-role"
  Attached policies: S3, DynamoDB, Secrets Manager, SQS

  Payment Service pod → runs on Node → gets node-role credentials
  Internal Tools pod  → runs on SAME Node → gets SAME node-role credentials
  Attacker compromises Internal Tools pod
  → Has S3, DynamoDB, Secrets Manager, SQS access
  → Can read payment data, secrets, everything

  Blast radius: ALL pods on ALL nodes share the node role

  WITH IRSA (IAM Roles for Service Accounts):
  Payment Service pod → payment-service-sa → payment-service-role
    → Only: S3 GetObject on receipts/*, DynamoDB on payments table

  Internal Tools pod  → internal-tools-sa → internal-tools-role
    → Only: CloudWatch PutMetricData

  Attacker compromises Internal Tools:
  → Only has CloudWatch write access → minimal damage
```

```
HOW IRSA WORKS (Simple Explanation)
=====================================

  EKS has an OIDC identity provider (like Google OAuth for your cluster)

  When pod starts:
  → K8s mounts a JWT token into the pod at a known path
  → JWT says: "I am the payment-service-sa service account in EKS cluster X"

  When pod calls AWS API (S3, DynamoDB, etc.):
  → AWS SDK reads the JWT token
  → Calls STS: "I have this JWT, please give me credentials for payment-role"
  → STS verifies JWT against EKS OIDC provider → validates pod identity
  → Issues temporary credentials (valid 1 hour, auto-renewed)

  RESULT: Pod has scoped AWS credentials. Zero hardcoded keys.
          Credentials rotate automatically every hour.
          If pod is compromised: only its specific permissions are exposed.
```

## QUESTION: "What is a PodDisruptionBudget and when does it save you?"

```
THE PROBLEM WITHOUT PDB
=========================

  You have 3 pods of Order Service.
  Node drain (for maintenance, upgrade, spot interruption):

  T+0s:  Node hosting Pod-A and Pod-B is being drained
  T+1s:  K8s evicts Pod-A → 2 pods left (Pod-B, Pod-C)
  T+2s:  K8s evicts Pod-B → 1 pod left (Pod-C)
  T+2s:  Pod-C handling 100% of traffic
  T+60s: Replacement pods become ready
  RESULT: 58 seconds of single-pod serving → timeouts under load

  WITH PDB (minAvailable: 2):
  T+1s:  K8s evicts Pod-A → 2 pods left
  T+1s:  K8s tries to evict Pod-B → BLOCKED by PDB (would leave 1 pod < min 2)
  T+30s: Replacement for Pod-A becomes Ready → 3 pods available → PDB allows
  T+31s: K8s evicts Pod-B safely (2 remaining still meet PDB)
  RESULT: Always at least 2 pods → no noticeable degradation
```

```
WHEN PDB PROTECTS YOU:
  ✅ Rolling deployment (maxUnavailable=0 in deployment + PDB)
  ✅ Node drain (kubectl drain during maintenance window)
  ✅ Cluster Autoscaler scale-in (removes underutilized nodes)
  ✅ Spot instance interruption (AWS reclaims spot node)
  ✅ kubectl cordon + drain by operator

  PDB does NOT protect against:
  ❌ Node crash / hardware failure (involuntary disruption)
  ❌ Pod crash due to OOMKill or application bug
  ❌ Direct kubectl delete pod (only protects voluntary evictions)

  WHAT YOU SAY:
  "Every stateless service in production should have a PDB with
  minAvailable set to 50-75% of normal replicas. PDB is free — it
  just adds a policy. The only cost is slower node drains, which
  is exactly what you want — safety over speed."
```

## QUESTION: "What is EKS CNI IP exhaustion? How do you prevent it?"

```
THE PROBLEM
============

  AWS VPC CNI: every pod gets a REAL VPC IP address (not overlay)

  /24 subnet = 256 IPs - 5 (AWS reserved) = 251 usable

  BUT: EC2 instances pre-warm IP slots even without pods:
  m5.large: can hold 3 ENIs × 10 IPs = 30 IPs pre-allocated on startup
  6 nodes × 30 IPs = 180 IPs reserved (even if only 30 pods running!)
  + 30 actual pod IPs = 210 IPs used
  → Only 41 IPs left → autoscaler tries to add Node 7 → "no IPs available"

  SYMPTOM: Pods stuck in "Pending" forever
  kubectl describe pod: "failed to allocate for range 0: no IP addresses available"
  Very confusing — pods look healthy, nodes look healthy, nothing obvious

  THIS IS VERY HARD TO FIX AFTER THE FACT — must plan BEFORE cluster creation
```

```
THE FIXES
==========

  Fix 1: Use /22 or larger subnets (plan before cluster creation!)
  /22 = 1024 IPs — handles most workloads
  /21 = 2048 IPs — enterprise production

  Fix 2: Prefix Delegation (no subnet resize needed)
  Instead of each ENI slot holding 1 IP, it holds a /28 (16 IPs)
  m5.large: 3 ENIs × 10 slots × 16 IPs = 480 pod IPs per node
  Run: kubectl set env daemonset aws-node -n kube-system ENABLE_PREFIX_DELEGATION=true

  Fix 3: Custom networking
  Assign pod IPs from a secondary CIDR (100.64.0.0/16 — RFC 6598)
  Primary subnet (node IPs): /24 (254 nodes max)
  Secondary CIDR (pod IPs): 100.64.0.0/16 (65,534 pod IPs)
  → Effectively unlimited pod IPs

  WHAT YOU SAY:
  "I learned this the hard way in production. We used /24 subnets and
  hit IP exhaustion at 60 pods. The fix was enabling prefix delegation
  without subnet changes — but the right answer is to plan /22+ subnets
  before you create the cluster. This is one of those things you
  cannot easily fix post-creation."
```

## TRAP: "Can HPA and KEDA conflict with each other?"

```
WHAT YOU SAY:
─────────────
"Yes — if both HPA and KEDA target the same Deployment, they will fight.
HPA scales down because CPU is low. KEDA scales up because queue is deep.
The deployment oscillates.

The fix: use only KEDA for that deployment. KEDA v2 actually creates an
HPA under the hood and manages it — it IS the HPA. You configure KEDA's
ScaledObject and KEDA handles the HPA creation.

If you want both CPU and queue metrics, configure KEDA with multiple
triggers: both an SQS trigger and a CPU trigger. KEDA will take the
maximum of all trigger outputs — if either metric says scale up, it scales."
```

---

## TRAP: "What happens when Cluster Autoscaler can't add nodes fast enough?"

```
WHAT YOU SAY:
─────────────
"Cluster Autoscaler takes 2-5 minutes to provision a new EC2 node — the
time to launch an instance, join the cluster, and become Ready.

During those 2-5 minutes, pending pods sit unscheduled. HTTP requests may
succeed (existing pods handle them) but at higher latency and risk of
timeout.

Two mitigations:
First: over-provision — run a few extra placeholder pods with low priority.
They take up capacity on existing nodes. When real pods are needed, they
are preempted, but the node is already there — no wait for EC2 launch.

Second: Karpenter (AWS's newer node provisioner) provisions nodes in
under 60 seconds — it launches EC2 instances in parallel and is
significantly faster than Cluster Autoscaler."
```

## TRAP: "A pod is OOMKilled repeatedly. How do you debug it?"

```
WHAT YOU SAY:
─────────────
"OOMKilled means the container used more memory than its limit — Linux
kernel killed the process.

Step 1: kubectl describe pod — look for 'OOMKilled' in the Last State section
        and the exit code 137 (SIGKILL from OOM killer)

Step 2: Check memory usage before the kill:
        kubectl top pod <pod-name> — current usage
        CloudWatch Container Insights — historical memory graph

Step 3: Three causes:
  A. Limit set too low — pod needs more memory than allocated
     Fix: increase memory request and limit

  B. Memory leak in application — usage grows over time
     Fix: heap dump analysis, check for unclosed connections,
     unbounded caches, static collections growing indefinitely

  C. Misconfigured JVM heap — JVM uses off-heap memory too
     -Xmx512m means max heap 512MB, but JVM also uses
     metaspace, thread stacks, direct buffers → total can be 800MB+
     Set memory limit = Xmx × 1.5 minimum

WHAT YOU SAY FOR JVM:
'I always set -Xmx to 70% of the container memory limit.
If limit=1GB, then -Xmx=700m. The remaining 30% covers metaspace,
thread stacks, Netty direct buffers, and JVM overhead.
Forgetting this is the most common OOMKill cause for Spring Boot apps.'"
```

## One-Sentence Summary (Say This to Close the Topic)

> "EKS scaling has three layers: HPA for CPU-bound APIs, KEDA for event-driven
> consumers that scale to zero, and Cluster Autoscaler for node provisioning.
> The two hidden traps: CPU limits throttle pods even when nodes have spare
> capacity (set high limits or none), and /24 subnets cause IP exhaustion
> (use /22+ or enable prefix delegation before cluster creation).
> Every stateless service needs a PodDisruptionBudget to survive node drains
> and rolling deployments without downtime."
