# SECTION 0 — NEW LEARNER FOUNDATION

```
IF YOU ARE NEW TO THIS TOPIC — START HERE
==========================================

WHAT IS A DATABASE CONNECTION?
  When your Spring Boot app wants to talk to PostgreSQL (RDS), it opens
  a "connection" — like a phone call to the database. The call takes
  20-50 milliseconds to set up (TCP handshake + login).

  Problem: If 500 pods each open 10 connections = 5000 "phone calls" open
           simultaneously. The database can only handle ~1000 at a time.
           Beyond that: "too many connections" error. App crashes.

WHAT IS A CONNECTION POOL (HikariCP)?
  Instead of opening/closing a connection per request, HikariCP keeps
  N connections open and REUSES them (like a taxi rank, not Uber surge).

  Pod with pool of 10: handles 100 concurrent requests using 10 connections
  Without pool:        100 concurrent requests → 100 new connections (slow!)

WHAT IS RDS AURORA?
  AWS's own cloud database (MySQL/PostgreSQL compatible, 5× faster).
  Automatically replicates data across 3 AWS data centres (AZs) in 6 copies.
  If one data centre fails → automatically switches to another in ~30 seconds.

WHAT IS RDS PROXY?
  A connection multiplexer that sits between your app and Aurora.
  500 app connections → proxy → 20 real DB connections.
  Like a telephone exchange: 500 callers, only 20 lines needed at once.

WHAT IS A READ REPLICA?
  A live copy of your database that handles only READ queries.
  Multiple services read from replicas → reduces load on the main (primary) DB.
  Trade-off: replica may be 50-200ms behind the primary (replication lag).

WHAT IS MULTI-AZ?
  AZ = Availability Zone = a separate physical data centre.
  Multi-AZ = your database runs in 2+ data centres simultaneously.
  If one catches fire, the other takes over automatically.
```

## QUESTION: "How do you handle database connection management at scale on AWS?"

```
WHAT YOU SAY:
─────────────
"This is one of the most common root causes of production incidents I've
seen. The problem is that each pod or Lambda opens its own DB connections,
and under traffic spikes you can exhaust Aurora's max_connections limit.

For Flipkart's order service on EKS, we solve this at two levels:

Level 1 — HikariCP inside the application.
Each pod gets a small connection pool — 5 to 10 connections. HikariCP
reuses connections instead of opening a new one per request. A pod
handling 100 concurrent requests only needs 10 DB connections.

Level 2 — RDS Proxy in front of Aurora.
Even with HikariCP, 200 pods × 10 connections = 2000 connections. Aurora
can't handle that. RDS Proxy multiplexes: those 2000 application connections
map to only 20-30 actual database connections.

The result: Aurora sees a constant, manageable number of connections
regardless of how much we scale the application."
```

```
HOW RDS PROXY MULTIPLEXES
===========================

  EKS Pod 1: [conn1][conn2]...[conn10]  ─┐
  EKS Pod 2: [conn1][conn2]...[conn10]  ─┤
  EKS Pod 3: [conn1][conn2]...[conn10]  ─┼──► RDS PROXY ──► Aurora (20 connections)
  ...                                   ─┤
  EKS Pod 200: [conn1]...[conn10]       ─┘
  Total: 2000 app connections → only 20 DB connections!

  HOW: When your transaction is idle (waiting between queries), RDS Proxy
  lends that DB connection to another application connection.
  Only during an active transaction is the DB connection "pinned" to you.
```

## QUESTION: "How does Aurora failover work? How does your app handle it?"

```
AURORA vs STANDARD RDS MULTI-AZ
=================================

  Standard RDS Multi-AZ:
    Primary (serving traffic) + Standby (not serving, just waiting)
    Failover: ~60s, DNS switches to standby

  Aurora Multi-AZ (better):
    Primary + Read Replicas (all serving read traffic)
    Storage: 6 copies across 3 AZs — always (not configurable, built-in)
    Failover: ~30s, read replica promoted to primary
    Faster because replica was already running, not cold standby
```

```
AURORA ENDPOINTS — Critical Distinction
=========================================

  Cluster endpoint (writer):    mydb.cluster-xxx.rds.amazonaws.com
    → Always points to CURRENT primary
    → Use for all write operations
    → After failover: DNS updates → still works ✅

  Reader endpoint:               mydb.cluster-ro-xxx.rds.amazonaws.com
    → Load balanced across ALL read replicas
    → Use for: reports, order history, search, analytics

  Instance endpoint:             mydb-instance-1.xxx.rds.amazonaws.com
    → Points to a SPECIFIC instance
    → TRAP: After failover, this instance may become a replica
            Your writes will fail with "read-only transaction" error
    → NEVER use instance endpoint for writes in production
```

```
WHAT YOU SAY ABOUT FAILOVER:
─────────────────────────────
"We always use the cluster endpoint in application.properties, never the
instance endpoint. The cluster endpoint automatically follows the primary
after failover.

HikariCP must be configured with keepalive enabled and a short
connection validation timeout. During failover (30 seconds), some
connections become stale. HikariCP detects stale connections via the
keepalive probe, evicts them, and opens fresh connections to the
new primary.

We also configure connection-timeout: 3 seconds. If HikariCP can't
get a connection in 3 seconds, the request fails fast with a proper
error — rather than queuing and timing out after 30 seconds, hanging
all threads."
```

## QUESTION: "What is the replication lag trap with Aurora read replicas?"

```
THE READ-YOUR-OWN-WRITE BUG
=============================

  User: clicks "Place Order"
  → POST /orders → writes to Aurora PRIMARY ✅
  → Redirect to order confirmation page
  → GET /orders/12345 → reads from READER endpoint
  → Reader replica: replication lag is 50-200ms
  → Order not replicated yet → "Order not found" returned
  → User sees: "Your order doesn't exist" (but it does!)

  REAL INCIDENT: Flipkart flash sale.
  Millions of orders placed simultaneously.
  Replication lag spikes from 50ms to 2000ms under write load.
  Order confirmation pages showing "Order not found" for 2 seconds.
  Customer support flooded with "did my order go through?" calls.
```

```
THE FIX — Read-Your-Writes Routing
====================================

  Write-sensitive reads (immediately after a write):
    → Use cluster endpoint (PRIMARY) for:
      - Order confirmation page
      - Cart after adding item
      - Profile after update
      - Payment status

  Write-insensitive reads (independent of recent writes):
    → Use reader endpoint for:
      - Browse product catalog
      - View order history (not just-placed)
      - Search
      - Reports and analytics

  WHAT YOU SAY:
  "In production, I configure two DataSources: a write DataSource pointing
  to the cluster endpoint, and a read DataSource pointing to the reader
  endpoint. @Transactional(readOnly = true) routes to the reader.
  For consistency-sensitive reads right after a write — like order
  confirmation — I explicitly use the write DataSource."
```

## QUESTION: "What are the HikariCP settings you tune for RDS Proxy?"

```
THE IDLE TIMEOUT TRAP
======================

  RDS Proxy: closes idle connections after 30 minutes by default
  HikariCP maxLifetime default: 30 minutes (1,800,000ms)

  WHAT HAPPENS:
  T+0s:   HikariCP creates DB connection → goes to idle pool
  T+1800s: RDS Proxy: "this connection idle 30 min → closing it"
  T+1830s: Thread requests connection from HikariCP
  T+1830s: HikariCP: "I have a connection! maxLifetime hasn't expired yet"
  T+1830s: Thread gets the dead connection → issues SQL
  T+1830s: "Connection reset by peer" → request fails with 500 error

  FIX: maxLifetime must be LESS than RDS Proxy idle timeout
       RDS Proxy idle timeout = 1800s
       Set maxLifetime = 1740000ms (29 minutes) = 30s buffer

  OTHER KEY SETTINGS:
  connectionTimeout: 3000ms    (fail fast — don't queue for 30 seconds)
  keepaliveTime:     60000ms   (probe idle connections every 60s, evict dead ones)
  idleTimeout:       600000ms  (10 min idle → return to pool / close)
```

## TRAP: "What does 'connection pinning' mean in RDS Proxy?"

```
WHAT YOU SAY:
─────────────
"Connection pinning means RDS Proxy can no longer multiplex a
DB connection — it stays dedicated to one application connection
for the duration of that session.

Pinning triggers include: SET statements, stored procedures,
multi-statement transactions, and some prepared statement operations.

The consequence: if every application transaction pins a connection,
you get no multiplexing benefit. 2000 app connections → 2000 DB
connections — same as without the proxy.

I avoid SET statements in application code when using RDS Proxy.
I also check the CloudWatch metric 'DatabaseConnectionsCurrentlySessionPinned'
to monitor if pinning is unexpectedly high."
```

---

## TRAP: "Why not just increase max_connections on Aurora?"

```
WHAT YOU SAY:
─────────────
"max_connections scales with instance memory — roughly 1000 for r5.large.
You can increase it, but each connection consumes memory and CPU on Aurora.
Maintaining thousands of idle connections wastes Aurora resources.

More importantly, opening a DB connection takes 20-50ms including TCP
handshake and authentication. For Lambda, that's a significant cold start
overhead. RDS Proxy maintains warm connections — Lambda connects to the
proxy and gets a connection in under 1ms.

Increasing max_connections treats the symptom. RDS Proxy treats the cause."
```

## TRAP: "How do you store the DB password for RDS Proxy in EKS?"

```
WHAT YOU SAY:
─────────────
"In EKS, I use IRSA — IAM Roles for Service Accounts. Each service gets
its own IAM role. The role has permission to call secretsmanager:GetSecretValue
for specific secret ARNs only.

At pod startup, the Spring Boot application calls Secrets Manager to fetch
the DB credentials. The credentials are never stored in the container image,
never in environment variables in the pod spec (which show up in 'kubectl
describe pod'), and never in application.properties.

Separately, RDS Proxy supports IAM authentication — the pod generates a
temporary token using its IAM role and uses that as the DB password.
This token expires every 15 minutes. No static password at all."

FLOW:
  Pod (with IRSA role) → Secrets Manager → gets DB password
  OR
  Pod (with IRSA role) → generates RDS IAM auth token (15min TTL)
  → connects to RDS Proxy with token → proxy validates via IAM
  → proxy connects to Aurora with real credentials
```

## One-Sentence Summary (Say This to Close the Topic)

> "RDS Proxy multiplexes hundreds of application connections into a small,
> stable set of DB connections, preventing connection exhaustion during
> traffic spikes — especially critical for Lambda and high-pod-count EKS.
> Always use the cluster endpoint (not instance endpoint), set HikariCP
> maxLifetime below the proxy's idle timeout, and route read-after-write
> operations to the primary to avoid replication lag bugs."
