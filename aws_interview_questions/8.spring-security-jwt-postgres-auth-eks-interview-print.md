## PROBLEM 1 — Never Store Passwords as Plain Text

```
WITHOUT hashing (naive — WRONG):
──────────────────────────────────
Database:
  email              | password
  piyush@gmail.com   | MyPass123   ← DISASTER
  rahul@gmail.com    | Secret456

If attacker gets DB access: every user's password is exposed instantly.
2023: 23 billion stolen credentials in circulation — many from plain text leaks.

WITH BCrypt hashing (correct):
────────────────────────────────
User registers with: MyPass123

BCrypt output: $2a$12$K8Rn7rFxNlv9cVMmHPMRYuHZ3LkNYj...  (60-char hash)

Database stores:
  email              | password_hash
  piyush@gmail.com   | $2a$12$K8Rn7rFxNlv9cVMmHPMRYu...

At login: BCrypt.matches("MyPass123", storedHash) → true or false
The hash cannot be reversed. Attacker gets the DB: passwords still safe.
Even Flipkart engineers cannot read user passwords.
```

---

## PROBLEM 2 — HTTP is Stateless: How Does the Server Know You Are Logged In?

```
WITHOUT JWT (session-based — does not scale in EKS):
──────────────────────────────────────────────────────
User logs in → server creates session in memory → gives user a session ID cookie

Request 1: user sends cookie → hits Pod A → Pod A has session → OK
Request 2: user sends cookie → hits Pod B → Pod B has NO session → 401!

EKS has 10 pods. Load balancer routes randomly.
Session stored in one pod's memory is invisible to the other 9 pods.
Fix: sticky sessions (bad) or shared Redis session store (extra infra).

WITH JWT (stateless — scales perfectly in EKS):
──────────────────────────────────────────────────
User logs in → server issues a JWT token → user stores it

JWT = three Base64 parts joined by dots:  Header.Payload.Signature

Payload contains:
  { "sub": "piyush@gmail.com", "roles": ["USER"], "exp": 1754000000 }

Signature = HMAC-SHA256(header+payload, SECRET_KEY) ← proves token is genuine

Request to ANY pod:
  User sends: Authorization: Bearer eyJhbGci...
  Any pod: verifies signature using same SECRET_KEY → valid → allow

No shared state. No session store. All 10 pods accept the token equally.
```

## PART 1 — "How do you store passwords? Walk me through it."

> **You say:**
>
> "Passwords are hashed with BCrypt before they ever touch the database.
> BCrypt has three properties that make it right for passwords.
>
> First — it is slow by design. Strength 12 takes about 250ms per hash.
> Fine for login — users barely notice 250ms. But for an attacker trying
> billions of passwords: 250ms × 1 billion = 8 years. MD5 and SHA-256 are
> fast — they hash millions per second, making brute force trivial.
>
> Second — BCrypt adds a random salt automatically. Even if two users have
> the same password, their hashes look completely different. Rainbow tables
> — precomputed hash databases — are useless against BCrypt.
>
> Third — the salt is embedded inside the hash string itself. No separate
> salt column needed. When you call matches(), BCrypt extracts the salt from
> the stored hash automatically."

```
BCrypt HASH — WHAT IS INSIDE IT
=================================

  $2a$12$K8Rn7rFxNlv9cVMmHPMRYuHZ3LkNYj...
   |  |  |                |
   |  |  22-char salt      rest = actual hash
   |  work factor (12 rounds of hashing)
   BCrypt version (2a)

  BCrypt.matches("MyPass123", storedHash):
  1. Extracts salt from storedHash (first 22 chars after $2a$12$)
  2. Hashes "MyPass123" with that salt
  3. Compares result to rest of storedHash
  Returns true if match. Original password never reconstructed.

  TWO USERS, SAME PASSWORD — DIFFERENT HASHES:
  ──────────────────────────────────────────────
  User A: "hello123" → $2a$12$ABCsalt...HASHXYZ
  User B: "hello123" → $2a$12$DEFsalt...HASHABC  ← completely different!

  Random salt per hash → rainbow tables useless
```

**How to explain the Spring Boot config:**
> "I configure a BCryptPasswordEncoder bean with strength 12. On registration,
> I call passwordEncoder.encode(rawPassword) — returns the 60-char BCrypt hash.
> I store that in the password_hash column. The raw password never hits the database.
> On login, Spring Security calls passwordEncoder.matches() automatically. I never
> call it myself."

## PART 3 — "How do you generate and validate JWTs?"

> **You say:**
>
> "JWT has three parts: header (algorithm), payload (claims), and signature.
> The signature is HMAC-SHA256 of header+payload using a secret key. If any
> part is tampered with, the signature check fails — token rejected.
> The secret key never leaves the server.
>
> I use the JJWT library. The secret key is fetched from AWS Secrets Manager at
> startup — not from application.properties. Access token: 15-minute expiry.
> Refresh token: 7 days, used to silently get new access tokens.
>
> For validation: JJWT parses the token and throws specific exceptions for expired
> tokens, invalid signatures, and malformed tokens. I catch each one and return
> the right error to the client."

```
JWT ANATOMY — WHAT IS INSIDE THE TOKEN
=========================================

  Token:  eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJwaXl1c2hAZ21haWwuY29tIiwiZXhwIjoxNzU0fQ.XYZ

  Part 1 — Header:   { "alg": "HS256" }
  Part 2 — Payload:
  {
    "sub":   "piyush@gmail.com",   ← user identifier
    "roles": ["ROLE_USER"],
    "iat":   1754000000,           ← issued at
    "exp":   1754000900            ← expires at (15 min later)
  }
  Part 3 — Signature:
  = HMAC-SHA256(Base64(header) + "." + Base64(payload), SECRET_KEY)

  TAMPER ATTEMPT:
  ────────────────
  Attacker changes "ROLE_USER" → "ROLE_ADMIN" in payload
  Re-computing signature requires SECRET_KEY — attacker does not have it
  Server verifies: HMAC(tampered payload, key) ≠ stored signature → REJECTED

  ACCESS vs REFRESH:
  ───────────────────
  Access token:   15 min TTL → used for every API call
  Refresh token:  7 days TTL → used only to get a new access token silently
```

**How to explain the JwtService:**
> "The JwtService has three public methods: generateAccessToken(), generateRefreshToken(),
> and isTokenValid(). The first two use JJWT's builder — set subject to email, add the
> roles claim, set expiry, sign with the key from Secrets Manager. isTokenValid() parses
> the JWT — JJWT verifies signature and expiry automatically. I just check the extracted
> email matches the current user."

## PART 4 — "How does the JWT filter work in Spring Security?"

> **You say:**
>
> "Every HTTP request passes through Spring Security's filter chain. I add a custom
> filter before Spring's built-in authentication filter. For each request it does
> five things: extract the JWT from the Authorization header, extract the email from
> the token, load the user from the database, validate the token, and if valid, set
> the authentication in the SecurityContext.
>
> If valid, Spring Security knows the user is authenticated for this request.
> If missing or invalid, the filter does nothing — Spring returns 401.
>
> The SecurityContext is thread-local and lives only for the duration of one HTTP
> request. No session, no shared state between requests or pods."

```
SPRING SECURITY FILTER CHAIN — REQUEST FLOW
=============================================

  Incoming HTTP request
  |
  ▼ JwtAuthFilter (runs first — your custom filter):
  |   1. Does Authorization: Bearer <token> header exist?
  |      No → pass through (handled as unauthenticated)
  |   2. Extract token (strip "Bearer " prefix)
  |   3. Extract email from JWT payload
  |   4. Load user from DB via UserDetailsService
  |   5. Validate: signature OK + not expired + email matches
  |   6. If valid: SecurityContextHolder.authentication = user
  |   7. Pass to next filter
  |
  ▼ ExceptionTranslationFilter:
  |   No authentication on protected endpoint → 401 Unauthorized
  |
  ▼ FilterSecurityInterceptor:
  |   Wrong role for the endpoint → 403 Forbidden
  |
  ▼ Your Controller executes (only if authenticated + authorized)

  KEY POINTS:
  ─────────────
  ✓ SessionCreationPolicy.STATELESS — no HTTP session ever created
  ✓ SecurityContext is thread-local — dies at end of each request
  ✓ Each request independently validated — no shared state
  ✓ All 10 EKS pods validate tokens identically (same key from Secrets Manager)
```

**How to explain SecurityConfig:**
> "Three settings: CSRF disabled (JWT is stateless, no CSRF risk), session policy
> STATELESS, and URL rules — /auth/** is public, /api/admin/** requires ADMIN role,
> everything else requires authentication. The JwtAuthFilter is registered before
> UsernamePasswordAuthenticationFilter with one line: addFilterBefore()."

## PART 5 — "How does login work end-to-end?"

> **You say:**
>
> "The login endpoint accepts email and password. It calls AuthenticationManager —
> Spring Security's entry point. AuthenticationManager calls UserDetailsService to
> find the user, then calls BCrypt.matches() internally. Wrong password throws
> BadCredentialsException — we return 401. You never write the BCrypt check yourself.
>
> If valid, we generate two tokens. Access token goes in the response body. Refresh
> token goes in an HttpOnly cookie — not in the response body. HttpOnly means
> JavaScript cannot read it at all. Even if the site has XSS, the refresh token
> is safe."

```
LOGIN FLOW — COMPLETE SEQUENCE
================================

  Client: POST /auth/login { email, password }
  |
  AuthenticationManager.authenticate(email, password)
  |
  UserDetailsService → SQL: SELECT * FROM users WHERE email = ?
  → UserDetails: hash=$2a$12$..., role=USER
  |
  BCrypt.matches(password, hash) → true
  (wrong password → BadCredentialsException → 401 returned, nothing issued)
  |
  JwtService.generateAccessToken()
  → { sub: piyush@gmail.com, roles:[USER], exp: now+15min } + HS256 signature
  |
  JwtService.generateRefreshToken()
  → { sub: piyush@gmail.com, exp: now+7days } + HS256 signature
  |
  Response:
  ├── Body:    { "accessToken": "eyJ..." }       ← client stores in JS memory
  └── Cookie:  refresh_token=eyJ...;             ← HttpOnly, Secure, SameSite=Strict
               HttpOnly; Secure; Path=/auth/refresh; Max-Age=604800

  TOKEN REFRESH (after 15 min):
  ──────────────────────────────
  Client → POST /auth/refresh
  → Browser sends HttpOnly cookie automatically
  → Server validates refresh token (still within 7-day window)
  → Issues new access token
  → User never prompted to log in again

  LOGOUT:
  ────────
  Client → POST /auth/logout
  → Server sets cookie Max-Age=0 (clears HttpOnly cookie)
  → Client discards access token from JS memory
  → Done
```

**How to explain token storage to interviewer:**
> "Access token in memory — a JavaScript variable, not localStorage. If the page
> refreshes, the token is gone, but the browser auto-sends the HttpOnly cookie to
> /auth/refresh to silently get a new one. HttpOnly + SameSite=Strict on the
> refresh cookie: XSS cannot read HttpOnly cookies, CSRF cannot forge SameSite=Strict
> requests. Best of both worlds."

### TRAP-1 — "Where should the client store the JWT — localStorage or cookie?"

> **You say:**
>
> "This is a classic XSS vs CSRF tradeoff.
>
> localStorage is accessible to JavaScript — any XSS vulnerability lets an attacker
> steal the token. Since access tokens are session credentials, this is severe.
>
> HttpOnly cookie cannot be read by JavaScript at all. Even XSS cannot touch it.
> But cookies are sent automatically on every request — CSRF risk.
>
> Production answer: access token in memory (JavaScript variable, not localStorage).
> Refresh token in HttpOnly + Secure + SameSite=Strict cookie. Memory is XSS-safe.
> SameSite=Strict neutralizes CSRF."

```
JWT STORAGE — TRADEOFFS
========================

  localStorage:
  + Survives page refresh, easy to access
  - JavaScript-readable → XSS can steal it instantly

  HttpOnly cookie:
  + JavaScript cannot read it → XSS safe
  - Auto-sent on every request → CSRF risk (fix: SameSite=Strict)

  Memory (JS variable):
  + No storage → nothing for XSS to steal from DOM or storage
  - Lost on page refresh → silently refresh via HttpOnly cookie

  FLIPKART PRODUCTION CHOICE:
  ─────────────────────────────
  Access token:   JS memory          — 15 min, XSS-safe
  Refresh token:  HttpOnly + Secure  — 7 days, SameSite=Strict → CSRF-safe
```

### TRAP-2 — "How do you invalidate a JWT before it expires? User changes password."

> **You say:**
>
> "Pure stateless JWTs cannot be invalidated — that is their limitation. With a
> 15-minute TTL, that window is acceptable for most cases.
>
> For immediate invalidation — account compromise — I add a tokenVersion integer
> column to the users table. When issuing a JWT, I embed the current tokenVersion
> as a claim. In the JwtAuthFilter, after signature validation, I load the current
> tokenVersion from the DB and compare it to the token's claim. If they differ,
> I return 401.
>
> User changes password → increment tokenVersion → all existing tokens instantly fail.
> Cost: one extra DB query per request — cached in Redis with 1-minute TTL to avoid
> hammering RDS at scale."

```
JWT INVALIDATION — tokenVersion PATTERN
=========================================

  WITHOUT tokenVersion:
  ──────────────────────
  User changes password at 14:00.
  Attacker has token issued at 13:55 (expires 14:10).
  15 minutes of unauthorized access — acceptable for most cases.

  WITH tokenVersion:
  ───────────────────
  DB column: users.token_version  (INTEGER, DEFAULT 0)

  JWT payload includes: { ..., "tokenVersion": 5 }

  JwtAuthFilter (after signature check):
  ├── Extract tokenVersion from JWT = 5
  ├── Load tokenVersion from Redis/DB = 6  ← user changed password
  └── 5 ≠ 6 → return 401 "Token invalidated"

  User changes password:
  UPDATE users SET token_version = token_version + 1
  → All existing JWTs now have wrong version → instant rejection

  REDIS CACHE for performance:
  Redis key = "tv:{email}"  TTL = 1 minute
  → At most 1 DB hit per user per minute (not per request)
  → Critical at Flipkart scale to avoid RDS overload
```

### TRAP-3 — "IAM Users vs IAM Roles — why use roles for EKS?"

> **You say:**
>
> "IAM Users have long-lived credentials — access key ID and secret that never
> expire unless manually rotated. At Flipkart with hundreds of services,
> managing hundreds of key pairs is operationally painful and error-prone.
>
> IAM Roles issue temporary credentials — expire in one to twelve hours,
> auto-rotated by the SDK. IRSA: the pod gets a service account token, exchanges
> it with STS for temporary credentials. If leaked, they expire within the hour.
>
> Least privilege: each service gets its own role with only the permissions it
> needs. Auth service role can only read auth secrets. Product service role can
> only read product images from S3. Compromise of one service cannot access
> another service's resources."

```
IAM USERS vs IAM ROLES
========================

  IAM User (avoid for services):
  ─────────────────────────────────
  AccessKeyId: AKIAIOSFODNN7EXAMPLE       ← permanent until deleted
  SecretKey:   wJalrXUt...               ← permanent until rotated

  Risk: leaked in Git/logs/env → permanent access until discovered
  Management: rotate manually → operational burden at scale

  IAM Role + IRSA (correct for EKS):
  ────────────────────────────────────
  Pod starts → EKS injects ServiceAccount JWT
  AWS SDK: STS.AssumeRoleWithWebIdentity(SA JWT)
  STS returns:
    AccessKeyId:  ASIAIOSFODNN7EXAMPLE   ← starts with ASIA = temporary
    SecretKey:    temp...
    Expiration:   1 hour from now        ← auto-rotated, zero management

  LEAST PRIVILEGE:
  ─────────────────
  flipkart-auth-role:
  ├── Allow: secretsmanager:GetSecretValue
  └── Resource: flipkart/rds/* and flipkart/jwt/* only
      CANNOT touch S3, SQS, SNS, or any other service

  flipkart-product-role:
  ├── Allow: s3:GetObject, s3:PutObject
  └── Resource: flipkart-products/* only
      CANNOT touch Secrets Manager at all

  Blast radius: auth service compromised → DB creds only, nothing else.
```

## ONE-LINER ANSWERS

**"Why BCrypt and not SHA-256?"**
> "SHA-256 is designed to be fast — millions per second, trivial to brute-force.
> BCrypt is designed to be slow. Strength 12 takes 250ms. Fine for login.
> 8 years for an attacker to try 1 billion passwords."

**"What happens if the JWT secret key is leaked?"**
> "Attacker can forge valid tokens. Fix: rotate key in Secrets Manager, restart pods.
> All existing tokens instantly invalid — signed with old key. With IRSA the key
> is never in any file — reduces the leak surface significantly."

**"Why 15 minutes for access token expiry?"**
> "Short enough that a stolen token expires quickly. Long enough for normal use.
> The refresh token (7 days, HttpOnly cookie) silently renews access tokens.
> Users never notice the 15-minute window."

**"What if the DB is down when a request comes in?"**
> "JwtAuthFilter calls UserDetailsService on every request to load the user.
> If RDS is down: loadUserByUsername() throws DataAccessException.
> JwtAuthFilter catches it, returns 503 Service Unavailable.
> At Flipkart scale, we use RDS Multi-AZ — automatic failover in under 60 seconds."

### TRAP-4 — "HS256 vs RS256 — which do you use and why?"

> **You say:**
>
> "This is the question that separates architect from senior.
>
> HS256 is symmetric — one secret key signs the token AND validates it. Every service
> that needs to validate JWTs must share that secret. In a microservices setup with
> 5-10 services, you're distributing a secret to every pod. If any one service is
> compromised, the attacker can forge tokens for any user in the system.
>
> RS256 is asymmetric — the auth service holds the private key and signs tokens.
> All other services only need the public key to validate. You can publish the public
> key openly — it cannot forge tokens, it can only verify them.
>
> In the Swiggy architecture, only the Auth Service has the private key in Secrets Manager.
> Order Service, Payment Service, Restaurant Service — they fetch the public key from a
> JWKS endpoint at startup and cache it. Even if Order Service is completely compromised,
> the attacker cannot forge tokens. The private key never left the Auth Service."

```
HS256 vs RS256 — THE ARCHITECT ANSWER
=========================================

  HS256 (symmetric):
  ───────────────────
  Auth Service signs:   HMAC(payload, SECRET_KEY)
  Order Service validates: HMAC(payload, SECRET_KEY) ← needs the SAME key

  Problem: distribute SECRET_KEY to every service
  If any service leaks it → attacker forges tokens for ALL users

  RS256 (asymmetric) — what architects use:
  ──────────────────────────────────────────
  Auth Service:
    Private key (in Secrets Manager) → signs tokens
    Public key  (published via JWKS) → validates tokens

  Every other service:
    Fetches public key from JWKS endpoint at startup
    Validates signatures locally — no shared secret

  Flipkart/Swiggy JWKS endpoint:
  https://auth.swiggy.com/.well-known/jwks.json
  → Returns public key JSON
  → Order, Payment, Restaurant services cache this at startup
  → Spring Security: jwk-set-uri: https://auth.swiggy.com/.well-known/jwks.json

  SECURITY BLAST RADIUS:
  ────────────────────────
  HS256: Order Service compromised → attacker has signing key → forges ANY token
  RS256: Order Service compromised → attacker has only public key → can verify but CANNOT forge

  RULE: Internal custom JWT with one service → HS256 is fine.
        Microservices where multiple services validate → RS256.
        Cognito/Keycloak/any identity provider → always RS256.
```

### TRAP-5 — "What is the JWT 'None algorithm' attack? How do you prevent it?"

> **You say:**
>
> "This is a well-known CVE from early JWT libraries. The JWT spec says the 'alg'
> header field tells the server which algorithm was used to sign the token. Some
> early libraries would actually honor whatever algorithm the client sent in the header.
>
> An attacker takes a valid JWT, decodes the header, changes `alg` to `none`, removes
> the signature entirely, and sends it. A vulnerable library says: algorithm is none,
> no signature required — token accepted. Suddenly the attacker can modify any claim —
> roles, email, expiry — and the server trusts it.
>
> Prevention: explicitly whitelist the allowed algorithms in your JWT parser. In JJWT
> you do this by specifying the signing key — the library only accepts tokens signed
> with that key using the expected algorithm. 'None' is never in the allowed set.
> Never use a parser that auto-detects algorithm from the token header."

```
JWT "NONE ALGORITHM" ATTACK
=============================

  VULNERABLE LIBRARY (old behavior):
  ─────────────────────────────────────
  Attacker takes: eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJoYWNrZXIiLCJyb2xlcyI6WyJBRE1JTiJdfQ.SIG
  Decodes header: { "alg": "HS256" }
  Changes to:     { "alg": "none" }
  Removes signature (keeps trailing dot)
  Sends: eyJhbGciOibm9uZSJ9.eyJzdWIiOiJoYWNrZXIiLCJyb2xlcyI6WyJBRE1JTiJdfQ.

  Vulnerable parser: "alg=none, no signature needed" → TOKEN ACCEPTED
  Attacker is now ADMIN.

  MODERN JJWT (safe — what we use):
  ───────────────────────────────────
  Parser is initialized with the signing key:
  Jwts.parser().verifyWith(signingKey).build()

  The parser ONLY accepts tokens signed with that specific key.
  If alg=none or any unexpected algorithm → exception thrown → 401.
  The token header's algorithm claim is IGNORED — server decides what to accept.

  RULE: Never use a JWT parser that reads the algorithm from the token itself.
        Always specify the expected algorithm and key on the server side.
```

### TRAP-6 — "BCrypt has a 72-character limit. What happens with longer passwords?"

> **You say:**
>
> "Most engineers don't know this. BCrypt silently truncates input at 72 bytes.
> A user with password 'abcdefg...73chars' and 'abcdefg...100chars' — if the first
> 72 characters are identical, BCrypt treats them as the same password. Both would
> pass login. This is a real security issue for applications that allow long passwords.
>
> The fix used at production scale: pre-hash the password with SHA-256 before
> passing it to BCrypt. SHA-256 produces a 32-byte fixed-length output regardless
> of input length. BCrypt then operates on that 32-byte value — well within the 72-byte
> limit. You lose nothing from BCrypt's properties; you just normalize the input length first.
>
> Alternatively, Argon2 has no such limit and is the modern recommendation from
> OWASP. Spring Security's Argon2PasswordEncoder is the upgrade path."

```
BCRYPT 72-CHAR TRUNCATION
===========================

  BCrypt internally:
  password → first 72 bytes only → hash
  Characters after position 72: silently dropped

  PROBLEM:
  Password A: "correcthorsebatterystaple...repeated...73chars_DIFFERENT"
  Password B: "correcthorsebatterystaple...repeated...73chars_AAAAAAAAAA"
  → First 72 chars identical → BCrypt generates same hash!
  → Both passwords pass login — security hole

  FIX 1: Pre-hash with SHA-256 before BCrypt:
  ──────────────────────────────────────────────
  rawPassword → SHA-256 → 32-byte hash (fixed length)
  → BCrypt(32-byte hash) → stored in DB

  At login:
  submittedPassword → SHA-256 → 32-byte hash
  → BCrypt.matches(32-byte hash, storedBCryptHash) → true/false

  Result: input to BCrypt is always exactly 32 bytes regardless of password length.
  BCrypt truncation issue completely eliminated.

  FIX 2: Use Argon2 instead (OWASP recommended):
  ─────────────────────────────────────────────────
  ✓ No length limit
  ✓ Memory-hard (GPU attacks much harder than BCrypt)
  ✓ Configurable memory, parallelism, iterations
  ✓ Spring Security: Argon2PasswordEncoder available out of the box

  WHAT TO SAY IN INTERVIEW:
  "We use BCrypt(12) with SHA-256 pre-hashing for the Flipkart production system.
   For new greenfield projects I'd recommend Argon2 — it's OWASP's current top choice
   and Spring Security supports it natively."
```

### TRAP-7 — "How do you rotate the JWT signing key in production with zero downtime?"

> **You say:**
>
> "Naive approach: update the key in Secrets Manager, restart all pods. Problem:
> during the rolling restart, some pods have the old key and some have the new key.
> Tokens issued by old-key pods are rejected by new-key pods. Users get 401 during
> a normal session. That's a production incident.
>
> The architect solution uses key IDs — the `kid` claim in the JWT header. The auth
> service maintains two active keys simultaneously during rotation: old key (kid=v1)
> and new key (kid=v2). New tokens are signed with kid=v2. Old tokens still have kid=v1.
> Every service's validator holds both public keys. It reads kid from the token header
> and picks the correct key to validate. Zero downtime.
>
> After all old tokens have expired — at most 15 minutes for access tokens — you
> remove kid=v1 from the validator. Rotation complete, zero 401s."

```
JWT KEY ROTATION — ZERO DOWNTIME
===================================

  NAIVE (causes 401s during rollout):
  ──────────────────────────────────────
  t=0: All pods using key-v1
  t=1: Rotate key in Secrets Manager to key-v2
  t=2: Rolling restart begins
       Pod A restarted → uses key-v2
       Pod B still running → uses key-v1
       Token signed by Pod B (kid=v1) → validated by Pod A → FAILS → 401
  t=3: User's session broken during a rolling restart

  ARCHITECT SOLUTION — Dual key with kid header:
  ───────────────────────────────────────────────
  JWT Header now includes:  { "alg": "RS256", "kid": "v1" }

  ROTATION STEPS:
  ─────────────────
  t=0:  All services have key-v1 in validator cache

  t=1:  Generate key-v2, add to Secrets Manager
        Auth Service now signs NEW tokens with kid=v2
        Validator cache: { v1: publicKey1, v2: publicKey2 }
        OLD tokens (kid=v1): still valid — validator has v1
        NEW tokens (kid=v2): valid — validator has v2

  t=16: All access tokens with kid=v1 have expired (15 min TTL)
        Remove key-v1 from validator cache
        Rotation complete

  ZERO 401s at any point during rotation.

  JWKS ENDPOINT (if using RS256):
  ─────────────────────────────────
  https://auth.swiggy.com/.well-known/jwks.json
  Returns: { keys: [ {kid:"v1", ...}, {kid:"v2", ...} ] }
  Services auto-fetch and cache — same as Cognito/Keycloak pattern.
```

### TRAP-8 — "How do you protect the /auth/login endpoint from brute force?"

> **You say:**
>
> "The login endpoint is publicly accessible — no JWT needed. Without protection,
> an attacker can try millions of password combinations. BCrypt's 250ms per hash
> helps, but at scale with distributed attackers it's not sufficient alone.
>
> Four layers of protection we use at Flipkart. One: rate limiting per IP using
> Redis — allow 5 login attempts per IP per minute, return 429 Too Many Requests
> after that. Two: rate limiting per email — 10 failed attempts per email in 15 minutes
> triggers a soft lock. Three: progressive delays — after 3 failures, add a 2-second
> delay to the response. After 5 failures, 5-second delay. Attackers slow down
> significantly. Four: CAPTCHA challenge after 3 consecutive failures from the same
> device fingerprint."

```
BRUTE FORCE PROTECTION — /auth/login
=======================================

  ATTACK:
  ────────
  Attacker script: try password list against piyush@gmail.com
  1000 attempts/second × 250ms BCrypt = still 4 attempts/second per thread
  Distributed across 100 IPs = 400 attempts/second

  LAYER 1: Rate limit per IP (Redis sliding window):
  ────────────────────────────────────────────────────
  Redis key: "login:ip:203.0.113.42"  TTL=60s
  Allow: 5 attempts per IP per minute
  On 6th attempt: return 429 Too Many Requests
  Header: Retry-After: 60

  LAYER 2: Rate limit per email (account protection):
  ──────────────────────────────────────────────────────
  Redis key: "login:fail:piyush@gmail.com"  TTL=15min
  On 10th failed attempt: soft lock
  Return: 429 with "Account temporarily locked. Try in 15 minutes."
  Alert sent to user's email (someone is trying to break in)

  LAYER 3: Progressive delay (slow attackers down):
  ───────────────────────────────────────────────────
  1-2 failures: normal response time
  3-4 failures: 2-second artificial delay added
  5+ failures:  5-second delay + CAPTCHA required

  LAYER 4: CloudFront + AWS WAF (infra level):
  ──────────────────────────────────────────────
  AWS WAF rule: block IP if > 100 requests to /auth/login in 5 minutes
  CloudFront: geographic blocking for unexpected regions
  This stops volumetric attacks before they reach Spring Boot

  COMBINATION RESULT:
  ──────────────────
  Legitimate user: 1-2 attempts → no friction
  Attacker with 1 IP: 5 attempts/min → effectively blocked
  Distributed attacker: WAF blocks at CDN level
```

### TRAP-9 — "What happens if three API calls get 401 simultaneously — refresh race condition?"

> **You say:**
>
> "This is a real production bug I've seen teams ship. The React app has the access
> token expire. Three API calls happen at the same time — order fetch, cart fetch,
> user profile fetch. All three get 401. All three trigger a token refresh simultaneously.
> Three refresh calls hit the server at the same time.
>
> The first refresh succeeds and the server marks the refresh token as used.
> The second and third arrive a millisecond later with the same refresh token —
> which is now invalid (or already rotated). They fail. Two of the three API calls
> throw errors. The user sees two broken components on the page.
>
> The fix is a single-flight pattern on the frontend: a global refresh promise.
> When the first 401 triggers a refresh, it stores the pending refresh promise
> globally. The second and third 401s see the promise is already in-flight and
> wait on the same promise. When it resolves, all three retry with the same new
> token. One refresh call, zero race condition."

```
TOKEN REFRESH RACE CONDITION
===============================

  BROKEN (naive — what most teams ship):
  ─────────────────────────────────────────
  t=0: Access token expires

  t=1: 3 API calls fire simultaneously
       All receive 401 Unauthorized

  t=2: All 3 trigger refresh independently
       3 simultaneous POST /auth/refresh with same refresh token

  t=3: Server processes first refresh → returns new access token
       Server marks refresh token as used (rotation)
       Second refresh arrives → refresh token already used → 401 AGAIN
       Third refresh → same → 401 AGAIN

  Result: only 1 of 3 API calls succeeds. User sees broken UI.

  FIXED (single-flight pattern — architect solution):
  ─────────────────────────────────────────────────────
  Global state: let refreshPromise = null

  401 interceptor:
  ├── Is refreshPromise already set? (another call already refreshing)
  │   YES → wait on the existing refreshPromise (don't call refresh again)
  │   NO  → create new refreshPromise = callRefreshEndpoint()
  │          store it globally
  │
  └── When refreshPromise resolves:
      └── All waiting callers get the new token
          All retry their original request with new token
          refreshPromise = null (reset for next expiry cycle)

  RESULT:
  ────────
  1 refresh call fires (not 3)
  All 3 API calls wait on same promise
  All 3 retry successfully with new token
  Zero broken UI components

  SERVER SIDE — refresh token rotation:
  ──────────────────────────────────────
  Each refresh token can only be used ONCE (stored in DB/Redis)
  After use: mark as consumed, issue new refresh token
  If a consumed token is presented: immediate account lock (replay attack detected)
```

## SCENARIO 4 — Aurora PostgreSQL (Read/Write Splitting)

> **You say:**
>
> "Aurora PostgreSQL is RDS-compatible but with two separate endpoints: a writer
> endpoint and a reader endpoint. All INSERT/UPDATE/DELETE go to the writer.
> All SELECT queries — reports, order history, search — go to the reader replica.
>
> In Spring Boot, we configure two DataSources. The key integration point is
> Spring's `@Transactional(readOnly=true)` — when a service method has this
> annotation, the routing DataSource automatically sends the query to the reader.
> No code change in the repository layer. The routing happens in the transaction
> infrastructure."

```
AURORA POSTGRESQL — WRITER + READER ENDPOINTS
================================================

  Aurora Cluster:
  ├── Writer endpoint: flipkart-cluster.cluster-xyz.us-east-1.rds.amazonaws.com
  │   → handles all writes (INSERT, UPDATE, DELETE)
  │   → single node — always consistent
  │
  └── Reader endpoint: flipkart-cluster.cluster-ro-xyz.us-east-1.rds.amazonaws.com
      → load-balanced across 1-15 read replicas
      → replication lag: typically < 100ms

  SPRING BOOT ROUTING:
  ─────────────────────
  Two DataSource beans configured:
  ├── primaryDataSource   → writer endpoint (from Secrets Manager)
  └── replicaDataSource   → reader endpoint (from Secrets Manager)

  AbstractRoutingDataSource checks transaction context:
  @Transactional(readOnly = false) → routes to primaryDataSource (WRITE)
  @Transactional(readOnly = true)  → routes to replicaDataSource  (READ)

  SERVICE LAYER USAGE:
  ─────────────────────
  @Transactional                   → write path → Aurora writer
  public OrderResponse placeOrder() { ... }

  @Transactional(readOnly = true)  → read path → Aurora reader replica
  public List<Order> getOrderHistory() { ... }

  No change in repository code — routing is transparent.

  AURORA ADVANTAGES OVER STANDARD RDS:
  ──────────────────────────────────────
  ✓ Failover: < 30 seconds (vs ~60s for RDS Multi-AZ)
  ✓ Storage: auto-scales up to 128 TB, no pre-provisioning
  ✓ Read replicas: up to 15 (vs 5 for standard RDS)
  ✓ Aurora Serverless v2: auto-scales compute — good for variable workloads
  ✓ Global Database: primary in us-east-1, replica in ap-south-1 (< 1s replication)
```

## SCENARIO 5 — RDS Proxy (Connection Pooling at AWS Layer)

> **You say:**
>
> "This is the scenario that catches engineers off guard at scale. PostgreSQL has a
> hard limit on max_connections — typically 100-200 for a db.t3.medium instance.
> With 20 ECS tasks each running HikariCP with a pool size of 10, that's already
> 200 connections. Add another service, add auto-scaling — you hit max_connections
> and get 'too many clients' errors.
>
> RDS Proxy solves this. It sits between Spring Boot and RDS, maintains a connection
> pool at the AWS layer, and multiplexes thousands of application connections onto
> a small number of actual database connections. The app connects to the proxy
> endpoint. The proxy manages the real connections to RDS.
>
> Spring Boot doesn't know it's talking to a proxy — the JDBC URL just changes.
> HikariCP still runs but its pool size can be set lower since the proxy handles
> the heavy multiplexing."

```
RDS PROXY — CONNECTION MULTIPLEXING
=======================================

  WITHOUT RDS Proxy (problem at scale):
  ───────────────────────────────────────
  20 ECS tasks × HikariCP pool size 10 = 200 connections
  Auto-scale to 40 tasks × 10          = 400 connections
  RDS max_connections (db.t3.medium)    = 170

  Result: "FATAL: remaining connection slots are reserved"
  Orders failing. Incident.

  WITH RDS Proxy:
  ────────────────
  20 ECS tasks × HikariCP pool size 10  = 200 app connections
                                               ↓
                                     RDS Proxy
                                     (connection pool at AWS layer)
                                     Multiplexes into 20 real DB connections
                                               ↓
                                     RDS PostgreSQL (max_connections: 170)
                                     20 connections used — plenty of headroom

  JDBC URL CHANGE (only config change needed):
  ──────────────────────────────────────────────
  Before: jdbc:postgresql://rds-endpoint:5432/flipkart
  After:  jdbc:postgresql://proxy-endpoint.proxy-xyz.us-east-1.rds.amazonaws.com:5432/flipkart

  Spring Boot: zero code change — just URL update in Secrets Manager.

  RDS PROXY ADDITIONAL BENEFITS:
  ─────────────────────────────────
  ✓ Faster failover: proxy maintains warm connections to new primary
    Standard RDS failover: 60s (app must reconnect)
    With RDS Proxy: < 15s (proxy reconnects, app never knows)
  ✓ IAM authentication: app authenticates to proxy via IAM token (no password)
  ✓ Secrets Manager integration: proxy fetches DB password itself
  ✓ Connection pinning awareness: tracks prepared statements per connection

  WHEN TO USE RDS PROXY:
  ──────────────────────
  ✓ Lambda functions hitting RDS (Lambda scales to thousands — classic problem)
  ✓ Microservices with auto-scaling (connection count unpredictable)
  ✗ Single monolith with predictable connection count — overhead not worth it
  ✗ Very low latency requirements — proxy adds ~1ms overhead
```

## SCENARIO 6 — PgBouncer (Connection Pooler for K8s-hosted Postgres)

> **You say:**
>
> "When PostgreSQL runs as a Kubernetes StatefulSet — not on RDS — there's no
> managed connection pooler. We deploy PgBouncer as a sidecar or a separate
> deployment in front of the Postgres pod. Spring Boot connects to PgBouncer,
> PgBouncer pools connections to Postgres.
>
> The critical gotcha: PgBouncer has three pooling modes. Transaction mode is most
> efficient — it multiplexes connections at the transaction boundary. But in
> transaction mode, prepared statements don't work. Spring Data JPA uses prepared
> statements by default. You must either set PgBouncer to session mode or disable
> prepared statements in the JDBC URL."

```
PGBOUNCER — POOLING MODES AND THE PREPARED STATEMENT GOTCHA
==============================================================

  THREE PGBOUNCER MODES:
  ─────────────────────────
  Session mode:
  ├── One real Postgres connection per client session
  ├── Prepared statements: WORK (connection held entire session)
  └── Least efficient — not much benefit over direct connection

  Transaction mode (most common):
  ├── Real connection assigned only during a transaction
  ├── Released back to pool when transaction commits/rolls back
  ├── Prepared statements: FAIL (connection changes between transactions)
  └── Most efficient — 10x connection reduction possible

  Statement mode:
  ├── Connection released after each statement
  ├── Cannot use transactions at all
  └── Use only for simple, stateless queries

  THE GOTCHA — Spring Data JPA + Transaction mode:
  ─────────────────────────────────────────────────
  Spring Data JPA sends: PREPARE stmt1 AS SELECT * FROM orders WHERE id = $1
  PgBouncer (transaction mode): routes EXECUTE stmt1 to a DIFFERENT connection
  Postgres: "prepared statement 'stmt1' does not exist" → ERROR

  FIX OPTION 1: Disable prepared statements in JDBC URL:
  ────────────────────────────────────────────────────────
  jdbc:postgresql://pgbouncer:6432/flipkart?prepareThreshold=0

  prepareThreshold=0 tells the JDBC driver: never use server-side prepared statements.
  Uses simple queries instead. Works with transaction mode.
  Small performance cost: no server-side statement caching.

  FIX OPTION 2: Use PgBouncer session mode:
  ──────────────────────────────────────────
  Switch PgBouncer to session mode.
  Prepared statements work.
  Less connection multiplexing benefit.
  Acceptable for moderate load.

  ARCHITECTURE WITH PGBOUNCER ON K8S:
  ─────────────────────────────────────
  Spring Boot pod
      |
      | jdbc:postgresql://pgbouncer-service:6432/flipkart?prepareThreshold=0
      v
  PgBouncer (K8s Deployment, 2 replicas for HA)
      |
      | maintains 10 real connections
      v
  Postgres StatefulSet pod (max_connections: 100)
  Persistent Volume (PVC) → data survives pod restarts
```

## SCENARIO 7 — Vault Dynamic Credentials (Rotating Without Pod Restart)

> **You say:**
>
> "Dynamic credentials are the next level after Secrets Manager. Instead of storing
> a fixed password, Vault generates a unique username and password for each pod,
> with a TTL of say 1 hour. When the TTL expires, Vault automatically generates
> new credentials. The pod's database access is revoked if it doesn't renew.
>
> The challenge with Spring Boot: HikariCP opens a connection pool at startup with
> the initial credentials. When Vault rotates credentials after 1 hour, those
> connections become invalid. New connection attempts fail.
>
> The fix: Vault agent + Spring Boot's datasource refresh. The Vault agent sidecar
> writes new credentials to a file. Spring Boot monitors that file and refreshes
> the DataSource bean when credentials change — without restart."

```
VAULT DYNAMIC CREDENTIALS — FLOW
===================================

  SETUP:
  ───────
  Vault Database Secrets Engine connected to Postgres:
  ├── Vault can CREATE and DROP users in Postgres
  ├── Each pod gets a unique user: "v-order-svc-AbC1234"
  └── TTL: 1 hour (configurable per role)

  POD STARTUP:
  ─────────────
  Vault Agent sidecar runs alongside Spring Boot container
      |
      | Pod authenticates to Vault (via K8s ServiceAccount JWT)
      v
  Vault generates: username=v-order-svc-AbC1234, password=xyz789, TTL=1hr
      |
      | Writes to: /vault/secrets/db-creds.properties
      | spring.datasource.username=v-order-svc-AbC1234
      | spring.datasource.password=xyz789
      v
  Spring Boot: spring.config.import=file:/vault/secrets/db-creds.properties
  HikariCP opens pool with these credentials

  AT TTL EXPIRY (1 hour later):
  ───────────────────────────────
  Vault Agent: lease approaching expiry
      |
      | Vault renews lease → new username + password written to file
      | /vault/secrets/db-creds.properties updated
      v
  Spring Boot Actuator refresh endpoint triggered (or file watcher)
      |
      | @RefreshScope on DataSource bean
      | HikariCP evicts old connections, reconnects with new credentials
      v
  Old Postgres user "v-order-svc-AbC1234" revoked by Vault
  New user "v-order-svc-Def5678" active

  AUDIT LOG IN VAULT:
  ────────────────────
  Every credential issuance and revocation logged
  "Pod X got credentials at 14:00, revoked at 15:00"
  Zero shared passwords — every pod has unique credentials
  Compliance: PCI-DSS, HIPAA, SOC2 all satisfied

  WHEN TO USE:
  ─────────────
  ✓ Financial services, healthcare, regulated industries
  ✓ Multi-tenant systems where credential isolation is required
  ✗ Standard e-commerce — Secrets Manager is simpler and sufficient
```

## SCENARIO 8 — SSL/TLS Enforcement on JDBC Connection

> **You say:**
>
> "By default, the PostgreSQL JDBC driver attempts SSL but falls back to plain text
> if SSL isn't available. For compliance — PCI-DSS, HIPAA, SOC2 — you must enforce
> SSL. The fix is one parameter in the JDBC URL: `sslmode=require`. No code change.
>
> On RDS, SSL is enabled by default. On self-hosted Postgres or a pod, you need to
> configure the server certificate. On RDS, AWS provides a CA bundle you download
> and add to a trust store."

```
SSL/TLS ON JDBC — COMPLIANCE REQUIREMENT
==========================================

  JDBC URL without SSL (default — data in plain text over network):
  jdbc:postgresql://rds-endpoint:5432/flipkart

  JDBC URL with SSL enforced:
  jdbc:postgresql://rds-endpoint:5432/flipkart?sslmode=require

  SSL MODES (increasing security):
  ──────────────────────────────────
  disable     → no SSL, never (never use in prod)
  allow       → try plain, upgrade if server offers SSL
  prefer      → try SSL, fall back to plain (DEFAULT — not safe for compliance)
  require     → SSL required, but don't verify server certificate
  verify-ca   → SSL + verify cert is signed by trusted CA
  verify-full → SSL + verify cert + hostname matches cert CN (strongest)

  PRODUCTION RECOMMENDATION:
  ──────────────────────────
  sslmode=verify-full
  + download AWS RDS CA bundle (rds-ca-2019-root.pem)
  + add to Java trust store:
    -Djavax.net.ssl.trustStore=/app/rds-truststore.jks

  JDBC URL:
  jdbc:postgresql://rds-endpoint:5432/flipkart
    ?sslmode=verify-full
    &sslrootcert=/app/rds-ca-2019-root.pem

  WHAT THIS PROTECTS AGAINST:
  ─────────────────────────────
  ✓ Man-in-the-middle: attacker on VPC network cannot read DB traffic
  ✓ Certificate spoofing: verify-full ensures you connect to the REAL RDS instance
  ✗ Does NOT protect against: SQL injection, stolen credentials
    (those are application-layer concerns)

  SPRING BOOT CONFIG (in Secrets Manager secret):
  ─────────────────────────────────────────────────
  spring.datasource.url:
    jdbc:postgresql://rds-endpoint:5432/flipkart?sslmode=require
  (verify-full needs the cert file — require is the minimum for compliance)
```

## SCENARIO 9 — Multi-Cloud PostgreSQL (GCP CloudSQL / Azure Database)

> **You say:**
>
> "The JDBC driver doesn't care which cloud the database is on — it only cares about
> a hostname and port. The main difference is how you authenticate and how you get
> the credentials into the application.
>
> On GCP with CloudSQL: you use the CloudSQL Auth Proxy as a sidecar — it handles
> authentication to GCP using Workload Identity (GCP's equivalent of IRSA) and
> presents a local socket on localhost:5432. Spring Boot connects to localhost.
> No credentials in the app at all — IAM handles it.
>
> On Azure Database for PostgreSQL: you connect via a private endpoint within the
> VNet. Credentials come from Azure Key Vault (equivalent of Secrets Manager).
> Azure Managed Identity is the equivalent of IRSA — pod authenticates to Key Vault
> without any hardcoded credentials."

```
MULTI-CLOUD POSTGRES — HOW CREDENTIALS CHANGE
================================================

  AWS EKS + RDS PostgreSQL:
  ──────────────────────────
  Credential source: AWS Secrets Manager
  Auth mechanism:    IRSA (IAM Role for Service Account)
  JDBC URL:          jdbc:postgresql://rds-endpoint:5432/db

  GCP GKE + CloudSQL PostgreSQL:
  ────────────────────────────────
  Credential source: CloudSQL Auth Proxy (sidecar)
  Auth mechanism:    GCP Workload Identity (equivalent of IRSA)
  JDBC URL:          jdbc:postgresql://localhost:5432/db
                     (proxy runs on localhost, handles auth to GCP)

  Proxy sidecar in pod spec:
  containers:
  - name: cloudsql-proxy
    image: gcr.io/cloud-sql-connectors/cloud-sql-proxy
    args: ["--private-ip", "project:region:instance"]
  → Proxy presents local socket, handles IAM auth transparently

  Azure AKS + Azure Database for PostgreSQL:
  ────────────────────────────────────────────
  Credential source: Azure Key Vault
  Auth mechanism:    Azure Managed Identity (equivalent of IRSA)
  JDBC URL:          jdbc:postgresql://server.postgres.database.azure.com:5432/db
                     ?sslmode=require

  Spring Boot:
  Uses Azure Spring Boot Starter for Key Vault integration
  (same concept as Spring Cloud AWS for Secrets Manager)

  COMPARISON TABLE:
  ──────────────────
  Cloud   | Postgres Service        | Credential Store   | Auth Mechanism
  ────────┼─────────────────────────┼────────────────────┼───────────────────
  AWS     | RDS / Aurora            | Secrets Manager    | IRSA
  GCP     | CloudSQL                | CloudSQL Proxy     | Workload Identity
  Azure   | Azure Database          | Azure Key Vault    | Managed Identity
  On-prem | Self-hosted / K8s pod   | HashiCorp Vault    | K8s Auth Method

  SPRING BOOT CODE: IDENTICAL across all 4
  Only the JDBC URL and credential source bootstrap changes.
  The UserDetailsService, JwtFilter, BCrypt: zero change.
```
