Three Main Layers
Frontend/CDN Layer
CloudFront serves React/Angular apps globally from edge locations. Users in Mumbai get content from Mumbai edge, not US servers.
Application Layer
Microservices running on EKS/EC2 behind ALB. Each service handles specific business logic - users, products, orders, payments.

VPC Network Design FOUNDATION
Three-tier subnet architecture for security and isolation
VPC: 10.0.0.0/16 │ ┌─────────────────┼─────────────────┐ │ │ │ ┌────▼────┐ ┌────▼────┐ ┌───▼─────┐ │ AZ-1 │ │ AZ-2 │ │ AZ-3 │ └────┬────┘ └────┬────┘ └────┬────┘ │ │ │ ┌────▼─────────────────┼─────────────────▼────┐ │ PUBLIC SUBNETS (10.0.1.0/24...) │ │ - ALB │ │ - NAT Gateway │ │ - Bastion Hosts │ └────┬─────────────────┼─────────────────┬────┘ │ │ │ ┌────▼─────────────────┼─────────────────▼────┐ │ PRIVATE SUBNETS (10.0.11.0/24...) │ │ - EKS Worker Nodes │ │ - Microservices (Pods) │ │ - No direct internet access │ └────┬─────────────────┼─────────────────┬────┘ │ │ │ ┌────▼─────────────────┼─────────────────▼────┐ │ DATABASE SUBNETS (10.0.21.0/24...) │ │ - RDS Instances │ │ - ElastiCache Clusters │ │ - OpenSearch Domain │ └─────────────────────────────────────────────┘
Why Three Tiers?
Public Subnets
Only load balancers and NAT gateways here. These need internet access. Application servers stay hidden in private subnets.
Private Subnets
Your Spring Boot apps run here. Can't be accessed from internet directly. Only load balancer can reach them. Secure by design.
Database Subnets
Most isolated layer. Only application layer can reach databases. Even if attacker bypasses ALB, they can't reach databases.
Security Benefits
  • Defense in depth - multiple layers of protection
  • Spread across 3 Availability Zones for high availability
  • NAT Gateway for outbound internet from private subnets
  • Security groups control traffic between layers

Database Strategy POLYGLOT PERSISTENCE
Right database for each use case
DATABASE STRATEGY │ ┌───────────────┼───────────────┐ │ │ │ ┌───────▼──────┐ ┌────▼─────┐ ┌─────▼────────┐ │ RDS │ │ DynamoDB │ │ ElastiCache│ │ (PostgreSQL) │ │ │ │ (Redis) │ └──────────────┘ └──────────┘ └──────────────┘ │ │ │ ┌──────┴─────┐ ┌──────┴──────┐ ┌────┴────┐ │Transactional│ │High-Throughput│ │Caching │ │- Orders │ │- Shopping Cart│ │- Sessions│ │- Payments │ │- User Sessions│ │- API │ │- Users │ │- Product Catalog│ │Results │ └────────────┘ └──────────────┘ └─────────┘
Why Multiple Databases?
RDS PostgreSQL
For orders, payments - needs ACID transactions. When money is involved, you need reliability. Strong consistency across complex relationships.
DynamoDB
Shopping cart updates happen constantly. Need single-digit millisecond latency. Simple key-value lookups, massive throughput. Perfect for cart.
ElastiCache Redis
Cache product details, user sessions. Reduces database load by 70-80%. Sub-millisecond latency. Essential for scale.
Performance Impact
  • RDS handles 50-100ms queries for complex transactions
  • DynamoDB delivers <5ms for simple lookups
  • Redis cache hits return in <2ms
  • Combined strategy serves millions of requests/minute

Why Kubernetes?
Auto-Scaling
Horizontal Pod Autoscaler scales based on CPU/memory. During flash sale, goes from 3 pods to 20 automatically. Scales down when traffic drops.
Self-Healing
If a pod crashes, Kubernetes restarts it automatically. If a node fails, pods move to healthy nodes. Zero manual intervention needed.
Zero-Downtime Deployments
Rolling updates deploy new version gradually. Health checks ensure traffic only goes to healthy pods. Rollback in seconds if issues.
Spring Boot Integration
  • Each microservice packaged as Docker image
  • Health checks via /actuator/health endpoint
  • Minimum 3 replicas per service across 3 AZs
  • Config and secrets from Kubernetes ConfigMaps/Secrets

Multi-Layer Caching PERFORMANCE
Three tiers of caching for maximum speed
USER REQUEST │ ┌────▼────┐ │CloudFront│ ─── Cache 1: Edge Cache │ (CDN) │ (Static Assets) └────┬────┘ TTL: 24 hours │ Hit? Yes → Return (10ms) │ No │ ┌────▼────┐ │ Redis │ ─── Cache 2: Application Cache │(ElastiCache)│ (API Responses) └────┬────┘ TTL: 5-10 minutes │ Hit? Yes → Return (2ms) │ No │ ┌────▼────┐ │ RDS │ ─── Cache 3: Database Query Cache │ (Read │ (Query Results) │ Replica)│ └─────────┘ Response: 50-100ms
Three-Tier Caching Strategy
CloudFront (Tier 1)
Images, JavaScript, CSS cached at edge locations globally. 90% cache hit rate. Users get assets in 10-20ms from nearest edge.
Redis (Tier 2)
Product details, user profiles cached. Cache-aside pattern. On miss, query database and cache result. Reduces DB load by 80%.
Read Replicas (Tier 3)
Route SELECT queries to read replicas, writes to primary. Distributes database load. Primary handles 20%, replicas handle 80%.
Cache Invalidation Strategy
  • Product descriptions: 1 hour TTL (rarely change)
  • Product prices: 5 minute TTL (change during sales)
  • Inventory: 30 second TTL (changes frequently)
  • On update: Delete from cache, next read refreshes

Asynchronous Processing SCALABILITY
Decoupling services with message queues
EVENT-DRIVEN ARCHITECTURE │ ┌────▼────┐ │ SNS │ │ Topic │ └────┬────┘ │ ┌───────┬───────┼───────┬───────┐ │ │ │ │ │ ┌────▼──┐ ┌─▼───┐ ┌─▼───┐ ┌─▼───┐ ┌─▼───┐ │SQS Q1│ │SQS Q2│ │SQS Q3│ │SQS Q4│ │SQS Q5│ └───┬──┘ └──┬──┘ └──┬──┘ └──┬──┘ └──┬──┘ │ │ │ │ │ ┌───▼──┐ ┌─▼───┐ ┌─▼───┐ ┌─▼───┐ ┌─▼───┐ │Payment│ │Email│ │Inven-│ │SMS │ │Analy-│ │Service│ │Svc │ │tory │ │Svc │ │tics │ └──────┘ └─────┘ └─────┘ └────┘ └─────┘
Why Asynchronous?
Fast Response to User
Order placed, return success in 300ms. Don't make user wait for payment, email, inventory. Queue those tasks, process in background.
Service Decoupling
If email service is down, order still succeeds. Services consume at their own pace. No cascading failures across services.
Scalability
During flash sale, 10,000 orders/sec. Each service scales independently based on its queue depth. Add more consumers as needed.
Order Processing Flow
  • User clicks "Place Order" → Order Service validates and saves
  • Publishes event to SNS → Fans out to 5 SQS queues
  • Each service processes independently: payment, email, inventory
  • Failed messages go to Dead Letter Queue for manual review

ALB Features
Path-Based Routing
Requests to /api/products/* go to Product Service. /api/orders/* go to Order Service. One load balancer, multiple services.
Health Checks
ALB checks /actuator/health every 30 seconds. If 2 consecutive checks fail, instance marked unhealthy. No traffic sent to unhealthy instances.
SSL Termination
ALB handles HTTPS encryption/decryption. Backend services use HTTP. Certificate from AWS Certificate Manager (free). Reduces load on apps.
High Availability Setup
  • ALB spans all 3 Availability Zones
  • Each service has min 3 instances across 3 AZs
  • If one AZ fails, other two handle 100% traffic
  • Connection draining: 30 sec wait before terminating instance

Three Pillars of Observability
Logs (CloudWatch Logs)
All Spring Boot logs sent to CloudWatch. Structured JSON logging. Query with Logs Insights: "Show all errors for user X in last hour".
Metrics (CloudWatch Metrics)
CPU, memory, request count, error rate, latency. Custom business metrics: orders/min, revenue/hour. Dashboards for real-time visibility.
Tracing (X-Ray)
Follow request across services. See: Order Service 50ms → Payment Service 2000ms (bottleneck!) → Inventory 20ms. Find slow services instantly.
Alerting Strategy
  • Critical alerts (page on-call): Error rate >5%, database CPU >90%
  • Warning alerts (Slack): Error rate >1%, latency >500ms
  • Include runbook link in every alert
  • Monitor alert fatigue - adjust thresholds based on actual incidents

Security - Defense in Depth SECURITY
Multiple layers protecting your application
SECURITY LAYERS (Outside → Inside) │ ┌───────────────▼────────────────┐ │ Layer 1: AWS WAF │ │ - SQL Injection Protection │ │ - XSS Protection │ │ - Rate Limiting │ └───────────────┬────────────────┘ │ ┌───────────────▼────────────────┐ │ Layer 2: AWS Shield │ │ - DDoS Protection │ └───────────────┬────────────────┘ │ ┌───────────────▼────────────────┐ │ Layer 3: Security Groups │ │ - Network Firewall Rules │ └───────────────┬────────────────┘ │ ┌───────────────▼────────────────┐ │ Layer 4: Application Layer │ │ - JWT Authentication │ │ - API Authorization │ └───────────────┬────────────────┘ │ ┌───────────────▼────────────────┐ │ Layer 5: Data Layer │ │ - Encryption at Rest (KMS) │ │ - Encryption in Transit (TLS) │ └────────────────────────────────┘
Defense in Depth Strategy
Perimeter Security
WAF blocks SQL injection, XSS attacks. Shield protects against DDoS. Rate limiting prevents abuse. Attackers stopped at the edge.
Network Security
Security groups are stateful firewalls. ALB allows 443 from anywhere. Apps allow 8080 from ALB only. DB allows 5432 from apps only.
Data Security
All data encrypted: RDS with KMS, S3 with SSE, DynamoDB encryption enabled. TLS 1.2+ for all traffic. Secrets in AWS Secrets Manager.
IAM Best Practices
  • Never hardcode credentials - use IAM roles for EC2/Lambda
  • Principle of least privilege - minimum permissions needed
  • MFA enabled for all human users
  • CloudTrail logging all API calls for audit trail

The Complete Journey
User Experience
Click "Place Order" → Success in 300ms. Behind scenes: validate order, check inventory, save to RDS, publish event. User happy with fast response.
Background Processing
Payment gateway called (2-3 sec), email sent (500ms), inventory updated (100ms), SMS sent (500ms). User doesn't wait for any of this.
Resilience
If payment fails, order still saved. User can retry. If email service down, order succeeds. Message stays in queue until service recovers.
Why This Architecture Works
  • Caching: Product details served from Redis in 2ms
  • Async: User doesn't wait for payment, emails
  • Multi-AZ: If one AZ fails, others handle traffic
  • Auto-scaling: Flash sale? Scale from 3 to 20 pods automatically
  • Monitoring: Know within 1 minute if something breaks
