## THE STORY: Flipkart User Login

> A user opens the Flipkart app and logs in with email and password.
> What must happen, and what can go wrong?

```
WHAT WE NEED TO BUILD
======================

  User: email=piyush@gmail.com  password=MyPass123

  Step 1: Registration
  User registers -> Spring Boot hashes password -> stores in PostgreSQL (RDS)

  Step 2: Login
  User sends credentials -> Spring Boot verifies -> issues JWT token

  Step 3: Protected endpoint
  User sends JWT in header -> Spring Boot validates -> returns data

  THREE PROBLEMS TO SOLVE:
  1. How do you store passwords safely? (never plain text)
  2. How do you prove the user is logged in on subsequent requests?
     (HTTP is stateless — server has no memory)
  3. In production on AWS EKS: where do you store the DB password
     and the JWT secret key? (never in code or application.properties)
```

---

## PROBLEM 1 — Never Store Passwords as Plain Text

### WITHOUT hashing (naive approach — WRONG):

```
Database (PostgreSQL):
| email              | password    |
|--------------------|-------------|
| piyush@gmail.com   | MyPass123   |  <- DISASTER
| rahul@gmail.com    | Secret456   |

If attacker gets DB access: every user's password exposed instantly.
If you use the same password elsewhere (banking, email): all compromised.
2023: 23 billion stolen credentials in circulation — many from plain text leaks.
```

### WITH BCrypt hashing (correct approach):

```
User registers with password: MyPass123

BCrypt hashes it:
$2a$12$K8Rn7rFxNlv9cVMmHPMRYuHZ3LkNYj...  (60 char string, different every time)

Database stores:
| email              | password_hash                                       |
|--------------------|-----------------------------------------------------|
| piyush@gmail.com   | $2a$12$K8Rn7rFxNlv9cVMmHPMRYu...                    |

At login: BCrypt.matches("MyPass123", storedHash) -> true or false
The hash cannot be reversed. Attacker gets the DB: passwords still safe.
Even Flipkart engineers cannot read user passwords.
```

---

## PROBLEM 2 — HTTP is Stateless: How Does the Server Know You Are Logged In?

### WITHOUT JWT (session-based — does not scale in EKS):

```
User logs in -> server creates session in memory -> gives user a session ID cookie

Request 1: user sends cookie -> hits Pod A -> Pod A has session -> OK
Request 2: user sends cookie -> hits Pod B -> Pod B has NO session -> 401!

EKS has 10 pods. Load balancer routes randomly.
Session stored in one pod's memory is invisible to other pods.
You need sticky sessions (bad) or a shared Redis session store (extra infra).
```

### WITH JWT (stateless — scales perfectly in EKS):

```
User logs in -> server issues a JWT token -> user stores it

JWT = three Base64 parts joined by dots:
  Header.Payload.Signature
  eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJwaXl1c2hAZ21haWwuY29tIiwiZXhwIjoxNzU0MDAwMDAwfQ.XYZ

Payload contains: { "sub": "piyush@gmail.com", "roles": ["USER"], "exp": 1754000000 }
Signature: HMAC-SHA256(header+payload, SECRET_KEY)  <- proves token is genuine

Request to any pod:
User sends: Authorization: Bearer eyJhbGci...
Any pod: verifies signature using the same SECRET_KEY -> valid -> allow
No shared state. No session store. All 10 pods accept the token equally.
```

## PROBLEM 3 — Where Do DB Password and JWT Secret Live in Production?

### WRONG (hardcoded or in application.properties):

```yaml
# application.properties — NEVER DO THIS
spring.datasource.password=flipkart-db-prod-p@ss
jwt.secret=mySecretKey123

# These get committed to Git.
# Any developer, contractor, or attacker with Git access reads them.
# Rotating: change code, redeploy. Painful.
```

### CORRECT (AWS Secrets Manager + IRSA):

```
EKS Pod (Spring Boot)
|
| "I need the DB password"
| -> calls AWS Secrets Manager API (via IRSA — no hardcoded credentials)
|
AWS Secrets Manager
| -> returns: { "password": "flipkart-db-prod-p@ss" }

Spring Boot loads it at startup. Never in any file. Never in Git.
Rotate password: update Secrets Manager, restart pods. Zero code change.
```

## PART 1 — "How do you store passwords? Walk me through the Spring Boot code"

> **You say:**
>
> "Passwords are hashed with BCrypt before they ever touch the database.
> BCrypt has three properties that make it right for passwords.
>
> First, it is slow by design — you configure the work factor (strength) which
> controls how many rounds of hashing it does. Strength 12 takes about 250ms per
> hash on modern hardware. This is fine for login — users barely notice 250ms.
> But for an attacker trying billions of passwords: 250ms × 1 billion = 8 years.
> MD5 and SHA256 are fast — they hash millions per second, making brute force trivial.
>
> Second, BCrypt automatically adds a random salt — a random string mixed into
> the password before hashing. Even if two users have the same password, their
> hashes are completely different. So an attacker cannot use rainbow tables —
> precomputed hash databases.
>
> Third, the salt is embedded in the hash output itself. You do not need a
> separate salt column in the DB. BCrypt.matches() extracts the salt from the
> stored hash automatically."

```java
// PasswordConfig.java
@Configuration
public class PasswordConfig {

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder(12);  // strength 12 = ~250ms per hash
        // strength 10 = default (~65ms), strength 12 = production recommended
        // Do NOT use strength < 10 in prod
    }
}


// User.java — JPA entity
@Entity
@Table(name = "users")
public class User {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(unique = true, nullable = false)
    private String email;

    @Column(nullable = false)
    private String passwordHash;   // stored hash, NEVER the raw password

    @Enumerated(EnumType.STRING)
    private Role role;             // USER, SELLER, ADMIN
}


// AuthService.java — registration
@Service
@RequiredArgsConstructor
public class AuthService {

    private final UserRepository userRepository;
    private final PasswordEncoder passwordEncoder;

    public void register(RegisterRequest request) {
        if (userRepository.existsByEmail(request.getEmail())) {
            throw new EmailAlreadyExistsException(request.getEmail());
        }

        User user = User.builder()
            .email(request.getEmail())
            .passwordHash(passwordEncoder.encode(request.getPassword()))
            // BCrypt: "MyPass123" -> "$2a$12$K8Rn7rFxNlv9cVMmHPMRYu..."
            // encode() adds random salt internally, no separate salt column needed
            .role(Role.USER)
            .build();

        userRepository.save(user);
    }
}
```

```
BCrypt HASH — WHAT IS INSIDE IT
=================================

  $2a$12$K8Rn7rFxNlv9cVMmHPMRYuHZ3LkNYj...
   |  |  |                |
   |  |  22-char salt      rest = actual hash
   |  work factor (12 rounds)
   BCrypt version (2a)

  BCrypt.matches("MyPass123", storedHash):
  1. Extracts salt from storedHash (first 22 chars after $2a$12$)
  2. Hashes "MyPass123" with that salt
  3. Compares result to rest of storedHash
  Returns true if match, false if not. Original password never reconstructed.
```

**One-liner:**
> "BCryptPasswordEncoder(12) — slow by design (250ms/hash), auto-salt embedded in
> hash output, no separate salt column needed. MD5/SHA1 are fast — trivially
> brute-forced. BCrypt with strength 12 makes brute force computationally infeasible."

## PART 2 — "How does Spring Security load the user from the database?"

> **You say:**
>
> "Spring Security needs a way to find a user by username — in our case, email.
> We implement UserDetailsService. This is a single-method interface: loadUserByUsername.
> Spring Security calls this automatically during login — you give it the strategy
> for finding the user, and Spring handles the rest.
>
> The returned UserDetails object tells Spring Security the stored password hash,
> the account status, and the authorities. Spring Security compares the submitted
> password against the stored hash using the PasswordEncoder automatically. You
> never call BCrypt.matches() yourself."

```java
// UserDetailsServiceImpl.java
@Service
@RequiredArgsConstructor
public class UserDetailsServiceImpl implements UserDetailsService {

    private final UserRepository userRepository;

    @Override
    public UserDetails loadUserByUsername(String email)
            throws UsernameNotFoundException {

        User user = userRepository.findByEmail(email)
            .orElseThrow(() -> new UsernameNotFoundException(
                "User not found: " + email));

        return org.springframework.security.core.userdetails.User.builder()
            .username(user.getEmail())
            .password(user.getPasswordHash())   // the BCrypt hash from DB
            .roles(user.getRole().name())       // USER, SELLER, ADMIN
            .build();
    }
}


// UserRepository.java
public interface UserRepository extends JpaRepository<User, Long> {
    Optional<User> findByEmail(String email);
    boolean existsByEmail(String email);
}
```

```
HOW SPRING SECURITY USES UserDetailsService
=============================================

  POST /auth/login
  Body: { "email": "piyush@gmail.com", "password": "MyPass123" }
  |
  AuthenticationManager.authenticate(
      new UsernamePasswordAuthenticationToken("piyush@gmail.com", "MyPass123")
  )
  |
  Spring Security calls:
  UserDetailsServiceImpl.loadUserByUsername("piyush@gmail.com")
  -> SQL: SELECT * FROM users WHERE email = 'piyush@gmail.com'
  -> returns UserDetails with passwordHash = "$2a$12$K8Rn..."
  |
  Spring Security internally:
  BCryptPasswordEncoder.matches("MyPass123", "$2a$12$K8Rn...") -> true
  |
  Authentication object returned -> login successful
  |
  AuthService generates JWT and returns it
  (Spring Security does NOT issue JWT automatically — you write that part)
```

**One-liner:**
> "Implement UserDetailsService.loadUserByUsername() to fetch user from PostgreSQL.
> Spring Security calls it during login and handles BCrypt verification automatically.
> You never call matches() yourself."

## PART 3 — "How do you generate and validate JWTs? Show me the code"

> **You say:**
>
> "JWT has three parts: header (algorithm), payload (claims), and signature.
> The signature is HMAC-SHA256 of header+payload using a secret key. If any
> part of the token is tampered with, the signature check fails — the token
> is rejected. The secret key never leaves the server.
>
> I use the JJWT library. For production, the secret key is fetched from
> AWS Secrets Manager at startup — not from application.properties. The
> access token has a short expiry of 15 minutes. The refresh token lives
> for 7 days and is used to get new access tokens without re-login.
>
> For validation: parse the token using the same secret key. JJWT throws
> exceptions for expired tokens, invalid signatures, or malformed tokens.
> I catch each specifically so I can return the right error to the client."

```java
// JwtService.java
@Service
public class JwtService {

    // Loaded from AWS Secrets Manager at startup — NOT application.properties
    private final SecretKey signingKey;

    public JwtService(SecretsManagerService secretsManager) {
        String base64Secret = secretsManager.getSecret("flipkart/jwt/signing-key");
        byte[] keyBytes = Decoders.BASE64.decode(base64Secret);
        this.signingKey = Keys.hmacShaKeyFor(keyBytes);
        // Key must be >= 256 bits (32 bytes) for HS256
    }

    // Generate access token (15 minutes)
    public String generateAccessToken(UserDetails userDetails) {
        return Jwts.builder()
            .subject(userDetails.getUsername())   // email as subject
            .claim("roles", userDetails.getAuthorities()
                .stream().map(GrantedAuthority::getAuthority).toList())
            .issuedAt(new Date())
            .expiration(new Date(System.currentTimeMillis() + 15 * 60 * 1000))
            .signWith(signingKey)
            .compact();
        // Output: "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJwaXl1c2gi...XYZ"
    }

    // Generate refresh token (7 days)
    public String generateRefreshToken(UserDetails userDetails) {
        return Jwts.builder()
            .subject(userDetails.getUsername())
            .issuedAt(new Date())
            .expiration(new Date(System.currentTimeMillis() + 7 * 24 * 60 * 60 * 1000L))
            .signWith(signingKey)
            .compact();
    }

    // Extract email from token
    public String extractEmail(String token) {
        return extractClaims(token).getSubject();
    }

    // Validate token
    public boolean isTokenValid(String token, UserDetails userDetails) {
        try {
            String email = extractEmail(token);
            return email.equals(userDetails.getUsername()) && !isExpired(token);
        } catch (JwtException e) {
            return false;
        }
    }

    private Claims extractClaims(String token) {
        return Jwts.parser()
            .verifyWith(signingKey)
            .build()
            .parseSignedClaims(token)
            .getPayload();
        // Throws: ExpiredJwtException, MalformedJwtException, SignatureException
    }

    private boolean isExpired(String token) {
        return extractClaims(token).getExpiration().before(new Date());
    }
}
```

```
JWT ANATOMY — WHAT IS INSIDE THE TOKEN
=========================================

  Token: eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJwaXl1c2hAZ21haWwuY29tIiwiZXhwIjoxNzU0MDAwMDAwfQ.XYZ

  Part 1 (Header): eyJhbGciOiJIUzI1NiJ9
  Decoded: { "alg": "HS256" }

  Part 2 (Payload): eyJzdWIiOiJwaXl1c2hAZ21haWwuY29tIiwiZXhwIjoxNzU0MDAwMDAwfQ
  Decoded: {
    "sub": "piyush@gmail.com",
    "roles": ["ROLE_USER"],
    "iat": 1754000000,   <- issued at
    "exp": 1754000900    <- expires at (15 min later)
  }

  Part 3 (Signature): XYZ
  = HMAC-SHA256(Base64(header) + "." + Base64(payload), SECRET_KEY)

  Tamper check:
  Attacker changes "roles": ["ROLE_USER"] to "roles": ["ROLE_ADMIN"]
  New signature would need SECRET_KEY to compute — attacker does not have it
  Server verifies: HMAC-SHA256(new payload, SECRET_KEY) != stored signature
  Token REJECTED.
```

**One-liner:**
> "JJWT library — subject=email, roles claim, HS256 signature with key from
> Secrets Manager. Access token: 15 min. Refresh token: 7 days.
> Tampering: signature mismatch → rejected. Expiry: ExpiredJwtException → 401."

## PART 4 — "How does the JWT filter work in Spring Security?"

> **You say:**
>
> "Every incoming HTTP request passes through Spring Security's filter chain.
> I add a custom filter called JwtAuthFilter before the UsernamePasswordAuthenticationFilter.
> For each request, this filter extracts the JWT from the Authorization header,
> validates it, and sets the authentication in the SecurityContext.
>
> If the token is valid, Spring Security knows the user is authenticated for
> this request. If the token is missing or invalid, the filter does nothing —
> Spring Security's default behavior kicks in and returns 401.
>
> The SecurityContext only lives for the duration of one HTTP request — it is
> thread-local. There is no session, no shared state between requests or pods."

```java
// JwtAuthFilter.java
@Component
@RequiredArgsConstructor
public class JwtAuthFilter extends OncePerRequestFilter {

    private final JwtService jwtService;
    private final UserDetailsServiceImpl userDetailsService;

    @Override
    protected void doFilterInternal(
            HttpServletRequest request,
            HttpServletResponse response,
            FilterChain filterChain) throws ServletException, IOException {

        String authHeader = request.getHeader("Authorization");

        // 1. Check if Authorization: Bearer <token> header exists
        if (authHeader == null || !authHeader.startsWith("Bearer ")) {
            filterChain.doFilter(request, response);
            return;   // no JWT — let Spring Security handle as unauthenticated
        }

        // 2. Extract token
        String token = authHeader.substring(7);   // remove "Bearer " prefix

        // 3. Extract email from token (throws if token malformed)
        String email = jwtService.extractEmail(token);

        // 4. Only proceed if email extracted and not already authenticated
        if (email != null && SecurityContextHolder.getContext().getAuthentication() == null) {

            // 5. Load user from DB (needed to get current roles/status)
            UserDetails userDetails = userDetailsService.loadUserByUsername(email);

            // 6. Validate token
            if (jwtService.isTokenValid(token, userDetails)) {

                // 7. Create authentication object and set in SecurityContext
                UsernamePasswordAuthenticationToken authToken =
                    new UsernamePasswordAuthenticationToken(
                        userDetails,
                        null,
                        userDetails.getAuthorities()
                    );
                authToken.setDetails(
                    new WebAuthenticationDetailsSource().buildDetails(request));

                SecurityContextHolder.getContext().setAuthentication(authToken);
                // Request is now authenticated for its lifetime
            }
        }

        filterChain.doFilter(request, response);
    }
}


// SecurityConfig.java
@Configuration
@EnableWebSecurity
@RequiredArgsConstructor
public class SecurityConfig {

    private final JwtAuthFilter jwtAuthFilter;

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
            .csrf(csrf -> csrf.disable())          // JWT = stateless, no CSRF needed
            .sessionManagement(session -> session
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/auth/**").permitAll()      // login, register = public
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())                // everything else needs JWT
            .addFilterBefore(jwtAuthFilter,
                UsernamePasswordAuthenticationFilter.class)   // JWT filter runs first
            .build();
    }

    @Bean
    public AuthenticationManager authenticationManager(
            AuthenticationConfiguration config) throws Exception {
        return config.getAuthenticationManager();
    }
}
```

```
SPRING SECURITY FILTER CHAIN — REQUEST FLOW
=============================================

  Incoming HTTP request
  |
  +-- JwtAuthFilter (runs first):
  |   Extract "Authorization: Bearer eyJ..."
  |   Validate signature + expiry
  |   If valid: set SecurityContextHolder.authentication = user
  |   If invalid/missing: do nothing (pass to next filter)
  |
  +-- UsernamePasswordAuthenticationFilter (for form login — skipped for JWT):
  |   Not used in stateless JWT setup
  |
  +-- ExceptionTranslationFilter:
  |   If request reaches protected endpoint with no authentication:
  |   Returns 401 Unauthorized
  |
  +-- FilterSecurityInterceptor:
      Checks: does authenticated user have required role?
      No ADMIN role on /api/admin/**? Returns 403 Forbidden
      Has role? Request passes to Controller.
```

**One-liner:**
> "JwtAuthFilter extends OncePerRequestFilter — extract token, validate, set
> SecurityContext. STATELESS session policy — no session created. Filter added
> before UsernamePasswordAuthenticationFilter. Each request is independent."

## PART 5 — "How does login work end-to-end? Show the AuthController"

> **You say:**
>
> "The login endpoint accepts email and password. It calls AuthenticationManager
> which internally calls UserDetailsService and BCrypt verification. If credentials
> are valid, we generate both an access token and a refresh token. The access token
> goes in the response body. The refresh token goes in an HttpOnly cookie — more
> on why that is safer in a moment."

```java
// AuthController.java
@RestController
@RequestMapping("/auth")
@RequiredArgsConstructor
public class AuthController {

    private final AuthService authService;

    @PostMapping("/register")
    public ResponseEntity<Void> register(@RequestBody @Valid RegisterRequest req) {
        authService.register(req);
        return ResponseEntity.status(HttpStatus.CREATED).build();
    }

    @PostMapping("/login")
    public ResponseEntity<AuthResponse> login(
            @RequestBody @Valid LoginRequest req,
            HttpServletResponse response) {

        AuthResponse authResponse = authService.login(req, response);
        return ResponseEntity.ok(authResponse);
    }

    @PostMapping("/refresh")
    public ResponseEntity<AuthResponse> refresh(
            @CookieValue(name = "refresh_token") String refreshToken,
            HttpServletResponse response) {

        AuthResponse authResponse = authService.refreshToken(refreshToken, response);
        return ResponseEntity.ok(authResponse);
    }

    @PostMapping("/logout")
    public ResponseEntity<Void> logout(HttpServletResponse response) {
        // Clear the HttpOnly cookie
        Cookie cookie = new Cookie("refresh_token", "");
        cookie.setMaxAge(0);
        cookie.setHttpOnly(true);
        cookie.setPath("/");
        response.addCookie(cookie);
        return ResponseEntity.ok().build();
    }
}


// AuthService.java — login method
@Transactional
public AuthResponse login(LoginRequest request, HttpServletResponse response) {

    // Spring Security verifies credentials (BCrypt check happens here)
    authenticationManager.authenticate(
        new UsernamePasswordAuthenticationToken(
            request.getEmail(),
            request.getPassword()
        )
    );
    // If wrong password: BadCredentialsException -> Spring returns 401

    UserDetails userDetails = userDetailsService.loadUserByUsername(request.getEmail());

    String accessToken = jwtService.generateAccessToken(userDetails);   // 15 min
    String refreshToken = jwtService.generateRefreshToken(userDetails); // 7 days

    // Refresh token in HttpOnly cookie (not accessible to JavaScript)
    Cookie refreshCookie = new Cookie("refresh_token", refreshToken);
    refreshCookie.setHttpOnly(true);   // cannot be read by JS -> XSS safe
    refreshCookie.setSecure(true);     // HTTPS only
    refreshCookie.setPath("/auth/refresh");
    refreshCookie.setMaxAge(7 * 24 * 60 * 60);  // 7 days in seconds
    response.addCookie(refreshCookie);

    return new AuthResponse(accessToken);  // access token in response body
}
```

```
LOGIN FLOW — COMPLETE SEQUENCE
================================

  Client: POST /auth/login { email, password }
  |
  AuthenticationManager.authenticate(email, password)
  |
  UserDetailsServiceImpl.loadUserByUsername(email)
  -> SQL: SELECT * FROM users WHERE email = ?
  -> Returns UserDetails with BCrypt hash
  |
  BCryptPasswordEncoder.matches(submittedPwd, storedHash)
  -> true: continue  |  false: throw BadCredentialsException -> 401
  |
  jwtService.generateAccessToken(userDetails)
  -> { sub: email, roles: [USER], iat: now, exp: now+15min }

  |

  -> { sub: email, iat: now, exp: now+7days }
  -> signed with SECRET_KEY
  |

  |

  Client uses it for 15 min.
  After 15 min: POST /auth/refresh (cookie sent automatically) -> new access token.
```

## PART 6 — "How do you wire this to PostgreSQL on AWS RDS in EKS production?"

> **You say:**
>
> "Three things need to come from AWS instead of application.properties in production:
> the RDS database password, the JDBC URL, and the JWT signing key.
>
> We store all three in AWS Secrets Manager. Two separate secrets: one for the
> database credentials, one for the JWT key. The Spring Boot pod uses IRSA —
> IAM Roles for Service Accounts — to authenticate to Secrets Manager without
> any hardcoded keys. At startup, the app fetches the secrets and wires them
> into the DataSource and JwtService beans.
>
> For RDS, we use Spring Cloud AWS Secrets Manager integration. It can automatically
> bind the secret to the DataSource configuration if the secret has the right keys.
> No custom fetch code needed — just configure the secret name in application.yaml."

```
AWS WIRING — SECRETS MANAGER + IRSA + RDS
==========================================

  STEP 1: Create secrets in AWS Secrets Manager:
  -----------------------------------------------
  Secret: flipkart/rds/postgres
  Value:  {
    "spring.datasource.url":      "jdbc:postgresql://rds-endpoint:5432/flipkart",
    "spring.datasource.username": "flipkart_app",
    "spring.datasource.password": "Str0ngP@ss!"
  }

  Secret: flipkart/jwt/signing-key
  Value:  {
    "jwt.signing-key": "base64-encoded-32-byte-key-here"
  }


  STEP 2: Create IAM role for the pod (IRSA):
  --------------------------------------------
  {
    "Effect": "Allow",
    "Action": [
      "secretsmanager:GetSecretValue"
    ],
    "Resource": [
      "arn:aws:secretsmanager:ap-south-1:123456789:secret:flipkart/rds/*",
      "arn:aws:secretsmanager:ap-south-1:123456789:secret:flipkart/jwt/*"
    ]
  }


  STEP 3: Annotate Kubernetes ServiceAccount:
  ---------------------------------------------
  apiVersion: v1
  kind: ServiceAccount
  metadata:
    name: flipkart-auth-sa
    namespace: flipkart
    annotations:
      eks.amazonaws.com/role-arn: arn:aws:iam::123456789:role/flipkart-auth-role


  STEP 4: Spring Boot application.yaml (no passwords!):
  -------------------------------------------------------
  spring:
    config:
      import: "aws-secretsmanager:flipkart/rds/postgres"
    # Spring Cloud AWS automatically fetches the secret and binds:
    # spring.datasource.url, .username, .password from the secret JSON
    jpa:
      hibernate:
        ddl-auto: validate
      database-platform: org.hibernate.dialect.PostgreSQLDialect

  # JWT key fetched manually in JwtService constructor via SDK
  aws:
    secretsmanager:
      jwt-secret-name: flipkart/jwt/signing-key


  STEP 5: JwtService loads key at startup:
  -----------------------------------------
  @Service
  public class JwtService {

      private final SecretKey signingKey;

      public JwtService(SecretsManagerClient smClient,
                        @Value("${aws.secretsmanager.jwt-secret-name}")
                        String secretName) {
          String secretJson = smClient.getSecretValue(
              GetSecretValueRequest.builder().secretId(secretName).build()
          ).secretString();

          String base64Key = new ObjectMapper()
              .readTree(secretJson).get("jwt.signing-key").asText();

          this.signingKey = Keys.hmacShaKeyFor(Decoders.BASE64.decode(base64Key));
      }
  }


  RUNTIME FLOW (no hardcoded credentials anywhere):
  --------------------------------------------------
  Pod starts
  -> IRSA: pod gets temp AWS credentials from EKS token projection
  -> Spring Cloud AWS: calls Secrets Manager with temp creds
  -> Gets DB URL + username + password
  -> Creates HikariCP connection pool to RDS PostgreSQL
  -> Gets JWT signing key
  -> JwtService ready
  Application healthy. Zero credentials in any file or environment variable.
```

**One-liner:**
> "Spring Cloud AWS with import: aws-secretsmanager:secretName — auto-binds DB
> credentials from Secrets Manager to DataSource. IRSA gives pods temporary AWS
> credentials. JWT key fetched via SDK at startup. Zero credentials in any file."

```
COMPLETE ARCHITECTURE — PROD EKS
==================================

  REGISTRATION:
  Client -> POST /auth/register { email, password }
         -> BCryptPasswordEncoder.encode(password)
         -> INSERT INTO users (email, password_hash, role) VALUES (...)
         -> 201 Created

  LOGIN:
  Client -> POST /auth/login { email, password }
         -> AuthenticationManager.authenticate()
         -> UserDetailsServiceImpl -> SELECT FROM users WHERE email=?
         -> BCrypt.matches(password, hash) -> true
         -> JwtService.generateAccessToken() -> eyJ...  (15 min, signed)
         -> JwtService.generateRefreshToken() -> eyJ... (7 days, signed)
         -> Set-Cookie: refresh_token=...; HttpOnly; Secure
         -> Response: { "accessToken": "eyJ..." }

  PROTECTED REQUEST:
  Client -> GET /api/orders/my-orders
            Authorization: Bearer eyJ...
         -> JwtAuthFilter extracts token
         -> JwtService.extractEmail() -> "piyush@gmail.com"
         -> UserDetailsServiceImpl -> load current user
         -> JwtService.isTokenValid() -> true
         -> SecurityContextHolder.setAuthentication(user)
         -> OrderController.getMyOrders() executes
         -> 200 OK

  TOKEN REFRESH (after 15 min):
  Client -> POST /auth/refresh (cookie sent automatically by browser)
         -> JwtService validates refresh token
         -> Issues new access token
         -> 200 OK { "accessToken": "eyJ..." (new) }

  Client -> POST /auth/logout

  ALB:                HTTPS termination, routes to pods
```

## TRAP QUESTIONS

---

### TRAP-1 — "Where should the client store the JWT — localStorage or cookie?"

> **You say:**
>
> "This is a classic XSS vs CSRF tradeoff.
>
> localStorage is accessible to JavaScript — if the site has any XSS vulnerability,
> an attacker can run script.js and steal the token. Since access tokens are long-lived
> session credentials, this is severe.
>
> HttpOnly cookie cannot be read by JavaScript at all — even if XSS runs, it cannot
> access the cookie. But cookies are automatically sent on every request to the domain,
> including from other sites — making it vulnerable to CSRF.
>
> The production answer: store the access token in memory (a JavaScript variable,
> not localStorage) and the refresh token in an HttpOnly Secure cookie. Memory
> storage means the token disappears on page refresh — the app uses the HttpOnly
> refresh cookie to silently get a new access token. HttpOnly + SameSite=Strict
> on the refresh cookie defends against CSRF."

```
JWT STORAGE — TRADEOFFS
========================

  localStorage:
  + Survives page refresh, easy to access in code
  - Accessible to JavaScript -> XSS steals token
  - Token theft = attacker has full session

  HttpOnly cookie:
  + Cannot be read by JavaScript -> XSS safe
  - Sent automatically on every request -> CSRF risk (mitigate with SameSite=Strict)

  Memory (JS variable):
  + Not accessible to XSS (no DOM/storage access needed)
  + Disappears on tab close / refresh -> short-lived risk
  - Lost on page refresh -> app must silently refresh via HttpOnly cookie

  FLIPKART PRODUCTION CHOICE:
  ---------------------------
  Access token:  memory (JS variable)      — 15 min, XSS-safe
  Refresh token: HttpOnly + Secure cookie  — 7 days, SameSite=Strict -> CSRF-safe
```

### TRAP-2 — "How do you invalidate a JWT before it expires? User changes password."

> **You say:**
>
> "Pure stateless JWTs cannot be invalidated — that is their limitation. If a user
> changes their password, all their existing access tokens remain valid until they
> expire in 15 minutes. For most cases, 15 minutes is acceptable.
>
> For immediate invalidation — say a user reports account compromise — we add a
> token version to the user record in PostgreSQL. We store a tokenVersion integer
> in the users table. When we issue the JWT, we embed the current tokenVersion as
> a claim. On every request, the JwtAuthFilter loads the user from DB and compares
> the token's version claim against the DB version. If they differ, the token is
> rejected.
>
> When a user changes their password or reports compromise, we increment
> tokenVersion in the DB. All existing tokens instantly fail the version check.
>
> The cost: one DB query per request to check tokenVersion. At Flipkart scale,
> we cache the tokenVersion in Redis with a short TTL to avoid hammering RDS."

```
JWT INVALIDATION — tokenVersion PATTERN
=========================================

  WITHOUT tokenVersion (pure stateless):
  ----------------------------------------
  User changes password at 14:00.
  Attacker still has token issued at 13:55 (expires 14:10).
  Attacker makes requests until 14:10. 15 minutes of unauthorized access.
  Acceptable for most cases. Not acceptable for financial operations.


  WITH tokenVersion (semi-stateless):
  -------------------------------------
  ALTER TABLE users ADD COLUMN token_version INTEGER DEFAULT 0;

  JWT payload includes: { ..., "tokenVersion": 5 }

  JwtAuthFilter:
  @Override
  protected void doFilterInternal(...) {
      ...
      if (jwtService.isTokenValid(token, userDetails)) {
          int tokenVersionInJwt = jwtService.extractTokenVersion(token);
          int tokenVersionInDb  = userRepository.getTokenVersion(email);
          // Cache this in Redis: key=email, TTL=1min to avoid DB hit per request

          if (tokenVersionInJwt != tokenVersionInDb) {
              response.sendError(401, "Token invalidated");
              return;
          }
          SecurityContextHolder.getContext().setAuthentication(...);
      }
  }

  User changes password:
  UPDATE users SET token_version = token_version + 1 WHERE email = ?;
  All existing JWTs now have wrong version -> instant rejection.
```

### TRAP-3 — "What is the difference between IAM Users and IAM Roles? Why use roles for EKS?"

> **You say:**
>
> "IAM Users have long-lived credentials — an access key ID and secret access key
> that never expire unless you manually rotate them. If leaked: attacker has
> permanent access until you notice and revoke. At Flipkart with hundreds of
> services, managing and rotating hundreds of IAM user keys is operationally painful
> and error-prone.
>
> IAM Roles have no long-lived credentials. They issue temporary credentials —
> access key, secret key, and session token that expire in 1 to 12 hours. IRSA
> uses IAM Roles: the EKS pod gets a Kubernetes service account token, exchanges
> it with STS for temporary AWS credentials. If those credentials are leaked,
> they expire in under an hour.
>
> Least privilege design: each service gets its own IAM role with only the
> permissions it needs. The auth service role can only access Secrets Manager
> for auth-related secrets. The product service role can only access S3 for
> product images. No service has access to another service's resources."

```
IAM USERS vs IAM ROLES
========================

  IAM User (avoid for services):
  --------------------------------
  access_key_id:     AKIAIOSFODNN7EXAMPLE   <- permanent until deleted
  secret_access_key: wJalrXUt...            <- permanent until rotated

  Risk: leaked in Git, logs, env var -> permanent access
  Management: rotate manually, track expiry -> operational burden at scale

  IAM Role + IRSA (correct for EKS):
  ------------------------------------
  Pod starts -> EKS injects service account token (JWT for AWS STS)
  Spring Boot app -> calls STS.AssumeRoleWithWebIdentity(SA token)
  STS -> returns:
    access_key_id:     ASIAIOSFODNN7EXAMPLE  <- starts with ASIA = temporary
    secret_access_key: temp...
    session_token:     FQoDYXd...
    expiration:        1 hour from now

  Risk: leaked -> expires in 1 hour max. Automatically rotated by SDK.
  Management: zero — AWS handles rotation.

  LEAST PRIVILEGE EXAMPLE AT FLIPKART:
  -------------------------------------
  flipkart-auth-role:
    Allow: secretsmanager:GetSecretValue
    Resource: arn:...:secret:flipkart/rds/*
    Resource: arn:...:secret:flipkart/jwt/*
    (CANNOT access flipkart/s3/* or any other service's secrets)

  flipkart-product-role:
    Allow: s3:GetObject, s3:PutObject
    Resource: arn:...:s3:::flipkart-products/*
    (CANNOT access Secrets Manager at all)

  Blast radius: if auth service is compromised, attacker gets DB creds.
  They CANNOT access S3, SNS, SQS, or any other service.
```
