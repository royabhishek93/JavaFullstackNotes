Request Flow: User → Response
Step 1: Edge Delivery
User in Mumbai requests page → CloudFront Mumbai edge serves static assets (HTML, JS, CSS) in 10-20ms. API requests go through to ALB.
Step 2: Load Balancing
ALB routes based on path: /api/products → Product Service, /api/orders → Order Service. Health checks ensure only healthy pods receive traffic.
Step 3: Microservice Processing
Spring Boot service checks Redis cache first (2ms hit), if miss queries database (50-100ms), caches result, returns response. Total: 50-200ms.

EC2 Instance Details
Each instance shows: Instance ID, type (t3.large = 2 CPU, 8GB RAM), Availability Zone, Private IP, current CPU/Memory usage, Security Groups, and IAM Role.
Kubernetes Pods
kubectl get pods shows: Pod name, Status (Running/Ready), CPU/Memory requests and limits, which node it's running on, and restart count.
Auto Scaling
Auto Scaling Group maintains desired count. If CPU >70%, adds instances. If <40%, removes them. Min 9 for HA, Max 30 for cost control.
Instance Types Explained
  • t3.medium: 2 vCPU, 4GB RAM - For light services (User Service)
  • t3.large: 2 vCPU, 8GB RAM - For standard services (Product, Order)
  • m5.xlarge: 4 vCPU, 16GB RAM - For EKS worker nodes
  • All in private subnets - No direct internet access, secure

Understanding RDS Components
Multi-AZ (High Availability)
Primary in AZ-1a handles all traffic. Standby in AZ-1b receives synchronous copies. If primary fails, automatic failover in 60-120 sec. Zero data loss.
Read Replicas (Performance)
2 read replicas in different AZs. Spring Boot routes SELECT queries to replicas. INSERT/UPDATE/DELETE to primary. Asynchronous replication with 1-2 sec lag.
Connection Pooling
HikariCP maintains 20 connections per app instance. With 9 instances, that's 180 connections. RDS supports 200 max. Always leave 10-20% buffer.
What Gets Stored in RDS?
  • Orders table: order_id, user_id, total_amount, status, created_at
  • Users table: user_id, email, password_hash, name, phone
  • Payments table: payment_id, order_id, amount, status, gateway_response
  • Need ACID transactions - money involved, must be reliable

Why DynamoDB for Cart?
Speed
Single-digit millisecond latency. Users add/remove items constantly. Need <5ms response. DynamoDB's direct key lookup achieves this. RDS would be 10-20x slower.
Scale
On-Demand mode auto-scales from 0 to millions of requests/sec. No capacity planning needed. During flash sale, handles 100,000 cart operations/sec automatically.
TTL Auto-Cleanup
expiresAt attribute set to 30 days from now. DynamoDB automatically deletes expired items. No cron jobs needed. Abandoned carts clean themselves up.
DynamoDB vs RDS - When to Use Each
  • DynamoDB: Simple lookups by key (cart, sessions) - <5ms latency
  • RDS: Complex joins, transactions (orders, payments) - ACID compliance
  • DynamoDB: Unpredictable traffic (auto-scales infinitely)
  • RDS: Structured data with relationships and foreign keys

Redis Impact on Performance
Latency Reduction
Database query: 50-100ms. Redis cache hit: <2ms. That's 25-50x faster. At 87% hit rate, 87 out of 100 requests are blazing fast.
Database Load Reduction
Without cache: 10,000 requests/sec → 10,000 DB queries. With 87% hit rate: Only 1,300 DB queries! Database handles 8x less load.
What Gets Cached?
Product details (change rarely - 10min TTL), User profiles (1hr TTL), Session data (30min TTL), API responses (5min TTL). High hit rate on frequently accessed data.
Cache Strategy
  • Product descriptions: 10 min TTL (rarely change)
  • Product prices: 5 min TTL (change during sales)
  • Inventory counts: 30 sec TTL (change frequently)
  • On update: Delete from cache, next read refreshes with latest data

ALB Features Explained
Path-Based Routing
One ALB, multiple services. /api/products → Product Service, /api/orders → Order Service. No need for separate load balancers. Saves money and simplifies architecture.
SSL Termination
ALB handles HTTPS encryption/decryption. Backend services use plain HTTP. Certificate from AWS Certificate Manager (free). Reduces CPU load on application servers.
Health Checks
Checks /actuator/health every 30 seconds. 2 consecutive failures → marked unhealthy → no traffic. 3 consecutive successes → marked healthy → traffic resumes. Automatic!
High Availability Setup
  • ALB spans 3 Availability Zones - if one AZ fails, others handle traffic
  • Connection draining: 30 sec wait before terminating during deployment
  • Round-robin load balancing across healthy targets
  • Cross-zone load balancing enabled - distributes evenly across all AZs

Why Async Processing?
Fast User Response
User sees "Order Placed" in 300ms. Don't make them wait for payment processing (2-3 sec), email (500ms), inventory update. Queue these tasks, process in background.
Service Decoupling
If Email Service is down, order still succeeds. Message stays in queue until service recovers. No cascading failures. Each service operates independently.
Scalability
During flash sale: 10,000 orders/sec. Each service has its own queue and scales independently. Add more consumers if queue depth grows. Perfect for traffic spikes.
Dead Letter Queue (DLQ) Pattern
  • Message fails 3 times → Moved to DLQ (not deleted)
  • CloudWatch alarm triggers on DLQ message count > 0
  • Ops team manually investigates and fixes issue
  • Can replay messages from DLQ after fix

Key Architectural Decisions
Why Async Processing?
User gets response in 400ms, not 3+ seconds. Payment, email, SMS happen in background. If any fails, order still succeeds. User doesn't wait, doesn't see failures. Better experience, more resilient.
Why Multiple Databases?
RDS for orders (ACID, joins, transactions). DynamoDB for inventory (fast, scales to millions). Redis for cart (in-memory, 2ms). Right tool for right job. Polyglot persistence.
Why Kubernetes?
Auto-scaling: traffic spike → more pods. Self-healing: pod crashes → restart automatically. Rolling updates: deploy without downtime. Better than managing EC2 instances manually.
Production Readiness Checklist
  • ✅ Multi-AZ: RDS, ElastiCache, ALB - survives AZ failure
  • ✅ Auto-scaling: EKS HPA scales pods based on CPU/memory
  • ✅ Monitoring: CloudWatch dashboards + alarms + X-Ray traces
  • ✅ Security: IAM roles, encryption at rest/transit, no hardcoded secrets
  • ✅ Disaster Recovery: RDS automated backups, cross-region S3 replication
  • ✅ Cost Optimization: Reserved instances, spot instances, S3 tiering

Network Security Layers
Public vs Private Subnets
Public subnet has route to Internet Gateway (0.0.0.0/0 → IGW). Private subnet routes through NAT Gateway for outbound only. Database subnet has NO internet route at all. Defense in depth.
NAT Gateway Pattern
Private instances need to call external APIs (payment gateway, email service). NAT Gateway allows outbound internet but blocks inbound. One NAT per AZ for HA. Costs $45/month per NAT.
Bastion Host Security
Never SSH directly to private instances. Bastion is hardened jump box in public subnet. Allow SSH only from company VPN IPs. All sessions logged to CloudWatch. Rotate bastion key monthly. Consider AWS Systems Manager Session Manager as keyless alternative.
Interview Must-Knows
  • Security Groups = Stateful (allow only), NACLs = Stateless (allow + deny)
  • 3-tier architecture: Public (ALB) → Private App → Private DB
  • NAT Gateway for private subnet outbound (NOT Internet Gateway)
  • Bastion host restricted to specific IPs, all SSH sessions audited

Security Best Practices
WAF Rule Priorities
AWS Managed Rules catch OWASP Top 10. Rate limiting prevents abuse (scraping, brute force). Geo-blocking stops traffic from high-risk regions. Custom rules for business logic (block specific patterns). Evaluate in order.
Secrets Rotation
Never hardcode passwords. Secrets Manager stores encrypted credentials. Lambda auto-rotates RDS password every 30 days. Application retrieves at runtime using IAM role. Zero-downtime rotation: creates new password, updates app, deletes old.
Least Privilege IAM
Each service gets only permissions it needs. Order Service can publish to SNS but not read from it. No wildcard Resource: "*". Specific ARNs only. Regular audit with IAM Access Analyzer to find unused permissions.

  • S3 Block Public Access enabled, databases in private subnets only

Deployment Best Practices
Blue/Green Strategy
Deploy new version (GREEN) alongside old (BLUE). Test GREEN with health checks for 2 min. Switch 100% traffic instantly via ALB target group. If issues: instant rollback to BLUE. Keep BLUE running for 1 hour as safety net.
Automated Testing
450 unit tests run in build (3 min). Integration tests in staging catch API contract breaks. Security scan blocks deploys with HIGH/CRITICAL vulns. Manual approval after staging = final human check before production.
Rollback Triggers
CloudWatch alarm on error rate >2% for 2 min triggers alert. On-call engineer can rollback in 30 sec by switching ALB back to BLUE. Automated rollback possible with Lambda + CloudWatch (advanced). Always test rollback procedure monthly.

DR Strategy Decisions
RTO vs Cost Tradeoff
Faster RTO = higher cost. Hot standby (instant failover) = 2x cost. Warm standby (our choice) = 20% extra cost, 15-min RTO. Cold standby = minimal cost, 4-hour RTO. Critical services get warm standby.
Why us-west-2 for DR?
Geographic separation from us-east-1 (3,000 miles). Unlikely both regions fail simultaneously. Similar pricing to us-east-1. All AWS services available. Low latency to users if primary fails.
Testing is Critical
Untested DR plan = no DR plan. Quarterly drills find issues (hardcoded endpoints, missing IAM permissions). Last drill: found RDS endpoint hardcoded, fixed before real failure. Document timings, improve runbook.
DR Interview Answers
  • RTO: 1 hour, RPO: 5 minutes for critical services (Order, Payment)
  • Multi-AZ handles single AZ failure (30-60 sec), Multi-region for region failure (15 min)
  • Automated backups every 5 min, cross-region replication to us-west-2
  • Quarterly DR drills test failover procedure, last drill: 18 min (target: 60 min)

Troubleshooting Methodology
Layered Approach
Always work top-down: User → CloudFront → ALB → App → Database. Check each layer's metrics before diving deeper. Eliminate layers systematically. Don't assume - verify each hypothesis with data.
Metrics Are Key
Can't debug without observability. CloudWatch showed Redis memory 98%. Logs showed 8M session keys. Cost Explorer showed DynamoDB spike. Always have dashboards ready for common scenarios.
Document Incidents
Write post-mortem after every incident. What happened, root cause, fix, prevention. Add monitoring/alerts to catch it earlier next time. Share with team - everyone learns. Build runbooks for common issues.
Interview Pro Tips
  • Always mention specific tools (CloudWatch Logs Insights, kubectl top, redis-cli)
  • Give timelines (Detected at T+2min, Fixed at T+25min)
  • Explain WHY you chose each debugging step (eliminate layers systematically)
  • End with prevention: "Added alarm to catch this earlier next time"

Scaling Strategy Explained
Why 70% CPU Target?
Too low (30%) = wasted money, too many idle pods. Too high (95%) = pods crash before scaling happens. 70% leaves 30% headroom for sudden spikes. Gives HPA 2-3 minutes to react before saturation.
Scale-Up Fast, Scale-Down Slow
Scale-up: 50% increase every minute (aggressive). Users need capacity NOW. Scale-down: 10% every 5 minutes (conservative). Prevents flapping. Traffic might spike again. Cost of extra pod < cost of slow app.
Custom Metrics > CPU
CPU/Memory are proxies. Real metric: business impact. Queue depth >1000? Scale up processing workers. P95 latency >400ms? Add more pods. Request rate >200/pod? Scale. More accurate than CPU guessing.

N+1 Queries Are Silent Killers
One query per item in loop = 100 queries for 100 items. Looks fine in dev (small dataset). Production (millions of records) grinds to halt. Solution: Join fetch or batch with IN clause. Reduces 101 queries to 1-2.
Connection Pool Math
Formula: (DB max connections × 0.8) ÷ number of pods. RDS: 3,600 max. 9 pods. Result: 320 per pod max. Use 200 (conservative). Monitor usage. If >90%, increase pool OR scale pods OR optimize queries.

Migration Best Practices
Why DMS Over Manual?
Manual: pg_dump takes 12+ hours, blocks writes, requires downtime. DMS: Full load + CDC means zero downtime. Source DB keeps running. Continuous replication keeps target in sync. Cutover in 25 minutes, not 12 hours.
Monitoring Replication Lag
CDC lag <5 sec = good, can cutover anytime. Lag >5 min = investigate (network issue? Target too slow? Transaction volume spike?). Always wait until lag = 0 before final cutover. Don't rush.
Keep Source DB as Backup
Don't decomission on-prem DB immediately. Keep running read-only for 7 days. If RDS has issues, can fail back quickly. After 7 days confidence, decomission. Safety first, optimize cost second.
